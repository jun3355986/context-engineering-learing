## 1. 源码调用链

一次请求从组装到发出，按下面的顺序走。每一步先说做什么，再给关键代码。

### 1.1 请求体长什么样：没有 `instructions` 字段

`codex-api/src/common.rs:279-304`，`ResponsesApiRequest` 的字段是：`model`、`stream`、`service_tier`、`input`、`tools`、`tool_choice`、`parallel_tool_calls`、`reasoning`、`store`、`stream_options`、`include`、`prompt_cache_key`、`text`、`client_metadata`、`access_programs`。

没有 `instructions`。所以「系统提示词」只能放在 `input` 里或别处。

### 1.2 `Prompt`：一次请求的原料

`core/src/client_common.rs:23-42`。对本单元有用的三个字段：

```rust
pub struct Prompt {
    pub input: Vec<ResponseItem>,                // 对话上下文条目
    pub(crate) tools: Arc<[ToolSpec]>,           // 注释：empty when supplied by history
    pub base_instructions: BaseInstructions,
    ...
}
```

### 1.3 `build_prompt`：工具和系统提示词可以被置空

`core/src/session/turn.rs:1666-1695`：

```rust
pub(crate) fn build_prompt(
    input: Vec<ResponseItem>,
    step_context: &StepContext,
    base_instructions: BaseInstructions,
    incremental_tools: bool,
) -> Prompt {
    let turn_context = &step_context.turn;
    Prompt {
        input,
        tools: if incremental_tools {
            Arc::default()                                   // 空
        } else {
            step_context.tool_router.model_visible_specs()
        },
        parallel_tool_calls: true,
        base_instructions: if incremental_tools {
            BaseInstructions { text: String::new(), provenance: None }   // 空
        } else {
            base_instructions
        },
        ...
    }
}
```

`incremental_tools` 为真时，`tools` 和 `base_instructions` 都发空，它们改由 `input`（历史）携带。

### 1.4 `incremental_tools` 什么时候为真

- `core/src/session/step_context.rs:55-62`：`model_info.use_responses_lite` **并且** 特性 `IncrementalTools` 开启。
- `core/src/session/world_state.rs:44-56`：Lite 模型下，历史为空时看特性开关；历史非空时看历史里有没有工具声明条目（`has_tool_declarations()`）。
- `use_responses_lite` 是模型表里的字段（`models-manager/models.json`）。在 `76ed3b4` 的表里，除 `gpt-5.5` 外其余模型都是 `true`。

### 1.5 发请求前的最后一步：前置工具和系统提示词

`core/src/client.rs:965-1006`（节选，注释为原文）：

```rust

```

`BaseInstructionsFragment` 的角色是 `developer`（`core/src/context/base_instructions.rs:45-47`）。最终请求体在 `client.rs:1078-1094` 构造，里面没有 `instructions`。

### 1.6 `input` 里其余的条目：初始上下文怎么拼

`core/src/session/mod.rs:4469-4741`，`build_initial_context_with_world_state`。思路：各个片段按角色分到两个桶里，每个桶合并成**一条**消息。

```rust

let mut contextual_user_sections = Vec::<RenderedFragment>::with_capacity(2);
...
// L4665-4666  （按片段的 role 分桶）
"developer" => developer_sections.push(fragment.render_fragment()),
"user" => contextual_user_sections.push(fragment.render_fragment()),
...
// L4679-4683  developer 桶合成一条 developer 消息
if let Some(developer_message) = crate::context_manager::updates::build_rendered_message(
    std::mem::take(&mut developer_sections),

    items.push(developer_message);
}
// L4693-4699  user 桶合成一条 user 消息
```

另有几种片段不进合并桶，单独成一条 developer 消息（`separate_developer_messages`，如 multi-agent 角色说明），代码在 L4645-4664。这个函数在 0.163.0 里有改动。

### 1.7 AGENTS.md：按字节算预算，尾部截断

- `core/src/config/mod.rs:254`：`pub(crate) const AGENTS_MD_MAX_BYTES: usize = DEFAULT_PROJECT_DOC_MAX_BYTES; // 32 KiB`；L4483 用 `cfg.project_doc_max_bytes.unwrap_or(AGENTS_MD_MAX_BYTES)` 取值。
- `core/src/agents_md.rs:68`：`let mut remaining = config.project_doc_max_bytes;`，预算在**所有**被发现的文件之间共用。
- `core/src/agents_md.rs:155-158`：

```rust
let size = data.len() as u64;
if size > remaining {
    data.truncate(remaining as usize);      // 按字节切，可能切在一个多字节字符中间
}
```

- `core/src/agents_md.rs:168`：`let text = String::from_utf8_lossy(&data).to_string();`，被切坏的字节会变成替换字符 U+FFFD。
- 多个文件之间的分隔符：`"\n\n--- project-doc ---\n\n"`（L49）。
- 发现范围：从项目根到当前目录逐级（`agents_md.rs` 的 `agents_md_paths`）。

### 1.8 技能目录：预算是窗口的 2%

`ext/skills/src/render.rs:126-153`（`skill_metadata_budget`），常量在 L19-25：

```rust
const DEFAULT_SKILL_METADATA_CHAR_BUDGET: usize = 8_000;
const MAX_CONFIGURED_SKILL_METADATA_TOKEN_BUDGET: usize = 10_000;
const SKILL_METADATA_CONTEXT_WINDOW_PERCENT: usize = 2;
const APPROX_BYTES_PER_TOKEN: usize = 4;
```

逻辑：用户配置了上限就取 `min(配置, 10_000)` 个 token；否则取 `窗口 × 2%` 个 token；拿不到窗口大小才退回 8,000 字符。

### 1.9 工具输出：进历史之前先截断

`core/src/context_manager/history.rs:568-577`：

```rust
if let ResponseItem::FunctionCallOutput { output, .. }
| ResponseItem::CustomToolCallOutput { output, .. } = &mut processed.item
{
    // The override already includes the tool's serialization allowance.
    let policy = metadata
        .and_then(|metadata| metadata.history_truncation_token_limit)
        .map(TruncationPolicy::Tokens)
        .unwrap_or_else(|| with_serialization_allowance(policy));
    truncate_function_output_payload(output, policy, estimate_audio_token_count);
}
```

- `with_serialization_allowance`（`utils/output-truncation/src/lib.rs:19-21`）：`policy * 1.2`。
- 模型表里的默认策略（`models-manager/models.json` 的 `gpt-6.1-sol` 条目，L177 起）：`truncation_policy = {mode: tokens, limit: 10000}`。
- `truncate_text`（`lib.rs:36`）对 `Tokens` 策略调用 `truncate_middle_with_token_budget`。从函数名看是保留两头、去掉中间，**本单元没读实现**，U02 再确认。

### 1.10 压缩线和压缩后保留的用户消息

- `protocol/src/openai_models.rs:529-540`，`auto_compact_token_limit()`：取 `窗口 × 9 / 10`，如果配置里有更小的值则取更小的。`usable_context_window()`（L523-527）是 `窗口 × effective_context_window_percent / 100`，默认百分比是 95（`models-manager/src/model_info.rs:132`）。
- `core/src/compact.rs:64`：`const COMPACT_USER_MESSAGE_MAX_TOKENS: usize = 20_000;`
- `core/src/compact.rs:702-731` 的 `build_compacted_history`：L724 `for message in user_messages.iter().rev()`，从最新的用户消息往前取，累计到 20,000 token（用 `approx_token_count` 估算）为止，装不下的消息只保留能放进去的文本部分。
- 这一块是 U03 的内容，这里只给入口。`compact.rs` 在 0.163.0 里改了约 135 行，没有核对过改动是否影响这个行为。

### 1.11 官方的调试入口

`core/src/prompt_debug.rs:26-120`，`build_prompt_input`。它搭一个会话、记录初始上下文和你的输入，最后 L119 `Ok(prompt.input)`。**只返回 `input`**，不含 `tools` 字段，也不含 `base_instructions`。CLI 入口是 `codex debug prompt-input [PROMPT]`。

### 1.12 Codex 怎么估 token

`ext/skills/src/render.rs:25` 和 `core/src/realtime_context.rs:45,577-578`：`字节数 / 4`，向上取整。这是估算，不是真实的 tokenizer。

## 2. 实验

脚本：`自学单元/U01-实验/u01_capture.py`（我写的，约 200 行，只用标准库）。每次运行建一个新的临时 `CODEX_HOME`，不碰 `~/.codex`。输出在 `自学单元/U01-实验/out/<名字>/`，每个请求存成 `req-N.json`。

通用说明：

- 表里的「字节」是该块文本的 UTF-8 字节数，「≈token」是字节除以 4 向上取整，和 Codex 自己的估算同一算法。中文每字 3 字节，这个估算对中文偏低。
- **下面的数字是我 2026-10-31 在 0.165.0 上预跑的结果，供你对照；你自己跑，数字可能略有出入**（路径长度、版本不同都会有几十字节的差别）。
- 脚本在 `codex exec` 里用 `stdin=DEVNULL`。`codex exec` 遇到不会关闭的管道 stdin 会一直等，我踩过这个坑（后台任务里卡了 2 分钟，假服务器一个请求也没收到）。

### 推测（没有直接证据）

- 推测：`incremental_tools` 的动机是少发重复的工具定义、让会话变成有状态。依据只是特性注释 `Track top-level tool definitions in world state and emit incremental context updates.` 和第三版 `src-codex-02` 的说法，本单元没有验证。
- 推测：各层按「稳定 → 易变」排序是为了让缓存前缀不变。这是第三版 `intro-02` 的说法，E5 显示了前缀不变，但「为什么这么排」要等 U04 实验缓存命中才能说。

## 6. 没做的和已知局限

- 实验在 0.165.0 上做，源码是 `76ed3b4`，不是同一版本（第 0 节）。
- 假服务器是非 OpenAI 的 provider，源码对它会清掉每条 `input` 里的 `internal_chat_message_metadata_passthrough` 等字段（`client.rs:1013-1032`）。我核对了：E1 的输出里这个字段出现 6 次，而假服务器抓到的请求里一次也没有。所以**真实 OpenAI 请求比我抓到的略大**，大多少没有量化。上面的「字节」和「≈token」统计只算文本内容，不受这个字段影响。
- E1~E5 都没有发过真实请求。E6 给了命令，没有运行。
- 没有在有 MCP 服务、插件、自定义技能的环境里测，所以「工具说明」只覆盖了内置工具。MCP 和技能怎么影响 `input[0]` 和 `skills_instructions`，是 U05 的内容。
- 第三版的 `research/codex.md`、`research/source-map/codex.md` 我没有读。
- 一次错误：我曾在 `git fetch` 里手写了一个编出来的 40 位哈希，被远端拒绝，没有造成影响。文中所有哈希都是从 GitHub API 或 `git rev-parse` 取到的。
