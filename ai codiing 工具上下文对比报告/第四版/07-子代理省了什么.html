子代理读完 12 万字节的日志，父会话只多了 932 字节；整个过程发出的输入却多了 33%

2026-11-02 · Codex 源码 76ed3b4 / CLI 0.165.0 · 模型 gpt-6.1-sol、gpt-5.5，思考级别都是 low（注明的除外）· 对照 Claude Code 官方文档（2026-11-02 查阅）

实验里让 gpt-6.1-sol 派一个子代理读 4 份各约 3 万字节的日志：子代理自己的请求从 59,292 涨到 178,940 字节，父会话的请求只从 54,878 涨到 55,810 字节。但整个过程发出去的输入合计 761,485 字节，比父会话自己读（573,510 字节）多 33%。子代理省的是父会话的窗口，不是总量。

子代理：父会话（你正在对话的那个会话）派出去干活的另一个会话，有自己的历史和窗口，干完把结果交回来。本章实验在 自学单元/U06-实验/：本机假 Responses 服务器同时扮演父会话和子代理（按请求里的 client_metadata.thread_id 分线程），日志来自假 MCP 服务器 u06_fake_mcp.py 的 dump_log（一次返回 400 行、29,769 字节）。模型的回答是剧本写死的，所以本章回答「请求里装了什么、发了多少字节」，不回答「真实模型会不会在该派的时候派」。请求大小的口径同第 2 章：每条 input 条目 json.dumps 字节数相加，再加顶层 tools 字段；token 按「字节 ÷ 4」估算。

一、没人要求派子代理，请求里也先放了 8,514 字节

最朴素的做法是：用户没要求，就什么都不放。Codex 的 gpt-6.1-sol 不是这样。第 2 章的请求里有两条「子代理说明」，加上工具定义里的一组协作工具，一共三块：1

块在请求哪里字节内容
协作工具input[0] 工具定义里的 collaboration 命名空间5,5296 个工具：spawn_agent（派）2,728、followup_task（给已有的子代理布置新任务）667、wait_agent（等）662、send_message（发消息）523、interrupt_agent（打断）437、list_agents（列出）381
角色说明一条 developer 消息，以 <multi_agent_role> 开头2,575你是 /root，团队里的主代理；怎么用上面的工具；收到的消息长什么样；共享同一个目录；4 个并发名额；用 fork_turns 决定带多少上下文
开关说明一条 developer 消息，以 <multi_agent_mode> 开头410「除非用户或 AGENTS.md、技能明确要求派子代理、委派或并行，否则不要派」

三块合计 8,514 字节 ≈ 2,129 token，占一次请求（实验里 54,878 字节）的 15.5%。第 2 章表里这两条说明写的是正文长度（2,400 和 271 字节）；本章按整条 json.dumps 计，带上外层标签和 JSON 外壳，是 2,575 和 410，所以数字不同。缺省的开关说明是「不要主动派」，所以多数对话里这 8.5 KB 是躺在请求里不用的。思考级别设成 ultra 时，开关说明换成另一条（661 字节）：「只要能并行，就应该派」。4

gpt-5.5 没有这三块

gpt-5.5 不改配置时的请求（思考级别 low，37,032 字节）里没有协作工具，也没有两条说明。它的子代理工具属于第 6 章讲过的「延后工具」，模型要先调 tool_search 才拿得到：实验里搜 spawn a sub-agent，返回 10,424 字节（5 个工具，其中 spawn_agent 一个就 6,711 字节），追加进历史。请求里平时只多一个 tool_search，829 字节。3

谁决定走哪一套

两个模型的差别来自模型表（models-manager/models.json）里每个模型的 multi_agent_version：gpt-6.1-sol 是 v2，gpt-5.5 是空。V2 的协作工具直接放进请求，两条说明只在 V2 里出现；没写的话按配置里的 features.multi_agent（缺省开）走 V1，V1 的工具延后。角色说明的文字也在模型表里，只有 4 个 gpt-6 开头的模型写了（gpt-6.1-sol、gpt-6-astra、gpt-6-sol、gpt-6-luna）。实验里给 gpt-5.5 开 V2（features.multi_agent_v2 = true）：6 个协作工具直接进了顶层 tools，不再需要 tool_search，净增 4,702 字节（9,414 → 14,116）；开关说明（410 字节）出现了，角色说明没有。2

看源码：V2、V1 还是关掉，按什么顺序决定

core/src/config/mod.rs 第 1637–1664 行，注释是我加的。2

pub(crate) fn multi_agent_version_override(&self) -> Option<MultiAgentVersion> {
    if self.features.enabled(Feature::MultiAgentV2) {
        Some(MultiAgentVersion::V2)        // ① features.multi_agent_v2 = true：强制 V2
    } else if !self.agents_enabled {
        Some(MultiAgentVersion::Disabled)  // ② [agents] enabled = false：整个关掉
    } else {
        None                               // ③ 都没写：交给下面
    }
}

pub(crate) fn multi_agent_version_from_features(&self) -> MultiAgentVersion {
    self.multi_agent_version_override().unwrap_or_else(|| {
        if self.features.enabled(Feature::Collab) {   // features.multi_agent，缺省开
            MultiAgentVersion::V1
        } else {
            MultiAgentVersion::Disabled
        }
    })
}

pub(crate) fn multi_agent_version_for_model(
    &self,
    model_multi_agent_version: Option<MultiAgentVersion>,
) -> MultiAgentVersion {
    self.multi_agent_version_override()
        .or(model_multi_agent_version)             // ④ 模型表的 multi_agent_version
        .unwrap_or_else(|| self.multi_agent_version_from_features())  // ⑤ 最后看 features
}

回答问题 1

一次都没让它派子代理，请求里有没有跟子代理有关的内容？多大？gpt-5.5 一样吗？

有。gpt-6.1-sol（思考级别 low）的请求里固定有三块：6 个协作工具 5,529 字节、角色说明 2,575 字节、开关说明 410 字节，合计 8,514 字节，占请求的 15.5%。gpt-5.5 不改配置时没有，它的子代理工具延后，要搜了才进历史（一次搜索 10,424 字节），平时只多一个 829 字节的 tool_search。差别来自模型表的 multi_agent_version。

二、同样读 4 份日志，父会话少了 11.9 万字节，总量多了 18.8 万字节

最朴素的做法是父会话自己读。读 4 份各 29,769 字节的日志，每次工具调用和输出都进父会话的历史，之后每一次请求都要带着。实验里父会话的请求从 54,878 字节涨到 174,526 字节，5 次请求发出的输入合计 573,510 字节。5

派子代理后，这些调用和输出留在子代理自己的历史里。同一个剧本，父会话派一个子代理（用缺省的 fork_turns，第三节讲），自己调 wait_agent 等它，子代理读 4 份日志后回一句结论：5

做法父会话最后一次请求父会话共几次请求子代理共几次请求整个过程输入合计
父会话自己读174,5265—573,510
派子代理，fork_turns 缺省（all）55,81035761,485（+32.8%）
派子代理，fork_turns = "none"55,83635732,677（+27.8%）

父会话少了 118,716 字节 ≈ 29,679 token，它从第一次请求到最后一次只多了 932 字节：spawn_agent 的调用和结果、wait_agent 的调用和结果、子代理的一句结论。总量反而多，是因为子代理的每一次请求都要把固定的开头（工具定义、系统提示词等，实验里 5 万多字节）再发一遍，子代理自己的历史也在涨。

滑块的初始值就是上面的实验（读 4 次、每次输出 29,769 字节、结论 24 字节、之后父会话不再请求）。请求大小按实验的增量算：每次工具调用多 143 字节加输出；spawn_agent 加 wait_agent 加结论让父会话多 908 字节加结论本身。「折价」按第 5 章的规则（gpt-6.1-sol：缓存读 0.05 倍、新写入 1.25 倍，每次接上上一次的缓存）推算，假服务器没有真实缓存，未实验。16

回答问题 2

子代理替父会话「省」了什么？自己读和派子代理，父会话的窗口、整个过程发出的输入各是多少？

省的是父会话的窗口：4 份 3 万字节的日志，自己读时父会话涨到 174,526 字节，派子代理只到 55,810 字节，少 118,716 字节 ≈ 29,679 token，之后每一次请求都少带这些，压缩也不用处理它们。不省总量：子代理的每次请求都重发固定开头，整个过程的输入合计 761,485 字节（fork_turns 缺省）或 732,677 字节（none），比自己读多 33% 或 28%。

三、子代理开头带了什么：gpt-6.1-sol 缺省带走父会话的全部历史

最朴素的做法是让子代理从空白开始，只给任务。这样子代理的请求最小，但它不知道父会话里说过什么。gpt-5.5 是这样做的；gpt-6.1-sol 相反，缺省把父会话的历史整份给它。

gpt-6.1-sol：spawn_agent 的参数 fork_turns 缺省是 all。工具说明写的是「Defaults to all」，源码里也是：没传或传空，就当作 all；传 none 才不带；传数字（如 "3"）也不会只带最近几轮，而是当作 all；传别的会报错。实验里传 "3" 的子代理第一次请求和不传一样（14 条，只有调用参数多了 23 字节）。7

gpt-5.5：spawn_agent 的参数 fork_context 缺省是 false。子代理的第一次请求只有 4 条：系统提示词、技能目录、AGENTS.md、一条任务消息，没有父会话的历史。8

动手看：子代理的第一次请求

三组都是实验里的第一次请求，每段宽度按字节数；鼠标放在段上看名字。「接得上父会话的缓存」是按第 5 章的规则推（请求开头逐字相同、且父会话发过这个开头），未实验。

和父会话的请求开头逐字相同新增，或和父会话不同内容和父会话相同，但前面已经不同

fork 之后，子代理的历史里有几处改动，都能在实验的请求里看到：6

  • 父会话的那次 spawn_agent 调用留着，结果被换成 aborted。子代理看到的是自己「被派出」的那次调用，没有真正的返回。
  • 追加 5 条：一条「你是新派出的子代理，前面的对话是继承来的父会话上下文，前面的身份和任务属于祖先」（504 字节）；子代理自己的角色说明（2,628 字节）；一条「这些工具不可用」（239 字节，实验里是 request_user_input_async）；再一条开关说明（410 字节）；任务消息（317 字节）。所以子代理的请求里同时有父的 /root 角色说明和自己的角色说明，两条开关说明。
  • none 时子代理的工具集也不同：工具定义 23,801 字节，比父会话少 1,546 字节（少了 request_user_input_async）。第一条就不同，后面内容再一样也接不上缓存。all 时保留父会话的工具定义，用追加说明表示不可用，开头因此不变。

缓存上，这个差别很大。按第 5 章的规则，all 的第一次请求里 54,878 字节可以读缓存（父会话的第一次请求已经写过，两边的 prompt_cache_key 也相同，都是整个会话的 id），折合约 2,066 token 的全价；none 要整份写入，折合约 16,725 token。9省窗口的是 none，省钱的反而是缺省的 all。这是按规则推的，真实服务的命中情况没测【待核实】。

fork 之后换模型

角色说明里写着「全量 fork 不接受模型覆盖」，但这只是给模型看的话，代码没有拦。实验里 fork_turns 缺省、同时传 model = "gpt-6-luna"：子代理用 gpt-6-luna 发请求，请求里保留父会话的整个开头，再追加一条 18,535 字节的 <model_instructions>（换成 gpt-6-luna 的指令），整份请求 78,777 字节，比同模型 fork 的 59,292 字节多 19,485 字节。13

对照：Claude Code 的子代理缺省从空白开始

官方文档（2026-11-02 查阅）：子代理缺省拿到「全新的、隔离的上下文窗口」，看不到你的对话历史，只有父会话写的那条委派消息；系统提示词用子代理自己的，加上工作目录等环境信息。CLAUDE.md 和 git 状态缺省会带，内置的 Explore、Plan 两种子代理不带。要继承对话得显式用 fork（文档里「fork the current conversation」一节）。Codex gpt-6.1-sol 的缺省正好相反。15

回答问题 3

子代理开始干活时带着父会话的哪些内容？gpt-6.1-sol 和 gpt-5.5 一样吗？对窗口和缓存各有什么影响？

不一样。gpt-6.1-sol 的 fork_turns 缺省 all：子代理带着父会话的全部历史（实验里第一次请求 59,292 字节，前 55,070 字节和父会话逐字相同），传 "none" 才从空白开始（53,520 字节）；传数字也当 all。gpt-5.5 的 fork_context 缺省 false，从空白开始（36,188 字节）。窗口上 none 小 5,772 字节（53,520 对 59,292）；缓存上 all 能接上父会话已写的开头，none 要整份重写。

四、回到父会话的是子代理的最终回答，整份进来，没有上限

子代理干完活，它的最终回答变成父会话历史里的一条消息。gpt-6.1-sol 里这是一条 agent_message，作者 /root/scan、收件人 /root，正文以 Message Type: FINAL_ANSWER 开头，后面是子代理的原话。wait_agent 本身不带内容，只回 {"message":"Wait completed.","timed_out":false}（170 字节）：工具说明里写着「Does not return the content」。10

最终回答没有长度上限。实验里让子代理最后回一段 3,000 行的文字（231,068 字节），父会话的请求从 55,226 字节一下涨到 289,787 字节，整段原样进了历史。我没在源码里找到截断这条消息的代码【待核实，搜索不穷尽】。所以前一节算的「父会话多 932 字节」，只在子代理的回答很短时成立；第二节的交互里把「子代理的结论」拉到 100 KB，父会话的优势就没了。

gpt-5.5 里同一段回答会进历史两次。实验里父会话调 wait_agent 等子代理，结果里是 {"status":{"…":{"completed":"结论：日志无异常"}}}，紧接着又追加一条 user 消息 <subagent_notification>…</subagent_notification>，里面是同一句结论。结论只有一句话时无所谓，几万字节时就是两份。10

子代理读了什么、试过什么，父会话看不到：它们只在子代理自己的历史里。要追问「你为什么排除了方案 B」，父会话得用 followup_task 或 send_message 再问一次。

回答问题 4

子代理干完活，父会话收到什么？收到的内容有长度上限吗？

收到子代理的最终回答原文，gpt-6.1-sol 里是一条 FINAL_ANSWER 的 agent_message，没有长度上限：实验里 231,068 字节整份进了父会话的历史。中间的工具调用和输出不进来。gpt-5.5 里 wait_agent 的结果和一条 <subagent_notification> 各带一份回答。

五、能开几个、套几层、怎么关

gpt-6.1-sol（V2）下，同时活着的代理总数缺省 4 个，包括父会话自己，所以最多 3 个子代理；层数没有限制。数字写在两个地方：配置缺省常量，和角色说明里那句「There are 4 available concurrency slots」。实验里父会话连派 4 个，第 4 个得到 collab spawn failed: agent thread limit reached。让每个子代理再派一个，一层一层往下，直到名额用完才停（/root/a/g/g 那一层成功，再下一层报同样的错）。[agents] 下的 max_threads = 1 把名额改成 2（父会话加 1 个子代理），角色说明里的数字同步变成 2。11

gpt-5.5（V1）下，缺省只能有一层。[agents] max_depth 缺省 1，V2 忽略它。实验里 gpt-5.5 的子代理请求顶层工具里没有 tool_search，也就找不到 spawn_agent；我没让它真的去派孙代理，只能说「没有入口」【中】。11

怎么关

下面每一项都是改完配置后抓一次 gpt-6.1-sol 的第一次请求（思考级别 low，不接 MCP，缺省 54,878 字节）。实验里用的是命令行 -c 键=值，同样的键可以写进 ~/.codex/config.toml。12

协作工具角色说明开关说明

三个容易踩的地方：

  • features.multi_agent = false 和 features.multi_agent_v2 = false 对 gpt-6.1-sol 都没有效果。前一个只在模型表没写版本时才生效，后一个只有设成 true 才算数（上面的源码）。要整个关，写 [agents] 下的 enabled = false，这时三块都消失，请求少 8,516 字节。
  • 只关两条说明：在 [features.multi_agent_v2] 下把 root_agent_usage_hint_text（角色说明）和 multi_agent_mode_hint_text（开关说明）设成空字符串。工具还在，模型还能派，只是不再有说明；缺省的开关说明本来是在拦它。
  • disable_native_tools = true 去掉了工具，两条说明却还在。请求里仍然告诉模型「用 spawn_agent 派子代理」，而这个工具不存在。这个开关的注释写的是给「宿主提供工具」的场景用的，日常用法里不要开。

对照：Claude Code 的上限和开关

官方文档（2026-11-02 查阅）：子代理缺省可以再派子代理，最多在主会话之下 3 层，环境变量 CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1 关掉嵌套；同时运行的子代理缺省上限 20 个（CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS 可改，需 v2.1.217 起），超了报 Concurrent subagent limit reached；一个会话里累计派多少次没有上限。关闭：在 permissions.deny 里写 Agent(Explore) 这样的规则关某一种，写 Agent 关全部委派。内置的 Explore、Plan 是只读的（禁用 Write 和 Edit）。Codex 的内置角色见设计笔记。15

回答问题 5

同时能开几个子代理，能一层套一层吗？想关掉子代理，或者只关掉请求里的两条说明，怎么写、省多少？

gpt-6.1-sol：代理总数缺省 4 个（含父会话，即 3 个子代理），层数不限，满了报 agent thread limit reached；gpt-5.5：缺省一层。整个关掉写 [agents] 的 enabled = false，请求少 8,516 字节（15.5%）；只关两条说明，把 root_agent_usage_hint_text 和 multi_agent_mode_hint_text 设成空串，少 2,985 字节，工具仍在。

设计笔记

  • 隔离省的是窗口，不是钱，也不是 token 总量。子代理的每次请求都重发固定开头，实验里总量多 28%–33%。按缓存规则折价后差别小得多：实验的默认值下，缺省 all 折合 63,480 token，自己读 59,527，多 6.6%；干完活之后父会话再发 3 次请求，all 就比自己读便宜（65,573 对 66,071），none 要再发 13 次才便宜。这是第二节交互的推算，未用真实服务验证。真正要省的是父会话的窗口：它决定什么时候压缩（第 4 章），压缩之后摘要里还剩什么。
  • 缺省全量继承，理由代码没写【推测】：一是缓存，前面算过，all 的开头和父会话逐字相同，能读缓存；二是不丢父会话里的隐性约束（用户说过的「别动 API」）。源码里有个配置 preserve_fork_prefix（缺省 false），说明是「全量 fork 时保留父会话模型可见的历史，并追加子代理指令」，缺省 false 时，代码会在继承的历史里过滤、替换部分 developer 消息（core/src/agent/control/spawn.rs:1124-1260）；实验里父会话的角色说明和开关说明仍留在子代理的请求里，过滤规则我没逐条核对，打开这个开关的效果也没实验【待核实】。
  • 「别派」靠提示词，不靠权限。缺省的开关说明只是一句话；子代理和父拥有同样的工具（none 时少 1 个），名额满了才拦。想真正限制，要关工具（[agents] enabled = false）。
  • 内置角色：源码里有 default、explorer、worker 三个内置角色（core/src/agent/role.rs:342-385），explorer 的说明是「用来问具体的、范围明确的代码库问题」，但它的配置文件 explorer.toml 是 0 字节，没有限制工具，也没有换模型。本章抓到的 gpt-6.1-sol 和 gpt-5.5 的 spawn_agent 参数里都没有 agent_type，模型挑不了角色。所以内置的三个角色里没有只读的。自己定义角色（[agents.名字] 加 config_file，config/src/config_toml.rs:784 附近的注释有例子）可以限制，本章没做实验【待核实】。14
  • 没测的：真实模型会不会该派的时候派、不该派的时候忍住（开关说明起多大作用）；真实服务上的缓存命中；子代理自己触发压缩时，结果怎样回到父会话；文件冲突（所有代理共用同一个目录，角色说明里写了「别人的改动你马上看得到」，隔离文件的办法我没找到【待核实】）。这些归第 11 章（评估）。

小结

  1. gpt-6.1-sol 的请求里固定有 6 个协作工具（5,529 字节）、角色说明（2,575）、开关说明（410），共 8,514 字节、占 15.5%；gpt-5.5 默认没有，工具延后，搜一次 10,424 字节。
  2. 读 4 份 3 万字节的日志，派子代理让父会话的最后一次请求从 174,526 降到 55,810 字节，但整个过程输入合计多 28%–33%；省的是父会话的窗口。
  3. gpt-6.1-sol 的 fork_turns 缺省 all，子代理带走父会话全部历史，开头和父会话逐字相同，能接缓存；"none" 才从空白开始，但要整份重写；gpt-5.5 缺省不带。
  4. 回到父会话的是子代理最终回答的原文，没有上限，实验里 231,068 字节整份进来；gpt-5.5 还会在 wait_agent 结果和通知里各放一份。
  5. gpt-6.1-sol 总共 4 个代理（含父会话）、层数不限；整个关写 [agents] enabled = false，少 8,516 字节；两条说明设成空串，少 2,985 字节；features.multi_agent = false 对它没效果。
