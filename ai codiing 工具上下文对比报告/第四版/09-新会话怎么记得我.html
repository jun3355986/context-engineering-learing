新会话想得起你，靠的是开头多塞的一份摘要：缺省关闭，由后台另外两个模型在之后的会话里写成，最多约 1 万字节

2026-11-02 · Codex 源码 76ed3b4 / CLI 0.165.0 · 对话模型 gpt-6.1-sol，思考级别 low · 记忆自己用的模型 gpt-5.6-luna（low）和 gpt-5.6-terra（medium）· 对照 Claude Code 官方文档（2026-11-02 查阅）

实验里把 Codex 的 memories 打开后，新会话的第一次请求多出一段记忆说明：摘要只有 162 字节时多 2,344 字节，摘要超过约 1 万字节就从中间截掉，最多多约 1.2 万字节（gpt-6.1-sol，low，记忆 v2 版）。这份摘要不是这个会话自己写的：你在一个会话里发出一轮输入时，后台另外两个模型回头处理更早的旧会话，把它们写成摘要。所以昨天说的话，要等今天你在某个会话里开口时才被提炼，提炼出的摘要再到下一个新会话才读得到。

记忆（memory）：本章专指 Codex 的 memories 功能：后台把旧会话提炼成一份文字摘要，新会话开头读进去。这个功能有 v1、v2 两个版本，提示词和存放目录都不同；这台机器上在用的是 v2，本章以 v2 为主，两者的区别在第二节末尾。会话文件、线程、TUI（Codex 在终端里的交互界面）见第 8 章。本章实验在 自学单元/U08-实验/：模型服务器是本机的假服务器；CODEX_HOME（Codex 存配置、会话和记忆的目录，缺省是 ~/.codex）每次用一个全新的临时目录；不联网、不消耗额度。后台两个模型写出的摘要是假服务器写死的，所以本章只回答「请求里有什么、磁盘和数据库里写了什么」，不回答「摘要写得好不好」。token 数是 Codex 本地估算（UTF-8 字节数 ÷ 4），不是真实分词；没在真实终端里按过键盘。

回答问题 1

新开一个会话，请求里的历史是空白的。你昨天说过「测试用 pnpm」，有哪几条路能让它今天还知道？各自是谁写的、什么时候读？

三条路：① 写进 AGENTS.md，每个新会话开头读；② codex resume 原样接着昨天的历史；③ 打开记忆，后台模型把昨天的会话提炼成摘要，新会话开头读一次。只在会话里说过、又没恢复那个会话，就只能靠第三条，而且最早要到再下一个新会话才生效。

二、写入：在你发出一轮输入时启动，后台跑两步，不进你的会话历史

记忆不是在会话结束时写的，而是在你发出一轮输入时启动的后台任务。启动条件有四个：memories 已打开；这是根会话（你直接开的会话），不是子代理（第 7 章）；不是临时会话（codex exec --ephemeral）；这一轮确实有输入。任务在后台异步跑，不等它，你这一轮的回答照常发出。3

先选哪些旧会话

任务要处理的是别的旧会话，不是当前这个。一个旧会话要同时满足下面四条才会被选中；符合的按最近一次活动从新到旧排，每次启动最多取 2 个。4

  • 来源是交互式的。Codex 给每个会话记一个「来源」，表示它是从哪里开的；被选的来源只有 cli、vscode、atlas、chatgpt 四种。codex exec 跑的会话来源是 exec，不会被选：实验里用 codex exec 连开两个会话，第二个开始时没有提炼请求；换成 codex app-server（第 8 章实验用过的服务进程）开的会话，来源是 vscode，就有。5
  • 该会话的记忆开关没关（线程的 memory_mode 是 enabled；用 generate_memories = false 时开的会话是 disabled，实验里确认了）。
  • 最近一次活动在 10 天以内（max_rollout_age_days，配置里可设 0–90）。
  • 已经空闲至少 6 小时，也就是最后一次活动之后过了 6 小时（min_rollout_idle_hours，配置里最小 1、最大 48），避免处理还在进行的会话。

第一步「提炼」：把每个旧会话压成一段摘要文字

第一阶段对每个被选中的旧会话发一次模型请求，让它写一段摘要。缺省模型是 gpt-5.6-luna，思考级别 low（配置项 extract_model 可换），最多同时处理 8 个。实验里这次请求共 7,367 字节：一条 3,355 字节的 developer 消息（给模型的指令，不是你说的话；内容是写摘要的要求）加一条 2,843 字节的 user 消息（旧会话渲染成的文字：环境信息、你说的话、模型的回答各一行），要求按 JSON 返回两项：rollout_summary（这个旧会话的摘要）和 rollout_slug（存摘要的文件名里用的短名）。6

旧会话太长时，Codex 只读会话文件末尾的 8 MiB，再按优先级装进提炼模型窗口的 70%：你说的话最先，其次模型的最终回答，工具输出排最后（每条最多留 2,000 token）。模型写出的摘要，Codex 会把密钥之类的敏感字符串遮掉；v2 还把摘要截到 9,000 字节以内。7

第二步「合并」：写文件的智能体合成一份摘要

第二阶段起一个只能写记忆目录的智能体，让它读新旧摘要的差异，改写 memory_summary.md。这里的智能体是一个能自己调用工具、读写文件、分多步干活的模型会话，相当于一个后台的小 Codex。缺省模型是 gpt-5.6-terra，思考级别 medium。沙箱只允许写记忆目录、不开网络、不问批准，并关掉子代理、MCP 和记忆本身。Codex 在记忆目录里用 git 记着上次合并后的样子，只有记忆目录和那时相比有变化、或上次的产物不合格时，才起这个智能体；成功一次后冷却 6 小时；失败 1 小时后重试。8

这个智能体一开口就是一次不小的请求：v2 下实验里 50,466 字节，其中合并要求那一条只有 4,349 字节，其余是工具定义、系统提示词和环境信息，还没读任何文件。8合并成功的标准写在代码里：v2 要求 memory_summary.md 第一行是 v1、不到 10,000 字节、有 ## User Profile、## User preferences、## General Tips、## What's in Memory 四个标题；不合格就记为失败，1 小时后重试。9

两个版本：v1 和 v2

记忆管线有两个版本，配置项 [memories] 下的 version 取 "v1" 或 "v2"，各用一个目录。源码里缺省是 v1；实验里 codex exec 不设就是 v1，codex app-server 开的会话不设却是 v2，这台机器的 ~/.codex/ 下也只有 memories_v2/（TUI 走的是 app-server）。原因我没在源码里找到【待核实】。10

时间线：为什么要等到「再下一个」会话

摘要是在会话开头读的（第三节），写它的任务在会话开始之后才启动，所以新内容进不了当前会话。实验：开会话 A，说一句话；把 A 在数据库里的更新时间往前拨 2 小时（假装过了两小时）；再开会话 B。B 的第一次请求里只有预先放好的旧摘要；提炼 A 的请求和合并请求是 B 开始那一轮时后台发出的（提炼请求甚至比 B 自己的第一次请求先到服务器）。11

会话开头读到的摘要开始一轮之后，后台做的事
A（周一）更早的摘要提炼比 A 更早的旧会话
B（周二，A 已空闲 6 小时以上）更早的摘要，没有 A提炼 A，合并出新摘要
C（B 之后新开）含 A 的摘要……

这是最快的情形；合并有冷却和失败重试，可能更晚。

对照：Claude Code 的做法

Claude Code 有两样东西：你写的 CLAUDE.md，和 Claude 自己写的 auto memory。后者在本地会话里缺省开，在 /memory 里切换（存成 ~/.claude/settings.json 的 autoMemoryEnabled），或设环境变量 CLAUDE_CODE_DISABLE_AUTO_MEMORY=1 关掉。21

差别在于：Claude Code 由正在干活的同一个模型在会话里当场写（界面提示「Saved 2 memories」），你说「记住：测试用 pnpm」就存，凡是能从代码里读出来的不存。Codex 是后台另外两个模型事后写，当场看不到。读也不同：Claude Code 每次会话开头载入 MEMORY.md 的前 200 行或前 25 KB（先到为准），它只是索引，主题文件用到时再读；Codex 把一份总摘要整段放进去。

回答问题 2

Codex 的记忆缺省开着吗？它由谁、在什么时候写下来？写的时候会不会占用你正在进行的这个会话？

缺省关（源码 default_enabled: false；全新 CODEX_HOME 里 codex features list 显示 memories 为 false）。打开后，写入在你发出一轮输入时启动的后台任务里完成：gpt-5.6-luna（low）把符合条件的旧会话各压成一段摘要，gpt-5.6-terra（medium）的合并智能体再合成 memory_summary.md。这些是单独的模型请求，不写进你这个会话的历史、不占它的窗口，但用同一个模型通道和账号，花的是同一份额度【按源码推，没用真实服务测】。

三、读取：开头多一段 developer 消息，摘要超过 2,500 token 就从中间截掉

记忆进请求的办法很朴素：把 memory_summary.md 填进一段固定的说明，放在第三条输入的开头。第 2 章讲过，gpt-6.1-sol 请求的 input 里，第一条是工具定义，第二条是系统提示词，第三条是技能目录和权限说明那条 developer 消息。实验里同一句话「你好，帮我看看测试怎么跑」，关记忆和开记忆各发一次，差别如下。12

摘要太长：从中间截，头尾各留一半

摘要超过 2,500 token（Codex 按 4 字节 1 token 估算，约 1 万字节）就从中间截掉。实验里放了一份 500 行的英文摘要（31,003 字节），请求里留下第 1–80 行和第 421–500 行，中间换成一句 …5251 tokens truncated…；30 KB 的汉字摘要也是留下约 1 万字节，约 3,300 个汉字。所以最重要的内容要放在摘要的开头或结尾。这个上限和合并那一步配套：合并要求让智能体把摘要写得「留有余量地低于 10,000 UTF-8 字节」，校验也要求不到 10,000 字节。139

摘要只在会话开头读一次

摘要读进来之后就存进了这个会话的历史，之后不会重读。实验：用一个会话读到旧摘要，再把 memory_summary.md 改成另一段文字，用 codex exec resume --last 接着这个会话：请求里还是旧摘要，新文字没有出现。AGENTS.md 不同：恢复旧会话时它会与存档里的基线比对，变了就追加新全文（第 8 章）；记忆没有这一步。14

另外三个实验结果：use_memories = false 时请求与不开记忆逐字一样；临时会话（--ephemeral）照样读记忆，只是不触发写入；换个目录开新会话，记忆段逐字相同（第五节）。14

记忆段排在第三条输入，前面是工具定义和系统提示词（第 2 章）。按第 5 章的规则，摘要一变，从第三条起的缓存前缀就不再相同，前两条仍能接上【按规则推，没有用真实服务验证】。

回答问题 3

打开记忆后，新会话的第一次请求里多了什么、占多大？摘要写得太长怎么办？你在会话中途改了这份摘要，已经开着的会话会知道吗？

多一段 developer 消息，在第三条输入的开头：模板 v2 是 2,096 字节、v1 是 6,717 字节，再加摘要。摘要超过 2,500 token（约 1 万字节，中文约 3,300 字）就留头尾各约一半、截掉中间。摘要在会话开头读一次、存进历史；你中途改文件，开着的会话和之后恢复的旧会话都不会重读。

四、纠错、关闭、淘汰：能改、能关、30 天没人引用就出局

记错了不能在摘要上直接划掉，要走笔记或改文件，等下一次合并才生效。有三条路。

  • 对 Codex 说「记住……」「忘掉……」「改成……」。读路径的说明写着：只有你明确要求时才更新记忆，办法是在记忆目录的 extensions/ad_hoc/notes/ 下新建一个 时间-短名.md 笔记，不许直接改记忆文件。合并智能体把每条笔记当作权威，写进摘要时标 [ad-hoc note]，笔记只当信息、不当指令。实验里确认了：记忆目录下的 extensions/ad_hoc/instructions.md（733 字节，写着上面这些规则）会在首次启动时写出，开 dedicated_tools 后请求里多出 add_ad_hoc_note 工具；没试过真实模型写笔记。18
  • 直接改文件。摘要是纯文本的 Markdown 文件。v2 的合并要求写着「应用用户的编辑和来源变化，不要把被修正或删除的结论恢复回来」。实验里手放一个 memory_summary.md 就让下一次启动起了合并智能体（见 out/read 里 phase2 的请求）；真实模型会不会照办，没测。18
  • 关、清。读和写各有一个开关（见开头的表）：use_memories = false 时新会话请求里没有记忆段；generate_memories = false 时新开的会话在数据库里记为 disabled，以后不被提炼。另有 disable_on_external_context（缺省关）：打开后，用过 MCP 或网页搜索的会话标成 polluted（可能混进了外部内容），不进记忆。清空会同时清数据库和记忆目录，不动已有会话。19

谁会被淘汰：引用次数优先，30 天没被引用就出局

合并时按引用次数从多到少取，超过 30 天没被引用的不再入选。「被引用」指模型在最终回答末尾附一段 <oai-mem-citation>，列出用了哪个文件、哪几行、哪个旧会话。Codex 把它从显示的回答里剥掉，转成结构化的 memoryCitation，给对应旧会话记一次使用、更新最近使用时间。实验里让假服务器的回答带上这样一段：显示的文字只剩正文，数据库里该会话的 usage_count 从空变成 1，last_usage 有了时间戳。16

入选规则（缺省 30 天，配置项 max_unused_days，可设 0–365）：最近一次被引用在 30 天内；从没被引用过的，看它自己的最近活动是否在 30 天内。入选的按使用次数降序、再按「最近引用或最近活动」降序排，取前 256 条（max_raw_memories_for_consolidation）。过期、又不是上次合并用过的记录，启动时会从数据库删掉（每次最多 200 条）。17

动手看：哪些记忆留下

下面 6 条记忆是我虚构的。把「取前几条」调小，看排序怎样决定谁先留下：被引用 2 次、最后一次在 25 天前的，排在从没被引用、只是 8 天前的前面。按源码里的排序和过滤规则画，未实验。17

回答问题 4

一条记错的记忆怎么纠正？怎么关、怎么清空？什么样的记忆会被淘汰？

纠正：对 Codex 说「记住/忘掉……」，它会在记忆目录的 extensions/ad_hoc/notes/ 下写一份笔记，下一次合并时当作权威；也可以直接改 memory_summary.md。都要等下一次合并才进摘要。关：use_memories = false 不读，generate_memories = false 不写；清空：/memories 里的 Reset all memories 或 codex debug clear-memories。淘汰：超过 30 天没被引用的不再进合并，被引用越多越先留下。

五、范围：一个用户一份，不按项目分

Codex 的记忆目录在 CODEX_HOME 下，一个用户一份，不按项目隔离。实验里在另一个工作目录开新会话，记忆段与第一个目录里的逐字相同（请求总大小相差 182 字节，是因为那个目录没有 AGENTS.md）。20

项目的区分靠摘要里的文字：每条提炼记录的文件头有当时的工作目录（cwd），v2 的合并要求让智能体把近期工作按 ### 项目范围、#### 日期 分组。分得对不对取决于写摘要的模型，代码没做隔离。所以项目 A 里的「测试用 pnpm」可能出现在项目 B 的摘要里；B 若不用 pnpm，要在 B 的 AGENTS.md 里写一句明确的规则，说清这个项目用什么。Claude Code 见第二节的对照框：按 git 仓库分目录，不同仓库互不相见。21

回答问题 5

你在项目 A 里留下的记忆，会带进项目 B 的新会话吗？Claude Code 也这样吗？

会。Codex 的记忆一个用户一份，不分项目，实验里换目录开会话注入的内容逐字相同；项目的区分只靠摘要里的文字，由写摘要的模型自己判断。Claude Code 不这样：auto memory 放在 ~/.claude/projects/<项目>/memory/，按 git 仓库分，只在本机。

设计笔记

  • 后台、事后写，而不是边聊边写。好处：写记忆的请求不进你的会话历史，不占窗口；代价：你看不到它写了什么，没有「这条对不对」的确认点，新内容至少晚一个会话才生效。代码没写理由【推测】。
  • 摘要开头读一次、之后不再更新。放在前缀靠前、之后不变的位置，对缓存有利；代价是会话中途学到的东西进不了当前会话【推测】。
  • 用引用次数决定谁留下。Codex 用模型附的引用给旧会话计数，没人引用的 30 天后出局，等于假设「被引用过」就是有用。一条记错的结论若被一再引用，会越排越前；我没找到对「引用了但错了」的处理【推测】。
  • 不按项目隔离。通用偏好（回答语言、提交风格）能跨项目复用是好处；项目事实（框架、命令）会串是代价。Codex 把区分交给写摘要的模型。
  • 其他 agent。本机没有它们的源码，没核对；以前整理的资料里对 Grok Build、oh-my-pi、pi、opencode 的说法，出处见证据表【待核实】。22

小结

  1. 三条路：你写的 AGENTS.md、原样接着旧历史的 codex resume、后台模型写的记忆摘要；只在会话里说过的话，只能靠记忆，而且最早到再下一个会话才生效。
  2. 缺省关；打开后，在你发出一轮输入时起后台任务：gpt-5.6-luna（low）提炼旧会话，gpt-5.6-terra（medium）合并成摘要；不进你的会话历史。
  3. 新会话第一次请求多一段 developer 消息，v2 模板 2,096 字节、v1 6,717 字节加摘要；摘要超过 2,500 token 从中间截；开头读一次，中途改了不会重读。
  4. 纠正走笔记（extensions/ad_hoc/notes/）或直接改文件，下一次合并才生效；use_memories、generate_memories 分别管读和写；30 天没被引用的出局，引用多的先留。
  5. Codex 一个用户一份、不分项目，项目区分靠摘要里的文字；Claude Code 按 git 仓库分目录。
