第 3 章

命令输出了 5 万行，模型只看到头尾约 1 万 token

2026-11-02 · Codex 源码 76ed3b4 / CLI 0.165.0 · 模型 gpt-6.1-sol，思考级别 low；对照 gpt-5.5，思考级别 low

让 agent 跑一条命令，输出 5 万行、288,894 字节。整份放进请求的话，按 Codex 的估算要 72,224 token（约 7.2 万）；第 2 章那次请求只说了一句话，一共 13,410 token，这里是它的 5 倍多。但 Codex 实际只放进去约 1 万 token：保留输出的开头一段和结尾一段，中间丢掉，换成一行标记。

本章的例子都是这一条命令：seq 1 50000，它打印 1 到 50000，每个数一行。后文的 72,224 token 就是它的原文大小，各组实验都从它出发；只有两处换了命令，换的地方会说明为什么换。token 数仍是 Codex 的估算：UTF-8 字节数 ÷ 4，向上取整（见第 2 章）。实验在本机起一个假的模型服务器，让 Codex 真的执行命令，再抓下它发出的下一次请求，不联网。16

一、5 万行的输出，模型看到哪几行

把一条很长的输出放进请求，最朴素的做法有三种，各有毛病。整份放进去：这一条就是 72,224 token，比请求里其他内容加起来还多，输出再长，窗口就装不下了。只留开头：测试和编译的失败摘要通常在最后，这样就丢了。只留结尾：命令开头写着它在做什么，最早的报错也在开头，这样也丢了。

Codex 的做法是保留开头和结尾，丢掉中间。上限默认是 1 万 token，Codex 按 1 token = 4 字节换算成 4 万字节，开头留 2 万字节，结尾留 2 万字节。原文 72,224 token，留下 1 万，中间的 62,224 token 丢掉，换成一行标记 …62224 tokens truncated…，意思是「这里截断丢掉了 62,224 token」。3

实测和这个算法对得上。gpt-6.1-sol 这次实验里，进入请求的输出是 40,158 字节，约 10,040 token；比 1 万多出的 40 token 是运行信息和截断说明（下一小节列出来），它们不算在上限里。保留下来的是第 1–4,221 行和第 46,668–50,000 行，共 7,554 行；中间第 4,222–46,667 行（42,446 行）丢掉，第 25,000 行就在里面。1 换成 gpt-5.5，保留的行完全一样，只是开头的运行信息多几行，总共 40,217 字节。2

模型知道自己少看了吗

知道少了多少，不知道少了哪几行。下面是 gpt-6.1-sol 那次实验里模型收到的输出，原样摘录，只把中间成千上万行连续的数字换成了（……）：13

前三行是运行信息：脚本跑完了、用了多久，后面跟着输出。截断以后，输出里多了三处说明：

  • Warning 那一行：原文有 72,224 token。
  • Total output lines 那一行：原文有 50,000 行。
  • 中间的标记：这里丢掉了 62,224 token。标记两边的 42 和 7 是切开后剩下的半截数字。Codex 按字节切，不按行切：开头的 2 万字节正好停在第 4,222 行「4222」的前两个字符，结尾的 2 万字节从第 46,667 行「46667」的最后一个字符开始，这两行就只剩半截，和标记连成了一行。

从这三处，模型知道原文多大、丢了多少。丢的是哪几行，只能靠前后保留下来的内容去推。seq 的输出是连续的数字，前面停在 4221、后面从 46668 接上，模型能算出丢的是第 4,222–46,667 行。换成一份构建日志，前后内容没有这种规律，模型只知道中间少了 62,224 token，推不出少的是哪些日志、里面有没有报错。

回答问题 1

5 万行的输出，模型看到什么、多少 token？

只看到开头和结尾：第 1–4,221 行和第 46,668–50,000 行，约 1 万 token（实测 10,040），原文是 72,224 token。中间 42,446 行换成了一行标记。既不是全部，也不是只留一头。

回答问题 2

模型知道自己少看了一部分吗？

知道少了多少：输出开头写着原文的 token 数和总行数，中间的标记写着丢掉了多少 token。不知道少的是哪几行，只能从前后保留下来的内容推断；内容没有规律时（比如构建日志）推不出来。

换成中文：同样的上限，装下的字更少

上面的 seq 输出全是数字和换行，一个字符占 1 字节。Codex 的上限按字节算（1 万 token = 4 万字节），一个汉字在 UTF-8 里却占 3 字节，所以同样的上限，能装下的汉字只有数字字符的三分之一。为了看实际效果，另做了一次实验（gpt-5.5，思考级别 low）：让命令输出一行 3 万个「汉」字，原文 90,001 字节，Codex 估算 22,501 token；进入请求的只有 13,332 个字。4

还有一层：Codex 的估算把一个汉字算成 0.75 token（3 字节 ÷ 4），模型真实的分词器给一个汉字的 token 数可能更多。如果是这样，Codex 以为放进去的是 1 万 token，按真实分词算会超过 1 万【推测：没用真实分词器测】。

二、在哪里截断：最多经过四个截断点

上一节的 1 万 token，不是在一个地方定下的。命令的输出从产生到进入请求，最多经过四个截断点，每个都有自己的上限。经过哪几个，取决于模型怎么调用命令：gpt-5.5 直接调用命令工具 exec_command；gpt-6.1-sol 不直接调用，它先写一段 JavaScript，交给代码工具 exec 运行，再由这段 JavaScript 调用 exec_command。exec 就是第 2 章说的 gpt-6.1-sol「3 组共 11 个工具」里的一个。

截断点发生在什么时候默认上限谁能改上限、怎么改
① 进程输出缓冲命令运行时，Codex 用一块内存收集输出1 MiB：开头、结尾各留 512 KiB，中间丢掉谁都不能改，写死在代码里5
② 命令工具 exec_command命令跑完，exec_command 把结果交出去时1 万 token模型：调用时传参数 max_output_tokens6
③ 代码工具 exec只有 gpt-6.1-sol 经过：JavaScript 跑完，结果交回模型时1 万 token模型：在 JavaScript 第一行写 // @exec: {"max_output_tokens": 30000}8
④ 写入历史输出写进会话历史时（会话历史和存档是两处，第三节讲区别）基数 × 1.2；基数默认 1 万，所以是 1.2 万 token你：在 ~/.codex/config.toml 里加一行，如 tool_output_token_limit = 2000，改的是基数9

拿 seq 1 50000 的 72,224 token 对着这张表走一遍，有两处和直觉不同：

  • gpt-6.1-sol 默认只截断一次，发生在截断点 ③。它在 JavaScript 里调用 exec_command 时没有传上限，这种情况下 ② 不截断，把 72,224 token 的原文整份交给 JavaScript；JavaScript 跑完、结果交回模型时，③ 才按 1 万 token 截断。所以上一节摘录的输出里只有一组截断说明。gpt-5.5 没有 ③，截断发生在 ②。两个模型到了 ④，输出都只剩约 1 万 token，没超过 1.2 万，不再截断。7
  • 截断点 ① 在本章的例子里碰不到。它的上限是 1 MiB（1,048,576 字节），防的是几百 MB 的输出撑爆内存；seq 1 50000 只有 288,894 字节，到不了。要看它起作用，得换一条更长的命令：seq 1 300000，输出 30 万行、1,988,895 字节（gpt-5.5 实验）。这次 ① 先丢掉中间的 940,319 字节，只把 1 MiB 交给 ②，② 再截断到 1 万 token。模型看到的仍是第 1–4,221 行，加上最后 2,857 行（第 297,144–300,000 行）。和 5 万行那次比，输出开头有两处不同：① 的标记 ... 940319 bytes omitted ... 写在正文最前面，而不是写在丢掉内容的位置；Total output lines 那一行没有了，模型不知道原文有多少行。Warning 里的原文 token 数仍按全文算，是 497,224。5

回答问题 4

模型能自己把上限调高吗？你在配置里调高呢？

模型自己调，有天花板：gpt-6.1-sol 最多拿到 1.2 万 token（你的基数 1 万 × 1.2）；gpt-5.5 只能把上限调低。你只在配置里调高 tool_output_token_limit 也不够：模型调用时没有同时把上限调高，最后还是 1 万。两边都调高，进入请求的输出才会超过 1.2 万（这一点是按源码推的，没做实验）。

三、截断时丢掉的那段去哪了

先交代 Codex 把命令输出放在哪。输出经过截断点 ①②③ 以后，Codex 把它同时写到两个地方：1011

  • 会话历史：放在内存里的对话记录，之后每次请求都从这里拼出来，模型看到的就是这一份。写进这里时，截断点 ④ 再截断一次。
  • 会话存档：磁盘上的 .jsonl 文件，在 ~/.codex/sessions/ 下，每个会话一个。写进这里时不经过 ④；但 ①②③ 在写入之前已经截断过了，所以存档里的也不是原文。

也就是说，原文在 ①②③ 那一步就丢了，两个地方都没有。直觉是存档会留一份完整的，实际没有：查了 gpt-6.1-sol 4 组实验的存档，5 万行的原文哪里都没有，搜不到第 25,000 行。两处记下的大小如下：

默认10,040 token10,040 token
模型调用 exec_command 时把上限设成 5 万10,040 token10,040 token
你把基数调成 2,0002,407 token10,040 token

前两组两边一样：截断发生在 ③（第二组 ② 也截断了一次），都在写入两处之前。后两组存档里的更多，因为这两组是 ④ 截断的，④ 只截断会话历史里那份，存档那份不动。基数调成 2,000 那组，请求里只有 2,407 token，存档里仍是 ③ 交出来的 10,040 token；两处都设成 3 万那组，请求里 12,007 token，存档里 30,039 token。存档里多出的这部分，这个会话里的模型看不到，只有你打开文件才看得到。

原文丢了，模型想看中间，只能再跑一次命令，这次改一改命令，只输出需要的那几行。拿本章的例子说，想看第 24,990–25,010 行，就跑 seq 1 50000 | sed -n '24990,25010p'，输出只有 21 行，不会被截断。

真实场景里，输出很长的多是测试和构建，比如 make test，重跑一遍可能要几分钟。预计输出会很长时，可以一开始就把完整输出写进文件，之后按需读文件的一部分：

  • 跑命令，输出写进文件：make test > test.log 2>&1。test.log 是工作目录里的一个普通文件，命令本身几乎不输出，不会被截断。
  • 找关键词在哪几行：grep -n ERROR test.log
  • 看某一段：sed -n '24990,25010p' test.log
  • 只看结尾：tail -n 200 test.log

这些命令要模型自己想到、自己发起，代价是多跑几次命令；而且模型没看到中间，得先猜要找什么，比如猜里面有 ERROR。

回答问题 3

截断时丢掉的那段，还能找回来吗？

找不回来。存档里记的是经过 ①②③ 截断的版本（默认约 1 万 token），288,894 字节的原文哪里都没留。只有截断点 ④ 例外：④ 只截断会话历史里那份，不截断存档，所以 ④ 丢掉的部分存档里还有，只是模型看不到。想看中间，只能再跑一次命令，用 grep、sed、tail 只取需要的那几行；或者一开始就把输出写进文件，再分段读。

对照：Claude Code 把太长的输出存成文件

据官方文档（2026-11-02 查阅），Claude Code 的 Bash 工具分两种情况：14

  • 命令成功：输出约 30,000 字符以内，直接给模型。超过了，Claude Code 把完整输出写进会话目录里的一个文件（超过 64 MiB 的部分截断），模型拿到的是文件路径和前 2,000 字符的预览，需要时自己读或搜这个文件。
  • 命令失败：输出约 10,000 字符以内直接给；超过了只给开头和结尾的摘录，不存文件。
  • 可调：设置项 bashOutputMaxChars 能把「直接给」的上限调高到 128,000 字符（v2.1.261 起）。

简单说：命令成功、输出又很长时，Codex 丢掉中间，Claude Code 把全文存进文件、给模型一个路径；命令失败时，两边都只留开头和结尾。

四、跑 10 次，前面的输出还在吗

还在。输出写进会话历史以后，之后的每次请求都带着它。第 2 章讲过：走 HTTP 时每次请求整份重发；走 WebSocket 时网络上只发新增的部分，但模型看到的仍是全部历史。Codex 源码里没找到清理旧工具输出的代码【源码搜索，没穷尽】。13

量一下每跑一次多出多少。gpt-6.1-sol 默认那组实验里，第一次请求是 54,808 字节；模型发起调用、命令跑完以后，第二次请求涨到 102,921 字节，多了约 1.2 万 token。多出的是两条记录：模型发起这次调用的那条（203 字节），和命令输出那条（47,910 字节）。输出那条比第一节说的 40,158 字节多出约 7,700 字节，因为请求是 JSON 格式，输出里的每个换行要写成 \n 两个字符。12

按 1 次实验推算：每跑一次只算这两条记录，没算模型每轮的回复；没做 10 次的实验。

要把这些旧输出从请求里去掉，只有两个办法：压缩，也就是把历史交给模型写成一段摘要（第 4 章）；或者新开一个会话。在那之前，每次请求都要重发这些旧输出（要多花多少钱，第 5 章算）。

Claude Code 的官方文档也没写会清理旧的工具输出，只写了窗口快满时自动压缩，以及换任务时用 /clear 清空对话。15 不过 Claude Code 的长输出写进历史的只有文件路径和 2,000 字符预览，同样跑 10 次，占的地方小得多。

回答问题 5

同一个会话跑了 10 次，前面的输出会从请求里清掉吗？

不会。每次约 1.2 万 token 都留在历史里，之后每次请求都重发；跑完 10 次，之后每次请求都多带约 12 万 token（按单次实验推算）。只有压缩或新开会话能把它们去掉。

看源码：上限取较小的那个

core/src/unified_exec/mod.rs 第 74、221–223 行，core/src/tools/context.rs 第 469–472、482–489 行，节选，注释是我加的。67

pub(crate) const DEFAULT_MAX_OUTPUT_TOKENS: usize = 10_000;

pub(crate) fn resolve_max_tokens(max_tokens: Option<usize>) -> usize {
    max_tokens.unwrap_or(DEFAULT_MAX_OUTPUT_TOKENS)   // 模型没传，就按 1 万
}

// 截断点 ②：模型直接调用命令时（gpt-5.5）
fn model_output_policy(&self) -> TruncationPolicy {
    let requested_policy = TruncationPolicy::Tokens(resolve_max_tokens(self.max_output_tokens));
    // 模型传的上限，和你配的基数比，取较小的
    if requested_policy.byte_budget() < self.truncation_policy.byte_budget() {
        requested_policy
    } else {
        self.truncation_policy
    }
}

// 命令在 JavaScript 里被调用时（gpt-6.1-sol）
output: match self.max_output_tokens {
    Some(max_tokens) => self.truncated_output(max_tokens),          // 传了：按它截断
    None => String::from_utf8_lossy(&self.raw_output).to_string(), // 没传：原文整份交给 JavaScript
},

注意 JavaScript 这条路径只看模型传的值，不和你配的基数比；你配的基数要到截断点 ④ 才起作用。

设计笔记

  • 为什么保留开头和结尾、丢掉中间。命令的开头常是它在做什么、最早的报错，结尾常是总结、退出状态和最后的报错，中间多是重复的进度。代码里没写理由【推测】。
  • 每个截断点只会让输出变短。模型不能靠一个参数把一条输出放大到占满窗口；代价是真想多看时，模型和配置两边都得改。gpt-6.1-sol 多出的截断点 ③ 像一道保险：一段 JavaScript 可以把好几次命令的结果拼在一起，交回模型前要再限一次长度【推测】。
  • 丢掉，还是存成文件。Codex 不留临时文件，做法简单，代价是找不回来；Claude Code 能找回，代价是模型要多读一次文件，这些文件也得定期清理。
  • 为什么不清理旧输出。另一种做法是：旧输出用过以后，换成一行「已省略」，这一步不调用模型（常叫「裁剪」）。代价是改了历史前面的内容，前缀缓存会失效（第 5 章）。Codex 选择历史前面一字不改，和第 2 章「稳定的在前、变化的追加在后」一致【推测】。

小结

  1. 5 万行（72,224 token）的输出，模型只看到第 1–4,221 行和第 46,668–50,000 行，约 1 万 token；中间换成一行标记。
  2. 模型知道少了多少（开头的说明和中间的标记），不知道少了哪几行。
  3. 截断时丢掉的找不回来：存档里记的是经过 ①②③ 截断的版本。只有截断点 ④ 丢掉的部分还在存档里，因为 ④ 只截断会话历史，不截断存档。想看中间，就再跑一次命令，用 grep、sed、tail 只取需要的行。
  4. 最后的大小取几个截断点里最小的上限：gpt-6.1-sol 的模型自己最多调到 1.2 万，gpt-5.5 的模型只能调低；只在配置里调高也不够，两边都要调高。
  5. 旧输出不会清掉，每次约 1.2 万 token，之后每次请求都重发，直到压缩或新开会话。
