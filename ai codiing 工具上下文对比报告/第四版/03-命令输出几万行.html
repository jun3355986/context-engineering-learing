第 3 章

命令输出了 5 万行，模型只看到头尾约 1 万 token

2026-11-02 · Codex 源码 76ed3b4 / CLI 0.165.0 · 模型 gpt-6.1-sol，思考级别 low；对照 gpt-5.5，思考级别 low

让 agent 跑一条命令，输出 5 万行、约 29 万字节。整份放进请求要 7.2 万 token，是第 2 章那次完整请求的 5 倍多。Codex 只放进去约 1 万 token：开头一段、结尾一段，中间换成一行标记。这一章看它截在哪、模型知不知道、截掉的能不能找回、上限能不能调，以及同样的命令跑多了会怎样。

本章的例子是 seq 1 50000：打印 1 到 50000，每个数一行。token 仍是 Codex 的估算：UTF-8 字节数 ÷ 4，向上取整（见第 2 章）。实验用本机假服务器让 Codex 真的执行命令，再抓下一次请求，不联网。16

15 万行，模型看到哪几行

朴素的做法有三种，各有毛病。整份放进去：一条命令 7.2 万 token，比请求里其他内容加起来还多，输出再大就装不下。只留开头：测试和编译的失败摘要通常在最后。只留结尾：丢了开头那段「命令在做什么」和最早的报错。

Codex 的做法是留头留尾，中间挖掉。默认上限 1 万 token，换成字节是 4 万：开头 2 万字节、结尾 2 万字节，中间换成一行 …62224 tokens truncated…（截掉了 62,224 token）。3

实测 gpt-6.1-sol：进入请求的输出是 40,158 字节，约 10,040 token。保留的是第 1–4,221 行和第 46,668–50,000 行，中间 42,446 行丢掉，第 25,000 行就在里面。两个切口都落在行中间，所以标记前后各有半个数字。1 换成 gpt-5.5，切点完全一样，大小 40,217 字节。2 标记和说明不算在 1 万里，所以结果比 1 万略多。

动手看：输出多少行时开始截

拖滑块改 seq 1 N 的 N。条按字节比例画：绿色进入请求，红色被丢掉。5 万行和 30 万行是实验数据，其余按同样的规则算。

按字节算，对中文不利。3 万个汉字是 90,001 字节，估算 22,501 token；进入请求的只有 13,332 个字（gpt-5.5 实验）。4 这个估算把一个汉字算成 0.75 token，真实分词常常不止，所以中文输出实际占的可能超过 1 万 token【推测：没用真实分词器测】。

知道少了多少，不知道少了哪几行。被截过的输出，开头多两行说明，中间有一行标记（再往前还有几行运行信息，如耗时、退出码）：3

回答问题 1

5 万行的输出，模型看到什么、多少 token？

只看到开头和结尾：第 1–4,221 行和第 46,668–50,000 行，约 1 万 token（实测 10,040）。中间 42,446 行换成了一行标记。既不是全部，也不是只留一头。

回答问题 2

模型知道自己没看到吗？

知道少了多少：输出开头写着原文的 token 数和总行数，中间的标记写着截掉多少 token。不知道少的是哪几行，只能从前后内容推断。

2截在哪：最多四道闸

上面那 1 万 token 不是在一处定下的。输出从命令到请求，最多经过四处截断，哪几处起作用跟模型有关：gpt-5.5 直接调用命令工具 exec_command；gpt-6.1-sol 不直接调，它写一段 JavaScript 交给代码工具 exec 运行，JS 里再调 exec_command。第 2 章说 gpt-6.1-sol 有「3 组共 11 个工具」，exec 就在里面。

闸在哪默认上限谁能改、怎么改
① 进程输出缓冲命令运行时，Codex 收集输出的内存缓冲1 MiB：头尾各留 512 KiB，中间丢掉不能改，写死在代码里5
② 命令工具 exec_command命令结果交出去时1 万 token模型：调用时传 max_output_tokens6
③ 代码工具 exec只有 gpt-6.1-sol：JS 跑完、结果交回模型时1 万 token模型：在 JS 第一行写 // @exec: {"max_output_tokens": 30000}8
④ 写入历史输出放进会话历史时基数 × 1.2 = 1.2 万 token你：在 ~/.codex/config.toml 里写 tool_output_token_limit = 2000 这样一行，改的是基数，默认 1 万9

有两处和直觉不同：

  • gpt-6.1-sol 默认只在 ③ 截一次。JS 里调 exec_command 时没传上限，② 就把原文整份交给 JS，不截；最后的输出里也只有一组说明。7
  • ① 平时看不出来。它防的是几百 MB 的输出撑爆内存。30 万行（1,988,895 字节）的实验里，缓冲留下 1 MiB，开头加一行 ... 940319 bytes omitted ...，再由 ② 截到 1 万 token。模型看到的仍是第 1–4,221 行和最后 2,857 行。这行标记写在开头，不在真正丢掉的位置；这次的说明里也没有总行数。5

回答问题 4

模型能自己调大上限吗？你在配置里调大呢？

模型自己调，有天花板：gpt-6.1-sol 最多拿到 1.2 万 token（你的基数 1 万 × 1.2），gpt-5.5 只能往小调。你只调大 tool_output_token_limit 也不够：最后的大小取几道闸里最小的那个，模型那一侧不跟着要大，还是 1 万。两边都调大才会变大（调大这一侧是按源码推的，没做实验）。

3截掉的那段去哪了

直觉是：Codex 会把会话写进存档，截掉的应该还在存档里。查了 4 次 gpt-6.1-sol 实验的存档（~/.codex/sessions/ 下的 .jsonl 文件），原始输出哪里都没有：5 万行的存档里搜不到第 25,000 行。1011

模型想看中间，只能重跑命令，让命令自己把输出变小：

  • 找关键词：grep -n ERROR build.log
  • 看某一段：sed -n '24990,25010p' build.log
  • 只看结尾：tail -n 200 build.log
  • 先存成文件再分段读：make test > /tmp/test.log 2>&1，再用上面几条读

代价是多跑一两次命令，而且得先知道要找什么。

回答问题 3

截掉的那段，还能找回来吗？

找不回来。存档里记的也是截过的版本（默认同样约 1 万 token），原始的 29 万字节哪里都没留。只有写入历史时（第 ④ 道）截掉的部分，存档里还在。要看中间，只能重跑命令，用 grep、sed、tail 让输出变小。

对照：Claude Code 把多出来的存成文件

据官方文档（2026-11-02 查阅），Claude Code 的 Bash 工具分两种情况：14

  • 命令成功：约 30,000 字符以内，直接给模型。超过了，就把完整输出存进会话目录里的一个文件（超过 64 MiB 的部分截掉），模型拿到的是文件路径和前 2,000 字符的预览，需要时自己读或搜这个文件。
  • 命令失败：约 10,000 字符以内直接给；超过了只给一段「头 + 尾」的摘录，不存文件。
  • 可调：设置项 bashOutputMaxChars 能把「直接给」的上限调到 128,000 字符（v2.1.261 起）。

一句话：成功的大输出，Codex 把中间扔掉，Claude Code 把全文放到磁盘上、给模型留一个路径；失败的输出，两边都是留头留尾。

4跑 10 次，前面的输出还在吗

在。输出写进历史以后，之后每次请求都带着它。第 2 章讲过：走 HTTP 时整份重发；走 WebSocket 时线上只发新增的部分，但模型看到的仍是全部。Codex 源码里没找到清理旧工具输出的机制【源码搜索，没穷尽】。13

量一下有多大。这条输出放进请求是 47,910 字节，比正文的 40,158 字节多出约 7,700 字节，因为每个换行在请求的 JSON 里要写成 \n 两个字符。加上模型发起调用的那条，第二次请求从 54,808 字节涨到 102,921 字节，多了约 1.2 万 token。12

按 1 次实验推算：每次只算「模型发起调用」和「命令输出」两条，没算模型每轮的回复；没做 10 次的实验。

让它们离开只有两条路：压缩，把历史交给模型写成一段摘要（第 4 章）；或者新开会话。在那之前，每一轮请求都要重发这些旧输出（要花多少钱，第 5 章算）。

Claude Code 的官方文档也没写会清理旧的工具输出，只写了窗口快满时自动压缩，以及换任务时用 /clear 清空对话。15 不过它的大输出进历史的只有路径和 2,000 字符预览，同样跑 10 次，占的地方小得多。

回答问题 5

同一个会话跑了 10 次，前面的输出会被清掉吗？

不会。每次约 1.2 万 token 都留在历史里，之后每次请求都重发；跑完 10 次，之后每次请求都多带约 12 万 token（按单次实验推算）。只有压缩或新开会话能让它们离开。

看源码：上限取较小的那个

core/src/unified_exec/mod.rs 第 74、221–223 行，core/src/tools/context.rs 第 469–472、482–489 行，节选，注释是我加的。67

pub(crate) const DEFAULT_MAX_OUTPUT_TOKENS: usize = 10_000;

pub(crate) fn resolve_max_tokens(max_tokens: Option<usize>) -> usize {
    max_tokens.unwrap_or(DEFAULT_MAX_OUTPUT_TOKENS)   // 模型没传，就按 1 万
}

// 第 ② 道：模型直接调命令时（gpt-5.5）
fn model_output_policy(&self) -> TruncationPolicy {
    let requested_policy = TruncationPolicy::Tokens(resolve_max_tokens(self.max_output_tokens));
    // 模型要的，和你的基数比，取较小的
    if requested_policy.byte_budget() < self.truncation_policy.byte_budget() {
        requested_policy
    } else {
        self.truncation_policy
    }
}

// 命令在 JS 里被调用时（gpt-6.1-sol）
output: match self.max_output_tokens {
    Some(max_tokens) => self.truncated_output(max_tokens),          // 传了：按它截
    None => String::from_utf8_lossy(&self.raw_output).to_string(), // 没传：原文整份交给 JS
},

注意 JS 这条路径只看模型传的值，不和你的基数比；你的基数要到第 ④ 道才起作用。

设计笔记

  • 为什么留头尾、挖中间。命令的开头常是它在做什么、最早的报错，结尾常是总结、退出状态和最后的报错，中间多是重复的进度。代码里没写理由【推测】。
  • 每道闸都只往小截。模型不能靠一个参数把一条输出放大到撑满窗口；代价是真想多看时，模型和配置两边都得改。gpt-6.1-sol 多出的 ③ 也像一道保险：一段 JS 可以把好几次命令的结果拼在一起，交回模型前要再限一次【推测】。
  • 扔掉，还是存成文件。Codex 不留临时文件，做法简单，代价是找不回来；Claude Code 能找回，代价是模型要多读一次文件，这些文件也得定期清理。
  • 为什么不清理旧输出。另一种做法是：旧输出用过以后，换成一行「已省略」，不调用模型（常叫「裁剪」）。代价是改动了历史前面的内容，前缀缓存会失效（第 5 章）。Codex 选择前面一字不改，和第 2 章「稳定的在前、变化的追加在后」一致【推测】。

小结

  1. 5 万行的输出，模型只看到第 1–4,221 行和第 46,668–50,000 行，约 1 万 token；中间换成一行标记。
  2. 模型知道少了多少（开头的说明和中间的标记），不知道少了哪几行。
  3. 截掉的找不回来：存档里也是截过的版本。只有写入历史时截掉的部分，存档里还在。要看中间就重跑命令，用 grep、sed、tail 缩小输出。
  4. 上限取几道闸里最小的：gpt-6.1-sol 的模型自己最多调到 1.2 万，gpt-5.5 的模型只能往小调；只调大你的配置也不够，两边都要调大。
  5. 旧输出不会被清掉，每次约 1.2 万 token，之后每次请求都重发，直到压缩或新开会话。
