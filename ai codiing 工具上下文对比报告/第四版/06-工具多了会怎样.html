第 6 章

接了 30 个 MCP 工具，gpt-6.1-sol 的请求一字没变：工具改由模型自己去找

2026-11-02 · Codex 源码 76ed3b4 / CLI 0.165.0 · 模型 gpt-6.1-sol、gpt-5.5，思考级别都是 low · 对照 Claude Code 官方文档和 Anthropic 接口文档（都是 2026-11-02 查阅）

实验里给 Codex 接上 3 个 MCP 服务器、共 30 个工具，gpt-6.1-sol 的请求和不接时一字不差，gpt-5.5 的请求多出 1,983 字节，而且这个数不随工具个数变。可是同样 30 个工具，换一个 Codex 不认识的模型名，请求一下多出 12,159 字节。区别在于工具的定义有没有写进请求：前两种情况，Codex 不把定义放进请求，模型要用时自己去找；新的问题也就出在找不到、找错、乱调上。

MCP（Model Context Protocol）是让 agent 接入外部工具的协议：一个 MCP 服务器是一个单独运行的程序，向 agent 提供一组工具，比如查问题单、查数据库。本章的 3 个 MCP 服务器是我写的假服务器（u05_fake_mcp.py），名字和描述照问题单（tracker）、数据库（database）、监控告警（monitor）的样子写，各 10 个工具。模型服务器也是本机的假服务器，它按我写的剧本回话：剧本让它搜什么、调什么，它就回什么，不联网。所以本章能证明「请求里有什么、Codex 把什么还给模型」，测不了「真实模型会怎么选」。字节数是把请求顶层的 tools 字段和 input 里每一条各自转成 JSON 文本后相加（第 2 章的算法），token ≈ 字节 ÷ 4（Codex 的估算）。3

下文常比两个模型。第 2 章讲过，gpt-6.1-sol 和 gpt-5.5 的请求本来就不一样：gpt-6.1-sol 的工具定义放在 input 的第 1 条，gpt-5.5 的放在请求顶层的 tools 字段，系统提示词也是两份。所以两个模型不接 MCP 时，请求大小本来就不同（实验里是 54,848 和 37,002 字节）。本章只比同一个模型接与不接 MCP 的差别。

一、30 个 MCP 工具，请求里一个都没有

最朴素的做法，是把每个工具的定义都写进请求。工具少时没问题。接上几个 MCP 服务器后，这份定义每次请求都要在最前面重发一遍（第 2 章），模型每次还要从里面挑。Anthropic 的文档给了一个量级：GitHub、Slack、Sentry、Grafana、Splunk 五个服务器，光工具定义就约 5.5 万 token；文档还说，可用工具超过 30–50 个之后，Claude 选对工具的能力会下降。1这是官方对 Claude 模型的说法，本章没有测过模型选工具的准确率【未测】。

Codex 的做法是 MCP 工具先不写进请求，等模型找的时候再给。Codex 登记每个 MCP 工具时，从两种方式里选一种：延后（Deferred），定义先不写进请求，模型要用时自己去找；直连（Direct），定义直接写进每一次请求。选哪种，看模型资料里这个模型的 supports_search_tool（支不支持搜索工具）：true 就延后，false 就直连。2

第 4 章讲过，Codex 有两份模型资料：源码自带的模型表，和官方通道登录后从 OpenAI 下载的模型列表。76ed3b4 的模型表里 11 个模型（含 gpt-6.1-sol 和 gpt-5.5）、2026-11-02 下载的列表里 10 个模型，这一项全是 true。两份资料里都没有的模型名，Codex 用一份后备资料，这一项是 false，MCP 工具就直连。什么时候会碰到这种模型名？比如在自定义通道里接别家的模型，config.toml 里写的模型名不在两份资料里【推测：没逐个查别家的模型名】。实验用 --model not-a-real-model 模拟这种情况。2

实验：同样 30 个工具，三种模型名下请求的变化。每一行是同一个剧本跑两次，一次不接 MCP，一次接 3 个服务器，比较两次的请求大小。3

表里的「资源工具」是 Codex 自带的 3 个工具（list_mcp_resources、list_mcp_resource_templates、read_mcp_resource），让模型列出和读取 MCP 服务器提供的资源，比如文件、文档。只要配了 MCP 服务器，gpt-5.5 和直连时的请求里就有这 3 个，和服务器有几个工具无关。所以 gpt-5.5 多出的 1,983 字节是固定的；只有直连时，请求才随工具个数增长。tool_search 是 gpt-5.5 找工具用的搜索工具，第二节讲。3

动手算：接多少个工具，请求涨多少

选一种模型名，拖「接几个工具」和「平均一个多大」。前两种是延后：多出的字节与工具个数无关（实验只验证过 30 个）。直连按「固定 1,943 字节 + 个数 × 平均大小」算，实验里 30 个（平均 340 字节）和 40 个（平均 589 字节，第五节）都对得上。

回答问题 1

接 3 个 MCP 服务器、共 30 个工具，请求里会多出这 30 个定义吗？gpt-6.1-sol 和 gpt-5.5 一样吗？

不会多出这 30 个定义。gpt-6.1-sol 的请求一字不变；gpt-5.5 多出 1,983 字节，是 3 个资源工具和搜索工具说明里的服务器名，不随工具个数增长。只有模型名不在 Codex 的两份模型资料里时，Codex 才把定义直接写进请求：30 个工具多出 12,159 字节，工具越多，请求越大。

二、请求里没有定义，模型靠什么找到工具

两个模型用两种办法找工具，但都要模型自己先多走一步。差别来自模型资料里的另一项 tool_mode（工具怎么调用）。gpt-6.1-sol 是 code_mode_only：第 3 章讲过，它不直接调用工具，而是写一段 JavaScript 交给 exec 工具运行，由这段脚本去调用别的工具。gpt-5.5 这一项是空的：每个工具在请求顶层的 tools 里单独列出，模型直接调用。4

gpt-5.5：调用 tool_search，搜到的定义追加在历史末尾

gpt-5.5 请求顶层的 tools 里有一个 tool_search，参数是搜索词 query 和最多返回几个 limit（缺省 8 个）。它的说明里列出能搜哪些「来源」：3 个 MCP 服务器 database、monitor、tracker，还有 Codex 自带的子代理工具（Codex 自己的一部分工具也是延后的）。模型调用 tool_search，Codex 在所有延后的工具里搜索，把搜到的工具的完整定义作为一条 tool_search_output 追加进历史。模型看到定义，才知道有这个工具、参数怎么填，再去调用 mcp__tracker.list_issues 这样的名字。5

实验里，剧本让假服务器搜 list open issues：返回 8 个工具，这一条 tool_search_output 3,210 字节。这次会话的 3 次请求里，顶层 tools 始终是 11,397 字节，没变，新内容只追加在末尾，所以请求的开头不变，第 5 章说的缓存照样接得上。5

gpt-6.1-sol：在 exec 的脚本里过滤 ALL_TOOLS

gpt-6.1-sol 的请求里没有 tool_search。exec 工具的说明里有这么一段：「有些延后的嵌套工具可能没写在本说明里。它们仍可从全局 tools 对象取用，并列在 ALL_TOOLS 里；要找一个，按 name 和 description 过滤 ALL_TOOLS。」（译自说明原文；接不接 MCP，这段都一样。）也就是说，脚本里能拿到一个叫 ALL_TOOLS 的列表，每项是一个工具的名字和描述；模型自己写代码在里面挑。6

实验里假服务器扮演模型，分两步发了两段脚本：6

  1. 先列出 ALL_TOOLS 里有几项、有哪些 MCP 工具名。结果是 41 项：30 个 MCP 工具，加 11 个 Codex 自带的工具（exec_command、apply_patch 等）。这一步的输出进历史，1,196 字节。
  2. 再按 issue 过滤，并调用其中一个： 
    const hits = ALL_TOOLS.filter(t => /issue/i.test(t.name + ' ' + t.description));
text(JSON.stringify(hits.map(t => t.name)));          // 打印过滤出的名字
const r = await tools.mcp__tracker__list_issues({state: 'open'});   // 调用其中一个
    过滤出 9 个名字，调用也成功了。这一步的输出进历史，629 字节。

进历史的只有脚本打印出来的部分。脚本要是把整个 ALL_TOOLS 都打印出来，是 18,723 个字符（约 4,700 token），低于第 3 章说的 1 万 token 输出上限，会整份进历史；只打印需要的几个名字，进历史的就少得多。

两种办法的共同代价：多一次往返。往返是指 Codex 发一次请求、模型回一次。不论哪种办法，模型都得先搜（或先写一段过滤脚本），等结果回来，才能发出真正的调用。这是请求里省掉 30 个定义的代价。

回答问题 2

请求里没有这些定义，模型怎么知道有哪些工具、怎么调用？两个模型一样吗？

不一样。gpt-5.5 调用 tool_search，Codex 把搜到的工具的完整定义追加到历史末尾，模型看到定义后再调用。gpt-6.1-sol 没有 tool_search，它在 exec 的脚本里过滤 ALL_TOOLS 这个列表，再在脚本里调用 tools.mcp__服务器__工具名(...)。差别来自模型资料里的 tool_mode。两种办法都要多一次往返。

三、搜索靠词对上：对不上返回空，对上了也可能排错

这一节只讲 gpt-5.5 的 tool_search，搜索由 Codex 来做。gpt-6.1-sol 的过滤代码是模型自己写的，怎么匹配由模型决定（实验里用的是正则表达式），不经过这套搜索。

Codex 的搜索是 BM25，不理解意思，只数词。BM25 是一种老的打分办法：看搜索词里的词在哪个工具的文字里出现、这个词稀不稀有，据此给每个工具打分，不懂同义词。Codex 按英文的规则把文字切成词。每个工具参加打分的文字有：工具全名、服务器名、标题、描述、各参数的名字（参数的说明不算）。打完分，Codex 取分数最高的 limit 个返回。7

动手看：12 次搜索，各返回什么

下面是 gpt-5.5、接 30 个工具时的实验结果：搜索词由剧本发出，搜索是 Codex 真的在做。每条我先写下「想要」的工具，再看它在不在返回里。搜索词是我写的，不是模型写的，所以这 12 条不是命中率，只用来说明搜索怎么工作。8

三种情况各有一例。

  • 词对不上，返回空。问题单工具的描述里写的是 issues，我搜 tickets，没有一个工具命中；搜 CPU usage，也对不上 query_metrics 描述里的「metric」「time series」；用中文搜英文描述的工具，同样为空。这时返回的是一条 160 字节的 tool_search_output，里面的 tools 是空列表，没有报错，也没有提示。模型看到的就是「没有这样的工具」。9
  • 想要的搜到了，但返回的大多不是想要的。list open issues 返回 8 个，想要的 list_issues 在里面，另外 7 个是 list_incidents、list_tables 这类带「list」的。close the bug 还带出了 Codex 自带的 close_agent、resume_agent，因为 Codex 自带的延后工具和 MCP 工具放在同一个搜索范围里。
  • limit 设得小，第一名可能不是想要的。同样搜 list open issues，limit 设成 1，返回的是 monitor.list_incidents；搜 issue、limit 设成 3，返回 add_label、add_comment、assign_issue，没有 list_issues。

动手算：搜索结果留在历史里，要多带多少

搜到的完整定义是追加进历史的，之后每次请求都带着，直到压缩（第 4 章）。实验里一次搜索的结果约「160 字节 + 每个工具约 380 字节」：返回 1 个是 641 字节，3 个是 1,335，7 个是 2,838，8 个是 3,210，都落在这条线附近；再加上模型发出搜索的那条调用，约 170 字节。拖「每次返回几个」「搜了几次」看合计。

回答问题 3

gpt-5.5 的搜索词和工具描述里的词对不上时，模型拿到什么？搜到了，就等于找对了吗？

对不上，模型拿到一个空列表，没有报错也没有提示。搜到了也不等于找对：Codex 按 BM25 的分数取前 limit 个返回，实验里 limit 设成 1 时，排第一的是 list_incidents，不是想要的 list_issues。模型拿到空结果后怎么改写搜索词、会不会放弃，是模型的行为，本章没测【未测】。

四、没搜过、写错、已关掉的工具名

搜索是模型找定义的办法，不是调用前必须过的一关。下面四个实验，都是让假服务器直接回一个工具调用，看 Codex 把什么还给模型：10

模型模型发出的调用Codex 还给模型的写进历史的字节
gpt-5.5mcp__tracker.list_issues：没搜过，名字是对的照常执行，返回工具的结果调用 149 + 结果 252
gpt-5.5同上，但这个 MCP 服务器的配置里没写 default_tools_approval_mode = "approve"「MCP tool call requires approval, but approval policy is never」，没有执行调用 149 + 结果 282
gpt-5.5mcp__tracker.list_tickets：名字写错「unsupported call: mcp__trackerlist_tickets」，没有执行调用 150 + 结果 159
gpt-6.1-solclock.sleep：这个工具已经用 -c features.sleep_tool=false 关掉了「unsupported call: clocksleep」，没有执行调用 136 + 结果 145

第二行要解释一下批准。Codex 缺省要你批准每一次 MCP 工具调用；codex exec 运行时不问你，它的批准策略是 never（从不问），所以直接拒绝。其余实验都在 ~/.codex/config.toml 里这个服务器的一节（如 [mcp_servers.tracker]）写了 default_tools_approval_mode = "approve"，意思是这个服务器的工具不用问、直接批准，调用才能走到底。报错里的名字是命名空间（服务器名或工具组名）和工具名直接拼在一起，中间没有分隔符，这是 Codex 的写法。10

关掉的工具，定义还在请求开头，模型照样调用时 Codex 不执行。第 5 章讲过，sleep 是 Codex 自带的一个工具（属于 clock 组），关掉它之后，请求开头的工具定义逐字不变（还是 25,347 字节，仍然列着 clock[sleep]），只在末尾追加一条 274 字节的说明：「The following namespaces are no longer available. Do not call tools in them unless those tools are declared in a later update: - clock」。这个实验在同一个会话里分两个进程：第 1 个进程里调用 clock.sleep，正常执行；第 2 个进程关掉它，模型不理会那条说明、照样调用，Codex 回「unsupported call」。11代价是白白多一次往返，调用和报错共约 280 字节留在历史里。真实模型会不会遵守那条说明、收到报错后怎么改，要真实模型才能测【未测】。

回答问题 4

模型没搜过就直接调用、写错名字、调用已关掉的工具，Codex 会怎样处理？

名字对，没搜过也能调通（前提是这个调用得到了批准）。名字写错或工具已关掉，Codex 回一句「unsupported call: …」，不执行，调用和报错留在历史里。所以关掉的工具虽然定义还在请求开头，模型照样调用也不会真的执行，只是白白多一次往返。

五、直连时一个工具多大，怎么减少

直连时，请求随工具个数成比例地涨，实验里一个工具 340–589 字节。下面都用两份资料里都没有的模型名（not-a-real-model），让 MCP 工具直连：12

接的 MCP 服务器MCP 工具定义合计（字节）平均一个（字节）
问题单服务器，10 个工具3,592359
3 个服务器，30 个工具10,204340
凑数服务器，40 个工具（每个描述约 300 字节，3 个带说明的参数）23,575589

我写的假工具描述只有一两句、1–3 个参数。真实 MCP 服务器的工具有多大，没拿真实服务器测过【待核实】。Codex 有个配置项 tool_input_schema_max_bytes，写在 MCP 服务器那一节里：源码注释说，一个工具的输入参数定义超过这个字节数，Codex 就把它压缩，缺省 5,000 字节。压缩成什么样，没做实验。13

最直接的办法是只放行用得到的工具。同样写在 ~/.codex/config.toml 里那个 MCP 服务器的一节：

[mcp_servers.tracker]
command = "…"
enabled_tools = ["list_issues", "create_issue"]   # 只登记这两个；另有 disabled_tools，作用相反：列出的不登记

实验里问题单服务器从 10 个工具缩到 2 个，工具定义从 3,592 字节降到 930 字节。13延后时这个办法同样有用：Codex 自带的测试检查过，没登记的工具搜不到。14

对照：Claude Code 缺省延后，可以按服务器改成直连

据官方文档（2026-11-02 查阅），Claude Code 的做法和 Codex 延后的思路一样，但能调的地方更多：15

  • 缺省全部延后。开局只载入工具名和服务器的 instructions（服务器自己写的用途说明），模型要用某个工具时，通过 ToolSearch 工具取它的定义。文档说没有每个服务器最多几个工具的固定上限，实际的上限是窗口。
  • 整体开关是环境变量 ENABLE_TOOL_SEARCH，启动前设，例如 ENABLE_TOOL_SEARCH=auto:5 claude。false 是全部直连；auto 是工具定义合计不到窗口的 10% 时直连；auto:5 把 10% 改成 5%。
  • 单个服务器改成直连：在项目的 .mcp.json 里，那个服务器的条目写 "alwaysLoad": true。
  • 过长的文字会截断：服务器 instructions 和直连工具的描述最多 4,096 字符，经搜索加载的工具描述最多 16,384 字符。

还有一处和 Codex 不同。按文档，Claude Code 的请求里其实仍带着延后工具的完整定义，只是标上 defer_loading，由服务器决定把哪些展开进模型的上下文；Codex 则根本不把延后的定义放进请求。我没抓过 Claude Code 的请求，这一点只有文档【待核实】。16

回答问题 5

工具定义直接写进请求时，一个占多少字节？有什么办法让它少占？Claude Code 缺省怎么做？

实验里平均一个 340–589 字节，用的是描述很短的假工具；真实服务器的工具多大没测【待核实】。最直接的办法是在 config.toml 里用 enabled_tools 只放行要用的工具（10 个缩到 2 个，3,592 字节降到 930 字节）。Claude Code 缺省把 MCP 工具全部延后，靠 ToolSearch 取定义；常用的服务器可以用 alwaysLoad 改成直连。

设计笔记

  • 省的是窗口和每次请求的重发，付的是往返和找不到。工具定义在请求开头，每次都重发；延后之后开头不变，也有利于第 5 章的缓存（实验里 3 次请求顶层 tools 都是 11,397 字节，搜索结果追加在末尾）。但每搜一次，就多一次往返。Anthropic 的文档建议把最常用的 3–5 个工具留作直连，Claude Code 的 alwaysLoad 就是这个用途；Codex 0.165.0 的配置里，我没找到按服务器改成直连的开关，但没有逐项穷尽【待核实】。
  • 「工具越多越容易用错」，目前只有三块证据。一是直连时定义占的字节数（本章实验）；二是官方对 Claude 模型说，工具超过 30–50 个后选择变差（文档，不是本章测的）；三是延后时搜索会漏、会排错（本章实验，搜索词是我写的）。真实对话里模型选错工具的比例，本章没有数据。
  • gpt-6.1-sol 不用 tool_search，改在脚本里过滤，代码没写原因【推测】。一个可能的好处：脚本可以只打印需要的几行，不必像 tool_search_output 那样把完整定义整份追加进历史；代价是模型得自己写对过滤代码。
  • Codex 自带的延后工具和 MCP 工具在同一个搜索范围里。实验里 close the bug 带出了 close_agent、resume_agent。接的工具越多，这类不相干的结果占掉名额的机会越多。
  • 别的做法。有的 agent 先用 BM25 搜工具、再通过一个统一的调用工具去调；有的让模型把工具调用写进一段代码里执行，和 gpt-6.1-sol 的 exec 类似。本机没有其他 agent 的源码，它们具体怎么做没核对【待核实】。

小结

  1. 接 30 个 MCP 工具，gpt-6.1-sol 的请求一字不变，gpt-5.5 多出固定的 1,983 字节；只有模型名不在 Codex 的两份模型资料里才直连，30 个工具多出 12,159 字节。
  2. 请求里没有定义时，gpt-5.5 调用 tool_search，gpt-6.1-sol 在 exec 脚本里过滤 ALL_TOOLS；差别来自模型资料的 tool_mode，两种都多一次往返。
  3. gpt-5.5 的搜索是只数词的 BM25：词对不上返回空列表，没有任何提示；limit 设得小时，第一名也可能不是想要的。
  4. 名字对，没搜过也能调用；名字写错或工具已关掉，Codex 回「unsupported call」，不执行，白白多一次往返。
  5. 直连时一个工具在实验里 340–589 字节；用 enabled_tools 只放行要用的。Claude Code 缺省延后，可以用 alwaysLoad 把单个服务器改成直连。
