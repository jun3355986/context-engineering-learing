第 6 章

接了 30 个 MCP 工具，请求没变大：代价从「装」挪到了「找」

2026-11-02 · Codex 源码 76ed3b4 / CLI 0.165.0 · 模型 gpt-6.1-sol、gpt-5.5，思考级别都是 low · 对照 Claude Code 官方文档和 Anthropic 接口文档（都是 2026-11-02 查阅）

实验里给 Codex 接上 3 个假 MCP 服务器、共 30 个工具：gpt-6.1-sol 的请求和不接时一字不差（工具部分 25,347 字节），gpt-5.5 只多出约 2 KB 固定内容。同样 30 个工具，换成 Codex 模型表里没有的模型名，请求一下多出 12,159 字节。工具没有消失，是从请求里挪到了「模型自己去找」这一步，新的问题出在找不到、找错、乱调上。

MCP（Model Context Protocol）是让 agent 接入外部工具的协议，一个 MCP 服务器提供一组工具。本章实验用本机假服务器和我写的假 MCP 服务器（u05_fake_mcp.py，3 个服务器各 10 个工具，名字和描述是照问题单、数据库、监控告警的样子写的），HTTP 通道，不联网。模型的回答是剧本写死的，所以本章能证明「请求里有什么、工具怎么返回」，测不了「真实模型会怎么选」。字节数口径同第 2 章：顶层 tools 字段和每条 input 条目各自 json.dumps 后相加，token ≈ 字节 ÷ 4（Codex 的本地估算）。

一、30 个 MCP 工具，请求里一个都没有

最朴素的做法，是把每个工具的名字、描述、参数定义都写进请求的工具列表。工具少时没问题。接上几个 MCP 服务器后，这份列表要在每一次请求的最开头重发一遍（第 2 章），模型每次还要从里面挑。Anthropic 的文档给了一个量级：GitHub、Slack、Sentry、Grafana、Splunk 五个服务器，光工具定义就约 5.5 万 token；并且 Claude 选对工具的能力，在可用工具超过 30–50 个之后下降。1这是官方对 Claude 模型的说法，本章没有测过模型选工具的准确率【未测】。

Codex 的做法是 MCP 工具先不放进请求，等模型搜到了再给。依据是模型表（models-manager/models.json）里每个模型的 supports_search_tool：为 true，MCP 工具登记为「延后」（Deferred）；为 false，登记为「直连」（Direct），定义直接写进请求。76ed3b4 的模型表里 11 个模型这一项全是 true，包括 gpt-6.1-sol 和 gpt-5.5。Codex 不认识的模型名，用一份后备资料，这一项是 false。2

实验：同样 30 个工具，三种模型名下请求的变化。每行是同一个剧本跑两次，一次不接 MCP，一次接 3 个服务器。3

模型名不接 MCP接 30 个工具多出多出的是什么
gpt-6.1-sol54,84854,8480工具部分 25,347 字节逐字相同，其余条目也相同
gpt-5.537,00238,985+1,9833 个「资源」工具共 1,943 字节，tool_search 的说明里多列了 3 个服务器名（+34）
模型表里没有的名字（实验用 not-a-real-model）38,59050,749+12,1593 个资源工具 1,943 + 30 个工具定义 10,204（平均 340 字节/个）

资源工具（list_mcp_resources、list_mcp_resource_templates、read_mcp_resource）让模型列出和读取 MCP 服务器提供的资源（文件、文档之类）。只要配了 MCP 服务器，gpt-5.5 和直连的请求里就有它们，和服务器有几个工具无关。3

动手算：接多少个工具，请求涨多少

选一种情形，拖「接几个工具」和「平均一个多大」。延后的两种情形与工具数无关（实验只验证了 30 个）；直连按「固定 1,943 + 个数 × 平均大小」算，实验里 30 个（平均 340 字节）和 40 个（平均 589 字节）都对得上。

不接 MCP 时的请求接了 MCP 多出的部分

回答问题 1

接 3 个 MCP 服务器、共 30 个工具，请求里会多出这 30 个定义吗？gpt-6.1-sol 和 gpt-5.5 一样吗？

不会多出定义。gpt-6.1-sol 的请求一字不变；gpt-5.5 多约 2 KB 固定内容（3 个资源工具 + 服务器名），不随工具数增长。只有模型名不在 Codex 模型表里时才直连，30 个工具多出 12,159 字节，工具越多越大。

二、没有定义，模型靠什么找到工具

两个模型用两种办法，但都是「模型自己发起一步」。差别来自模型表的 tool_mode：gpt-6.1-sol 是 code_mode_only（只给一个 exec 入口，模型写 JavaScript 去调其他工具，第 3 章讲过），gpt-5.5 是空，走独立的函数工具。4

gpt-5.5：调 tool_search，定义追加在历史末尾

请求的顶层 tools 里有一个 tool_search，参数是 query 和 limit（缺省返回 8 个）。它的说明列出有哪些「来源」（Codex 自带的子代理工具，加上 database、monitor、tracker 三个服务器）。模型调它，Codex 在所有延后工具里做搜索，把命中的完整定义作为一条 tool_search_output 放进历史；然后模型才能调 mcp__tracker.list_issues。实验里查 list open issues：返回 8 个工具，这一条 3,210 字节；3 次请求里顶层 tools 始终是 11,397 字节，没变，新内容只追加在末尾。5

gpt-6.1-sol：在 exec 的脚本里过滤 ALL_TOOLS

它的请求里没有 tool_search。exec 的说明里有这么一段：「有些延后的嵌套工具可能没写在本说明里。它们仍可从全局 tools 对象取用，并列在 ALL_TOOLS 里；要找一个，按 name 和 description 过滤 ALL_TOOLS。」（译自说明原文，接不接 MCP 这段都一样。）实验里让脚本这样写：6

const hits = ALL_TOOLS.filter(t => /issue/i.test(t.name + ' ' + t.description));
text(JSON.stringify(hits.map(t => t.name)));
const r = await tools.mcp__tracker__list_issues({state: 'open'});

ALL_TOOLS 有 41 项（30 个 MCP 工具 + 11 个 Codex 自带的嵌套工具），过滤出 9 个名字，调用也成功了。进入历史的只有脚本打印的部分：第一次 1,196 字节，第二次 629 字节。模型要是把整个 ALL_TOOLS 打印出来，是 18,723 个字符（约 4,700 token），而且 exec 的输出有上限（第 3 章）。

两种办法的共同代价：多一次往返。模型得先搜（或先写一段过滤脚本），结果回来，才能发出真正的调用。这是请求里省下 30 个定义的代价。

core/src/mcp_tool_exposure.rs 第 84–88 行，和 core/src/tools/spec_plan.rs 第 265–272 行（节选，注释是我加的）。2

回答问题 2

请求里没有这些定义，模型怎么知道有哪些工具、怎么调用？两个模型一样吗？

不一样。gpt-5.5 调 tool_search，Codex 把命中的完整定义追加到历史末尾，模型再调。gpt-6.1-sol 没有 tool_search，在 exec 的脚本里过滤 ALL_TOOLS，再直接调 tools.mcp__服务器__工具名(...)。差别来自模型表的 tool_mode。两种都要多一次往返。

三、搜索靠词对上：对不上返回空，对上了也可能排错

Codex 的搜索是 BM25，不理解意思，只数词。BM25 是一种老办法：查询里的词在哪个工具的文字里出现、这个词稀不稀有，据此打分，不懂同义词。Codex 用英文分词。每个工具参与打分的文字是：工具全名、服务器名、标题、描述、各参数的名字（不含参数的说明）。7

动手看：我搜了 12 次，各返回什么

下面是 gpt-5.5、30 个工具下的真实结果（剧本让它查这些词，Codex 真的在搜）。每条我先写下「想要」的工具，再看它在不在返回里。查询词是我写的，不是模型写的，这 12 条不是命中率，只说明机制。8

三种情况各有一例。

  • 词对不上，返回空。描述里写的是 issues，我搜 tickets，没有一个工具命中；CPU usage 对不上 query_metrics 的「metric」「time series」；中文查询对上英文描述，同样为空。返回是一条 160 字节的 tool_search_output，tools 是空数组，没有报错，也没有提示。模型看到的就是「没有」。9
  • 命中了，但名额被别的占了。list open issues 返回 8 个，其中只有 list_issues 是想要的，另外 7 个是 list_incidents、list_tables 这类带「list」的。close the bug 还带出 Codex 自带的 close_agent、resume_agent，因为内置的延后工具和 MCP 工具共用一个索引。
  • 名额少时排错。同样查 list open issues，limit 设成 1，返回的是 monitor.list_incidents；查 issue、limit 设成 3，返回 add_label、add_comment、assign_issue，没有 list_issues。

动手算：搜索结果留在历史里，要多背多少

搜到的完整定义是追加进历史的，之后每次请求都带着（直到压缩，第 4 章）。实验里一次搜索的结果约 160 字节 + 每个工具约 380 字节（1 个 641、3 个 1,335、7 个 2,838、8 个 3,210，都落在这条线附近），再加上搜索调用本身约 170 字节。拖「每次返回几个」「搜几次」。

回答问题 3

搜索词和工具描述对不上时，模型拿到什么？搜到了，就等于选对了吗？

对不上就拿到一个空数组，没有报错也没有提示。搜到也不等于选对：返回按 BM25 分数取前 limit 个，实验里 limit 为 1 时排第一的是 list_incidents 而不是 list_issues。模型之后怎么改写查询、会不会放弃，是模型的行为，本章没测【未测】。

四、没搜过、写错、被关掉的名字

搜索是找定义的办法，不是调用的门槛。三个实验都是让假服务器直接回一个工具调用，看 Codex 把什么还给模型：10

模型模型写出的调用还给模型的多进历史的
gpt-5.5mcp__tracker.list_issues，没搜过，名字是对的照常执行，返回工具的内容调用 149 + 输出 252 字节
gpt-5.5同上，但 MCP 服务器没配 default_tools_approval_mode = "approve"「MCP tool call requires approval, but approval policy is never」调用 149 + 输出 282 字节
gpt-5.5mcp__tracker.list_tickets，名字写错「unsupported call: mcp__trackerlist_tickets」调用 150 + 输出 159 字节
gpt-6.1-sol，用 -c features.sleep_tool=false 关掉了 clock.sleepclock.sleep「unsupported call: clocksleep」，没有执行调用 136 + 输出 145 字节

第二行是 MCP 工具默认要用户批准（codex exec 里批准策略是 never，就直接拒绝）；其余实验都在服务器配置里写了 default_tools_approval_mode = "approve"，让调用能走到底。报错里的名字是命名空间和工具名直接拼在一起，没有分隔符，这是 Codex 的写法。10

第 5 章的问题有答案了：关掉工具，开头的定义还在，调它不会真的执行。关掉 sleep_tool 之后，请求开头的工具定义逐字不变（还是 25,347 字节，仍然列着 clock[sleep]），只在末尾追加一条 274 字节的 developer 消息：「The following namespaces are no longer available. Do not call tools in them unless those tools are declared in a later update: - clock」。模型要是不理会，照调 clock.sleep，Codex 回「unsupported call」。11代价是浪费一次往返，加上调用和报错共约 280 字节留在历史里。模型会不会遵守那条说明、收到报错后怎么改，要真实模型才能测【未测】。

回答问题 4

没搜过就直接调、写错名字、调已关掉的工具，会发生什么？关掉工具后定义还在开头，会不会误用？

名字对，没搜过也能调通（过批准那一关的话）；名字写错或工具已关，Codex 回一句「unsupported call: …」，不执行，调用和报错留在历史里。所以关掉工具后「误用」不会产生真实调用，只会浪费一次往返。

五、直连时一个工具多大，怎么压

直连时请求随工具数线性涨，实验里一个工具 340–589 字节。模型名不在 Codex 模型表里（自建通道常见这种情况【推测】），MCP 工具直接写进请求。12

配置（模型表里没有的名字）MCP 工具部分平均一个
问题单服务器，10 个工具3,592 字节359
3 个服务器，30 个工具10,204 字节340
凑数服务器，40 个工具（描述约 300 字节，3 个带说明的参数）23,575 字节589

我写的假工具描述只有一两句、1–3 个参数。真实 MCP 服务器的工具有多大，没拿真实服务器测过【待核实】。Codex 对每个工具的输入定义有个压缩阈值，缺省 5,000 字节，配置项是 tool_input_schema_max_bytes（源码注释，没做实验）。13

最直接的办法是只放行用得到的工具。写在 ~/.codex/config.toml 里那个 MCP 服务器的一节：

[mcp_servers.tracker]
command = "…"
enabled_tools = ["list_issues", "create_issue"]   # 只注册这两个；另有 disabled_tools 是反过来排除

实验里问题单服务器从 10 个工具缩到 2 个，工具部分 3,592 → 930 字节。13延后模式下同样有用：自带测试检查了被禁用的工具搜不到。14

对照：Claude Code 默认延后，并且能按服务器豁免

Claude Code 默认把所有 MCP 工具延后，开局只载入工具名和服务器的 instructions（服务器自述用途的文字），模型要用时通过 ToolSearch 取定义；官方文档说没有每服务器工具数的固定上限，实际上限是上下文窗口。启动前设环境变量 ENABLE_TOOL_SEARCH（例如 ENABLE_TOOL_SEARCH=auto:5 claude）：false 是全部直连，auto 是工具定义合计低于窗口 10% 时直连，auto:5 是把 10% 改成 5%。在项目 .mcp.json 里那个服务器的条目写 "alwaysLoad": true，这个服务器的工具始终直连。过长的文字会被截断：服务器 instructions 和直连工具的描述 4,096 字符，经搜索加载的工具描述 16,384 字符。15按文档，Claude Code 的请求里仍带着这些工具的完整定义，只是标了 defer_loading，由服务端决定哪些展开进上下文；这和 Codex 根本不往请求里放不同，我没抓过 Claude Code 的请求【待核实】。16

回答问题 5

工具定义直接写进请求，一个占多少字节？怎么压？Claude Code 默认怎么做？

实验里平均一个 340–589 字节，真实服务器可能更大。用 enabled_tools 只放行要用的（10 个缩到 2 个，3,592 → 930 字节）。Claude Code 默认延后，靠 ToolSearch 取定义，可用 alwaysLoad 把常用服务器豁免成直连。

设计笔记

  • 省的是窗口和每次请求的重发，付的是往返和找不到。工具定义在请求开头，每次重发；延后之后开头不变，也利于第 5 章的缓存（实验里 3 次请求顶层 tools 都是 11,397 字节，搜索结果追加在末尾）。但每多一步搜索，就多一次请求。Anthropic 的文档建议把最常用的 3–5 个工具留作直连，Claude Code 的 alwaysLoad 就是这个用途；Codex 0.165.0 的配置里没找到逐服务器的等价开关，搜索不穷尽【待核实】。
  • 「越多越容易用错」目前只有三块证据。一是直连时定义占的字节数（本章实验）；二是官方对 Claude 模型说 30–50 个工具后选择变差（文档，非本章测量）；三是延后时检索会漏、会排错（本章实验，查询词是我写的）。模型在真实对话里选错的比例，本章没有数据。
  • gpt-6.1-sol 不用 tool_search，改在脚本里过滤，原因代码没写【推测】。脚本过滤可以只打印需要的几行，不必像 tool_search_output 那样把完整定义整份塞回历史；代价是模型得自己写对过滤代码。
  • 内置延后工具和 MCP 工具共用一个搜索索引。实验里 close the bug 带出了 close_agent、resume_agent。接的工具越多，这类串味的机会越多。
  • 别的做法。第三版资料提到 Grok Build 先 BM25 检索再用 use_tool 调用、opencode v2 让模型把调用写进 execute 的代码里；本机没有这两个 agent 的源码，没核对【待核实】。

小结

  1. 接 30 个 MCP 工具，gpt-6.1-sol 的请求不变，gpt-5.5 多约 2 KB 固定内容；只有模型名不在 Codex 模型表里才直连，30 个工具多出 12,159 字节。
  2. 没有定义时，gpt-5.5 调 tool_search，gpt-6.1-sol 在 exec 脚本里过滤 ALL_TOOLS；差别来自模型表的 tool_mode，两种都多一次往返。
  3. 搜索是数词的 BM25：词对不上返回空数组，没有任何提示；名额少时第一名也可能不是想要的。
  4. 名字对，没搜过也能调；名字错或已关掉的工具，Codex 回「unsupported call」，不执行，浪费一次往返。
  5. 直连时一个工具实验里 340–589 字节；用 enabled_tools 只放行要用的。Claude Code 默认延后，可用 alwaysLoad 豁免。
