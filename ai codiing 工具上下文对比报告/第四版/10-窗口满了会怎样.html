实验里 gpt-6.1-sol 的会话已经用了约 19.4 万 token，我再发一条约 12 万 token 的日志，服务器拒绝了这次请求。Codex 回了一句「Codex ran out of room in the model's context window」，没有压缩，也没有重发；接着发的两句短话各被拒一次。直到手动压缩：压缩请求自己被拒 7 次，每次删掉历史里最旧的一条，第 8 次才装得下。

窗口：一次请求最多能装的 token 数。压缩：把前面的对话写成摘要换掉原文（第 4 章）。token 仍是 Codex 的估算：UTF-8 字节数 ÷ 4 向上取整（第 2 章）。实验用本机假服务器：它自己带一个窗口，把请求里各条的字节数 ÷ 4 相加，超过就拒绝；连的是自定义通道，所以压缩走第 4 章讲的本地压缩。真实服务器按真实分词计数，拒绝的时机会和 Codex 的估算有出入；OpenAI 官方通道的远端压缩只读了源码，没做实验。脚本和输出在 自学单元/U09-实验/。1

一、「满」有几条线

Codex 里和「满」有关的数有四个，下表是 gpt-6.1-sol 用源码自带表时的值（第 4 章：官方登录时模型目录里窗口是 500,000，算法相同）。2

名字值谁用
窗口272,000模型表里写的上限
有效窗口 = 窗口 × 95%258,400Codex 认为「满」的线；界面剩余百分比以它为基准
压缩线 = 窗口 × 90%244,800自动压缩的触发线（第 4 章）
单条消息上限1,048,576 字符输入框和 codex app-server 在发出前检查，超了不发3

单条消息的上限按字符算，不按 token 算。一个汉字占 3 字节，Codex 估算 ÷ 4，所以满上限的汉字消息估算约 78.6 万 token（1,048,576 × 3 ÷ 4），是窗口的近三倍；同样长度的纯英文约 26.2 万。所以「一条消息就超窗」是可能发生的，实验 A 就是 40 万个汉字。

输入框下面的「X% left」用的是上一次请求的用量：(有效窗口 − 用量) ÷ (有效窗口 − 12,000)，12,000 是写死的、当作固定开头的基线。用量走到压缩线 244,800 时显示约 6%（按源码算，没在终端界面里看过）。4

二、请求被拒：不重发，话留在历史里

最朴素的做法是被拒了就压缩、再发一次。Codex 的主请求没有这一步：服务器在流里发来一条 response.failed（意思是「这次请求失败了」），错误码是 context_length_exceeded，Codex 把它记成「窗口超限」，标记会话已满，这一轮以失败收场。实验 A、B 里这一轮都只有 1 次请求。你看到的是这句话：

Codex ran out of room in the model's context window. Start a new thread or clear earlier history before retrying.

app-server 推送的这一轮状态是 failed，错误信息 contextWindowExceeded。5

被拒的话已经写进历史。实验 B 里，被拒的那次请求有 11 条；之后每发一句短话，下一次请求就多一条：12、13、14。那条 12 万 token 的日志一直在里面，每次都被一起发出去。6

下一句开头压不压缩，要看一个算式。「标记已满」的做法是把「上次用量」（第 4 章：上一次服务器报的数）改成：

上次用量 = max(有效窗口 − 会话累计用量, 0)

会话累计用量是此前每次请求服务器报的 total_tokens 加起来，每次请求都把整段历史重新算一遍。实验 A 里累计 147,534，上次用量记成 258,400 − 147,534 = 110,866；实验 B 里发了两次请求累计就是 297,537，已经超过 258,400，上次用量记成 0。7下一轮开头，Codex 拿「上次用量 + 之后新增条目的估算」（也就是被拒的那条消息）和压缩线 244,800 比：A 是 110,866 + 约 30 万，开头先压缩；B 是 0 + 约 12 万，不压缩，下一句直接发出去，整段历史没变小，于是再被拒一次。8

长会话里累计早就超过 258,400，所以按这条公式推，被拒之后「标记已满」常常等于没标；只有被拒的那条消息自己的估算就到了 244,800 以上，下一轮才会自动压缩【按公式推，只有 A、B 两组做过实验】。重启也没用：实验 B 里新开一个进程 resume 接着旧线程，第 6 句话照样被拒，因为那条日志在存档里。9

回答问题 1

服务器拒绝这次请求后，Codex 会自动压缩再重发吗？你接着发的下一句话会怎样？

不会。主请求被拒就直接报错，这一轮只发了 1 次请求，没有压缩也没有重发；被拒的那条消息留在历史里。下一句开头压不压缩，看「窗口 × 95% − 会话累计用量」这个算式：实验 A 压缩，实验 B 不压缩，下一句原样发出去又被拒一次。

三、压缩请求也被拒：从最旧的一条删起

压缩请求是整段历史加一段提示词（第 4 章），历史超窗，压缩请求也超窗。本地压缩的做法是：被拒就删掉历史最前面的一条（和它配对的工具调用与输出一起删），重新计重试次数，再发；删到只剩一条还被拒，才标记已满并报错。注释写的理由是「从头删，保住按前缀匹配的缓存，同时让最近的消息完整」。10

看源码：被拒就删最旧的一条再试

core/src/compact.rs 第 359–371 行，节选，注释是我加的。10

Err(e) if matches!(e.details(), CodexErrorDetails::ContextWindowExceeded) => {
    if turn_input_len > 1 {                 // 压缩请求里不止一条
        // 注释原文：从头删，保住前缀缓存，保住最近的消息
        error!("Context window exceeded while compacting; removing oldest history item. Error: {e}");
        history.remove_first_item();         // 删最旧的一条（配对的调用/输出一起删）
        retries = 0;                         // 重试次数清零
        continue;                            // 再发一次
    }
    sess.set_total_tokens_full(turn_context.as_ref()).await;  // 只剩一条：标记已满
    return Err(e);
}

第几次请求：
Codex 放的固定开头你的话模型回复压缩提示词

删的顺序是：先 Codex 自己放的，后才是你的话。历史最前面是工具定义（25,347 字节），最先被删；第二次删的是历史里的系统提示词，可压缩请求发现历史里没有系统提示词会补回去，所以第 2 次和第 3 次请求逐字相同，白发了一次；然后是技能目录、两条子代理说明、AGENTS.md；到第 7 次删完这些，请求还是被拒，才轮到你的第 1 句话（36 万字节），这一删就装得下了。13

摘要是在删剩下的东西上写的。第 8 次请求里没有第 1 句话，第 1 句里的「不要改数据库 schema」摘要看不到。这次摘要是假服务器写死的，真实模型会写成什么测不出来，但它只能转述它看到的。压缩完成后，新历史按第 4 章的规则留你亲手发的消息：从新到旧、预算 2 万 token，那条日志被截成 80,180 字节（头尾各一半），第 4、5 句留下，第 1、2 句不在。压缩后的下一次请求是 33,996 token。所以那条规则在摘要里没有，在留下的原话里也没有。14

更极端的情况是实验 A。单条消息就比窗口大，压缩请求被拒了 11 次，每次删一条，连日志本身也删掉，第 12 次请求里只剩系统提示词和压缩提示词两条，摘要什么对话都没看到。之后日志仍以截短的形式（80,234 字节）留在历史里。

官方通道不是这一套。源码里「删最旧一条」只出现在本地压缩这一处。官方通道的远端压缩（第 4 章）在发出前，把历史里的工具输出从新到旧换成一句提示，直到估算装得下；没有工具输出可换了，就原样发。只读了源码，没做实验。15

回答问题 2

压缩请求自己也被拒，Codex 怎么办？删的是哪些？摘要里还有你第 1 句里那条规则吗？

被拒一次就删历史最前面的一条再发一次，直到装得下：先删 Codex 自己放的工具定义、技能目录、子代理说明、AGENTS.md，才轮到你最早的话（实验 B 删到第 1 句，共 7 次被拒）。摘要只能依据删剩下的内容写，第 1 句里的规则不在其中；压缩后留下的原话也只有最近约 2 万 token，第 1 句同样不在。

四、服务器怎么报，Codex 才认

Codex 只认一种报法：流里的 response.failed 事件，错误码是 context_length_exceeded。HTTP 400 的响应体里即使写着同一个错误码，也会被当成普通的无效请求，原样把服务器的正文显示给你。Codex 自带的单元测试用的是流里的格式；真实 OpenAI 服务实际怎么报，我没有抓到，【待核实】。16

回答问题 3

你连的服务在超窗时回的是 HTTP 400。Codex 还会照上面的办法处理吗？

不会。Codex 只认流里 response.failed 加 context_length_exceeded 这一种。HTTP 400 被当成普通错误：主请求报服务器的原文，下一句开头的压缩请求原样重发 6 次后失败，历史不会变小，之后每句话都重复一遍。

五、固定部分就占满窗口：每一步都压

前面都假设压缩能把历史压下来。如果压缩线以下的空间连固定部分都装不下，压缩就压不动，而且每一步都会再压一次。实验 D 在 ~/.codex/config.toml 里写：

model_context_window = 14000

这行告诉 Codex 这个模型的窗口只有 14,000 token（自建模型窗口小时要这样配）。于是有效窗口 13,300，压缩线 12,600，而 gpt-6.1-sol 一句话的请求固定部分就是 1.3 万多 token（第 2 章）。服务器这边不拒绝，只看 Codex 自己怎么做。第 1 轮假服务器让模型连调 5 次工具（脚本只让 JS 输出一个 ok，不执行命令）。18

动手看：模型调了 k 次工具，发了多少

两组各取同一次实验里前面的请求；不改窗口的对照组不压缩，小窗口组每次调完工具都先压缩。

5 步下来，对照组 6 次请求，估算输入合计 83,616 token；小窗口组 11 次请求（6 次正常、5 次压缩），合计 152,090 token，多 82%。压缩没有用：压缩只能换掉对话，动不了固定部分（第 4 章），所以压完的请求仍约 1.38 万 token，高于压缩线，下一步又压。第 2 轮开头也先压了一次。

这条路上没有刹车。源码在这一步留的注释是「只要压缩能把用量压到远低于线，就不用担心死循环」；我在 core/src 里搜了「连续」「次数」之类的计数，没找到（搜索，未穷尽）。所以模型接着干多少步，就压多少次，真实模型一轮几十步的话，就是几十次压缩【按这条规则推，没用真实模型试】。19

现实里会碰到：固定部分是第 2 章的 1.3 万加 AGENTS.md（最多 32,768 字节，约 8,192 token）再加第 6 章里直连的 MCP 工具。按规则算，窗口 32,768 token 的自建模型，压缩线是 29,491，固定部分加起来约 2.2 万，离线只剩约 7,900。

回答问题 4

窗口很小，固定部分就快占满，模型每调一次工具要接着干的时候，Codex 会一直压下去吗？

会。模型每要接着干一步，用量都在线上，Codex 就压一次；压缩动不了固定部分，压完仍在线上。实验 D 里 5 次工具调用压了 5 次，输入合计比对照组多 82%。代码里没有连续压缩的次数上限。

对照：Claude Code 把「压不动」分成几种，并且会停

据官方文档（code.claude.com/docs/en/errors、troubleshooting，2026-11-02 查阅，页面里最新的版本号是 v2.1.309；只有文档，没抓过请求）：

  • 超窗的提示：终端里是 Context limit reached · /compact or /clear to continue，-p 输出里是 Prompt is too long。22
  • 自动压缩的顺序：先把最旧的几轮写成摘要、留最新的；一整轮都摘要不了时，最后一招是把你最新的一条 prompt 原文留下、之前的全部写成摘要。要带过去的内容没有模型回复、你自己的话又不到约 1,000 token 时跳过，让你 /clear。22
  • 压缩本身失败：显示 Prompt is too long · automatic compaction failed: <原因>；对话只有一轮时显示 this conversation is a single exchange and cannot be compacted。22
  • 压完又被立刻填满：连续几次后报 Autocompact is thrashing，停止重试（文档没写具体次数）。对应本章第五节：Codex 没有这一步。23
  • 请求体另有 32 MB 的限制：压缩也塞不下时，文档让你按两下 Esc 回退，或 /clear。24

文档的版本说明里有一条：v2.1.269 之前，一整轮都摘要不了的会话「每一轮都失败」。这类卡死在 Claude Code 里也出现过。

回答问题 5

撞到窗口以后你能做什么？Claude Code 遇到同样的情况怎么处理？

Codex 里三条：/compact 手动压缩（会按第三节的办法删到装得下）、Esc 两下回退到被拒那句之前（最干净，原话都在）、/new 开新会话。Claude Code 的自动压缩有「保留你最新一条 prompt」的最后一招，压完又立刻填满几次就停下报错，请求体超 32 MB 另有提示；它和 Codex 一样，到头来要靠你 /clear、回退或少贴内容。

设计笔记

  • 主请求被拒不自动压缩重发。代码没写理由。【推测】压缩请求要带整段历史，此时它多半也装不下；在一轮中间重发还可能让已经跑过的工具再跑一次。
  • 「标记已满」用累计总量去减。看起来是想把「已用」补满到窗口，但累计总量每次请求都重复计整段历史，很快超过窗口，补不上。是不是有意的，代码里看不出来【待核实】。
  • 从最旧的一条删。注释给的理由是保住前缀缓存和最近的消息。保最近的消息说得通；保前缀缓存我没对上：删掉最前面的一条，整个前缀都变了，按第 5 章的规则这次请求接不上之前的缓存【待核实：也许指别的缓存，代码没说】。代价是第三节：摘要看不到最早的话，而最早的话常常是规则。
  • 没有熔断。是有意还是没做到，不知道。Claude Code 选了「连续几次就停」，代价是停了以后即使条件变好也不再自动试，要你手动；Codex 选了一直试，代价是第五节的反复压缩。
  • 只认流里的失败事件。【推测】官方服务就是这样报的，Codex 没有给第三方做兼容；代价是自建网关一旦换了报法，自动善后全部失效。

小结

  1. 请求被拒时 Codex 只报错：不压缩、不重发，被拒的话留在历史里；下一句开头压不压缩，看「窗口 × 95% − 会话累计用量」这个算式，长会话里常常不压。
  2. 压缩请求被拒时，本地压缩从最旧的一条逐条删，先 Codex 自己放的固定部分，后才是你的话；摘要在删剩下的内容上写，最早的规则可能不在里面。
  3. Codex 只认流里 response.failed 加 context_length_exceeded；HTTP 400 被当普通错误，原样重发 6 次，历史不变。
  4. 固定部分占满窗口时，模型每接着干一步就压一次，代码里没有次数上限。
  5. 出路：/compact、Esc 两下回退、/new；Claude Code 保留最新一条 prompt、压完又填满几次就停。
