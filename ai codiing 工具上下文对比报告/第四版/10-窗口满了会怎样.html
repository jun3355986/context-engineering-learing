窗口真满了会怎样？为什么有时报错后怎么发都失败，有时手动压缩又会丢掉最早的规则？

2026-11-02 · Codex 源码 76ed3b4 / CLI 0.165.0 · 模型 gpt-6.1-sol，思考级别 low · 本机假服务器实验 · 对照 Claude Code 官方文档（2026-11-02 查阅，页面里最新版本号 v2.1.309）

实验里，一段对话已经用了约 19.4 万 token。我再贴进一条约 12 万 token 的日志，总长度超过窗口上限，服务器拒绝了这次请求。Codex 只回了一句「Codex ran out of room in the model's context window」，既没有自动压缩，也没有重发；接着连发两句短话，每次都被服务器原样拒绝。直到我手动输入 /compact，压缩请求自己又连续被拒 7 次——每次删掉历史里最旧的一条，删到第 8 次才装进窗口。

按直觉，请求撞上窗口上限时，agent 应该自动把历史压缩一下再重发。但在 Codex 里，正常对话请求和压缩请求面对超窗是两套完全不同的处理逻辑：前者直接放弃报错，而且那条惹祸的超长消息还会留在会话历史里；后者才会从头逐条删除旧记录，一路删到装得下为止。为了看清这两套逻辑的边界，本章用本机程序模拟了一个带 272,000 token 窗口上限的服务器（按第 2 章的「UTF-8 字节数 ÷ 4」估算 token，走第 4 章的本地压缩），分别测试了被拒后的自动恢复、手动压缩的删除顺序、不同报错格式的影响，以及小窗口下的反复压缩。1

一、撞窗之前，先分清四条「满」的线

第 4 章讲过，Codex 平时会在请求快满时提前触发自动压缩。既然有自动压缩，为什么还会一头撞上服务器的窗口上限？因为「压缩线」「窗口上限」和「输入框放行上限」各算各的账。下表是 gpt-6.1-sol 使用源码自带模型表时的四条线（若通过官方通道登录并使用下载的模型列表，窗口上限为 500,000 token，其余按相同比例折算）。2

自动压缩是在你刚发的新消息写进历史之前（或上一轮工具调用之间）按已有用量检查的。如果已有对话还没到 244,800 token 的压缩线，而你这一句突然贴进一大段日志，一次跨越了剩下的空间，请求就会不经压缩直接发给服务器，当场触发超窗拒绝。

甚至你只发一句话就能直接撑爆窗口。因为单条输入上限按字符数（约 104.8 万字符）检查，而不是按 token 检查。一个汉字占 3 个 UTF-8 字节，按 Codex「字节数 ÷ 4」估算，一条塞满上限的纯汉字消息约合 78.6 万 token，接近 272,000 窗口上限的三倍。所以在输入框里贴进几十万字的中文日志，客户端会畅通无阻地放行，随后被服务器一把拦下。

终端输入框下方显示的「X% left」（剩余百分比），是用上一次请求服务器报的用量计算的：(有效窗口 − 上次用量) ÷ (有效窗口 − 12,000)，其中 12,000 是源码写死当作固定开销的基线。当用量刚好走到压缩线 244,800 token 时，界面大约显示还剩 6%。4

二、请求被拒：当场报错不重发，且长会话下一句还不压缩

一旦请求超出窗口被服务器拒绝，最符合直觉的补救是「自动压缩一次，再把刚才那句话重发一遍」。但 Codex 对正常对话发出的请求（下称「主请求」，区别于专门用来生成摘要的「压缩请求」）没有设计重发步骤。只要服务器在流式响应里发来 response.failed 事件且错误码为 context_length_exceeded，Codex 就把会话标记为「窗口已满」，直接结束这一轮并向你报错：

Codex ran out of room in the model's context window. Start a new thread or clear earlier history before retrying.

更棘手的是，虽然这次请求失败了，你刚发出去的那条超大消息却已经写进了会话历史。在实验里，第 3 轮贴进一条约 12 万 token 的日志被拒后，我接着连发两句很短的话，发给服务器的请求条目数依次从 11 条涨到 12 条、13 条——那条 12 万 token 的日志原封不动地躺在历史里，跟着每一次新请求一遍遍重发。56

一个反直觉的算式缺陷：聊得越久，报错后越不会自动压缩

既然被拒时 Codex 已经给会话打了「窗口已满」的标记，为什么我接着发下一句短话时，它不在新一轮开头自动压缩呢？问题出在「标记已满」时的那行计算公式上。

为了在下一轮开头触发自动压缩，Codex 需要把记录里的「上次请求用量」改大。但源码并不是直接把它设成有效窗口（258,400），而是用有效窗口减去整个会话开启以来的累计总用量：

上次用量 = max(有效窗口 − 会话累计用量, 0)

这里的「会话累计用量」，是此前每一次请求服务器返回的 total_tokens 累加之和。因为每次请求都带着整段历史重发，只要你已经聊了好几轮，累加出来的总和就会远远超过单次窗口的 258,400。一旦累计值超过 258,400，减出来是负数，和 0 取最大值后，「上次用量」反而被清零成了 0！7

到了下一句话开头，Codex 用「上次用量 + 新增消息估算」去和压缩线（244,800）比较。我们用两组实验对照这个结果：

  • 短会话单条撑爆（实验 A）：前两轮各聊了约 4 万 token，两次请求的累计用量只有 147,534（还没超过 258,400），第 3 轮发了一条约 30 万 token 的超大消息被拒。此时「上次用量」被记为 258,400 − 147,534 = 110,866，加上这 30 万 token 远超压缩线，所以第 4 轮一开头就会触发自动压缩。
  • 长会话累加撑爆（实验 B）：前两轮各聊了约 9 万 token，两次请求累加的会话总用量已经达到 297,537（超过了 258,400），第 3 轮再发一条 12 万 token 的日志被拒。此时公式算出的「上次用量」变成了 0！第 4 轮开头拿 0 + 12 万 和 244,800 比较，Codex 误以为窗口还很空，跳过自动压缩直接把整段历史原样发出，于是再撞一次墙。哪怕关掉进程用 resume 恢复会话，那条日志依然在存档里，发新话照样被拒。89

回答问题 1

贴进一条大日志导致请求超出窗口被拒后，Codex 会自动压缩并重发吗？你接着发的下一句话为什么还可能继续被拒？

不会自动重发。主请求被拒后当场报错，且那条大日志会留在会话历史里。至于下一句话开头压不压缩，取决于 max(有效窗口 − 会话累计用量, 0) + 被拒消息大小 是否达到压缩线：在长会话里，累计用量早已超过有效窗口，算出来的基数反而归零；只要被拒的那条消息本身不到 24.48 万 token，下一句就不会触发自动压缩，原样发出后再次被拒。

三、压缩请求也被拒：从最旧的一条删起，连早期规则一起删

既然自动压缩指望不上，我们在实验 B 连续被拒之后手动输入 /compact。但第 4 章讲过，本地压缩发出的是「整段现有历史 + 一段压缩提示词」。既然现有历史已经比窗口大，压缩请求发出去自然也会被服务器拒绝。

这时候，压缩请求专属的退让机制才真正出手：每被服务器拒绝一次，Codex 就删掉当前历史里最前面（最旧）的一条记录，把重试计数清零，再发一次压缩请求；如此循环，直到服务器装得下为止。如果删到只剩最后一条还是装不下，才彻底放弃并报错。10

怪象一：先删工具和系统说明，且系统提示词「删了又补」白发一次

「删历史最前面的一条」听起来像是从你的第 1 句对话删起。但在 gpt-6.1-sol 的请求里，排在历史最前面的并不是你的话，而是 Codex 开局放进去的 6 条固定开头（工具定义、系统提示词、技能目录、两条子代理说明、AGENTS.md）。于是删除顺序变成了先拆 Codex 自己的脚手架，最后才删你的早期对话。

更滑稽的是第 2 次和第 3 次压缩请求：第 1 次被拒后，Codex 删掉了排第一的工具定义（约 2.5 万字节）；第 2 次还是被拒，Codex 接着删掉了排第二的系统提示词（约 2.2 万字节）。然而组装第 3 次压缩请求时，代码检查发现「历史里怎么没有系统提示词？」，于是又用后备字段把同一份系统提示词原封不动地补了回来！结果第 3 次发出去的压缩请求和第 2 次一模一样，白白撞了一次墙，直到第 4 次越过它继续往下删技能目录。1112

怪象二：你最早交代的规则，既进不了摘要，也留不下原话

在实验里，我在第 1 句话开头特意写了一条禁令：「我叫 Drake。规则：不要改数据库 schema。」后面接填充文字凑成约 9 万 token。

等第 8 次压缩请求终于发成功时，第 1 句话已经在第 7 次被拒后删掉了。也就是说，负责写摘要的模型根本没见过你的第 1 句话，自然不可能把那条禁令写进摘要里。不仅如此，压缩完成后按第 4 章规则保留「最近 2 万 token 用户原话」时，是从最新的一句往前留：那条 12 万 token 的日志被截成约 8 万字节塞满预算，最早的第 1、2 句话同样落选。压缩完成后，下一句正常请求的体积降到了 33,996 token，会话成功救活了，但你在第 1 句里立下的规矩也彻底蒸发了。13

如果是实验 A 那种「单条消息就有 30 万 token、自己就比窗口大」的极端情况，压缩请求会被连拒 11 次，把包括那条大日志在内的所有对话记录删得一干二净；到第 12 次成功时，请求里只剩系统提示词和压缩提示词两条，模型对着空气写出一份空摘要，而那条超大日志随后仍会以约 8 万字节的截短形态留在新历史里。13

实验说明与官方远端压缩的差异

本机实验里假服务器返回的摘要是写死的一句话（剧本里恰好带了那条规则文字，仅作占位）；上面「真实模型看不到第 1 句」的结论由第 8 次压缩请求的实际发送内容直接证出。另外，源码中「被拒后逐条删最旧记录」只出现在本地压缩（compact.rs）；OpenAI 官方通道使用的远端压缩在发出前只会把历史里的工具输出从新到旧替换成简短提示，换完还超窗就原样发送。1314

回答问题 2

整段历史已经比窗口还大，手动打 /compact 时连压缩请求自己都被拒，Codex 会按什么顺序删历史？你第 1 句话里交代的规则还能保住吗？

本地压缩每被拒一次，就删掉历史最前面的一条再重发：先依次删掉 Codex 放的工具定义、技能目录、子代理说明和 AGENTS.md（系统提示词删掉后会被自动补回，导致白发一次），接着才从你的第 1 句话往后删。由于第 1 句话在压缩成功前就被删掉了，写摘要的模型看不到它，压缩后按「从新到旧 2 万 token」保留原话也轮不到它，因此只写在第 1 句话里的规则保不住。

四、服务器怎么报超窗，Codex 才认账？

前面讲的「标记已满」和「压缩时删最旧一条」，有一个大前提：Codex 必须认出这次失败是因为「窗口满了」。

源码里的识别条件非常苛刻——只认流式响应（SSE）里的 response.failed 事件，且事件里的 error.code 必须等于 context_length_exceeded。如果你连接的是自建网关、代理或第三方兼容服务，它在超出窗口时没有建立流，而是直接返回一个 HTTP 400 状态码（哪怕响应体 JSON 里写着一模一样的 "code": "context_length_exceeded"），Codex 也会把它当成普通的「无效请求（InvalidRequest）」，原样把 JSON 报错贴在屏幕上。15

实验 C 把假服务器的超窗报错方式改成了直接回 HTTP 400，其余条件与实验 A 完全相同（第 3 轮发 30 万 token 消息）。两相对照，后果截然不同：

比较阶段实验 A：流里发 response.failed实验 C：直接回 HTTP 400
第 3 轮（超窗被拒当轮）发 1 次请求；识别为 contextWindowExceeded，提示「ran out of room」发 1 次请求；归为普通错误（other），原样显示服务器 JSON
第 4 轮（接着发一句短话）自动压缩连发 12 次（前 11 次逐条删旧记录，第 12 次成功），随后正常请求 1 次成功触发压缩但不删任何记录，把同一份 1.58 MB 的请求一字不差连发 6 次，耗时约 6 秒后彻底失败
第 5 轮及重启恢复后每次只发 1 次正常请求，正常对话每说一句话，就再把整段历史原样重发 6 次，全部失败
会话历史变化压成摘要，历史瘦身恢复正常一条没删，每句失败的新话还继续往里垒（条目数 12 → 13 → 14）

为什么实验 C 里每说一句话都要傻乎乎地连发 6 次一模一样的压缩请求？因为 HTTP 400 没有触发「删最旧一条」的分支，而是落进了常规网络错误的重试逻辑（首次发送 + 缺省重试 5 次 stream_max_retries = 5，每次之间还要等待退避）。整段 1.58 MB 的历史一个字节没少，重发 5 次当然每次都继续撞上 HTTP 400。如果你用的自定义服务端是这种报法，第二节和第三节的所有自动善后都会失灵，只能靠第六节的手动回退或新开会话自救。16

Codex 源码自带的单元测试使用的是流式 response.failed 格式；OpenAI 官方线上服务在超窗时实际返回哪一种格式，本文未做抓包验证【待核实】。15

回答问题 3

如果自建网关或第三方服务在超窗时直接返回 HTTP 400 错误，而不是在流里发失败事件，Codex 还能认出这是「窗口满了」吗？

认不出。Codex 只认流式事件里的 response.failed 加 context_length_exceeded。直接返回 HTTP 400 会被当成普通错误：哪怕触发了压缩，被拒后也不会删旧记录，而是把完全相同的超长历史原地重试 5 次（共发 6 次）后报错退出，会话彻底卡死。

五、固定开头就占满压缩线：每调一次工具都白压一次

前面讨论的是「发出去的请求被服务器拒了」。还有一种相反的困境：服务器根本没拒绝，但因为你给模型配的窗口太小，Codex 自己陷入了「每走一步都要先压缩一次」的死循环。

第 4 章讲过，压缩只能把历史里的对话和工具输出换成摘要，动不了每次请求必带的固定开头（工具定义、系统提示词、AGENTS.md 等）。对于 gpt-6.1-sol，光这些固定开头就要占掉约 1.34 万 token（第 2 章）。如果你接了一个窗口较小的本地模型，在 ~/.codex/config.toml 里配了：

model_context_window = 14000

那么有效窗口是 13,300 token，自动压缩线（90%）只有 12,600 token——比 1.34 万的固定开头还低！结果就是：哪怕对话压得只剩固定开头，请求体积（约 1.38 万 token）依然高于 12,600 的压缩线。

实验 D 测试了这种配置：让模型在第 1 轮里连续调用 5 次工具（每次只输出一个 ok），服务器全部正常放行。结果模型每调完一次工具准备接着往下干时，Codex 一查用量「超过 12,600」，就立刻发一次压缩请求；压完一看还是 1.38 万，下一步调完工具又再压一次。17

动手看：模型连续调 k 次工具，小窗口多发了多少请求

拖动滑块改变第 1 轮里模型连续调用工具的次数 k，对比缺省窗口（272,000 token，不触发压缩）与 14,000 小窗口（每步都触发压缩）的请求次数和累计输入 token。

仅仅调用 5 次工具，小窗口组就发了 11 次请求（6 次正常请求夹着 5 次毫无作用的压缩请求），累计输入 token 比对照组多出 82%。而且源码里没有任何连续压缩的熔断上限——那一段代码的注释直接写着「只要压缩能把用量降到远低于阈值，就不用担心死循环」。如果一个真实任务让模型连续调用 30 次工具，它就会在中间白白空转压缩 30 次。18

这并不是只在极端测试里才会碰到的数字。一个 32,768 token 窗口的自建模型，压缩线是 29,491 token；而在 Codex 里，gpt-6.1-sol 的固定开头（13,410 token）加上写满上限的 AGENTS.md（32,768 字节 ≈ 8,192 token）就已经占去 21,602 token，如果再直连十几个 MCP 工具（第 6 章），还没开口说话就会逼近压缩线。

回答问题 4

自建模型窗口设得很小（比如 1.4 万 token），光固定开头就快占满窗口，模型每调一次工具接着往下干时，Codex 会一直徒劳地压缩下去吗？

会。因为压缩削减不了固定开头，压完后的用量仍然高于压缩线。源码没有设置连续压缩次数上限（熔断机制），所以模型在一轮里连续调多少次工具，Codex 就会在每一步之前各插一次无效压缩。实验里 5 次工具调用触发了 5 次压缩，总输入 token 暴涨 82%。

六、撞窗之后的脱困指南，以及 Claude Code 的做法

当你在终端里看到 Codex ran out of room in the model's context window 时，继续直接发消息多半还会失败（第二节）。此时你有三条出路，推荐优先用回退：

脱困办法具体操作实验验证结果代价与适用场景
1. 回退（推荐）确保输入框为空，连按两下 Esc，选中报错那句话并回车撤回（第 8 章）撤回那条 12 万 token 的日志后，下一次请求恢复为 11 条、193,873 token，立刻成功；即使中间做过压缩也能一并撤销19最干净：前两轮原话和第 1 句的规则完好无损。撤回后别再直接贴大日志，改让模型用工具按行读取文件（第 3 章）
2. 手动压缩在输入框里打 /compact 回车压缩请求连发 8 次（前 7 次逐条删旧记录，第 8 次成功），压缩后下一句请求降为 33,996 token11会丢早期上下文：如果超窗很多，压缩过程会删掉最早的几句对话，只写在第 1 句话里的规则会丢失（第三节）
3. 新开会话在输入框里打 /new 回车20源码确认命令存在（未单独跑实验）当前对话全部清空，只剩 AGENTS.md 和跨会话记忆（第 9 章）

对照：Claude Code 怎么防卡死、怎么报「压不动」

查阅 Claude Code 官方文档（errors 与 troubleshooting，2026-11-02，文档内最高版本号 v2.1.309），它在超窗和反复压缩这几步比 Codex 多做了两道保护：

  • 自动压缩保底策略：优先把最旧的几轮写成摘要、保留近期对话；如果连一整轮都摘要不了，最后一招是保留你最新那条 prompt 原文、把之前全部压成摘要；若内容太少没法压，直接提示你用 /clear。单轮对话超窗时会明确报 this conversation is a single exchange and cannot be compacted。21
  • 反复压缩有熔断（防死循环）：如果压缩成功但立刻又被填满，连续发生几次后就会报 Autocompact is thrashing 并停止自动重试，避免出现本章第五节那种无休止的空转压缩。22
  • 区分「token 超窗」与「请求体超 32 MB」：超窗在交互界面报 Context limit reached · /compact or /clear to continue；如果请求体体积超过 32 MB 物理上限（压缩也救不了），则单独提示连按两下 Esc 回退或 /clear。2123

不过文档的更新日志也记录道：在 v2.1.269 之前，Claude Code 遇到「一整轮都摘要不了」的会话时同样会陷入每一轮都失败的卡死状态。可见这类边界坑两家都踩过。

回答问题 5

一旦撞上窗口报错，手头有哪几种脱困办法？各自会丢掉什么？Claude Code 遇到同样情况又怎么处理？

在 Codex 里首选连按两下 Esc 回退到报错那句之前，它能把惹祸的大消息从历史里干净摘除，同时保住早期的原话和规则；次选打 /compact 手动压缩（代价是会从头删掉旧记录，可能丢失第 1 句话里的规则）；最后是打 /new 重开会话。Claude Code 则在自动压缩里加了「只留最新一条 prompt」的兜底，并且遇到「压完又立刻填满」几次后会触发 Autocompact is thrashing 熔断停机。

设计笔记

  • 为什么主请求被拒不自动压缩重发？源码没有写理由。【推测】一来此时整段历史已经超窗，直接发压缩请求多半也会被拒；二来如果在一轮工具调用中途自动重发，可能会导致已经执行过的外部副作用被重复触发，不如把选择权交给用户。
  • 「标记已满」为什么要用有效窗口减去会话累计用量？从函数名 fill_to_context_window 看，作者本意似乎是想把当前用量补足到窗口上限，以便下一轮触发自动压缩；但代码把「单次请求用量」和「跨轮累加的会话总用量」混在了一起，导致长会话里减出负数归零。这很可能是个实现疏漏，源码中看不出有意为之的理由【待核实】。
  • 压缩被拒时「从头删」真的能保住前缀缓存吗？源码注释写的是「从头删，以保住前缀缓存并保留最近的消息」。保留最近的消息完全合理；但按第 5 章的前缀缓存规则，一旦删掉排在第一条的工具定义，整份请求的开头就变了，不可能再接上之前的缓存前缀【待核实：除非服务端另有局部匹配机制，否则这条注释的理由并不成立】。
  • 立规矩别只写在第 1 句话里。无论是第 4 章正常的 2 万 token 原话保留预算，还是本章第三节超窗压缩时的「从头删除」，最早的第 1 句话都是最先被牺牲的对象。需要跨长会话始终生效的硬规则（如「不要改数据库 schema」），应当写进项目的 AGENTS.md——即使它在超窗压缩过程中被删掉，压缩完成后重建新历史时也会被重新插回（第 4 章）。

小结

你遇到的情况Codex 内部会发生什么 / 你该怎么处理
发消息超出窗口被服务器拒绝当场报错，不压缩也不重发；那条大消息会留在历史里。长会话里因累计用量算式归零，下一句开头也不会自动压缩。
超窗后手动执行 /compact压缩请求每被拒一次就删掉历史最前面的一条（先删固定开头，再删你的第 1 句话），直到装得下；只写在第 1 句话里的规则会丢失。
服务端用 HTTP 400 报超窗Codex 认不出这是超窗（只认流里的 response.failed），会把同一份超长压缩请求原样重试 5 次后彻底卡死。
小窗口下固定开头已超压缩线每次工具调用后都会触发一次无效压缩，没有次数熔断上限，导致请求数和 token 消耗成倍增加。
撞窗报错后想继续干活首选在空输入框连按两下 Esc 回退掉那条大消息（保住早期对话和规则），然后让模型改用工具分段读文件。
