第 5 章

重发的历史不用重算：缓存省钱、省等待，不省窗口

2026-11-02 · Codex 源码 76ed3b4 / CLI 0.165.0 · 模型 gpt-6.1-sol，思考级别 low · 价目来自 OpenAI 官方文档，对照 Claude Code 官方文档（都是 2026-11-02 查阅）

每次请求都把整段历史重发一遍（第 3 章）。实验里一个会话连发 5 次请求，每一次都是上一次原样加一截尾巴：从 54,870 字节涨到 56,512 字节，前面一个字节没动。服务器认出这段一模一样的开头，就不必从头再算；按 OpenAI 的价目，gpt-6.1-sol 这部分只收普通输入价的 5%。

token 仍是 Codex 的估算：UTF-8 字节数 ÷ 4，向上取整（见第 2 章）。实验用本机假服务器，分 HTTP 和 WebSocket 两种通道各跑一遍，每轮是一次 codex exec 或 codex exec resume --last，不联网。本章的「价钱」都写成普通输入价（输入 token 没碰缓存时的单价）的倍数，不写美元；用 ChatGPT 账号登录时，缓存命中的部分怎么折算进套餐额度，官方没公开【待核实】。1

一、重发的部分按什么价算

最朴素的做法是每次都从头算。模型读输入时，要为每个 token 算一组中间结果（技术名叫 KV，可以理解成「读到这里为止的笔记」），后面的 token 都要参考前面的笔记。会话里请求一次比一次长，开头那段被算了一遍又一遍。

提示词缓存（prompt caching）是把算好的中间结果存一段时间。下一次请求的开头和存过的一字不差，服务器就直接取出来用，只算新增的尾巴。它存的是计算结果，不是聊天记录：请求里没带的内容，模型照样看不到，缓存不会让它多「记得」什么。2

省下的是钱和等待时间。OpenAI 文档对 gpt-6.1-sol 这类模型（GPT-5.6 及之后）的规定：2

这部分输入按普通输入价的几倍收
没碰缓存的1
从缓存读出来的（gpt-6.1-sol）0.05
这次新写进缓存的，存 30 分钟（默认）1.25
这次新写进缓存的，存 12 小时2.5

每个 token 只按其中一种计价，不叠加。缓存默认就开，不用传参数；开头不到 1,024 token 不缓存。Codex 0.165.0 不传任何缓存参数（源码里没有 prompt_cache_options），所以用的就是默认的 30 分钟。3 文档还说缓存能缩短「开始回答之前处理输入的时间」，但不保证每次都更快。

窗口一点没省。命中缓存的 token 仍在请求里，模型仍要「看」它们。Codex 算窗口占用，用的是服务器报的总数，命中的部分照算，第 4 章的压缩线照样一步步逼近。4

去哪看命中了多少。服务器每次回复都报 cached_tokens，Codex 读进来叫 cached_input_tokens。实验里让假服务器每次报 4,321，三处都看得到：4

  • codex exec --json：最后一行 turn.completed 的 usage，是整个会话累计的数（实验第 1 轮 3 次请求，显示 12,963）。
  • 会话存档 ~/.codex/sessions/ 下的 .jsonl：每次请求一条 token_count，其中 last_token_usage 是这一次的。
  • 交互界面里打 /status：「Token usage」一行是「没命中的输入 + 输出」，不含命中的部分；codex exec 结束时打印的「tokens used」也是这个口径。

回答问题 1

重复发的部分要按全价再算吗？缓存省的是什么？窗口会变小吗？

不用。只要开头和上一次一字不差、缓存没过期（默认 30 分钟），重复的部分从缓存读，gpt-6.1-sol 只收普通输入价的 5%，服务器也不用重算，开始回答前的等待通常更短。代价是新写进缓存的部分按 1.25 倍收。窗口占用不变：命中的 token 仍在请求里，照样算进压缩线。

二、从哪一个字开始接不上

从第一处不同开始，后面全要重算，哪怕没改。每个 token 的中间结果都依赖它前面的全部内容；前面变了，后面那份结果就不是原来那份了。所以一次改动影响多大，看它在哪，不看它改了几个字。2

「开头」不只是文字。OpenAI 文档列的：OpenAI 自己加的说明、developer 消息、工具定义（名字、描述、参数、顺序）、对话历史，还有几个请求设置，比如模型、思考级别（reasoning.effort）、是否允许并行调工具。会话中途把思考级别从 low 换成 high，开头的文字一个没变，缓存也接不上。2

缓存存在每次请求的结尾。不额外指定时，服务器在「最后一条合格消息」末尾存一份。合格的是：用户消息、连着的几条工具结果里的最后一条、开头那组 developer 消息里的最后一条。Codex 的请求总是以你的话或工具输出结尾，所以每次基本整份存下；下一次能接上的，是改动之前最近那一次旧请求的结尾。2

没接上，比不用缓存还贵。接不上的部分要重新写进缓存，按 1.25 倍收。缓存过期也是这样：30 分钟没用到，下一次整份重写。

回答问题 2

只改一个工具、或 AGENTS.md 里的一个字，后面没改的还能用缓存吗？

不能。从改动那条起，后面全部重写，按 1.25 倍收。工具定义和 AGENTS.md 都在请求的最前面，在实验那次请求里，改了它们，14,128 token 整份重写，花费是正常追加时的约 20 倍。好在 Codex 尽量不让这种事发生：项目 AGENTS.md 一个会话只读一次，中途改了文件不会进请求；gpt-6.1-sol 的工具变了也只在末尾追加说明（第三节）。

三、Codex 怎么让开头不变

实验里，每一次请求都是上一次原样加尾巴。3 个进程、5 次请求，逐条比较 input：5

请求发生在条数字节和上一次比
1第 1 轮开始754,870—
2第 1 次工具调用后955,252前 7 条不变，加「工具调用 + 输出」
3第 2 次工具调用后1155,634前 9 条不变，同上
4第 2 轮（新进程 resume）1355,924前 11 条不变，加「回复 + 你的话」
5第 3 轮（新进程，关掉一个工具）1656,512前 13 条不变，加「回复 + 工具变更说明 + 你的话」

除了 input，请求里其他字段五次都一样，包括 prompt_cache_key（下面说）。换了进程也没变，因为续接会话时历史是从存档原样读回来的。

中途的变化都追加在末尾，不改前面。第 2 章说过会话设置是这样，下面几种也是：

  • 关掉一个工具。第 3 轮用 codex exec -c features.sleep_tool=false resume --last "…" 关掉了 clock 组里的 sleep 工具。开头那条 25,347 字节的工具定义原样留着，里面仍有 sleep；末尾多了一条 274 字节的 developer 消息：「The following namespaces are no longer available. Do not call tools in them…: - clock」。模型靠这句知道它不能用了。6
  • 加工具、换模型。Codex 自带测试里的场景说明：换模型时，在末尾追加一条说明、变了的工具定义和替换后的系统提示词，「不改写前缀」；等下次压缩，再把它们并回开头。这套做法叫 incremental_tools（增量工具），只用在把工具定义放进 input 的模型上，比如 gpt-6.1-sol；CLI 0.165.0 默认打开（源码 76ed3b4 里还是「开发中、默认关」）。gpt-5.5 的工具放在请求的顶层 tools 字段，同一个测试的另一组显示：每次带完整的当前工具表，变了就整份换掉，按 OpenAI 文档，这会让缓存从工具定义处断开。7
  • 跨了一天。环境信息那条里有 <current_date>2026-11-02</current_date>。日期变了，Codex 不改那条，而是在末尾追加一条新的环境信息。【读了源码，没实验】8
  • 改项目的 AGENTS.md。一个会话只读一次（第 2 章），中途改了文件，本会话的请求里还是旧版本，开头也就不变。代码没写理由，可能就是为了保住缓存【推测】；Claude Code 的文档对 CLAUDE.md 明确这样解释（见下面对照）。

prompt_cache_key 是给服务器的分组提示。Codex 每次请求都带它，值是会话 id；子代理这类内部会话用「来源:父会话 id」。按 OpenAI 文档，对较早的模型，它帮服务器把相关请求送到同一批机器上，提高命中的机会；对 gpt-6.1-sol 这类新模型，它是可选的，主要用来分开统计缓存用量。两种情况都不保证命中，命中只看开头是否一字不差。9

对照：Claude Code 自己放缓存标记

据官方文档（2026-11-02 查阅），Claude Code 连的是 Anthropic 的接口，要在请求里自己放缓存标记（cache_control，最多 4 个），指明「存到这里」。思路和 Codex 一样是「少变的放前面、新内容加在末尾」，但写得更细：1415

  • 三层：系统提示词和工具定义 → 项目上下文（CLAUDE.md、自动记忆、不带 paths: 的规则）→ 对话。后面一层变了，前面的仍能命中。
  • 存多久：默认 5 分钟；用 Claude 订阅、还在套餐额度内时，主对话请求 1 小时。写入 5 分钟的按 1.25 倍、1 小时的按 2 倍；读按 0.1 倍（Opus 5.5、Sonnet 5.5 是 0.05 倍）。可在设置里用 promptCacheTtl 自己选。
  • 会断缓存的操作：换模型；多数模型上改思考强度；开快速模式；工具定义没延后加载时连上或移除 MCP 服务器；压缩；图片攒多了被批量移除；升级 Claude Code。会话中途换模型时，如果缓存还热，它会先问你确认。
  • 不断缓存的：会话中途改 CLAUDE.md（也不生效，等 /clear、/compact 或重启）；技能、计划模式的说明都作为消息追加；/rewind 退回到旧的开头，正好命中旧缓存。
  • 看命中：输入框打 /usage，会话一栏有一行「Prompt cache (main)」，写命中比例、没命中几次、可能的原因（v2.1.251 起）。

回答问题 3

下一次请求的开头和上一次一样吗？关工具、跨天、resume 呢？

一样。实验的 5 次请求，每次都是上一次原样加尾巴，resume 换了进程也一样。中途的变化都追加在末尾：关掉工具是加一条「这些工具不能用了」的说明（gpt-6.1-sol；gpt-5.5 会整份换工具表），跨天是加一条新的环境信息，改项目 AGENTS.md 则本会话根本不读。

四、WebSocket 只发新增的条目

走 HTTP 时，每次请求整份重发。实验里第 1 轮第二次请求的请求体 56,816 字节，其中 99% 是上一次发过的。5

走 WebSocket 时，同一条连接上只发新增的。请求带上 previous_response_id（上一次回复的编号），input 只放上一次之后新增的条目，服务器按编号把前面接上。实验把假服务器的通道配置改成 supports_websockets = true 重跑：10

  • 同一进程里，工具调用后的两次请求各只发 1 条（工具输出，257 字节），整条消息 1,989 字节，HTTP 下是约 5.7 万字节。上一次模型回的工具调用不用再发，服务器那边本来就有。
  • 假服务器按编号拼回完整请求，和 HTTP 下的逐字一样（去掉条目 id 和临时目录名之后）。模型那边收到的上下文没少。11
  • 每个进程连上后先发一条 generate: false 的空请求（预热），只带设置不带内容；第一次真正的请求接在它后面，所以 input 要整份发。resume 是新进程、新连接，同样整份发（57,688 字节）。
  • 连不上时退回 HTTP。第一次跑实验，假服务器的握手回应写错了，Codex 每个进程试了 7 次，之后这个进程的请求全走 HTTP。

只发新增，有条件。Codex 每次先检查：除 input 外的字段（模型、工具、思考设置、prompt_cache_key 等）都没变，并且新的 input 是以「上一次的 input + 上一次的回复」开头的。有一条不满足，就整份重发。这和缓存的条件很像，都要求前面一字不差。10

看源码：前面一字不差，才只发新增的

core/src/client.rs 第 1500–1530 行，节选，注释是我加的。10

fn get_incremental_items(&self, request, last_response) -> Result<Vec<ResponseItem>, _> {
    let previous_request = self.websocket_session.last_request.as_ref()
        .ok_or(NonIncrementalReason::NoPreviousRequest)?;   // 这条连接上没发过：整份发
    // 模型、工具、思考设置等任何一项变了：整份发
    if let Some(reason) = responses_request_properties_mismatch(previous_request, request) {
        return Err(NonIncrementalReason::RequestPropertyChanged { reason });
    }
    // 基准 = 上一次的 input + 上一次服务器回的条目
    let previous_items = previous_request.input.iter().chain(&last_response.items_added);
    let mut current_items = request.input.iter();
    for previous in previous_items {
        let Some(current) = current_items.next() else {
            return Err(NonIncrementalReason::InputShortened { .. });  // 变短了（比如压缩）
        };
        if !response_items_equal_ignoring_internal_metadata(previous, current) {
            return Err(NonIncrementalReason::InputMismatch { .. });   // 中间有一条不同
        }
    }
    Ok(current_items.cloned().collect())   // 剩下的就是新增条目
}

它和缓存是两层东西。只发新增，省的是上传的字节和服务器解析请求的工夫；模型要处理的还是完整的上下文。缓存省的是模型那边的计算。HTTP 下整份重发，照样能命中缓存。走 WebSocket 时，用量和计价会不会因此不同，OpenAI 的缓存文档没提 WebSocket，也没提 previous_response_id【待核实】。2

回答问题 4

WebSocket 只发新增条目，算缓存吗？省的是什么？

不算。它省的是传输：同一条连接上，下一次请求只带上一次回复的编号和新增条目（实验里 1,989 字节对 HTTP 的约 5.7 万字节），服务器把前面接上，模型看到的上下文一条不少。模型那边要不要重算，由缓存决定，和走哪种连接无关。换进程、换设置、历史被改写（比如压缩），都会退回整份发送。

五、压缩一次，缓存重建一次

压缩请求本身能吃到缓存。第 4 章的实验里，本地压缩请求是上一次请求原样加两条（回复 + 压缩提示词），前 13 条一条没动，开头整份接得上。Claude Code 的文档也说，缓存还热时，它的摘要请求从缓存读。1214

压缩之后的第一次请求，大部分要重写。用第 4 章的数据逐条比：压缩后第 0、1 条（工具定义、系统提示词，共 47,495 字节 ≈ 11,874 token）内容和压缩前一样，但条目 id 换了新的；从第 2 条起内容就不同了，因为保留的原话排到了技能目录前面（第 4 章第二节）。id 算不算进匹配，OpenAI 文档没写【待核实】。所以最好的情况，开头约 1.19 万 token 能接上，剩下约 2.2 万 token 按 1.25 倍重写；最坏的情况整份重写。12

划不划算，看压缩前有多大。不压缩，以后每次请求都要从缓存读一遍旧的大开头，每次付它的 5%；压缩了，要多付压缩请求和一次重写，之后每次读的变短。实验那组压完只少了 1,038 token，要发五百多次请求才追平，等于回不了本，它只是用来演示的。按官方压缩线 45 万压到 4 万（压缩后的大小是假设值），第 3 次请求起就比不压便宜（开头接不上时第 4 次）。

回答问题 5

压缩一次多付多少？几次请求后回本？

压缩请求本身能读缓存，多付的主要是压缩后第一次请求：除了开头约 1.19 万 token 的工具定义和系统提示词（id 不算进匹配时），其余按 1.25 倍重写。回本看压缩前有多大：45 万压到 4 万，第 3 次请求起就比不压便宜（开头接不上时第 4 次）；实验里 3.5 万只压掉 1 千，要五百多次请求才追平。压缩主要是为窗口，钱上只有大会话才省。

设计笔记

  • 追加不改写，代价是旧内容留着。关掉的工具，定义还在开头，只靠末尾一句话说明不能用；变化多了，说明散在历史各处，模型得自己把前后对上。压缩时再把它们并回开头（自带测试的场景说明）。会不会因此更容易用错工具，没测过【推测】。
  • 项目 AGENTS.md 一次只读一次：保缓存，也意味着改了不生效。想让新规则马上起作用，只能新开会话。Claude Code 对 CLAUDE.md 是同一个取舍，文档写明了原因；Codex 源码没写【推测】。
  • 缓存没接上，比不用缓存贵 25%。写入按 1.25 倍收，所以「中途换模型、换思考级别」不是免费的。Claude Code 在缓存还热时换模型会先问一句，Codex 没有这个提示（第 4 章说过，Codex 换模型还可能先压一次）。
  • WebSocket 的服务器怎么记得上一次。Codex 的请求都带 store: false（不让服务器保存回复），却还能用 previous_response_id 接上，可能是服务器把上一次的内容留在这条连接的内存里，所以一换连接就得整份重发【推测】。
  • 别的做法。第三版资料提到，有的 agent 自己在请求里放多个缓存标记，把变化快慢不同的部分分层存；Claude Code 的「三层」就是这种。本机没有其他 agent 的源码，没核对【待核实】。

小结

  1. 重发的开头不用按全价再算：接上缓存的部分，gpt-6.1-sol 只收普通输入价的 5%，也少等一会；新写进缓存的按 1.25 倍；窗口占用一点不少。
  2. 缓存从第一处不同开始接不上，后面没改的也要重写；工具定义、AGENTS.md 都在最前面，改了就整份重写。
  3. Codex 一个会话里的请求总是上一次原样加尾巴：关工具、跨天、换模型都追加在末尾，项目 AGENTS.md 中途不重读，resume 也不改开头。
  4. WebSocket 只发新增条目，省的是传输，不是计算；模型看到的上下文不变，换进程或历史被改写就整份重发。
  5. 压缩后大部分要按 1.25 倍重写；压缩前越大越快回本，45 万压到 4 万时第 3 次请求起就省钱。
