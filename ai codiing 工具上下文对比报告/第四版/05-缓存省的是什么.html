第 5 章

重发的历史不用重算：缓存省钱、省等待，不省窗口

2026-11-02 · Codex 源码 76ed3b4 / CLI 0.165.0 · 模型 gpt-6.1-sol，思考级别 low · 价目来自 OpenAI 官方文档，对照 Claude Code 官方文档（都是 2026-11-02 查阅）

第 2 章说过，Codex 每发一次请求，都把整段对话历史从头再发一遍。实验里一个会话连发 5 次请求，请求从 54,870 字节涨到 56,512 字节，而且每一次都是上一次的内容一字不改、末尾再加几条。服务器认出这段和上次一模一样的开头，就不必从头再算；按 OpenAI 的价目，gpt-6.1-sol 的这段开头只收没用缓存时的 5%。

「全价」指输入 token 没用上缓存时的单价。本章的价钱都写成全价的倍数，不写美元；用 ChatGPT 账号登录时，用上缓存的部分怎么折算进套餐额度，官方没公开【待核实】。token 仍是 Codex 的估算：UTF-8 字节数 ÷ 4，向上取整（见第 2 章）。实验在本机起一个假的模型服务器，它只记下收到的请求、按脚本回话，不联网，也不真的缓存。实验分 3 轮，第 1 轮是一次 codex exec，第 2、3 轮各是一次 codex exec resume --last（接着上一个会话聊），所以 3 轮是 3 个进程。1

Codex 把请求发给服务器有两种连接方式。HTTP：每次请求单独发一次，把整份请求发过去。WebSocket：连上以后一直不断开，同一条连接上可以来回收发很多次。用 ChatGPT 账号或 OpenAI API 密钥连 OpenAI 的服务（第 4 章叫「官方通道」）时，Codex 缺省走 WebSocket；连你在配置文件里写的别的服务地址（「自定义通道」）时缺省走 HTTP。实验的假服务器属于自定义通道，两种连接方式各跑了一遍：第一、二、三节用 HTTP 那一遍的数据，第四节讲 WebSocket 哪里不同。

一、重发的部分按什么价算

最朴素的做法是每次都从头算。模型读输入时，要为每个 token 算一组中间结果，后面的 token 都要参考前面所有 token 的中间结果。这组中间结果技术上叫 KV（键和值），可以理解成「读到这里为止的笔记」。会话里的请求一次比一次长，开头那段每次都要重新算：到第 30 次请求，开头的工具定义已经算了 30 遍。

提示词缓存（prompt caching，下文简称缓存）是服务器把算好的中间结果存一段时间。下一次请求的开头和存下的那段一字不差，服务器就直接取出来用，只算后面新增的部分。缓存存的是计算结果，不是聊天记录：请求里没带的内容，模型照样看不到，缓存不会让模型多记得什么。2

缓存省下的是钱和等待时间。先说钱。OpenAI 文档对 GPT-5.6 及之后的模型（gpt-6.1-sol 也在内）这样定价：2

这部分输入按全价的几倍收
没用上缓存的1
从缓存读出来的0.1（gpt-6.1-sol 是 0.05）
这次新写进缓存的，存 30 分钟（缺省）1.25
这次新写进缓存的，存 12 小时2.5

「新写进缓存」是指：这部分是服务器这次新算的，算完存起来留给下一次用。每个 token 只按表里的一种价收：新写进缓存的按 1.25 倍收，不是先收 1 倍、再另收 1.25 倍。所以缓存第一次写入时，比不用缓存多付 25%，要靠后面几次从缓存读回来。

缓存缺省就开，请求里不用带参数。开头不到 1,024 token 不缓存；Codex 的请求光是开头那几条固定内容（工具定义、系统提示词等）就有约 1.37 万 token，总能缓存。想存 12 小时，要在请求里带参数指定；Codex 0.165.0 不带（源码里搜不到 prompt_cache_options 这类参数），所以用的是缺省的 30 分钟。3

再说等待时间。文档说缓存能缩短模型开始回答之前处理输入的时间，但不保证每次都更快。快多少本章没测，假服务器没有真的缓存。

窗口一点没省。用上缓存的 token 仍在请求里，模型仍要「看」它们，只是不用重新算。Codex 算窗口占用，用的是服务器报的这次请求的 token 总数，用上缓存的部分照样算在里面；第 4 章的压缩线照样一步步逼近。4

去哪看用上了多少缓存

服务器每次回复都报一个数 cached_tokens，意思是这次输入里有多少 token 是从缓存读的；Codex 读进来，改名叫 cached_input_tokens。假服务器没有真的缓存，实验让它每次固定报 4,321，看这个数在 Codex 里出现在哪：4

  • 能看到：会话存档。存档是 Codex 写在磁盘上的会话记录（第 3 章），在 ~/.codex/sessions/ 下，每个会话一个 .jsonl 文件。每次请求后有一条 token_count 记录，其中 last_token_usage 是这一次请求的数。
  • 看不到：/status 和「tokens used」。在交互界面的输入框里打 /status，「Token usage」一行算的是「没用上缓存的输入 + 输出」；codex exec 结束时打印的「tokens used」也是这个算法。两处都不含用上缓存的部分。

回答问题 1

一个会话发到第 30 次请求，重复发的部分要按全价再付吗？缓存省的是什么？窗口占用会变小吗？

不用按全价付。只要这次请求的开头和上一次一字不差、缓存没过期（缺省存 30 分钟），重复的部分从缓存读，gpt-6.1-sol 只按全价的 5% 收；服务器也不用重算，开始回答前的等待通常更短。代价是新写进缓存的部分按全价的 1.25 倍收。窗口占用一点不变：用上缓存的 token 仍在请求里，照样算进压缩线。

二、从哪一个字开始接不上

从第一处不同开始，后面的全要重算，哪怕后面一个字没改。第一节说过，每个 token 的中间结果都要参考它前面的全部内容；前面变了一个字，后面每个 token 的中间结果都和存下的那份不一样了。所以一处改动让缓存损失多少，看它在请求里的位置，不看它改了几个字：改在越前面，后面要重算的越多。2

「开头」不只是你看得到的文字。OpenAI 文档把缓存要比较的这段开头叫前缀（prefix），它包括：OpenAI 在服务器端加的说明、developer 消息（第 2 章：Codex 放规则和设置的那几条）、工具定义（名字、描述、参数、顺序）、对话历史，还有几个请求设置，比如模型、思考级别（reasoning.effort）、允不允许一次并行调用几个工具（parallel_tool_calls）。所以会话中途把思考级别从 low 换成 high，请求里的文字一个没变，缓存也接不上。2

服务器在每次请求的末尾存一份缓存。服务器不为每个 token 单独存一份，而是在某个位置存一份「从第一个 token 到这里为止」的中间结果，这个位置叫断点。请求里不指定断点时（Codex 不指定），服务器把断点放在最后一条合格的消息末尾。合格的消息有三种：你说的话；连着几条工具结果里的最后一条；开头那组 developer 消息里的最后一条。Codex 的请求总是以你的话或工具输出结尾，所以每次请求的断点基本就在请求末尾，整份请求都存了下来。2

下一次请求能接上的，是改动之前最近的那个断点。拿实验的 5 次请求举例：假如第 5 次请求改了第 2 次工具输出（第 11 条）。第 3 次请求的断点在第 11 条末尾，那份缓存里已经算进了旧的第 11 条，用不上；第 2 次请求的断点在第 9 条末尾，在改动之前，所以前 9 条能从缓存读，第 10 条起全部重算。这是按文档的规则推的，没有用真实服务验证【推测】。

没接上，比不用缓存还贵。接不上的部分要重新算、重新写进缓存，按全价的 1.25 倍收。缓存过期也是这样：30 分钟内没有请求用到它，下一次请求就要整份按 1.25 倍重写。

回答问题 2

只改了一个工具的定义，或者 AGENTS.md 里的一个字，后面没改的内容还能用缓存吗？

不能。从改动的那一条起，后面全部重写，按全价的 1.25 倍收。工具定义和 AGENTS.md 都排在请求的最前面：在实验的第 5 次请求里，改了它们，14,128 token 要整份重写，这次请求的花费是只在末尾追加时的约 20 倍。好在 Codex 尽量不改前面：AGENTS.md 改了、gpt-6.1-sol 的工具变了，Codex 都是在末尾追加，不改开头那份（第三节）。

三、Codex 怎么让开头不变

实验里，每一次请求都是上一次一字不改、末尾再加几条。3 个进程一共发了 5 次请求，比较脚本把相邻两次请求的 input 逐条比较：5

请求什么时候发的条数字节和上一次请求比
1第 1 轮开始（第 1 个进程，codex exec）754,870—
2第 1 轮，模型第 1 次调用工具之后955,252前 7 条不变，加 2 条：工具调用和工具输出
3第 1 轮，模型第 2 次调用工具之后1155,634前 9 条不变，同样加 2 条
4第 2 轮开始（第 2 个进程，resume）1355,924前 11 条不变，加 2 条：第 1 轮的最终回复、你第 2 轮的话
5第 3 轮开始（第 3 个进程，resume 时关掉一个工具）1656,512前 13 条不变，加 3 条：第 2 轮的回复、一条工具变更说明、你第 3 轮的话

请求里 input 以外的字段也逐个比过：只有 client_metadata 每轮不同，因为里面带着这一轮的编号；OpenAI 文档列出的前缀里没有这一项。其余字段五次都一样，包括 prompt_cache_key（本节最后说）。换了进程，开头也没变：resume 时，Codex 从存档里把历史原样读回来，再接着往后加。5

中途的变化都追加在末尾，不改前面。第 2 章讲过，会话设置（权限、协作模式等）变了，Codex 在末尾追加一条新的。下面四种变化也是这样处理的：

  • 关掉一个工具。sleep 是 Codex 自带的一个工具，让模型等一会儿，属于 clock 这一组。第 3 轮用 codex exec -c features.sleep_tool=false resume --last "…" 关掉了它。第 5 次请求开头那条 25,347 字节的工具定义一字没改，里面仍有 sleep；末尾多了一条 274 字节的 developer 消息：「The following namespaces are no longer available. Do not call tools in them…: - clock」。模型只能靠这句话知道 clock 组的工具不能用了；它要是照样去调用，Codex 不会执行（第 6 章做了实验）。6
  • 换模型、加工具。第 2 章讲过，gpt-6.1-sol 的工具定义是 input 里的第 1 条，gpt-5.5 的工具定义放在请求顶层的 tools 字段。两种放法，工具变了时处理不一样。Codex 自带的测试里有一个会话中途换模型的场景：gpt-6.1-sol 这种放法下，Codex 在末尾追加三样东西：一条说明、变了的工具定义、替换后的系统提示词，测试说明里写着「不改写前缀」；等下一次压缩，再把它们合并回开头。这套做法在 Codex 里叫 incremental_tools（增量工具）。gpt-5.5 那一组测试则显示：每次请求都带完整的当前工具表，工具变了就整份换掉；按 OpenAI 文档，缓存会从工具定义那里断开。这一条只有自带测试，没自己做实验；源码 76ed3b4 里 incremental_tools 标的是「开发中、缺省关」，本机装的 CLI 0.165.0 用 codex features list 查，显示已经打开。7
  • 日期跨了一天。第 2 章讲过的环境信息那一条里写着当天的日期 <current_date>2026-11-02</current_date>。日期变了，Codex 不改那一条，而是在末尾追加一条新的环境信息。这一条读了源码，没做实验（实验没有跨天）。8
  • 改了 AGENTS.md。第 2 章讲过两份 AGENTS.md：全局那份 ~/.codex/AGENTS.md 每次请求前都重读，改了就在末尾追加新全文；项目里那份，同一个进程里只读一次，中途改了文件，这个进程后面的请求里还是旧版本（第 2 章；同一个进程中途改文件的实验还没做）。退出后用 resume 接着聊时，新进程会重读项目那份，和存档里记下的旧版本比较，不一样就在末尾追加新全文，并注明「替换之前的 AGENTS.md」（第 8 章做了实验）。几种情况都不改开头那份旧的。代码没写为什么同一个进程里不重读项目那份，可能是为了保住缓存【推测】；Claude Code 的文档对 CLAUDE.md 明确写了是这个理由（见下面的对照）。16

prompt_cache_key 是给服务器的分组提示。Codex 每次请求都带这个字段，值通常是会话编号；子代理和父会话用的是同一个（第 7 章的实验）；只有 Codex 在后台自己开的内部会话（比如第 9 章的记忆合并）用「来源:父会话编号」。按 OpenAI 文档，对较早的模型，服务器靠它把同一组请求送到同一批机器上，提高接上缓存的机会；对 gpt-6.1-sol 这类 GPT-5.6 之后的模型，它可有可无，主要用来分开统计各组请求用了多少缓存。两种情况它都不保证接上：接不接得上，只看开头是否一字不差。9

对照：Claude Code 自己放断点

据官方文档（2026-11-02 查阅），Claude Code 连的是 Anthropic 的接口，断点要请求方自己在请求里放（叫 cache_control 标记，最多 4 个）。思路和 Codex 一样，是「少变的放前面，新内容加在末尾」，但分得更细：1415

  • 分三层，从前往后排：系统提示词和工具定义 → 项目上下文（CLAUDE.md、自动记忆、不带 paths: 的规则）→ 对话。后面一层变了，前面的层仍能从缓存读。
  • 缓存存多久：缺省 5 分钟；用 Claude 订阅、还在套餐额度内时，主对话的请求存 1 小时。可在设置文件里用 promptCacheTtl 自己选。写进 5 分钟缓存的按全价的 1.25 倍收，写进 1 小时的按 2 倍；读按 0.1 倍（Opus 5.5、Sonnet 5.5 是 0.05 倍）。
  • 会让缓存接不上的操作：换模型；在多数模型上改思考强度；开快速模式；连上或移除 MCP 服务器（工具定义没延后加载时）；压缩；图片攒多了被批量移除；升级 Claude Code。会话中途换模型时，如果缓存还没过期，它会先问你确认。
  • 不影响缓存的操作：会话中途改 CLAUDE.md（改了也不马上生效，要等 /clear、/compact 或重启）；技能、计划模式的说明都作为新消息追加在末尾；/rewind 退回到旧的开头，正好接上旧的缓存。
  • 看用上了多少缓存：在输入框打 /usage，会话一栏有一行「Prompt cache (main)」，写着用上缓存的比例、几次没接上、可能的原因（v2.1.251 起）。

回答问题 3

在 Codex 的一个会话里，下一次请求的开头会和上一次一样吗？关掉工具、跨天、改 AGENTS.md、resume 呢？

一样。实验的 5 次请求，每次都是上一次一字不改、末尾再加几条；resume 换了进程也一样，因为历史是从存档原样读回来的。中途的变化都追加在末尾：关掉工具，是追加一条「这些工具不能用了」的说明（gpt-6.1-sol；gpt-5.5 会整份换掉工具表）；跨了一天，是追加一条新的环境信息；改了项目的 AGENTS.md，同一个进程里不重读，resume 时才在末尾追加新全文。

四、WebSocket 只发新增的条目

走 HTTP 时，每次请求整份重发。实验第 1 轮的第 2 次请求，整个请求体 56,816 字节，其中 99% 是第 1 次请求已经发过的。5

走 WebSocket 时，同一条连接上只发新增的。请求里带上 previous_response_id（上一次回复的编号），input 里只放上一次之后新增的条目；服务器按编号找到上一次的请求和回复，把前面接上。自定义通道要走 WebSocket，在 config.toml 里这个服务的配置下（实验里是 [model_providers.mock]）加一行 supports_websockets = true。实验就这样改了配置，同样跑 3 轮：10

  • 同一个进程里，只发新增的条目。第 1 轮里，模型每调用一次工具，Codex 发下一次请求时，input 只有 1 条：工具输出，257 字节。连同模型名、设置等字段，这次在连接上发的整条 WebSocket 消息是 1,989 字节；HTTP 下同一次请求约 5.7 万字节。模型上一次回的工具调用也不用再发，服务器那边本来就有。
  • 发过去的少了，模型看到的没少。假服务器按编号把前面拼回去，拼出的完整请求和 HTTP 那一遍里对应的那次请求逐字相同。比较前去掉了三样每次运行都随机生成的东西：条目编号（请求里每一条都带一个编号 id，形如 msg_01a19b5e-…）、临时目录名、回复编号。11
  • 每个进程的第一次请求整份发。每个进程连上以后，先发一条 generate: false 的请求（不让模型生成回答），只带设置、不带对话内容，源码里叫预热（prewarm）。预热没带对话内容，第一次真正的请求没有可以接的，input 仍整份发。resume 是新进程、新连接，所以第 2、3 轮的第一次请求也整份发（第 2 轮那次是 57,688 字节）。
  • 连不上就改走 HTTP。第一次跑实验时，假服务器的握手回应（建立 WebSocket 连接时服务器回的那一步）写错了，Codex 在每个进程里试了 7 次，之后这个进程的请求全走 HTTP。

只发新增，有两个条件。Codex 每次发请求前先检查：第一，除 input 外的字段（模型、工具、思考设置、prompt_cache_key 等）都和上一次一样；第二，新的 input 是以「上一次的 input + 上一次的回复」开头的。有一条不满足，就整份重发。这和缓存的条件很像，都要求前面一字不差。10

fn get_incremental_items(&self, request, last_response) -> Result<Vec<ResponseItem>, _> {
    let previous_request = self.websocket_session.last_request.as_ref()
        .ok_or(NonIncrementalReason::NoPreviousRequest)?;   // 这条连接上没发过：整份发
    // 模型、工具、思考设置等任何一项变了：整份发
    if let Some(reason) = responses_request_properties_mismatch(previous_request, request) {
        return Err(NonIncrementalReason::RequestPropertyChanged { reason });
    }
    // 基准 = 上一次的 input + 上一次服务器回的条目
    let previous_items = previous_request.input.iter().chain(&last_response.items_added);
    let mut current_items = request.input.iter();
    for previous in previous_items {
        let Some(current) = current_items.next() else {
            return Err(NonIncrementalReason::InputShortened { .. });  // 变短了（比如压缩）
        };
        if !response_items_equal_ignoring_internal_metadata(previous, current) {
            return Err(NonIncrementalReason::InputMismatch { .. });   // 中间有一条不同
        }
    }
    Ok(current_items.cloned().collect())   // 剩下的就是新增条目
}

只发新增和缓存是两回事。只发新增，省的是网络上传的字节和服务器解析请求的工夫；模型要处理的还是完整的上下文。缓存省的是模型那边的计算。走 HTTP 整份重发，开头一字不差，照样能接上缓存。走 WebSocket 时，用量和计价会不会因此不同，OpenAI 的缓存文档没提 WebSocket，也没提 previous_response_id【待核实】。2

回答问题 4

走 WebSocket 时，第二次请求只发新增的一两条。这算缓存吗？它省的是什么？

不算缓存。它省的是传输：同一条连接上，下一次请求只带上一次回复的编号和新增的条目（实验里 1,989 字节，HTTP 下约 5.7 万字节），服务器把前面接上，模型看到的上下文一条不少。模型那边要不要重算，由缓存决定，和走哪种连接无关。换了进程、改了设置、压缩改写了历史，Codex 都退回整份发送。

五、压缩一次，缓存重建一次

前四节讲的都是开头不变的情况。压缩是 Codex 自己改掉开头的时候：第 4 章讲过，压缩时 Codex 把整段历史发给模型写摘要，再用摘要换掉大部分历史。本章的实验没有压缩，这一节改用第 4 章实验的请求来算：压缩前的请求 35,003 token，压缩后 33,965 token。

压缩请求本身能接上缓存。第 4 章实验里，让模型写摘要的那次请求（压缩请求），是上一次请求一字不改、末尾加两条：模型的回复和要它写摘要的提示词，共 161 token；前 13 条一条没动，开头整份能接上。Claude Code 的文档也说，缓存还没过期时，它写摘要的请求从缓存读。1214

压缩之后的第一次请求，大部分要重写。把第 4 章压缩前后的请求逐条比较：第 1、2 条（工具定义和系统提示词，共 47,495 字节，约 11,874 token）内容没变，但条目编号（第四节）换了：压缩后 Codex 重新生成这两条，编号也跟着换新。从第 3 条起内容就不同了：保留下来的第 2 轮原话，排在了技能目录等 4 条设置前面（第 4 章第二节）。编号算不算进缓存比较，OpenAI 文档没写【待核实】。所以压缩后的第一次请求：最好的情况，开头约 1.19 万 token 能接上，其余约 2.2 万 token 按 1.25 倍重写；最坏的情况，编号也算，3.4 万 token 整份重写。12

压缩在钱上是先多付、后少付。多付的是两次请求：压缩请求本身（大部分从缓存读），加上压缩后第一次请求的重写。少付的是以后的每一次请求：开头变短了，每次从缓存读的部分少了。少付的累计起来抵掉多付的那一笔，就算回本。

压缩前越大，越快回本。第 4 章实验的那次压缩只少了 1,038 token，压缩后每次请求只少付约 52 个 token 的全价（1,038 × 0.05；下面的钱数都这样折合），压缩那两次请求却要付约 3 万；要到压缩后第 549 次请求才追平，实际会话里等于回不了本。这次少得少，是因为第 4 章实验里占地方的是你贴的两段长日志，而压缩恰好保留你的原话。换一组大的数：官方通道下 gpt-6.1-sol 的压缩线是 450,000 token（第 4 章），假设压缩后剩 40,000（这个数是假设的，没实验）。这时压缩后每次请求少付 20,500，压缩那两次请求付约 5.8 万，到压缩后第 3 次请求，累计花费就比不压缩少；如果编号也算、开头接不上，要到第 4 次。

回答问题 5

压缩一次要多付多少？压缩后要发几次请求，省下的钱才能抵掉多付的这一笔？

压缩请求本身能从缓存读，多付的主要是压缩后的第一次请求：除了开头约 1.19 万 token 的工具定义和系统提示词（条目编号不算进比较时），其余都按 1.25 倍重写。几次回本，看压缩前有多大：45 万压到 4 万，压缩后第 3 次请求起累计花费就比不压缩少（开头接不上时第 4 次）；第 4 章实验里 3.5 万只压掉 1 千，要到第 549 次才追平。压缩首先是为了窗口，钱上只有压缩前很大时才省。

设计笔记

  • 追加不改写，代价是旧内容留在历史里。关掉的工具，定义还在开头，只靠末尾一句话说明不能用（模型照样调用时 Codex 不执行，第 6 章）；变化多了，说明散在历史各处，模型要自己把前后对上。压缩时 Codex 再把它们合并回开头（自带测试的场景说明）。会不会因此更容易用错工具，没测过【推测】。
  • 项目 AGENTS.md 同一个进程里不重读：保住了缓存，代价是改了不马上生效。想让新规则起作用，要退出后 resume 或新开会话；resume 后旧规则和新规则会同时留在历史里，直到下一次压缩（第 8 章）。Claude Code 对 CLAUDE.md 是同一个取舍，文档写明了原因；Codex 源码没写原因【推测】。
  • 缓存没接上，比不用缓存贵 25%。写入按 1.25 倍收，所以中途换模型、换思考级别都不是免费的。Claude Code 在缓存还没过期时换模型会先问一句，Codex 没有这个提示；而且 Codex 里 gpt-5.5 和 gpt-6.1-sol 来回换，每换一次还会先压缩一次（第 4 章）。
  • WebSocket 的服务器怎么记得上一次。Codex 的请求都带 store: false（不让服务器保存这次的回复），却还能用 previous_response_id 接上，可能是服务器把上一次的内容留在这条连接的内存里，所以一换连接就要整份重发【推测】。
  • 别的做法。有的 agent 自己在请求里放多个断点，按变化快慢把请求分层缓存；Claude Code 的三层就是这样。本机没有其他 agent 的源码，它们具体怎么放没核对【待核实】。

小结

  1. 重发的开头不用按全价再付：接上缓存的部分，gpt-6.1-sol 只按全价的 5% 收，也少等一会儿；新写进缓存的按 1.25 倍收；窗口占用一点不少。
  2. 缓存从第一处不同开始接不上，后面没改的也要重写；工具定义、AGENTS.md 都在最前面，改了就整份重写。
  3. Codex 一个会话里的请求总是上一次一字不改、末尾再加几条：关工具、跨天、换模型、改 AGENTS.md 都追加在末尾，resume 也不改开头。
  4. WebSocket 只发新增条目，省的是传输，不是计算；模型看到的上下文不变；换进程、改设置或压缩改写了历史，就整份重发。
  5. 压缩后的第一次请求大部分要按 1.25 倍重写；压缩前越大越快回本，45 万压到 4 万时，压缩后第 3 次请求起就省钱。
