单元 01 · 建立直觉

一句话，很多次请求

先修无。会看聊天记录就行。
读完你能说出"一句话"背后发生了什么；读懂一个最小消息列表。

场景：两句话，怎么花了这么多钱？

小林第一次用 Codex CLI，输入了一句话：

"帮我安排下周五的班级郊游，两个班，60 人，下午 4 点前必须回到学校。顺便看看操场集合点怎么安排。"

然后他去泡了杯茶。回来时屏幕上滚过一串条目：查地图、查公交、读了一份《研学地点说明》、又查了天气……最后 AI 给出行程。月底对账他懵了：我就说了两句话，为什么像聊了半小时？

这背后有两个他看不见的事实：

① "一句话"触发的是一串模型请求——AI 每走一步，都要"带着当前所有材料"再问一次模型：接下来做什么？

② 每次请求带的材料，远比你输入的文字多——系统指令、工具说明、此前全部对话、工具查回来的结果……都在里面。

交互：把这次任务走一遍逐步 / 连续播放

任务时间线 演示数据（步骤与材料为教学构造）
模式：逐步阅读（点"下一步"或选择速度后点播放）
第 0 步 · 起点
你按下回车。此刻材料列表里只有你这一条消息。
这一步发生了什么
看时间线时留意两件事

① 材料只增不减：每出现一步，列表就变得更长——下一次请求几乎原样带上这里的一切。② 模型调用夹在工具两侧：工具执行本身不调模型，但"要求调用"和"拿到结果后继续"各要一次请求。

给四件事起名字

名字一句话定义生活对照
任务（task / turn）从你说一句话开始、到 AI 彻底停下为止的全过程；途中可能发生很多次请求与工具调用。一次"帮我把郊游安排好"的委托
模型请求（model request）把当前所有材料打包，发给模型问一次"接下来做什么"。把桌上材料推给专家看一眼
工具（tool）程序提供给模型使用的功能（读文件、跑命令、查资料）。模型不能自己动手，只能"要求"调用。专家说"我看看那本书"，助理去拿
工具结果（tool output）工具执行后的返回值，写进消息列表，出现在下一次请求里。助理把翻到的那一页递回来

再认识两个结构名词：消息角色（role）——列表里每条消息的身份：user 是你的话、assistant 是模型回复、developer 是程序维护的"工作说明"；工具调用与结果配对——模型说"调用工具 X"时带一个编号 call_id，之后必须有对应结果。程序把它当不变量强制检查：每个调用都有结果、每个结果都能对上调用（或明确标记为外部工具事件）。

当心 · 两个初学最易立的错误认知

① "AI 记得我们所有的聊天"——不。它每次能"记得"的，只是这次请求实际带上的材料；材料会被裁剪、替换（单元 04、05）。② "工具结果完整保存、随时完整"——不一定：工具输出进入列表前就可能被限长；磁盘保存与当前列表也不是同一份东西（单元 06）。

AI 停下来等工具结果的那段时间，模型被调用了几次？
A. 0 次，工具是本地跑的　B. 1 次（发出调用那次）　C. 2 次（发出调用 + 拿到结果后继续）
看答案

C。模型先被问"现在做什么"→要求调用工具；工具执行完、结果写入列表后再被问一次"接下来做什么"。工具执行本身不调模型，但两侧各要一次请求。

判断题：工具结果出现在消息列表里，说明它一定会出现在下一次请求里。
看答案

错。"进入列表"与"出现在下次请求"之间还有处理步骤：配对与内容检查、限长、窗口紧张时的整理。现有材料可能被裁剪或摘要替代（单元 04、05）。

为什么程序要死守"每个调用都有结果"的配对？缺一条会怎样？
看答案

请求是结构化数据，服务端按"调用—结果"对应关系配对读取。缺结果，上文悬空（模型不知道工具做了什么）；缺调用的"野结果"无法归属。程序宁可在本地补齐占位或移出孤立条目，也不发送结构非法的请求——这就是那几条不变量存在的原因。

单元 02 · 理解流程

聊天之外，还有一份"当前工作条件"

先修单元 01（任务与请求的概念）。
读完你能说出工作目录/规则/工具怎么会出现在请求里，以及"变了才说"的差分逻辑。

场景：她没重发任何东西，AI 却知道项目规矩

婷婷换了台电脑，打开昨天的工作会话继续问："接着改登录页。"奇怪的事：AI 依然知道项目规则（"本项目时间一律用 UTC"）、知道新换的工作目录。她输入的文字里，没有任何一条提到这些。

先猜一下：如果只把"聊天记录"发给模型，够不够？

设想你接手别人转来的工作，只拿到聊天记录：不知道工作在哪个文件夹（没法动手）、不知道团队规矩（改得对不对没法判断）、不知道手头有什么工具。聊天里可能都提过——但可能是一周前说的、可能已经改了。靠翻聊天还原现状，既不可靠又浪费空间。

程序的选择与你不谋而合：不靠聊天推断现状，而是单独维护一份"当前情况单"，每次请求按当前实际状态准备。

人话直给

程序里有一张当前工作条件表：工作目录、网络开关、权限、项目规则、可用工具。它按栏目维护、只记当前有效的内容，每次请求前把最新状态渲染给模型。它在源码里的正式名字叫 WorldState——第一次见面，我们叫它"当前工作状态"，以后不再用直译。

请求组成演化器演示数据
当前：只带"聊天文本"的朴素做法（这是错的——看它缺了什么）
设想 ①
请求里实际装了什么
关键机制：变了才说，没变不啰嗦

这套情况单并非每次都完整重发。程序记着上一版快照，请求前做比较：没变→不追加任何说明；变了→生成一条"替换说明"（某栏目换成新内容）；删了→生成"不再适用说明"。点上面的"切换"按钮看两种情形。

项目规则从哪里来，能装多少

项目规则文件（AGENTS.md）的发现规则是固定的：从项目根目录到当前工作目录沿路找（不遍历整个项目子树）；同一目录下特定覆盖文件名优先；项目未被标记为可信时不读取；所有项目规则文件共享一个字节预算（默认 32 KiB ≈ 3.2 万字节，可配置）——超预算时从文件尾部截掉。（"字节"是电脑计量文字体积的单位，直觉先记"约 3 万字的量级"，细节单元 05 再展开。）

当心 · 三条最容易错的说法

① "文件名是 AGENTS 就自动完整进模型"——要位置对、项目可信、没超预算。② "规则写进文件，模型就一定遵守"——规则进请求（材料问题）与模型照做（行为问题）是两件事，后者要靠结果检查。③ "规则重新注入能补回最初没读进来的部分"——不能：预算内被截掉的尾巴从未进过模型视野，后来的重组也不会把它变出来。

一次请求的完整账本

把单元 01 和本单元接上，"一次请求到底装了什么"可以给出完整账（教学示意，顺序与形态因场景而异）：

基础指令+ developer 材料（工作状态渲染 + 已加载规则）+ 对话历史+ 工具说明+ 本次用户输入

注意最后一项在底部：稳定材料在前、易变内容在后，对一类重要机制（缓存，单元 08）极其有利——这是刻意排布，不是巧合。

单元 03 · 掌握机制（核心章）

空间快不够了：用量怎么算，什么时候整理

先修单元 01–02。本单元开始出现数字计算，会先补最小单位。
读完你能独立完成 7 类触发演算：基础线、范围限额、有效窗口、两条线的判定、模型限额与用户覆盖。

先补最小单位：token

模型不是按"字"处理文字的，而是按 token（令牌）——把文字切碎后的小块。一次请求能装多少 token 有硬上限，叫上下文窗口（context window）；请求里的全部材料（指令、历史、工具结果、你的输入）和模型的输出共用这一个池子。

口径说明用途
模型真实 tokenizer服务端把文本切块后的准确数量计费与上限的最终裁判
服务端返回的 usage每次响应附带"这次输入/输出各多少 token"程序校准本地估算的依据
本地近似估算Codex 固定快照：UTF-8 字节数 ÷ 4，向上取整服务端返回之前的快速估计

第三行的几个字节课（演示）："hello" 5 字节 → 2 tokens；"Plan the trip." 14 字节 → 4 tokens；汉字"回" 3 字节 → 1 token；"下午4点前返校" ≈ 14 字节 → 4 tokens。

先建个直觉——"字节"是电脑计量文字体积的单位（UTF-8 编码下：英文 1 个字符约 1 字节、汉字 1 个约 3 字节；细节单元 05 展开）。表中的"字节数 ÷ 4"就是把体积粗换成 token。

当心

"÷4"是 Codex 内部近似口径，不是任何模型的真实计费标准，对中文是粗估；真实数字以服务端 usage 为准。后面凡本地估算都会标注。

四本账与两条线

变量含义通俗理解
W解析后的上下文窗口桌子总共多大
p有效窗口比例，字段缺省 95允许用多大比例
H = W × p ÷ 100有效窗口上限真正的可用上限
M / C模型元数据限额 M（可被用户配置 C 覆盖）提前整理的下限原料
A当前活动用量＝上次服务端用量＋本地新增估算桌上现在堆了多少
P本窗口开始时的输入基线（prefill）上次收拾后的起点

两条线：范围线（默认口径下 = min(模型字段, 90%×W)，即"基础线"与更低字段值取小）或整段线（所有材料不超过 H）。任一满足 = "到线"。

为什么是 90% 和 95%，不是 100%？

① 模型回复也吃同一个池子，顶满就没空间写回复；② 整理本身也要调用模型（写摘要需要输出空间）。90% 是这一实现的整理基础线（不是模型原理规定），95% 是有效窗口比例的字段缺省——两者都可能被模型元数据或用户配置改写。

裁剪算法：头、尾与标记

中文伪代码：头尾裁剪（近似 token 口径）
  输入：文本 s、预算 max_tokens
  若 字节数(s) ≤ max_tokens×4 → 原样返回        # 装得下就不裁
  max_bytes = max_tokens × 4
  左预算 = max_bytes ÷ 2        # 整数除法：奇数时少 1 字节
  右预算 = max_bytes − 左预算    # 奇数时多 1 字节（左右并非严格均分！）
  头部 = 从 0 到左预算的最近 UTF-8 边界
  尾部 = 从（总长−右预算）的最近 UTF-8 边界到结尾
  标记 = "…N tokens truncated…"（N 按被移除字节数 ÷ 4 估算）
  返回 头部 + 标记 + 尾部
两个亲手算的例子（15 字节英文 / 68 字节中文） 
例 A：20 个字母、预算 15 字节
  左 = 15÷2 = 7        → 头部 "abcdefg"
  右 = 15−7 = 8        → 尾部 s[12..] = "stuvwxyz"
  移除 5 字节 → N = ceil(5/4) = 2 → 标记 "…2 tokens truncated…"
  结果：abcdefg…2 tokens truncated…stuvwxyz
  （保留 7+8=15 字节 + 标记；标记是额外添加的）

例 B：68 字节中文、预算 20 字节
  左 10 字节 → 停在最近字符边界：3 个汉字（9 字节）
  右 10 字节 → 从 58 字节向上对齐边界 → 60（尾部 8 字节）
  移除 48 字节 → N = 12 → 标记 "…12 tokens truncated…"

两个不能想当然的点：① 左右不是严格均分（奇数预算差 1 字节给尾部）；② 标记不占预算，所以"输出含标记后一定严格等于预算"是错的——真实输出比预算略长。裁剪按字节算、落刀看字符边界（floor_char_boundary / ceil_char_boundary）：汉字 3 字节，切在中间会产生无效半截字节。

场景：同样的开头，为什么第二次更快更便宜

小林连续问了两句：①"帮我把行程里的公交段列出来。"②"把行程里的午饭段列出来。"两句的开头——系统指令、工具说明、全部对话历史——几乎完全一样。官方给这套"重复开头"的优化起名：Prompt Caching（提示词缓存）。

人话直给

模型读材料时，会给每个 token 计算一份"中间状态"（官方叫 KV 状态，key-value states）。缓存把这些状态存下来——下次请求如果开头部分（前缀）一字不差，模型直接拿回这份状态，跳过大半重新计算。

术语含义注意
前缀（prefix）请求开头"未改变的那部分 token"匹配的是完整渲染后的上下文（含指令、工具、历史），不只是你可见的文字
缓存断点（cache breakpoint）标记"前缀到此为止可以存/取"的终点新代际支持显式+隐式；旧代际只有隐式、按固定间隔
命中（cache hit）请求到达了一台仍持有匹配缓存条目的机器，且前缀匹配不保证：路由、过期、负载都影响
三条关键澄清（官方原文性质）

① 缓存存的是 KV tensors（中间状态），不是 token 本身；② 命中后本次上下文的总长度不变——省的是"重新计算"，不是"少发材料"；③ 缓存输入依然计入速率限制（TPM）。

三个容易记错的关系：① 两项都是输入明细，不能再加到 input_tokens 上；② 普通输入 = input − cached − write；③ 计费当量 = 普通×1 + 读取×0.1 + 写入×1.25——写入的 1.25 倍是完整单价（不是"普通价上再加 1.25 倍"）。

账单计算器费率：写 1.25× / 读 0.1×（新代际示例）

缓存与上下文管理其他部分的交界

机制与缓存的关系
压缩 / 摘要会改变前缀：替换历史后，"从第一个变化的 token 起"旧缓存无法复用；压缩后首发请求命中更低，新前缀稳定后回升
修改旧消息改旧消息不如追加新消息：改写让该消息之后的前缀全部失配
工具变更工具名/描述/顺序变化都会改变渲染前缀 → 破坏复用（工具说明在前部）
长期记忆 / 检索 / 子 Agent / fork / 恢复都通过"改变本次请求的前缀"影响缓存：恢复是重建材料，fork 派生新边界，子 Agent 有独立会话与独立缓存键——都是"新前缀"，不该期待顺手命中
上下文窗口缓存不缩小窗口占用；cached 输入仍计入 TPM 与本次完整上下文

拆账：input=50,000、cached=40,000、write=2,000。求普通输入与当量（新代际费率）。cached 要不要从 50,000 再减一次？
看答案

普通 = 50,000 − 40,000 − 2,000 = 8,000；当量 = 8,000 + 40,000×0.1 + 2,000×1.25 = 8,000 + 4,000 + 2,500 = 14,500。cached 是 input 的明细拆分，已在 50,000 里，不能再减第二次。

判断题：两次请求"文字看起来一样"，就一定命中缓存。
看答案

错。反例（任举两条）：渲染前缀因设置/工具/顺序变化而不一致；缓存过期或未路由到持有条目的机器；前缀未达最小可缓存长度；隐式/显式模式切换导致查找边界不同。

压缩之后，缓存复用会怎样？用"前缀"一词解释。
看答案

压缩替换了历史，从"第一个变化的 token"开始旧前缀不再匹配——压缩后首发请求通常复用较少；但变化点之前的稳定部分仍可能命中，且新前缀稳定后命中会恢复。压缩改变前缀 → 缓存按前缀退化，不会整体归零。

命中缓存后，这次的窗口占用会变小吗？速率限制呢？
看答案

都不会变小。缓存省的是重新计算（算力、费用、首字延迟方向）；完整上下文仍要占满，cached 输入仍计入 TPM。把缓存当"窗口扩容"或"上下文缩短"都是错的。

综合自测结业前自检，覆盖全部单元

"这句话我刚才说过"——它可能存在于哪三层？"我看到了"与"模型看到了"为什么可能不一致？（U1/U6）
看答案

三层：存档（大概率在）/ 活动历史（可能已被替换）/ 请求（可能不在）。"我看到了"通常指前两层（尤其文件层），"模型看到"只看第三层；压缩后替代历史覆盖旧列表就是两层分离的现实例子。

规则文件超了 32 KiB 预算，关键行在尾部。至少两条补救。（U2/U5）
看答案

把关键内容移到文件头部；拆分文件让发现范围覆盖；提高配置预算（若允许）；或把要点显式写进对话（人工冗余）。

W=128,000、M 缺失、用户无配置：范围线多少？A=116,000 到线吗？（U3）
看答案

90%×128,000 = 115,200；116,000 ≥ 115,200 → 已到线（整段线 121,600 未到，但 OR 已触发）。

整理前有 5 条用户消息（8k/12k/3k/9k/14k，旧→新），本地预算 20k。最终保留清单？（U4）
看答案

倒着装：14k（剩 6k）→ 9k > 6k → 边界截短（保头尾约 6k），停止。最终：[9k 截短片段] → [14k] → [摘要]；3k/12k/8k 不保留（除非摘要带走）。注意"选完边界即停"。

为什么"工具结果在历史里被裁了，但磁盘上可能还是全的"？（U5）
看答案

活动历史保存裁剪后的副本，存档写入未裁剪原载荷——不同流水线上的不同对象（另有各自的持久化预算，如 64 KiB 分片上限）。

恢复会话时，"复用检查点替代历史"与"重放全部旧消息"的差别？（U6）
看答案

前者一步采用"整理时保存的替代材料"（规则重渲染+保留的消息+摘要/压缩条目），成本低、忠实于整理时的取舍；后者会重新经历全部旧消息（重复计算、把已被替换的内容带回来，与系统语义不符）。系统用前者 + 回放检查点之后的后缀。

远端压缩验收要求"恰好一个压缩条目"。收到两个会怎样？（U7）
看答案

验收失败：判 Fatal（"expected exactly one compaction output item"），替代历史不安装；活动历史保持原样，等下轮再试或提示用户。

两次请求文字相同却没命中缓存，写三种可能原因。（U8）
看答案

渲染前缀其实不同（工具/设置/顺序变了）；过期或未路由到持有条目的机器；前缀低于最小可缓存长度；显式/隐式模式切换导致查找边界不同（任选三条）。

"已否决方案"保存到第二天——存进摘要就够吗？为什么？（U9）
看答案

不够。"否决"是状态，需要结构化保存与更新语义（约束表；被否的标"已否决"而非删除，渲染时可见）；只存摘要等于把关键状态交给有损概括，且无法验证还在不在。第二天正确做法：恢复后先重述验证，再继续。
