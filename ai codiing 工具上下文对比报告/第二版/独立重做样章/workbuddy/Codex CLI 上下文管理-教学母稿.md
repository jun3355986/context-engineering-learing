## 读完之后你能做什么

一次学完（配合练习），你应该能在**上下文管理这个专项**上完成六件事：

1. **解释信息流**：画出一次任务里的多次模型请求和工具循环，说清"保存的记录、当前的材料、实际发出的请求"分别在哪里。
2. **推演预算**：给定窗口、用量和配置，算出一条自动整理线是否到线，并预测整理后哪些材料会被带上。
3. **找到丢失点**：一条约束消失时，判断它是在工具出口、活动历史、摘要、还是恢复环节丢的。
4. **读懂关键源码**：看懂固定版本里触发、保留、裁剪、替换、恢复的关键分支（不需要会写 Rust）。
5. **设计与排障**：为一个小型 Agent 设计上下文流程，处理约束丢失、摘要失败和恢复。
6. **验证与迁移**：用一个没在教程里讲过的任务，自证设计仍然成立。

学习路线按九个小单元推进：

| 单元 | 回答的问题 | 读完能做到 |
|---|---|---|
| 01 一次任务，多次请求 | 一句请求背后发生了什么？ | 分清任务/请求/工具，读懂消息列表 |
| 02 聊天之外的工作条件 | 规则和环境怎么会出现在请求里？ | 说出当前工作状态与项目规则的去向 |
| 03 什么时候整理 | 空间不够时程序怎么算、怎么判断？ | 独立演算触发条件 |
| 04 整理后带上什么 | 压缩会删掉一切吗？ | 推演保留清单与产物形态 |
| 05 信息在哪一步没的 | 关键约束为什么会消失？ | 沿三处限长定位丢失点 |
| 06 关掉再打开 | 恢复会话到底恢复了什么？ | 解释三层记录与恢复顺序 |
| 07 失败与手动整理 | 整理失败会怎样？ | 判断失败后的状态与出路 |
| 08 同样开头的第二次请求 | 缓存省了什么、没省什么？ | 拆读 usage 并算账 |
| 09 自己设计一套 | 把这些机制用在你的 Agent 上 | 提交可验收的设计与验证方案 |

# 单元 01 · 一句话，很多次请求

> 对应交互：任务时间线（逐步播放一遍"一句话"背后的五次模型往返）。

## 场景：两句话，怎么花了这么多钱？

小林第一次用 Codex CLI。他输入了一句话：

> 帮我安排下周五的班级郊游，两个班，60 人，**下午 4 点前必须回到学校**。顺便看看操场集合点怎么安排。

然后他去泡了杯茶。回来时，屏幕上已经滚过了十几个条目：查地图、查公交、读了一份"研学地点说明.txt"、又查了天气……最后 AI 给出了一份行程。

月底账单来了，小林懵了：**我就说了两句话，为什么像聊了半小时？**

这背后有两个他看不见的事实：

1. **"一句话"触发的是一串模型请求，而不是一次。** AI 每做一步（读文件、跑命令、查资料），都要"带着当前的所有材料"再问一次模型：现在该怎么办？
2. **每次请求带的材料，远比你输入的文字多。** 系统指令、工具说明、你之前的全部对话、工具查回来的结果……都在里面。

## 先看它到底发生了什么

跟着时间线走一遍（正是交互版里可以逐步播放的那张时间线）：

```
你发出消息：'安排郊游……下午 4 点前返校'
│
├─【模型请求 ①】带着：你的消息 + 基础指令 + 工具说明清单
│     模型回复：'我需要先查公交线路' → 要求调用工具 '查公交'
│
├─【工具执行】查公交(线路A到学校) → 返回 300 行结果
│
├─【模型请求 ②】带着：你的消息 + 上一步的调用记录 + 300 行工具结果
│     模型回复：'再读一下研学地点说明' → 要求调用工具 '读文件'
│
├─【工具执行】读文件 → 返回 40 行说明
│
├─【模型请求 ③】带着：前面全部 + 刚才的文件内容
│     模型回复：最终行程建议（此时它引用'4 点前返校'来安排返程时间）
```

每一格里的"带着"，在程序里是一个**消息列表**——上一轮问过什么、答过什么、工具取回了什么，全部按时间顺序排列，下一次请求近乎原样地再带上。

这解释了小林的疑惑：

- "一句话" = 一次**任务**（task），
- 背后是 N 次**模型请求**（model request），
- 每次请求都近似带上**此前积累的全部材料**。

**【人话】** 说白了：AI 每走一小步就会"回头把所有资料重新摊开在桌上"再问一次模型。你不说的话，它记不住；它说过的、查过的，都在这张桌子上摞着，越摞越高。

## 给四件事起名字

上面故事里的四个东西，教程中会一直使用这些名字：

| 名字 | 一句话定义 | 生活对照 |
|---|---|---|
| **任务**（task / turn） | 从你说一句话开始，到 AI 彻底停下来为止的全过程。途中可能发生很多次请求和很多次工具调用 | 一次"帮我把郊游安排好"的委托 |
| **模型请求**（model request） | 把当前所有材料打包，发给模型问一次"接下来做什么" | 把桌上材料推给专家看一眼 |
| **工具**（tool） | 程序提供给模型使用的功能，比如读文件、跑命令、查资料。模型不能自己动手，只能**要求**调用工具 | 专家说"我看看那本书"，助理去书架上拿 |
| **工具结果**（tool output） | 工具执行后的返回值，会被写进消息列表，出现在下一次请求里 | 助理把书翻到某一页递回来 |

还要认识两个结构名词：

- **消息角色**（role）：列表里每条消息有身份。`user` 是你的话；`assistant` 是模型的回复；`developer` 是程序维护的"给模型的工作说明"（规则、环境信息）；工具有自己的调用与结果条目。
- **工具调用与结果配对**：模型说"调用工具 X"（带一个调用编号 `call_id`），之后必然有一条对应的结果条目。程序会强制检查这种配对是否完整——**每个调用都有结果、每个结果都能对上调用**（或明确标记为外部工具事件）。这不是礼貌问题，而是不变量：破坏配对会让下一次请求结构非法。

## 一个最小的消息列表示例

下面是一个**教学简化的数据样例**（数字是编的，结构模仿真实请求；交互版中"任务时间线"的每一步展开的就是它）：

```json
[
  {"role": "developer", "类型": "基础指令",       "内容": "你是 Codex……"},
  {"role": "developer", "类型": "当前工作状态",   "内容": "工作目录 /project；允许的网络：否；已加载规则：AGENTS.md……"},
  {"role": "user",      "内容": "安排郊游……下午 4 点前必须返校"},
  {"role": "assistant", "类型": "工具调用",       "工具": "查公交", "call_id": "call_001", "参数": {"线路": "A→学校"}},
  {"role": "tool",      "类型": "工具结果",       "call_id": "call_001", "内容": "（300 行公交查询结果）"},
  {"role": "assistant", "内容": "我再读一下研学地点说明"},
  …
]
```

**【当心】** 两个初学时最容易立的错误认知：

1. "AI 记得我们所有的聊天"——不。它每次能"记得"的，只是这次请求**实际带上**的那份材料。加上引号是因为这既不是人类记忆，也不等于完整历史（后面几单元会看到材料如何被裁剪和替换）。
2. "工具结果是完整保存的"——不一定。工具输出在进入列表前就可能被限长（单元 05 专讲）。磁盘上保存的记录与当前列表也不是同一份东西（单元 06）。

## 真实实现：请求是拼出来的

Codex CLI 发一次请求前，会组装一个叫 `Prompt` 的结构。简化后的中文伪代码：

```text
函数 组装请求(当前材料列表, 步骤上下文, 基础指令):
    返回 {
        input:            当前材料列表,      // 消息、工具调用与结果的数组
        tools:            当前可用工具的说明清单,   // 工具名、参数格式
        base_instructions: 基础指令,         // 模型的"岗位说明书"
        output_schema:    期望输出格式（可选）,
    }
```

对应的真实代码（Rust，节选自 `build_prompt`，已压缩无关参数）：

```rust
// codex-rs/core/src/session/turn.rs  L1563–1591（节选）
pub(crate) fn build_prompt(
    input: Vec<ResponseItem>,
    step_context: &StepContext,
    base_instructions: BaseInstructions,
    incremental_tools: bool,
) -> Prompt {
    Prompt {
        input,
        tools: if incremental_tools { …省略… } else {
            step_context.tool_router.model_visible_specs()
        },
        parallel_tool_calls: true,
        base_instructions: …,
        output_schema: turn_context.final_output_json_schema.clone(),
        …
    }
}
```

逐句说明：

- `input: Vec<ResponseItem>`："材料列表"这个参数的类型是"一组 ResponseItem"。**ResponseItem（响应条目）**是这个程序里模型可见材料的最小单位：一条用户消息、一条模型回复、一次工具调用、一条工具结果，各算一个条目。
- `tools: … model_visible_specs()`：把**当前允许给模型看的工具说明**装进请求。工具说明本身也占空间——它和聊天无关，但每次请求都带着。
- `parallel_tool_calls: true`：允许模型一次要求多个工具调用。
- `output_schema`：某些场景（如要求结构化输出）会附带期望格式。

还有一条**配对不变量**在每次材料进入历史前被强制执行（`normalize_history`，`codex-rs/core/src/context_manager/history.rs` L962–980，注释原文列举三条不变量）：

```rust
// 每个函数/自定义工具调用都必须有对应的输出条目
normalize::ensure_call_outputs_present(items);
// 配对输出必须有对应的调用；命名外部工具事件可以独立存在
normalize::remove_orphan_outputs(items);
// 模型不支持图片/音频时，从消息和工具输出里剥离这类内容
normalize::strip_images_when_unsupported(input_modalities, items);
normalize::strip_audio_when_unsupported(input_modalities, items);
```

**【当心】** 第三条不变量说明一件事：**改用不支持图片的模型时，历史里的图片会在进入请求前被剥离**——这属于"材料在你没察觉时被改写"的又一种来源。

## 自测

**① 顺序题**：小林看到"AI 停下来等工具结果"的那段时间里，模型被调用了几次？
A. 0 次，工具是本地跑的，与模型无关
B. 1 次：发出"调用工具"那次
C. 2 次：发出调用的那次 + 拿到结果后让它继续的那次
D. 不确定，看实现

**② 判断题**：工具结果出现在消息列表里，说明它一定会出现在下一次请求里。（对/错）

**③ 配对题**：为什么程序要死守"每个调用都有结果"的配对？如果缺一条会发生什么？

<details>
<summary>参考答案</summary>

**① C。** 模型先被问一次"现在做什么"，它要求调用工具；工具执行完，结果写入列表，模型再被问一次"接下来做什么"。工具执行本身不调用模型，但**两侧各要一次模型请求**。

**② 错。** "进入列表"和"出现在下一次请求"之间还有处理步骤：配对与内容检查、限长、当窗口紧张时的整理。现有材料可能被裁剪或摘要替代（单元 04、05）。

**③** 因为请求是结构化数据：模型服务端按"调用—结果"的对应关系配对读取。缺结果会让上文悬空（模型不知道工具做了什么），缺调用的"野结果"无法归属。程序宁可在本地补齐占位或在进入历史时移除孤立条目，也不发送结构非法的请求——这就是那三条不变量存在的原因。
</details>

# 单元 02 · 聊天之外，还有一份"当前工作条件"

> 对应交互：请求组成演化器（从"只有聊天文本"逐层加料到"完整请求"）。

## 场景：为什么它知道"我们项目不许用某个库"？

婷婷换了台电脑，重新打开昨天的工作会话继续问："接着改登录页。"

奇怪的事来了：

- AI 依然知道**项目规则**："本项目所有时间必须用 UTC。"
- AI 知道**刚才换过的工作目录**，读文件时找对了地方。
- 她没有重发任何一条历史消息。

她输入的文字里，没有任何一条提到"UTC"或"目录"。这些信息是从哪条缝里钻进去的？

## 先猜一下：只带"聊天记录"够不够？

设想你接手别人转来的工作，只拿到聊天记录，其他什么都不给你：

- 你不知道**工作在哪个文件夹**（没法动手）；
- 不知道**这个团队有哪些规矩**（改得对不对没法判断）；
- 不知道**手头有什么工具**（以为只有螺丝刀，其实有台钻）。

聊天记录里可能都提过——但可能是一周前提的、可能是改了又改的。靠"翻聊天"来还原现状，既不可靠也浪费空间。

程序的选择与你不谋而合：**不靠聊天推断现状，而是单独维护一份"当前情况单"，每次请求按当前实际状态准备。**

## 这份"当前情况单"

**【人话】** 说白了，程序里有一张**当前工作条件表**：工作目录是什么、网络开不开、有哪些权限、项目规则文件里写了什么、有哪些工具可用。它按栏目维护，只记**当前有效**的内容——去年删掉的规矩不会赖着不走。每次请求前，程序按这张表的最新状态，把需要的栏目渲染成给模型看的说明。

它在源码里的名字叫 `WorldState`。首次出现时我们这样介绍它：**当前工作状态（源码名 `WorldState`）**，就是 Codex 当前需要让模型知道的环境和设置。以后正文不再用"世界状态"这种直译。

栏目（section）是一组固定的名字，比如：

```text
WorldState.sections 的简单示意（栏目名真实，内容为教学简化）：
  环境信息：    工作目录 = /project/youxue
  沙箱与权限：  可写目录 = 项目内；网络 = 允许
  项目规则：    已加载 AGENTS.md（来源：/project/youxue/AGENTS.md）
  可用工具：    shell, 读文件, 写文件, 查资料……
  协作模式：    默认
```

## 关键机制：变了才说，没变不啰嗦

你可能会想：这套"情况单"每次都完整重发一遍，岂不是非常浪费？

真实实现比这聪明（也更省）：程序记着**上一版情况单**，请求前做**比较**：

```text
中文伪代码：情况单的差分更新
  当前 = 生成当前情况单快照()
  如果 当前 == 上次快照:
      不追加任何说明            # 规则没变，模型凭历史里的旧说明就好
  否则:
      找出变化栏目
      生成"替换说明"：某栏目现在换成新内容   # 例如：工作目录从 A 改成 B
      如果 某栏目被删除:
          生成"不再适用说明"
  把生成的说明追加进请求材料，并更新快照
```

具体到项目规则文件（`AGENTS.md`）：**内容没变就不重发；变了就发一条替换说明；被删了发"不再适用"**。所以婷婷看到的现象就有了第二个解释——

**规则并不是"一直在聊天记录里"，而是程序按当前状态重新准备，放进本次请求的 developer 材料里。** 哪怕她换了电脑、开新会话，只要那份规则文件还在、还能被读到，它就会出现在新请求里。

## 项目规则从哪里来，能装多少

项目规则文件的发现范围（`AGENTS.md`）是固定的：

- 从**项目根目录到当前工作目录**沿路找；不遍历整个项目子树；
- 同一目录下，特定覆盖文件名优先于通用文件名；
- 项目**未被标记为可信时不读取**项目规则；
- 所有项目规则文件**共享一个字节预算**（默认 **32 KiB**，可配置）——超出预算，**从文件尾部截掉**。

**【当心】** 三条最容易错的说法：

1. "文件名叫 AGENTS 就自动完整进模型"——不一定：要位置对、项目可信、没超预算。
2. "规则写在文件里，模型就一定会遵守"——规则进请求与"模型照做"是两件事：前者是材料问题，后者要靠结果检查。
3. "规则重新注入能补回最初没读进来的部分"——不能。**预算内被截掉的尾巴，从没进过模型视野，后来的重组也不会把它变出来。**

## 一次请求的完整组成（把两个单元接上）

到这里，"一次请求到底装了什么"可以给出一张完整的账了。**教学示意**（顺序与具体形态因场景而异）：

```
一次模型请求
├── 基础指令（base instructions）      岗位说明书：你是怎样的助手
├── developer 材料                      程序维护的工作说明
│    ├── 当前工作状态（WorldState 渲染）
│    └── 已加载的项目规则（AGENTS 等）
├── 对话历史（消息、工具调用与结果）      上一单元的消息列表
├── 工具说明（tools schema）            可用工具及其参数格式
└── 本次用户输入                        你刚敲下的那行字
```

注意最后一项出现在**底部**：如果把"稳定不变的材料"排在前面、"易变的内容"排在后面，对一类重要机制（缓存，单元 08）非常有利——这是程序的排布取舍，不是巧合。

# 单元 03 · 空间快不够了：用量怎么算，什么时候整理

> 对应交互：预算演算器（五个数字预设 + 自由改参数，实时看两条线判定）。
>
> 这一单元的计算量最大。建议：先跟着五个例子走一遍，再自己改一个数字预测结果。

## 先补一个最小的单位：token

要谈"空间"，先得认识丈量单位。而这个单位，大部分读者平时根本不会遇到。

**【人话】** 说白了，模型不是按"字"处理文字的，而是按 **token（令牌）**——一种把文字切碎后的小块。你写的一个词、半句话、一个标点，都可能被切成若干个 token。**模型的一次请求能装多少 token，是有硬上限的**。

这个上限叫**上下文窗口**（context window）。请求里的全部材料（指令、历史、工具结果、你的输入）加上模型的输出，共用这一个大池子——**不是"输入一个窗口、输出另一个窗口"**。

token 和字数怎么换算？分三种口径，别混：

| 口径 | 说明 | 用途 |
|---|---|---|
| 模型真实 tokenizer | 服务端把文本切块后的准确数量 | 官方计费与上限的最终裁判 |
| 服务端返回的 usage | 每次响应附带"这次输入/输出各多少 token" | 程序校准本地估算的依据 |
| 本地近似估算 | Codex 固定快照的粗估：**文本 UTF-8 字节数 ÷ 4，向上取整** | 在服务端返回之前，程序自己先估个大概 |

对第三行做几个**字节课**计算（教学演示）：

```text
"hello"            → 5 字节          → ceil(5/4) = 2 tokens
"Plan the trip."   → 14 字节         → ceil(14/4) = 4 tokens
一个汉字"回"        → 3 字节（UTF-8） → ceil(3/4) = 1 token
"下午4点前返校"     → 4 个汉字 + 2 个ASCII字符 ≈ 4×3 + 2 = 14 字节 → 4 tokens
```

**【当心】** 这个"÷4"是 Codex 内部的**近似口径**，不是任何模型的真实计费标准；对中文是粗估。真实数字以服务端 usage 为准。教程后续凡是本地估算都标"近似"。

## 场景：它怎么知道"快装不下了"

小林的会话聊了两个小时：行程改了四版、工具查了十几次。忽然屏幕上一行提示：**"正在压缩上下文……"**

小林没做任何操作。程序是怎么知道"该整理了"的？它心里有几本账？

## 四本账，先给名字

程序维护四条数字（名字沿用真实字段含义，教学变量名做了简化）：

| 变量 | 含义 | 通俗理解 |
|---|---|---|
| **W** | 模型解析后的**上下文窗口**（context window） | 这张桌子总共多大 |
| **p** | 有效窗口比例（字段缺省 **95**，可被模型元数据或配置改写） | 桌子实际允许用多大比例 |
| **H = W × p ÷ 100** | **有效窗口**（usable context window） | 桌子真正的可用上限 |
| **A** | 当前活动上下文用量（active context tokens） | 桌上现在堆了多少 |
| **P** | 本窗口开始时的**输入基线**（prefill） | 你收拾过一次桌子后，当时的起点高度 |

再认识两条"线"的原料：

- **范围限额**：默认口径（`total`）下是 `min(M字段, 90% × W)`，其中"90% × W"是**基础线**；`M字段`是模型元数据或用户配置给出的自动整理限额（没有就用基础线；有就取更小者）。
- **整段线**：就是有效窗口 H。

以及一个容易忽略的角色——**用量 A 是怎么量出来的**：

```text
中文伪代码：当前用量的来源
  A = 上次服务端返回的 usage.total_tokens
      + 估算（在上次模型输出之后、本地新加入的条目）
      + 若服务端未含旧推理内容，另做补计
```

即：**A 不是每次把所有文本重新数一遍，也不是从会话开头累计到现在的账单总和**；它以服务端上一次的实测为锚点，加上本地刚加进来的材料。

> **本节最重要的一句话**：程序判断"该整理了"要同时看两条线——**范围线**（对 total 口径是"从会话开始积累的全部材料"，对增长口径是"从基线之后增长的量"）**或** **整段线**（所有材料不得超过的有效窗口 H）。任一满足，则"到线"为真。

### 为什么是 90% 和 95%，不是 100%？

两个原因（都指向同一件事：**要给"输出"和"整理动作本身"留空间**）：

1. 模型回复也吃同一个池子。让输入顶到 100%，就没有空间写回复了。
2. **整理本身也要调用模型**（生成摘要/交接材料）。它需要输出空间来写摘要——如果输入已经顶满，摘要就写不完。

所以：

- **90% 基础线**（`(W×9)/10`，整数除法）是这一实现的**自动整理下限**，不是模型原理规定；且一旦模型元数据或用户配置给了更低的限额，取更小者。
- **95%** 是有效窗口比例的**字段缺省**；它也可能被具体模型改写。两条线都会触发，但一条"提前整理"、一条是"可用上限"，管的事不同。

## 五个数字例子（交互版里可点击预设）

统一舞台（**教学演示**数字）：W = 100,000 tokens、p = 95、无更低模型限额、无用户覆盖 →
**基础线 = 90,000；H = 95,000**。默认范围口径 `total`（A 对范围线做比较）。

每个例子先自己算一遍，再看结论。

**例 1 · 差一点，不到线**：A = 89,999，无增长口径。
→ 89,999 < 90,000；89,999 < 95,000。**两条线都没到**，不整理。

**例 2 · 恰好到线**：A = 90,000。
→ 90,000 ≥ 90,000。**范围线到线**（"达到"用的是"≥"，不是">"），进入整理流程。

**例 3 · 增长未到线、整段也没到**：用户把范围口径设为增长（`body_after_prefix`）并给出限额 C = 30,000；P = 60,000；A = 85,000。
→ 增长 = A − P = **25,000**，25,000 < 30,000，增长线没到；整段 85,000 < 95,000，也没到。**不整理**。
（如果这里用默认 total 口径：85,000 < 90,000，同样不整理——两种口径这个例子都不触发。）

**例 4 · 增长没到，但整段顶到桌子边**：同样的 C = 30,000；P = 80,000；A = 95,000。
→ 增长 = 15,000 < 30,000，增长线没到；但整段 **95,000 ≥ 95,000**——**整段线到线**，仍然要整理。
这个例子说明：**范围线放宽，不等于整段线也跟着放宽**。整段线是独立的硬检查。

**例 5 · 模型限额与用户覆盖怎样改变结论**：
- 假设模型元数据给出限额 M = 85,000（低于 90% 基础线）→ 范围限额 = min(85,000, 90,000) = **85,000**。此时 A = 87,000 就已经到线（而例 1 的舞台下它还差得远）。
- 假设用户显式配置 C = 50,000 → 解析后 M 字段被覆盖为 50,000 → 范围限额 = min(50,000, 90,000) = **50,000**。A = 52,000 就到线。
- 反方向：用户配置 C = 120,000（高于基础线）→ 仍取 min(120,000, 90,000) = **90,000**，**90% 的钳制保留**。
- 特例：只有 M 没有 W（窗口未知）→ 直接取 M。

五个例子的结论对照表：

| 例 | 关键是哪条线 | 结论 |
|---|---|---|
| 1 | —（都未到） | 不整理 |
| 2 | 范围线（恰好 ≥） | 整理 |
| 3 | 增长口径：增长线未到 + 整段未到 | 不整理 |
| 4 | 整段线（95,000 ≥ H） | 整理 |
| 5 | min 钳制改变范围线本身 | 取决于钳制后的值 |

## "到线"之后：谁在什么时候执行

"到线"只是**第一层**判断。真正发起整理前，还有**第二层**——执行的时机与入口（固定快照中已定位的入口）：

| 入口 | 触发条件 | 初学者读法 |
|---|---|---|
| **新任务开始前**（轮前） | 检查当前用量是否到线 | 开始下一步之前先看桌子满没满 |
| **同一任务还要继续**（轮中） | 模型还要继续（`needs_follow_up`）**且**（有新窗口请求 **或** 到线） | 活还没干完，但桌上已经堆不下 |
| **任务完成后的可选整理**（轮后） | 配置的比例 q > 0，且到线或达到 q 对应的比例；无待处理输入；未取消；未启用专门的实验预算模式 | 干完一段后"提前收拾"；**缺省关闭**（q 缺省为 0） |
| **切换模型** | 前后双方都有"整理兼容性哈希"且不同；或换到了窗口更小的模型且当前用量触及新条件 | 换了更小的桌子，或旧交接材料不兼容 |
| **手动 /compact** | 不要求到线，随时可以 | 你主动说"帮我把桌子收拾一下" |

轮前检查有一个**要特别记住的细节**：它发生在**新用户输入写入之前**。源码在这一处留了 TODO，明说了现状：**还没有把"即将写入的新输入"估算进去**。所以一次巨大的粘贴（比如把 5 万字日志直接粘进对话）仍可能一步跨过安全线。这是"有界但非万能"的真实工程取舍。

## 真实实现：两段源码

**第一段**：90% 基础线与 min 钳制的来源（`openai_models.rs` L529–540）：

```rust
// codex-rs/protocol/src/openai_models.rs  L529–540（节选）
pub fn auto_compact_token_limit(&self) -> Option<i64> {
    let context_limit = self
        .resolved_context_window()
        .map(|context_window| (context_window * 9) / 10);   // ① 90% 基础线
    let config_limit = self.auto_compact_token_limit;        // ② 模型字段（可被用户配置覆盖）
    if let Some(context_limit) = context_limit {
        return Some(
            config_limit.map_or(context_limit, |limit| std::cmp::min(limit, context_limit)),
        );                                                   // ③ 取更小者
    }
    config_limit                                             // ④ 窗口未知则直接用字段
}
```

逐句解读：

- ① `(context_window * 9) / 10`：整数运算下就是"取 90% 向下取整"。**90% 不是玄学比例**，是这份实现选定的整理基础线。
- ② `self.auto_compact_token_limit`：模型元数据里的字段；注意它是一个 `Option`（**可能没有值**——"None 不是 0"）。没有值不代表限制为零，而是"没有专门限制，用基础线"。
- ③ `map_or(context_limit, min)`：有字段值时取 **min（字段值, 基础线）**；这一步就是例 5 的钳制。**用户配置不是无限上调的后门**。
- ④ 窗口未知（`None`）时直接用字段——这样即使算不出 90%，至少有字段兜底。

**第二段**：两条线的最终判断（`context_window.rs` L60–110，节选）：

```rust
// codex-rs/core/src/session/context_window.rs  L60–110（节选）
let (auto_compact_scope_tokens, auto_compact_scope_limit, …) =
    match config.model_auto_compact_token_limit_scope {
        AutoCompactTokenLimitScope::Total => (
            active_context_tokens,                       // 范围用量 = 全部
            model_info.auto_compact_token_limit(),       // 范围限额 = 90% 线/字段 min
            None,
        ),
        AutoCompactTokenLimitScope::BodyAfterPrefix => {
            let window = sess.auto_compact_window_snapshot().await;
            let baseline = window.prefill_input_tokens.unwrap_or(active_context_tokens);
            let scope_limit = config.model_auto_compact_token_limit
                .or_else(|| model_info.auto_compact_token_limit());
            (
                active_context_tokens.saturating_sub(baseline),   // 用量 = 增长量
                scope_limit,
                window.prefill_input_tokens,
            )
        }
    };

let full_context_window_limit = model_info.resolved_context_window().map(|w| {
    w.saturating_mul(model_info.effective_context_window_percent) / 100  // H = W×p/100
});

let full_context_window_limit_reached =
    full_context_window_limit.is_some_and(|limit| active_context_tokens >= limit);
let token_limit_reached = buffered_limit
        .is_some_and(|limit| auto_compact_scope_tokens >= limit)
    || full_context_window_limit_reached;               // 两条线，OR
```

逐句解读（只抓关键语法）：

- **`match` + 两个分支**：这就是 `total` 与 `body_after_prefix` 两种口径的由来；枚举的默认值是 `Total`。
- **`saturating_sub`（饱和减法）**：`A − P` 若为负，结果不是负数、也不会回绕成天文数字，而是**夹到 0**。**"饱和减法"不能读成 `max(0, 差值)` 那么简单**——它在语义上是"防下溢"的整型安全操作，效果类似但动机不同（差值在这条路径本来就可能为负：基线可能大于当前值）。教学上记住结论：**增长口径下不会出现负增长**。
- **`unwrap_or(active_context_tokens)`**：基线还没有时（本窗口还没收到过服务端 usage），就把"当前用量"当作基线——这样增长 = 0，"还没开始增长"是安全默认。**None 在这里不当作 0**：不是"基线为零、全部都是增长"。
- **`is_some_and(...) || ...`**：两条线各自先判断"有这条线 **且** 到线"，然后 **OR**。任一为真，`token_limit_reached` 为真。
- **`buffered` 前缀**：范围线在实验性的 TokenBudget 配置下可能加一个"后备缓冲"。**本教程主线把它排除**；看到这个词时记住：默认路径下它就是范围限额本身。

## 自测

**① 演算题**：W = 200,000，p = 95，模型字段 M = 150,000。求基础线、范围限额、H，并回答 A = 152,000 时到线吗？

# 单元 04 · 整理之后带上什么：保留算法

> 对应交互：压缩四幕演示（自动/手动分开；旧材料 → 生成产物 → 成功替换 → 后续请求）。自动模式下，**触发条件不成立会停在第一步并说明原因**，不演示假的成功。

## 场景：整理=全部换一段摘要吗？

小林担心："它整理的时候，是不是把我们聊的东西都扔了，只留一小段总结？"

答案分两半：

- **旧材料的大部分确实不再逐条带上**——这是整理的意义；
- **但有两种东西会被尽力留下**：① 你的**近期原话**（在预算内原样保留）；② **当前有效的规则与环境**（整理后重新摆回来）。

而且"整理"的真实产物有两种形态，先认识它们，再谈保留。

## 两条产物路径：先看你的服务商是谁

代码里整理有两条实现路径，由 **provider（模型提供方）的能力**决定（不是随机选，也不是用户开关）：

| 路径 | 谁来写"交接材料" | 产物形态 | 何时走这条 |
|---|---|---|---|
| **本地摘要路径**（local / responses） | **客户端编排**：程序挑好材料，让模型写一份**文字交接摘要** | 你能读懂的一段文字摘要 | 提供方不支持远端压缩时 |
| **远端压缩 v2**（remote_v2） | **服务端**完成压缩 | 一个**压缩条目**（`encrypted_content` 加密内容，客户端只见其形状，读不到明文） | OpenAI 官方 / Azure 系 provider **默认**走这条 |

**这是一条本次核查新增的事实**：在本快照中，`ProviderCapabilities::from_config` 对 **OpenAI 与 Azure responses 系**的提供方默认给出远端压缩支持（`RemoteCompactionSupport::V2`），其他提供方默认不支持（即走本地摘要）。换言之：**用官方 OpenAI 账号的用户，默认看到的是远端 v2 路径的产物**——那段"交接材料"不是你能读的文字摘要，而是服务端生成的加密压缩块。

```rust
// codex-rs/model-provider/src/capabilities.rs  L31–41（节选）
let defaults = Self {
    remote_compaction: if info.is_openai()
        || is_azure_responses_provider(&info.name, info.base_url.as_deref())
    {
        RemoteCompactionSupport::V2          // 官方 OpenAI / Azure → 默认支持 v2
    } else {
        RemoteCompactionSupport::Unsupported // 其他 → 默认回退本地摘要
    },
    ..Self::default()
};
```

（该判断可被 provider 配置里的显式 `remote_compaction` 覆盖，见同文件 L42–51；官方测试 `openai_provider_enables_remote_compaction` 断言了 OpenAI provider 的默认值是 V2。）

另外注意：那条 `RemoteCompactionV2` 的 **feature 开关**在本快照中已标记为 `Stage::Removed`（不再作为本地开关使用），它现在只用于**无条件**向服务端声明"本客户端支持远端压缩"（构建 `x-codex-beta-features` 头时特判直通）。**"默认走远端"的判定点是 provider 能力，而不是这个名字里有 V2 的开关**——这种"名字还在、语义变了"的痕迹，是读源码时最需要防的坑之一。

## 两条路径的保留算法：共同骨架

无论哪条路径，保留都遵循同一副骨架：

```text
中文伪代码：整理时的保留骨架（教学归纳）
  ① 筛候选：谁有资格"原样留下"？      # 类型过滤，不按语义评重要性
  ② 用预算：从新到旧把候选装进共享预算  # 最近的先装
  ③ 边界处理：装不下的边界条目截短（保头尾）
  ④ 另加产物：摘要 / 压缩条目单独追加   # 不占"原样保留"的预算
  ⑤ 重组规则：重新渲染当前工作状态与规则
```

两条路径在每一步的参数不同：

| 步骤 | 本地摘要路径 | 远端 v2 |
|---|---|---|
| ① 候选 | **只收真正的用户消息**（排除旧摘要消息——通过摘要前缀识别） | 用户消息 + 钩子提示；AgentMessage 有条件（排除子代理进度/完成通知，单条 ≤ 10,000 tokens）；特殊客户端工具结果**要开关**（本快照默认关闭） |
| ② 预算 | **20,000 tokens**（源码常量） | **64,000 tokens**（源码常量） |
| ③ 边界 | 纯文字且放得下→原样；否则生成**文字回退**：`truncate_text(…, 剩余预算)`（保头尾）；然后**停止** | 按"组"处理（消息与附带通知成组）；特殊工具结果**整条保留，否则停止**；普通消息边界截短；图片另有预算 |
| ④ 产物 | 追加**文字摘要**（可读） | 追加服务端**压缩条目**（含加密内容） |
| ⑤ 重组 | 两者相同：重新构建初始上下文 + 渲染当前 `WorldState` | 同左 |

### 一个完整的数字演算（本地摘要路径）

用**真实单位**（不是缩比格数），假设预算 P_max = **20,000**（源码常量），三位用户的过往原话（教学数据）：

```text
从旧到新的用户消息：M1 = 12,000 tokens、M2 = 10,000、M3 = 6,000

倒着装（从新到旧）：
  装 M3（6,000 ≤ 20,000）     → 剩 14,000
  装 M2（10,000 ≤ 14,000）    → 剩 4,000
  看 M1（12,000 > 4,000）     → 边界截短：把 M1 的头、尾各留一部分，
                                合计约 4,000 tokens 的片段 + 截断标记
  按规则在此停止（不回头再挑更早的小消息补缝）

最终顺序（还原时间顺序 + 产物另加）：
  [M1 截短片段] → [M2] → [M3] → [新摘要]
  ＊另外：当前规则与环境在 ⑤ 被重新摆回到列表靠前位置
```

**【当心】** 从这个演算里能读出两条重要边界：

1. **"重要"不参与筛选**——算法不判断"M1 里有没有关键约束"，只看类型、预算和顺序。M1 中间若有"必须 14:30 集合"，它要么在头尾片段里侥幸留下，要么只靠摘要传递——**摘要能不能保住它，客户端代码无法保证**（那是模型生成质量的问题，未运行实验不能编造结论）。
2. **20,000 不是"触发线"，也不是"最终请求大小"**——它只是"给旧用户原话留的共享预算"。同一封请求里还有重组后的规则、摘要本身、工具说明等。三组数字（20,000 / 64,000 / 触发线）互相独立。

### 远端 v2 的边界细节（比本地多一层）

远端 v2 的边界处理有几个本地没有的分支（教学归纳 + 源码锚点）：

- **整组保留**：消息与它的"附带通知"作为一组处理，预算够则整组纳入；
- **特殊工具结果**：要求**整条**保留；放不下就**停止**继续纳入更早条目（不拆半条）；本快照中"保留特殊客户端工具结果"的开关**默认关闭**；
- **剩余为零后**：循环用 `continue` 跳过（不再纳入），但不会再回头补装更早条目——"从新到旧、一旦装不下就定格"的主线成立；
- **图片预算**：图片条目单独受 `compaction_image_budget`（本快照 **Stable、默认开启**）约束；超大图片可能耗尽边界预算且**不回填**更早消息——"64,000 纯文字规则"不能拿来保证原图完整。

## 自动还是手动：条件和行为都不同

压缩演示的两种方式要分清（交互版中两者选项独立、互不偷偷切换）：

| | **自动压缩** | **手动 /compact** |
|---|---|---|
| 前提 | **必须先"到线"**（单元 03 的两条线）；条件不成立时**不会发生**——演示会停在第一步说明原因 | 不要求到线，随时可用 |
| 过程中 | 可能发生在轮前 / 轮中 / （可选的）轮后 | 用户主动发起；程序**停止当前旧任务**，另起一个专门的整理任务 |
| 完成后 | 轮中成功 → **继续原来的工作循环**（工具循环接着跑） | 整理本身作为一次独立任务完成；**不等于原任务自动续跑**（你想继续需要再发输入） |
| 产物 | 与路径有关（本地摘要 / 远端压缩块） | 同左 |

**【当心】** 不要混用"方式的自动"与"观看的自动"：交互教程里"逐步阅读 / 自动播放"是**演示的观看方式**（有速度、暂停、回看），与"自动压缩 / 手动压缩"是两回事。改参数、回看、重置都不会偷偷改变你的选择。

## 真实实现：保留算法的三个关键片段

**片段一**：20,000 常量与"从新到旧"的骨架（`compact.rs` L690–770 节选）：

```rust
// codex-rs/core/src/compact.rs（节选；完整片段见章末链接）
const COMPACT_USER_MESSAGE_MAX_TOKENS: usize = 20_000;      // L63

let mut remaining = max_tokens;
for message in user_messages.iter().rev() {                 // ① 从新到旧
    if remaining == 0 { break; }
    let tokens = approx_token_count(&message.message);      // ② 每条单独估算
    let content = if tokens <= remaining
        && content.iter().all(|part| matches!(part, ContentItem::InputText { .. })) {
        content.clone()                                     // ③ 纯文字且装得下 → 原样
    } else {
        vec![ContentItem::InputText {
            text: truncate_text(&message.message, TruncationPolicy::Tokens(remaining)),
        }]                                                  // ④ 否则 → 文字回退（保头尾）
    };
    selected_messages.push(…);
    if tokens > remaining { break; }                        // ⑤ 边界处理完就停
    remaining = remaining.saturating_sub(tokens);
}
selected_messages.reverse();                                // ⑥ 还原时间顺序
history.push(CompactionSummary::new(summary_text));         // ⑦ 产物另加
```

逐句解读：

- ① `iter().rev()`：**倒着遍历**（从最新到最旧）。语义是"最近的用户话优先获得预算"。
- ② `approx_token_count`：每条用**近似估算**（就是"字节 ÷ 4"那套），不是精确 tokenizer。
- ③ `all(|part| matches!(part, InputText))`：内容块**全是文字**才可能原样；带图片的消息不进这条分支。
- ④ `truncate_text`（单元 05 详解）：超预算或带媒体 → 生成**文字回退**，保头尾。**图片在这个分支被换成文字**——"带图消息原图必留"是错的。
- ⑤ 注意顺序：先把边界消息推入列表、**然后** `break`——"边界收进来，循环到此为止"，不会继续挑更早的。
- ⑥ `reverse()`：选的时候从新到旧，**最终顺序仍按时间正序**。摘要排最后。
- ⑦ `CompactionSummary` 是**另加的**，不占 20,000 预算。

**片段二**：候选过滤——"排除旧摘要"怎么做的（`compact.rs` L587–603）：

```rust
fn compacted_user_message<'a>(…) -> Option<CompactedUserMessage<'a>> {
    let Some(TurnItem::UserMessage(user)) = crate::event_mapping::parse_turn_item(item)
    else { return None; };                                   // ① 不是真用户消息 → 跳过
    let message = user.message();
    if is_summary_message(&message) { return None; }         // ② 是旧摘要 → 跳过
    Some(CompactedUserMessage { … })
}
fn is_summary_message(message: &str) -> bool {
    message.starts_with(format!("{SUMMARY_PREFIX}\n").as_str())  // ③ 靠前缀识别
}
```

- ① `let … else`：这是 Rust 的"守卫"写法——不满足条件直接返回 `None`（跳过这一条），满足才继续往下。
- ②③ 摘要消息被编码成"用户消息"形态（历史里没有单独的"摘要"角色），所以**靠一个固定前缀识别并排除**。**同一个变量的含义要看清上下文**：这里 `user.message()` 可能是"你真正说过的话"，也可能是"上一轮摘要伪装成的用户消息"——算法用前缀把它们分开。

**片段三**：远端 v2 的加载顺序与"整组"（`compact_remote_v2.rs` L625–722 摘述）：

```rust
// 骨架（非逐行）：
for group in groups_from_newest_to_oldest {
    if remaining == 0 { continue; }                       // ① 已清零：跳过，不再纳入
```

## 自测

**① 定位题**：小林使用 OpenAI 官方账号。压缩完成后，他在历史里看到的交接材料最可能是什么形态？
A. 一段可读的中文摘要
B. 一个含 `encrypted_content` 的压缩条目
C. 旧消息原样全在
D. 什么都没有

**② 演算题**：本地摘要路径，预算 20,000；用户消息从旧到新为 9,000 / 15,000 / 8,000。写出选取过程与最终顺序。

**③ 判断题**："20,000 是压缩触发阈值，一超过就开始压缩。"（对/错，说明理由）

**④ 设计意图题**：为什么两条路径都"从新到旧"，而不是"按重要程度排"？

<details>
<summary>参考答案</summary>

**① B。** 官方 OpenAI provider 默认 `RemoteCompactionSupport::V2`，产物是服务端压缩条目（客户端侧含加密内容）。A 是本地摘要路径（提供方不支持远端压缩时）的形态。

**②** 倒着装：先 8,000（剩 12,000）；再 15,000 > 12,000 → **边界截短**：15,000 这条保留头尾合计约 12,000 tokens 的片段，收尾停止（更旧的 9,000 不再尝试）。最终顺序：**[15,000 的截短片段] → [8,000] → [摘要]**（外加最前面重组好的规则与环境）。注意 9,000 那条：**它不会"补缝"**——算法在边界消息后停止。

**③ 错。** 20,000 是**整理后给旧用户原话的直接保留预算**。触发判断看的是单元 03 的 90% 范围线与 95% 整段线。两者对象、用途完全不同——这是"三组不能混的数字"里最重要的两组。

**④** 因为"重要程度"无法在客户端廉价又可靠地评估：读懂语义再挑等于又跑一次模型（成本、延迟都不可接受，而且可能挑错）。**时间新近性是可用、稳定、便宜的代理信号**；深层语义的保全被交给摘要/压缩产物的生成环节（模型来做），客户端只负责机械规则。这也是"整理会不会保住你关心的细节"最终无法被客户端代码单方面保证的原因。
</details>

# 单元 05 · 信息在哪一步没的：三处限长与裁剪

> 对应交互：裁剪对照器（关键行放在中段，滑动预算直观看到"消失的位置"）。

## 场景：AI 忘了 14:30，但它记得 16:00

小林的工具查回了一段 300 行的公交时刻表。表格中间有一行：`"测试提醒：集合点东门，14:30 前必须到达。"`（教研组要求的补充约束）。

后来 AI 安排行程时，16:00 返校它记得牢牢的，**14:30 却像从没出现过**。

去哪里找责任？如果只盯着"是不是压缩惹的祸"，会错过前面还有**两道关卡**。完整链路是**三处限长**：

```text
第①处：工具出口         第②处：活动历史            第③处：摘要请求
原始输出 300 行  →   写进当前列表时的副本   →   整理时给模型看的副本
（实际发给模型前）     （历史裁剪，存档另存）     （超限还会再缩）
```

## 第①处：工具出口——"给模型的预览"

命令产生 100,000 行输出，不等于模型收到 100,000 行。第一道关卡在**工具结果交给模型消费之前**：先按预算裁剪，然后**包一层说明头**，注明原始规模：

```text
Warning: truncated output (original token count: 24800)
Total output lines: 300

（裁剪后的内容：开头一部分 …N tokens truncated… 结尾一部分）
```

对应实现 `formatted_truncate_text`（`codex-rs/utils/output-truncation/src/lib.rs` L23–34）：内容超出字节预算时，先记录**原始近似 token 数**与**总行数**，再做"保头尾"裁剪，最后拼上说明头。**所以模型看不到"完整原文"，它看到的是一份带警告的预览。**（"原始 token 数"这个数字很关键：它让模型知道"我拿到的是残缺的"。）

## 第②处：活动历史——写进列表时的独立裁剪

工具结果"登记进当前列表"时，还会经历一次裁剪，规则是：

- **裁剪对象**：进入**活动历史**的那份副本（`FunctionCallOutput` / `CustomToolCallOutput` 的内容）；
- **原信封保留**：同一时刻，写入会话存档（rollout）的是**未裁剪的原载荷**——这两份是不同的东西；
- **预算来源**：优先用条目自带的覆盖值；否则用模型策略附带的"序列化余量"（在预算基础上加 **20%**——给 JSON 转义、结构包装留的空间）。

源码注释把这个设计说得很直白：

```rust
// codex-rs/core/src/context_manager/history.rs  L517–519（原文注释）
/// Records output and annotates the original envelopes with captured provenance.
/// Tool output truncation applies only to live history, preserving full rollout payloads.
```

即"**裁剪只作用于活动历史；存档的完整载荷保留**"。为什么？因为活动历史要配平窗口，而存档要承担"以后还能查回来"的职责。

但是——**【当心】** 存档保留 ≠ 处处完整。存档链路自身还有独立的预算（例如分片存储模式下命令输出与 MCP 结果各有 **64 KiB** 的持久化上限，超出加 `... command output truncated for persistence ...` 标记）。**"磁盘上有原文"这句话永远要追问一句：哪一层、哪个文件、上限多少。**

### 多块工具输出怎样共用一个预算

一个工具结果里可能有多个内容块（多段文字、图片、音频）。处理函数 `truncate_function_output_items_with_policy`（L164–251）的行为：

- 文字块**按顺序**消耗块内共享预算；装得下的整块留；
- 装不下的边界块**截短**（又是保头尾），截完预算置零；
- 预算耗尽后剩余文字块**整体略去**，结尾加 `[omitted N text items ...]` 提示；
- **图片直接保留**（在这层函数不扣预算）；音频按估算消耗，装不下则整体略去并加 omitted 提示。

注意最后两点与远端压缩的图片预算是**两套逻辑**（一个是工具出口层，一个是压缩保留层），不要画成一个全局滑块。

## 第③处：摘要请求——"整理用的材料也会被缩"

到了整理环节，程序给模型看的是一份**历史副本**。若这份副本自己都超限（比如刚好卡在极限），程序会**移除副本里最早的条目再试**——"为了压缩所用的材料，也可能被进一步缩减"（细节见单元 07）。

**链条总结**：一条关键信息要活到下一次请求，必须连续通过"出口 → 历史 → 整理 → 恢复"四关。**任何一关都可以成为丢失点，排查时不要只怀疑压缩。**

## 裁剪算法本身：头、尾与标记

现在把"保头尾"拆开看。裁剪函数在 `codex-rs/utils/string/src/truncate.rs`，核心是**近似 token 预算 → 转换字节预算 → 头尾分配 → UTF-8 边界修正 → 拼接标记**：

```text
中文伪代码：头尾裁剪（近似 token 口径）
  输入：文本 s、预算 max_tokens
  若 s 为空 → 返回空
  若 max_tokens > 0 且 字节数(s) ≤ max_tokens×4 → 原样返回   # 装得下就不裁
  max_bytes = max_tokens × 4
  左预算 = max_bytes ÷ 2          # 整数除法，奇数时少 1 字节
  右预算 = max_bytes − 左预算      # 奇数时多 1 字节（左右并非严格均分）
  头部 = s 从 0 到 左预算的最近 UTF-8 边界
  尾部 = s 从 (总长−右预算) 的最近 UTF-8 边界到结尾
  标记 = "…N tokens truncated…"（N 按被移除字节数÷4 估算）
  返回 头部 + 标记 + 尾部
```

真实代码（节选）：

```rust
// codex-rs/utils/string/src/truncate.rs（节选）
const APPROX_BYTES_PER_TOKEN: usize = 4;                        // L4

pub fn approx_token_count(text: &str) -> usize {                // L101–104
    let len = text.len();
    len.saturating_add(APPROX_BYTES_PER_TOKEN.saturating_sub(1)) / APPROX_BYTES_PER_TOKEN
}                                                               // 等价于 ceil(字节/4)

fn split_budget(budget: usize) -> (usize, usize) {              // L156–159
    let left = budget / 2;
    (left, budget - left)                                       // 左 floor；右 = 总数 − 左
}

fn format_truncation_marker(use_tokens: bool, removed_count: u64) -> String {
    if use_tokens { format!("…{removed_count} tokens truncated…") } // L161–167
    else { format!("…{removed_count} chars truncated…") }
}

fn assemble_truncated_output(prefix: &str, suffix: &str, marker: &str) -> String {
    let mut out = String::with_capacity(prefix.len() + marker.len() + suffix.len() + 1);
    out.push_str(prefix);
    out.push_str(marker);                                        // L177–183
    out.push_str(suffix);
    out
}
```

### 两个亲手算的数字例

**例 A（英文，15 字节预算）**：文本为 20 个字母 `abcdefghijklmnopqrst`（与题无关，就是 20 个字符），预算 15 字节。

```text
左 = 15÷2 = 7 → 头部 = "abcdefg"
右 = 15−7 = 8 → 尾部 = s[20−8=12..] = "stuvwxyz"
移除 = 20−15 = 5 字节 → N = ceil(5/4) = 2 → 标记 "…2 tokens truncated…"
结果：abcdefg…2 tokens truncated…stuvwxyz
（数一数：保留 7+8 = 15 字节内容 + 标记；标记是额外添加的）
```

**【当心】** 两个不能想当然的点：

1. **左右不是严格均分**：15 字节时左 7 右 8——奇数预算差的那 1 字节给了尾部。
2. **标记不占预算**：`"…2 tokens truncated…"` 是额外拼上去的。所以**"输出含标记后一定严格等于预算"是错的**——真实输出会比预算略长一点。

**例 B（中文，字符边界）**：假设一段 68 字节的中文（约 22 个汉字 + 标点），预算 20 字节。

```text
左 = 10 字节 → 停在最近的 UTF-8 字符边界：10÷3 = 3 个汉字（9 字节）≤ 10 → 头部 9 字节
右 = 10 字节 → 从总长−10 = 58 字节向上对齐字符边界：最近边界是 60 → 尾部 8 字节
移除 = 68 − 20 = 48 字节 → N = ceil(48/4) = 12 → 标记 "…12 tokens truncated…"
```

**为什么边界要对齐**：汉字在 UTF-8 里占 3 个字节，切在中间会把 1 个字符切成无效的半截字节。真实代码用 `floor_char_boundary`（向下找边界）和 `ceil_char_boundary`（向上找边界）处理——**裁剪按字节算，但落刀看字符**。

### 把约束追踪走一遍（交互版演示的正是这个）

回到小林的 300 行时刻表，用"三段放置"演示约束在最坏情况下的命运：

```text
原始（教学构造，300 行 ≈ 24,800 近似 tokens）：
  行 1–10     ：线路基本信息……（头部）
  行 11 附近  ：'14:30 集合点东门' ← 关键约束『放在头部』
  行 150 附近 ：'临时……测试提醒：14:30…' ← 关键约束『放在中部』
  行 290–300  ：末班车 16:10（尾部）

按"保头尾"裁剪后（示意）：
  头部保留：行 1–10（约束在行 11 附近时可能刚好擦边留下）
  中部消失：行 11–289 整体被移除，只剩 "…N tokens truncated…"
  尾部保留：行 290–300

结论速览：
  约束放『中部』 → 裁剪阶段就消失，后面三步（摘要/压缩/恢复）再努力也没机会看见它
  约束放『已读部分』→ 还可能被摘要带走
```

**【当心】** 这是本单元最实用的一条工程建议：**关键约束要放在工具输出的头尾（或让工具显式置顶），不要指望它躺在中段侥幸过关**。同理，人对模型的表达也一样：最要紧的约束写在消息的开头或结尾。

## 排查四问：丢失点定位表

一条约束不见了，按顺序问四个问题（而不是直接怪"压缩"）：

| 问题 | 去哪查 | 判断线索 |
|---|---|---|
| **① 从未读进来？**（发现/可信/预算） | 规则文件位置、项目可信状态、32 KiB 项目规则预算 | 文件在搜索范围里吗？关键行是不是在文件**尾部**而被截掉？ |
| **② 进过历史，但被裁了？**（出口/活动历史） | 工具输出实际形态 | 有 `Warning: truncated` 头吗？关键行原位置在中段吗？省略标记 `…N tokens truncated…`？ |
| **③ 进过历史，但摘要漏了？** | 摘要/压缩产物（本地路径可读文本；远端路径读不到明文） | 直接问模型"复述这条约束"只能间接验证；最终以任务结果为准 |
| **④ 都在，但旧决定没作废？** | 历史中同一决定的新旧版本 | 搜同一决定名：是否新旧并存？最简单的人为修复：明确说一句"**之前那条 XX 作废，改用 YY**" |

**四问的意义**：把"模型不听话"分解成可查的信息链路问题。每一问都有对应的"人为对策"：①把文件放在读得到的范围/头部；②把关键信息放在头尾；③重要约束自己再强调一次+用任务结果验证；④显式声明作废。

## 真实实现：再多看两眼

裁剪函数还有一个"预算为 0"的极端分支——只返回标记本身（`max_bytes == 0` 时 `format_truncation_marker(…)`，L67–73）；以及**字符口径**的兄弟函数 `truncate_middle_chars`（按字节）、`truncate_middle_with_marker`（标记**会从预算里扣**的硬限版本）。两族函数的差别：

- **token 预算版**（我们主线讲的）：标记额外添加，适合"接近即可"的模型材料；
- **硬字节限额版**：标记先从预算扣掉，保证结果**真的不超过**字节上限，适合硬约束（如协议上限）。

**同一件事的两个函数有细微语义差**，这正是"读函数名不够、要看注释与调用方"的例子。

# 单元 06 · 关掉再打开：三层记录与恢复

> 对应交互：三层状态机（压缩前 / 压缩后 / 关闭 / 重开 四态 × 磁盘、活动历史、下次请求 三层）。

## 场景：昨天的会话，今天续上

小林合上电脑。今天打开终端，`codex resume`，选中昨天的会话，继续问："把行程再压缩一版。"

AI 接得上话。小林好奇：**昨天压缩过一次，今天恢复的到底是什么？** 是完整的原始记录，还是那一小段摘要？

答案要用**三层**来讲——过去很多误解，都来自把这三层当成一层。

```text
第③层 下一次模型请求        ← 真正影响模型行为的，只有这一层
     ↑ 组装自
第②层 当前活动历史（内存）   ← 可能已被裁剪/压缩/恢复改写
     ↑ 加载自；压缩时又被写回
第①层 会话存档（磁盘记录）   ← 事件逐个追加写入，压缩不删除旧记录
```

先把三层的边界说清（**这是本单元的主结论**）：

- **磁盘上有** ≠ **活动历史里有**；
- **活动历史里有** ≠ **下次请求带上**（还要过组装与裁剪）；
- **下次请求带上** ≠ **模型一定照做**（行为是另一层问题）。

## 压缩时到底写了什么

整理完成时程序做两件事（固定快照的实现）：

1. **替换当前活动历史**：用"替代历史"（重组后的规则 + 直接保留的旧消息 + 新摘要/压缩条目）替换内存里的历史；
2. **向磁盘追加一条"压缩检查点"**：一条记录，里面装着这次替代历史的**完整副本**（`replacement_history`）、窗口编号与 ID、用量摘要、恢复元数据等。

```rust
// codex-rs/core/src/session/mod.rs  L4181–4213（节选，省略具体字段取值）
let replacement_history = items.clone();                 // ① 复制替代历史
state.replace_annotated_history(                          // ② 替换内存历史
    items, …, HistoryReplacement::Compaction { … },
);
…
CompactedItem {
    message: metadata.message,                            // ③ 摘要文本（本地路径可读）
    replacement_history: Some(replacement_history),       // ④ 替代历史整份存入检查点
    window_number: Some(metadata.window_number),          // ⑤ 窗口身份
    …window_id / previous_window_id / resume_metadata…,
}
// 随后打包成 RolloutItem::Compacted(…) 交给持久化写入
```

逐点解读：

- ③④⑤ 就是"压缩检查点"的形状：**它保存的不是"被删掉了什么"，而是"替代后是什么"**。旧记录仍留在之前已写入的存档行里——追加式写入，不覆盖（这也是"压缩后能不能找回"的证据基础）。
- **没有任何"删除旧 JSONL"的操作**——但再次强调：**存档保的是文件内容，不是"以后自动回模型"的承诺**。

### 一个容易被忽略的并发细节

整理在后台进行时，用户（或系统）**可能又提了新的目标更新**（比如改需求、改约束）。如果直接拿"整理开始前的快照"覆盖一切，新更新会丢。固定快照的处理是：

```text
在安装替代历史之前：
  先等待已接受更新的持久化完成（持写锁防乱序）
  再扫描当前历史中的所有"目标更新"条目
  把"整理输入快照里没有、替代历史里也没有"的新更新
      —— 按原顺序 —— 追加到替代历史之后
```

即：**"整理期间新接受的更新按原顺序补入替代列表，避免旧快照覆盖新目标。"** 这是"替换历史"为什么不等于"时间倒流"的关键保护。

## 恢复时到底采用什么

`resume` 的负载过程（`rollout_reconstruction.rs` L492–515 的核心）：

```rust
// 节选（省略函数外壳）
if let Some(checkpoint) = history_checkpoint
    && let Some(items) = &checkpoint.compacted.replacement_history
{
    history.replace_annotated(items.clone());          // ① 用检查点的替代历史重建
    history.restore_review_context(…);                  // ② 恢复审查上下文（若有）
}
let rollout_suffix = history_checkpoint.map_or(rollout_items, |checkpoint| checkpoint.suffix);
for item in rollout_suffix {
    match item {                                        // ③ 逐条回放"检查点之后"的记录
        RolloutItem::ResponseItem(response_item) => {
            history.replay_annotated_item(response_item, truncation_policy);
        }
        …其他类型分别处理…
    }
}
```

逐句解读：

- ① **先采用选中的检查点里的替代历史**——不是从头重放全部旧消息。这就是"恢复 ≠ 重发全历史"的实现含义。
- ③ **后缀回放**：检查点之后新产生的记录（包括压缩后你又聊的那些）逐条重新施加到历史上，保证"压缩之后发生的事"不丢。
- 前置条件（需在完整阅读时注意）：扫描是**倒序**的，只有找到"同时含替代历史与窗口编号"的**最新**可用检查点才提前停止；旧格式或字段缺失可能退回扫描更多记录。**"读了更完整的文件"仍不等于"把旧消息全部发给模型"**——后面还有重建步骤。

## 四态对照（交互版逐格演示）

| 层面的状态 | 压缩前 | 压缩后 | 关闭程序 | 重开 resume |
|---|---|---|---|---|
| ① 存档 | 已有全部记录 | **追加**检查点（旧记录仍在） | 不动 | 不动 |
| ② 活动历史 | 原始列表 | **被替换**为替代历史 | 内存态消失 | 由"检查点替代历史 + 后缀回放"重建 |
| ③ 下次请求 | 原列表组装 | 带上替代历史 | — | 与压缩后一致（除非后缀里又有变化） |

**【当心】** 两个最常见的误读：

1. **"磁盘上全都有，所以随时能全恢复"**——恢复只采用替代历史 + 后缀；**旧原话不会自动回来**。想把某条老记录补回来，要靠"重新读文件/重新检索"这类显式动作，而且还要它此刻还在磁盘、还在读得到的范围里。
2. **"恢复 = 精确还原昨天那一刻"**——也不是：恢复是**重建当前工作材料**的过程，期间双向的差异都会出现（压缩前被替换掉的部分不会回来；后缀里新发生的变化会补上）。

# 单元 07 · 整理失败与手动整理

> 对应交互：失败分支选择器（挑一种失败，看"哪些变了、哪些没变"）。

## 场景："正在压缩"卡住了

小林的会话到了极限，屏幕显示"正在压缩上下文……"，过了几秒，报了一行错。他慌了：**坏了，是不是把桌子搞乱了？**

先给结论：**"整理失败"≠"什么都没发生"，但也通常不等于灾难**。要看清两件事：

1. 失败发生在**哪一小步**；
2. 哪份状态**已经变了**、哪份**还没安装**。

## 把"整理"拆成有先后的四步

```text
① 准备：复制当前历史做"整理副本"，组装给模型看的材料
② 请求：把材料发给模型（本地摘要 / 远端压缩请求）
③ 验收：产物合格吗？（是否有完成事件？压缩条目数量对不对？）
④ 安装：替换活动历史 + 追加检查点（单元 06 的两件事）
```

**只要能分清"③失败"与"④失败"，大多数恐慌就会消失**：

- ③ 失败 → ④ 不会执行 → **活动历史保持原样**（没被换坏）；
- ④ 一旦执行 → 那就是**成功路径**了（替换与追加都完成）。

## 失败分类表（固定快照的实现）

| 失败情境 | 程序怎么做 | 你看到的结果 |
|---|---|---|
| **本地路径：整顿用副本超限** | 移除副本里**最早**的条目，**重置重试计数**，再试；副本只剩 1 条仍超限 → 标记用量已满、返回错误 | 提示错误；原始记录未动；下次可再试 |
| **本地路径：普通错误**（网络等） | 按 provider 的**重试上限**退避重试；耗尽后返回错误 | 提示错误；本轮结束 |
| **本地路径：中断 / 取消 / 会话预算耗尽** | **不重试**，直接返回错误 | 立即停止 |
| **远端 v2：流错误** | 每种传输重试预算 **min(provider 设置, 2)**（比普通请求更保守） | 重试后仍失败才报错 |
| **远端 v2：验收不合格** | 两种情况直接判失败：**没等到完成事件**；或**压缩条目数量 ≠ 1**（要求"恰好一个"） | 报错；替代历史未安装 |
| **上一模型整理失败后的**后备 | 条件满足时（错误类型合适、模型或访问方案有差异、OpenAI 提供者且授权匹配）**用当前模型再试一次** | 后备也失败才最终报错 |

两段关键源码：

```rust
// codex-rs/core/src/compact.rs  L338–349（节选）
Err(e) if matches!(e.details(), CodexErrorDetails::ContextWindowExceeded) => {
    if turn_input_len > 1 {
        // Trim from the beginning to preserve cache (prefix-based) and keep recent messages intact.
        error!("Context window exceeded while compacting; removing oldest history item. Error: {e}");
        history.remove_first_item();
        retries = 0;                       // ① 重置计数
        continue;
    }
    sess.set_total_tokens_full(turn_context.as_ref()).await;   // ② 只剩一条：宣布局满
    return Err(e);
}
```

**逐句解读**：

- ① `retries = 0`：这不是笔误，也不是"无限重试"——**这是另一类循环的计数**（"缩副本重试"与"普通错误退避"是两种循环语义）。读代码时**看到 `= 0` 要先问"这是哪个计数器的语义"**，别急着判"死循环"。
- ② `set_total_tokens_full`："宣布局满"是**显式状态写入**：程序把本地记录的用量标记为已满，让**上层（轮前检查等）**据此做后续决策（例如提示用户手动整理或开新会话）。**错误返回与状态标记是两件事**，都要看。
- 注意 `if turn_input_len > 1` 这个条件：只有在**副本里还有多条**时才缩；只剩一条就放弃——**有界性**（不会缩到空数组，也不会无限循环）。

```rust
// codex-rs/core/src/compact_remote_v2.rs  L477–487（节选）
let Some(response_id) = completed_response_id else {
    return Err(CodexErr::Stream(
        "remote compaction v2 stream closed before response.completed".to_string(),
    ));                                                // ① 没等到"完成"：失败
};
if compaction_count != 1 {
    return Err(CodexErr::Fatal(format!(
        "remote compaction v2 expected exactly one compaction output item, got {compaction_count} …"
    )));                                               // ② 压缩条目不是恰好一个：失败

```

**为什么要求"恰好一个"？** 因为替代历史里"那一段压缩材料"必须与"一个条目"一一对应；多一个或少一个都会让后续恢复、预算与替换语义失去对齐点。**这叫验收（validation）**——不是"拿到东西就算成功"，而是"拿到的东西符合契约才算成功"。**只看 `Ok` 就判断整个业务成功**在这里是典型误读：外层还有安装与持久化步骤。

## 失败之后：什么变了，什么没变

| 状态 | ③失败后 | 说明 |
|---|---|---|
| 活动历史 | **保持原样**（替代历史未安装） | 这是"没被搞乱"的主要含义 |
| 会话存档 | 只增不减；失败诊断、部分事件可能已追加 | "失败≠零痕迹"，但旧记录不会因此消失 |
| 已执行的工具动作 | **不会撤销** | 命令真的跑过了；副作用已经发生。压缩失败不能"撤回"它们 |
| 本轮/新输入 | 轮前失败：**新输入先被记录**再报错（源码原注释："Compaction runs before the new input is recorded, so preserve it on every failure"）；轮中失败：本轮结束；轮后失败：**保留已完成的回答**，只记一条警告 | 三种时机的善后不同 |
| 下一次 | 用量仍可能处于"满"或接近满 | 提示你手动整理 / 缩小输入 / 开新会话 |

## 手动整理：与自动的区别

| | 自动 | 手动 /compact |
|---|---|---|
| 触发 | 到线且正处在某个检查点（轮前/轮中/轮后） | 用户随时发起；**不要求到线** |
| 对当前任务 | 轮中成功 → 继续工作循环 | **停止当前旧任务**，整理作为独立任务执行 |
| 完成后 | 回到原来的流程 | **不等同于原任务自动继续**：整理完了，你需要再发输入（或新任务）才继续干活 |
| 失败影响面 | 可能中断当前正在进行的答复（轮前/轮中）或只记警告（轮后） | 只影响这次独立任务 |

**实操建议**（把机制变成行动）：

- 会话说"正在压缩"且失败时：**先别再狂发消息**（每一条新输入都会增加压力）；看一眼错误、必要时把关键要求重新发一遍或开新会话。
- 长任务到达极限前，主动 `/compact` 比被动等自动更可控（手动不要求到线）。
- **开新会话是最便宜的兜底**：源码自己也在成功后发出警告——原文大意："长会话与多次压缩可能降低模型准确性，尽量保持会话简短聚焦。"**这是源码里的自我警告，不是教程的发挥。**

**① 判断题**：压缩失败了，说明这次会话"什么都没发生"。（对/错，给出至少两条"已经发生"的事）

# 单元 08 · 同样开头的第二次请求：缓存

> 对应交互：前缀复用与账单演算器（两条请求的前缀对齐 + 三组账目）。
>
> 本节第一部分依据 2026-10-14 当日核查的 OpenAI 官方 API 文档；第二部分是**我们对该固定 CLI 快照的独立核查结果**；两者分开陈述。

## 场景：同样的开头，为什么第二次更快更便宜

小林连续问了两句：

> ① 帮我把行程里的公交段列出来。
> ② 把行程里的午饭段列出来。

两句的开头部分——系统指令、工具说明、全部对话历史——几乎完全一样。如果每次都从头算起，是不是太亏了？

官方给这套"重复开头"的优化起了名字：**Prompt Caching（提示词缓存）**。

## 用两张纸解释机制

**【人话】** 说白了：模型读你的材料时，会给每个 token 计算一份"中间状态"（官方叫 **KV 状态**，key-value states）。**缓存就是把这些中间状态存下来**——下次请求如果**开头部分（前缀）一字不差**，模型可以直接**拿回这份状态，跳过大半重新计算**。

三个配套术语：

| 术语 | 含义 | 注意 |
|---|---|---|
| **前缀（prefix）** | 请求开头"未改变的那部分 token" | 匹配的是**完整渲染后的上下文**（含指令、工具、历史），不只是你可见的文字 |
| **缓存断点（cache breakpoint）** | 标记"前缀到此为止可以存/取"的终点 | 新模型支持显式与隐式；旧模型只有隐式、按固定间隔 |
| **命中（cache hit）** | 请求到达了一台仍持有匹配缓存条目的机器，且前缀匹配 | 不保证；路由、过期、负载都影响 |

**关键澄清（官方原话性质）**：缓存存的是 **KV tensors（中间状态），不是 token 本身**。命中后，**本次上下文的总长度不变**——省的是"重新计算"，不是"少发材料"。**缓存输入依然计入速率限制（TPM）**。

## 官方规则速览（2026-10-14 核查）

| 行为 | 新代际（GPT-5.6 及以后） | GPT-5.5 / 5.5 Pro | 更早模型 |
|---|---|---|---|
| 最小可缓存前缀 | **1,024** 个可见输入 token（不含隐藏系统内容） | 依请求设置 | 依请求设置 |
| 断点 | 支持**显式** + 隐式 | 仅隐式（固定每 **2,048** token 间隔） | 仅隐式（按模型固定间隔） |
| `cached_tokens` 上报 | 精确（合格边界、扣除隐藏 token） | 扣隐藏 token 后**向下取整到 128 的倍数** | 同左 |
| 缓存读取费率 | **0.1×** 未缓存输入（个别新模型 0.05×） | 依模型费率 | 依模型费率 |
| 缓存写入费率 | **1.25×** 未缓存输入 | 无额外写费用 | 无额外写费用 |
| 生命周期控制 | `prompt_cache_options.ttl`，唯一值/默认 `"30m"`（至少保留 30 分钟，可能更久） | `prompt_cache_retention`（仅 24h） | `in_memory`（约 5–10 分钟不活动，最长 1 小时）或 `24h`（通常约 30 分钟，最长 24 小时） |
| key 的作用 | 可选（自动路由；key 用于分离计费） | 用稳定 key 帮助路由 | 同左 |

几个配套事实：每次请求最多 **4 次**缓存写入；新代际的查找范围是"前 2 个 + 最新 50 个显式断点"（隐式模式还含隐式断点与最多 20 个更早的合格消息端点）；**缓存不跨组织、不跨区域**；条目过期后不可手动清除；组织的零数据保留（ZDR）策略会影响默认保留值。

## 请求与 usage：逐字段拆账

一次请求里与缓存相关的关键字段（教学简化 JSON，字段名真实）：

```json
{
  "model": "gpt-5.x",
  "input": [ …完整渲染的上下文… ],
  "prompt_cache_key": "session-7f3c…",       // 缓存路由与计费归属（可选/因代际而异）
  "prompt_cache_options": { "ttl": "30m" }    // 生命周期控制（新代际）
}
```

响应里，账目在 `usage` 中分开列：

```json
{
  "usage": {
    "input_tokens": 100000,                    // 本次输入总数（含下面两项）
    "input_tokens_details": {
      "cached_tokens": 96000,                  // ← 从缓存读取（按读取费率）
      "cache_write_tokens": 0                   // ← 写入缓存（按写入费率）
    },
    "output_tokens": 1200
  }
}
```

**三个容易记错的关系**：

1. `cached_tokens` 与 `cache_write_tokens` 都是**输入明细**，**不能再加到 `input_tokens` 上**；
2. **普通输入** = `input_tokens` − `cached_tokens` − `cache_write_tokens`；
3. 计费当量（新代际示例）：`普通×1 + 读取×0.1 + 写入×1.25`。**写入的 1.25 倍是完整单价**（写入 token 按 1.25 倍率计费，不是"在普通价上再加 1.25 倍"）。

## 三组亲手算的账（新代际费率：读 0.1×、写 1.25×）

**账 A · 首次写入**：输入 100,000，其中 100,000 全部写入缓存（首次见到这个前缀）。

```text
普通输入 = 100,000 − 0 − 100,000 = 0
当量 = 0×1 + 0×0.1 + 100,000×1.25 = 125,000
相对"全部按普通价"：125,000 / 100,000 = 1.25×
```

**账 B · 再次读取（完整命中）**：同样 100,000，其中 96,000 命中、4,000 新增普通输入、无写入。

```text
普通输入 = 100,000 − 96,000 − 0 = 4,000
当量 = 4,000×1 + 96,000×0.1 + 0×1.25 = 4,000 + 9,600 = 13,600
```

**账 C · 两次合计**：最理想化地假设"写 100,000、下次完整读 100,000"（官方文档给的同型结论）：

```text
两次当量 = 1.25×100,000 + 0.1×100,000 = 135,000 → 相当于 1.35× 一次普通输入
            对比：完全不缓存、老老实实算两遍 = 2.0×
十次请求（1 次写 + 9 次完整读）= 1.25 + 9×0.1 = 2.15×（不缓存 = 10×）
```

**【当心】** 一个"最小长度"的成本陷阱（官方文档专门给了一张图）：前缀太短时，为了凑到最小可缓存长度（如 1,024）而**硬加无用文字**，可能反而不划算——在"读 0.1×、写 1.25×、缓存 10 次"的假设下，**原始前缀 ≤102 tokens 时永远不获益**；103 tokens 的前缀要请求至少约 1,963 次才回本；而 ≥221 tokens 的前缀，扩到 1,024 在 10 次请求内就更便宜。**结论：别为了凑缓存阈值写废话。**

## 缓存与上下文管理其他部分的交界

这张关系表是本章的"合流处"（把前七单元的机制与缓存对上）：

| 机制 | 与缓存的关系 |
|---|---|
| 压缩 / 摘要 | **会改变前缀**：替换历史后，"从第一个变化的 token 起"旧缓存无法复用；压缩后**首个**请求通常命中率更低，之后随新前缀稳定而回升 |
| 修改旧消息 | 写请求里"改旧消息"不如"**追加新消息**"：改写会让该消息之后的前缀全部失配 |
| 工具变更 | 工具名、描述、顺序变化都会改变渲染前缀 → 破坏复用（工具说明在前部） |
| 过期 | 条目按生命周期过期；过期后同样文字也不保证命中 |
| 长期记忆 / 检索 / 子 Agent / fork / 恢复 | 它们都通过"**改变这次请求的前缀**"来影响缓存：恢复会话是重建材料（通过检查点），fork 派生新历史边界，子 Agent 有独立会话与独立缓存键——**都是"新前缀"，不该期待顺手命中旧缓存** |
| 上下文窗口 | **缓存不缩小窗口占用**；cached 输入仍计入 TPM 与本次完整上下文 |

## 独立核查：固定 CLI 快照与缓存的实际连接

教程惯例：**API 文档说支持某字段 ≠ 这个 CLI 会发这个字段**。所以我们回到固定快照，查了两个方向（本次核查新增）：

**方向一：请求侧——CLI 发不发缓存键？**

```rust
// codex-rs/core/src/client.rs  L641–653（节选）
fn prompt_cache_key(&self, responses_metadata: &CodexResponsesMetadata) -> String {
    if let Some(prompt_cache_key) = &self.prompt_cache_key_override {
        return prompt_cache_key.clone();          // ① 特定会话（如审查会话）用覆盖值
    }
    if let SessionSource::Internal(source) = &self.state.session_source
        && let Some(parent_thread_id) = responses_metadata.parent_thread_id
    {
        return format!("{source}:{parent_thread_id}");  // ② 内部子会话：来源+父线程
    }
    responses_metadata.session_id.clone()          // ③ 常规请求：会话 ID
}
```

并在请求构造处显式赋值：`let prompt_cache_key = Some(self.prompt_cache_key(responses_metadata));`（同文件 L1049）。也就是说：**这个快照的 CLI 常规请求会携带一个稳定的缓存键，默认等于会话 ID**——同一会话的请求倾向于落在同一缓存分组；不同会话/子会话各有自己的键。（`prompt_cache_key_override` 的实例：guardian 审查会话用 `guardian:{父线程}`，`review_session.rs` L285–297。）

- ✅ 能证明：**该快照在请求里带缓存键、在响应对账缓存读写明细**——"CLI 与缓存机制的实际连接"不是全靠 API 文档推测的；

## 自测

**① 拆账题**：某请求 `input_tokens = 50,000`、`cached_tokens = 40,000`、`cache_write_tokens = 2,000`。求普通输入与计费当量（新代际费率），并回答"cached_tokens 要不要从 50,000 里再被减一次"。

**② 判断题**：两次请求"文字看起来一样"，就一定会命中缓存。（对/错，说出至少两条反例因素）

**③ 关系题**：压缩之后，缓存复用会怎样？请用"前缀"这个词解释。

**④ 容量题**：命中缓存后，这次的上下文窗口占用会不会变小？速率限制呢？

<details>
<summary>参考答案</summary>

**①** 普通输入 = 50,000 − 40,000 − 2,000 = **8,000**；当量 = 8,000×1 + 40,000×0.1 + 2,000×1.25 = 8,000 + 4,000 + 2,500 = **14,500**。注意：`cached_tokens` 是 `input_tokens` 的**明细拆分**，已经在 50,000 里了，不能再被减第二次（这正是"别把缓存 token 重复相加"的意思）。

**② 错。** 反例因素（任举两条）：① 渲染前缀因**设置/工具/顺序**变化而不一致（不是"文字相同"就够——匹配的是**渲染后**的完整前缀，含系统指令与工具定义）；② 缓存**过期**或所在机器不同（未到达持有条目的机器/跨组织区域）；③ 前缀未达到最小可缓存长度；④ 隐式/显式模式切换导致查找边界不同。

**③** 压缩**替换了历史**，所以从"第一个变化的 token"开始，旧前缀不再匹配——**压缩后的首次请求通常复用较少**。但"变化点之前"的稳定部分（若有）仍可能命中；且压缩后形成的新前缀随着后续追加相处稳定，命中会恢复。用一句话：**压缩改变前缀 → 缓存按前缀退化，不会整体归零。**

**④ 都不会"变小"。** 缓存省的是**重新计算**（算力、钱、首字延迟方向）；本次的**完整上下文仍要占满**（缓存的 token 依然是本次输入的一部分），并且**cached 输入依然计入 TPM 速率限制**。把缓存当成"窗口扩容"或"上下文缩短"都是错的。
</details>

| 时延 | 首字延迟、总时长；整理期间额外耗时 | 记录整理触发与耗时本身（整理也花钱花时间） |

**【当心】** 一个全教程反复提醒的纪律：**"1 − 处理后/处理前"只是体积缩减率**，不能替代任务质量。压缩率再漂亮，约束丢了就是丢了。

## 迁移任务：同一套思路，换一个界面

> 场景：你修改一个"用户信息"HTTP 接口——**加一个新字段，但旧客户端（老 App）不能坏**。任务跨了一天：白天改代码、跑测试（测试日志很长）；晚上关电脑；第二天继续。

把九个单元的机制映射到这条任务上（对照表，**这是迁移的核心动作**）：

| 机制（本教程） | 在这条任务里的对应物 | 你要做的动作 |
|---|---|---|
| 关键约束（4 点返校） | "旧客户端必须兼容"（兼容性约束） | 明确写进第一条消息的**头尾**；在约束表里标"有效" |
| 长工具结果 | 测试日志（几百行，报错在中段） | 让工具输出**保头尾+摘要置顶**；关键错误行取出来单独复述一遍 |
| 三处限长 | 日志在出口/历史/整理时的三次缩减 | 预判：中间的错误行最先死；给出重读方案（重跑相关测试/看报告文件） |
| 整理触发 | 会话到线时的自动压缩 | 算一遍你用的模型窗口下的两条线；决定"提前手动整理"的时机 |
| 整理产物 | 摘要/压缩条目 | 检查交接材料里"兼容性约束"是否在场（人可读路径）；远端路径则用重述验证 |
| 保存与恢复 | 隔天 `resume` 后继续 | 恢复后**先验证约束还在**（问一遍"旧客户端兼容要求是什么"），再动手 |
| 失败处理 | 整理/测试失败 | 本轮不动历史；诊断后重试；副作用（已推送的提交）不重复 |
| 缓存 | 同一会话内重复发送的稳定前缀 | 别为了"凑缓存"改写旧消息；追加新信息 |
| 验证 | 最终验收 | 老客户端用例全绿 + 约束违背数 0 + 用量费用记录 |

（Java/Spring 开发者旁注：这套映射与"多模块 Maven 构建日志 + 接口兼容性 + 隔天恢复"的日常经验一一对应；不熟悉 Java 的读者把这个任务当"任何改代码、保兼容、查长日志"的工作即可。）

**你的迁移提交**（与交付 1–4 同格式）：① 材料清单（含"兼容性约束"与"日志"两行特殊处理）；② 状态流程（标出一处与 Codex 实现**故意不同**的地方并说明理由）；③ 约束保全方案（含"恢复后先验证"的步骤）；④ 验证设计（旧客户端怎么测、日志关键行怎么保证可见）。

## 综合自测（结业前自检）

**①** 用户说"这句话我刚才说过"——请定位它可能存在于哪三层，并说明"我看到了"与"模型看到了"为什么可能不一致。（U1/U6）

**②** 一条规则文件超了 32 KiB 预算，关键行在尾部。写出至少两条可能的补救。（U2/U5）

**③** W=128,000、M 字段缺失、用户无配置：范围线的值是多少？A=116,000 时到线吗？（U3）

**④** 整理前列表有 5 条用户消息（8k/12k/3k/9k/14k，从旧到新），本地摘要预算 20k。写出最终保留清单。（U4）

**⑤** 为什么"工具结果在历史里被裁了，但磁盘上可能还是全的"？（U5）

**⑥** 恢复会话时，"复用检查点替代历史"与"重放全部旧消息"的差别是什么？（U6）

**⑦** 远端压缩验收要求"恰好一个压缩条目"。如果收到两个，程序会怎么处理？（U7）

**⑧** 两次请求文字相同却没命中缓存，写三种可能原因。（U8）

**⑨** 你的 Agent 要把"已否决方案"保存到第二天——存进摘要就够吗？为什么？（U9）

<details>
<summary>参考答案</summary>

**①** 三层：磁盘存档（大概率在）/ 活动历史（可能已被替换/裁剪）/ 本次请求（可能不在）。"我看到了"通常指前两层（尤其文件层），"模型看到"只看第三层；压缩后替代历史覆盖了旧列表，就是两层分离的现实例子。

**②** 示例：把关键内容移到文件**头部**；拆分为多个文件并让发现范围覆盖关键目录；提高配置的规则预算（若允许）；或把要点显式写进对话（人工冗余）。

**③** 范围线 = 90% × 128,000 = **115,200**；A=116,000 ≥ 115,200 → **已到线**（整段线 121,600 未到，但 OR 判断已触发）。

**④** 倒着装：14k（剩 6k）→ 9k > 6k → 边界截短（保头尾约 6k 片段）→ 停止。最终：**[9k 的截短片段] → [14k] → [摘要]**；3k/12k/8k 不保留（除非摘要带走）。注意"选完边界即停"。

**⑤** 因为活动历史保存的是**经过裁剪的副本**，而存档写入的是**未裁剪的原载荷**；两者是不同流水线上不同对象（另有各自的持久化预算，如 64 KiB 分片上限）。

**⑥** 前者一步到位采用"整理时保存的替代材料"（规则重新渲染 + 保留的消息 + 摘要/压缩条目），成本低、忠实于整理时的取舍；后者会重新经历全部旧消息（代价是重复计算与"把已被替换的内容带回来"，与系统语义不符）。系统采用前者 + 回放检查点之后的**后缀**。

**⑦** 验收失败：判为 Fatal 错误（"expected exactly one compaction output item"），替代历史**不安装**；活动历史保持原样，等下轮再试或提示用户。

**⑧** 示例：渲染前缀其实不同（工具/设置/顺序变了）；缓存过期或未路由到持有条目的机器；前缀低于最小可缓存长度；显式/隐式模式切换导致查找边界不同（任选三条）。

**⑨** 不够。"否决"是一种**状态**，需要**结构化保存与更新语义**（建"约束表"，被否的标为"已否决"而不是删除，渲染时可见"已否决"状态）；只存进摘要等于把关键状态交给有损概括，且无法验证它是否还在。第二天的正确做法：恢复后**先验证**（重述检查），再继续。
</details>

## B · 速查卡

**三组绝不能混的数字**

| 组 | 数字 | 管什么 |
|---|---|---|
| 触发线 | 90%（基础线，可被字段/配置按下） + 95%（H 缺省比例） | 何时开始整理 |
| 保留预算 | 20,000（本地）/ 64,000（远端 v2） | 整理后直接保留旧候选的空间 |
| 存储预算 | 32 KiB（项目规则）/ 64 KiB（分片命令输出、MCP 结果） | 磁盘与加载环节的独立上限 |

**常用常量与费率（按章节出处）**

`(W×9)/10`；`H=W×p/100, p=95`；20,000 / 64,000 / 10,000（单条 AgentMessage）；4 字节≈1 token；`split_budget` 左 floor 右 ceil；截断标记"…N tokens truncated…"（额外长度）；写 1.25×、读 0.1×；1 写 1 读 = **1.35×**；10 次（1 写 9 读）= **2.15×**；最小可缓存 **1,024**（新代际）；旧代际 implicit 间隔 **2,048**（5.5）、cached 取整 **128** 倍数；每次请求最多 **4** 次缓存写入；远端 v2 重试 ≤ **min(provider,2)**；TTL 30m（新代际）/ in_memory 5–10 分钟（最长 1 小时）/ 24h（通常 30 分钟）。

**行为速记**

- 到线 = 范围线 **OR** 整段线；轮前检查**不含**即将写入的新输入（有 TODO）。
- 整理骨架 = 筛候选 → 从新到旧装预算 → 边界截短 → 产物另加 → 重组规则。
- 成功安装 = 替换内存 **+** 追加检查点；恢复 = 替代历史 **+** 后缀回放。
- 失败 ≠ 无变化；替换后不回滚。
- 缓存 = 省计算，不省容量；压缩换前缀 → 缓存按前缀退化。
