聊天之外，Codex 还要知道当前工作条件

Codex 实际逻辑

刚才我们一直追踪“你说了什么、工具查到了什么”。现在补一个问题：老师的活动要求已修改，负责查询的工具也换了，下一次问模型时怎样告诉它？只带上旧聊天，可能还在用昨天的条件。

Codex 因此还会维护一张“当前工作情况表”。放到编程任务里，它记录当前在哪个项目工作、已经读入哪些项目规则、有哪些工具和操作权限。需要时，程序把相关栏目整理成消息，加入下一次请求。

这张情况表在本教程叫当前工作状态。正式源码名是 WorldState；有些材料将它直译成“世界状态”。现在知道它只管这次工作的条件，就容易理解这个名字了。

“比较状态”也有具体含义：例如上次允许工具 A，这次改成工具 B；程序比较新旧情况表，生成“工具已变化”的说明。没变的栏目无需再追加一条更新，已经采用的规则仍可留在后续上下文中。它不意味着自动读完电脑里的文件。

Codex 实际逻辑
把一次模型调用想成“寄出一包工作资料”。Codex 要装入工作要求、采用的消息和可用工具说明，再交给模型服务。下面是概念结构，省略了协议字段细节：
模型请求
├─ 适用指令：如何完成任务、哪些约束要遵守
├─ 输入消息：当前工作状态 + 当前采用的历史 + 新输入
│  └─ 工具调用及对应结果、文件片段、图片等内容块
└─ 可用工具：工具名称、用途、参数结构
“读取文件”返回的是文件片段；“声明 read_file 工具”只是告诉模型可以请求读取文件。有工具不等于文件已经读过。
发送前还会整理消息结构，例如保证工具调用与输出匹配，并移除当前模型不支持的媒体类型。规则文件也有加载预算，并非所有规则都会无限量装入。

AGENTS.md 从哪里读，为什么也可能不完整？
刚才的“老师活动要求”，放到编程项目中可以写成一份项目说明文件。AGENTS.md 就是供 Agent 阅读的这类文件：例如使用什么测试命令、哪些目录允许修改、团队有哪些约定。
项目规则通常沿项目根到当前目录查找；同目录先看 override 文件，再看 AGENTS.md，再看配置的 fallback 文件名，不是遍历所有子目录。项目是否可信也影响读取。
项目文档共享字节预算，默认 32 KiB、可配置；超预算时文件尾部可能不被加载。当前规则没变时，无需再追加一条相同的规则更新消息；已有规则仍属于后续请求采用的上下文。变化时生成替换说明，删除时说明不再适用。压缩后重建当前状态，不会自动补回原先未加载的尾部。

先看一个编程例子：你说“修复订单金额计算”。模型第一次拿到你的目标、已经加载的项目规则以及可用的工具定义；它请求读取 OrderService.java 后，Codex 执行读取，再把工具调用和读取结果加入下一份请求。文件名、文件内容和工具定义分别是不同的数据。


正式对应：Prompt 是客户端准备的一次请求对象；ResponseItem 是输入列表中每个条目的类型；WorldState 是“当前工作状态”的内部容器。模型收到的是它们整理后的指令、条目和工具说明。


对象具体结构与用途
Prompt.inputVec<ResponseItem>：一份有顺序的条目列表，含消息、工具调用、对应输出等。Vec 可以先理解为列表。
ResponseItem::Messagerole 标明发言角色；content 是内容块列表，不保证只有一段纯文字。
Prompt.tools可提供给模型的工具定义。普通路径单独放在该字段；增量工具路径把适用定义交由历史承载，字段可为空。

Prompt.output_schema可选的输出 JSON 结构约束；它规定回答的结构，不负责读取项目文件。

状态怎样变成消息：先捕获本步的配置和环境，创建栏目；再与已保存的栏目快照比较，生成需要追加的说明。规则栏目 ID 是 agents_md：内容没变化时返回空更新；内容变化时附“替换原规则”的说明；原规则移除时附“原规则不再适用”的说明。无变化只表示不追加重复更新，后续请求仍可采用已留在历史中的规则。


压缩后的行为：共享重建流程把当前工作状态按完整模式呈现，得到新的基线。它重建的是当前已加载的状态；不会借此读取硬盘上所有文件。


发送前还要检查结构：调用与结果需要配对，孤立结果需清理或满足独立工具事件条件，模型不支持的图片与音频会被移除。比如保留了“调用 A”，却没有 A 的结果，程序要先规范化这份列表，再生成模型输入。

本例的新材料：规则 6 格 + 用户要求 8 格 + 摘要 14 格 = 28 格。任务做到一半触发自动压缩时，可直接用这 28 格继续；新任务开始前自动整理后，再加入该例中 4 格的新消息，形成 32 格的请求。手动 /compact 则只展示整理完成，等你再发消息说明下一步，不假定它自动恢复刚才的工作。
拖动材料量滑块，只改变重复查询和讨论过程的长短；本例要保留的事实不变。真实压缩的体积、耗时与内容要通过实际运行观察，不能用本例的比例预测。
为什么“已经答完”时，这里不自动压缩？
这处检查的目的，是让 Codex 能继续处理还没完成的任务。如果最终方案已经发出，当前没有下一步要做，就不会因为这条规则启动压缩。
你再发一条新消息时，Codex 会在开始新任务前检查已有材料。这个时点，新消息本身可能还没加入，所以不能把滑块理解成“包含新消息的最终请求总量”。
源码还提供“任务结束后提前整理”的单独功能，是否执行取决于配置。本页把它放在进阶说明中，避免和“任务做到一半要继续”混在一起。

第一个动画用了“格”。真实程序使用 token 计量：模型先把文字等输入切成自己的处理单位，一段文字包含多少 token，需要按模型的切分方式计算，不能把一个字直接当成一个 token。工具说明、图片等也会消耗输入预算。

第二种计量先记住“本次整理后起步时已经带了多少”。例如起步 60,000，现在 85,000，新增就是 25,000。若配置只允许再增长 30,000，此时还没到这条线；但整段用量仍要检查 95,000 那条线。

为什么这里数“字节”？文字在电脑里用编码保存，字节是这种表示的长度单位。以 UTF-8 编码为例，A 占 1 字节，中 占 3 字节。这个函数用“约 4 字节算一个 token”估算长度，而不调用模型的真实分词器。
一个汉字可能跨多个字节，程序不能切在字的中间，因此会退到完整字符的边界。截断标记是额外插入的文字；原文片段合预算，不等于结果连标记一起严格等于预算。
这解释了为什么“磁盘记录还在”也不保证能找到工具最初输出的每个字：输出可能在进入历史之前就已被裁短。需要某行时，应缩小读取范围，重新获取来源。

先算一个纯英文例子：文本 ABCDEFGHIJKLMNO 是 15 个 UTF-8 字节。预算只有 2 个近似 token，则原文预算为 8 字节：开头留 4 字节，末尾留 4 字节。结果是 ABCD…2 tokens truncated…LMNO；E～K 被删，中间标记额外加入。程序没有阅读字母含义，也没有判断 E～K 是否重要。


正式对应：TruncationPolicy::Tokens(n) 会走近似 token 裁剪。approx_token_count(text)=ceil(UTF-8 字节数/4)；允许留下的原文为 n×4 字节，再把预算分给头尾。字符串的 len() 在 Rust 中返回字节数，例如“中文”通常是 6 字节，不是 2。


计数实际按字节估算
pub fn approx_token_count(text: &str) -> usize {
    let len = text.len();
    len.saturating_add(APPROX_BYTES_PER_TOKEN.saturating_sub(1)) / APPROX_BYTES_PER_TOKEN
}
  1. text.len() 得到 UTF-8 字节长度。
  2. 常量 APPROX_BYTES_PER_TOKEN 为 4；先加 3，再整除 4，相当于向上取整。
  3. saturating_add 避免极大整数加法溢出；这里没有调用模型 tokenizer。

重连等待：本地摘要使用共享退避，基数 200 ms，每次约翻倍，加约 ±10% 随机扰动。默认五次普通重试大致按 200、400、800、1,600、3,200 ms 的基数等待；这些不是真实网络耗时预测。


远端 v2：常规流重试阈值取 min(provider.stream_max_retries(), 2)。先由错误的 retry_delay 判断是否可重试；达到计数阈值时若成功从 WebSocket 切换到 HTTPS，会重置计数。因此“常规阈值是 2”不能写成“整个远端压缩永远最多请求三次”。

例子 → 定义
术语在例子中的含义正式含义与边界
Prompt prefix / 提示前缀第二次开头仍相同的工具、规则、车程记录。完整模型输入从开头到某个位置的连续部分。工具定义、顺序和相关设置也可能影响它；只比较聊天框可见文字不够。
KV states / 键值状态第一次处理这些材料时留下的中间计算结果。模型注意力计算中使用的 key/value 张量。缓存保存这类计算状态，后续处理可以利用它们参考先前内容。
Cache breakpoint / 缓存断点1,024 或 2,048 的保存位置。可保存、查找某段前缀状态的边界。它是输入中的位置，与调试器暂停程序的断点用途不同。
Cache hit / 缓存命中这次找到了 2,048 位置的旧状态。当前请求找到一个仍可用、完整前缀匹配且设置兼容的缓存条目。未找到叫 cache miss / 未命中，需要重新处理相关输入。
Prompt Caching / 提示缓存第二次复用前面材料的处理结果。在服务端保存并复用相同输入前缀的 KV 状态，降低重复计算与相应输入成本。它与第 3 章生成新摘要是两种不同处理。


现在可以完整读出刚才的数字：本次输入 2,304；命中 2,048；其余 256 重新处理；回答重新生成；窗口仍按本次完整输入计算。

API 真实条件


下面集中讲官方指南中的GPT-5.6 及以后模型，让你先学会一套规则。较早模型的差异放在后面的折叠说明。核对日期：2026-10-14。


要决定什么当前官方规则工程含义
最短多长才能缓存？至少 1,024 个可见输入 token；服务隐藏系统内容不计入这个最低长度。300 token 的共同规则，即使每次完全一样，也不能直接当成已满足这个门槛。1,024 是可缓存前缀的长度门槛，与第 2 章压缩触发线用途不同。
谁选择断点？implicit：服务选择；explicit：应用明确标记。只使用 explicit 模式却没放任何显式断点，不会使用缓存或产生缓存写入。
自动选择哪里？最新的合格消息末尾。用户消息、连续工具结果组中的最后一条、开头连续开发者消息组中的最后一条是合格位置。消息结构会影响查找边界。把旧消息保留、再追加一条新消息，比改写旧消息更容易保留原边界。
能写几个位置？每次请求至多四次缓存写入；保留 implicit 自动断点时，它占一个名额。需要更多控制时，把标记放在变化频率不同的材料末尾，而不是给每一行都加标记。
能存多久？prompt_cache_options.ttl 当前支持 "30m"，也是默认值。最近一次写入或复用后至少 30 分钟。复用会刷新存活时间，不再次收写入费用。超过 30 分钟并不意味着恰好删除；实际命中还受条目可用性影响。
为什么相同还可能未命中？还需要兼容设置、可查找的断点、未失效的条目，以及请求到达持有它的机器。缓存保存在服务端具体机器上。相同前缀和相同会话都不能单独保证命中。


这些是当前 OpenAI API 规则。固定版本 Codex CLI 的请求组装与压缩源码采用另一条版本依据；应逐项核对它实际发送的字段，才能判断正在使用哪些缓存能力。

字段中文解读这个例子怎样算
usage这次模型调用的用量记录。这里仅展示输入部分；它不能代替整个任务的累计账单。
input_tokens本次输入 token 总数。2,304，已经包含下面的缓存读取和写入明细。
cached_tokens从缓存复用的输入 token 数。2,048 × 0.1 = 204.8。
cache_write_tokens按缓存写入价格计费的输入 token 数。本次为 0；若是首次写入的请求，本例就是 2,048。
没有单独列出的普通输入总数减读取，再减写入。2,304 − 2,048 − 0 = 256；费用 256 × 1。


合计 204.8 + 0 + 256 = 460.8。也可写成通用计算式：


普通输入数 = 输入总数 − 缓存读取数 − 缓存写入数
输入费用 = 普通输入数 × 普通单价
         + 缓存读取数 × 缓存读取单价
         + 缓存写入数 × 缓存写入单价


以上 usage 和费用为完整可算的假设样例，不是实测 API 返回。判断真实命中，要读实际返回的字段；不同接口的字段层级可能不同。

想看公式时，再把中文变量对上输入框


“稳定前缀数”是每次相同的开头材料长度，“变化后缀数”是每次变化的新问题长度，“调用次数”是总共发出几次请求，“读取比例”是缓存读取单价与普通输入单价之比。写入比例固定为本主路线的 1.25。

看懂名词之后，下一步是把它用于一个新任务。假设你要开发一个会读文件、运行命令、持续修复错误的 Agent，请先做出下面四项设计，再用真实运行来验证。

  2. 状态流程：写出“工具已返回 → 是否还要继续 → 是否到用量线 → 整理成功/失败 → 下一次请求”的条件与动作。

迁移练习：修改一个接口，隔天再继续
从理解到设计
离开郊游故事，换一个未讲过的任务：给查询接口增加一个可选筛选条件，旧客户端不传这个条件时必须保持原行为。“兼容”就是旧调用方式仍然可用。
  1. 先读接口约定和相关代码；运行测试得到很长日志。
  2. 处理中发生压缩；摘要只写“增加筛选”，遗漏“旧客户端行为不变”。
  3. 第二天恢复会话，准备继续改代码。
请写下：哪条是硬约束？长日志应保留什么、其余怎样重读？从哪里确认压缩后的材料？恢复后先检查什么？怎样证明没有破坏兼容？
对照参考思路
硬约束是“旧客户端不传新参数时保持原行为”，应明确放入当前请求，并保留接口约定的来源位置。长日志保留失败摘要、相关行、测试命令与完整日志位置；不知道的部分重新读取。
恢复后核对目标、约束、已改文件和待办，再读取当前代码与遗漏的约定。至少检查“不传新参数”和“传新参数”两条行为；还要确认测试实际覆盖这些行为，不能仅凭测试进程退出码推定兼容已经证明。
一次失败不够判断是压缩问题。需要对照原始来源、进入请求的材料、摘要与最终修改，定位约束在哪一步消失或被误用。
怎样做一次真实观察
实践验收
  1. 记录条件：CLI 版本、源码对应关系、模型、配置与启用的功能；不要把本课快照当成你安装版本的证明。
  2. 选可核对的小任务：写两条硬约束，准备可重新读取的资料；记录压缩前完成到哪里。
  3. 观察事件与材料：区分工具输出被裁短、压缩开始、压缩完成、替代历史与后续请求。不可读的服务端压缩内容记为不可直接观察。
  4. 核对结果：任务是否满足约束、是否重复工作、是否需要重读；然后看用量和缓存。公开分享前隐去会话里的私人内容。
