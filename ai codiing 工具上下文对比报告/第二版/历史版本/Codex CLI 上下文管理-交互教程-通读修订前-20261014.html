为什么本机文件、缓存和记忆都不等于上下文？

文件在电脑里，只说明它存在。Codex 需要读取相关内容，并把内容加入请求，模型这次才有机会用上。

另存的长期笔记也一样，要经过查找和读入。缓存则用于复用相同材料的处理结果；它不会让一次请求能无限装入内容。

“工作桌”只比喻当前使用的材料；“资料柜”只比喻已经保存的记录。两者都不是模型的大脑。

Codex 实际逻辑
把一次模型调用想成“准备一次函数调用的参数”。Codex 要准备指令、消息与工具说明，再交给模型服务。下面是概念结构，省略了协议字段细节：
模型请求
├─ 适用指令：如何完成任务、哪些约束要遵守
├─ 输入消息：当前工作状态 + 当前采用的历史 + 新输入
│  └─ 工具调用及对应结果、文件片段、图片等内容块
└─ 可用工具：工具名称、用途、参数结构
“读取文件”返回的是文件片段；“声明 read_file 工具”只是告诉模型可以请求读取文件。有工具不等于文件已经读过。
发送前还会整理消息结构，例如保证工具调用与输出匹配，并移除当前模型不支持的媒体类型。规则文件也有加载预算，并非所有规则都会无限量装入。

AGENTS.md 从哪里读，为什么也可能不完整？
项目规则通常沿项目根到当前目录查找；同目录先看 override 文件，再看 AGENTS.md，再看配置的 fallback 文件名，不是遍历所有子目录。项目是否可信也影响读取。
项目文档共享字节预算，默认 32 KiB、可配置；超预算时文件尾部可能不被加载。当前规则没变时，无需再追加一条相同的规则更新消息；已有规则仍属于后续请求采用的上下文。变化时生成替换说明，删除时说明不再适用。压缩后重建当前状态，不会自动补回原先未加载的尾部。

动画里的 88 格、28 格怎样算？
“格”是本教程人为给卡片标的用量，不是真实 token。默认旧材料：规则 6 格 + 用户要求 8 格 + 查询与讨论过程 74 格 = 88 格。
本例的新材料：规则 6 格 + 用户要求 8 格 + 摘要 14 格 = 28 格。任务做到一半触发自动压缩时，可直接用这 28 格继续；新任务开始前自动整理后，再加入该例中 4 格的新消息，形成 32 格的请求。手动 /compact 则只展示整理完成，等你再发消息说明下一步，不假定它自动恢复刚才的工作。
拖动材料量滑块，只改变重复查询和讨论过程的长短；本例要保留的事实不变。真实压缩的体积、耗时与内容要通过实际运行观察，不能用本例的比例预测。
为什么“已经答完”时，这里不自动压缩？
这处检查的目的，是让 Codex 能继续处理还没完成的任务。如果最终方案已经发出，当前没有下一步要做，就不会因为这条规则启动压缩。
你再发一条新消息时，Codex 会在开始新任务前检查已有材料。这个时点，新消息本身可能还没加入，所以不能把滑块理解成“包含新消息的最终请求总量”。
源码还提供“任务结束后提前整理”的单独功能，是否执行取决于配置。本页把它放在进阶说明中，避免和“任务做到一半要继续”混在一起。
真实 Codex 怎么计量？为什么源码里既有 90% 又有 95%？
token 是模型计算输入规模的单位，不等于一个汉字，也不等于一条消息。
本教程固定的源码版本，在通常的 total 计量方式下：模型窗口记作 W，自动压缩基础限额取“解析后的模型限额”和 W × 90% 的较小值；用户配置可覆盖模型限额，缺少该限额才只用 90%。有效窗口使用另一个比例字段，缺省为 95%。达到相应限额会触发判断。
例如仅为演算，假设模型未提供更低限额、用户也未覆盖，取 W = 100,000 token：90,000 是上述自动压缩限额，95,000 是上述有效窗口。它们不是同一个数字的两种写法，也不是“聊到第几轮”。实际模型元数据、配置与计量模式可能不同。
另有按固定前缀之后的增长计量的方式，以及主动请求新窗口、换模型等分支。第 8 章带你读其中一条真实判断；完整条件见下面源码。

为什么不把所有原话都留下？
原话也要占空间。程序会给直接保留的内容分配一部分预算，并优先尝试放入较新的内容；放不下时，某条消息可能只剩一部分，较早消息也可能不再逐条带入。
可以把重建看成两份材料：一份是生成的摘要，另一份是额外留下的旧内容。20,000 和 64,000 限制的是第二份能留下多少，不负责决定什么时候开始压缩。下面用逐条装入的过程说明这两个预算。
“本地摘要”和“远端压缩”到底差在哪里？
这里的“本地”指客户端组织摘要流程，并不表示模型在你的电脑离线运行。新摘要仍可能由远程模型生成。
远端流程由服务返回压缩结果；其中可能含有加密字段。客户端能看到条目类型，却不能读出其中每个事实，所以本页不会给加密块编一份“内部原文”。
上面的按钮只用于比较两种实现，不会切换你实际 Codex 的设置。实际选哪种流程，要看服务能力和配置。

文字摘要路线：程序生成摘要以后，还会从用户说过的原话中挑近期内容，合计最多使用约 20,000 token 的预算。摘要另加，当前适用指令也另外重新准备。
远端 v2 路线：先按条目类型筛选，再让合格条目共享约 64,000 token。它可以包含用户内容和特定条目，不等于“所有旧消息都保留 64,000”。服务返回的新压缩条目另行放入。
要算的对象能否直接把预算当总量？
20,000 的原话 + 新摘要 + 重建的当前指令不能。原话是其中一部分。
64,000 的合格旧条目 + 新压缩结果 + 重建指令不能。各部分仍要共同装进最终请求。
实际用于裁剪的计数这里常用 UTF-8 字节数 ÷ 4 的近似，与模型真实 tokenizer 不完全相同。
例如：本例旧用户消息估算为 5,000、9,000、12,000。按“从新到旧”挑选，先放最新的 12,000，剩 8,000；再碰到 9,000 的消息时，就只能留下其中约 8,000 的头尾片段，更早的 5,000 不再直接带上。

保存下来的“继续工作状态”是什么？
可以把它理解成一张标记：“从这里往后，用这份整理后的材料继续。”源码里的一些记录会携带 replacement_history，也就是替代旧材料的新消息集合。
恢复会话时，程序可以先采用这份新材料，再接上后续消息。即使它为了恢复状态读过记录文件，也不代表文件中每句话都会重新发给模型。
恢复聊天还不等于把项目文件回退到某一天。文件当前是什么内容，需要另外检查。
能保证所有原始输出一直留在记录里吗？
不能。这里确认的是：普通会话正常压缩时，会追加压缩记录，没有沿这条流程清空旧记录文件。
但很长的工具输出可能在保存之前就已被裁短；记录策略也会筛选内容。临时会话、写入失败、之后的清理又是其他情况。因此，重要原文最好有可定位、可重新读取的来源。

不能把这一点简化成“失败时什么都不变”。部分流程在尝试期间可能已经追加输出或错误记录；我们能确认的是，新替代材料要走到成功步骤才会安装。
工具已经执行的动作，也不会因为摘要报错而自动撤销。例如程序在压缩前已写入文件，继续任务前需要先检查当前文件，再决定是否重做；不能盲目重复。

用自己的数字算“写一次、读多次”是否合算
沿用官方计价思路
下面沿用官方对新模型的计价区分：写缓存、读缓存与未缓存输入分别计费。只演算输入成本，令普通输入单价为 1；不计输出、重试或缓存失效。假设每次后缀都不同，显式断点只写稳定前缀。
公式：无缓存 = N × (P + S)；本例缓存 = 1.25P + (N−1) × 读取比例 × P + N × S。只用一次时，写缓存可能更贵；默认输入不是你的真实账单。

把缓存接回 Codex：输入稳定与材料缩短会互相影响
缓存与上下文
追加消息通常保留已有前缀；改写早期指令、工具定义或历史，会改变后面的前缀匹配。压缩能减少后续输入，但也可能改写原有前缀，使旧缓存只能复用到变化之前。这是两种机制的取舍，不能简单说“压缩后一定更便宜”或“命中缓存就无需压缩”。
观察时要同时记录输入 token、缓存读取 token、压缩本身的请求以及后续几次请求。仅看一次缓存命中率，无法判断整个任务的成本和质量。

从理解到设计
离开郊游故事，换一个未讲过的任务：给查询接口增加一个可选筛选条件，旧客户端不传这个条件时必须保持原行为。“兼容”就是旧调用方式仍然可用。

  2. 处理中发生压缩；摘要只写“增加筛选”，遗漏“旧客户端行为不变”。
  3. 第二天恢复会话，准备继续改代码。
请写下：哪条是硬约束？长日志应保留什么、其余怎样重读？从哪里确认压缩后的材料？恢复后先检查什么？怎样证明没有破坏兼容？
对照参考思路
硬约束是“旧客户端不传新参数时保持原行为”，应明确放入当前请求，并保留接口约定的来源位置。长日志保留失败摘要、相关行、测试命令与完整日志位置；不知道的部分重新读取。
恢复后核对目标、约束、已改文件和待办，再读取当前代码与遗漏的约定。至少检查“不传新参数”和“传新参数”两条行为；还要确认测试实际覆盖这些行为，不能仅凭测试进程退出码推定兼容已经证明。
一次失败不够判断是压缩问题。需要对照原始来源、进入请求的材料、摘要与最终修改，定位约束在哪一步消失或被误用。
怎样做一次真实观察
实践验收
  1. 记录条件：CLI 版本、源码对应关系、模型、配置与启用的功能；不要把本课快照当成你安装版本的证明。
  2. 选可核对的小任务：写两条硬约束，准备可重新读取的资料；记录压缩前完成到哪里。
  3. 观察事件与材料：区分工具输出被裁短、压缩开始、压缩完成、替代历史与后续请求。不可读的服务端压缩内容记为不可直接观察。
  4. 核对结果：任务是否满足约束、是否重复工作、是否需要重读；然后看用量和缓存。公开分享前隐去会话里的私人内容。
