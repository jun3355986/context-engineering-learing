## 0. 两套链一页对照（先看骨架，再看细节）

两套工具**同形**：都走"组装 → 触发 → 摘要 → 保留 → 工具输出 → 恢复"六个节点。**差别在每一段的具体做法**。

```text
节点        ① Codex（a07c8eb）                       ② pi（b45e0eb）
────────────────────────────────────────────────────────────────────────────
组装   build_prompt：input+tools+base_instructions     _installAgentRequestProjection：
       +output_schema；WorldState 差分更新                projection.messages + tools；
                                                        系统提示词具名 section + 逐段 diff
触发   两条线：范围线 min(M,90%W) OR 整段线 W×95%       一条线：A > W − reserveTokens(16384)
摘要   本地模板 / 远端 v2（替代历史 encrypted_content） 固定结构摘要 + UPDATE 增量；序列化截断
保留   候选=真用户消息，从新到旧装 20,000 共享预算      切点=user/assistant 边界，绝不切 toolResult
工具输出 ceil(bytes/4) 头尾 + 分片 64KiB + 落盘预览     2000 行/50KB 先到者；read 保头 / bash 保尾
恢复   替代历史 + 后缀回放                              持久化断点：摘要 + firstKeptEntryId 直接重建
```

**一句话记忆**：**Codex 把"两条线 + 替代历史 + 后缀回放"当骨架；pi 把"一条线 + 可重建投影 + 持久化断点"当骨架。** 两者都在**磁盘上追加、不删旧记录**——差别在**模型看见什么、怎么重建**。

## 1. 节点① · 组装（请求怎么拼出来）

**pi 走读**

- **进入条件**：一次 run 开始；agent 内核**每次发请求前**调 `prepareRequest` 钩子（pi 在此挂钩子）。
- **处理**：`_installAgentRequestProjection`（`core/agent-session.ts:788-845`）取 `buildSessionProjection().messages` 作**规范上下文**，配 `agent.state.tools.slice()`：

```ts
// agent-session.ts:793-800（节选，快照 b45e0eb）
const projection = this.sessionManager.buildSessionProjection();
const canonicalContext = {
  ...request.context,
  messages: projection.messages,        // ← compaction 已应用的投影
  tools: this.agent.state.tools.slice(), // ← 可执行工具实现
};
```

- **系统提示词侧**：`buildSystemPromptSections()`（`core/system-prompt.ts:128-193`）生成具名 section，除 `preamble` 外每段包 `<同名标签>`；`diffSystemPromptSections()`（`:217-229`）**逐段 diff**，只把**变化段**作为补丁追加。
- **前后状态**：**前**＝磁盘只追加 JSONL 树 + 内存 `agent.state`；**后**＝本次请求的 `canonicalContext`（**不改会话**）。section 清单：`preamble / tools / rules / docs / addendum / project_context / skills / cwd / <自定义>`。
- **失败**：本节点**无失败分支**（纯拼接）；但扩展可在接缝改写——`context` / `context_with_system` / `before_provider_request`（`pi-ext-02`）。
- **证据**：`pi-assembly-01`、`pi-assembly-02`、`pi-rule-01`、`pi-rule-02`。

**与 Codex 同节点对照**

| 对照点 | Codex（`a07c8eb`） | pi（`b45e0eb`） |
|---|---|---|
| 组装函数 | `build_prompt`（`core/src/session/turn.rs` L1563–1591）：`input + tools + base_instructions + output_schema` | `_installAgentRequestProjection`：`projection.messages + tools` |
| 规则发现 | 项目根 → 当前目录，**不遍历子树**；`AGENTS.md` 差分更新；规则共享 **32 KiB 字节预算**（A4/A5/A6） | `AGENTS.override.md → AGENTS.md → CLAUDE.md`；**agent 目录（全局）+ cwd 祖先链**（`pi-rule-01`）；**未发现字节预算常量**（该证据卡"不能证明"栏已注明） |
| 前缀稳定手段 | 差分片段（`codex-diff-01`） | 具名 section + 逐段 diff 补丁（服务提示词缓存前缀） |

> **不排名次**：两侧都在"**只把变化的部分重发**"；Codex 落在规则/工作状态，pi 落在系统提示词 section。**做法不同，不是优劣。**

**自测①**：为什么 pi **不直接把内存消息数组发出去**？
<details><summary>答案</summary>
因为要先算一份**投影**——`projection.messages` 已经把 `compaction` 条目算进去了。`messages` 声明 **provider 可见载荷**，`context.tools` 保留**可执行实现**，两者分开是为了**让工具实现的元数据不进请求体**（`pi-assembly-01`）。
</details>

## 2. 节点② · 触发（什么时候"到线"）

**pi 走读**

- **进入条件**：三处时机——**轮中**（每批工具结果落定、下一次 assistant 之前，`prepareNextTurn`）、**新用户提示前**（`_prepareRun`）、**运行结束后**（`_handlePostAgentRun → _checkCompaction`）；外加**手动** `/compact`。
- **处理**：`shouldCompact()`（`core/compaction/compaction.ts:267-270`）——**唯一阈值线**：

```ts
// compaction.ts:267-270（节选，快照 b45e0eb）
export function shouldCompact(contextTokens: number, contextWindow: number, settings: CompactionSettings): boolean {
	if (!settings.enabled) return false;
	return contextTokens > contextWindow - settings.reserveTokens;   // ← 唯一阈值
}
```

默认常量（`compaction.ts:126-130`）：`reserveTokens = 16384`、`keepRecentTokens = 20000`、`enabled = true`。
- **用量怎么量**（`pi-trigger-02`）：优先取**最近一条有效 assistant 的 usage**（`totalTokens` 或 `input+output+cacheRead+cacheWrite`），其后用 **`ceil(chars/4)`** 估算；**usage 早于最近一次 `context_edit`/`compaction` 时全量重估**（避免压缩后仍拿旧的大 usage 误触发）。
- **前后状态**：**前**＝当前投影用量 `A`；**后**＝要么继续请求，要么进入压缩（节点③）。
- **失败**：命中 provider `context overflow` 或"可恢复的 length stop" → `_runAutoCompaction("overflow", …)`，**只允许一次** compact-and-retry（`_overflowRecoveryAttempted`，`pi-fail-01`）。
- **证据**：`pi-trigger-01/02/03`、`pi-fail-01`。

**与 Codex 同节点对照**

| 对照点 | Codex（`a07c8eb`） | pi（`b45e0eb`） |
|---|---|---|
| 阈值线数量 | **两条**：范围线 `min(M, 90%W)` **OR** 整段线 `W×95%`（`codex-trigger-01/02`） | **一条**：`A > W − 16384`（`pi-trigger-01`） |
| 预留口径 | 预留**分两笔**（有效窗口比例 + 整段线） | 预留**不拆**——`reserveTokens` 同时覆盖"模型回复空间 + 摘要输出空间" |
| 范围口径 | `Total` / `BodyAfterPrefix`（比"全部材料"或"基线后增长量"） | 单一 `contextTokens`（无 scope 分支） |
| 时机 | 轮前 / 轮中 / 轮后 + （新快照 `76ed3b4`）**后台投机压缩** | 轮中 / 新提示前 / 运行结束后 + 手动；**未含"模型切换触发"**（`pi-trigger-03`） |

> **红线一提醒**：Codex 新快照**新增 `session/async_compaction.rs`**；其**特性登记**在 `features/src/lib.rs` L2066–2071（**`Stage::UnderDevelopment`、`default_enabled=false`**）——属"**有条件实现（默认关、开发中）**"，**不能写成"Codex 默认会做后台压缩"**。
> **数字纪律**：200K 窗口下 pi 触发点 ≈ `200000 − 16384 = 183616`，是**教学换算【演示】**，**非实测**（`pi-trigger-01` 的"不能证明"栏）。

**自测②**：pi 的 `reserveTokens` 和 Codex 的"两笔预留"分别解决了什么？
<details><summary>答案</summary>
pi 用**一笔** `reserveTokens(16384)` 同时给"模型回复"和"摘要输出"留空间——**阈值线只有一条**，简单；Codex 把预留**拆成两笔**（比例字段 + 整段线）——**触发判定有两级**，可被更低字段按下。**两者都是"给输出留地方"，不是谁更准**（无实测，`NOT_RUN`）。
</details>

## 3. 节点③ · 摘要（旧历史怎么变成一段话）

**pi 走读**

- **进入条件**：`shouldCompact` 为真（自动），或用户 `/compact`（手动），或溢出恢复。
- **处理**：两条入口都**先过 `prepareCompaction()` + `session_before_compact` 钩子**（可取消 / 可自定义摘要），再调底层 `compact()`：
  - 手动 `compact()`（`agent-session.ts:2794-2939`）——**先 `abort()` 当前操作**，且**不重试、不续跑**被打断的那一轮。
  - 自动 `_runAutoCompaction(reason, willRetry)`（`:3127-3274`）——`reason ∈ {overflow, threshold}`。
  - 摘要提示词**固定结构**（`compaction.ts:507-538`）：`Goal / Constraints & Preferences / Progress(Done/In Progress/Blocked) / Key Decisions / Next Steps / Critical Context` + `<read-files>/<modified-files>`。
  - **有旧摘要时改用 UPDATE 提示词**（`PRESERVE all existing information… ADD new…`）→ **增量摘要**，旧摘要作为 `<previous-summary>` 传入（`pi-summary-01`）。
  - 摘要 `maxTokens = min(floor(0.8 × reserveTokens), model.maxTokens)`；序列化把 **toolResult 截到 2000 字符、省略 thinking 块**（`pi-summary-03`）。
- **前后状态**：**前**＝内存历史（含 `messagesToSummarize`、`previousSummary`）；**后**＝成功后 `appendCompaction()` 追加 `CompactionEntry{summary, firstKeptEntryId, tokensBefore}`（`core/session-manager.ts:1261-1287`）。
- **失败**：摘要 `stopReason=error` 或 `length` → **抛错，禁止半截摘要落盘**（"must not become a session checkpoint"）；摘要调用**尝试调工具**也判失败；流式瞬时错误走 `retryAssistantCall`（默认 `maxRetries=3`）（`pi-fail-01/02`）。
- **证据**：`pi-compact-01`、`pi-summary-01/03/04`、`pi-fail-01/02`。

**与 Codex 同节点对照**

| 对照点 | Codex（`a07c8eb`） | pi（`b45e0eb`） |
|---|---|---|
| 摘要来源 | **本地模板** `SUMMARIZATION_PROMPT` / **远端 v2**（`encrypted_content`） | 本地 LLM 调用；**固定结构模板** + 有旧摘要时 **UPDATE 增量** |
| 提交语义 | 新快照（`76ed3b4`）改为"**成功后一次性提交**"（不半提交，`codex-fail-02`） | **只在成功后 `appendCompaction`**；失败/取消不追加、不安排内部重试（`pi-fail-02`） |
| 溢出处理 | `ContextWindowExceeded` → 移除副本最早项、`retries=0` 重试 | 溢出恢复**仅一次** `compact-and-retry`（`pi-fail-01`） |
| 摘要落点 | 替换内存历史 + 追加 `CompactedItem` 检查点 | 追加 `CompactionEntry`（**只追加，不删旧条目**） |

> **两侧共同点（写下来）**：**压缩本身不产生外部副作用**（只追加会话条目）；**失败不留下半成品**。**但**——压缩前**已经执行过的工具动作不会撤回**（工具副作用在压缩之前已发生，术语表 §10"副作用"）。

**自测③**：pi 的摘要失败后，会话会怎样？
<details><summary>答案</summary>
**抛错、不写检查点、不安排内部重试**，只**保留已发生的编辑**；因为**只有成功才 `appendCompaction`**，所以**不会留下半成品**（`pi-fail-02`）。⇒ **可重复执行 `compact()`**（幂等性由"只在成功时追加"保证）。
</details>

## 4. 节点④ · 保留（切点切在哪、留下什么）

**pi 走读**

- **进入条件**：`compact()` 内准备"摘要哪些消息"时。
- **处理**：`isCutPointMessage()`（`core/compaction/compaction.ts:351-364`）——**绝不切在 `toolResult`**：

```ts
// compaction.ts:351-364（节选，快照 b45e0eb）
function isCutPointMessage(message: AgentMessage): boolean {
	switch (message.role) {
		case "user": case "assistant": case "bashExecution":
		case "custom": case "branchSummary": case "compactionSummary":
			return true;
		case "toolResult":
			return false;    // ← 工具结果必须跟随它的工具调用
	}
	return false;
}
```

- **切点算法**：`findProjectedCutPoint()`（`:802-870`）从最新往回累加 `estimateTokens`，累计 ≥ `keepRecentTokens(20000)` 时取"**≥ 当前下标的最接近合法切点**"；**若无合法切点则退回起点**；若**单个用户消息跨度本身超预算** → **split turn**，生成**两份摘要再合并**（`:994-1033`）。
- **前后状态**：**前**＝待摘要消息集；**后**＝`firstKeptEntryId`（**保留段起点**，写进 `CompactionEntry`）。
- **失败**：无合法切点 → **退回起点**（可能摘要全部）；这是**设计上的兜底**，不是异常。
- **证据**：`pi-summary-02`。

**与 Codex 同节点对照**

| 对照点 | Codex（`a07c8eb`） | pi（`b45e0eb`） |
|---|---|---|
| 保留预算 | **20,000**（本地）/ 64,000（远端 v2）（`codex-retain-01/02`） | `keepRecentTokens = 20000`（`pi-summary-02`） |
| 保留候选 | **只收"真正的用户消息"**（排除摘要前缀），从新到旧装预算，装不下就停 | **切点**走在 `user/assistant/bashExecution/custom/branchSummary` 边界 |
| 切点规则 | 边界处按剩余预算**截短单条** | **绝不切在 `toolResult`**；无合法切点退回起点；超长单轮走 **split turn** |
| 不变量 | 历史维护**"调用↔结果配对"不变量**（移除孤立输出，`history.rs` L962–980） | 切点规则**本身**就是在维护配对（结果必须跟随调用） |

> **同数字、不同机制**：两侧保留预算都写着 **20,000**——但 Codex 是"**装预算挑候选**"，pi 是"**往回累加找切点**"。**数字相同 ≠ 做法相同。**

**自测④**：pi 为什么**绝不切在 `toolResult`**？无合法切点时怎么办？
<details><summary>答案</summary>
因为**工具结果必须跟随它的工具调用**——切在结果处会**破坏"调用↔结果配对"不变量**（术语表 §1"工具调用与结果配对"）。**无合法切点时退回起点**（`pi-summary-02`）。
</details>

## 5. 节点⑤ · 工具输出（单条输出怎么治理）

**pi 走读**

- **进入条件**：工具执行完成、**写回消息列表之前**。
- **处理**：两条**独立上限**，**先到者胜**（`core/tools/truncate.ts:11-13`）：

```ts
export const DEFAULT_MAX_LINES = 2000;
export const DEFAULT_MAX_BYTES = 50 * 1024; // 50KB
export const GREP_MAX_LINE_LENGTH = 500;    // 每行 grep 上限
```

  `read/grep/find/ls` → `truncateHead`（保头）；`bash` → `truncateTail`（保尾）；**绝不返回半行**（除 bash tail 行内极端情形 `:205-212`）；UTF-8 边界对齐。
- **bash 超限落盘**（`core/tools/bash.ts:333-355`）：`output.snapshot({ persistIfTruncated: true })` → **超限即持久化**，请求里只留**尾部预览 + 文件路径**：

```text
[Showing lines <start>-<end> of <total> (50.0KB limit). Full output: <tempPath>]
```

- **前后状态**：**前**＝全量输出（`output-accumulator.ts` 用 `maxBytes*2` 滚动缓冲控制内存）；**后**＝`toolResult` 条目（含 `details.truncation`、`fullOutputPath`）；**下一次请求只带预览**。
- **失败**：极端 bash tail **行内**情形可能出现**半行**（`:205-212`，源码注释明示的例外）。
- **能否找回原文**：**能**——读 `fullOutputPath` 指向的临时文件（保存边界＝该临时文件；lifecycle 由 `closeTempFile` 管理）。
- **证据**：`pi-trunc-01/02`。

**与 Codex 同节点对照**

| 对照点 | Codex（`a07c8eb`） | pi（`b45e0eb`） |
|---|---|---|
| 计量口径 | `ceil(bytes/4)`（**按字节**，`codex-trunc-01`） | **2000 行 / 50KB**，**先到者胜**（`pi-trunc-01`） |
| 裁剪方向 | **头尾**（保头保尾、删中间，加截断标记） | `read` 族**保头** / `bash` **保尾**（**按工具分流**） |
| 分片预算 | 分片输出与 MCP 结果各 **64 KiB**（`rollout/src/policy.rs` L16–19） | **单条**两条上限；`grep` 另设**单行 500 字符** |
| 落盘 | 落盘 + 请求里只留**预览头部**；活动历史裁剪只作用 **live 副本**，rollout 保存**未裁剪原载荷** | bash 超限落临时文件，请求里只留**尾部预览 + 路径** |
| 共享预算 | 同一请求内**多块输出共享预算**（×1.2 余量） | **未发现**对应"多块共享预算"机制（`pi-trunc-01` 未列） |

> **不排名次**：Codex 用"字节 + 头尾"，pi 用"行/字节双上限 + 按工具分流"。**都是"进列表前限长"，落盘都在，都能找回原文。**

**自测⑤**：pi 的 bash 输出超限后，**模型**看到什么？**原文**去哪了？
<details><summary>答案</summary>
模型看到的是**尾部预览 + 一行提示**（`[Showing lines X-Y of N (50.0KB limit). Full output: <path>]`）；**全量原文**写进**临时文件**（`fullOutputPath`）。**模型不会自动读回原文**——要找回只能**主动读那个文件**（`pi-trunc-02`）。
</details>

## 6. 节点⑥ · 恢复（关掉再打开，恢复了什么）

**pi 走读**

- **进入条件**：`SessionManager.open()` / `continueRecent()` 读回会话文件（`core/session-manager.ts:1766-1801`）。
- **处理**：磁盘形态＝**只追加 JSONL 树**（每行一条目，按 `id/parentId` 成树，`CURRENT_SESSION_VERSION = 3`，`:41`）；压缩**只追加** `CompactionEntry`，**不删除**任何旧条目。恢复时 `buildContextEntries`（`:476-512`）找到**最新 compaction**，输出 = `[compaction] + firstKeptEntryId 起的所有条目 + compaction 之后的所有条目`——**不重跑压缩、不重算摘要**。
- **摘要对模型长什么样**：`sessionEntryToContextMessages` → `convertToLlm` 把 compaction 条目转成**一条 user 消息**，内容包在 `<summary>…</summary>` 前后缀里（`core/messages.ts:11-17`）：

```ts
export const COMPACTION_SUMMARY_PREFIX = `The conversation history before this point was compacted into the following summary:\n\n<summary>\n`;
export const COMPACTION_SUMMARY_SUFFIX = `\n</summary>`;
```

- **前后状态**：**前**＝磁盘 JSONL 树；**后**＝**重建的投影**（摘要 + 保留段 + 后续条目）。更早的原始条目**被省略**（**仍在文件里**）。
- **失败**：摘要失败不落盘 → 恢复时**用更早的 compaction 断点**（因为失败的压缩根本没写进去）。
- **证据**：`pi-persist-01`、`pi-recover-01`、`pi-version-03`。

**与 Codex 同节点对照**

| 对照点 | Codex（`a07c8eb`） | pi（`b45e0eb`） |
|---|---|---|
| 落盘形态 | rollout 存档（追加、**不删旧记录**） | **只追加 JSONL 树**（`id/parentId`） |
| 写回动作 | ①替换内存历史 ②追加 `CompactedItem` 检查点 ③`persist_rollout_items`（`session/mod.rs` L4130–4222） | `appendCompaction` 追加 `CompactionEntry`（`session-manager.ts:1261-1287`） |
| 恢复路线 | **替代历史 + 后缀回放**（`rollout_reconstruction.rs` L480–520） | **持久化断点**：摘要 + `firstKeptEntryId` 直接重建（`buildContextEntries`） |
| 摘要呈现 | 替代历史列表 | compaction 条目 → **一条 user 消息**（`<summary>…</summary>`） |
| 找回原文 | 旧记录仍在 rollout 存档里 | 旧条目仍在 JSONL 里 |

> **统一裁决（C-03 / C-12）**：两侧都是 **"摘要不可逆 ≠ 源记录被删除"**——**模型可见层不可自动恢复**；**磁盘原文在保留期内可查**。"绝不可能找回"**仅对模型可见层成立**（`pi-recover-01`、`pi-version-03`）。

**自测⑥**：pi 恢复时会**重跑压缩**吗？被压掉的细节**能自动回到模型**吗？
<details><summary>答案</summary>
**不会重跑**——`buildContextEntries` 直接用**持久化的** `CompactionEntry.summary + firstKeptEntryId` 重建投影（**压缩只付一次代价**）。**被压掉的细节不会自动回到模型可见上下文**；但**原始条目仍在磁盘 JSONL 里**，**人工可读**（`pi-recover-01`）。

## 8. 闭源统一示范：Claude / Grok 的"可见边界如何理解"

> **本节的定位**：M10 只说了"闭源工具走**可观测行为链**"。本节给**统一示范**——**没有源码时，一条结论要怎么写成"不越界"的样子**。素材来自 `02-工具/claude-code-cli/证据导读.md`（T05）与 `02-工具/grok-builder/证据导读.md`（T12）。

### 8.1 第一步：把"证据"分三级、逐句挂角标

| 等级 | 名称 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| **①** | 官方文档 / 发布说明（**承诺行为**） | 产品**承诺**的默认行为、配置键名、单位与边界 | **承诺 ≠ 该版本实际这样跑**；文档不写的实现细节不可得 |
| **②** | 官方分发件 / 本地 CLI 可观测项（**标注观察方法**） | 特定版本**确实存在**哪些标志、配置键、目录、文件与字段 | **标志存在 ≠ 该机制默认启用**；本机残留 ≠ 官方默认布局 |
| **③** | 社区线索 | **只是线索**，用于提出待核验问题 | **不得**独立证明任何默认行为；**不得写成"源码"** |

**角标写法**：`【①文档】` / `【②分发件观察】` / `【③社区线索】`。**高风险主张**（触发阈值、落盘行为、压缩不可逆性）**必须同时给等级与"不能证明"**。
**两个常引示例（与交付件 1 同一套 ID）**：Claude 的 CLI 侧可观测项走 `claude-cache-01..05`（只写"**客户端可观测部分**"）；Grok 的**版本漂移**走 `grok-version-02`（1.0.50 → 1.0.52，**同一条文档行号都会偏移**——引文档**必须带版本关系**）。

### 8.2 第二步：用 **U 表**把"不可观测"显式登记

闭源工具不写"我没看到"，而写 **U 表（不可观测边界清单）**——每条三栏：**不可观测项 / 原因 / 影响结论**。这就是**"未知保留未知"的可操作形态**：

| 包 | U 表条目（示例） | 结构示范 |
|---|---|---|
| **T05 Claude** | `U-01` 内核常量名与公式（旧报告 `effectiveWindow − 13_000` 等）→ 原因：**闭源二进制，本轮未反编译** → 影响：`LQ-11`、`C-01/C-02`（Claude 部分）标**未决**，**不用旧报告数值当事实** | 见 `claude-code-cli/证据导读.md` §4（`U-01`–`U-07`） |
| **T12 Grok** | `U-03` 服务端 prompt cache 的**命中实现 / TTL / 缓存键 / 前缀断点** → 原因：**服务端行为，CLI 只能读到 `cache_read_input_tokens`/`cache_creation_input_tokens`** → 影响：`grok-cache-02` 只写"**客户端可观测部分**" | 见 `grok-builder/证据导读.md` §4（`U-01`–`U-07`） |

**U 表的三条使用纪律**：
1. **凡 U 表命中处**，结论一律标 **未决 / 文档承诺级**，**不得**用"社区还原数值"填坑。
2. **`UNOBSERVABLE` 是状态词，不是失败词**——它表示"**本地源码读不出来**"，与"机制不存在"**严格分开**。
3. **不得补造源码**：任何把**反混淆产物 / 二进制字符串**当"源码"引用的做法，**两包一律不采纳**。

### 8.3 第三步：把"源码链"翻译成"可观测行为链"

**统一示范**：同一条链路，**开源写法**与**闭源写法**逐节点对应——

| 节点 | 开源工具（pi / Codex）写什么 | 闭源工具（Claude / Grok）**只能**写什么 |
|---|---|---|
| 组装 | 函数名 + 行号 + SHA（如 `_installAgentRequestProjection`） | **【①文档】承诺**的组装顺序 + **【②分发件观察】**可核对的落盘件（Grok：`system_prompt.txt` / `prompt_context.json`） |
| 触发 | 阈值公式 + 常量（如 `W − 16384`） | **【①文档】**的**配置键名与默认值**（Grok：`auto_compact_threshold_percent` 默认 85）；Claude：**默认百分比未公布** → 标未决 |
| 摘要 | 模板原文 + `maxTokens` 公式 | **【①文档】**的"先清旧工具输出再摘要"（Claude 两段式）；**摘要 prompt 具体文本** → **U-05，不可得** |
| 保留 | 切点函数 + 预算常量 | **【①文档】**承诺的"保留最近若干"；**选择算法细节** → **U-06，文档承诺级** |
| 工具输出 | 上限常量 + 落盘路径拼接 | **【①文档】**的内联上限与预览长度（Claude：30,000 字符 / 2,000 预览 / >64 MiB 截断） |
| 恢复 | 恢复函数 + 重建规则 | **【①文档】**"摘要不改磁盘、原文留在 transcript"（`claude-resume-05`）；Grok：`updates.jsonl` 重放 |

**示范结论（照这个口径写）**：
- ✅ 正确："**【①文档】Claude Code 承诺先清理较旧工具输出、再按需摘要对话**（`claude-compact-05`）；**是否走服务端 `clear_tool_uses_20250919`（API 能力）还是客户端实现——文档未明说，标未决**。"
- ❌ 错误："Claude 的 `clear_tool_uses` 函数在 XX 行调用"——**闭源无源码，这是补造**。
- ✅ 正确："**【②分发件观察】Grok 会话目录存在 `summary.json` / `compaction_checkpoints/`**；**其内部摘要算法不可得**（`U-01`）。"
- ❌ 错误："Grok 的两趟压缩内部按 XX 规则分段"——**`U-01` 命中，不得补造**。

> **一句话**：**闭源工具不是"讲不清"，而是"讲清边界"**——**能证明的给角标，不能证明的进 U 表**。这套写法与开源链**同样严格**，只是**证据来源不同**。
