1. 说出"**token 是计量的最小单位**"，并解释为什么**同一段中文，不同工具估出的数字不一样**（口径不同，且多为低估）。

## 场景：没人操作，屏幕却冒出"正在压缩上下文……"

小林的会话聊了两个小时：行程改了四版、工具查了十几次。忽然屏幕上滚过一行提示：**"正在压缩上下文……"**

小林**没做任何操作**。他盯着这行字犯嘀咕：

> 它怎么知道"该收拾桌子了"？是我哪一步点错了，还是它自己算的？它心里到底有**几本账**？

答案：**程序自己算的**。它一直维护着几条数字，每拍都对着**几条线**比一比——**到线了就动手**。本单元就是把这几本账和这几条线一次说清。

## 核心概念

### 一、最小单位 token：同一个数字，三家算法不同

要谈"空间"，先认**丈量单位**。这个单位大部分读者平时根本遇不到。

**【人话】** 模型不是按"字"处理文字的，而是按 **token（令牌）**——把文字切碎后的小块。一个词、半句话、一个标点，都可能被切成若干 token。**模型一次请求能装多少 token 是有硬上限的。**

这个上限叫**上下文窗口（context window，记作 W）**。请求里的全部材料（指令、历史、工具结果、你的输入）**加上模型的输出**，共用这一个大池子——**不是"输入一个窗口、输出另一个窗口"**。

token 和"字数"怎么换算？**分三种口径，别混**：

| 口径 | 说明 | 用途 |
|---|---|---|
| **模型真实 tokenizer** | 服务端把文本切块后的准确数量 | 官方计费与上限的**最终裁判** |
| **服务端返回的 usage** | 每次响应附带"这次输入/输出各多少 token" | 程序校准本地估算的**锚点** |
| **本地近似估算** | 程序在服务端返回前自己先估个大概 | 触发判定的**日常输入** |

**【当心】第三行是全课最容易踩的坑**：本地估算**各家算法不同，而且多为低估**——这正是冲突 **C-06** 的裁决要点：

- ① **Codex**：`ceil(UTF-8 字节数 ÷ 4)`（**按字节**）【源码常量】`codex-trunc-01`
- ③ **pi**：`Math.ceil(字符数 ÷ 4)`（**按字符**）【源码常量】`pi-trigger-02`
- ⑤ **ocv1 / ⑥ ocv2**：`round(字符数 ÷ 4)`，**CJK 下偏低估**（4 个汉字 = 12 字节，只算 1）【源码常量】`OBS-ocv1-token-01` / `OBS-ocv2-token-01`
- ⑦ **Gemini**（历史·存档）：非 ASCII 按 **1.5/字符**，对中文是**高估**（不是保守）`OBS-gemini-trunc-01`
- ⑨ **dsh**：`ceil(字符数 ÷ 4)`，**对中文低估**（实测 400 汉字 = **108** token）【源码常量/实测】`dsh-trigger-01`、`OBS-dsh-meter-01`
- ④ **oh-my-pi**：**不走 `chars/4` 口径**，用量优先取 provider 的 `contextTokens` `ohmy-trigger-02`
- ⑧ **Grok**：随包文档/配置里**未见** `chars/4` 式估算（只用字节/字符口径）`grok-toolout-01/03`

> **C-06 裁决**：**"`len//4` 对中文保守"不成立**——口径分列、多口径**低估**，且**不外推全 tokenizer**。真实数字以服务端 usage 为准（T19 可核）。**【T19 实测：dsh 启发式对中文/混合文本低估 ≈2.1×（32,775 vs provider 77,958）；ocv1 免费模型 cost=0 可核验；其余为订阅/代理、费用不可核验；真实分词仍 UNOBSERVABLE（证据：T19/05-dsh.md、06-ocv1.md §0）】**

### 二、四本账 + 三条线

**【人话】** 说白了：程序不是"每拍把所有字重数一遍"，而是**以服务端上次的实测为锚点**，加上本地刚加进来的材料，得到一个"当前用量"。再拿这个用量去和几条**预先算好的线**比。

程序维护的**四本账**（教学变量名做了简化，名字沿用真实字段含义）：

| 变量 | 含义 | 通俗理解 |
|---|---|---|
| **W** | 上下文窗口（context window） | 这张桌子**总共**多大 |
| **p** | 有效窗口比例（字段缺省 **95**，可被模型元数据/配置改写） | 桌子**实际允许用**多大比例 |
| **H = W × p ÷ 100** | 有效窗口（usable context window） | 桌子**真正的可用上限** |
| **A** | 当前活动上下文用量（active context tokens） | 桌上**现在堆了多少** |
| **P** | 本窗口开始时的输入基线（prefill） | 你**收拾过一次桌子后**的起点高度 |

**A 是怎么量出来的**（不是从会话开头累加的账单总和）：

```
A = 上次服务端返回的 usage.total_tokens
    + 估算（在上次模型输出之后、本地新加入的条目）
    + 若服务端未含旧推理内容，另做补计
```

再认**三条线**（术语表 §2 固化的**三层结构**，不得当成两套机制）：

| 线名 | 口径 | 说明 |
|---|---|---|
| **基础线（90%）** | `(W × 9) / 10` | 范围线的**默认原料**，**非模型原理规定** |
| **范围线** | `min(M, 基础线)` | 对 `total` 口径是**全部材料**；对增长口径是**基线之后的增长量** |
| **整段线** | `H = W × p ÷ 100` | **所有材料都不得超过**的硬检查线 |

> **本节最重要的一句话**：**触发线（伞名）= 范围线 OR 整段线**；任一为真，就叫"**触发到线**"。
>
> 注：**自动整理限额 M**（`auto compact token limit`）= 模型元数据字段；**这是 Codex 专有口径，dsh 无 M 字段，不得套用**。

**为什么是 90% 和 95%，不是 100%？** 两个原因都指向同一件事——**要给"输出"和"整理动作本身"留空间**：

1. 模型回复**也吃同一个池子**；输入顶到 100%，就没地方写回复了。
2. **整理本身也要调用模型**（生成摘要/交接材料），它需要输出空间——输入顶满，摘要就写不完。

**【当心】别写"90–95% 是统一压缩阈值"这类总括句。** 该说法已被**九工具全部否证**（**C-01/C-02**）：各家口径从 50% 到"窗口减固定值"都有。**口径只能逐工具列**——见下文对照表。

### 三、"到线"之后：谁在什么时候执行（三时机对照）

"到线"只是**第一层**判断。真正动手前还有**第二层**——**执行的时机与入口**：

| 入口 | 触发条件 | 初学者读法 |
|---|---|---|
| **轮前**（新任务开始前） | 检查当前用量是否到线 | 开始下一步**之前**先看桌子满没满 |
| **轮中**（同一任务还要继续） | 模型还要继续（`needs_follow_up`）**且**（有新窗口请求 **或** 到线） | 活还没干完，但桌上已堆不下 |
| **轮后**（任务完成后的可选整理） | 配置比例 `q > 0` 且到线/达到 q；无待处理输入；未取消 | 干完一段"提前收拾"；**缺省关闭**（q 缺省 0） |
| **切换模型** | 前后双方整理兼容性哈希不同；或换到窗口更小的模型 | 换了更小的桌子，或旧交接材料不兼容 |
| **手动 /compact** | **不要求到线**，随时可 | 你主动说"帮我把桌子收拾一下" |

**【当心】轮前检查有个必须记住的细节**：它发生在**新用户输入写入之前**。源码在此留了 TODO，明说**还没把"即将写入的新输入"估算进去**——所以一次巨大的粘贴（比如 5 万字日志）**仍可能一步跨过安全线**。这是"有界但非万能"的真实工程取舍。**【T19 部分：触发时点已有观测（claude ≈98%、grok 85%/72%），但"一次巨大粘贴跨过安全线"未专门注入 → 保留未决（证据：T19 总表 §3）】**

## 五个数字算例（本单元产出物演练）

> **统一舞台（教学演示）**：W = 200,000、p = 95、默认范围口径 `total`。**每个例子先自己算一遍再看结论。**

**例 1【演示】· Codex 两线 OR 判定（完整走一遍）**
设模型字段 M = 150,000，A = 152,000。
→ 基础线 = 200,000 × 9 ÷ 10 = **180,000**；范围线 = min(150,000, 180,000) = **150,000**；H = 200,000 × 95% = **190,000**。
→ A = 152,000：**152,000 ≥ 150,000，范围线到线**（整段 152,000 < 190,000 未到）。**到线成立。**

**例 2【源码常量】· 同一窗口，"预留式"三兄弟同台（W = 200,000）**
- ③ pi：`W − 16384` = **183,616** `pi-trigger-01`
- ④ oh-my-pi：`W − max(15%×W, 16384)` = 200,000 − 30,000 = **170,000** `ohmy-trigger-01`
- ⑥ ocv2：`W − max(10%×W, 16000)` = 200,000 − 20,000 = **180,000** `ocv2-trigger-01`

**【当心】** ⑧ Grok 的触发线是 `85% × W` = **170,000**（`grok-trigger-02`）——**数字和 oh-my-pi 一样，口径完全不同**（一个"预留 15%"，一个"85% 触发"）。**数字相同 ≠ 机制相同**，引用时务必写清是哪一类。

**例 3【源码常量】· dsh 双上限（W = 200,000，输出预留 O = 16,000）**
→ `floor(min(0.8 × 200,000, 200,000 − 16,000 − 65,536))` = `floor(min(160,000, 118,464))` = **118,464** `dsh-trigger-01`
→ 读法：**比例上限（160,000）和"留足输出+余量"上限（118,464）取更小者**——**双上限**，不是单条比例线。

**例 4【源码常量】· ocv1 绝对预留（与窗口大小无关）**
→ `reserved = compaction.reserved ?? min(20000, maxOutputTokens)`；若 maxOutput = 32,000，则 reserved = **20,000**，`usable = limit.input − 20,000` `ocv1-trigger-01/02`
→ 读法：ocv1 是**绝对预留口径**（非百分比、非两线）——**窗口再大，也先扣掉这 2 万**。

**例 5【演示】· 同一个数字，三种估算口径（C-06 演示）**
同一段 **400 个汉字**（UTF-8 共 1,200 字节）：
- ⑨ dsh：`ceil(400 ÷ 4)` = **100**（按字符）——**实测 108，低估** `OBS-dsh-meter-01`
- ① Codex：`ceil(1,200 ÷ 4)` = **300**（按字节）——**非"保守"**，只是口径不同 `codex-trunc-01`
- ⑦ Gemini：400 × 1.5 = **600**（非 ASCII 1.5/字符）——对中文**高估** `OBS-gemini-trunc-01`

→ 同一段话，估出的 token 数 **100 / 300 / 600** 三档。**这就是"本地估算只能当粗估"的实感**；真实值以服务端 usage 为准。

**五例结论对照**：

| 例 | 用的线 / 口径 | 结论 |
|---|---|---|
| 1 | 范围线（min 钳制）+ 整段线 | A ≥ 范围线 → **到线** |
| 2 | 预留式（减固定值/减比例） | 三种窗口同台，线不同 |
| 3 | 双上限取小 | 118,464 才是真线 |
| 4 | 绝对预留 | 与窗口无关 |
| 5 | 估算口径（C-06） | 同文本三档数字 |

## 真实实现锚点（Codex 代表实现）

**锚点一 · 90% 基础线与 min 钳制**：`codex-rs/protocol/src/openai_models.rs` L529–540 `auto_compact_token_limit()`【源码常量】`codex-trigger-02`

```rust
let context_limit = self.resolved_context_window()
    .map(|w| (w * 9) / 10);                       // ① 90% 基础线（整数除法）
let config_limit = self.auto_compact_token_limit; // ② 模型字段（可被用户配置覆盖）
if let Some(context_limit) = context_limit {
    return Some(config_limit.map_or(context_limit, |l| std::cmp::min(l, context_limit)));
}                                                 // ③ 取更小者
config_limit                                      // ④ 窗口未知则直接用字段
```

逐句：① `(w*9)/10` = 90% 向下取整，**不是玄学比例**；② 字段是 `Option`——**"None 不是 0"**（没值≠限额为零，而是"用基础线"）；③ **用户配置不是无限上调的后门**（min 钳制保留）；④ 窗口未知时字段兜底。

**锚点二 · 两条线的最终判断**：`codex-rs/core/src/session/context_window.rs` L60–110【源码常量】`codex-trigger-01`

```rust
match config.model_auto_compact_token_limit_scope {
    Total => (active_context_tokens, model_info.auto_compact_token_limit(), None),
    BodyAfterPrefix => {
        let baseline = window.prefill_input_tokens.unwrap_or(active_context_tokens);
        (active_context_tokens.saturating_sub(baseline), scope_limit, ...)  // 用量 = 增长量
    }
};
let full_context_window_limit = w.saturating_mul(p) / 100;               // H = W×p/100
let token_limit_reached = buffered_limit.is_some_and(|l| scope_tokens >= l)
    || full_context_window_limit_reached;                                // 两条线，OR
```

只抓三个关键语法：**`match` 两分支** = `total` 与 `body_after_prefix` 两种口径（默认 `Total`）；**`saturating_sub`（饱和减法）** = `A − P` 为负时**夹到 0**（增长口径下不会出现负增长）；**`unwrap_or(active_context_tokens)`** = 基线还没建立时把当前用量当基线（增长 = 0，"还没开始增长"是安全默认，**不当作 0**）。

> 更细的源码走读（`Option`/`match`/`buffered` 前缀等）属 **L4**，见 M10 源码桥接与样章 U03「本章源码依据」。

| ④ **oh-my-pi** | `W − max(15%W, 16384)` → 200K = **170,000** | `ohmy-trigger-01` | 入口已装；函数级 |
| ⑤ **OpenCode v1** | **绝对预留**：`reserved = min(20000, maxOutput)`，`usable = limit.input − reserved` | `ocv1-trigger-01/02` | 函数级 |
| ⑥ **OpenCode v2** | **混合比例**：`W − max(10%W, 16000)` → 200K = **180,000** | `ocv2-trigger-01` | 函数级 |
| ⑦ **Gemini**（历史·存档） | `0.5 × W` → 1M = **524,288** | `gemini-trigger-02` | 已弃后续；**仅存档** |
| ⑧ **Grok Build** | `85% × W` | `grok-trigger-02` | **文档级**（闭源） |
| ⑨ **deepseek-harness（dsh）** | **双上限**：`floor(min(0.8W, W − O − 65536))` | `dsh-trigger-01` | 函数级 OBSERVED；**无 M 字段** |

**读表三件事**（不排名次，只讲口径形状）：

1. **三大类**：**比例式**（②⑧⑦，按窗口的百分之几）、**预留式**（③④⑤⑥⑨，窗口减固定值/比例值）、**两线式**（①，范围线 OR 整段线）。**同一件事，九种画法。**
2. **"预留"在保什么**：都在**给输出和整理动作留空间**（同 M03 §二 的两个原因）。但留多少、按比例还是按绝对值，**各家不同**。
3. **"默认值"是引用红线**：② 默认百分比**未公布**、⑧ 有内部文档冲突（Q-01~Q-05 登记不裁决）——**凡未证一律不写数字**。

**【当心】两个别写错的说法**：

- ❌ "统一在 90–95% 压缩"——**被九工具全部否证**（C-01/C-02）。
- ❌ "大窗口模型就不会压缩"——**反例**：Gemini 1M 窗口仍按 `0.5×W` 触发（**C-08**，历史存档证据；旧标签已撤回）。

## 自测（含答案）

**① 演算题**：W = 200,000，p = 95，模型字段 M = 150,000。求**基础线 / 范围线 / H**，并回答 A = 152,000 到线吗？

**② 判断题（陷阱）**：某模型元数据**没给**限额字段 M。有同学说"那就等于限额为 0，永远不压缩"。错在哪？

**③ 判断题**：轮前检查把"用户马上要发的这条巨大粘贴"也算进去了。（对/错）

**④ 口径题**：把下面三个工具各归到"比例式 / 预留式 / 双上限"一类：⑧ Grok（`85%×W`）、④ oh-my-pi（`W − max(15%W,16384)`）、⑨ dsh（`min(0.8W, W−O−65536)`）。

**⑤ 估算题（C-06）**：同一段 400 汉字，为什么 dsh 估 100、Codex 估 300、Gemini 估 600？这说明"`len//4` 对中文保守"这个说法对吗？

<details>
<summary>参考答案</summary>

**①** 基础线 = 200,000 × 9 ÷ 10 = **180,000**；范围线 = min(150,000, 180,000) = **150,000**；H = 200,000 × 95% = **190,000**。A = 152,000：**152,000 ≥ 150,000 → 范围线到线**（整段 152,000 < 190,000 未到）。**到线成立。**

**② 错在"把 None 当 0"。** 字段缺失时程序**回退到 90% 基础线**（`map_or(context_limit, …)`）：**没有专门值 = 用默认线**，不是"限额为零"。把"缺失"和"零"混起来，是读 `Option` 类型最常见的错误。

**③ 错。** 源码留了 TODO：轮前检查发生在**新输入与上下文更新写入之前**，尚未把即将到来的内容估算进去。**巨大输入仍可能一步超限。**

**④** ⑧ Grok = **比例式**；④ oh-my-pi = **预留式**；⑨ dsh = **双上限**（比例上限与"留输出余量"上限取更小者）。

**⑤** 因为**口径不同**：dsh `ceil(chars/4)` 按**字符** → 400÷4 = 100；Codex `ceil(bytes/4)` 按**字节** → 1,200÷4 = 300；Gemini 非 ASCII **1.5/字符** → 600。所以"`len//4` 对中文保守"**不成立**（C-06）：口径分列、**多口径低估**、且**不外推全 tokenizer**。真实值以服务端 usage 为准。**【T19 实测：dsh 启发式对中文/混合文本低估 ≈2.1×（32,775 vs provider 77,958）；真实分词仍 UNOBSERVABLE（证据：T19/05-dsh.md）】**

</details>

## 速查卡（贴墙版）

- **单位**：token 是计量最小单位；本地估算**各家不同、多为低估**（**C-06**）——真实值看服务端 usage。
- **四本账**：**W**（窗口）/ **p**（比例，缺省 95）/ **H = W×p/100**（有效窗口）/ **A**（当前用量）/ **P**（输入基线）。
- **三条线**：**基础线 90%**（原料）→ **范围线 `min(M, 90%W)`**（可被模型字段按下）；**整段线 = H**（硬检查）。
- **一句话判定**：**触发到线 = 范围线 OR 整段线**（伞名"触发线"）。
- **三时机**：**轮前**（不含即将写入的新输入！）/ **轮中**（还要继续且到线）/ **轮后**（缺省关闭）；另有**切模型**与**手动 /compact**。
- **八工具口径**：比例式（②⑧⑦）/ 预留式（③④⑤⑥⑨）/ 两线式（①）——**不排名次**。
- **当心**：❌"90–95% 统一阈值"（C-01/C-02 否证）；❌"None = 0"；❌"大窗口不压缩"（C-08）。
