## 学完你能做什么

1. 用一句话说清 **"全量装填 vs 按需读入"** 的分岔，并指出它发生在**请求组装之前**。

3. 说出**渐进式披露**在做什么（目录只放**名字 + 一句描述**，正文**用时再读**），并给出各家的目录描述上限。

## 场景：10 万字的代码库，怎么不整本塞进去

小林让 AI 改一个函数。这个仓库有 **3,000 个文件、几十万字**。

**如果全量装填**：把整个仓库塞进请求——桌子当场撑爆（M03 的窗口根本装不下），而且 99% 的内容与这次改动**无关**，纯属浪费。

**真实发生的是"按需读入"**：AI 先 `glob` 找到"改这个功能可能相关的 5 个文件"，再 `grep` 搜到"这个函数名出现在第 2 个文件第 40 行"，最后 `read` **只读那一段**——**需要哪段、取哪段**。

```text
全量装填（stuff-all）              按需读入（retrieve / JIT）
─────────────────────            ─────────────────────────
一次把资料全搬上桌               先给"目录/名字"，用时再搬
桌子立刻满、贵、噪声大            每次只搬"这一小段"
内容 99% 无关                   内容高相关、可续读、可定位
```

**关键直觉**：**"读什么进来"是上下文管理的第一道闸门，它比压缩更靠前**——压缩是"搬上桌之后减体积"，而检索是**一开始就决定搬不搬**。**东西没搬上桌，就不必压缩它。**

**【当心】一个常见误解**：以为"上下文管理"就是"压缩"。其实**排在第一位的省法是"根本不读进来"**——这正是本单元的核心。

## 核心概念

### 一、"全量装填 vs 按需读入"：第一道选择

**【人话】** 面对一份大资料，程序只有两个选择：

- **全量装填（stuff-all）**：整本搬上桌。简单，但**贵、慢、噪声大**，大仓库直接装不下。
- **按需读入（retrieve / just-in-time, JIT）**：**先给一份"索引/名字/目录"，需要哪段再取哪段**。省，但需要模型"会找"。

**八工具（+ Gemini 存档）的检索侧，主流选择都是"按需读入"**——证据形态是各家都**内建了检索工具**（`read`/`grep`/`glob`/`find`/`ls` 等）。**但注意口径**：证据能证明的是"**官方文档/源码里没有全量装填路径**"（如 Gemini 复跑 `stuffAll|bulkLoad|preloadAllFiles|loadAllFiles` 命中 **0**，`gemini-retrieval-01`），**不能证明"全量装填一定不存在"**（`dsh-retrieval-01` 的"不能证明"栏明示）——**未知保留未知**。

**【当心】"有 read 工具" ≠ "保证按需"**：工具存在只说明**能力**在，**模型实际会不会"按需"而不是"一把梭全读"**属**模型行为**，各家证据卡都把它列为"不能证明"（`pi-retrieval-01`、`ocv1-retrieval-01`、`ocv2-retrieval-01`）→ **【T19 实测：行为分化——pi 同条件 3 轮中 1 轮只读头部、2 轮自主分页读完（offset 717→1428→2151）；codex 二次检索取回、omp 精确取回 artifact（证据：T19/02-pi.md §1.4、01-codex.md §A-3、04-omp.md §A5）】**。

### 二、检索族机制拆解：三件套 + 渐进式披露 + `@文件`

**（1）三件套：read / grep / glob**

| 工具 | 管什么 | 关键动作 | 代表证据 |
|---|---|---|---|
| **read**（读） | **取正文** | 支持 **offset/limit 分页续读**——读不完可以"接着读下一段" | `pi-retrieval-01`、`ocv1-retrieval-01`、`ocv2-retrieval-01` |
| **grep**（搜） | **按内容定位** | 搜到"这个函数名在第几行"，再定向读那一段 | `pi-retrieval-01`、`grok-retrieval-01` |
| **glob / find / ls**（列） | **按路径列文件** | 先拿到"候选文件清单"，再决定读哪个 | `pi-retrieval-01`（`find`/`ls`）、`ohmy-retrieval-01`（`glob`） |

**"分页续读"是"按需"的关键细节**：`read` 一次读不完（超上限），不是"丢了"，而是**告诉你"下一段从第 N 行开始"**（各家续读提示见下 §三）。这跟 M05 的"落盘 + 预览 + 路径"是一对搭档：**M05 管"进不来的先存着"，M09 管"要用时怎么取回来"**。

**（2）渐进式披露（progressive disclosure）：目录先给，正文再读**

**【人话】** 技能（skills）有成百上千条时，**不能把每条手册都塞进提示词**。做法是：**提示词里只放"技能名 + 一句描述"的目录**，模型**真要用某条技能时，才去读它的完整手册**。

这就是**渐进式披露**（术语表 §8）。各家的"目录描述上限"不一样，**必须逐家看**：

| 工具 | 目录里放什么 / 上限 | 证据 |
|---|---|---|
| ⑨ **dsh** | 首个请求前发一条 durable `user/message` **目录**（名字 + 截断描述，`catalogDescriptionMaxLength` 默认 **500**）；模型用 `skill` 工具按名加载**全文** | `dsh-rule-02` |
| ② **Claude Code** | 技能**描述**（`description` + `when_to_use` 合并后）在列表中**截断于 1,536 字符**；正文调用时才加载 | `claude-skill-01` |
| ③ **pi** | 提示词只放**技能名 + 一句描述**；完整手册按需再读 | `pi-rule-02` |
| ⑤ **ocv1** | 系统提示词只放 `name/description/location`；正文经 `skill` 工具按需读 | `ocv1-rule-01`（工具概览） |

**【当心】** ④oh-my-pi 的技能走 **`skill://` 按需读**（`ohmy-rule-01`）；**同一套"渐进式披露"思想，各家实现名不同**——**不要用一家的 500 去套另一家**（②是 1,536 字符，⑨是 500）。

**（3）`@文件` 引用语义：提及 ≠ 附带内容**

**【人话】** 你在输入里 `@某个文件`，直觉上"我把文件给它了"。**但多数实现里，`@` 只是"路径补全/候选"——内容并没有附进来。**

⑨dsh 写得最直白：`file-reference`（`@file` 提及）**只做路径补全，不附内容**——**"Selecting a candidate never reads or attaches file contents"**；模型**必须再调 fs 工具**才能看内容（`dsh-retrieval-01`）。

```text
你输入： @src/api.ts 这个函数怎么改？
dsh 实际：把 "src/api.ts" 作为候选路径给模型
           ≠ 把 src/api.ts 的正文塞进请求
模型下一步：调 read 工具，才真正把正文读进来
```

**【当心】这是"全量装填 vs 按需读入"的一个反直觉落点**：连"用户显式提及的文件"都**不默认附带内容**——**"提及"只是给了个"该读它"的信号**，读不读、读多少，仍走**按需读入**这条路。（Claude 侧的 `paths:` 规则同源：只有当 Claude **Read/Write/Edit 命中匹配文件**时，规则才进历史，`claude-rules-02`。）

**读表三件事**（不排名次，只讲口径形状）：

1. **"按需"是九家的共同形态**：①–⑨**都内建检索工具**，官方文档/源码里**未见**"全量装填"路径（⑦复跑 `stuffAll…` 命中 0）。**但"未见"≠"不存在"**——各家"不能证明"栏都保留了这条（未知保留未知）。
2. **上限的"单位/层数"必须逐家看**：`read` 侧口径有 **token**（②25,000）、**行 + 字节双上限**（③④⑤⑥⑨）、**字节**（⑨51200）——**"数字大"不等于"读得多"**（②是 token，③是 2000 行/50KB 取先到者）。
3. **`read` 上限 ≠ 出口限长**：这里的 `read` 上限是**"一次读入"的闸门**；M05 的出口限长是**"结果进列表前"的闸门**——**两处都裁，目标不同**（M05 §二）。

**【当心】三个别写错的说法**：

- ❌ "某工具有 `read` 工具，所以它是按需读入"——**能力 ≠ 行为**，模型实际策略属 【T19 实测：行为分化——pi 同条件 3 轮中 1 轮只读头部、2 轮自主分页读完；codex 二次检索取回（证据：T19/02-pi.md §1.4、01-codex.md §A-3）】。
- ❌ "`@文件` 会把文件内容带进来"——**dsh 明确不附内容**（`dsh-retrieval-01`）；**提及只是信号**。
- ❌ "各家 `read` 上限可以直接比大小"——**单位不同**（②token / ③行·字节 / ⑨字节），**不得互套**。

### 四、跨会话引用：引用"别处的历史"要有上限

**【人话】** 有时你想让 AI 参考**另一个会话**（比如上周那次排障）。dsh 的 `session-reference` 就干这个：把**其他会话**作为**有界只读快照**注入为**第二条 user 角色消息**（`## Referenced sessions`），并**带固定"不可信背景"警告**。

**关键在"有界"**：`session-reference` 是 **opt-in**（非默认装配），且**每源都有硬上限**——

```text
maxReferences           默认 3     ← 一次最多引用 3 个其他会话
referenceContextFraction 默认 0.2   ← 引用内容占比上限
每源自动预算             max(65536, floor(contextWindow×4×0.2)) 字节
```

（`dsh-retrieval-02`；均为 README 文本，**未运行**。）

**为什么要上限？** 因为"引用别处的历史"如果**不限量**，就等于**把别人的整张桌子搬过来**——直接违反"按需读入"的第一原则。**上限 = 把"跨会话引用"也纳入预算管理**。

**【当心】跨会话引用 ≠ 长期记忆**：`session-reference` 是**显式提及**（你/模型点名"参考那个会话"），**不是**后台自动抽取的记忆（dsh 默认**未发现**长期记忆实现，`dsh-memory-01`）——**术语表 §5 的"长期记忆"与这里的"显式引用"是两回事**（记忆专题见 M08）。

**图 2 · 检索族三件套与"续读"**

```
   glob/find/ls ──► "候选文件清单"           （按路径列）
        │
   grep ─────────► "函数名在 api.ts:40"      （按内容定位）
        │
   read(offset=40, limit=50) ──► 第 40–90 行  （取正文）
        │  读不完？
```

**① 判断题（陷阱）**：某工具有 `read` 工具，说明它一定是"按需读入"、不会全量装填。（对/错）

<summary>参考答案</summary>

**① 错。** 有 `read` 工具只说明**能力**在；**"是否按需、而不是一把梭全读"属模型行为**，各家证据卡都把它列为"不能证明"（`pi-retrieval-01`、`ocv1-retrieval-01`、`ocv2-retrieval-01`）→ **【T19 实测：行为分化——pi 同条件 3 轮中 1 轮只读头部、2 轮自主分页读完（offset 717→1428→2151）（证据：T19/02-pi.md §1.4）】**。**能力 ≠ 行为。**

**②** ②Claude 是 **tokens**（`claude-toolout-03`）；③pi 是 **行 + 字节双上限取先到者**（2000 行 / 50KB，`pi-trunc-01`）；⑨dsh 是 **行 + 字符 + 字节三重**（51200 字节，`dsh-trunc-01`）。**不能直接比大小**：**单位不同**（token / 行 / 字符 / 字节），且③是**双上限取先到者**——**"数字大"不等于"读得多"**。

**④** （示例三类线索）**(a) 形态**：有没有内建检索工具 / 有没有"全量装填"路径；**(b) 一次读入上限**：`read` 的 `offset`/`limit` 与上限（**先看单位**）；**(c) 目录与引用**：渐进式披露的**描述上限**（⑨500 / ②1,536 字符）+ 引用语义（`@file` 是否附内容、跨会话 `maxReferences`）。**三处都要查，不能只看一处。**

## 速查卡（贴墙版）

- **第一道选择**：**全量装填（stuff-all） vs 按需读入（retrieve/JIT）**——**"读什么进来"比"压缩"更靠前**；**没搬上桌就不必压缩**。
- **检索族三件套**：**glob/find/ls（列文件）→ grep（定位行）→ read（取正文，可 `offset`/`limit` 续读）**。
- **渐进式披露**：目录只放**名字 + 一句描述**，正文**用时再读**；描述上限逐家看（⑨**500** / ②**1,536 字符** / ③一句）。
- **`@文件` 引用语义**：**提及 ≠ 附带内容**（dsh：`@file` 只做路径补全，**须再调工具**才见正文，`dsh-retrieval-01`）。
- **一次读入上限（逐家口径）**：②**25,000 tokens** / ③**2000 行·50KB** / ④**≤3000 行** / ⑤⑥**2000 行·2000 字符·50KiB** / ⑨**2000 行·2000 字符·51200 字节**——**单位不同，不得互套**。
- **跨会话引用要有上限**：dsh `session-reference` `maxReferences` 默认 **3**、`referenceContextFraction` 默认 **0.2**（**opt-in**）——**"引用别处的历史"也纳入预算**。
- **产出物**：**两列检索判断卡**（①形态？②上限在哪？③读不完怎么办？④目录先给还是后给？⑤提及带内容吗？）。
- **当心**：❌"有 read 工具 = 按需"（能力≠行为，T19）；❌"`@文件` 会带内容"；❌"各家上限比大小"（单位不同）；❌"检索 = 摘要"（检索**补资料** ≠ 摘要**减体积**）。
