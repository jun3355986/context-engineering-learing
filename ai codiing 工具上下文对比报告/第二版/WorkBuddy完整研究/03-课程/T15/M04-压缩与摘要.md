## 学完你能做什么

1. **破除误解**："整理 ≠ 把全部对话换成一页摘要"——真实产物至少两种形态，且**大部分近期原话会被原样留下**。

## 场景：小林的两句担心

小林看完 M03 已会算"到线"，现在担心两件事：

> **担心一**："它整理时，是不是把聊过的东西**全扔了**，只留一小段总结？"
>
> **担心二**："被扔掉的东西，我**还能找回来吗**？"

答案分两半，正是本单元两条主线：

- **担心一**：旧材料**大部分**确实不再逐条带上——这是整理的意义；但**两种东西会被尽力留下**：① 你的**近期原话**（预算内原样保留）；② **当前有效的规则与环境**（整理后重新摆回靠前位置）。而且"整理"的产物**不止一种形态**。
- **担心二**：分两层——**模型这次看得见的那份材料**里，被压缩的内容**不能自动恢复**；但**磁盘上的原文**，保留期内**通常可查回**。这正是统一裁决 **C-03 / C-12**。

## 核心概念

### 一、"整理"的两种产物形态：先看你的服务商是谁

整理有**两条实现路径**，由 **provider（模型提供方）的能力**决定——不是随机选，也不是用户开关。

| 路径 | 谁来写"交接材料" | 产物形态 | 何时走这条 |
|---|---|---|---|
| **本地摘要路径**（local / responses） | **客户端编排**：程序挑好材料，让模型写一份**文字交接摘要** | 你能读懂的一段文字摘要 | 提供方不支持远端压缩时 |
| **远端压缩 v2**（remote_v2） | **服务端**完成压缩 | 一个**压缩条目**（`encrypted_content` 加密内容，客户端只见形状，读不到明文） | OpenAI 官方 / Azure 系 provider **默认**走这条 |

**【人话】** 整理后"交接材料"长什么样，取决于你把请求发给了谁：发给官方 OpenAI / Azure，拿到的是**服务端生成的加密压缩块**；发给其他提供方，拿到的是**能读的文字摘要**。

**【源码常量】** `ProviderCapabilities::from_config` 对 **OpenAI 与 Azure responses 系**默认给出远端压缩支持（`RemoteCompactionSupport::V2`），其他提供方默认不支持（回退本地摘要）。依据 `codex-retain-02`（`capabilities.rs` L31–51；`provider.rs` L713–726）。

**【当心】** 读源码的坑：那条名字带 `V2` 的 feature 开关在本快照已标 `Stage::Removed`——**它现在只用于无条件向服务端声明"本客户端支持远端压缩"，不再是本地开关**。"默认走远端"的判定点是 **provider 能力**，不是这个开关。

### 二、保留算法的共同骨架（无论哪条路径）

两条路径产物不同，但**保留**遵循同一副骨架（教学归纳）：

```text
① 筛候选：谁有资格"原样留下"？        # 类型过滤，不按语义评重要性
② 用预算：从新到旧把候选装进共享预算    # 最近的先装
③ 边界处理：装不下的边界条目截短（保头尾）
④ 另加产物：摘要 / 压缩条目单独追加     # 不占"原样保留"的预算
⑤ 重组规则：重新渲染当前工作状态与规则
```

两条路径在每一步的参数不同：

| 步骤 | 本地摘要路径 | 远端 v2 |
|---|---|---|
| ① 候选 | **只收真正的用户消息**（排除旧摘要消息——靠摘要前缀识别） | 用户消息 + 钩子提示；AgentMessage 有条件（排除子代理进度/完成通知，**单条 ≤ 10,000 tokens**【源码常量】） |
| ② 预算 | **20,000 tokens**【源码常量】 | **64,000 tokens**【源码常量】 |
| ③ 边界 | 纯文字且放得下→原样；否则生成**文字回退** `truncate_text(…, 剩余预算)`（保头尾），然后**停止** | 按"组"处理（消息与附带通知成组）；特殊工具结果**整条保留，否则停止**；普通消息边界截短；图片另有预算 |
| ④ 产物 | 追加**文字摘要**（可读） | 追加服务端**压缩条目**（含加密内容） |
| ⑤ 重组 | 两者相同：重新构建初始上下文 + 渲染当前 `WorldState` | 同左 |

依据 `codex-retain-01`（`compact.rs` L574–603、L690–770）、`codex-retain-02`（`compact_remote_v2.rs` L78–82、L548–597、L625–722）。

**【人话】** 整理像**装箱**：**最近的用户原话优先装箱**（从新到旧），装到预算用完；**装不下的边界那条砍成"头一段+尾一段"塞进去，然后收手**（不回头挑更早的小条目补缝）；摘要**另外贴**在箱尾，**不占**装原话的额度；最后把"当前规则与环境"重新摆回箱首。

### 三、一个完整的数字演算（本地摘要路径）

用**真实单位**。预算 P_max = **20,000**【源码常量】，三位用户过往原话（教学数据【演示】）：

```text
从旧到新的用户消息：M1 = 12,000 tokens、M2 = 10,000、M3 = 6,000
倒着装（从新到旧）：
  装 M3（6,000 ≤ 20,000）     → 剩 14,000
  装 M2（10,000 ≤ 14,000）    → 剩 4,000
  看 M1（12,000 > 4,000）     → 边界截短：头、尾各留一部分，
                                合计约 4,000 tokens 片段 + 截断标记
  按规则在此停止（不回头再挑更早的小消息补缝）
最终顺序（还原时间顺序 + 产物另加）：
  [M1 截短片段] → [M2] → [M3] → [新摘要]
  ＊另外：当前规则与环境在 ⑤ 被重新摆回列表靠前位置
```

**【当心】** 两条重要边界：

1. **"重要"不参与筛选**——算法不判断"M1 里有没有关键约束"，只看**类型、预算、顺序**。M1 中间若有"必须 14:30 集合"，它要么在头尾片段里侥幸留下，要么只靠摘要传递——**摘要能否保住它，客户端代码无法保证**（那是模型生成质量的问题；未运行实验，不能编造结论）。
2. **20,000 不是"触发线"，也不是"最终请求大小"**——它只是"给旧用户原话留的**共享预算**"。**三组数字（20,000 / 64,000 / 触发线）互相独立**，不得混用。

### 四、"被压缩的内容去哪了"：两层事实（C-03 / C-12）

这是最容易被写错的一点，统一裁决 **C-03 / C-12** 钉死为**两事实并存**：

| 层 | 被压缩的内容在哪 | 能不能自动恢复 |
|---|---|---|
| **模型可见层**（这次请求带上的那份） | 已被**替代历史**（摘要 + 保留项）替换，原文不在 | **不可自动恢复**（不是"程序删了"，是"它不在这一份里"） |
| **磁盘原文层**（会话存档 / 落盘文件） | 九工具**均有落盘/存档入口**，原文**保留期内可查** | **可查回**（人工/工具从磁盘读，而非模型自动想起） |

依据：T14 矩阵 E 表；`pi-persist-01`（pi 追加式 JSONL，**原条目不删**）；`ocv1-summary-04`（v1 磁盘原始消息**从不删除**）；`ocv2-summary-04`（v2 磁盘原始消息**不删**）；`dsh-persist-01`（dsh 追加式 JSONL）。

**【当心】** 两句别写错：

- ❌ "被压缩的内容**绝不可能**找回"——只在**模型可见层**成立；磁盘原文保留期内可查（C-12）。
- ❌ "摘要就是权威指令"——摘要是一份**模型写的二手材料**（属"资料"，不是"指令"），可能漏、可能错（术语表 §3「坏摘要」）。**别把摘要当用户指令照做**——这是「指令与资料边界」在压缩场景的落点。

**保留期差异**（要查回时看）：②Claude Code 约 **30 天**；⑤ocv1 / ⑥ocv2 截断目录约 **7 天**（`claude-cleanup` / `ocv1-trunc`）。**保留期是"可查窗口"，不是"永久档案"。**

```
整理前（旧历史）                      整理后（替代历史 replacement_history）
┌───────────────────────────┐        ┌───────────────────────────────┐
│ [旧摘要(被前缀识别,排除)]  │        │ ① 重组后的规则与环境（靠前）    │
│ M1(12,000)                 │        │ ② [M1 截短片段](头尾~4,000)     │
│ M2(10,000)                 │  ──→   │ ③ [M2] 原样                     │
│ M3(6,000)                  │        │ ④ [M3] 原样                     │
│ 工具结果 / 图片 / …         │        │ ⑤ [新摘要] 另加（不占原话预算） │
└───────────────────────────┘        └───────────────────────────────┘
         │ 磁盘原文另存（不删，保留期内可查）
         ▼
   【保存的记录】← 这里还找得到 M1/M2/M3 的完整原文
```

五步骨架（对应交互 I-压缩四幕）：**①筛候选 → ②用预算(从新到旧) → ③边界截短(保头尾+停手) → ④产物另加(摘要/压缩块) → ⑤重组规则**。

**数据点**：本地 20,000 与远端 64,000 均为**源码常量**（`codex-retain-01/02`）；12,000/10,000/6,000 为**教学数据【演示】**。

## 真实实现锚点（Codex 代表实现）

**片段一**：20,000 常量与"从新到旧"骨架（`compact.rs` L690–770 节选）【源码常量】

```rust
const COMPACT_USER_MESSAGE_MAX_TOKENS: usize = 20_000;      // L63
let mut remaining = max_tokens;
for message in user_messages.iter().rev() {                 // ① 从新到旧
    if remaining == 0 { break; }
    let tokens = approx_token_count(&message.message);      // ② 每条单独估算
    let content = if tokens <= remaining && all_input_text(&content) {
        content.clone()                                     // ③ 纯文字且装得下 → 原样
    } else {
        vec![InputText { text: truncate_text(&message.message, Tokens(remaining)) }] // ④ 否则→文字回退(保头尾)
    };
    selected_messages.push(…);
    if tokens > remaining { break; }                        // ⑤ 边界处理完就停
    remaining = remaining.saturating_sub(tokens);
}
selected_messages.reverse();                                // ⑥ 还原时间顺序
history.push(CompactionSummary::new(summary_text));         // ⑦ 产物另加
```

逐句：① `iter().rev()` 倒着遍历，最近的用户话优先拿预算；③ 内容块**全是文字**才可能原样，**带图片的消息不进这条分支**（"带图消息原图必留"是错的）；⑤ 先把边界消息推入、**然后** `break`——"边界收进来，循环到此为止"；⑦ `CompactionSummary` **另加**，**不占** 20,000 预算。

**片段二**：候选过滤——"排除旧摘要"（`compact.rs` L574–603 节选）【源码常量】

```rust
let Some(TurnItem::UserMessage(user)) = …parse_turn_item(item) else { return None; }; // ① 不是真用户消息→跳过
if is_summary_message(&user.message()) { return None; }                              // ② 是旧摘要→跳过
// is_summary_message: message.starts_with("{SUMMARY_PREFIX}\n")                     // ③ 靠前缀识别
```

要点：摘要消息在历史里**没有独立角色**，被编码成"用户消息"形态——算法**靠固定前缀识别并排除**。**同一个变量可能是"你真说过的话"，也可能是"上一轮摘要伪装成的用户消息"**。

**片段三**：远端 v2 的加载顺序与"整组"（`compact_remote_v2.rs` L625–722 摘述）【源码常量】

```rust
for group in groups_from_newest_to_oldest {
    if remaining == 0 { continue; }                    // ① 已清零：跳过，不再纳入
    let token_count = source_tokens + notice_tokens;   // ② 条目+附带通知 成组计量
    if token_count <= remaining { push(group); remaining -= token_count; }   // ③ 整组装下
    else if is_retained_tool_output(&group.source) { break; }                // ④ 特殊工具结果：整条或停
    else if remaining > notice_tokens { push(truncate_message_text_to_token_budget(…)); remaining = 0; } // ⑤ 边界截短收尾
}
```

远端 v2 比本地多一层边界分支：**整组保留**、**特殊工具结果整条或停**、**图片另有预算**（`compaction_image_budget` Stable、默认开启）——"64,000 纯文字规则"不能保证原图完整。

> 自动 vs 手动：**自动压缩必须先"到线"**（M03 两条线），条件不成立**不会发生**；**手动 `/compact` 不要求到线**，随时可用。自动成功后**继续原工作循环**；手动整理是**一次独立任务**，**不等于原任务自动续跑**。

**读表三件事**（不排名次，只讲形态差异）：

1. **保留预算是"策略旋钮"，不是"标准答案"**：Codex 用**两个固定常量**（20k/64k），ocv1 用**随窗口浮动的公式**（`usable×0.25` 夹 `[2000,15000]`），ocv2 改成**固定 15k**，dsh 用**比例 0.16**。**同一概念四家四种口径**——引用必须逐工具写清，不得用"统一 90–95%"这类总括句（C-01/C-02 已否证）。
2. **"摘要"与"裁剪"是两层，别合并成一个词**：oh-my-pi / Grok / dsh 都有"**先裁工具输出、再摘要**"的两段结构（`ohmy-summary-03`、`grok-summary-02`、`dsh-trunc-04`）——**裁剪不调用模型，摘要要调用模型**，性质不同（术语表 §3）。**层数不是维度**（C-10）。
3. **"校验"是 v2 一代的新动作**：ocv2 有**模板校验 + 一次 NUDGE**，Gemini 有**二次校验 probe**，dsh 有**收缩校验**——都在回答"**摘要本身会不会不合格**"。但**校验通过 ≠ 内容保真**（保真度依赖模型，属 T19）。

**【当心】** 两句别写错：❌ "所有工具都用一段文字摘要"——Codex 官方 OpenAI 默认走**远端加密压缩块**，pi/ocv1/ocv2/dsh 是**结构化多段模板**。❌ "增量合并是无损的"——pi/ocv1/ocv2/dsh 的增量**均判为有损**；**连续压缩是否漂移**（摘要漂移 C-04 / LQ-09）→ 【T19 实测：单次/多轮压缩后约束基本未丢（E1 全 PASS），但 **grok 为反例**——3 次连续压缩后硬约束丢失（HC-01 空、HC-03=0）；失真程度未量化（证据：T19/07-grok.md §1/§2）】。

## 产出物示范：同一份材料的前后对照表

以"郊游 / 接口兼容"统一主线为例。**你要做的动作**：把整理前后的同一份材料逐条标"原样留下 / 变摘要 / 移除 / 落盘"，并写清**理由与代价**。

| 材料 | 整理后归宿 | 理由 | 代价 |
|---|---|---|---|
| 你最新一句"接口必须向后兼容" | **原样留下**（近期原话，在预算内） | 最近、最可能相关；类型合格 | 占保留预算 |
| 更早一句"必须 14:30 集合" | **变摘要**（若落在被摘要的旧段里） | 预算装不下；只有摘要能携带它 | **摘要可能漏掉它**——客户端不保证 |
| 300 行公交/日志查询结果 | **移除**（或先经出口限长/落盘，M05） | 体积大、时效低 | 若结论只在其中，模型这次看不到 |
| 当前规则与环境（UTC / 权限） | **重组后摆回靠前** | 一直有效，必须每次带 | 占空间 |
| 被移除段的**磁盘原文** | **落盘**（会话存档，保留期内可查） | 承担"以后还能查回来" | 保留期有限；需人工/工具去查，**模型不会自动想起** |
| 上一轮摘要 | **排除**（靠前缀识别） | 防止"摘要套摘要"重复占用 | 若旧摘要已失真，失真被继承 |

**【人话】** 这张表就是 L3 的核心动作——**你不必知道程序每一行代码，但要能对每条材料说出"它去哪了、为什么、代价是什么"**。M03（触发）+ M04（摘要/保留）+ M05（出口限长/落盘）+ M06（恢复）合起来才是完整的一张表。

## 自测（含答案）

**① 判断题**："整理就是把所有对话换成一页摘要。"（对 / 错，说明理由）

**② 演算题**：本地摘要路径，预算 20,000；用户消息从旧到新为 **9,000 / 16,000 / 7,000**。写出选取过程与最终顺序。旧的 9,000 会被"补缝"装进来吗？

**③ 定位题**：小林用 OpenAI 官方账号。压缩完成后，他在**模型可见历史**里看到的交接材料最可能是什么形态？
A. 一段可读的中文摘要　B. 一个含 `encrypted_content` 的压缩条目　C. 旧消息原样全在　D. 什么都没有

**④ 分层题**：小林想知道"被压缩掉的 14:30 还能不能找回"。请分**模型可见层**与**磁盘原文层**分别回答，并指出统一裁决编号。

**⑤ 设计意图题**：为什么两条路径都"**从新到旧**"，而不是"按重要程度排"？

**⑥ 对照题**：ocv1 保留预算是"随窗口浮动的公式"，ocv2 是"固定 15,000"。能说"谁更好"吗？为什么？

<details>
<summary>参考答案</summary>

**① 错。** 整理**大部分**旧材料确实不再逐条带上，但产物至少两种形态（文字摘要 / 远端加密压缩块），且**近期用户原话会被原样保留**、**当前规则与环境会被重组摆回**。"全部换成一页摘要"漏掉了"保留"和"重组"。

**②** 倒着装：先装 7,000（剩 13,000）；看 16,000 > 13,000 → **边界截短**：保留头尾合计约 13,000 tokens 片段，然后**收尾停止**。最终顺序：**[16,000 截短片段] → [7,000] → [摘要]**（外加最前重组好的规则与环境）。**更旧的 9,000 不会被"补缝"**——算法在边界消息后停止，这是骨架第 ③ 步的硬规则。

**③ B。** 官方 OpenAI provider 默认 `RemoteCompactionSupport::V2`，产物是服务端压缩条目（客户端侧含加密内容）。A 是本地摘要路径（提供方不支持远端压缩时）的形态。

**④** **模型可见层**：不可自动恢复——它已被替代历史替换，**不在这一次请求里**（C-03/C-12）。**磁盘原文层**：会话存档里**通常可查**（保留期内）——但要**人工/工具去磁盘读**，模型不会自动想起。裁决 **C-03 / C-12**。

**⑤** "重要程度"无法在客户端**廉价又可靠**地评估：读懂语义再挑等于又跑一次模型（成本、延迟都不可接受，且可能挑错）。**时间新近性是可用、稳定、便宜的代理信号**；深层语义保全被交给摘要/压缩产物的**生成环节**（模型来做），客户端只负责机械规则。这也是"整理会不会保住你关心的细节"最终**无法被客户端代码单方面保证**的原因。

**⑥ 不能排名次。** 两者是**不同取舍**：ocv1 随窗口浮动（大窗口给更多、小窗口给更少），ocv2 固定 15,000（行为更可预测）。**无 T19 统一条件实测前，任何"谁更省/更好"的排序都作废**。

</details>
