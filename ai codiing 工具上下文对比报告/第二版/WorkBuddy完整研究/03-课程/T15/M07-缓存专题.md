## 场景：同样的开头，第二次为什么更便宜

小林连续问了两句：

> ① 帮我把行程里的**公交段**列出来。
> ② 把行程里的**午饭段**列出来。

两句的**开头部分**——系统指令、工具说明、全部对话历史——几乎**一字不差**。如果每次都从头算起，是不是太亏了？

答案：程序（和模型服务端）有一类专门"复用相同开头"的优化，官方叫 **Prompt Caching（提示词缓存）**。但它**不是"把材料存起来下次少发"**——这个直觉是**错的**，正是本单元要拆的第一个坑。

## 核心概念

### 一、缓存省了什么、没省什么

**【人话】** 模型读你的材料时，会给每个 token 算一份"中间状态"（官方叫 **KV 状态**，key-value states）。**缓存就是把这份中间状态存下来**——下次请求如果**开头部分（前缀）一字不差**，模型可以直接**拿回这份状态，跳过大半重新计算**。

| 缓存**省**的 | 缓存**不省**的 |
|---|---|
| **重新计算**（算力、钱、首字延迟方向） | **本次上下文的总长度**——命中的 token 依然是本次输入的一部分 |
| 稳定前缀那一段的"重算成本" | **速率限制（TPM）**——cached 输入**依然计入** |
| （在服务端命中时）首字更快 | **上下文窗口占用**——**缓存不缩窗口** |

**【当心】全单元最容易被写错的一句**：❌ "缓存让上下文变短了 / 窗口变大了"。**都不对**。缓存省的是**重算**；"少发材料"是**压缩/摘要**（M04）干的事，**两者不是一回事**。

**匹配单位 = 完整渲染后的前缀（token 级）**。术语表 §6 把"**前缀**"定义为**缓存匹配的单位**：

- 匹配的是**完整渲染后的上下文**（含系统指令、工具定义、历史），**不只是你可见的那几句文字**；
- **没有"按文件缓存"、也没有"按消息段缓存"**——若把某个文件插到前缀中间，**它之后的内容全部失配**；
- 因此程序的排布取舍是：**稳定材料排前面、易变内容排后面**（M02 已埋下伏笔）。

三个配套术语：

| 术语 | 含义 | 注意 |
|---|---|---|
| **前缀（prefix）** | 请求开头"未改变的那部分 token" | 匹配的是**完整渲染后的上下文**，不只是可见文字 |
| **缓存断点（cache breakpoint）** | 标记"前缀到此为止可以存/取"的终点 | 各家放置规则不同（见八工具对照） |
| **命中（cache hit）** | 请求到达了**一台仍持有匹配条目**的机器，且前缀匹配 | **不保证**；路由、过期、负载都影响 |

> 服务端官方给出的"最小可缓存前缀 / 断点间隔 / TTL"等参数属**服务端/API 侧文档**（样章单元 08 已核查）；**本快照 CLI 发的是历史字段、认的是历史字段**——**别把 API 新参数安到 CLI 上**。

### 二、缓存与压缩 / 容量 / 记忆的边界（R14 强制）

术语表 §6 标题就写死了：缓存族"**与摘要/记忆严格分开**"。**边界四问**必须背下——这四句是本单元的"落点红线"：

| 边界 | 一句话 | 证据 / 出处 |
|---|---|---|
| **缓存 ≠ 摘要（压缩）** | 缓存**不改变材料**（前缀原样复用）；摘要**改变材料**（替换历史）——两者目的相反：一个"省重算"，一个"减体积" | 术语表 §6 标题；M04 两层事实；`codex-cache-01` |
| **缓存 ≠ 外部记忆** | **外部记忆**是"不在消息列表里、可再取用"的记忆（术语表 §5）；缓存在**服务端**存 KV 状态，**不改变本次请求带哪些材料** | 术语表 §5/§6；`pi-cache-01`（记忆/摘要请求的写缓存策略另计） |
| **缓存 ≠ 容量扩展** | 缓存**不缩窗口占用**（cached 输入仍占本次上下文、仍计 TPM） | 样章单元 08；术语表 §6 |
| **缓存 ≠ 少发材料** | "少发"是压缩/检索的产物；缓存**一个 token 都不少发** | M04；术语表 §6 |

**为什么"压缩按设计失效对话层"？** 因为压缩**替换了历史**，前缀**从第一个变化的 token 起**不再匹配——**这是设计后果，不是 bug**：

```text
压缩前  [基础指令 | 工具说明 | 旧历史……………… | 你的输入]   ← 缓存按此前缀建立
压缩后  [基础指令 | 工具说明 | 替代历史(摘要/压缩块)… | 你的输入]   ← 从"第一个变化 token"起失配
              └── 变化点之前：仍可能命中 ──┘└──── 变化点之后：全部重建 ────┘
```

**一句话**：**压缩改变前缀 → 缓存按前缀退化，但不会整体归零。** 变化点**之前**的稳定段（如基础指令、工具说明）若未变，**仍可能命中**；压缩后形成的**新前缀**随着后续追加逐渐稳定，命中会**回升**。

### 三、一次"更慢更贵"的周转从哪来（前缀退化五种来源）

缓存命中**不是保证**。能让"同样的开头"**失配**的常见来源（**都通过"改变前缀"起作用**）：

| 来源 | 怎么改变前缀 | 出处 |
|---|---|---|
| **压缩 / 摘要** | 替换历史，变化点之后全部重建 | M04；样章 U08 |
| **修改旧消息** | 改写某条旧消息 → **它之后**的前缀全部失配 | 样章 U08 |
| **工具变更** | 工具名/描述/**顺序**变化 → 渲染前缀变化（工具说明在**前部**） | 样章 U08 |
| **过期** | 条目按 TTL 过期 → 同文字也不保证命中 | 术语表 §6（TTL 口径随产品） |
| **恢复 / fork / 子 Agent / 记忆注入** | 恢复靠检查点**重建**材料；fork 派生**新历史边界**；子 Agent **独立会话、独立缓存键**——**都是"新前缀"** | M06；样章 U08 |

**【当心】一句工程建议**：想保住命中，**"追加新消息"优于"改写旧消息"**——改写会让该消息之后的前缀全部失配。**但别为了"凑缓存"去硬加无用文字**（前缀太短时，写入溢价可能反而不划算；样章 U08 已给该成本陷阱）。**也别为了缓存去改写历史——那是拿正确性换省钱。**

## 真实实现锚点（Codex 代表实现）

> **惯例**：API 文档说支持某字段 **≠** 这个 CLI 会发这个字段。所以回到固定快照，查**请求侧**与**响应侧**两条链。

**锚点一 · 请求侧：CLI 发不发缓存键？**（`codex-rs/core/src/client.rs` L641–653、L1049）【源码常量】`codex-cache-01`

```rust
fn prompt_cache_key(&self, responses_metadata: &CodexResponsesMetadata) -> String {
    if let Some(prompt_cache_key) = &self.prompt_cache_key_override {
        return prompt_cache_key.clone();               // ① 特定会话（如审查会话）用覆盖值
    }
    if let SessionSource::Internal(source) = &self.state.session_source
        && let Some(parent_thread_id) = responses_metadata.parent_thread_id
    {
        return format!("{source}:{parent_thread_id}"); // ② 内部子会话：来源 + 父线程
    }
    responses_metadata.session_id.clone()              // ③ 常规请求：会话 ID
}
```

要点：**这个快照的 CLI 常规请求会携带一个稳定的缓存键，默认等于会话 ID**——同一会话的请求**倾向**落在同一缓存分组；**不同会话/子会话各有自己的键**（所以子 Agent"不该期待顺手命中旧缓存"）。

**锚点二 · 响应侧：CLI 认不认缓存账？**（`codex-rs/codex-api/src/sse/responses.rs` L117–151）【源码常量】`codex-cache-01`

```rust
let input_tokens_details = val.input_tokens_details.unwrap_or_default();
TokenUsage {
    input_tokens: val.input_tokens,
    cached_input_tokens: input_tokens_details.cached_tokens,           // ① 读取明细
    cache_write_input_tokens: input_tokens_details.cache_write_tokens, // ② 写入明细
    …
}
```

**这两条证据能证明什么、不能证明什么**：

- ✅ **能证明**：该快照**请求带缓存键、响应对账读写明细**——"CLI 与缓存机制的实际连接"**不是全靠文档推测**。
- ❌ **不能证明**：本次请求**一定命中**（那是服务端路由与状态问题，**以运行时返回的 usage 为准**）。
- ❌ **不能证明**：终端界面**一定展示**这些明细（核查的是写入 `TokenUsage` 的路径，界面展示是另一条链）。
- ❌ **不能**把 API 文档的**新参数**（如 30m TTL、显式断点）安到这份 CLI 上。

> 更细的源码走读属 **L4**，见 M10 源码桥接与样章 U08。

| ⑨ **deepseek-harness（dsh）** | **usage 映射**；**未发现 CLI 缓存键** | `dsh-cache-01/02` | 函数级 OBSERVED；**无键** |

**读表三件事**（不排名次，只讲形态差异）：

1. **"发键 / 认账 / 放断点"是三件不同的事**：① 发键且认账；② 认账并报**失效原因**；③④ 关注**摘要/预热**的写缓存策略；⑤⑥ 关心**断点放哪**；⑨ **没有 CLI 缓存键**（"没找到"≠"没有做"）。
2. **"有键"不代表"一定命中"**：键只帮**路由**；**命中与否看服务端**（`codex-cache-01` 只能证明"发了键、认了账"）。
3. **"计数"和"明细"粒度不同**：②⑦⑧给**计数/桶**，①给**读/写明细**，⑤⑥只给**usage 字段**——**引用时必须逐工具写清是哪一层**，不得用"所有工具都能看到缓存明细"这类总括句。

**【当心】两句别写错**：

- ❌ **"缓存能保证省钱/命中率 X%"**——**服务端命中/TTL 九工具全部 UNOBSERVABLE**（T14 F 表）。**本单元不承诺任何命中率**；能说的只有 **CLI 侧可观测字段**。
- ❌ **"dsh 也有缓存键"**——术语表 §6 明确：`prompt_cache_key` 在 **dsh 侧不成立**（未发现 CLI 缓存键，T13R）。

## usage 拆账：三组账单（本单元产出物演练）

> **统一舞台（教学演示）**：一次请求输入 **100,000** tokens，其中**稳定前缀 96,000**、本次新增 **4,000**。费率（**服务端文档示例，非实测**）：普通 **1×** / 读取 **0.1×** / 写入 **1.25×**。**每个例子先自己算一遍再看结论。**

**拆账三关系**（先记死，别算错）：

1. `cached_tokens` 与 `cache_write_tokens` **都是 `input_tokens` 的明细拆分**，**不能再加到 `input_tokens` 上**；
2. **普通输入** = `input_tokens` − `cached_tokens` − `cache_write_tokens`；
3. **计费当量** = `普通×1 + 读取×0.1 + 写入×1.25`（写入的 1.25 是**完整单价**，不是"普通价再加 1.25 倍"）。

**账 ① · 一次命中**（前缀未变，完整命中）

```text
普通输入 = 100,000 − 96,000(读) − 0(写) = 4,000
当量 = 4,000×1 + 96,000×0.1 + 0×1.25 = 4,000 + 9,600 = 13,600   （≈ 0.136× 全额）
→ 省下了重算那 96,000 的大头。这是"同样开头"应有的样子。
```

**账 ② · 一次失效**（前缀被改，如改了旧消息 / 工具集变了）

```text
cached = 0；cache_write = 100,000（首次见新前缀）
普通输入 = 100,000 − 0 − 100,000 = 0
当量 = 100,000×1.25 = 125,000   （= 1.25× 全额）
→ 这一次比"完全不缓存"还贵 25%（写入溢价），是在为后续命中铺路。
```

**账 ③ · 一次压缩周转**（压缩替换历史 → 前缀退化）

```text
压缩后：变化点之前的稳定段 20,000 仍匹配（读）；新前缀 40,000 需写入；本次新增 4,000
cached = 20,000；cache_write = 40,000
普通输入 = 100,000 − 20,000 − 40,000 = 40,000
当量 = 40,000×1 + 20,000×0.1 + 40,000×1.25 = 40,000 + 2,000 + 50,000 = 92,000
→ 比账①(13,600)贵得多：这就是"压缩后首个请求通常更慢更贵"的账。
  之后新前缀稳定，请求回到账①形态——所以叫"按前缀退化，不整体归零"。
```

**三账对照**：

| 账 | 场景 | 当量（【演示】） | 相对全额 | 一句话 |
|---|---|---|---|---|
| ① | 一次命中（前缀未变） | **13,600** | ≈0.14× | 缓存应有的样子 |
| ② | 一次失效（前缀被改） | **125,000** | 1.25× | 比不缓存还贵（写入溢价） |
| ③ | 一次压缩周转 | **92,000** | ≈0.92× | 压缩后首请求更慢更贵，随后回升 |

**【当心】账 ③ 读法**：**92,000 不是"压缩的成本"**——它是"**前缀变了导致这一次复用少**"的账。压缩的**模型调用成本**是另一笔（M04 的摘要调用），**两笔账不要混**。数字全部为**【演示】**，**不得当作真实费率或真实命中**。

## 自测（含答案）

**① 拆账题**：某请求 `input_tokens = 50,000`、`cached_tokens = 40,000`、`cache_write_tokens = 2,000`。求**普通输入**与**计费当量**（用本单元演示费率），并回答"`cached_tokens` 要不要从 50,000 里**再**减一次"。

**② 判断题（陷阱）**：命中缓存后，这次的**上下文窗口占用**会变小，**速率限制**也会更宽松。（对 / 错，说明理由）

**③ 边界题（R14）**：把下面四句里**错的**挑出来，并各用一句话纠正：
A. 缓存就是"把材料存起来，下次少发"　B. 缓存和摘要是一回事　C. 缓存能让窗口变大　D. 缓存能替代外部记忆。

**④ 关系题**：压缩之后，缓存复用会怎样？请用"**前缀**"这个词解释，并说明"整体归零"对不对。

**⑤ 对照题**：① Codex 与 ⑨ dsh 在"CLI 缓存键"上有什么差别？能说"dsh 没做缓存"吗？

**⑥ 红线题**：小林问"用这个工具缓存命中率能到多少？"你该怎么回答？为什么？

<details>
<summary>参考答案</summary>

**①** 普通输入 = 50,000 − 40,000 − 2,000 = **8,000**；当量 = 8,000×1 + 40,000×0.1 + 2,000×1.25 = 8,000 + 4,000 + 2,500 = **14,500**。**不能再减一次**：`cached_tokens` 是 `input_tokens` 的**明细拆分**，已经在 50,000 里了——把缓存 token 重复相加是常见错误。

**② 错。** 两者都**不变**：缓存省的是**重新计算**；命中的 token **依然是本次输入的一部分**（**不缩窗口占用**），且 **cached 输入依然计入 TPM**。把缓存当成"窗口扩容 / 上下文缩短"都是错的（术语表 §6 边界）。

**③** A、B、C、D **全错**。纠正：A. 缓存**不改变材料**，省的是**重算**，不是"少发材料"；B. **缓存 ≠ 摘要**——缓存复用前缀，摘要**替换**历史（目的相反）；C. 缓存**不缩窗口占用**；D. 缓存是**服务端 KV 状态**，不改变本次请求带哪些材料——**外部记忆**是"消息列表外可再取用的记忆"（术语表 §5），两者不是一回事。

**④** 压缩**替换了历史**，所以**从"第一个变化的 token"起**旧前缀不再匹配——**压缩后首次请求复用较少**。但"变化点之前"的稳定段（基础指令、工具说明）**仍可能命中**，且新前缀随后续追加相处稳定、命中**回升**。所以"整体归零"**不对**：**压缩改变前缀 → 缓存按前缀退化，不会整体归零**（样章 U08）。

**⑤** ① Codex **请求带 `prompt_cache_key`（默认=会话ID）**；⑨ dsh **未发现 CLI 缓存键**（`dsh-cache-01/02`；术语表 §6：dsh 侧不成立）。**不能**说"dsh 没做缓存"——只能说**"未发现 CLI 缓存键"**（"没找到"≠"没有做"）；且服务端命中/TTL **九工具全部 UNOBSERVABLE**，无从判断实际复用。

**⑥** 回答：**无法给出命中率数字**。原因：**服务端命中/TTL 九工具全部 UNOBSERVABLE**（T14 F 表）——本地只能看到 **CLI 侧可观测字段**（如 ① 的读写明细、②⑧ 的计数/桶），**看不到服务端是否真的命中、命中多少**。任何命中率承诺都**越过了证据边界**，须待 T19 以 usage 为准。【T19 实测：CLI 侧 cacheRead 可观测且 >0（codex 37,632~48,896；pi 3,072；claude 19,840~27,136；omp 3,136；dsh 最大 84,608；ocv1 9/12 命中）；**服务端命中率/TTL 仍 UNOBSERVABLE**（证据：T19/01-codex.md §A-4、03-claude.md §5、06-ocv1.md §4）】

## 速查卡（贴墙版）

> 撕下来贴桌上：**缓存省重算，不省容量；前缀是匹配单位；压缩改前缀 → 按前缀退化。**

- **省 / 不省**：省**重新计算**（钱、算力、首字延迟方向）；**不省**窗口占用、**不省** TPM。
- **匹配单位**：**完整渲染后的前缀**（token 级）——**无按文件 / 无按段缓存**。
- **边界四问（R14）**：**≠摘要 / ≠外部记忆 / ≠容量扩展 / ≠少发材料**。
- **前缀退化五源**：**压缩、改旧消息、工具变更、过期、恢复/fork/子Agent/记忆注入**——都靠"改变前缀"。
- **拆账三关系**：读/写是 `input_tokens` 的**明细**（**别重复相加**）；普通 = 输入 − 读 − 写；当量 = 普通×1 + 读×0.1 + 写×1.25。
- **八工具**：①发键+明细 / ②计数+失效原因 / ③④摘要禁写+预热 / ⑤前2system+末2非system / ⑥断点cap4+白名单 / ⑦仅读计数 / ⑧三桶+ticks / ⑨usage映射·**无键**——**不排名次**。
- **红线**：服务端命中/TTL **九工具全部 UNOBSERVABLE**——**不承诺命中率**。
