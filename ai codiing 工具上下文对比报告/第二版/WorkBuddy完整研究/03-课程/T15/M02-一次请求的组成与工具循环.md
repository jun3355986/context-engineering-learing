## 先修（读完 M01 你应该已经有这些）

- **任务**（task/turn）：从你说一句话到 AI 彻底停下为止的全过程。
- **模型请求**（model request）：把当前材料打包发给模型问一次"接下来做什么"。
- **工具**（tool）与**工具结果**（tool output）：模型不能自己动手，只能"要求"调用；结果是工具跑完的返回值。
- **消息列表**（message list）：按时间顺序排列、下一次请求要带的材料数组。

如果这四个名字里有一个说不清，回看 M01 §"给四件事起名字"。

---

## 学完你能做什么

1. **单步追踪**一次完整的工具循环：模型 → 要求调工具 → 工具执行 → 再问模型，四拍一步不落。
2. **预测**下一次请求会包含哪几块（基础指令、developer 材料、历史、工具说明、本次输入）。
3. **标注来源**：说清每一块"来自程序"还是"来自你"。
4. **认出坏结构**：调用缺结果、结果缺调用时，请求会怎样非法。
5. **对照八工具**：说出各工具把请求拼成什么形状（有的发角色消息，有的发一条合成 system，有的干脆没有 system 字段）。

**本单元产出物（L2）**：你**手写一次请求的组成清单**，逐块标出"程序给的 / 我给的"。

## 场景：小林盯着"下一步"发愣

小林（M01 里那位）现在明白了一件事：他的一句话触发了**一串**模型请求。但他还是想不通：

> 模型不是"聊着聊着就记住了"吗？为什么每做一步都要把全部材料**重新摊开**问一次？这一次请求里到底装了什么？

他的困惑里藏着 L2 的全部内容：**请求是"拼"出来的，不是"聊"出来的。** 每一拍，程序都按当前状态，把若干块材料重新组装成一个结构化请求再发出去。

## 核心概念

### 一、一次请求的组成清单（五块料）

先给你一个生活对照。你要把一份工作交给一位专家，但你**每次只能通过一扇小窗**把材料递进去，而且专家过目即忘——递什么，他就只看什么。于是每次递材料，你都得把"岗位说明书 + 当前情况单 + 之前的来往 + 能用的工具 + 这次的具体要求"一起递。

程序做的事和你一样。一次请求，**教学示意**（顺序与形态因场景而异），由五块料拼成：

```
一次模型请求
├── ① 基础指令（base instructions）      "你是怎样的助手" —— 岗位说明书
├── ② developer 材料                     程序维护的工作说明
│    ├── 当前工作状态（WorldState 渲染）   工作目录 / 权限 / 网络
│    └── 已加载的项目规则（AGENTS.md 等）   "本项目时间必须用 UTC"
├── ③ 对话历史（消息、工具调用与结果）      之前所有来往
├── ④ 工具说明（tools schema）            有哪些工具、怎么调用
└── ⑤ 本次用户输入                        你刚敲下的那行字
```

**关键：逐块标来源。** 这是 L2 产出物的核心动作。

| 块 | 谁给的 | 为什么 |
|---|---|---|
| ① 基础指令 | **程序** | 固定岗位说明书，你通常看不到也不该改 |
| ② developer 材料 | **程序** | 按**当前状态**渲染，不靠聊天推断（M01→M02 的桥） |
| ③ 对话历史 | **一半程序、一半你** | 你发的话 + 模型回复 + 工具结果，由程序按时间序维护 |
| ④ 工具说明 | **程序** | 工具清单本身也占空间，与聊天无关却每次都带 |
| ⑤ 本次用户输入 | **你** | 唯一 100% 由你决定的一块 |

**【人话】** 说白了：**你只控制了五块里的最后一块**。其余四块是程序按当前状态替你准备好的。所以"我明明只说了一句话，请求却那么长"——那四块才是大头。

**【当心】** 一个初学陷阱：以为 ⑤ 排在最后是随意的。不是。**稳定不变的材料排前面、易变的内容排后面**，对"前缀缓存"非常有利（M07 专讲）。这是程序的排布取舍。

> 说明：② 的"差分更新"（规则没变不重发、变了发一句替换说明）与 ④ 的"工具说明每次全带"是两种不同策略；前者在 M03 展开，本单元只要求你**认出这两块都来自程序**。

### 二、工具循环：一步是怎么走完的

小林看到屏幕上"AI 停了一下，然后接着干"。那一下里，程序走了**四拍**：

```
【第 1 拍】问模型："现在该做什么？"
            带上：①基础指令 + ②developer 材料 + ③历史 + ④工具说明 + ⑤本次输入
            ↓
【第 2 拍】模型回复：'我需要先查公交' → 要求调用工具（带一个调用编号 call_id）
            ↓
【第 3 拍】工具执行：查公交(线路A→学校) → 返回 300 行结果
            程序把"调用记录 + 结果"写进消息列表
            ↓
【第 4 拍】再问模型："现在该做什么？"
            带上：前面全部 + 刚才的调用与结果
            → 模型决定继续调工具，或给出最终回答
```

**要点**：工具执行本身**不调用模型**，但它**两侧各要一次模型请求**（第 1 拍和第 4 拍）。这就是 M01 那道顺序题的答案来源。

**【人话】** 说白了：模型像一位"过目即忘"的专家，每递一次材料才睁一次眼。工具是助理，助理跑腿的时候专家在闭眼；助理把结果递回窗口，专家才再睁眼问一句"然后呢"。

### 三、配对不变量：调用与结果必须成对

第 2 拍模型说"调用工具 X"（带 `call_id`），第 3 拍必然产生一条对应结果。程序**强制检查**这种配对是否完整，这就是**配对不变量**：

- **每个调用都有结果**（缺了要补占位）；
- **每个结果都能对回调用**（对不上的是"野结果"，移除）；
- 命名外部工具事件可以独立存在（例外项）。

**【当心】坏结构长什么样**——这是基线单元只给答案、没给演示的缺口，这里补上：

```
坏结构 A：调用缺结果（悬空调用）
  [... assistant: 调用工具"查公交"(call_id=call_001) ]
  [... 下一拍直接就是 user 或新的 assistant ...]   ← call_001 没有结果
  后果：上文悬空，模型不知道工具做了什么；服务端按"调用—结果"配对读取，会判结构非法。

坏结构 B：野结果（孤儿结果）
  [... tool: 结果(call_id=call_999) ...]           ← 找不到 call_999 这个调用
  后果：结果无法归属，程序在进入历史时移除孤立条目。

坏结构 C：内容类型不匹配（隐性改写）
  历史里有图片，但本次换用了不支持图片的模型
  后果：图片会在进入请求前被剥离——属于"材料在你没察觉时被改写"。
```

程序宁可**在本地补齐占位或移除孤立条目**，也不发送结构非法的请求。这不是礼貌问题，是**不变量**。

**【人话】** 说白了：调用和结果像"问"和"答"，不能只有问没有答、也不能冒出没问过的答。程序在材料进历史前把这一对一对捋顺，捋不顺的当场修掉。

### 四、最小消息列表示例

下面是一个**教学简化的数据样例**（数字是编的，结构模仿真实请求）：

```json
[
  {"role": "developer", "类型": "基础指令",     "内容": "你是 Codex……"},
  {"role": "developer", "类型": "当前工作状态", "内容": "工作目录 /project；网络：否；已加载规则：AGENTS.md……"},
  {"role": "user",      "内容": "安排郊游……下午 4 点前必须返校"},
  {"role": "assistant", "类型": "工具调用",     "工具": "查公交", "call_id": "call_001"},
  {"role": "tool",      "类型": "工具结果",     "call_id": "call_001", "内容": "（300 行公交查询结果）"},
  {"role": "assistant", "内容": "我再读一下研学地点说明"}
]
```

注意每条消息都有 **role（消息角色）**：`user` 是你的话，`assistant` 是模型回复，`developer` 是程序维护的工作说明，`tool` 是工具结果。**模型可见材料的最小单位叫响应条目（ResponseItem）**。

## 八工具对照：一次请求怎么拼

> 口径来自 **T14 矩阵 B 表"请求组装"行**，逐格附证据ID。**不排名次**；未证处如实标"文档级/未证"。Gemini CLI 官方已弃用（2026-06-18 起个人层停服），⑦列仅作**历史存档**，不进入正文对照主线。

| 工具 | 组装口径（一句话） | 证据ID | 证据等级 / 边界 |
|---|---|---|---|
| ① **Codex** | **角色消息 + 差分片段**：`Prompt{input, tools, base_instructions}`，基础指令按"模型/指令差分片段"处理 | `codex-diff-01`（D17） | 函数级 OBSERVED；片段实际内容未运行 |
| ② **Claude Code** | **文档级**：请求按"system prompt / project context / conversation"三层排序 | `claude-assembly-01` | 闭源；分发件+文档观察，非源码 |
| ③ **pi** | **投影 + 具名 sections**：`projection.messages`（compaction 已应用）+ tools 拼请求；系统提示词按可替换的具名 section（`preamble/tools/rules/docs/project_context/skills/cwd`…）组织 | `pi-assembly-01/02` | 入口级；投影由 `buildSessionProjection()` 生成 |
| ④ **oh-my-pi** | **同 pi 基座**：`buildSessionContext()` 从 leaf→root 路径重建；系统提示词 = 模板 + 各 prelude guidance + 一个**末尾** `<project-context>` 块 | `ohmy-assembly-01/02` | 入口已装 omp/18.11.0；函数级 |
| ⑤ **OpenCode v1** | **一合成 system + 投影**：`agent.prompt`/`SystemPrompt.provider(model)` + env + instructions + mcp + skills + user.system 合成**一条** system；messages = 投影消息 | `ocv1-assembly-01/02` | 函数级 OBSERVED |
| ⑥ **OpenCode v2** | **2 段 system + 指令基线**：`system=[agent.system ?? 基础提示词, initial]`（仅 2 段）；`initial` = 指令纪元基线渲染；v1 的四类块被折叠进 `initial` 与增量 | `ocv2-assembly-01/02` | 函数级 OBSERVED；末步追加 `MAX_STEPS_PROMPT` + `toolChoice:"none"` |
| ⑦ **Gemini**（历史·存档） | **双系统**：默认服务链路 vs 实验图管线（图管线**默认关**） | `gemini-version-02` | 已弃后续；仅存档，不得把图管线常量当默认 |
| ⑧ **Grok Build** | **文档级**：系统提示词（默认 / `--system-prompt-override` 整体替换 / `--rules` 追加 `<human_rules>` 块）+ AGENTS.md + `<memory>` + tools + messages | `grok-assembly-01/02` | 闭源；分发件观察 |
| ⑨ **deepseek-harness（dsh）** | **`header.config + deriveMessages() + header.tools`，无 `system` 字段**；提示词由 `system/message` 节点承载；工具增删发 `developer/message` | `dsh-assembly-01/02` | 入口已装 dsh/0.2.0-rc.2；函数级 |

**读表三件事**（不排名次，只讲形状差异）：

1. **"system 在哪"各家不同**：v1 是**一条合成 system**；v2 是**2 段**；dsh **根本没有 `system` 字段**（提示词塞进 `system/message` 节点）；Codex 用 **`base_instructions` + 角色消息**。同一个"岗位说明书"，在九家是九种容器。
2. **"稳定前缀"是共同心思**：oh-my-pi 把 `<project-context>` 放在**末尾**、Claude 按"变化频率"三层排序——都是为了前缀缓存（M07）。**不同工具不约而同地把"稳定"排前面。**
3. **"投影"是关键词**：pi/ocv1/ocv2 的 messages 都不是"内存数组原样"，而是**投影/重算**的产物——`projection.messages`（pi）、`toLLMMessages(...)`（ocv2）。这为 M04（压缩后重排）埋下接口。

**【当心】** 两个别写错的说法：

- ❌ "所有工具都有 system 提示词"——**dsh 没有 `system` 字段**（`dsh-assembly-01`）。"system 是通用概念"不成立。
- ❌ "v1 和 v2 是同源所以组装一样"——**同源≠零耦合**：v1 一条合成 system，v2 明确改成 **2 段**（`ocv2-assembly-01`）。引用时分界按出货标签。

## 自测（含答案）

**① 预测题**：你在原会话里什么都没改，直接再问一句。下一次请求的**组成清单**里，哪几块会变、哪几块大概率不变？

**② 判断题**：工具结果出现在消息列表里，说明它一定会出现在下一次请求里。（对/错）

**③ 排查题**：AI 没遵守"时间必须用 UTC"这条项目规则，你怀疑规则没进模型。列出至少两条要检查的位置。

**④ 来源标注题**：把下面五块分别标上"程序 / 你"：基础指令、developer 材料、对话历史、工具说明、本次输入。

**⑤ 配对题**：程序为什么要死守"每个调用都有结果"？如果历史里冒出一条"孤儿结果"（结果对不回任何调用），程序怎么处理？

<details>
<summary>参考答案</summary>

**①** **变**：⑤本次用户输入（新的一句）；③对话历史（追加了你的新消息，可能还有新的工具调用/结果）。**大概率不变**：①基础指令、④工具说明；②developer 材料**通常不变**（差分逻辑：栏目无变化不重发完整副本，变化时发替换说明）。注意"不变"指内容，是否重发要看各工具的差分/投影实现。

**② 错。** "进入列表"与"出现在下一次请求"之间还有处理步骤：配对与内容检查、限长（M05）、窗口紧张时的整理与摘要替代（M04）。这也是 M01 自测②的延续。

**③** 检查（示例）：规则文件的**位置与可信状态**（在发现范围内吗？项目被信任吗？）；**字节预算尾部截断**（是否超预算且关键行在文件尾部）；**内容是否变化而差分没发出替换**；以及"材料进没进 + 模型照没照做"是两段。**规则进请求 ≠ 模型遵守。**

**④** 基础指令=**程序**；developer 材料=**程序**；对话历史=**一半程序、一半你**；工具说明=**程序**；本次输入=**你**。**五块里你只控制最后一块。**

**⑤** 因为请求是结构化数据，服务端按"调用—结果"对应关系配对读取。缺结果会让上文悬空，缺调用的"野结果"无法归属。程序宁可在本地补齐占位或在进入历史时**移除孤立条目**，也不发送结构非法的请求——这就是三条配对不变量存在的原因。

</details>

## 速查卡（贴墙版）

- **一句话**：请求是"拼"出来的，不是"聊"出来的；**你只控制五块里的最后一块**。
- **五块料**：①基础指令 ②developer 材料 ③历史 ④工具说明 ⑤本次输入（①②④来自程序，⑤来自你，③一半一半）。
- **四拍循环**：问模型 → 模型要求调工具 → 工具执行写回 → 再问模型（工具执行本身不调模型）。
- **配对不变量**：每个调用都有结果、每个结果对回调用；坏结构 = 悬空调用 / 野结果 / 内容类型不匹配。
