## 场景：一条 300 行的日志，怎么吃掉半个窗口

小林的工具查回了一段 **300 行**的公交时刻表。其中一行写着：`"测试提醒：集合点东门，14:30 前必须到达。"`

后来 AI 安排行程时，**16:00 返校它记得牢牢的，14:30 却像从没出现过**。

小林的第一反应是："肯定是压缩把它弄丢了。"——**但这个判断太早了**。在"压缩"之前，这段日志其实还要过**两道关卡**：

```text
第①处：工具出口          第②处：活动历史            第③处：摘要请求
原始输出 300 行  →   写进当前列表时的副本   →   整理时给模型看的副本
（实际发给模型前）     （历史裁剪，存档另存）     （超限还会再缩）
```

**关键直觉**：一条约束要活到下一次请求，必须**连续通过"出口 → 历史 → 整理 → 恢复"四关**。**任何一关都可以成为丢失点**——排查时**不要只怀疑压缩**。

## 核心概念

### 一、工具输出为什么是最大的隐形膨胀源

**【人话】** 人打字是"一句一句"的，工具输出是"一整段一整段"的。一次 `cat`、一次 `git log`、一次 `grep`，动辄几百上千行、几万到几十万字符——**它们悄悄挤进消息列表，而用户根本没"说"过这些字**。

用量级感受一下【演示】：同一段 **300 行**公交表 ≈ **22,003 字节 / 17,190 字符**（T03 样本）；按 pi 的 `ceil(chars/4)` 口径 ≈ **4,298 token**；而普通用户一轮对话往往只有几十到几百 token。**一条工具输出 = 几十轮对话的量。** 一次任务里工具被调用十几次，**膨胀主要来自这里，不是来自"聊得久"**。

所以各家工具都设了一道"**闸门**"：**工具结果在进入消息列表前，先按预算限长**。这道闸门就叫**出口限长（output truncation）**。

**【当心】两个别混的东西**：

- **出口限长 ≠ 触发线**：触发线（M03）管的是"整张桌子到没到线"；出口限长管的是"**单条**工具结果太长，先切一刀"。
- **限长 ≠ 落盘**：限长只是"请求里放不下这么多"，**原文未必被删**——多数工具会把全量原文**写到磁盘**，请求里只留预览 + 路径（见 §四）。

### 二、三处限长：一条约束要过几道关

**【人话】** 同一条信息，在三个不同的时刻、被三个不同的"人"动了刀。把这三处画成一条链：

| 关卡 | 什么时候动刀 | 动刀的是谁 | 产物形态 | 典型手段 |
|---|---|---|---|---|
| **① 出口限长** | 工具结果**交给模型消费之前** | 工具结果包装函数 | 带警告头的**预览** | 保头尾裁剪、加说明头、超限落盘 |
| **② 活动历史** | 结果**登记进当前列表**时 | 历史管理函数 | 列表里的**裁剪副本** | 独立预算再裁一次；**存档另存原载荷** |
| **③ 摘要请求** | 到线**整理**时 | 压缩/摘要流程 | 给模型看的**历史副本** | 副本自身超限时再移除最早条目 |

**记住一句话**：**出口是"给模型的预览"，活动历史是"列表里的副本"，摘要是"整理用的副本"。** 三者**是三份不同的东西**，不能画成一个全局滑块。

**为什么②和①要"裁两次"？** 因为两者**目标不同**：①保证"单条不撑爆一次工具往返"；②保证"整张列表配平窗口"。所以同一条输出可能**先被①裁一次、再被②裁一次**——**两次预算互相独立**。

**【当心】** ②处有个**极易误判**的点：**活动历史被裁 ≠ 存档也少了**。写入会话存档（rollout）的是**未裁剪的原载荷**；裁剪**只作用于活动历史**。样章原文注释写得很直白：

```rust
// codex-rs/core/src/context_manager/history.rs  L517–519（原文注释）
/// Records output and annotates the original envelopes with captured provenance.
/// Tool output truncation applies only to live history, preserving full rollout payloads.
```

**但——**存档保留**也**不等于处处完整：存档链路自身还有独立预算（例如分片存储模式下命令输出与 MCP 结果各有 **64 KiB** 的持久化上限，超出加 `... command output truncated for persistence ...` 标记）`样章 C11`。所以**"磁盘上有原文"这句话永远要追问一句：哪一层、哪个文件、上限多少。**

### 三、裁剪算法：保头尾、标记、单位口径

**【人话】** 最常见的一刀叫**头尾裁剪（truncate middle）**：**保头、保尾、删中间、加一个标记**。为什么保尾？因为很多输出的**结论在末尾**（`BUILD FAILURE`、汇总行、`Tests run 42 / Failures 1`）；为什么保头？因为**开头常有上下文**（文件路径、命令、表头）。

用 Codex 的实现把算法拆开（`codex-rs/utils/string/src/truncate.rs`）`codex-trunc-01`：

```text
中文伪代码：头尾裁剪（近似 token 口径）
  输入：文本 s、预算 max_tokens
  若 s 为空 → 返回空
  若 max_tokens > 0 且 字节数(s) ≤ max_tokens×4 → 原样返回   # 装得下就不裁
  max_bytes = max_tokens × 4
  左预算 = max_bytes ÷ 2          # 整数除法，奇数时少 1 字节
  右预算 = max_bytes − 左预算      # 奇数时多 1 字节（左右并非严格均分）
  头部 = s 从 0 到 左预算的最近 UTF-8 边界
  尾部 = s 从 (总长−右预算) 的最近 UTF-8 边界到结尾
  标记 = "…N tokens truncated…"（N 按被移除字节数÷4 估算）
  返回 头部 + 标记 + 尾部
```

**三个必须记住的细节**（否则引用一定写错）：

1. **单位是"近似 token"，实现却按字节落刀**：Codex 的 `approx_token_count` 等价于 `ceil(UTF-8 字节数 ÷ 4)`【源码常量】`codex-trunc-01`——**按字节，不按字符**（M03 §一 的 C-06 口径）。
2. **左右不是严格均分**：`split_budget` 左 = `budget/2`（向下取整），右 = `总数 − 左`——**奇数预算差的那 1 字节给了尾部**。
3. **标记不占预算**：`…N tokens truncated…` 是**额外拼上去**的。所以**"含标记后输出一定严格等于预算"是错的**——真实输出会比预算略长一点。

**裁剪按字节算，但落刀看字符**：汉字在 UTF-8 里占 3 字节，切在中间会切出无效半字节。真实代码用 `floor_char_boundary` / `ceil_char_boundary` 对齐——**"中文不会被切成半个字"** 在多数实现里成立（oh-my-pi 的 `OBS-ohmy-trunc-01` 已观察佐证）。

**单位口径必须逐工具看**（这是全单元最容易混的地方）：

| 单位 | 工具举例 | 说明 |
|---|---|---|
| **字节** | ①Codex、④oh-my-pi、⑧Grok | 按 UTF-8 字节；中文 3 字节/字 |
| **字符** | ②Claude、⑦Gemini、⑨dsh（bash 侧） | 按字符计，中文 1 字符/字 |
| **行** | ③pi、⑤/⑥OpenCode、⑨dsh（read 侧） | 与字节上限**取先到者** |
| **token** | ①Codex（近似）、⑨dsh（spill 侧） | 多为本地粗估（M03 §一） |

**【当心】单位不同，数字不能互套**：②Claude 的 **30,000 是字符**、⑧Grok 的 **65,536 是字节**、③pi 的 **50KB 与 2000 行取先到者**——**"30k 和 64KiB 谁更宽"没有统一答案**，必须写明单位。

### 四、落盘与找回：预览 + 路径范式

**【人话】** 限长不是"删掉"，多数工具的套路是：**全量原文写磁盘 → 请求里只留一小段预览 + 一个路径**。模型看到的是"**这是一段被截断的内容，全文在 X 文件里**"，需要时可以**用 `read`/`grep` 再读回来**。

**统一的"预览 + 路径"范式**（以 pi 为例）`pi-trunc-02`：

```text
[Showing lines 1001-2000 of 3000 (50.0KB limit). Full output: /tmp/pi-xxxx.txt]
```

各家落盘**入口名不同**：③pi 落**临时文件**；④oh-my-pi 落 **`artifact://<id>`**（16 MiB 上限，头 3 MiB 保留 + 滚动尾）`ohmy-trunc-01/02`；⑨dsh 走 **`spill-local`**（`spill-policy`，`maxInlineTokens` 默认 **12500**，**省略该配置即关闭落盘**）`dsh-trunc-03`。

**"被限长/被压缩的内容去哪了"——统一裁决 C-03 / C-12 把它钉成两事实并存**：

| 层 | 内容在哪 | 能不能自动恢复 |
|---|---|---|
| **模型可见层**（这次请求带上的那份） | 已被**预览/摘要**替换，原文不在 | **不可自动恢复** |
| **磁盘原文层**（落盘文件 / 会话存档） | 九工具**均有落盘/存档入口**，原文**在保留期内可查** | **可查回**（人工/工具从磁盘读取，而非模型自动想起） |

**保留期是"可查窗口"，不是"永久档案"**：②Claude Code 落盘有 **64 MiB 截断**上限，transcript 约 **30 天**口径（`claude-cleanup`）；⑤ocv1 / ⑥ocv2 截断目录约 **7 天**（`ocv1-trunc-01`、`ocv2-trunc-01/02`）；其余工具**文档未给保留期**——**未知保留未知**。

**【当心】** ❌ 别写"工具输出超限就永久丢了"——**只在模型可见层成立**（C-03/C-12）。❌ 也别写"落盘就一定能全量找回"——②Claude 落盘**本身有 64 MiB 截断**（`claude-toolout-01`）。

**约束追踪（交互 I-裁剪器演示的正是这个）**：把 `14:30 集合点东门` 放在 300 行的**不同位置**，看它最坏情况下的命运：

```text
约束放『中部』    → ①出口裁剪阶段就消失，后面三步再努力也没机会看见它
约束放『头部/尾部』→ 还能过①，但仍可能被②历史裁剪或③摘要带走
约束放『用户消息里』→ 不进工具输出，走的是另一条路（M01/M02）
```

**【当心】这是本单元最实用的一条工程建议**：**关键约束要放在工具输出的头尾（或让工具显式置顶），不要指望它躺在中段侥幸过关**。同理，人对模型的表达也一样：**最要紧的约束写在消息的开头或结尾**。

## 真实实现锚点（Codex 代表实现）

**锚点一 · 工具出口包装（预览 + 警告头）**：`codex-rs/utils/output-truncation/src/lib.rs` L23–34【源码常量】`codex-trunc-02`

```text
Warning: truncated output (original token count: 24800)
Total output lines: 300

（裁剪后的内容：开头一部分 …N tokens truncated… 结尾一部分）
```

内容超出字节预算时，先记录**原始近似 token 数**与**总行数**，再做"保头尾"裁剪，最后拼上说明头。**所以模型看不到完整原文，它看到的是一份带警告的预览。**（"原始 token 数"这个数字很关键：它让模型知道"我拿到的是残缺的"。）

**锚点二 · 多块共享预算**：`truncate_function_output_items_with_policy`（同文件 L164–251）【源码常量】——一个工具结果里可能有多个内容块：

- 文字块**按顺序**消耗块内共享预算；装得下的整块留；
- 装不下的边界块**截短**（又是保头尾），截完预算置零；
- 预算耗尽后剩余文字块**整体略去**，结尾加 `[omitted N text items ...]` 提示；
- **图片直接保留**（在这层函数不扣预算）；音频按估算消耗，装不下则整体略去并加 omitted 提示。

**【当心】** 这里的"图片保留"与**远端压缩的图片预算**是**两套逻辑**（一个是工具出口层，一个是压缩保留层），**不要画成一个全局滑块**。

**锚点三 · 活动历史裁剪与存档分离**：`codex-rs/core/src/context_manager/history.rs` L517–576【源码常量】`样章 C10`——裁剪对象是**进入活动历史的那份副本**；**原信封保留**（写入 rollout 的是未裁剪原载荷）；预算优先用条目自带覆盖值，否则用模型策略附带的"序列化余量"（在预算基础上加 **20%**，给 JSON 转义/结构包装留空间）。

**锚点四 · 分片持久化预算 64 KiB**：`codex-rs/rollout/src/policy.rs` L16–19（样章 C11）——分片存储模式下命令输出与 MCP 结果各有 **64 KiB** 持久化上限。

> 更细的源码走读（`floor_char_boundary`/`ceil_char_boundary`、硬字节限额版 `truncate_middle_with_marker` 与 token 预算版 `truncate_middle` 的语义差）属 **L4**，见 M10 源码桥接与样章 U05「本章源码依据」。

## 八工具对照：工具输出治理全表

> 口径来自 **T14 矩阵 C 表"工具输出治理"行**，**逐格附证据ID**。**不排名次**；闭源/未证处如实标。⑦Gemini 官方已弃用（2026-06-18 起个人层停服），**仅作历史存档**，不进入正文对照主线。

| 工具 | 限长口径（一句话） | 超限原文去哪 | 证据ID | 等级 / 边界 |
|---|---|---|---|---|

**读表三件事**（不排名次，只讲口径形状）：

1. **限长的"层数"不同**：多数工具是**一层出口限长**（①②③④⑤⑥⑦⑧）；**⑨dsh 是三层**（read/bash 出口 + `spill-policy` + `tool-result-pruner`）。**"一层还是三层"是形态差异，不是优劣。**
2. **保头 / 保尾 / 保头尾**不同：④oh-my-pi 是 **head/tail 分流**（T19 实测为「保头尾掐中间」）；③pi 按工具类型分（read 保头 / bash 保尾）；**⑤⑥ 的 shell 路径为纯 tail——「开头的说明/路径」在⑤⑥会先丢**（**T19 实测更正：原「⑥仅 head」表述已废**）。
3. **⑧Grok 独有 pruning**：`[compaction.pruning]` 默认 `enabled=true`；`soft_trim_threshold` **4000 字符**、`soft_trim_head`/`soft_trim_tail` 各 **1500 字符**；`hard_clear_age_turns` 默认 **10**（超龄替换为占位符）；`keep_last_n_turns` 默认 **3**（最近 3 轮工具结果**永不剪**）`grok-toolout-03`——**剪枝发生在压缩语境，与出口限长是两层**。

**【当心】三个别写错的说法**：

- ❌ "工具输出超限就永久丢了"——**只在模型可见层成立**（C-03/C-12）；磁盘原文在保留期内可查。
- ❌ "30k / 64KiB 谁更宽"——**单位不同（字符 vs 字节），不得互套**（`grok-toolout-01`）。
- ❌ “所有工具都保头尾”——反例：**⑤⑥ shell 路径纯 tail（无头段）、③pi bash 保尾**（`ocv1-trunc-01`/`ocv2-trunc-01/02`，**T19 实测更正**）；⑧Grok **T19 实测为头/尾各 10,000 字符**（`grok-toolout-01` 文档未描述，实测已补）。

| 问题 | 去哪查 | 判断线索 | 人为对策 |
|---|---|---|---|

## 自测（含答案）

**① 演算题**：文本 30 个 ASCII 字符，预算 10 字节（Codex 头尾口径）。给出头尾内容、移除字节数与标记数字，并回答"最终字节数是否等于 10"。

**② 判断题（陷阱）**：工具结果被活动历史裁剪了，说明存档里也少了。（对/错）

**③ 定位题**：用户报告"AI 忘了 4 点前返校"。请给出你的**四问排查顺序**与各自的检查动作，并判断最可能落在三处限长的哪一处。

**④ 口径题**：②Claude 的 30,000、⑧Grok 的 65,536、③pi 的 50KB——**单位各是什么**？为什么**不能直接比大小**？

**⑤ 落盘题**：某工具把超限原文落盘了。有同学说"那就一定能全量找回"。请举出**一个反例**并说明依据。

<details>
<summary>参考答案</summary>

**①** 左 = 5、右 = 5（10÷2 恰好均分）；头 = 前 5 字符，尾 = 后 5 字符（s[25..]）；移除 = 20 字节 → N = `ceil(20/4)` = **5**；结果 = 5 字符 + `…5 tokens truncated…` + 5 字符。**最终字节数不等于 10**（10 + 标记长度），因为**标记不占预算**。

**② 错。** 活动历史裁剪**只作用于进入活动历史的副本**；存档（rollout）写入的是**未裁剪原载荷**。不过要追问："存档有"≠"以后一定读回到模型"（M06 话题），且存档自身还有独立预算（**64 KiB 分片**，`codex-trunc-03`）。

**③**（示例）①查它有没有进过记录：规则文件/消息本身在范围里吗？（对照 32 KiB 与发现范围）②查工具输出形态：有没有 `Warning: truncated`、关键行是否在**中段**；③问"这条约束在摘要里吗"（本地路径可查文本；远端路径不可见，以任务结果验证）；④搜历史里是否新旧说法并存，必要时**显式声明作废**。**最可能落在第②处（出口/活动历史）**——若关键行在工具输出中段。

**④** ②Claude 30,000 是**字符**；⑧Grok 65,536 是**字节**；③pi 50KB 是**字节**且与 **2000 行取先到者**。**不能直接比大小**：单位不同（字符 vs 字节），且 pi 是**双上限取先到者**——**"数字大"不等于"实际留得多"**（`grok-toolout-01`：单位不同，不得互套）。

**⑤ 反例**：②Claude Code 落盘**本身有 64 MiB 截断上限**（`claude-toolout-01`）——**"落盘"不等于"全量"**。依据：T14 矩阵 C 表 + 冲突表 **C-03/C-12**：磁盘原文**在保留期内**可查，且**受该层自身预算约束**；模型可见层仍不可自动恢复。

</details>

## 速查卡（贴墙版）

- **膨胀源**：工具输出是**最大隐形膨胀源**——一条 300 行日志 ≈ 几十轮对话（【演示】量级）。
- **三处限长**：**①出口限长**（预览 + 警告头）→ **②活动历史**（裁剪副本，**存档另存原载荷**）→ **③摘要请求**（历史副本，超限再缩）。
- **裁剪算法**：**保头尾、删中间、加标记**；**标记不占预算**；**左右非严格均分**（奇数差 1 字节归尾）；**按字节算、看字符落刀**。
- **单位必须逐工具看**：字节（①④⑧）/ 字符（②⑦⑨bash）/ 行（③⑤⑥⑨read）/ token（近似）——**不得互套**。
- **落盘范式**：全量原文写磁盘 → 请求里留**预览 + 路径**（pi 临时文件 / oh-my-pi `artifact://` / dsh `spill-local`）。
- **找回两层事实（C-03/C-12）**：**模型可见层不可自动恢复**；**磁盘原文层保留期内可查**（②64 MiB 截断、⑤⑥ 7 天、②约 30 天）。
- **产出物**：**损失点定位表**（四问：没读进来？被裁了？摘要漏了？旧决定没作废？）。
- **当心**：❌“超限就永久丢”；❌“不同单位的限值直接比大小”；❌“所有工具都保头尾”（反例⑤⑥纯 tail——**T19 实测更正**）。
