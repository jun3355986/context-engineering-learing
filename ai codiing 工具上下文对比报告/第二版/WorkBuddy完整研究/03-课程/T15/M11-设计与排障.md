## 先修（读完 M01–M10 你应该已经有这些）

- **M01–M03**：记录 / 材料 / 请求是三层；请求由**五块料**拼成（**配对不变量**）；窗口 W / 用量 A / 有效窗口 H，**触发线 = 范围线 OR 整段线**。

- **M09–M10**：检索是**第一道闸门**（按需读入 ≠ 全量装填，**提及 ≠ 附带内容**）；一条真实调用链的**关键分支、配置门控与状态变化**（L4 桥接）。

## 场景：从"读懂别人"到"自己设计"

小林已经读完了 Codex 的九单元，也能读源码。现在他要给**班级郊游助手**做上下文管理设计。他不再问"Codex 是怎么做的"，而是问：

> **设计问**：我这个助手的**状态**有哪些？一轮任务**按什么顺序**读写？关键约束（"下午 4 点前返校"）怎么保证**不丢**？
>
> **排障问**：如果整理失败了、恢复后约束丢了、工具结果被裁了，我**怎么发现、怎么修**？哪些动作**不能重复执行**？

这两个问，正好对应 L5 的两件事：**设计**（把机制拆成能力，做出一份方案）与**排障**（出问题时按路径定位）。样章 U09 的已知教训给了靶子：**有个助手整理后忘掉了"下午 4 点前返校"，也有助手把"已否决的地点"复活了**。

**关键直觉**：**L5 的产物不是"抄一份 Codex 的实现"，而是"一份能复核、能自洽、能迁移的方案"**——它可以与 Codex 不同，但必须**说得出理由、给得出反例、经得起检查**。

## 核心概念

### 一、设计四件套：L5 的最小交付

**【人话】** 做上下文管理设计，不必写代码，但要交**四样东西**，缺一不可：

| 件 | 回答什么 | 关键要求 | 对应单元 |
|---|---|---|---|
| **① 状态图** | **有哪些状态对象**（材料列表、约束表、用量计、检查点），各自**何时被读、被写** | 每个对象都要标"一轮任务里哪一刻读、哪一刻写" | M02/M03/M04 |
| **② 伪代码** | **一轮任务的流程**（读输入 → 更新约束 → 组装 → 调模型 → 工具 → 用量检查 → 整理/恢复） | 必须写出**取舍理由**（为什么用户消息优先、为什么约束单独建表） | M03/M04/M06 |
| **③ 失败处理** | **失败分类 + 有界重试 + 副作用/幂等** | 给一张"失败 → 检查 → 行动"表；标出**不可重复执行**的动作 | M04/M06/§二/§三 |
| **④ 检查方法** | **怎么发现它坏了**（排障清单 + 评估维度） | 排障要按**症状 → 机制 → 单元**定位；评估要**质量/成本/延迟/可恢复并查** | §五/M12 |

**【当心】最常见的漏项是第④件**：很多人只交状态图与伪代码，**不写"怎么检查"**。但 L5 的验收口径是"**可复核**"——没有检查方法，方案就无法被独立验证，也谈不上"迁移"。

**状态图长什么样（骨架，**示范之一、非唯一答案**）**：

```text
状态对象：ctx.messages 材料列表 / ctx.constraints 约束表{文本,来源,状态(有效/已否决),更新时间}
         / ctx.usage 用量计{服务端用量,本地估算,基线} / ctx.checkpoint 替代历史
一轮任务：读输入 → 更新 constraints（新约束入表；被否的标"已否决"而不删）
        → 组装请求（约束表渲染在头部；messages 按时间序）→ 调模型
        → 若要求工具：执行并登记结果（配对检查；超限裁剪 + 标记）
        → 用量检查：范围线或整段线到线？ 是 → 整理（筛候选：用户消息优先 → 从新到旧装预算
              → 边界截短 → 追加摘要/压缩产物 → 重组状态与规则 → 写入检查点，追加不删旧记录）
        → 输出或继续循环
```

（骨架取自样章 U09「交付 2」，**你的设计可以不同，但必须自洽**。）

### 二、失败分类与有界重试：为什么"失败 ≠ 灾难"

**【人话】** 整理失败时，先别慌——要看清**两件事**：失败发生在**哪一小步**；哪份状态**已经变了**、哪份**还没安装**。样章把"整理"拆成有先后**四步**：

```text
① 准备：复制当前历史做"整理副本"，组装给模型看的材料
② 请求：把材料发给模型（本地摘要 / 远端压缩请求）
③ 验收：产物合格吗？（有完成事件吗？压缩条目数量对不对？）
④ 安装：替换活动历史 + 追加检查点（M06 的两件事）
```

**只要能分清"③失败"与"④失败"，大多数恐慌就会消失**：③失败 → ④不执行 → **活动历史保持原样**（没被换坏）；④一旦执行 → 那就是**成功路径**了。

**两条设计原则**（这是本单元要求你写进"失败处理"的）：

1. **失败分类**：按原因分（超窗口 / 中断 / 取消 / 预算耗尽 / 验收不合格），**各走各的出路**——不是"一律重试"。
2. **有界重试**：重试必须**有上限**，而且**不同循环用不同计数**。

**【当心】看到 `retries = 0` 先别判"死循环"**：Codex 本地压缩在超窗口时**移除副本最早项 + `retries = 0` 再试**。这里的 `= 0` 不是笔误、也不是无限重试——它是**"缩副本循环"**的计数归零，与**"普通错误退避"**是**两种循环语义**（`codex-fail-01`）。缩副本每缩一次问题**真的变小了**（有进展），所以计数重置；退避重试针对"外部一闪而过的错误"，总次数要有上限。

**【当心】"拿到东西就算成功"是误读**：远端 v2 要求**恰好一个压缩条目**（`compaction_count != 1` 即判 Fatal）——这叫**验收（validation）**："拿到的东西**符合契约**才算成功"。只看 `Ok` 就判断整个业务成功，会漏掉后面的**安装与持久化**步骤（`codex-fail-02`）。

### 三、幂等与重复执行：恢复重建的是"材料"还是"动作"？

**【人话】** 关掉再打开（M06），程序重建的是**对话历史/材料**，**不是重跑已完成的动作**。所以：

- **已经产生的副作用不可回退**——整理前已经写进磁盘的文件，压缩失败**不会撤回**；⑧ Grok 的 `/rewind` **只截断对话、不还原文件**（`grok-recover-01`）；⑧ Grok 的 sandbox **一旦应用即不可逆**（`grok-fail-02`）。
- 会不会把**同一条命令再跑一遍**，取决于恢复后模型**是否被重新驱动**去调那个工具——这是**幂等/重复执行**问题。

```text
副作用（不可回退）：写盘 / 已推送的提交 / 已应用的 sandbox 设置
幂等（可安全重复）：读文件 / 检索 / 幂等查询
重复执行风险：恢复后模型重新发起同一次写操作 → 二次写入
```

**【当心】这是本单元最需要标"未知"的地方**：**"恢复后是否重复执行工具"目前未裁决**——各家证据卡把它列为"不能证明"，机制细节待实验回填 → **【T19 部分：E4 条件下未见工具重复执行（codex 恢复轮 0 命令、pi 溢出恢复 0 工具动作）；专门副作用注入未做 → 保留未决（证据：T19/01-codex.md §A-6、02-pi.md §5）】**。设计时你能做的是：**把"不可重复的动作"标出来、给它们加防护**（例如记录已完成动作、恢复后先核对），而**不能宣称**"恢复一定不会重跑"。

### 四、场景决策表：怎么"选"，而不是"排名次"

**【人话】** L5 要你**为场景做选择**。选择不是"谁更强"，而是"**在这个场景下，哪种做法更合适、它的反例是什么**"。T14 G 表给了 **8 个场景**，每个都配**一个反例/陷阱**——**反例才是决策表的灵魂**：它告诉你"什么情况下这个建议会翻车"。

**三条使用纪律**（写进你的方案）：

1. **按场景查，不排名次**：矩阵**不含任何"谁更省/更快/更强"排序**，相关比较须待 **T19** 统一条件实测后回填。【T19 实测：已获各工具用量数据（见 T19-结果总表 §3），但执行模型/provider 不同 → **条件不可比，仍不排名次**；小样本（3 次）不声称统计显著（证据：T19-结果总表.md §1/§3）】
2. **每个决定配一个反例**：一个"建议"没有反例，就等于没做决策表（U09 的评分表要求"每个选择给出代价与一个反例"）。
3. **未知保留未知**：口径不一（如 ⑧ Grok `respect_gitignore` 默认值 README 说 true / config 说 false）**登记不裁决**。

## 八工具失败对照全表（逐格引证据ID）

> 口径来自 **T14 矩阵 D 表"失败"行** 与各工具包 `*-fail-*` 证据卡，**逐格附证据ID**。**不排名次**；闭源/未证处如实标。⑦ Gemini **仅作历史存档**，不进正文对照主线。

| 工具 | 溢出 / 失败处理 | 副作用 / 回退 | 证据ID | 等级 / 边界 |
|---|---|---|---|---|
| ① **Codex** | **移除副本最早项 + `retries=0`** 重试（缩副本循环）；只剩 1 条 → `set_total_tokens_full` + 返回错误；远端 v2 新增 **`ResponseIncomplete` 分支**与尝试隔离（D10） | 写盘不回退（通用）；**压缩提交单次尝试隔离**（成功后一次性提交） | `codex-fail-01/02` | 函数级；本地有界 |

| ⑧ **Grok Build** | `models.max_retries` 默认 **8**；限流总尝试 `rate_limit_retry_threshold`；子 Agent 429 等待默认 8 / 上限 32；**`doom_loop_recovery`** 重采样 | **sandbox 一旦应用即不可逆**（设计）；`usage_is_incomplete`/`cost_is_partial` 计量分类 | `grok-fail-01/02` | **文档级**（闭源）；**版本漂移** 1.0.50→1.0.52 |
| ⑨ **deepseek-harness（dsh）** | `llm-retry` normal 默认 **5** 次、退避 500ms–10s（always 无上限）；`compactionRetries` 默认 **1**、`maxOverflowRetries` 默认 **1**；压缩失败分支（`ManualCompactionError`：busy/cancelled/changed/summary/commit/persistence）；孤儿锁检测 | 追加式 JSONL，**原文保留**；**`PRUNE_MARKER`**（pruner） | `dsh-fail-01/02/03`、`dsh-trigger-01`、`dsh-trunc-04` | 源码级 |

**读表三件事**（不排名次，只讲形态）：

1. **"有界"是共同点**：①–⑨ 的重试**都有上限**（①缩副本有界；③仅一次；④3/10；⑤5+doom 3；⑥10；⑧8；⑨5/1/1）——**差异在"哪条循环有界、上限多大"**。
2. **"验收"与"重试"是两件事**：① 远端 v2 的"**恰好一个**压缩条目"、③ pi 的"**成功才提交**"、⑨ dsh 的**收缩校验**——都属**验收**；只看重试次数会漏掉它。
3. **"崩溃恢复"不是每家都有**：**⑥ ocv2 有 write-ahead claim**（跨进程）；⑤ ocv1 **未见**跨进程 claim（进程内标 `interrupted`）——**同为 OpenCode，v1/v2 在此处分叉**（`ocv2-recover-02`）。

**【当心】三个别写错的说法**：

- ❌ "① 的 `retries=0` 是死循环"——是**两种循环语义**（缩副本 vs 退避），`codex-fail-01`。
- ❌ "② 连续失败 3 次就熔断"——**机制成立（thrashing 停重试），但"3 次"无一级出处**（`claude-error-01`）。
- ❌ "⑥ 全仓没有 doom_loop"——**不成立**（实为 169 命中）；正确口径是"**出货路径未发现阈值判定逻辑**"、性质标**推断**（`ocv2-fail-02`）。

## 真实实现锚点（代表实现）

**锚点一 · 有界性：缩副本循环（Codex）**：`codex-rs/core/src/compact.rs` L338–349（快照 `a07c8eb`）【源码常量】`codex-fail-01`

```rust
Err(e) if matches!(e.details(), CodexErrorDetails::ContextWindowExceeded) => {
    if turn_input_len > 1 {                        // ① 副本还有多条才缩（有界）
        history.remove_first_item();               // ② 移除最早项（保前缀 + 保近期）
        retries = 0;                               // ③ 缩副本循环计数归零（≠ 退避计数）
        continue;
    }
    sess.set_total_tokens_full(turn_context.as_ref()).await;   // ④ 只剩一条：宣布局满
    return Err(e);
}
```

逐句：① `turn_input_len > 1` 保证**不会缩到空数组、不会无限循环**（有界性）；③ `retries = 0` 是**另一个计数器的语义**，读代码时先问"这是哪个计数"；④ **错误返回与状态标记是两件事**——`set_total_tokens_full` 是显式状态写入，让上层据此决策（提示手动整理 / 开新会话）。

**锚点二 · 验收：恰好一个压缩条目（Codex 远端 v2）**：`codex-rs/core/src/compact_remote_v2.rs` L477–487【源码常量】`codex-fail-02`

```rust
let Some(response_id) = completed_response_id else {
    return Err(CodexErr::Stream("… stream closed before response.completed"));   // ① 没等到完成：失败
};
if compaction_count != 1 {
    return Err(CodexErr::Fatal(format!(
        "remote compaction v2 expected exactly one compaction output item, got {compaction_count} …")));   // ② 条目≠1：失败
}
```

**为什么要求"恰好一个"**：替代历史里"那一段压缩材料"必须与"**一个条目**"一一对应；多一个或少一个都会让后续恢复、预算与替换语义**失去对齐点**。这就是**验收**——"拿到的东西符合契约才算成功"。

**锚点三 · 成功才提交（pi）**：`packages/coding-agent/src/core/agent-session.ts` L2873–2875 等【源码常量】`pi-fail-02`——**压缩只在成功后 `appendCompaction`**（无半提交）；失败/取消**不追加 compaction**、不安排内部重试，仅保留已发生的 omission 编辑。

> 更细的源码走读（`match` 分支、`Option`、重试计数语义、崩溃 claim 结算）属 **L4**，见 M10 源码桥接与样章 U07「本章源码依据」。**失败注入实验（D 维度）待 T19。**

## 产出物示范：小型方案（四件套）

> **本单元交付**：为一个小任务（可用样章 U09 的"行程规划 Agent"或"接口兼容迁移"）提交**四件**。**示范之一，非唯一答案**；你的设计可以不同，但必须自洽、有理由、有反例。

**① 状态图（示范）**：列出状态对象（材料列表 / 约束表 / 用量计 / 检查点），每个标"**何时读、何时写**"；标出哪些材料"**必须每次带**"、哪些"**按需带**"。

**② 伪代码（示范）**：写出一轮任务顺序（见 §一骨架），**必须出现取舍理由**：为什么**用户消息优先**（保留算法）、为什么**约束单独建表不跟摘要走**（摘要**有损**，关键状态交给概括无法验证）。

**③ 失败处理（示范）**：

| 失败 | 怎么发现 | 行动 | 不可重复的动作 |
|---|---|---|---|
| 整理失败 | 四步哪一步断的（③验收 / ④安装） | 活动历史保持原样；记录诊断；下轮再试或提示用户 | 已写盘的文件 / 已推送的提交 |
| 恢复后丢约束 | **恢复后先验证**（重述检查"旧客户端兼容要求是什么"） | 从约束表重新渲染；必要时重发 | —（读操作可重复） |
| 工具结果被裁剪 | 日志关键行是否在场 | 重读方案（重跑测试 / 看报告文件）；防重复读取 | 重跑测试若会写盘需防护 |

**④ 检查方法（反例自检 + 排障清单）**：把**场景决策表**中你的场景那一行的**反例**抄进来，作为"**我的方案在什么情况下会翻车**"的自检项；再配 §五 排障清单。

**【当心】一条全教程反复提醒的纪律**：**"1 − 处理后/处理前"只是体积缩减率**，**不能替代任务质量**。压缩率再漂亮，**约束丢了就是丢了**（U09 综合自测⑨）。

## 五、排障检查清单（从"约束丢了"到"账单不对"）

> **用法**：按**症状**查行 → 定位到**机制** → 去对应单元看细节。**每一行都先问"哪一层"**（磁盘 / 活动历史 / 请求），因为三层分离是最常见的误判源（M06）。

| 症状 | 先查哪里 | 可能原因 | 对应机制 | 行动 / 单元 |
|---|---|---|---|---|
| **关键约束丢了**（模型不照做） | 请求里**还有没有**它 | 出口限长 / 裁剪 / 摘要遗漏 / 没检索回来 | M04/M05/M09 | 约束**单独建表**、每轮**重新渲染**、恢复后**先验证** |
| **已否决的方案复活** | 摘要 vs 约束表 | 有损摘要改写状态；"否决"没结构化保存 | M04/M08 | 建约束表，被否的标"**已否决**"而**不删**；【T19 实测：连续压缩后约束基本未丢（E1 全 PASS），但 **grok 为反例**——3 次连续压缩后硬约束丢失（证据：T19/07-grok.md §1/§2）】（C-04/LQ-09） |
| **压缩（整理）失败** | 四步哪一步断的 | ③验收不合格 / ④安装未执行 | M04/M06 | 活动历史**保持原样**；**先别再狂发消息**；下轮再试或开新会话 |
| **恢复后重复执行** | 幂等 / 副作用 | 副作用**不可回退**；恢复后模型重新发起写操作 | M06/§三 | 标出不可重复动作 + 加防护（记录已完成动作、恢复后核对）【T19 部分：E4 条件下未见工具重复执行；专门副作用注入未做 → 保留未决（证据：T19/01-codex.md §A-6、02-pi.md §5）】 |
| **缓存没命中** | 前缀是否变了 | 压缩改了前缀 / 工具顺序变 / 模式切换 | M07 | **别为凑缓存改写旧消息**；追加新信息 |
| **账单不对** | 分开拆账 | 缓存 token **重复相加** / 中文 token 被 `chars/4` **低估** | M07/§二 | 用**真实 tokenizer**；缓存**读/写分开**；不承诺命中率（UNOBSERVABLE） |
| **内容找不回** | **分两层** | 模型可见层 vs 磁盘原文层 | M06/M09 | 走落盘/存档入口；**C-03/C-12**：两事实并存、层不同 |

**【当心】排障的第一原则**：**先分清"哪一层"**——"我看到"（磁盘/历史）与"模型看到"（请求）**经常不一致**。把三层当一层，是绝大多数排障绕弯路的根源（M06 主结论）。

## 自测（含答案）

**① 设计题（四件套）**：L5 的"设计四件套"是哪四件？哪一件最容易被漏掉，为什么它不能漏？

**② 失败题（双计数）**：Codex 本地压缩在超窗口时 `retries = 0`。这是"无限重试"吗？为什么？它属于哪种循环？

**③ 验收题**：远端 v2 要求压缩条目"**恰好一个**"。收到两个会怎样？为什么"恰好一个"是**验收**而不是苛求？

**④ 幂等题**：`resume` 之后，程序会**把昨天已经跑过的命令再跑一遍**吗？为什么"副作用不可回退"？本单元对此的**证据状态**是什么？

**⑤ 场景题**：用户想"开箱即用就有长期记忆"。按 T14 G 表，**建议**是什么？**反例**是什么？

**⑥ 排障题**：模型"忘掉了下午 4 点前返校"。按排障清单，**第一步**先查什么？可能的原因有哪些？

**⑦ 口径题**：同学说"② Claude 连续失败 3 次就熔断"。这句话**哪里成立、哪里不成立**？

<details>
<summary>参考答案</summary>

**①** 四件：**① 状态图**（有哪些状态对象、何时读/写）、**② 伪代码**（一轮任务流程 + 取舍理由）、**③ 失败处理**（失败分类 + 有界重试 + 副作用/幂等）、**④ 检查方法**（排障清单 + 评估维度）。**最易漏第④件**——L5 的验收口径是"**可复核**"，没有检查方法，方案无法被独立验证，也谈不上迁移。

**②** **不是**无限重试。`retries = 0` 是**"缩副本循环"**的计数归零（`codex-fail-01`），与**"普通错误退避"**是**两种循环语义**。缩副本每缩一次问题**真的变小了**（`turn_input_len > 1` 时移除最早项，每次至少减 1 条 → **有界**）；退避重试针对"外部一闪而过的错误"，总次数有上限。若两者共用一个计数器，缩副本的成功率会被无关错误耗尽额度。

**③** 判为 **Fatal 错误**（"expected exactly one compaction output item"），**替代历史不安装**；活动历史**保持原样**（`codex-fail-02`）。**为什么是验收**：替代历史里"那一段压缩材料"必须与"一个条目"一一对应，多/少都会让后续**恢复、预算与替换语义失去对齐点**——"拿到的东西**符合契约**才算成功"，只看 `Ok` 是误读。

**④** **恢复重建的是"材料/对话历史"，不是"重跑已完成的动作"**（M06）。**副作用不可回退**：整理前已写盘的文件，压缩失败不会撤回；⑧ Grok `/rewind` 只截断对话、不还原文件（`grok-recover-01`）；⑧ sandbox 一旦应用即不可逆（`grok-fail-02`）。**证据状态**：**"恢复后是否重复执行工具"目前未裁决**，各家列为"不能证明" → **【T19 部分：E4 条件下未见工具重复执行（codex 恢复轮 0 命令、pi 溢出恢复 0 工具动作）；专门副作用注入未做 → 保留未决（证据：T19/01-codex.md §A-6、02-pi.md §5）】**——设计时能标出不可重复动作并加防护，但**不能宣称**"一定不会重跑"。

**⑤** **建议**：注意**大多默认关**（④oh-my-pi off / ⑦Gemini false / ⑧Grok 关）。**反例**：❌ 别写"有记忆=默认开"；②Claude **文档未描述**后台机制（`claude-memory-03`）。**"未发现"≠"没有"**。

**⑥** **第一步先查"哪一层"**——请求里**还有没有**这条约束（可能它还在磁盘/历史，只是没进本次请求）。**可能原因**：出口限长 / 活动历史裁剪 / 摘要遗漏（M04/M05/M09）。**行动**：约束**单独建表**、每轮**重新渲染**、恢复后**先验证**（重述检查）。

**⑦** **成立的部分**：机制成立——自动压缩反复失败时**停止重试**并报 thrashing（`claude-error-01`）。**不成立的部分**：**"3 次"无一级出处**——文档用 "several times"/"a few attempts"，具体数字**未决**。**登记不裁决**。

</details>

## 速查卡（贴墙版）

- **设计四件套**：**① 状态图 / ② 伪代码 / ③ 失败处理 / ④ 检查方法**——**最易漏第④件**（可复核）。
- **整理四步**：① 准备 → ② 请求 → ③ 验收 → ④ 安装。**③失败 → ④不执行 → 活动历史保持原样**。
- **失败分类 + 有界重试**：按原因分（超窗口/中断/取消/预算耗尽/验收不合格），**各走各的出路**；**缩副本循环 ≠ 退避循环**（`retries=0` 不是死循环）。
- **验收**：不是"拿到就算成功"，是"**符合契约**才算成功"（① 远端 v2 要求**恰好一个**压缩条目）。
- **幂等与重复执行**：恢复重建**材料**、不重跑**动作**；**副作用不可回退**；**是否重复执行未裁决 → 【T19 部分：E4 条件下未见工具重复执行；专门副作用注入未做 → 保留未决（证据：T19/01-codex.md §A-6、02-pi.md §5）】**。
- **场景决策表**：**按场景查、不排名次**；**每个决定配一个反例**（T14 G 表 8 场景）。
- **排障第一原则**：**先分清"哪一层"**（磁盘 / 活动历史 / 请求）——"我看到"≠"模型看到"。
- **当心**：❌"`retries=0` 是死循环"；❌"② 连续失败 3 次熔断"（数字无出处）；❌"⑥ 全仓无 doom_loop"（实为 169 命中）；❌"压缩率漂亮=任务质量好"。
