## 0. 主链路总览：一次任务里上下文发生什么

```
用户输入
  → [A] 组装 build_prompt（input + tools + base_instructions + output_schema）
  → [B] 轮前触发检查 run_pre_sampling_compact（到线则先整理）
  → [C] 模型请求（可能连续多步；中途工具结果被出口限长后写回）
  → [D] 轮中触发：needs_follow_up 时到线则整理，然后 continue
  → [E] 轮后触发（可选）：turn_end 阈值
  → [F] 压缩完成：替换内存历史 + 追加 CompactedItem 检查点
  → [G] 下一次请求用替代历史；重启用「替代历史 + 后缀回放」恢复
```

主链路调用者：`session/turn.rs` 的回合循环（`run_turn` 系列）。**主链路本体（A/C/G 与轮前/轮中/轮后骨架）在两份快照中保持不变**；新快照只**扩展**了触发门控与一条**后台/投机压缩**支路（见 §2.4）。

关键证据（新快照；旧快照亦成立）：

## 1. 主链路逐段解读

- **写回**：组装结果即本次模型请求；请求后由服务端返回 usage，回填当前用量。
- **中文解读（伪代码先行）**：

```text
请求 = [ 基础指令 ] + [ 当前工作状态/规则 ] + [ 历史材料(按不变量清洗过) ] + [ 工具说明 ]
禁止：出现没有配对结果的工具调用条目（配对不变量）
```

### 1.2 当前工作状态与项目规则（`WorldState` / `AGENTS.md`）

## 2. 触发链路（窗口计量与触发线）

### 2.1 计量与两条线（调用者 → 条件 → 判定）

- **调用者**：轮前 / 轮中 / 轮后三个时机都先取 `context_window_token_status`。
- **当前用量 A**：`get_total_token_usage()` = 上次服务端 `usage.total_tokens` + 最后模型输出后的本地新增估算（含必要推理补计）。
- **整段线（硬检查线）**：`full_context_window_limit = W × p / 100`，`p` 缺省 **95**（`effective_context_window_percent`）。`W = context_window.or(max_context_window)`。
- **范围线（软触发线）**：`auto_compact_scope_limit = min(模型字段 M, 90% 基础线)`；无 M 用基础线 `(W×9)/10`；窗口未知直接用字段 M。
- **范围口径**：`Total`（比较全部材料）或 `BodyAfterPrefix`（比较基线之后的增长量 `A.saturating_sub(P)`，P=首轮 input_tokens）。
- **到线判定**：`token_limit_reached = （软限额+缓冲）或 整段线` 之一满足；另有 `turn_end_compaction_threshold_reached`（轮后可选，`model_post_turn_compact_threshold_percent>0`）。
- **中文解读**：

```text
范围线 = min(模型字段 M, 90% × W)      # 软触发（可被更低字段按下）
整段线 = W × 95%                        # 硬检查
到线   = (A ≥ 范围线+缓冲) 或 (A ≥ 整段线)
```
- **证据（新快照）**：`B1` `protocol/src/openai_models.rs` L518–527；`B2` 同文件 L529–540；`B4/B5` `core/src/session/context_window.rs` L60–110；`B6` `context/history.rs` L922–960；`B11` `state/auto_compact_window.rs` L38–43、L105–141。
- **新旧对照**：`core/src/session/context_window.rs`（130 行）、`protocol/src/openai_models.rs`、`state/auto_compact_window.rs` **三者逐字节相同** → **B1/B2/B3/B4/B5 在新快照逐字成立**（C-01/C-02 的 Codex 裁决无需改）。

### 2.2 轮前（PreTurn）

- **条件**：新输入写入**之前**检查（不估算即将输入）。
- **处理**：到线则先整理再发请求。新快照此处外加门控 `auto_compaction_enabled`（见 §2.4 与 §5）。
- **证据**：`B7` `core/src/session/turn.rs` L180–184（基线与新快照语义一致）。

### 2.3 轮中（MidTurn）/ 轮后（PostTurn）

- **轮中**：`needs_follow_up && (new_window_request || token_limit_reached)`，成功后 `continue` 工作循环。新快照把该条件包在 `auto_compaction_enabled` 下，并**新增** `candidate.is_some()` 触发项（后台压缩就绪）。
- **轮后**：`q>0 且（到线 或 A×100≥H×q）`、无待处理输入、未取消、非 TokenBudget；失败只记 warn 保留回答。
- **证据**：`B8` `core/src/session/turn.rs` L548–575、L609–654（基线）→ 新快照对应 L607–673；`B9` 同文件 L718–757、`config/mod.rs` L4355–4357（q 缺省 0）。
- **新旧对照**：**轮中触发条件有实质扩展**（新增后台压缩候选通道 + 门控），见 §5 与 `问题与审查.md` §1。

### 2.4 【新快照新增】后台 / 投机压缩（AsyncCompaction）

- **调用者**：`core/src/session/turn.rs` 在 PreTurn/MidTurn/PostTurn 检查点调 `async_compaction::maybe_start`。
- **条件（`session/async_compaction.rs` `enabled`）**：`Feature::AsyncCompaction` 开 **且** 未启用 TokenBudget **且** provider 的 `remote_compaction == V2`。阈值：`A×100 ≥ W全窗 × async_compaction_threshold_percent`（**默认 65**）。
- **处理**：在后台 `spawn` 一个**投机**压缩请求，产出 `BackgroundCompactionCandidate`；后续检查点用 `take_ready` 取回，**仅当** `candidate.prefix.generation == 当前 history_version` 才采用（历史被替换则作废）；也可由前台 `wait_for_pending` 等待。
- **失败/副作用**：**丢弃的请求仍计入已发生用量**（注释原文 "Discarded requests still charge completed usage"）；`shutdown` 取消残余网络任务并等待用量结算。
- **实现状态**：**`Stage::UnderDevelopment`，`default_enabled=false`** → 属「有条件实现（默认关、开发中）」，**不能写成默认行为**。
- **证据**：`session/async_compaction.rs` L40–142（阈值实算 L74–78）；`features/src/lib.rs` L2066–2070；`config/mod.rs` L225（默认 65）、L3316–3328（校验 1..=100）；`features/src/feature_configs.rs` L574–582。
- **新旧对照**：`session/async_compaction.rs` **为新快照新增文件**，旧快照不存在 → 这是**新快照相对基线唯一新增的压缩触发支路**。

## 3. 工具结果链路（单条输出治理）

- **调用者**：工具执行完成后，写回消息列表之前。
- **条件/处理**：大输出在**进入消息列表前**限长；超出阈值时**落盘**、请求里只留**预览**头部；同一请求内多块输出**共享预算**；序列化另留余量（×1.2）；图片直通、音频单独计费。
- **写回**：限长/裁剪后的结果写进消息列表，成为下一次请求的一部分；**全量原文**另行落盘。
- **找回原文**：落盘文件是被裁内容的读取入口；活动历史裁剪只作用于 live 副本，rollout 保存**未裁剪原载荷**。
- **证据**：`C7` `utils/string/src/truncate.rs` L4、L62–183（基线）→ 新快照 L17–100；`C8` `utils/output-truncation/src/lib.rs` L23–34；`C9` 同文件 L17–21、L164–251；`C10` `core/src/context_manager/history.rs` L517–576；`C11` `rollout/src/policy.rs` L16–19（分片输出与 MCP 结果各 **64 KiB 字节**，注意与 64K token 不同）。
- **新旧对照**：`utils/output-truncation/src/lib.rs`、`rollout/src/policy.rs` **逐字节相同** → C8/C9/C11 两快照均成立。`truncate.rs` 被**重构**（见 §5），语义等价，C7 的 `ceil(bytes/4)` 与「左 floor、右=总数−左」仍成立。

## 4. 持久化 / 恢复链路

### 4.1 保存（压缩完成 → 写盘）

- **调用者**：压缩流程成功后（`core/src/session/mod.rs` 检查点写入段）。
- **处理**：① 用替代历史**替换内存历史**；② 构造 `CompactedItem` 检查点（含 `replacement_history`、window id、`latest_token_usage_record`、`resume_metadata`）；③ 追加写入 rollout 数组并 `persist_rollout_items`。
- **失败分支**：PostTurn 摘要仅在成功后提交；失败必须**同时保持 live 历史与已持久化 rollout 不变**（新快照把「逐条提交」改为「成功后一次性提交」，见 §5）。
- **状态写回**：存档**追加、不删旧记录**（旧记录物理保留在 rollout 里）。
- **证据**：`D1` `core/src/session/mod.rs` L4181–4222（基线）→ 新快照 L4321–4376；`D2` 同文件 L4156–4180（整理期间新更新的持久化锁与按序补入）。
- **新旧对照**：`CompactedItem` 结构字段**两快照相同**（新快照仅在同一函数上下文中拆分了 `started_item` 的发送时机）；D1/D2 均成立。

### 4.2 恢复（重启 → 采用替代历史 + 后缀回放）

- **调用者**：`codex resume` / 应用启动重建历史时。
- **处理**：读回最新检查点的 `replacement_history`，在其**之后**回放后续记录条目（ResponseItem→replay、RetainedContext、InterAgentCommunication 等）。
- **能否找回原文**：能——旧记录仍在 rollout 存档里，属「摘要不可逆 ≠ 源记录删除」（裁决 C-03/C-12）。
- **证据**：`D3` `core/src/session/rollout_reconstruction.rs` L492–515。
- **新旧对照**：`rollout_reconstruction.rs`（655 行）**逐字节相同** → D3 在新快照逐字成立。故 LQ-10 对 Codex 的结论（**走「持久化断点 + 后缀回放」而非纯重放历史**）两快照一致。

### 4.3 手动 `/compact`

- **调用者**：用户输入 `/compact [附加说明]`。
- **条件/分流**：TokenBudget 分支分流；V2 → 远端任务；Unsupported → 本地任务，输入 `compact_prompt || SUMMARIZATION_PROMPT`。
- **证据**：`D7` `core/src/tasks/compact.rs` L29–110；`D8` `prompts/templates/compact/prompt.md` L1–9。
- **新旧对照**：`tasks/compact.rs`（111 行）与 `prompts/templates/compact/prompt.md` **均逐字节相同** → D7/D8 成立。

## 5. 缓存链路（CLI 侧可证部分）

- **调用者**：每次 Responses 请求构造处。
- **处理（CLI 发什么）**：请求携带 `prompt_cache_key`——默认 = `session_id`；内部子会话 = `{source}:{parent_thread_id}`；可选 `prompt_cache_key_override` 覆盖。
- **处理（CLI 认什么）**：响应 usage 解析 `input_tokens_details.cached_tokens / cache_write_tokens` → `TokenUsage.cached_input_tokens / cache_write_input_tokens`。
- **写回/下一次**：计数变更检测含 `prompt_cache_key_changed` 分支，用于 websocket 增量复用判定。
- **中文解读**：CLI **只负责“发键”和“认明细”**；命中与否、TTL、断点规则由服务端决定——源码读不出。
- **证据**：`E3` `core/src/client.rs` L646–658（基线 L641–653）、L1060（基线 L1049）；`E4` `codex-api/src/sse/responses.rs` L117–151、`protocol/src/protocol.rs` L2362–2382；`E5` `core/src/client.rs` L448–449。
- **新旧对照**：`client.rs` 有重构（提取 `ResponsesHttpExecutor`、新增非 RLite 清空 `content_item_metadata`），但 `prompt_cache_key` 函数体与新老一致 → `E3/E4/E5` 两快照均成立。详见 §6。

## 6. 【新快照变化】压缩内容来源标注（context fragments）

- **调用者**：`core/src/compact.rs` 在重建替代历史、需要截短单条用户消息时。
- **处理（变化点）**：基线用 `truncate_text(&message.message, TruncationPolicy::Tokens(remaining))` 生成纯文本回退；新快照改用 `codex_context_fragments` 的 `set_annotated_content` + `truncate_annotated_text`，**按同一来源下标选择文本与其标注**，不克隆被丢弃的图片/音频、不臆测其文本来源。
- **协议面**：`protocol/src/models.rs` 新增 `ContentItemMetadata / ContentItemProvenance / ContentItemNamespace` 与 `content_item_metadata` 字段，以及 `clear_content_item_metadata`。
- **客户端面**：`core/src/client.rs` 新增「非 RLite 端点清空 per-content attribution」（`if !model_info.use_responses_lite { clear_content_item_metadata() }`）。
- **状态写回**：标注进入 `ResponseItem::Message` 的 passthrough 元数据，随请求发送（仅 RLite 端点接受）。
- **证据**：`core/src/compact.rs` L757–789（新）；`protocol/src/models.rs` L992–997、L1514–1528（新）；`core/src/client.rs` L1007–1012（新）。
- **新旧对照（关键）**：属**新快照新增**的内容保真机制；对教学的影响是「被裁的内容其来源标注现在可保留」——属细节增强，**不改变** §3 的限长主结论。
