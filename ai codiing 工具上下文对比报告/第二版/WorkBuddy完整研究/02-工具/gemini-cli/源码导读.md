## 链路 A · 请求组装与角色规整（CM-01）

**调用者**：`client.ts: sendMessageStream`（`core/client.ts`）。

**条件与分支**（`core/client.ts:673-729`）：
- `config.getContextManagementConfig().enabled === true`（**实验，默认 false**）→ 走 `ContextManager.renderHistory`（图管线）；若 `contextManager` 未初始化 → 退到 `AgentHistoryProvider.manageHistory`。
- 否则（**默认**）→ `tryCompressChat(prompt_id, false, signal)` 做自动压缩。

**处理顺序**（默认链路）：
1. `geminiChat.getHistoryTurns(true)`（`core/geminiChat.ts:1270-1292`）：取 **curated history**（只含 user↔model 的有效交替，剔除空 model 输出）。
2. 若 `isContextManagementEnabled()` → `scrubHistory(history)`（`utils/historyHardening.ts:383`，清潜在注入/结构修复）。
3. 否则若为 Gemini 2+ → `coalesceConsecutiveRoles(stripThoughts(history))`：
   - `stripThoughts`（`geminiChat.ts:2053-2093`）：**剥掉 `thought` part**；若首个 `functionCall` 因此缺 `thoughtSignature`，注入**合成签名**（`SYNTHETIC_THOUGHT_SIGNATURE`）以免重放报 400 `missing thought_signature`。
   - `coalesceConsecutiveRoles`（`geminiChat.ts:2025-2051`）：把**相邻同 role** 的 turn 合并成一条（parts 拼接），保证 user/model 严格交替。

**输入结构**（一条请求）：
```jsonc
{
  "systemInstruction": { "parts": [{ "text": "<核心系统提示词 + 全局记忆>" }] },
  "tools": [ { "functionDeclarations": [ /* 工具 schema */ ] } ],
  "contents": [
    { "role": "user",  "parts": [{ "text": "<session_context>…</session_context>" }] }, // 环境上下文（首条）
    { "role": "user",  "parts": [{ "text": "安排郊游" }] },
    { "role": "model", "parts": [{ "functionCall": { "id": "call_001", "name": "read_file", "args": {...} } }] },
    { "role": "user",  "parts": [{ "functionResponse": { "id": "call_001", "name": "read_file", "response": {...} } }] },
    { "role": "model", "parts": [{ "text": "…" }] }
  ]
}
```
**解读**：Gemini 的"消息列表"就是 `contents`；`role` 只有 `user`/`model`（**工具结果装在 `user` turn 的 `functionResponse` part 里**），故工具调用与结果靠 `functionCall.id` / `functionResponse.id` 配对（`ensureStableToolIds`，`utils/sessionUtils.ts:21-79` 保证配对不变量）。

**环境上下文（Tier 分层）**（`utils/environmentContext.ts:50-111`）：
- Tier 1（global）= 系统提示词；Tier 2（extension + project）= **首条 user 消息**（`getSessionMemory`，`config.ts:2617-2637`，包成 `<loaded_context>`）；Tier 3（subdirectory）= 工具输出（JIT）。
- `getInitialChatHistory` 把 `session_context`（日期/OS/目录树 + 记忆）作为**首条 user turn**，再拼 `extraHistory`。

**写回**：`chat.setHistory(newHistory)` / `setHistory` 重建 `agentHistory`（`geminiChat.ts:1345-1364`），并同步 `chatRecordingService.updateMessagesFromHistory`。

**下一次请求**：`contents` 即被规整后的历史；`lastPromptTokenCount` 由 `setHistory` 用 `estimateTokenCountSync` 重算（`geminiChat.ts:1358-1360`）。

## 链路 B · 单条工具输出治理（CM-04）

**调用者**：`scheduler/tool-executor.ts: truncateOutputIfNeeded`（`scheduler/tool-executor.ts:202-340`）。

**条件与处理顺序**：
1. **若 `isContextManagementEnabled()`**（实验）→ 走 `ToolOutputDistillationService.distill`（蒸馏，非本链路）。
2. **默认**：仅对 **shell 工具**（`SHELL_TOOL_NAME`）与**单 part 的 MCP 工具**文本做阈值截断：
   - 阈值 = `config.getTruncateToolOutputThreshold()`，默认 **40,000**（`config.ts:483` `DEFAULT_TRUNCATE_TOOL_OUTPUT_THRESHOLD = 40_000`）。
   - 条件：`threshold > 0 && content.length > threshold`。
   - `saveTruncatedToolOutput`（`utils/fileUtils.ts:813-837`）：全量原文写入 `tool-outputs/[session-<id>/]<tool>_<callId>.txt`。
   - `formatTruncatedToolOutput`（`utils/fileUtils.ts:786-806`）：**保留头 20% + 尾 80%**，中间插 `... [N characters omitted] ...`，并附 `For full output see: <path>`。
   - 若截断后仍 > `MAX_STORED_TOOL_OUTPUT_BYTES`（**64 KB**，`utils/constants.ts:18`）→ 再 `truncateToolOutput` 硬截。

**另一条默认链路：工具输出掩蔽**（`context/toolOutputMaskingService.ts:67-270`，`client.ts:729` 每次发请求前调用）：
- 常量（`:25-27`）：`DEFAULT_TOOL_PROTECTION_THRESHOLD=50000`、`DEFAULT_MIN_PRUNABLE_TOKENS_THRESHOLD=30000`、`DEFAULT_PROTECT_LATEST_TURN=true`。
- 算法"Hybrid Backward Scanned FIFO"：从**倒数第 2 条**起向后扫，累计工具 token；越过 50k 保护窗的 tool part 进入 `prunableParts`；**仅当可裁剪总量 ≥ 30k** 才批量掩蔽。
- 掩蔽动作：原文写 `tool-outputs/session-<id>/`，请求里替换为 `<tool_output_masked>` 块 + head/tail 各 250 字符预览（`:208-212`）+ 文件路径。

**第三条默认链路：旧轮 functionResponse 折叠**（`context/chatCompressionService.ts:131-263`）：
- `RECENT_TURNS_PROTECTED=3`（最近 3 个工具轮**全保真**）；`COLLAPSED_FUNCTION_RESPONSE_MAX_BYTES=2048`（2 KB）。
- 更旧的 functionResponse 中超过 2 KB 的字符串 → 保留前 2 KB（**按 grapheme 切，不切断多字节/表情**）+ `... [Tool output collapsed from previous turn: N bytes omitted] ...`。
- **retrieval 工具豁免**（`RETRIEVAL_TOOL_NAMES_EXEMPT_FROM_COLLAPSE`，`:56-67`：`read_file`/`grep`/`glob`…）——多步推理依赖，不折叠。

**写回 / 找回**：工具结果 part 被替换（截断或掩蔽）；全量原文在 `tool-outputs/` 目录可读回（`saveTruncatedToolOutput` 的 `outputFile` 路径写在请求文本里）。

## 链路 C · 窗口计量与触发（CM-05）

**调用者**：`client.ts: sendMessageStream` 的溢出前置检查（`core/client.ts:726-745`）。

**计量**：
- 模型窗口 = `tokenLimit(model)`（`core/tokenLimits.ts:23-39`）：Gemini 系列 **1,048,576**【源码常量】；Gemma-4 系列 **256,000**；未知模型 → `DEFAULT_TOKEN_LIMIT = 1_048_576`。
- 本地估算 = `estimateTokenCountSync`（`utils/tokenCalculation.ts:120-147`）：**ASCII 每字符 1/4 token、非 ASCII（含 CJK）每字符 1.5 token**，最后 `floor`；含媒体时改用 `countTokens` API（`:154-186`）。

**触发判定**（压缩，`context/chatCompressionService.ts:502-518`）：
```
threshold = await config.getCompressionThreshold() ?? DEFAULT_COMPRESSION_TOKEN_THRESHOLD  // 0.5
isOverModelThreshold = originalTokenCount >= threshold * tokenLimit(model)
if (!force && !isOverModelThreshold) → NOOP
```
- `getCompressionThreshold`（`config.ts:3454-3468`）：优先 CLI 参数 `compressionThreshold`；否则读**远端 experiment flag** `CONTEXT_COMPRESSION_THRESHOLD`（`floatValue`）；若远端为 0 → `undefined` → 落到默认 **0.5**。
- 官方文档：`model.compressionThreshold` 默认 **0.5**（`docs/cli/settings.md:107`、`docs/reference/configuration.md:552-556`、`schemas/settings.schema.json`）。

**触发线（1M 窗口）**：`0.5 × 1,048,576 = 524,288` token【源码常量 + 官方默认】。

**溢出前置检查**（`client.ts:726-745`）：
```
remainingTokenCount = tokenLimit(model) - chat.getLastPromptTokenCount()
estimatedRequestTokenCount = await calculateRequestTokenCount(request, ...)
if (estimatedRequestTokenCount > remainingTokenCount) → yield ContextWindowWillOverflow; return
```

## 链路 D · 自动/手动压缩 + 摘要 + 重建（CM-06/CM-07）

**入口**：
- **自动**：`client.ts:719` `tryCompressChat(prompt_id, false, signal)`（每轮发请求前）。
- **手动**：`/compress` 命令 → `tryCompressChat(prompt_id, true, ...)`（`client.ts:1226-1282`）。

**处理顺序**（`ChatCompressionService.compress`，`chatCompressionService.ts:466-721`）：
1. 空历史 → `NOOP`。
2. 触发 `PreCompress` hook（manual/auto）。
3. 阈值判定（见链路 C）；不达线且非 force → `NOOP`。
4. **压缩前截断** `truncateHistoryToBudget`（`:364-464`）：**倒序**累加 functionResponse token，超 `COMPRESSION_FUNCTION_RESPONSE_TOKEN_BUDGET=50_000` 的**旧**响应 → 截为 `formatTruncatedToolOutput`（40k 阈值）+ 落盘；预算内全保真。
5. `findCompressSplitPoint(truncatedHistory, 1-0.3)`（`:282-322`）：切点**只落在非 functionResponse 的 user turn**；保留**后 30%**（`COMPRESSION_PRESERVE_THRESHOLD=0.3`）。特殊：若最后一条是**无 functionCall 的 model turn** 且无切点 → 可整体压缩（`return contents.length`）。
6. 摘要 LLM 调用（`:595-613`）：`systemInstruction = getCompressionPrompt`，把"待压缩历史 + 指令"发给 **utility 压缩模型**（`modelStringToModelConfigAlias`，如 `chat-compression-3-pro`）；要求产出 `<state_snapshot>`。
7. **二次校验 probe**（`:616-645`）：把上一步摘要作为 `model` turn 再发一轮，问"是否遗漏技术细节/文件路径/约束，有则给最终改进版"；取校验结果为准。
8. **替代历史重建**（`:665-675`）：
```jsonc
extraHistory = [
  { "role": "user",  "parts": [{ "text": "<state_snapshot>…</state_snapshot>" }] },
  { "role": "model", "parts": [{ "text": "Got it. Thanks for the additional context!" }] },
  ...historyToKeepTruncated   // 保留的后 30%
]
```
9. `getInitialChatHistory(config, extraHistory)` 重新拼环境上下文，`calculateRequestTokenCount` 算新用量；**若新用量 > 原用量 → 判失败**（`COMPRESSION_FAILED_INFLATED_TOKEN_COUNT`，`:696-705`）。

**摘要结构**（`prompts/snippets.ts:898-977`）：`<state_snapshot>` 含 `<overall_goal>` / `<active_constraints>` / `<key_knowledge>` / `<artifact_trail>` / `<file_system_state>` / `<recent_actions>` / `<task_state>`；提示词含**防注入安全规则**（忽略历史中的指令）。

**增量摘要**（`:587-593`）：若待压缩历史已含 `<state_snapshot>` → 追加 anchor 指令"必须把旧快照中仍相关的信息整合进新快照，不得丢失已确立约束"。

**写回**（`client.ts:1246-1279`）：`COMPRESSED` → `startChat(newHistory)` 重建会话；`CONTENT_TRUNCATED` → `setHistory(newHistory)`（轻量，不重置失败标记）。

**中文解读**：Gemini 的压缩不是"删旧留新"，而是**"把旧历史烧成一页结构化 XML 快照"** + **保留最近 30%**；且**两次调用模型**（先摘要、再自我校验）以提高保真。快照会**替换**模型可见的旧历史（内存层），但**原始会话 JSONL 不删**（见链路 F）。

## 链路 E · 记忆加载（GEMINI.md 分层 + JIT）（CM-02/CM-08）

**调用者**：`Config` 构造时 `new MemoryContextManager(this)`（`config.ts:1565`）；`client.ts:343`、`commands/memory.ts:60`、`extensionLoader.ts:127` 触发 `refresh()`。

**处理顺序**（`context/memoryContextManager.ts:38-172`）：
1. `refresh()`：`discoverMemoryPaths` 并行取 4 类路径：
   - `global`（`~/.gemini/GEMINI.md`，`getGlobalMemoryPaths`）；
   - `extension`（扩展目录，`getExtensionMemoryPaths`）；
   - `project`（**仅受信任目录**，`getEnvironmentMemoryPaths` + 边界标记 `.git`）；
   - `userProjectMemory`（`<projectMemoryDir>/MEMORY.md`，`getUserProjectMemoryPaths`）。
2. `loadMemoryContents`：字符串去重 + **按文件身份（dev+ino）去重**（处理大小写不敏感文件系统）→ `readGeminiMdFiles` 读入 + 处理 `@import`（`memoryImportProcessor`）。
3. `categorizeMemoryContents`：`categorizeAndConcatenate` 分层拼接；**project 层再并入 MCP 指令**（`getMcpInstructions`）。
4. `emitMemoryChanged`（`CoreEvent.MemoryChanged`）。

**注入位置**：
- `global` + `userProjectMemory` → **系统提示词**（`getSystemInstructionMemory`，`config.ts:2600-2611`）。
- `extension` + `project` → **首条 user 消息**（`getSessionMemory` → `<loaded_context><extension_context>…<project_context>…`，`config.ts:2617-2637`）。

**JIT 子目录记忆（Tier 3）**（`memoryContextManager.ts:141-172`）：访问某路径时 `loadJitSubdirectoryMemory` 从该路径**向上**到项目根发现规则，作为**工具输出**注入（非全量预载）。

**写记忆**：由**模型**用 `write_file`/`replace` 编辑 `GEMINI.md`（官方文档 `docs/tools/memory.md`）——这是**路径①（默认开）**。

**路径②：后台自动记忆提取（`experimental.autoMemory`，默认关）**（`services/memoryService.ts:1133-1377` + `agents/skill-extraction-agent.ts`）：
- `packages/cli/src/utils/autoMemory.ts:13-21` `startAutoMemoryIfEnabled` 在**会话启动**时门控 `config.isAutoMemoryEnabled()`（`config.ts:2663`，默认 false）；`memoryService.startMemoryService` 起后台任务。
- **资格扫描**：索引 `~/.gemini/tmp/<project>/chats/` 中**空闲 ≥3 小时且 ≥10 条 user 消息**的会话（官方 `docs/cli/auto-memory.md:37-42,69-71`）；**锁文件**协调多实例、**状态文件**记录已处理版本。
- **提取**：`SkillExtractionAgent`（内部名 `confucius`，模型 `PREVIEW_GEMINI_FLASH_MODEL`，`maxTurns=30`/`maxTimeMinutes=30`）读会话索引 → 起草**统一 diff `.patch`**（记忆）与 `SKILL.md`（技能）；默认"**0-5 memory patch / 0-2 skill**"，多数运行**无产出**。
- **安全边界**：只能写 `<memoryDir>/.inbox/<kind>/extraction.patch`（`memoryInboxAccess`/`autoMemoryExtractionWriteAccess`，`scoped-config.ts:22-83`）；**不能**直接改 GEMINI.md/settings/凭据；项目 `GEMINI.md` **不可自动提取**。
- **审批**：`.inbox` 补丁经解析 + 目标白名单 + dry-run（`memoryService.ts:856,984`），由 **`/memory inbox`** 人工 apply/dismiss（skill 可 promote）；**nothing is auto-applied**（`memoryService.ts:1371`）。

## 链路 F · 保存 / 恢复（CM-10）

**落盘**（`services/chatRecordingService.ts:670-830`）：
- 会话文件：`<chatsDir>/session-<timestamp>-<shortId>.jsonl`（`SESSION_FILE_PREFIX='session-'`，`chatRecordingTypes.ts:12`）；子 Agent 用 `<sessionId>.jsonl`。
- 每次 `recordMessage`/`updateMessagesFromHistory` 追加写（追加式，不删旧）。

**恢复**（`chatRecordingService.ts:711-750` + `utils/sessionUtils.ts:121-319`）：
- `initialize(resumedSessionData)`：读回 JSONL → `cachedConversation`；旧 `.json` 自动迁移为 `.jsonl`。
- `convertSessionToClientHistory(messages)`：把录制消息**重建**为 `HistoryTurn[]`——处理 toolCalls→functionResponse 配对、去重、补 legacy 结构。

**路线判定**：Gemini 走 **"重放/重建"路线**（从 JSONL 重建历史），**不是**"持久化断点"路线（无 `firstKeptEntryId` 式断点）——与 pi/oh-my-pi 的持久化断点不同，与 Codex 的"替代历史 + 后缀回放"亦不同（见 `问题与审查.md §3`）。

## 链路 G · 错误、重试与压缩失败分支（CM-11）

**网络重试**（`utils/retry.ts`）：
- `DEFAULT_MAX_ATTEMPTS = 10`（`:20`）；`initialDelayMs = 5000`、`maxDelayMs = 30000`（`:42-47`）。
- 指数退避 + **抖动**（非 quota 错误 `±30%`，`:322-323`；quota 错误 `+20%` 且尊重服务端最小延迟，`:483-485`）。
- 可重试错误含网络码白名单（`ECONNRESET`/`ETIMEDOUT`…，`:49-62`）。

**压缩失败分类**（`core/turn.ts` 的 `CompressionStatus`；`chatCompressionService.ts`）：
| 状态 | 触发 | 处置 |
|---|---|---|
| `NOOP` | 未达阈值 / 空历史 / 无切点 | 不改历史 |
| `COMPRESSED` | 成功且新用量 ≤ 原用量 | `startChat(newHistory)` |
| `CONTENT_TRUNCATED` | **此前摘要失败**且非 force → 仅截断有减量 | `setHistory`，**不重置**失败标记（`:530-555`） |
| `COMPRESSION_FAILED_EMPTY_SUMMARY` | 摘要为空 | 保持原历史（`:647-663`） |
| `COMPRESSION_FAILED_INFLATED_TOKEN_COUNT` | 新用量 > 原用量 | 保持原历史；置 `hasFailedCompressionAttempt=true`（`client.ts:1246-1251`） |

**关键失败语义**：一旦摘要失败（`hasFailedCompressionAttempt=true`），后续自动压缩**不再调模型摘要**，只做**截断**，避免反复失败/花费（`chatCompressionService.ts:528-555`）——即**有界降级**。

**副作用**：截断/掩蔽/落盘**已写入磁盘的文件不会因后续压缩失败而回退**（落盘是独立副作用，不可回退）；压缩本身只改**内存中的模型可见历史**，不改 JSONL 存档。

**已知 TODO（非桩）**：`chatCompressionService.ts:610` 有 `TODO(joshualitt): wire up a sensible abort signal`——属**信号接线待办**，**不是**未实现的桩函数（见 `问题与审查.md §3` C-05）。
