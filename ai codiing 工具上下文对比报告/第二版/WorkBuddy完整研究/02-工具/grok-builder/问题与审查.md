## 3. 旧结论 / 冲突裁决（逐条）

| ID | 旧表述 | Grok 侧裁决 | 依据 |
|---|---|---|---|
| **C-01/C-02** | 触发阈值「90%–95%」总括句 | **否证（Grok 侧）**：Grok 默认 **85%**（`auto_compact_threshold_percent`），非 90–95%；支持"各家不同、须逐工具核" | `grok-trigger-02` |
| **C-03/C-12** | "压缩不可逆 / 恢复找不回" | **支持"两事实并存"**：压缩改**模型可见层**（替代历史 + checkpoint）；磁盘 `updates.jsonl` **追加不删**，`grok export`/`grok usage` 可取回；"找不回"限制为**模型可见层** | `grok-persist-01`、`grok-summary-01` |
| **C-04** | "旧摘要只做字符串级 merge"（无损暗示） | **未决**：Grok 有 `compaction_mode`(summary/transcript/segments) + `compaction_detail` 逐字层级，但保真度**未实测**（依赖 T19/LQ-09） | `grok-summary-03` |
| **C-05** | 桩函数被当作已实现能力 | **Grok 侧不适用**：闭源二进制，无"桩函数"可观测；文档描述的机制均有配置键/目录/事件佐证 | 本包无"源码级桩"概念（U-01） |
| **C-06** | `len(text)//4` 对中文"保守" | **不适用（范围限定）**：在 **Grok 随包文档与配置字段（1.0.50/1.0.52 两版）内未见** `chars/4` 式 token 估算；Grok 只给**字节**口径（bash 65536 字节）与**字符**口径（剪枝 4000 字符）。**推断**（非"全仓零命中"——闭源无源码可检索）；不得把 Claude/Codex 的 `//4` 套到 Grok | `grok-toolout-01/03` |
| **C-07** | "零 API 调用的压缩" | **不支持**：压缩是一次**独立 side-model 调用**（`usage` 明说"Compaction and other side-model calls are excluded"，即**存在**该调用）；记忆后台复盘亦有模型开销（`daily_token_cap` 默认 20,000,000） | `grok-compact-03`、`grok-memory-03` |
| **C-08** | Gemini "大窗口不压缩" | **Grok 侧对照**：Grok **有**压缩且默认 85% 触发——非"大窗口不压缩" | `grok-trigger-02`、`grok-compact-01` |
| **C-10** | 多层管道说法（层数非维度） | **支持"层数不是维度"**：Grok 的"缩短"= **剪枝层 + 摘要层**（两性质，非层叠管道）；不按层数比较成熟度 | `grok-summary-02` |
| **LQ-04** | L1 是否保留源文？工具输出原文存哪？ | **保留**：会话 `updates.jsonl`/`chat_history.jsonl` 追加不删；剪枝/摘要只改**模型可见层** | `grok-persist-01`、`grok-toolout-03` |
| **LQ-05** | 三家压缩阈值全表 | **Grok 侧给出**：触发线 = `auto_compact_threshold_percent`（默认 85%）× `context_window`；500,000→425,000 tokens（演示）；另有绝对阈值 `compaction_at_tokens` | `grok-trigger-02` |
| **LQ-08** | 后台持续抽取会话记忆 | **有条件成立**：Grok **有**"每轮后台复盘写观察"，但为**默认关**的实验特性（`memory.enabled=false`） | `grok-memory-03/04` |
| **LQ-09** | 压缩后再次触发如何处理 | **结构性可答**：再次触发继续压缩；`compactions_remaining` 控制"压缩剩余上下文如何发送"；**失真未决**（待 T19） | `grok-compact-03`、`grok-summary-03` |
| **LQ-10** | resume 两条路线 | **Grok = 重放/重建路线**（`updates.jsonl` 是驱动 `/resume` 与恢复的权威日志）；`/rewind` 只截断对话 | `grok-recover-01` |
| **LQ-11** | 硬上限/两笔钱 | **Grok 侧不适用该三分法（范围限定）**：Grok 用"百分比阈值 + 绝对 `compaction_at_tokens`"两口径；**在随包文档/配置字段内未见**"有效窗口−常数"式三分法（**推断**，闭源无源码可检索） | `grok-trigger-02` |

## 5. 客户端 vs 服务分层（结论）

见 `工具概览.md §3`（16 行逐条分列）。**结论**：Grok Build 的上下文机制**绝大部分 CLI 侧可观测**（组装、规则/技能发现、限长、剪枝、触发判定、落盘、记忆捕获、恢复、重试）；**服务端仅承担**摘要执行、真实计量与**全部 prompt cache 行为**（不可观测）。**分界清晰**，无"同源难判定"问题（与 OpenCode v1/v2 的"同源≠零耦合"不同）。

### 9.5 T13（deepseek-harness）可复用经验
1. **版本漂移必登记**：若工具**默认自动升级**（如 Grok `auto_update` 默认开），观测期间二进制可能被替换——须在会话起始与观测点各取一次版本自报，并用**冻结件 + 独立 HOME**离线复现旧版自带文档。
2. **随分发件携带官方文档 = 高价值一级证据**：优先查 `README`/`docs/` 提取物（本包 `26-config-reference.md` 是完整字段表）；用**逐文件 diff** 定位版本差异，只把与目标机制相关者计入结论。
3. **内部文档冲突要登记而非裁决**：同一官方文档集可能自相矛盾（本包 `/rewind`、规则文件大小、`respect_gitignore` 三处）；按冲突表纪律**标未决/版本差异**，不挑"更自信的一段"。
4. **闭源工具要分清"字节/字符/token"三单位**：Grok 用**字节**（bash 65536）与**字符**（剪枝 4000）两种口径；**在随包文档/配置字段内未见** token 估算公式（**推断**，非"全仓零命中"）——**不得**把其他工具的 `chars/4` 套过来。
