## 1. 五个重点问题（按任务卡优先级）

### 问题 1｜触发预算条件口径（对 167K/83.5% 的裁决）

**裁决：分三层，部分成立 + 公式未决。**

| 主张 | 裁决 | 依据 |
|---|---|---|
| "Claude 有'窗口'口径与'触发'口径两件事" | ✅ **成立** | claude-trigger-01（窗口 4 入口，100K–1M）、claude-trigger-02（触发按窗口百分比） |
| "触发是按窗口百分比" | ✅ **成立** | `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` ∈ [1,100]，"低于默认才生效、高于默认被忽略"【①env-vars】 |
| "默认在 90%–95% 压缩"（C-01 总括句） | ❌ **否证** | 文档默认口径是"达到模型上下文上限"；例外为 200K 边界或 ≈967K（对 1M ≈96.7%）【①model-config】 |
| "≈167K" | ⚠️ **部分成立** | 官方 sub-agents 文档出现**示例** `preTokens:167189`（≈83.6% of 200K）【①官方示例】。**不是**默认阈值 |
| "83.5% 是默认触发比例" | ⚠️ **未决** | 文档只给可覆盖区间 1–100，**未给默认比例**；83.59% 是由示例值**反算** |
| "有效窗口 = 原始窗口 − 20,000；触发线 = 有效窗口 − 13,000 = 167K；硬上限 = −3,000 = 177K" | ⚠️ **未决（U-01）** | 三个常量名/公式在**官方文档与可合法观察的分发件中均无出处**；与 `claude-ds`（针对 v2.1.88）一致，疑为对反混淆产物的读数。**本轮未下载平台二进制、未做任何逆向**，故**既不证实也不否证** |
| "熔断：连续失败 3 次" | ⚠️ **限制** | 机制成立（thrashing 时停止重试）；**数字"3 次"无一级出处**（文档用 "several times"/"a few attempts"） |

**给课程的写法**：写"Claude Code 的压缩触发由**窗口**（可配 100K–1M）与**窗口百分比**共同决定，默认在模型上下文上限附近触发，可用 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` **调低**提前触发"；**不要**写"默认 167K/83.5%"，如需给具体数，标为"某次观测/官方示例值"。→ 支持 冲突表 C-01/C-02 **Claude 部分转"部分裁决"**。

### 问题 2｜工具输出落盘/清理（对"保头 2KB + 全量落盘"的核验）

**裁决：基本成立，四点修正。**

| 旧说法 | 裁决 | 修正 |
|---|---|---|
| "输出 >30k 字符" | ✅ 基本成立 | 默认内联约 **30,000 字符**（可经 `BASH_MAX_OUTPUT_LENGTH` 30,000/硬顶 150,000 或 `bashOutputMaxChars` ≤128,000 调整） |
| "保头 2KB 预览" | ⚠️ 修正 | 是"最多前 **2,000 字符**"（**字符**非字节，**非** token） |
| "全量落盘" | ⚠️ 修正 | 落盘**有 64 MiB 截断上限**；"全量"是近似 |
| （旧说法未提）失败路径 | ➕ 补充 | **失败结果**内联约 10,000 字符，超限只给**头尾摘录且无文件路径** → 不落盘 |
| （旧说法未提）清理 | ➕ 补充 | 落盘文件在 `projects/<project>/<session>/tool-results/`，随 `cleanupPeriodDays`（默认 30 天）删除 |

→ 涉及结论 claude-toolout-01/02/04；V-01。

### 问题 3｜记忆/恢复语义与"压缩不可逆 vs 物理保留"

**裁决：两个事实并存，不矛盾（与 Codex 部分同型）。**

- **压缩不可逆**（对"当前请求历史"）：压缩用摘要替换旧轮次；原工具输出与中间推理从当前历史**消失**；`/rewind` Summarize、`/compact`、自动压缩都属此类【①context-window】。
- **物理保留**（对磁盘）：**"Summarizing doesn't change files on disk, and the original messages stay in the session transcript"**【①checkpointing】；旧 transcript 以 `.superseded-*`/`.orphaned-*` **搁置保留**【①claude-directory】。
- **边界**：磁盘保留默认 **30 天**（`cleanupPeriodDays`），auto memory 目录不随清理删；checkpoint 快照保留最近 **100 个**。
- **对 C-12 的裁决**：学习笔记 §10 "resume 绝不可能找回"属**过度绝对化** → **限制**：应写"被压缩的内容**不会再逐字进入当前请求**；但在保留期内，原文仍在磁盘 transcript 中，可通过 `/rewind`、`/export`、直接读 `.jsonl` 或 `claude --resume` 查证"。
- **不支持的旧说法**：把"压缩不可逆"直接等同"源记录被删除"。

→ claude-resume-02/03/05、claude-compact-06；V-07。

### 问题 4｜缓存：客户端可观测 vs 服务端边界

**裁决：客户端可观测"计数与失效原因"，不可观测"实现与断点"。**

- **可观测**：`cache_read_input_tokens`、`cache_creation_input_tokens`、statusline `prompt_cache`、`/usage` 的 `Prompt cache (main)` 行与 likely-cause（v2.1.260+）、`usage.cache_creation.ephemeral_1h/5m_input_tokens`。
- **不可观测（U-03）**：KV 张量、前缀断点位置、服务端过期实现、跨组织隔离细节。
- **机制要点**：前缀精确匹配、无按文件/按段缓存；改 system prompt 层 → 全失效；压缩按设计失效对话层；摘要请求暖时复用缓存、冷时重处理全文；TTL 5 分钟/1 小时按"主对话/其它"两个请求桶分配。
- **代价**：缓存**不减体积**、不改文本；压缩/切模型/改 effort/加 MCP 等会带来一次"更慢更贵"的周转。

→ claude-cache-01…05；`证据导读.md §3` 客户端/服务端边界表。

### 问题 5｜连续摘要/"多层管道"（C-04/C-10）与"零 API 调用压缩"（C-07）

| 冲突 | 裁决 | 依据/原因 |
|---|---|---|
| **C-10 多层管道（"六层压缩/多层机制"）** | ⚠️ **不支持"六层"叙事；可证实的缩短层 = 2** | 官方明确两段式"先清较旧工具输出，再按需摘要"；其余（子代理隔离、`/clear`、`/rewind`）不是压缩层。**层数不是维度，不得按数量比较成熟度** → V-04 |
| **C-04 旧摘要只做字符串级 merge（无损暗示）** | ⚠️ **未决** | 官方只说摘要"替换旧轮次"、摘要请求"带同前缀 + 末尾指令"，**未描述**增量/字符串合并；单一片段不能裁决，需 T19 连续三次压缩实验 |
| **C-07 零 API 调用压缩** | ✅ **拆开裁决**：(a) 对话摘要/压缩**会新增一次模型调用**（"压缩大上下文本身就是一次大请求"）→ "零调用"**不成立**；(b) **服务端工具结果清除**在同一请求内由 API 应用、不新增调用 → 此处"零调用"**成立** | claude-compact-07（成本页原文）、claude-compact-08（API context editing）→ V-05 |
| **LQ-08 后台持续抽取会话记忆** | ⚠️ **文档未描述，不支持旧表述** | 官方只描述"会话中 Claude 读写记忆文件"+会话启动注入一次；最接近的是 memory tool 在接近清除阈值时的**自动提醒**。**文档不写 ≠ 不存在**，故标"未证实 + 文档未描述" → V-06 |
