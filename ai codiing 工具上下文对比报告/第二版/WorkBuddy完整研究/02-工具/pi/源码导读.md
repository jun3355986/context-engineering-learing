# pi · 源码导读

> 本文件解决什么问题：把 pi 的上下文管理**主链路**走一遍——**组装 → 预算 → 工具输出 → 整理 → 恢复 → 扩展点**，每条给出「调用者 → 条件 → 处理 → 状态写回 → 下一次请求/恢复」，并含**失败分支**与**核心片段中文解读**。
> 纪律：正式代码与教学伪代码分开标注；核心逻辑给中文解读，不只说"点链接看源码"。所有行号对快照 `b45e0eb`；链接基址见 frontmatter。
> 定位：`packages/coding-agent/src/core/` 是主战场；`packages/ai`、`packages/agent` 是更低层的 provider/agent 内核（本任务只按其被调用点引用）。

---

## 0. 主链路总览

```text
用户提交提示
   │
   ├─(A) 组装：buildSystemPromptSections() 生成具名 section 的系统消息
   │            + buildSessionProjection() 生成"规范化会话投影"(compaction 已应用)
   │            + 工具声明 tools          → prepareRequest 拼成一次模型请求
   │
   ├─(B) 预算：estimateProjectedContextTokens() 估当前用量
   │            shouldCompact(A > W − reserveTokens)?  → 触发整理
   │
   ├─ 模型流式回复（可能含 toolCall）
   │
   ├─(C) 工具输出：truncateHead/Tail(2000 行 / 50KB 先到者)；bash 超限落临时文件
   │            结果作为 toolResult 条目追加到会话
   │
   ├─(D) 整理（auto/manual）：findProjectedCutPoint() 找切点 → compact() 调 LLM 生成摘要
   │            → appendCompaction() 追加 CompactionEntry{summary, firstKeptEntryId, tokensBefore}
   │            → 投影重建（旧条目仍留在文件里，但不再进模型）
   │
   └─ 循环直到无 queued/工具结果
   │
(E) 恢复：SessionManager.open()/continueRecent() 读回 JSONL → 投影按最新 compaction 直接重建
(F) 扩展点：事件钩子改写请求/摘要/分支；资源注册增补工具/技能/provider
```

**一句话**：pi 把"历史"当作**可重建的投影**——磁盘上是**只追加的树**，模型看到的只是"当前分支 + 最新摘要 + `firstKeptEntryId` 之后"的投影。

## 1. 链路 A：请求组装与角色（CM-01 / CM-02）

### A1. 组装点：`_installAgentRequestProjection`（`core/agent-session.ts:788-845`）

**调用者**：agent 内核每次发请求前的 `prepareRequest` 钩子。
**处理**：取 `buildSessionProjection()` 得到的 `projection.messages` 作为**规范上下文**，配上 `tools: agent.state.tools.slice()`。

```ts
// agent-session.ts:793-800（节选）
const projection = this.sessionManager.buildSessionProjection();
const canonicalContext = {
  ...request.context,
  messages: projection.messages,                  // ← compaction 已应用的投影
  tools: this.agent.state.tools.slice(),          // ← 可执行工具实现
};
```

**中文解读**：pi **不直接把内存消息数组发出去**，而是先算一份"投影"。`projection.messages` 已经把 `compaction` 条目算进去了（见链路 E）。`messages` 声明 provider 可见的载荷，`context.tools` 保留可执行实现——两者分开，是为了让工具实现的元数据不进请求体。

**状态写回**：请求本身；不改会话。

### A2. 系统提示词：具名 section（`core/system-prompt.ts:128-193`）

**处理顺序**：`buildSystemPromptSections()` 生成有序 section，再统一包一层 XML 同名标签。

```ts
// system-prompt.ts:188-192（节选）
const sections: SystemPromptSections = { preamble: promptSections.preamble };
for (const [name, content] of Object.entries(promptSections)) {
  if (name !== "preamble") sections[name] = `<${name}>\n${content}\n</${name}>`;
}
```

**中文解读**：`preamble` 是裸文本；其余每个 section 被 `<同名标签>` 包住（如 `<rules>…</rules>`、`<project_context>…</project_context>`、`<skills>…</skills>`）。**为什么要包标签**：`diffSystemPromptSections()`（`system-prompt.ts:217-229`）能**逐段 diff**，只把变化的 section 作为补丁追加，未变的 section 不重发——这直接服务**提示词缓存**（前缀稳定）。

section 清单（`system-prompt.ts:151-186`）：`preamble / tools / rules / docs / addendum / project_context / skills / cwd / <自定义>`。`contextFiles` → `project_context`（`:173`，`renderProjectContext` `:79-86`，每条包 `<project_instructions path="…">`）。

### A3. 项目规则发现（CM-02）（`core/resource-loader.ts:184-274`）

**条件**：`--no-context-files` 未设时（`cli/args.ts:336`）。
**处理**：候选名 `AGENTS.override.md → AGENTS.md → AGENTS.MD → CLAUDE.md → CLAUDE.MD`（`:185`）；从 **agent 目录（全局）** 起，再沿 **cwd 逐级向上** 到根，收集祖先目录的规则（`:253-269`），并**排除被 worktree 遮蔽的重复项**（`:214-230`）。

**中文解读**：这是"规则怎么自己冒出来"的答案——**不是遍历整棵子树**，而是"全局 + 最近祖先链"。越靠近 cwd 的规则越晚加入（`:262` 用 `unshift`，使近处规则在后、优先级语义明确）。

### A4. 技能渐进式披露（CM-02）（`core/skills.ts:358`）

`formatSkillsForPrompt(skills, fileReadTool)` 只把**技能名 + 一句描述**放进 `<skills>` section；**完整手册按需再读**（`docs/how-pi-works.md:"Full skill instructions are loaded on demand."`）。→ 与术语表"技能（渐进式披露）"一致。

## 2. 链路 B：窗口计量与触发（CM-05）

### B1. 阈值判定（`core/compaction/compaction.ts:267-270`）

```ts
export function shouldCompact(contextTokens: number, contextWindow: number, settings: CompactionSettings): boolean {
	if (!settings.enabled) return false;
	return contextTokens > contextWindow - settings.reserveTokens;   // ← 唯一阈值
}
```

**默认常量**（`compaction.ts:126-130`，与 `core/settings-defaults.ts:9-13` 一致）：

```ts
export const DEFAULT_COMPACTION_SETTINGS: CompactionSettings = {
	enabled: true,
	reserveTokens: 16384,
	keepRecentTokens: 20000,
};
```

**中文解读**：pi 只有**一条阈值线**：`当前用量 > 窗口 − 预留`。`reserveTokens` 同时覆盖"模型回复空间"与"摘要输出空间"（**不拆两笔**，对照 Claude Code 的 `-20K/-13K` 两步扣减）。200K 窗口下触发点 ≈ `200000−16384 = 183616`（教学换算，非实测）。

### B2. 用量怎么量：usage 优先 + 本地估算（`compaction.ts:140-262`）

- `calculateContextTokens(usage)`：`usage.totalTokens || input+output+cacheRead+cacheWrite`（`:140-142`）——**含缓存读写**。
- `getAssistantUsage`：跳过 `aborted`/`error`/全零的 assistant（`:148-161`）。
- `estimateContextTokens`：取**最近一条有效 assistant 的 usage** 作底，其后的消息用 `estimateTokens` 累加（`:196-224`）。
- `estimateTokens`：**`Math.ceil(chars/4)`**（中文是粗估）（`:298-349`；image 按 4800 字符计 `:276`）。
- `estimateProjectedContextTokens`：若 usage 早于最近一次 `context_edit`/`compaction`，则**丢弃旧 usage 全量重估**（`:226-262`）——避免"压缩后仍拿压缩前的大 usage 误触发"。

### B3. 触发时机（三处 + 手动）（`core/agent-session.ts`）

| 时机 | 入口 | 行号 | 说明 |
|---|---|---|---|
| **轮中** | `_compactBeforeNextAssistantResponse` ← `prepareNextTurnWithContext` | `777-786`、`905-906` | 每批工具结果落定、下一次 assistant 之前检查（"活没干完但装不下"） |
| **新提示前** | `_prepareRun` | `1893-1896` | 提交新用户提示前，用最近 assistant 复检（覆盖"被中止的回复"） |
| **运行结束后** | `_handlePostAgentRun` → `_checkCompaction` | `1974`、`2977-3114` | 溢出/超阈检查 |
| **手动** | `compact()`（`/compact`） | `2794-2939` | 见链路 D |

**溢出的特殊路径**（`_checkCompaction` `:3007-3074`）：命中 provider `context overflow` 或"可恢复的 length stop"时，走 `_runAutoCompaction("overflow", …)`，**只允许一次** compact-and-retry（`_overflowRecoveryAttempted` `:3049-3072`）。

**中文解读**：pi 的 mid-turn 触发点落在 `prepareNextTurn`——即**"上一批工具刚干完、下一步要问模型"的空档**，而非更细的每次工具调用之间。这与学习笔记里 pi「每批工具结果落定后」的说法一致。

## 3. 链路 C：单条工具输出治理（CM-04）

### C1. 两条独立上限（`core/tools/truncate.ts:11-13`）

```ts
export const DEFAULT_MAX_LINES = 2000;
export const DEFAULT_MAX_BYTES = 50 * 1024; // 50KB
export const GREP_MAX_LINE_LENGTH = 500;    // 每行 grep 上限
```

**处理顺序**：`truncateHead`（保头，用于 `read/grep/find/ls`）或 `truncateTail`（保尾，用于 `bash`）；**先到者胜**（行数或字节）。**绝不返回半行**（除 bash tail 的行内极端情形 `:205-212`）。UTF-8 边界对齐：`truncateStringToBytesFromEnd` 从尾部回退到字符起点（`:247-262`）。

### C2. bash 超限落盘（`core/tools/bash.ts:333-355`）

```ts
// bash.ts:333-336（节选）
const snapshot = output.snapshot({ persistIfTruncated: true });  // ← 超限即持久化
await output.closeTempFile();
return snapshot;
// bash.ts:342-353：超限时追加
//   [Showing lines <start>-<end> of <total> (50.0KB limit). Full output: <tempPath>]
```

**中文解读**：这正是术语表"落盘 / 预览 / 出口限长"三件套在 pi 的实现——**源头层治理**：全量原文写临时文件，进入消息列表的只有**尾部预览 + 文件路径**。`output-accumulator.ts` 用滚动缓冲（`maxBytes*2`，`:60`）控制内存，`readFullOutput(maxBytes)` 超大时**保首尾各半**（`:149-160`）。

**状态写回**：`toolResult` 条目（含 `details.truncation`、`fullOutputPath`）；**下一次请求**只带预览。**能否找回原文**：能——读 `fullOutputPath` 指向的临时文件（保存边界＝该临时文件；lifecycle 由 `closeTempFile` 管理）。

## 4. 链路 D：整理 / 压缩（CM-06 / CM-07）

### D1. 手动入口 `compact()`（`agent-session.ts:2794-2939`）
先 `abort()` 当前操作 → `prepareCompaction()` → 触发 `session_before_compact` 钩子（可取消/自定义）→ 否则调 `_runDefaultCompaction()` → 成功后 `appendCompaction()`（`:2877`）。手动**不重试、不续跑**被打断的那一轮。

### D2. 自动入口 `_runAutoCompaction(reason, willRetry)`（`agent-session.ts:3127-3274`）
`reason ∈ {overflow, threshold}`；成功后 `appendCompaction()`（`:3207`）；`willRetry` 为真则返回 `true` 让外层 `agent.continue()`。

### D3. 切点：绝不切在 toolResult（`compaction.ts:351-364`、`446-501`）

```ts
function isCutPointMessage(message: AgentMessage): boolean {
	switch (message.role) {
		case "user": case "assistant": case "bashExecution":
		case "custom": case "branchSummary": case "compactionSummary":
			return true;
		case "toolResult":
			return false;    // ← 工具结果必须跟随它的工具调用
	}
	return false;
}
```

**切点算法**（`findProjectedCutPoint` `:802-870`）：从最新往回累加 `estimateTokens`，累计 ≥ `keepRecentTokens(20000)` 时，取"≥ 当前下标的最接近合法切点"。若无合法切点则退回起点。若一个用户消息跨度本身超预算 → **split turn**（`isSplitTurn`），生成**两份摘要再合并**（`:994-1033`）。

### D4. 摘要生成（`compaction.ts:507-538`、`645-766`）

- 摘要 **maxTokens = min(floor(0.8 × reserveTokens), model.maxTokens)**（`:712-715`）；split 的 turn-prefix 摘要 = `0.5 × reserveTokens`（`:1090-1093`）。
- 有 `previousSummary` 时用 **UPDATE 提示词**（`PRESERVE all existing information… ADD new…` `:540-579`）→ **增量摘要**，旧摘要作为 `<previous-summary>` 传入（`:730-732`）。
- 序列化 `serializeConversation()`（`utils.ts:120-155`）：`[User]`/`[Assistant]`/`[Assistant tool calls]`/`[Tool result]`；**toolResult 截到 2000 字符**（`utils.ts:94,149`）；**thinking 块省略**（`utils.ts:114-118`，理由见注释：回放的 thinking 常不在活跃上下文，带上会让摘要请求比被摘要对象还大）。

```ts
// compaction.ts:755-761（节选）—— 失败即抛，不写检查点
const failure = getSummarizationFailure(response, "Summarization");
if (failure) throw new Error(failure);
if (response.content.some((block) => block.type === "toolCall"))
	throw new Error("Summarization attempted to call a tool");
```

`getSummarizationFailure`（`:585-593`）：`stopReason === "error"` → 失败；`"length"` → **摘要被截断，禁止落盘**（"must not become a session checkpoint"）。

### D5. 摘要结构（`compaction.ts:507-538` 提示词原文格式）

```markdown
## Goal
## Constraints & Preferences
## Progress   ### Done / ### In Progress / ### Blocked
## Key Decisions
## Next Steps
## Critical Context
<read-files>…</read-files> / <modified-files>…</modified-files>   ← 由 formatFileOperations 追加
```

文件清单由 `extractFileOperations`（`:60-88`，从 `read/write/edit` 工具调用抽取）+ `computeFileLists`/`formatFileOperations`（`utils.ts:67-87`）生成，并**跨默认压缩累积**（`docs/compaction.md:"File tracking therefore accumulates…"`）。

### D6. 写回与重建（`session-manager.ts:1261-1287`）

```ts
// session-manager.ts:1272-1285（节选）

  type: "compaction", id, parentId: this.leafId, timestamp,
```

**投影重建**（`session-manager.ts:476-512`、`543-573`）：`buildContextEntries` 找到**最新 compaction**，输出 = `[compaction] + firstKeptEntryId 起的所有条目 + compaction 之后的所有条目`；更早的原始条目**被省略**（仍在文件里）。

**下一次请求**：`sessionEntryToContextMessages`（`:439-466`）把 compaction 条目转成一条 **`compactionSummary` 消息**（`messages.ts:62-67`），`convertToLlm`（`messages.ts:148-196`）再把它包装成**一条 user 消息**：

```ts
// messages.ts:11-17
export const COMPACTION_SUMMARY_PREFIX = `The conversation history before this point was compacted into the following summary:\n\n<summary>\n`;
export const COMPACTION_SUMMARY_SUFFIX = `\n</summary>`;
```

**中文解读**：摘要对模型表现为"一条 user 消息，内容是 `<summary>…</summary>`"。加上系统消息（`CompactionEntry.systemMessage` 保存了压缩边界处的**完整提示词/工具状态** `session-manager.ts:102-103`），模型即可无缝续聊。

### D7. 轻量替代：`context_edit`（CM-07 旁支）

`ContextEditEntry`（`session-manager.ts:175-180`）：`replacement:null` = **从模型上下文省略该条目**；`{content}` = **只替换其内容**。这是 pi 比"整段摘要"更细的裁剪手段（如溢出恢复时把被弃的那次 assistant 尝试省略掉，`agent-session.ts:1252`）。**注意**：`context_edit` 只改**模型看到的投影**，不改磁盘原始条目。

### D8. 分支摘要（`compaction/branch-summarization.ts:293-382`）
`/tree` 切换分支时可对"离开的分支"生成 `BranchSummaryEntry`（`fromId` 指回跳转点）；预算 `tokenBudget = contextWindow − reserveTokens(16384)`（`:313`）；摘要格式到 `Next Steps` 止（无 `Critical Context`）。

## 5. 链路 E：保存 / fork / 恢复（CM-10）——路线判定

### E1. 磁盘形态：只追加 JSONL 树（`session-manager.ts:1172-1196`）

```ts
// session-manager.ts:1186-1188（节选）
} else {
  appendFileSync(this.sessionFile, `${JSON.stringify(entry)}\n`);
}
```

会话是**每行一个 JSON 条目、按 `id/parentId` 成树**的 JSONL（`CURRENT_SESSION_VERSION = 3`，`session-manager.ts:41`）。压缩**只追加** `CompactionEntry`，**不删除**任何旧条目（`docs/sessions.md:"It does not delete the original session entries."`）。

### E2. 恢复：`SessionManager.open/continueRecent`（`:1766-1801`）
`open` 读回文件条目（`:1766-1786`）；`continueRecent` 取最近会话（`:1793-1801`）。恢复后**不重跑压缩**，而是 `buildSessionProjection()` 直接用**持久化的** `CompactionEntry.summary + firstKeptEntryId`。

### E3. LQ-10 裁决：**pi 属"持久化断点"路线（路线 B）**

**证据链**：
1. 压缩产物**持久化**：`CompactionEntry{summary, firstKeptEntryId, tokensBefore}` 追加进 JSONL（`session-manager.ts:1272-1287`）。
2. 恢复**直接采用**断点：`buildContextEntries` 用 `firstKeptEntryId` 切分，**不重算摘要**（`session-manager.ts:499-511`）；`prepareCompaction` 只在**需要新一次压缩**时才调用（`agent-session.ts:2810/3141`）。
3. 文档同口径：`docs/how-pi-works.md:"Compaction inserts a summary entry that replaces older messages in subsequent model requests. The original entries remain in the session tree."`
4. 重复压缩时，"被摘要跨度"从**上一次压缩的保留边界**起算（`docs/compaction.md`），说明断点被**当作权威**，不是每次从头重放全部原始条目。

**⇒ 结论**：恢复**不重放全部历史重算**，而是"摘要 + 保留段"直接加载（**压缩只付一次代价**，代价是**被压掉的细节不会自动回到模型**）。**原始条目仍在磁盘**——所以"找回原文"在**文件层**是可能的，但在**模型可见上下文层**不会自动恢复。⇒ 支持冲突表 C-03/C-12 的部分裁决：**"摘要不可逆" ≠ "源记录被删除"**。

### E4. fork / clone / import（`core/agent-session-runtime.ts:262-402`）
`fork` 用 `createBranchedSession(leafId)`（`session-manager.ts:1632`）把选中分支复制成**新会话文件**；`/clone`、`/import` 同理。`session_before_fork/switch` 钩子可取消。

## 6. 链路 F：扩展点（"扩展能改什么"）

pi 扩展＝进程内 **TypeScript 模块**，工厂函数注册工具/命令/provider/渲染器/**事件处理器**（`docs/how-pi-works.md:"Extensibility…"`）。**与上下文管理直接相关的事件**（`core/extensions/types.ts`）：

| 事件 | 时机 | 能改什么 | 行号 |
|---|---|---|---|
| `context` | 每次 LLM 调用前 | 改写**不含 system** 的消息；pi 之后会恢复 prompt/tool 状态 | `types.ts:885-888` |
| `context_with_system` | 同上、`context` 之后 | 改写**含 system** 的完整消息；**处理器拥有 prompt 与工具声明** | `types.ts:895-898` |
| `before_provider_request` | 发请求前 | **替换最终 payload** | `types.ts:901-904` |
| `before_agent_start` | 一次 run 开始前 | 改 `systemPromptOptions`、注入消息、切换工具集 | `types.ts:932-958` |
| `session_before_compact` | 自动/手动压缩前 | **取消压缩**，或提供**自定义摘要**（含 `firstKeptEntryId`/`tokensBefore`/`usage`/`details`）；可读 `preparation`（`messagesToSummarize`/`previousSummary`/`fileOps`/`settings`）与 `reason`/`willRetry` | `types.ts:785-795` |
| `session_compact` / `session_compact_failed` | 压缩后 | 观测（不可改内容） | `types.ts:798-821` |
| `session_before_tree` / `session_before_switch` / `session_before_fork` | 分支/切换前 | 取消或自定义分支摘要 | `types.ts:771-784,847-860` |

**中文解读**：pi 的扩展点是"**在链路的若干接缝上挂事件**"。最重的一个接缝是 `session_before_compact`：它把**压缩后的产物**（summary + firstKeptEntryId）交给扩展决定——扩展可以**完全替换 pi 的摘要算法**（甚至可以换模型、换格式）。**默认不含**：pi 本体没有 sub-agents、没有 plan mode、没有长期记忆（README）；这些若出现，属**扩展行为**。

## 7. 失败分支汇总（CM-11）

| 场景 | 分类 | 处理 | 行号 |
|---|---|---|---|
| 摘要生成 `stopReason=error` | 生成失败 | 抛错，**不写检查点** | `compaction.ts:585-593,755-761` |
| 摘要生成 `stopReason=length` | 输出被截断 | 视为失败（禁止半截摘要落盘） | 同上 |
| 摘要尝试调用工具 | 非法输出 | 抛错 | `compaction.ts:759-761` |
| provider 溢出 / 可恢复 length | 溢出 | `_runAutoCompaction("overflow", willRetry)`；**仅一次** | `agent-session.ts:3007-3074` |
| 流式中断（terminated/socket） | 瞬时错误 | `completeSummarization` 走 `retryAssistantCall`（`retry.maxRetries=3`） | `compaction.ts:619-639`；`settings-defaults.ts:retry` |
| 用户/扩展取消 | 中止 | 保留已发生的编辑，**不追加 compaction**，不安排内部重试 | `agent-session.ts:2873-2875,2915-2938` |
| 扩展 `cancel` | 主动取消 | 抛 "Compaction cancelled" | `agent-session.ts:2833-2841` |
| 压缩失败 | 报错 | `compaction_end(errorMessage)` + `session_compact_failed` | `agent-session.ts:3242-3266` |

**副作用分析**：压缩本身**不产生外部副作用**（只追加会话条目）；**只有在成功后**才 `appendCompaction`，失败则不留下半成品。⇒ **可重复执行 `compact()`**（幂等性由"只在成功时追加"保证），但**已执行过的工具动作不会因压缩失败而撤回**（工具副作用在压缩之前已发生）。

## 8. 缓存（CM-12）

- **摘要请求禁写缓存**：`completeSummarization` 设 `cacheRetention:"none"`（`compaction.ts:631`）——一次性摘要"unlikely to be reused"，写了反而污染。
- **会话侧缓存预热** `CacheWarmer`（`core/cache-warmer.ts:162-…`）：默认 `cacheWarming:"streaming"`（`settings-defaults.ts`），把刚写的缓存条目在过期前用**单 token 输出上限**重发一次以"保持热度"；有成本阈值（`CACHE_WARMING_MINIMUM_EXPECTED_SAVINGS = $0.05`，`:21`）、TTL 取自模型 `promptCache` 档位。
- **命中统计** `cache-stats.ts`：`CACHE_TTL_MS = 5min`，统计"上一次请求在缓存里、这一次没命中"的浪费（`NOISE_FLOOR_TOKENS=1024` 忽略噪声）。
- **用量含缓存**：`calculateContextTokens` 把 `cacheRead/cacheWrite` 计入窗口占用（`compaction.ts:140-142`）。
