## 2. OBS-01｜入口与凭据/设置加载层（OBSERVED）

### 2.1 命令与结果（逐字）

```bash
$ pi --version
1.2.0

$ pi auth check --model deepseek-v4.1-flash --provider opencode-go --json --no-refresh
{"status":"ready","provider":"opencode-go","authType":"api_key"}

# 运行 1：默认设置解析
$ cd /tmp/pi-t06-obs/proj && pi -p "Run this exact bash command: sh gen.sh  Then reply with ONLY the exact text of the last line it printed." \
      --session-dir /tmp/pi-t06-obs/sessions --mode json
退出码 = 1
stderr:
  Warning: Invalid settings file /Users/junjielong/.pi/agent/settings.json:
    EEXIST: file already exists, mkdir '/Users/junjielong/.pi/agent/settings.json.lock'
  No API key found for the selected model.

# 运行 2：显式 --provider/--model
$ cd /tmp/pi-t06-obs/proj && pi -p "..." --provider opencode-go --model deepseek-v4.1-flash \
      --session-dir /tmp/pi-t06-obs/sessions --mode json
退出码 = 1
stderr:
  Warning: Invalid settings file .../settings.json: EEXIST: ... 'settings.json.lock'
  Credential store read failed for opencode-go: EEXIST: ... '/Users/junjielong/.pi/agent/auth.json.lock'
```

### 2.2 观察到的现象（OBSERVED，附证据）

1. **可执行入口存在且能自报版本**：`pi --version` → `1.2.0`。
2. **provider 就绪可查**：`pi auth check …--json` → `{"status":"ready","authType":"api_key"}`（**显式传 `--provider/--model`** 时成立）。
3. **设置/凭据加载被陈旧锁目录阻塞**：
   - `~/.pi/agent/{settings.json,auth.json,models-store.json}.lock` 是三个**空目录**（创建时间 2026-10-14 23:41 ~ 10-15 00:22，疑似上次异常退出残留）；pi 用 **mkdir 式锁**，目录已存在即 `EEXIST`。
   - 后果链：settings.json 读失败 → **默认 provider/model 解析失败** → `No API key found for the selected model`；即便显式传参，**auth.json.lock 仍使凭据库读失败** → `Credential store read failed`。
4. **两次运行均未发生模型推理**：`--mode json` 输出**仅一条 session 头**（见下），无 assistant/tool 事件，**无费用产生**。
   - `{"type":"session","version":3,"id":"01a13b39-…","timestamp":"2026-10-14T16:23:28.257Z","cwd":"/private/tmp/pi-t06-obs/proj"}`
   - 副产物：**观察到 pi 的会话头结构** `{type:"session", version:3, id, timestamp, cwd}`（与快照 `session-manager.ts:41,43-50` 的 `CURRENT_SESSION_VERSION=3` 一致）。

### 2.3 判据纪律：以退出码为准 + 一次负例（全组观察纪律①）

| 判据 | 期望 | 本轮实测 |
|---|---|---|
| **入口就绪** | 退出码 `0`，且 `auth check` 报 `ready` | `pi auth check` = `ready` ✅ |
| **入口阻塞（负例）** | 退出码 **非 0** 且 stderr 给出原因 | `pi -p` **退出码 = 1** + 两条 EEXIST 原因 ✅ |

- **负例已做**：本轮失败的 `pi -p` 运行**就是一次负例**——它证明该入口的退出码**不是恒 0**（对照 T03 曾出现的"退出码恒 0、看着通过"陷阱，本处是"该失败即失败"）。⇒ 判据可用退出码，不靠"看着像通过"。
- **判据落到 §3 各观察项**：每条观察以 `pi -p …` 的**退出码**判入口是否成功，再以**事件流 + 检查器**判机制行为。

### 2.4 结论（范围严格限定）

- **OBS-01 = OBSERVED**：观察的是**入口与配置/凭据加载层**的**真实行为**，包括一个**可复现的失败模式**（陈旧 mkdir 锁 → EEXIST → 凭据库不可读）。
- **OBS-01 不能证明什么**：❌ 不能证明任何上下文管理机制在运行时的行为（阈值、压缩、恢复、工具输出）；本次**没有跑通一次模型轮**。
- **归因限制**：本次失败**与 pi 的上下文管理算法无关**，是**宿主环境的陈旧锁**所致；不得据此推断 pi 的压缩/恢复行为。**结论级纪律**：阻塞 ≠ "机制不可运行/没有实现"。

- 按 T03 §7「缺凭据则该条件 `NOT_RUN`」→ 模型轮机制观察记 `NOT_RUN`（原因见 §0：入口被陈旧锁目录阻塞 EEXIST，未发生任何模型调用；清理授权待用户）。
