# pi · 数据走查

> 本文件解决什么问题：用 **T03 冻结合成数据包**做"输入 → 处理 → 输出 → 丢失/保留"的可算走查，给每个 `pi-*` 结论配一个 `DW-*` 走查 ID。**不调用真实模型**：数字来自快照源码算法 + 对 T03 文件的直接量算。
> 数字纪律（术语表 §12）：**【源码常量】**= 快照真实常量；**【量算】**= 对 T03 文件直接测量/按源码公式计算；**【演示】**= 教学假设。
> 关键实测数字（可复算）：`长工具结果-公交查询-v1.txt` = **300 行 / 22,003 字节 / 17,190 字符**；pi `estimateTokens = ceil(17190/4) = 4,298`【量算】。

## 1. 工具输出治理（对应 pi-trunc-01/02、pi-retrieval-01）

### DW-trunc-01｜T03 长结果在 pi 默认限长下**不会被工具出口截断**

- **输入**：`长工具结果-公交查询-v1.txt`（300 行 / 22,003 B / 17,190 字符）。
- **pi 的两条上限**【源码常量】：`DEFAULT_MAX_LINES=2000`、`DEFAULT_MAX_BYTES=50×1024=51,200`（`tools/truncate.ts:11-12`）。
- **处理**：`truncateHead`/`truncateTail` 先比行数再比字节，取先到者。
- **输出**：`totalLines=300 ≤ 2000` 且 `totalBytes=22,003 ≤ 51,200` → **`truncated=false`**（`truncate.ts:87-101`）。
- **丢失/保留**：**全部 300 行原样进入消息列表**。
- **边界例子（重要，供 T19）**：**T03 现有 E2 样本对 pi 偏小**——它既不超 2000 行也不超 50KB。要触发 pi 的**工具出口**截断，样本须 **>2000 行 或 >50KB**。⇒ 建议 T19 的 pi 侧 E2 另造 ≥60KB 或 ≥2,100 行的合成输出（**不改 T03 v1，另存 v2**）。

### DW-trunc-02｜bash 超限时的落盘与预览（按源码公式推演）

- **输入**（演算）：一段 3,000 行、约 126,000 B 的合成输出。
- **处理**【源码常量】：`bash` 用 `truncateTail`（保尾，`tools/bash.ts:20,342-353`）；`output-accumulator` 滚动缓冲 `maxRollingBytes = maxBytes×2 = 102,400`（`output-accumulator.ts:58-60`）。
- **输出**：进入消息列表的是**尾部预览**（≤2000 行且 ≤50KB）+ 追加文本 `[Showing lines <start>-<end> of 3000 (50.0KB limit). Full output: <tempPath>]`；全量原文写入临时文件。
- **丢失/保留**：**头部中间丢失**（不在请求里）；尾部保留；**原文可在 `<tempPath>` 找回**。
- **边界例子**：`truncateTail` 的极端情形——单行本身 >50KB 时取**行尾部分**并置 `lastLinePartial=true`（`truncate.ts:205-212`）。

### DW-retrieval-01｜按需读取

- **输入**：大仓库目录（演示）。**处理**：模型先 `ls/find/grep` 定位，再 `read(path, offset, limit)` 分段读（`tools/read.ts:96,168-192`）。**输出**：请求只带被读段。**丢失/保留**：未读文件不进上下文。**边界**：`read` 命中首行超限时返回空内容 + `firstLineExceedsLimit=true`（`truncate.ts:103-119`）。

## 2. 窗口计量与触发（对应 pi-trigger-01/02/03）

### DW-trigger-01｜用 T03 数据估算"离触发线还有多远"

- **输入**：T03 行程任务的消息序列 `消息序列.jsonl`（18 条，3,974 B）+ 一条 300 行结果。
- **处理**【源码常量 + 量算】：按 `estimateTokens=ceil(chars/4)`；18 条消息 ≈ `ceil(3974/4)=994` tokens；公交结果 = `ceil(17190/4)=4,298` tokens。
- **输出（演示 200K 窗口）**：`W=200,000`、`reserve=16,384` → 触发线 = `200,000−16,384 = 183,616`。当前 ≈ `994+4,298+系统提示词` ≪ 183,616 → **不触发**。
- **丢失/保留**：不触发则**无丢失**。**边界**：要触发阈值需累计 ≈183.6K tokens（演示口径）。
- **用途**：给 T19 一个"要造多大上下文才触发"的量级。

### DW-trigger-02｜"最近 usage + 其后估算"的口径

- **输入**：一串 assistant（含 `usage`）+ 其后的 toolResult。
- **处理**【源码常量】：取**最后一条有效 assistant** 的 usage（`totalTokens||in+out+cacheRead+cacheWrite`），其后每条 `ceil(chars/4)` 累加（`compaction.ts:196-224`）。
- **输出**：`tokens = usageTokens + trailingTokens`。**丢失/保留**：N/A。**边界**：usage 早于最近一次 `context_edit/compaction` → **全量重估**（`compaction.ts:232-261`）。

### DW-trigger-03｜三时机触发的条件

- **输入**：一轮里 3 个工具结果落定。**处理**：`prepareNextTurnWithContext` 在**下一次 assistant 之前**调 `_compactBeforeNextAssistantResponse`（`agent-session.ts:905-906`）。**输出**：`shouldCompact` 为真才压缩。**边界**：若**最后一批工具结束整个 run 且无排队消息**，跳过该轮间检查（`docs/compaction.md`）。

## 3. 压缩与摘要（对应 pi-compact-01、pi-summary-01..05）

### DW-summary-01｜摘要结构 + 文件清单累积

- **输入**：模型可见消息集（含 `read/edit/write` 工具调用）。**处理**：按固定模板生成摘要（`compaction.ts:507-538`），并 `extractFileOperations`+`computeFileLists` 追加 `<read-files>/<modified-files>`（`utils.ts:30-87`）。
- **输出**（结构）：
  ```markdown
  ## Goal … ## Constraints & Preferences … ## Progress(Done/In Progress/Blocked)
  ## Key Decisions … ## Next Steps … ## Critical Context …
  <read-files>…</read-files> <modified-files>…</modified-files>
  ```
- **丢失/保留**：旧摘要信息在 UPDATE 提示词下"应保留"（`compaction.ts:540-575`）；**是否真保留属有损，待 T19**。

### DW-summary-02｜切点把 T03 的"决策更新线"切在哪（演算）

- **输入**：T03 消息序列 MSG-001…MSG-018；已知"决策从待定→已否决"线在 MSG-004/006/009（见 T03 README §E3）。
- **处理**【源码常量】：`keepRecentTokens=20,000`；从最新往回累加到 ≥20,000 才切；切点只能落在 user/assistant/bashExecution/custom 边界，**绝不在 toolResult**（`compaction.ts:351-364,446-501`）。
- **输出**：切点将在"第 N 条 user/assistant"处；`firstKeptEntryId` 指向该条；其后的近期原文全保留。
- **丢失/保留**：切点**之前**的消息 → 进摘要（有损）；**之后** → 原文保留。**边界**：若单个 user 跨度 >20,000 tokens → `isSplitTurn=true`，生成两份摘要合并（`compaction.ts:994-1033`）。

### DW-summary-03｜T03 大结果在"摘要序列化"里被截到 2000 字符（**关键损失边界**）

- **输入**：同一份 17,190 字符的公交结果，作为 `toolResult` 进入一次压缩。
- **处理**【源码常量】：`serializeConversation` 对 toolResult 调 `truncateForSummary(content, 2000)`（`utils.ts:94,100-104,146-151`）。
- **输出**【量算】：摘要请求里只带**前 2,000 字符**（≈**前 39 行**）+ 标记 `[... 15190 more characters truncated]`；**被截掉 15,190 字符**。
- **丢失/保留（逐条）**：
  | 关键事实 | 文件行号 | 是否进摘要序列化 |
  |---|---|---|
  | 车程 55 分钟（判定规则） | 第 5 行 | ✅ 保留 |
  | **推荐班次 14:50→15:45** | 第 152 行 | ❌ **被截掉** |
  | **不可用班次 15:20→16:15（HC-01 证据）** | 第 154 行 | ❌ **被截掉** |
  | 结论注释 / 车辆报价 1400 元 | 第 295-298 行 | ❌ **被截掉** |
- **解读**：这条走查给出一个**反直觉的重要结论**——
  - **活跃上下文**里：该结果 300 行**原样都在**（DW-trunc-01，不触发出口限长）；
  - **一旦发生压缩**：摘要只能看到该结果的**前 2000 字符**，中/尾的关键事实**不会进入摘要**，除非模型在压缩前已把它们写进回复/摘要之外的条目。
- **对 T19 的启示**：pi 的"大输出丢失"风险**主要发生在压缩序列化层（2000 字符），而非工具出口层（50KB）**。E2 应分两层分别测：出口层（>50KB / >2000 行）与压缩层（任意 >2000 字符的结果）。

### DW-summary-04｜摘要如何回到模型

- **输入**：一条 `CompactionEntry{summary, firstKeptEntryId, tokensBefore}`。
- **处理**【源码常量】：`sessionEntryToContextMessages` → `compactionSummary` 消息（`session-manager.ts:461-464`）→ `convertToLlm` 包成 **user 消息**（`messages.ts:176-183`）。
- **输出**：模型看到 `"The conversation history before this point was compacted into the following summary:\n\n<summary>\n…\n</summary>"`。
- **边界**：若 `CompactionEntry.systemMessage` 存在，投影里 `[systemMessage, summary]` **两条**（`session-manager.ts:461-463`）。

### DW-summary-05｜context_edit 的两种效果

- **输入**：一条既有 assistant/toolResult 条目 + 一条 `context_edit{targetId, replacement}`。
- **处理**【源码常量】：`projectContextEntry`——`replacement===null` → 返回 `[]`（**从投影省略**）；有值 → **只替换内容**，保留角色/ID（`session-manager.ts:519-540`）。
- **输出**：该条目进不进模型可见上下文，取决于 `replacement`。
- **丢失/保留**：磁盘原文**不变**；仅投影变化。**边界**：`appendContextEdit` 要求目标在当前分支上，否则抛错（`session-manager.ts:1371`）。

## 4. 保存 / 恢复（对应 pi-persist-01、pi-recover-01）

### DW-persist-01｜压缩后文件与投影的对照

- **输入**：压缩前条目 `[hdr, usr, ass, tool, usr, ass, tool, tool, ass, tool]`（`docs/compaction.md` 示意图）。
- **处理**【源码常量】：`appendCompaction` 追加第 11 条 `cmp`（`session-manager.ts:1261-1287`），**不删前 10 条**。
- **输出**：文件 = 11 条（原始 10 + `cmp`）；**模型可见投影** = `[system?, summary, usr4…tool9]`（`buildContextEntries` 以 `firstKeptEntryId` 起）。
- **丢失/保留**：文件层**全保留**；模型层**旧条目被摘要替代**。

### DW-recover-01｜resume 直接采用断点（LQ-10 走查）

- **输入**：含 `cmp` 的会话文件。**处理**【源码常量】：`SessionManager.open()` 读回条目（`session-manager.ts:1766-1786`）→ `buildSessionProjection()`（`:543-573`）直接用 `cmp.summary + cmp.firstKeptEntryId`。
- **输出**：恢复后模型上下文 = 摘要 + 保留段 + `cmp` 之后的条目；**不重跑摘要生成**。
- **裁决**：pi = **持久化断点（路线 B）**。
- **丢失/保留**：被压细节**不回模型**；但**文件里仍在**（人工/工具可读），与 C-03/C-12 一致。

## 5. 失败与缓存（对应 pi-fail-01/02、pi-cache-01）

### DW-fail-01｜溢出只恢复一次

- **输入**：provider 返回 `context overflow`。**处理**【源码常量】：`_checkCompaction` → `_runAutoCompaction("overflow", willRetry)`，置 `_overflowRecoveryAttempted=true`（`agent-session.ts:3049-3074`）。**输出**：成功则重试该轮一次；再失败 → 报 `"Context overflow recovery failed after one compact-and-retry attempt…"`（`:3051`）。**边界**：`assistant.stopReason==="aborted"` 时不压缩（`:2986`）。

### DW-fail-02｜成功才提交 / 摘要失败不落盘

- **输入**：一次压缩过程中，摘要返回 `stopReason="length"`。**处理**【源码常量】：`getSummarizationFailure` 判失败 → `throw`（`compaction.ts:585-593,755-758`）→ `_runAutoCompaction` catch 分支发 `compaction_end(errorMessage)`（`agent-session.ts:3242-3266`），**不调 `appendCompaction`**。
- **输出**：文件**不新增** `cmp` 条目。**副作用**：压缩前已发生的工具副作用不回退。

### DW-cache-01｜摘要请求不写缓存

- **输入**：一次摘要调用。**处理**【源码常量】：`cacheRetention:"none"`（`compaction.ts:631`）。**输出**：该校验"summary 请求不污染缓存"。**丢失/保留**：N/A。**边界**：会话正常请求侧默认 `cacheWarming:"streaming"`（`settings-defaults.ts`），可能**额外发一次保活请求**。

## 6. 组装与扩展（对应 pi-assembly-01/02、pi-rule-01/02、pi-ext-01/02）

### DW-assembly-01｜一次请求的"部件清单"

- **输入**：某轮 `projection.messages` + `agent.state.tools`。**处理**：系统提示词 sections + 投影消息 + 工具声明拼成请求（`agent-session.ts:793-810`）。**输出**：`{messages:[system?, …投影…, 新用户消息], tools:[…]}`。
- **边界**：虚拟模型路由时**按路由到的模型**再查一次阈值（`agent-session.ts:839-842`）。

### DW-assembly-02｜系统提示词差分

- **输入**：上一次的 `sections` 与新计算的 `sections`。**处理**：`diffSystemPromptSections` 只输出变化段（含删除置 `null`）（`system-prompt.ts:217-229`）。**输出**：未变段**不重发**。**边界**：`forceSystemPrompt` 时无 section，整段 `content` 是不透明字符串（`:199-205`）。

### DW-rule-01｜规则发现的路径集合

- **输入**：cwd = `/repo/pkg/sub`，`/repo/AGENTS.md` 与 `/repo/pkg/AGENTS.md` 存在。**处理**：向上收集，近者后置（`resource-loader.ts:253-269`）；`AGENTS.override.md` 优先于 `AGENTS.md`（`:185`）。**输出**：`[全局,…,/repo/AGENTS.md, /repo/pkg/AGENTS.md]`（顺序示意）。**边界**：被 worktree 遮蔽的项**去重**（`:214-230`）。

### DW-ext-01｜扩展替换摘要的输入结构

- **输入**：`session_before_compact` 事件。**可读**：`preparation.{messagesToSummarize, turnPrefixMessages, previousSummary, fileOps, firstKeptEntryId, tokensBefore, settings}`、`reason`、`willRetry`、`signal`（`types.ts:785-795`）。**可写**：`{cancel:true}` 或 `{compaction:{summary, firstKeptEntryId, tokensBefore, usage?, details?}}`。**输出**：pi 采用扩展摘要（标记 `fromHook`）。

### DW-ext-02｜请求改写钩子

- **输入**：`context` / `context_with_system` / `before_provider_request` 事件。**处理**：依次可改写消息、替换 payload（`types.ts:885-904`）。**输出**：改写后的请求。**边界**：`context` 处理的 messages **不含 system**，pi 之后会**恢复** prompt/tool 状态（处理器不能把 prompt 丢掉）。

## 走查结论汇总（给 T19 的三条可执行提示）

1. **T03 E2 样本对 pi 偏小**（DW-trunc-01）：300 行/22KB 既不超 2000 行也不超 50KB → pi 工具出口**不截断**。测 pi 出口截断须另造 **>2000 行 或 >50KB** 的合成输出（另存 v2）。
2. **pi 的"大输出失真"主要在压缩序列化层**（DW-summary-03）：任何超过 **2000 字符**的 toolResult 在**摘要输入**中只剩前 2000 字符。测"关键事实丢失"应把**压缩**这一环单独控变量。
3. **恢复=持久化断点**（DW-recover-01）：设计 resume 实验时，验证重点是"摘要 + `firstKeptEntryId` 起"的投影，而非"从头重放"。
