## 1. 观察 `OBS-ohmy-trunc-01` · 工具输出限长函数级执行（已运行）

**目的**：验证 `ohmy-trunc-01` 主张的"3000 行 / 50 KiB 先到者、保头、多字节不切断"在**出货代码**上成立。

**为什么是"函数级"而非"产品级"**：产品入口 `omp` 未安装（§2）；但 `@oh-my-pi/pi-tui@18.10.4` 是官方已发布分发包，其 `truncateHead` 即 oh-my-pi 工具输出限长的**同一份出货代码**。这是**真实执行**（非源码阅读），但仍**不等于**产品端到端验证。

**命令**（工作目录 `/tmp/omp-obs`，仓库外，未触碰只读快照）：
```bash
npm init -y && npm i @oh-my-pi/pi-tui@18.10.4 --no-audit --no-fund
bun run check.ts
```

**检查器**（`/tmp/omp-obs/check.ts`，合成数据）：4 个断言——
1. 负例/对照：10 行未到线 → `truncated=undefined` 且内容不变（若被截断则判据不可信）；
2. 3500 行 → `truncatedBy="lines"`、`outputLines=3000`；
3. 单行 60000 字节 → `truncatedBy="bytes"`、`firstLineExceedsLimit=true`、`content=""`；
4. 600 行 CJK（>51200 字节）→ `truncatedBy="bytes"`、输出 ≤51200 字节、UTF-8 往返一致（不切半字）。

**预期事件 / 判据**：全部断言 PASS 且退出码 0。**停止条件**：任一断言 FAIL 或异常 → 记失败并停止（不追加重跑）。

**实际结果**（原始输出）：
```text
constants: DEFAULT_MAX_LINES=3000 DEFAULT_MAX_BYTES=51200
[PASS] under-limit passthrough :: truncated=undefined contentUnchanged=true
[PASS] over-lines truncates to DEFAULT_MAX_LINES :: truncatedBy=lines outputLines=3000 totalLines=3500
[PASS] single line over byte cap -> firstLineExceedsLimit :: truncatedBy=bytes firstLineExceedsLimit=true outBytes=0
[PASS] CJK truncation keeps valid UTF-8 and within byte budget :: truncatedBy=bytes outBytes=51174 utf8Valid=true
RESULT: ALL_PASS
EXIT_CODE=0
```
**首轮负例（证明检查器能报错，非"恒 0"）**：首版 CJK 用例输入 200 行（26889 字节）**未到线**，我的期望值写错为"应截断" → 检查器如实报 `[FAIL]` 并 `EXIT_CODE=1`；修正输入到 >51200 字节后复跑得 `ALL_PASS / 0`。

> **原始记录（T08R 后补录）**：检查器脚本、本次运行的原始 stdout/stderr/退出码，以及复演"错误期望 → FAIL"的负例控制输出，已留存于 `过程观察-原始记录/`；索引见 `过程观察-原始记录/OBS-ohmy-trunc-01-记录.md`。复跑输出与上文逐字一致。

**版本双重口径**：
| 口径 | 值 |
|---|---|
| 实际执行版本（入口自报） | npm `@oh-my-pi/pi-tui@18.10.4`（`npm view` 自报 version=18.10.4） |
| 研究快照 SHA / 冻结分发包 | 快照 `f979f46`（`packages/tui/package.json` version=18.10.4） |
| 是否一致 | **版本号一致（都 18.10.4）**；但**非同一份代码**（main 快照 vs 已发布发包）。故本观察**只**用于佐证 `ohmy-trunc-01` 的**出货常量与函数行为**，不外推到快照 main 的其余行号 |

**归因限制**：本观察**不涉及模型**，故不存在"变化来自模型而非机制"的归因风险；但也**不证明**产品默认参数在真实会话中如何被各工具调用（阈值由调用方传入，产品侧默认值来自 `DEFAULT_MAX_*`，未跑产品入口核对）。

**污染登记**：见 §3。

**退出码判据**：`EXIT_CODE=0` = 通过；`EXIT_CODE=1` = 有断言失败。

## 2. 产品入口 `omp` 端到端观察 · NOT_RUN

**命令（拟）**：`curl -fsSL https://omp.sh/install | sh` → `omp`（随后按 T03 合成任务跑"超窗/压缩/恢复"最小观察）。

**NOT_RUN 确切原因**（三要素齐）：
1. **查的路径**：`which omp`（未命中，exit 1）；`ls ~/.omp`（不存在）；`npm ls -g`（无 `@oh-my-pi/*`）。见 §3 命令输出。
2. **凭什么**：安装 `omp` 是**新装全局可执行**，属任务书 §7「升级或覆盖已有工具/变更全局配置」需**作者另行明确授权**的动作；本任务卡未授权安装；且真实机制实验的**统一调度在 T19**。
3. **官方怎么说**：官方入口即 `curl -fsSL https://omp.sh/install | sh`（版本表 §1），本地观测环境表（版本表 §3）亦记 `omp（oh-my-pi）= 未安装`。

**结论**：`NOT_RUN`——**不代表** oh-my-pi 机制不存在；所有机制结论均以**快照源码 + 仓库文档**为证据，并逐卡标"不能证明"。

**为什么不用快照源码直接跑**：快照无 `node_modules`；在快照内 `bun install` 会**写入只读快照**（违反硬约束），且原生 `crates/pi-*` 需 Rust 构建，超出 ≤10 分钟上限。故改为**仓库外**安装**官方已发布包**做函数级观察（§1）。
