实验台 ① · 掌握机制（M03）

它怎么知道「桌子快满了」？

程序一直维护着几条数字，每拍对着几条线比一比——到线了就动手。这一台给你窗口、用量与一组配置，让你自己算出「到没到线」，并切换八种工具口径看同一件事的九种画法。

先修M02（请求是「拼」出来的）。
读完你能手算一条自动整理线到没到线，并说出用的是哪条线。

人话直给四本账 + 三条线

程序不是「每拍把所有字重数一遍」，而是以服务端上次的实测为锚点，加上本地刚加进来的材料，得到「当前用量 A」；再拿 A 去和几条预先算好的线比。四本账是 W（窗口）、p（有效窗口比例，缺省 95）、H = W×p÷100（有效窗口）、A（当前用量）；外加 P（输入基线）。

三条线：基础线 (W×9)/10（90% 向下取整，范围线的默认原料）→ 范围线 min(M, 基础线)（M = 模型字段，Codex 专有）→ 整段线 = H（所有材料都不得超过的硬检查）。触发到线 = 范围线 OR 整段线。

当心 · 两个别写错

❌「90–95% 是统一压缩阈值」——该说法已被九工具全部否证（C-01/C-02）；各家口径从 50% 到「窗口减固定值」都有。
❌「模型字段 M 缺失 = 限额为 0」——None 不是 0：字段缺失时程序回退到 90% 基础线。

实验台 ② · 掌握机制（M05）

一条 300 行的日志，怎么吃掉半个窗口

工具输出是最大的隐形膨胀源。一条关键约束要活到下一次请求，必须连续通过「出口 → 历史 → 整理 → 恢复」四关——任何一关都可以是丢失点。这一台让你亲手滑动预算、移动关键行的位置，看它最坏情况下死在哪一关。

先修M04（列表里的材料怎么被改写）。
读完你能做一张损失点定位表，指出约束在三处限长的哪一处丢的。

三处限长不是三份，是三关

关卡什么时候动刀动刀的是谁产物形态
① 出口限长工具结果交给模型消费之前工具结果包装函数带警告头的预览（保头尾裁剪、加说明头、超限落盘）
② 活动历史结果登记进当前列表时历史管理函数列表里的裁剪副本；存档另存原载荷
③ 摘要请求到线整理时压缩/摘要流程给模型看的历史副本，超限再缩

出口是「给模型的预览」，活动历史是「列表里的副本」，摘要是「整理用的副本」——三者是三份不同的东西，不能画成一个全局滑块。①和②要「裁两次」是因为目标不同：①保证单条不撑爆一次工具往返；②保证整张列表配平窗口。

文本 30 个 ASCII 字符，预算 10 字节（Codex 头尾口径）。头尾各留多少？移除多少字节？标记数字是多少？最终字节数等于 10 吗？
看答案

左 = 5、右 = 5（10÷2 恰好均分）；头 = 前 5 字符，尾 = 后 5 字符；移除 = 20 字节 → N = ceil(20/4) = 5；结果 = 5 字符 + …5 tokens truncated… + 5 字符。最终字节数不等于 10（10 + 标记长度）——标记不占预算。

实验台 ③ · 掌握机制（M04）

整理之后，桌上留下了什么？

整理 ≠ 把全部对话换成一页摘要。真实产物至少两种形态，且大部分近期原话会被原样留下。这一台把保留算法的五步骨架拆成一幕一幕，逐步演推「谁留下、谁变短、谁被扔、摘要排在哪」，并演示连续压缩。

先修M03（什么时候必须整理）。
读完你能对每条材料说出「它去哪了、为什么、代价是什么」。

两条路径 + 五步骨架

整理有两条实现路径，由 provider 能力决定：本地摘要路径（客户端编排，产物是可读文字摘要）与 远端压缩 v2（服务端完成，产物是含 encrypted_content 的加密压缩条目，客户端只见形状）。两条路径产物不同，但保留遵循同一副骨架：

① 筛候选→ ② 用预算（从新到旧）→ ③ 边界截短（保头尾、就停手）→ ④ 产物另加（不占原话预算）→ ⑤ 重组规则
当心 · 三组数字互相独立

20,000（本地保留预算）/ 64,000（远端 v2 保留预算）/ 触发线——三组数字互相独立，不得混用。20,000 不是触发线，也不是最终请求大小，它只是「给旧用户原话留的共享预算」。

为什么两条路径都「从新到旧」，而不是「按重要程度排」？
看答案

「重要程度」无法在客户端廉价又可靠地评估：读懂语义再挑等于又跑一次模型（成本、延迟都不可接受，且可能挑错）。时间新近性是可用、稳定、便宜的代理信号；深层语义保全交给摘要产物的生成环节。这也是「整理会不会保住你关心的细节」最终无法被客户端代码单方面保证的原因。

实验台 ④ · 掌握机制（M06）

关掉再打开，恢复的是哪一份材料？

同一个会话，程序里有三份不同的东西：存档（磁盘）、活动历史（内存）、下次请求。这一台让你在「压缩前 / 压缩后 / 关闭程序 / 重开 resume」四个状态之间切换，看三层各自怎么变——并回答「被压掉的原话还在不在」。

先修M04/M05（材料怎么被改写、落盘）。
读完你能画出四态对照表，并分两层回答「能不能找回」。

主结论四句必须背下

磁盘上有 ≠ 活动历史里有；活动历史里有 ≠ 下次请求带上（还要过组装与裁剪）；下次请求带上 ≠ 模型一定照做（行为是另一层问题）；再补一句：磁盘上有原文 ≠ 模型此刻看得见原文（这是 C-03/C-12 的关键）。

整理（压缩）完成时，程序做两件事：① 替换当前活动历史（用替代历史 = 重组后的规则 + 保留的旧消息 + 新摘要/压缩条目）；② 向磁盘追加一条「压缩检查点」（含替代历史整份副本、窗口编号、用量摘要、恢复元数据）。检查点保存的不是「删掉了什么」，而是「替代后是什么」；旧记录仍留在之前已写入的存档行里——追加式写入，不覆盖。

形态一句话恢复时做什么代表

第一道选择：全量装填 vs 按需读入

全量装填（stuff-all）

一次把资料全搬上桌。桌子立刻满、贵、噪声大——大仓库直接装不下，且 99% 内容与本次改动无关。

按需读入（retrieve / JIT）

先给「目录/名字」，用时再搬；每次只搬这一小段，内容高相关、可续读、可定位。

八工具的检索侧，主流选择都是「按需读入」——证据形态是各家都内建了检索工具。但口径要写清：证据能证明的是「官方文档/源码里没有全量装填路径」，不能证明「一定不存在」——未知保留未知。而「有 read 工具」只说明能力在，模型实际会不会一把梭全读属模型行为 → 【T19 实测：pi 同条件 3 轮行为分化（1 轮只读头部 / 2 轮自主分页 offset 717→1428→2151 读完）；codex 中段丢失后二次检索取回（证据：T19/02-pi §1.4、01-codex §A-3）】。

实验台 ⑥ · 掌握机制（M07 / M11）

同样的开头，第二次为什么更便宜？

缓存省的是重新计算，不是「少发材料」——这个直觉是错的，正是本台要拆的坑。三组账单让你亲手拆读一段 usage；场景决策表让你学会「按场景查，而不是比高低」。

先修M04/M06（压缩替换历史）、M02（稳定材料排前面）。
读完你能读出缓存读取/写入明细，并解释一次「更慢更贵」的周转来自哪里。

省了什么、没省什么

缓存省的缓存不省的
重新计算（算力、钱、首字延迟方向）本次上下文的总长度——命中的 token 依然是本次输入的一部分
稳定前缀那一段的重算成本速率限制（TPM）——cached 输入依然计入
（在服务端命中时）首字更快上下文窗口占用——缓存不缩窗口

匹配单位 = 完整渲染后的前缀（token 级）：没有「按文件缓存」，也没有「按消息段缓存」——若把某个文件插到前缀中间，它之后的内容全部失配。压缩改变前缀 → 缓存按前缀退化，但不会整体归零：变化点之前的稳定段（基础指令、工具说明）若未变，仍可能命中。

边界四问（R14 强制）必须背下

边界一句话
缓存 ≠ 摘要（压缩）缓存不改变材料（前缀原样复用）；摘要改变材料（替换历史）——目的相反：一个省重算，一个减体积
缓存 ≠ 外部记忆外部记忆是「不在消息列表里、可再取用」的记忆；缓存在服务端存 KV 状态，不改变本次请求带哪些材料
缓存 ≠ 容量扩展缓存不缩窗口占用（cached 输入仍占本次上下文、仍计 TPM）
缓存 ≠ 少发材料「少发」是压缩/检索的产物；缓存一个 token 都不少发
红线 · 不承诺命中率

服务端命中 / TTL 九工具全部 UNOBSERVABLE——本地只能看到 CLI 侧可观测字段（① 读写明细、②⑧ 计数/桶），看不到服务端是否真的命中、命中多少。任何命中率承诺都越过了证据边界，须待 T19 以 usage 为准。【T19 实测：CLI 侧 cacheRead 可观测且 >0（claude 19,840~27,136、dsh 最大 84,608、ocv1 9/12 命中）；服务端命中率/TTL 仍 UNOBSERVABLE——「不承诺命中率」边界不变（证据：T19/03-claude §5、05-dsh §缓存、06-ocv1 §4）】

某请求 input_tokens=50,000、cached_tokens=40,000、cache_write_tokens=2,000。求普通输入与计费当量（用本台演示费率），并回答「cached_tokens 要不要从 50,000 里再减一次」。
看答案

普通输入 = 50,000 − 40,000 − 2,000 = 8,000；当量 = 8,000×1 + 40,000×0.1 + 2,000×1.25 = 8,000 + 4,000 + 2,500 = 14,500。不能再减一次：cached_tokens 是 input_tokens 的明细拆分，已经在 50,000 里了——把缓存 token 重复相加是常见错误。

压缩之后，缓存复用会怎样？请用「前缀」这个词解释，并说明「整体归零」对不对。
看答案

压缩替换了历史，所以从「第一个变化的 token」起旧前缀不再匹配——压缩后首次请求复用较少。但「变化点之前」的稳定段仍可能命中，且新前缀随后续追加相处稳定、命中回升。所以「整体归零」不对：压缩改变前缀 → 缓存按前缀退化，不会整体归零。

① Codex 与 ⑨ dsh 在「CLI 缓存键」上有什么差别？能说「dsh 没做缓存」吗？
看答案

① Codex 请求带 prompt_cache_key（默认=会话ID）；⑨ dsh 未发现 CLI 缓存键。不能说「dsh 没做缓存」——只能说「未发现 CLI 缓存键」（「没找到」≠「没有做」）；且服务端命中/TTL 九工具全部 UNOBSERVABLE。

实验台 ⑦ · 理解流程（M02）

一次请求是怎样「长出来」的？

请求是「拼」出来的，不是「聊」出来的——你只控制五块料里的最后一块。这一台把一次任务里的多次请求与工具循环逐步演推，你可以连续播放、暂停、回看任意一步。

先修M01（任务 / 请求 / 工具 / 消息列表）。
读完你能手写一次请求的组成清单，逐块标出「程序给的 / 我给的」。

五块料与四拍循环

① 基础指令+ ② developer 材料+ ③ 对话历史+ ④ 工具说明+ ⑤ 本次用户输入

逐块标来源：①基础指令=程序；②developer 材料=程序；③对话历史=一半程序、一半你；④工具说明=程序；⑤本次输入=你。你只控制了五块里的最后一块。稳定材料排前面、易变内容排后面——这是刻意排布，对前缀缓存有利（M07）。

工具循环四拍：问模型 → 模型要求调工具 → 工具执行写回 → 再问模型。工具执行本身不调用模型，但它两侧各要一次模型请求。

预测题（先猜后看）：从「模型要求调用工具」到「工具结果写回」这段工具执行时间里，模型被调用了几次？
看时间线时留意两件事

① 材料只增不减：每出现一步，列表就变得更长——下一次请求几乎原样带上这里的一切（直到触发整理，见实验台①③）。② 模型调用夹在工具两侧：工具执行本身不调模型，但「要求调用」和「拿到结果后继续」各要一次请求。

配对不变量：调用与结果必须成对

坏结构长什么样后果
A 调用缺结果（悬空调用）[assistant: 调用工具 call_001] 后直接是 user 或新的 assistant上文悬空；服务端按「调用—结果」配对读取，会判结构非法
B 野结果（孤儿结果）[tool: 结果 call_999] 找不到 call_999 这个调用结果无法归属，程序在进入历史时移除孤立条目
C 内容类型不匹配历史里有图片，但本次换用了不支持图片的模型图片在进入请求前被剥离——「材料在你没察觉时被改写」

程序宁可在本地补齐占位或移除孤立条目，也不发送结构非法的请求。这不是礼貌问题，是不变量。

自测先猜，再看答案

AI 停下来等工具结果的那段时间，模型被调用了几次？
A. 0 次，工具是本地跑的　B. 1 次（发出调用那次）　C. 2 次（发出调用 + 拿到结果后继续）
看答案

C。模型先被问「现在做什么」→要求调用工具；工具执行完、结果写入列表后再被问一次「接下来做什么」。工具执行本身不调模型，但两侧各要一次请求。

工具结果出现在消息列表里，说明它一定会出现在下一次请求里。（对/错）
看答案

错。「进入列表」与「出现在下一次请求」之间还有处理步骤：配对与内容检查、限长（M05）、窗口紧张时的整理与摘要替代（M04）。

程序为什么要死守「每个调用都有结果」？如果历史里冒出一条「孤儿结果」，程序怎么处理？
看答案

因为请求是结构化数据，服务端按「调用—结果」对应关系配对读取。缺结果会让上文悬空，缺调用的「野结果」无法归属。程序宁可在本地补齐占位或在进入历史时移除孤立条目，也不发送结构非法的请求。
