# 从十章教程走到真实 Codex CLI

本次运行确认了四种现象：**自动整理后同一轮继续回答、真实输入 `/compact` 后等待新指令、长工具输出保留首尾并裁掉中间、服务端报告缓存输入复用**。动画帮助理解机制；下面的数据来自真实 CLI 与模型调用。

想自己操作，先读同目录的 [README.md](README.md)。想核对数据，读 [public-results.json](public-results.json) 与 [observed](observed/) 中的摘录。摘录保留原始记录的文件名、行号与时间；它不是完整原始日志的复制。完整日志留在独立实验目录，公开包没有认证文件或不可读压缩块正文。

## 2. 自动压缩：新材料换上以后，这一轮接着回答

任务只发了一次：依次完整读取 A、B、C，保留三条硬约束，最后报出三个文件末尾的标记。runner 没有发送主动整理请求，也没有输入 `/compact`。

真实顺序是：

```text
turn/start（唯一一条用户任务）
读取 A → 读取 B → 读取 C
item/started：contextCompaction
rollout：写入 compacted 检查点和 replacement_history
item/completed：contextCompaction
整理后的普通模型请求 → 最终 JSON → turn/completed
```

[事件摘录](observed/automatic-events.jsonl) 对应原始开始与完成记录59、62行，[检查点结构](observed/automatic-checkpoint.json) 对应 rollout 第24行。先安装检查点，再报告整理完成。检查点的新活动历史共6项：3条 developer消息、2条 user消息、1个服务端压缩块。旧工具读取仍留在磁盘记录中，但不再是这份 replacement_history 的直接工具条目。

三个末尾标记不在任务提示词里，只在实际读出的文件里：

```json
{"TAIL_A":"NONCE_3B94A2585BC1","TAIL_B":"NONCE_F18624E3CD52","TAIL_C":"NONCE_575B2680BF92"}
```

整理后最终 JSON 的三个值全部正确。这支持“整理后仍能使用本次观察到的具体信息”。本次三次工具读取都已在整理前完成，整理后继续的是**最终回答**，没有验证剩余工具步骤或多轮连续压缩。

| 时刻 | 实际记录 | 怎样读 |
| --- | ---: | --- |
| 生成读取A的普通请求 | input 12,034 | 第一份结果尚未加入 |
| 生成读取B的普通请求 | input 16,104 | 已有A结果 |
| 生成读取C的普通请求 | input 20,151；总量20,231 | C结果尚未加入 |
| 整理完成的历史估计通知 | total 9,304；input/output均0 | 客户端重算估计，不是输入9,304的一次普通API请求 |
| 整理后回答的普通请求 | input 12,460；cached 11,904；output108 | 新活动材料实际用于继续回答 |

**为什么上表20,231还没到22,000，后来却开始整理？** 这个用量是“准备读C”的请求。C返回之后又加入约19,930字节的渲染文本。固定源码会把新材料计入活动历史的近似估计，所以客户端检查时使用的数值不等于上一请求的用量。

帮助理解的示意演算是 `20,231 + ceil(19,930 / 4) ≈ 25,214`。这不是运行日志直接输出的精确触发值A，元信息、历史结构与推理调整也可能参与实际估算。本次直接看到了自动整理事件，**没有测到触发瞬间的精确A**。

同样，20,151→12,460不能直接算压缩率：前一普通请求还没有C结果，后一请求使用了重新构建的材料。这里分别展示请求规模、历史估计和结构变化，不把不同口径的差值算作节省的计费token。服务端压缩块不可读，也不补写一份假想摘要。

## 3. 手动 `/compact`：整理结束与继续工作是两个动作

先完成缓存实验的三个短任务，再恢复这次会话。在真实CLI输入框键入 `/compact`，隔1秒回车，避免输入被终端当成粘贴正文。整理检查点安装后静候6秒，再发新的核对请求。

[输入与静候时间线](observed/manual-tui-timeline.json) 包括：

| 终端启动后时刻 | 操作或观察 |
| --- | --- |
| 8.001秒 | 键入字面 `/compact` |
| 9.009秒 | 回车提交命令 |
| 随后 | 检查点0→1 |
| 检查点完成后的6秒 | rollout无增长，没有新用户消息 |
| 20.164秒 / 21.174秒 | 键入、提交新的用户核对请求 |
| 25.509秒 | 新任务完成 |

整理前最后普通请求input=14,127；新用户消息之后input=12,446、cached=8,448、output=28。最终三约束JSON正确。

这次旧任务已经结束，直接证明的是**空闲时手动整理完成后等待输入，新指令后继续回答**。没有实测手动整理中断正在运行的工具。新的请求又注入了含三条约束的AGENTS，因而“最终三项答对”不能单独证明约束由压缩块保留；自动实验的三个文件独有标记是更强的信息可用性证据。

不要在shell中执行 `/compact`，也不要把 `codex exec '/compact'` 当成相同实验；后者可能只是普通用户文本。公开包同时给出人工操作步骤和真实PTY驱动。

## 4. 工具输出裁剪：完整日志与模型返回不是同一个出口

原文件136,009字节、1,602行，头、中、尾都含标记。真实工具只执行一次 `cat`，不允许grep或重读。

| 采集位置 | 显式调用max_output_tokens=128 |
| --- | ---: |
| 原文件 / commandExecution.aggregatedOutput | 136,009字节 |
| 嵌套exec返回的output文本 | 622字节 |
| custom_tool_call_output的结果列表经JSON序列化 | 886字节 |
| 首尾标记 | 保留 |
| 中间第802行标记 | 缺失 |
| 裁剪提示 | original_token_count=34003；…33875 tokens truncated… |

[真实调用与裁剪后文本](observed/truncation-call-comparison.json) 对应 rollout 第12、13行。返回值里已能直接验证头尾保留、中间消失；模型最后写 `middle_marker="UNKNOWN"` 与结果相符，但它的回答只是辅助证据。

622含警告、行数和省略标记，886又包含JSON包装。提示中的34,003约等于UTF-8字节数除4向上取整；不是模型tokenizer测出的精确数。不能要求整个JSON恰好等于128×4字节。

补充对照把 `tool_output_token_limit=256`，而实际调用 `max_output_tokens=60000`。[记录](observed/truncation-config-comparison.json) 显示保存JSON=40,712字节，其中第二个text块40,107字节，外层约以10,000预算裁剪；下一普通请求input=12,431。**这次没有捕获最终发给模型的工具项，尚不能直接验证配置256在所有层的精确钳制。** 小的后续输入与历史限长相容，但输入差值不是工具内容的精确token数。

这份结果提示开发者：先说清自己观测的是执行日志、嵌套工具返回、外层工具结果还是最终请求，再解释预算。不要把普通 `function_call_output` 的实现直接套到本次Code Mode路径。

如果中间恰好是唯一错误原因，机械头尾裁剪就会漏掉。读者可另开任务按第802行重读，再比较结果；本次没有执行这一可选练习，不能计入已验证结果。

## 5. 缓存命中：用逐请求usage确认

同一会话连续三次短请求，不用工具，只在末尾追加核对问题。三个完成请求的`last`明细是：

| 请求 | input | cached input | output | cached / input |
| --- | ---: | ---: | ---: | ---: |
| 1 | 11,934 | 0 | 28 | 0% |
| 2 | 14,076 | 11,776 | 28 | 83.66% |
| 3 | 14,127 | 13,952 | 28 | 98.76% |

[缓存事件摘录](observed/cache-events.jsonl) 关联原始记录42、78、114行。第二、三次`cachedInputTokens>0`，是服务端报告输入计算复用的证据。`cached`属于`input`的一部分，不再加到输入总数，也不从窗口容量中删除。官方定义和usage解释见[Prompt Caching指南](https://developers.openai.com/api/docs/guides/prompt-caching)。

三次`cacheWriteInputTokens`均报告0；字段可能因未提供而取缺省值，不能推出写入免费或根本没发生。ChatGPT登录也没有提供API账单，本次不把98.76%写成节费比例。

运行时间可能受网络、推理、输出规模、排队等影响；本次没有成对对照延迟因果。相同前缀也不保证复现时每次命中，要以当次usage为准。

## 6. 把日志对上源码，读者下一步怎么查

正文固定源码帮助理解这次现象，实际发布包的版本则限制实测结论的范围：

- [任务循环的继续判断与自动整理](https://github.com/openai/codex/blob/a07c8ebd57feedc4cf5dfe854c8e9101de54186b/codex-rs/core/src/session/turn.rs#L574-L610)：先判断任务是否还需继续，再检查token条件或新窗口请求。用真实事件确认本次走到了整理节点；不拿源码公式假装日志已暴露精确A。
- [手动整理任务完成与返回](https://github.com/openai/codex/blob/a07c8ebd57feedc4cf5dfe854c8e9101de54186b/codex-rs/core/src/tasks/compact.rs#L27-L111)：整理完成事件不等于自动制造下一个用户目标。对应本次静候与新消息两个阶段。
- [完整日志、普通返回和Code Mode返回](https://github.com/openai/codex/blob/a07c8ebd57feedc4cf5dfe854c8e9101de54186b/codex-rs/core/src/tools/context.rs#L380-L574)：先追踪取的是哪一个出口，再比较预算；它解释为什么“原始输出完整”与“工具返回变短”能同时发生。
- [服务端usage转换](https://github.com/openai/codex/blob/a07c8ebd57feedc4cf5dfe854c8e9101de54186b/codex-rs/codex-api/src/sse/responses.rs#L108-L151)：服务端缓存明细转成CLI的cached_input_tokens；字段映射不等于提供了真实账单。

这次完成的是四个机制的单次运行验证。长期保留率、多次整理的事实漂移、恢复后精确请求体、读者独立迁移能力和跨工具比较，仍需各自设计实验。复现包不会将这些尚未完成的范围写成通过。
