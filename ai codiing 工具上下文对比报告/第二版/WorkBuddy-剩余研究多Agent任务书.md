## 3. 主 Agent 如何组织团队

### 3.1 角色与文件责任

默认按 WorkBuddy 实际并发能力安排：**主 Agent + 最多三个子 Agent 同时工作**。这是推荐上限，先核对实际能力。角色按任务复用，不为每个角色永久占一个运行席位。

| 角色 | 工作 | 交回的东西 | 写入边界 |
| --- | --- | --- | --- |
| 主 Agent | 维护目标、依赖、版本、术语、结论；裁决冲突；整合课程 | 看板、派发单、验收决定、母稿、总矩阵、交接记录 | 公共登记表、总母稿和最终整合文件由主 Agent 单独写。 |
| 工具研究 Agent | 一次负责一个工具的一组具体机制 | 官方来源、证据卡、调用链、例子、源码导读、缺口 | 仅写分配的 `工具/<工具>/` 和该任务工作目录。 |
| 实验 Agent | 准备/执行合成任务，提取可观察证据 | 条件、脚本、原始日志、对照、指标、失败解释 | 仅写对应实验目录；不改其他人的源码快照。 |
| 教学与交互 Agent | 按已验收证据写教学单元、图解和练习 | 单元稿、交互、静态替代、检查记录 | 仅写分配单元和资源目录。 |
| 独立审查 Agent | 重新访问原始证据；检查概念衔接、深度、交互 | 有位置与依据的问题单、通过/返工建议 | 写审查报告，不直接抢写被审查文件。 |

一次可安排“两位工具研究者 + 一位审查者”；进入实验或写作批次时替换角色。审查者与作者分开；另一个 Agent 只改措辞不能算事实审查。Agent 审查也不能替代真实读者测试。

### 3.2 状态和验收

任务状态统一为：`TODO → READY → RUNNING → SUBMITTED → REVIEWING → ACCEPTED`。其他状态为 `REWORK`、`WAITING_USER`、`BLOCKED`。实验运行状态另列 `OBSERVED / NOT_RUN / UNOBSERVABLE / FAILED`，不可混用成“机制不存在”。

主 Agent 每次派发前检查依赖是否已通过，指出具体产物和验收者；每次回收核对文件确实存在、证据能定位、关键结论能解释。返工要写出问题位置、违反的标准、应修改内容与复验方法。

看板至少记录：任务 ID、子任务 ID、目标、依赖、负责人、写入范围、状态、产物路径、审查路径、验收理由、待答问题、下一步。任何任务都不凭“子 Agent 说完成了”直接改为 ACCEPTED。

有歧义时，一次集中提问，并把依赖该答案的任务设为 WAITING_USER；其余已具备输入的任务继续。真正无法观测的闭源机制可用充分的文档/运行证据和边界说明完成研究项；身份尚未确认、尚未检索或应做却未做的核验，仍是缺口。

## 4. 每个工具都交同一份研究包

九工具任务的具体执行要求只在此处定义。工具任务 T04～T06、T08～T13引用它，不各自改变问题模板。

### 4.1 机制覆盖表

逐项登记：请求组装与角色、项目规则/技能加载、资料选择与代码检索、单条工具输出治理、窗口计量与触发、自动/手动压缩、摘要/裁剪/重建、长期记忆、子 Agent 交接、保存/fork/恢复、错误与副作用、缓存及总成本。

对每项填 `有实现 / 有条件实现 / 仅文档可证 / 不适用 / 尚未证实`，并给依据。未找到代码不等于没有实现；接口名和桩函数也不等于默认行为。不能用一份 generic 摘要充当全部机制的研究。

### 4.2 每项机制必须回答

1. 具体解决什么问题？不处理会造成什么结果？
2. 谁调用、什么时机、哪些条件成立？列真实配置名、默认值、覆盖关系、单位和边界。
3. 输入的具体结构是什么？给小消息样例、角色、内容块、调用 ID 和来源。
4. 处理顺序是什么？过滤、选择、裁剪、摘要、落盘分别处理哪份数据？
5. 哪些内容原样留下、变成摘要、移除、保存在外部？给前后对照。
6. 成功后写回哪个状态，下一次模型请求或恢复流程怎样使用？
7. 失败怎样分类、重试与回退，哪些动作已经发生，是否可能重复副作用？
8. 能否找回原文？说明具体读取入口与保存边界。
9. 代价、适用条件和反例是什么？信息保真与质量优先，再谈长度和费用。
10. 什么能通过源码、官方文档或运行记录证明，什么仍不可观测？

### 4.3 每工具最小交付

- `工具概览.md`：身份、版本、语言、Stars与日期、能力覆盖、适用范围。
- `源码导读.md`：至少一条代表性主链路；复杂工具另拆触发、工具结果、持久化、缓存链路。每条走完“调用者 → 条件 → 处理 → 状态写回 → 下一次请求/恢复”，包含失败分支。
- `证据/`：关键结论的证据卡、固定 SHA 链接；闭源部分给官方文档/官方包与观察依据。
- `数据走查.md`：输入、输出、丢失/保留和边界例子，有可算数字。
- `过程观察.md`：可运行机制的最小一次真实观察，或确切不可运行原因；这不是性能对比实验。
- `问题与审查.md`：旧冲突、未决问题、审查修正和最后状态。

源码中文解读保留原语言，先解释例子与数据对象，再解释关键条件、循环、返回值、异步顺序和写回。正式代码与教学伪代码分开标注；核心逻辑的解释不能只剩“请点链接看源码”。

### 4.4 证据卡

```yaml

性质: 事实 / 推断 / 建议

实现状态: 默认 / 条件 / 实验 / 桩或空实现 / 未证实
来源: 官方URL或固定SHA链接、文件、函数、行号
数据走查: 对应样例ID
运行证据: 实验ID，或NOT_RUN及原因
不能证明: 当前证据不能外推到什么
冲突裁决: 支持、限制或撤回哪个旧结论，为什么
核验日期: 实际日期
```

## 5. 任务清单与依赖

以下共 **23 个主任务**。每个主任务在执行时展开成单任务卡；工具研究任务再按“身份/文档、源码、数据走查/观察、独立复核”四小步提交。所有新增任务由主 Agent 赋新子 ID并更新覆盖表，不通过临时扩展改变总目标。

依赖按具体范围检查：子任务只使用已验收的某工具/某机制时，可以先派发该部分；表中完整依赖决定主任务的最终验收。某工具等待身份确认时，比较表可先登记其他已完成工具，课程和平台稿可继续制作只引用已验收结论的单元；总覆盖状态仍保留缺口，最终全量验收等待相关前置完成。

## 7. 实验和修改的执行边界

- 作者将本任务书作为执行指令交给WorkBuddy后，执行范围包含研究、下载允许取得的源码、合成项目、编写与验证教材，以及最小必要的真实实验。真实调用优先使用已有合法登录；首轮每条件3次，不自动扩成大规模基准，记录消耗，额度受限时保存结果并转做其他任务。
- 真实实验前先写规程与成功判据；每次运行在规程中设明确时间/轮数/调用预算边界，先小任务验证入口；默认单轮最多10分钟、20次工具动作，超过时记录原因，再由主Agent调整规程，不自动扩大整个批次。发现重复压缩、无界循环或未知远端结果时停止该轮，保留日志、判断原因后决定恢复路径。
- 新购付费服务、变更全局配置/登录、升级或覆盖已有工具、读写生产/内部项目、联系外部读者或发布文章需要作者另行明确授权。先完成其余已授权工作，集中列出确实需要的动作与原因。
- 实验在独立合成项目运行，不读取内部服务凭据或生产数据；原始日志与公开摘录分开，凭据不写入正文、截图或提交文件。
- 修改范围限于新研究目录与该研究的独立工作区。已有样章、其他Agent正在维护的教程/实验及全局环境保持原状。出现同一路径被修改时主Agent先协调文件归属，不强行覆盖。
- 默认遵循项目配置；Java扩展示例先核对jenv实际版本，遵从`.java-version`或明确构建约束，不自行切换全局JDK。

## 8. 高质量通过标准

每个小任务验收按四类分别打勾，任何必需项不通过都留在REWORK或明确未完成状态。

**事实**：身份与快照明确；数字有单位/条件/配置；调用链走到实际使用；桩、功能门控、文档、源码和运行分别核对；冲突有证据裁决。

**教学**：先问题和可观察例子，再术语；概念衔接有理由；数据结构和源码可用中文解释；核心难点有图或操作、有先猜后反馈的题、有返回补学入口；清楚之外保留真实深度。

**工程**：具体触发值、条件、结构、处理顺序、写回、失败和恢复都有落点；前后材料可追踪；作用过的文件/工具动作与会话替换分开；质量、成本、延迟和恢复的取舍有范围。

**产物**：文件能打开、链接能定位、代码片段与快照一致、图与文字数据一致、交互按各状态实际操作、手机可读、静态与交互相互对应。截图存在不等于已看图；浏览器通过不等于真实模型通过。

验收不以字数、页数、章节数或Stars排名代替上述标准。为保持可执行性，研究Agent提交小结论和小数据走查，主Agent整合为课程；文章目录、实验计划和平台选题分别不能代替成稿、实际运行和图片素材。
