# 「Head First 式」写作规范

> **用途**：做研究、让 AI 写解读/研究报告时，把本文件（或其中的「指令摘要」）附在任务里，并加一句「请按《Head First 式》写作规范撰写」，产出的报告就会像《Head First》系列一样——**把概念直接说明白、读完能记住**。
>
> 版本 v1.1 · 2026-10-11（新增 §8 不足与适用场景） · 适用：解读 / 研究 / 学习类报告、讲义、技术说明文档

---

## 0. 给 AI 的指令摘要（最重要的一节）

**你是被要求按本规范写作的 AI。直接执行以下要求：**

1. 每一节都从**具体场景/问题**开场，禁止以定义开场；
2. 每个核心概念先给一句**「人话直给」**（"说白了，……"），再上术语；
3. 术语首次出现必须**中英对照 + 例子或配图**，不许「裸奔」；
4. 同一概念至少用 **2–3 种姿势**复述（图、例子走查、对话体、类比）；
5. 关键处标**「当心」**：最易踩的坑、最易混淆的概念；
6. 每节留 **1–3 个自测题**（先猜，再看答案）；
7. 每节末尾**压缩要点**；全文结束给一张**速查卡**；
8. 保持严谨：公式、数字、推导按原样保留，不为好读牺牲准确；
9. 中文输出；英文术语保留原词；重要概念补「来源背景 + 易混概念对照」；
10. 注意边界：**概念解释**优先用本风格；参考手册、结论/数据类内容保持结构化惯例（结论先行），不强行套场景与玩笑。

## 1. 什么是「Head First 式」

**一句话：先制造疑问，再给答案；同一概念换 3–5 种姿势反复出场。**

它的本质不是「排版花哨」，而是**让读者的大脑始终处于「作业」状态**——不给它任何被动划过的机会。

**背景**：Head First 是 O'Reilly 的技术书系列，2003 年由 Kathy Sierra 和 Bert Bates 以《Head First Java》开创。它针对的是「教材式写法」的通病——**定义 → 论证 → 例子**：读的时候都懂，合上书就忘。两位作者翻遍记忆与注意的神经科学、学习理论、游戏设计与广告心理学，得出一个朴素结论：**学习不是把信息灌给读者，而是让他的大脑真正「产生一次变化」**。整套书都在回答一个问题：**怎么让这场变化发生**。

## 2. 六条认知原则（「为什么」层面）

1. **视觉优先**——图带着信息、贴着文字放；重要概念配结构图/流程图。
2. **对话口吻**——直接对「你」说话，像懂行的朋友深夜补课；允许幽默。
3. **逼读者动脑**——先给问题让他猜，再给答案；自己推出过的结论才记得牢。
4. **抓住注意**——反直觉案例、意外细节、悬念；平铺直叙 = 大脑直接丢包。
5. **触动情绪**——「这坑我踩过」的痛感、惊讶、好笑；带情绪的记忆优先级更高。
6. **多感官上手**——写一遍、说一遍、跑一遍；多一条通道多一条回忆线索。
7. **（贯穿项）重复**——同一概念换形式反复出场，每次「换件衣服」。

## 3. 篇章结构：报告版「七拍剧本」

Head First 每章都按同一套剧本走。写报告时，把**每一节**当作它的「一章」来搭：

| # | 节拍 | 在报告里落地 |
|---|------|--------------|
| ① | 开场：有人碰上麻烦 | 每节开头 2–3 句场景（谁、遇到了什么问题） |
| ② | 抛概念（大白话版） | "说白了，X 就是……" |
| ③ | 术语落地 | 正式定义 + 英文原词 + 紧邻配图 |
| ④ | 多角度复述 | 图解 / 例子走查 / 对话体 / 类比，选 2–3 种 |
| ⑤ | 动手输出 | 1–3 个「先猜再看答案」的自测题 |
| ⑥ | 答疑纠偏 | 读者视角 FAQ + 「当心」框 |
| ⑦ | 压缩收尾 | 节尾要点（子弹句）；全文给「速查卡」 |

---

## 4. 段落级公式：把任何概念「直接说明白」的五步

1. **先问「它解决什么麻烦」**——2–3 句具体场景，不做抽象铺垫；
2. **一句大白话直给**——"说白了，……"，先把直觉交出去；
3. **术语落地**——正式定义 + 英文原词 + 紧跟一个例子或一张图；
4. **标出坑**——最容易被带偏的点，配一个反例；
5. **留一个自测题**——先猜，答案稍后再揭。

> 核心：**不是把话说简单，而是先让大脑进入「解决问题」模式，再喂信息。**

---

## 5. 禁止项（出现即返工）

- ✗ 概念第一句话就是定义——必须场景/问题先行；
- ✗ 一个概念只用一种讲法——至少两种姿势；
- ✗ 术语裸奔——没解释、没英文原词、没例子；
- ✗ 文字墙——连续多段无图、无例、无互动；
- ✗ 为花哨而花哨——无关玩笑、故事盖过信息密度；
- ✗ 丢严谨——公式、数字、推导必须原样保留，严肃内容不戏说化。

> 备注：Head First 原书也被批评过「啰嗦、难当工具书」。所以应用时**取其骨架**——先问题后答案、多姿势复述、逼输出；同时**控制篇幅**，不为风格牺牲信息密度。

## 6. 示例：同一个概念的两种写法

**✗ 老写法（定义式）**

> Embedding 是将离散对象映射到连续向量空间的技术，通过训练使语义相近的对象距离更近，从而支持相似度计算与检索。

**✓ Head First 式**

> **场景**：图书馆里没有书名，也不许翻页——怎么找出「和手上这本气质最像」的另一本？
> **人话直给**：给每本书偷偷量一组「气质尺寸」——文风、情绪、题材……量完你会发现，气质像的书，这组数字也挨得近。
> **术语落地**：这组坐标就是 embedding（嵌入）——"像不像"从此可以算距离。
> **当心**：坐标量歪了，「果园的苹果」会和「苹果公司」被拍成亲兄弟——这就是「上下文决定语义」要解决的问题。
> **自测**：「银行（河边的）」和「银行（存钱的）」，坐标会一样吗？先猜，答案见下文。

- ☐ 每个核心概念是否有一句「人话直给」？
- ☐ 术语是否中英对照 + 例子/配图？
- ☐ 每个概念是否至少用了两种姿势复述？
- ☐ 是否标了「当心」坑点？
- ☐ 是否有自测题、节尾要点、全文速查卡？
- ☐ 是否保留严谨性、控制篇幅（没有变成啰嗦戏说）？

## 8. 不足与适用场景（先知道边界，再决定用不用）

**不足（用之前要知道的代价）：**

1. **啰嗦、信息密度低**——同一内容篇幅通常膨胀 1.5–2 倍；对熟悉主题的读者是负担。
2. **不适合当工具书**——概念散在场景与故事里，想「查定义」很难定位；它是为「从零学会」设计的，不是为「快速查阅」设计的。
3. **写作成本高**——每个概念都要配场景、例子、（可能的）图与自测；素材不足时硬凑花样，会显得尬。
4. **有稀释严肃性的风险**——公式、推导、合规/财务结论类内容过度口语化会显得轻浮甚至产生歧义；数字与结论必须保持原样。
5. **不是所有读者都吃这套**——原书作者也承认有人就是讨厌这种风格；逻辑导向、只想看结论的读者需要「速览通道」。
6. **风格可能过载**——场景、玩笑、自测堆太多会喧宾夺主（原书也被批评过「花哨盖过内容」）。

**适合的场景（优先用）：**

- 学习 / 入门：新概念、新领域、给非专家解释专业内容；
- 需要「记住并会用」的解读：课程笔记、教程、方案科普、算法直觉；
- 概念多、术语密的报告：多姿势复述 + 人话直给正是为此而生；
- 跨背景沟通：给产品 / 运营 / 管理层讲技术。

**不适合的场景（慎用或换写法）：**

- 参考手册、API 文档、速查表——改用结构化表格 + 干净定义；
- 决策备忘录 / 结论性汇报——结论先行更合适，只在「解释」部分局部用 HF 式；
- 严肃推导、合规 / 法律 / 财务正式文本——保留严谨文体，最多借用「当心框」「示例」等局部元素；
- 有硬篇幅约束的交付物（一页纸简报）。

**折中原则**：HF 式的收益集中在「解释概念」，不在「传达结论」。一份文档可以混搭——结论与数据用传统写法，概念解释用 HF 式，并在开头给「30 秒速览」照顾赶时间的读者。

## 9. 怎么用这份文档

- **方式 A（推荐）**：研究任务 + 本文件，附一句：「请按《Head First 式》写作规范撰写关于 ____ 的报告。」
- **方式 B**：把 **§0 指令摘要**贴进常用 AI 工具的自定义指令 / AGENTS.md，让风格默认生效。
- **方式 C**：报告不合格时，把 **§5 禁止项**贴回去要求返工。
- **极简咒语**（不想带整份文件时直接用）：

> 用 Head First 风格写：先场景后概念；概念先大白话再上术语；术语中英对照配例子；每个概念换 2–3 种姿势讲；标坑点；加自测；结尾速查卡。
