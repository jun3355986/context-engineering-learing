压缩之后，它还记得你的哪句话？

你第一句就说了“不许改方法签名”，聊了一下午之后，Codex 还是改了。这一章把压缩后的新上下文拆开给你看：哪些东西原样留下，哪些只剩一句转述，以及你该把重要的要求放在哪里。

读完你能做到

  1. 说出压缩后 Codex 原样带上的三样东西。
  2. 解释为什么“粘贴一大段日志”会把你更早的要求挤掉。
  3. 为一条要求选对位置：规则文件、任务笔记，还是最新一条消息。
01 · 一个真实会发生的下午

“我第一句话就说过了啊”

小周在一个老 Java 项目里让 Codex 重构 UserService。下面是这次会话的主要节点。

小周 · 第 1 条重构 UserService。注意：public 方法签名一个都不许改，getUser(id) 必须兼容老客户端。
Codex明白。我先读一下 UserService 和它的调用方。
⋯ 小周粘贴了三大段 Maven 测试日志和堆栈，Codex 跑了几十条命令 ⋯
Codex 自动压缩了一次上下文
小周 · 第 7 条好，接下来把缓存接上，用 Caffeine。
Codex已完成。为了传入缓存策略，我把 getUser(id) 改成了 getUser(id, CacheOptions)，并更新了 12 处调用。

它没有“变笨”。是第 1 条消息没能进入压缩后的新上下文。

这段对话是为教学编写的情景，后面的模拟器会用同一组消息复现它。

02 · 先猜一下

压缩之后，哪些东西会原样回到上下文？

点选你认为会原样保留的卡片，然后揭晓。“原样”指一字不差地放回去，不是被别人转述。

03 · 一张图看懂

压缩后的新上下文只有三层

压缩时，Codex 把旧的活动历史换成一份新材料。新材料只由下面三层组成：

① 重建

当前的指令和规则

系统与开发者指令、AGENTS.md、环境信息。按“现在”重新生成，不是从旧历史里抄。

② 原话

你最近说的话

只收你发出的消息，从最新往回装，装满预算就停。边界那条只留头尾。

③ 摘要

一份交接摘要

模型按固定提示写的“进展、决定、约束、下一步”。

不原样带上

Codex 的回答、命令和输出、推理过程

它们还在磁盘的会话记录里（见样章 01），但不再原样进入新上下文。

一句人话压缩后，Codex 原样带上的只有「规则文件 + 你最近的话 + 一份摘要」。它自己说过的话、跑过的命令输出，都只剩摘要里的转述。

第 ② 层的预算叫原话预算。在本章主讲的文字摘要路线里，它是 20,000 token。Codex 用字节估算 token：大约 4 个字节算 1 个。所以 20,000 token 约等于 8 万个英文字符，或 2.6 万个汉字。

别把它和“什么时候压缩”混在一起

20,000 不是“聊到 2 万 token 就压缩”。什么时候压缩由上下文窗口和自动压缩线决定；20,000 只决定压缩之后留下多少原话。

    你应该看到了三件事

    1. 粘贴进对话的日志，算作你的原话。它们离压缩最近，最先装进预算，把第 1 条挤了出去。
    2. 让 Codex 自己读日志，第 1 条就留下了。命令输出不进原话预算，压缩后需要时再跑一次就行。

    远端路线预算更大，短会话里第 1 条能留下；勾上「再多聊一阵」，它一样会被挤出去。预算大只是推迟问题。

    05 · 第 ③ 层是怎么写出来的

    摘要是同一个模型，按一段固定提示写的

    压缩时，Codex 把当前历史连同下面这段提示发给模型，让它写一份“交给下一个模型”的交接摘要。这是源码里的原文：

    压缩提示原文prompts/templates/compact/prompt.md
    You are performing a CONTEXT CHECKPOINT COMPACTION. Create a handoff summary for another LLM that will resume the task.

Include:
- Current progress and key decisions made
- Important context, constraints, or user preferences
- What remains to be done (clear next steps)
- Any critical data, examples, or references needed to continue

Be concise, structured, and focused on helping the next LLM seamlessly continue the work.
    中文意思
    你在做一次上下文检查点压缩。为接手任务的另一个模型写一份交接摘要，包含：
    • 当前进展和关键决定
    • 重要背景、约束或用户偏好
    • 还剩什么要做
    • 继续工作需要的关键数据、例子或引用
    要简洁、有结构，帮下一个模型无缝接上。

    提示里明确要求写“约束”。所以小周那句话可能出现在摘要里。但这是对模型的要求，不是程序的保证：摘要要压得很短，模型会自己挑重点。

    没有愚蠢的问题

    写摘要时，模型能看到我的第 1 条消息吗？
    通常能，因为写摘要的请求带着当前历史。但如果历史已经长到连这次请求都放不下，Codex 会从这份副本里删掉最早的一项再试。最早的内容最容易在这一步消失。
    摘要会不会把上次的摘要当成我的原话保留？
    不会。旧摘要带着固定前缀，挑原话时会被认出来并跳过。
    能改这段提示吗？
    源码里有一个配置项 compact_prompt，设置后替换这段默认提示。你可以要求“逐字保留用户提出的所有约束”。摘要仍由模型来写，只是要求变了。
    压缩多了会怎样？
    文字路线每次压缩成功后，Codex 会提示：长会话和多次压缩会降低准确性，能开新会话就开。上一份摘要不会原样留下，只作为写新摘要的材料。转述的转述，细节容易越来越少。
    06 · 如果你来设计

    换你做 Codex：压缩时该留什么？

    先别看 Codex 的答案。假设你要设计这一步，手上有三个方案。点开看各自的代价。

    最近 N 轮的用户消息、回答、命令输出全部原样保留

    好处最近的细节一点不丢，模型接着干最顺。
    代价一次命令输出可能就有上万 token。留下的大多是能重新读到的日志，压缩省下的空间很快又被占满。

    旧历史全部换成一份摘要

    好处最省空间，压缩后上下文非常干净。
    代价你说过的每一句话都要靠模型转述。转述漏一句，就再也没有原文可以对照。

    原样保留用户说的话（有预算），其余交给摘要 —— Codex 的选择

    好处你的意图有原文；日志和文件能重新读，不必原样保留。
    代价预算是按“新到旧”花的，不看内容重要不重要。早期的关键要求最先被挤掉。

    为什么这样分？设计推断

    源码没有写理由。一个说得通的解释是：按“能不能重新取得”来分。命令输出和文件内容可以重新跑、重新读；Codex 自己的回答可能含有中途的错误判断；只有你的话是任务意图的唯一来源，丢了就找不回来。

    方案 C 留下了一个漏洞：它保护“你说过的话”，但不分轻重。下一节就是补这个漏洞的办法。

    07 · 你能做什么

    按“要活多久”给要求找位置

    放在哪里适合什么为什么能活下来代价
    AGENTS.md整个项目都成立的规则：不改公共 API、用哪个测试命令属于第 ① 层，每次压缩都重新装入所有项目文档共享一个默认 32 KiB 预算，超出的尾部不加载；写多了反而丢
    任务笔记文件
    例如 PLAN.md    		这次任务的进度、决定、待办存在磁盘上，压缩碰不到；要用时重新读Codex 要主动去读。在 AGENTS.md 里写一句“开始前先读 PLAN.md”
    最新一条消息里重申眼下这一步最怕违反的约束最新原话最先装进预算要靠你记得每次说
    让 Codex 自己读日志测试输出、堆栈、构建日志不占原话预算，给更早的要求留位置命令输出会更快填满窗口，压缩可能更早发生
    开一个新会话任务换了方向，或已经压缩过好几次从干净的上下文开始，配合笔记文件交接要手动交接：先让 Codex 把进度写进笔记

    小周的会话应该这样开头

    AGENTS.md 里写：public 方法签名不得修改；开始前先读 PLAN.md。
    第 1 条消息只说任务：“重构 UserService，进度记在 PLAN.md。”
    测试挂了就说“你跑一下 mvn test 看看”，不贴日志。

    08 · 带去看其他工具

    四个问题，看懂任何一个工具的压缩

    Claude Code、Gemini CLI 等工具也会压缩，答案各不相同。拿这四个问题去问，比记结论有用：

    1. 压缩后原样留下什么？Codex：规则、近期用户原话、摘要。
    2. 规则文件会不会重新装入？Codex：会。
    3. 摘要你能不能读、能不能改提示？Codex：文字路线能读，可用 compact_prompt 改提示；远端路线是加密块。
    4. 压缩失败时丢的是什么？Codex：写摘要的请求超窗时，只从这份请求副本里删最早的条目再试；压缩没成功，就不替换旧历史。

    对比篇会逐个工具回答这四个问题，每个答案都附源码或实验。

    11 · 真实运行

    在你自己的电脑上看见它

    已实测压缩发生在任务中途，任务照样完成

    环境：codex-cli 0.152.0，模型 gpt-5.6-sol，ChatGPT 登录，2026-10-14。为了用少量资料触发压缩，把窗口设为 100,000、自动压缩线设为 22,000（配置项 model_auto_compact_token_limit；这是实验配置，不是默认值）。

    任务：依次读取 A、B、C 三份资料，再按提示里的约束输出 JSON。读完第三份后自动压缩发生；会话记录里写入一个压缩检查点，新上下文有 6 项：5 条消息加 1 个服务端压缩块。压缩后的请求输入为 12,460 token，最终 JSON 里三份资料各自的结尾标记全部正确。

    “1 个服务端压缩块”说明这次走的是远端压缩路线。

    待运行要求放在哪里，压缩后还守不守

    这个实验验证本章的核心结论，还没有跑过。步骤已经写好，你可以先跑。

    准备：一个小 Java 项目，含 UserService.getUser(id) 及其调用方
配置：调低 model_auto_compact_token_limit，让压缩在第 5～6 轮前发生
三组，同一任务，每组至少跑 3 次：
  组 1  要求只写在第 1 条消息；中途粘贴日志，总量超过保留预算
  组 2  同组 1，但日志改为让 Codex 自己跑 mvn test 读取
  组 3  要求写进 AGENTS.md；第 1 条消息不提
检查：
  ① 会话记录里压缩检查点的新上下文，是否含那条要求的原文
  ② git diff 里 getUser 的签名是否被改

    远端路线的摘要是加密的，只能检查 ①里“原话”那部分；判断以 ② 为准。要让组 1 的要求被挤出，粘贴总量需要超过 64,000 token。

    12 · 留给想深挖的你

    边界、依据与事实状态

    适用边界：本章的简化在哪里
    • 两条路线。本章以文字摘要路线讲解，因为它的每一步都能在源码里读到。远端路线的候选还包括扩展钩子注入的提示、另一个代理发来的消息等；部分工具输出和开发者消息需要功能开关才会保留。远端摘要是加密内容，客户端保存并传递，但读不到。
    • 哪条路线生效取决于提供方和配置。本章没有核对完整的选择条件。
    • 边界截断。放不下的那条消息会裁成头尾两段，中间删掉，按字节估算。之后不会再回头装更早的短消息。
    • 图片。文字路线里，带图片的消息只留文字部分，图片不保留。
    • 插入位置。重建的规则实际插在“最后一条用户消息”之前，摘要放在最后。三层图为了好懂按类别画。
    • 压缩前后钩子。源码里压缩前后会运行钩子，钩子可以中止这次压缩。本章没有展开配置方式。
    • AGENTS.md 的尾部。超出 32 KiB 共享预算的部分不加载，压缩后重建也不会补回。
    • 版本。源码讲解固定在提交 a07c8eb；实验用的 CLI 是 0.152.0。两者不保证每个内部函数完全相同。
