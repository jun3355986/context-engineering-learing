第二部分 · 主线·第 11 章

会话时间线：恢复、分叉与回退

Agent 的“记忆”不在模型里，在磁盘上。会话日志只追加，恢复不是重放整段，而是“最近检查点 + 之后的后缀”；分叉不是复制上下文，而是换一个叶子；回退不是删行，而是把模型可见的历史截短，日志本身一行不少。

  • 约 19 分钟
  • 1 个交互
  • L2 → L3

读完你能做到

  1. 给定一份日志和检查点位置，算出恢复时要回放哪些行、模型最终看到什么。
  2. 区分“回退对话”与“回退文件”两种语义，并说出各自可逆与不可逆的部分。
  3. 在“同文件换叶”和“复制成新会话”之间做选择，并解释切分支时摘要的代价。

01 · 先分清三样东西

“它记得结论，却不记得那次失败的测试”

第二天早上，你用 --continue 接上昨晚的会话。Agent 准确说出“把 legacy.ts 改成 type-only import”，还记得你要求“不要动 public API”。你问它：“昨晚那两次测试为什么失败？”它停了一下，说：“我需要重新跑一遍。”

这不是记忆坏了。昨晚的会话在跑到一半时触发过压缩，检查点之前那些测试日志被摘要替换了；恢复时，系统只把检查点里的替换历史和检查点之后的新消息装回模型，不会把更早的原始工具输出重新读一遍。结论留下了，失败栈没有。

要理解这件事，先分清三样东西：

  • 日志（log）：只追加的事实记录。每条输入、每次工具调用、每个压缩检查点，都按顺序写进去，旧行不删。它是审计与恢复的唯一真实来源。
  • 检查点（checkpoint）：日志里的一种特殊行。它不记录“发生了什么”，而记录“从这一行开始，模型可见历史应该长什么样”。压缩检查点通常带一份替换历史或一个摘要。
  • 投影（projection）：从日志和检查点算出来的、真正发给模型的消息序列。同一个日志，可以有多个投影；换模型、换压缩策略、换分支，投影都可能不同。

恢复不是“把日志从头读一遍”，而是“找到最近的检查点，再把之后的后缀接上”。

这条规则带来三个直接后果。第一，恢复成本与“上次检查点之后写了多少”成正比，不与整个会话长度成正比。第二，检查点必须自包含：它得单独说明“模型应该看到哪些消息”，否则后缀接不上。第三，压缩不可逆，但日志可逆：摘要替换了投影，原始行还在磁盘上，只是不再进入模型。

分叉和回退则是同一套结构的两个操作。分叉是在树上加一个新叶子：父节点不变，新节点从某一点长出去；如果写到新文件，就是“另开一本账”。回退是把 HEAD 移到树上的另一个节点：模型可见历史变成“从根到新 HEAD 的路径”，被绕过的节点仍在日志里，只是不在路径上。一个只追加的系统，靠“指针 + 标记”实现撤销，而不是靠删除。

日志在，不等于状态在

对话可以精确回退到某一条消息，文件却不一定。多数工具把“回退对话”和“回退文件”做成两件事：前者只改投影，后者要覆盖工作区。两者不同步时，模型会看到一个“代码已经改了、但对话说还没改”的世界。这是本章最后一组取舍。

02 · Codex 主线

一条只追加的 rollout，和一个自包含的检查点

Codex 把会话写成 JSONL 格式的 rollout：每条输入、工具调用、压缩检查点、world state 都按顺序追加，旧记录不删除。恢复时，它先找到最新的 CompactedItem，用里面的 replacement_history 作为起点，再回放之后的后缀。提交固定为 76ed3b4。

2.1 日志：记录“发生过”，不记录“现在该看什么”

rollout 的职责是完整：模型收到什么、调用了什么工具、返回了什么、什么时候压缩过，都写进去。源码里有一句关键注释：内存中的 live 历史可以被截断，但 rollout 里保存的是原始载荷。history.rs#L520-L545 已核实 这句话把“事实”和“投影”分开了：日志是事实，内存历史只是当前投影。

为什么必须只追加。第一，审计：你事后能查清“它当时到底看到了什么”，而不是只看摘要。第二，恢复：检查点之后的任意一条消息都可以重放。第三，分叉：从旧节点长出新枝时，旧路径不能被改写。代价是日志会膨胀，而且包含完整的文件内容和工具输出，磁盘、备份、隐私都要跟着处理。多数工具的做法是“不自动删，交给上层清理”，Codex 的事实卡片也没有记录自动过期策略。

2.2 检查点：存的是“替换后的历史”，不是“摘要文本”

CompactedItem 里带四类东西：replacement_history（替换后的完整历史）、窗口编号与前后窗口 id、当时的 token 用量记录、以及恢复所需的 resume_metadata。session/mod.rs#L4321-L4356 已核实 注意它存的是“模型应该看到的那串消息”，不是“一段摘要 + 一段原文”的配方。

为什么存替换历史。因为恢复时不想再跑一次压缩。压缩是一次模型调用：有成本、有延迟，而且输出不确定；如果恢复时重跑，同一个会话两次打开可能得到不同的历史。代价是检查点本身很大：它把摘要和保留段又复制了一遍，和原始日志有重叠。压缩次数越多，检查点越多，磁盘上的重复也越多。

这也解释了一个常见误解：“压缩后原文被删了。” 原文没有被删，它还在更早的日志行里；只是最新检查点的替换历史不再引用它。你仍然可以用工具读日志，但模型不会自动看到。

2.3 恢复：找最新检查点，只回放后缀

rollout_reconstruction 先扫描日志，选出最新的检查点，然后把检查点之后的后缀逐条回放：普通响应项、保留上下文、子代理的代理间消息都在其中。rollout_reconstruction.rs#L485-L520 已核实 这条链路也把上一章的子代理接回来了：子代理完成消息是日志里的一种输入项，恢复时会跟着后缀一起回来。

为什么不是从头重放。从头重放要把整个会话重新组装一遍，token 成本高、启动慢；更麻烦的是，压缩是模型调用，重放时要么重跑压缩（不确定），要么在重放过程中再识别一次检查点（等于又做了一遍恢复）。代价是检查点必须“自包含到可以直接当历史用”：少一个字段，后缀就可能接在一段不完整的历史上。实现上通常还要校验窗口编号与模型，防止拿旧模型的检查点喂给新模型。

2.4 分叉：协议层有参数，core 侧靠历史版本

Codex 在 app-server 协议里提供 ThreadForkParams，core 侧用历史版本号与检查点支持“从某条历史继续”。thread.rs#L544-L560 已核实 从参数命名看，它把“回到过去”表达为一次 fork（新线程），而不是在原名上截断；新线程与旧线程在 UI 里怎么呈现，本快照没有核实。

为什么用新线程而不是原地截断。原地截断会让“之前的结论”与“现在继续的方向”混在同一个 id 下，审计时分不清哪段是旧路、哪段是新路；新线程天然把两条路分开，也更容易并行。代价是线程数量膨胀，用户要自己管理“哪个 fork 是有效的”；如果 UI 不显示父子关系，过几天就找不到源头。本快照只确认了协议参数，TUI 的具体 fork 交互没有核实1。

2.5 回退：本快照所见的是线程分叉

本快照的 core 与协议里能找到的是 fork；“在原名上截断到某条消息”的 rewind 入口没有找到，和上一节是同一个空白。这意味着 Codex 的“撤销上一轮”更像是：从那条消息之前 fork 一个新线程，或者恢复一个更早的线程；被放弃的那一轮仍留在旧线程里。对使用者来说，效果是“回到过去继续”，但对上下文来说，新线程不会自动继承旧线程那轮的中间工具输出——除非 fork 点就在它之前。

为什么可以接受。Codex 把“会话”当成可分支的持久对象，而不是一条可随意剪接的录音带。分支比剪接更安全：任何一次“回到过去”都不会破坏已有记录。代价是“我只想删掉刚才那句话”这种小操作，成本比一个 /rewind 高；用户要理解 fork 与恢复的区别。

✓要点小结

  • rollout 只追加：记录事实，不决定投影；内存历史可以被截断，日志不会。
  • 检查点存的是替换后的完整历史，恢复时不再重跑压缩，代价是检查点体积与重复。
  • 恢复 = 最新检查点 + 后缀回放；成本与后缀长度成正比。
  • Codex 把分支表达为新线程（ThreadForkParams），旧线程保留；逐消息 rewind 未见入口。
  • “压缩不可逆”指的是投影不可逆，不是日志被删。

    04 · 七个工具

    同一棵树，七种走法

    下面七个工具各有一个弹窗。可以按“树在哪里”分成三派：JSONL 树（Claude Code、pi、oh-my-pi）用 parentUuid / parentId 在同一个文件里成树；数据库投影（opencode v1/v2）把消息写进 SQLite，再按压缩边界重排；日志 + 表面（Grok Build、DeepSeek Harness）用只追加日志加一个“可见视图”，回退靠标记或 replace。pi 有树但没有 checkpoint/rewind；opencode v1/v2 没有树也没有 rewind；dsh 连 rewind 都没有。这些空白和“有”一样重要。弹窗里的“设计意图”是作者根据源码结构做的分析，不是工具作者的自述4。

    键盘：Esc 关闭；Tab 在弹窗内循环。Claude Code 的结论来自非官方 v2.1.88 源码，只代表该版本。

    三个必须如实写的空白。opencode v1 与 v2 都只有 parentID 单亲关系：子会话算一层分支，但没有“树状多分支”，也没有 rewind；v1 的 revert 是文件回滚，不是对话回退。dsh 没有 /rewind、没有 undo、没有树状多分支，回退能力在本版不存在3。pi 有树与 /fork，但没有 checkpoint/rewind，回退靠树导航或 fork。把这三处写成“有”，会让读者对能力边界产生错误预期。Claude Code 的 /rewind 内部，文件回退有明确实现，对话侧的截断则由选择器 UI 完成，后者是【推断】2。

    06 · 设计取舍

    为什么“回到过去”有六种代价

    下面六组取舍，决定了同一份日志能支持什么样的恢复、分叉与回退。每组都给出两派做法与一句代价。它们不是互斥的：一个工具可以同时选“日志为源”和“检查点 + 后缀”，但在具体实现上总要付出某一面的成本。

    取舍一：日志为源，还是数据库投影

    日志派（Codex、Claude Code、pi、oh-my-pi、Grok Build、dsh）把 JSONL / 事件日志当唯一真实来源，投影现场计算。好处是可读、可审计、可用文本工具查；坏处是每次启动都要解析、校验、重放，日志大了会慢。数据库派（opencode v1/v2）把消息与 part 写进 SQLite，查询与分页快，投影由 filterCompacted 或 seq 边界现场重排。

    代价：数据库查询快，但“真实来源”变成二进制文件，出了问题不能 cat 一行看；迁移、备份、跨版本兼容都要额外处理。日志派透明，但大文件读取有上限（Claude Code 单次读 50 MB），超过就只能放弃。

    取舍二：检查点 + 后缀，还是全量重放

    检查点派（Codex、pi、opencode v1/v2）只回放最近检查点之后的部分，恢复成本与“上次压缩之后写了多少”成正比。全量重放派（更朴素的做法）从第一条消息开始重建，逻辑简单，不依赖检查点字段是否完整。

    代价：检查点快，但检查点必须自包含，字段少了就接不上；而且压缩次数越多，检查点越多，磁盘重复越大。全量重放简单，但长会话启动慢，而且如果重放过程中要重新判断“哪里压缩过”，逻辑会变得和恢复一样复杂。多数成熟工具最终都会选检查点，因为启动延迟是用户能直接感知的。

    取舍三：同文件换叶，还是复制成新会话

    同文件换叶派（pi 的 /tree、oh-my-pi 的 /tree）在同一个 JSONL 里移动 HEAD，分支共享一份日志，磁盘省、关系清楚。新文件派（pi 的 /fork、omp 的 createBranchedSession、Grok 的 /fork、opencode 的 --fork）把选中分支复制成新会话，父子关系变弱，但两条路可以独立演化。

    代价：同文件换叶省空间，但日志会越来越长，分支之间的 id 关系也更难读；一旦文件损坏，所有分支一起坏。新文件隔离好、易分享，但复制要花时间与磁盘，而且“哪份是最新的”要靠标题或外部索引维护。Grok 的 /fork 还支持可选 worktree，把文件也一起隔离，代价是合并。

    取舍四：回退对话，还是回退文件

    只回退对话派（Grok TUI 默认 conversation_only、pi 的树导航、opencode v2 的 fork）只改变模型可见历史，磁盘不动。它可逆：你还能再切回原来的节点，文件也没被覆盖。同时回退文件派（Claude Code 的 fileHistoryRewind、Grok shell 的 all / files_only、opencode v1 的 revert）会把工作区恢复到某个快照，通常不可逆。

    代价：只回退对话会让“对话说没改、文件其实改了”同时存在，模型下一轮可能基于错误前提行动；同时回退文件能让状态一致，但会覆盖你在这之后手动做的修改。Grok 的做法是先做只读预览、检测外部修改（modified_externally / deleted_externally / created_externally）再写回，这是在“不可逆”上再加一道确认。Claude Code 的快照上限 100 个，超过就只剩最近的历史，老节点回不去。

    取舍五：切分支时生成摘要，还是直接切

    摘要派（pi 的 BranchSummaryEntry、omp 的 branchWithSummary() / rewind(report)）在离开一条分支时，把被放弃的路径压成一条摘要，挂在跳转点。新分支的模型知道“刚才试过什么、为什么放弃”。直接切派只移动 HEAD，不生成任何摘要，历史更短、更干净。

    代价：摘要要再调一次模型（pi 的预算 contextWindow - 16,384，输出上限 4,096；omp 文档写 2,048），有成本也有延迟；摘要还会把“被放弃路径”的细节变成二手信息，模型可能误以为那就是当前状态。直接切最便宜，但模型可能重复刚被放弃的方案。omp 的 branchSummary.enabled 默认 false，说明它认为这笔钱不必默认花。

    取舍六：检查点粒度，按 prompt 还是按请求

    粗粒度派（Grok Build 每个用户 prompt 一个回退点）让用户容易理解：“回到我上一次说话之前”。细粒度派（dsh 在每个模型请求前、每个顶层工具产生外部副作用前、下一步开始前都刷盘）恢复更精确，能对上“工具已经改了文件”这种边界。中间派（Claude Code 每条消息一个文件快照，未变化的文件复用上一版本）在成本与精度之间折中。

    代价：粒度越细，写入越多、日志越大，恢复时要重放的片段也越多；粒度越粗，回退越像“重来一轮”，中间的半成品状态保不住。选哪种，取决于你更怕“丢了一步”还是更怕“写得太频繁”。dsh 的 fail-closed 策略（写不成功就不跑）把一致性放在可用性之前，代价是一次磁盘故障就会阻塞整个 turn。

    07 · 小测验

    三道题，检验你是否真的会恢复

    Q1

    一份日志有 120 行，最新检查点在第 80 行，检查点的替换历史已经包含前 70 行的摘要与最近 10 行原文。恢复时要回放多少行？为什么不是 120 行？

    解析

    回放第 81–120 行，约 40 行后缀；检查点本身提供“起点历史”，不需要再回放 1–79 行。不是 120 行，因为恢复用的是“检查点 + 后缀”，不是全量重放；也不是 0 行，因为检查点之后的新消息必须接上，否则模型看不到昨晚最后几轮。见图 11-1与 2.3 恢复。

    Q2

    回退到 #3 之后，日志行数会减少吗？文件会跟着回退吗？如果两者不一致，会出什么问题？

    解析

    日志不会减少：回退通常是追加一条标记（Grok 的 RewindMarker）或移动 HEAD，被绕过的节点仍在。文件是否回退取决于模式：Grok TUI 默认 conversation_only 不动文件，shell 的 all / files_only 才回滚；Claude Code 的 /rewind 会走文件快照。不一致时，模型看到的历史说“还没改”，磁盘却已经改了，下一轮可能基于错误前提继续。见取舍四与演示。

    Q3

    你要在一个长会话里试两条重构路线，最后只保留一条。选“同文件换叶 + 分支摘要”，还是“每次 fork 成新文件”？各自的代价是什么？

    解析

    同文件换叶省磁盘、分支关系清楚，切回来快；代价是日志越来越长、文件损坏会带走所有分支，而且切分支时要么丢上下文、要么花一次摘要调用。新文件隔离好、易分享、可并行，代价是复制耗时与磁盘，且要自己维护“哪份有效”。如果两条路线会同时改代码，还要叠 worktree；如果只是试探，同文件换叶 + 摘要更轻。见取舍三与取舍五。

    工具弹窗 · pi

    pi

    oh-my-pi

    会话是只追加的 JSONL 条目日志，靠 id / parentId 成树。压缩只追加 CompactionEntry（含 summary、firstKeptEntryId、tokensBefore、method 等），不删除原始条目。/clear 写入 reset_boundary：晚于最新压缩的边界会让摘要与保留段一起失效，只发射 reset 之后的条目。/tree 是同文件叶子移动，离开的分支可生成 BranchSummaryEntry，用 branchWithSummary() 挂在导航目标上；createBranchedSession() 才另写新文件。checkpoint / rewind 是模型可调用的两个工具：checkpoint(goal) 记录当前条目 id 与消息计数；rewind(report) 把探索报告作为分支摘要，把叶子切回 checkpoint 位置，再追加一条 rewind-report 自定义消息；同一 checkpoint 只能 rewind 一次。

    工具弹窗 · dsh

    DeepSeek Harness

    会话是只追加的 SessionEvent 日志，模型历史由 deriveMessages() 从“surface”派生：surface 是“产生消息的事件”的有序视图，每个消息事件必须带 surfaceOp——append（进入尾部）或 {op:'replace', startSeq, endSeq}（遮蔽一段既有节点）。被 replace 遮蔽的原始事件仍在日志里，但不再出现在派生历史中，因此重放是确定性的。缓存策略：纯尾部增长 O(新增节点)，只有 replacement 或消息投影变化才整体重建。恢复：持久化后端读日志，session-checkpoint-policy 在每个模型请求前、每个顶层工具产生外部副作用前、下一步开始前刷盘（fail-closed：写不成功就不跑），崩溃后用合成 closer 收尾未完成的 turn/step，没有“继续未完成 turn”的部分恢复。分叉用 buildForkSeed(events, boundary) 复制到边界的前缀，追加 session/end-seed {inherited:true}，再用 openTurnClosers 补齐未闭合的 step/turn。没有 /rewind、没有 undo、没有树状多分支。

    关键参数与默认值
    日志追加式 SessionEvent，JSONL 后端；surface 操作 append / replace；检查点在模型请求前 / 顶层工具前 / 下一步前；分叉 = 前缀 + session/end-seed + 合成 closers；回退 / undo 无。已核实
    设计意图
    用“日志 + 可见视图”两层结构同时满足“不可变审计”与“可压缩 / 可替换”，并把缓存失效收敛到 contentGeneration 一个变量。代价是没有面向用户的回退入口，想回到过去只能 fork 或读日志；崩溃恢复也只保证一致，不保证续跑。推断
    来源
    core/session/src/index.ts#L966-L1005 · surface.ts#L49-L56 · fork.ts#L1-L30 · session-checkpoint-policy/README.md#L12

    “无 rewind”是按“源码未找到”得出的【推断】，不是官方声明；插件层是否提供不在本次核对范围内。dsh 的 fork 是“前缀 + 合成 closer”，不是在同一文件里换叶。
