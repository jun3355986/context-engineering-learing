第二部分 · 主线·第 13 章

缓存友好设计：让前缀只增不改

上下文管理的成本大头，往往不是“装了多少”，而是“每次重装多少”。前缀缓存按字节从头匹配：开头改一个字符，后面的全部重算。本章讲三件事：怎么让前缀稳定、天生易变的内容该放哪、以及压缩这笔“用一次失效换长期变小”的交易什么时候划算。

  • 约 18 分钟
  • 1 个关联演示
  • L2 → L3

读完你能做到

  1. 拿到一次请求的拼接顺序，指出哪一处改动会让缓存从哪个位置开始失效。
  2. 用“失效一次的成本 ÷ 每次省下的成本”估算压缩的回收轮数，并判断任务剩一轮时该不该压。
  3. 给出一份可执行的观测方案：看哪些 usage 字段、怎么归因、哪些数字跨工具不可比。

01 · 先看账单

“明明只是换了个分支名”

场景 · 一句话改在最前面，整晚都在重算

周三晚上，一个小团队把 git status 的输出塞进了系统提示词的第一段，方便 Agent 知道当前分支。那天合并频繁，分支名每十几分钟变一次。任务还是那些任务，代码还是那些代码，但当月账单是上月的三倍。他们删了很多工具输出，却没有意识到：每次分支变化，都让整段历史从第一个字节起重新计费。

这件事反直觉的地方在于：他们做的每一步“减量”都是对的。少读文件、少跑测试、截断日志，token 确实少了。但缓存不是按“总量”算的，它按前缀算。

把服务端的缓存想成一排已经算好的积木。一次请求进来，它从第一块开始比对；只要第 1 块到第 k 块逐字节相同，这 k 块就可以直接复用上次的计算结果（KV 页），只有第 k+1 块之后需要重算。第 k+1 块就是失效点。它由“第一个不同的字节”决定，不由“改了多少”决定。

所以一次请求的输入其实分三类计价，而不是两类：

  • 未缓存输入：没有命中任何缓存、需要从头算的部分。
  • 缓存写入：这次算完，写进缓存供下次复用的部分。单价通常高于普通输入。
  • 缓存读取：命中已有缓存、直接复用的部分。单价通常最低。

省 token 和省钱是两件事。删掉一万 token 但把前缀改了，可能比不删更贵。

三个常见误判

一，以为“内容一样”就命中——消息顺序、空白、工具定义的排序变了，字节就变了。二，以为“追加一条消息”一定安全——追加在历史末尾安全，追加进系统提示词的中间不安全。三，以为命中率越高越好——下一节会看到，压缩会故意制造一次失效，换取之后每次更小的输入。

02 · Codex 主线

客户端只做两件事：发键，认账

和压缩、裁剪不同，缓存不是 Codex 在客户端“实现”出来的能力。它由服务端完成，CLI 只负责两件事：给这次请求一个稳定的缓存键，以及把响应里的缓存明细读回来。搞清楚这条边界，才能理解为什么本章的大部分“设计”其实是在约束拼接顺序。

2.1 发键：prompt_cache_key 的三种取值

Codex 在请求里带 prompt_cache_key。取值有三档：显式配置的 prompt_cache_key_override 优先；内部子会话用 {source}:{parent_thread_id}，把同一父会话派生的子任务归到一组；其余情况用 session_id。client.rs#L646-L665 已核实

键的作用是“路由到哪一排缓存”，不是“缓存什么”。同一会话的多轮请求用同一个键，才有可能复用上一轮算好的前缀；一旦换了键，即使内容完全一样，也可能落到另一台机器、另一份缓存上。子会话用父会话 ID 派生键，是为了让子代理的第一段系统提示词尽量复用父会话已经写好的缓存。推断

为什么不让客户端指定断点。把断点、TTL、淘汰策略都留在服务端，客户端就不必跟着模型版本改协议；代价是客户端看不见缓存的实际状态，只能从 usage 里事后读。1

2.2 认账：三个字段决定你能观测到什么

响应 usage 里的 input_tokens_details.cached_tokens 与 cache_write_tokens 被解析进 TokenUsage.cached_input_tokens 与 cache_write_input_tokens。responses.rs#L117-L151 protocol.rs#L2362-L2382 已核实

这三个字段（未缓存输入、缓存读、缓存写）足以算出一个会话的“缓存账”，但不足以解释“为什么没命中”。最常用的命中率口径是 cached_input_tokens ÷ 总输入 token；分母是否包含缓存写，各家不同，所以这个数字只在同一口径内可比。Codex 侧没有内置的失效归因；要做归因，只能自己在客户端记录每次请求的拼接哈希，再和 usage 对齐。这一点和 Claude Code 有明确差距：后者有专门的缓存失效检测模块，会对比系统提示词哈希、工具哈希、TTL/scope 变化，给出“本可命中却没命中”的原因promptCacheBreakDetection.ts#L31。源码 v2.1.88

2.3 排序：三原则比任何参数都重要

Codex 的请求骨架是 base_instructions（稳定）+ 工具表（稳定）+ 历史（增长）+ 尾部增量。这个顺序不是随手排的，它对应三条可以迁移到任何工具的原则。

原则一：按变化频率排序。越稳定的内容越靠前，越易变的内容越靠后。系统提示词的静态段、工具定义、项目规则在前；日期、当前分支、todo 状态、环境提醒在后。顺序一旦反过来，最易变的东西就站在了最前面，后面再稳定也没用。

工具定义是前缀里最重、也最容易被“顺手改一下”的部分。三条做法可以让它稳定：排序固定——按名字排序，而不是按 map 的插入序，opencode v1 就是这么做的transform.ts#L357-L404 已核实；模式切换不改工具目录——dsh 的 plan mode 只换提示词约束、不动工具 schema，源码注释明确写了这是为了请求缓存稳定cordis.patch.yml#L340 已核实；工具表变化走增量——Codex 的 incremental_tools 在不需要时置空 tools，避免整张表重发turn.rs#L1666-L1695 已核实。代价是：按名字排序会让工具顺序不符合语义分组；模式切换不改表，意味着某些模式下模型看得见却用不了某些工具；增量工具要求客户端与服务端都支持，换 provider 就可能退化。

原则二：只追加，不改写。新消息加在历史末尾，不动前面任何一条。追加是唯一“零失效”的写操作：前 k 块全部保持原样，只有新加的第 k+1 块需要计算。omp 把日期与 cwd 提醒从系统提示词尾部移到“每次请求的首个用户轮”，就是这条原则的极端应用：宁可让提醒出现在对话里，也不让它污染系统提示词。date-cwd-reminder.ts#L1-L14 已核实

原则三：必须改时，从最靠后的位置改。如果一条信息非改不可（比如规则文件更新了），优先“在末尾追加一条替换说明”，而不是回写到系统提示词中间。Codex 的 AGENTS.md 差分注入就是这个思路：只发变化的那一段，未变的部分字节不动。agents_md.rs#L44-L80 已核实 dsh 把系统提示词做成 surface 节点，内容不变就不重写；必须更新时，按路由能力选择“原地替换”或“在缓存历史之后追加一条 update”，后者就是为保住已缓存前缀准备的。system-prompt.md#L43 推断

把三条原则串起来，就是一句话：让“相同”尽可能长，让“不同”尽可能靠后。缓存优化的全部技巧，都是这句话的变形。

2.4 压缩的账：先失效，再省钱

压缩和缓存的关系，是本章最容易被讲错的地方。常见说法是“压缩会破坏缓存，所以要少压缩”。这只说了一半。压缩确实会让前缀从切点起失效，但它同时把之后每次请求的输入变小了。真正该问的是：这次失效的成本，能在剩下的对话里赚回来吗？

用一个教学模型算，假设摘要在固定前缀之后立即写入。设 P 为系统提示词与工具定义（压缩不动它），B 为压缩前的总输入，A 为压缩后的总输入（摘要 + 保留段 + 尾部），r 为缓存读取相对普通输入的单价，w 为缓存写入相对普通输入的单价。压缩后第一个请求要重写 B − P，之后每次省下 B − A。

教学模型 · 不是任何工具的真实计价 
// 只算缓存这一项，不含压缩请求本身的成本
invalidate  = (B - P) * (w - r)      // 一次性重写多付的钱
savePerCall = (B - A) * (1 - r)      // 之后每次少付的钱
// 回本轮数：还要再跑几次，这次失效才不亏
breakEven   = invalidate / savePerCall
 
// 例：B=180k, P=30k, A=45k, r=0.1, w=1.25
// invalidate=172.5k, savePerCall=121.5k, breakEven≈1.4

这个例子里，压缩后只要再跑两轮就回本。但把场景换一下：任务只剩最后一轮，压缩就是净亏——172.5k 的重写成本只换回一次 121.5k 的节省，还多了一次摘要请求。所以“该不该压”不只取决于窗口够不够，还取决于任务还剩多长。

优先级应该是：先保证不溢出，再谈缓存；先保证任务做完，再谈省钱。

这也解释了为什么各家在压缩时反复强调“复用暖前缀”。pi 的摘要请求显式设 cacheRetention: "none"，理由是“一次性摘要不太可能复用，写缓存反而污染”；compaction.ts#L619-L639 已核实 dsh 则相反，让摘要请求逐字节复用系统提示词、当前工具定义与被遮蔽区间，使这次调用的输入尽量成为原对话的前缀。compaction-basic/README.md#L108 推断 两种选择都对：前者赌“摘要不复用”，后者赌“摘要请求本身能命中”。

2.5 驱逐：为什么必须一次清到水位

图片驱逐和压缩是同一类操作：它们都在历史的某个位置“替换”内容，因此失效点就在被替换的那一块。区别是压缩只发生一次，驱逐可能反复发生。如果每轮只删一张图，每一轮都会在历史中段产生一个新的失效点，等于每轮都把后半段重写一遍。

Grok Build 的做法是滞回：请求体逼近 50MB − 3MB 时触发，一次回收到 25MB。image_budget.rs#L19-L35 已核实 opencode v2 是 25MiB 触发、降到 15MiB，从最旧的图片开始删。model-request.ts#L122-L216 已核实 两个数字不同，思路一致：批量驱逐 + 滞回区间，把“每轮一次小失效”换成“很久一次大失效”。

代价是峰值内存更高，而且一次删得多，可能删掉本该保留的证据图。但相比每轮都打断缓存，这个代价通常更便宜。

Q没有傻问题

问：那把系统提示词整个删短，不是每次都更省？

答：删短省的是“每次输入”，但如果因此改了前缀，第一次要付全量写入；更关键的是，删掉规则会让任务成功率下降。省下来的钱可能不够赔返工。缓存优化的目标是“单位成功任务成本”，不是“单位请求成本”。第 16 章会把这两个指标分开讲。

✓要点小结

  • 缓存命中的长度由第一个不同字节决定；改一个词和改一万字，失效范围可能一样大。
  • 前缀稳定三原则：按变化频率排序、只追加不改写、必须改时从最靠后的位置改。
  • 压缩的缓存账 = 一次重写成本 ÷ 每次节省；任务剩得越短，越不该压。
  • 工具定义要稳定：排序固定、模式切换不改工具目录、按需加载不要把工具表整体重排。
  • 驱逐要批量加滞回，不要每轮删一点；观测只能看 usage 字段，归因要自己做。

06 · 设计取舍

下面五组取舍，是这张表背后真正的分歧。每组都给出“A 派怎么做”“B 派怎么做”和一句代价。本节引用的参数不重复给 permalink，统一见第 05 节表格与各工具弹窗。

取舍一：一个断点，还是四个断点

少而准：Claude Code 在消息层每请求只放一个 cache_control，位置是最后一条消息；它把“4”留给系统提示词的分块上限，两者不是一回事。多而密：opencode v2 的 auto 会同时给最后一个工具、首末 system、尾部消息打点，上限 4；Grok Build 打 3 处显式断点，第 4 个槽故意留给网关。

代价：断点少，缓存页保留得少，长会话里更早的前缀可能已经过期；断点多，每次请求都可能多写几页 KV，写放大更明显。Claude Code 的源码注释直接说了“多标记会让倒数第二个位置也被保护，白白多留一轮 KV 页”——这是少派的理由；多派的理由是“跨轮复用的机会更多”。谁对，取决于你的会话是“长而连续”还是“短而频繁”。

取舍二：把易变内容移出前缀，还是留在原地

移出派：omp 把日期与 cwd 提醒从系统提示词尾部挪到首个用户轮；dsh 用新增 user 消息承载时间；Grok 把日期固定在会话启动值，跨午夜才追加一条 reminder。留在原地派：不少实现仍把“当前时间、当前分支、当前目录”写在系统提示里，因为它们认为“模型更重视系统提示里的信息”。

代价：移出之后，系统提示词变得完全静态，缓存最稳；但信息离“指令区”更远，模型可能不如以前重视，而且每条提醒都要占一条消息。留在原地则相反：模型更容易遵守，却可能在每次日期变化时打断整段前缀。若你的 Agent 跑的是几分钟的短任务，日期根本不会变，这个取舍几乎不存在；跑整夜的批处理，它就会变成账单上的第一行。

取舍三：压缩早一点，还是晚一点

早压：在 70%–80% 就压，压缩请求自己有足够空间，失败概率低，之后还有很长的路可以摊薄失效成本。晚压：逼近 90%–95% 才压，尽量少压几次，减少信息损失和摘要调用。不压：任务只剩最后一两轮时，宁可带着接近满的窗口跑完。

代价：早压会在任务还没走完时丢掉细节，而且多一次摘要成本；晚压可能让压缩请求自己超窗，进入第 14 章的删最旧重试；不压则要承担溢出的风险。用 2.4 的公式看，这个取舍可以量化：breakEven 大于剩余轮数，就不该压；但若剩余轮数大于 0 且窗口已接近上限，溢出的代价通常高于一次失效。

取舍四：摘要请求写缓存，还是明确不写

不写派：pi 给摘要请求设 cacheRetention: "none"，因为摘要是一次性的，写进去只会挤占缓存页。复用派：dsh 与 Grok 让摘要请求复用系统提示词、工具定义与被遮蔽区间，使这次调用的输入尽量命中已有前缀，只有尾部指令是新的。

代价：不写最干净，但摘要请求要全额付费；复用能省一次输入，却要求“摘要请求的拼接顺序必须和主请求逐字节一致”，实现稍有不慎就会既没命中、又多了耦合。这也是为什么“暖前缀”通常只在大上下文、频繁压缩的实现里出现：小会话省下的钱不够覆盖这段复杂度。

取舍五：客户端自己摆断点，还是交给服务端

客户端派：Claude Code、opencode、Grok 都显式下发断点，能精确控制“哪一块值得缓存”。服务端派：Codex 只发 prompt_cache_key，断点、TTL、淘汰都由服务端决定。前者跨 provider 可移植性差（每家字段名不同），后者则完全依赖服务端的策略。

代价：客户端摆断点，控制力强，但要跟着 provider 协议走，字段一改就得适配；服务端托管，接入简单，但你看不见断点，也改不了 TTL。Codex 的 cached_tokens 只能告诉你“命中了多少”，不能告诉你“为什么没命中”；Claude Code 则专门写了失效归因模块。这是控制权换来的可观测性差异。

还有一组横切的取舍：命中率作为目标，还是作为诊断。把命中率当目标，容易走向“为了命中而不敢压缩、不敢裁剪”，最后窗口里塞满过期内容；把它当诊断，才会去问“这次失效是压缩造成的，还是日期变化造成的”。第 16 章会把这个问题展开成指标设计。

07 · 小测验

三道题，检验你是否真的会定位失效点

Q1

一次请求的拼接顺序是：系统提示（含当前日期）→ 工具定义 → 历史 → 本轮输入。现在只把“当前日期”从 10 月 18 日改成 10 月 19 日，其他一字未动。失效点在哪里？如果把这句日期移到“本轮输入”里，失效点又在哪里？

解析

第一种情况，失效点在系统提示的第一块，也就是整段请求的最开头：日期变了，系统提示、工具、历史全部要重算。第二种情况，系统提示、工具、历史都保持原样，只有最后一条新输入需要计算，前缀全部可复用。这就是“易变内容放哪”比“断点放几个”更重要的原因。见2.3 排序与 图 13-1。

Q2

压缩前总输入 180k，系统提示与工具 30k，压缩后 45k。缓存读单价是普通输入的 0.1，写单价是 1.25。只算缓存这一项，压缩后还要跑几轮才回本？如果任务只剩最后一轮，应该压吗？

解析

一次性重写成本 =（180k − 30k）×（1.25 − 0.1）= 172.5k；每次节省 =（180k − 45k）×（1 − 0.1）= 121.5k；回本 ≈ 1.4 轮，也就是再跑两轮才不亏。任务只剩一轮时，压缩在缓存账上是纯亏，还多一次摘要请求；但如果窗口已经接近上限、不压就会溢出，那仍然要压——溢出的代价通常高于一次失效。见2.4 压缩的账。

Q3

一个团队把“当前分支名”放在系统提示最前面，又把图片驱逐改成“每轮删一张”。两个做法各自破坏了哪条原则？分别怎么改？

解析

分支名放在最前面，破坏了“按变化频率排序”：最易变的内容站在了最前，后面再稳定也救不回来，应该移到尾部或改成每轮追加的提醒。每轮删一张图，破坏了“最小改写 / 批量驱逐”：失效点会每轮往前挪，等于每轮重写后半段，应该改成滞回区间一次清到目标水位（Grok 是 50MB 触发、回收到 25MB）。见2.3 排序与2.5 驱逐。

工具弹窗 · claude-code

Claude Code

缓存标记分两层。系统提示词被切成最多 4 块：计费/归属头、CLI 前缀、边界前的静态内容、边界后的动态内容。消息层则恰好只放 1 个 cache_control，位置是最后一条消息；fork 时前移到倒数第二条，避免把 fork 自己的尾巴写进缓存。

关键参数
消息级标记 1 个/请求；系统提示最多 4 块；TTL 默认 ephemeral，满足资格升 1h；skipCacheWrite 时标记前移。源码 v2.1.88
设计意图
“只放一个”是为了避免倒数第二个位置也被保护，白留一轮 KV 页。TTL 资格一次性锁存，防止会话中途 overage 翻转导致整段缓存失效。和别家最大的差异是：它把“可见的断点数量”压到最少，把控制力放在分块顺序上。
来源
claude.ts#L3063-L3106、api.ts#L296-L360

源码与官方文档在“按变化频率排序以优化前缀缓存”上一致；但“4 个断点”在源码里是系统提示词块上限，不是消息层标记数，两者不要混。两者一致

工具弹窗 · pi

pi

pi 走“section 化”路线：系统提示词拆成具名 section，变化时只追加一个 section patch，未变部分字节不变。摘要请求显式不写缓存，另有 CacheWarmer 在 TTL 的 90% 处重放请求保温。

关键参数
cacheWarming: "streaming"；预热触发 TTL × 0.9 且至少提前 10 秒；节省下限 $0.05；安全上限 streaming 60 分钟 / idle 30 分钟；摘要 cacheRetention: "none"。已核实
设计意图
把“改提示词”从“重写整段”降级为“追加一个 patch”，让前缀尽量长；摘要不写缓存，是因为它一次性、复用概率低。代价是多了一套 section 差异计算和预热成本。
来源
system-prompt.ts#L212-L229、cache-warmer.ts#L14-L31

cache-stats.ts 统计“上次命中、这次未命中”的浪费，噪声下限 1024 token；低于这个量级的差异不要当成回归。

工具弹窗 · omp

oh-my-pi

omp 把“易变内容移出前缀”做得最彻底：静态提示词块在前，<project-context> 永远是最后一块，缓存断点落在它之前；日期与 cwd 提醒从系统提示词尾部移到每次请求的首个用户轮。

关键参数
断点在 <project-context> 之前；日期/cwd 提醒插首个用户轮；prompt-cache lookback 留 6 个位置余量；预热沿用 pi 的 TTL × 0.9 / $0.05 / 60·30 分钟。已核实
设计意图
让系统提示词与工具数组在会话内字节稳定，只有跨天或换目录才变。裁剪还有缓存守卫：候选结果之后的 suffix 仍在热前缀里时不动。代价是“当前时间”离指令区更远，模型对时间的敏感度可能下降。
来源
system-prompt.ts#L1026-L1036、date-cwd-reminder.ts#L1-L14

omp 是 pi 的 fork，预热与缓存统计逻辑同源，但断点位置与“易变内容位置”是它自己改的，不能直接外推到 pi。

工具弹窗 · opencode-v1

opencode v1

applyCaching 在交给 provider 前，给前 2 条 system 消息和后 2 条非 system 消息打 provider 级 ephemeral 标记。前缀稳定靠两点：工具定义按名字排序、system 由固定顺序的块拼成。

关键参数
缓存点：前 2 条 system + 后 2 条非 system；promptCacheKey = sessionID，请求头带 x-session-affinity；可按 provider 选项关闭或强制。已核实
设计意图
用少量、位置固定的标记覆盖“最值得复用”的两端：系统提示的开头和历史尾部。代价是任何一块 system 内容变化都会让整条 system 字符串变化，前缀立即失效；它没有围绕缓存做压缩调度。
来源
provider/transform.ts#L357-L404、transform.ts#L1324-L1334

服务端命中率与 TTL 不可观测，卡片标【待核实】；表里的“已核实”只指客户端确实下发了这些标记。

工具弹窗 · opencode-v2

opencode v2

v2 把缓存做成策略层，默认 "auto"：给最后一个工具定义、首末两段 system、尾部 1 条消息打断点，总数上限 4。手工设在 part 上的 CacheHint 先占预算，auto 只填剩余槽位。

关键参数
AUTO = { tools: true, system: true, messages: { tail: 1 } }；BREAKPOINT_CAP = 4；按协议白名单 RESPECTS_INLINE_HINTS 决定是否下发；亲和 id 取 parentID ?? fork 源 ?? 自身。已核实
设计意图
不同 provider 对缓存标记的支持差异很大，策略层把“打不打、打哪里”集中管理，网关还能按模型 ID 特化。代价是多了一层抽象，调试时要同时看策略、白名单和网关规则。
来源
cache-policy.ts#L17-L47、model-request.ts#L278-L295

v2 是 beta（v2.0.29），字段与默认值可能在下个版本变化；不要把这里的 4 个断点外推到 v1。

工具弹窗 · grok-build

Grok Build

缓存分三层：前缀稳定（日期在会话内固定、记忆索引存在就跳过、技能/MCP 公告只发增量）、显式断点（3 处 ephemeral + 1 槽留给网关）、以及替换操作的代价管理（图片驱逐用滞回、压缩后重放暖前缀）。

关键参数
断点 3 显式 + 1 槽网关（共 4 上限）；Thinking / RedactedThinking 不可打点，向前找；图片 50MB − 3MB 触发、回收到 25MB。已核实
设计意图
把第 4 个槽留给网关自动缓存，避免“打第 5 个被拒”；日期固定是为了让跨午夜的会话不因一个数字重写整段。代价是显式断点与网关策略可能互相挤占，需要留槽。
来源
messages.rs#L3-L70、image_budget.rs#L19-L35

针对 xAI 自家 Responses 后端的 cache_control 字段未在源码中找到，那部分缓存由服务端透明处理，属【推断】。

工具弹窗 · dsh

DeepSeek Harness

dsh 把系统提示词做成 surface 节点：内容不变就不重写；变化时按路由能力选“原地替换节点 0”或“在缓存历史之后追加一条非空 update”。后者专门为保住已缓存前缀而存在。

关键参数
系统提示更新方式：原地替换 / systemPromptUpdate: 'in-history'；plan mode 不改工具目录；压缩、prune、图片 offload 都从首个被替换 token 起失效。推断
设计意图
把“替换”与“追加”分开：能追加就不替换，能只换一个节点就不重写整段。代价是 surface 需要维护节点版本，恢复与回滚时要判断哪个版本对应当前投影。
来源
system-prompt.md#L43、compaction-basic/README.md#L108

这些结论来自同仓文档与包 README，不是逐行源码；plan mode 的缓存注释有源码支持，其余按【推断】表述。
