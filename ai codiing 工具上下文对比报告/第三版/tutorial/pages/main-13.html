缓存友好设计：稳定前缀与压缩成本

第 5 章讲过，相同前缀有机会复用计算，但仍占上下文窗口；第 6 章则讨论何时清理。本章进一步看实现：怎样把易变内容放到后面，压缩后哪些内容要重算，以及怎样用实际读写费用判断压缩是否划算。

  • 第 13 类
  • 约 25 分钟
  • 1 个关联演示
  • L2 → L3

读完你能做到

  1. 拿到一次请求的拼接顺序，指出哪一处改动会让缓存从哪个位置开始失效。
  2. 在明确缓存与计价假设后，用“一次性额外成本 ÷ 每轮节省”估算压缩的回本轮数。
  3. 给出一份可执行的观测方案：看哪些 usage 字段、怎么归因、哪些数字跨 agent 不可直接比较。

01 · 先看账单

分支名放在开头，为什么会增加重算

场景 · 分支信息更新，缓存读却少了

设想周三晚上，团队为了让 agent 知道当前分支，把 git status 输出放进系统提示词第一段。分支频繁变化，缓存读随之减少。他们先删日志、缩短输出，却没检查改动位置。即使月底账单变成上月的三倍，也不能单凭涨幅认定是缓存造成的，还得对照每轮用量与单价。

删日志、少读无关文件，能减少输入；是否省钱，还要看删改发生在哪里。若改动出现在靠前的位置，后面保留的大段材料可能无法沿用旧计算。第 5 章的前缀，就是从请求开头开始的一段连续内容。

沿用第 5 章的两排方块：两次请求从第一块开始比较，相同的开头仍有复用机会，第一处不同就是失效点。后面的块即使没改，也依赖已经变化的前文，不能直接沿用旧状态。缓存保存的是计算中间状态（KV 状态），实际比较以服务商渲染后的请求与 token 序列为准，不能一概说成按原始文本字节比较。

算费用时，要再区分三类用量。它们是否分别收费、单价是多少，取决于供应商、模型与缓存配置：

  • 普通输入：没有按缓存读取或缓存写入计费的输入。
  • 缓存写入：计算后保存中间状态，供后续复用。部分模型采用高于普通输入的写入价，也有模型不另收写入费。
  • 缓存读取：复用已有状态的输入，通常享有折扣。读写费率要查具体模型，不能由 agent 名称推定。

少带材料能省窗口；能否省钱，还取决于剩下的材料按什么价格处理。被删除的 token 已经不在新请求里，不会再收一次重写费。

三个常见误判

一，以为“内容一样”就一定命中：还要满足存活时间（TTL）、最低缓存长度、模型设置和服务端路由等条件。二，把缓存断点当作失效点：断点（cache breakpoint）指定缓存到哪里，失效点是两次请求的第一处不同。三，以为命中率越高越好：缓存不减少窗口占用，必要的压缩与裁剪仍要做。

02 · Codex 主线

Codex 如何发送缓存键和读取用量

前缀能复用多少，由请求内容与服务端缓存共同决定。Codex CLI 在本章所查版本中，负责发送缓存键、解析用量，并组织请求内容；缓存状态由服务端维护。以下先看客户端可确认的部分，再讨论怎样安排内容、核算压缩成本。

2.1 缓存键：prompt_cache_key 的三种取值

Codex 在请求里带 prompt_cache_key。取值有三档：显式配置的 prompt_cache_key_override 优先；内部子会话用 {source}:{parent_thread_id}，把同一父会话派生的子任务归到一组；其余情况用 session_id。client.rs#L646-L665 已核实

同一键可用于把相关请求归到一组，但不能代替内容匹配，也不能保证命中。上述内部子会话规则会让同来源、同父线程的子会话共用键；它们的键不等于父会话自己的默认键，因此不能据此推定会复用父会话的缓存。具体路由与复用效果仍取决于后端。推断

这个版本把哪些控制留给了服务端。所查请求构造没有显式缓存断点、TTL 或淘汰参数；客户端只能从返回用量观察结果。这里只描述该提交的 CLI 路径，不据此认定所有 OpenAI API 都不能配置缓存。【待核实】的是该后端的具体保留与路由策略。1

2.2 用量：区分总输入、缓存读与缓存写

响应的用量统计（usage）包含总输入 input_tokens；input_tokens_details.cached_tokens 与其中的 cache_write_tokens 分别进入 TokenUsage.cached_input_tokens、cache_write_input_tokens。缺省的写入量记为 0，不能据此认定服务端没有保存缓存。responses.rs#L117-L151 protocol.rs#L2362-L2382 已核实

在三类计费互不重叠的接口中，普通输入量为“总输入 − 缓存读 − 缓存写”，费用再分别乘对应单价；多档 TTL 的写入还需要分档明细。

Codex 的命中率可用“缓存读 ÷ 总输入”，pi 的总输入则要把其普通输入、读、写相加。观测时每轮记录这些量、模型与费率、键是否变化、各段内容哈希，以及压缩、裁剪等事件；先对齐口径，再定位变化。

usage 本身不能解释未命中的原因。Claude Code 的 promptCacheBreakDetection.ts#L31 会比对系统提示、工具、TTL 与缓存共享范围（scope）等变化，提供客户端侧的归因线索。源码 v2.1.88

2.3 内容顺序：稳定内容在前，更新尽量追加

知道怎样读用量后，再看怎样减少不必要的重算。可把请求示意为“基础说明与工具定义 → 历史 → 本轮新增内容”。Codex 分别传入 base_instructions、tools 与 input 等字段；最终渲染顺序取决于后端，不能把 JSON 字段顺序当作模型收到的顺序。下面三条原则针对渲染后的内容。

原则一：按变化频率排序。越稳定的内容越靠前，越易变的内容越靠后。静态系统说明、工具定义、项目规则尽量保持稳定；日期、分支、todo 状态、环境提醒尽量作为后续更新。若易变内容出现在前面，后面再稳定，也无法直接接着旧状态复用。

工具定义也属于请求内容，名称、描述、参数结构和排列顺序都可能影响匹配。固定排序：opencode v1 在 request.ts#L184 按名称排序，缓存标记另由 transform.ts#L357-L404 设置。已核实 模式切换保留工具目录：dsh 的 plan mode 用提示词限制行为，注释明确说明保留工具 schema 是为请求缓存稳定。cordis.patch.yml#L340 已核实

支持时采用增量协议，即只补充本次新增或变化的定义：Codex 在 incremental_tools=true 时把本次 tools 与 base_instructions 都置空，由历史中的声明与更新承担。turn.rs#L1666-L1695 已核实

这些做法也有限制：名称顺序未必符合语义分组，保留工具目录也不等于限制了执行权限。增量协议需要后端支持；少传字段也不等于模型少看了这些定义。

原则二：能追加，就不改写旧消息。在渲染前缀和请求设置都不变时，末尾新增消息不会破坏此前的相同内容；是否命中仍要看缓存条件。omp 的日期与 cwd（当前工作目录）提醒，首次附在首条用户消息上；日期或目录变化时附到新增用户消息，没有新用户消息就追加 developer 提醒，保留此前发过的内容。date-cwd-reminder.ts#L1-L14 已核实

原则三：必须更新时，明确替换范围。在末尾追加更新说明，可以保留此前的前缀，但也要说明旧规则何时失效。Codex 的 AGENTS.md 状态比较在内容未变时不发更新；变化时追加完整的新规则及替换说明，删除时发失效通知，并非只发送文件中改过的几行。agents_md.rs#L44-L80 已核实 dsh 则把系统提示记录为 surface 节点，即当前发给模型的消息序列中的一项；按路由能力选择原地替换，或在缓存历史之后追加非空更新。system-prompt.md#L43 推断

这三条原则都在争取更长的相同前缀，但不能为了保缓存一直保留过期内容。需要压缩或裁剪时，先保证下一次请求能装下、材料仍准确，再算重算的费用。

2.4 压缩成本：比较新写入与后续缓存读取

压缩把一段旧历史换成摘要，从第一处不同开始需要重算；被删掉的旧历史已经不再收费。后续省下的也不是每轮一整份普通输入费：如果不压缩本来能读缓存，比较基准就应是继续读取旧历史的费用。

设稳定前缀为 P，压缩前总输入为 B，压缩后总输入为 A；A 包含 P、摘要与保留段。读、写单价相对普通输入分别为 r、w。

假设 0 ≤ P < A < B、w ≥ r > 0；旧输入已全缓存、P 不变，压缩后 A − P 首次全按写入计费，以后全按读取计费；缓存不过期，两种方案相同的新增输入与输出费用抵消。摘要调用的净增成本记为 C，也换算到同一费用单位。

教学模型 · 假设计价互斥，单价以普通输入为 1 
// extraOnce 是新后缀首次写入相对读取的额外费用
extraOnce   = (A - P) * (w - r)      // 只对新请求中保留的后缀算写入
savePerCall = (B - A) * r           // 每轮少读旧历史省下的钱
breakEven   = (extraOnce + C) / savePerCall
// n 包含压缩后的第一次正常调用；累计差额 ≤ 0 才回本
deltaCost   = extraOnce + C - n * savePerCall
// B=180k, P=30k, A=45k, r=0.1, w=1.25；先设 C=0
// extraOnce=17.25k, savePerCall=13.5k, breakEven≈1.28

这里的 k 表示千个 token 按普通输入单价折算的费用单位，不是金额。首次正常调用中，不压缩读 180k × 0.1 = 18k；压缩后读前缀并写新后缀，付 30k × 0.1 + 15k × 1.25 = 21.75k，多付 3.75k。第二次每轮少付 13.5k，所以忽略摘要调用时，累计两次才回本。任务只剩一次，在这组假设下不省钱；实际还要加 C。若没有写入溢价，应换实际费率重算，不能套用结论。

优先级应该是：先保证不溢出，再谈缓存；先保证任务做完，再谈省钱。

摘要调用的成本也能优化，但“避免新写入”与“读取已有缓存”是两件事。pi 为一次性摘要设 cacheRetention: "none"，同时尽量沿用调用方的 sessionId；这个选项不能单独证明摘要输入一定全额付费。compaction.ts#L619-L639 已核实 dsh 文档则说明，摘要请求复用系统提示、工具定义与被摘要区间，让输入尽量对齐已有前缀；能否命中仍要看路由、缓存状态和请求转换。compaction-basic/README.md#L108 推断

2.5 图片驱逐：用两个阈值减少反复改写

图片驱逐就是从发给模型的历史中移除旧图片，通常换成说明文字。它和压缩都会改写历史，但两者都可能发生多次。若每轮只删一张，历史会反复出现新的失效点；原样保留的后续内容也可能要重新计算。

可以设置两个阈值：达到上限才清理，一次降到更低的目标，留出一段增长空间，这叫滞回。Grok Build 默认按 50MiB 的请求预算计算，序列化对话体达到 50 − 3 = 47MiB 时触发，目标降到 25MiB；实际阈值可随后端的请求体上限变化。image_budget.rs#L19-L35 已核实

opencode v2 则统计内联图片载荷，超过 25MiB 才从旧到新移除，目标不高于 15MiB；远程引用不计入这份载荷。model-request.ts#L122-L216 已核实 MiB 是 1024² 字节，两家的计量对象不同，不能直接比作窗口大小。

代价是一次会移除更多图片，后续若需对照，就得重新取得图片；若光文本就已超预算，删图片也未必够。批量清理减少了频繁改写的机会，实际收益还要结合使用频率与费用判断。

Q你可能会问

问：那把系统提示词整个删短，不是每次都更省？

答：删短确实能减少后续输入；第一次改动可能让仍留在请求里的后缀重新计算，但不会为已经删掉的内容付费。还要看删掉的是重复文字还是必要规则：若任务质量因此下降，返工可能抵消节省。优化应看“单位成功任务成本”，第 23 章会进一步区分它与“单位请求成本”。

✓要点小结

  • 先找渲染后请求的第一处不同；此前相同的内容仍需满足缓存条件，才可能命中。
  • 前缀稳定三原则：稳定内容靠前、更新尽量追加、更新时明确哪些旧内容失效。
  • 压缩回本轮数 =（新后缀额外写入费 + 摘要净增成本）÷ 每轮少读旧历史的费用，前提是模型假设成立。
  • 工具定义尽量稳定；固定排序、保留目录与增量协议各有适用条件，不能代替执行权限控制。
  • 图片可按两个阈值批量清理；把 usage 与请求差异、压缩和裁剪事件对齐，才能解释费用变化。

06 · 设计取舍

缓存控制、信息更新与压缩时机的取舍

前面的差异涉及五个可分别决定的问题：缓存边界、更新位置、压缩时机、摘要请求和控制范围。它们并非互斥路线；选择时都要看具体后端与任务，不能仅凭断点数量判断成本。

取舍一：消息尾部一个标记，还是多处分层标记

Claude Code 在正常启用缓存的消息层放一个标记。系统提示最多 4 块是另一项计数，既不等于“全请求只有一个断点”，也不代表 API 的断点上限。opencode v2 的自动放置预算则是全请求最多 4 个，包含工具、system 与消息；Grok 的 Anthropic Messages 路径最多设 3 处，再留 1 槽给网关。比较前必须先统一计数范围。

代价：多处分层标记可以照顾变化频率不同的前缀，也会占用 API 的标记额度；写入费用看实际写入量与 TTL，不按标记个数直接相乘。Claude Code 的注释给出一个特定后端的理由：少一个消息标记，可让上一轮不再需要的局部注意力 KV 页及时释放。这个内存管理理由不能推广为所有 provider 上“断点越多，账单越高”。

取舍二：追加状态更新，还是原地更新提示词

追加更新：omp 的日期/cwd 提醒在值变化时追加，dsh 用新增 user 消息承载时间，Grok 在跨午夜后追加日期提醒。原地更新：dsh 的另一条路由策略允许直接替换系统提示节点。追加保留旧前缀；原地替换让当前位置直接反映新状态，却可能使后面的大段历史重算。

代价：追加后，旧值与新值同时留在历史中，要写清更新范围，避免歧义；原地更新的状态更集中，但会改变匹配前缀。项目规则和工具仍可能更新，所以系统提示的稳定性要逐项检查。状态更新能否被正确采用，还应通过跨天、换目录等具体任务验证。

取舍三：压缩早一点，还是晚一点

早压给摘要调用与失败重试留空间，之后也可能有更多轮次消化一次性成本。晚压可以少丢几次原始细节、少调几次摘要。若只剩少量工作且下一次请求能装下，也可以暂不压缩。用窗口 70%–80% 或 90%–95% 作示意有助于讨论，但这些不是各 agent 通用的触发档位，还要扣输出预留等预算。

代价：早压增加摘要次数与信息损失风险；晚压可能使摘要调用本身超窗，进入第 21 章的失败恢复。第 2.4 节的公式只能在假设成立时判断费用：回本轮数超过剩余调用数，说明缓存账未回本。若不压就装不下，则必须先解决窗口问题，不能让费用公式覆盖这个约束。

取舍四：避免摘要写缓存，同时争取读取旧缓存

pi 明确给一次性摘要设 cacheRetention: "none"，目的是避免为不太会复用的请求内容新建缓存。它仍尽量沿用调用方的路由标识。dsh 文档要求摘要调用复用系统提示、工具与被摘要区间，Grok 也准备对齐原对话的压缩输入。这是在分别决定“新内容要不要写”与“旧内容能不能读”，两者可以组合。

代价：争取读取旧缓存，要求相同模型/路由下的渲染前缀保持一致；图片移除、工具变化或缓存过期都可能破坏预期。避免写入是否也影响读取，要看 provider 如何实现该选项，不能由 "none" 推导“摘要全额付费”。回本核算中的 C 应采用摘要调用的实际费用。

取舍五：客户端自己摆断点，还是交给服务端

客户端指定：Claude Code、opencode 和 Grok 的部分后端路径会显式下发断点，指定值得缓存到哪里。服务端决定：所查 Codex CLI 请求未显式指定这些边界。两种方式都仍依赖服务端支持；显式标记也不能替服务端决定最终是否命中。

代价：客户端指定断点，需要适配 provider 协议并处理额度与 TTL；交给服务端时，这部分实现较少，边界却较难直接观察。无论哪一种，缓存读取量只能说明用了多少，不能独自解释为什么没命中。Claude Code 的失效检测模块提供请求变化线索，仍需结合实际用量验证。

这些取舍最后都要回到任务结果。若为了命中率而拒绝必要的压缩、裁剪，窗口可能一直被过期内容占用。把命中率用于诊断，再结合成功率、总费用与等待时间判断策略，才知道一次失效是否值得；第 23 章会展开这些指标。

07 · 小测验

练习：定位失效点并核算压缩成本

Q1

一次请求的拼接顺序是：系统提示（含当前日期）→ 工具定义 → 历史 → 本轮输入。现在只把“当前日期”从 10 月 18 日改成 10 月 19 日，其他一字未动。失效点在哪里？如果把这句日期移到“本轮输入”里，失效点又在哪里？

解析

第一种情况，失效点在日期值首次不同的位置，不一定是系统提示的第一个 token。只有它之前仍相同且符合缓存条件的部分有机会命中，后面的工具与历史需基于新前文重算。第二种情况要区分迁移与后续使用。第一次把日期移走也会改旧前缀；布局稳定后，把每次日期作为尾部新输入追加，并保留旧消息，才不会反复改变前面的内容。见2.3 排序与 图 13-1。

Q2

压缩前总输入 180k，固定前缀 30k，压缩后总输入 45k（含固定前缀）。读、写倍率分别是 0.1、1.25。假设原输入已全缓存，新后缀首次全写、之后全读，缓存不过期，忽略摘要调用及两方案相同的增量费用：从压缩后第一次正常调用起，累计几次回本？只剩一次时呢？

解析

新后缀为 45k − 30k = 15k；首次写入相对读取的额外成本是 15k × (1.25 − 0.1) = 17.25k。每轮少读旧历史省 (180k − 45k) × 0.1 = 13.5k，回本为 17.25 ÷ 13.5 ≈ 1.28，所以累计两次正常调用才回本。一次时仍多付 3.75k；计入摘要成本后要再加 C，不能保证两次就够。若下一次请求装不下，应先解决窗口问题。见2.4 压缩的账。

Q3

一个团队把“当前分支名”放在系统提示最前面，又把图片驱逐改成“每轮删一张”。两个做法各自破坏了哪条原则？分别怎么改？

解析

分支名放在开头，使易变状态早于稳定内容，应在可行时改成尾部追加的更新，并明确旧值失效。每轮删一张图会反复改写历史，但失效点不一定“每轮往前挪”；按旧图顺序删时，它也可能往后移。可设置上限与较低目标，批量清理，减少触发频率；Grok 默认是 47MiB 触发、目标 25MiB，并随后端预算调整。见2.3 排序与2.5 驱逐。

DeepSeek Harness

dsh 将系统提示存为 surface 节点，即当前发给模型的消息序列中的一项。不变则不重写；变化时按路由能力原地替换节点 0，或在历史后追加非空更新（in-history）。后者能避免回头改写旧前缀，但不保证实际缓存命中。

关键参数
系统提示更新：原地替换 / systemPromptUpdate: 'in-history'；plan mode 保持工具目录不变。按文档设计，压缩、prune（裁剪工具结果）、图片 offload（移出内联图片）会改变所替换位置起的前缀状态；此前仍可能复用。推断
设计意图
将“追加更新”和“原地替换”作为明确策略，同时让摘要请求尽量复用系统提示、工具与被摘要消息。代价是恢复时要从会话记录重建当前有效消息序列（投影），并正确处理更新与压缩后的规则状态。只替换一个节点，仍可能影响它之后的缓存复用。
