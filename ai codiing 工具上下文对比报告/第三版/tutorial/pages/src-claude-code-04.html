01 · 功能说明

37 个来源，三类 delta

getAttachments() 是一个并发聚合器。它把 37 个 maybe(...) 调用分成三组：用户输入相关（@ 文件、MCP 资源、agent 提及、技能发现）、全线程相关（日期变化、延迟工具、agent 列表、MCP 指令、文件变更、嵌套记忆、技能列表、plan 模式、todo、teammate 信箱等）、仅主线程（IDE 选中、诊断、token 用量、预算、验证提醒等）。每组并发执行，最后拉平、过滤掉 null/undefined。源码 v2.1.88

附件不是「系统提示的一部分」，而是追加在消息尾部的独立消息；这决定了它只能影响尾部缓存，不会破坏前缀。

37 这个数字是逐个数出来的：用户输入组 4 个（其中技能发现受特性开关控制）、全线程组 22 个、主线程组 11 个。部分来源受 feature() 或环境变量门控，实际执行数会少于 37；但「来源很多、每个都可能产出附件」这个事实不变。源码 v2.1.88

附件有两种用法。绝大多数是「状态提醒」：日期变了、文件变了、todo 快到期了，发一条就够，下一次不一定再发。少数是「清单」：agent 列表、延迟工具、MCP 指令，它们描述的是「当前可用的能力集合」，会反复变化，而且模型必须知道完整集合才能正确调用。对清单类附件，整份重发太贵，于是有了 delta。源码 v2.1.88

为什么 delta 只做这三类？因为它们同时满足两个条件：内容会变，且模型必须知道完整集合。日期变化不需要完整集合，只需要「今天几号」；文件变更只需要「哪个文件变了」；todo 只需要提醒。agent 列表、工具列表、MCP 指令则不同：模型要判断「这个 agent 能不能用」「这个工具能不能调」「这个服务器有什么约束」，缺一条就可能做错。推断

再看三组来源的分工，会更清楚附件的定位。用户输入组只在有输入时运行，处理「@ 文件」「MCP 资源」「agent 提及」「技能发现」，这些是「这一句话带来的临时上下文」；全线程组每轮都跑，处理「线程级状态」，比如日期、delta、文件变更、记忆、技能列表、plan、todo；主线程组只在主会话跑，处理「UI/计费/诊断」这类子代理不需要的信息。三组的分层依据不是「重要性」，而是「作用域」。源码 v2.1.88

这也解释了为什么 delta 放在全线程组：agent 列表、延迟工具、MCP 指令对主线程和子代理都适用。子代理也需要知道自己能调用哪些工具、哪些 agent；如果只在主线程注入，子代理会缺声明。作用域决定注入位置，而不是反过来。推断

1000ms 的超时也值得注意。所有来源并发跑，谁先完成谁先返回；超过 1 秒就 abort，未完成的来源不产出附件。这意味着附件是「尽力而为」的：某个 MCP 服务器慢、某个目录扫描卡住，不会阻塞整轮请求，只是那一类附件缺席。缺席的后果由各自的使用方承担：delta 缺席会下一轮补，诊断缺席可能这一轮看不到错误。推断

04 · 逐段解读

把「清单」变成「事件流」

第 1 段　10.2% 的教训：清单放错位置，整段 schema 失效

注释把因果链写得很完整：agent 列表原本嵌在 AgentTool 的描述里；MCP 异步连接、/reload-plugins、权限模式变化都会改变列表；列表一变，工具描述变；工具描述在请求的 schema 数组里，属于前缀的一部分；于是整段工具 schema 缓存失效。这个比例是「约 10.2% 的 fleet cache_creation」。源码 v2.1.88

把清单从工具描述搬到附件，改变了它的位置：工具描述变回静态，schema 前缀稳定；列表变化只追加一条尾部消息，缓存从追加点之后失效。同样一份数据，放在前缀里是「全局失效」，放在尾部是「局部追加」。这是整节最值得记住的一句话。推断

这个教训也解释了为什么 delta 要「只发变化」而不是「每次全量」：全量虽然也在尾部，但每次都要写一大段，缓存写入成本高；delta 没有变化时零字节，有变化时只写差量。省的是写入，不只是读取。推断

把这条因果链拆成四步，可以当成一张检查表。第一步，这段内容是否在请求的前缀里？如果是，它一变就会影响后面所有缓存。第二步，它是否会被频繁改动？如果会，前缀里的每一次改动都很贵。第三步，它是否必须完整呈现？如果不是，可以改成尾部增量。第四步，尾部增量是否稳定？如果不稳定，还要加排序、去时间戳。四步里任何一步答错，都会把「省 token」变成「反复重建缓存」。推断

注释里的「10.2% of fleet cache_creation」是整仓少见的量化数据。它不是说「10.2% 的请求失败」，也不是「10.2% 的成本」，而是「缓存创建量里约 10.2% 来自这个原因」。这个口径很重要：cache_creation 是「写缓存」的量，通常比 cache_read 贵；把它降下来，直接省的是写入成本，间接省的是「因为写入而没能复用」的机会成本。推断

第 2 段　重建：为什么从历史里算，不用内存 Set

announced 不是模块级变量，而是每次调用时从 messages 里重建：遍历所有附件消息，遇到 agent_listing_delta 就把 addedTypes 加进集合、把 removedTypes 删掉。这样得到的集合，等于「这段历史里所有公告的净效果」。源码 v2.1.88

为什么不用内存 Set？因为内存 Set 会在三种情况下失配：恢复会话时内存是空的，但历史里有公告；fork 时子会话复制了历史，但没有复制内存；压缩时历史被替换，内存还留着旧集合。从历史重建，把「已公告」变成「可由历史推导的状态」，恢复、fork、压缩都自动对齐。推断

代价是每次都要扫一遍消息数组，复杂度 O(n)。对一个几千条消息的会话，这个扫描不贵，而且只在生成附件时做一次；相比「缓存失效导致整段重算」，这点 CPU 可以忽略。推断

还有一个语义上的好处：重建只看「历史里实际存在的 delta」，不看「内存里以为存在的 delta」。如果某个 delta 因为压缩、过滤、恢复失败而消失，重建会自动认为「没公告过」，下一次补发全量或差量。它把「状态一致性」变成了「日志重放」问题，而不是「两个副本同步」问题；日志只有一个副本，不存在两个副本之间的同步窗口，也不存在同步失败。推断

第 3 段　求差：added 与 removed 各自怎么算

added 是「当前池里有、已公告集合里没有」的 agent；removed 是「已公告集合里有、当前池里没有」的 type。注意 removed 只存 type 字符串，不存完整定义——移除时不需要描述，只需要名字。源码 v2.1.88

如果两边都为空，函数返回 []。这是 delta 的关键优化：没有变化时，一条消息都不发，零 token、零缓存写入。对比「每次发全量」，省下的不只是列表本身，还有「每次都追加一条消息」带来的历史增长。源码 v2.1.88

isInitial: announced.size === 0 用来标记「这是第一次公告」。第一次时，added 就是全集，removed 为空；接收方看到 isInitial 为真，就知道「这是完整列表」，不需要再去历史里找旧公告。压缩后重播时，传空历史，announced 为空，isInitial 自然为真，同一套逻辑复用。源码 v2.1.88

这里有一个边界：如果已公告集合不为空，但当前池恰好等于已公告集合，added 与 removed 都为空，函数返回 []，而不是一条 isInitial: false 的空 delta。这是对的：没有变化就不该产生消息。但它也意味着「模型看不到一条确认信息」；模型只能通过「没有新消息」推断「没有变化」。在协议设计上，沉默即同意：没有消息本身就是一种状态，接收方必须把「空」解读为「无变化」，而不是「未知」。推断

第 4 段　排序：为什么必须确定

added 在返回前按 agentType 排序，removed 直接 sort()。注释解释：agent 的加载顺序不确定（插件加载竞争、MCP 异步连接），如果不排序，同样的集合可能生成不同顺序的 addedLines，字节不同，缓存就会失效。源码 v2.1.88

这是一个「确定性输出」的要求。delta 的内容是集合，但序列化后是数组；数组顺序不稳定，等于内容不稳定。排序把「集合语义」映射成「稳定字节」，这是缓存友好的基本功。所有做增量注入的系统都会遇到这个问题：状态相同，但序列化不同，缓存照样失效。推断

排序还会影响「差量本身」：如果当前池与已公告集合都按 type 排序，added 的顺序就只取决于 type，不取决于插件加载顺序；下一次重建时，同一个集合会生成同一条 delta 的字节。反过来，如果不排序，即使两次的集合完全一样，字节也可能不同，服务端会认为「有变化」，白写一次缓存。推断

第 5 段　过滤：和 AgentTool 保持同一套规则

在求差之前，代码先过滤 agent 池：收集 MCP 服务器名、读权限上下文、按 MCP 要求过滤、按 deny 规则过滤、按 allowedAgentTypes 过滤。注释说这套过滤要「与 AgentTool.tsx 保持同步」。源码 v2.1.88

为什么必须同步？如果 delta 公告了一个「实际不可用」的 agent，模型会尝试调用，然后失败；如果漏公告一个「实际可用」的 agent，模型不知道它能用，能力被浪费。过滤规则是「什么算可用」的唯一来源，公告和调用必须共用，否则就会出现「说得到、做不到」。推断

还有一个前置检查：如果 AgentTool 不在工具池里，直接返回空。因为公告了也没法调用，纯属浪费上下文。这个检查放在最前面，避免后面所有计算白做。源码 v2.1.88

过滤顺序也有讲究：先按 MCP 要求过滤，再按 deny 规则过滤，最后按 allowedAgentTypes 限制。这个顺序和 AgentTool 的过滤顺序一致，保证「公告的集合」与「实际可调用的集合」是同一个。如果顺序反了，可能出现「先按 allowed 限制，再按 MCP 过滤」的中间集合，与调用侧不一致。源码 v2.1.88

第 6 段　形状：一条附件，四个字段

返回的附件有五个字段：addedTypes（给程序看）、addedLines（给模型看，已格式化）、removedTypes（给模型看）、isInitial（是否首次）、showConcurrencyNote（是否显示并发提示）。源码 v2.1.88

为什么同时保留 addedTypes 和 addedLines？前者用于下一次重建集合（只需要 type），后者用于渲染消息（需要描述、工具、模型等格式化信息）。两者分开，避免「为了重建集合而解析自然语言」。推断

showConcurrencyNote 依赖订阅类型：非 pro 用户显示并发提示。这意味着同样的 agent 列表，在不同订阅下渲染出的附件字节不同；但订阅在会话内稳定，不会每轮变，所以不影响缓存。推断

第 7 段　重播：压缩后为什么要传空历史

压缩会把历史里的 delta 消息删掉。如果不重播，下一轮重建 announced 时集合为空，函数会输出全量——这其实是「自愈」，但自愈发生在「下一轮」，压缩后的第一轮会缺声明。Claude Code 选择在压缩结果里直接重播，让第一轮就完整。源码 v2.1.88

重播的方式很巧：调用同一个函数，传 [] 作为 messages。集合为空、当前池不变，added 就是全集、isInitial 为真，输出全量。一个函数，两种模式，不需要维护两套「全量/增量」代码。源码 v2.1.88

这也意味着「全量」不是特殊的消息类型，而是一条 isInitial: true 的普通 delta。接收方（模型）看到 isInitial，理解为「这是完整列表」；看到 isInitial: false，理解为「在之前的基础上增删」。语义统一，解析简单。推断

第 8 段　代价：重建、超时与遗漏

第一类代价是重建成本：每轮扫历史，O(n)。第二类是超时：getAttachments() 设了 1000ms 的 abort，所有来源并发跑；如果某个来源慢，可能整体被取消，delta 也会缺失。第三类是遗漏：如果历史里的 delta 消息因为某种原因被过滤/丢弃，重建出的集合会偏小，下一次会多发一些「新增」，但不会崩。源码 v2.1.88

这三类代价都指向同一个设计取向：delta 是「可重建的缓存」，不是「唯一真实来源」。丢了可以重建，错了下一轮会自愈；它不承担「记录用户意图」的职责，也不承担「审计历史」的职责，只承担「让模型知道当前能力集合」的职责。理解这一点，就不会把它当成必须精确持久化的状态，也不会为了「补上一条完整的历史记录」而牺牲缓存。推断

但「可重建」有一个前提：历史必须保留那些 delta 消息。如果某个压缩路径把 delta 删掉、又没有重播，下一轮重建会得到空集合，于是发全量；这虽然能自愈，但会让压缩后的第一轮缺声明。源码在压缩结果里显式重播，就是为了补上这个窗口。任何新增的压缩路径，都必须记得调用同一段重播逻辑，否则就会制造一个「一轮的空白」。推断

✓要点小结

  • 37 个附件来源分三组并发执行，1000ms 超时，结果追加在消息尾部。
  • agent 列表、延迟工具、MCP 指令做成 delta：只发新增/移除，无变化零字节。
  • 已公告集合从历史重建，不用内存 Set，恢复/fork/压缩自动对齐。
  • 排序保证同样的集合生成同样的字节，避免无谓的缓存失效。
  • 清单放前缀会导致整段 schema 失效（约 10.2% cache_creation），放尾部只影响追加点。

05 · 与其他工具的差异

四种「只注入变化」，四种状态载体

Claude Code 用尾部附件做 delta，Codex 用世界状态做 section diff，pi 用系统提示 section patch，Grok 用已公告集合。目标相同，载体不同。推断

第一个对照是「状态存在消息里还是消息外」。Claude Code 把状态存在消息里（旧 delta 本身就是消息），所以能随历史一起恢复、fork、压缩；Codex 把状态存在持久化快照 + rollout patch 里，消息里只有片段；pi 存在会话的 sections 里，系统提示是投影；Grok 存在公告快照文件里。消息内状态最自解释，但占上下文；消息外状态最省，但需要额外的恢复逻辑。推断

第二个对照是「差分发生在系统提示还是消息尾部」。Codex 与 pi 的差分结果进入系统提示/提示词 section，属于请求前缀；Claude Code 的 delta 进入消息尾部，属于追加。前者的好处是「模型总能在系统提示里看到完整状态」，坏处是「一变就影响前缀」；后者的好处是「只影响尾部」，坏处是「状态分散在历史里，需要重建」。推断

第三个对照是「无变化时的行为」。四家都做到「零字节」或「零 patch」，但实现不同：Claude Code 返回空数组，Codex 返回空 updates，pi 不生成 patch，Grok 不发差量。零字节是缓存友好的极致；任何「每次发一条心跳」的设计，都会让缓存每轮失效。推断

第四个对照是「状态错了怎么恢复」。Claude Code 的 delta 是「可重建缓存」：下一轮从历史重算，错了会自愈，丢了会补发；Codex 的快照是「持久化基线」：丢了会退到 Unknown，多发一条替换；pi 的 sections 是「会话投影」：丢了就重新生成整段；Grok 的公告快照是「文件状态」：丢了可能重复公告。可重建的设计更宽容，但依赖「历史不丢」；持久化基线的设计更精确，但依赖「快照不丢」。两种都要面对同一个问题：压缩会删历史，所以压缩后必须显式重播或重建。推断

把四个对照合起来，Claude Code 的 delta 是「消息内的、尾部的、可重建的」增量；Codex 的 section diff 是「快照驱动的、系统提示/历史里的、持久化的」增量。前者轻、后者准；前者适合频繁变化的能力清单，后者适合必须精确对账的规则与环境状态。选哪种，取决于你更怕「缓存失效」还是更怕「状态不一致」。推断

还有一条容易被忽略的差异：Claude Code 的 delta 是「给模型看的自然语言」，Codex 的 section 片段也是自然语言，但 pi 的 patch 是「结构化 JSON」。自然语言更适合模型直接理解，结构化 patch 更适合程序精确重放。前者把解析负担交给模型，后者交给运行时。没有哪种绝对更好，关键看你的消费方是模型还是运行时；如果你的运行时需要严格重放（比如回滚、审计），结构化 patch 更合适；如果只是让模型知道「现在有什么」，自然语言更省事。推断

06 · 思考题

三道题，从重建到缓存

Q1

历史里有三条 agent delta：+A、+B、-A。当前可用 agent 是 {B, C}。下一次 delta 会包含什么？isInitial 是 true 还是 false？

提示（不给答案）

按顺序应用：announced 先加 A，再加 B，再删 A，得到 {B}。当前池是 {B, C}，所以 added = [C]，removed = []。

isInitial 看的是 announced.size === 0；这里 size 是 1，所以为 false。附件只包含新增的 C，不包含 B。

再想一步：如果历史里还有一条更早的 -B、之后又 +B，顺序会影响最终集合。重建是按时间顺序应用的，所以最终状态取决于最后一条操作；这也是为什么 delta 必须按历史顺序扫描，不能只取最后一条。

Q2

如果把「已公告集合」改成模块级 Set，在恢复会话、fork、压缩三种场景下各会发生什么？

提示（不给答案）

恢复会话：内存 Set 是空的，但历史里已有公告；下一次会把所有 agent 当成「新增」再公告一遍，浪费 token，模型可能看到重复定义。

fork：子会话复制了历史，但没有复制内存；同样会重复公告。压缩：历史被替换，内存还留着旧集合；下一次会认为「已经公告过」，于是不发，模型反而缺声明。三种场景的错法不同，但根因相同：内存状态与历史不同步。

Q3

你想给 delta 加一个 generatedAt 时间戳，方便调试。这个改动会带来什么后果？如果一定要保留可调试性，你会怎么做？

提示（不给答案）

时间戳每轮都不同，delta 的字节就每轮都不同。即使 agent 列表没变，附件也会变成「有变化」，缓存从追加点之后失效；更糟的是，announced 重建只关心类型，时间戳对语义没有贡献，纯属噪声。

要调试，可以把时间戳放在日志/遥测里，而不是放进模型可见的附件；或者只在 isInitial 为真时放一次，后续 delta 不带。原则是：凡是进入请求体的字段，都要对「模型理解」有贡献，否则就是缓存负担。

还可以把时间戳换成「内容哈希」：哈希只在内容变化时变，既能调试「这是哪一版」，又不会每轮抖动。代价是哈希对模型没有语义，仍然占一点 token；如果只用于排查，最好放在服务端日志里。
