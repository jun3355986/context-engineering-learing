头尾保留的截断预算

工具输出太长时，Codex 不砍头也不砍尾，而是把中间挖掉，换成一句「…N tokens truncated…」。听起来简单，但要同时做对四件事：按 token 估预算、左右对半分、UTF-8 不切半个字符、标记不占预算。这一节读的就是这四件事。

读完你能做到

  1. 用一个公式算出给定字符串在 max_tokens 下的左右预算与保留字节数。
  2. 解释为什么最终结果可能超过 max_tokens，以及这是不是 bug。
  3. 说清多块输出共享预算时，文本、图片、音频各自怎么处理。
  4. 比较 Codex、pi、opencode v1、DeepSeek Harness 四家「保留哪一端、原文能否回读」的差异。

读之前

01 · 功能说明

为什么是「挖中间」，不是「砍尾巴」

工具输出有两种典型形态。一种是命令回显：开头是命令行，结尾是错误信息或统计，中间是大段无关日志。另一种是文件内容：开头是导入与类型定义，结尾是导出与主逻辑，中间是重复的实现。两种形态都指向同一个结论：头和尾有信息，中间最容易冗余。推断

砍尾巴会丢掉错误信息，砍头会丢掉「这是什么命令」。挖中间是唯一能同时保住两端的做法。

Codex 把这件事做成一个纯函数：输入字符串与 token 预算，输出「头 + 标记 + 尾」。它不关心调用方是 shell、文件读取还是 MCP 工具，也不关心内容语义；所有判断都落在「保留多少字节」上。这种「只做机械截断」的设计，让它可以被所有工具复用，也让行为可预测。已核实

在整条链路里，它位于「工具返回结果」和「写入活历史」之间。上游的 formatted_truncate_text() 先判断是否超限，超限时加一行说明头（原始 token 数、总行数），再调用 truncate_text()；truncate_text() 按策略分派，token 策略走本节这个函数。下游把结果写进历史，原始载荷仍留在 rollout 存档里。已核实

先给结论：这个函数保证「保留的文本不超过预算」，但不保证「最终字符串不超过预算」。标记是额外加的，说明头也是额外加的。理解这一点，后面看代码时就不会把「超预算」误判成 bug。已核实

为什么要在「写入历史」时截断，而不是「发请求」时截断？因为历史是活的：一条工具结果写进去之后，会被后续很多轮请求反复读取。写入时截一次，后面每轮都省；发请求时截，每轮都要重算，而且模型看到的投影会随预算变化而抖动。Codex 选择在写入时定稿，代价是「原文只留存档、消息里不可逆」；收益是「一次成本，长期复用」。推断

这个选择还有一个副作用：同一份存档在不同截断策略下恢复，得到的活历史长度可能不同。因为恢复时会按「当前策略」重新套用截断，而不是沿用写入时的结果。这也解释了为什么 rollout 里必须保留原始载荷——否则换一个更宽松的策略，也找不回已经被砍掉的中间。推断

从工程角度看，这套函数刻意只依赖 &str 和两个整数，不依赖任何配置、模型或网络。它可以在一次请求里被调用几十次，也可以被单元测试穷举边界。把「策略」留在调用方、把「机制」做成纯函数，是这类基础设施代码最值得学的一点：机制越纯，越容易被复用和验证。推断

纯函数还有一个好处：它可以在写历史之前被单独测试。测试里用 "é中😀é"、"😀😀😀" 这类边界输入，就能覆盖「预算小于一个字符」「全是被挖掉的中间」等极端情况，不需要构造完整的请求或启动模型。截断这种「看起来简单、边界很多」的逻辑，最值得这样测。已核实

pub fn plan_token_truncation(s: &str, max_tokens: usize) -> Option<TextTruncation> {
    let max_bytes = approx_bytes_for_tokens(max_tokens); // token → 字节
    if s.len() <= max_bytes {
        return None; // 没超，原样返回
    }
    let (left_budget, right_budget) = split_budget(max_bytes); // 对半分
    let removed = s.floor_char_boundary(left_budget)..s.ceil_char_boundary(s.len() - right_budget);
    let removed_tokens = approx_tokens_from_byte_count(s.len() - max_bytes);
    Some(TextTruncation {
        removed, // 要被挖掉的字节区间
        marker: format!("…{removed_tokens} tokens truncated…"),
    })
}

pub fn truncate_middle_with_token_budget(s: &str, max_tokens: usize) -> (String, Option<u64>) {
    let Some(truncation) = plan_token_truncation(s, max_tokens) else {
        return (s.to_string(), None); // 没超：原文 + None
    };
    let truncated = assemble_truncated_output(
        &s[..truncation.removed.start], // 头
        &s[truncation.removed.end..], // 尾
        &truncation.marker, // 中间的标记
    );
    let total_tokens = u64::try_from(approx_token_count(s)).unwrap_or(u64::MAX);
 
    if truncated == s { // 防御：边界对齐后可能没真正删掉东西
        (truncated, None)
    } else {
        (truncated, Some(total_tokens)) // 返回原始 token 数，供上层记录
    }
}

pub fn approx_token_count(text: &str) -> usize {
    let len = text.len();
    len.saturating_add(APPROX_BYTES_PER_TOKEN - 1) / APPROX_BYTES_PER_TOKEN // ceil(len/4)
}
 
fn split_budget(budget: usize) -> (usize, usize) {
    let left = budget / 2;
    (left, budget - left) // 奇数预算时右边多 1 字节
}

04 · 逐段解读

四个动作：估、分、对齐、拼

第 1 段　估：token 与字节的换算

常量 APPROX_BYTES_PER_TOKEN = 4 写在文件开头（L6）。预算换算只有两行：approx_bytes_for_tokens(tokens) = tokens × 4，approx_token_count(text) = ceil(len / 4)。两个方向都是估算，不是真实分词。已核实

为什么用 4？源码没有注释解释。已核实从效果看，这是一个跨语言的折中：英文大约 4 字节一个 token，中文一个字 3 字节、往往也接近一个 token，代码与符号的密度更高。用固定 4 的好处是实现简单、无依赖、可预测；坏处是对中文和代码的误差方向不同——中文可能低估，代码可能高估。推断

误差方向很重要。低估意味着「以为还在预算内，实际已经超了」，截断不够；高估意味着「提前截断」，浪费预算。Codex 在工具出口还有一层 ×1.2 的序列化余量（output-truncation L17-L21），可以理解为对低估的补偿。推断

估算是预算系统的第一道误差源。所有「按 token 截断」的工具，本质上都在用一个近似值做硬决策。

第 2 段　分：为什么对半分

split_budget(max_bytes) 把预算切成 budget/2 与 budget - budget/2。奇数时右边多 1 字节。这个选择没有语义判断，纯粹是「头尾同等重要」的默认假设。已核实

对半分的代价是：如果内容明显「头重要尾不重要」，会浪费一半预算在尾部。比如一个 JSON 输出，开头是结构、结尾是闭合括号，中间是数据；对半分能保住结构和闭合，但保不住更多数据。要做得更好，需要按内容类型给不同权重，比如 shell 输出尾部权重更高、文件读取头部权重更高。Codex 没有这么做，因为它要的是一个通用函数，而不是每个工具一套启发式。推断

对半分的好处是可解释。用户看到「…N tokens truncated…」时，可以预期头和尾各留了大约一半；调试时也容易复现。启发式权重虽然可能更优，但很难让用户建立稳定预期。推断

还有一个实现上的细节：split_budget 把「余数」给了右边。预算 41 字节时，左 20、右 21。这个 1 字节的偏向没有语义，只是整数除法 + 减法的自然结果。它不会造成可见差异，但如果你在写测试断言「左右完全相等」，就会在奇数预算上失败。已核实

第 3 段　对齐：不切半个字符

Rust 的字符串是 UTF-8 字节序列，不能随便按字节下标切片。代码用 floor_char_boundary(left_budget) 把前缀终点退到最近的字符边界，用 ceil_char_boundary(len - right_budget) 把后缀起点进到最近的字符边界。前者只会让头更短，后者只会让尾更短，所以保留总量不会超过预算。已核实

这两个函数的方向容易记反：前缀要「向下取整」，因为切在字符中间会留下半个字符；后缀要「向上取整」，因为起点必须落在字符开始处，否则会从半个字符开始。一个向下、一个向上，保证两端都是完整字符。已核实

对齐的副作用是「实际保留可能略少于预算」。最坏情况是一个 4 字节的 emoji 跨在边界上，左右各退/进 3 字节，保留量比预算少 6 字节。对预算来说这是安全方向；对「尽量多用预算」来说这是小损失。测试里用 "é中😀é" 与 max_tokens=1 验证了这一点：预算 4 字节，最终只剩头尾两个 é。已核实

为什么不做「按行截断」？按行看起来更自然：保留前 N 行和后 M 行，不会切到半个字符，也不会切到半行。但行长度差异极大：一行可能是 10 个字符，也可能是 10 万字符的压缩 JSON。按行数分配，无法保证 token 预算；按字节分配再对齐到行，又会让短行浪费大量预算。按字节 + 字符边界，是「预算可控」与「不切坏字符」之间的最小折中。推断

这个测试还揭示了一个容易忽略的语义：截断可能把整段内容「压缩到只剩两端各一个字符」。对 "😀😀😀" 这种全是 4 字节字符的串，预算 1 token（4 字节）时，左预算 2 字节落不到任何完整字符，右预算 2 字节也落不到，结果只剩标记。也就是说，「头尾保留」在极端情况下会退化成「只保留标记」，而不是「至少保留一个字符」。调用方如果假设「结果一定非空且包含原文」，需要自己加判断。已核实

第 4 段　拼：标记为什么不算预算

plan_token_truncation() 先算出 removed 区间，再生成标记。标记的长度没有参与 max_bytes 的计算，也没有从左右预算里扣除。规划函数的注释（L15-L16）明确写了这一点：标记在保留文本预算之外。已核实

这是一个有意的取舍。如果标记也占预算，那么预算很小时（比如 10 token），标记可能占掉一半，留给正文的只有几个字节，结果几乎不可读。把标记放在预算外，保证「无论预算多小，至少能看到一句解释」。代价是最终长度可能超过预算，超出的部分就是标记的长度。推断

测试里 max_tokens=0 的结果是 "…2 tokens truncated…"，原文 "abcdef" 被完全挖掉。这验证了「0 预算不是空字符串，而是只剩标记」。如果上层把「输出为空」当成错误，这个行为就会制造麻烦；Codex 的调用方显然接受「只有标记」这种结果。已核实

标记里的 N 也不是精确的「被删 token 数」，而是 ceil((原长 − 预算) ÷ 4)。它用的是「超出预算的字节数」，不是「实际被删字符的 token 数」。因为对齐可能多删了几个字节，这个 N 会略小于真实删除量；又因为 4 是估算，它和真实分词器也有偏差。它的作用是「给一个量级」，不是「精确计数」。推断

返回值里的 Some(original_token_count) 也值得一说。它返回的是原始 token 数，不是「被删掉的」token 数；调用方拿到它，可以写日志、打点、或者在说明头里告诉模型「原文有多大」。如果只返回截断后的字符串，上层就不知道这次截断损失了多少信息，也无法判断「是否需要提醒用户重跑」。推断

最后的 truncated == s 是一个防御分支。理论上只要 s.len() > max_bytes，removed 就非空；但 UTF-8 对齐后，如果整个字符串都在边界之外，removed 可能覆盖全部内容，拼出来只剩标记，不可能等于原串。这个判断更像是为未来改动兜底：如果某天 plan_token_truncation 的逻辑变了，返回了「空删除区间」，这里不会误报 Some。推断

第 5 段　多块：共享一份预算

单个字符串的截断之外，工具输出还可能是多块：文本、图片、音频混在一起。truncate_function_output_items_with_policy() 用一个 remaining_budget 贯穿所有块，按顺序扣减。文本按字节或 token 计价，图片直接放行（不占这份预算），音频用调用方传入的估算函数计价。已核实

顺序在这里很关键。预算先到先得：前面的文本块拿满，后面的文本块可能只剩一点，甚至被记成 omitted_text_items 只留一个计数。空文本块会被直接跳过，因为它不贡献内容却占一个数组位置。图片不占预算，意味着「一张图 + 一大段文本」的结果里，文本可能被截得很短，但图片仍然完整。已核实

这套规则没有「按重要性排序」，也没有「先给图片留预算」。它假设调用方已经把重要的块放在前面。如果调用方把日志放在图片之前，日志会先吃掉预算，图片仍然放行，最终请求可能比预期大。这是「共享预算」的边界：它只控制文本与音频，不控制图片。推断

第 6 段　调用方：说明头与 ×1.2

formatted_truncate_text() 在真正截断前先算原始 token 数与总行数，截断后把这两项拼成说明头：Warning: truncated output (original token count: N) 与 Total output lines: M。说明头也在预算之外，最终结果比「头 + 标记 + 尾」又多一段。已核实

说明头的价值在于「让模型知道自己看的是残片」。没有它，模型可能把截断后的输出当成完整结果，进而得出错误结论。有了它，模型至少知道「原文有 N 个 token、M 行，我只看到一部分」，可以选择让用户重跑、读文件或换一种命令。推断

×1.2 的序列化余量则在更外层：with_serialization_allowance(policy) 把策略乘以 1.2，注释说是为序列化与头部预留。它和标记、说明头是三笔独立的额外开销，都不在「保留文本」的预算里。读代码时如果把这三笔混在一起，就会得出「预算完全不准」的错误结论；分开看，每一笔都有明确目的。已核实

把四笔开销列出来，账就清楚了：保留文本 ≤ max_tokens；标记约 20 字节；说明头约 60 字节；序列化余量是策略层的 20%。最终请求里这一条工具结果的真实大小，是四者之和。任何「按 max_tokens 估算请求大小」的做法，都必须把这四笔加回去，否则会低估。推断

第 7 段　与压缩时截断的关系

这套函数不只用于工具出口。压缩时，候选用户消息如果放不下，也会调用 truncate_annotated_text()，而后者内部用的是同一套头尾保留逻辑（见第 29 章第 3 段）。错误信息、沙箱报错、附加上下文也各自调用 truncate_middle_with_token_budget，只是传入的 max_tokens 不同（例如沙箱错误用 900）。已核实

调用点分散带来的一个后果是：同一份文本在不同位置可能被截两次。比如一个工具输出先在 formatted_truncate_text() 里被截到 10k token，写进历史后又在压缩阶段被 truncate_annotated_text() 按 20k 预算重新处理。第二次通常不会再截（因为已经小于 20k），但如果中间又拼了别的片段，就可能触发二次截断。推断

这说明它是一个「基础原语」，而不是「工具专用函数」。理解它的行为，等于理解了 Codex 所有「中间截断」场景的共同底线：头尾保留、UTF-8 对齐、标记不占预算。不同调用方只需要选一个预算数字，不需要各自实现一套截断。推断

代价是「语义适配」被留给了调用方。压缩场景希望保留「用户需求的开头与结尾」，工具场景希望保留「命令与错误」，两者都用对半分，未必各自最优。但统一原语带来的可测试性、可解释性，通常比每个场景单独调参更重要。推断

✓要点小结

  • 预算按 tokens × 4 换成字节，左右各一半，UTF-8 边界只退不进。
  • 标记、说明头、×1.2 余量都在保留预算之外，最终长度可能超过 max_tokens。
  • 被挖掉的中间用「…N tokens truncated…」标记，N 是量级，不是精确分词。
  • 多块输出共享一份预算：文本扣减、音频估算、图片放行。
  • 原始输出仍留在 rollout；消息里只有残片与标记，没有回读指针。

05 · 与其他 agent 的差异

保留哪一端，决定模型还能不能自救

截断策略的分歧不在「留多少」，而在「留哪一端」以及「原文能不能回读」。前者决定模型看到什么，后者决定模型能不能自己补看。

第一个对照是「保留位置」与「工具语义」的匹配。pi 让读类工具保头、bash 保尾，因为文件开头有结构、命令结尾有错误；Codex 统一挖中间，不区分工具，因为它要的是一个跨工具通用的原语。统一策略的好处是行为可预测，坏处是对某类工具不够贴合：比如 git diff 的尾部可能比头部更重要，挖中间会同时保住两端，但也可能把关键的 diff 块挖掉。推断

第二个对照是「原文可回读」。pi、opencode、dsh、Grok 都会在消息里留下路径或句柄，模型可以再读一次；Codex 的消息里只有标记，没有路径。原文虽然留在 rollout 存档里，但模型在当轮看不到「去哪读」。这意味着 Codex 更依赖「头尾保留得足够好」，而不是「让模型自己补看」。两种设计的代价不同：前者要求截断策略更准，后者要求文件系统与权限更可靠。推断

第三个对照是「预算单位」。Codex 与 dsh 用估算 token，pi、opencode、Grok 用字节或行数。字节/行数的优点是可直接测量、无分词依赖；缺点是同样 50 KB，中文与英文的 token 数差很多。token 估算的优点是更贴近计费，缺点是估算本身有误差。没有哪种绝对更好，关键看你要优化的是「请求大小」还是「账单大小」。推断

第四个对照是「截断发生的时机」。Codex 在写入活历史时截断，之后每轮复用同一份残片；pi、opencode 在工具返回时截断并落盘；dsh 在 tools/post-execute 之后按共享预算处理；Grok 在工具实现内部按上限截断。时机越靠前，原文越完整、后续策略越可调；时机越靠后，模型看到的投影越稳定、缓存越友好。Codex 选择「靠后但一次定稿」，等于用「不可逆」换「可预测」。推断

06 · 思考题

三道题，从算数到改策略

Q1

一个 100 字节的纯 ASCII 字符串，max_tokens = 10。左右预算各多少字节？被挖掉多少字节？标记里的 N 是多少？最终字符串大约多少字节？它满足「不超过 10 token」吗？

提示（不给答案）

预算 = 10 × 4 = 40 字节；split_budget(40) 得到 20 与 20；被挖掉的是 100 − 40 = 60 字节；N = ceil(60/4) = 15。

标记 "…15 tokens truncated…" 本身约 22 字节，加在 40 字节之外，所以最终约 62 字节。按 4 字节/token 估算约 15.5 token，明显超过 10。这不是 bug，是「标记不占预算」的直接结果。

再算一步：如果调用方看到「结果 62 字节」就以为预算失效，把 max_tokens 调到 5，标记仍然是 22 字节，正文只剩 20 字节，最终仍有 42 字节。预算越小，标记占比越大，这是这套设计在极小预算下的固有失真；如果调用方经常传很小的预算，应该考虑单独限制标记长度或直接拒绝。

Q2

一段 900 字节的中文（约 300 个汉字），max_tokens = 100。按 Codex 的估算会保留多少字节？如果真实分词器大约 1 个汉字 1 token，这次截断够不够？你会怎么改？

提示（不给答案）

900 字节 ÷ 4 = 225 token，超过 100；预算 400 字节，左右各 200 字节；UTF-8 边界对齐后，大约保留 133 个汉字（400 ÷ 3）。

按真实 1 字 1 token 算，133 字约 133 token，仍然超过 100。要修正，可以把中文的字节/token 比调低（比如 2 或 2.5），或者改用真实分词器。代价是失去「无依赖、可预测」这两个优点。

Q3

多块输出里有一张图片、一段 10 万字节的日志、一段 2 千字节的错误信息，顺序是「日志 → 图片 → 错误」。预算 10k token。结果会怎样？如果希望错误信息一定保住，你会怎么改？

提示（不给答案）

日志先吃掉全部预算（10 万字节 ≈ 25k token，远超 10k），被截断；图片直接放行，不占预算；错误信息轮到时 remaining_budget 已经是 0，只会增加 omitted_text_items，内容完全不进结果。

最直接的改法是调整顺序，把错误信息放在日志之前。更稳的做法是给「错误/摘要类块」单独的保留预算，或者先按块类型排序再扣减。代价是策略变复杂，且需要调用方给块打类型标签。
