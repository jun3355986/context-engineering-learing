检查点：一条消息 + seq 边界

v1 的检查点跨两条消息，靠一个 id 找到保留段；v2 把它压成一条消息，摘要和保留段都装在里面，再用单调的 seq 切出一段连续历史。这一节读这条消息长什么样，以及「按 seq 取段」为什么让顺序重新变得可信。

  • 约 15 分钟
  • 2 个代码块 · 3 张图
  • L4
  • 源码 042d083（beta v2.0.29）

读完你能做到

  1. 列出 v2 检查点消息的字段，并说出哪些字段只在原生压缩时出现。
  2. 解释 latestCompaction() 的三种 boundary 各自滤掉了什么。
  3. 说明 entriesForRunner() 为什么要在一个事务里同时取消息与指令基线。
  4. 把 v1 的「两条消息 + 重排」与 v2 的「一条消息 + seq」并排讲清。

读之前

v2 的存储是 SQLite，消息表有一个单调递增的 seq 列。压缩写入一条 type: "compaction" 的消息；读取时按 seq 取「这条及之后」的连续段。没有重排，也没有「按 id 找保留段」这一步。

01 · 功能说明

检查点是一条消息，不是一对消息

SessionMessage.Compaction 是一个按 status 区分的联合类型：running、completed、failed。已核实completed 分支的字段是：

status: "completed"、reason: "auto" | "manual"、可选 model、可选 providerState、summary、recent、可选 providerContext、可选 cost 与 tokens。已核实

摘要、保留段、原生窗口、这次压缩自己的花费，全在同一条记录里。读取方只需要一个 seq，不需要再去找「摘要消息」和「保留起点」。

summary 是模型写的结构化摘要；recent 是保留段的文本（由 splitConversation() 生成），不是原始消息的引用；providerContext 只在原生压缩时出现，里面是 provider 返回的加密窗口与 provenance。已核实

投影成模型消息时，providerContext 存在就直接解码成原生块；否则包装成一个 user 消息：

<conversation-checkpoint> + 一句「当作历史、不要当新指令」+ <summary>…</summary> + <recent-context>…</recent-context> + </conversation-checkpoint>。已核实

03 · 源码摘录

两段：找边界，按边界取段

第一段是 latestCompaction() 的查询，33 行；第二段是 messageEntries()，25 行。合计 58 行，两段都能独立读懂。

文件：packages/core/src/session/history.ts　行号：L28-L60（34 行，完整）

TypeScript 
// 只取 seq 一列：调用方只需要边界，不需要整条消息
export const latestCompaction = Effect.fnUntraced(function* (
  db: DatabaseService,
  sessionID: SessionSchema.ID,
  boundary: Boundary,
) {
  return yield* db
    .select({ seq: SessionMessageTable.seq })
    .from(SessionMessageTable)
    .where(
      and(
        eq(SessionMessageTable.session_id, sessionID),
        eq(SessionMessageTable.type, "compaction"),
        sql`json_extract(${SessionMessageTable.data}, '$.status') = 'completed'`, // 只要完成的
        boundary === "latest"
          ? undefined // latest：模型中立，任何检查点都算
          : or(
              sql`json_extract(${SessionMessageTable.data}, '$.providerContext') is null`, // 文本检查点
              boundary === "local"
                ? undefined // local：只看文本摘要，原生窗口不算
                : and(
                    ...Object.entries(boundary).map(
                      ([key, value]) =>
                        sql`json_extract(${SessionMessageTable.data}, ${`$.providerContext.provenance.${key}`}) = ${value}`,
                    ),
                  ),
            ),
      ),
    )
    .orderBy(desc(SessionMessageTable.seq)) // 最近的在前
    .limit(1)
    .get()
    .pipe(Effect.orDie)
})

04 · 逐段解读

三个边界概念，一次事务

第 1 段　boundary 的三种语义

Boundary 是 "latest" | "local" | Provenance。已核实它们回答的是同一个问题：「这条检查点，当前读者能不能用？」

latest：模型中立。任何 completed 的检查点都算，不管它是文本摘要还是原生窗口。用于「只要给我一份能读的历史」的场景。

local：只看文本摘要。providerContext is null 才算数。用于「我要原始转录 / 本地视图」的场景——原生窗口是别家 provider 的加密载荷，本地读不懂。

Provenance：只认「当前模型能重放」的原生窗口。SQL 里按 providerContext.provenance.* 的每个键值匹配。已核实这防止把 Anthropic 的加密窗口发给 OpenAI。

三种边界对应三种读者，而不是三种存储。存储只有一种：一条 compaction 消息；差别在查询时怎么过滤。

第 2 段　seq 大于等于：为什么不用 id 找保留段

v1 的 tail_start_id 是一个消息 id，读取时要 findIndex 找到它的位置再切片。v2 不需要：检查点自己就有 seq，保留段直接写在 recent 里，后面的消息按 seq >= compaction.seq 取。已核实

这带来两个好处。第一，顺序可信：orderBy(asc(seq)) 出来的就是时间顺序，不会像 v1 那样重排。第二，查询可下推：>= 是索引条件，分页与增量读取都容易。

代价是保留段从「消息引用」变成「文本」。模型读到的是 <recent-context> 里的一段文字，而不是若干条带 role 的消息。它不能再对保留段里的工具调用做续接，也不能靠 tool_call_id 找回结果。v2 的选择是：保留段只用于「读」，不用于「续」。

第 3 段　为什么要过滤「原生检查点之前的 system 消息」

const native = entries.findLast(isCheckpoint)，然后过滤掉 type === "system" && seq < native.seq 的条目。已核实原因是指令 epoch：原生压缩完成时，advanceEpoch() 已经把当前的指令值提升为基线；更早的那些「指令更新」消息已经被基线覆盖，再回放就是重复。

这与下一节的主题直接相连：epoch 推进的时机就是「压缩完成」，而读取时要用同一条规则过滤旧增量。两处必须一致，否则模型会看到「基线 + 基线之前的增量」。

第 4 段　事务：消息与基线必须同一快照

entriesForRunner() 把 messageEntries() 与 InstructionState.initial() 放进同一个 db.transaction()。已核实如果分两次读，中间可能发生一次压缩提交：消息读到了新检查点之后的段，基线却还是压缩前的值，拼出来的请求会自相矛盾。

这也是「每次请求重新投影」的代价：读取路径必须保证一致性，不能靠内存缓存。v1 的 filterCompacted 是纯函数，没有这个问题；v2 把状态放进了数据库，就必须用事务把它锁住。

第 5 段　三种状态与崩溃恢复

检查点是一条消息，但它的 status 会在三个值之间移动。读取方必须对三个值都有确定行为：

status 含义 投影成模型消息 恢复时怎么处理
running进行中压缩请求已发出、未结算空（不投影）结算成 compaction.interrupted
completed完成摘要与保留段已就绪检查点消息作为边界使用
failed失败摘要失败或被拒空（不投影）不推进 epoch

表注：to-llm-message.ts#L303-L304 对 status !== "completed" 直接返回空数组；崩溃结算见 runner/llm.ts#L332-L385。

「不投影」这一点很重要：一条 running 的检查点不会让模型看到半截摘要。toLLMMessages() 的判断是 if (message.status !== "completed") return []，干净利落。已核实所以崩溃后重建上下文，模型看到的是「检查点之前的历史」——可能很大，但至少是完整的。

崩溃恢复分两步。第一步是 write-ahead claim：execution.ts 在开始执行时于同一事务写 time_suspended 标记，正常结束时释放；进程被 kill 时标记留着，下次启动据此判断「上次没跑完」。已核实第二步是结算：启动 drain 之前，把所有遗留 running 的压缩结算成 compaction.interrupted，把所有 streaming / running 的工具结算成 aborted。已核实

这套机制比 v1 强在哪？v1 只有「进程内中断清理」：中断时把未结算的工具标成 error 并加 metadata.interrupted。已核实如果进程直接崩溃，没有下一次启动的结算，遗留状态就一直是 running。v2 把「恢复」变成数据库属性，不再依赖进程优雅退出。

代价是「谁有权结算」。结算逻辑必须在任何新工作开始之前跑：如果新请求先于结算读到一条 running 检查点，latestCompaction 只认 completed，于是会退到更早的边界、或干脆没有边界——上下文可能突然从「压缩后」变回「压缩前」。两条规则要一起看：查询只认 completed，恢复负责把 running 清掉。少一条都会留下不一致。

第 6 段　fork、model 字段与「一条消息」的边界

检查点里的 model 在 schema 上是可选字段，但 publish() 每次都会写入 context.model.ref，文本压缩也不例外。已核实它的作用有两个：记录这次摘要由哪个模型产出；以及在原生压缩时，与 providerContext.provenance 一起回答「这段加密窗口能不能被当前模型重放」。

文本检查点不需要 model，因为摘要是一段普通文本，任何模型都能读。这也是 boundary = "local" 能跨模型使用的原因：它只挑 providerContext is null 的检查点。

fork 时，boundary 的 before / through 决定复制到哪条消息。如果边界落在一条原生检查点之后，子会话会继承 providerContext；如果子会话换了 provider，replayable() 会把它过滤掉，退回到文本摘要或更早的边界。已核实这是「一条消息自包含」的代价：它把 provider 绑进了记录里。

最后一个边界：检查点消息本身也是一条普通消息，会被 messageEntries() 的 seq >= 选中，也会被 replayable() 检查。它没有特殊通道，没有「跳过自己」的逻辑。这种「把元数据也当消息」的做法让读取路径统一，代价是每次查询都要多一层类型判断。

第 7 段　为什么是 seq，不是 time_created

v1 用 time_created 排序，v2 用 seq。两者都能表达「先后」，差别在「同一毫秒」与「导入消息」。

time_created 是毫秒时间戳，同一毫秒内写入的多条消息需要额外的 tie-breaker；v1 的 page() 就用 desc(time_created), desc(id) 两级排序。已核实seq 是单列单调值，天然唯一，不需要 tie-breaker。

更麻烦的是导入。从别的工具迁移过来的会话，time_created 可能不是单调的（时区、时钟回拨、批量导入）；seq 由持久事件写入时分配（projector 直接取 event.durable.seq），导入时按 index + 1 重新编号（session/transfer.ts#L84），与外部时间无关。已核实这也是 v1 注释里那句「IDs are only a deterministic tie-breaker because imported messages do not necessarily have monotonic IDs」的背景。

代价是 seq 只在单个会话内有意义，不能跨会话比较；time_created 可以。v2 的所有查询都以 session_id 为前缀，所以这不是问题。选 seq 等于承认「会话是独立的时间线」，与 v2 的 event-sourcing 模型一致。

第 8 段　cost 与 tokens 记的是什么

检查点上的 cost 与 tokens 很容易被误解为「压缩后上下文有多大」。schema 的注释写得很明确：Usage of the compaction request itself, not the size of the resulting context.已核实

它们记的是「生成这条摘要花了多少」：输入是发给摘要模型的历史，输出是摘要文本，可能还有缓存读写与推理 token。多次模型调用（例如 NUDGE 之后重试）会累加。publish() 从 spent 这个 Map 里取总和，附在事件上。已核实

这个区分对成本分析很重要。想知道「压缩后上下文多大」，要看下一条 assistant 的 tokens.input，或者 estimateContext()；想知道「压缩本身多贵」，才看检查点的 cost。两个数经常被混在一张报表里，结论就会错。

另一个细节：失败的压缩也有 cost 与 tokens（CompactionFailed 带 CompactionUsage）。已核实因为模型调用一完成就计费，失败不等于免费。统计「压缩开销」时如果只算成功的，会低估。

✓要点小结

  • v2 检查点是一条消息，running / completed / failed 三态。
  • completed 带 summary、recent、可选 providerContext、cost、tokens。
  • boundary 有三种：latest（中立）、local（只看文本）、Provenance（只认可重放的原生窗口）。
  • 读取是 seq >= checkpoint.seq 的连续段，不重排，顺序可信。
  • 保留段以文本存在检查点里，模型能读不能续；消息与指令基线必须同一事务读取。

05 · 与其他工具的差异

检查点的四种记法

「压缩后从哪继续」这个问题，四家给了四种答案：pi 记 id、omp 记 id + reset 边界、v1 记 id 并重排、v2 记 seq 并取连续段。差别不在功能，而在「读取方要对顺序负责到什么程度」。

表注：v2 042d083（beta）；v1 733b2c6；pi b45e0eb；omp f979f46。「顺序可信」指读取结果的下标与时间顺序一致。

三点对照：

一是检查点的原子性。v1 要写两条消息 + 一个字段，三条记录之间没有事务保证；v2 只有一条消息，写入是原子的。这直接减少了「摘要写了但指针没写」这类中间状态。v2 用 status 显式表达中间态：running 时可以崩溃，恢复时结算成 interrupted。

二是保留段的结构。pi 与 v1 保留原始消息，模型可以继续调用；v2 把保留段文本化，模型只能读。这不是退步，而是「检查点即归档」的设计：v2 希望一条消息就能完整描述「压缩后的世界」，不依赖外部指针。

三是多次压缩。v1 需要「隐藏上一对压缩消息」，读取时只认最后一个带 tail_start_id 的标记；v2 只认最近一条 completed，更早的天然在 seq 窗口之外。规则更少，副作用是「上一次的摘要不会自动继承」——v2 靠 previousCompaction() 在生成新摘要时显式带上，而不是读时拼接。

06 · 思考题

三道题，从读 SQL 到判断 boundary

Q1

会话里有 seq 10（文本检查点）、seq 20（原生检查点）、seq 30（文本检查点）。用 boundary = "local" 查，边界是哪条？换成 "latest" 呢？

提示（不给答案）

local 的 SQL 条件里 providerContext is null 为必需，所以 seq 20 被排除；降序取第一条，是 seq 30。

latest 的 boundary 分支是 undefined，不过滤，降序第一条也是 seq 30。

把 seq 30 改成原生检查点再想一次：local 会退到 seq 10，latest 仍是 seq 30。

Q2

为什么 messageEntries() 要过滤「原生检查点之前的 system 消息」，而不只是过滤检查点本身？

提示（不给答案）

system 消息在 v2 里承载「指令更新」的增量文本。原生压缩完成时，advanceEpoch() 把当前值提升为基线。

基线已经包含那些增量的结果，再回放就是重复，甚至可能与基线冲突（旧增量说「改成 A」，基线说「现在是 B」）。

这也是下一节「指令 epoch」的入口：读取侧的过滤规则必须与写入侧的推进时机一致。

Q3

如果产品要求「压缩后保留段仍能继续调用工具」，v2 的检查点结构要怎么改？代价是什么？

提示（不给答案）

现在 recent 是一段文本，模型读到的是 <recent-context>。要续接，就得恢复成结构化消息，并且保留 tool_call_id 与结果。

可以改成「检查点 + 消息引用」：检查点存边界，保留段仍从消息表按 seq 取。这样结构回来了，但「一条消息自包含」的优点没了。

代价还包括顺序：引用方案要保证被引用的消息不会被后续操作改写，否则检查点描述的世界与消息表不一致。
