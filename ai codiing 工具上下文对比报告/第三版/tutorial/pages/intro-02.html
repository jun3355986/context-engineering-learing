一次请求里装了什么

你只打了一句话，发出去的请求里却已经有五层材料。先弄清这五层是什么，才知道该删哪里。

  • 约 9 分钟
  • 前置：第 1 章
  • L1 → L2

读完你能做到

  1. 说出一次请求里固定出现的五类材料，以及每一类从哪来。
  2. 指出哪一块最容易变大、哪一块几乎不变。
  3. 解释拼接顺序为什么会影响第 5 章的缓存账。

01 · 一个“我什么都没干”的请求

2.8 万 token，从哪来的

早上九点零五，你开了一个全新会话，只打了一行字：「登录接口 500，帮我看看」。agent 的状态栏已经显示用掉两万八千 token。你还没让它读任何文件。

你往上翻，对话里也确实只有这一句。于是你怀疑是不是计数错了。

场景 · 你打的字，常常是最小的一块

按下回车时，agent 并不只发出你这一句。它先放一份“岗位说明书”（系统提示），再附上能用的全部工具，再贴上项目规矩、当前目录和今天的日期，最后接上对话记录和你刚打的这句话。这些合在一起，才是模型收到的请求（request）。

用第 1 章的白板来说：你写的只是最底下的一行，上面早已被 agent 写满了。

这一章就把白板上的内容一层层拆开看。不用记参数，只要记住每层“从哪来、多久变一次”。

02 · 请求的骨架

系统提示、工具、规则、环境、历史

先拆一个真实请求。不同 agent 的字段名不一样，骨架却很像。以 Codex 为例，它每次调用模型前都会重新组装一遍请求，里面有四块：历史记录、模型能用的工具清单、系统提示，以及结构化输出的格式要求。

出处：Codex 用 build_prompt 组装 Prompt，四块依次是 input、tools、base_instructions、output_schema。已核实 client_common.rs#L22-L40、turn.rs#L1666-L1695

Codex 用的是 OpenAI 的 Responses API，请求里没有单独的 system 字段；平时说的“系统提示词”，在 Codex 里叫 base_instructions。名字不同，位置一样，都排在最前面。

Claude Code 的系统提示分前后两部分：前面是固定不变的七段（身份、系统通则、做事方式、行动准则、工具使用、语气、输出效率），后面是随环境变化的动态段，中间插一个边界标记（boundary）把两部分隔开。工具定义不放在系统提示里，单独作为一个列表发送。

出处：系统提示由 getSystemPrompt 返回的字符串数组拼成，工具定义走 toolSchemas。源码 v2.1.88 prompts.ts#L444-L577、claude.ts#L1358-L1379

打个比方，这像出差回来找财务报销：公司的财务制度是系统提示；报销系统里能填的几张表单是工具定义；部门自己的惯例（比如“打车只能选经济型”）是规则文件；你在哪个城市、今天几号是环境信息；之前来回的几封邮件是历史；最后那句“帮我报一下”，才是你这次的输入。

把各层摆在一起看，结论可能和你想的相反：最少变化的几层往往体积最大，每次都变的那句话反而最小。所以想省上下文，第一步不该是把自己的话写短。

系统提示：一份写死的岗位说明书

它告诉模型：你是谁、怎么做事、什么时候该先问。agent 会尽量让这一层保持不变。Claude Code 用边界标记把固定段和动态段隔开；大多数动态段生成一次就缓存起来，直到你执行 /clear 或 /compact 才重新生成。

出处：源码 v2.1.88 systemPromptSections.ts#L16-L58

工具定义：远不止“一个工具一句话”

每个工具都要向模型交代清楚：叫什么、做什么、有哪些参数、哪些必填。工具一多，这一层就很长。Claude Code 的办法是延迟加载 MCP 工具：一开始只告诉模型工具名字，模型真要用时再取完整定义；也可以改成按比例判断，这些工具的定义超过窗口的 10% 才延迟加载。Codex 也有类似开关，由模型的元数据决定 MCP 工具是延迟加载，还是一开始就全部给出。

出处：Claude Code 源码 v2.1.88 toolSearch.ts#L46-L49、#L154-L198（10% 阈值在 ENABLE_TOOL_SEARCH=auto 时生效）；Codex 看模型元数据 supports_search_tool 已核实 mcp_tool_exposure.rs#L63-L90

规则文件：逐级拼接，不互相覆盖

Codex 会从当前目录往上找到项目根目录，再把沿途每一级的 AGENTS.md 从根目录到当前目录依次拼起来；总大小默认不超过 32 KiB，超出的部分从末尾截掉。Claude Code 也是拼接，顺序是：组织统一下发的策略规则、你用户目录下的规则、项目里逐级的规则、本地私有规则。拼好之后，它会被包成一条用户消息，插到消息列表的最前面。

出处：Codex 的上限由 project_doc_max_bytes 控制 已核实 agents_md.rs#L60-L160、mod.rs#L254；Claude Code 源码 v2.1.88 claudemd.ts#L790-L950、api.ts#L449-L474

请留意最后这一点：在 Claude Code 里，规则文件不在系统提示里，而是一条普通消息。以后排查“为什么改了 CLAUDE.md 没生效”时，这个细节很关键。

环境与权限：零散地插在消息里

Codex 的请求里没有单独的“环境”字段：当前目录、时间这类信息会写成几段带标签的文本，当作普通消息放进历史。Claude Code 则把当前日期和规则文件包在一起，放在消息列表最前面。所以“现在几点”这一句，在不同 agent 的请求里位置完全不同。

出处：Codex 用 <environment_context>、<current_time_reminder> 等片段 已核实 contextual_user_message.rs#L1-L40；Claude Code 用 <system-reminder> 包裹 源码 v2.1.88 api.ts#L449-L474

历史：唯一每轮都长的部分

你说的话、模型的回复、它调了什么工具、工具返回了什么，都会按顺序追加进来。第 3 章会专门画它的增长曲线。这里先记住：历史是唯一会随轮次一直变长的一层，不加控制就没有上限。

04 · 顺序决定花多少钱

稳定的放前面，易变的放后面

五层的先后顺序看似随意，其实是刻意安排的：从最稳定排到最容易变。

原因第 5 章细讲，这里先说结论：提示词缓存（prompt cache）只对“从开头起完全相同”的那一段生效，这一段叫前缀（prefix）。前面改一个字，后面的缓存就全部失效。所以 agent 会把几乎不变的说明和工具清单放在最前面，把经常变的时间、提醒和你的新消息放在最后。Codex 把当前时间单独做成一段放在末尾，没有写进系统提示的开头；Claude Code 对 agent 列表、MCP 指令只发送变化的部分。它的源码注释提到：agent 列表以前写在工具描述里，列表一变，整段工具定义的缓存就失效，这一项曾占到全体用户缓存写入量（cache_creation）的约 10.2%。

出处：源码 v2.1.88 attachments.ts#L1477-L1556

05 · 回到开头

先看清请求里有什么，再决定删什么

回到开头那个 2.8 万 token 的请求：你的话可能只有几十 token，其余都是 agent 替你准备的材料。这些材料不算浪费，模型要靠它们知道自己在哪个项目里、要守哪些规矩、手上有哪些工具可用。

所以，想省上下文，先别删自己的提问，先查那几层体积大、又很少变的材料：规则文件是不是太长，MCP 是不是连得太多，工具描述是不是太啰嗦。在这些地方砍掉几千 token，比每句话少打几个字省得多。

Q你可能会问

问：规则文件是不是每轮都要重新读一遍、重新拼一遍？

答：不用。规则读一次、拼一次就行，之后也不会每轮再插一份新的。Codex 会把规则和上一次的快照逐段比较：没变就不发；变了，就发一条“已替换”的通知，再附上新的全文。Claude Code 把这部分内容算好一次就缓存起来，直到你执行 /clear 或 /compact。所以遇到“我改了规则，它没反应”，先确认规则有没有被重新读取，别急着怀疑模型不听话。

出处：Codex 的快照比较在 WorldState 里 已核实 mod.rs#L380-L395

✓要点小结

  • 一次请求 = 系统提示 + 工具定义 + 规则 + 环境与权限 + 历史 + 你这句话，再加输出预留。
  • 你打的那句话常常是最小的一块；工具定义随工具数量增长，历史随轮次增长，这两层都没有固定上限。
  • 规则文件逐级拼接，不互相覆盖；Codex 默认上限 32 KiB，超出部分从末尾截掉。
  • 环境信息没有单独的字段，而是零散地插在消息里。
  • 各层按“稳定 → 易变”排序，是为了让缓存的前缀尽量保持不变。
