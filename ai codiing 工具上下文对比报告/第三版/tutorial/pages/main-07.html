历史裁剪：不调用模型的减量

上下文里最占地方的往往不是你的话，而是十轮之前的工具结果。删掉它们不需要再问一次模型，也不该让模型“重新总结一遍”。这一章讲的是减量链里最便宜的一层：只改模型能看见的投影，不动磁盘上的原文。

读完你能做到

  1. 用四个问题判断一个动作是裁剪还是压缩：调不调模型、改的是投影还是内容、原文还在不在、可不可逆。
  2. 解释 opencode 的 40k 保护线、20k 最小收益与 omp 的两档陈旧省略各自在防什么。
  3. 设计一条“裁剪优先、压缩兜底”的减量链，并说出它在缓存与一致性上的代价。

01 · 先说边界

“删掉”和“换掉”不是一回事

下午四点，上下文到了 78%。历史里有 12 次 grep、7 次 read、3 次测试输出。其中 9 次 grep 是零命中，2 次 read 读的是同一个文件的旧版本，测试输出里只有最后一次还有效。你想把这些清掉，但不想让模型重新总结一遍任务——因为任务本身没变，变的只是“还需要看见的细节”。

这时候该用裁剪（trimming），不是压缩（compaction）。两者的边界可以用四个问题划清：

  • 调不调模型？裁剪不调；压缩要调，压缩本身就是一次完整的模型请求。
  • 改的是投影还是内容？裁剪只改“模型可见的投影”，日志原文不动；压缩生成一段新的摘要，用它替换一段历史。
  • 原文还在不在？裁剪后原文仍在，可以还原；压缩后原文通常只在会话日志里，模型看到的是“另一个模型写的交接笔记”。
  • 可不可逆？裁剪可逆（换回投影即可）；压缩不可逆，摘要一旦生成，细节和控制权都变少了。

裁剪是把窗帘拉上一半，压缩是换一扇窗户。

02 · 主线：Codex 的缺位与 Grok 的三段式

Codex 无此能力，主例换成 Grok Build

Codex 没有“定期清空旧工具结果”的独立通道。它不调用模型的减量只有三类：写入历史时的输出截断（第 13 章）、压缩重试时删除最旧条目、以及规范化阶段的丢弃。全仓未找到类似 clear old tool results 的独立 pass。history.rs#L968-L982 已核实1

这三类分别是什么：

  • 写入时截断：只作用于单条输出，不处理“旧结果是否还有用”。
  • 压缩重试删最旧：压缩请求自己超窗时，remove_first_item 删掉最旧一条并同步删除配对的另一半，避免产生孤立调用。history.rs#L685-L700 已核实 它不是“日常裁剪”，而是失败分支。
  • 规范化丢弃：固定四项——补输出、删孤立输出、剥图片、剥音频。history.rs#L968-L982 已核实 这是为了让历史合法，不是为了省空间。

所以本章的主例换成 Grok Build：它有一条完整的、按轮龄分三段、只改请求副本的裁剪链，是七家里最适合讲“零成本减量”的实现。

2.1 触发：超过半窗才动手

Grok 的裁剪在请求构建时执行，作用对象是副本，不改持久化历史。触发条件硬编码在 should_prune：total_tokens > context_window / 2。request_builder.rs#L125-L130 已核实 也就是说，窗口用不到一半时，一个字节都不动。

为什么是 50%，而不是等到 85%。因为裁剪本身是零成本的，早做不会多花钱；而等到接近阈值再裁，往往已经来不及——下一轮工具结果可能直接把上下文推过线。50% 是一个“提前削峰”的位置：既不影响前半程的完整性，又给后半程留出缓冲。代价是每次请求都要扫一遍历史做判定，长会话下有可观的 CPU 开销。

2.2 三段式：保护、软裁剪、硬清空

Grok 把工具结果按“轮龄”分成三段。轮龄的定义很特别：从后往前数 User 项的个数，因此一轮里多次工具调用共享同一个轮龄。request_builder.rs#L132-L177 已核实

0–2 轮 原样保留。最近 3 轮内的工具结果永不裁剪。
3–9 轮 · 超过 4,000 字符 软裁剪：留头 1,500 + 分隔符 + 尾 1,500。
≥10 轮 硬清空：整段替换为 [Tool result omitted — too old]。
任意轮龄 · ≤4,000 字符 不动。小结果裁了也省不了多少。

图 07-1　Grok Build 的三段式。参数：keep_last_n_turns = 3、soft_trim_threshold = 4000、soft_trim_head = 1500、soft_trim_tail = 1500、hard_clear_age_turns = 10。

软裁剪为什么是“头 1,500 + 尾 1,500”，而不是只留头。工具结果的信息分布通常是“开头有命令与摘要、结尾有结论与报错”。中间才是最长的过程。留两头等于用 3,000 字符买下“知道这是什么、结果如何”这两件事，把“具体每一行”留给回读。代价是中间可能藏着唯一一条警告，和第 13 章的中间截断一样，命中率取决于内容。

硬清空为什么到第 10 轮才做。因为轮龄是“重要性”的粗糙代理：越久远的工具结果，越可能已经被后续结果覆盖（同一个文件重读过、同一个测试重跑过）。10 轮是一个经验阈值：足够长，避免误删仍然有效的工作状态；足够短，避免上下文被“僵尸结果”长期占据。代价是它不判断内容，只看年龄——一个 9 轮前读的、至今没变的关键配置文件，会在第 3 轮被软裁剪、第 10 轮被清空，尽管它仍然有效。

2.3 只改副本：UI 与实发请求会对不上

裁剪作用在请求副本上，持久化历史不动。这带来一个可逆性上的好处，也带来一个可观测性上的坑：/context 的 used 仍按未裁剪的会话计算，所以“裁剪后实际发出去的 token”可能低于 UI 显示。request_builder.rs#L125-L177 已核实

这不是 bug，而是“投影”与“原文”分离的必然结果。用户看到的是原文占用，模型看到的是投影。两者不一致时，用户会误以为“还有很多空间”，实际发出去的可能只有一半。代价是排障时要同时看两个数；好处是裁剪永远可逆——下一轮条件变了（比如用户又问了那个文件），可以重新把结果放回投影。

2.4 这一层的代价

第一，轮龄不等于重要性。10 轮前的架构决策可能比 2 轮前的 ls 更重要，但轮龄只看位置。第二，阈值是字符数，对中文与代码的 token 密度不敏感。第三，每次请求重建副本，长会话下 CPU 开销线性增长。第四，它与缓存冲突：裁掉中间一段，后面的前缀位移，prompt cache 可能整段失效。本快照里没有看到这条链的缓存守卫，等于用缓存换空间。推断2

这四点解释了为什么其他家在裁剪上都加了“守卫”或“开关”，而不是照抄三段式。

03 · 四家的零成本减量链

同样是删旧结果，四种约束

除了 Grok，另外四家各有一条不调模型的减量链。它们的差别不在“删不删”，而在用什么当保护线、什么时候跑、删完怎么记。

3.1 opencode v1 的 prune：默认关，保护 40k，可擦超过 20k 才动手

v1 只有一种不调模型的裁剪：compaction.prune，默认关闭。开启后从最新消息往回扫：数到第 2 个 user turn 才开始动手；遇到已完成压缩的 assistant 摘要就停；对每个已完成工具结果累加估算 token，前 40,000 token 受保护不动，超过部分才计入“可擦”；只有可擦总量 > 20,000 token 才真的写回。compaction.ts#L271-L317 已核实

擦除方式是给 part 打 state.time.compacted = Date.now()，原文仍在库里，只是序列化时显示 [Old tool result content cleared]。skill 工具的输出永远不擦。compaction.ts#L28-L33 已核实 调用点在主循环退出之后（runLoop 末尾 fork），不在压缩之前同步跑。prompt.ts#L1338 已核实

为什么要有“最小收益”20k。擦除本身会产生占位符文本，占位符也要 token。如果每次只擦出几百 token，净收益可能为负。设一个 20k 的门槛，等于说“要么一次擦够，要么别擦”。代价是很多小节省永远攒不到 20k：每次会话结束时都差一点，旧结果就一直留着。

为什么默认关。因为它会改写历史（虽然是标记式的改写），而改写会让“重放同一段会话得到同一个上下文”这件事不再成立。默认关，把选择权交给知道自己需要它的用户。

3.2 omp 的两档陈旧省略：删“被覆盖的”和“没用的”

oh-my-pi 有两层不调模型的裁剪，都发生在压缩之前。第一层是 pruneToolOutputs()（阈值裁剪）：保护最近 40,000 token 的工具输出，只有总节省 ≥ 20,000 token 才动手；小于 50 token 的结果不裁（占位符本身约 8 token，裁了反而变大）；永远保护 skill 结果、skill:// 读取结果和当前 plan 参考文件。pruning.ts#L77-L83 已核实

第二层是 pruneSupersededToolResults()（逐轮陈旧裁剪），这是它比 opencode 多出来的一档：

  • 被覆盖的读取：同一个文件被更新的一次 read 覆盖后，旧结果换成 [Superseded by a newer read of this file]。
  • 无用的结果：工具主动标记 useless 的结果（零命中搜索、空目录列表等）换成 [Uneventful result elided]。

这一档的价值在于“语义判断”而不是“体积判断”：一次零命中的 grep 可能只有 200 字符，按体积永远达不到裁剪门槛，但它对模型的价值是零，而且留着会诱导模型再搜一次。把它换成“这次搜索没有命中”，既省了 token，也省了一次重复调用。代价是“无用”由工具自己判定，判错就会删掉有用的空结果语义（比如“确认这个目录确实是空的”本身就是一个结论）。

两层都有缓存守卫：候选结果之后的 suffix 仍在热缓存前缀里时不改（cacheWarmSuffixTokens），或按 provider 的 prompt-cache lookback 位置限制；模型有 prefix-bound thinking 时守卫更严（阈值设为 0）。裁剪是原地改写并 rewriteEntries() 持久化，失败会 undo() 恢复内存，避免内存与磁盘分叉。pruning.ts#L452 已核实

3.3 dsh 的 pruner：8,192 / 4,096 / 1,024，只在压缩前跑

dsh 的历史裁剪只有一个正式机制：ctx.toolResultPruner。它把当前 surface 上超预算的工具结果替换成“头 + 固定省略标记 + 尾”：默认超过 8,192 个 Unicode 码点触发，保留头 4,096、尾 1,024，中间替换为 [... tool result middle pruned ...]；按码点切片，不会劈开代理对。pruner/config.ts#L8-L13 已核实

关键限制：它只在压缩触发合格后运行（pressure 或 overflow 确认之后、选区之前），低于压力的会话一个字节都不动。目的正是“先做无模型的削峰，可能因此完全不需要摘要”。pruner/README.md#L48-L52 已核实3

它还有一个很讲究的细节：替换事件会保留工具调用、step、错误与元数据，只有 content 变；紧邻它之前会写一条 compaction/prune 影子计价事件，把被替换节点按 token meter 计价，让纯投影消费者直接做减法。compaction.md#L105-L133 已核实 这解决了“裁剪后账目对不上”的问题：不用重新遍历整段历史，只看影子事件就知道省了多少。

代价是裁剪不覆盖“陈旧”语义，只按体积切：一个 9,000 码点的旧文件读取会被裁，一个 2,000 码点的过期读取不会。它也不按轮龄清理，没有任何“这条已经没用了”的判断。

3.4 另外三家：pi 没有、Claude 默认关、v2 直接删掉

pi 没有自动把旧工具结果换成占位符的常规裁剪器。唯一的原地裁剪机制是 context_edit 条目：replacement: null 表示把目标条目从模型投影中省略，{content} 表示只替换内容；它只改模型可见投影，不改磁盘原始条目。实际使用点主要是溢出恢复：把刚失败的那次 assistant 尝试及其工具结果省略掉，然后压缩重试。session-manager.ts#L175-L180 已核实 另有一个用户侧的小口子：!! 前缀的 bash 执行消息带 excludeFromContext，convertToLlm() 会整条丢弃。messages.ts#L148-L196 已核实

Claude Code 的 microcompactMessages 有两条路。时间触发：距最后一条助手消息超过 gapThresholdMinutes（默认 60 分钟）时，把旧的可清理工具结果替换成 [Old tool result content cleared]，只保留最近 keepRecent 条；该配置默认 disabled。缓存编辑：只对主线程、受支持模型、且 CACHED_MICROCOMPACT 特性开启时生效，不修改本地消息，而是在 API 层插入 cache_edits（删除指定 cache_reference），让服务端丢弃旧结果而不使缓存前缀失效。microCompact.ts#L253-L293 源码 v2.1.88 源码注释明确：旧版“直接清空旧结果”的路径已删除；外部构建、非 ant 用户、不支持的模型上这里什么都不做，压力完全交给 autocompact。

opencode v2 则把 v1 的 prune 删掉了：配置规范化里把它标成 unsupported。normalize.ts#L333-L334 已核实 它对旧工具输出的治理只发生在构造压缩请求时：flattenAndDropOldest 把历史文本化、必要时按 exchange 整块丢最旧的，并插入 [N older exchanges omitted]。compaction.ts#L457-L504 已核实 这已经是压缩流程的一部分，不存在“平时就静默擦掉旧结果”的通道。

06 · 设计取舍

为什么大多数裁剪默认是关的

下面五组取舍，解释“机制都有、默认各异”的原因。每组给两种路线与代价。

取舍一：原地改写，还是只改投影

原地改写（omp、dsh、Claude 的时间触发）把替换写进会话记录，下一次读取直接看到占位符，不需要每次重建。“只改投影”（Grok 的请求副本、pi 的 context_edit）保留完整原文，每次请求重新算一遍。

代价：原地改写省 CPU、状态一致，但“历史”被永久改变，重放不再等价，且写坏之后需要 undo() 这类补偿；只改投影可逆、可审计，但每次请求都要重算，长会话下成本线性增长，而且 UI 与实发请求容易对不上（Grok 的 /context 就是这样）。

omp 的做法是折中：原地改写，但保留被替换节点的原文与元数据，失败可回滚；dsh 更彻底，原文作为 append-only 事件永久保留，替换只是 surface 上的新事件。

取舍二：按轮龄，还是按预算

按轮龄（Grok 的 3 / 10 轮、opencode 的“至少保留 2 个 user turn”）可预测、易解释：用户能说清“为什么这条被删”。按预算（opencode 的 40k 保护、omp 的 40k / 20k、dsh 的 8,192 码点）直接对着“要省多少”设计，效率更高。

代价：轮龄不衡量重要性，久远但关键的结果会被误删；预算不衡量时间，刚刚产生但体积很小的结果可能被留下，而很久以前的一条巨大结果被保留在保护线内。两者的最坏情况不同：轮龄错在“删了不该删的”，预算错在“没删该删的”。

取舍三：要不要设“最小收益”

opencode 的 > 20,000 与 omp 的 minimumSavings: 20_000 是同一类设计：擦除会产生占位符，占位符本身占 token；如果一次只擦出几百 token，净收益可能为零甚至为负。不设门槛的实现（Grok、dsh）更简单，但会频繁产生“擦了个寂寞”的碎片。

代价：门槛越高，越容易出现“每次都差一点”的死区——旧结果一直攒着，直到某次突然跨过门槛被一次清空。用户看到的行为是“长期不动、偶尔大动”，很难建立稳定预期。

取舍四：裁了会不会更贵（缓存守卫）

裁剪改变历史中间的一段，后面的内容整体位移，prompt cache 的前缀可能从裁剪点开始全部失效。省下的 token 可能远小于缓存失效带来的成本。omp 为此加了缓存守卫：候选结果之后的 suffix 仍在热缓存前缀里时不改，或按 provider 的 prompt-cache lookback 位置限制；模型有 prefix-bound thinking 时守卫更严（阈值设为 0）。pruning.ts#L537 已核实 Claude Code 的 cache_edits 走另一条路：不改本地消息，直接告诉服务端删除缓存引用，从而不动前缀。

代价：守卫会让“明明可以裁”的情况变成“不能裁”，裁剪率下降；cache_edits 依赖模型与特性开关，外部构建直接不生效。Grok 干脆不设守卫，用“缓存换空间”，这是另一种合理选择——当上下文已经过半，空间比缓存更紧急。

取舍五：什么时候跑，默认开还是关

请求前同步跑（Grok、dsh）保证“这一次发出去的一定是裁过的”，代价是每次请求都多一段 CPU，且裁剪结果影响缓存。循环结束后异步跑（opencode v1）不阻塞当前任务，但本轮不受益——它裁的是“下一次会话”。只在压缩前跑（dsh、omp）把裁剪当成压缩的前置削峰，好处是“可能因此不需要摘要”，坏处是“不到压力线就永远不裁”。

默认值的分歧也在这里。默认开（Grok、omp、dsh）意味着用户不用知道这件事就能受益，代价是行为不可预期、排障困难；默认关（opencode v1、Claude 的时间触发）把控制权交给用户，代价是大多数用户永远不会打开，上下文压力全部落到压缩上。Claude Code 的现状最能说明问题：源码注释说旧版清空路径已删除，外部构建里 microcompact 什么都不做，压力完全交给 autocompact。microCompact.ts#L253-L293 源码 v2.1.884

还有一组横切的取舍：裁剪与压缩的顺序。先裁后压（dsh、omp）能用零成本手段降低压缩请求的体积，减少“压缩请求自己超窗”的概率；先压后裁没有意义，因为压缩已经把旧结果换掉了。pi 的顺序是“截断 → 可选 context_edit → 摘要”，中间缺少 omp 那种按预算批量裁剪旧结果的层，所以它更容易走到压缩。

07 · 小测验

三道题，检验你分不分得清

Q1

opencode v1 开启 prune。历史里有 100k token 的已完成工具结果，最近 2 个 user turn 内占 20k，其余 80k 更旧。保护线 40k、最小收益 20k。实际会擦掉多少？为什么？

解析

先扣掉最近 2 个 user turn 的 20k（不参与），剩 80k 可参与；其中最新的 40k 受保护，可擦是 40k；40k > 20k，门槛通过，于是这 40k 被擦。最近 20k 与受保护的 40k 留下，总计 60k 原文 + 若干占位符。若可擦只有 15k，则因为不到 20k 门槛，一个都不擦。见 3.1。

Q2

下面四个动作，哪些调用了模型？哪些属于裁剪？A. omp 的 pruneToolOutputs；B. dsh 的 toolResultPruner；C. Claude Code 的 cache_edits；D. pi 的 /compact。

解析

只有 D 调用模型。A、B 是本地替换，C 是让服务端删缓存引用，三者都不生成摘要，都属于裁剪。C 的特殊之处是“不改本地消息”，因此连投影都不变，只是服务端少了一份缓存内容；它仍然是裁剪，因为没有模型参与、原文还在。见 第 01 节边界表 与 3.4。

Q3

Grok Build 里，一条 10,000 字符的工具结果在第 5 轮、第 11 轮分别会被怎么处理？为什么 /context 显示的占用可能高于实际发出去的请求？

解析

第 5 轮：轮龄 ≥ 3、内容 > 4,000 字符，走软裁剪，保留头 1,500 + 尾 1,500（约 3,000 字符）。第 11 轮：轮龄 ≥ 10，整段替换为 [Tool result omitted — too old]。裁剪只作用于请求副本，/context 的 used 仍按未裁剪的会话计算，所以 UI 会显得更满。见 2.2 与 2.3。
