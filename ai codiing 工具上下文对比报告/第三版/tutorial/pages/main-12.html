跨会话记忆：把经验写进磁盘，而不是写进上下文

记忆不是“更长的上下文”。它是一条独立的读写链路：什么时候写、写什么、怎么合并、什么时候取、取多少、什么时候删。最危险的不是记不住，而是记错了还每次都被注入，最后变成模型的“常识”。

  • 第 12 类
  • 约 20 分钟
  • 1 张回路图
  • L2 → L3

读完你能做到

  1. 判断一条信息该写进规则文件、会话日志还是会话记忆，并说出理由。
  2. 画出一条记忆从写入到注入的链路，指出哪一步最可能引入错误、哪一步最该设预算。
  3. 针对一条错误记忆，设计“发现—止损—纠错—防止复发”四步处理。

01 · 先分清三种持久化

“它一进门就说：这个项目用 Jest”

周一早上，新会话的第一条消息还没发完，Agent 已经在计划里写：“用 Jest 补三个单测。” 你愣了一下——项目上个月已经迁到 Vitest，package.json 里连 jest 都删了。你问它为什么这么说，它回答：“项目记忆里写着测试框架是 Jest。”

它不是幻觉，也不是读错了文件。它读的是一条三个月前写入的记忆：那时候项目确实用 Jest。记忆没有过期，也没有被新事实覆盖，于是每次新会话都把它当作“已知前提”注入。模型没有理由怀疑它，因为注入的位置和措辞都很像一条稳定的项目约定。

这就是跨会话记忆和“长上下文”最根本的区别：长上下文只影响这一次回答，记忆会影响以后每一次回答。一条错误的记忆会复利：后面的每一轮都在沿用这个错误。

先分清三种持久化，再谈记忆。

  • 规则文件（AGENTS.md、CLAUDE.md）：人写的、稳定的约束。它回答“必须怎么做”，改动应该经过 review。错误规则的代价大，但通常有人负责。
  • 会话日志：一次会话的事实记录。它回答“这次发生了什么”，只追加、不自动跨会话注入。它可审计，但不会主动影响下一次。
  • 记忆：从过去会话里提炼出来的、跨会话复用的经验。它回答“以前通常怎么做”，由模型或后台管线写入，天然可错、需要过期与纠错。

三者最容易被混用的场景是“把一次会话的结论直接写进规则文件”。比如“这次迁移发现 legacy.ts 要改成 type-only import”，如果写进 AGENTS.md，它就从“一次性事实”变成了“永久规范”，下个月代码结构变了，规则还在。更合适的做法是写进记忆，并带上日期、来源与适用范围；或者只留在会话日志里，等同类问题第二次出现再提炼。

这条回路上有四个关键决定，后面每一节都会回到它们：写什么（候选选择）、什么时候写（会话结束、压缩前、周期整理）、怎么取（索引一次、每轮检索、按项目隔离）、怎么删（过期、衰减、人工纠错）。四个决定里，最难的是删——因为删除需要判断“这条经验已经不适用了”，而模型通常只会热情地记录，不擅长怀疑自己。

错误的记忆比没有记忆更贵

没有记忆，模型每次都要重新读文件，慢但可纠正。错误记忆会让模型跳过读文件这一步，直接基于旧结论行动；它还会在返回里引用这条记忆，让你的下一轮判断也被污染。更糟的是，有些实现会把“模型引用过这条记忆”当成有用性的证据，于是错误记忆反而更容易被保留。

02 · Codex 主线

一条后台管线，两个阶段，一条读路径

Codex 的记忆不是“边聊边记”，而是一条在根会话启动时触发的后台管线：先判断这次会话该不该跑记忆，再异步做两阶段处理，最后把结果写进状态库。读的时候，另一条路径把记忆作为指令注入，并解析模型对记忆的引用。提交固定为 76ed3b4。

2.1 触发：只在根会话、只跑一次、不阻塞对话

触发条件写得很具体：根会话启动、非临时会话（ephemeral 不跑）、功能开启、不是子代理会话、状态库可用。memories/README.md#L1-L40 已核实 这四条合起来是在回答一个问题：“这次会话有没有资格产生跨会话知识？” 子代理不跑，是因为它的历史是父任务的一部分，不该独立变成长期记忆；临时会话不跑，是因为它可能只是一次试验。

管线是后台异步的：Phase 1 从各线程的 rollout 里提取候选记忆，Phase 2 做合并、整合并落成产物。memories/README.md#L1-L40 已核实 两阶段拆开的好处是：抽取可以便宜、宽进；合并可以贵、严出。抽取阶段宁可多收，合并阶段再做去重、冲突消解和措辞收敛。

为什么不在对话中同步写。同步写会污染当前上下文：模型一边干活一边决定“这条要不要记”，容易把临时假设写进去，还会拖慢每一轮。后台写让主对话保持干净。代价是用户看不见写的过程：这次会话结束后到底记了什么、记错没有，没有一个即时的确认点。

2.2 读路径：作为开发者指令注入，并统计引用

读取由 codex-memories-read 负责：把记忆作为 developer 指令注入，并解析模型对记忆的引用（citations），做使用统计。memories/README.md#L1-L40 已核实 这条设计有两个要点：注入位置是 developer 消息，不是 system 提示；可观测性是引用解析，而不是只看“注入了多少条”。

引用统计的价值在于：它能区分“注入了但没用”和“注入了且被采纳”。如果一条记忆连续很多次被注入、却从未被引用，它可能已经过时或与当前任务无关；如果一条记忆被引用后经常导致返工，它可能是错的。没有引用统计，记忆系统只能看体积，看不出质量。

为什么放 developer 指令。developer 消息的权威性高于普通用户消息，又不必改写 system 提示的固定前缀；这对缓存友好，也让“记忆”和“规则”在层级上分开2。代价是模型可能把记忆当成硬约束，即使它已经过期；因此注入时最好带来源与时间，读路径也要有“与当前仓库冲突时以仓库为准”的优先级。

2.3 隔离与检索：现有材料没有写清的部分

记忆是否按项目隔离，现有材料只写到“由状态库与工作区决定”，没有给出具体字段；检索排序、条数上限、过期策略也没有在 README 里描述1。这意味着我们能确认“有写入、有读取、有引用统计”，但不能确认“它一定按仓库隔离”或“它一定按相关性排序”。写教程时必须把这两件事分开：机制存在是已核实，隔离与排序的实现是待核实。

这个空白本身也有教学价值：跨会话记忆最容易被想当然的两件事，恰恰是“它只影响这个项目”和“它只取相关的”。如果实现按全局状态库存、按时间倒序取，那么你在 A 项目学到的经验会出现在 B 项目，而且最旧的记忆可能最先被注入。没有读到实现，就不能替它假设。

2.4 纠错：管线里最薄的一环

能确认的是两阶段写入与读路径，但没有记录用户可见的记忆编辑、删除或“这条不对”入口。这意味着纠错主要依赖两种间接手段：后续会话产生新事实、合并阶段覆盖旧结论；或者用户直接去状态库里处理（这已经超出普通用户的路径）。

为什么纠错难。写入是批量的、后台的，读取是隐式的、每次发生的；中间没有一个“确认”步骤。模型不会主动说“我依据的是三个月前的记忆，请确认”，它只会把记忆当事实用。代价是一条错误记忆可能活很久，直到某次合并碰巧把它覆盖。对使用者的启示是：不要把关键约束只交给记忆，稳定规范仍应写进规则文件，让 review 流程兜底。

✓要点小结

  • Codex 的记忆是根会话启动时的后台两阶段管线：先抽取候选，再合并落盘。
  • 读路径把记忆作为 developer 指令注入，并用引用解析统计“有没有被用”。
  • 按项目隔离、检索排序、条数上限在本快照未核实，不能想当然。
  • 纠错入口在现有材料里没有记录；稳定约束应留在规则文件，不要只靠记忆。
  • 记忆的价值不在“存得多”，而在“取得准、退得掉”。

03 · 七个编码智能体

有的在写，有的在整理，有的干脆不做

下面七个 agent 各有一个弹窗。先记住一个事实：八个 agent 里有四个没有跨会话记忆——pi、opencode v1、opencode v2、DeepSeek Harness。这些空白是明确的产品选择；跨会话的延续交给规则文件、会话恢复或扩展。剩下的四个里，Claude Code、oh-my-pi、Grok Build 各有完整实现，Codex 是后台管线。弹窗里的“设计意图”是作者根据源码结构做的分析，不是工具作者的自述3。

键盘：Esc 关闭；Tab 在弹窗内循环。Claude Code 的结论来自非官方 v2.1.88 源码，只代表该版本。

Grok Build 是本章最好的对照案例。它把“写”和“取”做成对称的两端：压缩前自动 /flush，把本轮可能被摘要丢掉的事实写进记忆；压缩后再检索一次，把相关记忆补回上下文。前者防止“压缩把还没记的事吃掉”，后者防止“压缩后模型忘了以前学过的经验”。这条对称设计回答了一个很多实现没回答的问题：记忆和压缩不是两个独立功能，它们在同一条时间线上互相补位。

四个“无此能力”要如实写。pi 没有独立记忆子系统，跨会话只能靠 AGENTS.md / CLAUDE.md 与扩展；opencode v1/v2 的出货源码里没有记忆写入、检索、整理模块；DeepSeek Harness 的核心包也没有记忆服务，跨会话只有 AGENTS.md、会话恢复与 @session 快照。pi README#L15-L19 已核实 这些空白不是缺陷清单，而是不同的产品边界：有的把“记忆”视为插件该做的事，有的认为规则文件已经够用。

05 · 设计取舍

为什么“记住”比“想起来”难

下面六组取舍，覆盖了从“这条信息该不该记”到“记错了怎么删”的全链路。每组都给出两派做法与一句代价。它们共同说明一件事：记忆系统的质量，主要不取决于存储多大，而取决于写入有多克制、注入有多准、删除有多可行。

取舍一：写进规则、写进记忆，还是只留在会话里

规则派把稳定约束写进 AGENTS.md / CLAUDE.md：谁都必须遵守、改动要 review、加载路径固定。记忆派把“以前通常怎么做”交给记忆：由模型或后台提炼，允许不完整、允许过期。会话派什么都不持久化，只让这次会话知道。

代价：规则太重，改一次要走流程，容易变成“写了没人看”的长文档；记忆太轻，错了没人负责，还会跨会话复利；只留会话最干净，但同类问题第二次出现时要重新发现。判断标准可以很朴素：如果这条信息错了，会不会造成不可接受的后果？ 会，就写规则；不会，就写记忆；只对这一次有效，就留在会话。

取舍二：自动写入，还是人工确认

自动派（Codex 的两阶段管线、Claude Code 的 auto memory、Grok 的 /flush）让模型或后台自己判断该记什么，用户零操作。人工派（Grok 的 /remember 先弹 review 面板、omp 的 learn 手动捕获）要求用户先确认再落盘。

代价：自动写入覆盖全、不打断心流，但错误也会被自动固化；人工确认质量高，但用户往往不知道“什么值得记”，最后要么全点通过，要么全不记。折中是“自动收集、延迟确认”：先进入 inbox，等整理阶段再让人 review，或者至少让用户能看到“这次记了什么”。

取舍三：会话结束再写，还是压缩前抢救

结束后写（omp 的 consolidation）等会话收尾，再统一提炼。它能看到完整对话，摘要质量高；但如果会话中途崩溃，或者压缩已经把细节吃掉，就来不及了。压缩前写（Grok 的 /flush，阈值 = 压缩阈值 − 4,000 token 余量，每个压缩周期最多一次）在摘要发生之前，把“即将被丢掉的事实”先写进记忆；压缩后再检索一次，把相关记忆补回来。

代价：结束后写简单，但有时序风险；压缩前写要在最紧张的时刻再发一次模型请求，成本和延迟都高，而且“每个周期只写一次”意味着写不进去就没了。Grok 的对称设计（flush + 重检索）是目前最完整的答案，但它也把记忆系统更深地绑进了压缩链路：压缩逻辑一改，flush 的阈值和时机就要跟着改。

取舍四：会话开始注入一次索引，还是每轮检索

一次注入派（Claude Code 的 MEMORY.md 入口、Grok 的有界索引）在会话开始时把索引放进上下文，让模型自己决定打开哪个主题。它省 token、缓存友好，模型有主动权。每轮检索派（findRelevantMemories 一类）按当前对话找相关条目，作为附件注入，相关性更高，但每轮都要算、都要占预算，还会让前缀变化、缓存失效。

代价：索引省，但模型可能不打开；检索准，但贵且不稳定——同一个问题换个说法，取到的记忆可能不同。Grok 的做法是折中：首轮注入索引，压缩后再检索一次，并且如果上下文里已经有 <memory-context> 就跳过，以保住缓存。这个“已经有就不重复注入”的小判断，比多取几条更能省钱。

取舍五：全局记忆，还是按项目隔离

全局派把记忆放在一个跨项目的库里，好处是“我在 A 项目学到的通用经验，B 项目也能用”。项目派（Claude Code 的每项目 memory/、omp 的 memory://root、Grok 的 workspace 作用域）按仓库隔离，好处是不会把 A 项目的框架、路径、约定带到 B 项目。

代价：全局记忆容易串味，尤其是“测试框架”“构建命令”这类项目相关事实；项目记忆则会让通用经验重复学习，每个项目都要重新攒。折中是分两类：通用偏好（输出语言、提交风格）放 global，项目事实（框架、目录、命令）放 workspace。Grok 明确提供两个作用域，正是这个思路。

取舍六：过期衰减，还是人工删除

衰减派（Grok 的 session 记忆 30 天半衰期、越老提示越强）让旧记忆自动降权，不需要用户逐条清理。人工派（/memory clear、/reset、直接编辑 Markdown）把删除权交给用户，精确但依赖人记得去删。不可改派（Grok 生成的 MEMORY.md 不可手改）则是防止“人工编辑把索引改坏”，只允许通过整理流程更新。

代价：衰减会自动放过仍然有效的旧知识，也会让“三年前的最佳实践”在还有用时被降权；人工删除精确，但人会忘；不可改最安全，但纠错路径变长。最稳的组合通常是三者叠加：写入时带来源与日期，读取时按时间降权，界面上给一个明确的“这条不对”入口，并允许整库重置。

最后回到“错误记忆污染”。它不是某一个环节的问题，而是四个环节一起失效：写入时没有来源，整理时没有冲突消解，检索时没有时间权重，删除时没有入口。防污染也不需要四个环节都做到满分，只要至少有一个环节能止损。比如检索时把“记忆”标注为启发式、并在与仓库冲突时以仓库为准；或者写入前让人 review；或者提供一键清空。最怕的是四个环节都“看起来很顺”，却没有任何一个能说“这条不算”。

06 · 小测验

三道题，检验你是否真的会“记”

Q1

“这个仓库用 pnpm，不要用 npm”应该写进规则文件、会话日志还是记忆？如果写成“上次迁移时 pnpm 装依赖比 npm 快”，又该放哪？

解析

第一句是稳定约束，写规则文件：它必须每次生效、改动要 review，错了会造成构建不一致。第二句是一次性观察，放会话日志或记忆都可以，但不该写成硬规范；如果放记忆，要带日期与来源，允许以后被“CI 缓存让 npm 更快”覆盖。判断标准：错了会不会造成不可接受后果；会，就规则；不会，就记忆；只对这一次有效，就留会话。见取舍一。

Q2

Grok Build 在压缩前 /flush、压缩后再检索一次。如果只做“压缩后检索”，会丢掉什么？如果只做“压缩前 flush”，又会缺什么？

解析

只做压缩后检索：本次会话里刚产生、还没写进记忆的事实，已经被摘要吃掉了，检索只能取到旧记忆，新经验没落盘。只做压缩前 flush：事实写进去了，但压缩后模型眼前的上下文里没有它，要等下一次会话才会被检索到；这一轮继续干活时仍然“忘了”。所以两者是对称的：flush 负责“别丢”，重检索负责“现在就用”。见03 节 Grok 段与取舍三。

Q3

团队发现一条错误记忆“测试框架是 Jest”已经污染了三周。请给出四步处理：发现、止损、纠错、防复发。

解析

发现：看引用统计或注入日志，确认这条记忆被哪些会话取过、是否被模型引用；止损：先禁用/删除这条记忆，或在项目规则里写明“以 package.json 为准”，阻止它继续被注入；纠错：写入一条带日期与来源的新记忆（“2026-09 起迁移到 Vitest，依据 package.json 与 CI 配置”），让合并阶段覆盖旧条目；防复发：给记忆加来源与时间、检索时按时间降权、与仓库冲突时以仓库为准、保留人工删除入口。四步里至少要有一个环节能“说不”。见取舍六与图 12-1。

Grok Build

记忆是实验性、默认关闭（[memory] enabled 与 [memory_v2] enabled 都默认 false）。两个作用域：global（跨项目）与 workspace（按仓库，clone/worktree 共享）。v2 用 Markdown：topics/（整理后的主题）与 observations/_inbox/（每轮之后落的新事实），再加一份有界的生成式 MEMORY.md 索引，索引每会话注入一次，让模型自己决定打开哪些 topic。/flush 是“现在就总结进记忆”：触发一次 LLM 摘要，写入带日期的会话日志；写入上限 8,000 字符；还会在压缩前自动跑一次（阈值 = 压缩阈值 − 4,000 token 余量，每个压缩周期最多一次），空闲 300 s 也可后台 flush；去重默认余弦相似度 0.92。/dream 把散落的 observation 折叠成 topic，有租约锁（3,600 s）、自动门控（间隔 ≥24 h 且累计 ≥5 个会话）、批量上限 256 KB、单条 note 16 KB、每批最多 20 条。压缩完成后还会再检索一次记忆，把可能被摘要丢弃的相关事实补回上下文。

关键参数与默认值

设计意图
把记忆写进“压缩的时间线”而不是会话末尾：先 flush 再压缩，压缩后再检索，保证“即将被丢掉的事实”和“已经学过的经验”都不丢。防污染靠来源加权、陈旧提示、/remember review 面板、以及生成的 MEMORY.md 不可手改。代价是 flush 在最紧张的时刻再发一次模型请求，且默认关闭意味着大多数用户享受不到。推断
