规则文件的发现与合并

你写了规则，Agent 也读了，但最后生效的可能不是你以为的那一条。规则文件从哪个目录开始找、往上找到哪里为止、几份文件怎么拼、超长时先砍谁——四步里任何一步不同，模型看到的就是另一段文字。

  • 第 2 类
  • 约 20 分钟
  • 1 张对比图
  • L2 → L3

读完你能做到

  1. 给定一棵目录树和一份 32 KiB 预算，算出最终进入上下文的是哪几段、哪一段被砍掉。
  2. 解释为什么所有 agent 都选择“拼接”而不是“覆盖”，以及这样做的代价。
  3. 说出 include 深度上限与循环风险的关系，并指出两家在文档与源码上的口径差异。

01 · 一条没有生效的规则

“我明明写在 AGENTS.md 里了”

下午两点，团队把“所有新接口必须带 request_id”写进了仓库根目录的 AGENTS.md。三天后，Agent 生成的新接口还是没有这个字段。你打开文件确认了一遍，内容在。你在仓库根目录启动 Agent，它也能复述这条规则。

问题出在另一台机器上：那位同事是在 services/payments/ 子目录里启动的。他的项目里另有一份 services/AGENTS.md，里面写着“本目录遵循旧版接口规范”。两份文件都进了上下文，但后一份更长、更具体、位置更靠后，模型照着它做了。根目录那条没有消失，只是被淹没了。

规则文件的难点不是“写什么”，而是“哪几份会同时到场、按什么顺序说话”。

这一章把“发现与合并”拆成四个决定：

  1. 从哪开始找：cwd、项目根，还是用户主目录。
  2. 找到哪里为止：项目根标记是什么，能不能越过它。
  3. 几份怎么拼：拼接、覆盖、去重、还是分桶。
  4. 太长怎么办：先砍宽的还是先砍窄的，砍到多少。

四个决定组合起来，就有了八个 agent 八种行为。下一节先看 Codex，因为它的四步写得最直白，也最容易复现。

02 · Codex 主线

从根往下一级一级拼，拼到 32 KiB 为止

2.1 先定项目根，再决定往哪走

Codex 从当前工作目录向上找项目根，默认以 .git 为标记。找到之后，它把“根 → 当前目录”沿途每一级的 AGENTS.md 按从浅到深的顺序拼接；不遍历子树，也不越过项目根。agents_md.rs#L1-L18 已核实

这里有两个可配置项。第一个是 project_root_markers，未设置时默认 [".git"]；把它设成空列表，等于禁用向上遍历，只在 cwd 找。第二个是 project_doc_fallback_filenames，默认空，可以追加候选名；带路径分隔符的候选会被忽略，避免有人用 ../secret.md 把规则指到仓库外。agents_md.rs#L225-L285 已核实

项目根标记本身也是从配置层合并来的，但合并时显式跳过 Project 层。原因很实际：如果项目里的配置能改“根标记”，一个不可信仓库就可以把根目录往上挪两层，让 Agent 去读你主目录里的规则文件。跳过 Project 层，等于把“根在哪”这个权力留在受管层、用户层和系统层。agents_md.rs#L190-L220 已核实

2.2 每级目录只取一份，但有优先顺序

到了某一级目录，Codex 不是把所有候选都读进来，而是按顺序找第一个存在的：AGENTS.local.md → AGENTS.md → 自定义候选。这个顺序把“本地覆盖”放在了最前面：同一目录下，AGENTS.local.md 通常被 .gitignore 忽略，适合放个人偏好；它一旦存在，同目录的 AGENTS.md 就不再参与。agents_md.rs#L225-L285 已核实

注意这是“每级取一份”，不是“全局取一份”。团队规则、模块规则、子目录规则仍然会同时到场，只是同一级不会出现两份互相打架的文件。这是拼接与覆盖的折中：层级之间拼接，层级内部择一。

2.3 32 KiB 是硬的，砍的是尾巴

合并后的总字节数受 project_doc_max_bytes 约束，默认 32 KiB（源码注释直接写了 // 32 KiB）。超出的部分从尾部截掉，而且是按“剩余字节”逐份分配的：先装根目录，剩余额度给下一级，装不下就在这一份的中间截断，后面的目录一份都进不来。agents_md.rs#L60-L160 已核实

这个顺序有一个反直觉的后果：越具体、越贴近当前目录的规则，越容易被砍掉。假设根目录的 AGENTS.md 有 20 KB，中间层 20 KB，cwd 10 KB，预算 32 KiB，那么根目录全留，中间层只剩约 12 KB，cwd 的 10 KB 一点都不剩。模型看到的是“团队通则 + 半份模块规则”，完全看不到当下这个目录的特殊约定。

Codex 没有为这个后果做特殊处理。它的假设是：根目录的规则最重要，应该优先保证；子目录规则是补充，丢了不至于出错。代价是当根目录文件膨胀时（很多团队会把它写成一本手册），子目录规则会静默失效，而且没有任何告警。

当心

“规则写了没生效”最常见的原因不是模型忽略，而是它根本没进上下文。把 project_doc_max_bytes 调大只能缓解，不能根治；更稳的做法是让根目录文件保持短，把模块细节放到子目录，并定期检查总字节数。

2.4 拼好之后，还要决定“这次发不发”

规则不是一次性塞进历史。Codex 把它作为 WorldState 的一个 section，逐轮计算快照并与上次比较：没变不发，变了发“替换通知 + 新全文”，删了发“不再适用”通知。world_state/agents_md.rs#L36-L80 已核实

这个设计把“规则内容”与“规则传输”分开了：内容是拼出来的文本，传输是按 section 的差分。好处是改了子目录规则，只需要发那一段；坏处是模型看到的规则是“一条条补丁”而不是一份完整文档，出现冲突时它未必能重建全貌。第 11 章会展开差分的细节。

2.5 Codex 没有文件内 include

Codex 的规则文件就是纯文本，现有材料里没有描述任何“在文件里引用另一个文件”的语法。想让多个文件生效，只能靠目录层级，不能靠 @import。这个选择让发现逻辑保持在“路径 + 字节”层面，代价是无法把一份共享规范放在仓库外再引用进来——你只能复制，或者用符号链接（而符号链接的行为不在本章的核实范围内）。

这一点很重要，因为下一节要讲的 include 深度、循环、递归展开，在 Codex 这里统统不存在。它的复杂度全部押在“层级 + 预算”上。

03 · 合并的四个机制

拼接、包含、上限、截断

八个 agent 的做法看起来五花八门，其实都在回答四个问题。先把这四个机制讲清楚，后面的图和表就只是“各家选了哪一档”。

3.1 拼接不是覆盖：所有约束同时在场

没有一家真正做“后一份覆盖前一份”。它们做的都是拼接：把每份文件渲染成一段，按某个顺序连起来。Claude Code 会给每份文件加一行 Contents of <path> (说明)，最后拼成一段统一文本，并在开头加一句“这些指令覆盖默认行为”；opencode v1 用 Instructions from: <path>；pi 给每份包一层 <project_instructions path="…">。claudemd.ts#L1153-L1195 源码 v2.1.88

为什么不覆盖？因为覆盖需要一个“键”。规则是自然语言，没有字段名，你无法判断“这两句话说的是同一件事”。强行覆盖只能按文件粒度做，结果是子目录的一句话会把根目录的十条规范整份作废，这显然更糟。

拼接的代价是冲突显性化：两份规则说反话时，模型必须自己裁决。常见的裁决依据是“更靠后、更具体、语气更强”。所以顺序本身就是优先级：越晚出现的，越容易被当成更具体的要求。Claude Code 的顺序是受管 → 用户 → 项目根 → cwd，pi 的顺序是远 → 近，Grok Build 也是 home → 项目根 → cwd，都遵循“越近越后”。

3.2 include：展开、深度与循环

Claude Code 支持在规则文件里用 @path 引用另一个文件，递归展开，深度上限 MAX_INCLUDE_DEPTH = 5；只允许文本类扩展名，避免把二进制读进上下文。claudemd.ts#L537 源码 v2.1.88

这里有一处必须并列写的差异：源码是 5 层，官方文档写的是“递归最多 4 跳”。两个数字不是笔误，而是版本口径不同——文档描述的是某个已发布版本的行为，源码是 v2.1.88 的实现。本教程采用源码的 5，同时标注【可能已变化】，因为新版本完全可能改回 4 或改成别的值。官方文档 源码 v2.1.88 【可能已变化】

深度上限同时承担了两个职责：限制体积，以及兜住循环。A 引用 B、B 又引用 A 时，如果没有独立的 visited 集合，递归会一直走到深度上限才停。本快照里能确认的只有深度判断，没有看到单独的循环检测逻辑1。这意味着一个三层循环会被展开三次，产生重复内容，而不是被识别成环。

其他 agent 的 include 形态不同：pi 把文件路径写进提示词，模型用 read 自己去读；omp 用 rule:// 内部 URL，按需读取正文；opencode v2 的就近发现是在 read 工具被调用时，把沿途的 AGENTS.md 作为 synthetic 消息注入。它们把“展开”换成了“按需取”，代价是模型必须主动去读。

3.3 体积上限：硬上限、软告警、没有上限

八家里只有两家给出明确的硬上限：Codex 32 KiB，DeepSeek Harness 64 KiB（整条基线消息）加单文件 1 MiB。Claude Code 有一个 MAX_MEMORY_CHARACTER_COUNT = 40_000，但它只用于告警和状态栏提示，不是硬截断——超过 4 万字符，规则仍然全部进上下文，只是你会看到一个警告。doctorContextWarnings.ts#L44-L66 源码 v2.1.88

其余几家在源码里没有找到截断逻辑：pi、omp、opencode v1/v23、Grok Build。Grok Build 甚至在用户手册里明确写“no character cap and no truncation”，把体积成本完全交给用户。12-project-rules.md#L183-L186 已核实

“没有上限”不等于安全。规则文件进的是一段固定预算的窗口，规则占得多，对话就剩得少；而且它通常在历史最前面，一旦超过某个点，压缩会优先把它当成“旧历史”处理。没有硬截断，只是把问题推迟到压缩阶段。

3.4 截断顺序：牺牲宽的还是牺牲窄的

Codex 从尾部截，等于牺牲窄的（更具体的）。DeepSeek Harness 反过来：超预算时先整份省略更宽的（更靠上的）文件，再截断最具体的那个文件。agent-instructions/README.md#L12 推断

两种顺序对应两种价值观。Codex 假设“通则比例外重要”，宁可让子目录规则消失，也要保证团队底线在场。dsh 假设“越具体越相关”，宁可丢掉根目录的手册，也要保住当下目录的约定。没有哪种一定对：在规范统一的团队里，前者更安全；在 monorepo 里各模块差异很大时，后者更实用。

真正危险的是“没有告警的截断”。两家都没有在截断时主动告诉模型“这里少了一段”，模型会以为自己看到了全部规则。如果你的规则文件经常接近上限，正确做法不是调大预算，而是拆文件、删重复、把细节移到按需加载（第 10 章）。

04 · 八个编码智能体查找路径

从全局到子目录，谁扫了哪几层

下面这张图把八个 agent 的查找范围横向排开，看它们分别扫了哪几层、哪一层是启动时全量加载、哪一层要等到“读到这个目录”才补进来。实心点＝启动时参与合并；空心虚线点＝触达时才加载；没有点＝不参与。

图里最值得记住的不是“谁扫得多”，而是扫描范围与合并顺序是两件事。扫描范围决定“哪些文件有机会进来”，合并顺序决定“进来之后谁最后说话”。pi 用 unshift 收集祖先链，所以离 cwd 越近的越靠后；omp 按 depth 排序，远的先、近的后；Grok Build 也是 home 先、项目根后、cwd 最后。三家扫描范围不同，但“近者后置”的结论一致。

Codex 是例外：它从根往 cwd 拼，顺序上也是“近者后置”，但它只有项目层，没有全局层。这意味着你在 ~/.codex/ 里写的偏好不会自动生效，必须放进仓库。代价是跨项目的个人习惯无处安放；好处是同一份仓库在任何机器上看到的规则完全一致，便于复现。

07 · 设计取舍

为什么没有人做真正的覆盖

取舍一：每级择一，还是同级全收

择一派（Codex、pi、opencode v1）在每一级只取一个文件，理由是“同一目录里两份规则必然打架，不如让用户自己决定留哪份”。全收派（Grok Build）把同目录命中的 AGENTS.md、Claude.md、CLAUDE.md、AGENT.md 全部读进来，理由是“多生态兼容，别人家的规则也应该生效”。

代价很清楚：择一派在换 agent 时会丢规则——你把 CLAUDE.md 改名为 AGENTS.md 却没删旧的，新的可能永远不生效。全收派则会把同一套规则的两份副本都读进来，体积翻倍，还可能因为措辞差异让模型无所适从。

取舍二：拼接，还是去重后拼接

opencode v1 是最纯粹的拼接：按插入顺序连起来，不去重、不折叠。omp 和 dsh 多做了一步：如果一份文件的规范化内容完全被另一份更近、更权威的文件包含，就丢掉前者。opencode v2 则在“读取时就近发现”这一层用 synthetic 消息的 metadata.instruction.paths 做台账，防止同一条规则重复注入。

去重的收益是体积，代价是判断本身可能出错。omp 的规则是“完全包含才丢”，改写、交错都不算包含，所以措辞稍变就失去去重效果；而“完全包含”也可能误伤——一份文件被另一份包含，但它的位置本来更靠前，删掉之后顺序语义变了。

取舍三：截断时牺牲宽，还是牺牲窄

Codex 牺牲窄的：预算从根开始分，分到后面没了就没了。dsh 牺牲宽的：先整份省略靠上的文件，再截最具体的。前者假设“通则必须保住”，后者假设“当下目录最相关”。

代价：Codex 在 monorepo 里容易让子模块规则静默失效；dsh 在规范集中的团队里可能丢掉最关键的安全条款。两种都可能出问题，区别是“丢掉的那部分你知不知道”。dsh 至少在文件消失时产生一条移除通知，Codex 是纯截断，没有任何提示。

取舍四：文件内 include，还是按需读取

Claude Code 选择在加载时递归展开 @path，深度 5 层。好处是模型一次就能看到全部内容，不需要额外工具调用；坏处是体积不可控，循环只能靠深度兜住。pi、omp 选择把路径留在提示词里，让模型用 read 或 rule:// 去取：体积可控，但多一次往返，而且模型可能不去取。

这条取舍和第 10 章的“渐进披露”是同一条线：你到底相信“一次给全”，还是相信“模型会按需来拿”。规则文件通常很短，所以展开派居多；但一旦允许 include，长度就不再由文件数决定，而是由引用图决定。

取舍五：启动快照，还是运行时热更新

Codex 每轮算 WorldState 快照、只发差异；opencode v2 用文件 watcher，100 ms 防抖后重扫并发出指令 diff；opencode v1 每步从磁盘重读、整段重拼；dsh 不在启动后持续监听，只有 read/write/edit 触达更深目录时才补进来。

热更新让“改完规则立刻生效”，代价是每次改动都可能打断缓存，而且“什么时候算改完”需要防抖。快照派按轮比较，天然有边界，但用户在会话中途改规则时，要等到下一轮才生效。dsh 的折中最小：只在真正触达时加载，既不做全局监听，也不保证立刻生效。

08 · 小测验

三道题，检验你是否真的会算

Q1

Codex，project_doc_max_bytes 默认 32 KiB。根目录 AGENTS.md 20,000 字节，services/AGENTS.md 20,000 字节，services/payments/AGENTS.md 10,000 字节，你在 services/payments/ 启动。三段各有多少进入上下文？

解析

根目录 20,000 全留，剩 12,768 字节；services 那份被截到 12,768 字节；payments 那份一字不进。总计不超过 32,768。这就是2.3 预算说的“牺牲窄的”：越贴近当前目录的规则越容易被砍掉，而且没有任何告警。实际使用中应把根目录文件压短，或调大 project_doc_max_bytes 并定期核对总量。

Q2

Claude Code 里 A 引用 B，B 引用 A，各写了一次。最终会发生什么？源码和官方文档在深度上分别怎么说？

解析

没有独立循环检测时，递归会一直走到深度上限才停，于是 A、B 的内容会重复若干次，而不是报“发现循环”。深度口径：源码 MAX_INCLUDE_DEPTH = 5，官方文档写“最多 4 跳”，两者不一致，本教程以源码为准并标【可能已变化】。见3.2 include。

Q3

一个 monorepo 有 40 个服务，每个服务目录都有自己的规则，根目录的 AGENTS.md 已经很厚。你会选 Codex 式的“截尾”，还是 dsh 式的“先省宽再截窄”？为什么？

解析

选 dsh 式。40 个服务的差异大于共性，根目录那份厚文件里大部分内容对当前服务无关；先省宽能保证“当下目录的约定”完整到场。代价是可能丢掉根目录里的安全条款，所以要把安全条款单独拆成一份短文件，放在每个服务都会读到的位置。若团队规范高度统一、子目录规则只是补充，Codex 式更安全。见3.4 截断顺序与取舍三。

脚注

  1. 【待核实】：claudemd.ts 里能确认 MAX_INCLUDE_DEPTH = 5 与递归展开，但通读该文件的 include 分支后没有找到独立的 visited 集合或环检测。缺的是“递归入口是否在别处做过路径去重”的证据。因此正文只写“深度上限是已知护栏”，不断言“存在环检测”。 ↩
