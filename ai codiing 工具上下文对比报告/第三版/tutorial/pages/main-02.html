第 9 章·第二部分 · 主线

规则文件的发现与合并

同一份仓库，换个启动目录，agent 读到的规则就会不同。它从哪里开始找、找到哪里为止、怎样合并文件、超长时保留哪部分，这四个决定共同影响模型最后看到的内容。

  • 第 2 类
  • 约 20 分钟
  • 1 张对比图
  • L2 → L3

读完你能做到

  1. 给定一棵目录树和一份 32 KiB 预算，算出最终进入上下文的是哪几段、哪一段被砍掉。
  2. 区分同目录只选一份、跨目录拼接和重复内容去重，并说明规则冲突怎样产生。
  3. 解释文件引用的深度限制与路径去重，并区分规则更新的几种时机。

01 · 一条没有生效的规则

根目录和模块规则互相冲突时会怎样

下午两点，团队把“所有新接口必须带 request_id”写进了仓库根目录的 AGENTS.md。三天后，同事在 services/payments/ 启动 agent，生成的新接口却没有这个字段。你从根目录启动时，agent 生成的接口又带着它。

排查后发现，services/AGENTS.md 还写着“本目录沿用旧版接口规范，不加 request_id”。这次同事的会话同时加载了两份文件，模型采用了模块规则。根目录的要求仍在上下文里，两份文件却给出了相反的指令。

排查规则为什么没生效，先查哪些文件被加载、按什么顺序拼接，再检查内容是否冲突。

这一章把“发现与合并”拆成四个决定：

  1. 从哪开始找：当前工作目录（cwd）、项目根，还是用户主目录。
  2. 找到哪里为止：项目根标记是什么，能不能越过它。
  3. 几份怎么拼：同级选一份、全部拼接，还是先去重、分类。
  4. 太长怎么办：先省略上层的通用规则，还是截掉下层的具体规则。

四个决定组合起来，就有了八个 agent 八种行为。下一节先看 Codex，因为它的四步写得最直白，也最容易复现。

02 · Codex 主线

Codex 怎样发现规则并分配 32 KiB 项目预算

2.1 先定项目根，再决定往哪走

Codex 从当前工作目录向上找项目根，默认以 .git 为标记。找到之后，它把“根 → 当前目录”沿途每一级的 AGENTS.md 按从浅到深的顺序拼接；不遍历子树，也不越过项目根。agents_md.rs#L1-L18 已核实

这里讲的是项目文件的发现路径。Codex 还有全局指令层：默认从 ~/.codex/AGENTS.override.md 或 ~/.codex/AGENTS.md 读取个人规则，再合并项目规则。固定提交的 LoadedAgentsMd 也明确接收宿主提供的用户指令。官方 AGENTS.md 指南 · agents_md.rs#L298-L346 已核实

两个配置项可以改变项目发现方式。project_root_markers 未设置时默认 [".git"]；设成空列表就只检查 cwd，找不到根标记时也只检查 cwd。project_doc_fallback_filenames 默认空，用来追加候选文件名；含路径分隔符的候选会被忽略。agents_md.rs#L225-L285 已核实

合并根标记配置时，代码跳过 Project 层，项目自己的配置不能改变这个搜索边界。这样可以防止仓库把查找范围扩展到上层目录。agents_md.rs#L190-L220 推断

2.2 每级目录只取一份，但有优先顺序

到了某一级目录，Codex 按顺序选择第一个存在的普通文件：AGENTS.override.md → AGENTS.md → 自定义候选。同目录有 override 文件时，AGENTS.md 不参与；空的 override 文件也已占用这个候选位置，后续读取时才跳过空内容。agents_md.rs#L225-L285 · 候选文件名常量 已核实

注意，这是“每级取一份”，不是整条链只取一份。根目录、模块目录、当前目录的规则仍会一起加载。同目录择一，跨目录拼接，是两个不同步骤。

2.3 预算先给根目录，用完就停止读取

project_doc_max_bytes 默认 32 KiB，即 32,768 字节。预算按项目文件读取的原始字节分配：先读根目录，剩余额度给下一级，当前文件装不下就截断，额度用尽就不再读后面的文件。宿主提供的用户指令、拼接分隔符和消息包装不计入这份项目文件预算。agents_md.rs#L60-L160 已核实

所以，越贴近当前目录的规则，越容易因预算用尽而缺失。根目录 20,000 字节、中间层 20,000 字节、当前目录 10,000 字节时，根目录全留，中间层只读 12,768 字节，当前目录那份不读。这里算的是文件读取量，拼接后的消息还会多出分隔文字。

这个顺序优先保留上层通用规则，代价是厚重的根目录文件会占掉子目录的额度。当前文件被截断时，代码会记录一条 tracing::warn! 日志；预算用尽后跳过的后续文件没有逐份提示。agents_md.rs#L160-L178 已核实

当心

规则没生效时，先确认文件是否被选中、内容是否读全，再排查指令冲突。根目录文件保持简短，模块细节放到子目录；仍超过预算时，再按实际需要调大 project_doc_max_bytes。

2.4 内容变化时，追加替换说明和完整新规则

第 8 章讲过，WorldState 记录模型当前应看到的状态。合并后的规则是其中一个 section（状态分区）。每次模型请求前，Codex 刷新规则，再把当前内容的快照与上次比较；这里的“快照”就是用于比较的一份状态记录。首次加载时加入规则，内容相同就不新增重复消息，变化时追加“替换通知 + 完整新规则”，规则消失时追加“不再适用”通知。world_state/agents_md.rs#L36-L80 · 每次请求前刷新 已核实

“只追加变化”说的是历史里是否新增消息，已有规则仍随可见历史进入模型上下文。比较单位是整个 agents_md 分区：子目录文件改了一句，也会带上完整的合并结果，不是只发那一句的补丁。好处是旧请求前缀能保留；代价是历史里会同时出现旧规则和替换说明，模型需要按说明采用新版。替换逻辑 推断

刷新状态不等于每次重读磁盘。AgentsMdManager 缓存项目发现结果，环境选择或信任等级变化时才重新发现；用户、线程指令由各自的 provider（指令提供接口）加载。只编辑项目规则文件，不会触发这条缓存的刷新。agents_md_manager.rs#L82-L136 已核实

2.5 Codex 没有文件内 include

Codex 的加载器按纯文本读取规则，没有解析 @path 的文件引用语法。include 指的是“读入规则时，顺着文件里的引用继续读另一份文件”；把 @shared.md 写进 Codex 规则，不会让加载器自动展开它。共享规范可以通过符号链接放入目录链；使用自定义文件名时，还要配置候选名。纯文本读取与符号链接 已核实

因此，Codex 的这条加载路径主要处理目录和字节预算；支持文件引用的 agent 还需要处理递归深度和重复路径。

03 · 合并的四个机制

规则怎样拼接、引用、限长和截断

Codex 按目录选文件，再按预算读取。把这条流程和其他 agent 对照，还会遇到文件内引用、重复内容去重等做法。下面分别说明这些机制，避免把它们都当成“优先级”。

3.1 文件都拼进上下文，冲突还需要模型处理

跨目录合并时，加载器通常保留多份文件的文字，再给每份加上来源标识。Claude Code 用 Contents of <path> (说明)，opencode v1 用 Instructions from: <path>，pi 用 <project_instructions path="…"> 包住内容。Claude Code 还会提示模型，这些规则覆盖默认行为。claudemd.ts#L1153-L1195 源码 v2.1.88

为什么不按字段覆盖？自然语言规则没有统一的字段名，加载器很难自动判断两句话是否规定了同一件事。整份替换又会连带删掉其他仍然适用的规范。因此，拼接便于保留独立约定，代价是矛盾也一起保留。推断

例如，上层要求加 request_id，下层要求不加，拼接后两句都还在。靠后的具体规则可以表达局部例外，拼接顺序却不等于执行保证：加载器没有按规则逐条检查生成结果。团队应直接消除矛盾，或写清例外适用的目录。

3.2 include：展开、深度与循环

Claude Code 支持 @path：加载器读到引用，就继续读被引用文件并展开其中的引用。它只接受文本类扩展名。源码的深度常量是 MAX_INCLUDE_DEPTH = 5。claudemd.ts#L537 源码 v2.1.88

5 层包含原文件，对应最多 4 次引用跳转。入口的 depth 是 0，每引用一次加 1，到 5 时停止读取。因此链条 A→B→C→D→E→F 只加载 A 到 E；官方文档的“最多 4 跳”与此一致。深度判断与递归调用 · 官方文档 两者一致

循环引用另有路径去重：processedPaths 保存已经处理的路径，并传给每次递归调用。A 引用 B、B 再引用 A 时，第二次遇到 A 就跳过，A 和 B 各加载一次。深度限制防止引用链过长；路径去重防止重复处理，二者职责不同1。

按需读取是另一种机制。omp 的 rulebook 在提示词里列出规则简介，模型需要时用 rule:// 读取正文；pi 的已发现项目规则则直接展开进提示词。opencode v2 还有自动追加：模型用 read 读到新目录里的文件时，运行时发现附近规则，再合成一条消息（synthetic）加入上下文。自动追加不要求模型另发一次“读规则”的请求。

3.3 字节上限和超长告警约束的对象不同

这里能确认的两种字节预算，计量对象不同：Codex 默认 32 KiB 限项目文件读取量；DeepSeek Harness 的 64 KiB 限整条渲染后基线消息，另有单文件 1 MiB。Claude Code 的 MAX_MEMORY_CHARACTER_COUNT = 40_000 则是单文件字符数的告警线，超过后提示，不在这里硬截断。doctorContextWarnings.ts#L44-L66 源码 v2.1.88

pi、omp、opencode v1/v2 的加载路径里尚未找到规则正文截断，缺少运行时是否另有限制的证据3。Grok Build 的用户手册则明确写明，无字符上限、不截断。12-project-rules.md#L183-L186 已核实

没有加载上限，规则照样占用上下文窗口。规则越长，留给对话和工具结果的空间就越少。压缩也不能自动解决规则过长：例如 Claude Code 的规则在每次请求前单独拼入，压缩旧历史并不会把这份规则一并缩短。第 8 章已说明它与会话历史的区别。

3.4 超预算时，优先保留上层还是当前目录

Codex 先读上层文件，预算用尽后就不读下层文件。DeepSeek Harness 反过来：超预算时先整份省略更宽的（更靠上的）文件，再截断最具体的那个文件。agent-instructions/README.md#L12 官方文档

可以从这两种行为看出不同的取舍：Codex 优先保留通用规则，dsh 优先保留当前目录的具体约定。在规范统一的团队里，前者便于保留共性要求；同一仓库里各模块差异很大时，后者更贴近当前任务。推断

dsh 超预算时会生成模型可见的 Workspace instruction budget ... 通知，列出省略、截断的文件路径；Codex 在当前文件被截断时记警告日志。这两种提示不能混为一谈。经常接近预算时，先删重复内容、压短通用规则，再决定调大预算或把细节移到按需加载。dsh 预算通知 官方文档

04 · 八个编码智能体查找路径

八个 agent 的初始目录链与按需发现

07 · 设计取舍

怎样选择文件发现、去重和更新策略

取舍一：每级择一，还是同级全收

Codex、pi 在每级目录按候选顺序取一份；opencode v1 则先选文件名类型，再收集这种类型沿祖先链的文件。Grok Build 会加载同目录命中的多个候选。前两类减少多种格式叠加，后一类便于兼容已有规范，这是对用途的推断。推断

择一要求用户了解文件名顺序。例如 pi 的同目录 AGENTS.md 存在时，写在 CLAUDE.md 里的新规则不会被选中。全收则要维护内容一致性：两份兼容文件都写了同一套规范，就会重复占用上下文。

取舍二：拼接，还是去重后拼接

去重先要问“按什么判重”。opencode v1 用 Set 合并解析后的文件路径；omp 判断规范化段落是否被另一份文件包含；dsh 只把同一候选组中 trim 后完全相同的内容合并。opencode v2 的就近发现则把已注入路径记在 metadata.instruction.paths 里，避免再次追加。

路径去重不能消除不同文件里的重复正文；完全相同的内容去重又识别不了改写过的同一条规范。包含去重能减少更多重复，但维护者要确认“删掉这份”没有丢掉来源和作用域。选哪种判重标准，取决于更看重规则原样保留，还是减少重复文字。推断

取舍三：预算先给通用规范，还是模块约定

Codex 从根目录开始分配项目预算；dsh 超预算时先省略上层文件，优先保留最具体的一份。选策略前先确认，当前任务依赖的规则主要放在哪里。

根目录集中放安全条款时，省略上层文件会丢掉必要约束；模块之间约定差异很大时，根目录占满预算又会让具体规则缺失。dsh 的预算通知能指出哪些文件被省略，Codex 的截断日志能帮助排查。提示能暴露问题，规则仍需精简或重新分配。

取舍四：文件内 include，还是按需读取

Claude Code 加载规则时展开 @path，模型首次看到的就是展开后的内容，无需再调用工具。路径去重防重复，四跳限制引用链长度，但文件多、每份都长时，总量仍会很大。omp 的 rulebook 只先给简介，需要正文时再用 rule:// 读取，代价是多一次工具调用，也依赖模型主动选择。

这与第 10 章的“渐进披露”相连：必须遵守的短规则适合预先加载，偶尔用到的长说明适合按需读取。pi 的项目规则已经全文加载，不应因为它也有按需加载的技能，就把项目规则归到只给路径的一类。

取舍五：请求前检查、文件监听，还是读写时发现

Codex 每次模型请求前刷新指令状态，但项目文件使用缓存，并非每次重读。opencode v1 每次组装请求时读规则；v2 用文件监听器（watcher），改动停止 100 ms 后再扫描，这叫防抖，可避免连续保存引起反复扫描。dsh 在成功读写文件或恢复会话时更新；切换 cwd 也会在下次请求前重载规则链。

决定缓存影响的，是更新后文字放在哪里。重写系统提示会改变请求前缀；像 Codex 这样在历史末尾追加新版规则，可以保留此前前缀。文件监听只负责发现变化，模型要到下一次请求才能看到更新。第 11 章会继续讲消息怎样追加。

08 · 小测验

小测验

Q1

Codex，project_doc_max_bytes 默认 32 KiB。根目录 AGENTS.md 20,000 字节，services/AGENTS.md 20,000 字节，services/payments/AGENTS.md 10,000 字节，你在 services/payments/ 启动。三份文件都只有 ASCII 字符，且没有 override 候选。各读取多少字节？

解析

分别读取 20,000、12,768、0 字节，共 32,768 字节。services 被截断时会记警告日志；payments 因额度用尽不再读取。32 KiB 限制的是项目文件读取量，合并后的消息还含分隔符等文字。保持根目录文件简短，才能给模块约定留出额度。见2.3 预算。

Q2

Claude Code 里 A 引用 B，B 引用 A，各写了一次。最终会发生什么？源码和官方文档在深度上分别怎么说？

解析

A、B 各加载一次。处理 A 时先把路径记入 processedPaths，处理 B 时沿用同一集合，所以 B 再引用 A 就会跳过。深度限制是另一项检查：原文件 depth=0，到 depth=5 停止，最多加载 0–4 共五层，正好等于四跳，与官方文档一致。见3.2 include。

Q3

一个 monorepo 有 40 个服务，每个服务目录都有自己的规则，根目录的 AGENTS.md 已经很厚。你会选 Codex 式的“截尾”，还是 dsh 式的“先省宽再截窄”？为什么？

解析

先查根目录和模块规则各写了什么，服务数量本身不足以决定。若各服务差异大，且根目录主要是当前任务无关的说明，dsh 式优先保留具体规则更合适；若根目录集中放必守的安全规范，优先保留上层更稳。两种策略都应先精简文件，并核对安全条款确实进入上下文；最具体的文件过长时，dsh 也会截断。见3.4 截断顺序与取舍三。
