01 · 功能说明

四块是逻辑分类，不是四个 JSON 字段

Codex 的请求体是 Responses API 形状，没有独立的 system 字段。它在代码里用一个 Prompt 结构体承载「这一轮要发给模型的东西」，字段很多，但真正决定上下文内容的只有四类：历史输入 input、工具定义 tools、岗位说明书 base_instructions、结构化输出约束 output_schema。已核实

四块是给人看的分类。到了线上，Codex 会把其中两块折进 input，把第三块整个省略。

这四类由 build_prompt() 一次拼好，再交给 build_responses_request() 序列化。序列化不是逐字段照搬：工具定义在支持 Responses Lite 的模型上会变成一个 AdditionalTools 开发者条目，岗位说明书会变成一个开发者条目（内部 kind 为 model.base_instructions），两者都被插到 input 的最前面；output_schema 则进入顶层的 text 控制参数。已核实

先把 Responses API 和 Chat Completions 的区别说清楚，后面才不会读错。Chat Completions 有 messages 数组，数组里第一条可以是 system；Responses API 的 input 也是数组，但角色只有 user、assistant、developer，指令类内容通常以 developer 条目出现。Codex 没有把「系统提示」放进一个专门的顶层字段，而是顺着这个形状，把它做成 input 里的一条开发者消息。已核实

「增量工具」是这条链路上的一个分支。它不是一个用户可配的开关，而是每轮由 current_window_uses_incremental_tools() 现算：模型必须支持 Responses Lite；如果历史还是空的，就看配置；如果历史已经有工具声明，就返回 true。为 true 时，build_prompt 把 tools 置为空数组、把 base_instructions.text 置为空串，让这次请求不再重复下发这两块。已核实

为什么要先讲清「逻辑四块」和「线上形状」的区别？因为很多关于上下文管理的讨论会把「系统提示词」当成一个固定字段，然后据此推断缓存边界。Codex 不这么发：岗位说明书是一条开发者消息，工具定义在 Lite 模型上也是一条开发者消息。它们的位置、顺序、是否重复，都会直接改变前缀缓存的命中点。推断

还有一个阅读上的提醒：本节说的「折叠」不是压缩，也不是把两段文本合并成一段。它只是把同一份内容从「结构体字段」搬到「消息数组的某个位置」，字节数基本不变，变的是它在请求里的角色和顺序。推断

pub(crate) fn build_prompt(
    input: Vec<ResponseItem>,
    step_context: &StepContext,
    base_instructions: BaseInstructions,
    incremental_tools: bool, // 本轮是否走「声明已在历史里」
) -> Prompt {
    let turn_context = &step_context.turn;
    Prompt {
        input,
        tools: if incremental_tools {
            Arc::default() // 空数组：本次不再下发工具定义
        } else {
            step_context.tool_router.model_visible_specs()
        },
        parallel_tool_calls: true, // 结构体里恒为真，线上还要再与一次
        base_instructions: if incremental_tools {
            BaseInstructions {
                text: String::new(), // 空文本：指令也已写进历史
                provenance: None,
            }
        } else {
            base_instructions
        },
        output_schema: turn_context.final_output_json_schema.clone(),
        output_schema_strict: !crate::guardian::is_basic_session_source(
            &turn_context.session_source,
        ), // guardian/basic 会话不严格校验
        cyber_access_program: turn_context.cyber_access_program,
    }
}

04 · 逐段解读

从结构体到线上请求，三次折叠

第 1 段　四个内容块与三个开关

input 是历史条目数组，类型是 ResponseItem，不是「消息字符串」。这意味着工具调用、推理、压缩摘要、环境片段都可能是数组里的一个元素，顺序就是模型读到的顺序。tools 是工具定义数组，注释写得非常直白：empty when supplied by history——为空不是「没有工具」，而是「工具已经写在历史里了」。已核实

base_instructions 是岗位说明书，类型是带 text 与 provenance 的结构。这解释了一个常见疑问：为什么 Codex 能区分「模型自带的提示」和「用户自定义的提示」？答案在 provenance 上，而不在文本内容里。output_schema 是可选的结构化输出约束，配合 output_schema_strict 决定服务端是否严格校验。已核实

另外三个字段容易被误认为「块」：parallel_tool_calls 是布尔开关，output_schema_strict 是校验开关，cyber_access_program 是安全策略上下文。它们不增加上下文内容的分类，但会改变请求行为的边界。把它们算进「四块」会让后面的对比失真。推断

记住这个区分：块是「装什么」，开关是「怎么解释装进去的东西」。

第 2 段　build_prompt：唯一的分叉点

这个函数只有三十行，却做了三件事。第一，原样接收 input，不在这里做裁剪或规范化——那些在更早的历史层完成。第二，根据 incremental_tools 同时决定 tools 与 base_instructions.text 是否为空。第三，从 turn_context 取本轮的结构化输出约束与安全策略。已核实

parallel_tool_calls: true 看起来是硬编码，但线上并不总是真。序列化时写的是 prompt.parallel_tool_calls && !model_info.use_responses_lite（client.rs#L1083）：Lite 模型强制关闭并行工具调用。这是一个「结构体表达意图，序列化表达约束」的分层，读代码时不能只看一边。已核实

output_schema_strict 对 guardian/basic 会话取反。源码没有解释原因，但从命名推断：guardian 是安全审查会话，输出结构可能由内部约定控制，不需要服务端严格校验；普通会话则默认严格。推断这一处不影响上下文体积，但会影响请求被拒绝的概率。

还有一个容易忽略的点：output_schema 不进入 input。它是「输出契约」，不是「模型读到的历史」，所以无论 Lite 还是非 Lite，它都走顶层的 text 参数。把四块里前三块和第四块分开看，会发现前三块影响「模型看到什么」，第四块影响「模型必须怎么回答」。这也是为什么压缩、截断、增量这些机制只作用于前三块，从来不动 output_schema。推断

为什么增量分支要同时清空「工具」和「岗位说明书」？因为这两块在 Lite 模型上都以开发者条目的形式存在于历史里。只清工具、不清指令，会让模型收到两份指令；只清指令、不清工具，会让工具表在历史与顶层各出现一次。两者必须同进同退。推断

第 3 段　增量开关：为什么不是配置项

current_window_uses_incremental_tools() 的判断顺序值得逐行读。第一步，模型不支持 use_responses_lite 就直接返回 false——这解释了为什么大多数模型仍然每轮收到完整工具表。第二步，历史为空时返回 step_context.incremental_tools_enabled()，也就是「首轮按配置决定」。第三步，历史非空时返回 state.history.has_tool_declarations()，也就是「历史里到底有没有声明过」。已核实

第三步是整段逻辑的核心。它不信任任何内存标志位，而是回到历史里找证据。这样做的好处是恢复、fork、压缩之后都不会出现「标志说已声明、历史里却没有」的错位。代价是每轮要扫一次历史，判断成本随历史长度增长；不过 has_tool_declarations() 的实现只需要找到第一个匹配项，通常是常数级。推断

首轮为什么还要看配置？因为首轮历史为空，没有证据可查。如果配置说「首轮就用增量模式」，那么 build_prompt 会把工具与指令都置空，而历史里还没有声明——这听起来会发出一个没有工具的请求。实际的保护在别处：build_world_state_for_step 在 new_window 时用同一个配置构建 TopLevelToolsState 与 ModelInstructionsState，把声明作为世界状态写入历史。也就是说，「首轮置空」只在同一轮已经把声明写进历史时成立。推断

一句话理解

增量工具不是「少发一次」，而是「把工具表从每轮请求的头部，搬到会话历史的开头」。搬过去之后，每轮只发变化；没变化就一个字节都不发。

第 4 段　线上折叠：谁被塞进了 input

序列化段的第一个分支是 Lite 模型：如果 prompt.tools 非空，就把它转成 ResponseItem::AdditionalTools，带一个由「线程 id + 工具 JSON」算出的稳定 id，角色是 developer，然后 prefix.push()。最后 tools 变量是 None，顶层字段不出现。已核实

第二个动作在 L996-L1005：只要 base_instructions.text 非空，就包成 BaseInstructionsFragment，同样是稳定 id、同样是 developer 角色，然后 prefix.push()。最后 input.splice(0..0, prefix) 把这两条插到历史最前面。注意这个顺序：先工具、后指令，两者都在历史之前。已核实

稳定 id 是缓存友好的关键。id 由内容哈希生成，同样的工具表、同样的指令文本，每轮算出的 id 相同；如果 id 随机，哪怕内容一样，序列化后的字节也不同，前缀缓存会从第一条就失效。这一处没有注释解释，但从 Uuid::new_v5 的用法可以直接读出来。推断

顺序也有讲究。prefix 先 push 工具，再 push 指令，最后 splice(0..0, prefix) 整体插到历史之前。也就是说，模型读到的是「工具声明 → 指令 → 历史」，而不是「指令 → 工具 → 历史」。如果某次重构把这两个 push 的顺序调换，内容没变，但字节顺序变了，前缀缓存会从工具声明那一行开始失效。这类改动在代码评审里几乎看不出来，只能靠提交说明或缓存命中率监控发现。推断

非 Lite 模型走另一条路：工具仍然是顶层 tools 字段，但岗位说明书依旧被折叠成 input 里的开发者条目。这一点最反直觉——很多人以为 base_instructions 会对应请求的 instructions 字段。本提交的 ResponsesApiRequest 里根本没有 instructions（common.rs#L278-L304）。已核实

第 5 段　历史规范化：四块之前的四道检查

normalize_history() 在 build_prompt 之前执行，做四次调用：给每个工具调用补上输出、删除没有对应调用的孤立输出、剥掉模型不支持的图片、剥掉模型不支持的音频。注释把它们概括成三条不变量，第三条同时覆盖图片与音频，函数体是四次独立调用。已核实

为什么这四道检查必须存在？因为 Responses API 对「调用与结果成对」有硬要求。历史里只要出现一个只有 function_call 没有 function_call_output 的条目，整个请求就可能被拒绝；反过来，孤立的输出也会让模型看到一个没有来由的结果。规范化把这两种情况都在客户端修好，避免把错误推到服务端。已核实

它和「四块」的关系是：input 不是原始历史的照搬，而是规范化后的投影。读 build_prompt 时如果只看函数体，会以为 input 就是磁盘上的历史；实际上它是「历史经过四道检查之后的版本」。推断

这个区别在调试时特别重要。模型报「工具调用没有结果」时，你去看磁盘上的 rollout，可能会发现调用与结果都在；但真正发给模型的 input 已经因为「孤立输出」或「配对缺失」被改过。反过来，模型报「图片无法读取」时，rollout 里图片可能完好，input 里却已经被替换成一段占位文本。只看存档、不看规范化后的投影，就会把问题归错地方。推断

第 6 段　省了什么，代价是什么

省下的是每轮重复下发的工具表与岗位说明书。工具表通常包含名称、描述、JSON Schema，MCP 工具多的时候可能有几十条；岗位说明书是整段系统提示。把它们从「每轮请求头部」搬到「历史开头」，后续轮次只需要在历史里保留一次，理论上每次采样都能省下这两块的序列化与传输。推断

代价有三类。第一，声明变成了历史的一部分，任何 agent 变更都必须以「增量声明」的形式追加，不能直接改头部；这就是 TopLevelToolsState 存在的理由。第二，历史被压缩或截断时，必须保证声明条目不被误删，否则模型会收到「没有工具」的请求。第三，恢复旧会话时，声明条目必须能被识别出来，否则会重复声明或漏声明。推断

这三类代价解释了为什么 AdditionalTools 要带稳定 id、为什么要单独的 TopLevelToolsState、为什么 has_tool_declarations() 要回历史里查。增量不是免费的省 token，它把「无状态请求」变成了「有状态会话」，所有恢复路径都要跟着变。推断

如果把账算得更细一点：省下的是每轮工具表与指令的「重复输入 token」，付出的是「历史多了一段声明」和「每次变化要发一条增量」。设工具表与指令合计 T 个 token，会话有 N 轮且工具集不变，全量模式大约付 N×T 的输入，增量模式大约付 1×T；但增量模式下这 T 个 token 仍然在历史里，每一轮请求都会作为上下文被重新读取。所以真实的节省不是 N×T，而是 (N−1)×T 的「传输与序列化」部分，计费上还要看服务端是否把历史前缀算进缓存读。这也是为什么增量工具必须和缓存友好设计一起看：只有前缀稳定，历史里的声明才会以缓存读的价格被复用，而不是每轮按全价重算。推断

✓要点小结

  • 四块是逻辑分类：input、tools、base_instructions、output_schema。
  • incremental_tools 由「模型是否 Lite + 历史是否已有声明」推导，不是用户开关。
  • Lite 模型把工具与指令都折进 input 头部；非 Lite 只折指令，工具仍走顶层字段。
  • base_instructions 在本提交不对应请求的 instructions 字段，而是一条开发者消息。
  • 省 token 的代价是会话变成有状态：压缩、恢复、fork 都必须保护声明条目。

05 · 与其他 agent 的差异

同样是「系统提示」，四家放在四个不同的层

把「系统提示放在哪」拆开看，会发现四家的分歧不在文案，而在承载它的数据结构：Codex 用开发者消息，pi 用具名 section 拼成文本，opencode v1 把四块压成一条 system 字符串，DeepSeek Harness 把系统提示本身当成一条会话事件。

表注：来源为各 agent 固定提交的源码与官方文档（Codex 提交 76ed3b4，pi 提交 b45e0eb，opencode v1 tag v1.19.0，dsh 为同仓文档口径）。

第一个对照是「系统提示」是否是一个真实对象。Codex 与 dsh 都把它变成历史里的一条消息/事件，因此它可以被重放、被替换、被增量更新；pi 与 opencode 则把它拼成字符串，字符串本身不参与历史，只在每次请求时重新生成。前者的好处是恢复与压缩有统一入口，坏处是历史里多了一条需要特殊识别的消息；后者实现简单，但每次改动都要重算整段。

第二个对照是「工具定义」是否与提示词同层。Codex 在 Lite 模型上把工具和指令都放进历史，等于让两者共享同一套增量机制；pi 把工具 section 留在提示词里，可执行实现另存，等于把「模型看到的声明」和「运行时能调用的实现」拆开；opencode 把工具数组单独发送、按名字排序，靠稳定排序保缓存。三种做法对应三种失败模式：Codex 怕历史被截断，pi 怕声明与实现不一致，opencode 怕某一块内容变化导致整条 system 字符串失效。

第三个对照是「首轮是否特殊」。Codex 的首轮必须把完整声明写进历史，后续轮才能省；pi 的首轮也要建立 section 基线；opencode 没有基线概念，每轮都是全量。这个差异决定了「恢复会话」的复杂度：有基线的系统必须把基线一起持久化，否则恢复后无法判断「哪些已经声明过」。Codex 用 world_state_baseline，pi 用 session 里的 sections，dsh 用 surface 事件；opencode 不需要，因为它每轮都重发。

第四个对照是「变更如何表达」。Codex 的增量工具是一条带稳定 id 的 AdditionalTools 条目，变更时追加新的声明，旧声明留在历史里，靠提示语告诉模型「后来的定义覆盖前面的」。pi 的 section patch 走的也是「只追加差异」这条路，但 patch 的语义是「这个 section 的新值」，不保留旧值；dsh 则把系统提示当成 surface 节点，变更时可以选择原地替换节点，或者在缓存历史之后追加一条 update。三种语义对应三种一致性模型：Codex 是「追加即覆盖」，pi 是「补丁即最新」，dsh 是「替换或追加由路由能力决定」。没有哪种绝对更好，关键看你的历史是否只追加、以及恢复时能不能重建基线。

06 · 思考题

三道题，从读赋值到改设计

Q1

build_prompt 里写的是 parallel_tool_calls: true，但 Lite 模型线上收到的是 false。这两处矛盾吗？如果只在 build_prompt 里改成 false，会影响非 Lite 模型吗？

提示（不给答案）

先看序列化那一行：prompt.parallel_tool_calls && !model_info.use_responses_lite。结构体表达的是「意图」，序列化表达的是「约束」。再想：如果只改结构体，非 Lite 模型会收到什么？

最后想一层：为什么不在 build_prompt 里就按模型分支，而要留给序列化？提示：build_prompt 拿不到 model_info 吗？它其实能拿到 step_context.settings.model_info。

Q2

用户在一个 Lite 模型会话里用了十轮，然后切到非 Lite 模型。下一轮 current_window_uses_incremental_tools() 返回什么？请求里会同时出现历史中的 AdditionalTools 和顶层 tools 吗？这样的请求合理吗？

提示（不给答案）

第一行判断是 if !model_info.use_responses_lite { return false; }，它在新模型上直接短路，不会再看历史。所以 build_prompt 会重新填入完整工具表。

历史里的 AdditionalTools 仍然存在，它会不会被当成普通历史条目发给新模型？看 normalize_image_details 的分支：ResponseItem::AdditionalTools { .. } => {}，规范化不会删它。那么新模型会同时看到两份声明。这合理吗？你需要查新模型是否支持 AdditionalTools，以及 build_responses_request 是否会在非 Lite 路径过滤它。

Q3

假设你要给 Codex 加一条「压缩后保留工具声明」的规则。只改 compact.rs 的候选筛选够不够？还需要动哪些地方？代价是什么？

提示（不给答案）

先分清两种「保留」：把声明条目当普通用户消息留下来，和把声明重新写进压缩后的历史。前者会被候选筛选挡掉（它不是 UserMessage），后者需要新的重建逻辑。

再看 has_tool_declarations()：它只认历史里的声明条目。如果压缩把声明弄丢，下一轮 incremental_tools 会返回 false，于是完整工具表被重新下发——这其实是自愈，但会多花一次全量 token。你要的「保留」是为了省这一次，还是为了正确性？

最后想代价：声明条目可能很大，压缩后立刻占用预算；而且它必须和当前工具表一致，否则模型会按旧声明调用已经不存在的工具。
