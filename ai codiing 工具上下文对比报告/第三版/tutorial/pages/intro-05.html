Prompt cache 与成本

同样的材料，同样的模型，账单能差十倍。差别只在你改了哪一块、改在第几位。

  • 约 15 分钟
  • 1 个交互
  • 前置：第 2 章

读完你能做到

  1. 说出缓存命中的唯一条件，以及为什么“意思一样”不算。
  2. 判断一次改动会让缓存从哪一块开始失效。
  3. 用“稳定在前、易变在后”改写自己的提示结构。

01 · 同一个项目，账单差五倍

同事只是把规矩放在了前面

你和同事用同一个模型、同一个仓库，干的是同一类活。月底看账单，他的花费只有你的五分之一。

你翻了聊天记录，发现他每次开新会话，第一句话都是「按 AGENTS.md 的规矩来」，然后贴同一段需求。你也贴了，只是你习惯先贴一段错误日志，再说需求，最后才提规矩。

材料一样多，字数也差不多。差的只是顺序。

场景 · 缓存只认从头开始的那一段

模型读一段材料要花算力。如果两次请求的开头完全一样，这份算力可以复用，不必重算。这个复用叫前缀缓存（prefix caching），也叫 prompt caching。它有个硬条件：从第一个 token 起，逐字节一致。你换了顺序、改了一个词、多了一个空格，从那一处往后都不再算“一样”。

缓存不是记住你说过什么，是记住“这段材料算过一遍”。

前半句区别很重要：它不理解语义，只比对字节。所以“意思一样但写法不同”在它眼里就是两段新材料。

02 · 缓存到底存了什么

存的是中间结果，不是记忆

模型处理输入时，每一层都会为前面的 token 算出一批中间状态。这些状态只依赖“它之前看到的内容”。于是工程上有了一个很自然的优化：把一段稳定前缀算出的状态存起来，下次遇到同样的前缀直接接着往下算。

几个词要分清：

  • 缓存写入（cache write）：第一次见这段前缀，算完顺手存下来。通常比普通输入贵一点。
  • 缓存读取（cache read）：前缀对上了，直接取用。通常只有普通输入价的一小部分。待核实1
  • 缓存命中（cache hit）：这次请求里有多少 token 走了读取。
  • TTL：缓存能活多久。过了时间，得重新写。

所以缓存省钱的前提是“重复”：同一段前缀在短时间内被反复使用。这也是为什么长会话、连续修 bug 这类场景收益最大——系统提示、工具定义、规则文件每轮都一模一样。

反过来，如果你每轮都改规则文件、换工具、在开头加时间戳，那缓存基本等于没有。

03 · 失效点在哪

改动的位置，决定作废的长度

把一次请求想成一排方块，从左到右按拼接顺序排：系统提示、工具定义、规则文件、环境、历史、你这句话。缓存从最左边开始比对，遇到第一处不同就停。

那一处，就是失效点（breakpoint）。它左边的全部命中，它自己要被重写，它右边的全部作废——哪怕右边一个字都没改。

04 · 谁在悄悄破坏前缀

四个常见动作，四个不同的代价

一、把易变内容塞到开头。最典型的是把当前时间、当前分支、当天的 TODO 写进系统提示第一行。这类信息每轮都变，等于每轮把整段前缀作废。所以工具会刻意把它们挪到尾部：Codex 把当前时间做成独立的 <current_time_reminder> 片段，按事件插进 input，而不是改说明书已核实（current_time_reminder.rs#L9-L45）。

二、每轮重排工具。工具定义的顺序变了，字节就变了。Claude Code 的做法是给系统提示切块、在消息层只放一个缓存标记，位置固定在最后一条消息；源码注释解释了为什么不放多个：多标记会让倒数第二个位置也被保护，白白多留一轮源码 v2.1.88（claude.ts#L3063-L3106）。系统提示层则最多切成四块，按“计费头 / CLI 前缀 / 静态 / 动态”分开源码 v2.1.88（api.ts#L296-L360）。

三、把动态列表写回工具描述。这条有实测代价：Claude Code 的注释写明，把 agent 列表放回工具描述，曾带来约 10.2% 的全局 cache_creation；后来改成只发增量 delta源码 v2.1.88（attachments.ts#L1490-L1556）。

四、压缩。压缩会把历史换成一摘要，前缀整体变样，缓存自然失效。这不是 bug，是取舍：用一次失效换回一大块空间。第 6 章会讲什么时候这笔买卖划算。

?动动脑

系统提示第一行写着「当前时间：2026-10-19 09:05」。你在 09:06 发出第二轮请求。缓存命中多少？

提示：比对是从第一个字节开始的。

结论：缓存只认前缀，改哪儿都一样贵——区别只在“作废多长”。改最后一块，前面几乎全命中；改第一块，整条全废。

Q没有傻问题

问：那我是不是应该把整段对话都塞进前缀，让它永远命中？

答：不行。缓存有寿命（TTL），过期要重写；前缀越长，每次改动的代价越大；而且历史一直在尾部增长，本来就在“末尾追加”，天然适合缓存。真正该固定的是前面那几层——系统提示、工具定义、规则文件。

06 · 把易变的挪到后面

三条可以今天就用上的规矩

  • 只追加，不修改。新信息作为新消息加到末尾，不要回头改前面的内容。
  • 先固定，再变化。规则、工具、长期约定放前面；时间、分支、临时状态放后面。
  • 改动要攒。既然改一次就失效一次，就一次改完，别每轮都微调规则文件。

这三条听起来像“整洁习惯”，其实是账单习惯。缓存不奖励写得漂亮，只奖励写得稳定。

有一点要提前说清：缓存是按“字节前缀”算的，所以同一个意思换个说法、调整一下标点，也会失效。这就是为什么工具生成的提示词往往长得很机械——它们优先保证稳定，而不是好读。

Codex 这边只做两件事：发一个 prompt_cache_key（默认取会话 ID），以及解析响应里的 cached_tokens / cache_write_tokens；命中率、TTL、断点位置都由服务端决定已核实（client.rs#L646-L665、responses.rs#L117-L151）。换会话就换了 key，缓存也跟着重新开始——这也是“开新会话”比“继续旧会话”贵的原因之一。

✓要点小结

  • 缓存复用的是“这段前缀算过一遍”的中间结果，不是记忆；它比对字节，不理解语义。
  • 命中要求从第一个 token 起完全一致；失效点之后的内容全部重算。
  • 缓存写通常比普通输入贵，缓存读通常便宜很多；TTL 到期要重写。
  • 破坏前缀的四个常见动作：开头塞易变内容、重排工具、把动态列表写回工具描述、压缩。
  • 工程规矩：只追加不修改、先固定再变化、改动要攒成一次。
