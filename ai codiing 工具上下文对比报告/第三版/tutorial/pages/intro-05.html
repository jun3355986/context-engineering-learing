Prompt cache 与成本

第 3 章说过，每轮都会重发此前的材料；但“重新发送”不等于“全部重新计算”。这一章讲清 prompt cache 如何复用相同前缀，并用一笔手算和一次交互看清它能省什么、不能省什么。

  • 约 14 分钟
  • 1 个交互
  • 前置：第 3 章

读完你能做到

  1. 解释缓存复用的是计算结果，不是模型记住了一段对话。
  2. 找出两次请求的第一处不同，判断哪段前缀仍有机会复用。
  3. 用缓存读与普通输入算一笔简化成本账，并知道缓存写入费要另算。
  4. 说出缓存为什么不能替代第 4 章的上下文清理。

01 · 明明重发了，为什么没全部重算

第二次请求里的 30,000 个缓存 token

你在同一个会话里修 bug。第一轮请求有系统提示、工具定义、规则和你的问题；第二轮只是在末尾追加一句“继续”，前面的材料原样保留。按照第 3 章的说法，第二轮仍要把这些历史一起发给模型。

假设第二轮共有 40,000 个输入 token，响应里的用量统计（usage）却显示：cached_tokens = 30,000。这说明其中 30,000 个 token 没有按普通输入从头计算，而是复用了此前已经算好的内容。剩下的 10,000 个，才需要按未命中部分处理。

场景 · 缓存复用的是“已经算过的前缀”

模型处理输入需要算力。如果后一次请求能找到与前一次相同的开头，服务端就可能复用这段开头对应的中间计算结果。这种机制叫提示词缓存（prompt caching），也常称前缀缓存（prefix caching）。它不是把上一轮答案背下来，更不是让模型拥有了跨请求记忆。

重发的是文本，复用的是计算；这两件事要分开。

上面的数字只是为了讲清账单口径的教学示例，不是某个 agent 的实测结果。真正判断时，要看响应里的 usage，而不是凭“内容看起来差不多”猜命中。

02 · 它到底存了什么

存的是计算的中间状态，不是聊天记忆

以常见的生成式大模型为例，处理输入时会计算一批中间状态，让后面的 token 能利用前面的信息。如果下一次请求的开头相同，这些已算好的状态就有机会继续使用，不必从第一个 token 再算一遍。OpenAI 的文档把它称为 KV 状态；你现阶段不必理解张量细节，只要记住“存的是算到一半的结果”。OpenAI · Prompt caching

围绕这份中间状态，有四个经常一起出现的词。用开头那次请求来对照，它们就不难分清：

  • 缓存写入（cache write）：把一段可复用前缀的中间状态存下来。第一次建立缓存，或缓存更新时可能发生。
  • 缓存命中（cache hit）：后续请求找到了可复用的匹配前缀。它描述“有没有复用成功”这件事。
  • 缓存读取（cache read）：在用量统计里，通常指本次按缓存读取处理的 token 数量。例子里就是 cached_tokens = 30,000；不同 API 的字段名可能不同。
  • 存活时间（time to live，TTL）：缓存条目可以保留多久。超过期限，前缀即使没变，也可能需要重新计算和写入。

缓存读取通常有价格折扣；缓存写入是否收费、读写倍率和 TTL 则随供应商与模型而变，不能把某一家某一档价格当成通用规律。Anthropic · Prompt caching 与 OpenAI · Prompt caching 都把这几类用量分开说明。

相同前缀，也不保证一定命中

前缀一致是必要条件，不是充分条件。缓存可能已过 TTL；模型或相关请求设置可能变了；匹配前缀可能未达到最小缓存长度；请求也可能没有被分配到保存该缓存的服务节点。是否启用缓存也取决于服务端实现。入门阶段先抓住“从开头匹配”，实际排查时再看供应商文档和 usage。

03 · 别和窗口容量混为一谈

命中以后，窗口占用会变小吗

不会。缓存命中只改变“这段输入要不要重算、如何计费”，不会把这段内容从请求里拿掉。那 30,000 个缓存 token 仍然属于本次输入，仍然占上下文窗口，也仍然可能带来第 4 章讲的质量问题。

你要管哪笔账 窗口账 缓存账
关心的问题 材料占多少空间，能不能装下？ 相同前缀有多少可以不用重算？
主要收益 避免超窗，减少无关材料和干扰。 降低重复计算，通常还能降低成本和开始回答前的等待时间。
主要办法 删减、截断、压缩、隔离。 稳定前缀、尾部追加、按服务文档配置缓存。
缓存命中后的影响 占用不变。 复用增加，普通输入计算减少。

04 · 为什么只改一处，后面也不能接着用

先找第一处不同，再看它影响多长

前缀（prefix）就是从请求开头开始的一段连续内容。把两次请求想成两排方块，都从第一块开始比较：前几块相同，就仍有复用机会；遇到第一处不同，比较停下。本章把这个位置叫作失效点。

为什么后面的方块自己没改，也不能直接复用旧状态？因为它们的中间状态是“在前文基础上”算出来的。第 5 块虽然文字没变，但第 4 块已经不同，第 5 块所依赖的前文就变了，旧计算结果不能直接当成同一件事继续用。

这里比较的不是“意思差不多”。改写一句话、调换工具顺序，甚至一个足以改变 token 切分的标点或空格，都可能让匹配提前停下。实际匹配以服务商渲染后的请求与 token 序列为准。

“失效点”不等于 API 的缓存断点

有些 API 还提供 cache breakpoint（缓存断点），用来指定“把前缀缓存到哪里”。它是缓存写入与查找的边界；本节的失效点则是两次请求比较出来的第一处不同。一个回答“存到哪”，另一个回答“从哪开始不能沿用旧结果”，不要混成一个术语。

05 · 哪些改动会让失效点提前

越靠前的改动，影响的后缀越长

理解失效点后，很多“缓存突然不生效”的现象就有同一条解释：改动出现在越靠前的位置，后面不能沿用旧状态的内容就越多。常见的不是某一种神秘配置，而是下面三类改动。

  • 把易变内容放在稳定材料之前。例如系统提示开头写当前时间、分支名或实时 TODO。时间一更新，后面的工具和规则即使没变，也无法接在旧前缀后面。
  • 重排或改写稳定定义。工具顺序、描述、参数结构，以及规则文件的措辞，都属于请求内容。只改顺序不等于内容相同，因为模型收到的序列已经不同。
  • 回头修改历史。编辑一条旧消息、把旧工具结果换成占位符、用摘要替换一段历史，都会从被修改的位置产生失效点。注意，修改点之前的相同前缀仍可能复用，并不是“整条缓存从零开始”。

两个实现例子：都把易变内容移出稳定前缀

  • Codex 把当前时间做成独立的 <current_time_reminder> 片段，按事件追加到输入消息列表（input），而不是不断更新开头的系统说明。已核实 current_time_reminder.rs#L9-L45
  • Claude Code 不再把不断变化的 agent 列表写回工具描述，而是只追加增量（delta）。其源码注释记录，旧做法对应的缓存写入曾约占全局缓存写入量（cache_creation）的 10.2%，用来说明这类前缀改动在工程上的代价。源码 v2.1.88 attachments.ts#L1490-L1556

压缩也属于第三类：它用摘要替换旧历史，所以从替换位置开始的缓存会失效，却换回了后续请求的窗口空间。这不是缓存机制出错，而是“用一次重算，换更短的后续输入”的取舍。

?动动脑

系统提示第一行写着「当前时间：2026-10-19 09:05」。下一次请求只把时间改成 09:06，后面的工具和历史都没动。整段系统提示还能作为相同前缀复用吗？

提示：先找第一处不同，不要只数改了几个字符。

对照答案：不能把整段系统提示都视为相同前缀。失效点在时间值第一次出现不同的位置；只有它之前仍然相同、且符合服务端缓存条件的那一小段才有机会命中。后面的工具和历史则需要基于新前缀重新计算。

06 · 先算账，再动手

先看懂 30,000 个命中 token 值多少钱

沿用开头的教学数字：本次输入 40,000 token，其中 30,000 走缓存读，10,000 走普通输入。为了只练公式，先假设普通输入是 0.020 元/千 token，缓存读是 0.002 元/千 token，并忽略本次缓存写入费与输出费。

  1. 如果完全没有缓存：40 × 0.020 = 0.800 元。这里的 40 表示 40 个“千 token”。
  2. 如果 30,000 命中：30 × 0.002 + 10 × 0.020 = 0.060 + 0.200 = 0.260 元。
  3. 窗口里仍是 40,000 token：变小的只是本次输入费用和重复计算，不是上下文长度。

这也说明“75% 的 token 命中”不等于“账单直接减少 75%”：只有命中部分享受缓存读价格，其余输入仍按各自类别计费。若还有缓存写入费，要把写入部分单独加进去。

再改一块，看失效点怎样改变这笔账

Q没有傻问题

问：既然缓存读取便宜，是不是多塞点材料进前缀也划算？

答：不能这样算。缓存 token 仍占窗口，也会增加无关信息和干扰；它还可能过期或根本不命中。正确顺序仍是先做第 4 章的“少而准”，再让保留下来的稳定前缀尽量复用。缓存是成本与延迟优化，不是整理上下文的替代品。

07 · 把易变的挪到后面

三条规矩，都是在保护相同前缀

到此，前面那些看似零散的建议可以收成三条。它们不是让提示词更“整洁”，而是减少失效点提前出现的次数：

  • 能在末尾追加，就不回头修改。新信息作为新消息放到尾部，让此前的前缀尽量保持原样；如果必须改旧历史，就接受从修改点开始重算。
  • 稳定内容在前，易变内容在后。长期规则、工具和示例尽量固定；时间、分支、临时状态不要插到它们前面。
  • 同一处改动尽量一次完成。不要每轮都微调规则或工具描述。一次次回头改，会不断制造新的失效点，也会增加可能没有后续复用的缓存写入。

最后把两章连起来：第 4 章决定哪些材料值得进入请求，第 5 章决定保留下来的材料怎样少做重复计算。先清理，再缓存；顺序反了，就只是在高效地重复处理一堆噪声。

✓要点小结

  • prompt cache 复用相同前缀的中间计算结果，不是聊天记忆，也不是复用上一条答案。
  • 从请求开头找第一处不同；失效点之后的旧状态不能直接沿用，即使文字没变。
  • 相同前缀只是命中的前提，TTL、模型与设置、缓存长度和服务端路由也会影响结果。
  • 缓存读、缓存写和普通输入是不同用量类别；算成本要看 usage，不能只猜命中率。
  • 缓存 token 仍占窗口。先减少噪声，再用“稳定在前、尾部追加、少改旧内容”保护缓存。
