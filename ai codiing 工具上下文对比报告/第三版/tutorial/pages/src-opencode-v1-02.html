prune：默认关闭的旧结果擦除

v1 有一个不调模型的减量器，叫 prune。它从最新消息往回扫，保护最近 40k 的工具输出，只有能擦掉超过 20 000 token 时才真的动手。它默认是关的，调用点还在主循环退出之后。这一节读它为什么这么保守，以及 v2 为什么把它整个删掉。

  • 2 个代码块 · 2 张图
  • L3 → L4
  • 源码 733b2c6（tag v1.19.0）

读完你能做到

  1. 说出 prune 的三条保护线：轮数、token 数、最小收益，以及它们各自的默认值。
  2. 解释「擦除」为什么只是打一个时间戳，以及序列化时如何变成占位文本。
  3. 说明 skill 结果为什么永不擦除，以及遇到已擦除结果时为什么直接终止扫描。
  4. 把 v1 的 prune 与 v2 的「压缩时文本化 + 丢最旧 exchange」放在一起比较。

读之前

「裁剪」与「压缩」的分界是：前者不调用模型，后者调用。prune 属于前者，但它不是「把旧消息删掉」，而是「给旧工具结果打一个标记，序列化时显示成占位符」。原文一直在 SQLite 里。理解这一点，才能理解它为什么可逆。

01 · 功能说明

三道门槛，一个时间戳

入口是 SessionCompaction.prune({ sessionID })。函数第一行读配置，第二行就是早退：if (!cfg.compaction?.prune) return。已核实也就是说，默认情况下这个函数什么都不做；配置注释把 prune 的默认值写成 false。已核实

它的策略可以概括成一句话：从最新往回数，最近两个 user 轮不动，最近 40k 的工具输出不动，剩下的如果加起来能省 20 000 以上，才一起擦。

三个常量：PRUNE_MINIMUM = 20_000、PRUNE_PROTECT = 40_000、PRUNE_PROTECTED_TOOLS = ["skill"]。已核实前两个是 token 数，第三个是工具名白名单。

擦除动作只有一行：part.state.time.compacted = Date.now()，然后 session.updatePart(part)。已核实序列化时，part.state.time.compacted 为真就把输出替换成 [Old tool result content cleared]。已核实原文没有删除，消息结构也没有改变，只是「读的时候显示成一句话」。

调用点在 runLoop 的末尾：yield* compaction.prune(...).pipe(Effect.ignore, Effect.forkIn(scope))。已核实三个细节：它在循环退出后、返回最后一条 assistant 之前执行；forkIn 让它在后台跑，不阻塞返回；Effect.ignore 吞掉所有错误。也就是说，prune 失败不会影响本轮任务的完成。

TypeScript 
// 默认关闭：没开就直接返回，连消息都不读
const prune = Effect.fn("SessionCompaction.prune")(function* (input: { sessionID: SessionID }) {
  const cfg = yield* config.get()
  if (!cfg.compaction?.prune) return
  yield* Effect.logInfo("pruning")
 
  const msgs = yield* session
    .messages({ sessionID: input.sessionID })
    .pipe(Effect.catchIf(NotFoundError.isInstance, () => Effect.succeed(undefined)))
  if (!msgs) return // 会话不存在：静默退出
 
  let total = 0 // 已扫过的工具输出总量
  let pruned = 0 // 可擦除的总量
  const toPrune: SessionV1.ToolPart[] = []
  let turns = 0 // 从新往旧数到的 user 轮数
 
  loop: for (let msgIndex = msgs.length - 1; msgIndex >= 0; msgIndex--) {
    const msg = msgs[msgIndex]
    if (msg.info.role === "user") turns++
    if (turns < 2) continue // 门槛 1：最近两轮不动
    if (msg.info.role === "assistant" && msg.info.summary) break loop // 到上次压缩就停
    for (let partIndex = msg.parts.length - 1; partIndex >= 0; partIndex--) {
      const part = msg.parts[partIndex]
      if (part.type !== "tool") continue
      if (part.state.status !== "completed") continue // 只处理已完成
      if (PRUNE_PROTECTED_TOOLS.includes(part.tool)) continue
      if (part.state.time.compacted) break loop // 更旧的也擦过了
      const estimate = Token.estimate(part.state.output)
      total += estimate
      if (total <= PRUNE_PROTECT) continue // 门槛 2：前 40k 不动
      pruned += estimate
      toPrune.push(part)
    }
  }
 
  yield* Effect.logInfo("found", { pruned, total })
  if (pruned > PRUNE_MINIMUM) { // 门槛 3：收益够大才动手
    for (const part of toPrune) {
      if (part.state.status === "completed") {
        part.state.time.compacted = Date.now() // 只打时间戳
        yield* session.updatePart(part)
      }
    }
    yield* Effect.logInfo("pruned", { count: toPrune.length })
  }
})

04 · 逐段解读

四次「停」，一次「才动手」

第 1 段　为什么先数轮，再看 token

turns 在遇到 user 消息时自增，小于 2 就 continue。已核实这是「最近两轮绝对安全」的硬保护：即使这两轮里有 200k 的工具输出，也不擦。理由是最近两轮通常就是当前任务的上下文，擦掉它们等于让模型失忆。

注意 continue 跳的是整条消息，不是「只跳过 user 消息」。所以最近两轮里的 assistant、tool 消息全部不处理。

这道保护与 40 000 的 token 保护是叠加的，不是二选一。最近两轮可能只有 2 000 token，那么 40 000 的保护线会继续往旧消息延伸；反过来，如果最近两轮就有 100 000 token，40 000 早就越过了，但轮数保护仍然挡住它们。

第 2 段　遇到上次压缩就停

if (msg.info.role === "assistant" && msg.info.summary) break loop：扫描到「摘要 assistant 消息」时整个循环结束。已核实因为摘要之前的历史已经被压缩替换，不会再进入模型上下文；继续擦它们没有收益。

这个判断也解释了 prune 与压缩的关系：prune 只处理「当前保留段」里的工具输出。它不会去动已经被摘要掉的部分，也不会跨过一次压缩往前扫。

第 3 段　「已擦除即停」而不是「跳过」

if (part.state.time.compacted) break loop。为什么不是 continue？因为扫描是从新往旧的：一旦遇到一条已经擦过的结果，说明更旧的结果在上一轮 prune 里也已经处理过了（上一轮要么全擦，要么全不擦）。再往前扫只会重复统计。已核实

这也意味着一个边界情况：如果用户手动改过某条旧结果的 compacted 标记，扫描会提前终止，更旧的结果这一轮不会被处理。这是「信任历史一致性」的代价。

第 4 段　20 000 的门槛：为什么是「全有或全无」

pruned 累加的是候选的估算 token；只有 > 20 000 才进入写回循环。已核实为什么设这么高的门槛？因为擦除会让前缀缓存失效一次。如果只省 3 000 token 却让整个前缀重算，成本可能反而更高。20 000 是一个「值得为它破坏一次缓存」的量级。

为什么不是「擦到刚好 20 000 就停」？因为代码先把候选收集完，再统一判断。实现简单，代价是有时一次擦掉 60 000，远超门槛。对使用者来说，这是「要么不动，要么动得彻底」。

还有两个细节。第一，Token.estimate(part.state.output) 只算输出文本，不算附件；第二，擦除只改 time.compacted，state.output 原样保留在库里。所以「擦除」是可逆的：把时间戳去掉，原文立刻回来。

与 v2 的对照：为什么 v2 把 prune 删了

v2 的配置规范化把 compaction.prune 标成 unsupported，出现就产生诊断（config/normalize.ts#L333-L334）。已核实v2 把「旧工具输出的治理」挪进了压缩流程：构造摘要请求时，flattenAndDropOldest() 把历史文本化（丢掉 reasoning、媒体、指令更新，切长短工具输出），仍装不下才按 exchange 整块丢最旧的，并插入 [N older exchanges omitted]（session/compaction.ts#L457-L504）。已核实一句话：v1 是「平时静默擦，压缩时再摘要」，v2 是「平时不动，压缩时一次性决定丢谁」。为什么改：压缩本来就要重写前缀，在那里丢内容的边际成本最低；平时擦则要单独承担一次缓存失效，收益不确定。前者省日常 token，后者让磁盘与模型可见历史保持更强的对应关系。

第 5 段　走查：从最新往回数，候选在哪里开始

设最近两个 user 轮之外有六个已完成工具结果，按从新到旧排列，token 如下：

①20 000grep20 00020 000否（≤ 40 000）
②30 000read30 00050 000是（跨线那条整体入选）
③15 000bash15 00065 000是
④30 000read30 00095 000是
⑤40 000bash40 000135 000是
⑥skillskill8 000143 000否（受保护工具）

表注：数字为示意。真实 Token.estimate 是 round(len / 4)；skill 的 8 000 计入 total 但不进候选。

结果是 pruned = 115 000（②+③+④+⑤），大于 20 000，于是这四个 part 全部被打上 time.compacted。①在累计跨线之前，整条留在候选之外——即使它自己有 20 000 token，也不会被擦。已核实这正是「按累计值保护、按整条 part 擦除」的组合效果。

如果同样的序列里②只有 15 000，那么累计到⑤时 total = 20 000 + 15 000 + 15 000 + 30 000 + 40 000，候选是 15+30+40 = 85 000，仍然超过门槛。要让它不触发，得把候选压到 20 000 以下——大约相当于只剩一条小结果。门槛的设计意图就是「小打小闹不值得破坏缓存」。

还有一个反直觉的点：skill 结果虽然不擦，但会推高 total。这意味着一条 8 000 token 的技能正文，会让 40 000 的保护线「更快被用完」，从而让更旧的结果更早进入候选。已核实如果你希望技能输出完全不影响裁剪决策，得把它从 total 里排除；当前实现没有这么做。

最后看开关。默认 compaction.prune 为 false，上面的计算根本不会发生；开启后它也只在一轮结束时异步跑一次。已核实所以它的定位不是「实时救火」，而是「会话跑久了，顺手清一清」。

第 6 段　默认关闭是不是过度保守

把 prune 的收益与代价写成一句话：它用「一次前缀缓存失效」换「后续每轮少读若干 token」。是否划算，取决于这次会话还会持续多久。

假设擦掉 115 000 token，下一次请求的前缀从第一个被擦的位置断开。此后的每一轮，输入都少 115 000；但第一轮要重新写缓存，写缓存的单价比读缓存高。于是存在一个「回本轮数」：会话在回本点之前结束，prune 就是亏的；之后才是赚的。推断1

这解释了默认关闭的合理性：CLI 会话里大量是「问一个问题、拿到答案就退出」的短会话，回本点根本到不了。反过来，常驻的 IDE 会话、跑一整天的大任务，prune 的收益会很明显。默认值服务的是前者，配置项服务的是后者。

20 000 的门槛也是同一个逻辑的粗粒度版本：它不计算回本点，只要求「省得足够多」。15 000 不擦、25 000 就擦，中间没有渐变。这种「阈值 + 全有全无」的设计在工程上很常见：它不最优，但可预测、好解释、不会每轮都抖动。

omp 的 prune 走得更远：它不只算总量，还看「候选结果之后的 suffix 是否还在热缓存前缀里」。在热前缀里就不改，等于把「回本点」的判断交给 provider 的缓存位置。已核实代价是需要 provider 的 lookback 信息，而 v1 要兼容大量 OpenAI 兼容端点，拿不到这个信息，只能退回「靠门槛猜」。

所以「默认关闭」不是保守，而是「缺少判断所需的信息时的安全默认」。v2 干脆删掉它，把决策集中到压缩时刻——那里本来就要重写前缀，擦除的边际成本为零。

第 7 段　prune 与压缩的相互作用

prune 在一轮结束时跑，压缩在阈值触发时跑。两者的顺序决定了一件事：摘要能不能看到被擦的原文。

答案是不能。压缩序列化历史时，遇到 part.state.time.compacted 为真的工具结果，直接输出 [Old tool result content cleared]（L76-L78）。已核实所以如果 prune 先擦、压缩后压，摘要模型看到的是占位符，不是原文。

这不一定坏。prune 擦的是「40 000 token 之外的旧结果」，本来就是要被摘要概括掉的内容；摘要看不到细节，只能写「曾经运行过若干命令」。如果这些细节重要，用户应该在会话还短的时候解决，而不是指望压缩记住。

但如果顺序反过来——先压缩、再 prune——情况不同：压缩时原文还在，摘要能读到；prune 只是在上一次压缩的保留段里再擦一遍。v1 的实际顺序是「压缩按需、prune 在每轮结束」，两者可能交替发生，取决于阈值什么时候到。已核实

这也给了一个使用建议：如果你打算靠摘要保留某个关键输出，不要开 prune，或者在它被擦之前手动压缩。开 prune 等于告诉系统「旧输出的细节可以永久放弃」，而摘要只能概括它看得见的东西。

✓要点小结

  • prune 默认关闭；开启后保护最近 2 轮与最近 40k 的工具输出。
  • 候选总量必须超过 20 000 token 才落地，落地时全擦，不擦一半。
  • 擦除只写 time.compacted，序列化时显示 [Old tool result content cleared]，原文仍在库里。
  • skill 结果永不擦；遇到已擦除结果直接终止扫描。
  • 调用点在循环退出后异步执行，失败被忽略；v2 删掉了这个能力，改在压缩时统一丢最旧 exchange。

05 · 与其他 agent 的差异

五种「擦旧结果」，保护线各不相同

同样是「旧工具输出换占位符」，四家的保护逻辑差异很大：v1 按轮数 + token 双保护，omp 的 prune 只看 token 且有缓存守卫，shake 按区域类型，pi 干脆没有自动裁剪。

三点对照：

一是双保护还是单保护。只有 v1 同时用「轮数」和「token」两条线。多一条线意味着更安全，也意味着更难预测：用户看到「还有 30k 旧输出没擦」，可能只是因为它们落在最近两轮里。

二是缓存守卫。omp 的 prune 在改一条候选之前，会检查它后面的 suffix 是否还在热缓存前缀里；在热前缀里就不改。v1 没有这层守卫，20 000 的门槛是它唯一的「值不值得破坏缓存」判断。

三是可逆性的实现方式。v1 与 omp 的 prune 都保留原文，只是打标记；omp 的 shake 把原文挪到 artifact，会话文件里只剩占位符；pi 的 context_edit 连原文都不动，只追加一条编辑记录。三种做法的「恢复」成本依次升高。

06 · 思考题

三道题，从门槛到默认值

Q1

最近两轮内有 50 000 token 的工具输出；更旧的结果一共 15 000 token。prune 会擦掉多少？如果把 PRUNE_PROTECT 改成 10 000 呢？

提示（不给答案）

先看轮数保护：最近两轮的 50 000 根本不进统计。再看的更旧部分：total 只有 15 000，永远不超过 40 000，所以 pruned 是 0。

改成 10 000 后，更旧的 15 000 里超出 10 000 的部分才会进候选；但候选只有 5 000，仍小于 20 000 的门槛。

Q2

为什么 skill 的结果永不擦除？如果放开这条限制，会有什么具体后果？

提示（不给答案）

技能正文不是「数据」，而是「行为指令」。它告诉模型按什么流程做事。

擦掉之后，模型可能还在按技能流程执行，但看不到具体步骤与约束；更糟的是，它可能把占位符当成「技能内容为空」，从而跳过必要检查。

omp 的保护名单更宽：连 skill:// 读取与 artifact 回读都保护，理由类似。

Q3

prune 默认关闭，但 v2 直接删掉了它。如果你是 v1 的维护者，会选择「改默认值」还是「加缓存守卫」？说出你的判断依据。

提示（不给答案）

先看默认关闭的原因：擦除会让前缀缓存失效，收益不确定。改默认值等于让所有用户承担这个风险。

再看缓存守卫的成本：要判断 suffix 是否在热前缀里，需要 provider 的缓存 lookback 信息；不是所有 provider 都给。

v2 的选择是「把决策集中到压缩时刻」，代价是平时不省 token、压缩请求更大。三条路都有代价，关键是你的用户更常遇到哪一种问题。

  1. 查了 session/compaction.ts 的 prune 实现与 v1/config/config.ts 的默认值，没有找到任何按 token 计价、按缓存单价计算回本点的代码；provider 的缓存读写单价不在仓库内，无法本地复现。因此这里只做定性推断：回本点存在，但给不出具体轮数。结论「默认关闭对短会话更安全」依赖这条推断，不依赖任何数值。 ↩
