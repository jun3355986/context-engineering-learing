用户侧怎么管理上下文：决策流程图

你手上只有四个动作。选错的代价，不是慢一点，是把该留的东西丢了。

  • 约 9 分钟
  • 前置：第 3 章

读完你能做到

  1. 说出清空、压缩、子代理、新会话四种动作各自的代价。
  2. 用三个问题判断该用哪一个，并说出理由。
  3. 判断什么情况下“不要压缩”，改用别的办法。

01 · 上一件事的日志，正在回答这一件事

“这个报错我见过，是数据库连接的问题”

你花了一上午排查登录接口的 500，最后定位到一个探活配置。下午两点，你在同一个会话里换成另一个问题：「首页的推荐位为什么不刷新？」

它回：「这个报错我见过，是数据库连接的问题，先看连接池。」——上一件事的日志还在上下文里，它顺着上午的模式往下走。

场景 · 不是它固执，是上一件事还没下桌

历史不会因为你换了话题就自动退场。上午那份日志、那串报错、那几条“先查连接池”的结论，仍然占着位置，也仍然在影响它怎么理解你的新问题。除了「继续」，你能做的只有四个动作：清空、压缩、派子代理、另开新会话。

管上下文不是“多给点信息”，是决定哪些信息该下桌。

这张决策图是本章的全部产出。后面几节，只是把图上的每个节点拆开讲清楚。

02 · 主图：三个问题，五个出口

先问“还是同一件事吗”

不要一上来就想“要不要压缩”。顺序应该是：先判断任务是否连续，再判断旧结论是否还有用，最后才判断上下文里有没有该清理的噪声。

图上没有“什么时候该继续追问”这种分支，因为那不需要决策——同一件事、上下文干净，继续就是最优解。真正需要判断的，是另外四条岔路。

03 · 四个动作的代价

没有哪一个全是好处

把这四个动作摊开看，你会发现它们都在拿一样东西换另一样东西：用“丢信息”换“省空间”，或者用“多一次调用”换“少一点噪声”。

动作 付出什么 什么时候用 什么时候别用
清空/clear 全部历史、当前任务状态。 任务确实换了，旧结论一个字都不想带。 还要引用上午的结论或文件路径。
压缩/compact 一次模型调用；细节变成摘要；前缀缓存失效。 同一任务、上下文臃肿、还需要连贯地接着做。 任务已经换了，或你只需要结论。
子代理subagent 一次委派；你要写清目标；它看不到主会话。 要翻很多文件、跑很多命令，但只需要结论。 需要来回讨论、需要它记住你的偏好。
新会话new session 重新组装系统提示与规则；缓存从零开始。 任务干净，旧结论只需几行。 还要连续追问细节，重贴成本高于收益。

表注：四个动作在多数 agent 里都存在，但命令名与触发方式不同；这里按能力描述，不绑定某个具体实现。

表里没列“继续”，因为它是默认选项，成本为零。但零成本有前提：任务连续，而且上下文里没有正在误导它的东西。这两个前提只要破一个，继续下去就是在给后面挖坑。

压缩：最容易被滥用的一招

压缩看起来最“温和”：不丢会话，还能腾地方。但它有三个隐形成本。

第一，它要再发一次请求。Claude Code 的压缩请求会复用主对话的系统提示、工具和历史，再追加一段“不要调用工具、先写分析再写摘要”的指令源码 v2.1.88（compact.ts#L387-L460）。历史越长，这次请求越贵。

第二，它会丢细节。摘要留下的是结论和待办，丢掉的是具体的行号、报错原文、你当时否掉的方案。Codex 的摘要模板要求写“进度与决策 / 约束与偏好 / 待办 / 关键数据”已核实（prompt.md#L1-L9），已经是尽量保住关键项，但仍然不是原文。

第三，它会让缓存失效。前缀变了，下一轮要从头算。省下的空间和丢掉的钱，得一起算。

所以正确姿势是：压缩前先说清“保留什么”。Claude Code 的 /compact 支持附加说明，Codex 的 /compact 也可以带一句补充源码 v2.1.88 已核实（Claude Code compact.ts#L40-L110、Codex compact.rs#L25-L60）。“保留探活配置的结论和那个文件路径”，比默认摘要有用得多。

04 · 另外两个动作的细节

清空很便宜，新会话不便宜

清空最彻底：历史没了，缓存也重新开始。但它还会顺带清掉系统提示里那些“算过一次”的动态段。Claude Code 在 /clear 和 /compact 时会调用 clearSystemPromptSections()，把记忆化的段清空源码 v2.1.88（systemPromptSections.ts#L16-L58）。所以清空后的第一轮，通常比你想的贵一点。

新会话比清空更干净：连“当前会话的状态”都不带。代价是你要重新交代背景。判断标准很简单——旧结论能不能压缩成三行？能，就新会话加三行；不能，就压缩。

子代理解决的是另一种问题：不是“历史太多”，而是“探索太脏”。让它去翻十个文件、跑五次测试，它自己的上下文会被塞满，但回到主会话的只有一段结论。Claude Code 的子代理默认从全新上下文开始，只有显式传 forkContextMessages 才继承父对话源码 v2.1.88（runAgent.ts#L248-L330）；Codex 的子会话也有独立的历史和 token 计数已核实（child_config.rs#L55-L160）。

任务已经做完，你只想问一句“刚才那个配置项叫什么来着”。该清空、压缩，还是接着问？

提示：你要的是一条信息，还是一段连续的工作？

05 · 规则文件也要维护

它不占“历史”，但占每一轮的前缀

规则文件容易被当成“写完就不管”的东西。实际上它每轮都在前缀里，而且是最贵的那一段——它一改，后面的缓存全废。

两条维护原则：只写模型猜不到的（目录约定、禁用命令、发布流程），不写代码里已有的（框架、语言、目录结构）。前者是信息，后者是噪音。第 4 章说过，噪音会稀释信号；第 5 章说过，改动会让缓存失效。两条加在一起，结论就是：规则文件要短，而且要少改。

要改的时候，攒成一次改完，别一边干活一边微调。每改一次，下一轮就重算一次前缀。

两家在“多长算太长”上的态度也不一样：Codex 有硬上限，合并后的 AGENTS.md 默认 32 KiB，超出从尾部截断已核实（agents_md.rs#L60-L160）；Claude Code 的 40,000 字符只用来触发“大文件告警”，并不硬截断源码 v2.1.88（doctorContextWarnings.ts#L44-L66）。也就是说，Claude Code 那边“写太长的后果”全靠你自己承担。

06 · 收口

四个动作，一条判断线

把这一章压成一句话：任务换了就清空或另开，任务没换就判断噪声；噪声只要结论就派子代理，还要接着做就压缩。

这也是图 1 想让你记住的东西。图可以忘，这条线别忘。

Q没有傻问题

问：压缩这么麻烦，为什么不让工具一直自动压缩，我什么都不管？

答：自动压缩解决的是“装不下”，不解决“该不该继续”。它按阈值触发，不会判断你是不是已经换了任务；而且压缩会丢细节、会让缓存失效。Claude Code 还给自动压缩加了熔断：连续 3 次失败就不再尝试，避免每轮都打一次注定失败的请求源码 v2.1.88（autoCompact.ts#L241-L351）。自动是兜底，不是策略。

✓要点小结

  • 四个动作：清空、压缩、子代理、新会话；「继续」是默认选项，不是动作。
  • 先判任务是否连续，再判旧结论要不要带走，最后判噪声多不多。
  • 压缩要再发一次请求、会丢细节、会让缓存失效；能只带结论就别压缩。
  • 清空和新会话都会让缓存从头开始；新会话更干净，但要重贴背景。
  • 规则文件短、少改、攒着一次改完——它每轮都在前缀里。
