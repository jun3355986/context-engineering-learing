shake 的机械省略

有一种减量不需要模型：把大块工具输出和长代码块换成一个短占位符，原文塞进 artifact，占位符里留一句「要读回原文，去 artifact://xxx」。oh-my-pi 管这个动作叫 shake。它便宜、可逆、但会永久改写历史——这正是它的价值与风险所在。

  • 约 14 分钟
  • 2 个代码块 · 3 张图
  • L3 → L4
  • 源码 f979f46

读完你能做到

  1. 说出 shake 会命中哪两类区域，以及哪三类工具结果永远被保护。
  2. 解释 accumulatedAfter 数组如何用一次倒序遍历实现「最近 16k 不动」。
  3. 区分「保守 / 激进 / 救援」三档配置，并说出各自的 protectTokens 与 minSavings。
  4. 把 shake 与 pi 的 context_edit、opencode v1 的 prune、omp 自己的 prune 放在一起比较。

读之前

shake 是 pi 没有的能力，属于 omp 新增。它不调用任何模型，纯本地字符串处理，所以很快；也正因为不调模型，它无法判断「这段内容语义上重不重要」，只能按位置、类型、体积来筛。理解这一点，才能理解它为什么要保护最近 16 000 token。

01 · 功能说明

不调模型的三步：找区域、算收益、换占位符

shake 的实现分成两层。纯函数层在 packages/agent/src/compaction/shake.ts，只做区域检测与原地改写，没有 I/O；编排层在 AgentSession.shake()，负责把原文写成 artifact、调用 rewriteEntries() 持久化、失败时回滚、重建运行时消息。已核实文件头注释把这条分层写得很明确：「Artifact offload, persistence, and provider-session teardown are orchestrated by the caller」。

shake 的输入是一整条分支的条目，输出是一组「字符区间」；它不生成新消息，只把已有文本的某些片段替换掉。

能命中的区域只有两类。第一类是工具结果：只取其中的文本块，图片等非文本块原样保留；整条结果会被替换成一行占位符。第二类是大块文本：用户、开发者、助手、自定义消息里的 fenced code block（``` 或 ~~~）与顶层 XML 元素，且单块至少 fenceMinTokens（默认 400）token。已核实

整个流程有一条硬门槛：总收益不够就不动手。计算方式是每个区域的 tokens - 16 求和（16 是占位符本身的粗略成本），低于 minSavings 就返回空数组。已核实这条门槛避免「删了十个 20 token 的结果，净收益为负」。

三档配置对应三种场景：自动维护用 DEFAULT_SHAKE_CONFIG（保护 16 000、最少省 4 000），手动 /shake 用 AGGRESSIVE_SHAKE_CONFIG（保护 4 000、无门槛），压缩死路救援用 RESCUE_SHAKE_CONFIG（保护 0、但把 artifact 回读结果也保护起来）。已核实

04 · 逐段解读

四个判断，一次改写

第 1 段　保护窗口：为什么先算「之后有多少」

朴素写法是「从后往前累加，累加到 16 000 就停，之前的都能删」。但那样需要在循环里同时做两件事：判断保护边界、收集区域。omp 用了一个更干净的办法：先倒序算一遍 accumulatedAfter[i]，表示「严格比 i 新的所有条目的 token 总和」，然后正序遍历时只要 accumulatedAfter[i] < protectTokens 就跳过。已核实

这样做的好处是判断变成 O(1)，且语义明确：一条条目是否受保护，只看它后面有多重。副作用是数组要占 O(n) 内存，但对一条会话分支来说可以忽略。

注意保护的是「最近 16 000 token」，不是「最近 N 条消息」。一个巨大的工具结果可能一条就超过 16 000，它自己会被保护；反过来，二十条小消息加起来不到 16 000，也全部受保护。

第 2 段　边界与例外：三种「不用省」

第一道是 boundaryIndex：keepBoundaryId 是最近一次压缩的 firstKeptEntryId，它之前的条目已经被摘要掉，永远不会再发给模型。改它们只会让持久化文件「看起来更干净」，对请求没有任何影响，所以直接跳过。已核实源码注释还补了一句：边界之后的缓存前缀它照样会动——因为 shake 本来就是一个「压缩类」的减量手段，不可能既省 token 又保缓存。

第二道是 prunedAt：已经省过的结果不再处理，避免占位符被「再省略一次」变成嵌套占位符。

第三道是 isProtectedToolResult()。默认名单是 ["skill", isSkillReadToolResult, isArtifactRecoveryToolResult]：技能正文、通过 skill:// 读到的内容、以及为了回读 artifact 而产生的工具结果。已核实前两个的理由是「技能正文是行为指令，省掉等于改规则」；第三个的理由更微妙：如果连回读 artifact 的结果都被省掉，模型就永远拿不回原文了，恢复链会断。

useless 是唯一的例外：工具自己标记「这条结果没有信息」（例如零命中的搜索），即使它在保护窗口内也可以省。条件是 isError !== true——错误结果不能省，因为错误信息本身可能就是下一步的线索。

第 3 段　块检测：为什么要保守

scanTextForBlockRanges() 逐行扫描，维护一个 inFence 布尔和一个 tagStack。规则有三条：未闭合的 fence 不产生区间；XML 只在 fence 之外识别；XML 必须严格配对（闭合标签名等于栈顶）才产生区间。已核实

保守是有理由的。如果一段代码块没有闭合（模型输出被截断），把它整段换掉可能吞掉后面的正常内容；如果 XML 标签不配对，按「第一个开始标签到最后一个结束标签」切会跨过无关段落。宁可漏省，不可错省——漏省只是少回收一点 token，错省会破坏语义。

单块还有 400 token 的下限。低于 400 的块换掉也省不了多少，反而增加一次 artifact 写入与一行占位符，净收益可能是负的。

第 4 段　改写：为什么工具结果只留一个文本块

applyShakeRegion() 对工具结果的处理是：找到第一个非空文本块，把它换成占位符；其余文本块全部丢弃；所有非文本块原样保留。已核实结果是「一条结果 = 一行占位符 + 若干图片」，既表达了「这里被省略过」，又没有丢掉图片。

块区域的替换则是一次字符串拼接：text.slice(0, start) + replacement + text.slice(end)。多个块共享同一个文本块时，必须从后往前替换，否则前一次替换会改变后一次的偏移。applyShakeRegions() 按 start 降序排序就是为这件事。已核实

还有一个记账细节：如果被改写的是 assistant 消息，代码会把「删掉的 token 数」累加到 elidedOutputTokens。已核实为什么？因为 usage.output 是账单，删掉文本并不会让 provider 退钱；下次统计上下文大小时，要把这部分减掉，否则会高估。这是「账单」与「上下文占用」两个口径分离的典型例子。

第 5 段　扫描器的四个边界

scanTextForBlockRanges() 只有五十多行，但它的边界条件决定了「会不会误伤」。逐个看：

未闭合的 fence。如果模型输出被截断，最后一个 ``` 没有闭合，扫描器会一直停在 inFence = true，直到文本结束也不产生区间。已核实这是有意的：没有闭合边界，就无法确定「块到哪里结束」，宁可不省。

fence 内的 XML。XML 检测被 if (!inFence) 包住，所以代码块里的 <div> 不会被当成 XML 块。已核实否则一段 HTML 示例会被切得七零八落。

同名标签嵌套。扫描器维护一个 tagStack，只有闭合标签等于栈顶才弹栈；弹到空才记录区间。已核实这意味着 <a><a></a></a> 能正确配对，而 <a></a></a> 这种多余的闭合不会误判。

区间合并。mergeRanges() 按起点排序，丢弃与已保留区间重叠的项。因为 fence 与 XML 区间总是正确嵌套（XML 检测在 fence 内关闭），重叠只可能是包含关系，保留外层即可。已核实

还有一条不在扫描器里、但同样影响结果的规则：fenceMinTokens = 400。小于 400 token 的块不入选，哪怕它很长。这条阈值对「短代码片段多、单块都不大」的会话很不友好——十块 300 token 的代码合计 3 000，却一块都省不掉。

第 6 段　shake 与 prune 的分工

omp 有两套不调模型的减量机制，容易混：pruneToolOutputs() 与 shake()。它们的目标不同，触发时机也不同。

维度 pruneToolOutputs shake
选择依据token 预算（保护 40k，最少省 20k）区域类型（工具结果文本、大块 fence/XML）
改写对象工具结果整体工具结果或消息内的字符区间
占位符[Output truncated - N tokens] 等[shaken ~N tokens — recover: artifact://…]
缓存守卫有（热前缀 suffix 不改）无
触发压缩前自动方法链中的一档，或手动 /shake

表注：omp f979f46。prune 的阈值见 packages/agent/src/compaction/pruning.ts#L77-L83；shake 的三档配置见 shake.ts#L47-L76。

两条机制的执行顺序是 prune 在前、shake 在后。原因很实际：prune 更温和（保留原文、只换占位符、有缓存守卫），应该先把「明显没用的」清掉；shake 更激进（改写原文、落 artifact），留给「prune 之后仍然超」的情况。如果反过来，shake 可能先把一条本可以被 prune 温和处理的结果整个搬走，得不偿失。

这也解释了为什么 shake 的保护窗口（16 000）比 prune 的（40 000）小得多：它是在「已经裁过一轮」的上下文上再动手，剩下的都是更靠近当前任务的内容，保护线自然要收紧。

第 7 段　怎么观测一次 shake 的效果

shake() 的返回值有四个字段：mode、toolResultsDropped、blocksDropped、tokensFreed，以及可选的 artifactId。已核实它们是评估 shake 是否值得的第一手数据。

tokensFreed 是「原始区域 token − 占位符 token」的累加，不是「请求实际减少了多少」。已核实两者可能差很多：如果被省略的区域本来就不在请求窗口里（例如在压缩边界之前），省下的 token 不会体现在请求上。所以评估时要同时看「被改写的条目数」与「下一次请求的实际 token」。

toolResultsDropped 与 blocksDropped 的比值也有信息量。工具结果占多数，说明瓶颈在命令输出；块占多数，说明瓶颈在模型生成的长代码/长文档。前者应该调工具输出上限（第 6 类），后者才该调 shake 的 fenceMinTokens。

artifactId 是「能不能回读」的关键。有 artifact 时占位符带 artifact:// 指针，模型可以主动读回；没有时只有 [shaken ~N tokens]，原文就真的只能靠会话文件了。评估「信息保留率」时，要区分这两种占位符——它们的可恢复性完全不同。

✓要点小结

  • shake 不调模型：只把工具结果文本与大块 fence/XML 换成占位符。
  • 保护最近 16 000 token（自动档）；useless 结果可越过保护窗口。
  • 技能正文、skill:// 读取、artifact 回读结果永不省略；图片原样保留。
  • 总收益不到 minSavings 就不动手；占位符自带 artifact:// 指针。
  • 它改写原文并落盘，不是改投影；失败靠深拷贝快照回滚。

05 · 与其他 agent 的差异

四种「不调模型的减量」，代价完全不同

shake 处在「裁剪」与「压缩」之间：它像裁剪一样不调模型，又像压缩一样会持久化改写历史。把四家的做法排在一起，能看清这条中间路线的位置。

← 左右滑动查看全部列，首列固定 →

agent 做法 改哪里 能否回读原文 默认开关
oh-my-piomp shake：工具结果 + 大块文本换占位符 条目原文，落盘 能，artifact:// 在方法链中默认启用
pipi context_edit：省略或替换指定条目 投影，追加条目 能，原文仍在文件里 仅溢出恢复等场景使用

表注：omp f979f46；pi b45e0eb；opencode v1 733b2c6。表中把 omp 的 shake 与 prune 分成两行，因为它们是两套独立机制：prune 按 token 预算批量裁，shake 按区域类型机械省略。

三点对照：

一是可逆性。pi 的 context_edit 最安全：原文不动，去掉编辑条目就恢复。v1 的 prune 次之：原文在库里，只是序列化时显示占位符，改回时间戳就能恢复。shake 最激进：原文只存在 artifact 里，会话文件本身已经变了。安全性与节省的彻底程度成反比。

二是触发者的意图。v1 的 prune 是「后台清理」，默认关闭，开了也只在一轮结束后跑；shake 是「压缩方法链的一员」，会在阈值触发时自动跑，也可以手动 /shake。前者是维护，后者是救火。

三是与缓存的关系。三者都会让前缀失效：改历史就是改前缀。omp 的 prune 加了缓存守卫（候选结果后面的 suffix 还在热前缀里就不改），shake 没有——它的定位就是「宁可牺牲一次缓存，也要把上下文降下来」。这也解释了为什么自动档要保护最近 16 000：尽量只动冷区。

Q2

提示（不给答案）

改写逻辑只保留「第一个非空文本块」作为占位符位置，其余文本块丢弃，非文本块全部保留。

第二问看 uselessResult 那个短路条件：!uselessResult && accumulatedAfter[i] < protectTokens 才跳过。所以 useless 为真时会越过保护窗口。

Q3

你要把「数据库 schema 文件」加入 shake 的保护名单。用什么条件判断？只按工具名够吗？加进去之后会有什么副作用？

提示（不给答案）

ProtectedToolMatcher 支持字符串（按工具名）和谓词（可以看配对的工具调用参数）。schema 文件通常是用 read 读的，按工具名会把所有 read 都保护起来。

谓词里能拿到 path，所以可以只保护路径匹配 schema.* 的结果。

副作用：保护名单越宽，可省略的区域越少，minSavings 越难达到，shake 可能直接 no-op，最后还是落到 soft 摘要。
