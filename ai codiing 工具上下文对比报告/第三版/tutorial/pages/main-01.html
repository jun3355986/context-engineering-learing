请求组装：系统提示词与工具定义

模型每次只看到一段平铺的 token 序列。系统提示词、工具定义、环境说明、历史消息，都是这段序列里的片段，谁在前、谁在后、谁每次都变，决定了它能不能命中缓存，也决定了它会不会忽略你的规则。

  • 第 1 类
  • 约 21 分钟
  • 1 张图
  • L2 → L3

读完你能做到

  1. 画出一次请求的四块拼装，并说出每一块在 API 里的真实位置。
  2. 判断某个改动会不会打断 prompt cache，以及打断的是哪一段。
  3. 解释“工具定义增量下发”省下了什么、又付出了什么代价。

01 · 先看清这张账单

同一个问题，两个仓库，两种答案

上午十点，你在两个仓库里问了同一句话：“把这个模块的错误处理统一一下。”

A 仓库的回答先读目录、再读两个文件，改完还跑了一遍测试。B 仓库的回答直接给出一个补丁，路径是错的，API 也是旧版的。你把同一句话再问一遍，B 还是错。你开始怀疑模型变笨了。

把两次请求拆开看，差别不在模型：A 仓库的工具表里有 read、grep、bash，B 仓库只暴露了三个工具，其中没有搜索；A 的规则文件里写着“改完必须跑 make test”，B 的规则文件在两个月前被移到了子目录，没有生效；A 的历史里已经有上一次的目录树，B 是全新会话。模型没有变，装进去的东西变了。

上下文管理的第一件事，不是省钱，而是确认“该在的东西真的在”。

这一章只回答三个问题：一次请求由哪几块拼成；它们按什么顺序排；为什么工具定义值得单独拿出来优化。后面的规则文件、按需加载、动态注入，都是在这张底图上加东西。

这张图有两个容易看错的地方。第一，工具定义不是一个独立段落，它在协议里是与消息数组并列的字段，但在计费和缓存上，它和系统提示一起被算进前缀。第二，环境信息在大多数实现里不是一个字段，而是若干条插在历史里的合成消息。所以“改系统提示”和“改环境说明”，代价可能完全不同：前者动的是前缀头部，后者只动尾部。

02 · Codex 主线

四块拼装，和一个“不发”的开关

Codex 的请求体是 Responses API 形状，没有独立的 system 字段。它的对应物叫 base_instructions，作为 instructions 下发；对话内容放在 input 消息数组里。每个采样步，build_prompt 都会返回一个 Prompt，固定四块。client_common.rs#L22-L40 已核实

2.1 四块各装什么

  • input：历史条目。由 ContextManager 持有的活历史，写入时已经规范化过，不会出现“有工具结果、没有对应调用”的孤立记录。
  • tools：本轮模型可见的工具规格。注意是“本轮可见”，不是“全部注册”。权限、沙箱模式、MCP 暴露策略都会在这里做一次过滤。
  • base_instructions：岗位说明书。身份、做事方式、工具使用通则都在这里，是整个前缀里最稳定的一段。
  • output_schema：结构化输出约束。普通会话 output_schema_strict = true；guardian / basic 会话为 false。

build_prompt 同时还固定写入 parallel_tool_calls = true。这个值不是“建议”，它改变了模型可以一次性发出多少个工具调用，也改变了工具结果的返回形状。很多人以为并行度是模型自己决定的，其实客户端在每次请求里都替它做了选择。turn.rs#L1666-L1695 已核实

为什么强调“本轮可见”。如果把“注册过的工具”直接当成“发出去的工具”，权限系统就形同虚设：一个被禁用的工具仍然占着 schema、仍然能被模型点名。Codex 在组装这一步做过滤，等于把权限判断前移到了请求边界。代价是工具表在会话中途可能变化，而变化又会打断前缀缓存——这正是后面 incremental_tools 想解决的问题。

2.2 环境与权限：不是字段，是片段

Codex 没有“环境信息”这个独立字段。它以 contextual user / developer 片段的形式插进 input：<environment_context> 装 cwd、平台等，<current_time_reminder> 装时间，AGENTS.md 的内容也以片段形式参与。contextual_user_message.rs#L1-L40 已核实

权限与沙箱说明也一样：一部分来自这些片段，一部分写在工具描述里。比如“这个工具在只读沙箱下会失败”这句话，可能出现在工具描述里，而不是系统提示里。这个选择有实际后果：

  • 片段可以逐轮更新，不必重写系统提示。切换工作目录时，只有那一条片段变，前缀不动。
  • 片段在历史里，可以被压缩、被裁剪、被回放。它不像系统提示那样“永远在”。
  • 片段是模型可见的自然语言，不是结构化字段。模型可以引用它，也可以忽略它。

代价是同一类信息有了两个来源。排查“为什么模型不知道现在是只读模式”时，你要同时看系统提示、工具描述和最近的片段，而不是看一个配置项。这是把稳定性换成可维护性的典型交易。

2.3 写进历史之前，先修一遍

历史不是“发生过什么就存什么”。Codex 在写入时执行一组固定不变量，normalize_history 负责四件事：给缺失的工具调用补上结果、删掉没有对应调用的孤立结果、剥离模型不支持的图片、剥离不支持的音频。history.rs#L968-L982 已核实

这四件事看起来像清理，实际上是协议适配：严格一点的 provider 会直接拒绝不配对的工具记录；宽松一点的会接受，但模型会把孤立结果当成新事实，开始编造它为什么存在。与其在每个 provider 分支里处理，不如在写入时统一成一种合法形状。

代价是不可逆。被剥掉的图片不会在下一轮回来；被补上的空结果会让模型以为工具真的返回了空。这也是为什么“历史规范化”必须和会话日志分开：日志保留原样，活历史才是裁剪过的投影。第 18 章会展开这个区分。

2.4 incremental_tools：把“每次都发”改成“只发变化”

当 incremental_tools = true 时，本次请求把 tools 置空、base_instructions 置为空文本，改由历史里已经写入的工具与指令增量承担。turn.rs#L1666-L1695 已核实

这个设计的动机很直接：工具表和大段指令在长会话里被重复发送几百次，而它们几乎不变。把它们挪进历史，只在新工具出现、旧工具消失、指令版本变化时追加一条增量，前缀就变短了，缓存也更容易命中。首次请求仍然要完整发一次，之后才是增量。

工具定义值得单独优化，原因有三。第一是体积：它和系统提示一起构成每轮都要发送的前缀，工具越多、描述越长，留给对话的空间越小。第二是稳定性：工具表在会话中途很少变化，是最适合“发一次就复用”的内容；相反，一旦它变了，通常意味着权限或插件状态变了，值得让模型知道。第三是缓存：工具定义排在历史之前，它一变，后面的全部内容都失去相同前缀。三点合起来，才有了“增量下发”这种看起来绕、算下来省的方案。

但代价比省下的 token 更值得注意：

  • 历史成了唯一真相。如果压缩、裁剪、回退把增量条目弄丢了，模型下一轮就看不到那个工具。工具“消失”不会报错，只会表现为模型说“我没有这个能力”。
  • 回放要能重建。恢复会话时不能只回放消息文本，还要回放“当时生效的工具集”。否则同一份日志在不同版本下恢复，工具表会不一致。
  • 调试变难。你在请求体里看不到工具定义，只能看历史。抓包工具、日志查看器都要跟着改。
  • 不适合短会话。首次请求仍要全量发；会话只有三五轮时，增量机制只增加了复杂度，没有省下什么。

本快照里 build_prompt 只接收这个开关，没有在函数内设默认值，默认值由调用方决定；本次也没有找到统一的全局默认1。所以“Codex 默认开增量工具”这个说法不成立，能不能用取决于上游怎么传。

下面是 build_prompt 的简化摘录，重点看四块的赋值和 incremental_tools 的分支，省略了错误处理与工具过滤。

// 每个采样步都重新组装一次，历史来自 ContextManager
let mut prompt = Prompt {
    input: history.for_prompt(),          // 已规范化
    tools: visible_tools.clone(),          // 本轮可见集
    base_instructions: base.clone(),       // 岗位说明书
    output_schema: schema.clone(),
    parallel_tool_calls: true,             // 固定写入
};
 
// 增量模式：把两个稳定块挪进历史，本次不再重复下发

    prompt.tools = Vec::new();
    prompt.base_instructions = String::new();
    // 增量条目已在写入历史时追加，这里不再补
}

2.5 顺序：稳定在前，变化在后

把四块排成一条序列，Codex 的顺序是：instructions → tools → input（从旧到新）。这不是审美选择，而是缓存协议的要求：prompt cache 以“前缀完全相同”为命中条件，任何靠前的字节变化，都会让它后面的全部内容重新计费。

所以“把规则文件放在系统提示里”和“把规则文件作为一条消息前插”不是等价方案。前者只要规则改一个字，整个前缀作废；后者只影响插入点之后的内容，而插入点通常在历史头部，仍然很贵，但至少工具表还在。真正便宜的位置是尾部：把易变信息追加在本轮输入之前，前面的东西一个字都不动。

这也是为什么几乎所有 agent 都会把“当前时间”做成一条独立提醒，而不是写进系统提示的第一段。Grok Build 甚至宁可加一条一次性的跨午夜提醒，也不肯改写启动时缓存的 <user_info> 日期。reminders.rs#L507-L522 已核实 第 11 章会专门讲这类注入。

Q你可能会问

问：既然工具表最稳定，为什么不把它放在系统提示最前面？

答：位置由协议决定，不由实现决定。工具的 schema 是独立字段，provider 在计费和缓存时自己决定拼接顺序；你能控制的是“这一轮发哪些工具”和“工具描述写多长”，不是它在序列里的绝对位置。真正能挪的，是那些以文本片段形式存在的东西：环境、规则、提醒。

✓要点小结

  • Codex 的请求是四块：input、tools、base_instructions、output_schema，没有独立 system 字段。
  • 环境、权限、时间都是 contextual 片段，插在历史里，可以逐轮更新，也会被压缩和裁剪。
  • 历史写入前先规范化：补结果、删孤立结果、剥不支持的模态，保证协议合法。
  • incremental_tools 把稳定块挪进历史，省前缀长度，代价是历史成了唯一真相。
  • 稳定在前、变化在后，是缓存友好的唯一通用规则。

05 · 设计取舍

为什么没有一种拼法通吃

下面五组取舍，是这张表背后真正的分歧。每组都写清“A 派在想什么”“B 派在想什么”，以及代价。参数不重复给链接，统一见上一节与各弹窗。

取舍一：系统提示是一整块，还是具名 section

一整块（Codex、Grok Build）实现简单：模板渲染成字符串，改就整段改。调试时你把请求体里的那段话读完，就知道模型看到了什么。具名 section（pi、dsh、Claude Code 的动态段）把提示词拆成有名字的块，每块可以单独计算、单独比较、单独替换。

分野来自“谁会改它”。如果只有发布新版本时才改，一整块够用；如果运行时会因为规则文件、技能清单、工作目录而变化，就必须能定位到块，否则每次变化都要重发全文。pi 的 section patch 和 dsh 的 order 注册表都是为后者准备的。

代价：section 化让“最终提示词长什么样”不再是源码里的一段常量，而是运行时拼出来的。排查时必须打印装配结果，不能只读模板。整块方案则相反：可读性最好，运行时能力最弱。

取舍二：规则放系统提示，还是放消息层

Claude Code 把 CLAUDE.md 放在消息层：一条 isMeta 的用户消息，用 <system-reminder> 包住，前插到消息列表头部。Codex 的 AGENTS.md 则是 WorldState 的一个 section，作为片段进 input。两家都不放系统提示。api.ts#L449-L474 源码 v2.1.88

原因有三点。第一，规则文件会变，系统提示不该跟着变。第二，规则需要“位置语义”：它应该出现在历史开始处，而不是永远排在最前面。第三，消息层的规则可以被压缩、被摘要、被替换，系统提示不行。

代价是规则失去了“不可协商”的地位。它和用户消息在同一个通道里，模型可能把它当成一段普通背景；压缩之后，它可能只剩摘要里的一句“用户偏好某种风格”。Claude Code 的对策是压缩后重新注入，Codex 的对策是压缩后重注初始上下文。两家都在补同一个洞。

取舍三：工具定义全量下发，还是增量/延迟

全量下发（opencode v1、dsh）最可预测：模型每一轮都能看到完整工具表，不存在“工具忽然不见”。代价是长会话里同一份 schema 被重复发送几百次；工具越多，前缀越长，能留给对话的空间越小。

增量（Codex incremental_tools）和延迟（Claude Code 的 tst 模式、Codex 的 supports_search_tool、Grok Build 的 search_tool）都在减少“每轮都发”的体积，但机制不同：增量是“发过一次就不再发”，延迟是“先只发名字，用到再取”。前者假设历史可靠，后者假设模型知道自己需要什么。

代价：增量把正确性押在历史上，裁剪、压缩、回退都可能让工具消失；延迟把正确性押在检索上，模型可能搜不到、或者根本不搜就声称自己没有这个能力。全量则把成本押在 token 上——这是唯一一种“贵但不会错”的方案，也是大多数 agent 在工具数量少时的默认选择。

取舍四：历史在内存追加，还是每步从存储投影

追加派（Codex 的 ContextManager）快：一次写入，之后只读。投影派（pi 的会话树、opencode v1 的 SQLite、omp 的叶子回溯）慢：每一步都要重新计算“模型现在应该看到什么”，但天然支持回退、分叉、压缩后重建。

分野来自“会话是不是线性的”。如果是，追加最简单；如果不是，投影几乎是唯一选择，因为同一份日志要能生成多个不同的可见历史。opencode v1 的注释说得很直白：每一步都从存储投影，而不是在内存里累积。

代价：投影派每次请求都要读库、走树、应用边界，首 token 延迟更高；追加派要做分叉时，得复制或重放历史，而且容易出现“内存里是旧的、磁盘上是新的”这种不一致。Codex 用 checkpoint + 后缀回放来缓解，代价是恢复逻辑变复杂。

取舍五：环境信息放头部，还是放尾部

放头部（传统做法）让模型一开始就知道自己在哪、能做什么，符合人类阅读习惯。放尾部（omp 的日期/cwd 提醒、Grok 的跨午夜提醒）牺牲一点“第一印象”，换来前缀稳定。

真正的差别在长会话：cwd 一天可能变十次，时间每轮都在变。放头部意味着每次变化都让整个前缀失效；放尾部只让最后几条消息失效。按 token 计费算，这个差距可能是几十倍。

代价：尾部信息更容易被忽略。模型在长上下文里对末尾的注意力并不比开头强，甚至更弱（“lost in the middle”说的是中间，但尾部同样不是万能位置）。所以放尾部时，通常要配合“每轮重复注入”或“关键节点再提醒一次”，这又增加了注入次数。第 11 章会把这条线讲完。

还有一条横切的取舍：要不要让用户看见装配结果。Codex 没有 /context 类命令，Claude Code 有分类计数，Grok Build 的 /context 分四段。看得见，用户能自己诊断“为什么规则没生效”；看不见，实现方少一层维护负担，但排障只能靠读源码。这是第 12 章的主题。

06 · 小测验

三道题，检验你是否真的会拼

Q1

一个长会话里，你把系统提示第一段的“你是某某助手”改成了“你是某某编程助手”。这一改会让哪些内容重新计费？如果改的是最后一条环境提醒呢？

解析

改第一段会让它之后的所有内容失效：系统提示剩余部分、工具定义、全部历史、本轮输入，都要重新计费。因为缓存要求前缀逐字节相同，第一个字节变了，后面就不再有“相同前缀”。改最后一条环境提醒，只影响这条提醒之后的内容，通常是本轮输入，代价小几个数量级。这就是2.5 顺序与图 01-1的核心：稳定在前，变化在后。

Q2

Codex 打开 incremental_tools 后，某一轮模型说“我没有写入文件的能力”，但工具其实注册了。列出两个最可能的原因。

解析

第一，承载工具增量的那条历史被裁掉或压缩掉了，模型看不到“这个工具可用”。第二，本轮可见集在过滤时没有包含它（权限、沙箱模式、MCP 暴露策略），tools 本来就是空的，增量里也没有。两者的区别很好判断：前者在会话早期能用、后来忽然不能用；后者从一开始就不能用。见2.4 增量工具与2.1 四块。

Q3

Claude Code 把 CLAUDE.md 放在消息层，Codex 把 AGENTS.md 放在片段里，两家都不放系统提示。这样做换来了什么？又失去了什么？

解析

换来的是前缀稳定和可替换：规则改了只动消息，不动系统提示；规则也能被压缩、被重注、被回放。失去的是“不可协商”的地位：规则和用户消息同通道，压缩后可能只剩一句摘要。两家的补救方式不同——Claude Code 压缩后按清单重附文件与技能，Codex 压缩后重注初始上下文。见取舍二与第 15 章。

agent 弹窗 · pi

pi

pi 发请求前不算“消息数组”，而是让 SessionManager 生成一份会话投影：沿当前叶子回溯成树路径，应用最新 compaction 的 firstKeptEntryId，再叠加 context_edit 的省略与替换，得到模型真正看到的消息序列。_installAgentRequestProjection() 劫持 agent 内核的 prepareRequest，把 projection.messages 装进 context.messages，把 agent.state.tools 作为可执行实现装进 context.tools。两者刻意分开：消息声明“provider 可见的装载清单”，tools 保留“可执行实现”，避免实现层元数据进入请求体。系统提示不是一整块字符串，而是具名 section：preamble 裸文本，其余每个 section 用同名 XML 标签包裹，按声明顺序拼接。

关键参数与默认值
section 顺序：preamble → tools → rules → docs → addendum → project_context → skills → cwd → 自定义 section；压缩摘要被包装成一条 user 消息，前缀为 “The conversation history before this point was compacted into the following summary:”，正文包在 <summary> 里；未找到“按 provider 动态裁剪工具定义”的逻辑。已核实
设计意图
让“模型看到的历史”成为一次可计算的投影，而不是一份只能追加的日志。这样压缩、编辑、换分支都只是改投影参数，不需要改原始记录。代价是每步都要走树、套边界，恢复与分叉的正确性依赖投影函数而不是日志本身。与 Codex 最大差异：Codex 维护活历史，pi 每次重新生成。推断
来源
agent-session.ts#L788-L845（投影装载）· system-prompt.ts#L128-L193（section 顺序）· messages.ts#L11-L22（摘要包装）· session-manager.ts#L543-L573（树投影）

agent 弹窗 · omp

oh-my-pi

omp 每次请求都从会话树叶子向根回溯得到当前分支，再按“最新 compaction / /clear 边界”重建上下文。有压缩时顺序固定：摘要消息在最前 → firstKeptEntryId 起的保留段 → 压缩之后的条目。摘要消息会携带 providerPayload（OpenAI remote / Anthropic native 回放载荷）、snapcompact 图像块和 historyRewriteAt。重建后统一做两道清理：剥离悬挂的 tool_use（没有配对 tool_result 的调用，连同受保护推理签名一起中和），丢弃 stopReason 为 aborted / error 的助手轮及其配对合成结果。系统提示由模板渲染，静态块之后统一追加一个 <project-context> 块（上下文文件、workspace tree / roots、active repo、会话追加文本），这样不同目录的会话共享静态前缀。

关键参数与默认值
路径遍历有环保护：遇到重复 id 即停；<project-context> 永远在静态块之后，Anthropic 的缓存断点正好落在这个块之前；日期/cwd 提醒不写进系统提示，而是插在本请求的首个用户轮之前。已核实
设计意图
把“分支”与“压缩”统一成“重建”，用一个函数同时处理回退、/clear、原生回放和悬挂工具调用。代价是重建必须处理所有历史形态，任何新条目类型都要在重建里加分支，漏一个就会产生非法请求。与 pi 的差别：pi 也有树投影，但 omp 额外处理 provider 原生压缩载荷与中止轮。推断
来源
session-context.ts#L238-L644（重建）· session-context.ts#L673-L734（清理）· system-prompt.ts#L1021-L1046（project-context 位置）

omp 是 pi 的 fork，但默认行为已实质不同：记忆、子代理、checkpoint 都是新增，压缩也从单函数改成五方法链。不要把 pi 的结论直接套到 omp 上。
