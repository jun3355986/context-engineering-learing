请求组装：系统提示词与工具定义

模型每次只看到一段平铺的 token 序列。系统提示词、工具定义、环境说明、历史消息，都是这段序列里的片段。谁在前、谁在后、谁每次都变，决定了能不能命中缓存，也会影响模型是否照着你的规则做。

01 · 一次请求里装了什么

同一个问题问两个仓库，差别出在请求的内容上

上午十点，你在两个仓库里问了同一句话：“把这个模块的错误处理统一一下。”

A 仓库的回答先读目录、再读两个文件，改完还跑了一遍测试。B 仓库的回答直接给出一个补丁，路径是错的，API 也是旧版的。你把同一句话再问一遍，B 还是错。你开始怀疑模型变笨了。

把两次请求拆开看，差别不在模型：A 仓库的工具表里有 read、grep、bash，B 仓库的工具表里没有任何搜索类工具；A 的规则文件里写着“改完必须跑 make test”，B 的规则文件在两个月前被移到了子目录，没有生效；A 的历史里已经有上一次的目录树，B 是全新会话。模型没有变，装进去的东西变了。

上下文管理的第一件事，不是省钱，而是确认“该在的东西真的在”。

这一章只回答三个问题：一次请求由哪几块拼成；它们按什么顺序排；为什么工具定义值得单独拿出来优化。后面的规则文件、按需加载、动态注入，都是在这个结构上往里加东西。

这张图有两个容易看错的地方。第一，层不等于字段。工具定义在多数 API 里是与消息数组并列的字段，不在消息里（Codex 的部分模型会把它放进 input）。但在缓存上，它和系统提示一起排在历史之前，算进前缀。第二，环境信息在 Codex 里不是一个字段，而是插在历史里的若干条片段；别的 agent 放法不同，有的写进系统提示，见本章 03 节的弹窗。所以在 Codex 里，“改系统提示”和“改环境说明”的代价完全不同：前者改在最前面，它之后的缓存全部失效；后者只在历史末尾追加一条新片段。

?动动脑

如果只允许你把一样东西从“每次请求都重发”改成“只发一次”，你会选系统提示、工具定义，还是环境说明？

提示：先问“它变了以后，后面的东西还能不能复用”。

对照答案：环境说明最不该选。它是三者里变得最勤的一块（工作目录、时间都会变），“只发一次”会让模型拿着过期的信息。系统提示和工具定义都很稳定，选哪个都说得通；本章偏向工具定义，因为它的体积随工具数量增长，又排在历史之前，一变就让后面的缓存全部失效（2.4 展开）。

02 · Codex 主线

Codex 怎么拼一次请求

Codex 每次向模型发请求，都先调用 build_prompt 拼出一个 Prompt，里面有四块：input、tools、base_instructions、output_schema。这四块是代码里的逻辑分类，不是线上请求的四个字段。Codex 用的是 OpenAI 的 Responses API，请求里没有独立的 system 或 instructions 字段：base_instructions 会被包成一条 developer 消息，放在 input 的最前面。对一部分模型，tools 也不单独成字段，而是变成 input 最前面的一条 additional_tools 条目。这类模型在模型元数据里标着 use_responses_lite，下文称 Lite 模型。第 30 章会逐行读这段代码。client_common.rs#L22-L40、common.rs#L278-L304、client.rs#L975-L1012 已核实

2.1 四块各装什么

  • input：历史条目。由 ContextManager 持有的活历史（内存里正在使用的那份历史，区别于存在磁盘上的会话日志）。每次生成请求时，Codex 会先复制一份，在副本上做规范化（见 2.3）。所以发出去的 input 里不会有“有工具结果、没有对应调用”的孤立记录。
  • tools：这次请求可见的工具规格。注意是“这次请求可见”，不是“全部注册”。权限、沙箱模式、MCP 暴露策略都会在这里做一次过滤。
  • base_instructions：岗位说明书，相当于系统提示。身份、做事方式、工具使用通则都在这里，是整个前缀里最稳定的一段。
  • output_schema：结构化输出约束。普通会话 output_schema_strict = true；guardian / basic 会话（Codex 里负责审批审查的内部会话）为 false。

build_prompt 同时还固定写入 parallel_tool_calls = true。这个值不是“建议”，而是客户端给出的许可：能不能一次发出多个工具调用，由客户端在每次请求里设定，不由模型决定。不过这只是 Prompt 里的值，实际生成请求体时，Lite 模型会被改成 false。turn.rs#L1666-L1695、client.rs#L1083 已核实

为什么强调“这次请求可见”。如果把“注册过的工具”直接当成“发出去的工具”，权限系统就形同虚设：一个被禁用的工具仍然占着 schema，仍然能被模型点名。Codex 在组装这一步做过滤，等于把权限判断前移到了请求边界。代价是工具表在会话中途可能变化，而它排在历史之前，一变就会让后面的缓存失效。2.4 的 incremental_tools 与这个问题有关。step_context.rs#L47-L48 已核实

2.2 环境与权限：不是字段，是片段

Codex 没有“环境信息”这个独立字段。它以上下文片段（contextual fragment，一小段带标签、角色为 user 或 developer 的消息）的形式插进 input。<environment_context> 装 cwd、平台等，<current_time_reminder> 装时间，AGENTS.md 的内容也是一种片段。contextual_user_message.rs#L1-L40 已核实

权限与沙箱说明也一样：一部分来自这些片段，一部分写在工具描述里。比如“这个工具在只读沙箱下会失败”这句话，可能出现在工具描述里，而不是系统提示里。这种放法有三个后果：

  • 片段可以单独追加更新，不必重写系统提示。切换工作目录时，只会在末尾多出一条片段，前缀不动。
  • 片段在历史里，会像其他消息一样被压缩、被裁剪，恢复会话时还要从存档里重放出来。它不像系统提示那样“永远在”。
  • 片段是模型可见的自然语言，不是结构化字段。模型可以引用它，也可以忽略它。

代价是同一类信息有了两个来源。排查“为什么模型不知道现在是只读模式”时，你要同时看系统提示、工具描述和最近的片段，而不是看一个配置项。这是拿可维护性换前缀稳定的典型交易。

2.3 发给模型之前，先规范化一遍

历史里存的东西，不一定是模型能直接接受的样子。每次生成请求时，Codex 先复制一份历史，在副本上调用 normalize_history。它保证几条规则始终成立（不变量）：给缺失的工具调用补上结果、删掉没有对应调用的孤立结果、剥离模型不支持的图片、剥离模型不支持的音频。history.rs#L968-L982、#L603-L617、turn.rs#L555-L557、#L1749-L1751 已核实

这四件事看起来像清理，实际上是协议适配：严格一点的 provider 会直接拒绝不配对的工具记录；宽松一点的即使接受，孤立的结果也会让模型看到一条来历不明的信息。

代价：规范化只改副本，存着的历史和磁盘上的会话日志保持原样，所以每次请求都要重做一遍，剥不剥图片和音频也按这次请求所用模型的能力决定。副本和存档因此会不一致：缺失的工具结果会被补成内容为 aborted 的结果，模型看到的是“这次调用被中止了”，存着的历史里却没有这一条。排查时要分清看的是哪一份。第 18 章会展开日志和活历史的区别。normalize.rs#L53-L66 已核实

2.4 incremental_tools：把工具和指令放进历史，之后只追加变化

当 incremental_tools = true 时，build_prompt 把 tools 置空、base_instructions 置为空文本。工具定义和模型指令不再由请求头部携带，而是作为条目写进历史（工具定义是一条 additional_tools 条目）；之后工具集变了，就往历史末尾追加更新。turn.rs#L1666-L1695、world_state.rs#L94-L101、models.rs#L1037、lib.rs#L266-L267 已核实

这个功能在这份代码里默认关闭，也不是用户直接配置的开关。传给 build_prompt 的布尔值由 current_window_uses_incremental_tools 算出：不是 Lite 模型，一律为假；历史还空着时（一段新历史刚开始），看功能开关 IncrementalTools，它处于“开发中”阶段，默认是 false；历史不空时，看历史里已经有没有 additional_tools 条目。所以“Codex 默认开增量工具”这个说法不成立。world_state.rs#L44-L56、step_context.rs#L55-L62、lib.rs#L1592-L1596 已核实

源码没有写这样做的动机，下面是根据结构做的推断。工具定义和指令并没有从请求里消失，只是换了位置：它们成了历史的一部分，随历史一起发送，进入模型的 token 并没有因此减少。变的是以后的改法。tools 字段排在历史之前，改一次就让后面整段历史失去相同前缀；放进历史之后，工具集变化只是末尾多一条更新，前面已缓存的部分不用动。第 30 章对这笔账算得更细。推断

工具定义值得单独优化，原因有三。第一是体积：它和系统提示一起构成每次请求都要发送的前缀，工具越多、描述越长，留给对话的空间越小。第二是稳定性：工具表在会话中途很少变化，最适合放在固定位置反复复用；相反，一旦它变了，通常意味着权限或插件状态变了，值得让模型知道。第三是缓存：工具定义排在历史之前，它一变，后面的全部内容都失去相同前缀。体积主要靠“延迟加载”去减（见取舍三），稳定性和缓存这两点，才是增量下发要处理的。

它的代价有下面几条，同样是根据结构做的推断：

  • 历史成了唯一依据。增量是否生效，看的是历史里有没有工具声明（has_tool_declarations()）。声明整条丢掉时，下一次请求会退回完整下发；更隐蔽的是之后追加的更新被裁掉，模型手里的工具表就会和实际可用的不一致。
  • 重放要能重建。恢复会话时要重放存档，不能只重放消息文本，还要把“当时生效的工具集”重建出来。否则同一份日志在不同版本下恢复，工具表会不一致。
  • 调试变难。请求的 tools 字段是空的，工具定义混在 input 的一条条目里，之后的更新又散在历史各处。抓包工具、日志查看器都要跟着改。
  • 不适合短会话。首次请求仍要把完整的工具表和指令写进历史；会话很短、工具集又不变时，增量机制只增加了复杂度，看不到收益。

下面是 build_prompt 的简化摘录，重点看四块的赋值和 incremental_tools 的分支，省略了错误处理与工具过滤。

2.5 顺序：稳定在前，变化在后

把请求排成一条序列，Lite 模型的顺序是：工具声明 → 指令 → 历史（从旧到新），三者都在 input 里；其他模型的 tools 仍是顶层字段，input 里是“指令 → 历史”。服务端怎么把顶层字段和 input 排成一段，源码里看不出来。共同点是稳定的内容在前，变化的内容在后。这是缓存的要求：prompt cache 以“前缀完全相同”为命中条件，任何靠前的字节变化，都会让它后面的全部内容重新计费。client.rs#L975-L1012 已核实

所以“把规则文件放在系统提示里”和“把规则文件作为一条消息前插”不是等价方案。前者只要规则改一个字，系统提示和排在它后面的全部历史都要重新计费；后者只影响插入点之后的内容，而插入点通常在历史头部，所以也很贵，只是系统提示还能命中。最便宜的位置是尾部：易变信息追加在已有历史的末尾，前面的东西一个字都不动。

同样的考虑也体现在时间的处理上：Codex、omp、Grok Build 把“当前时间”或日期做成独立的提醒，而不是写进系统提示的第一段。Grok Build 甚至宁可加一条一次性的跨午夜提醒，也不肯改写启动时缓存的 <user_info> 日期。第 11 章会专门讲这类注入。reminders.rs#L507-L522 已核实

Q你可能会问

问：工具表这么稳定，agent 能自己决定它在序列里排第几吗？

答：要看它在请求里是什么形式。顶层的 tools 字段排在哪里，是 provider 的接口定的（Anthropic 的文档写明是 tools → system → messages），agent 改不了；它能控制的是这次请求发哪些工具、工具描述写多长。放进 input 或 messages 的文本片段（环境、规则、提醒）由 agent 自己安排位置。Codex 的 Lite 模型把工具声明也做成了这样的条目。

✓要点小结

  • Codex 的请求在代码里是四块：input、tools、base_instructions、output_schema；线上没有独立的 system 或 instructions 字段，指令是 input 开头的一条 developer 消息。
  • 环境、权限、时间都是上下文片段，插在历史里，可以随时追加更新，也会被压缩和裁剪。
  • 每次生成请求时，先在历史的副本上规范化：补上缺失的结果、删掉孤立结果、剥掉模型不支持的图片和音频。
  • incremental_tools（默认关闭）把工具和指令记进历史，之后只追加变化。请求里的 token 没有减少；好处（推断）是工具集变化时不用改动前面已缓存的部分，代价是历史成了唯一依据。
  • 稳定在前、变化在后，是缓存友好最通用的规则。

03 · 七个编码智能体

七个 agent 各自怎么拼：系统提示、历史、工具定义

下面七个 agent 各有一个弹窗。读的时候盯住三件事：系统提示是一整块还是具名 section；历史是在内存里追加，还是每一步都从存储里重新算出这一步要发的消息（这种做法叫“投影”：日志完整保留，压缩、裁剪只改算出来的那一份）；工具定义是全量下发还是有增量/延迟。这三件事会反复出现在后面的章节里。

05 · 设计取舍

为什么没有一种拼法通吃

下面五组取舍，是这张表背后的主要分歧。每组都写清“A 派在想什么”“B 派在想什么”，以及代价。参数不重复给链接，统一见上一节与各弹窗。各组里的代价多是根据结构推断的，源码没有逐条写明。

取舍一：系统提示是一整块，还是具名 section

一整块（Codex、Grok Build）实现简单：模板渲染成字符串，改就整段改。调试时你把请求体里的那段话读完，就知道模型看到了什么。具名 section（pi、dsh、Claude Code 的动态段）把提示词拆成有名字的块，每块可以单独计算、单独比较、单独替换。

分野来自“谁会改它”。如果只有发布新版本时才改，一整块够用；如果运行时会因为规则文件、技能清单、工作目录而变化，就必须能定位到块，否则每次变化都要重发全文。pi 的 section patch 和 dsh 的 order 注册表都是为后者准备的。

代价：section 化让“最终提示词长什么样”不再是源码里的一段常量，而是运行时拼出来的。排查时必须打印装配结果，不能只读模板。整块方案则相反：可读性最好，运行时能力最弱。

取舍二：规则放系统提示，还是放消息层

Claude Code 把 CLAUDE.md 放在消息层：一条 isMeta 的用户消息，用 <system-reminder> 包住，前插到消息列表头部。这条消息不存进会话历史，每次请求时才拼上去，而且发生在压缩之后。Codex 的 AGENTS.md 则是 WorldState（记录“模型当前该看到什么”的状态，哪一块变了才产生一条更新片段）的一个 section，作为片段进 input，是历史的一部分。两家都不放系统提示。api.ts#L449-L474、query.ts#L659-L660 源码 v2.1.88

可能的原因有两点（源码没有写明动机）。第一，规则文件会变，系统提示不该跟着变。第二，消息层可以随时增删、替换，不必动系统提示。推断

代价有两个。一是规则的约束力不如系统提示：它和用户消息走同一个通道，模型有可能把它当成普通背景。Claude Code 前插的那条消息末尾就写着：这些上下文可能与任务相关也可能无关，除非高度相关，否则不必回应。二是压缩。Codex 的规则片段在历史里，压缩时可能被当成旧对话摘要掉，所以压缩后要把初始上下文重新放回去。Claude Code 的情况不同：CLAUDE.md 不在历史里，每次请求都重新前插，压缩改不到它；压缩后要补回的是最近读过或写过的文件和技能，规则不用补。

取舍三：工具定义全量下发，还是增量/延迟

全量下发（opencode v1、dsh）最可预测：模型每次请求都能看到完整工具表，不存在“工具忽然不见”。代价是长会话里同一份 schema 要随每次请求重复发送；工具越多，前缀越长，能留给对话的空间越小。

要降低工具定义的成本，有两种着力点不同的思路。延迟是少发内容：先只发名字，用到再取。Claude Code 默认的工具搜索模式 tst、Codex 的 supports_search_tool、Grok Build 的 search_tool 都属于这一类，第 10 章会讲。增量（Codex incremental_tools）不少发内容，只是把工具表放进历史，之后的变化只追加更新。前者假设模型知道自己需要什么，后者假设历史可靠。

代价：增量把正确性押在历史上，声明条目和更新条目要在压缩、裁剪、回退、恢复时都保得住、顺序不乱；延迟把正确性押在检索上，模型可能搜不到，或者根本不搜就声称自己没有这个能力。全量下发最直接，成本全在 token 上，但不会因为历史出问题而丢工具。

取舍四：历史在内存追加，还是每步从存储投影

追加派（Codex 的 ContextManager）快：新内容直接追加进内存里的历史，发请求时只要复制一份再做规范化。投影派（pi 的会话树、opencode v1 的 SQLite、omp 的叶子回溯）慢：每一步都要重新计算“模型现在应该看到什么”，但天然支持回退、分叉、压缩后重建。pi 和 omp 把会话存成一棵树，每条记录指向它的上一条；最新的一条叫叶子，从叶子一路回溯到根，就是这一步要发的历史。

分野来自“会话是不是线性的”。如果是，追加最简单；如果不是，投影几乎是唯一选择，因为同一份日志要能生成多个不同的可见历史。opencode v1 的注释说得很直白：每一步都从存储投影，而不是在内存里累积。

代价：投影派每次请求都要读库、走树、应用边界，首 token 延迟更高；追加派要做分叉时，得复制或重放历史，而且容易出现“内存里是旧的、磁盘上是新的”这种不一致。Codex 的办法是以存档为准：恢复时从最近一次压缩的结果开始，再重放之后的记录，代价是恢复逻辑变复杂。

取舍五：环境信息放头部，还是放尾部

放头部（传统做法，写进系统提示）让模型一开始就知道自己在哪、能做什么。放尾部（Codex 的环境变更片段、Grok Build 的跨午夜提醒）不动前面已缓存的内容，变了就在末尾追加一条。omp 取中间：把日期和 cwd 提醒放在第一条用户消息之前，系统提示和工具表保持不变，但这条提醒一变，后面的历史仍要重算。

差别在长会话里最明显：cwd 一天可能变十次，时间提醒如果每次请求都更新，就一直在变。放头部意味着每次变化都让整个前缀失效；放尾部只让最后几条消息失效。历史越长，两者的差距越大。

代价：追加在尾部的提醒，会随着对话变长被越来越多的新消息推到历史中间。模型对长上下文中间部分的利用往往较差（“lost in the middle”现象）。所以放尾部时，通常要配合定期重复注入，或者在关键节点再提醒一次，这又增加了注入次数。第 11 章会把这条线讲完。推断

还有一条横切的取舍：要不要让用户看见装配结果。Codex 没有 /context 类命令，Claude Code 有分类计数，Grok Build 的 /context 分四段。看得见，用户能自己诊断“为什么规则没生效”；看不见，实现方少一层维护负担，但排障只能靠读源码。这是第 12 章的主题。

06 · 小测验

缓存失效、增量工具、规则位置：三道题

Q1

一个长会话里，你把系统提示第一段的“你是某某助手”改成了“你是某某编程助手”。这一改会让哪些内容重新计费？如果改的是最后一条环境提醒呢？

解析

改第一段会让它之后的所有内容失效：系统提示剩余部分、全部历史、本轮输入，都要重新计费。因为缓存要求前缀逐字节相同，第一个字节变了，后面就不再有“相同前缀”。排在系统提示前面的工具定义不受影响（Codex 的 Lite 模型和 Anthropic 的 API 都把工具放在系统提示之前）。改最后一条环境提醒，只影响这条提醒之后的内容，通常是本轮输入，代价小得多。这就是2.5 顺序与图 01-1的核心：稳定在前，变化在后。

Q2

Codex 打开 incremental_tools 后，某一轮模型说“我没有写入文件的能力”，但工具其实注册了。列出两个最可能的原因。

解析

第一，这个工具不在这次请求的可见集里：权限、沙箱模式、MCP 暴露策略在过滤时把它去掉了，不管开不开增量，请求里都没有它。第二，会话中途工具集变过，历史里追加过一条“该工具已移除”的更新，模型按最新的声明回答推断。两者的区别在时间：前者从一开始就不能用，后者是在会话中途才消失。注意，如果只是承载声明的那条历史被压缩或裁掉，下一次请求会退回完整下发，一般不会表现为“工具消失”。见2.4 增量工具与2.1 四块。

Q3

Claude Code 把 CLAUDE.md 放在消息层，Codex 把 AGENTS.md 放在片段里，两家都不放系统提示。这样做换来了什么？又失去了什么？

解析

换来的是前缀稳定和可替换：规则改了只动消息，不动系统提示。失去的是约束力：规则和用户消息走同一个通道，模型可能把它当成普通背景。压缩时两家也不同：Codex 的规则片段在历史里，压缩后要把初始上下文重新放回去；Claude Code 的 CLAUDE.md 不在历史里，每次请求都重新前插，压缩改不到它，压缩后补回的是文件和技能。见取舍二与第 15 章。

pi

pi 发请求前不算“消息数组”，而是让 SessionManager 生成一份会话投影：沿当前叶子（会话树里最新的那条记录）回溯成树路径，应用最新 compaction 的 firstKeptEntryId，再叠加 context_edit 的省略与替换，得到模型实际看到的消息序列。_installAgentRequestProjection() 接管 agent 内核的 prepareRequest，把 projection.messages 装进 context.messages，把 agent.state.tools 作为可执行实现装进 context.tools。两者刻意分开：消息声明“provider 可见的装载清单”，tools 保留“可执行实现”，避免实现层元数据进入请求体。系统提示不是一整块字符串，而是具名 section：preamble 裸文本，其余每个 section 用同名 XML 标签包裹，按声明顺序拼接。

opencode v2

v2 每一步先 context.select（固定 session / agent / 指令源 / 工具快照），再 context.load（解析模型、按 boundary 读历史、渲染指令基线）。runStep 先跑一次自动压缩，若刚压完就重建上下文重来；否则 baseTranscript 生成至多两段 system：[agent.system ?? 基础提示词, initial]，其中 initial 是指令基线的渲染结果，环境、规则、MCP 指令、技能清单、code mode 目录全部折叠在这里。消息来自 toLLMMessages(投影消息)；到步数上限的最后一轮，把 MAX_STEPS_PROMPT 作为一条 assistant 消息追加，并设 toolChoice: "none"。工具由 registry 快照产出：codemode: false 的内置工具按名字排序进 definitions，execute 追加在末尾。

关键参数与默认值
system 至多 2 段（空段被过滤）；基础提示词按当前工具名注入 ${OPENCODE_TOOL_GUIDANCE}（shell / write / edit 三组）；末步保留工具定义只设 toolChoice: "none"，注释说明是为了维持 provider 缓存前缀；插件 session.context 钩子可以改名、删除工具，凭空新增的会被丢弃。已核实
设计意图
把 v1 的四类块折叠成“基座 + 一条可复用基线”，让基线成为稳定的缓存前缀；末步用 toolChoice: none 而不是删工具，也是同一个目的。代价是指令源必须按“最共享 → 最不共享”严格排序，排错序就会让缓存断在最贵的位置。这个版本是 beta，字段可能继续变。推断

Grok Build

系统提示是一份 MiniJinja 风格模板 templates/prompt.md，由 PromptContext 提供占位符、ToolBridge::render_prompt() 调 TemplateRenderer 渲染；模板按 PromptMode（Extend 默认 / Full）与 PromptAudience（Primary / Subagent）选择基础模板，Extend 时自定义 body 追加在基础模板之后。工具定义不嵌在提示词里，而是独立 ToolDefinition 数组随请求发送；MCP 工具不在该数组里，模型通过 search_tool / use_tool 间接调用。第一条用户消息不是用户原文，而是一个前缀包：<user_info>（OS、shell、cwd、当天日期）＋ 规则区块（AGENTS.md 等，包在 <system-reminder> / <rules> 里）＋ 技能清单 ＋ MCP 服务器清单 ＋ workflow 清单，然后才是 <user_query> 包裹的真实请求。

关键参数与默认值
默认身份标签 "Grok"；PromptMode 默认 Extend；PromptAudience 默认 Primary；模板变体 none / codex / 自定义，codex 走 apply_patch_prompt.md；压缩后系统提示固定为两句话的 COMPACT_SYSTEM_PROMPT。已核实
设计意图
把“一次性的开场信息”压进第一条用户消息，而不是系统提示，这样系统模板保持稳定、换目录或换规则不必重渲染；只有在模型族切换或身份标签变更时才改写会话里的 system 项，同一模型内不会每次请求都重写。代价是首条消息很重，而且规则与请求混在同一条消息里，模型需要自己区分“背景”和“任务”。推断
来源
templates/prompt.md#L1-L40（模板）· prompt/context.rs#L11-L40（渲染上下文）· prompt/user_message.rs#L1-L16（首条消息构成）

DeepSeek Harness

系统提示由 ctx.systemPrompt 的具名 section 注册表拼装：section 带 order，升序拼接，同序按名字的 code unit 排序；装配后由 agent-loop 用 renderPrompt 渲染，并作为一条 system/message 会话事件提交（surface 节点 0），而不是作为请求的 system 字段。这样系统提示本身也进入可重放、可替换的模型历史。固定顺序片段：harness 身份开场白 order = -1000、persona prefix 0、第一方指导居中、persona suffix 10200。工具 schema 由 ctx.tools 的 provider 在本轮装配时给出，ToolProviderResult.schemas 是“本轮可见集”，knownNames 用来区分“配置写错的工具名”和“本作用域故意隐藏的工具”。

关键参数与默认值
includeHarnessIdentity = true；includeRuntimeContext = true；personaPrefix / personaSuffix 默认空串；toolOrder 未设时按注册序，且必须含且仅含一个 '<unlisted-tools>' 占位；多个 complete: true section、未解析变量、toolOrder 列出未注册工具，都会直接失败而不发畸形提示词。推断
设计意图
把系统提示也变成会话事件，等于让“提示词”拥有和消息一样的能力：可重放、可替换、可在压缩后重建。代价是装配失败必须硬失败，否则会把畸形提示词写进日志；toolOrder 的占位约束也让配置更脆。与 Codex 最大差异：Codex 的 base_instructions 是请求字段，dsh 的是历史第一条。推断

docs/subsystems/system-prompt.md#L25-L45（order 与渲染为 system/message）· core/system-prompt/README.md#L28-L56（配置默认值）· mcp-client/README.md#L12（MCP instructions 并入）
