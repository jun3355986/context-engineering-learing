单次工具输出控制

上下文爆炸很少是“聊得太久”，更多是一次 cat、一次测试、一次 grep 把几兆字节塞进了历史。控制单次工具输出，是减量链里代价最低的一环：它不调模型，不改历史，只在“结果进入上下文”的那一刻做一次裁剪。

  • 约 15 分钟
  • 0 个交互
  • L2 → L3

读完你能做到

  1. 区分头保留、尾保留与中间截断三种形状，并为一种工具输出选出合适的一种。
  2. 设计一条“落盘 + 指针 + 回读”的链路，并说出它在什么情况下会失效。
  3. 判断一个阈值该按字节、按行还是按 token 定，并解释 Claude Code 50k 与官方文档 10k 的冲突。

01 · 一次 cat 的代价

“它只看了日志的最后二十行”

下午两点，你让 Agent 查一个构建失败的原因。它很勤快，先 cat build.log。这个文件 2.8 MB，前面是 4 万行依赖安装日志，最后 30 行才是真正的报错。上下文占用从 41% 跳到 93%，Agent 只看到了尾部，然后开始猜。你让它看第 1200 行的警告，它说“日志里没有这一行”——因为中间那段已经被截掉了。

这就是单次工具输出控制要解决的两件事：别让一次输出吃掉整个窗口，以及截掉的部分还能不能找回来。前者是截断形状，后者是落盘与回读。

截断有三种基本形状，选哪种取决于“这类输出里，有用的信息通常在哪”：

  • 头保留（head）：读文件、列目录、搜索命中。开头通常是声明、导入、配置，后面的内容可以按需再读。
  • 尾保留（tail）：构建日志、测试输出、长命令的 stderr。结论和报错在最后，前面是过程。
  • 中间截断（middle）：一段既需要开头上下文、又需要结尾结论的大块内容，比如一个很长的 diff、一份完整的产品需求。Codex 用的是这一种：左预算取一半，右预算取剩下的，中间换成标记。

截断不是“丢数据”，而是“决定模型先看见哪一段”。

这三种形状没有优劣，只有匹配。把构建日志做成头保留，等于把最有用的 30 行扔掉；把源码文件做成尾保留，等于让模型从最后一个花括号往回猜。真正需要设计的是：同一类输出，在不同 agent 里应该用同一种形状吗？答案通常是否定的——读文件与跑命令的信息分布不同，所以多数 agent 给读类工具用 head、给 bash 用 tail。

当心 · 截断发生在“写入历史”时，不是“显示”时

Codex 的截断作用在活历史（live history）写入的那一刻，而不是 TUI 渲染时。history.rs#L560-L580 已核实 这意味着模型从来没见过被截掉的部分，后续也不会“想起来”；除非它主动去存档或原文件里再读一次。

02 · Codex 主线

三段式：留头、留尾、中间标记

Codex 的单次输出控制集中在 utils/string/src/truncate.rs 与 utils/output-truncation 两个 crate。它做四件事：按 token 预算切、保住 UTF-8 边界、插入一个不占预算的标记、把原文留在 rollout 存档里。提交固定为 76ed3b4。

2.1 预算怎么分：左右各一半，但左边先取整

token 策略先估算总 token：ceil(字节数 / 4)，再由调用方决定预算是多少。切分时左预算取 floor(总预算 / 2)，右预算取“总预算 − 左”，然后在字节层面找最近的 UTF-8 字符边界，避免把一个多字节字符劈成两半。truncate.rs#L62-L90 已核实

中间被替换成 …N tokens truncated…，这个标记不占保留预算。truncate.rs#L17-L29 已核实 这一点值得单独说：如果标记也计入预算，那么预算越小、标记占比越大，最后可能只剩标记本身。把它排除在预算之外，是一个很小但很关键的设计。

多块输出（文本与音频混合）共享同一份预算，逐块扣减；超出部分折叠成省略计数。output-truncation/lib.rs#L164-L200 已核实 序列化时还会另留 20% 余量（policy × 1.2），因为转成请求 JSON 之后会多出转义与结构开销。output-truncation/lib.rs#L17-L34 已核实

为什么左右各一半，而不是按内容重要性分配。因为截断发生在工具出口，此刻还不知道模型要用哪一段。左右各一半是一个“不押注”的策略：既保住开头的声明与上下文，也保住结尾的结论。代价是中间被砍掉的那段可能正好是模型最需要的——比如 4 万行日志里第 1200 行的唯一一条警告。

2.2 说明头：让模型知道自己看到的是残片

工具出口还有一层 formatted_truncate_text，会在正文前加一段说明：原始 token 数、总行数、以及“已截断”的事实。output-truncation/lib.rs#L17-L34 已核实 这不是装饰。没有说明头，模型会把“看到的 8k”当成“全部只有 8k”，于是得出“日志里没有这条警告”的结论；有了说明头，它至少知道“还有更多，需要时去读原文”。

这也是“截断”与“撒谎”的分界线：截断本身不可避免，但不告诉模型“我截断了”，就会让模型把残片当全量。所有做得细的 agent 都会在结果里留下这类元信息——opencode 的 [showing lines 1-N of M; full output saved to …]、omp 的 Full output: artifact://…、dsh 的 Omitted N bytes. Full formatted result stored at: …，本质都是同一件事。

2.3 原文去哪了：rollout 存档，而不是重新执行

被裁掉的中间原文仍然完整保存在 rollout 存档里。需要时可以从存档找回，而不是重新执行工具。history.rs#L560-L580 已核实 这个区别很重要：重新执行可能得到不同的结果（文件已经变了、测试有随机性、网络请求有副作用），而从存档找回是幂等的。

但 Codex 没有给模型一个“读存档”的通用工具。模型能做的是重新读文件、重新跑命令，或者用 read 的 offset/limit 分页。这意味着“原文还在”对系统成立，对模型不一定可达。真正把“落盘 + 指针 + 回读”做成闭环的是 pi、omp、opencode、Grok 与 dsh，它们的做法在第 04 节。

另一个容易忽略的细节：恢复会话时回放历史，会重新套用当前的截断策略。因此同一份存档在不同策略下恢复出的活历史长度可能不同。rollout_reconstruction.rs#L508-L515 已核实 这既是优点（改策略能立即生效）也是坑（恢复出来的会话和当初跑的不一样）。

2.4 阈值从模型元数据来，不在源码里写死

Codex 的截断预算来自模型元数据的 truncation_policy，例如 tokens(10_000)；源码不写死一个全局值，缺失时由调用方传入策略。history.rs#L560-L580 已核实

为什么把阈值放在模型元数据里。因为“一次工具输出该有多大”取决于窗口与任务：200k 窗口上一次 10k 的输出只占 5%，32k 窗口上就是 31%。把阈值和模型绑定，等于承认“同一个绝对值在不同窗口上不是同一件事”。代价是用户很难一眼知道当前生效的是多少，只能从说明头里反推。

2.5 这套做法的代价

第一，中间截断会丢掉“唯一的一条”。日志里的错误往往只有一行，位置随机；左右各留一半，命中的概率并不高。第二，1.2 的序列化余量是经验值，遇到大量转义字符（比如嵌套 JSON 的字符串）仍可能低估。第三，存档对模型不可见，所以“原文还在”只解决了审计与恢复，没有解决“模型下一轮还想看”。

这也是为什么后面几家的重点不在“切得更聪明”，而在“切完给一个能读回的指针”。截断形状决定第一眼看到什么，指针决定还有没有第二次机会。

03 · 三种形状

同一段输出，三种切法

下面这张图把三种形状画在同一段 100% 的输出上。蓝色是保留，灰色斜纹是被替换成标记的部分。第四行是“落盘 + 指针”：保留下来的不是内容，而是一行路径。

3.1 怎么选：看信息分布，不看工具类型

判断标准只有一条：这类输出里，决定下一步行动的信息在最前面、最后面，还是两头都有。读源码文件，声明与导入在最前面，函数体在后面，模型通常先看头部再决定读哪段，所以 head 合理；跑测试，失败摘要与堆栈在最后，前面是收集与编译，所以 tail 合理；看一份完整 diff，开头的文件路径与结尾的统计都有用，中间的大段上下文可以省，所以 middle 合理。

反例是把“工具名”当标准。pi 给 read/grep/find/ls 用 head、给 bash 用 tail，是因为这些工具的输出分布不同，而不是因为“读类工具就该 head”。如果 bash 跑的是 head -100 file，输出本身已经截过，再套 tail 就会丢掉真正想看的前 100 行。

3.2 落盘 + 指针 + 回读：一条链的三个断点

落盘不是“把内容写进文件”就完了，它是一条三段的链：写文件 → 在上下文里留一个可解析的指针 → 模型有能力按指针回读。任何一段断了，这条链就退化回“普通截断”。

  • 写文件：要保证路径唯一、内容完整、失败时保留原文（dsh 的 fail-open）。
  • 指针：要包含足够的信息让模型知道“这是什么、有多大、怎么读”。只有路径不够，模型可能不知道这是被截断的全量。
  • 回读：要有支持 offset/limit 的读工具，或者一个专门的 read_output。否则模型只能整文件再读一遍，等于把省下的 token 又花回去。

三个断点各有典型失败：路径被清理（opencode 保留 7 天，Claude Code 的 tool-results 随会话按 cleanupPeriodDays 到期，官方文档默认 30 天）；指针被模型忽略（它直接说“输出太长”）；回读把全文重新灌回来（省了个寂寞）。第 06 节的取舍会逐条展开。

06 · 设计取舍

为什么默认值差五倍

下面五组取舍，解释了为什么同样是“单次工具输出”，有的工具留 40 KB，有的留 50,000 字符，有的干脆按 token 算。每组给出两种路线与代价，参数不重复给 permalink。

取舍一：头、尾，还是中间

头派（pi 的读类、omp 的 read/glob/grep、opencode v2）相信“声明与结构在前面”。尾派（pi 的 bash、omp 的 bash）相信“结论在最后”。中间派（Codex）拒绝押注，两头都留。

代价：头派在构建日志上会丢掉唯一的那条报错；尾派在源码文件上会让模型从最后一个花括号往回猜；中间派两头都留，但每头只有一半预算，命中“唯一一条”的概率仍不高，而且它会丢掉最长的一段连续上下文——对需要理解整段函数的任务最不利。

一个常见的改法是“按工具分别配置方向”，pi 与 omp 都这么做。它把选择权交给工具作者，而不是让一个全局策略适配所有输出。代价是新增工具时必须显式声明方向，忘了就落回默认值。

取舍二：截断，还是落盘 + 指针

只截断（Codex 的活历史）最省事：上下文里只有一份被裁过的内容，没有额外文件，也没有回读成本。但它把“原文”变成了系统内部状态，模型不可达。

落盘 + 指针（Claude Code、pi、omp、opencode、Grok、dsh）多花一次磁盘写、多留一行指针，换来“模型可以再读”。指针本身只占几十个 token，相对于被省掉的几万 token 可以忽略。

代价：第一，路径会失效——opencode 保留 7 天，Claude Code 的 tool-results 随会话按 cleanupPeriodDays 到期；第二，模型可能不读，直接凭预览下结论；第三，回读可能把全文重新灌回来，尤其是模型不会用 offset/limit 的时候。落盘链路真正的难点不是写文件，而是让模型知道该怎么读、读哪一段。

取舍三：单条上限，还是按消息聚合预算

单条上限假设“一次工具调用最多这么大”，但并行工具调用会打破这个假设：一条用户消息里可能同时回来 8 个 tool_result，每个都刚好在单条上限之下，合计却是 8 倍。Claude Code 为此加了第二道闸：单条用户消息内所有 tool_result 合计超过 200,000 字符时，按大小降序挑最大的块落盘，直到回到预算内。toolResultStorage.ts#L205-L242 源码 v2.1.88

为什么按大小降序，而不是按时间。目标是“用最少的落盘次数换回最多的空间”，所以先处理最大的块。按时间会先落盘最早的结果，可能落了一堆小的还没回到预算内。

代价：聚合预算要在“所有结果都到齐”之后才能算，意味着并行调用期间上下文会短暂超预算；如果其中一个结果正在被模型使用，落盘它会打断当前推理。单条上限没有这个问题，但会被并行调用绕过。

取舍四：阈值按字节、按行，还是按 token

三家三种口径，背后是三种“硬限制”：

  • 按字节（Grok 40 KB、pi/omp 50 KiB、opencode 50 KiB）：硬限制来自请求体或传输层，字节是可直接测量的量，不需要 tokenizer。
  • 按行（pi、omp、opencode 的 2,000 / 3,000 行；Grok 的 1,000 行）：硬限制来自“人读得完”和“模型能定位”。行数与 token 不成正比，但它是稳定的、与内容无关的单位。
  • 按 token（Codex 的 tokens(10_000)、dsh 的 maxInlineTokens）：硬限制来自窗口，token 才是真正要省的东西。代价是需要估算，而估算会偏。

代价：字节制对中文与代码不敏感——50 KB 的中文可能只有 17k token，50 KB 的 JSON 可能有 30k token；行制对超长单行无效（一行 2 MB 的压缩 JSON 仍然是一行）；token 制最贴近窗口，但每次截断都要估算，且估算误差会直接变成预算误差。多数 agent 是“字节与行取先到者”，等于用两个便宜的量近似一个贵的量。

取舍五：默认值激进还是保守

Claude Code 的源码给通用工具结果设了 50,000 字符的单条上限，toolLimits.ts#L13-L49 源码 v2.1.88 而官方文档说“工具或 hook 输出超过 10,000 字符落盘”。官方文档 两者差五倍。本教程以源码为准，采用源码值：50,000 字符；文档的 10,000 可能是旧版本口径，标【可能已变化】。3

这个冲突本身比数字更有意思。50k 字符约等于 12.5k token，在 200k 窗口上占 6%；10k 字符约 2.5k token，占 1.25%。前者更信任“模型能处理大块输出”，后者更信任“小步读取”。代价：默认值越大，单次输出越可能把窗口吃掉一大块，但模型一次能看到更多上下文；默认值越小，落盘越频繁，回读次数越多，任务被切得更碎。Claude Code 的折中在 Bash 上体现得最清楚：Bash 用 30,000（与文档一致），因为它知道命令输出最容易爆。

还有一组横切的取舍：截断发生在哪一层。在工具实现里截（Grok 的 read_file 自带 1,000 行），最贴近数据源，但每个工具都要写一遍；在统一出口截（opencode 的 Truncate.output、omp 的 streaming-output），一致性好，但拿不到工具语义；在写入历史时截（Codex），能保证“活历史一定不超”，但已经把内容搬进内存。三层各有盲区，多数 agent 同时用了两层。

07 · 小测验

三道题，检验你会不会切

Q1

Claude Code 一条用户消息里并行回来了三个工具结果：80k、70k、60k 字符。单条阈值 50k、聚合阈值 200k。哪些会被落盘？落盘后上下文里留下什么？

解析

三个都超过单条 50k，所以先各自落盘；合计 210k 也超过聚合 200k，但落盘已经把内联量降到“三份预览”。留下的是一段路径加前 2,000 字节预览。若只有 80k 与 60k 两个（合计 140k），则仍按单条规则各自落盘——聚合预算是第二道闸，不替代第一道。见 取舍三。

Q2

一次构建日志有 4 万行，报错在最后 30 行，但第 1,200 行有一条关键警告。用头保留、尾保留、中间截断各会看到什么？你会怎么设计才能两头都不丢？

解析

头保留看到依赖安装的开头，报错与警告都丢；尾保留看到报错，丢掉第 1,200 行；中间截断两头各留一部分，可能保住警告也可能保住报错，命中取决于预算与位置。更稳的做法是尾保留 + 落盘指针 + 提示“完整日志在 <path>，可用 grep 搜 warning/error”，让模型先看结论，再按需回读中间。见 第 03 节 与 取舍二。

Q3

同一个 50 KB 的工具输出，在中文散文、缩进很深的 JSON、单行压缩的 JS 三种内容下，按字节截断与按 token 截断分别会发生什么？哪种口径更适合做窗口预算？

解析

按字节截断在三种内容下都停在 50 KB，但对应的 token 数差很多：中文约 17k、深缩进 JSON 可能 25k 以上、单行 JS 取决于符号密度。按 token 截断会停在同一个预算，但需要估算，且对单行内容仍要按字符边界回退。窗口预算更适合按 token；传输或存储限制更适合按字节。实际系统常把两者叠加：先按字节挡住极端值，再按 token 做窗口预算。见 取舍四。

DeepSeek Harness

dsh 的 spill（默认开）挂在 tools/post-execute 之后，按一份共享估算 token 预算（文本 + 图片 + 图片描述 + 通知合计）保留头尾：超预算的结果按原顺序保留两端，每端分掉“扣除省略通知后剩余预算”的一半；中间被省略的区间内的图片也一并省略；输出一段固定通知，给出省略字节数与完整结果的落盘路径，并提示用 read 的 offset/limit 读，或 grep 这个路径。图片本体不进该文件，文件里记录每张图的可读路径，模型再 read_image。只有通知能放下、预览放不下时允许“仅通知”；连通知都超预算则保留原文。任何存储失败都保留原内容（fail-open）。
