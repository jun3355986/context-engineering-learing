压缩方法链与回退

pi 只有一种压缩：调模型写摘要。oh-my-pi 把压缩做成了一条链——服务端压缩、历史转图、交接文档、机械省略、模型摘要，按顺序试，不可用就跳过，不够就往下走。这一节读这条链的选择逻辑，以及它为什么必须写成递归。

读完你能做到

读之前：这是一份 fork

oh-my-pi 的 README.md 明确写着它是 pi 的 fork。已核实它保留了 pi 的「树 + 投影 + 摘要 + 保留段」骨架，也保留了 keepRecentTokens = 20000、split turn 双摘要、摘要模板、缓存预热这些实现。本节讲的方法链、服务端压缩、snapcompact、handoff、shake 是新增；阈值从「固定预留」改成「窗口比例下限」是改动。读的时候请始终分清这两类。

01 · 功能说明

一次压缩不是「调一个函数」，而是「走一条链」

入口是 runAutoCompaction(reason, willRetry, options)。reason 有四个取值：overflow、threshold、idle、incomplete，分别对应「溢出恢复」「轮后/轮中阈值」「空闲维护」「输出被截断后的续跑」。已核实方法顺序来自配置 compaction.methodOrder，默认是：

["remote", "snapcompact", "handoff", "shake", "soft"]已核实

这条顺序不是「从好到差」，而是「从最省事到最费事」：先问 provider 能不能自己压，再试不调模型的历史转图，再试生成交接文档，再试机械删除，最后才调模型写摘要。

函数先做两件与链无关的事：检查 compaction.enabled（idle 例外），以及检查是否走了实验性的 notes 路径。然后解析方法顺序，从 options.methodIndex ?? 0 开始遍历，对每个候选调用 isCompactionMethodUsable()，第一个可用的就是本次方法。

这一节的第二个重点是 shake。它是唯一一个「可以执行、可以产生效果、但仍然选择继续」的方法：如果它腾出的空间不足以让上下文回到恢复带（阈值 × 0.8），#runAutoShake() 返回 "fallback"，调用方用 methodIndex + 1 递归重新进入 runAutoCompaction()。已核实为什么要递归而不是写一个 for 循环往下走？因为 shake 可能已经改写了历史，后续方法的输入必须是「改写后的」上下文；重新进入函数能保证所有前置检查（启用开关、实验路径、推测压缩、abort controller）都再跑一遍。

for (let index = startIndex; index < methods.length; index++) {

04 · 逐段解读

四层判断，一个递归

第 1 段　闸门：同一份配置，不同 reason 走出不同路径

isCompactionMethodUsable() 只有三个分支：

remote → canUseRemoteCompaction()：要么配置了 remoteEndpoint，要么当前模型支持 provider 原生压缩。已核实

snapcompact → !excludeMedia && model?.input.includes("image")：模型必须能读图，且本次没有被「排除媒体方法」标记。已核实

handoff → reason !== "overflow"：溢出恢复时跳过。已核实

后两个条件的理由值得展开。handoff 的做法是「生成一份交接文档，把它当作摘要继续」，它需要把整段历史再发一次给模型；而 overflow 的前提正是「上一次请求已经超了」，再发一次同样的输入只会再溢出一次。所以溢出路径直接跳过它，而不是「试了再说」。

excludeMediaMethods 来自 413 / payload-too-large 这类错误：请求体太大，而 snapcompact 会增加图片帧，用它来救字节超限等于火上浇油。源码注释写得很直白：「a byte/payload-limit 413 recovery must not retry with an even larger, media-heavy request」。已核实

这就是 reason 的作用：它不是日志标签，而是闸门的输入。同一条 methodOrder，在 threshold 下可能选 handoff，在 overflow 下会跳到 shake。

第 2 段　跳过刚失败的原生压缩

第二个 if 处理一个很具体的场景：推测压缩（speculation）已经在后台试过 remote 并失败了。如果这时还按顺序选 remote，就会把同一个注定失败的请求再发一次，白等一轮超时。

注意它的条件里有一个 methods.slice(index + 1).some(...)：只有「后面还有可用方法」时才跳过。如果 remote 是唯一可用的方法，跳过它就等于什么都不做，那还不如再试一次。这是一个「回退必须有着落」的守卫，和很多重试框架里的「最后一次不降级」是同一个思路。

armedSpec 是另一条支线：推测压缩可能已经产出了摘要，这时直接认领结果，不再执行方法。但 snapcompact 例外——它是本地操作，几乎瞬时完成，一个「可能已经过时」的 LLM 摘要不应该覆盖它。已核实

第 3 段　shake：唯一会「执行后继续」的方法

shake 的语义是「机械省略」：把工具结果和大块 fenced/XML 文本换成占位符，原文落到 artifact。它不调模型，所以快；也正因为快，它经常「删了一些，但不够」。

#runAutoShake() 的判定在 L5779-L5814，逻辑是三步：

一，reclaimed = toolResultsDropped + blocksDropped > 0。一个都没删，说明没有可省略的区域。已核实

二，算剩余上下文。优先用调用方传进来的 triggerContextTokens 减去 result.tokensFreed，再与 thresholdTokens × 0.8 比较；没有传就用 getContextUsage() 的当前值。已核实用 provider 侧的触发值而不是本地估算，是因为本地估算会低估 thinking 签名之类的负载。

三，shouldFallBack = reason !== "idle" && ((reason === "overflow" && !reclaimed) || stillOverThreshold)。已核实三种恢复型 reason 只要「仍高于恢复带」就继续；idle 例外，因为空闲维护有 60 秒以上的定时器，下一轮会重新测，不会空转。

那个 0.8 的系数不是随手写的。源码里叫 COMPACTION_RECOVERY_BAND，作用是滞回：如果只要求「低于阈值」，上下文会在阈值附近来回抖动，每轮都触发一次 shake，而第二次 shake 已经没有东西可删，就会死循环（源码注释提到 issue #2119/#2275）。要求降到阈值的 80%，等于强制「一次退够」。

第 4 段　递归：为什么不是 while

回退那一行是 return await this.runAutoCompaction(reason, willRetry, {...options, methodIndex: methodIndex + 1, fallbackFromShake: true})。用递归而不是循环，有三个实际好处：

第一，输入必须重取。shake 改写了会话条目，后续方法要基于新上下文工作。重新进入函数，preparedContextTokens、triggerContextTokens、推测压缩的认领都会重新计算；如果留在循环里，很容易不小心复用旧值。

第二，前置检查要重跑。启用开关、实验路径、abort controller 的安装、session.compacting 钩子，都在函数开头；递归天然保证它们对新方法生效。

第三，调用栈就是决策链。出问题时日志能看出「shake → soft」这条路径，而不是一堆循环变量。fallbackFromShake 这个标志还会告诉下游「历史已经改过一次」，避免某些方法再做一次同样的省略。

代价是栈深度。方法只有五个，且每个方法最多回退一次（methodIndex 单调递增），所以最坏深度是 5，不会爆栈。

第 5 段　六条触发路径与推测压缩

方法链解决「怎么压」，触发路径解决「什么时候压」。omp 有六条，全部最终汇到 runAutoCompaction()，只是 reason 不同：

表注：六条路径的清单来自 docs/compaction.md#L70-L77；各路径的跳过规则来自 isCompactionMethodUsable() 与 runAutoCompaction() 的 reason 判断。子代理强制开启轮中压缩。

「轮中阈值」是 pi 也有的一条：工具结果落定、下一次 assistant 之前检查一次。它的价值在于「不等这一轮结束，先把上下文降下来」；风险是压缩会打断正在进行的工具序列。omp 对此的处理是 midTurnEnabled，默认 true，子代理强制开启。已核实

「输出未完成」值得单独说。模型因为 length 停下，说明回复被截断；此时上下文里可能多了一条半截的 assistant 消息。omp 会按 incomplete 走同一条链，但如果 shake 之后仍然会撞上同一个输出上限，就会连续触发——所以它有「连续恢复上限」的守卫（源码注释提到 #2119/#2275）。这是编排层的保护，不属于方法链本身。

最后是推测压缩。链在真正跑之前，可能已经有一个后台任务按「第一可用方法」生成了摘要；#claimArmedSpeculation() 会尝试认领它。已核实认领的条件包括：当前分支、模型、设置都没变；一旦变了，认领被拒绝，老老实实重跑。为什么值得做？因为压缩的等待时间主要花在模型写摘要上，如果能在阈值触发前就开始写，用户感知的停顿会短很多。代价是可能白跑——上下文没到阈值、或用户切了模型。

推测压缩与 snapcompact 有一个明确的优先级：armedSpec 对 snapcompact 无效。因为后者是本地瞬时操作，没有必要让一个可能过时的 LLM 摘要覆盖它。已核实这条规则写在 const armedSpec = method === "snapcompact" ? undefined : claimedSpec，一行代码，省掉一次无谓的模型调用。

第 6 段　为什么服务端压缩排第一

把 remote 放在链首，是一个有争议的选择。它的优点是「最省本地算力」：provider 自己在服务端完成压缩，返回一个不透明的窗口，客户端不需要发第二次请求，也不需要解析摘要。对长会话，这能省掉一次完整的模型调用。

代价是「不可见」。你拿不到摘要文本，无法在 UI 里展示「压成了什么」，也无法在压缩后做二次编辑。omp 用 providerReplayThroughEntryId 记录「从哪条开始由原生窗口替代」，重建时把整段替换成 provider 的载荷。已核实这要求后续请求仍然走同一个 provider——换模型就重放不了。

失败的成本也更高：remote 一旦失败，链要往下走，而它排在最前，等于每次都先试一次最慢的路径。omp 的缓解是「原生压缩刚刚失败过就跳过，前提是后面还有可用方法」（前面提到的 methods.slice(index + 1).some(...) 守卫）。已核实这个守卫只在「有退路」时生效，避免了「唯一方法也被跳过」。

如果换成「soft 排第一」，行为会更可预测：每次都是本地摘要，文本可见，跨模型可重放。但长会话的压缩延迟会明显增加。默认顺序反映的是一个产品判断：优先省时间和钱，接受可观测性的损失。

✓要点小结

  • 默认链 remote → snapcompact → handoff → shake → soft，从「最省事」排到「最费事」。
  • reason 是闸门输入：overflow 跳过 handoff，413 排除 snapcompact。
  • shake 是唯一「执行后仍可继续」的方法；不够就带 methodIndex + 1 递归重入。
  • 「够不够」看剩余是否低于阈值 × 0.8，滞回用来防抖与防死循环。
  • 骨架（树、投影、保留段、双摘要）继承自 pi；方法链、服务端压缩、历史转图、交接文档是新增。

05 · 与其他 agent 的差异

别人是一条路，它是一棵树

多数 agent 只实现一种压缩：调模型写摘要。oh-my-pi 把「不调模型也能减」的几种手段排在前面，把「调模型」留作兜底。这不是「更强」，而是「把一次失败的等待换成了多次尝试的机会」。

三点对照：

一是回退的触发条件。omp 的 shake 会「执行后判断够不够」，这是因为它便宜且可增量；opencode v2 的 deliver 会在发送阶段按比例收缩，也是「执行后判断」，但它收缩的是同一个摘要请求，不是换方法。前者换手段，后者换大小。

二是服务端压缩的位置。omp 把它放在链首，因为成功时最省本地算力；v2 按模型元数据 compaction.type === "native" 二选一，不做回退；Codex 则是本地与远端两套实现，由调用路径决定。把「可选优化」放在链首，意味着它失败一次就会拖慢整条链——omp 用「失败后跳过」的守卫缓解这一点。

三是可配置性。omp 允许用户重排五个方法，甚至可以只留 ["soft"] 退回 pi 的行为；pi 只有一个开关 enabled。可配置性带来一个隐性成本：不同用户的压缩行为可能完全不同，评测与支持都更难。

06 · 思考题

三道题，从走链到改链

Q1

配置是默认顺序，模型不支持图片，provider 没有原生压缩端点，reason 是 overflow。这一轮会选哪个方法？如果 shake 删了 3 000 token 但剩余仍在阈值 90%，接下来发生什么？

提示（不给答案）

逐个过闸门：remote 不可用、snapcompact 不可用、handoff 因 overflow 不可用、shake 可用。

然后看 shouldFallBack：reason !== "idle" 为真；reclaimed 为真，所以第一个括号不成立；stillOverThreshold 为真（90% > 80%）。

于是回退到 methodIndex + 1，也就是 soft。

Q2

把 methodOrder 改成 ["snapcompact"]，模型不支持图片。会发生什么？这算「安全失败」吗？

提示（不给答案）

选择循环里没有任何候选通过闸门，method 保持 undefined，函数返回 COMPACTION_CHECK_NONE。

再看 hasUsableCompactionMethod()（L210-L219）的注释：它专门为避免「配置看起来有方法、实际静默 no-op」而写。这说明「什么都不做」在实践中是个需要被检测的状态，而不是一个正常结果。

Q3

你要在链里插入一个「先删图片、再摘要」的新方法。只改 methodOrder 够吗？还需要动哪些地方？

提示（不给答案）

CompactionMethod 是枚举，COMPACTION_METHODS 是白名单，resolveCompactionMethodOrder() 会把不认识的值丢掉。所以先要加枚举。

然后 STRATEGY_BY_COMPACTION_METHOD 要给出映射，isCompactionMethodUsable() 要给出可用条件，runAutoCompaction() 的执行分支要能处理它。

最后想清楚：它是不是「执行后还能继续」的类型？如果是，就要像 shake 一样返回 "fallback"，否则失败会直接结束整条链。扩展 API 没有「注册新方法」的口子，这也是 omp 的一个边界。
