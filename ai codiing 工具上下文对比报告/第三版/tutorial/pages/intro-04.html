窗口装得下，不等于模型用得好

容量是一回事，注意力是另一回事。塞满窗口，只是把问题从“放不下”换成了“找不到”。

  • 约 13 分钟
  • 前置：第 1 章
  • L1 → L2

读完你能做到

  1. 区分名义窗口与有效上下文，各举一个例子。
  2. 解释位置效应与 context rot，并判断哪类信息会被“看见却没用上”。
  3. 用“少而准”替换“多而全”，说出三种具体做法。

01 · 材料都给了，它偏偏漏掉第二条

“测试环境没有外网”

你把两千行网关日志、三个相关文件、外加五条历史约束，一起粘贴进去，问：「这个请求为什么超时？」

它给了一段很像样的分析：连接池、重试次数、DNS 缓存。你等着它说“测试环境没有外网，所以这个探活注定失败”，它没说。那条约束就在你消息的第二条，白纸黑字。

你把那句话单独再发一遍。它立刻道歉，改口，答案就对了。整段材料一个字没多、一个字没少，变的只是那句话的位置。

场景 · 装进去，不等于被看见

模型这一次确实“读到了”全部材料——它没有超窗，也没有报错。但它把注意力分给了那些更像“典型超时原因”的段落，漏掉了你写的那句例外。这类失败不会报错，只会给你一个看起来合理、实际不对的答案。

窗口是桌子的大小，不是屋里所有人的注意力。

前两章都在算“装不装得下”。这一章算另一笔账：装进去之后，还有多少真的被用上。

02 · 两个词要分开

名义窗口与有效上下文

上下文窗口（context window）是名义容量：模型一次最多能接收多少 token。它是一个硬数字，写在模型规格里。

有效上下文（effective context）是另一回事：在这堆材料里，模型实际能稳定用上的那部分。它没有官方数字，只能靠任务表现去测。

开会打比方：会议室能坐五十人，这是容量；但真正能形成结论的，往往是前十分钟的发言和最后拍板那几句。坐满五十人，不等于五十个人都参与了决策。

这也是为什么 /context 这类命令解决不了这个问题。它按类别列出系统提示、工具、规则、消息各占多少源码 v2.1.88（analyzeContext.ts#L918-L1000），量的是容量；它不会告诉你“这段材料里有多少真的会被用上”。

所以“我有 100 万 token 窗口”回答的是容量问题；它不回答“放进去 80 万，模型还能不能找到第 2 条约束”。

03 · 位置效应：中段最容易被跳过

同样的材料，放在不同位置，结果不一样

研究者做过一类很直接的实验：把一段关键信息放在长文档的开头、中间、结尾，其他内容不变，看模型能不能用上它。结论形状很稳定——两头好，中间差。这个现象有个形象的名字：lost in the middle（中段遗失）。待核实1

这解释了很多“它明明看到了”的争论。模型确实读到了那段文字，但在生成答案时，中间位置的信息分到的权重更低。你越往后堆，越容易把关键约束埋进中段。

在多轮会话里，“中间”还有第二层含义：不只是某份文档的中段，也是整段会话的中段。第 3 轮到第 15 轮的讨论，既不在最新几条消息里，也不在你开头写的那段背景里，正好落在两头之间。这就是为什么聊得越久，中间那些“说好过”的决定越容易失效。

04 · 变长本身就会掉分

context rot：不是找不到，是用不好

位置效应说的是“放在哪”。还有一层更麻烦的：只要材料变长，即使任务没变、干扰不多，整体表现也会下降。社区给这个现象起了个名字，叫 context rot（上下文腐化）。待核实2

原因是多重的：注意力被摊薄；长材料里更容易出现相互矛盾的说法；模型倾向于复用最近看到的模式，而不是最早写下的规则。结果就是那句熟悉的抱怨——“前面说得好好的，怎么到后面就变了”。

噪声不只是“无关”，还包括冲突。规则文件说“用 pnpm”，历史里某条报错说“npm install 失败”，模型就得在这两条里选一个。冲突越多，选错的概率越高——哪怕两条都写得清清楚楚。

冲突还分显性和隐性。显性的是两条规则互相打脸；隐性的是同一条规则在不同层级各写了一遍，措辞略不同。后者更麻烦，因为你会以为它们在表达同一件事，模型却可能读成两个约束。维护规则文件时，删掉重复比补充新条目更有价值。

05 · 所以，少而准

把“多给点总没坏处”改成“只给这一轮要用的”

承认了有效上下文这回事，做法就变了。三个立刻能用的动作：

  • 只贴相关片段：不要整份日志，给报错前后三十行；不要整个目录，给命中的文件。
  • 把约束放在两头：开头说一次，任务快结束时再说一次。不是啰嗦，是绕开中段。
  • 把探索丢给子代理：让它去翻十个文件，只把结论带回来，别把十份原文带回主会话。

贴材料前，先过三个问题：这段内容这一轮真的会被引用吗？它有没有可能和已有规则冲突？如果它只是“以后可能有用”，那就别贴，等要用时再读。第三个问题的答案通常是“不贴”——因为“以后”真的到了，你可以再读一次。

工具自己也在这么做。Claude Code 的只读子代理默认不注入 CLAUDE.md，源码注释给出的理由是每周能省下 5–15 Gtok源码 v2.1.88（runAgent.ts#L370-L410）。Codex 的压缩摘要模板里专门留了“约束与偏好”一节，就是为了让这类容易被埋掉的信息在压缩后还活着已核实（prompt.md#L1-L9）。

对团队来说，这条结论还有一个不客气的推论：规则文件不是越长越好。每加一条“以防万一”，都在稀释真正重要的那几条。定期删掉已经失效、重复、和代码里已能看出来的规矩，比继续追加更有收益。

Q没有傻问题

问：那我把所有重要内容都放开头，不就行了？

答：开头的位置也有限，而且它会挤掉历史。更划算的做法是“重复关键约束”，而不是“把所有材料前移”。一句话重复两次的成本，远低于把两万 token 的日志搬来搬去。真正的目标是提高信噪比，不是调整搬运顺序。

✓要点小结

  • 名义窗口是容量，有效上下文是实际用得上的部分，两者不是一回事。
  • 位置效应：开头和结尾的信息更容易被用上，中段最容易被跳过。
  • context rot：材料变长，即使任务不变，整体表现也会下降。
  • 噪声和冲突都会稀释信号；两条都写清楚的矛盾规则，比一条模糊规则更危险。
  • 少而准：只贴相关片段、关键约束放两头、探索交给子代理。
