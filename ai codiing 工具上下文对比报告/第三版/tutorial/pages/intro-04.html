窗口装得下，不等于模型用得好

前几章解决“材料能不能装进窗口”，这一章解决“装进去以后，模型能不能稳定找到并用上”。沿着同一个超时报错，我们分清容量、位置、长度和干扰这四件事。

  • 约 12 分钟
  • 前置：第 3 章
  • L1 → L2

读完你能做到

  1. 区分“没进入请求”和“进入请求却没用好”，不再把它们都叫失忆。
  2. 用控制变量的方法分清位置效应、输入变长和干扰信息。
  3. 重排一次真实请求，并说清每个删改动作解决的是哪类问题。

01 · 材料都给了，它偏偏漏掉关键句

“测试环境没有外网”

下午四点二十分，你排查一个网关超时。你把两千行日志、三个相关文件和五条约束一起发给 agent，其中写着：测试环境不能访问外网，不要用外网探活判断服务状态。这句话夹在两段日志中间。

它给了一段很像样的分析：连接池、重试次数、DNS 缓存，最后建议你检查外网探活。关键句明明在输入里，答案却像没读过它。

为了弄清原因，你另开两个对照请求。A 保持原样；B 使用同一批材料，只把那句约束移到末尾，其他内容和顺序都不动。这一次，B 正确地先排除了外网探活。你没有增加新信息，只改变了已有信息的位置。

场景 · 进入输入，不等于进入答案

两次请求都没有超窗，也没有发生压缩，关键句都实际进入了模型输入。因此，这不是“材料没装进去”，而是“材料装进去了，却没有稳定地影响回答”。这类失败通常没有报错，只会给你一个看起来合理、实际跑偏的答案。

窗口决定桌上能摆多少材料；它不能保证模型决策时会用上每一张纸。

这一章就追踪这张“被漏掉的纸”：先确认它真的进了请求，再分别检查位置、输入长度和周围干扰。每次只改变一个条件，你才能知道问题究竟出在哪。

02 · 先分清三道关卡

装得下、真的装进去、最后被用上

第 1 章讲的上下文窗口（context window）是名义容量：一次请求最多能容纳多少输入与输出 token。它有明确的规格上限，超了就会被拒绝，或者由 agent 提前压缩、截断。

本教程说的有效上下文（effective context）不是一个隐藏的 token 额度，而是“模型在某个任务上能稳定利用的信息范围”。100 万 token 的窗口里，并不存在一条固定的“有效上下文只有 30 万”分界线；它要换个模型、换个任务、换种材料重新测。

从你说出一句话，到它影响答案，中间至少有三道关卡。排查时按顺序来，能少绕很多弯：

关卡 你要确认什么 失败时更像什么
1 · 容量 输入和输出预留有没有超过窗口？ 请求报错，或 agent 触发压缩、截断。
2 · 组装 关键句是否真的进入这次请求，还是已被裁掉？ 磁盘原文还在，但模型这次拿到的副本里没有。
3 · 利用 关键句在输入里，答案有没有遵守或引用它？ 没有报错，却漏约束、答非所问或采用旧结论。

开头的例子已经通过前两关，所以接下来只查第三关。Claude Code 的 /context 主要帮你观察第一关：它按类别列出系统提示、工具、规则和消息各占多少，却不能证明哪句话最终影响了答案。源码 v2.1.88 analyzeContext.ts#L918-L1000

03 · 第一个变量：位置

同一批材料，只换顺序，表现也可能变

开头的 A/B 对照，和 2023 年论文《Lost in the Middle》的思路相同。研究者在多文档问答中固定问题和文档集合，只把含答案的那篇文档移到开头、中间或结尾；在键值检索中，也只调整目标键值对的位置。这样，答案本身没变，位置成了主要变量。

这些实验在多种模型和设置下反复观察到一种常见趋势：关键信息在开头或结尾时表现较好，在中间时较差，曲线因此常呈 U 形。这个现象叫lost in the middle（中段遗失）。它不是“所有模型、所有任务都必然如此”的定律；论文里也有特定任务接近满分、位置影响不明显的例子。已核实 Liu 等，§3–§5

这里的“位置”指模型实际收到的完整请求，不只是你输入框里的那段文字。系统提示、工具定义、历史消息和工具结果都在这条序列里。你在第三轮说过的决定，到第二十轮时可能既远离开头，也远离最新一条消息，于是落进了整次请求的“中段”。

工程上可以据此提出一个可检验的办法：把简短的关键约束放在任务说明附近，或在最终指令前再强调一次。但它只是降低风险，不是保证命中；如果你的模型和任务不同，最好用自己的 A/B 测试验证。

?动动脑

同样一句“不要改数据库 schema”，一次夹在两段日志中间，另一次放在最终任务指令前。哪次更值得先试？

提示：只移动这句话，不改写，也不额外重复。

对照答案：通常先试后者，因为它远离了材料中段，也更靠近最终任务。注意题目特意要求“不额外重复”：如果把原句再发一遍，你同时改变了位置和重复次数，就不能再把效果全归因于位置。

04 · 第二、三个变量：长度与干扰

位置不动，只增加背景，也可能掉分

把关键句移到末尾，并不能解决所有问题。现在做另一组对照：A 只有关键句和相关日志；B 保留这些内容，关键句位置也不动，只在后面追加一批本轮用不到的旧日志。若 B 的表现变差，这次就不能归因于“关键句被移到中段”，因为位置没有变。

Chroma 在 2025 年的技术报告中，把这类“输入 token 增加后，模型使用上下文的可靠性下降”的现象称为 context rot（上下文腐化）。报告测试了 18 个模型，并在多组受控任务里尽量固定问题与答案，只改变输入长度、目标位置或干扰条件。结果是：在这些任务中，输入变长时，模型表现往往变得更不稳定，而且下降不一定是平滑的。已核实 Hong 等，Context Rot

这仍然不是一条“超过某个 token 数就必坏”的规格。报告没有给出通用阈值，也没有证明唯一的内部机制。你只需带走一个可操作的结论：窗口尚未装满，也可能已经出现质量问题；不要等占用率达到 90% 才开始清理。

新增材料并不都是一种东西。为了知道该删什么，可以分成三类：

  • 无关背景：与当前问题没有关系的旧讨论。例如你正在查网关超时，上午的推荐位日志就只是额外长度。
  • 相似干扰（distractor）：看起来很像答案，却不能回答当前问题。例如另一个服务也报超时，但原因完全不同。Chroma 的实验发现，干扰项的影响并不均匀，有些特别容易把答案带偏。
  • 冲突信息：两处材料给出不能同时遵守的要求。例如规则写“统一用 pnpm”，旧结论却写“这里必须用 npm”。这时首先要消除冲突，而不是把两条都再强调一遍。

工程上常用信噪比概括这件事：能帮当前任务作出正确决定的是信号，让它变长、分心或误判的是噪声。注意，“噪声”是相对于本轮任务说的；一份日志此刻该移走，不代表它永远没价值。

05 · 回到故障，按线索定位

别问“模型怎么又笨了”，先问哪个条件变了

现在可以把前面的概念变成排查顺序。下表不是让你给一次失败贴唯一标签，而是帮你决定第一步先改什么。同一次失败可能同时有位置、长度和冲突问题，所以每轮只改一个主要条件，再观察结果。

你观察到的线索 优先检查 第一步
原文件里有关键句，实际请求里没有 请求组装、截断或压缩 先把信息重新放进请求，别急着换措辞。
短材料能答对；材料变长后，关键句又埋在中段 位置效应 只移动关键句做 A/B，不同时增加重复。
关键句位置没变，追加旧日志后开始跑偏 输入长度、无关背景或相似干扰 撤掉新增材料，再按相关性分批加回。
模型在两种互相矛盾的做法之间摇摆 规则与历史是否冲突 指定唯一有效版本，删除或标记旧规则。

06 · 把方法用回开头那次请求

不是再补一段提示，而是重新组织材料

开头那次超时排查，可以这样改。每个动作都对应前面的一类原因，不是为了把提示词写得更漂亮：

  1. 先给任务和少量硬约束。开头写清“分析测试环境的网关超时；不能访问外网，不要建议外网探活”。这是在处理位置问题，但不能保证模型一定遵守。
  2. 只放本轮要用的证据。先给超时前后三十行、相关配置和报错堆栈；完整日志保留路径，需要时再读。这里解决的是长度和无关背景，不是把信息永久删除。
  3. 把相似案例标清边界。如果必须附上另一个服务的超时日志，明确写“仅用于比较格式，不是本次故障原因”，避免它成为相似干扰。
  4. 先统一冲突，再发请求。规则已经要求 pnpm，就删除旧记录里“改用 npm”的临时结论，或注明它已失效。不要让模型替你决定哪条规则现在有效。

要翻很多文件时，把探索过程隔出去

如果答案需要搜索十个文件，可以把这项工作交给子代理（subagent）：它是由主 agent 启动的一次独立 agent 调用，有自己的上下文。子代理读完十份材料，只把结论、必要证据和文件路径带回主会话，十份原文不必全部挤进主上下文。第 17 章会展开它的隔离边界；这里先把它理解为“探索在外面做，结论回到主桌”。

工程印证：agent 也在选择“该带什么”

  • Claude Code 的部分只读子代理默认不注入 CLAUDE.md，避免把主会话的规则包无差别复制给每个子代理。源码 v2.1.88 runAgent.ts#L370-L410
  • Codex 的压缩摘要模板单列“约束与偏好”，让这类信息在摘要里有明确位置，而不是混在过程叙述里。已核实 prompt.md#L1-L9

这些实现说明 agent 会做上下文选择；它们本身不是位置效应或 context rot 的实验证据，研究证据见第 3、4 节的原始来源。

Q你可能会问

问：那我把所有重要内容都放开头，不就行了？

答：不够。所有内容都争“开头”，开头本身也会变长；冲突和相似干扰更不会因换位置而消失。更稳妥的顺序是：先删掉本轮不用的，再统一冲突，最后把少量关键约束放到容易被利用的位置。位置优化是最后一步，不是清理上下文的替代品。

07 · 小结

从“多给一点”改成“给本轮真正要用的”

下次再遇到“它明明看过”，你可以用一句话提醒自己：看过是输入事实，用上是任务结果，中间还隔着组织方式。先做小规模对照，再决定移动、删减还是统一规则，比凭感觉补一大段提示更可靠。

✓要点小结

  • 先分三道关卡：容量是否够用、材料是否进入请求、进入后是否被用上。
  • 有效上下文不是固定的隐藏窗口，要随模型、任务和材料实测。
  • 位置效应研究的是“同一信息放在哪”；context rot 关注的是输入变长后可靠性如何变化。
  • 无关背景、相似干扰和冲突信息是三类不同问题；先辨认，再清理。
  • 实用顺序：排除未装入 → 减少无关材料 → 消除冲突 → 优化关键约束的位置。
