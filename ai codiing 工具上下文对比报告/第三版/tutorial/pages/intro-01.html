上下文窗口是什么

AI 没有突然变笨。它只是把你说过的话，挤出了那块看得见的地方。

  • 约 12 分钟
  • 1 个交互
  • L1 → L2

读完你能做到

  1. 用 token 而不是字数，估一段材料要占多少窗口。
  2. 说清「窗口 = 输入 + 输出」为什么是同一块空间。
  3. 解释输出预留为什么必须留，并说出超窗的三种结局。

01 · 一个真实会发生的下午

“我第一句话就说过了啊”

下午三点四十七分。你让 agent 把导入脚本改成流式处理，顺手加了一句硬约束：不要动数据库 schema。它回“明白”，前十几轮都守规矩。

第二十轮，它为了让一段测试通过，给 users 表加了一列。你往上翻，第一句话明明还在。你问它为什么忘，它很诚恳地道歉，然后接着忘。

场景 · 它不是失忆，是看不见

模型没有一间叫“记忆”的仓库。每一轮开口前，它只能看见这次请求里装进去的材料；装不进去的，等于没说过。装材料的这块地方，就是上下文窗口（context window）。

窗口就是模型面前的一块白板：这一轮能看多少，全看板上还剩下多少地方。

白板不是仓库。每轮开始，材料都要重新摆上去；上一轮被擦掉的，下一轮不会自己回来。这一章只做一件事：把这块白板量清楚。

如果 agent 在同一轮里把同一个文件读了两遍，它占的白板会变大吗？

提示：白板不会因为“内容重复”而自动扩容。

02 · 先统一尺子

token 不是字数，是模型切出来的小块

你打开日志，数了数：300 行，大概 6000 个字符。“不多啊。”它却报：约 3000 token。换一份 2000 字的中文需求文档，你以为是“小文件”，它却吃掉一大块白板。

token 是模型读写文本时用的最小计量单位。它不按“字”切，按自己的词表切：一个常见英文单词可能是一块，一个汉字也可能是一块，标点、缩进、换行同样要占。

所以，同一个文件读两遍，就是两份 token。白板不会因为“内容重复”给你打折。

工程上常用的粗估是“4 个字符 ≈ 1 个 token”：Codex 截断工具输出时按 bytes / 4 估算，Claude Code 的本地粗估用 chars / 4。但这把尺子量中文会明显偏小——同一个意思，中文通常比英文更费 token，一个汉字常常就在 1 个 token 上下，甚至更多。别背系数，记量级：一页中文文档，可能就是一两千 token。推断

代码更阴：缩进、括号、重复的字段名，全都算。一个 500 行的配置文件，可能比一篇 3000 字的文章还重。

对照：agent 自己也在估

  • Claude Code 的本地粗估是 chars / 4，只求快；精确值要等服务端返回 usage。源码 v2.1.88 tokenEstimation.ts#L203-L210
  • Codex 在截断工具输出时按 bytes / 4 估算，并另留 20% 序列化余量。已核实 truncate.rs#L17-L29、lib.rs#L17-L34

两家都在“估”，说明本地算出来的 token 数本来就允许有误差；真正结算看服务端。

当心：字符数不等于 token 数

用 字符数 ÷ 4 估中文，很容易估少。要快，就按“中文 1 字 ≈ 1 token”往上兜；要准，就看服务端返回的 usage。

03 · 白板的面积是固定的

输入和输出，抢的是同一块地方

一次请求里，模型要先“读”再“写”。读进去的系统提示、工具定义、规则文件、历史消息，是输入 token；它写出来的回答和工具调用参数，是输出 token。两边不是两个池子，而是同一块白板的上下两半。

这就是很多人第一次被绊倒的地方：以为 200k 窗口 = 可以塞 200k 输入。不是。输入塞到 200k，请求连一个字的回答都写不出来——它会在开始前被拒。

?动动脑

窗口 200k，输入已经 195k。你让它写一份 10k token 的重构方案，会发生什么？

提示：输出也从同一块白板里扣。先算还剩多少。

04 · 为什么每次都要先留一块

输出预留：给答案留的座位

先回到那道题：195k 输入 + 10k 输出 = 205k，超了 5k。结局不是“方案写得短一点”；没开自动压缩时，请求会在开始写之前被拒。

白板的右下角，你用胶带划出一块：这块留给模型写答案。输入写得再满，也不能越过这条胶带。这块被圈起来的地方，就是输出预留（output reserve）。

预留不是已经写上去的字，而是用胶带围出来的空地：模型不一定写满，但请求必须先圈出“最多可能写多少”。不圈，常见后果不是回答变短，而是请求直接被判超窗。

不同 agent 留法不一样：

对照：输出预留，各家怎么算

  • Claude Code：有效窗口 = 模型窗口 − min(模型最大输出, 20_000)；后面的自动压缩线、阻塞线都在这条有效窗口上算。源码 v2.1.88 autoCompact.ts#L28-L49
  • Codex CLI：用百分比余量：整段硬线取窗口的 95%，自动压缩软线取 90%。已核实 openai_models.rs#L393-L395、context_window.rs#L60-L110

两条路都在做同一件事：在“塞满”之前刹住。一个把余量写成固定 token 数，一个写成百分比。

Q没有傻问题

问：预留 20k，是不是每次都白白浪费 20k？

答：不是。预留是上限，不是消耗；模型写 2k，就只花 2k。真正浪费的是“没留”——那会让请求超窗，或者让 agent 在快满时被迫压缩，把细节挤掉。

06 · 装不下的时候

三种结局，没有一种是免费的

刚才那块白板，是你用手拖满的。真实会话里没人在拖：你只是不停地说、不停让它读文件，历史自己往上长。等它越过某条线，程序才动手。

动手的不是模型。模型只负责读和写，看不见自己还剩多少地方；量 token、判断该不该减量、选哪种减法，都是外面那层 agent 运行时干的活。到了那一步，能选的动作只有三个：

  • 压缩：把旧历史交给模型写成摘要，腾出地方。细节会丢，摘要本身还要再占一块。
  • 截断：直接丢掉旧消息，或砍掉过长的工具输出。快，但丢掉的东西不会自己回来。
  • 报错：什么都不做，请求被拒。最诚实，也最耽误事。

三个动作丢掉的东西不一样：压缩丢细节、留下大意；截断连大意一起丢；报错不丢内容，丢的是这一次请求。所以没有哪个选项更好，只有你此刻更能接受哪种损失。

各家选的阈值不同：Codex 先在 90% 软线触发压缩，95% 是硬线（来源见上面的输出预留一节）；Claude Code 在有效窗口下留 13,000 token 缓冲，再触发自动压缩源码 v2.1.88（autoCompact.ts#L62-L91）。

这些取舍会在第 6 章「用户侧怎么管理上下文」和主线「压缩」一章展开。现在只要记住：它们都是“把已经装进去的东西拿掉”，没有一种能凭空扩容。

07 · 但装得下，只是第一关

白板够大，不等于模型看得清

假设窗口足够大，所有材料都塞进去了。模型就一定能用好吗？不一定。长上下文里，中间位置的信息更容易被忽略（lost in the middle）；相互冲突的指令、无关的日志，也会稀释真正重要的那几句。

窗口装得下，只说明材料摆上了白板；模型能不能找到并用上那几句，是另一回事。

第 4 章会讲“用得好”这件事。在那之前，第 2 章先拆开一次请求，看看白板上到底摆了哪几样东西。

✓要点小结

  • token 是容量和计价的单位，不是字数；中文通常比英文更费 token。
  • 上下文窗口 = 输入 + 输出，共用同一块固定空间。
  • 输出必须预留：不留，请求可能直接超窗。
  • 超窗只有三条路：压缩、截断、报错，都要拿掉已有内容。
  • 装得下不等于用得好；下一关是模型能不能找到并用上。
