上下文窗口是什么

AI 没有突然变笨，只是你早先说的话，已经不在它这一轮能看到的范围里。

  • 约 11 分钟
  • 1 个交互
  • L1 → L2

读完你能做到

  1. 用 token 而不是字数，估一段材料要占多少窗口。
  2. 说清「窗口 = 输入 + 输出」为什么是同一块空间。
  3. 解释输出预留为什么必须留，并说出超窗的三种结局。

01 · 一个真实会发生的下午

“我第一句话就说过了啊”

下午三点四十七分。你让 agent 把导入脚本改成流式处理，顺手加了一句硬约束：不要动数据库 schema。它回“明白”，前十几轮都守规矩。

第二十轮，它为了让一段测试通过，给 users 表加了一列。你往上翻，第一句话明明还在。你问它为什么忘，它很诚恳地道歉，然后接着忘。

场景 · 它不是失忆，是看不见

模型没有一个叫“记忆”的仓库。每次回答之前，它只能看到这次请求里装进去的材料；没装进去的，对它来说就等于没说过。装这些材料的地方，就是上下文窗口（context window）。

可以把窗口想成模型面前的一块白板：这一轮它能看到的，只有板上写着的内容，而板子的面积是固定的。

白板和仓库不同：每轮开始，材料都要重新写上去；上一轮被擦掉的内容，下一轮不会自己回来。这一章先把这块白板量清楚：它有多大，都被谁占着。

?先想一想

如果 agent 在同一轮里把同一个文件读了两遍，它占的白板会变大吗？

提示：白板不会自动把重复的内容合并成一份。

02 · 先统一尺子

token 不是字数，是模型切出来的小块

你打开一份日志：300 行，大约 6000 个字符，看着不多。agent 却显示它占了约 3000 token，因为日志里满是时间戳、路径和编号，这类内容会被切得很碎。换成一份 2000 字的中文需求文档，你以为是个小文件，它同样会占掉一大块白板。

token 是模型读写文本时用的计量单位。模型不按“字”切分文本，而是按自己的词表切：一个常见的英文单词可能是一个 token，一个汉字也可能是一个，标点、缩进、换行同样要算。

顺便回答上面那道题：同一个文件读两遍，就占两份 token，重复的内容不会打折。

工程上常用的粗估是“4 个字符 ≈ 1 个 token”，Codex 和 Claude Code 在本地估算时都这么算（见下面的对照框）。但用它估中文会明显偏少：一个汉字常常就要 1 个 token 左右，甚至更多。不用背系数，记住量级就行：一页中文文档，大概就是一两千 token。推断

代码也比看上去更费 token：缩进、括号、重复的字段名都要算。一个 500 行的配置文件，占的 token 可能比一篇 3000 字的文章还多。

对照：agent 自己也在估

  • Claude Code 的本地粗估是 chars / 4，只求快；精确值要等服务端返回 usage。源码 v2.1.88 tokenEstimation.ts#L203-L210
  • Codex 在截断工具输出时按 bytes / 4 估算；截断预算还会多算 20%，留给 JSON 包装和“已截断”说明行。已核实 truncate.rs#L17-L29、lib.rs#L17-L34

两家都在“估”，说明本地算出来的 token 数本来就允许有误差；真正结算看服务端。

容易踩的坑：字符数不等于 token 数

用 字符数 ÷ 4 估中文，很容易估少。想快速估算，就按“1 个汉字 ≈ 1 个 token”，宁可估多；想要准确的数字，就看服务端返回的 usage。

03 · 白板的面积是固定的

输入和输出，抢的是同一块地方

一次请求里，模型要先“读”再“写”。读进去的系统提示、工具定义、规则文件、历史消息，是输入 token；它写出来的回答和工具调用参数，是输出 token。两者共用同一块白板：输入写得越多，留给输出的地方就越少。

很多人第一次就栽在这里：以为 200k 的窗口能装下 200k 的输入。实际上，输入一旦占满 200k，就没有地方写回答了，请求在模型开始生成之前就会被拒绝。

?先想一想

窗口 200k，输入已经 195k。你让它写一份 10k token 的重构方案，会发生什么？

提示：输出也从同一块白板里扣。先算还剩多少。

04 · 为什么每次都要先留一块

输出预留：先给回答留出地方

先回答那道题：195k 输入 + 10k 输出 = 205k，超出 5k。结果不会是“方案写短一点”；如果没开自动压缩，请求在开始写之前就会被拒绝。

想象你在白板一角用胶带圈出一块，专门留给模型写答案；输入写得再满，也不能越过这条胶带。这块圈出来的地方，就是输出预留（output reserve）。

圈出来的是一块空地，上面还没有字。模型不一定写满，但请求必须先按“最多可能写多少”把地方圈好。不圈的话，请求常常会直接被判超窗。

不同 agent 留法不一样：

对照：输出预留，各家怎么算

  • Claude Code：有效窗口 = 模型窗口 − min(模型最大输出, 20_000)；后面的自动压缩线、阻塞线都在这条有效窗口上算。源码 v2.1.88 autoCompact.ts#L28-L49
  • Codex CLI：用百分比余量：整段硬线取窗口的 95%，自动压缩软线取 90%。已核实 openai_models.rs#L393-L395、context_window.rs#L60-L110

两家做的是同一件事：在窗口塞满之前停下来，给回答留出空间。区别是 Claude Code 按固定 token 数留，Codex 按百分比留。

Q你可能会问

问：预留 20k，是不是每次都白白浪费 20k？

答：不会。预留的是上限，实际用多少算多少：模型只写了 2k，就只用掉 2k。不留才吃亏：请求可能直接超窗，或者 agent 在快满时被迫压缩，把细节丢掉。

06 · 装不下的时候

三种结局，没有一种是免费的

刚才的白板是你亲手拖满的。真实会话里没人拖：你不停地提要求、让它读文件，历史自己就涨上去了。涨过某条线时，程序才会出手。

出手的不是模型。模型只负责读和写；统计 token、判断该不该减量、选哪种减法，都由模型外面那层 agent 程序来做。到了这一步，能选的做法只有三种：

  • 压缩：把旧历史交给模型写成摘要，腾出地方。细节会丢，摘要本身还要再占一块。
  • 截断：直接丢掉旧消息，或砍掉过长的工具输出。快，但丢掉的东西不会自己回来。
  • 报错：什么都不做，请求被拒。最诚实，也最耽误事。

三种做法丢的东西不一样：压缩丢细节、留下大意；截断连大意一起丢；报错不丢内容，丢的是这一次请求。所以没有哪种一定更好，要看你此刻更能接受哪种损失。

各家的触发线不同：Codex 用到 90% 就自动压缩（软线），95% 是不能越过的上限（硬线）；Claude Code 在有效窗口下面再留 13,000 token 的缓冲，用到这里就自动压缩。

出处：Codex 见上面「输出预留」对照框；Claude Code 源码 v2.1.88 autoCompact.ts#L62-L91

这些取舍会在第 6 章「用户侧怎么管理上下文」和主线的「压缩」一章展开。现在只要记住：三种做法都是把已经装进去的东西拿掉，没有一种能让白板变大。

07 · 但装得下，只是第一关

白板够大，不等于模型看得清

假设窗口足够大，所有材料都塞进去了。模型就一定能用好吗？不一定。长上下文里，中间位置的信息更容易被忽略（lost in the middle）；相互冲突的指令、无关的日志，也会稀释真正重要的那几句。

窗口装得下，只说明材料摆上了白板；模型能不能找到并用上那几句，是另一回事。

第 4 章会讲“用得好”这件事。在那之前，第 2 章先拆开一次请求，看看白板上到底摆了哪几样东西。

✓要点小结

  • token 是容量和计价的单位，不是字数；中文通常比英文更费 token。
  • 上下文窗口 = 输入 + 输出，共用同一块固定空间。
  • 输出必须预留：不留，请求可能直接超窗。
  • 装不下时只有三条路：压缩、截断、报错，没有一条能让窗口变大。
  • 装得下不等于用得好；下一关是模型能不能找到并用上。
