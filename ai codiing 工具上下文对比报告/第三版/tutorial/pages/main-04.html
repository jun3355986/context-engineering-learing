动态注入：提醒、状态与增量

Agent 运行中总有新事实要告诉模型：换了目录、过了午夜、待办完成了、规则改了。这些信息放哪里、什么时候放、放几次，决定了它是“被看见”还是“把缓存打穿”。

  • 第 4 类
  • 约 21 分钟
  • 1 张图
  • L2 → L3

读完你能做到

  1. 区分“改系统提示”和“追加消息”两种注入，并预测各自的缓存后果。
  2. 说出 Codex、pi、opencode v2 三种“只注入变化”的实现差异。
  3. 给定一个重复注入的场景，设计出去重与顺序规则。

01 · 一句话说三遍

“当前目录是 …”

一个会话跑了四个小时。你换了三次工作目录，每次 Agent 都能正确读写新目录的文件。你以为是模型自己记住了 cd，其实每一轮都有一条提醒插在消息里：“当前工作目录是 /repo/services/payments”。

同一件事也可能走向反面。另一个实现把这条提醒写进了系统提示的第一段，每次换目录都重写一次。功能上没错，但账单上很明显：每换一次目录，整个前缀（系统提示、工具定义、全部历史）都重新计费一次。四个小时下来，成本可能是前者的几十倍。

动态注入的核心不是“写什么”，而是“写在哪里”。位置决定缓存，次数决定成本，去重决定模型会不会被同一句话烦到。

本章把注入分成两类，再讲三种“只发变化”的实现：

  • 改系统提示：直接编辑那段最稳定的文本。语义最强，缓存代价最大。
  • 追加消息：在历史里插一条 user / developer / synthetic 消息。前缀不动，只影响插入点之后。

“只发变化”是第二类的精细化：不是每轮都追加一条完整提醒，而是比较“模型已经有了什么”和“现在应该有什么”，只发差的那部分。Codex 用 section 差分，pi 用 section patch 消息，opencode v2 用指令 diff 事件。

这张图解释了一个常见误区：很多人以为“系统提示里的信息更权威，模型更会遵守”。实际上，同样一句话放在尾部消息里，模型照样会读；而放在系统提示里唯一确定的好处是“它一定在”，代价是“它一变就全废”。

所以真正的问题不是“哪个位置更好”，而是“这条信息多久变一次”。一天变一次的时间、一月变一次的规则、每轮都变的 todo 状态，应该有三个不同的位置。

02 · Codex 主线

把“模型可见状态”做成一堆可比较的 section

2.1 WorldState：稳定的 id，逐轮的快照

Codex 用一个叫 WorldState 的结构维护“模型可见状态”。每个 section 有稳定的 id，每次采样前逐 section 计算快照，并与上次比较；只有变化的 section 才产生 WorldStateUpdate 片段。对应到 AGENTS.md 就是三句话：没变不发、变了发“替换通知 + 新全文”、删了发“移除通知”。world_state/mod.rs#L380-L395 已核实

这里有一个容易忽略的设计：没有变更阈值。任何字节差异都算变化，哪怕只是多了一个空格。这看起来粗暴，其实是刻意的：阈值需要判断“这个差异重要吗”，而判断本身就要理解内容；与其猜，不如让“内容不变”成为唯一的免发条件。

代价是格式化的噪声也会触发重发。如果规则文件被编辑器自动整理了行尾空格，下一次快照就会认为“变了”，发一遍替换。对缓存来说，这和真的改了一条规则没区别。

2.2 不是所有注入都走 section

时间不走 WorldState。它以 CurrentTimeReminder 的形式，用 developer 角色、<current_time_reminder> 标记写入，格式是 %Y-%m-%d %H:%M:%S UTC。current_time_reminder.rs#L9-L45 已核实 它每轮都可能变，所以不能进 section——进了就会每轮触发一次“替换通知”，反而更贵。

同类片段还有一批：钩子产生的附加上下文、压缩摘要、子代理通知、图片缩放提示、不支持模态的占位文本。它们都按事件插入 input，不改系统提示。contextual_user_message.rs#L1-L40 已核实

这形成了一个清晰的分层：

  • WorldState section：内容较大、变化不频繁、需要“替换而不是追加”的状态，比如规则文件。走差分。
  • Contextual fragment：内容小、每轮可能变、只需“告诉模型一次”的事实，比如时间、图片被缩放过。直接追加。
  • 系统提示：几乎不变的身份与通则。运行时不碰。

代价是同一类信息要有明确的归属。新加一个“当前分支名”，你得先决定它进 section 还是 fragment：进 section 可以替换、不会堆积，但每次变化都要走差分；进 fragment 简单，但会在历史里留下很多条“分支是 X”。选错了不会报错，只会在几百轮之后表现为上下文里全是过期提醒。

2.3 钩子与摘要也走同一条通道

钩子产生的附加上下文以 hook_additional_context 片段进入历史；压缩摘要作为一条 user 消息放在末尾；子代理完成消息作为输入项回到父会话。三者形态不同，机制相同：都是“往 input 里加一条”，都不改 base_instructions。

这个统一带来一个好处：所有动态信息都在历史里，可以被回放、被压缩、被裁剪。也带来一个坏处：它们和用户消息混在一起，压缩时可能被当成“旧对话”摘要掉。Codex 的对策是压缩后重注初始上下文，把 WorldState 里的关键 section 放回摘要之前。

2.4 顺序：谁在谁前面

一轮请求里，Codex 的注入顺序大致是：系统提示（不变）→ 历史里的 contextual 片段（按发生时间）→ 本轮新输入。WorldState 的替换通知插在它该在的位置，通常靠近历史头部，因为它代表“环境状态”而不是“刚发生的事”。

顺序影响两件事。第一，模型读到的因果链：先看到“目录变了”，再看到“用户要求改文件”，它才能理解为什么要改这个目录。第二，缓存断点：越靠前的注入，影响的范围越大。所以同一个事实，能放尾部就不要放头部；必须放头部时，尽量让它稳定。

Q你可能会问

问：既然 section 差分这么麻烦，为什么不每轮都把完整状态发一遍？

答：因为“完整状态”会随着历史累积变成几十条重复。模型看到十遍“当前目录是 X”，不会更遵守，只会更困惑：到底哪一条还有效？差分的本质不是省 token，而是让历史里每个事实只有一条有效版本。

✓要点小结

  • Codex 把状态拆成 WorldState section 与 contextual fragment 两类，前者差分，后者追加。
  • section 差分没有阈值，任何字节差异都触发“替换通知 + 新全文”。
  • 时间、图片缩放、钩子输出、子代理通知都走 fragment，不改系统提示。
  • 顺序上，环境状态靠近头部，事件靠近尾部；越靠前，缓存代价越大。

03 · 只注入变化

三种实现，三种“前提”

“只发变化”听起来是一句话，落到实现上有三种完全不同的形态。它们的差别不在算法，而在“变化”相对于什么来计算：相对于系统提示的 section 集合、相对于模型已经看到的 section、还是相对于磁盘上的文件内容。

3.1 Codex：section 快照差分

参照系是“上一次给这个会话算出的快照”。每一轮重新计算每个 section 的当前值，与上一轮存下来的值比较。变了就发替换，没变就什么都不发。模型不需要知道“旧值是什么”，因为替换通知里带新全文。

这种实现的前提是客户端持有状态。它必须记住每个 section 上次的值，而且这份记忆要和会话绑定。会话恢复时，如果记忆丢了，第一轮会把所有 section 当成“新变化”重发一遍——不致命，只是多花一次钱。

3.2 pi：section patch 消息

参照系是“模型当前已有的 sections”。_preparePromptAndToolLoadout() 用 diffSystemPromptSections() 比较“模型当前已有的 sections”与“本次期望的 sections”，只为发生变化的 section 生成一条新的 system 消息——content 为空、sections 为 patch；未变化的 section 不重发。值变化给新值，section 被删除给 null。agent-session.ts#L1743-L1755 已核实

这和 Codex 有一个关键差别：patch 是有状态的协议，它假设模型“记得上一版”。如果那条 patch 消息被压缩掉了，模型手里就没有“上一版”，后续的 patch 无处应用。pi 的会话树投影部分缓解了这个问题——被压缩的历史仍然在树里，投影时可以重建——但跨会话恢复时，patch 链是否完整取决于日志。

代价：patch 比“替换通知 + 新全文”省得多，但它把正确性押在“模型见过上一版”上。一旦链条断了，模型看到的就是一段“只写了变化、没写基准”的文本，比不注入更糟。

3.3 opencode v2：指令 diff 冻结进事件

参照系是“库里的 current_values”。InstructionState.observe 对比磁盘现状与库里的值，有变化就 commit 发 InstructionsUpdated，把渲染好的增量文本冻结进持久事件。源码注释说明了为什么要冻结：Location 作用域的源事后无法重建，所以必须在提交时就把 diff 文本算好、存下来。instruction-state.ts#L21-L78 已核实

diff 用 createPatch(..., {context: 3})，当 diff 文本比整段替换还长时改用整段替换。被替换掉的旧值按 hash 存进 InstructionBlobTable，读取时批量取回（500 一批）。

代价：冻结让“回放”可靠：同一份事件流在任何时候重放，看到的 diff 都一样；但它也让“修正”变贵。如果当时算出的 diff 有误（比如漏了一个文件），事后无法重算，只能再发一条新的替换事件。这是“可重放”与“可修正”的经典冲突。

3.4 三者的共同前提与不同失败

三种实现都依赖一个前提：“模型已经看到的东西”是可重建的。Codex 靠客户端记住上次快照；pi 靠历史里的 patch 链；v2 靠事件流里的 diff。前提不成立时，失败方式各不相同：

  • Codex 记忆丢失 → 全量重发，多花钱，但内容正确。
  • pi patch 链断裂 → 模型缺少基准，看到“变化”却不知道变化前是什么。
  • v2 事件流被截断 → 重放时缺少某一段 diff，指令基线不完整。

所以“只发变化”不是免费的优化，它把“每次发全量”的正确性问题，换成了“如何保证参照系不丢”的一致性问题。后者更难测：全量发错了，模型至少看到完整内容；差分发错了，模型看到的是残缺内容，而且它不会告诉你缺了什么。

04 · 顺序与去重

同一句话，别让模型看见三次

动态注入最容易出的两个问题，是顺序错乱和重复。顺序错乱让模型误解因果，重复让模型浪费注意力，还会让缓存白白失效。

4.1 注入顺序的四条经验

把各家的做法归纳一下，有四条反复出现：

  1. 环境先于任务：cwd、平台、日期这类“我在哪”的信息，应该在本轮任务之前。omp 把日期/cwd 提醒插在首个用户轮之前，就是这条。
  2. 规则先于请求：规则文件、MCP 指令、技能清单，应该在用户请求之前到位。否则模型会先按默认习惯做，再看到规则，已经晚了。
  3. 事件靠近发生点：工具完成、子代理返回、后台 shell 结束，应该紧跟在触发它的那一轮之后，而不是堆到会话开头。
  4. 模式切换显式化：plan → build 这类状态变化，要有一条明确的提示，而不是让模型从工具可用性里推断。opencode v1 的 BUILD_SWITCH 就是干这个的。

顺序也有代价。把规则放太前，压缩时容易被当成旧历史；把事件放太后，模型可能已经基于旧状态做了决定。没有一种顺序能同时满足“一定看到”和“一定最新”，只能按信息的半衰期排。

4.2 去重的四种台账

去重需要一份“已经说过了”的记录。四家的台账放的地方不同：

  • 历史里（Claude Code）：从历史中的旧 delta 重建“已公告集合”，只追加新增/移除项。好处是台账和历史同生共死，不会出现“台账说有、历史里没有”。
  • 专用字段（omp 的 ttsr_injection）：在重建上下文时汇总成 injectedTtsrRules，避免重复注入。
  • 持久事件（opencode v2 的 metadata.instruction.paths）：synthetic 消息带路径台账；如果这条消息因压缩或回退掉出可见历史，会被重新发现并重注入。
  • 指纹（Grok Build）：技能用 announced_names，MCP 用 (tool_count, description_hash, tool_names_hash) 指纹，只有变化时才重发公告。

四种台账里，只有“历史里”和“持久事件”两种能正确处理“注入内容被压缩掉”的情况。专用字段和指纹都可能出现“台账说已经说过，但模型已经看不见了”——这时模型缺信息，而系统以为它不缺。

4.3 去重失败的两种形态

第一种是重复注入：同一份提醒每轮都发，历史里积了几十条。模型不会因此更遵守，反而可能因为“最新那条”和“旧那条”措辞略有不同而摇摆。解决办法是给每条注入一个稳定的 key，按 key 去重。

第二种更隐蔽：该重注的没重注。注入内容被压缩掉了，台账还在，系统认为“已经说过了”。模型于是缺了一条它以为自己有的信息。v2 的对策是让台账跟着消息走：消息没了，台账也就没了，下次会重新发现。这个设计值得抄。

代价：跟着消息走意味着压缩后可能重复注入一次。多花一点 token，换“不会缺信息”，这个交易通常是划算的。

07 · 设计取舍

为什么“改系统提示”通常是最后的选择

取舍一：改系统提示，还是追加消息

改系统提示的语义最强：它和身份、通则并列，模型最容易当成“必须遵守的设定”。追加消息更像“临时通知”，模型可能把它当成背景。但改系统提示的缓存代价最大：任何字节变化都会让整个前缀失效。

所以绝大多数 agent 把“稳定”留给系统提示，把“变化”挪到消息层。Codex 的 base_instructions、Claude Code 的静态 7 段、Grok 的 prompt.md 模板，都是运行时不碰的。真正会变的东西——规则、时间、todo——全部走消息。

代价：消息层的信息更容易被压缩掉，也更容易被用户消息淹没。补救办法是“压缩后重注”，这又增加了实现复杂度。

取舍二：每轮都提醒，还是变化才提醒

每轮提醒（opencode v1 的计划模式）简单、不会漏，但历史里会堆很多条重复。变化才提醒（Codex 的 section 差分、pi 的 patch）省 token，但依赖“参照系不丢”。

分野来自信息的半衰期。todo 状态变化频繁，适合“变化才发”；“不要动 public API”这种约束可能几十轮都不变，但一旦被压缩掉就再也不会回来，适合“定期重注”。Claude Code 的 todo 提醒按“距上次提醒的轮数”触发，就是这两种的折中。

代价：变化才发的实现，在压缩、回退、恢复之后容易“以为说过”。每轮都发的实现，则会把上下文变成一堆重复通知，反而稀释注意力。

取舍三：全量替换，还是差分补丁

Codex 的 section 变化发“替换通知 + 新全文”，pi 发 patch，v2 发 diff。全量替换最稳：模型不需要记得旧版，读到就是完整内容。patch 最省：只发变化的那几行。diff 居中：带上下文行，能定位。

代价：全量替换在 section 很大时很贵；patch 在链条断裂时会产生“只看到变化、看不到基准”的残缺；diff 需要额外的上下文行，而且“diff 比全文长就改全文”这条规则本身说明：差分包不一定更小。

取舍四：注入到用户消息，还是单独一条消息

opencode v1 把提醒追加到最后一条用户消息的 parts 末尾，标 synthetic: true。这样做的好处是“提醒紧挨着请求”，模型不会把它当成上一轮的事；坏处是它改变了那条用户消息的字节，而那条消息可能已经被缓存过。

Grok、omp、v2 更倾向单独一条 synthetic 消息。好处是边界清晰、可以单独去重、可以单独回放；坏处是消息条数变多，模型需要在两条之间建立联系。

代价：改用户消息省一次“建立联系”的推理，但让缓存粒度变粗；单独消息更干净，但要求模型理解“上一条是背景，这一条才是任务”。

取舍五：台账放历史，还是放外部存储

放历史（Claude Code 从旧 delta 重建、v2 的 metadata.instruction.paths）的优点是“历史没了，台账也没了”，不会出现“系统以为说过、模型其实没看到”。放外部存储（omp 的专用字段、Grok 的指纹文件）的优点是稳定、不受压缩影响，但会出现同样的错位。

代价：台账跟着历史走，压缩后可能重复注入一次；台账独立存储，压缩后可能漏注入一次。前者多花 token，后者让模型缺信息。多数场景下，宁可多花。

08 · 小测验

三道题，检验你是否会算缓存

Q1

同样是“当前时间是 14:05”，方案 A 写进系统提示第二段，方案 B 作为一条 developer 消息追加在历史末尾。一轮之后时间变成 14:06，两种方案的缓存后果分别是什么？

解析

A：系统提示第二段变了，它之后的全部内容——系统提示剩余部分、工具定义、全部历史——都失去相同前缀，需要重新处理。B：只有新追加的那条消息是新的，前面的系统提示、工具定义、旧历史全部保持相同前缀，缓存继续命中。见图 04-1与2.2。

Q2

pi 的 section patch 消息被一次压缩丢掉了，下一轮又生成了新的 patch。模型会看到什么？为什么这比“不发”更糟？

解析

它会看到一段“只写了变化、没写基准”的文本：某个 section 被改成新值，但模型不知道旧值是什么，也不知道这个 section 原本存在。这比不发更糟，因为不发时模型至少知道自己没有这条信息；残缺的 patch 会让它以为掌握了完整状态。见3.2与3.4。

Q3

你要给一个长会话加“每 5 轮提醒一次 todo 状态”。提醒内容会随 todo 更新而变化。设计时你会把台账放在哪里，怎么避免“压缩后漏提醒”？

解析

台账跟着消息走：每条提醒带一个 key（轮次区间 + todo 内容 hash），从可见历史里重建“已提醒集合”。压缩后如果提醒消息不在了，key 也就不在，下一轮会重新提醒一次；这比“台账独立存储、压缩后漏提醒”安全。同时把“距上次提醒的轮数”也记在消息里，避免重复注入。见4.2 去重的四种台账与4.3。

agent 弹窗 · pi

pi

pi 的动态注入不是“往对话里塞 system reminder”，而是系统提示词的 section 级补丁：每次新一轮请求前，_preparePromptAndToolLoadout() 用 diffSystemPromptSections() 比较“模型当前已有的 sections”与“本次期望的 sections”，只为发生变化的 section 生成一条新的 system 消息（content 为空、sections 为 patch）；未变化的 section 不重发。这既实现了“规则 / 工具 / cwd 变化时只注入变化部分”，也保住了提示词前缀的缓存稳定性。反过来，pi 没有 todo / 计划状态注入（无 plan mode），没有日期或环境变化的周期性提醒；cwd 只是一个普通 section，cwd 变了才会进入 patch。

关键参数与默认值
patch 语义：值变化 → 新值；section 被删除 → null；无固定注入周期，事件驱动，不是定时器。已核实
设计意图
用“section diff”替代“整段重发”，把系统提示当成可增量修改的结构，而不是一整块常量。代价是 patch 依赖模型“见过上一版”，且只对系统提示内的内容有效；需要临时提醒（比如“测试失败了”）时，pi 没有专门的注入通道，只能靠工具结果本身。推断
来源
agent-session.ts#L1743-L1755（调用点）· system-prompt.ts#L217-L229（patch 语义）

pi 的极简取舍在这里最明显：它不做 todo 注入，也不做定时提醒，把所有“动态”都压进 section 变化。需要更多注入能力时，得靠扩展。

agent 弹窗 · omp

oh-my-pi

omp 有三类动态注入，都刻意避开“改系统提示前缀”。第一类是日期 / cwd 提醒：每次 provider 请求时渲染一次，插到该请求的首个用户轮前面；它按 (date, cwd) 确定性生成，同一会话同一天字节稳定，午夜或换目录才变——这样系统提示词与工具数组的前缀缓存不会被目录切换打断。第二类是 TTSR 注入：ttsr_injection 条目记录注入过的规则名，重建上下文时汇总成 injectedTtsrRules，避免重复注入。第三类是上下文笔记（实验性）：context_notes 以 journal 条目挂在分支上，只有最新可见修订进入模型上下文，/clear 会清空可见笔记，单次替换上限 16,384 UTF-8 字节。todo 状态由 syncTodoPhasesFromBranch() 从分支同步，不属于提示词注入。

关键参数与默认值
日期 / cwd 提醒每请求一次，按 (date, cwd) 去重；笔记单次写入上限 16,384 UTF-8 字节（文档口径）；compaction.experimentalContextManagement 默认 false。已核实
设计意图
把“易变但重复”的信息做成确定性函数：同样的输入生成同样的字节，缓存就不会因为“渲染顺序变了”而失效。代价是提醒只能表达 (date, cwd) 两个维度，其它变化（比如分支切换）得另找通道。推断
来源
date-cwd-reminder.ts#L1-L40（提醒生成）· session-context.ts#L337-L348（插入位置）· session-context.ts#L646-L671（上下文笔记）· docs/compaction.md#L152-L180（笔记上限）

“按 (date, cwd) 确定性生成”是 omp 与其它家最大的差别：它不追求“提醒最新”，而追求“同一天内字节不变”。这让它能在跨午夜时只加一条一次性提醒，而不是重写启动时的日期。

注入的统一入口是 agent/pre-step 瀑布的 enter(messages) 决策：监听器可以改写或拒绝本轮被领取的输入，也可以在拒绝后关闭这一轮（不产生 step）。已装插件各自挂在这个点上：time-context 每 ≥10 分钟（或每步，配 refreshIntervalMs: 0）追加一条持久读时消息（当前时间、浏览器时区、距上一条模型可见消息的间隔）；session-reference 在引用消息后插快照；todo 列表跨轮持久、每次更新整表替换；plan mode 把规则作为系统提示词 section，并刻意保持工具目录不变（原文注释：The tool catalog stays the same across modes for request-cache stability），只靠提示词约束行为。压缩期间也允许 inject() 追加无关上下文，所以手动压缩只要求“选中的区间”稳定。
