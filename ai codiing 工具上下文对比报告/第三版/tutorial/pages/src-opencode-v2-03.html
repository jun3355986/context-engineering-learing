指令 epoch 推进

规则文件每改一行，v1 就把整条系统提示重拼一遍；v2 把它拆成「基线 + 增量」，再给基线一个版本号。压缩完成时，版本号前移，之前所有增量一次性作废。这一节读这个版本号怎么观察、怎么提交、怎么推进。

读之前

这里的「指令」不只是 AGENTS.md，还包括技能清单、MCP 指令、code mode 目录等一切会被渲染进系统提示的东西。v2 把它们抽象成有序的「指令源」，每个源提供 read / initial / changed / removed 四个渲染函数。

01 · 功能说明

基线、增量、版本号

v2 的系统提示由两段组成：agent.system ?? 基础提示词，以及 initial——指令基线的渲染结果。已核实基线不是「每次从磁盘重读」，而是存在 InstructionStateTable 里的一组值：

epoch_start（本版本基线从哪个 seq 开始）、through_seq（已经应用到哪个 seq）、initial_values（基线的值）、current_values（当前的值）。已核实

四个字段其实只有两个概念：基线（initial_values + epoch_start）和当前（current_values + through_seq）。增量就是两者之间的差。

每次请求前的流程是 observe → commit：

observe() 并行做两件事：从磁盘/配置读一遍指令源（Instructions.read），从库里取当前状态。然后 observeAgainst() 用 Instructions.diff(observed, previous) 算出 delta 与 blobs，并把 current 更新为「旧值 + delta」。已核实

commit() 先判断：不是首次同步、且 delta 为空，就直接返回，不产生事件。否则 renderUpdateText() 把 delta 渲染成一段人类可读的「新增/删除/改动」，连同 delta 一起发布成 InstructionsUpdated 事件；首次同步则只发 delta，并带 metadata.instructions.initial = true。已核实

模型请求时，baseTranscript() 用 initial_values 渲染基线，事件流里的增量消息跟在后面。压缩完成时，投影器调用 advanceEpoch(seq)：把 epoch_start 与 through_seq 都设成这个 seq，把 initial_values 设成 current_values。已核实

// 并行读：磁盘上的指令源 + 库里的当前状态
export const observe = Effect.fn("InstructionState.observe")(function* (
  db: DatabaseService,
  instructions: Instructions.List,
  sessionID: SessionSchema.ID,
): Effect.fn.Return<Observation, Instructions.InitializationBlocked> {
  const [observed, stored] = yield* Effect.all([Instructions.read(instructions), find(db, sessionID)], {
    concurrency: "unbounded",
  })
  const result = yield* observeAgainst(observed, stored?.current_values)
  return {
    sessionID,
    initial: !stored, // 库里没有状态 = 首次同步
    previous: stored?.current_values ?? {},
    ...result, // current / delta / blobs / admission
  }
})

// 不是首次同步、且没有变化：什么都不发
export const commit = Effect.fn("InstructionState.commit")(function* (
  db: DatabaseService,
  bus: Bus.Interface,
  instructions: Instructions.List,
  observation: Observation,
) {
  if (!observation.initial && Object.keys(observation.delta).length === 0) return
  // 增量文本在提交时渲染并冻结：事后重渲需要原来的 Location 作用域源
  const text = observation.initial ? "" : yield* renderUpdateText(db, instructions, observation)
  yield* bus.publish(
    SessionEvent.InstructionsUpdated,
    {
      sessionID: observation.sessionID,
      delta: observation.delta, // 结构化差异，供后续 apply
      ...(text.length > 0 ? { text } : {}), // 渲染文本，供模型读
    },
    {
      // 首次同步建立基线，不是时间顺序上的历史
      ...(observation.initial ? { metadata: { instructions: { initial: true } } } : {}),
      commit: () => insertBlobs(db, observation.blobs), // 值按 hash 存
    },
  )
})

// 压缩完成：把当前值提升为基线，两个 seq 一起前移
export const advanceEpoch = Effect.fn("InstructionState.advanceEpoch")(function* (
  db: DatabaseService,
  sessionID: SessionSchema.ID,
  epochStart: number,
) {
  yield* db
    .update(InstructionStateTable)
    .set({
      epoch_start: epochStart,
      through_seq: epochStart,
      initial_values: sql`${InstructionStateTable.current_values}`, // 列引用，不是值拷贝
    })
    .where(eq(InstructionStateTable.session_id, sessionID))
    .run()
    .pipe(Effect.orDie)
})

04 · 逐段解读

观察、冻结、推进

第 1 段　observe：为什么先比 current_values，而不是 initial_values

observeAgainst(observed, stored?.current_values) 把「磁盘现状」与「当前值」比，而不是与基线比。已核实因为增量是累积的：基线是 seq 0 的值，当前值是「基线 + 所有已提交的增量」。如果与基线比，每次都会把「已经发过的增量」再算一遍。

initial: !stored 的判断也很关键。库里没有状态意味着这是新会话（或 fork 出来的子会话），第一次提交要建立基线，而不是发一条「从无到有」的增量。首次同步的 text 是空字符串，只带 delta 与 metadata.instructions.initial = true。已核实

Effect.all(..., { concurrency: "unbounded" }) 让读盘与读库并行。这不是性能优化的小事：指令源可能包含网络请求（MCP instructions 要拉取），串行会让每一步的请求准备变慢。

第 2 段　commit：为什么必须冻结文本

源码注释写得很清楚：「The rendered text is frozen into the durable event because re-rendering it later would require the original Location-scoped instruction sources.」已核实「Location 作用域」指的是：指令源的路径是相对于某个工作目录解析的；事后重放时，如果 cwd 变了、文件被删了、MCP server 断了，就渲染不出当时那段文本。

所以事件里同时存两份东西：delta（结构化的 hash 差异）与 text（渲染好的人话）。前者供 apply() 更新状态、供 fork 继承；后者直接给模型看。已核实这也解释了 InstructionBlobTable 的存在：delta 里只放 hash，真正的值按 hash 存，避免重复。

「无变化不提交」也是一条缓存友好规则。每一步都发一条空事件，会让转录里堆满无意义的系统消息，模型每次都要多读几段「没有变化」的说明。

第 3 段　advanceEpoch：一次 SQL 更新，三个字段

initial_values = sql\`${InstructionStateTable.current_values}\` 是列引用，不是把值读出来再写回去。已核实这样更新在同一条 SQL 里完成，不会出现「读的时候 current 变了」的竞态。

三个字段的语义：epoch_start 是本版本起点，through_seq 是已应用到的位置，initial_values 是基线值。推进之后，through_seq == epoch_start，表示「新版本还没有任何增量」。已核实下一次 observe() 会从这个新基线开始算差。

为什么可以「一次性覆盖」旧增量？因为压缩已经把旧历史截断。模型不会再按时间顺序读到「先改成 A、又改成 B」，它只看到「现在是 B」。基线的职责就是回答「现在是什么」，而不是「怎么变成现在」。已核实

第 4 段　fork：为什么继承「最新」基线而不是「边界时刻」的

Session.fork 用 InstructionState.current 与 InstructionEntry.snapshot 给子会话建基线。已核实它不是把父会话的整条增量历史复制过来，而是取「当前值」作为子会话的 initial_values。

理由与 advanceEpoch 一样：子会话从某个边界开始，不需要知道「父会话怎么一步步变成现在」。它只需要「现在是什么」，再加上边界之后的新增量。代价是：如果父会话在边界之前有一条「已删除」的指令，子会话看不到删除动作，但基线里也没有这条指令——结果一致，过程丢失。

第 5 段　状态表与 blob：四个字段背后的两个坑

InstructionStateTable 只有四个业务字段，但每个都对应一类失败：

字段 写入时机 读错会怎样
epoch_startadvanceEpoch基线起点错位，旧增量被重复回放
through_seqapply / advanceEpoch增量被重复应用，或漏应用
initial_valuesadvanceEpoch / initialize基线缺项，模型看不到某条规则
current_valuesapply下一次 diff 从错误起点算，补丁抖动

表注：字段定义与写入点见 instruction-state.ts#L89-L154；initialize 用于 fork / 迁移时直接落一组值。

第一个坑是值以 hash 存储。initial_values 与 current_values 里放的不是文本，是 blob 的 hash；真正的值在 InstructionBlobTable。已核实好处是同一段规则被多次引用时只存一份；坏处是「状态表有 hash、blob 表没值」会让读取直接 Effect.die。源码里的 requireBlob() 找不到就抛错，没有降级。已核实

第二个坑是批量读取的分片。loadBlobs() 按 500 个 hash 一批，用 concurrency: 4 并发查询。已核实这个数字不是随便定的：SQLite 的 IN 子句有变量上限，500 是一个安全的批量；并发 4 是在单文件数据库上避免写锁争用的折中。改这两个数不会改变语义，但会影响长会话的恢复速度。

第三个坑不在表里，而在顺序：commit() 先 bus.publish()，发布参数里带一个 commit: () => insertBlobs(...) 回调。已核实也就是说，blob 的写入与事件的持久化是同一个提交的一部分；如果事件没落盘，blob 也不应该落盘。这个设计让「事件流」成为唯一真源，状态表只是它的投影——与 v2 整体的 event-sourcing 架构一致。

排障建议：如果怀疑 epoch 出错，先查 epoch_start 与最近一条 Compaction.Ended 的 seq 是否相等。不等，说明推进没发生或发生在错误的 seq 上；相等但模型仍看到旧增量，则去查 messageEntries() 的 system 过滤条件（上一节 L102-L106）。两处一起看，基本能定位。

第 6 段　增量的三种形态与缓存账

「发增量」不是只有一种写法。Instructions 给每个源提供四个渲染函数，落到文本上大致有三种形态：

形态 什么时候用 体积 可读性
小增量新增/删除一个条目最小需要对照上下文
unified diff文件内容改动中（带 3 行上下文）好，能看出改哪
整段替换diff 比原文还长最大最直接

表注：diff 使用 createPatch(..., {context: 3})；比较后若 diff 文本更长则改整段替换，见 instruction-discovery.ts#L123-L149。

三种形态的选择标准是「体积优先」：能小就小，小不了就整段。没有「可读性优先」的选项。原因很实际：增量是发给模型的，不是给人看的；模型读 diff 的能力足够，省下的 token 才是真金白银。

从缓存角度看，三种形态的收益依次递减。小增量只在尾部追加几行，前缀几乎不动；unified diff 会带上文件名与上下文行，追加得更多；整段替换等于把这段规则重发一遍，如果它在系统提示里（initial 之后），前缀从替换点断开。所以「diff 太长就整段替换」这条规则，有时候会为了可读性牺牲缓存——但源码的判断是「diff 比原文长」，此时整段反而更短，缓存账也是划算的。

真正影响缓存的是基线放在哪。v2 把 initial 放在系统提示的第二段（[agent.system ?? 基础提示词, initial]），增量作为消息追加在对话里。只要 initial 不变，系统提示这段前缀就是稳定的；advanceEpoch 改变 initial 时，前缀必然失效一次——这就是压缩的缓存代价，无法避免。压缩换来的，是后面每轮少读一大段历史。

第 7 段　压缩失败为什么不推进 epoch

投影器只为 Compaction.Ended 注册了 advanceEpoch；Compaction.Failed 只走 run(db, event)，写一条失败记录，不动状态表。已核实

这是正确的：失败意味着没有新的检查点，历史没有被截断，基线也不应该前移。如果失败也推进，initial_values 会变成「压缩尝试之后的值」，但 epoch_start 指向的 seq 位置上并没有可用的检查点；下一次 messageEntries() 会从一个不存在的边界开始读。

中断（compaction.interrupted）同理，由恢复流程结算成失败，不推进。只有 completed 才推进——这也是「三态」设计的意义：把「尝试过」与「成功」分开，让状态推进只有一个入口。

一个边界情况：如果压缩成功、事件已发，但投影器在 run(db, event) 之后、advanceEpoch 之前崩溃，会留下「检查点已写、epoch 未推进」的不一致。当前代码里 advanceEpoch 只挂在 Ended 的投影上，跨这两步的崩溃窗口是存在的；要彻底消除，需要在恢复流程里额外校验 epoch_start 是否落后于最近一条 completed 的 seq。这是把推进放在投影器里的代价——收益是事件重放能得到同样的结果。

把 v1 与 v2 的指令处理并排，改动集中在「状态存在哪」：

维度v1（733b2c6）v2（042d083）为什么改
状态存放无，每步从磁盘重读状态表 + blob hash可增量、可 fork、可审计
变化粒度整条 system 字符串指令源 diff / patch补丁更小，尾部追加
压缩之后无特殊处理advanceEpoch旧增量一次性折叠进基线

表注：v1 的整段重拼意味着任何一块变化都会让 system 字符串变化；v2 的基线只要不变，前缀就稳定。

✓要点小结

  • 状态表四个字段：epoch_start、through_seq、initial_values、current_values。
  • observe 与 current_values 比，算出 delta；commit 把渲染文本冻结进事件。
  • advanceEpoch 在 Compaction.Ended 的投影里执行，把当前值提升为基线。
  • 压缩截断了历史，所以基线可以一次性覆盖旧增量，不需要按时间重放。
  • fork 继承最新基线，而不是边界时刻的基线；结果一致，过程丢失。

05 · 与其他 agent 的差异

「只发变化」的三种粒度

pi 按 section 打补丁，v2 按指令源发增量，v1 每步整段重拼。三者都叫「只发变化」，但「变化」的单位与「基线」的维护方式完全不同。

← 左右滑动查看全部列，首列固定 →

agent 变化单位 基线 压缩后 缓存收益
opencode v2opencode-v2 指令源（可到 unified diff） 持久化在状态表 推进 epoch，当前值变基线 基线稳定，增量在尾部
pipi 具名 section（八段） 转录里重放 无特殊处理 取决于 provider 是否支持中途系统消息
oh-my-piomp TTSR 规则名 / 日期提醒 注入记录 + 首用户轮 压缩后重新注入 易变内容移出系统前缀
opencode v1opencode-v1 无（整段重拼） 无 不适用 任何一块变化即全失效

表注：v2 042d083（beta）；pi b45e0eb；omp f979f46；v1 733b2c6。v2 的 unified diff 由 createPatch(..., {context: 3}) 生成；补丁比整段替换长时改用整段。

三点对照：

一是基线的存放位置。pi 把补丁存在转录里，每次请求重放出完整提示词；v2 把基线存在表里，增量是事件。前者无状态、易恢复，后者可审计、可 fork。代价是 v2 多了一张表与一套事务。

二是压缩与基线的关系。只有 v2 把「压缩完成」当成「基线可以前移」的信号。pi 不这么做，因为它的 section 补丁不依赖历史长度；v1 没有基线概念。这让 v2 在长会话里越用越省：压缩次数越多，旧增量被折叠得越干净。

三是文本冻结的必要性。v2 冻结渲染文本，是因为指令源是 Location 作用域的，事后无法重建；pi 的 section 是纯函数渲染，随时可以重算，所以不需要存文本。这不是谁更先进，而是「源是否可重放」的差异。

06 · 思考题

三道题，从状态字段到失败恢复

Q1

某会话的 epoch_start = 0、through_seq = 37、current_values = {a: h1, b: h2}、initial_values = {a: h0}。压缩在 seq 40 完成，四个字段各变成什么？

提示（不给答案）

advanceEpoch(40) 把 epoch_start 与 through_seq 都设成 40。

initial_values 被设成 current_values 的列引用，也就是 {a: h1, b: h2}。

current_values 不变。压缩之后、下一次 observe 之前，基线与当前值相等。

Q2

如果 commit() 不冻结 text，只发 delta，会出什么问题？举一个具体场景。

提示（不给答案）

delta 里是 hash，不是内容；渲染需要原始值。值存在 blob 表里，但「怎么渲染」依赖指令源的当前状态。

场景：会话进行到一半，用户切了目录，或删掉了某个 AGENTS.md，或 MCP server 断开。事后重放这条增量时，渲染函数拿不到当时的源，可能渲染出空、报错，或渲染成「新目录下的同名文件」。

冻结文本等于把「当时模型看到的字节」固化下来，重放永远一致。

Q3

fork 继承「最新基线」而不是「边界时刻的基线」，会让子会话看到什么、看不到什么？如果产品要求「子会话必须精确复现父会话在边界时刻的规则」，该怎么改？

提示（不给答案）

看到：边界时刻之后的规则状态（因为最新基线包含边界之后的所有提交）。看不到：边界之后发生的「改了什么」的过程，以及被删除指令的删除动作。

要精确复现，就得同时复制 epoch_start 时刻的 initial_values 与到边界为止的所有 delta，再在子会话里重放。代价是子会话不再「轻」。

还要处理一个冲突：父会话在 fork 之后继续修改规则，子会话不应受影响——所以复制必须是快照，不是引用。
