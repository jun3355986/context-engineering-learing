规则差分：只发变化

AGENTS.md 改了一个字，Codex 不会把整份规则再发一遍——至少不会以「新的一段前缀」的方式重发。它把规则当成一份有状态的世界快照，逐轮比较，只在变化时追加一条「替换通知 + 新全文」，删除时追加一条「不再适用」。这一节读这段最小的差分实现。

01 · 功能说明

差分的是「状态」，不是「文本」

Codex 把模型可见的环境状态拆成若干个具名 section：AGENTS.md、环境、权限、插件、工具目录、模型指令等。每个 section 都有自己的快照类型和 render_diff() 实现。每轮采样前，WorldState 遍历所有 section，把当前值与上次保存的快照比较，只有变化的 section 才产出更新片段。已核实

这里的「差分」不是把新旧两版 AGENTS.md 做逐行 diff，而是比较「这一份规则的整体状态」：有还是没有、文本是否相等、目录是否相同。

这个区别决定了三件事。第一，变化时发的是新全文，不是补丁；模型不需要理解 diff 语法，只需要理解「这段替换之前所有同名规则」。第二，未变化时一个字节都不发，历史不增长，前缀缓存不受影响。第三，删除时发的是一条移除通知，因为旧全文还留在历史里，必须显式告诉模型「它不再适用」。已核实

在整条链路里，这段代码位于「发现规则」和「发请求」之间。上游 agents_md.rs 负责从项目根到 cwd 逐级找到并拼接 AGENTS.md；AgentsMdState::new() 把结果包成一个 UserInstructions 片段；render_diff() 决定这一轮要不要把它变成一条新消息；下游 merge_world_state_updates() 把片段转成 ResponseItem，追加到历史。已核实

为什么要把规则做成「世界状态」而不是「每轮拼进系统提示」？因为规则会在会话中途变化：用户改了 AGENTS.md、切了目录、加载了新的子目录规则。如果每轮都拼进系统提示，任何一次改动都会让整段前缀失效；做成状态差分，改动只追加在历史尾部，前面的对话前缀仍然可以命中缓存。推断

还有一个更实际的理由：规则不是唯一会变的东西。权限模式、工具目录、插件说明、模型指令都会变。如果每个都写一套「变了就重发」的逻辑，代码会迅速失控。Codex 的做法是把它们统一成 WorldStateSection：每节自己决定快照长什么样、变化时发什么，外层只负责遍历、比较、收集。AGENTS.md 只是这套骨架上的一个实现，也是最适合拿来教学的一个。推断

fn render_diff(
    &self,
    previous: PreviousSectionState<'_, Self::Snapshot>,
) -> SectionTransition<Self::Snapshot> { // (新快照, 要追加的片段)
    let current = match &self.instructions { // 当前状态 → 快照
        Some(instructions) => AgentsMdSnapshot {
            directory: instructions.directory.clone(),
            text: Some(instructions.text.clone()),
        },
        None => AgentsMdSnapshot::default(), // 两个字段都是 None
    };
    if matches!(previous, PreviousSectionState::Known(previous) if previous == &current) {
        return (None, Vec::new());
    }
 
    let previous_may_contain_instructions = match previous {
        PreviousSectionState::Known(previous) => previous.text.is_some(),
        PreviousSectionState::Unknown => true, // 旧会话：宁可信其有
        PreviousSectionState::Absent => false,
    };
    let instructions = match (&self.instructions, previous_may_contain_instructions) {
        (Some(instructions), true) => UserInstructions { // 有 → 有：替换
            directory: instructions.directory.clone(),
            text: format!("{REPLACEMENT_NOTICE}\n\n{}", instructions.text),
        },
        (Some(instructions), false) => instructions.clone(), // 无 → 有：直接发
        (None, true) => UserInstructions { // 有 → 无：移除通知
            directory: None,
            text: REMOVAL_NOTICE.to_string(),
        },
        (None, false) => return (Some(current), Vec::new()), // 无 → 无：静默
    };
    (
        Some(current), // 无论发不发，都把当前快照交回去
        vec![WorldStateUpdate::fragment(instructions)], // 恰好一条
    )
}

04 · 逐段解读

四个分支，三种语义

第 1 段　快照为什么只有两个字段

AgentsMdSnapshot 存的是 directory 和 text。没有文件路径列表、没有 mtime、没有内容哈希。这是「模型可见状态」的最小充分集：模型只知道「这些规则来自哪个目录」和「规则正文是什么」，它不知道文件何时被修改，也不该知道。已核实

把 directory 放进快照，意味着「同样的文本出现在不同目录」也会被判定为变化。假设项目根和子目录各有一份内容相同的 AGENTS.md，合并后的文本一样，但目录不同；模型看到的提示是「这些规则来自 /repo/sub」，来源变了，语义也可能变（比如规则的作用范围）。所以目录必须参与比较。推断

反过来说，文件内容的「修改时间」不参与比较。用户把 AGENTS.md 保存了两次但内容没变，不会触发任何通知；这是对的，因为模型看到的字节没变。推断

这也解释了「合并后的文本」为什么不能直接拿来当快照。上游会把「根 → cwd」沿途每一级的 AGENTS.md 拼成一份文本，如果只看最终文本，你无法区分「根目录的规则改了」和「子目录的规则改了」；而 directory 字段至少保留了「这份合并结果来自哪个目录」这一层信息。严格说它仍然不足以定位到具体文件，但对模型来说，「规则来自哪个目录」通常比「来自哪个文件」更有用，因为目录决定了作用范围。推断

第 2 段　未变化：返回 None 不是删除

第一个分支返回 (None, Vec::new())。这里最容易读错：None 不是「把快照删掉」，而是「不更新快照，沿用已存的那份」。render_with() 在 L518-L522 明确处理了这一点：如果 section 返回 None，就从 stored 里取旧快照补上。已核实

为什么要这样设计？因为 render_diff 的返回值同时承担两个职责：告诉调用方「新快照是什么」，以及「要追加哪些片段」。未变化时，新快照和旧快照相同，没必要重复传递；但调用方仍然需要一份完整快照来落盘。用 None 表示「沿用」，用 Some 表示「更新」，就把两个职责分开了。推断

如果误把 None 当成删除，下一次比较就会把「已知」变成「未知」，进而触发一次多余的替换通知。状态机里最贵的错误，往往就是把「没变化」误读成「消失了」；前者只是少发一条消息，后者会让模型重新遵守一份已经作废的规则。推断

第 3 段　三态 previous：为什么需要 Unknown

PreviousSectionState 有三个值：Known、Unknown、Absent。Known 是「有持久化快照，可以逐字段比较」；Absent 是「确定没有」；Unknown 是「没有快照，但历史里可能有一条旧的规则片段」。已核实

Unknown 来自 render_history_diff() 的兜底：如果没有持久化快照，就去历史里找 matches_legacy_fragment 认得的片段；找到就返回 Unknown，找不到才返回 Absent。这样做的原因是兼容旧会话：旧版本可能把 AGENTS.md 直接拼进历史，没有快照；恢复后不能假设「没声明过」，否则会漏发替换通知，模型会同时遵守新旧两份规则。已核实

Unknown 被保守地当成「上次有」处理。代价是可能多发一条替换通知，收益是不会漏掉旧规则的作废声明。在规则这种「错了会持续犯错」的内容上，宁可多发一条，也不能让旧规则继续生效。推断

第 4 段　为什么变化时发全文，而不是发 diff

如果发的是行级 diff，模型需要先理解 diff 语法，再把补丁应用到历史里的旧文本上。这会引入三类风险：模型可能应用错位置；补丁可能因为上下文不匹配而失败；旧文本可能已经被压缩或截断，补丁失去锚点。发全文则把「应用补丁」变成「替换整段」，模型只需要理解一句自然语言通知。推断

代价是 token：AGENTS.md 上限 32 KiB，改一个标点也要重发整份。但这份成本只在变化的那一轮发生，而且后续轮次会把它当成普通历史，不再重复。相比「每轮都拼进系统提示」，这仍然是省的；相比「行级 diff」，它用一次性的全文成本换掉了正确性风险。推断

更关键的是，旧全文不能被删。Codex 的历史是追加式的，压缩之前不会回头改旧消息；即使想做行级 diff，也没有一个「原地替换」的操作可用。于是「替换通知 + 新全文」成了唯一自洽的选择：旧文本留在原处，新消息在语义上覆盖它。已核实

从模型视角看，这套语义也更自然。人读一份修订说明时，最关心的不是「第 3 行第 12 列改了什么」，而是「哪一版现在有效」。「这些规则替换之前全部」这句话直接回答了后者；行级 diff 回答的是前者，还需要读者自己推断后者。对语言模型来说，显式的「哪一版有效」比精确的「改了哪里」更不容易出错。推断

第 5 段　删除为什么要单独发通知

「当前无 + 上次有」这个分支只发一条 REMOVAL_NOTICE，不带任何正文。这条消息只声明「之前那条不再适用」，不重复新规则是什么。如果没有这条通知，模型会在历史里看到一份 AGENTS.md，然后继续遵守它——因为在它的视角里，没有任何东西撤销过这份规则。推断

这也是「追加式历史」的代价：删除一个状态，不能靠「不发送」来表达，必须靠一条显式的否定消息。所有基于追加日志的系统都会遇到这个问题：dsh 用「移除通知」，Grok Build 用 rewind marker，pi 用 section patch 的 null。表达「不存在」永远比表达「存在」更贵。推断

这里还有一个语义细节：移除通知不带 directory，正文只有一句「不再适用」。为什么不带目录？因为通知的作用是「作废之前所有同名规则」，而不是「作废某一个目录下的规则」。如果带上目录，模型可能会理解成「只有那个目录的规则失效，其他目录的仍然有效」，这与实际语义不符。Codex 选择让通知尽量短、尽量绝对，就是为了避免这种歧义。推断

第 6 段　缓存收益与粒度代价

未变化时零字节，这是缓存友好的理想状态。变化时只追加一条消息，前面的系统提示、工具定义、历史对话都不变，缓存从追加点之后失效，而不是从请求开头失效。对于一个聊了很长的会话，这意味着改一次 AGENTS.md 不会让整段对话重新计费。推断

但要小心一个方向性错误：这里的「缓存从追加点失效」指的是消息历史这一段。系统提示与工具定义在请求的最前面，它们本来就不受这条追加消息影响；真正被保住的，是「追加点之前的所有消息」。如果 AGENTS.md 是在系统提示里，改动会让整段系统提示失效，进而让整条消息历史都失去可复用的前缀。把规则从系统提示搬到历史尾部，最大的收益就在这里。推断

粒度代价也很明显：section 级差分只能回答「这一份规则变没变」，不能回答「哪一行变了」。如果一份 32 KiB 的 AGENTS.md 只改了一个字，重发的仍然是 32 KiB。要做得更细，就得引入行级 diff、补丁应用和锚点校验，复杂度和失败面都会上升。Codex 选择了「粗粒度、可证明正确」的那一端。推断

第 7 段　基线落盘：恢复时靠什么对齐

update_world_state() 在拿到 diff 后，立刻用新快照覆盖 world_state_baseline，并通过 world_state_item() 把「快照的 merge patch」写进 rollout。也就是说，磁盘上保存的不是「AGENTS.md 全文」，而是「这一轮状态相对上一轮的补丁」；恢复时按顺序应用补丁，就能重建基线。已核实

这里有一个容易被忽略的约束：快照不能序列化成 null。因为 merge patch 里的 null 表示删除，如果某个合法状态被序列化成 null，恢复时就会被当成「这一节不存在」，下一次比较从 Absent 开始，可能漏发替换通知。trait 的注释专门写了这一点（mod.rs#L306-L308）。已核实

如果基线丢了会怎样？render_history_diff() 会退回到历史里找旧片段：找到就 Unknown，找不到就 Absent。前者会多发一条替换通知，后者可能漏发。所以快照必须持久化：它是正确性的一部分。推断

再往前一步：section 的 ID 必须稳定。trait 的注释写明它会被写进 rollout，改动它等于让旧会话找不到自己的快照；add_section() 还会对重复 ID 直接 assert。这两条约束一起保证了「恢复时能对上号」。如果某个重构把 agents_md 改成 agents_md_v2，旧会话恢复时就会退到 Unknown，多发一条替换通知；如果改成和别的 section 重名，程序会直接崩溃，而不是悄悄错乱。已核实

把这段代码放在更大的背景里看，它其实是「让提示词具备数据库语义」的一次尝试：状态有主键（section ID）、有快照（当前值）、有变更日志（追加的片段）、有恢复机制（merge patch）。规则文件只是第一张表；工具目录、权限、环境都可以按同一套模式接入。理解了一张表，其他表只是换字段；差异在快照结构与通知文案，骨架不变，变的只是字段名与通知措辞。推断

✓要点小结

  • 差分单位是 section，不是行；变化时发新全文，不发补丁。
  • 四种状态组合：替换、直发、移除、静默；只有前三种会产生消息。
  • 未变化返回 None 表示「沿用旧快照」，不是删除。
  • Unknown 是旧会话的保守兜底：宁可多发替换，不漏作废。
  • 删除必须显式通知，因为追加式历史不会回头删掉旧规则。

表注：来源为各 agent 固定提交的源码与官方文档（Codex 提交 76ed3b4，dsh 为同仓文档口径，pi 提交 b45e0eb，opencode v1 tag v1.19.0，Grok Build 为源码 + 用户手册）。

第一个对照是「差分发生在哪一层」。Codex 与 dsh 都在「规则文件」这一层做状态对账，变化时发的是文件级的新全文/移除通知；pi 在「系统提示 section」这一层做补丁，规则只是众多 section 之一；opencode 与 Grok 干脆不做差分，每轮重建整段。层次越靠上，差分的收益越大，但实现也越依赖「历史是否可追加」这个前提。

第二个对照是「删除是否可表达」。Codex 用一条独立通知，pi 用 null 补丁，dsh 用移除通知，opencode 与 Grok 靠「下一次重建时自然消失」。前三种都需要模型理解「否定」，后两种不需要，但代价是每轮重建整段提示，缓存无法只失效尾部。删除语义越显式，缓存越友好，模型的理解负担也越重。

第三个对照是「体积上限」。Codex 有 32 KiB 上限，超出从尾部截断；dsh 有整条基线消息的字节预算，超预算先省略更宽的文件、再截断最具体的文件；pi、opencode、Grok 在本快照里都没有找到单文件硬上限。上限不只影响成本，也影响差分的粒度：有上限的系统更倾向于「整份替换」，因为文本本来就被截断过，做行级 diff 的锚点不稳定。推断

把这三条轴放在一起，可以看出一个规律：越靠近「系统提示」的实现，越倾向于每次全量；越靠近「历史消息」的实现，越倾向于差分。原因不在设计品味，而在成本结构。系统提示是请求的前缀，改一个字就要重算整段；历史消息是尾部，追加一条只影响新增部分。Codex 把规则搬进历史，才换来了差分的可能；opencode 把规则留在 system 字符串里，就只能每轮重建。推断

第四个对照是「谁负责发现变化」。Codex 每轮由宿主重新读取 AGENTS.md，再把结果交给 section 比较；dsh 只在 read/write/edit 触达更深目录时才把新规则带进下一次请求，不是持续 watch；opencode 在 read 工具输出里就近追加规则；Grok 在每轮开始时全量加载。前三者都在「变化发生的那一刻」或「下一次请求前」处理，后两者把成本摊到每轮。选择哪种，取决于你更怕「规则陈旧」还是更怕「每轮开销」。

06 · 思考题

三道题，从状态机到设计

Q1

AGENTS.md 从 A 改成 B，下一轮又改回 A。假设两轮之间没有其他变化，Codex 会发几条通知？模型最终看到的是 A 还是 B？旧的两份文本还在历史里吗？

提示（不给答案）

每次比较的基线是「上一轮的快照」，不是「最初的状态」。A→B 时当前是 B、上次是 A，走「有 → 有」；B→A 时当前是 A、上次是 B，还是「有 → 有」。

历史是追加式的：T1 的 A、T2 的替换通知+B、T3 的替换通知+A 会同时存在。模型要靠最后一条通知来判断哪份有效。

Q2

恢复一个旧会话时没有持久化快照，历史里也找不到 AGENTS.md 片段，但磁盘上现在有一份 AGENTS.md。下一轮会发生什么？如果历史里其实有一份旧片段，只是匹配器没认出来，又会发生什么？

提示（不给答案）

先看 render_history_diff() 的三分支：有快照 → Known；没快照但历史里有 legacy 片段 → Unknown；两者都没有 → Absent。

Absent + 当前有 走「无 → 有」，直接发全文，不带替换通知；Unknown + 当前有 走「有 → 有」，带替换通知。两种情况模型最终都看到新全文，差别在于有没有显式作废旧规则。哪种更安全？

Q3

产品经理要求「只发改动的那几行，省 token」。你会怎么改 render_diff？改完之后，压缩、恢复、缓存三条路径各会出什么问题？

提示（不给答案）

行级 diff 需要一个稳定的锚点。压缩会把旧消息换掉，锚点可能消失；恢复会重放历史，补丁的应用顺序必须严格；缓存要求补丁的字节稳定，而 diff 算法很容易因为上下文行数变化而产生不同输出。

更根本的问题：模型不是 patch 工具。它可以把「替换全部旧规则」执行得很稳，但把「第 12 行到第 14 行改成……」执行错位的概率高得多。省下的 token 可能被一次错误理解的代价抵消。

如果一定要做，比较稳妥的折中是「按小节替换」：把 AGENTS.md 拆成若干具名小节，变化时只发「某一节的新全文 + 该节名」，而不是发行号补丁。这样既有差分收益，又保留「整段替换」的语义；代价是上游要先把文件结构化，纯文本规则做不到。
