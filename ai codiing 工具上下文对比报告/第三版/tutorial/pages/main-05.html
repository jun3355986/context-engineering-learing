Token 计量与可视化

“还剩多少”是所有减量动作的前提。麻烦在于，同一段会话在不同口径下会给出三个不同的数字：服务端回报的 usage、客户端按字符除以四的估算、以及 /context 里按类别逐项计数的结果。理解这三个数字的来历，比记住任何一个阈值都重要。

  • 约 16 分钟
  • 1 个交互
  • L2 → L3

读完你能做到

  1. 给定一次会话，分别用服务端 usage 与 chars/4 估算占用，并说出差值可能来自哪五类原因。
  2. 解释“输出预留”和“触发阈值”为什么要分成两个数，以及比例制与绝对留白制的代价。
  3. 看一张 /context 风格的拆解图，指出哪几段是实测、哪几段是估算、哪一段只是缓冲。

01 · 三个数字

“到底是 62% 还是 81%？”

下午三点四十，你在修一个导出模块。屏幕底部的状态栏写着 62%，你判断还能再跑两轮测试。第二轮结束，Agent 突然开始压缩历史，把前面读过的四个文件全换成了摘要。你翻回去看：压缩前最后一次请求的 usage 是 158,400，窗口 200,000，也就是 79.2%。62% 是客户端自己按字符估算的，它少算了工具定义和一段 JSON。

这不是某个 agent 的 bug，而是“计量”这件事本身有三个层次：

  • 服务端 usage：模型服务在响应里回报的 input / output / cache_read / cache_write。它是计费与真实窗口占用的唯一权威，但只在一次请求结束之后才更新。
  • 本地估算：客户端把还没发出去的消息按“字符数 ÷ 4”折算成 token。它随时可用，但对中文、代码、JSON 和图片都会偏。
  • 分类计数：/context 这类视图把系统提示、工具定义、规则文件、历史消息逐类数一遍。它最接近“钱花在哪”，但通常要额外调用计数 API，或者依赖一份快照。

减量策略的可信度，上限就是计量的可信度。

如果计量偏低，压缩会在你以为还早的时候突然触发；如果偏高，你会提前压缩，白白丢掉还没用上的原文。更隐蔽的是“口径不一致”：状态栏按估算显示 62%，压缩器按实测判定 81%，两个模块各自都对，合起来就是用户看不懂的行为。

场景 · 同一个会话，三个百分比

第 12 轮，状态栏 62%，/context 显示 71%，压缩器内部判定 81%。差别不在算术，而在“算不算工具定义”“算不算缓存读”“算不算还没发出去的尾随消息”。本章就是把这三个数拆开。

先记住一个判断顺序：能拿到服务端 usage 时，以它为准；拿不到时，用估算，并且明确知道估算会往哪个方向偏；两者都有时，取较大值，而不是平均值。后者是 oh-my-pi 的选择，理由在 2.5 节解释。

02 · Codex 主线

一把尺子，两次读数

Codex 没有 /context 命令，也没有分类占用条。它的计量只有一条链路：上一次服务端 usage + 此后本地新增的估算增量，再用这个数去比两条阈值线。代码提交固定为 76ed3b4。这条链路简单到可以在一个函数里读完，但也因此暴露了“没有可视化”的全部代价。

2.1 混合计量：为什么不能只用一种数

Codex 的 get_total_token_usage 取上一次响应的 usage.total_tokens，加上“最后一条模型输出之后新增消息”的估算值。context_window.rs#L83-L110 已核实 这个设计要解决两个失败模式：

  • 只用 usage 会滞后。一次工具调用可能返回 40k 字符，下一次模型请求还没发出，usage 仍然停留在上一轮。此时如果按 usage 判断，压缩器会认为“还很空”，直到新请求被服务端拒绝。
  • 只用估算会漂移。估算按 ceil(字节数 / 4) 计算，truncate.rs#L89-L98 已核实 对英文散文接近，对中文、缩进很深的代码、重复键名的 JSON 都会偏。连续几十轮之后，误差会累积成一个可观的数字。

混合计量的本质是“用实测校准、用估算补盲区”。它假设两者之间的偏差在短时间内不会剧烈变化，因此“上次真值 + 这段时间的增量估算”比“上次真值”或“全量重估”都更接近现实。代价是它有一个隐含假设：上一次 usage 对应的历史，与当前历史共享同一个前缀。如果中间发生过压缩、切模型或历史重排，这个假设就不成立，必须整段重估。

pi 和 opencode v2 都把这条规则写得更显式。pi 在发现最近一次 context_edit 或 compaction 晚于 usage 来源条目时，会丢弃旧 usage、对投影全量重估，避免“压缩后仍用压缩前的大 usage 误触发”。compaction.ts#L140-L262 已核实 opencode v2 则要求“最近一次测量锚点晚于最后一个检查点”，否则不自动触发。compaction.ts#L900-L923 已核实

2.2 两条线：物理上限与策略上限

Codex 用同一个“当前用量”去比两条线。第一条是整段线：窗口 × 95%，由 effective_context_window_percent 控制，默认 95。openai_models.rs#L393-L395 已核实 第二条是范围线：默认取 min(模型声明的 auto_compact_token_limit, 窗口 × 90%)，可由配置覆盖。openai_models.rs#L517-L540 已核实 任意一条到线就触发。

范围线还有一个容易忽略的开关：auto_compact_token_limit_scope，取 Total 时比全部材料，取 BodyAfterPrefix 时只比“首轮固定前缀之后新增的部分”。context_window.rs#L60-L81 已核实 后者是为大系统提示、大工具表准备的：前缀再大，也不该把可用于对话的额度吃掉。

为什么是两条线，而不是一条。整段线是物理上限，再往前走 API 会直接拒绝；范围线是策略上限，它要在“还能再跑一轮模型 + 一次工具调用”的地方停下。两者的调整频率也不同：整段线跟着模型窗口走，范围线跟着任务类型走。代价是配置面变大。如果模型元数据里的 auto_compact_token_limit 不准，范围线就会过早或过晚触发，而用户只看到一个笼统的“自动压缩”。

2.3 输出预留：Codex 把它藏进了百分比里

“输出预留”指的是：窗口由输入和输出共享，必须给模型本次要生成的 token 留出空间，否则输入刚好占满时，请求会因为“没有位置放输出”而失败。不同 agent 处理方式差别很大：

  • Codex 没有独立的输出预留字段，95% 这条线事实上充当了预留：5% 的窗口留给输出与协议开销。推断1
  • Claude Code 显式先减：有效窗口 = 模型窗口 − min(模型最大输出, 20_000)，自动压缩线再减 13_000，阻塞线再减 3_000。autoCompact.ts#L28-L49 源码 v2.1.88
  • DeepSeek Harness 用两个显式量：输出预留 O 与 65,536 headroom，阈值取 min(W × 0.8, W − O − B)。config.ts#L153-L204 已核实
  • Grok Build 的源码里没有“输出预留”这个概念，阈值只按 total_tokens / context_window 计算。已核实

比例制的好处是跨模型自洽：换一个 1M 窗口的模型，5% 自动变成 50k，不需要改配置。绝对留白制的好处是可解释：你能明确算出“这一轮最多能生成 20k”。代价分别是：比例制在超大窗口上留得过多，在小窗口上留得过少；绝对制在窗口变化时需要重新调参，否则会过度保守。Claude Code 的选择是两者叠加——先按“最大输出不超过 20k”封顶，再减一个固定的 13k 缓冲，等于同时承认“输出有上限”和“压缩本身要花时间”。

?动动脑

窗口 200k，Claude Code 的最大输出是 32k。它的自动压缩线在哪？如果换成 1M 窗口、最大输出仍是 32k，这条线会移动多少？

提示：先算 min(32k, 20k)，再减 13k。第二个问题里，20k 封顶不变，所以移动的是窗口本身。

2.4 没有 /context：Codex 的可见性缺口

Codex 不提供 /context 之类的分项视图。用量以事件形式上报给 TUI，具体呈现方式在本快照里没有找到确证。context_window.rs#L83-L110 待核实2 这意味着用户能看到“是否接近上限”，但看不到“系统提示占了多少、工具定义占了多少”。

这不是实现疏漏，而是一个取舍：分类计数需要把每一类内容单独送进 tokenizer 或计数 API。Codex 的请求体是 Responses API 形状，工具定义、指令、历史都在同一个 input 数组的不同位置，逐类拆分的成本不低；而它已经有“实测 + 增量”这条足够准的链路，再做一个分类视图，收益主要在“解释”而不在“决策”。

代价很具体：当上下文异常膨胀时，用户无法判断是工具输出、规则文件还是工具定义导致的。只能靠猜，或者手动 /compact。这也是为什么后面几家的 /context 都把“工具定义”单独列一行——它常常是那个被忽略的大块。

2.5 窗口从哪来，能不能换

Codex 的窗口大小来自模型元数据，随模型切换而变化；本快照里没有找到“用户单独调小窗口”的通用开关。推断3 这一点和 pi 类似：pi 直接取 model.contextWindow，未发现用户可单独切换窗口的设置，换窗口只能换模型。compaction.ts#L140-L262 已核实

反过来，Grok Build 与 Claude Code 都把“窗口”做成了一个可操作的对象。Grok 的 /context-window 只在模型声明了多个窗口时出现，接受 500k 这类短标签或原始 token 数，会话级生效；底层复用切换模型的路径，所以切模型族会立即触发一次压缩，单纯调小窗口则在下一次采样前检查。context_window.rs#L10-L99 已核实 Claude Code 则是模型名带 [1m] 或带 beta header 时用 1M 窗口；CLAUDE_CODE_AUTO_COMPACT_WINDOW 只能把窗口调小，CLAUDE_AUTOCOMPACT_PCT_OVERRIDE 也只能调低百分比。autoCompact.ts#L62-L91 源码 v2.1.88

为什么“只能调小”是一个反复出现的设计。调大窗口意味着真实请求可能超过服务端允许的上限，客户端无法保证安全；调小则是保守方向，最坏结果是提前压缩。代价是用户无法用“假装窗口更大”来测试长上下文策略，只能换模型。对做评测的人是麻烦，对普通用户是保护。

2.6 估算的误差从哪里来

chars/4 是一个“平均而言成立”的常数，误差方向取决于内容：

  • 中文：一个汉字通常接近一个 token，但只算 0.25 个（4 字节 ÷ 4）。估算会偏低，在中文为主的会话里偏差最大。
  • 代码与 JSON：大量短标识符、标点、重复键名，tokenizer 的实际切分比 4 字节/token 更碎。估算也偏低，但幅度小于中文。
  • 英文散文：接近 4 字节/token，误差最小。
  • 图片与音频：按字节折算几乎没有意义。Codex 对音频单独估算 token，不按字节折算；output-truncation/lib.rs#L160-L175 已核实 其他工具各有自己的常数（第 16 章）。
  • 缓存 token：算不算 cache_read 会直接改变分子。Claude Code 的计数把 input + cache_creation + cache_read + output 全部相加，tokens.ts#L226-L261 源码 v2.1.88 而有的实现只取 input。

Codex 对这个偏差的处理不是“修正公式”，而是“留安全垫”：95% 与 90% 两条线都留了余量，截断时还会把预算乘 1.2 作为序列化余量。output-truncation/lib.rs#L17-L34 已核实 这是工程上常见的选择：与其追求一个精确的估算器，不如承认它会错，并让阈值足够保守。

误差方向是【推断】：本教程没有用同一批语料跑过 Codex 的分词器与 chars/4 的对照，只根据字符编码与常见 tokenizer 的行为推断。4

教学模型：预留固定按窗口的 15% 计，触发线固定在 85%，已用的四段为示意值，不是任何 agent 的真实默认值。真实工具里预留与触发线是两个独立参数。

读这张图分三步。第一步看已用总高：它决定“现在离触发还有多远”。第二步看哪一段最厚：历史通常最厚，但在长会话刚开始时，工具定义往往才是第二大块。第三步看预留区：它不是“已用”，而是“不能用”，所以真正可用的空间是窗口减去预留，再减去已用。

口径要分开标：系统提示、工具定义、规则这三段通常只能估算，因为它们没有单独的服务端 usage；历史段可以用“最近一次实测 + 尾随增量”；预留段既不是实测也不是估算，而是一个策略参数。把三者混在一个百分比里，就会得到本章开头那种“62% 还是 81%”的争执。

当心 · 分类视图也会骗人

Claude Code 的 /context 用 count_tokens API 逐类计数，API 不可用时回退到 Haiku 计数，并且每次带工具的计数调用都有 500 token 的前导开销，逐工具计数时要扣掉。analyzeContext.ts#L918-L1000 源码 v2.1.88 这意味着分类数字之间有±几百 token 的固定偏差，别拿它去对账到个位。

3.1 五类误差，分别影响哪一段

第一类，分词器差异。影响所有“估算”段，尤其是中文与代码。它不改变历史段的实测部分，但会改变尾随增量。

第二类，重复计数。同一个工具定义可能既出现在“工具定义”里，又作为系统提示的一部分被计入。Grok 的处理最直白：工具、Skills、MCP、workflows、AGENTS.md 单独列在“Already counted above”区，并明确标注已包含在上面四项里，不重复计入。context_info.rs#L312-L360 已核实

第三类，缓存 token 的口径。缓存读通常比新输入便宜，但它仍然占用窗口。把 cache_read 排除在“已用”之外，会得到一个乐观得多的百分比。

第四类，多模态。图片按张、按 tile、按固定 token 数或按字节计，四家四种做法。一张 2 MB 的截图在 A 家是 765 token，在 B 家可能是 1,500，在 C 家按请求体字节算。分类视图若把图片算进“历史”，偏差会很大。

第五类，编排开销。有些 provider 会回报“可计费但不回放进对话前缀”的编排 token。oh-my-pi 在计算上下文占用时会把这部分减掉，因为算进去会虚高触发。context-usage-runtime.ts#L21-L47 已核实 这一步在只看“账单”的视图里通常不会做。

3.2 换窗口时，什么会动，什么不会

把窗口从 200k 换到 1M，已用的 132.4k 一点没变，变的是三样东西：预留从 30k 变成 150k，触发线从 170k 变成 850k，空闲从 37.6k 变成 717.6k。换句话说，换窗口不会让历史变短，只会让“还早”变得更早。

这正是“可切换窗口”最容易误导人的地方。用户看到空闲变多，以为可以塞进更多东西；但真正决定模型能不能用好的是有效上下文，而不是名义窗口。第 4 章讲过 context rot：窗口越大，中间位置的信息越容易被忽略。1M 窗口给了你更多“装得下”的空间，不等于给了你更多“用得好”的空间。

也因此，阈值必须和窗口联动，而不是写死一个绝对 token 数。Grok 的阈值解析有六级：环境变量、用户模型级、用户会话级、远端 per-model、远端全局、常量 85，而且随模型目录下发的值优先于常量（grok-4.6 目录值是 80）。compaction.rs#L36-L89 已核实 这六级的存在说明一件事：阈值不是一个“正确值”，而是一个随模型、随任务、随用户偏好变化的策略参数。

04 · 七个编码智能体

七种量法，七种可见性

Codex 的链路已经在主线里拆过。下面七个 agent 各有一个弹窗，重点看三件事：它信谁（服务端 usage、估算、还是两者取大）、它怎么算预留、它让用户看到什么。这三件事决定了同一个会话在七个 agent 里会显示七个不同的百分比。

06 · 设计取舍

为什么没有一个百分比

下面五组取舍，是“同一段会话显示不同数字”背后的真正分歧。每组给出两种路线、各自在想什么，以及代价。本节不重复 permalink，统一见第 05 节表格与各 agent 弹窗。

取舍一：只信实测、只信估算，还是混合

只信实测（opencode v1 的触发）最准确，但有一个致命缺口：两次请求之间新增的工具结果没有读数，必须等到下一次请求才知道超了。opencode v1 接受了这个缺口，代价是“没有 provider 回报之前不会自动压缩”，第一次溢出只能靠错误驱动。overflow.ts#L8-L34 已核实

只信估算简单、随时可用，但误差会累积，中文与代码场景偏差最大。没有哪家完全这么做，但很多 agent 在“尾随增量”这一段实际上就是纯估算。

混合（Codex、Claude Code、pi、opencode v2、Grok、dsh）是主流。分歧在“两者不一致时怎么办”：oh-my-pi 取较大值，理由是 provider 报的 prompt token 可能因为请求被压缩或混淆而偏小，只信它会让真实历史无界增长。compaction.ts#L316-L354 已核实 取较大值是保守方向：宁可早压，不可晚炸。

代价：取较大值会让估算偏高时频繁误触发；取最近一次实测则可能在工具结果堆积时漏判。混合方案还必须处理“锚点失效”（压缩、切模型、历史重排），否则会拿一个不再对应的真值去加增量。

取舍二：阈值按比例，还是按绝对留白

比例派（Codex 95% / 90%、omp 15%、opencode v2 10%、dsh 0.8、Grok 85 / 80）跨模型自洽，换窗口不用改配置。绝对派（Claude Code 的 13k、dsh 的 65,536 headroom）可解释、可预算：你能说清“这 13k 是留给压缩请求本身的”。

真实系统几乎都是两者叠加。Claude Code 先按比例算有效窗口，再减绝对缓冲；dsh 同时取 0.8W 与 W − O − B 的较小值，等于“比例上限”和“绝对留白”谁更保守听谁的。

代价：比例制在 1M 窗口上会留出 150k，压缩后仍然很空，用户会觉得“压了个寂寞”；绝对制在 32k 小窗口上可能一上来就触发，因为 65k headroom 比窗口还大。dsh 的 min() 正是为了防止后者，但它也意味着小窗口下比例项永远不生效。

取舍三：做分类视图，还是只给一个总数

分类派（Claude Code、Grok、dsh）愿意为“解释”付成本。Claude Code 用 count_tokens API 逐类计数，不可用时回退到小模型；Grok 用会话快照字段拼四段，并把工具、技能、MCP 单独列在“已计入”区；dsh 用重放日志算出 systemTokens / toolsTokens / messageTokens 三个投影。

总数派（Codex、pi、opencode）只给“用了多少 / 还剩多少”。实现便宜、读数快，但用户无法定位膨胀源。

代价：分类视图要么多花一次 API 调用（Claude Code），要么依赖一份可能过时的快照（Grok），要么需要重放整段日志（dsh）。三者都可能与“真正发出去的那次请求”有偏差。总数派则把诊断成本转嫁给用户：你只知道超了，不知道为什么。

取舍四：窗口可切换，还是锁死

可切换（Grok 的 /context-window、Claude Code 的 1M beta）让用户能在“更大窗口”和“更稳行为”之间选。Grok 甚至允许传 500k 这种短标签，并在切模型族时立即压缩，避免把旧历史硬塞进新窗口。

锁死（Codex、pi、dsh）把窗口当成模型属性，用户只能换模型。实现简单，也不会出现“用户把窗口调大后请求被服务端拒绝”的尴尬。

代价：可切换意味着客户端要维护“声明窗口”和“真实可用窗口”两套数，还要处理切换瞬间的历史兼容（压缩、重排、缓存失效）。锁死则让“用大窗口跑长任务”变成换模型的副作用，用户很难做细粒度实验。Claude Code 的折中是“只能调小”：保留了实验能力，去掉了越界的风险。

取舍五：输出预留显式，还是隐含在百分比里

显式（Claude Code、dsh、opencode v1/v2）把“给输出留多少”写成独立参数。好处是能单独调：任务需要长输出时调大预留，需要长输入时调小。坏处是参数变多，且预留与压缩阈值会互相挤压——预留太大，阈值就被推到窗口很靠前的位置。

隐含（Codex 的 95%、Grok 完全不留）把预留折进一个百分比。配置面小，但用户无法回答“为什么 200k 窗口只能用 190k”。Grok 的做法最激进：源码里根本没有输出预留，阈值只按 total_tokens / context_window 算，等于假设服务端会自行处理输出空间。

代价：显式预留在小窗口上很容易把可用空间压到不可用；隐含预留则可能在“输入刚好满、输出又很长”的请求上直接失败。前者的失败是“压缩太早”，后者的失败是“请求被拒”，后者更难恢复。

还有一组横切的取舍：计量频率。每次工具调用后重算（Codex、omp）最及时，但每次都要遍历新增消息；只在请求前算一次（opencode v1）最省，但会漏掉请求之间的增长；重放整段日志（dsh）最可复现，但成本随会话长度线性增长。频率越高，越接近真实；频率越低，越容易被一次大输出打穿。

07 · 小测验

三道题，检验你会不会读数

Q1

窗口 200k，Claude Code 的最大输出 32k。它的自动压缩线是多少？如果把窗口换成 1M、最大输出不变，这条线移动到哪里？

解析

200k 时：有效窗口 = 200,000 − min(32,000, 20,000) = 180,000；自动压缩线 = 180,000 − 13,000 = 167,000，也就是名义窗口的 83.5%。1M 时：有效窗口 = 1,000,000 − 20,000 = 980,000；压缩线 = 967,000，约 96.7%。注意封顶是 20k 而不是 32k，所以窗口越大，预留占比越小，压缩线越贴近窗口顶端。见 2.3 输出预留。

Q2

一段中文为主的会话，服务端 usage 是 158k，客户端按 chars/4 算是 124k。哪个更可信？为什么差这么多？如果压缩器只信估算，会发生什么？

解析

服务端 usage 更可信。中文一个汉字通常接近一个 token，但按 UTF-8 是 3 字节、按 chars/4 只算 0.75 个 token，估算系统性偏低；再加上工具定义与 JSON 的符号密度，34k 的差距是合理的。如果压缩器只信估算，它会认为还有 76k 空间，实际只剩 42k，结果是在下一两次工具调用后直接被服务端拒绝。见 2.6 误差来源 与 3.1 五类误差。

Q3

把窗口从 200k 切到 1M，已用 132.4k 不变。哪些数字会变？为什么“空闲变多”不等于“能装更多有效信息”？

解析

会变的是预留（15% 从 30k 到 150k）、触发线（170k 到 850k）、空闲（37.6k 到 717.6k）与百分比（66.2% 到 13.2%）。不会变的是已用的四段内容。空闲变多只代表“名义窗口还有位置”，不代表模型能有效利用中间位置的信息——第 4 章的 context rot 与 lost in the middle 在更大窗口上依然成立。可以在第 03 节演示里逐个切换验证。

v2 把 v1 的“只看上一轮”改成“锚点 + 之后逐条累加”：estimatePrompt 找到最近一条本 provider 回报过 usage 的 assistant 消息作锚点，之后的消息用 round(len/4) 逐条估算；measured 是 input + cache.read + cache.write + output + reasoning。触发上限 calculateCeiling 用 窗口 − max(10% 窗口, 16,000)，窗口未知（≤0）时返回 +∞，永不自动触发。它还有一个额外条件：最近一次测量锚点必须晚于最后一个检查点，否则不压——因为加密的原生窗口在本地估算为 0，必须等 provider 回报一次真实用量。媒体按固定值估算：图片 1,500、PDF 2,000。

关键参数与默认值
ESTIMATE_ERROR = 0.15；预留 max(10%W, 16_000)；未知窗口 200_000 只用于给压缩请求定预算；输出上限动态按 窗口 − 已用 − 估算×1.15 计算；OUTPUT_TOKEN_FALLBACK = 32_000。已核实
设计意图
锚点法比“只看上一轮 total”更稳：它保留了锚点之前的实测，不把整段重估；同时用 1.15 的放大系数给输出留余量。代价是锚点之前的媒体与图片预算存在盲区，且“锚点必须晚于检查点”会让刚压缩完的会话暂时不触发。推断

Grok Build

Grok Build 的 /context 是七家里最接近“教科书拆解”的：四段分别是 System prompt（系统消息估算）、Messages（所有非 system 项）、Reasoning/overhead（used − system − messages，把推理与缓存差异一律塞进 overhead）、Free（total − used）；四者用三级 min() 逐级夹紧，保证不越界。工具定义、Skills、MCP、workflows、AGENTS.md 单独列在“Already counted above”区，并明确标注已包含在上面四项里，不重复计入。阈值解析有六级，常量 85，grok-4.6 的目录值是 80。窗口可以切换：/context-window 只在模型声明多个窗口时出现，接受 500k 这类短标签，会话级生效。

关键参数与默认值
BYTES_PER_TOKEN = 4；IMAGE_TOKEN_ESTIMATE = 765；阈值常量 85，grok-4.6 目录 80；grok-4.6 窗口 500_000；源码中没有输出预留；/context-window 需模型声明多窗口。已核实
设计意图
把“无法归类的部分”显式命名成 overhead，而不是硬塞进某一类，从而让四段之和永远自洽。min() 夹紧是为“估算值大于实测值”的异常输入兜底。代价是 overhead 变成一个黑箱，用户不知道里面是推理、缓存还是计费差异。推断

DeepSeek Harness

DeepSeek Harness 的计量服务是 ctx.tokenMeter，它重放持久会话日志来定价，不调模型、可复现。估算用固定密度：4 字符/token，每个 content block 加 4 的结构开销，每条消息再加 4 的角色框架开销；图片在路由声明了视觉计价时用路由价，否则按结构 JSON 估。measure(session) 返回 totalTokens、surfaceTokens 与逐节点明细；只有当“最新成功调用的规范化请求 envelope”与当前被测 envelope 完全一致时，才复用 provider 上报用量，否则整段重估。UI 是 composer 旁的圆环加展开面板，没有 /context 斜杠命令。

关键参数与默认值
4 字符/token；block / message 各 +4；阈值 floor(min(W × 0.8, W − O − 65,536))；保留 floor((W − O) × 0.16)；O 取 envelope maxTokens → 适配器默认 → 0；三个投影键 tokenUsage / contextPressure / contextBreakdown。已核实
设计意图
把“计量”做成纯函数：同一份日志重放两次必须得到同一个数，方便 A/B 与回归。代价是每次测量都要遍历日志，长会话下成本可观；同时“envelope 一致才复用 usage”很严格，稍有格式差异就整段重估。推断
