压缩：把历史换成摘要

窗口快满时，Agent 不会“忘记”，它会把前面的对话交给模型写成一份交接摘要，再删掉原文。真正难的不是写摘要，而是三个决定：什么时候压、从哪里切、切完还留什么。

  • 第 8 类
  • 约 28 分钟
  • 2 个交互
  • L2 → L3

读完你能做到

  1. 给定窗口、触发阈值、输出预留和保留量，指出压缩会在哪条消息处触发、切点落在哪里。
  2. 判断一个切点是否合法，并解释为什么工具调用与结果必须整对保留。
  3. 说出“只留摘要”和“压缩后重附文件与技能”两种路线的代价，并按场景选一种。

01 · 先看清这笔交易

“我第一句话就说过了啊”

下午四点，你让 Agent 重构导出模块。它读了 20 个文件、跑了 3 次测试、改了 4 个调用方。第 40 轮，它突然把 public API 改了。你翻回去看：第 3 轮你明确说过“不要动 public API”。它当时还复述了一遍。

这不是模型“没注意”，而是那段话已经不在它眼前了。上下文窗口装不下 40 轮工具输出，Agent 必须做一次减法。这里的减法有两种，代价完全不同：

  • 裁剪（trimming）：不调用模型，只改变“模型能看到的投影”。原文还在，随时可以还原。这是第 14 章的主题。
  • 压缩（compaction）：调用模型，把一段历史写成摘要，再用摘要替换原文。原文通常只留在会话日志里，模型看到的是“另一个模型写的交接笔记”。

压缩的本质是一笔交易：用“信息”和“控制权”，换“空间”。

信息指原文里的细节：文件内容、diff、测试输出的具体行号。控制权指你还能不能精确地告诉模型“回到第 12 轮的状态”。摘要一旦生成，这两样都变少了。所以评价一个压缩实现，不能只看“压完还剩多少 token”，还要看它决定保留什么、丢弃什么、以及切点是否合法。

后面所有的实现差异，都可以放回这三个问题里看：何时触发（阈值与时机）、切在哪里（保留谁、丢弃谁、如何保证边界合法）、切完怎么重建（摘要怎么放、要不要重附文件与技能）。

压缩不是免费的

压缩本身是一次完整的模型请求：要把待压缩的历史再发一遍，还要生成摘要。它既花 token，也花时间；如果实现把摘要插在历史开头，还会让 prompt cache 的前缀失效。更糟的是，压缩请求自己也可能超窗——这是第 21 章“失败恢复”要处理的问题。

02 · Codex 主线

一条压缩链路的五个决定

Codex 的压缩分两条实现：本地压缩（compact.rs，客户端把摘要写进历史）和远端 v2 压缩（compact_remote_v2.rs，服务端返回替换历史）。本节以本地链路为主，因为它把“保留谁”写得最清楚；远端只在预算不同的地方单独标注。提交固定为 76ed3b4。

2.1 触发：两条阈值线，三种时机

Codex 先用两把尺子量同一段历史。当前用量 = 上一次服务端返回的 usage.total_tokens + 之后本地新增消息的估算增量。第一条是整段线：窗口 × 95%（effective_context_window_percent 默认 95，openai_models.rs#L393-L395）。第二条是范围线：默认取 min(模型声明的 auto_compact_token_limit, 窗口 × 90%)，配置项可以覆盖。openai_models.rs#L526-L540任意一条到线，就判定需要压缩。context_window.rs#L83-L110 已核实

范围线还分两种口径：Total 比全部材料，BodyAfterPrefix 只比“首轮固定前缀之后新增的部分”。后者是为大系统提示、大工具表准备的：前缀再大，也不该把可用于对话的额度吃掉。context_window.rs#L60-L81 已核实

到线之后，Codex 在三个位置真正发起压缩：

  • 轮前：新输入写入之前先检查，适合“这一轮一开始就会超”的情况。turn.rs#L193-L200 本快照还留了一条 TODO：轮前检查没有把“待写入的新输入”估算进去，所以刚好卡线时，可能在新输入落库后才越线。turn.rs#L189-L192 已核实
  • 轮中：模型要求继续（needs_follow_up）、且本轮已经到线时压缩。它不会在“这一轮马上要结束”时压，因为没有下一次模型调用，压了也用不上。turn.rs#L654-L686
  • 轮后：model_post_turn_compact_threshold_percent，默认 0，即关闭。turn.rs#L779-L800

还有两条不常被提到的路径：切换模型时，如果新旧模型的压缩兼容哈希不同、或新模型窗口更小，Codex 会先用旧模型压一次，避免把旧历史硬塞进新窗口；手动 /compact 则走独立任务。turn.rs#L1412-L1452 已核实 后台/投机压缩是开发中特性，默认关闭，阈值 65%，失败只记日志。config/mod.rs#L225

为什么是两条线。整段线是物理上限：再往前走，API 会直接拒绝。范围线是策略上限：它要在“还能再跑一轮模型 + 一次工具调用”的地方停下，而不是等撞墙。两条线分开，才能让“硬失败”和“提前收缩”用不同的旋钮调。代价是配置面变大：模型元数据里的 auto_compact_token_limit 一旦不准，范围线就会过早或过晚触发。

2.2 候选：20k 预算，只收真实用户消息

真正决定“压缩后还记得什么”的，不是摘要模板，而是候选选择。Codex 本地压缩的规则是：只把真实用户消息纳入候选，排除压缩摘要自身（避免摘要套摘要），也排除 FINAL_ANSWER 这类代理消息；预算 COMPACT_USER_MESSAGE_MAX_TOKENS = 20_000，从最新往回累加，放不下就停。compact.rs#L622-L639 compact.rs#L715-L805 已核实

最容易被忽略的边界是“最新一条自己就放不下”。这时 Codex 不会跳过它，而是把它的文本截到剩余预算，然后停止；图片和音频不会跟着进保留段。compact.rs#L739-L802 已核实 这解释了为什么压缩后模型有时会“记得任务、忘了任务里的细节”：细节在最新那条长指令的后半段，被截掉了。

为什么只收用户消息。用户消息是唯一不可再生的“意图”：模型可以重新读文件、重新跑测试，但无法重新猜出你当时为什么说“别动 public API”。助手消息本来就在被摘要；工具结果体积最大、可重新获取；把它们放进 20k 保留段，性价比最低。代价是压缩后模型手里没有精确的代码和 diff，必须重新读文件，慢而且可能读到已经变化的内容。

估算口径是 ceil(字节数 / 4)，不是分词器实测。对中文、代码和 JSON，这个比例会偏。truncate.rs#L89-L98 已核实 偏差方向取决于内容，本教程不把它当成精确值 推断。

Q你可能会问

问：为什么不把工具结果也摘要进去？反正都是模型写。

答：摘要模型看到的也是同一段历史，工具结果往往占 70% 以上的 token，却只贡献少量决策。Codex 把 20k 全留给用户原话，是在赌“意图比日志更难重建”。这个赌注在“需要精确行号”的任务上会输，所以压缩后要重新读文件。

2.3 摘要：一次不带工具的独立请求

压缩请求复用当前历史，在末尾追加 SUMMARIZATION_PROMPT；请求的 tools 为空，避免模型在“写摘要”时顺手调用工具。模板只有 9 行，要四样东西：进度与关键决策、重要上下文与用户偏好、还没做完的事、继续工作所需的关键数据与引用。prompt.md#L1-L9 已核实

生成的摘要不是裸文本，前面会拼一段固定前缀：“另一个语言模型开始解决这个问题，并留下了思考摘要……请在此基础上继续，避免重复工作。”summary_prefix.md#L1 已核实 这段话的作用不是装饰：它告诉下一个模型“这是交接笔记，不是用户的新指令”，同时提醒它“工具状态还在”。

手动 /compact 走 tasks/compact.rs，可以替换摘要模板（compact_prompt 配置）。tasks/compact.rs#L63-L95 已核实 但本快照的 Op::Compact 不带参数，任务入口也忽略了输入；“/compact [附加说明]”的说法在本快照找不到实现 待核实1。

为什么单独发一次请求，而不是让主模型“边干边总结”。压缩需要一个干净的输出契约：只要摘要，不要工具调用，不要继续任务。独立请求还能单独设模型、单独重试、单独计费。代价是这次请求本身也要装下待压缩的历史；历史太大时，压缩请求会先超窗，进入下一节的失败分支。

2.4 重建：替换内存历史，再写一个检查点

拿到摘要后，Codex 从空历史开始重建：先放选中的用户消息，最后放摘要。也就是说，被压缩掉的助手消息、工具调用、工具结果不会以任何形式回到模型眼前；它们只留在 rollout 存档里。compact.rs#L702-L818 已核实

随后 replace_compacted_history 做两件事：把重建后的历史装回内存，并向 rollout 追加一条 CompactedItem 检查点。检查点里带 replacement_history、窗口编号、token 用量、以及恢复所需的 resume_metadata。session/mod.rs#L4321-L4356 已核实

还有一个容易漏掉的细节：初始上下文（WorldState、AGENTS.md 片段等）会在重建时被重新注入，位置优先放在最后一条真实用户消息之前；如果没有真实用户消息，就放在摘要之前，保证摘要仍然是“最后一条”。compact.rs#L641-L700 已核实 压缩完成后还会触发一次 SessionStart(Compact) 钩子。session/mod.rs#L4377-L4380 已核实

压缩成功后还会发一条警告：长会话和多次压缩会让模型变得不那么准确，能开新会话就尽量开。compact.rs#L442-L445 已核实

为什么先替换内存、再写检查点。模型下一步只会读内存历史；检查点是为了“以后还能恢复”，不是为了“现在能跑”。两者顺序反过来，会出现“磁盘上已经压缩、内存里还是旧历史”的短暂不一致。代价是这套操作必须原子：压缩流中途失败不能半提交，否则检查点和内存会对不上。

下面这段是 compact.rs 候选选择循环的简化摘录（省略错误处理与元数据），重点看“从新到旧、放不下就截断并停止”这三步。

Rust · compact.rs（简化） 
// 预算 20k；从最新一条真实用户消息往回装
let mut remaining = max_tokens;
for message in user_messages.iter().rev() {
    if remaining == 0 { break; }
    let tokens = approx_token_count(&message.message); // 字节数 / 4
    // 只有纯文本、且整条装得下，才原样保留
    let preserve_content = tokens <= remaining
        && content.iter().all(|part| matches!(part, ContentItem::InputText { .. }));
    // 装不下时：截断文本，丢掉图片与音频，然后停止
    if !preserve_content {
        set_annotated_content(&mut item, truncate_annotated_text(parts, remaining));
    }
    selected_messages.push(ResponseItemEnvelope { item, metadata });
    if tokens > remaining { break; }
    remaining = remaining.saturating_sub(tokens);
}
// 反转回来，按时间顺序接在初始上下文之后；最后再追加摘要
selected_messages.reverse();

2.5 失败：压缩请求自己超窗时，只能继续删

压缩请求是普通请求，也会遇到 ContextWindowExceeded。Codex 的处理很直接：如果待压缩输入不止一条，删掉最旧一条，重置重试计数，再试；如果只剩一条，把总用量标记为“满”，返回错误。compact.rs#L359-L371 已核实 源码注释说明了为什么删最旧：保留基于前缀的缓存，同时让最近消息不受影响。

其他错误分三类：中断、取消、会话预算耗尽、响应不完整——直接返回，不重试；普通 provider 错误按退避重试；轮后压缩失败只记警告，已经完成的那一轮照样保留。compact.rs#L338-L388 已核实 后台压缩失败则直接丢弃结果，但已经发生的 token 仍然计费。async_compaction.rs#L125-L140 已核实

为什么重试前必须先删。同一个 payload 再发一次，必然再超；能改变的只有输入大小。删最旧一条既缩小输入，又尽量不破坏缓存前缀。代价是每重试一次就永久少一条历史；如果超窗的是一条不可分割的巨型消息（比如一次 80k 的测试日志），删到只剩它时就没有退路了。本快照里也没有会话级的“连续失败熔断”，与 Claude Code 的 3 次熔断不同 推断。

✓要点小结

  • Codex 用 95% 整段线和 90% 范围线判断“该压了”，在轮前、轮中、轮后三个位置执行。
  • 本地压缩只保留真实用户消息，预算 20k；助手与工具消息压缩后不再回到上下文。
  • 摘要是独立请求，工具为空，带固定“交接笔记”前缀，最后以一条 user 消息放回历史末尾。
  • 内存历史被整体替换，同时写一条 CompactedItem 检查点，供恢复使用。
  • 压缩请求自身超窗时删最旧一条重试；只剩一条就只能报错。

03 · 交互演示一

把切点拖出来

下面这条会话有 14 条消息、约 187k token，其中 3 组工具调用与结果。演示假设压缩发生在“刚越过触发线”的那一刻：因此阈值越高，参与本次压缩的历史越长；输出预留越大，可用输入越小，触发越早。

先按默认值看一眼，再依次做三个实验：只把阈值从 80% 拉到 60%，只把保留量从 20k 拉到 40k，只把输出预留从 16k 拉到 30k。每次只动一个变量，观察切点序号和三种颜色各覆盖了哪些消息。

交互演示

压缩阈值、保留量与切点

先固定两个滑块，只动第三个。切点序号会变，条形图上的红线也会跟着移动。

红线 = 触发线

教学模型，不是任何 agent 的真实算法。窗口固定 200k；tokens 为示意值；“进摘要”只统计真实用户消息，其余前缀消息算作丢弃。把阈值调到 70%、保留量保持 20k，可以看到切点自动避开工具配对。

三个结果值得记住。第一，阈值决定“什么时候压”，不直接决定“保留多少”；它通过“压缩发生时历史有多长”间接影响切点。第二，保留量才是切点的主要旋钮：保留量越大，切点越靠前，进摘要的内容越少。第三，输出预留会压缩可用输入：预留从 16k 提到 30k，触发线下降约 7%，压缩会更早发生。

04 · 交互演示二

切点不能拆散一对工具调用

一条工具调用和它的结果，在协议上是一条原子记录。切点落在两者之间，会得到一条“有结果、没有调用”的历史；严格一点的 API 直接拒绝，宽松一点的模型会把这段结果当成新的事实，开始编造它为什么存在。

合法切点

合法切点共有 10 个（0…12 中去掉 3、6、9）。修复方向默认“前移”，即把整对调用与结果都留在保留段；也可以“后移”，把整对丢进摘要，但会失去最近的工作状态。

为什么多数 agent 选择“前移”而不是“后移”。结果通常是最近一次工作状态的快照：测试有没有过、文件现在长什么样。把它丢掉，模型下一轮可能重复刚才的失败。前移只多花这一对结果的 token，后移则要重新执行工具。代价是保留段可能因此超出预算；这时实现要么允许超一点，要么把更早的整对也一起保留，形成连锁。pi 的 findCutPoint 已核实 与 dsh 的 selectCompactableRange 已核实 都在切点选择里显式处理了这个约束。

05 · 七个编码智能体

同一件事，七种切法

Codex 已经在主线里拆过，下面七个 agent 各有一个弹窗。可以粗略分成三派：只留用户消息（Codex）、保留最近一段原文（pi、oh-my-pi、opencode v1/v2、DeepSeek Harness）、整段替换 + 固定重附清单（Claude Code、Grok Build）。分野不在“会不会写摘要”，而在“切点怎么找、切完补什么”。

键盘：Esc 关闭；Tab 在弹窗内循环。Claude Code 的结论来自非官方 v2.1.88 源码，只代表该版本。

07 · 设计取舍

为什么没有一种切法通吃

下面五组取舍，是这张对比表背后真正的分歧。每组都给出“选 A 的人在想什么”“选 B 的人在想什么”，以及一句代价。没有正确答案，只有和场景匹配的答案。本节引用的参数不重复给 permalink，统一见第 06 节表格与各 agent 弹窗。

取舍一：切点保守，还是激进

保守派（Codex、Grok Build）只保留一类可靠的东西：Codex 保留真实用户消息，Grok 保留系统消息、用户前缀、AGENTS.md、最后真实请求及其后的消息。切点规则简单，永远不会拆散工具配对。激进派（pi、omp、opencode、dsh）从最新往回保留一大段原文，连工具结果一起留，只把“更早的历史”换摘要。它们要保住最近的工作状态，因此必须写复杂的合法切点算法。

代价：保守派压缩后手里没有精确代码和测试输出，模型要重新读；激进派每次压缩都要处理“预算、整组、turn 边界、单回合拆分”四个约束，实现和调试成本高得多，而且保留段越大，压缩收益越小。

取舍二：保留预算固定，还是按窗口比例

Codex、pi、omp 都用 20k 这个固定值；opencode v1 用 clamp(25%, 2k, 15k)，DeepSeek Harness 用 16%，opencode v2 用 15k 加 max(10%, 16k) 的缓冲。固定值假设“模型再大，最近的工作集也差不多这么大”；比例派假设“窗口越大，最近的工作集也越大”。

代价：固定值在 1M 窗口上会显得过小，压缩后仍要频繁回读；比例派在 32k 小窗口上可能只剩 2k，刚发生的事情也留不住。固定值可预测、好调；比例派跨模型行为不一致，用户很难建立直觉。

取舍三：压缩前剥图，还是给图片留预算

Claude Code 在发压缩请求前剥掉图片块，避免压缩请求自己超窗源码 v2.1.88；Codex 有 CompactionImageBudget 特性，给图片单独留预算；omp 的 snapcompact 干脆把被丢弃的历史渲染成 PNG，用视觉模型“看历史”；opencode v2 则按请求体字节预算处理图片。四种做法对应四种对“图片是什么”的理解：噪声、证据、可压缩的视觉摘要，或纯粹的体积。

代价：剥图省 token，但压缩后模型再也看不到那张报错截图；留预算保住证据，却可能让压缩请求本身超窗；渲成图需要视觉模型，且文字细节会糊；按字节驱逐最贴近 API 限制，但和 token 预算不是一回事。

取舍四：压缩后重附文件与技能，还是只留摘要

Claude Code 在压缩后按固定清单重附：最近修改的最多 5 个文件（每个 5k、总 50k）、本会话用过的技能正文（每个 5k、总 25k），再加计划、工具增量、agent 列表、MCP 指令和 SessionStart 钩子输出。源码 v2.1.88Codex 不重附，只把初始上下文放回去。pi 折中：不重附文件正文，但把“读过哪些文件、改过哪些文件”作为清单写进摘要。

代价：重附让模型马上能继续改代码，但要花 50k–75k token，还可能把压缩前的旧文件内容重新带回来，覆盖磁盘上的新版本；只留摘要最省，但模型下一轮大概率要重新读同样的 5 个文件，慢，而且可能读到与摘要不一致的内容。清单是中间路线：知道去哪读，但不知道内容。

取舍五：单回合过长时拆分，还是截断/整段替换

pi 和 omp 用 isSplitTurn：切点落在回合中间时，把“用户消息到切点之前”的轮前缀单独摘要，再与历史摘要合并；前缀预算约为 0.5 × reserveTokens。Codex 不拆：最新用户消息放不下就截断文本，剩下的交给摘要。Grok Build 走另一条路：整段替换，但强制保留最后一条真实请求及其后的消息。

代价：拆分能同时保住“这轮要做什么”和“之前做了什么”，代价是两次摘要调用、一次合并，以及更长的压缩时间；截断最便宜，但可能正好切掉那句关键约束；整段替换实现简单，却依赖“最后一条真实请求”这一条规则，遇到一轮里多次改需求就会丢中间状态。

还有一个横切的取舍：兜底次数。opencode v1 压缩失败就直接停，pi 只给一次 compact-and-retry，opencode v2 用 0.7 / 0.5 / 0.35 三级收缩，omp 用五方法链逐级回退。次数越多，用户越少看到“压缩失败”，但每次重试都要再发一遍历史，成本和延迟都翻倍。这也是第 21 章的主题。

08 · 小测验

三道题，检验你是否真的会切

Q1

窗口 200k、输出预留 16k、触发阈值 80%、保留量 20k。把保留量单独调到 40k，切点会往前移还是往后移？为什么？

解析

往前移（序号变小，保留更多消息）。保留段是从最新往回装的，预算从 20k 变成 40k，就能多装下更早的整条消息，切点自然前移。注意“前移”指更靠近历史开头，不是更靠近现在。可以在演示一里只拖“保留量”验证：默认 20k 时切点在第 12 条之前，拉到 40k 会移到第 10 条之前。

Q2

切点落在“工具调用”和它的“工具结果”之间，会发生什么？有哪两种合法修法？多数 agent 为什么选前移？

解析

结果是保留段里出现一条没有对应调用的工具结果，调用本身却进了摘要。严格 API 会拒绝这种历史，宽松模型会把结果当成新事实。两种修法：把切点前移到调用之前（整对保留），或后移到结果之后（整对丢弃）。多数 agent 选前移，因为结果代表最近的工作状态，丢掉会导致重复执行；前移只多花这一对的 token。见演示二与 取舍一。

Q3

Codex 压缩后只保留真实用户消息，Claude Code 还会重附最近 5 个文件和技能。两种做法各自的代价是什么？什么场景下你会选后者？

解析

Codex 的做法省 token、重建简单，但模型失去精确的代码、diff 与测试状态，下一轮要重新读文件。Claude Code 的重附让模型能立刻继续改代码，代价是 50k 文件 + 25k 技能的预算，而且可能把旧版本文件重新带回上下文。若任务正处在“连续修改同一组文件”的中段，重附更划算；若是长任务刚告一段落、要换方向，只留摘要更干净。见2.4 重建与取舍四。

agent 弹窗 · omp

oh-my-pi

oh-my-pi 的压缩不是单一算法，而是一条方法链：默认顺序 remote → snapcompact → handoff → shake → soft。remote 用 provider 原生服务端压缩，不可用或失败就逐级回退；snapcompact 把被丢弃历史渲染成 PNG（不调 LLM，但需要视觉模型）；handoff 生成交接文档；shake 做机械省略；soft 才是普通 LLM 摘要。切点从最新往回按整组累加：assistant 与它的全部 toolResult 的 token 一起计入，只在合法切点处比较预算；超过 keepRecentTokens 即停。切点不在轮首时同样走 isSplitTurn，生成“历史摘要 + 轮前缀摘要”再合并。

关键参数与默认值

v2 把触发收成三种：auto（每步开头，due 成立才压）、overflow（provider 报上下文过长且尚未产出任何输出）、manual（/compact 往 inbox 塞一条控制项，在步边界消费）。路径分两条：模型元数据 compaction.type === "native" 时走 compactNatively，请 provider 返回加密窗口；否则 summarize 先把对话切成 older / recent，recent 以文本存进检查点。摘要回复必须命中模板标题，否则追加一次 NUDGE，两次都不合格就 compaction.failed。发送前 deliver 还会收缩：装不下就文本化、丢最旧 exchange，provider 再拒就按 0.7 / 0.5 / 0.35 三轮降目标。

关键参数与默认值
auto 默认 true；keep 默认 15_000；buffer 未设时 max(10% 窗口, 16_000)；SHRINK_STEPS = [0.7, 0.5, 0.35]；模板 7 段，Relevant Files 最多 15 个；旧模板 ## Additional Context 存在时走重写分支。已核实
设计意图
把“估算偏低”和“媒体撑爆请求”分开处理：先按 token 估，装不下再文本化，仍被拒就按比例缩目标。代价是压缩路径有三层状态（native / summarize / shrink），B 与 v1 的默认值不可互相外推；本快照是 beta v2.0.29，字段可能继续变。推断

Grok Build

Grok Build 用整段替换：把旧历史整体换成一封摘要加保留消息。它不做“保留尾部 N 条”的精细选择，而是按固定顺序装配：系统消息、重新渲染的首条用户消息前缀、重新注入的 AGENTS.md 原文、最后一条真实用户请求、最后一条真实用户轮之后的消息，最后才是摘要。摘要提示词是 9 段结构，要求用 <summary> 包裹、禁止调用工具，并明确要求把上一次 <conversation_summary> 的内容合并继承。压缩产物有三种模式：summary、transcript（摘要 + 指向完整日志的指针）、segments（默认，摘要 + 逐段 markdown）。

关键参数与默认值
阈值 85（grok-4.6 目录为 80）；摘要最多 3 次尝试、每次 120 s 超时、间隔 3 s；最短有效摘要 500 字符；每次压缩墙钟预算 300 s；模式默认 Segments(detail)；compactions_remaining = 1（grok-4.6 目录）。已核实
设计意图
用“固定装配顺序”代替“复杂切点算法”：规则简单、不会拆配对，还能保证 AGENTS.md 和最后请求一定在场。代价是中间轮次的助手推理与工具结果全部丢失；full-replace 也无法拆分一个超长单元，遇到单条巨型结果只能靠前置裁剪削峰。推断

DeepSeek Harness

DeepSeek Harness 把压缩拆成“接缝 + 后端 + 人工消费者”：抽象 CompactionEngine、默认后端 dsh-compaction-basic、手动命令 /compact。一次成功压缩是一个事务：compaction/start 日志锁 → 摘要 → compaction/summary（含被遮蔽 seq 集合、token 数、模型与用量）→ 用一条 user 消息加 surfaceOp: replace 替换选区 → compaction/end。选区从最新节点往前累加 token 到 retainTokens，再往前挪到工具调用/结果配对平衡的位置；起点永远是“第一个不是 system 的节点”，系统提示词永不被遮蔽。摘要 8 段，放进 <compacted-summary>，前置固定 checkpoint 前言；摘要调用复用系统提示词、当前工具定义与被遮蔽区间，逐字节对齐上一请求以命中暖前缀缓存。

关键参数与默认值
thresholdRatio = 0.8；headroomTokens = 65_536；retainRatio = 0.16（与 retainTokens 互斥）；摘要 maxTokens = headroomTokens；compactionRetries = 1；maxOverflowRetries = 1；auto = true。手动 /compact 不接受参数。已核实
设计意图
把“切哪”做成一个纯函数：预算、配对平衡、系统提示词三个约束同时满足，价格判断全部交给 token meter。事务化保证崩溃只会留下未配对 start（可检测的孤儿锁），而不是假的成功。代价是选区只能从“第一个非 system 节点”开始，无法只压缩中段；摘要失败时若还未替换，只能带完整历史继续。推断
