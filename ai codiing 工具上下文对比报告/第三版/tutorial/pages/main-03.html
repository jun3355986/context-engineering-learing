按需加载与渐进披露

接入的工具和技能越多，随请求发送的清单就越长，一次任务却只用得到其中一部分。渐进披露（progressive disclosure）把详细内容留到需要时再加载：先让模型看到名称、描述或检索入口，选中后再读取技能正文、获取工具定义。

  • 第 3 类
  • 约 19 分钟
  • 1 张时序图
  • L2 → L3

读完你能做到

  1. 分别说出 Skills、MCP 延迟、@ 引用三者的触发时机与失败模式。
  2. 区分四种“MCP 延迟”：模型能力开关、客户端默认延迟、检索式调用、代码模式目录。
  3. 给定一组工具数量与调用频率，判断该预加载还是该延迟，并说出代价。

01 · 一份越来越长的清单

工具清单为什么要按需展开

你给 agent 接了 6 个 MCP 服务器：GitHub、Jira、Sentry、数据库、Figma、内部知识库。MCP 是让 agent 接入外部工具和数据的协议。每个服务器提供 8 到 15 个工具，加起来 60 多个。接完之后，agent 开始选错工具：查 issue 时调用数据库工具，偶尔还把两个名字很像的工具参数搞混。

先看工具清单占了多少上下文。假设每个工具的名称、描述和参数结构（schema）合计平均占 200 token，60 个工具就是 12,000 token。全量发送时，这部分会随每次模型请求重复发送，也增加了模型要比较的候选。减少候选是一个排查方向，效果要用同一任务对照验证。

渐进披露的基本道理是：先提供选择所需的信息，再加载被选中的详细内容。

本章比较三种加载入口：前两种让模型选择，第三种由用户点名。它们放入上下文的内容也不同。

  • Skills（技能）：先给名称和描述，模型按任务读取操作指引；用户也可以直接点名技能。
  • MCP 延迟：先给名称、目录或检索入口，完整工具定义等到检索后才提供；代码模式则通过代码调用工具。
  • @ 文件引用：用户选文件。有的 agent 读取并附上内容，有的只插入路径，随后还要读文件。

因此，看到“支持按需加载”，还要继续查：模型最初看到了什么，谁触发加载，加载后拿到什么。Codex、Claude Code、Grok Build、opencode v2 都有减少初始工具定义的路径，下面分别看它们怎样实现。

02 · Codex 主线

两条通道：技能看描述，MCP 看模型能力

2.1 Skills：先列名称和描述，再读操作指引

技能把操作步骤写在 SKILL.md 里。文件开头的 frontmatter 是一段 YAML 元数据，用来声明名称、描述等字段。Codex 从配置的技能目录发现文件，也加载内置的 .system 技能；提供给模型的目录包含名称、描述和来源位置。技能加载 API · 目录与触发规则 已核实

模型看到任务与描述匹配，就按来源位置读取技能指引；用户也可以直接选技能。CLI 支持 $skill-name，结构化选择按技能路径解析。源码里另有“隐式调用识别”：识别命令是否读了技能文件或执行了技能脚本，用来记录调用，不能把它理解为“命令名称匹配后才选技能”。显式选择 · 调用识别 已核实

  • 目录负责说明“有哪些技能、什么时候用、去哪读”，无需预先塞入所有操作步骤。
  • 选中后的加载才负责提供操作指引；本地技能可以读文件，环境提供的技能包使用 skills.read。

目录也有预算：默认按模型窗口的 2% 估算 token，窗口未知时用 8,000 字符；超预算先缩短描述，再省略条目并告警。skills.max_context_tokens 可覆盖预算，上限 10,000 token。skills.include_instructions 默认开启，控制目录指令的注入1。预算算法 已核实

2.2 MCP：由模型元数据决定“直连”还是“延迟”

技能加载的是操作指引，MCP 工具加载的是名称、描述和参数定义。普通 MCP 工具的默认注册策略由模型元数据 supports_search_tool 决定：true 时设为 Deferred，完整定义先不直接提供给模型，由 tool_search 按需检索；false 时设为 Direct，直接提供定义。mcp_tool_exposure.rs#L63-L90 已核实

三个细节值得记住：

  1. supports_search_tool 字段未填写时取 false；已填写的模型元数据决定实际值。openai_models.rs#L481-L482 已核实
  2. tool_search 的出现还要求策略允许该入口，并存在带 search_info（检索信息）的延迟工具。spec_plan.rs#L368-L413 已核实
  3. 最终暴露方式还受服务器/连接器的 omit_tools_from、命名空间与 Code Mode（代码调用模式）策略影响。注册时的默认值只是第一步，排查时要看最终工具表。暴露策略 已核实

这里要查的是模型配置与实际暴露策略。只看“服务器已经接入”还不够：模型必须拿到工具定义，或拿到能找到它的入口。这也解释了开头的场景为什么要同时检查工具表和检索结果。

2.3 @ 引用：先分清路径和附件

Codex TUI（终端界面）的文件选择会把普通文件路径插入输入框，文件内容随后由模型调用工具读取；图片另走附件路径。@ 还可以选择插件等对象，形成带 app://、plugin:// 的结构化提及。这几种输入要分开看2。文件与图片分支 已核实

Claude Code 的 processAtMentionedFiles 则在发送请求前尝试读取文件，生成附带内容的消息；opencode v1 把 @name 解析成 file part（文件附件条目），v2 在处理输入时读取附件。dsh 的 @file 只插入路径文本。用户点名同一文件，各家进入上下文的内容不同。

2.4 技能正文和工具定义分别怎样到达模型

现在可以把两条路径接起来：技能目录帮助模型判断“这套操作步骤适不适合任务”，选中后读取指引。MCP 的检索入口帮助模型找到可调用工具，再取得参数定义。文件路径则只提供读取位置。

这三条路径都可能停在“知道存在、还没拿到内容”这一步。排查漏用技能，就看目录、描述和读取记录；排查工具不可用，就看注册、权限与检索结果。模型回答“没有这个能力”时，先核对这条信息链，再判断是否确实缺少能力。

03 · 三种按需加载

加载由谁触发，失败后查什么

沿着刚才的三条路径看时序：技能先给描述，MCP 先给检索入口或目录，详细内容在后续动作中取得。文件引用分两支：附件式在请求前读内容，路径式等模型调用读取工具。图中最后一行把这两个结果并列列出。

3.1 触发时机

Skills 通常由模型按名称和描述匹配任务，用户也可以直接指定。描述写得过宽，例如“处理文档”，容易和 Markdown、PDF 等任务都匹配；写清“生成、读取或编辑 PDF”更有助于模型选择。触发还受目录可见性、技能策略和模型判断影响。

MCP 延迟由检索或代码调用触发。Claude Code 的 ToolSearchTool、Codex 的 tool_search 负责找到工具定义；Grok Build 的 search_tool 返回匹配工具，再用 use_tool 调用。opencode v2 的 Code Mode 则让模型把工具调用写进交给 execute 执行的代码。

@ 文件引用由用户输入触发。附件式引用省掉模型自己选择、读取文件的步骤，但内容会占用窗口；路径式引用先指定位置，正文延后读取。不写 @ 时，模型也可以通过搜索、读取工具找到文件。

3.2 失败模式

三种机制的失败方式不一样，排查方法也不一样：

  • Skills 漏选：先看模型是否收到这条技能，再检查描述被缩短后是否还保留用途和触发条件，最后检查有没有读取正文的记录。Claude Code v2.1.88 单条描述上限为 250 字符；Grok 的总预算不足时会缩短描述，最后退为只列名称并省略条目；dsh 默认每条 500 字符。
  • MCP 搜不到：先查服务器连接和权限，再查检索入口与结果。Codex 检查 search_info；Grok 检查检索词与名称、描述是否匹配；Claude Code 检查网关是否支持 tool_reference（检索结果里的工具引用块）。它的 v2.1.88 默认路径会对非第一方代理地址关闭搜索，显式配置后再按模型支持情况判断。
  • 文件引用没带来内容：先分清当前 agent 采用附件还是路径文本，再查权限、路径、大小与读取结果。Claude Code 的这段附件路径会过滤读取失败项；opencode v2 则会返回附件错误，不能统一按“静默跳过”排查。附件错误处理 已核实

技能与工具目录还有一个共同问题：内容已经变化，模型收到的清单却没更新。这里的“快照”就是某个时刻保存的一份清单；“差异更新”只追加新增、移除等变化。Grok 用指纹检测公告变化，Claude Code 用 deferred_tools_delta 记录工具变化，opencode v2 也会更新清单。更新的范围和时机要分别检查，文件引用则检查所指文件是否读到了最新内容。

3.3 四种减少初始工具定义的机制

上面的失败线索要与具体机制对应。下面四条路径分别看“如何启用”和“怎样调用”：

一、模型能力开关（Codex）。普通 MCP 工具默认按 supports_search_tool 选择直接或延迟暴露，最终还受 §2.2 的策略影响。模型通过 tool_search 获取定义。能力标志为 false 时先查直接工具表；为 true 时再查检索入口和结果。

二、客户端搜索模式（Claude Code）。v2.1.88 的 getToolSearchMode() 未配置时返回 tst，表示使用工具搜索；模型支持、网关和工具可见性还会影响实际启用。ENABLE_TOOL_SEARCH=auto 则在可延迟工具定义超过窗口 10% 时启用。延迟定义以 defer_loading 标记发送，模型通过 ToolSearchTool 的 tool_reference 结果取用。auto 阈值 · 模式默认值 源码 v2.1.88

三、检索后间接调用（Grok Build）。MCP 工具不进入模型的 function tools 数组，先提供服务器公告。模型用 search_tool 做 BM25 检索（一种按词语匹配与相关性评分的检索），再用 use_tool 调用。单个工具或服务器描述在检索展示中截断到 2048 字符；检索词和描述匹配不好时，要检查返回候选。search_tool/mod.rs#L1-L34 已核实

四、代码调用模式（opencode v2）。codemode: false 的工具直接提供定义；其余工具，包括 MCP 工具，列入目录并通过 execute 内的代码调用。目录只展示一部分时，代码先用同步的 search(...) 查工具，取回结果中的调用路径。禁用 execute 会关闭这条调用路径。codemode/instructions.ts#L8-L46 已核实

比较时应分别记录：初始可见内容、发现入口、调用入口，以及关闭后的行为。尤其要区分“客户端不发送定义”和“已发送、由 API 延迟向模型展开”，两者的传输开销不同。

06 · 设计取舍

怎样权衡目录大小、检索和读取成本

取舍一：目录给“名字”，还是给“名字 + 描述 + 时机”

Codex 与 pi 都提供名称、描述和读取位置。Claude Code v2.1.88 把描述与 whenToUse 合并后限到 250 字符，dsh 默认每条描述 500 字符。Grok 先限制描述与使用时机合计 400 字节，再受清单总预算约束。

这些预算控制的是目录，不是操作指引。描述应优先说明用途和触发条件，把具体步骤留在正文。目录太短时容易丢失选用依据，太长则挤占窗口；字符数和字节数也不能当作同一种上限直接排名。

建议：用实际任务检查描述。例如“处理文档”范围太宽；“只在生成 PDF 时使用”又会漏掉读取 PDF。把应该触发和不该触发的任务各选几例，检查目录匹配和正文读取记录，再调整描述。

取舍二：延迟策略由哪些条件决定

Codex 先看模型元数据，再应用暴露策略；Claude Code v2.1.88 先取 tst 等搜索模式，再检查模型、网关和工具入口。Grok 的 MCP 调用固定经过搜索与调用工具，opencode v2 则按 codemode 分流。

这些条件分布在不同层，不能简化成“交给模型”或“交给用户”。排查配置时，应依次记录默认策略、覆盖配置、最终可见工具，以及检索入口是否可用。

代价：直接提供定义少一个发现步骤，却要持续携带工具清单；延迟可以减少初始定义，但增加发现步骤。比较时用实际工具定义的 token 数、调用频率和失败率，才能判断收益。

取舍三：检索式、目录式，还是代码式

检索式通过查询找到工具，目录式帮助模型先看分组再展开。代码式让模型把多个调用写进一次 execute，还可以在代码里检索；因此这三种方式可以组合，opencode v2 就同时使用目录和代码。

代价：检索式要检查名称、描述和检索结果，不能只看工具名是否含有某个词；目录式要检查分类是否清楚；代码式要检查执行权限及代码错误。以 Grok 的 BM25 为例，名称与描述都会影响匹配。推断

取舍四：@ 是“附件”，还是“路径文本”

Claude Code 与 opencode v1/v2 有读取附件内容的路径；Codex TUI 的普通文件选择和 dsh @file 先插入路径，模型随后再读。Grok 与 pi 的文件内容也通过读取工具取得。

附件式把读取提前到模型请求前，省掉模型主动读文件的步骤；路径式先提供位置，让模型按需读取或分页。两者都要检查读取是否成功，附件式还要检查大小和格式限制。

代价：自动附上内容会提前占用窗口；只给路径则容易让用户误以为文件已经读过。验收时应看实际附件或读取结果，光看输入框里的文件名无法判断。

取舍五：怎样发现目录变化并通知模型

Grok 用 (tool_count, description_hash, tool_names_hash) 指纹比较工具公告；Claude Code 从历史里的差异消息（delta）重建已公告集合。opencode v2 的技能新增、移除用小段更新，描述修改等情况重述清单；dsh 则追加完整替换目录。

“检查有没有变化”和“向模型追加什么”是两个步骤。每次重算得到相同文本，不会因为重算本身改变缓存前缀；只追加变化也不表示旧目录不再占上下文。选型时应测试中途增加、删除和修改工具后，模型能否及时看到正确清单。

小测验

Q1

用户说“帮我看看这个 issue”，但 agent 回答“我没有访问 Jira 的能力”。Jira 已经接好了。列出三种可能原因，并说明分别该查哪里。

解析

一、延迟工具没有被找到：看检索词、名称和描述，并检查 tool_search / search_tool 的候选结果。二、工具未进入当前可见集：查连接、权限、最终暴露策略和搜索入口，不能只看 supports_search_tool 或 tst。三、中途接入后目录没更新：查公告、指纹或差异消息。参照3.2 失败模式与3.3 四种机制。

Q2

把 Codex 的 supports_search_tool、Claude Code 的 tst、Grok 的 search_tool、opencode v2 的 Code Mode 各用一句话区分：谁决定延迟、模型要做什么才能拿到工具。

解析

Codex：能力标志与暴露策略共同决定，模型用 tool_search 取定义。Claude Code v2.1.88：默认模式是 tst，模型与网关等条件通过后，由 ToolSearchTool 取得工具引用。Grok：MCP 固定走 search_tool 检索、use_tool 调用。opencode v2：按工具的 codemode 选项分流，目录里的工具由 execute 代码调用。参照3.3。

Q3

一个团队只有 5 个技能、3 个 MCP 服务器（共 12 个工具），任务以“读代码 + 改代码”为主。你会开 MCP 延迟吗？为什么？

解析

我会先测试直接加载，前提是产品支持切换策略，再与延迟加载对照。题目还缺每个工具定义的 token 数和实际使用频率，12 个工具也可能带来很大的清单。若定义较短且经常使用，直接加载省一次发现步骤；若定义很长而大部分任务用不到，延迟更值得测试。记录定义占用、检索耗时和调用成功率，不设“超过 30 个”这样的通用阈值。参照取舍二与01 节。
