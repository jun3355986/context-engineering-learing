按需加载与渐进披露

工具和技能的清单会随插件数量线性增长，但一次任务真正用到的往往只有两三个。渐进披露（progressive disclosure）做的就是“先给目录，再给正文”：启动时只放名字和一句描述，模型需要时再拉全文。

  • 约 18 分钟
  • 1 张时序图
  • L2 → L3

读完你能做到

  1. 分别说出 Skills、MCP 延迟、@ 引用三者的触发时机与失败模式。
  2. 区分四种“MCP 延迟”：模型能力开关、客户端默认延迟、检索式调用、代码模式目录。
  3. 给定一组工具数量与调用频率，判断该预加载还是该延迟，并说出代价。

01 · 一份越来越长的清单

“工具太多，它反而不会用了”

你给 Agent 接了 6 个 MCP 服务器：GitHub、Jira、Sentry、数据库、Figma、内部知识库。每个服务器暴露 8 到 15 个工具，加起来 60 多个。接完之后，它开始犯一些奇怪的错：查 issue 时去调用数据库工具，改代码前先查一遍 Figma，偶尔还会把两个名字很像的工具参数搞混。

你以为是模型不够聪明。实际上是工具表太长：60 个工具，每个平均 200 token 的描述和 schema，光工具定义就占了一万多 token，而且它们全部排在前缀里，每一轮都重复。模型要在这么长的列表里做选择，选错的概率自然上升。

渐进披露的第一性原理：选择成本与候选数量成正比，所以先缩小候选，再让模型做选择。

这一章讲三种按需加载。它们的共同点是“目录先行、正文后到”，但触发者、目录形态、失败模式完全不同：

  • Skills：目录是名字 + 描述，触发者是模型（它决定要不要读正文）。
  • MCP 延迟：目录可能只是名字，甚至只是一行“有这些工具”，触发者是模型的一次检索或一次代码调用。
  • @ 引用：没有目录，触发者是用户（他明确点名一个文件）。

把三者混为一谈，是这一章最常见的误解。尤其是“MCP 延迟加载是 Claude Code 独有能力”这句话——它是错的，而且错得很具体：Codex 有、Grok Build 有、opencode v2 有，只是机制不同。

02 · Codex 主线

两条通道：技能看描述，MCP 看模型能力

2.1 Skills：frontmatter 变目录，正文按需读

Codex 把 SKILL.md 的 frontmatter 解析成元数据，按根目录加载技能（包括内置的 .system 技能），再按显式的 @skill 提及或命令匹配选中。skills/src/lib.rs#L1-L60 已核实 配置项 skills.include_instructions 控制是否注入 <skills_instructions> 这个 developer 块；本次核对没有在配置段找到它的显式默认值1。

注意“按显式提及或命令匹配选中”这句话。它意味着 Codex 的技能选择有两条路：用户明确点名（@skill），或者命令名恰好匹配。它不像 Claude Code 那样把“名称 + 描述 + whenToUse”全部列出来让模型自己判断。两种做法各有代价：

  • 只给名字，目录短，但模型不知道什么时候该用，容易漏。
  • 给名字 + 描述 + 使用时机，命中率高，但目录长，而且描述写不好会误导。

Codex 偏向前者。它的假设是“技能由用户或命令触发”，不是“模型自己发现”。这个假设在技能少的团队里成立，在技能几十个的团队里就开始漏。

2.2 MCP：由模型元数据决定“直连”还是“延迟”

这是 Codex 最容易被忽略的一段。当模型元数据 supports_search_tool = true 时，MCP 工具以 ToolExposure::Deferred 注册——不进首轮 Prompt.tools，只保留检索元数据，由 tool_search 工具按需拉取；为 false 时退回 Direct，全部工具一次性下发。mcp_tool_exposure.rs#L63-L90 已核实

三个细节值得记住：

  1. supports_search_tool 是 #[serde(default)] 布尔，缺省 false。也就是说，默认是不延迟的，延迟是“模型声明自己支持”才开启。openai_models.rs#L481-L482 已核实
  2. 即使模型支持，tool_search 本身也只在“至少有一个可检索的延迟工具、且有 search_info”时才出现在工具表里。否则模型连检索入口都没有。spec_plan.rs#L368-L413 已核实
  3. 延迟与否是按工具决定的，不是按服务器。同一个 MCP 服务器可以一部分工具直连、一部分延迟。

为什么交给模型元数据，而不是配置项。因为延迟加载依赖一个模型能力：它得知道“自己可以去检索工具”，并且能理解检索结果的格式。老模型没有这个训练，给它 tool_search 反而会增加误用。把开关放在模型元数据里，等于让“能力”决定“策略”。代价是用户无法强制开启：模型说不支持，你就只能全量下发，哪怕工具表已经很长。

2.3 @ 引用：Codex 没有通用文件展开

Codex 的 @ 在本次核对的源码里表现为结构化的工具提及（ToolMentionKind、app://、plugin://），没有找到“把 @file 内容直接展开进提示词”的通用路径2。它更接近“点名一个工具或资源”，而不是“把文件内容塞进来”。

这和 Claude Code 的 @ 是两件事。Claude Code 的 processAtMentionedFiles 会把文件内容作为附件插入，不是用户原文的一部分；opencode v1 的 resolvePromptParts 会把 @name 转成 file part；dsh 的 @file 只插入路径文本，不读内容。三种语义，三种代价，后面会展开。

2.4 为什么 Codex 把两条通道分开

技能是“知识”，MCP 是“能力”。知识可以只给摘要，让模型自己判断要不要深入；能力必须先知道“存在”，否则模型不会去调用一个它不知道的工具。所以 Codex 对技能用“描述 + 显式提及”，对 MCP 用“延迟 + 检索入口”。

这个划分有一个隐含前提：模型知道自己缺什么。技能场景里，模型看到“有一个叫 pdf 的技能”，能判断当前任务要不要用它；MCP 场景里，模型看到“有一批延迟工具”，得先检索才知道有没有能用的。前者靠语义匹配，后者靠关键词检索。检索失败时，模型不会说“我搜不到”，它会说“我没有这个能力”——这是延迟加载最典型的失败模式。

03 · 三种按需加载

谁触发、给什么、怎么坏

把三种机制放在一条时间线上，差别一眼就能看出来：Skills 在启动时给“描述”，MCP 延迟给“名字或目录”，@ 引用在用户输入时直接给“内容”。前两者的正文都要等一次主动动作，后者没有“后到”这一步。

3.1 触发时机

Skills 的触发是语义匹配：模型读目录里的名字和描述，判断“这个任务像不像它”。所以触发质量完全取决于描述写得好不好。描述里写“处理 PDF”，模型只会在遇到 PDF 时想起它；写“处理文档”，它可能在处理 Markdown 时也去读，读完发现不对，浪费一次往返。

MCP 延迟 的触发是检索或代码调用。Claude Code 的 ToolSearchTool、Codex 的 tool_search、Grok Build 的 search_tool 都是“给关键词，返回工具定义”；opencode v2 的 Code Mode 则是“给一段代码，代码里调用工具”。前者要求模型会写检索词，后者要求模型会写代码。

@ 引用 的触发是用户输入。它不需要模型判断，也不需要检索，代价是把“选什么”完全交给用户。用户忘了写 @，模型就看不到那个文件；用户写了 20 个 @，上下文一次被塞满。

3.2 失败模式

三种机制的失败方式不一样，排查方法也不一样：

  • Skills 漏选：模型没读正文就开始干活。先看目录里有没有这条技能，再看描述是否被截断，最后看模型是不是根本不认为任务相关。Claude Code 的单条描述上限是 250 字符，超出会被截；Grok Build 的清单有总预算，超出按条目裁剪；dsh 每条 500 字符。
  • MCP 搜不到：模型说“我没有这个工具”。先看延迟工具是否真的注册了 search_info，再看检索词是否匹配工具名，最后看网关是否支持 tool_reference 这类返回块。Claude Code 在非第一方 ANTHROPIC_BASE_URL 且未显式设置 ENABLE_TOOL_SEARCH 时会禁用延迟，原因就是代理不一定转发这些块。
  • @ 静默失败：路径写错、文件是二进制、文件太大。多数实现不会报错，只是不附内容；模型于是基于“用户提到了这个文件”却看不到内容，开始编造。

三者共同的失败是“目录过期”：技能清单、MCP 公告、工具目录都是在某个时刻生成的快照，如果中途装了新插件而目录没更新，模型会不知道新工具存在。所以几乎所有实现都有“变更检测 + 增量公告”：Grok 用 (tool_count, description_hash, tool_names_hash) 指纹，Claude Code 用 deferred_tools_delta，Codex 在每轮重新组装工具表。

3.3 四种“MCP 延迟”，别混为一谈

这是本章最需要说清的一段。四种机制都叫“延迟”，但决定权、目录形态、失败模式都不同：

一、模型能力开关（Codex）。supports_search_tool 为 true 才延迟，默认 false。目录是检索元数据，入口是 tool_search。决定权在模型元数据，用户不能强制。失败模式是“模型不支持 → 全量下发 → 前缀变长”，不是“搜不到”。

二、客户端默认延迟（Claude Code）。getToolSearchMode() 在未设置环境变量时返回 tst，即所有 MCP 工具与标记为 shouldDefer 的工具都不进首轮 schema，只暴露名字，模型用 ToolSearchTool 拉完整定义（defer_loading + tool_reference 块）。ENABLE_TOOL_SEARCH=auto 时改为按阈值判断：延迟工具定义超过窗口 10% 才启用延迟。toolSearch.ts#L46-L49 源码 v2.1.88 决定权在客户端，默认就延迟；失败模式是网关不转发 tool_reference 时整条链路不可用。

三、检索式调用（Grok Build）。MCP 工具根本不进 function tools，只注入一段“服务器公告”。模型先用 search_tool（BM25 关键词检索）找工具，再用 use_tool 调用；单个 MCP 工具或服务器描述硬截断到 2048 字符。search_tool/mod.rs#L1-L34 已核实 决定权在客户端架构，失败模式是“检索词不对 → 找不到 → 模型以为没有”。

四、代码模式目录（opencode v2）。除 codemode: false 的内置工具外，全部 MCP 工具与元工具都不进工具定义，只以“目录行”形式写进指令基线；模型必须通过 execute 工具写代码来调用，目录不完整时在代码里用同步的 search(...) 查工具名。codemode/instructions.ts#L8-L46 已核实 决定权在工具注册时的 codemode 选项；失败模式是模型不会写代码，或者 execute 被权限禁掉导致整条通道关闭。

四者的共同点是“工具定义不占首轮 schema”，共同点之外几乎全不一样。写评测或做选型时，把它们当成同一种能力，会得出完全错误的结论。

06 · 设计取舍

目录越详细，越省往返，也越占地方

取舍一：目录给“名字”，还是给“名字 + 描述 + 时机”

pi 给 4 行：name、description、location，正文靠 read。Claude Code 给名称 + 描述 + whenToUse，单条 250 字符。dsh 给名称 + 描述，500 字符。Grok 给名称 + 截断描述，清单有按窗口比例算的总预算。

信息越多，模型越容易判断“该不该用”，往返次数越少；但目录本身占前缀，而且每条描述都要维护。250 字符大约是三句话，够写“什么时候用、什么时候不用”；500 字符能加一个例子；4 行 pi 式目录最省，但模型常常要靠猜。

代价：描述写得好是资产，写得差是负债。一句“处理文档”会让模型在十几个场景里都去读正文，每次都花一次往返；一句“仅在用户要求生成 PDF 时使用”能挡掉大部分误触发，但也可能挡掉真正的需求。

取舍二：延迟的开关交给模型、客户端，还是用户

Codex 交给模型元数据（supports_search_tool），Claude Code 交给客户端默认值（tst），Grok 交给架构（MCP 一律不进 function tools），opencode v2 交给工具注册选项（codemode）。

交给模型最保守：不支持就不延迟，绝不会因为延迟而让模型失去能力。交给客户端最激进：默认全延迟，模型必须学会检索。交给架构最彻底：连“直连”这条路都不留。交给注册选项最灵活：同一个工具可以按需选择进不进目录。

代价：越激进，省下的前缀越多，失败时的表现越差——模型不会说“检索失败”，它说“我没有这个工具”。越保守，越安全，但工具一多就回到“清单太长、选择困难”的原点。

取舍三：检索式、目录式，还是代码式

检索式（Codex tool_search、Claude Code ToolSearchTool、Grok search_tool）把“找工具”变成一次关键词查询，优点是目录可以极简，缺点是把负担转给模型的检索词。目录式（omp 的 xd://、v2 的 catalog 行）把工具分组，模型先选组再展开，优点是结构清晰，缺点是组名起不好就没人点。代码式（v2 的 Code Mode）让模型写代码调用工具，优点是一次可以串多个调用、省往返，缺点是模型得会写代码，而且错误更难定位。

代价：检索式对工具命名最敏感——工具名里没有“issue”这个词，搜“issue”就找不到。目录式对分类最敏感。代码式对沙箱和权限最敏感：execute 一被禁，整条通道关闭。

取舍四：@ 是“附件”，还是“路径文本”

Claude Code 与 opencode v1/v2 把 @ 物化成附件，内容直接进本轮；dsh 的 @file 只插路径文本，模型还得调用文件工具去读；Grok 与 pi 没有专门的 @ 通道，一律走 read。

物化的好处是“用户点名 = 一定看到”，不依赖模型是否愿意读；坏处是一次可以塞进很大的内容，而且用户很难感知它占了多少 token。路径文本的好处是体积可控、模型可以分页读；坏处是用户以为“我已经给它了”，模型却还没读。

代价：物化派要处理“文件太大”“二进制”“路径不存在”三种边界，多数实现选择静默跳过；路径派要把“我提到了但没读”这个歧义留给模型解释。

取舍五：目录快照，还是每次重算

Grok 用指纹 (tool_count, description_hash, tool_names_hash) 判断公告是否变化，只在变化时重发；Claude Code 从历史里的旧 delta 重建“已公告集合”；opencode v2 在技能清单变化时用差分，新增删除出小增量，其余整段重述；Codex 每轮重新组装工具表。

快照省 token，但会“过期”；重算不会过期，但每轮都要付一次组装的代价，而且容易打断缓存。真正的分界是“工具集在会话中途变不变”：插件装完就不动的场景，快照够用；会动态加载 MCP 的场景，必须能检测变化。

07 · 小测验

三道题，检验你是否分得清

Q1

用户说“帮我看看这个 issue”，但 Agent 回答“我没有访问 Jira 的能力”。Jira 已经接好了。列出三种可能原因，并说明分别该查哪里。

解析

一、MCP 延迟生效但检索没命中：查工具名与检索词是否匹配，看 tool_search / search_tool 的返回。二、延迟未生效但工具没进可见集：查权限、服务器是否连接、supports_search_tool 或 tst 的取值。三、目录过期：会话中途接的服务器，公告还没更新，查 delta / 指纹。见3.2 失败模式与3.3 四种延迟。

Q2

把 Codex 的 supports_search_tool、Claude Code 的 tst、Grok 的 search_tool、opencode v2 的 Code Mode 各用一句话区分：谁决定延迟、模型要做什么才能拿到工具。

解析

Codex：模型元数据决定，模型调 tool_search 检索。Claude Code：客户端默认 tst 决定，模型调 ToolSearchTool 拉定义。Grok：架构决定（MCP 不进 function tools），模型先 search_tool（BM25）再 use_tool。v2：工具注册选项决定，模型写一段代码用 execute 调用。四者都叫延迟，决定权与动作都不同。见3.3。

Q3

一个团队只有 5 个技能、3 个 MCP 服务器（共 12 个工具），任务以“读代码 + 改代码”为主。你会开 MCP 延迟吗？为什么？

解析

不必开。12 个工具的前缀成本有限，而延迟会引入“检索失败”这一新失败模式，还会让模型多一次往返。延迟的收益随工具数量增长，成本却是固定的：多一个检索步骤、多一种失败可能。等到工具超过 30 个、或者大部分工具在单次任务里用不到时，再考虑延迟。见取舍二与01 节。

工具弹窗 · claude-code

Claude Code

Skills 两段式：启动时只把「技能名 + 描述 + whenToUse」放进 skill_listing 附件；完整 SKILL.md 只有被调用时才作为一条用户消息注入。列表有预算：按上下文窗口的 1% 折算成字符（×4 字符/token），每条描述硬截断 250 字符，内置技能不参与截断。MCP 工具默认延迟：getToolSearchMode() 在未设置环境变量时返回 tst，即所有 MCP 工具与标记为 shouldDefer 的工具都不进首轮 schema，只暴露名字，模型需要时用 ToolSearchTool 拉完整定义（defer_loading + tool_reference 块）。ENABLE_TOOL_SEARCH=auto 时改为按阈值判断：延迟工具定义超过窗口 10% 才启用延迟。@ 引用走 processAtMentionedFiles，把文件内容作为附件插入，而不是用户原文。

工具弹窗 · pi

pi

技能只在系统提示里暴露「名称 + 一句描述 + 文件位置」，完整 SKILL.md 由模型在任务匹配时用 read（或 bash，取决于可用工具）自行读取；formatSkillsForPrompt() 会跳过 disableModelInvocation 的技能。技能描述有长度校验：名称上限 64 字符、描述上限 1024 字符，超长不截断，而是产生校验告警。MCP 不在核心内实现，而以 extensions/mcp 扩展形式提供，扩展可注册工具、命令、provider、渲染器。read 工具支持 offset/limit 分页续读，因此“先看局部、需要再放大”是通用读取模式，而不是专门的文件引用语法。

把“技能正文”完全交给通用读取工具，不再造一套专用加载器：模型已经会用 read，技能正文只是另一个文件。代价是没有“技能专属”的预算与截断，正文多长就进多少；描述超长时只有告警，坏描述会一直留在目录里。推断

工具弹窗 · omp

oh-my-pi

技能在提示词里只放名称、描述和位置，正文通过 skill://<name> 内部 URL 按需读取（read 与 grep 都支持），hide: true 的技能不出现在提示词但 skill:// 仍可访问。rulebook 里的规则同理：提示词只给 description，正文通过 rule:// 读取，只有 alwaysApply 规则才全文注入。MCP 工具全部保持启用，但“展示位置”由 loadMode 决定：一部分作为顶层工具，一部分收进 xd:// 目录，系统提示只给目录名，模型需要时再展开。扩展与自定义工具同样走 discoverable 加载模式。

工具弹窗 · opencode-v1

opencode v1

技能是标准三段式：发现 skills/**/SKILL.md，系统提示里只放 Skill.fmt(list, {verbose:true}) 渲染的清单（名称、描述、位置），正文由 skill 工具按名字读取后返回 <skill_content> 块。MCP 这一侧默认没有按需加载：服务端暴露的每个工具都注册成完整工具定义进入请求，系统提示只额外附上各 server 的 instructions；只有打开实验开关 experimentalCodeMode 时才会多出一个 execute 工具，并在它的 description 里附带 MCP 工具目录。@ 引用由 resolvePromptParts 在入场时解析：文本中的 @name 若能 stat 到文件就转成 file part，否则尝试当作 agent 名。

关键参数与默认值

MCP 默认全量是最保守的选择：不会出现“模型不知道工具存在”，代价是工具多时前缀膨胀。Code Mode 作为实验开关，把“要不要延迟”交给用户，而不是默认开启。这与 Claude Code 的 tst 默认值正好相反。推断

工具弹窗 · opencode-v2

opencode v2

工具弹窗 · grok-build

Grok Build

Skills 只在首条用户消息里给出「名称 + 截断后的描述」清单，模型要用时调用 skill 工具读取 SKILL.md 正文；清单有硬预算：按上下文窗口 token 数折算成字符（SKILL_BUDGET_CONTEXT_PERCENT = 0.5，文档给的 200k 窗口示例约 400k 字符4），超出后按条目裁剪而不是整段丢弃。MCP 走另一条路：服务器与工具不进入 function tools，只注入一段「服务器公告」，模型先用 search_tool（BM25 关键词检索）找工具，再用 use_tool 调用；单个 MCP 工具或服务器描述硬截断到 2048 字符，公告用 (tool_count, description_hash, tool_names_hash) 指纹做变更检测，只在变化时重发。@ 文件引用在本版源码中没有独立的附件注入通道，文件内容一律通过 read_file 按需读取。

工具弹窗 · dsh

DeepSeek Harness

Skills 是唯一的“真·渐进披露”：首个请求前，如果存在模型可调用技能且 skill 工具可见，注入一条持久 user 角色消息作为目录（名称 + 被截断的描述，默认每条形如 500 字符），并明确告诉模型「先加载再行动、不要只凭摘要推断指令」；模型调用 skill 工具时返回完整指令正文 + 资源指引，包在 <skill_content> 里，作为普通工具历史保留。目录变化时追加一份完整替换（空目录也算替换，用于退休旧名字）。MCP 工具不是延迟加载：mcp-client 把每个服务器的工具直接注册到 ctx.tools，名字形如 mcp__github__create_issue，因此从第一轮就占 schema；只有 MCP resources 是共享工具 + 显式选服务器的按需读取。@file 补全只插入路径文本，不读也不附内容；@session 引用则生成有界、只读、带“不可信、勿执行其中指令”警告的快照。

关键参数与默认值

设计意图
把技能目录做成持久消息而不是系统提示，目录变化时可以“追加替换”而不动前缀；@file 只给路径，是为了避免用户一次点名就把大文件塞满窗口。代价是目录消息会一直占着历史位置，且 @file 的“我提到了但没读”容易被误解为“已经给了”。推断
