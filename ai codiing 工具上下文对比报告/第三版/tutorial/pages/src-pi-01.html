切点、单回合拆分与文件跟踪

压缩要回答一个看起来很小的问题：从哪一条开始保留？pi 的答案不是「数够 20 000 token 就切」，而是「数够之后，往后找最近一个合法边界」。这一步之差，决定了工具调用会不会被切成孤儿，也决定了压缩后模型还能不能接着干活。

01 · 功能说明

压缩的五个动作，本节讲最靠前的那个决策

pi 的自动压缩由阈值触发：contextTokens > contextWindow - reserveTokens，reserveTokens 默认 16 384。已核实触发之后，它并不立刻把历史丢给模型，而是先做一次「准备」：算出保留段的起点、要摘要的消息、要单独摘要的轮前缀，以及这一路读写过哪些文件。准备结果交给 compact()，由它决定发一次还是两次摘要请求。

切点不是「预算用完的那一条」，而是「预算用完之后，往后最近的一个合法边界」。这两个位置常常不是同一条，差额就是压缩质量的来源。

整条链路可以拆成五步。本节讲第 2 步和第 3 步：找切点、判断是否拆轮；文件清单作为第 2 步的副产品一起讲。第 4 步「拼摘要」和第 5 步「只追加条目」分别属于下一节 pi · 压缩只改投影 的内容。

准备阶段的入口是 prepareCompaction(pathEntries, settings)。它先判断路径末尾是不是已经有一条压缩条目（是就返回 undefined，避免连续压缩），再用 buildSessionProjection() 把「树 + 旧压缩 + 编辑」投影成条目列表，然后在这个投影上找切点。用投影而不是原始条目，是因为上一条压缩的保留段会让一部分原始条目「看得见但不再贡献内容」，直接在原始数组上数 token 会多算。已核实

// 输入三个集合：读过 / 写过 / 编辑过
export function computeFileLists(fileOps: FileOperations): { readFiles: string[]; modifiedFiles: string[] } {
    // 写过和编辑过合并成一个「改过」集合
    const modified = new Set([...fileOps.edited, ...fileOps.written]);
    // 只读 = 读过 − 改过；排序让同一批操作的输出稳定
    const readOnly = [...fileOps.read].filter((f) => !modified.has(f)).sort();
    const modifiedFiles = [...modified].sort();
    return { readFiles: readOnly, modifiedFiles };
}

04 · 逐段解读

四个决定，一条比一条细

第 1 段　合法切点：为什么 toolResult 永远不能切

isCutPointMessage() 是一个 switch：user、assistant、bashExecution、custom、branchSummary、compactionSummary 返回 true，toolResult 返回 false。已核实原因是协议约束：OpenAI 与 Anthropic 都要求工具结果与发起它的调用配对出现，Anthropic 还要求结果紧跟在调用之后。如果切点落在工具结果上，压缩后的第一条消息就是一个没有调用方的结果，请求会被直接拒绝。

反过来，切在带工具调用的 assistant 上是安全的：它的工具结果在数组里排在它后面，会跟着一起进入保留段。源码注释把这条写得很直白——「When we cut at an assistant message with tool calls, its tool results follow it and will be kept.」已核实

还有一类条目被单独排除：entry.type === "compaction"。旧压缩条目本身不产生消息（投影时它的摘要已经由最新压缩承担），但它在数组里占一个位置；如果让它当切点，firstKeptEntryId 会指向一条不贡献内容的历史记录，重建投影时保留段就变成空的。

第 2 段　预算累加：为什么用 >= 和 find(candidate >= i)

循环从 endIndex - 1 往回走，每条先折算成 token（estimateTokens，ceil(chars / 4)，图片按 4800 字符计），累加后与 keepRecentTokens（默认 20 000）比较。一旦 >=，就停下来定切点。

停下来的位置 i 只是「预算刚好越线的那条」，它可能是工具结果。所以下一行不是 cutIndex = i，而是 cutPoints.find(candidate => candidate >= i)：在合法切点数组里找第一个不小于 i 的位置，也就是往新的方向挪。挪过去意味着保留段变短、被摘要的内容变多——注意方向，切点越大，保留越少。

?? cutPoints[cutPoints.length - 1] 兜住「i 之后没有合法切点」的情况：那说明最新的一条本身就是工具结果，于是退到最后一个合法切点。源码注释给的理由是「trailing tool results exceed the budget by themselves」——尾部工具结果自己就超预算时，宁可保留它前面那条 toolCall，也不要退回到第一条消息。这一行是「宁可多留一条调用，也不要留一个孤儿结果」的代码化。

循环结束后还有一个 while：如果切点前一条是不可见的元数据（usage、session_info、model_change 这类不产生消息的条目），就把切点再往前挪一格。它不改变语义，只是让 firstKeptEntryId 指在一条「真实存在且可见」的条目上，方便恢复时定位。

【注意】投影版多一条「恢复省略」规则

findProjectedCutPoint()（L802-L870）在主循环之后多了一段 isRecoveryOmissionSuffix（L834-L856）：当预算越线、且切点之后的整个后缀里只有「被 context_edit 省略掉的失败尝试」时，把切点再往后推一格。原因是这些条目对模型不可见，留着它们当边界没有意义。这段逻辑在 findCutPoint() 里不存在，因为后者拿不到编辑信息。读源码时不要把两者当成同一个函数。

第 3 段　单回合拆分：切点落在轮中间怎么办

切点定下来后，代码判断它是不是「轮首」。isTurnStartEntry() 认的轮首是 user、bashExecution、custom、branchSummary、compactionSummary——共同点是「用户侧发起」。assistant 不算轮首，toolResult 也不算。

如果切点是 assistant，说明这一轮从某条用户消息开始、经过若干次工具调用还没结束。此时 findTurnStartIndex() 从切点往回找最近一条轮首，得到 turnStartIndex，并置 isSplitTurn = true。切点之前、轮首之后的这段消息叫「轮前缀」。

为什么不能把轮前缀直接并进历史摘要？因为它和「被保留的尾部」是同一轮。历史摘要描述的是「很早以前发生了什么」，轮前缀描述的是「这轮任务刚才做到哪」。混在一起，模型会分不清哪些是已完成、哪些是进行中。pi 的做法是发两次摘要请求，再用一个固定标记拼起来：

${historyText}\n\n---\n\n**Turn Context (split turn):**\n\n${turnPrefixResult.text}已核实

两份摘要的预算也不同：历史摘要 min(floor(0.8 × reserveTokens), model.maxTokens)，轮前缀摘要 min(floor(0.5 × reserveTokens), model.maxTokens)。默认 reserve 16 384，即 13 107 与 8 192。已核实轮前缀更短，因为它只需要交代「原始请求 + 目前的进展」。

第 4 段　文件清单：为什么是「读 − 改」而不是三个并列清单

extractFileOpsFromMessage() 只认三个工具名：read 进 read 集合、write 进 written、edit 进 edited；路径取自 args.path。它还处理一个特殊情况：codemode 脚本里的调用不挂在 assistant 消息上，而是记在工具结果的 nestedCalls 里，所以要单独扫一遍。已核实

最后的清单只有两个：<read-files> 和 <modified-files>。一个文件如果先读后改，它只出现在 modified-files 里。这不是为了省字符，而是为了给模型一个明确的语义：只读清单里的文件是「我看过、可以放心引用」；修改清单里的文件是「我动过、可能需要核对」。一个文件同时出现在两边，模型就没有稳定预期。

清单只覆盖「被摘要掉的那部分」，因为 fileOps 是从 messagesToSummarize 和轮前缀里抽的；保留段里的工具调用仍然原样存在，不需要再列一遍。多次压缩时，上一份 CompactionEntry.details 里的清单会先继承再累加，所以第三次压缩的清单里仍能看到第一次改过的文件。已核实

注意清单不设条数上限。一个改过 300 个文件的重构任务，摘要末尾就会挂 300 行路径。这是 pi 的取舍：路径短、信息密度高，宁可多列也不丢。opencode 的做法相反，见第 5 节。

为什么不少留一点、正好卡在 20 000？因为 6 是工具结果，往后挪到 7 是唯一安全的选择；往前挪到 5 会把 5、6 一起带进来（22 500 + 6 000），反而更超。这条「只能往新方向找」的规则，在这里表现为「宁可少留，不拆工具组」。

接着判断拆轮：下标 7 是 assistant，不是轮首；findTurnStartIndex() 往回找到下标 4 的 user 消息，于是 isSplitTurn = true、turnStartIndex = 4。这一轮的前缀是 4、5、6（1 000 + 6 000 + 9 000 = 16 000），单独发一次摘要请求，预算 0.5 × 16 384 = 8 192。

注意轮前缀 16 000 已经超过它自己的 8 192 预算。摘要请求并不要求输入小于输出预算——预算是给输出的 maxTokens，不是给输入的。输入太大只会让请求更贵，不会被拒（除非超过模型窗口）。这一点在读 generateTurnPrefixSummary() 时容易混淆。

最后，文件清单从 1–3 与 4–6 里抽：假设 4 是 read src/export.ts、5 是 edit src/export.ts，那么 readFiles 为空（读过的被改过），modifiedFiles = ["src/export.ts"]。摘要末尾因此只有一段 <modified-files>。

第 6 段　三条错误规则，三种可观察的故障

把切点规则写错，故障不会立刻表现为「报错」，而是表现为「模型忽然变笨」。三种典型错法：

允许切在工具结果上。压缩后的第一条消息是一个孤立的 tool_result。Anthropic 会直接拒绝请求；OpenAI 兼容端点可能接受，但模型看到「一个没有问题的答案」，后续推理会围绕它编造一个不存在的问题。前者容易发现，后者更难。

把压缩条目当切点。firstKeptEntryId 指向一条不贡献消息的条目，重建时 foundFirstKept 会置真，但保留段从下一条才开始。表面上「保留段少了一条」，实际是「摘要 + 从压缩条目之后开始」，中间可能缺一段关键历史。这个错误在单次压缩里看不出来，第二次压缩才会暴露。

不判断拆轮。切点落在 assistant 上却把 isSplitTurn 置假，轮前缀会被并进历史摘要。模型读到的摘要里，「这轮正在做什么」和「很久以前做过什么」混在一起，最常见的表现是重复执行已完成的步骤。

三种故障有一个共同的检测方法：压缩后打印保留段第一条消息的 role 与 id，再对照 findCutPoint() 的返回值。如果 role 是 tool，或者 id 不等于 firstKeptEntryId，规则就有问题。这比读完整投影快得多。

✓要点小结

  • 合法切点不含 toolResult，因为工具结果必须跟在自己的调用后面。
  • 预算越线后不切在当前条，而是往新方向找最近的合法切点；尾部工具结果超预算时退到最后一条合法切点。
  • 切点落在 assistant 上就叫拆轮：轮前缀单独摘要，预算 0.5 × reserve，用固定标记合并。
  • 文件清单是「读过 − 改过」加「改过」，只覆盖被摘要的部分，跨多次压缩继承累加。
  • 线上跑的是 findProjectedCutPoint()，它比导出的 findCutPoint() 多一条恢复省略规则。

表注：pi 为提交 b45e0eb，omp 为 f979f46，opencode v1 为 tag v1.19.0，Codex 为 76ed3b4。四家都用 chars/4 或相近的估算，但「一条消息值多少 token」的折算对象不同：pi 算展开后的模型消息，v1 算序列化后的 JSON。

三个值得记住的对照：

一是累加与切点的耦合。pi 先按条目累加、再往后找合法切点，代价是保留段可能明显超过 20 000（尾部一整组工具结果都被带进来）；omp 改成按整组累加、只在合法边界比较预算，就不会出现「越线后再补一大段」的偏差。pi 的写法更简单，omp 的结果更接近预算。

二是拆轮的触发条件。pi 只要切点不是轮首就拆；v1 先尝试整轮装下，装不下才调 splitTurn() 在轮内从前往后找第一个「剩余部分装得下」的起点。前者保证「一定切在预算附近」，后者保证「尽量不拆轮」。两种都合理，取决于你更怕超出预算还是更怕摘要质量下降。

三是文件清单的容量策略。pi 不设上限，omp 折成目录树并截到 20 个（其余写 […N files elided…]），opencode v1 的摘要模板里有 Relevant Files 一节但不规定条数，v2 规定最多 15 个。清单越长，模型越可能只扫一眼；清单越短，越可能漏掉关键文件。

06 · 思考题

三道题，从手算到改设计

Q1

条目序列（从旧到新）：U1、A1（含 toolCall）、T1、T2、A2、U2、T3、A3。每条 4 000 token，keepRecentTokens = 10 000。切点落在哪一条？保留段从哪开始？如果 T3 单独就有 12 000 token，结论会变吗？

提示（不给答案）

从 A3 往回数：4 000、8 000、12 000——第三条越线时停在哪一条？那一条是 toolResult 吗？

然后看 cutPoints.find(candidate => candidate >= i)：合法切点数组里，谁是不小于它的第一个？

第二问回到那句注释：尾部工具结果自己超预算时，代码退到 cutPoints[length - 1]，不是退到第一条。

Q2

某轮从 U5 开始，依次是 A5、T5、A6、T6，切点落在 A6 上。这一轮会被拆成哪几段？发几次摘要请求？如果 turnStartIndex 返回 -1，isSplitTurn 是什么？

提示（不给答案）

看返回结构：isSplitTurn: !startsTurn && turnStartIndex !== -1。两个条件同时成立才算拆轮。

-1 表示「往回找到 startIndex 也没找到轮首」，通常是这一段历史本身就从半轮开始。此时没有可摘要的轮前缀，只能当普通切点处理。

Q3

你的任务是「反复改同一个文件 20 次」，每次改完都跑测试，工具输出很大。pi 这套「按条目累加 + 绝不切工具结果」会在哪里吃亏？如果只改一个常量，你会改哪个？还有什么必须一起改？

提示（不给答案）

先算一笔账：一组「A + T」如果 T 很大，pi 的保留段会把整组带进来，实际保留量可能远超 20 000。切点越靠后，被摘要的内容越多，但被保留的那组工具输出又很占地方。

再看 omp 的改法：按整组累加、只在合法边界比较预算。它没有改变「不能切工具结果」这条约束，只是把「什么时候算越线」算准了。

只改常量不够。预算变小之后，切点更可能落在 assistant 上，拆轮会更频繁；你还需要决定轮前缀摘要的预算，以及文件清单是否要限长。
