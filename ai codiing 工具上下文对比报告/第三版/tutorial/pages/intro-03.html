Agent 循环中上下文如何增长

没有哪一次请求突然变长。是一轮一轮，每次多一点点，最后撞线。

  • 约 12 分钟
  • 前置：第 2 章
  • L1 → L2

读完你能做到

  1. 说清一轮循环里，上下文按什么顺序长了哪几段。
  2. 指出三个增长源，并排出谁最粗。
  3. 看懂增长曲线上的两条阈值线，知道什么时候必须减量。

01 · 第九轮开始，它开始问你同一个问题

“你刚才说的那个配置，是在哪个文件？”

下午两点十分，你让它修一个偶发失败的测试。前两轮很顺：它读了两个文件，改了一行，跑了一次测试。第三轮开始读日志，第四轮又读了三个文件。

第九轮，它问：「你刚才说的那个配置，是在哪个文件？」那句话你在第三轮就回答过。会话没有断，你也没清空，但它就是没接上。

场景 · 不是它变笨，是桌子被堆满了

Agent 不是“一次想完”，而是循环（agent loop）：模型看一遍材料，决定调一个工具；工具返回结果，材料变多；模型再看一遍，再决定下一步。每转一圈，桌上就多几张纸。转到某一步，它得先腾地方，而你最早放的那张，可能正好被挪走。

上下文不是一次装满的，是一轮一轮堆上去的；堆的过程有固定套路。

02 · 一轮里发生了什么

你说话、它动手、工具交回一沓纸

一轮（turn）通常长这样：你的消息先进去；模型采样（sampling）一次，输出一段话，或者一个工具调用（tool call）；工具真正执行，把工具结果（tool result）交回来；这份结果作为新的一条消息追加进历史，模型再采样一次。

注意最后半句：模型每采样一次，都是一次全新的请求。它不是“在脑子里继续想”，而是把整摞材料重新交一遍。所以一次“读文件并修改”的动作，可能包含三到四次请求，每次都带着前面全部历史。

把它换算成直觉：你说一句话，可能两百 token；模型回一句“我看一下”，再加一次工具调用，四百 token；工具把整个文件打回来，六千 token。三者不是一个量级。

03 · 三个增长源

历史、工具输出、系统追加

第一源：历史本身。每一轮至少追加两条（模型回复、工具结果），它们不会自己消失。第 20 轮的请求里，前 19 轮全在。

第二源：工具输出。这是最粗的一条。读文件、跑测试、搜代码，返回的都是成百上千行。它还有个别扭的地方：同一份内容你读两遍，就占两份 token；工具不会因为“重复”给你打折。

第三源：系统侧追加。提醒、待办状态、日期变化、技能列表、MCP 指令，都会在你不注意时加进来。它们单条不大，但每轮都加。

工具输出的形态也值得分清。读文件是“一次一大块”；搜索是“很多小块，每块带路径和行号”；跑测试是“结尾一段结论 + 前面几百行日志”。三种里最容易失控的是第三种：你只想要最后那句“3 failed”，却把整段日志收了进来。

三个源叠在一起，就形成了那条熟悉的曲线：前面平，中间陡，最后撞线。

04 · 曲线与两条线

增长不是线性的，刹车也不是

下图是一条示意曲线：横轴是轮次，纵轴是这次请求的输入 token。第 3 到第 8 轮因为连续读文件，斜率明显变陡；到第 12 轮碰到软线，触发一次压缩，曲线掉下来一截，然后继续往上爬。

两条线的数字来自真实 agent：Codex 的整段硬线取窗口的 95%，自动压缩软线取 90%已核实（openai_models.rs#L393-L395、context_window.rs#L60-L110）。Claude Code 的算法不同：先算有效窗口（模型窗口 − min(模型最大输出, 20_000)），再减 13,000 作为自动压缩线源码 v2.1.88（autoCompact.ts#L28-L49、#L62-L91）。

两条线在同一个地方刹车：不是等装满，而是提前留出一截。因为压缩本身也要发请求、也要占地方，真到 100% 才动，连压缩都塞不进去。

?动动脑

假设你每轮都让 agent 读一个 500 行的文件，粗略算 6,000 token，其他开销忽略。第 10 轮时，只算这些文件读取，历史里已经堆了多少？

提示：每一轮请求都带着前面所有轮的读取结果——第 10 轮的这一份请求里，躺着 10 份。

05 · 循环没有天然的终点

“做完了”是模型说的，不是循环说的

循环什么时候停？通常是模型认为任务完成、不再调用工具；或者外部设了步数、预算、时间上限。也就是说，结束条件是行为判断，不是容量判断。模型可以在上下文快满时仍然觉得“再读一个文件就好”。推断1

所以减量得写进循环设计里，不能等出了问题再补。减量有三种代价，从低到高：

  • 控制单次工具输出：读进来时就截断，或把全文落盘、只留路径和预览。
  • 裁剪历史：把旧工具结果换成占位符，不调用模型，便宜但不可逆（在活历史里）。
  • 压缩：请模型把旧历史写成摘要，最贵，也最容易丢细节。

工具确实在做前两件事。Codex 在工具输出写入历史时按策略截断，中间用 …N tokens truncated… 标记，被裁掉的原文仍留在 rollout 存档里；序列化和头部还另留 20% 余量已核实（truncate.rs#L17-L29、lib.rs#L17-L34）。Claude Code 则把超过阈值的工具结果整段落盘，消息里只留一个文件路径加前 2,000 字节预览；通用阈值是 50,000 字符源码 v2.1.88（toolResultStorage.ts#L27-L34、#L137-L199）。

Q没有傻问题

问：工具结果都是“证据”，删了它不就查不到了吗？

答：删的是上下文里的副本，不是原文。Codex 把被截掉的中间部分留在 rollout 存档，Claude Code 把超限结果写到磁盘上的 tool-results/ 目录，消息里留路径。模型需要时可以再读回来——代价是多一次工具调用，而不是永久失忆。这也解释了为什么“落盘 + 指针”比“直接丢”更常见。

06 · 什么时候必须减量

三个信号，都比报错早

等你看到“上下文超限”的报错，说明前面的信号都被忽略了。可观测的信号有三个：

  • 占用贴住软线：状态栏或 /context 显示已用九成，剩下的空间撑不过下一次读文件。
  • 开始重复提问：它问你第三轮就回答过的事，说明早期内容已经被挤到不重要的位置。
  • 约束被违反：你开头说的“别动 schema”被忘了。这一条最危险，因为容量看起来还宽裕。

前两个是容量信号，第三个是质量信号。第 4 章会解释：为什么容量没满，第三种也会发生。

看到信号，先别急着压缩。先问一句“这还是同一件事吗”：如果只是这一轮读得太多，控制工具输出就够；如果任务已经换了一半，压缩不如另开一局（第 6 章给判断图）。

07 · 收口

曲线是设计出来的

回头看那条曲线：它不是自然现象，是几个选择叠加的结果——工具输出封不封顶、历史留不留、压缩线画在哪。换一组选择，曲线就换一个形状。

下一章要拆掉一个更隐蔽的假设：只要窗口够大，曲线就永远不会撞墙。真的吗？

✓要点小结

  • 每采样一次就是一次完整请求，历史全量重发；一轮里可能有好几次采样。
  • 三个增长源：历史累积、工具输出、系统侧追加。工具输出通常最粗。
  • 增长不是线性的：连续读文件的那几轮，斜率会突然变陡。
  • 阈值是提前刹车：Codex 90% 软线 / 95% 硬线，Claude Code 用有效窗口减 13,000。
  • 循环的终点由“模型说完了”决定，不由容量决定，所以减量要提前设计。
