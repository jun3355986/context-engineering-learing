Agent 循环中上下文如何增长

上下文很少是一下子变长的：每轮多一点，积到最后就顶到了窗口上限。

  • 约 10 分钟
  • 前置：第 2 章
  • L1 → L2

读完你能做到

  1. 说清一轮循环里，上下文依次多了哪几段。
  2. 说出上下文增长的三个来源，并判断哪个涨得最多。
  3. 看懂增长曲线上的两条阈值线，知道什么时候必须减量。

01 · 第九轮，它问了一个你答过的问题

“你刚才说的那个配置，是在哪个文件？”

下午两点十分，你让 agent 修一个偶发失败的测试。前两轮很顺：它读了两个文件，改了一行，跑了一次测试。第三轮开始读日志，第四轮又读了三个文件。

第九轮，它问：「你刚才说的那个配置，是在哪个文件？」那句话你在第三轮就回答过。会话没有断，你也没清空，但它就是没接上。

场景 · 不是它变笨，是白板写满了

Agent 不是一次想完就交卷，它在循环（agent loop）里工作：模型看一遍材料，决定调用一个工具；工具返回结果，材料变多；模型再看一遍，决定下一步。每转一圈，白板上就多写几段。写到某一步，板子不够用了，就得擦掉一些，而你最早写上去的那句，可能正好被擦掉。

上下文是一轮一轮写满的，而且每轮怎么增长，有固定的规律。

02 · 一轮里发生了什么

你说话，模型调工具，工具交回结果

一轮（turn）通常是这样：先放进你的消息；模型采样（sampling）一次，也就是生成一次输出，可能是一段话，也可能是一次工具调用（tool call）；工具执行后交回工具结果（tool result）；这份结果作为一条新消息追加进历史，模型再采样一次。

关键在于：模型每采样一次，都是一次全新的请求。它没法接着上一次“在脑子里继续想”，每次都要把白板上的全部内容重新发一遍。所以“读文件并修改”这样一个动作，可能包含三四次请求，每次都带着前面的全部历史。

换成具体数字感受一下：你说一句话，大约两百 token；模型回一句“我看一下”再发起一次工具调用，大约四百 token；工具把整个文件内容返回，可能就是六千 token，比前两者大了一个数量级。

03 · 三个增长源

历史、工具输出、系统自动追加

来源一：历史本身。每一轮至少追加两条（模型回复、工具结果），它们不会自己消失。第 20 轮的请求里，前 19 轮的内容都还在。

来源二：工具输出。三者里它的体积最大：读文件、跑测试、搜代码，返回的动辄成百上千行。还要注意，同一份内容读两遍就占两份 token，不会因为重复而打折。

来源三：系统自动追加的内容。每轮发请求前，agent 会检查提醒、待办、日期、技能列表、MCP 指令这些项目有没有变化，有变化才追加一条，比如日期跨了一天、新连上一个 MCP、该提醒你看一眼待办了。单条都不大，但追加进去的内容会留在历史里，之后每轮都跟着重发，积少成多。

出处：以 Claude Code 为例：每轮请求前由 getAttachments() 收集这些附件，MCP 指令、agent 列表等只追加有变化的部分。源码 v2.1.88 attachments.ts#L743-L1003、#L1559-L1590

工具输出还分几种形态：读文件是一次一大块；搜索是很多小块，每块带着路径和行号；跑测试是前面几百行日志，加上结尾一段结论。最容易失控的是跑测试：你只想看最后那句“3 failed”，却把整段日志都收了进来。

三个来源叠在一起，就形成了下面这条曲线：开头平缓，中间变陡，最后顶到上限。

04 · 增长曲线与两条阈值线

上下文怎么涨，什么时候该压缩

下图是一条示意曲线：横轴是轮次，纵轴是每次请求的输入 token。第 3 到第 8 轮连续读文件，曲线明显变陡；到第 12 轮碰到软线，触发一次压缩，曲线掉下来一截，然后继续往上涨。

图里的两条线用的是 Codex 的数字：用到窗口的 90% 时自动压缩（软线），95% 是不能越过的上限（硬线）。Claude Code 的算法不同：先从模型窗口里扣掉给输出预留的部分（最多 20,000 token），得到有效窗口，再往下留 13,000 token，作为自动压缩的触发线。

出处：Codex 已核实 openai_models.rs#L393-L395、context_window.rs#L60-L110；Claude Code 有效窗口 = 模型窗口 − min(模型最大输出, 20_000) 源码 v2.1.88 autoCompact.ts#L28-L49、#L62-L91

两家算法不同，思路一样：不等窗口装满，提前留出一段空间就开始压缩。原因是压缩本身也要发一次请求，让模型读旧历史、写摘要，这次请求同样占窗口。等到 100% 才动手，连压缩请求都发不出去。

?先想一想

假设你每轮都让 agent 读一个 500 行的文件，粗略算 6,000 token，其他开销忽略。第 10 轮时，只算这些文件读取，历史里已经堆了多少？

提示：每轮请求都带着之前所有轮的读取结果，所以第 10 轮的请求里有 10 份。

05 · 循环没有天然的终点

什么时候算“做完了”，由模型判断

循环什么时候停？通常是模型认为任务完成、不再调用工具，或者碰到外部设置的步数、预算、时间上限。也就是说，停不停，看的是任务做没做完，不是窗口还剩多少。所以窗口已经用到九成时，模型照样可能再读一个文件。推断1

因此，减少上下文的办法要事先设计进循环里，不能等出了问题再补。常见做法有三种，代价从低到高：

  • 控制单次工具输出：结果太长时，读进来就截断；或者把全文存到磁盘，消息里只留文件路径和开头一段预览。
  • 裁剪历史：把旧的工具结果换成一句占位说明。不用调用模型，所以便宜；代价是改了就撤不回来，之后发给模型的请求里再也没有原文。
  • 压缩：让模型把旧历史写成摘要。要多调用一次模型，所以最贵，也最容易丢细节。

第一种几乎每个 agent 都在做，看两个例子。Codex 把工具输出写进历史时会截断：保留开头和结尾，中间换成一行 …N tokens truncated…。截掉的内容没有丢，完整原文还保存在会话存档（rollout 文件）里。截断预算还会多算 20%，因为输出放进请求时要包一层 JSON，前面还要加一行“已截断，原始共 N token、M 行”的说明，这些都要占地方。Claude Code 的做法是：工具结果超过阈值（默认 50,000 字符），就把全文存到磁盘，消息里只留文件路径和前 2,000 字节的预览。

出处：Codex 截断 已核实 truncate.rs#L17-L29，20% 余量与说明行见 with_serialization_allowance、formatted_truncate_text（lib.rs#L17-L34）；Claude Code 源码 v2.1.88 toolResultStorage.ts#L27-L34、#L137-L199

Q你可能会问

问：工具结果是排查问题的证据，删掉之后不就查不到了吗？

答：删掉的只是上下文里的那份副本，原文还在。Claude Code 把超长结果写进磁盘上的 tool-results/ 目录，消息里留着文件路径，模型需要时按路径读回来就行，代价只是多一次工具调用。Codex 把完整输出留在会话存档里，但没有给模型提供读存档的工具，模型要找回内容，只能重新读文件或重新跑命令（第 13 章细讲）。正因为能找回来，“存到磁盘、消息里留路径”比直接丢掉更常见。

06 · 什么时候必须减量

三个信号，都比报错早

等你看到“上下文超限”的报错，前面的信号其实早就出现了。能观察到的信号有三个：

  • 占用接近软线：状态栏或 /context 显示已用九成，剩下的空间可能撑不过下一次读文件。
  • 开始重复提问：它问你第三轮就回答过的事，说明早期的内容要么已经被压缩掉，要么被后来的大量内容淹没了。
  • 约束被违反：你开头说的“别动 schema”被忘了。这一条最危险，因为容量看起来还宽裕。

前两个是容量信号，第三个是质量信号。第 4 章会解释，为什么容量没满，第三种情况也会发生。

看到信号，先别急着压缩，先问自己：现在做的还是同一件事吗？如果只是这一轮读得太多，控制工具输出就够了；如果任务已经换了一半，与其压缩，不如新开一个会话（第 6 章有判断图）。

07 · 小结

曲线是设计出来的

回头看那条曲线，它的形状是几个设计选择共同决定的：工具输出要不要封顶，旧历史留不留，压缩线画在哪里。换一组选择，曲线就换一个形状。

下一章讨论一个更隐蔽的想法：只要窗口够大，曲线就永远碰不到上限，问题也就解决了。真是这样吗？

✓要点小结

  • 每采样一次就是一次完整请求，历史全量重发；一轮里可能有好几次采样。
  • 三个增长来源：历史累积、工具输出、系统自动追加。工具输出通常最大。
  • 增长不均匀：连续读文件的那几轮，曲线会突然变陡。
  • 压缩线都设在装满之前：Codex 是 90% 软线、95% 硬线，Claude Code 是有效窗口减 13,000。
  • 循环什么时候停，由模型判断任务是否完成，不看窗口还剩多少，所以减量要提前设计。
