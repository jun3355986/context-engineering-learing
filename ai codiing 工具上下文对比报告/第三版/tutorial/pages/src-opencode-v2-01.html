三入口触发与 due 判定

v2 把压缩拆成三个入口：每步开头的自动检查、溢出后的恢复、用户手动的命令。三个入口共用同一个 compact()，但预算与前置条件不同。真正决定「这一轮压不压」的不是阈值，而是 due() 里那两条不变量。

01 · 功能说明

三个入口，一个函数

auto：runStep() 在准备上下文之后、发请求之前调用 compact({ reason: "auto", context })。如果返回 completed，就换一条新的 assistant 消息 id、continue 重新跑这一步。已核实

overflow：steps.attempt() 捕获「上下文过长且尚未产出任何输出」的错误，调用 recoverOverflow，后者执行 compact({ reason: "overflow", context })；成功则重建上下文重发，同一步只允许一次。已核实

manual：/compact 往 inbox 塞一条 compaction 控制项，drain() 在步边界消费它，带上 reason: "manual" 调用同一个 compact()。已核实

三个入口的差别不在「压什么」，而在「预算多少」和「允不允许跳过」。

入口内部的前三道判断是共用的：

一，开关：trigger.reason !== "manual" && !settings.auto 时直接返回 skipped。手动压缩不受 auto 开关限制。已核实

二，到期：只有 auto 才检查 due()；overflow 与 manual 不检查——它们本身就是「必须压」的信号。已核实

三，预算：先按当前模型算 ceiling；如果模型窗口未知，用 UNKNOWN_WINDOW = 200_000 算一个 cap 给压缩请求用（但不用于触发）。overflow 时 budget = min(cap, floor(estimate × 0.7))，其余用 cap。已核实

// trigger 带 reason 与 context；settings 是运行时配置
const compact = Effect.fn("SessionCompaction.compact")(function* (trigger: Trigger): Effect.fn.Return<Outcome> {
  const settings = state.get()
  const context = trigger.context
 
  // 自动关闭时，只有手动还能压；overflow 也不行
  if (trigger.reason !== "manual" && !settings.auto) return { status: "skipped" }
  // 只有 auto 看 due；overflow / manual 是「必须压」的信号
  if (trigger.reason === "auto" && !due(context, calculateCeiling(context.model.limit, settings.buffer)))
    return { status: "skipped" }
  // 模型元数据声明支持原生压缩：走 provider，不写本地摘要
  const native = context.model.compaction?.type === "native"
  const agent = native ? undefined : yield* agents.get(Agent.ID.make("compaction"))
  const model =
    (agent?.model &&
      (yield* models
        .resolve({ ...context.session, model: agent.model }, catalog.available)
        .pipe(Effect.orElseSucceed(() => undefined)))) ??
    context.model // 压缩 agent 没配模型就用当前模型
  const ceiling = calculateCeiling(model.limit, settings.buffer)
  // 窗口未知：触发永远不成立，但压缩请求仍要有个目标大小
  const cap = Number.isFinite(ceiling)
    ? ceiling
    : calculateCeiling({ ...model.limit, context: UNKNOWN_WINDOW }, settings.buffer)
  // provider 刚拒过，说明估算低；第一次尝试就瞄准 70%
  const budget =
    trigger.reason === "overflow" ? Math.min(cap, Math.floor(estimateContext(context) * SHRINK_STEPS[0])) : cap
 
  // 若压缩 agent 换了模型，用它重新加载上下文的一小部分
  const selected = model === context.model ? trigger : { ...trigger, context: { ...context, model } }
  const compaction = native
    ? compactNatively(selected, budget, settings.keep)
    : summarize(selected, budget, settings.keep)
  return yield* compaction.pipe(
    Effect.matchEffect({
      onSuccess: (result) => publish(selected, result),
      onFailure: (failure) => publish(selected, failure),
    }),
  )
})

// 例外 1：最后一条就是刚完成的压缩 → 先让 runner 重建请求
const due = (context: SessionContext.Loaded, ceiling: number) => {
  const messages = context.messages
  const last = messages.at(-1)
  if (last?.type === "compaction" && last.status === "completed") return false
  // 例外 2：加密的原生窗口本地估不出大小，等 provider 回报一次
  const measured = messages.findLastIndex((message) => hasMeasuredPrompt(message, context.model.ref))
  if (measured < messages.findLastIndex(SessionProviderContext.isCheckpoint)) return false
  return estimateContext(context) >= ceiling
}

04 · 逐段解读

两道否决，两个预算

第 1 段　开关：为什么 overflow 也受 auto 约束

第一行判断是 trigger.reason !== "manual" && !settings.auto 就跳过。已核实也就是说，用户关掉自动压缩后，溢出也不会自动救——只有手动 /compact 能压。这是一个明确的产品选择：把「自动」的定义扩大到「所有非手动触发」，而不是只限阈值触发。

v1 的规则不同：isOverflow() 里 compaction.auto === false 直接返回 false，溢出信号根本不产生；但一旦产生，压缩流程不会再检查开关。已核实两者结果相近，语义不同：v1 是「不检测」，v2 是「检测但不压」。

第 2 段　due 的两条例外

第一条例外：最后一条消息是 status === "completed" 的压缩条目，直接返回 false。已核实因为压缩刚完成，runner 还没用新检查点重建请求；此时 estimateContext() 仍按旧消息估算，必然还是超阈值。不挡住就会连续压缩，每次都把上一次的摘要再摘要一遍。

第二条例外：measured（最近一次同 provider 的用量锚点）早于最后一个检查点，返回 false。已核实为什么？原生压缩（OpenAI Responses compact / Anthropic compaction beta）返回的是一段加密窗口，本地无法估算它的大小；只有 provider 下次回报 usage，才知道「压缩后到底多大」。在拿到这个数之前触发，等于用旧的大估算去压一个已经变小的上下文。

两条合起来说明：due() 不是「阈值判断」，而是「阈值判断 + 两个数据新鲜度检查」。它防的是「用过期数据做决定」。

第 3 段　ceiling：10% 与 16 000 取大

calculateCeiling() 的逻辑是：

window = limit.input || limit.context；window <= 0 返回 +∞；buffer 有值就用 window - buffer；否则 window - max(floor(window × 0.1), window ≥ 32_000 ? 16_000 : 0)。已核实

200k 窗口：max(20 000, 16 000) = 20 000，ceiling = 180 000。32k 窗口：max(3 200, 16 000) = 16 000，ceiling = 16 000。16k 窗口：window ≥ 32 000 不成立，max(1 600, 0) = 1 600，ceiling = 14 400。

为什么小窗口要留 10% 而不是 16 000？因为 16 000 已经接近半个窗口，留完就没有历史可压了。源码注释写得很清楚：「A window too small to give up RESERVE_MIN keeps 10%.」

未知窗口返回 +∞ 也值得注意：触发永远不成立（除非 provider 报溢出），但 cap 会用 UNKNOWN_WINDOW 算一个有限值给压缩请求。已核实这是「不知道多大，但总得给摘要请求一个目标」的折中。

第 4 段　overflow 的 0.7：为什么先自降一档

budget = min(cap, floor(estimateContext(context) × SHRINK_STEPS[0]))，而 SHRINK_STEPS = [0.7, 0.5, 0.35]。已核实溢出意味着 provider 刚刚拒绝了这份请求，说明本地估算偏低；如果还按 cap 去构造摘要请求，很可能第二次被拒。

0.7 不是「目标上下文大小」，而是「摘要请求允许的大小」。摘要请求会把要压缩的历史序列化后发给模型；如果历史本身就有 180k，按 180k 发还是会被拒。先降到 126k，就有更大概率一次成功。

这与 v1 的 overflow 处理不同：v1 在 overflow 模式下先把「触发溢出的那条用户消息」剥掉再压，压完再把它重放回去（compaction.ts#L340-L356、#L484-L487）。已核实v1 减的是「输入里的一条消息」，v2 减的是「摘要请求的目标大小」，再配合 deliver() 的 0.7 / 0.5 / 0.35 三轮收缩。

第 5 段　三种触发 reason，两种落盘 reason

Trigger 有三种：auto、overflow、manual。已核实但落到检查点上时只剩两种，因为 publish() 里有一行映射：

const reason = trigger.reason === "manual" ? "manual" : "auto"已核实

也就是说，溢出恢复产生的检查点，reason 记的是 auto。schema 的 CompactionCompleted.reason 也只允许 auto / manual。已核实

这个映射有一个实际后果：事后无法从检查点区分「正常到期压缩」与「溢出救火」。两者都记成 auto。要做这类统计，只能从别处取证据：溢出压缩的 tokens.before 通常非常接近窗口上限，或者去读日志里的 Compaction.Started / Compaction.Ended 事件（它在 L394 统一写 reason: "auto"，同样区分不了）。这是 beta 快照的一个可观测性缺口，不是设计意图的声明。

把三种 reason 与 omp 的六条触发放在一起看，会发现一个共同趋势：触发路径越多，记录字段越倾向于收敛。omp 的 reason 有四个值（overflow / threshold / idle / incomplete），但检查点里也只存 method 与统计数据，不存 reason。原因类似：检查点的职责是「重建上下文」，不是「记录运维事件」。想审计，要靠事件流。

第 6 段　走查：三步之内压不压

设窗口 200k、buffer 未设、模型有 limit.input = 200 000。ceiling 是 200 000 - max(20 000, 16 000) = 180 000。连续三步的估算如下：

步 estimate 最后一条 锚点 vs 检查点 due
1175 000user锚点更晚false（未到 180 000）
2182 000user锚点更晚true → 压缩
3182 000compaction（completed）—false（例外 1）

表注：估算值只用于演示；真实 estimateContext = 锚点实测 + 之后逐条 chars/4。

第 2 步压缩时 budget = cap = 180 000，keep = 15 000。摘要请求要把 older 部分文本化后发出去；如果装不下，deliver() 会先丢最旧的 exchange，再按 0.7 / 0.5 / 0.35 收缩。

第 3 步是例外 1 的典型场景：压缩刚完成，最后一条就是检查点，due() 直接返回 false。等到 runner 用新检查点重建上下文，最后一条变成新消息，估算也会从「新基线」重新算起——此时如果 measured 还早于检查点，仍会被例外 2 挡住。

如果模型窗口未知（limit.input 与 limit.context 都是 0），ceiling = +∞，第 1、2 步都不会触发 auto；只有 provider 报溢出才会压，且预算用 200k 重算出的 cap。这是「不知道多大就不主动压」的保守策略。

第 7 段　改的其实不是阈值，是估算

把 v1 与 v2 的公式并排，会发现阈值几乎一样。v1：usable = input - min(20 000, maxOutputTokens)；v2：ceiling = window - max(10%, 16 000)。200k 窗口、32k 输出时，v1 是 180 000，v2 也是 180 000。已核实

真正的差别在「拿什么比」。v1 用上一轮的 tokens.total，它只覆盖「上一轮请求 + 回复」；v2 用「锚点实测 + 锚点之后逐条估算」，覆盖「锚点之后新增的所有消息」。如果用户在两次压缩之间连发了五条长消息，v1 的数会明显偏小，v2 不会。

这也解释了为什么 v2 要加「锚点必须晚于检查点」：估算的可信区间是「从锚点到当前」，如果锚点在检查点之前，中间隔了一次压缩，估算的基数就错了。v1 没有这个问题，因为它每次都用最新一轮的实测值，天然在检查点之后——代价是它看不到「最新一轮之后」的新增。

所以两者的取舍是：v1 用「新鲜但覆盖窄」的数据，v2 用「覆盖宽但需要锚点」的数据。前者在连续对话里容易低估，后者在原生压缩后容易暂时不触发。没有一种估算在所有场景下都准。

第 8 段　手动压缩的两个坑

手动入口最容易被当成「安全阀」：自动不压的时候，用户按一下就好。但它绕过了 due()，也绕过了 settings.auto，于是有两个坑。

刚压完又压一次。用户看到上下文百分比还很高（因为百分比读的是旧 usage），再按一次 /compact。此时 compact({reason:"manual"}) 不看 due()，会把刚生成的检查点连同它的 recent 文本再摘要一遍。结果是「摘要的摘要」，信息损失叠加。v1 也有类似问题，但它至少在隐藏上一对压缩消息时做了处理。

重复排队。SessionPendingTable 上有一个部分唯一索引：uniqueIndex(...).on(session_id).where(type = 'compaction')。已核实它保证同一会话同时只有一条待处理的压缩控制项。没有这个索引，用户连点两次就会排队两条，第二条在第一条完成后立刻执行——正好是上一个坑。

两个坑的共同解法在产品层：手动压缩后禁用按钮，直到 Compaction.Ended 或 Failed 到达。服务端的唯一索引只是兜底，不是交互设计。

✓要点小结

  • 三个入口：auto（每步开头）、overflow（未产出时）、manual（inbox）；共用 compact()。
  • 关掉 auto 后，overflow 也不会自动压，只有手动能压。
  • due() 有两条例外：刚压完、锚点早于检查点；它们防的是「用过期数据决定」。
  • ceiling = window - max(10%, 16 000)；未知窗口返回 +∞，但压缩请求仍用 200k 算目标。
  • overflow 预算先乘 0.7，因为 provider 刚拒过，估算偏低。

05 · 与其他工具的差异

v1 看实测，v2 看锚点，pi 看尾部

触发判定是三家里差别最大的地方。v1 完全信任上一轮的 tokens，pi 用「最近一次 assistant usage + 之后累加」，v2 则要求「锚点必须晚于检查点」。三种做法对应三种失败模式。

三点对照：

一是「上一轮」与「锚点」的区别。v1 用上一轮的 total，前提是「上一轮之后没有新增消息」；一旦用户连着发了几条，这个数就偏小。v2 从锚点往后逐条加，能覆盖「锚点之后新增的消息」。pi 也是这个思路，但它会在压缩后丢弃旧 usage、全量重估——v2 用「锚点须晚于检查点」达到类似效果。

二是预算的保守程度。v1 的 reserved = min(20 000, maxOutputTokens)，v2 是 max(10%, 16 000)。对 200k 窗口，v1 留 20 000、v2 留 20 000，一样；对 32k 窗口，v1 留 min(20 000, 8 000) = 8 000，v2 留 16 000，v2 更保守。

三是入口的语义。pi 有「轮中」触发（工具结果落定、下一次 assistant 之前），v2 只有「每步开头」；omp 有六条，包括空闲维护。入口越多，压缩越及时，也越容易在不该压的时候压。v2 用 due() 的两条例外来收这个口子。

06 · 思考题

三道题，从算 ceiling 到判断 due

Q1

窗口 64k、buffer 未设。ceiling 是多少？如果 buffer = 8 000 呢？如果窗口未知呢？

提示（不给答案）

未设 buffer：window ≥ 32 000 成立，max(6 400, 16 000) = 16 000。

设了 buffer：直接 window - buffer，不再取 10%。

未知窗口：window <= 0，返回 +∞；但 cap 会用 200k 重算。

Q2

一次原生压缩刚完成，最后一条消息是 status: "completed" 的 compaction。下一轮 auto 会压吗？再下一轮呢？

提示（不给答案）

第一问看 due() 的第一条例外：last?.type === "compaction" && last.status === "completed" 直接返回 false。

第二问：runner 用新检查点重建请求后，最后一条不再是 compaction；但还要过第二条例外——如果 measured 仍早于检查点（provider 还没回报），依然不压。

所以原生压缩后可能连续几步都不触发，直到拿到一次真实 usage。

Q3
