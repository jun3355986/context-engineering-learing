01 · 六个碎片，拼不成一句话

“你都懂，但你说不清”

面试官问你：「你怎么理解 Agent 的上下文管理？」你脑子里冒出窗口、token、context rot、缓存、压缩、子代理，六个词各说两句，说完自己都觉得散。

问题不在知识量，在缺一张把它们串起来的图。串不起来的知识，用的时候调不出来。

场景 · 缺的不是概念，是顺序

上下文管理不是六个并列的技巧，是一条有先后顺序的流水线：先决定装什么，再算装了多少，装不下就减，减不动就隔离，最后用缓存、恢复、扩展、评估保证它长期跑得稳。顺序错了，技巧就互相打架。

说白了，一次请求有它的一生：组装、计量、减量、隔离、质量兜底。

02 · 主图：五段流水线

16 个格子，一条主链

图里的编号就是本教程主线 16 章的顺序。蓝色是不发起模型调用的环节，橙色是主链路上会发起模型调用的环节。虚线是回边——失败时往回走。

读这张图有个顺序：先看左边五段的名字，再看每段里的编号，最后看右边那条虚线。别一上来就盯 16 个格子，那样还是碎片。

03 · 五段各自在干什么

每段只回答一个问题

组装：装什么。决定这次请求里放哪些材料、按什么顺序放。第 1 到第 4 类都在这一段：请求骨架、规则合并、按需加载、动态注入。这一段决定了前缀长什么样，也就决定了第 5 章那笔缓存账。

这也是第 2 章要花一整章拆骨架的原因：第一段拼错了，后面每一段都在替它擦屁股。

计量：装了多少。第 5 类。用服务端 usage 加本地增量算占用，再和阈值比。它本身不改内容，只负责“报数”和“报警”。

减量：装不下怎么办。第 6 到第 9 类，按代价从低到高排：先控制单次工具输出，再裁剪历史，再压缩，最后才动多模态。这个顺序不是随意排的——越靠前越便宜，也越不容易丢关键信息。

隔离与延续：怎么不让它互相污染。第 10 到 12 类。子代理把探索关在另一个上下文里；会话时间线让历史可恢复、可分叉；跨会话记忆决定哪些东西值得带到下一次。

质量：怎么长期跑得稳。第 13 到 16 类。缓存友好让重复的部分不变贵；失败恢复处理溢出和压缩失败；扩展点让你在不改核心的情况下介入；评估回答“这套策略到底有没有变好”。

五段不是五个独立模块，是一条链：组装出问题，计量看得见；计量报警，减量才启动；减量失手，失败恢复兜底；兜底之后，缓存又成了新的约束。

拿一次普通请求走一遍：组装把系统提示、工具、规则、环境、历史拼成四万 token 的前缀；计量算出四万一千，离软线还远，于是这一段直接跳过；没有需要隔离的探索，子代理不启动；缓存因为前缀没变而命中大半。整条链上真正“动手”的只有第一个格子和最后一个格子，中间三段都在待命。

只有出问题时，中间三段才登场。这也是为什么很多人对它们没感觉——平时它们确实什么都不做。

04 · 哪些环节调模型

大多数环节是“改写文本”，不是“再问一次”

这张图最实用的一层信息，是分清“花钱的环节”。

  • 不调模型：规则合并、按需加载、注入、计量、工具输出截断、历史裁剪、缓存打点、评估统计。它们是本地计算，快，也便宜。
  • 调模型：压缩、子代理、以及失败恢复里的压缩重试。它们要再发一次请求，慢，也贵。
  • 看实现：跨会话记忆的写入通常是一次后台调用，读路径只是注入；多模态的“转文字描述”如果由模型生成，也算一次调用，但 Codex 与 Claude Code 目前都没有这条路径。

分清这一点，你就能预判动作的代价：裁剪旧工具结果是“改投影”，几乎瞬间完成；压缩是“再跑一遍模型”，要等，要钱，还可能丢细节。第 3 章那条增长曲线上的每次回落，背后都是一次真实的模型调用。

还有一层容易被忽略：压缩产出的不只是摘要。Claude Code 压缩完会按固定清单重新附带最近修改的最多 5 个文件（每个不超过 5,000 token，总预算 50,000）、plan 文件、本会话调用过的技能正文源码 v2.1.88（compact.ts#L122-L131、#L517-L585）。所以压缩后的上下文不是“只剩一段摘要”，而是“摘要 + 一批必需品”。这也解释了为什么压缩省下的空间，往往比你估的少。

05 · 回边：失败不是终点

溢出之后，流程会往回走

主链是向下的，但真实运行里有一条向上的虚线：请求溢出或压缩失败时，流程回到减量，重新选切点、重新压缩，再试一次。

这条回边有两个现实约束。第一，重试有次数上限：Claude Code 连续 3 次自动压缩失败就熔断，本会话不再尝试，避免每轮都打一次注定失败的请求源码 v2.1.88（autoCompact.ts#L241-L351）。第二，压缩请求自己也可能超窗：Codex 的做法是删掉最旧一条再重试，只剩一条还超，就只能报错已核实（compact.rs#L345-L380）。

所以“回边”不是万能补救。到了某一步，系统只能承认失败，把错误交给你——这也是为什么第 6 章那几个动作仍然需要人来选。

回边还分主动和被动。主动的是“快到线了就压缩”，由计量触发；被动的是“服务端已经拒绝，再压缩一次重试”。Claude Code 的被动路径每轮只允许尝试一次，成功后用专门的状态重跑本轮源码 v2.1.88（query.ts#L1150-L1183）。被动压缩的代价更高：你已经付了一次被拒绝的请求。

06 · 收口：入门结束

你现在有一张地图了

七章下来，你应该能回答四个问题：窗口是什么、里面装了什么、它怎么变多、怎么才能既装得下又用得好。剩下的，是把这张图上的每一格拆开，看八个工具各自怎么做。

这张图也可以当复习工具用。合上教程，自己画一遍五段；画不出来，说明某一段你还没真的理解。画出来之后，再把 16 个编号填进去；填错的那一格，就是下一章该精读的地方。

第二部分每一章开头，你都可以回到图 1 找一个编号：那一章讲的就是那个格子。第 13 类讲缓存，你会想起第 5 章的失效点；第 8 类讲压缩，你会想起第 3 章的曲线和第 6 章的取舍。

Q没有傻问题

问：如果我要自己写一个 Agent，这 16 类要全做吗？

答：不用。最小可用版本只需要三样：组装（第 1 类）、计量（第 5 类）、单次工具输出控制（第 6 类）。这三样能让你看见上下文、并且不让它瞬间爆掉。压缩、子代理、记忆这些，等你真的遇到“一轮任务跑几十步”的场景再加——先加复杂度，往往会先得到一堆难查的 bug。

✓要点小结

  • 五段主链：组装 → 计量 → 减量 → 隔离与延续 → 质量。
  • 16 类各归其位；减量内部按代价从低到高排：输出 → 裁剪 → 压缩 → 多模态。
  • 会再发模型请求的是压缩、子代理和压缩重试；跨会话记忆的写入多在后台另算。
  • 失败有一条向上的回边，但受重试次数限制，不是万能兜底。
  • 最小可用版本：组装 + 计量 + 单次输出控制，其余按需加。
