用 section 补丁保住前缀缓存

系统提示词最容易变成「每次都整段重发」的东西：换了个目录、装了个技能、规则文件改了一行，整块提示就变了，缓存从第一个字节开始失效。pi 的解法是把提示词拆成具名 section，变化时只写一条补丁，让旧的那几段字节原样不动。

读之前

「前缀缓存」要求请求开头有一段字节级不变的前缀。系统提示词通常就在开头，所以它的任何改动都会让缓存从改动处失效。本节讨论的不是「怎么让提示词更短」，而是「怎么让没变的部分真的没变」。

01 · 功能说明

提示词不是一整块字符串，而是八个小格子

buildSystemPromptSections() 返回一个 Record<string, string>：键是 section 名，值是已经渲染好的文本。只有 preamble 是裸文本；其余每个 section 都会被包成同名 XML 标签，例如 <rules>…</rules>、<project_context>…</project_context>。已核实标签不是装饰：模型后续收到的补丁会用同一个标签名，模型因此能把「这段是新版 rules」对应到原来的位置。

section 化的真正目的不是「好读」，而是让「哪一块变了」变成一个可以比较的字符串。

顺序是固定的：preamble → tools → rules → docs → addendum → project_context → skills → cwd，最后接调用方通过 sections 传入的自定义 section。已核实固定顺序有两个好处：同一份配置每次渲染出的字节完全一致；模型读到的结构稳定，不会因为某个 section 缺失而错位。

组装完之后，_preparePromptAndToolLoadout() 拿「模型当前已有 sections」与「本次期望 sections」做差：只把变化的键写进一条新的系统消息，content 留空，sections 放补丁；没变化就返回 undefined，一条消息都不加。已核实这条消息不会替换历史里的旧系统消息，它只是追加在转录里。

请求真正发出时，packages/ai 有两种处理方式：支持中途系统消息的 provider（例如 Anthropic）保留这条消息，把它渲染成「Updated system prompt section "rules": …」；不支持的 provider 会把所有系统消息折叠成一条，按名字重放补丁后重新渲染完整提示词。已核实这个分叉很关键，第 4 节会专门讲它对缓存的真实影响。

// previous 是「模型已有」的 section 表，value 可能为 null（已删除）
export function diffSystemPromptSections(
    previous: Record<string, string | null>,
    current: SystemPromptSections,
): Record<string, string | null> | undefined {
    const patch: Record<string, string | null> = {};
    for (const [name, text] of Object.entries(current)) {
        if (previous[name] !== text) patch[name] = text; // 新增或改值
    }
    for (const name of Object.keys(previous)) {
        if (current[name] === undefined) patch[name] = null; // 删掉
    }
    return Object.keys(patch).length > 0 ? patch : undefined;
}

04 · 逐段解读

三个判断，一条分叉

第 1 段　自定义提示词会带走三个 section

看 if (customPrompt) 的分支：只设置 preamble。也就是说，一旦用户提供了自定义系统提示词，tools、rules、docs 三段就不会生成，而 addendum、project_context、skills、cwd 仍然照常追加。这个边界很容易读错：不是「自定义提示词替换整块」，而是「替换前言，结构性 section 继续存在」。

为什么保留后四个？因为它们承载的是「环境事实」：追加指令、项目规则、可用技能、当前目录。这些事实与「助手是谁」无关，删掉会让模型失去定位能力。反过来，tools 和 rules 是对前言里行为约定的展开，前言被换掉后它们可能自相矛盾，所以一起省掉。

第 2 段　隐藏工具：声明与提示词必须一致

declaredTools 先减掉 hiddenTools；随后 tools 列表、rules、skills 的读取提示都基于这个减法后的列表。已核实源码注释解释了原因：被隐藏的工具仍然可以通过另一个工具到达，但请求里不带它的声明，提示词就不能假装它存在。

这一点和缓存有关：hiddenTools 来自 prepareLoadout 钩子，可能逐轮变化。如果它变了，tools 和 rules 两个 section 都会变，补丁里就会出现两大段。反过来，只要 loadout 稳定，这两段就一个字节都不动。

cwd 那行有一个小动作：cwd.replace(/\\/g, "/")。Windows 路径统一成正斜杠，避免「同一目录、两种写法」造成的假变更。这是一个典型的缓存友好细节——它不改变语义，只消除噪声。

第 3 段　差分：为什么需要 null

两个循环不对称。第一个遍历 current：值不同就写进补丁。第二个遍历 previous：current 里没有这个键，就写 null。如果没有第二个循环，「删除」就无法表达——接收方会把缺失当成「没变化」，于是一个已经被移除的 section 永远留在提示词里。

什么时候会删除？最典型的是 skills：这次加载到了技能，下次技能目录被清空，skills 键就消失了。还有 project_context：切换到没有规则文件的目录。这两种情况都必须让旧 section 消失，否则模型会拿旧技能清单去调用不存在的技能。

返回值是 undefined 而不是空对象，也有意义：调用点用 sections ? {...} : undefined 判断要不要造消息。空对象在 JS 里是真值，如果返回 {}，每轮都会追加一条空补丁，转录里堆满无意义的系统消息。

第 4 段　分叉：补丁最终怎么变成请求

这是本节最容易被忽略、也最值得记住的一处。packages/ai 在 resolveTranscript() 里按 supportsMidConvoSystemMessages 分成两条路：

支持中途系统消息的 provider（如 Anthropic）保留转录里的多条系统消息。请求里第一条系统消息是最初的完整提示词，后续补丁各自渲染成一段「Updated system prompt section "rules": …」。已核实前缀因此稳定：第一条系统消息永远是第一次那八段。

不支持的 provider 走 collapseSystemMessages()：把全部系统消息折叠成一条，按顺序重放补丁（null 删除、其他覆盖），再渲染成完整文本。已核实此时发出去的仍是整段新提示词，前缀从第一个变化的 section 起就变了。

所以「section 补丁保住前缀缓存」这句话有前提。在支持中途系统消息的链路上，它保住的是请求前缀；在折叠链路上，它保住的是转录可读性与补丁体积，缓存收益接近于零（除了「没变化时根本不发」这一条仍然成立）。opencode v1 的整段重拼、v2 的「基线 + 增量」也是同一个分叉的不同答案，第 5 节展开。

一个反直觉的结论

「只发变化」并不自动等于「缓存命中」。真正决定命中的是provider 看到的字节序列。如果传输层必须把补丁重放成完整提示词，那么补丁只节省了存储和带宽，没有节省缓存。评估一个「增量提示词」设计时，先问：这个 provider 支持在对话中途插入系统消息吗？

第 5 段　section 的稳定性排序：谁该放前面

既然补丁按 section 生效，一个自然的问题是：哪个 section 应该排在前面？答案不是「重要的放前面」，而是「变得最少的放前面」。因为前缀缓存的断点从第一个变化的字节开始，越靠前的 section 变化，后面跟着失效的越多。

section 内容来源 变化频率 位置评价
preamble前言内置文本或 customPrompt几乎不变最前，合理
tools工具清单loadout + snippets换工具集时变靠前，可接受
rules行为规则工具 guideline随工具集变与 tools 绑定
docs文档路径安装路径几乎不变稳定
addendum追加指令用户配置低稳定
project_context规则文件AGENTS.md 等编辑时变靠后，合理
skills技能清单技能目录装/卸时变靠后，合理
cwd当前目录运行时切换目录时变最后，合理

表注：顺序来自 buildSystemPromptSections() 的插入顺序，不是按字母或重要性排序。自定义 section 追加在最后。

这个排序基本符合「越易变越靠后」的原则，只有一个例外：rules 夹在 tools 与 docs 之间，而它随工具集变化。如果某次 loadout 只换了一个工具，tools 与 rules 都会变，docs 之后的 section 也一起失效。已核实这不是 bug，而是「工具清单与规则必须一致」的代价：两者都由 declaredTools 决定，不能拆开。

自定义 section 的位置值得单独提醒。for (const [name, content] of Object.entries(customSections)) 用对象插入顺序追加；如果扩展在两次运行里以不同顺序注册 section，即使内容完全一样，渲染结果的字节顺序也会变。已核实差分看到的是「两个 section 的值都变了」，于是发两条补丁——其实只是顺序换了。修法很简单：注册时按名字排序，或在扩展侧保证稳定顺序。

排障时怎么定位这种抖动？在 _preparePromptAndToolLoadout() 后面打一行日志，输出 Object.keys(sections ?? {})。如果每轮都出现同样的键，说明有东西在稳定地改变它们；再逐个 section 对比 buildSystemPromptSections(options) 与 getCurrentSystemMessage(messages)?.sections 的值，就能找到源头。常见原因有三个：cwd 被解析成绝对路径但分隔符不一致、技能列表顺序不稳定、工具 loadout 受权限检查影响逐轮变化。

第 6 段　补丁机制的三个边界

section 补丁不是万能的。三个边界值得记住：

强制提示词。forceSystemPrompt 一旦设置，请求头会被投影成一段不透明文本：_installAgentForcedPromptProjection() 把系统消息折叠成一条，用强制文本替换头部。已核实结构化 sections 仍然照常差分、照常持久化，但它们在请求里被强制文本盖住。所以补丁的缓存收益对这段头部不生效——强制文本只要变一个字，整个前缀就断。扩展想用强制提示词，就要接受这个代价。

工具增删走另一条通道。工具变化不写进 sections，而是 toolsAdded / toolsRemoved。两条通道分开的好处是「提示词补丁」与「工具声明」互不干扰；坏处是「工具变了但提示词没变」时，模型可能按旧规则调用新工具。源码用「tools 与 rules 都由 declaredTools 生成」来保证一致，但扩展仍可能只改一边。

自定义 section 的命名。SYSTEM_PROMPT_SECTION_NAME 要求小写字母开头、只含小写字母/数字/下划线/连字符，且不能叫 preamble。已核实不合法的名字会直接抛错，而不是跳过。这是「宁可启动失败，也不要生成一个模型对不上的标签」的选择。

三个边界合起来说明：补丁机制的稳定性依赖「所有变化都走同一条渲染路径」。任何绕开 buildSystemPromptSections() 的改动，都会让差分看到假变化，或者让模型看到不一致的提示词。

✓要点小结

  • 提示词拆成八个具名 section，只有 preamble 裸文本，其余包同名标签。
  • customPrompt 只替换前言，tools / rules / docs 随之消失，其余照常。
  • 差分返回补丁：改值写新值，删键写 null，无变化返回 undefined。
  • 补丁是追加进转录的；请求时按 provider 能力决定「保留为中途系统消息」还是「折叠重放」。
  • 只有支持中途系统消息的链路，补丁才真正保住请求前缀；折叠链路只省存储。

05 · 与其他 agent 的差异

四家都在做「只发变化」，差在变化的粒度

粒度的排序大致是：Codex 按文件快照（整份 AGENTS.md 变了就重发这一份）、pi 按section、opencode v2 按指令源（还能发 unified diff）、Claude Code 按附件源。粒度越细，补丁越小，但重建逻辑越复杂。

三点对照：

一是删除语义。没有删除语义的差分是不完整的：文件被删、技能被卸载、目录切换，都会让某个 section 消失。pi 用 null，Codex 用单独的移除通知，v2 在 delta 里用 "removed" 标记。三种写法，同一个需求。

二是补丁的持久性。pi 把补丁当普通消息存进转录，重放时合并；v2 把渲染好的增量文本冻结进事件，理由是「事后无法重建 Location 作用域的源」。前者轻，后者可审计。代价也不同：pi 的转录会随着补丁增多而变长，v2 的事件流同样只增不减。

三是失败模式。pi 的差分只比较「当前渲染结果」与「转录里重放出来的 sections」。如果某个扩展在 before_agent_start 里改了提示词选项但没走同一条渲染路径，差分可能反复抖动，每轮都发一条补丁。v1 没有这个问题——它每轮都整段重发，永远不会「漏发」，只是永远不命中缓存。

先想 section 的顺序：time 如果排在 cwd 之前，它后面所有 section 的字节都跟着移动；如果排在最后，至少只有它自己变。

再想 provider：对折叠型链路，任何 section 变化都会导致整段重渲染，排最后也救不了前缀。omp 的做法是把日期/cwd 提醒移到「每次请求的首个用户轮」，完全离开系统提示词。

最后一个问题：这个时间戳真的需要精确到分钟吗？如果只需要日期，变化频率会从每 10 分钟降到每天一次。
