01 · 功能说明

把「一段提示」拆成「一组可缓存的段」

getSystemPrompt() 的返回类型是 Promise<string[]>，不是 string。数组里每一项是一段完整的提示文本，顺序就是拼装顺序。数组被分成三部分：静态段（身份、通则、做事方式、行动准则、工具使用、语气、输出效率）、边界常量 __SYSTEM_PROMPT_DYNAMIC_BOUNDARY__、以及由注册表管理的动态段（会话指引、记忆、环境、语言、输出风格、MCP 指令、scratchpad、工具结果清理提示等）。源码 v2.1.88

数组不是为了好看，是为了让下游能按「段」打缓存标记，而不是把整段提示当成一个不可分割的字节块。

下游有两步。第一步 splitSysPromptPrefix() 把数组切成最多四块：计费/归属头、CLI 前缀、边界之前的静态内容、边界之后的动态内容。第二步 buildSystemPromptBlocks() 给每一块套上 cache_control：静态块可以带 scope: 'global'，动态块不带 scope。源码 v2.1.88

这个设计的关键不在「分段」本身，而在边界的位置。边界之前的内容对所有组织、所有会话都一样，可以跨组织复用；边界之后的内容含用户/会话特定信息，不该跨组织缓存。把这两类内容放在同一个字符串里，服务端只能整段缓存或整段不缓存；拆成数组并显式标出边界，才能让静态部分享受更广的缓存范围。推断

先说明一个容易误解的点：动态段「动态」不等于「每轮都变」。绝大多数动态段在会话内是稳定的：语言、输出风格、环境信息、记忆内容，通常只在会话开始时算一次。真正每轮重算的只有显式标了 DANGEROUS_uncached 的段，例如 MCP 指令。理解这一点，才不会把「动态」误读成「每轮重新生成」。源码 v2.1.88

为什么一定要用数组，而不是先拼成一个字符串再切？因为字符串一旦拼好，段与段之间的边界就只能靠「约定的分隔符」来猜。猜错一个分隔符，静态内容就可能被划进动态块，或者反过来。数组把边界变成类型系统的一部分：每个元素天然是一段，下游只需要知道「第几项之前是静态」即可。这也是为什么边界常量本身也是数组里的一个元素，而不是一个注释标记。推断

这套结构还有一个副作用：空段可以直接返回 null，由最后的 filter 统一剔除。这样每个段函数不需要关心「我是不是最后一个」「要不要补换行」，只需要返回字符串或 null。拼装逻辑集中在 return 一处，阅读时能一眼看到完整顺序。源码 v2.1.88

但 filter 也带来一个可观测性问题：如果某个段返回 null，最终数组里不会留下任何痕迹。调试时你只能看到「少了这一段」，看不到「它为什么被过滤」。这也是为什么源码给每个段起了名字：名字是唯一的线索，日志与缓存都按名字索引。推断

名字还有一个作用：它是缓存键。改名字等于换了一个新段，旧缓存永远命中不了；改内容但保留名字，才会在「下一次计算」时更新值。重构时如果把 env_info_simple 改名，表面看只是重命名，实际会让所有会话的这段缓存失效一次。推断

export async function resolveSystemPromptSections(
  sections: SystemPromptSection[],
): Promise<(string | null)[]> {
  const cache = getSystemPromptSectionCache() // 会话级缓存
 
  return Promise.all(
    sections.map(async s => {
      if (!s.cacheBreak && cache.has(s.name)) {
        return cache.get(s.name) ?? null // 命中：连 null 也直接返回
      }
      const value = await s.compute() // 未命中：现算
      setSystemPromptSectionCacheEntry(s.name, value)
      return value
    }),
  )
}

04 · 逐段解读

三段代码，三个边界

第 1 段　静态七段：顺序就是契约

七个静态段按固定顺序调用：身份/简介、系统通则、做事方式、行动准则、工具使用、语气风格、输出效率。顺序不是随手排的，它决定了模型读到约束的先后：先知道「我是谁」，再知道「怎么做事」，最后知道「怎么说话」。源码 v2.1.88

第三段是条件段。如果输出风格配置存在且 keepCodingInstructions 明确为 false，这一段返回 null，最终被 filter 掉。也就是说，所谓「静态七段」在实际请求里可能是六段。教程里为了叙述方便说「七段」，读代码时要记住它有一个合法的缺省分支。源码 v2.1.88

静态段的「静态」是相对于会话而言：它们不含 cwd、日期、用户输入，只依赖工具集与输出风格。工具集在会话内通常稳定，输出风格更稳定。因此这些段适合放在边界之前，享受更广的缓存范围。推断

把七段的职责拆开看，会发现它们覆盖的是「行为约束」的不同层次：身份段回答「你是谁」，系统通则回答「哪些事不能做」，做事方式回答「接到任务怎么推进」，行动准则回答「什么时候该停、什么时候该问」，工具使用回答「怎么调用工具」，语气与输出效率回答「怎么说话、说多长」。这些内容共同构成模型的「岗位说明书」，但它们都不依赖具体仓库或具体用户，所以可以跨会话复用。推断

静态段也不是完全无输入：身份段与做事方式段依赖 outputStyleConfig，工具使用段依赖 enabledTools。如果会话中途工具池变了（比如 MCP 连接），工具使用段的内容会变，静态块就不再字节稳定。源码没有为它单独标 DANGEROUS，说明工具池变化被视为「会话级事件」，通常伴随清空或重建，而不是每轮抖动。推断

第 2 段　边界：一个字符串常量，三处代码依赖

边界不是注释，也不是空行，而是一个真实存在的字符串常量 __SYSTEM_PROMPT_DYNAMIC_BOUNDARY__。它被放进数组，随后被 splitSysPromptPrefix() 用严格相等找到并丢弃；它之前的内容归为静态块，之后的内容归为动态块。源码 v2.1.88

这个常量的注释写得很重：「Do not remove or reorder this marker without updating cache logic in …」，并点名了两个下游文件。原因是它同时承担三个职责：数组里的分隔符、切块函数的定位锚、缓存 scope 的分配依据。任何一处改动，只要没同步另外两处，就会出现「静态内容被当成动态」或「动态内容被当成静态」的错误。源码 v2.1.88

边界只在 shouldUseGlobalCacheScope() 为真时插入。第三方 provider 或缺少全局缓存能力时，数组里没有这个常量，splitSysPromptPrefix() 会退化为「归属头 + 前缀(org) + 其余(org)」三块。也就是说，边界是「有全局缓存才启用」的优化，不是所有环境都存在。源码 v2.1.88

第 3 段　动态注册表：稳定的是「名字」，不是「值」

动态段用 systemPromptSection(name, compute) 注册。名字是稳定键，值是计算函数。十个基础段分别是 session_guidance、memory、ant_model_override、env_info_simple、language、output_style、mcp_instructions、scratchpad、frc、summarize_tool_results。另有三个特性门控段：numeric_length_anchors、token_budget、brief。源码 v2.1.88

注册表的意义是把「这一段怎么算」与「这一段在数组里的位置」分开。位置由数组字面量决定，计算由 compute 决定。要改某段的算法，只改 compute；要调顺序，只动数组。两者互不牵连，代码评审时也容易看出改动影响的是「内容」还是「顺序」。推断

这些段的「动态」程度并不一样。env_info_simple 依赖 cwd、平台、日期，跨天或换目录才变；memory 依赖记忆文件，文件改了才变；output_style 依赖配置，基本不变；mcp_instructions 依赖 MCP 连接状态，可能在两轮之间变。把它们都放在边界之后，是因为它们都含「用户/会话特定」信息，不适合跨组织缓存；但它们的失效频率差异很大，所以只有 MCP 段被标为每轮重算。源码 v2.1.88

这也带来一个设计上的不对称：同样在动态区，env_info_simple 有记忆化，MCP 指令没有。判断标准不是「这个段重不重要」，而是「它会不会在没有清空事件的情况下自己变」。环境信息的变化有明确触发点（跨天、换目录、worktree），MCP 连接没有统一的清空入口，所以只能每轮重算。推断

第 4 段　记忆化：为什么连 null 也要缓存

resolveSystemPromptSections() 先看 cache.has(name)，命中就返回缓存值；未命中才 await compute()，再写回。注意判断的是 has，不是 get() !== undefined。这意味着「这一段算出来是 null」也会被记住，下一轮不再重算。源码 v2.1.88

为什么 null 要缓存？因为 compute 可能很贵：读记忆文件、扫技能目录、算环境信息，都是 I/O 或遍历。如果某个段在当前会话里不适用（比如没有语言配置），它每轮都会返回 null；不缓存的话，每轮都要白跑一次 I/O。缓存 null 等于记住「这个会话不需要这一段」，而不是「还没算过」。推断

代价是：如果某个段从 null 变成有值（比如会话中途加载了语言配置），缓存不会自动失效，必须显式清空。这也是为什么 clearSystemPromptSections() 存在，以及为什么它不只在大动作（/clear、/compact）时调用，还在会话恢复、worktree 切换时调用。源码 v2.1.88

第 5 段　DANGEROUS_uncached：什么时候值得每轮重算

DANGEROUS_uncachedSystemPromptSection() 返回 cacheBreak: true，记忆化逻辑会跳过它，每次都 await compute()。当前代码里只有 MCP 指令用了这个构造函数，理由写在调用处：MCP 服务器可能在两轮之间连接或断开，缓存住旧指令会让模型按已经失效的工具说明行动。源码 v2.1.88

第三个参数 _reason 只用于代码评审，运行时完全不读（下划线前缀就是「未使用」的约定）。也就是说，「为什么值得破坏缓存」这件事没有强制校验，只能靠评审。这是一个很诚实的设计：把风险写在函数名里（DANGEROUS），把理由留给人类。源码 v2.1.88

「每轮重算」不等于「每轮都破坏缓存」。如果算出来的字节和上一轮相同，缓存仍然命中；只有内容真的变了，才会从这一段开始失效。注释写的是「This WILL break the prompt cache when the value changes」，限定词是「when the value changes」。源码 v2.1.88

第 6 段　缓存几何：分段省下的到底是什么

很多人以为「动态段放后面，改了只失效后面」。这只对了一半。系统提示在请求里位于消息之前，动态段又是系统提示的最后一部分；它一变，后面所有消息的缓存前缀都跟着失效。真正被保住的是边界之前的静态块，而不是消息历史。推断

那分段还有什么意义？意义在 scope。静态块可以标 global，跨组织复用；动态块不标 scope，避免把用户特定信息写进全局缓存。如果没有边界，整段系统提示只能按 org 缓存，复用范围小一个层级。省下的不是「一次失效的长度」，而是「每次命中能复用的范围」。推断

这也解释了为什么 DANGEROUS_uncached 的注释强调「late MCP connect」：MCP 连接是会话中途事件，一旦指令变化，动态块变化，消息前缀失效；但如果把它缓存住，模型会一直看到旧指令。两害相权，Claude Code 选择「正确性优先，缓存失效可接受」。推断

从账面上看，这个选择并不便宜：MCP 指令往往包含多个服务器的工具说明，可能占几千 token；连接一次、断开一次，就会让后续消息的缓存前缀失效两次。但如果不这样做，模型可能调用一个已经不存在的工具，或者漏掉一个新接入服务器的使用约束。前者是「多花钱」，后者是「做错事」，优先级很清楚。推断

更一般地说，缓存友好的设计不是「永不失效」，而是「让失效发生在可控的位置」。Claude Code 把易变内容集中到动态区，把静态区隔在边界之前，等于把「失效的爆炸半径」限制在边界之后；至于边界之后是几千 token 还是几万 token，取决于动态段本身的大小，而不是整个系统提示。推断

第 7 段　代价：缓存范围与新鲜度的取舍

这套设计把「新鲜度」交给了显式的清空事件。环境信息、语言、输出风格在会话内不会自己变，所以记忆化安全；cwd 变了、worktree 切了，由工具主动清空；MCP 连接变了，交给 DANGEROUS_uncached 每轮重算。每种变化都有对应的处理路径，没有一条是「自动检测所有变化」。源码 v2.1.88

代价是「漏清空」。如果某个新功能引入了会中途变化的段，却忘了接清空事件，模型会一直看到旧值，而且很难排查——因为缓存命中时，compute 根本不会执行。这也是为什么源码把 DANGEROUS 写进函数名：它在提醒后来者，缓存不是免费的，新鲜度需要显式付费。推断

✓要点小结

  • getSystemPrompt 返回字符串数组：静态段 → 边界 → 动态段。
  • 边界只在全局缓存可用时插入；没有边界时退化为三块 org 缓存。
  • 动态段按名字记忆化，命中就返回，连 null 也缓存。
  • DANGEROUS_uncached 每轮重算，但只有值变化才破坏缓存。
  • 分段真正省下的是「静态块的复用范围」，不是「消息历史的失效长度」。

05 · 与其他工具的差异

同样是分段，分法完全不同

「把系统提示拆成段」不是 Claude Code 独有的做法。pi、oh-my-pi、DeepSeek Harness 都拆，但拆的粒度、拼接方式、失效机制各不相同。下面这张表按「段怎么定义、怎么拼、怎么失效」三列对比。推断

← 左右滑动查看全部列，首列固定 →

工具 段怎么定义 怎么拼 怎么失效 来源

表注：来源为各工具固定提交的源码与官方文档（Claude Code v2.1.88 源码，pi 提交 b45e0eb，omp 提交 f979f46，dsh 为同仓文档口径，opencode v1 tag v1.19.0）。

第一个对照是「段是数据结构还是拼接约定」。Claude Code 与 pi 都把段当成真实对象：有名字、有计算函数、有缓存状态；opencode 只是把四类块拼成字符串，段本身不保留身份。前者能做「按段失效」，后者只能「整段重建」。这也解释了为什么 opencode 的缓存更脆弱：任何一块变化，整条 system 字符串都变。推断

第二个对照是「失效是拉还是推」。Claude Code 用「显式清空 + 记忆化」，是推模式：谁变了谁负责清；pi 用「section patch」，是拉模式：每轮比较期望值与当前值，只发差异；omp 把易变内容移到尾部，用位置换稳定；dsh 把系统提示当成会话事件，用「替换节点 / 追加 update」两种写入语义。推模式简单，但漏清空就陈旧；拉模式稳，但每轮要算 diff。推断

第三个对照是「边界是否显式」。Claude Code 用一个真实字符串常量做边界，并警告不要移动；omp 用「<project-context> 永远最后」这个位置约定；pi 用 section 名；opencode 没有边界。显式边界的好处是下游可以按位置切块，坏处是多一个必须同步维护的契约；隐式约定更灵活，但更难保证所有调用方都遵守。推断

第四个对照是「缓存范围」。Claude Code 的边界服务于 global scope，目标是跨组织复用静态前缀；pi 的 section patch 服务于「不重发未变段」，目标是减少请求体积；omp 把易变内容移到尾部，目标是让前缀字节稳定；dsh 把系统提示当成会话事件，目标是让它可以被重放和替换。四个目标不一样，所以四种实现的「成功指标」也不一样：Claude Code 看跨组织命中率，pi 看 patch 体积，omp 看前缀稳定时长，dsh 看重放一致性。推断

这也是读源码时最容易踩的坑：看到「分段」就以为四家在做同一件事。实际上，Claude Code 的分段是为了「分配缓存 scope」，pi 的分段是为了「做增量补丁」，omp 的分段是为了「隔离易变内容」，dsh 的分段是为了「把提示词变成可重放事件」。同样是数组，背后的目的完全不同。推断

06 · 思考题

三道题，从结构到取舍

Q1

为什么边界常量只在 shouldUseGlobalCacheScope() 为真时插入？如果没有插入，splitSysPromptPrefix() 会怎么处理？静态段还能享受 global 缓存吗？

提示（不给答案）

看 splitSysPromptPrefix() 的三段注释：全局缓存 + 有边界 → 4 块；第三方 / 无边界 → 3 块，前缀与其余都按 org 缓存。

边界的作用是给「静态内容」一个可识别的终点。没有终点，切块函数无法区分静态与动态，只能把边界之后的所有内容合并成一块。静态段仍然在，但不再单独获得 global scope。推断

Q2

如果 resolveSystemPromptSections() 改成「缓存值非空才命中」，会发生什么？请从正确性和成本两个角度回答。

提示（不给答案）

当前代码判断的是 cache.has(name)，不是值是否为空。改成「非空才命中」后，所有算出 null 的段每轮都会重新执行 compute。

正确性上通常没问题，因为这些段本来就返回 null；成本上会反复做 I/O 或遍历。更隐蔽的问题是：如果某个 compute 有副作用（比如打点、读文件），每轮重跑会放大副作用。

再想一层：缓存 null 的真正含义是「这个会话确定不需要这一段」，而不是「这一段暂时算不出来」。如果某个段依赖的配置可能在会话中途出现，它就不该用普通记忆化，而该用 DANGEROUS_uncached 或显式清空。

Q3

产品经理要求「把环境信息移到边界之前，这样它也能享受 global 缓存」。你会怎么解释这件事不能做？如果一定要做，需要补哪些约束？

提示（不给答案）

环境信息包含 cwd、平台、日期等用户/会话特定内容。放到 global scope 意味着可能被跨组织复用，等于把一个用户的路径信息泄漏给另一个组织。

如果一定要做，至少要保证这段内容里没有任何用户/会话特定字段，并且有独立的失效机制；否则缓存命中时会返回别人的环境。代价是「环境信息」不再是环境信息，而是一段通用说明。
