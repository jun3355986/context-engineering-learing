filterCompacted 重排替代历史

v1 的磁盘上，消息永远按时间排列；模型看到的却不是。压缩之后，一条「压缩标记」和它的摘要会被搬到保留段前面，数组下标从此不再等于时间顺序。这一节读这个重排函数，以及它给后续代码留下的陷阱。

读之前

v1 的存储是 SQLite：MessageTable 存消息头，PartTable 存内容片段。读取按 time_created 倒序分页，再翻成正序。压缩不改这些行，只在读出来之后重排。所以「磁盘顺序」与「模型顺序」是两个概念。

01 · 功能说明

检查点不是一个对象，是「两条消息 + 一个字段」

压缩成功时，v1 写入三样东西：一条 user 消息（其中有一个 type: "compaction" 的 part）、一条 summary: true 的 assistant 消息（父 ID 指向那条 user 消息）、以及那个 compaction part 上的 tail_start_id。已核实三者合起来才是「检查点」。

摘要消息告诉模型「之前发生了什么」，compaction part 告诉读取代码「从哪条开始保留」，tail_start_id 就是那根指针。

filterCompacted() 的任务是：在按时间排列的消息数组里，找到最后一条带 tail_start_id 的压缩标记，把它和它的摘要一起搬到保留段前面，输出「压缩标记 → 摘要 → 保留段 → 之后的消息」这个顺序。已核实

这张图解释了两件事。第一，旧消息不是「被删掉」，而是根本没被读进来：输入是倒序的，循环在遇到 tail_start_id 指向的 U3 时就 break，U1、U2 留在数据库里但没有进入 result。第二，压缩对的位置被提前了：它本来在数组末尾（最后写入），重排后跑到最前。所以「数组下标 = 时间顺序」从这一刻起不再成立。

// completed：已经完成的「压缩对」集合，元素是压缩 user 消息的 id
export function filterCompacted(msgs: Iterable<WithParts>) {
  const result = [] as WithParts[]
  const completed = new Set<string>()
  let retain: MessageID | undefined
  for (const msg of msgs) {
    result.push(msg) // 先全收，后面再切片
    if (retain) {
      if (msg.info.id === retain) break // 收到保留起点就停
      continue
    }
    // 这条 user 消息是某个已完成压缩的「标记」
    if (msg.info.role === "user" && completed.has(msg.info.id)) {
      const part = msg.parts.find((item): item is CompactionPart => item.type === "compaction")
      if (!part) continue
      if (!part.tail_start_id) break // 没有保留段：后面的都不要了
      retain = part.tail_start_id
      if (msg.info.id === retain) break
      continue
    }
    if (msg.info.role === "user" && completed.has(msg.info.id) && msg.parts.some((part) => part.type === "compaction"))
      break // 这条分支到不了这里，保留为防御
    // 一条 assistant 摘要「完成」了，就把它的父 user 记进集合
    if (msg.info.role === "assistant" && msg.info.summary && msg.info.finish && !msg.info.error)
      completed.add(msg.info.parentID)
  }
  result.reverse() // 转成时间正序
 
  // 找最后一条「带 tail_start_id 的压缩标记」
  const compactionIndex = result.findLastIndex(
    (msg) =>
      msg.info.role === "user" &&
      msg.parts.some((item): item is CompactionPart => item.type === "compaction" && item.tail_start_id !== undefined),
  )
  const compaction = result[compactionIndex]
  const part = compaction?.parts.find(
    (item): item is CompactionPart => item.type === "compaction" && item.tail_start_id !== undefined,
  )
  const summaryIndex = compaction
    ? result.findIndex(
        (msg, index) =>
          index > compactionIndex &&
          msg.info.role === "assistant" &&
          msg.info.summary &&
          msg.info.parentID === compaction.info.id,
      )
    : -1
  const tailIndex = part?.tail_start_id ? result.findIndex((msg) => msg.info.id === part.tail_start_id) : -1
  // 三切片：压缩对、保留段、其余
  if (tailIndex >= 0 && tailIndex < compactionIndex && summaryIndex > compactionIndex) {
    return [
      ...result.slice(compactionIndex, summaryIndex + 1),
      ...result.slice(tailIndex, compactionIndex),
      ...result.slice(summaryIndex + 1),
    ]
  }
  return result // 条件不成立：原样返回
}

04 · 逐段解读

扫描、反转、切片：三步都有坑

第 1 段　扫描：倒序输入才是关键

filterCompacted() 的参数是 Iterable<WithParts>，看起来没约束顺序。但 filterCompactedEffect() 传进来的是 stream(sessionID)，而 stream() 的实现是「按页取最新的一段，页内倒着 push，再往前翻页」，所以它产出的是从新到旧。已核实这个前提决定了后面所有分支能否成立。

倒序之下，先看到的是最新消息。一旦遇到 assistant + summary + finish + 无 error，就把它的 parentID 记进 completed；再往旧走，遇到那条 parent 的 user 消息时，completed.has(id) 成立，取出 tail_start_id，把 retain 设成它，然后一直 continue 到 msg.info.id === retain 才 break。已核实整个过程就是「从最新收到保留起点」。

所以 completed 不是「先记标记后确认」，而是「先看到摘要，再回头认领它的标记」——只有在倒序输入下才写得这么短。

这也解释了 if (!part.tail_start_id) break：一条没有保留段的压缩意味着「全部历史都进摘要」，再往旧读也没有意义，直接停。retain 与 completed 的分工是：前者控制「读到哪里」，后者负责「认出哪条 user 消息是压缩标记」。

代价是函数的正确性依赖调用方。如果有人把 stream() 改成升序，或者直接传一个升序数组，completed 会在看到标记时还是空的，整段早退逻辑失效，结果退化成「全量历史 + 未替换的压缩标记」。函数签名没有表达这个约束，只能靠注释与调用点。

怎么读才不绕

把函数拆成两半：前半段（L534-L556）假设输入倒序，做「收集 + 截断」；后半段（L557-L584）先 reverse() 成升序，再做「定位 + 三切片」。前半段决定数组里剩哪些消息，后半段决定它们的顺序。

第 2 段　反转与下标：为什么用 `findLastIndex`

result.reverse() 之后，数组是时间正序。`compactionIndex` 用 `findLastIndex` 找最后一条带 `tail_start_id` 的压缩标记：多次压缩时，只有最新那条决定当前保留段。已核实这与 pi 找「路径上最后一条 compaction」是同一个思路。

summaryIndex 找的是「在压缩标记之后、role === "assistant"、summary 为真、parentID 等于压缩标记 id」的第一条。已核实三个条件缺一不可：只按 summary 找，可能找到上一次压缩的摘要；只按 parentID 找，可能找到普通回复。

tailIndex 是保留起点的位置。三个下标必须满足 tailIndex < compactionIndex < summaryIndex，重排才有意义；否则原样返回。这个守卫很重要：如果数据被手动改过、或 fork 重映射出错，切片会拼出一个顺序错乱的数组，还不如不排。

第 3 段　三个切片：顺序与内容

第一个切片 slice(compactionIndex, summaryIndex + 1) 是「压缩标记 + 摘要」，第二个 slice(tailIndex, compactionIndex) 是「保留段」，第三个 slice(summaryIndex + 1) 是「摘要之后的新消息」。已核实拼接结果就是模型看到的顺序。

注意第二个切片不包含 compactionIndex 本身（右开区间），所以压缩标记不会重复。第三个切片从 summaryIndex + 1 开始，也不包含摘要。三个切片刚好覆盖「检查点 + 保留段 + 后续」，但会丢掉 tailIndex 之前的内容——这正是「替代历史」的含义。

如果 tailIndex === 0（保留起点就是第一条），第二个切片为空，结果就是「压缩对 + 之后」。如果 summaryIndex === -1（找不到摘要），条件不成立，返回原数组，后续转换会把压缩标记当成一条普通 user 消息——这通常意味着数据不一致。

第 4 段　与 v2 并排：从「重排」到「seq 连续段」

v2 把检查点收成一条消息：type: "compaction"，字段有 status、reason、model、summary、recent、providerContext、cost、tokens。已核实它不再需要「摘要消息」这一条独立记录，因为摘要与保留段都在同一条消息里。

读取时，latestCompaction() 按 seq 降序找最近一条 status = "completed" 的压缩（还要按 boundary 判断是否可重放），然后取 seq >= 该条 seq 的所有消息，按 seq 升序返回。已核实没有重排，没有三切片，数组顺序就是 seq 顺序。

第 5 段　分页与 fork：重排之外的两处配套

重排函数不是孤立的。它上面有分页读取，下面有 fork 的 id 重映射；任何一处出错，三个下标的守卫都会失效，函数退化成「原样返回」。

分页。page() 按 time_created 倒序取 limit + 1 条，用多取的一条判断 more，然后把这一页反转成正序返回。已核实游标是 { id, time }，下一页用 older(before) 继续往前。所以单页内是正序，页与页之间是「新页在前」——stream() 再把每页倒着 push，才得到全局倒序。这个双层反转很容易读错，读 filterCompacted 前建议先读 page()。

分页大小 50。stream() 里的 size = 50 是硬编码。已核实它不影响正确性，只影响「一次读多少」。对超长会话，filterCompacted 会在遇到 retain 时提前 break，所以它通常只需要读最后一两页；但如果保留段很长（例如 tail_start_id 很旧），它会一页页往前翻，直到找到那个 id。

fork。Session.fork 新建会话、逐条复制消息并重映射 id，tail_start_id 也一起重映射。已核实这一步必须做：压缩 part 里存的是旧会话的消息 id，复制到新会话后如果不改，findIndex 找不到，tailIndex = -1，重排被跳过，模型就会看到「压缩标记 + 摘要 + 全部旧历史」——检查点形同虚设。

失败的表现。三种数据问题都会让重排「安静地不生效」：tail_start_id 指向不存在的 id、summaryIndex = -1（摘要缺失）、tailIndex >= compactionIndex（顺序异常）。函数都返回原数组，不报错。已核实所以排障时不能只看「有没有报错」，要看「返回顺序对不对」。

怎么验证。拿一条压缩过的会话，打印 filterCompacted 结果的前三条 id：应该是「压缩 user → 摘要 assistant → 保留段第一条」。如果不是，按 tail_start_id、摘要的 parentID、tailIndex 三个值逐个查。这个检查比读代码快得多。

第 6 段　latest() 为什么存在

重排之后，数组里「最后一条」可能不是最新消息。v1 的 latest() 就是为了在不信任位置的前提下找「最新」。源码注释直说：filterCompacted 会把数组变成 [压缩 user, 摘要, 保留段, continue-user]，所以位置不是时间顺序，id 只做确定性 tie-breaker。已核实

latest() 的做法不是「取最后一个」，而是扫描数组，按消息类型与完成状态分别记录最后一个 user、最后一个 assistant、最后一个已完成的 assistant。已核实这样即使数组顺序被打乱，也能找到正确的「最近一条」。

这给出一个通用模式：一旦读取层会重排，所有「取最后一条」的代码都要改成「按时间/状态找最大」。v1 里这类函数不止一个（latest、lastAssistant、completedCompactions），它们都遵循同一个原则：不靠位置，靠状态或时间。

反过来说，如果你在 v1 的代码里看到 msgs.at(-1)，要格外小心：它可能是在重排之前的数组上调用（安全），也可能是在 filterCompacted 之后（危险）。区分方法只有一个：看调用点拿到的是原始 stream() 结果，还是 filterCompacted() 的返回值。

✓要点小结

  • v1 的检查点 = 压缩 user 消息 + 摘要 assistant 消息 + part 上的 tail_start_id。
  • filterCompacted() 把「压缩对」搬到最前、「保留段」接上、「其余」放后面，数组顺序从此不等于时间。
  • 三个下标必须满足 tail < compaction < summary，否则原样返回。
  • 源码自己写了警告：不能用数组下标推断时间，id 只做确定性排序。
  • v2 改成一条检查点消息 + seq 连续段，用「更重的记录」换「可信的顺序」。

05 · 与其他 agent 的差异

三种「替代历史」的读法

pi 用「压缩条目 + firstKeptEntryId」在树路径上截取，v1 用「重排 + tail_start_id」，v2 用「seq 连续段」。三家都不删原文，但读出来的顺序与定位方式完全不同。

三点对照：

一是顺序可信度。pi 与 omp 的输出永远时间正序，调用方可以放心用下标；v2 用 seq 升序，也可信；v1 明确不可信。这不是小事：任何「取最后一条消息」「按 index 找上一条」的代码，在 v1 里都必须改成按 id 或按 time_created 找。源码专门留了 L591-L594 的注释警告后来者。

二是保留段的存储位置。pi 与 v1 都指向原始消息，v2 把保留段序列化成文本放进检查点。前者的好处是「保留段仍是结构化消息」，可以继续工具调用；后者把「历史」变成「一段文本」，模型只能读、不能再调用工具。v2 的检查点因此更像「一份归档」，而不是「一段可续跑的历史」。

三是多次压缩的处理。v1 的做法是「隐藏上一对压缩消息」（previousSummary 取最近一条），读的时候只认最后一个带 tail_start_id 的标记；v2 只认最近一条 status = "completed" 的检查点，更早的自然落在 seq 边界之外。两者结果相近，但 v2 的规则更少、更容易用一句 SQL 表达。

Q2

如果 summaryIndex = -1（找不到摘要），会发生什么？模型会看到什么？这算「安全失败」吗？

提示（不给答案）

看条件：summaryIndex > compactionIndex 为假，直接 return result。

于是压缩标记那条 user 消息会原样进入转换。它的 parts 里只有 type: "compaction"，没有文本；转换后可能变成一条空 user 消息，或者被过滤掉。

这不是安全失败：模型可能看到「一条空的用户消息 + 完整旧历史」，也可能看到「旧历史完全没被替代」。无论哪种，都与预期不符。

Q3

你的代码要「取最后一条 assistant 消息的 token 用量」。在 v1 里用 msgs.at(-1) 为什么可能错？应该怎么改？

提示（不给答案）

重排后最后一条可能是保留段末尾、也可能是被挪到后面的旧消息；顺序不等于时间。看 L591-L594 的注释。

改用 time_created 或 id 排序后再取，或者用 latest() 这类明确按时间/完成状态筛选的函数。

更普遍地说：任何依赖数组位置的逻辑，在 filterCompacted 之后都要重新审视。
