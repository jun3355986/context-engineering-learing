01 · 功能说明

先决定「该压了」，再决定「压完长什么样」

Grok Build 的压缩叫 full-replace：它不挑一段尾巴保留，而是把整段对话交给模型写摘要，然后用一份全新的历史替换掉旧历史。源码注释写得很直白——grok-build does not select a tail to keep; it summarizes the whole conversation and rebuilds a fresh history from scratch（code_compaction/compact.rs 文件头）。已核实

「整段替换」听起来很粗暴，但它把一个问题拆成了两个可以分别验证的小问题：什么时候该压，以及压完的历史由哪几块拼成。

第一个问题由 check_auto_compact_needed() 回答，它在每次采样前被调用一次，返回 Some 就立刻压缩。第二个问题由 assemble_compacted_history() 回答，它是一个纯函数：输入七个已经准备好的片段，输出一个新的消息数组，不读磁盘、不发请求、不碰会话状态。这种「判定」与「装配」彻底分开的写法，让装配部分可以单独写单元测试——仓库里确实有一组测试专门断言插槽顺序（grok_build_order_recent_before_summary）。

把整条链路摊开，压缩一共有五步。本节讲第 1 步和第 4 步：一头一尾，正好是「要不要压」和「压成什么样」。

为什么要先看这两步？因为大多数关于压缩的困惑都出在这里。用户看到的是「压完之后我的需求还在，但文件内容没了」；工程师要能回答的是「它在第 1 步用什么数做的判断，在第 4 步按什么顺序拼的零件」。这两件事都能从源码里读出来，不需要猜。

有一个前提要先说清：压缩的产物不是「旧历史加一段摘要」，而是「一份全新的历史」。旧的工具结果、旧的助手回复、旧的推理过程，一条都不会进新历史。它们唯一的存在方式是摘要里的一句话。这一点决定了后面所有的顺序问题。

pub(crate) fn should_auto_compact(&self, total_tokens: u64, context_window: NonZeroU64)
    -> Option<AutoCompactTriggerInfo> {
    let cw = context_window.get();
    if xai_token_estimation::exceeds_threshold(total_tokens, cw,
            self.compaction.threshold_percent.get()) { // used*100 >= cw*pct
        let percentage = xai_token_estimation::usage_percentage_u8(total_tokens, cw);
        Some(AutoCompactTriggerInfo { tokens_used: total_tokens, context_window: cw,
            percentage, reason_override: None })
    } else { None } // 没到线，什么都不做
}

04 · 逐段解读

五个决定，从「什么时候」到「什么顺序」

第 1 段　估算值：不是上一次的 usage，而是 usage 加增量

判定的输入只有一个数：get_estimated_total_tokens()。它不是「上一次模型返回的 total_tokens」，而是上一次上报值加上此后新增项的字节估算。源码里的字段叫 total_tokens + estimated_tokens_since_model，意思很明确：工具结果刚写进历史、模型还没看过，这段时间的增量必须自己估，否则压缩永远慢一轮。

估算函数在 xai-token-estimation 里，规则是 字节数 / 4（整数除法，向下取整），图片每张记 765 token。已核实这里有个容易被忽略的细节：s.len() 是 UTF-8 字节数，不是字符数。一段中文按 3 字节一个字算，会被估成 0.75 token/字；而真实分词器对中文大约是 1 到 1.5 token/字。也就是说，中文内容会被这套估算系统性低估。对英文为主的代码仓库问题不大，对中文长文档就是风险。

阈值本身不是硬编码的 85。解析顺序是五级覆盖加一个常量兜底：环境变量 GROK_AUTO_COMPACT_THRESHOLD_PERCENT → 用户配置的 [model.<id>] → 用户配置的 [session] → 远端下发的 per-model 值 → 远端全局值 → 常量 85。已核实实际使用时，模型目录常常会下发一个更保守的值，比如 grok-4.6 是 80。所以「Grok Build 在 85% 压缩」这句话只在没有其他配置时成立。

比较用的是整数运算：used * 100 >= cw * pct。边界取 >=，1000 token 的窗口、85% 的阈值，850 token 就触发，849 不触发。源码里有一条测试专门钉住这个语义，注释还说明它比旧版的 > 早一个 token 触发。已核实

注意：这套判定没有「输出预留」

阈值只按 total_tokens / context_window 算，不扣 max_output。也就是说，它假设「历史装到 85% 时，剩下的 15% 够模型写回复」。这一点和 DeepSeek Harness 的公式（阈值取 0.8W 与 W − O − B 的较小值，显式扣掉输出预留和 headroom）是两种哲学：前者简单、把风险留给请求失败后的恢复路径；后者保守、在触发前就把空间算清。

第 2 段　五条触发路径：同一条压缩，五个入口

第 1 段讲的是其中一条路径。完整清单有五条，分别落在链路的不同位置：

① 采样前阈值触发。check_auto_compact_needed() 在每次采样前运行，估算值到线就压。这是最常见的一条，也是唯一一条「按比例」的路径。

② 预检溢出。check_preflight_overflow() 在工具循环的末尾运行：工具结果刚写进历史，估算值可能直接越过 100%。这时不等采样失败，先压一次再 continue 回到循环开头。已核实它和①的区别是判据：①看比例，②看「是否已经超过窗口」。

③ 采样报错后压缩重发。请求发出去，服务端返回上下文超限，should_compact_on_error() 先确认错误信息里的窗口确实小于本地估算，再压一次、重发。这条路径的存在说明前两条都可能漏：估算偏低、服务端窗口比本地认为的小、或者单条工具结果一次塞爆。

④ 手动 /compact。用户主动触发。这一版 TUI 明确拒绝任何参数（/compact takes no arguments.），但压缩提示词的构建器仍然保留了 user_context 插槽——协议层支持「带指令压缩」，只是当前前端没开放。已核实

⑤ 模型切换。maybe_compact_on_model_switch() 在换模型后比较新旧窗口，只有窗口变小才压；同时清掉「因预算导致的抑制」，保留 credit / auth 这类与窗口无关的抑制。已核实

五条路径最后都汇到同一个函数，产出的都是一个 AutoCompactTriggerInfo（token 数、窗口、百分比、可选的 reason 覆盖）。后面所有步骤不再关心「是谁触发的」。这种「多入口、单出口」的结构值得学：触发条件可以有很多个，压缩实现只应该有一份。

判定入口里还有一个顺序细节值得注意：is_flushing 的检查排在读窗口之前，而「抑制状态」的检查排在估算之后。前者是「别和记忆写入抢历史」，后者是「压不压得起」。这两个判断分开写，是因为它们的解除条件不同——flush 结束就自动解除，压缩抑制则可能一直持续到上下文预算发生变化。源码里 size 与 schema 两类失败被标成「粘性抑制」，只有预算变化才解除。已核实

第 3 段　摘要：9 段结构，以及那句「继承上一次」

摘要提示词是一个 19 行的文本文件，正文要求模型按 9 个编号段落输出：Primary Request and Intent、Key Technical Concepts、Files and Code Sections、Errors and Fixes、Problem Solving、All User Messages、Pending Tasks、Current Work、Optional Next Step。已核实每一段都要求「即使为空也要写标题并填 None」，这样格式稳定，后续解析和继承都不会因为缺段而错位。

九个段落里有三个是为「下一次压缩」准备的，不是为这一次：

第 3 段「Files and Code Sections」要求给出完整路径、为什么重要、以及改过的代码全文（最近一次修改要完整）。工具结果在压缩后全没了，这份清单是模型以后想回到某个文件时唯一的线索。

第 6 段「All User Messages」要求按顺序列出所有非工具结果的用户消息，并特别注明「不要把这段压缩指令本身算进去」。它防的是模型把系统生成的压缩提示当成用户说过的话。

第 9 段「Optional Next Step」要求引用最近一条消息的原文，说明「你停在哪」。这条是为了压缩后能无缝续跑，而不是重新规划。

真正的关键是提示词第 3 行，原文是：If earlier turns include a prior compaction summary ... treat it as authoritative for the early history and carry its still-relevant information forward into your new summary so nothing important is lost across successive compactions.已核实

这句话把「压缩」从一次性操作变成了可迭代操作：第二次压缩的输入里包含第一次的摘要，模型被要求把旧摘要的事实合并进新摘要，而不是重新概括一遍对话。

没有这句话会发生什么？第一次压缩把 100 轮压成 2,000 字；第二次压缩时，模型看到的是「摘要 + 最近 20 轮」，它会把摘要当成一段普通背景，重新写一份「最近 20 轮的摘要」。早期那 80 轮的信息在第二次压缩时就悄悄消失了。这就是「压缩漂移」：每一轮都看起来合理，几轮之后关键约束不见了。

提示词还有三道保险：禁止调用工具；只输出一个 <summary> 块；不输出单独的分析段。输出之后，代码还会清洗：剥掉 <analysis> 草稿、把正文里的控制标签插入零宽空格「拆掉」、压缩多余空行。清洗后的字符数如果小于 MIN_SUMMARY_SEED_CHARS = 500，视为退化，按瞬时失败重试。已核实最多 3 次尝试，每次超时 120 秒，间隔 3 秒。

第 4 段　七个插槽：为什么最近消息在摘要之前

装配函数的输出顺序是：系统提示词 → 用户信息前缀 → AGENTS.md → 最后一条真实用户请求 → 最近消息 → 摘要 → 状态提醒。源码注释把它写成 [SP, UP', AGENTS_MD?, UQ_last?, recent…, summary, reminder?]，问号表示可选。

「最近消息在摘要之前」是这份代码里最反直觉的一处，源码注释只写了 Recent messages come first, then the summary.，没有解释。合理的解释是角色定位：摘要描述的是「更早发生的一切」，它应该出现在被它概括的内容之后；如果摘要排在最近消息之前，模型读到的顺序就变成「先看总结，再看几轮具体对话」，很容易把那几轮对话当成摘要之后的续写，而不是摘要所覆盖的范围。

第二处反直觉的是 AGENTS.md。它是重新注入的：压缩前从 agent 里重新取一次渲染好的 <system-reminder> 块，压缩后原样放进第 3 个插槽。源码注释写明理由：项目指令不能依赖摘要模型，它必须逐字存活。已核实这条设计解决了一个常见故障：压缩后模型突然「忘了」项目里的命名规范，因为那段规则只存在于被摘要掉的系统提醒里。

第三处是摘要的包装。摘要正文不是裸文本，前面固定加一段前言：This session is being continued from a previous conversation that ran out of context. The summary below covers the earlier portion of the conversation.已核实这段前言有两个作用：告诉模型「这是续接，不是新任务」；给下一次压缩一个可识别的标记（提示词里提到的 "This session is being continued" preamble 就是它）。

还有一个容易忽略的细节：摘要用的是 T::new_user_meta(...)，不是 new_user，也不是 assistant 消息。它是一条「用户角色、但不是用户原话」的消息。这个选择在三家实现里高度一致——Codex 的摘要也是用户消息，DeepSeek Harness 的压缩检查点同样是 user/message。原因是协议约束：多数模型的对话模板要求「最后一条是用户消息」才能续写；把摘要放进 assistant 角色，下一次请求就变成「助手刚说完一段总结，用户没说话」，模型容易把它当成待续写的半成品。

最后一条状态提醒（system_reminder）装的是「压缩这一刻的环境事实」：改过哪些文件、有哪些后台任务在跑、有哪些子代理没结束、哪些 MCP 服务器连着。它放在最后，因为它是「现在」而不是「过去」，而且每次压缩都要重新生成。注意它排在摘要之后，也就是说，模型读到的最后一句是「当前环境」——顺序是刻意设计的。

第 5 段　生产路径上的「7 段」通常只有 4 到 6 条

上面的七个插槽来自通用装配器 xai-grok-compaction。但 Grok Build 的 shell 实际调用的是 xai-chat-state 里的 build_compacted_history()（compaction_utils.rs L920-L991），它是同一套顺序的超集：多了一个「agent message anchor」插槽，还可以通过 summary_before_recent 开关把摘要提到最近消息之前。

更关键的是 for_compaction()（L691-L710）：它把 recent_messages 直接置空。源码注释给出的理由是 For a single-real-user-turn sub-agent, keeping recent_messages frees almost nothing and re-cues the model to re-read the same files.已核实回归测试的名字更直白：grok_build_compaction_drops_working_tail_regression_206460，注释说保留的尾巴最后只剩下 Tool call omitted... 这种死 token。

所以准确的表述是：装配器有七个插槽，但 Grok Build 在压缩时主动放弃了第 5 个。真实产物通常是「系统提示词 + 前缀 + AGENTS.md + 最后请求 + 摘要 + 状态提醒」，六条；没有 AGENTS.md 或状态提醒时更少。

这个订正不影响理解顺序，但影响你读压缩后的会话：如果你在日志里数出六条消息，那不是实现漏了一段，而是设计上就不要那段尾巴。放弃尾巴的代价很实在——压缩前最后几轮的工具结果（比如刚读到的文件内容）不会保留，模型只能靠摘要里的「Files and Code Sections」重建。

第 6 段　代价：一次替换，缓存从切点开始失效

full-replace 的缓存代价可以精确描述：新历史的前两个插槽（系统提示词、用户前缀）与旧历史逐字节相同，可以命中缓存；从第三个插槽开始就分叉了——旧历史那里是第一条用户消息，新历史那里是 AGENTS.md 或最后一条请求。所以缓存的有效前缀大约只到系统提示词结束。

这也是为什么装配顺序把最稳定的东西放前面：系统提示词、用户前缀、AGENTS.md 都是「会话内基本不变」的内容。理论上它们可以形成一段较长的可复用前缀，但压缩把中间的历史抽走了，后续请求的前缀仍然对不上——除非下一次压缩又生成同样的开头。源码没有为压缩做「暖前缀」的特殊处理（DeepSeek Harness 会逐字节复用被遮蔽区间来暖摘要请求），所以压缩后的第一次请求基本是全价。

✓要点小结

  • 五条触发路径，最后都汇成一个 AutoCompactTriggerInfo；阈值默认 85，可被五级配置覆盖。
  • 估算 = 上次上报值 + 新增字节数 ÷ 4；中文按字节算，会被低估。
  • 摘要是 9 段固定结构；「继承上一次摘要」是多次压缩不丢信息的关键一句。
  • 七段装配：SP → 前缀 → AGENTS.md → 最后请求 → 最近消息 → 摘要 → 提醒；摘要贴尾。
  • 生产路径主动丢掉最近消息，所以实际通常只有 4 到 6 条；缓存从第三个插槽起失效。

05 · 与其他 agent 的差异

同样是「压缩后留一点」，五家留的东西完全不同

把五家 agent 放在一张表里，分歧点立刻显现：Grok Build 和 DeepSeek Harness 都是「整段替换」，但一个重新装配七段、一个只落一条替换消息；Codex 和 pi 都是「保留一段」，但一个只留用户消息、一个留连续尾巴；Claude Code 干脆不留对话，改留「文件与技能清单」。

三个值得单独说的对照：

一是「保留」的语义。Codex 的 20,000 token 预算装的是用户原话，所以压缩后模型还能看到你三小时前那句「不要改 public API」；Grok Build 没有这个预算，它把这些话交给摘要的第 6 段「All User Messages」。前者保真度高、占空间；后者省空间、但依赖摘要模型愿不愿意逐条抄。Grok Build 的提示词用全大写 List ALL messages 来强调，说明这件事确实容易被偷懒。

二是「原文重注」的范围。Grok Build 只重注 AGENTS.md 与用户信息前缀；Claude Code 重注的是「最近改过的 5 个文件 + 用过的技能正文 + plan」。前者假设「规则比代码重要」，后者假设「代码比规则重要」。这个假设直接决定压缩后模型的第一反应：是先去读文件，还是先遵守规则。

三是摘要的继承方式。Grok Build 在提示词里要求「把旧摘要的事实带过来」；DeepSeek Harness 在提示词里要求「合并旧 <compacted-summary>、丢弃过时项」；pi 则把上一次摘要作为 previousSummary 传入并切换成 UPDATE 版提示词。三家做法不同，但都承认同一件事：不显式要求继承，模型就会重新概括，早期信息一定漂移。

最后说 full-replace 的结构性代价。它无法处理「单个不可分割单元超过窗口」的情况：一条巨长的工具结果或一条超长用户消息，压缩只会把它写进摘要，而摘要请求本身也会超窗。Grok Build 的应对是在压缩请求前做图片预算整形、并保留「逐级降级输入」的阶梯（verbatim → fitted → lossy），但阶梯的实现在 shell 侧，不在这个纯函数里。这也是为什么第 3 步「准备待摘要历史」在图上被单独列成一步。

06 · 思考题

三道题，从读代码到改设计

Q1

窗口 200,000，阈值取默认 85，当前估算 169,000。会触发压缩吗？如果这段历史是纯中文，你的判断需要修正吗？

提示（不给答案）

先算 200000 × 85 / 100，再看比较符是 > 还是 >=（xai-token-estimation 的测试钉住了边界）。

再想估算的单位：estimate_tokens 用的是 s.len()（UTF-8 字节）还是字符数？中文一个字几字节？这意味着 169,000 这个「估算值」对应的真实 token 是更多还是更少？

Q2

如果把 assemble_compacted_history 里的 summary_item 移到 recent_messages 之前，会发生什么？请从「模型如何理解顺序」和「缓存前缀」两个角度各说一条。

提示（不给答案）

摘要的固定前言是「This session is being continued…」，它是一段「对更早内容的概括」。如果它出现在最近两轮具体对话之前，模型读到的因果顺序是什么？

缓存角度：摘要文本每次压缩都不同（模型输出），把它前移会让「稳定前缀」变长还是变短？

Q3

你的任务是「连续改 8 个文件，最后统一 review」。Grok Build 的 full-replace 会在哪里让你难受？只允许改一个地方，你改哪里、代价是什么？

提示（不给答案）

先看第 5 小节：生产路径把 recent_messages 置空，理由是「留着也只是 Tool call omitted 这种死 token」。如果你的任务恰恰依赖最近几轮的工具结果，这个理由还成立吗？

再对照 pi：它保留「切点之后的连续尾巴」，并且绝不切在 toolResult 上。如果照搬，Grok Build 需要在装配前多做哪一件事（提示：谁来保证工具调用和结果成对）？

最后想清楚：只改装配、不改「收集待摘要历史」那一步，够不够？
