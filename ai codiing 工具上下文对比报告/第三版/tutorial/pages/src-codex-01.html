01 · 功能说明

压缩要回答两个问题，这一节只看第二个

触发压缩时，Codex 要做两件事：让模型写一段摘要，以及决定摘要之外还要保留哪些原文。第一件事靠提示词模板，第二件事靠代码里的候选筛选和预算循环。后者更值得读，因为它决定「压缩完之后，模型还记得你的哪几句话」。

「保留」不是把旧消息原样搬过去，而是重新挑一遍、重新裁一遍：留下谁、留多长，都由这次压缩重新算。

在整条链路里，Codex 的压缩分五步。这一节讲第 2 步，也就是「挑候选 + 按预算保留」。它上接触发判定，下接摘要请求；不理解这一步，后面「替换历史」看到的结果就会显得莫名其妙——为什么压缩完还有一堆用户消息，而工具输出一条不剩。

第 2 步的入口在 compact.rs。它由一个收集函数和一个重建函数组成：先 collect_annotated_user_messages() 把历史过滤成候选列表，再 build_compacted_history() 在预算内挑人、裁长度、拼成新的历史。外层任务（run_inline_auto_compact_task）只负责把这两步串起来。已核实

fn compacted_user_message<'a>(
    item: &'a ResponseItem,
    harness_metadata: Option<&'a CodexHarnessMetadata>,
) -> Option<CompactedUserMessage<'a>> {
    // parse_turn_item 只把 role=user、且不是隐藏片段的消息认成 UserMessage
    let Some(TurnItem::UserMessage(user)) = parse_turn_item(item) else {
        return None; // 助手回复、工具结果、隐藏片段：出局
    };
    let message = user.message(); // 扁平化文本，只用来算 token、认摘要
    if is_summary_message(&message) {
        return None; // 上次压缩写的摘要，不能再当候选
    }
    Some(CompactedUserMessage { message, original: item, harness_metadata })
}

// 输入候选与摘要，输出一条新的、长度受控的历史（L715-L720）
fn build_compacted_history_with_limit(
    mut history: Vec<ResponseItemEnvelope>, // 调用点传空 Vec
    user_messages: &[CompactedUserMessage<'_>], // 候选，时间正序
    summary_text: &str,
    max_tokens: usize, // 默认 20_000
) -> Vec<ResponseItemEnvelope> {
    let mut selected_messages = Vec::new();
// 第 1 步：从最新一条往回走，边走边扣额度（L722-L727）
    if max_tokens > 0 { // 预算为 0 时一条不留
        let mut remaining = max_tokens; // 剩余额度
        for message in user_messages.iter().rev() { // 从最新往回
            if remaining == 0 { break; } // 刚好用完，不再往前
            let tokens = approx_token_count(&message.message); // ceil(字节÷4)
            let ResponseItem::Message { id, content, .. } = message.original
            else { continue }; // 防御：候选理论上都是 Message
            let mut harness_metadata = message.harness_metadata.cloned();
            // 第 2 步：额度够、且全是文本，才算「能原样搬」（L739-L742）
            let preserve_content = tokens <= remaining
                && content.iter()
                    .all(|part| matches!(part, ContentItem::InputText { .. }));
            let mut item = ResponseItem::Message { // 重建干净的消息
                role: "user".to_owned(), id: id.clone(),
                content: if preserve_content { content.clone() }
                    else { Vec::new() }, .. }; // 装不下先留空，其余字段略
// 第 3 步：搬不过去就按剩余额度截断文本（L757-L789）
            if !preserve_content {
                // …（省略 31 行：按源下标取文本、丢弃图片音频，再截断）
                set_annotated_content(
                    &mut item, truncate_annotated_text(parts, remaining));
            }
            // 截断过就只在元数据标记「来源不完整」（L790-L794，略）
            selected_messages.push(ResponseItemEnvelope {
                item, metadata: harness_metadata }); // 先放进去
// 第 4 步：放不下就收工，压进去的不撤回（L799-L802）
            if tokens > remaining { break; } // 留截断版后停
            remaining = remaining.saturating_sub(tokens); // 装得下就扣额度
        }
        selected_messages.reverse(); // 倒回时间正序（L804）
    }
    history.extend(selected_messages);
    history.push(ResponseItemEnvelope::new( // 摘要固定追加在最后
        ContextualUserFragment::into(CompactionSummary::new(summary_text))));
    history
}

04 · 逐段解读

四段代码，四个决定

第 1 段　候选：谁有资格被保留

整条筛选链只有三道判断，但第一道判断背后藏着一次函数调用。parse_turn_item() 把 role == "user" 的消息交给 parse_user_message()，而后者第一件事就是 is_contextual_user_message_content()——只要消息里带任何一个隐藏片段的标记，就返回 None，这条消息连 UserMessage 都算不上。已核实

被这一道挡掉的是一个很长的名单：AGENTS.md 指令、环境状态、shell 命令回显、子代理通知、技能提示、上一轮被中断的提示……它们都以用户消息的形状存在历史里，但都不是你说的。contextual_user_message.rs#L22-L37 里有完整的匹配器列表。可见的 hook prompt 也会被单独归成 TurnItem::HookPrompt，同样进不了候选。

第二道判断是摘要前缀。压缩写出的摘要本身是一条用户消息（内容是 SUMMARY_PREFIX 加正文），如果不排除，第二次压缩会把第一次的摘要当成「用户原话」再留一遍，摘要就会自我复制、逐次膨胀。第三道判断是 TurnItem::UserMessage 的类型本身，它顺手挡掉了助手回复、推理、工具调用和工具结果。

所以「只收真实用户消息」不是一句设计口号，而是三层过滤叠出来的结果：不是隐藏片段、不是上次摘要、类型必须是用户消息。

第 2 段　预算：20 000 从哪来，为什么从新到旧

候选列表是按时间正序的，但循环先用 iter().rev() 把它翻过来，从最新一条开始。理由很直接：越近的话越可能还在被讨论，越旧的话越可能已经被摘要覆盖。如果从旧到新，最先被塞满的会是几万轮之前那句「你好，帮我看看这个仓库」，最近十分钟的需求反而被截断。

每条消息的 token 由 approx_token_count() 给出，实现是 ceil(UTF-8 字节数 ÷ 4)，APPROX_BYTES_PER_TOKEN = 4 写在 truncate.rs#L6。已核实它算的是 message.message，也就是扁平化后的文本，不是原始结构体；图片和音频在这里不计入，这也解释了下面为什么「非纯文本」会被单独处理。

关于 20 000 这个数字，源码只给了一行常量，没有注释说明依据。已核实合理的解释是：压缩后腾出来的空间要同时容纳系统提示、工具定义、重新注入的初始上下文、摘要本身，以及这批原文；保留量太大，压完立刻又贴近阈值，就会来回抖动。假设窗口是 200 000，20 000 约占十分之一，是个保守的「安全余量」而不是「最大化保留」。推断

远端压缩是另一套数：保留预算 64 000，单条助手消息上限 10 000，重试 2 次（compact_remote_v2.rs#L87-L91）。已核实本地 20k 更保守，一个可能是本地路径还要把初始上下文插回同一份历史，得留出余量。推断

第 3 段　切点：放不下的时候，到底发生了什么

这里是最容易被讲错的一处。很多介绍会说 Codex「放不下就跳过，继续往前找更小的那条」——不是。代码的顺序是：先算 preserve_content，装不下就把 content 置空、走截断分支，用 truncate_annotated_text(parts, remaining) 把文本裁到剩余额度，先把这条 push 进去，然后才 break。

也就是说，边界那条消息不是被丢弃，也不是被跳过，而是「留半条」。truncate_annotated_text() 裁的是头尾保留、中间替换成 …N tokens truncated… 标记，所以读者仍能看到这句话的开头和结尾。

【订正】大纲说「放不下立即停止」，源码是「先截断再停」

两步差别在结果上：立即停止 → 边界那条整条消失；先截断再停 → 边界那条留半条。后者的代价是这条消息可能语义不完整（比如需求写了一半），好处是最新的一条总不至于一个字都留不下。已核实

为什么不跳过、继续往前找一条更小的？因为跳过会破坏「时间连续性」这个隐含前提：留下来的消息仍然必须是一段连续的历史，中间缺一条，模型读到的就是「用户先说 A，然后突然说 C」。而且跳过意味着循环可能扫完全部历史，最坏情况是 O(n) 次无效比较，收益却是留下一条更旧的、更可能无关的话。

还有两个边界：remaining == 0 在循环开头就 break，所以「刚好装满」不会再多留一条 0 token 的空壳；max_tokens == 0 时整个 if 块被跳过，结果里一条用户消息都没有，只剩摘要。

第 4 段　重建：摘要永远在最后

循环结束时 selected_messages 是「新到旧」的顺序，直接拼进历史会让模型看到时间倒流，所以最后一步 reverse() 把它翻回正序。随后 history.extend() 接上候选，history.push() 把摘要追加在末尾——摘要必须在最后，因为它是「对前面所有内容的总结」，放在中间会让模型把它当成一句普通的历史发言。

调用点传进来的是 Vec::new()，所以这一刻历史里只有「保留的用户消息 + 摘要」。初始上下文（系统指令、AGENTS.md、环境）随后由 build_compaction_replacement_history() 生成并插回，插入位置规则写在 insert_initial_context_before_last_real_user_or_summary() 的注释里：优先插在最后一条真实用户消息之前。已核实

这也解释了一个看起来矛盾的现象：压缩后工具输出全没了，但 AGENTS.md 还在。因为前者只能靠摘要记住，后者是重新生成的，压根没打算「保留」。

✓要点小结

  • 候选只有真实用户消息：隐藏片段、上次摘要、助手与工具内容全部排除。
  • 预算 20 000 token，从最新一条往回累加，额度按 ceil(字节÷4) 估算。
  • 放不下不跳过、不丢弃：边界那条用剩余额度截断后留下，然后立即停止。
  • 最后 reverse() 恢复时间正序，摘要固定追加在最后。
  • 工具输出和助手推理只能靠摘要被记住，这是这套设计最大的代价。

05 · 与其他工具的差异

同样是「压缩后留一点」，四家留的东西完全不同

两个值得记住的对照：

一是候选宽度。Codex 只留用户消息，等于承认「助手说过什么不重要，摘要能概括」；pi 留连续尾部，等于承认「工具结果的精确细节不能概括」。前者省预算，后者省重读。选哪个取决于你的任务是「多轮讨论」还是「反复改同一个文件」。

二是切点自由度。pi 要求切点落在合法边界、绝不切在工具结果中间，为此写了专门的搜索逻辑；Codex 根本不需要，因为候选里没有工具结果，剩下的都是独立用户消息，切哪儿都不会破坏配对。约束少，是因为候选窄——这是一个用「保留范围」换「实现简单」的取舍。

06 · 思考题

三道题，从读代码到改设计

Q1

某条候选消息的扁平化文本是 8 000 字节，remaining 正好是 20 000。它能被原样保留吗？此时 tokens 是多少？如果这条消息里还夹了一张图片，结论会变吗？

提示（不给答案）

先看 approx_token_count() 的换算式（truncate.rs#L87-L90）：它是向上取整，不是截断。再看 preserve_content 是不是「额度够」并且「全是文本」两个条件同时成立。

最后想一件事：tokens 是从 message.message 算的，而图片在不在这个扁平化文本里？

Q2

把 COMPACT_USER_MESSAGE_MAX_TOKENS 改成 5_000。历史里有 10 条真实用户消息，从旧到新每条 3 000 token。压缩后保留几条？最后保留的那条完整吗？还剩多少额度？

提示（不给答案）

循环是从新到旧的，所以「先留下的两条」是最新的那两条，不是最旧的两条。按 3 000 一条算，从第几条开始出现「不够」？

关键在 break 写在 push 之后：那一条在停之前有没有被放进去？它拿到的额度是 remaining 还是 tokens？

Q3

假设你的任务总是「改了 6 个文件、最后让我 review 改动」，用户消息很少。Codex 这套候选策略会在哪里失效？只改一处代码，你会改哪里？代价是什么？

提示（不给答案）

先对照第 5 节的表：pi 为什么坚持「绝不切在 toolResult」，Claude Code 为什么干脆改成重附「最近 5 个文件」，而不是保留消息。

再看一个线索：仓库里已有 compact_retained_tool_outputs.rs，专门处理「没有配对调用的命名工具输出」，注释写明这类输出「要么整条留、要么整条丢」，共享同一份预算。说明保留工具输出不是做不到，而是必须配一套「整条取舍」的规则。

最后想清楚：改一处代码不够。放宽候选之后，切点约束也必须跟着改，否则会拼出没有配对的孤立调用。
