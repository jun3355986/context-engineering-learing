压缩选区的三个约束

压缩要回答一个问题：从哪一刀切下去，既能把预算降下来，又不会切出一段「有调用没结果」的残骸。DeepSeek Harness 的 selectCompactableRange 用 39 行同时满足三个约束：尾部预算、工具配对、系统提示词保护。这一节逐行读它怎么找那一刀。

01 · 功能说明

选区是压缩事务的第一步，也是唯一一步「纯计算」

dsh 的压缩是一个有开始、有摘要、有结束的事务：compaction/start 拿锁，摘要事件落地，然后用一条 user/message 加 surfaceOp: replace 替换选区，最后 compaction/end 释放锁。选区决定了「替换哪一段」，是整个事务里唯一不产生副作用的一步。

选区的结果不是「保留哪些消息」，而是「压缩哪一段连续区间」。这两个说法看起来等价，实际上差很远：前者可以从历史中间挑挑拣拣，后者只能从头开始切一刀。

dsh 选的是后者。函数返回 { start, end }，start 永远是「第一个不是 system 的节点」，end 是「保留下来的尾巴之前那一个节点」。也就是说，压缩的永远是一段前缀：从历史开头到某个位置，剩下的尾部逐字保留。中间不能挖洞，后面不能跳段。

这个「只压前缀」的选择，是理解整段代码的钥匙。它意味着不需要考虑「保留下来的部分中间有个洞怎么办」，也不需要处理「摘要该插在哪里」——摘要就插在原来的位置，替换掉整段前缀。所有复杂度都被推到了「切在哪」这一个决定上。

三个约束由此而来。第一，尾巴要够长：从尾部往前累加，至少保留 retainTokens 那么多。第二，切点要「配对平衡」：不能在一条工具调用和它的结果之间切。第三，起点不能是系统提示词：从第一个非 system 节点开始。三个条件同时满足，才返回一个区间。

谁会调用这个函数？有三条路。自动压力路径（compactIfNeeded(agent, 'pressure')）在每步开始前判断阈值，过了就跑 pruner、重测、选区；溢出恢复路径（'context-overflow'）在请求失败后跳过阈值，直接把保留量设成 0 再选区；手动路径（compactNow）走空闲维护通道，不做阈值判断，并且同样把保留量传 0——它压的是「除系统提示词外能压的最大前缀」。已核实三条路共用一份选区算法，保证「自动压的」和「手动压的」在几何上一致——用户按 /compact 不会得到一段形状奇怪的历史。

手动路径还多两道保护：会话里有未关闭的 turn 时报 busy，摘要期间 surface 变了报 changed，两者都不做替换。这说明「选区」只是几何，能不能落地还要看「这段时间里世界有没有变」——第 1 节讲过的 generation 就是用来回答这个问题的。已核实

// 返回一个可安全压缩的闭区间；没有就返回 null（这是正常结果，不是错误）
export function selectCompactableRange(
  session: Session,
  measurement: TokenMeasurement, // 每个 surface 节点的计价快照
  retainTokens: number, // 尾部至少保留多少 token
): { start: SessionSeq; end: SessionSeq } | null {
  const pricedNodes = measurement.nodes
  if (pricedNodes.length === 0) return null // 空历史，没什么可压
  const surfaceNodes = session.surface.nodes
  if (surfaceNodes.length !== pricedNodes.length
    || surfaceNodes.some((seq, index) => seq !== pricedNodes[index]?.seq)) {
    throw new Error('compaction: token-meter surface does not match the current session surface')
  } // 计价快照必须与当前 surface 逐位对齐，否则预算算错
// 约束三：起点是「第一个非 system 节点」；节点 0 是 system 时从 1 开始
  const firstIdx = systemHead(session, surfaceNodes[0]!) === undefined ? 0 : 1
  let accumulated = 0
  let keepFromIdx = pricedNodes.length // 默认为「全部保留」
  for (let index = pricedNodes.length - 1; index >= 0; index -= 1) {
    accumulated += pricedNodes[index]!.tokens // 从最新往回累加
    keepFromIdx = index
    if (accumulated >= retainTokens) break // 尾巴够了，停
  }
  if (keepFromIdx <= firstIdx) return null // 整段都不够 retain，无法压缩
// 约束二：切点必须配对平衡；不平衡就往前挪，直到平衡或没得挪
  while (keepFromIdx > firstIdx) {
    if (toolPairingBalancedBefore(session, surfaceNodes[keepFromIdx]!)) break
    keepFromIdx -= 1
  }
  if (keepFromIdx <= firstIdx) return null // 退到起点仍不平衡：没有安全切点
  const first = surfaceNodes[firstIdx]! // 起点固定
  const cutoff = surfaceNodes[keepFromIdx - 1]! // 终点是尾巴的前一个
  return { start: first, end: cutoff }
}

04 · 逐段解读

四个决定，一个反直觉的返回值

第 1 段　对齐：计价快照必须与 surface 逐位相同

函数第一件事不是找切点，而是校验 measurement.nodes 与 session.surface.nodes 长度相同、每个位置的 seq 相同，否则直接抛错。已核实这不是过度谨慎：选区用 token 数累加，一旦计价快照对应的是「上一个版本的 surface」，累加出来的位置就是错的，切点会落在完全无关的地方。

为什么不在函数内部重新测量？因为测量是外部的事，而且有成本。调用方先用 meter.measure(session) 拿一份快照，判断「是否过阈值」，再拿着同一份快照来选区。同一个快照同时用于「要不要压」和「压哪一段」，才能保证两个决定基于同一份事实。如果中途有人改了 surface（比如注入了一条消息），校验会拦住它，让这次压缩失败重选，而不是带着过期数据继续。

第 2 段　累加：从尾部往前，够了就停

第二件事是算「尾巴从哪开始」。循环从最后一个节点往前，accumulated 逐项累加节点 token，达到 retainTokens 就 break，此时的 keepFromIdx 就是尾巴的起点。已核实

有一个容易读错的初值：keepFromIdx 一开始被设成 pricedNodes.length，也就是「尾巴从末尾之后开始」，等价于「全部保留」。如果整段历史的 token 加起来都没到 retainTokens，循环会一直走到下标 0，keepFromIdx 变成 0，随后 0 <= firstIdx 成立，返回 null——历史太短，压了也腾不出空间，不如不压。

按默认配置算一个具体例子。窗口 W = 200,000，输出预留 O = 8,000，headroom B = 65,536：阈值 = min(160,000, 200,000 − 8,000 − 65,536) = 126,464，保留量 = floor(192,000 × 0.16) = 30,720。已核实假设尾部四个节点从新到旧是 20,000、2,000、1,000、12,000 token：累加到 20,000 不够，加 2,000 变 22,000，加 1,000 变 23,000，再加 12,000 变 35,000 才越过 30,720，于是尾巴从那个 12,000 的节点开始，总长 35,000——比预算多出 4,280。这多出来的部分就是「不能劈开节点」的代价：为了不切断一条 12,000 token 的消息，尾巴只能整体保留。

为什么不能按「字节数」或「消息条数」来定尾巴？因为预算的单位是 token，而 token 的分布极不均匀：一条工具结果可能顶一百条用户消息。按条数算，遇到一个大结果就会严重超预算；按字节算，又会被 JSON 结构与多字节字符干扰。按节点累加是唯一能保证「不低于 retainTokens」的做法，代价是粒度粗——最后一个节点可能让尾巴超出预算不少。

第 3 段　回退：配对平衡，不劈开调用与结果

算完位置还要退。如果切点正好落在「一条 assistant 消息声明了工具调用、结果还没出现」的位置，压缩区就会包含调用、保留区包含结果，模型看到一条没有来源的工具结果，请求直接被服务端拒绝。

判定方式很轻：给每个切点算一个「在途调用数」。遇到 assistant/message，数它带了几个 tool-call 块就加几；遇到 tool/result 减一；其他事件不变。切点处计数为 0 就是平衡。已核实这个计数是增量维护的：每次 surface 变化就重建，之后只折新增节点，所以查一个切点是 O(1)。

并行调用是这套计数的一个好测试。一条 assistant 消息里带三个 tool-call 块时，eventDelta 返回 3；接下来三条 tool/result 各减一，只有第三条落地后计数才回到 0。已核实如果按「消息条数」而不是「调用块数」来算，三个并行调用会被当成一个，切点就会落在「三个调用只回来一个结果」的位置——请求必然被拒。这是「按语义单位计数」而不是「按容器计数」的典型例子。

不平衡就 keepFromIdx -= 1，把尾巴往前扩一个节点，再查新切点。这个「往前挪」的方向很重要：它让尾巴变大、压缩区变小，永远不会让压缩区变大。所以整个过程是保守的——宁可少压，不会多压。

这份平衡表是怎么维护的？它按 replaceGeneration 缓存（第 1 节讲过的那个「结构代」）：surface 一旦发生替换，下标全变，表就整体重建；普通追加只折新增节点。源码注释解释了为什么按 surface 顺序而不是按 step 标记来算——压缩会改变 surface 位置，step 标记却不会跟着变，两者一对齐就会错。已核实这也是「两层结构」带来的连锁收益：有了可靠的 surface，才可能有一个 O(1) 的配对查询。

挪到头会怎样？keepFromIdx 减到 firstIdx 时循环结束，随后返回 null。这意味着「整个前缀都在一个未闭合的调用里」，没有安全切点。这种情况一般出现在一个超长回合的中途：模型连着调了十次工具，中间没有可以下刀的地方。

第 4 段　返回值：起点是固定的，只有终点在动

函数最后返回 { start: first, end: cutoff }，其中 first 是 surfaceNodes[firstIdx]，cutoff 是 surfaceNodes[keepFromIdx - 1]。已核实整段搜索只改变了 keepFromIdx，firstIdx 从头到尾没动。

这就是「只压前缀」的代码体现。它带来的第一个后果是实现极简：不需要维护「保留段列表」，不需要考虑多段摘要怎么拼，摘要永远替换一个连续区间。第二个后果是无法只压中间：如果你有一段很老的、很大的工具结果夹在中间，选区要么把它一起压掉（连着前面所有内容），要么根本压不到它（因为切点在它后面）。

那中间的大块内容怎么办？靠 pruner。第 3 节会讲，压缩触发之后、选区之前，会先跑一次确定性的工具结果裁剪，把中间那些超长的结果原地换短。裁剪是「按条改内容」，压缩是「按段换摘要」，两者刚好互补：一个能钻进中间，一个只能切前缀。

这解释了一个设计上的分工：「精准但零成本」的活交给裁剪，「粗糙但要理解语义」的活交给压缩。如果只有压缩，中间的大块只能连着前缀一起被摘要，损失太大；如果只有裁剪，遇到「整段对话都需要概括」时就无能为力。

还有一层后果不那么直观：因为压缩区是前缀，替换之后「保留尾部」里不会出现「半条调用」。切点已经保证了平衡，替换节点本身又是一条完整的 user 消息，所以压缩后的历史在工具配对上是自洽的。这一点比看起来重要——如果切点允许不平衡，替换后就会出现「摘要消息后面跟着一个找不到调用的 tool/result」，服务端直接 400。所以配对约束不只是「别切坏」，它是「替换之后请求还能发出去」的前提。

第 5 段　null 是正常结果，不是错误

函数有三处返回 null：历史为空、整段都不够 retainTokens、退到起点仍不平衡。三处都表示「没有可安全压缩的区间」，调用方据此决定「这次不压」。已核实

这个约定很重要。如果返回错误，调用方要么把它当失败重试（浪费），要么把它当致命错误（中断用户请求）。返回 null 把「无事可做」和「做失败了」分开，让上层能做出正确反应：压力路径下 null 就直接返回，不写任何事件；溢出路径下 null 意味着「连一段都压不了」，只能把原始错误抛给用户。

溢出路径与手动路径都有一个特殊处理：selectCompactableRange(session, measurement, 0)，保留量传 0。已核实意思是「除了系统提示词，其他都可以压」。对溢出路径来说，这是三个约束里唯一被主动放弃的一个：已经确认超窗，没有余裕再谈「保留多少」，预算约束让位于「必须腾出空间」；对手动路径来说，则是用户明确要求压缩，保留量让位于压缩量。

压力路径则要耐心一些。调用方先判阈值，过了才跑 pruner、重测、选区；选区成功就压缩，压缩后再重测一次。如果仍高于阈值，就再来一轮，最多 compactionRetries + 1 次（默认 1 + 1 = 2 次尝试）。两次之后还高，抛错。已核实这个重试循环解释了一个常见现象：一次压缩之后上下文仍然接近满，不是因为压缩没生效，而是因为「保留量 + 系统提示词 + 工具定义」本身就接近阈值——这时候再压也没用，只能减工具或换窗口。

第 6 段　预算公式：为什么保留量必须小于阈值

resolveCompactSpec() 里有一条校验：retainTokens 必须严格小于 thresholdTokens，否则加载即报错。已核实理由不难推：如果保留量比触发阈值还大，那么「压缩后剩下的尾巴」本身就超过了触发线，下一次请求立刻又满足压缩条件，形成死循环。

默认值下这个关系是安全的：保留量约 0.16 × (W − O)，阈值约 0.8 × W（或被 headroom 压低），前者远小于后者。但当窗口很小、headroom 很大时，阈值会被压到很低——比如 100,000 的窗口配 65,536 的 headroom，阈值只剩 26,464，而保留量还有 14,720，两者已经很接近。再调大保留比例就会触发校验。已核实这条校验的价值在于：它把「配置错了会在运行时死循环」提前到了「启动时报错，并告诉你该调哪个参数」。

它还有一个副作用值得知道：校验失败是加载期错误，不是运行期错误。也就是说，一个配错的 compaction-basic 根本装不起来，宿主会直接看到「retainTokens 必须小于 threshold」这句话，而不是在某个长会话跑到一半时突然开始反复压缩。把「不可接受的配置组合」变成「装不上」，比任何运行期兜底都便宜。

✓要点小结

  • 选区是一段前缀：起点固定为第一个非 system 节点，只有终点在动。
  • 三个约束：尾巴 ≥ retainTokens、切点配对平衡、起点不碰系统提示词。
  • 配对平衡 = 切点之前的「tool-call 数 − tool/result 数」为 0；不平衡就往前挪，越挪压缩区越小。
  • null 表示「没有安全区间」，是正常结果；溢出路径把保留量设为 0。
  • 中间的大块内容不归选区管，归压缩前那次工具结果裁剪管。

05 · 与其他工具的差异

切点：连续前缀、候选集合、整轮边界

表注：dsh 见本节 permalink；Codex 见提交 76ed3b4 的压缩预算实现；pi 见 findCutPoint 与 isSplitTurn；opencode v1 见 select 与 splitTurn。

对照一：前缀 vs 候选集。dsh 的压缩区必须从第一个非 system 节点开始，所以它压的永远是「最早的连续一段」。Codex 不一样：它从历史里挑出真实用户消息，按 20,000 token 预算从新到旧装，装不下的那条截断后停止。挑出来的消息在时间上不连续——中间隔着助手回复与工具结果，但这些内容本来就不进候选。前者保留了「时间连续性」，后者保留了「用户原话」。已核实

对照二：预算的计量对象。dsh 的 retainTokens 是「尾巴上所有节点的 token 总和」，包含工具结果、助手回复、用户消息；Codex 的 20,000 只算「被选中的用户消息」；pi 的 keepRecentTokens 又是「切点之后所有条目的估算总和」。同样是 20,000 这个数量级，装的东西完全不同——比较预算数字必须先看计量对象，否则会得出错误结论。

对照三：配对约束的代价。dsh 用「不平衡就往前挪」处理配对，代价是压缩区可能比预算允许的更小；pi 用「合法切点白名单」处理，候选点只包括 user / assistant / bashExecution 等类型，绝不切在 toolResult，代价是要写一套切点搜索；opencode v1 用「整轮边界 + 必要时拆轮」，代价是拆轮时要处理「一轮被切成两半」的语义。三种做法的共同点是：宁可少压，不可切出孤儿调用。

最后说 dsh 这套选区的两个局限。第一，它压不到中间：一段很老的大工具结果，如果切点在它后面，它就会被一起压掉；如果切点在它前面，它就在保留区里原样留着。第二，它对「一轮特别长」无能为力：如果整个前缀都在一个未闭合的调用链里，配对约束会让它返回 null。dsh 的补救是 pruner 与溢出路径的保留量 0，而不是像 pi 那样引入「拆轮 + 双摘要」。这是一个明确的取舍：用更少的机制覆盖更常见的场景。

补一个第五家对照：Claude Code 压根不做「选区」。它压缩整段对话，然后把「最近改过的 5 个文件、用过的技能正文、plan 文件」按固定预算重新附上（文件 50,000、技能 25,000）。源码 v2.1.88所以它不需要配对约束——重附的是「新的内容块」，不是「旧历史的切片」。这提示了一件事：配对问题只属于「保留原消息」的方案；如果你改成「重新生成内容」，配对问题自动消失。代价是你必须回答「重新生成什么」，而这个问题比「切在哪」难得多。

06 · 思考题

三道题，从手算到改约束

Q1

surface 依次是：system(2,000)、u1(3,000)、a1(1,000，带 1 个 tool-call)、tr1(8,000)、u2(2,000)、a2(1,000，带 1 个 tool-call)、tr2(12,000)。retainTokens = 30,720。返回的区间是什么？如果 tr1 不存在（即 u1、a1 之后直接是 u2），结果会变吗？

提示（不给答案）

从尾往前累加：12,000 → 13,000 → 15,000 → 23,000（含 tr1 的 8,000）还没到 30,720，再往前是 a1 的 1,000 → 24,000，u1 的 3,000 → 27,000，system 的 2,000 → 29,000，仍不到。所以循环走到底，keepFromIdx = 0，0 <= firstIdx(1)，返回 null。

这道题的结论是「总量不够，压不了」。把 tr2 改成 30,000 再算一遍：从尾部累加到 tr2 是 30,000，还差 720，加上 a2 的 1,000 → 31,000 越过，keepFromIdx 落在 a2（下标 5）。再看配对：a2 是带 tool-call 的 assistant，切在它之前时前面的 tr1 已闭合，在途计数为 0，平衡，不用再挪。返回的区间是 [u1, u2]——注意 u2 也被压进去了，只有 a2 与 tr2 留在尾巴里。

Q2

把返回值的 start 改成 surfaceNodes[keepFromIdx]（也就是尾巴起点），会发生什么？

提示（不给答案）

那样压缩区就变成「从尾巴起点到尾巴起点」，是空区间；或者如果你同时调整 end，就变成「只压尾巴」，把要保留的内容压掉、把要压缩的内容留着。

更重要的是：replace 要求 startSeq 与 endSeq 都是当前 surface 节点，且是闭区间。一个「从中间开始」的区间在语义上是可以表达的，但 dsh 的摘要提示词、检查点结构、后续的「保留尾部」假设都建立在「压前缀」之上。改一行返回值不足以支撑这个语义变化。

Q3

你的会话总是「一个超长回合，模型连续调 30 次工具，中间没有用户消息」。dsh 的选区会怎么表现？你会改哪一处，代价是什么？

提示（不给答案）

先想配对：30 次调用如果首尾相接、每次结果都闭合，那么每个「结果之后、下一次调用之前」的切点都是平衡的，选区能正常工作。真正麻烦的是「最后一次调用还没返回」——那时最后一个平衡切点可能在很前面。

再看预算：一整轮里没有用户消息，尾巴按节点累加，可能一个巨大的 tr 节点就超过保留量，导致切点落在它之前，压缩区几乎为空。

改法参考 pi 的 isSplitTurn：允许在轮内部切，并为「轮前缀」单独写一份摘要，再与主摘要合并。代价是要多一次摘要调用、多一套合并规则，还要保证两份摘要不重复不矛盾。
