设计你自己的上下文策略

策略不是一组抄来的参数。它是一串有顺序的决定：先看清任务长什么样，再分预算。接着定减量的先后，最后才做隔离、延续和验收。顺序颠倒，参数越调越乱。

  • 约 30 分钟
  • 2 个练习
  • L4
  • 前置：第 23 章

读完你能做到

  1. 用五个维度描述一个任务，并从约束推出预算与减量顺序，而不是先选工具。
  2. 给出一个可执行、可验收的策略，写清每一步的触发条件与代价。
  3. 用评分点检查自己或别人的策略，指出哪一步缺了依据。

01 · 三个方案，都缺前提文字 · Karpathy L1

“调成 70% 就好了”

场景 · 周一上午的三份方案

团队要给内部代码助手定上下文策略。A 说：把压缩阈值从 90% 调到 70%，省得总是爆。B 说：上子代理，把所有探索都丢出去。C 说：换个 1M 窗口的模型，问题就没了。三个人都没说：任务多长、工具输出多大、几个人同时用、代码能不能出内网。三份方案都不算错，但都没法验收。

问题不在结论，在顺序。A 先选了参数，B 先选了机制，C 先选了模型。三个人都跳过了同一个问题：这个任务的压力从哪里来。压力来源不同，解法完全不同：

  • 压力来自工具输出（一次测试 20k token）——先做截断与落盘，压缩是后面的事。
  • 压力来自历史长度（80 轮对话）——压缩和裁剪都要用，且切点要对齐任务阶段。
  • 压力来自并发的探索（读了 60 个文件才找到一处）——子代理隔离比压缩更省。
  • 压力来自合规（历史不能出网）——先把架构限死，再谈参数。

所以策略的第一步不是“选什么”，是“量什么”。

02 · 五步框架图表 · Karpathy L2

从任务特征推到验收指标

下面五步是有顺序的。前一步的输出，是后一步的输入。任何一步跳过，后面的决定就没有依据。

  1. 任务特征：长度、工具密度、并发、合规、可分解性。回答“压力从哪来”。
  2. 预算分配：窗口减去固定开销，得到可用历史；再定阈值与保留段。
  3. 减量顺序：先做不改历史的，再做可还原的，最后才做不可逆的。
  4. 隔离与延续：哪些历史该留在主会话，哪些该丢给子代理，哪些该写进记忆。
  5. 验收指标：一个主指标、两个护栏、三到五个探针问题。

第五步会回头改第一步和第二步。验收发现“短任务变差”，说明阈值定早了。发现“约束丢失”，说明保留段或摘要模板有问题。这个回边是正常的，不代表框架错了。

为什么是五步，不是七步？因为这五步各自产出一个可以直接写进策略表的东西。它是一组约束、一组数字、一个顺序、一套隔离方案、一组指标。再多一步，就会和已有步骤重叠。再少一步，策略表就会缺一行。

五步不是瀑布。做到第三步发现预算不够，要回到第二步重分。做到第五步发现指标不动，要回到第一步重新量任务。把它当成一个循环，而不是一张一次性填完的表。

框架还有三个反直觉的地方。第一，预算要在选减量之前算，因为“还剩多少”决定了能不能用压缩之外的办法。第二，减量顺序按可逆性排，不按成本排，最便宜的那一步不一定该先做。第三，验收要在写策略时定，不能等跑完再挑指标。跑完再挑的指标，一定支持你已经做的决定。

这棵树只定架构，不定参数。参数在下面五节里算。另外，树上的“否”不是“永远不需要”，是“当前不需要”。任务变长、合规变严，要重新走一遍。

03 · 第一步：量任务图表 · Karpathy L2

五个维度，三种档位

不要给任务打分，打分会产生假的精确感。用“低 / 中 / 高”三档描述即可，重要的是每一项都能指向一个后续决定。

← 左右滑动查看全部列，首列固定 →

维度 怎么量 它决定什么 高档位的样子
长度 一次任务的轮次、工具调用次数、最长一次连续不中断的时长。 压缩会不会触发、阈值定多早、要不要按阶段切会话。 超过 30 轮，或单次任务跑满一小时。
工具密度 平均每轮工具结果占多少 token；最大一次工具输出多大。 先做截断还是先做压缩；要不要落盘回读；保留段留多少。 每轮都有工具，单次输出常超 10k token。
并发 同时运行的会话数、每个会话的子代理数、是否需要 worktree 隔离。 隔离方式、存储与日志的写入压力、缓存是否互相污染。 多人同时用，或一个任务并行改多个模块。
合规 历史能否离开本机；能否被第三方留存；是否需要逐条审计与删除。 服务端压缩能不能用；日志要留多久；记忆能不能写。 代码不出内网，或对话内容受监管。
可分解性 子任务能否独立验收；子任务之间要不要共享文件状态。 能不能用子代理隔离；要不要 worktree；返回什么结构。 能拆成“扫描 / 改 / 验证”三段，各自有明确产出。

五个维度里，合规是唯一“一票否决”的：它不参与权衡，只排除选项。其余四个可以互相补偿，比如长度高但工具密度低，未必要压缩。

没有历史数据时，怎么快速量？挑三个真实任务。从日志里数四个数：总轮次、工具调用次数。再数单次工具输出的 p95 token、任务结束时的窗口占用。四个数不用精确，量级对就够。比如“20 轮、60 次工具、p95 是 8k、结束时 120k”。这组数已经能判断压力主要来自工具输出，而不是对话长度。先量三个，比先调十个参数有用。

工具密度还有一个间接影响：它决定“压缩后模型要不要重读”。工具输出多的任务，压缩后往往要重新跑测试、重新读文件。这部分成本要算进 CPS。工具输出少的任务，压缩后靠摘要就能继续。同一个阈值，在两类任务上的实际收益可能相反。

一个任务只有 12 轮，但每轮都读一个 3,000 行的文件。它算“短任务”还是“长任务”？该先做什么？

提示：长度看轮次，压力看 token。12 轮也可能塞满窗口。

04 · 第二步：分预算文字＋算例 · Karpathy L1

先减固定开销，再谈历史

预算不是“窗口有多大”，是“历史能用多少”。固定开销先扣掉，剩下的才是可分配的历史。

预算公式 
可用历史 = 窗口 − 系统提示 − 工具定义 − 规则文件 − 输出预留 − 安全余量
 
触发阈值 = 可用历史 × 阈值比例
压缩后占用 ≈ 摘要 + 保留段 + 固定开销

以 200k 窗口为例，一套可以落地的数字：

  • 系统提示 + 工具定义：12k（工具越多越大，MCP 全量下发时会明显上涨）。
  • 规则文件：8k（多级拼接后的总量，不是单文件）。
  • 输出预留：16k。注意它不只是“最大输出”，还要覆盖工具调用的参数。一次写文件、一次大 patch 都算输出。
  • 安全余量：10k。给估算误差、图片、临时附件留的位置。
  • 可用历史：200 − 12 − 8 − 16 − 10 = 154k。
  • 阈值：154 × 70% ≈ 108k；保留段：20k。
  • 压缩后一次请求约 12 + 8 + 摘要（约 3k）+ 20 = 43k。这已经回到阈值以下，留出继续跑的空间。

这些比例是示例，不是任何工具的默认值1。真实值要按你的工具表大小、规则体积和输出上限重算。算完写进策略表，别留在脑子里。

三个容易算错的地方：

  1. 把“窗口”当“可用历史”：直接按 90% 触发，结果压缩请求自己就超窗。压缩要再发一遍历史，它比正常请求更大。
  2. 输出预留只按文本算。工具调用的 JSON 参数、思考内容、并行工具的多份参数，都会吃输出预算。
  3. 忘了压缩后的固定开销：压缩只减历史，不减系统提示和工具表。工具表很大时，“压完还是很满”是正常的。

05 · 第三步：排减量图表 · Karpathy L2

按可逆性排，不按成本排

很多人按“哪个便宜”排减量：截断最便宜，压缩最贵。这个排法在工程上会出事，因为它忽略了另一件事：做完还能不能回去。

四级各自的触发条件不一样，不要用同一个阈值串起来：

  • 截断：单次工具输出超过上限时立刻做，和窗口无关。上限按“模型需要多少才能判断”定，不按“窗口还剩多少”定。
  • 裁剪：旧工具结果已经过期（文件被改过、测试已重跑）时做。判据是“还能不能用”，不是“有多旧”。
  • 压缩：历史总量到阈值时做。粒度要落在任务边界：按模块、按工单、按阶段，而不是按 token 数硬切。
  • 新会话：前三步做完仍然装不下，或任务目标已经变了。切之前写一份交接摘要，否则等于重新开始。

顺序错了会怎样？先压缩再截断，等于把“本可以直接丢掉的工具输出”也写进了摘要。既花了摘要的 token，又把噪声留在了摘要里。先新会话再裁剪，等于丢掉了本可以还原的原文。这两种都很常见，因为“压缩”听起来最像解决方案。

“不可逆”不等于“不能用”。有些信息本来就不需要精确回读。比如三轮前的测试输出、已经合并的 diff、被否决的方案。对这些内容，压缩往往比裁剪更彻底。裁剪把一段内容换成占位符，省下的是那一段。压缩把整段改写成几句话，省得更多，代价是细节也没了。判断标准不是“可不可逆”，是“后面还需不需要逐字回读”。

还有一条实践规则：减量的每一级都要有“关闭开关”。不是为了上线后关，而是为了做消融时能单独关掉。没有开关的策略，无法回答“是哪一级在起作用”。它只能整体比较。

一次只动一层

调策略时，一次只改一级。同时开截断、裁剪、压缩，指标变好你不知道是谁的功劳。变坏也不知道该回退哪一个。这条在第 23 章的 A/B 里叫“只允许一个变量不同”。

06 · 第四步：隔离与延续文字 · Karpathy L1

该留下的留下，该丢出去的丢出去

减量解决“装不下”，隔离解决“不该装”。判断标准只有一句话：这段历史后面还要被继续改写吗？

  • 还要改写：留在主会话。比如正在改的那个文件、正在调的接口。
  • 只要结论：丢给子代理或工具，只回结果。比如“这个函数在哪些地方被调用”。你要的是列表，不是 60 个文件的原文。
  • 跨任务复用：写进记忆或规则。比如“这个仓库的测试必须先起 Docker”。
  • 已经结束：封存成交接摘要，开新会话。

子代理不是越多越好。它适合“读得多、写得少、结论短”的子任务。它不适合需要频繁回改的编辑任务。因为父会话看不到中间过程，一旦方向错了，只能整段重来2。一个实用的分工：

  • 扫描 / 定位 / 调研 → 子代理，返回结构化列表（路径 + 行号 + 一句话）。
  • 改代码 / 跑测试 → 主会话，因为要连续看 diff 和失败输出。
  • 并行改不同模块 → 每个模块一个 worktree 加一个子代理。父会话只收“改了哪些文件 + 测试结果”。

延续的关键是交接摘要的格式。不要写“上面聊了很多，继续”。要写五行：目标、已完成、未完成、约束、验收命令。这五行足够让一个新会话接着干，而且比整段历史短一个数量级。

一份能用的交接摘要长这样。目标——把 order 包的日期库迁到 date-fns。已完成——3 个文件、测试绿。未完成——checkout 包的 12 个调用点。约束——不改 public API、不改导出签名。验收——pnpm test order && pnpm lint。一百多字，比原始历史短两个数量级，但足够接着干。

07 · 第五步：定验收图表 · Karpathy L2

写策略的时候就把验收写进去

验收不是最后补的。策略里每一条“我们这样做”，都要能对应一个“怎么知道它有用”。指标定义见第 23 章，这里只讲怎么选。

你改了什么 主指标 护栏 探针问题
调压缩阈值 CPS（每成功任务成本） SR、IRR 早期约束、验收命令
加子代理 父会话 token 增量 SR、子代理返回长度 子代理结论是否被父会话采用
开记忆 跨会话任务的 SR 污染率、记忆命中率 上次的决策理由、偏好
换服务端压缩 CPS IRR、审计可回放率 被删段里的路径与决策

只选一个主指标。两个主指标等于没有主指标——冲突时无法裁决。护栏的作用是“一票否决”，不是“再看好不好”。

护栏阈值不要拍脑袋。成功率护栏通常取“下降不超过 1 个百分点”，因为它接近评测噪声的下限。IRR 护栏取“不低于基线 95% 且绝对值不低于 80%”。前者防止相对退化，后者防止基线本来就很低。阈值写进策略表，跑完不改。

09 · 练习一文字 · Karpathy L1

10 万行 monorepo 的重构任务

已知条件

仓库 10 万行，40 个包，pnpm monorepo，TypeScript。任务：把 3 个包里的日期库从 moment 迁到 date-fns。涉及约 180 个文件。约束：不能改 public API。CI 必须全绿。两名工程师并行改不同包。代码不能出内网。工具密度高：每改完一批就跑测试，单次输出 2k–20k token。

先别往下读。拿一张纸，用第 08 节的六行模板写一版。写完再对照下面的参考策略。

参考策略

约束
长度高（跨包、多轮）；工具密度高；并发 2；合规硬约束（不出内网）；可分解性高（按包拆）。
预算
200k 窗口；系统与工具 14k、规则 6k、输出预留 16k、余量 10k；可用历史 154k；阈值 70%（约 108k）；保留段 20k。
减量顺序
① 测试输出只留“失败用例 + 首尾各 20 行”，其余落盘；② 已改过的文件读取换占位符（路径 + 改动摘要）；③ 到阈值时按包压缩，不按全局压；④ 单包结束后封存交接摘要，开下一个包的新会话。
隔离
“扫描 moment 调用点”交给子代理，只回“文件 + 行号 + 用法类型”三列；改码与跑测试留在主会话；两个包各开一个 worktree，父会话只收每个包的改动文件列表与测试结果。
记忆
只写两条：迁移映射表（moment API → date-fns API）、public API 白名单。任务结束写入，按仓库隔离。
验收
主指标 CPS；护栏 SR（CI 绿且 public API 无 diff）、IRR（4 个探针：白名单、映射表、验收命令、禁止修改的导出）。

为什么按包压缩，而不是全局压缩？因为包是天然的验收边界。一个包改完、测试绿了，它的历史就可以整段换成“改了什么 + 测试结果”。全局压缩会把三个包的细节混进同一份摘要。后面要查“这个包为什么改了这行”就查不到了。

还有一个容易忽略的点：迁移任务的映射表本身占预算。180 个文件涉及十几种用法，映射表可能有 2k–4k token。放规则还是放记忆，取决于它是否跨会话复用。只服务这一次迁移，放记忆；长期都要遵守，放规则文件。

评分点（每项 2 分，共 10 分）

  1. 预算里有没有输出预留：只写“窗口 200k、阈值 80%”得 0 分。算出可用历史并给压缩后占用估值得 2 分。
  2. 压缩粒度是否对齐任务边界：按包/按阶段得 2 分。只说“到阈值就压”得 1 分。按固定 token 硬切得 0 分。
  3. 有没有用隔离处理“读得多”的子任务：扫描给子代理、回结构化列表得 2 分。只把子代理当“并行改码”用得 1 分。
  4. 有没有守住不可逆约束：public API 白名单进入探针或护栏得 2 分。只在提示词里写一句“不要改”得 0 分。
  5. 验收是否可执行：给出命令、阈值、探针问题得 2 分。只写“看效果”得 0 分。

最常见的失分点是第 1 项和第 4 项。前者把窗口当可用历史，后者把约束交给模型自觉。

评分点不是考试，是自查。写完策略后，逐条问自己“这一项我有没有写”，比问“这一项我写得对不对”更有用。对错要靠实验回答，有没有写只靠自己。

10 · 练习二文字 · Karpathy L1

客服工单里的长对话

已知条件

每个工单 40–120 轮，中英混杂，客户会在中途改需求。坐席用 Agent 查订单、发邮件、查知识库，工具密度低但调用频繁。50 个坐席同时在线。合规要求：对话要保留 6 个月、可逐条审计。客户个人信息不能进第三方服务。需要跨工单记住客户偏好，但不能记住无关的隐私。

先写一版再对照。这一题的陷阱是：它看起来像“长对话摘要”，其实一半是“结构化抽取”。

参考策略

约束
长度高（轮次多但每轮短）；工具密度中；并发高（50 坐席）；合规硬约束（可审计 + 不出网）；可分解性低（一个工单必须一个上下文）。
预算
32k 小窗口；系统 3k、工具 2k、输出预留 3k、余量 2k；可用历史 22k；阈值 80%（约 17.6k）；保留段 6k。
减量顺序
① 订单/物流查询只保留字段（订单号、状态、金额、时间），不保留原始 JSON；② 每 10 轮把对话折叠成结构化事实卡（诉求、承诺、订单号、金额、情绪、待办）；③ 到阈值时再生成叙事摘要，事实卡作为附件保留；④ 工单结束封存，不新开会话。
隔离
一个工单一个会话；知识库检索交给工具，只回命中的三条与摘要；跨工单只写结构化 CRM 字段，不写自由文本。
记忆
白名单字段：语言偏好、联系方式偏好、历史投诉类型。写入前脱敏，30 天过期，可按客户删除。
验收
主指标一次解决率；护栏 IRR（承诺事项、订单号、退款金额）、审计可回放率 100%；探针 4 个，答案只能来自被折叠的段落。

这一题的关键决定是把“事实”和“叙述”分开。事实卡是结构化的，字段固定，压缩不会丢。叙述摘要可以写得很顺，但容易漏掉金额和承诺。先抽事实、再写摘要，等于给摘要加了一层校验。摘要与事实卡冲突时，以事实卡为准。

第二个关键决定是记忆只写白名单。客服场景里，“客户上次说喜欢电话回访”有用。“客户上次提到家里有事”不该被记住。白名单不是技术限制，是合规边界。

评分点（每项 2 分，共 10 分）

  1. 有没有结构化的中间层：事实卡/槽位得 2 分。直接叙事摘要得 1 分。只做截断得 0 分。
  2. 合规是否落到机制：脱敏、白名单、可删除、审计日志，至少三项得 2 分。只写“注意隐私”得 0 分。
  3. 并发是否影响选型：考虑多租户存储与日志写入得 2 分。完全没提得 0 分。
  4. 指标是否对业务有意义：一次解决率/审计可回放率得 2 分。只写 token 成本得 0 分。
  5. 保留段是否覆盖“承诺”：明确保留最近承诺与订单信息得 2 分。只按轮数保留得 1 分。

这一题最常见的失分点是“只做摘要、不做结构化”。叙事摘要读起来顺。但金额、订单号、承诺时间这类字段一旦写错，后面每一轮都会沿用错误值。第二个失分点是记忆写成自由文本，导致无法按客户删除。

11 · 交卷前自检文字 · Karpathy L1

五问，答不上来就还没写完

  1. 压力从哪来？说得出是工具输出、历史长度、并发探索，还是合规，而不是“感觉不够用”。
  2. 预算是算出来的还是抄来的？每一项固定开销都有数字，且加起来不超过窗口。
  3. 减量顺序能不能单独回退？四级各自有开关，关掉一级不影响另外三级。
  4. 隔离后父会话知道结果吗？子代理返回结构化结果，失败时有明确信号，不是静默消失。
  5. 不达标时回退哪一步？写清“先回退阈值，再回退压缩粒度”，而不是“整体重做”。

这五问对应五步框架，也对应策略模板的六行。写完策略后隔一天再读一遍，通常能发现至少一处“当时觉得显然、现在说不清”的地方。

评审时，把这张表和策略一起发出去，比只发结论有效。评审人通常不会从头读你的推理，但会直接看“约束”和“验收”两行。约束是否覆盖了真正的硬限制，验收是否能被第三方执行。这两行过了，中间的预算与减量才有讨论的基础。

最后一件事：策略是活的。任务从“改一个包”变成“迁三个包”，长度和并发都变了，阈值就该重算。团队从“能出网”变成“不能出网”，架构可能整段作废。把它当成一份会过期的文档，而不是一次性作业。每次改完，在模板底部写一行“本次变更与原因”，下次评审时能省很多解释。

脚注
