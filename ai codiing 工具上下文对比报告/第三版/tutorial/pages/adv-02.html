失败：五次事故，一条因果链

上下文事故很少是“模型变笨了”。它们通常有一个可复现的起点：一条约束没进规则文件，一个切点拆散了工具对，一处易变内容站在缓存前缀里，一次子代理返回太长，或者一次回退只退回了一半。这一页复盘五次事故，并把每次事故拆成可操作的修复。

  • 约 23 分钟
  • 1 个交互
  • L4

读完你能做到

  1. 用“现场 → 症状 → 根因 → 修复 → 预防”五段，复盘任意一次上下文事故。
  2. 把症状映射回 16 类中的至少一类，并给出配置、流程、代码三档修复。
  3. 为每个案例设一个可观测指标，在下一次事故前报警。

01 · 复盘的方法

不要从“模型错了”开始

周五下午五点二十，团队把一个月里的五次事故摆到桌上。五次都发生在同一套工具上，五次都有人说过“这次模型不太行”。但把日志摊开看，五次都能找到一个具体的上下文变化：一条约束被摘要改写，一个切点落在工具调用中间，一段日期被塞进系统提示，一个子代理返回了 9k 字，一次回退只退了对话。

这一页用固定五段复盘：

  1. 现场：具体时间、任务、轮次、窗口占用。
  2. 症状：能看见、能计数、能复现的现象。
  3. 根因：回到 16 类中的哪一类，必要时给两个类。
  4. 修复：配置、流程、代码三档，从便宜到贵。
  5. 预防：一个指标或一个检查项，能提前报警。

先记住这条因果链

案例一不是“模型忘了”，而是“约束从来没进过一个不会被压缩的地方”。下面这条链把五个环节连起来；后面四个案例，只是把其中某一环换掉。

02 · 案例一

压缩后，三条硬约束只剩下一条

现场

周四 15:40，一个“把导出模块拆成独立包”的任务跑到第 41 轮。窗口占用 18.2 万 token，期间压缩了 6 次。开工时用户说过三条硬约束：不要改 public API；测试命令是 pnpm test:unit；保留 export 的命名。三条都只出现在对话里，没进 AGENTS.md。

症状

  • 模型把 src/index.ts 的三个导出名改成了新包的命名。
  • 它把测试命令写成 npm test，并说“项目里没有 test:unit”。
  • 问它为什么改，它回答：“摘要里没有看到这条限制。”
  • 压缩记录显示：第 6 次压缩后，摘要只有 1.1k 字，三条约束一条都不在。

根因

第 8 类（压缩）是直接原因。Codex 本地压缩只把“真实用户消息”纳入候选，预算 20k，从新到旧累加，放不下就停；最新一条长指令自己放不下时，会被截到剩余预算。第 15 章 2.2 摘要模板只要求四类信息：进度与决策、重要上下文与偏好、待办、关键数据与引用。第 15 章 2.3 “不要改 public API”既不是进度，也不是待办，很容易被写成一句“保持 API 稳定”。

第 2 类（规则文件）是结构性原因。三条约束都只在对话里，而对话正是压缩的对象。规则文件会作为系统提示或项目上下文重新注入，不进入压缩候选；Codex 压缩后还会把初始上下文重新放回。第 15 章 2.4 约束没进规则，就等于把唯一的副本放在会被改写的地方。

还有一层累积效应：第 2 次压缩的输入里已经包含第 1 次的摘要，第 3 次又包含第 2 次的摘要。每一轮都可能丢掉上一版摘要里的一点细节，而没有任何一步会把它补回来。1

修复（三档）

改配置。把三条约束写进 AGENTS.md 或 CLAUDE.md，放在文件最前面。Codex 的规则文件总量默认 32 KiB，三条约束只占几十字节，完全放得下。agents_md.rs#L60-L160 已核实 同时把压缩保留预算调高，或开启压缩后重附文件。

改流程。长任务每压缩两次，就把三条约束原样复述成一条短消息，放在最新一条用户消息里；压缩后立刻跑一次约束检查，不合格就补一条。不要等模型改完代码再发现。

改代码。在摘要提示词里加一段固定要求：“以下约束必须逐字保留，不得改写。”压缩后用脚本做字符串比对；三条里少一条就重试，或拒绝这次压缩。代码改动最贵，但它把“靠模型自觉”换成了“靠检查失败”。

怎么预防

设一个指标：hard_constraint_retention = 摘要中逐字出现的硬约束数 ÷ 硬约束总数。目标 100%，低于 100% 就报警。再设一个二级指标：first_constraint_loss_round，记录第一次丢失硬约束发生在第几次压缩；它比“本次是否丢失”更早暴露趋势。

如果你只能改一件事：把三条约束从对话搬进规则文件。它最便宜，也最不容易被下一次压缩吃掉。

03 · 交互演示

下面这个演示不调用模型。它用一张手写的“示意衰减表”，让 12 条事实在每次压缩后进入保留、变形、丢失三种状态。左侧是控件；画布内左栏是 12 条事实（3 条硬约束），右栏是每次压缩后的摘要。

建议按三个实验看：第一，保持“标准”模板，把压缩次数从 1 拉到 6，观察第一条硬约束在第几次消失；第二，切到“精简”，看它提前到第几次；第三，打开“重附文件”，观察文件类事实恢复、硬约束不恢复。

教学模型，不是任何 agent 的真实摘要算法。12 条事实与衰减表都是手写示意；“字数”是渲染文本的字符数，不是 token 实测。硬约束只判保留或丢失，不判变形。后期摘要可能更短，因为事实被丢掉了，不代表更安全。

三个读数

第一，精简模板的损失不是线性的。 默认“标准”模板、4 次压缩时，三条硬约束还剩两条；切到“精简”，第一条硬约束会在第 3 次就消失，因为精简只保留“约束”和“进度”两段，文件、状态、待办都不记录。

第二，重附文件救不了约束。 打开“重附文件”后，已读文件和新建的 package.json 会按磁盘原文恢复，摘要长度也会增加；但三条硬约束仍然按原表衰减。文件里没有“不要改 public API”，重附再多次也补不回来。

第三，摘要变长不等于更安全。 “详细”模板保留的事实更多，摘要通常也更长；但它只是把丢失推迟，并把更多事实写进摘要，不能保证关键约束逐字保留。长度是成本指标，不是保真指标。

04 · 案例二

切点落在工具调用和结果之间

现场

周二 11:05，一个“找出所有旧导出入口”的任务跑到第 18 轮。一次 grep 返回了 60k 字符，压缩在第 12 轮和第 13 轮之间触发。切点正好落在一次工具调用和它的结果之间：调用进了摘要，结果留在保留段。

症状

  • 下一次请求直接返回 400，错误指出 tool_result 没有对应的 tool_use。
  • 换一个宽松的 provider 后请求通过了，但模型说“搜索结果为空”，然后重复执行同一个 grep。
  • 重复搜索又产生 60k 输出，窗口再次到线，形成循环。

根因

第 8 类（压缩切点）是直接原因。切点选在了“结果之前、调用之后”，这在消息层面看是一个合法边界，在工具协议层面却不是。工具调用和结果是一条原子记录，拆开就得到一条“有结果、没有调用”的历史。第 15 章第 4 节

第 1 类（请求组装）是协议原因。严格 API 会直接拒绝这种历史；宽松模型会把结果当成新的事实，开始编造它为什么存在。

第 14 类（失败恢复）是放大原因。压缩失败后没有回落，下一次请求继续用同一份坏历史；重复搜索又把窗口推回触发线。

修复（三档）

改配置。打开成对切点。pi 的 findCutPoint 明确规定“绝不切在 toolResult”，切在带工具调用的 assistant 时，其结果会随后保留；DeepSeek Harness 的 selectCompactableRange 会从预算位置往前挪到工具配对平衡处。第 15 章第 4 节

改流程。压缩前做一次 dry-run：列出切点两侧的消息类型，确认没有孤立的调用或结果。把这一步写进发版检查，和“跑测试”放在同一张清单上。

改代码。在两个位置兜底：切点选择时，如果落在结果之前，就前移到调用之前；历史重建后，如果发现孤立结果，就删除它或补一个占位调用。前移会多保留一对结果，后移会丢掉最近的工作状态；多数 agent 选前移。

怎么预防

设指标 orphan_tool_results = 压缩后历史中“没有配对调用的结果”数量。目标恒为 0；大于 0 就拒绝提交这次压缩。再加一条 pairing_repair_count，记录切点被修复的次数；它持续上升，说明预算或切点算法需要调整。

如果你只能改一件事：让切点只能落在合法的消息边界，并且工具调用与结果整对保留。

05 · 案例三

缓存失效，把账单推高三倍

现场

月末对账，团队发现这个月的模型账单是上个月的三倍。任务量只涨了 20%，代码没大改。排查后发现：系统提示词的第一段放了 git status，第二段放了当前时间，第三段放了 todo 列表；分支名每天变十几次，todo 每轮都变。同期，团队把自动压缩阈值从 90% 调到了 75%。

症状

  • cached_input_tokens ÷ 总输入 token 从 78% 掉到 12%。
  • 每轮首 token 延迟明显上升，长会话更明显。
  • 成本曲线和“压缩次数”高度同步：压得越勤，账单越高。
  • 删掉很多 agent 输出后，token 总量下降了，账单却没降。

根因

第 13 类（缓存友好设计）是主因。缓存按前缀匹配，从第一个不同的字节起失效。把 git status、时间、todo 放在系统提示词最前面，等于每一轮都从第一个字节起重算。第 20 章

第 4 类（动态注入）是结构原因。易变内容不是不能注入，而是不该注入到稳定前缀里。oh-my-pi 把日期与 cwd 提醒移到首个用户轮；Grok Build 把日期固定在会话启动值，跨午夜才追加一次 reminder；DeepSeek Harness 用新增 user 消息承载时间。第 20 章第 6 节

第 8 类（压缩）是放大器。每次压缩都会替换历史中段，从被替换的第一个 token 起失效；压缩越频繁，失效越频繁。早压本身没错，错在“早压 + 易变前缀 + 高价值缓存”三件事同时发生。

修复（三档）

改配置。把系统提示词改成“稳定段在前、易变段在后”：静态规则、工具定义、项目约定在前；日期、分支、todo 放到首个用户轮或尾部提醒。工具定义按名字排序，避免顺序漂移。

改流程。把压缩安排在任务边界，不要每小时压一次；长停顿前手动压一次，比每分钟自动压更省。每次压缩后记录“失效了多少 token”，把它当成一项成本，而不是免费操作。

改代码。加一层缓存归因：每次请求记录系统提示词哈希、工具表哈希、压缩事件；把 cached_tokens 和这些事件对齐。Claude Code 有专门的 promptCacheBreakDetection 模块做归因，可以作为设计参考。promptCacheBreakDetection.ts#L31 源码 v2.1.88

怎么预防

设三个指标：cache_read_ratio（缓存读 ÷ 总输入）、invalidation_tokens_per_compaction（每次压缩造成失效的 token 数）、cost_per_successful_task（每个成功任务的成本）。第一个看趋势，第二个看单次质量，第三个看最终账单。只看第一个，容易为了命中率不敢压缩；三个一起看，才能判断“这次压缩值不值”。

如果你只能改一件事：别让易变内容站在缓存前缀里。把它移到尾部，或者移到首个用户轮。

06 · 案例四

三个子代理，把父上下文撑爆

现场

周三 16:20，一个“审查 120 个文件的导出使用”的任务。主会话派了 3 个只读子代理，分别看 src/、packages/、tests/。每个子代理返回 8k–12k 字的自由文本，包含文件清单、逐条引用和推理过程。父上下文从 60k 涨到 190k，下一轮就触发了压缩。

症状

  • 父上下文单轮增加约 90k，其中 85% 是子代理返回。
  • 下一轮触发压缩，压缩后的摘要只剩“三个子任务都完成了”。
  • 三个子代理的结论互相矛盾：一个说“没有循环依赖”，一个说“有两处”。父模型无法判断谁对。
  • 父模型再派子代理复核，又产生一轮长返回，形成循环。

根因

第 10 类（子代理隔离）是主因。子代理的中间过程被隔离了，但返回没有隔离。Claude Code 默认给子代理全新上下文，只读代理还省掉 CLAUDE.md 与 gitStatus；返回给父代理的是最终内容块 + agentId + 用量尾注。runAgent.ts#L370-L410 源码 v2.1.88 这条路径没有显式的“返回长度上限”。2

第 5 类（预算）是放大器。父上下文本来只剩 140k 空间，三个 10k 字返回就吃掉了大部分余量；再加上工具结果，必然到线。

第 8 类（压缩）是二次伤害。压缩把子代理返回的细节删掉，只留下“完成了”；父模型失去了判断矛盾结论的依据。

修复（三档）

改配置。给子代理设输出上限；只读任务用只读代理；限制并发数。oh-my-pi 的 task 子会话要求 schema 校验返回，深度默认 2；opencode v1/v2 默认深度 1；Grok Build 默认后台执行，可选 worktree 隔离。第 17 章

改流程。给子代理一个固定返回模板：结论（一句话）、证据（文件:行）、置信度、待确认项。全文写进文件，父会话只收模板和文件路径。三个子代理的返回先合并去重，再交给父模型。

改代码。父端做两层限制：单次返回超过 2k token 就截断，并附全文路径；合并阶段按“文件:行”去重，冲突项单独列出。不要让父模型自己从 30k 字里找矛盾。

怎么预防

设两个指标：subagent_return_tokens（单次返回 token）和 parent_context_delta（父上下文单轮增量）。建议上限分别是 2k token 和父窗口的 15%。超过就报警，并检查返回模板是否被绕过。

如果你只能改一件事：让子代理回“结论 + 指路”，不要回“全文”。

07 · 案例五

回退到第 12 轮，文件却停在第 30 轮

现场

周五 10:30，一个重构任务跑到第 30 轮，中间压缩过 2 次。团队决定回退到第 12 轮，换一个方案。回退后，对话历史回到了第 12 轮，但工作区文件仍然是第 30 轮的状态；当前上下文里还留着第 2 次压缩生成的摘要。

症状

  • 模型说“我们还没改过 export.ts”，但磁盘上的 export.ts 已经是改过的版本。
  • 它把第 13–30 轮已经做过的修改又做了一遍，产生重复代码。
  • 测试结果与对话状态不一致：摘要说“测试通过”，实际跑出来是失败的。
  • git diff 里既有第 12 轮之前的改动，也有第 30 轮的改动，无法判断哪些该保留。

根因

第 11 类（会话时间线）是主因。回退通常只回退“对话历史”，文件回退是另一条链路。Claude Code 的 /rewind 会打开消息选择器，真正的文件恢复由 fileHistoryRewind 执行，依赖每轮对话前创建的文件快照，最多保留 100 个；对话侧与文件侧必须一起回退。fileHistory.ts#L54-L57 源码 v2.1.88

第 8 类（压缩）是残留原因。压缩只替换内存历史，原始记录仍在存档里；但回退到压缩前，模型看到的是“旧摘要 + 新文件”，而不是“旧原文 + 旧文件”。摘要不可逆，这一步无法靠回退修复。第 18 章 2.23

第 6、7 类（工具输出控制与裁剪）是次要原因。回退后重新读文件，读到的是磁盘上的新版本；旧版本的工具结果已经被裁剪或替换，模型没有对照物。

修复（三档）

改配置。开启文件快照或检查点；保留原始 transcript；压缩时不要删存档。Claude Code 的快照上限是 100 个，超过后最旧的会被淘汰，长任务要配合分支使用。

改流程。回退前先建一个新分支或 git stash；回退后先跑 git status 和测试，再让模型继续。不要在压缩后回退到压缩前；如果必须回退，先重新读一遍关键文件，并把摘要标记为“可能过期”。

改代码。回退时同时恢复对话与文件，并生成一份“状态对账”摘要：哪些文件改了、测试现在是什么状态、摘要里的文件清单与磁盘是否一致。对账不通过就阻止继续。

怎么预防

回退后跑三项检查：git status 是否只剩预期改动；测试是否与摘要描述一致；摘要里的文件清单是否都能在磁盘上找到对应版本。再加一个指标 duplicate_edit_rate（回退后重复修改的比例），它持续上升，说明回退链路没有对齐。

如果你只能改一件事：回退时同时回退对话和文件。只回退一半，比不回退更危险。

08 · 把五次事故放在一起

五个症状，四类根因，一组指标

五次事故看起来各不相同，根因却集中在四类：约束没进规则（第 2 类）、切点不合法（第 8 类）、前缀不稳定（第 13 类）、边界不闭合（第 10、11 类）。它们都通过同一个放大器起作用：压缩。

如果整页只能改一件事

把硬约束移出对话，写进规则文件；然后给每次压缩加一道断言：三条约束必须逐字出现。前者消除根因，后者兜住漏网。两件事加起来，比换模型、加窗口、调阈值都便宜。

一张五分钟检查清单

  1. 这次任务的硬约束，是否有一条不在规则文件里？
  2. 上一次压缩的切点，是否落在工具调用与结果之间？
  3. 系统提示词的最前面，是否有每轮都会变的内容？
  4. 子代理的返回，是否有 schema、字数上限和全文落盘？
  5. 回退时，对话与文件是否在同一条链路上？

五个问题里有一个答“否”，就先修那一项，再谈调参。上下文事故的修复顺序，永远是先修结构，再修参数。

09 · 小测验

三道题，检验你会不会定位根因

Q1

案例一里，三条硬约束在第六次压缩后全丢了。为什么第一优先级是「把约束写进规则文件」，而不是「把压缩阈值调低」？

解析

阈值只改变压缩发生的时点，不改变「约束只存在于会被摘要改写的地方」这个结构。规则文件每轮重新注入，压缩碰不到它；调阈值只是让同一场事故晚一点发生。修复顺序是先修结构、再修参数，案例里的三档修复也是按这个顺序排的。

Q2

案例二的切点落在 tool_use 与 tool_result 之间，为什么结果是 400，而不是「模型回答变差」？

解析

请求在协议层就不合法：tool_result 必须对应一条 tool_use。切点把配对拆开，客户端发出去的请求会被直接拒绝，轮不到模型判断。修法是切点校验：目标恒为 0，大于 0 就拒绝这次压缩，回退到最近的合法边界。这类错误应该在发送前拦住，不该交给服务端发现。

Q3

案例三把自动压缩阈值从 90% 调到 75%，缓存命中率从 78% 掉到 12%，账单涨了三倍。这两件事怎么连起来的？

解析

压缩会重写历史前缀，而 prompt cache 的命中条件是前缀完全相同。阈值调低，压缩更频繁，前缀被更频繁地改写，命中率自然塌。省下的 token 抵不过缓存失效后的重算成本。修复方向不是把阈值调回去，而是让压缩切点对齐稳定边界，减少不必要的前缀变动（见第 20 章）。
