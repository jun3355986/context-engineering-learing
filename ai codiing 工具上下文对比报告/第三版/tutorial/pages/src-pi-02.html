压缩只改投影，不删历史

压缩之后，磁盘上的会话文件一条都没少。模型看到的上下文却短了一大截。这两个事实同时成立，靠的是一个很薄但很关键的中间层：投影（projection）。读懂它，你就理解了 pi 的会话模型，也理解了为什么「恢复会话」不需要重跑压缩。

读之前

这一节的关键名词只有两个：条目（entry）是磁盘上的一行 JSON，消息（message）是发给模型的一条 {role, content}。一条条目可能展开成 0 条、1 条或多条消息——这个「不一定相等」是全部设计的起点。

01 · 功能说明

压缩写进去的是一条「指针」，不是一段「删除」

压缩完成时，pi 向会话文件追加一条 CompactionEntry，字段有 summary、firstKeptEntryId、tokensBefore、details、usage、fromHook，以及一个容易忽略的 systemMessage。已核实它没有删除任何旧条目，也没有改写旧条目，只是把「从这里往前的都可以不看了」这句话写成了一个 id。

「历史变短」发生在读取时，不发生在写入时。写入只做一件事：追加一条带指针的记录。

读取时，buildContextEntries() 沿当前叶子回溯出一条路径，找到最新的压缩条目，然后拼出三段：压缩条目自己（它会展开成摘要消息）、从 firstKeptEntryId 起的保留段、压缩条目之后的新条目。更早的原始条目仍在路径上，但不再进入结果。

这套设计带来三个直接后果。第一，压缩是可逆的：删掉那条压缩条目（或把叶子移到它之前），历史立刻恢复原样。第二，压缩是可重复的：第二次压缩不需要重读原始消息，它读的是上一次的投影，摘要因此是「摘要的摘要」。第三，压缩是便宜的：写入只有一次追加，没有重写整个文件。

// 沿叶子回溯成一条路径，再找路径上「最后一条」压缩
export function buildContextEntries(
    entries: SessionEntry[],
    leafId?: string | null,
    byId?: Map<string, SessionEntry>,
): SessionEntry[] {
    const path = buildSessionPath(entries, leafId, byId);
    let compaction: CompactionEntry | null = null;
 
// 循环不 break，所以拿到的是路径上最新的那条压缩
    for (const entry of path) {
        if (entry.type === "compaction") {
            compaction = entry;
        }
    }
 
    if (!compaction) {
        return path; // 没压过：路径就是上下文
    }
 
    const compactionIdx = path.findIndex((entry) => entry.id === compaction.id);
    if (compactionIdx < 0) {
        return path;
    }
 
// 结果以压缩条目自己开头，它展开成一条摘要消息
    const contextEntries: SessionEntry[] = [compaction];
    let foundFirstKept = false;
    for (let i = 0; i < compactionIdx; i++) {
        const entry = path[i];
        if (entry.id === compaction.firstKeptEntryId) {
            foundFirstKept = true; // 从这条起才保留
        }
        // 系统消息永远跳过：它们会在请求组装时重新生成
        if (foundFirstKept && !(entry.type === "message" && entry.message.role === "system")) {
            contextEntries.push(entry);
        }
    }
    // 压缩之后的条目全部保留，不再筛选
    contextEntries.push(...path.slice(compactionIdx + 1));
    return contextEntries;
}

04 · 逐段解读

四次筛选，一次追加

第 1 段　为什么要先建路径，再找压缩

buildSessionPath() 从 leafId 出发，沿 parentId 一路向根走，最后反转成「旧 → 新」。这一步决定了「当前看到的是哪条分支」。pi 的会话是树，不是线性日志：/tree 换一个叶子，路径就变了，压缩条目也可能不在路径上。

接着的 for 循环没有 break，所以 compaction 最终指向路径上最后一条压缩条目。为什么不用 find 从头找第一条？因为一条分支上可以有多次压缩，只有最新那条的 firstKeptEntryId 才是有效的保留起点；旧压缩的保留段可能已经被新压缩重新摘要过了。

这里还有一个容易读漏的细节：compactionIdx 是从路径里找的，不是从原始 entries 数组里找的。如果同一个会话文件里存在多条分支，某条压缩条目可能只属于另一条分支，它不该影响当前投影。

第 2 段　三段拼接：摘要、保留段、之后的条目

结果数组的第一项是压缩条目自己。它会在 sessionEntryToContextMessages() 里展开成一条摘要消息；如果条目里带了 systemMessage，会展开成「系统消息 + 摘要」两条。已核实这就是为什么压缩后模型还能看到「你是谁、有哪些工具」——系统提示被快照进了压缩条目，而不是靠重新读取配置。

然后是循环：从路径开头走到压缩条目前一条，只有在遇到 firstKeptEntryId 之后才开始 push。注意 foundFirstKept 一旦置真就再也不会变假，所以保留下来的是一段连续的历史，不是「所有 id 大于某个值的条目」。

循环里还有一道过滤：entry.type === "message" && entry.message.role === "system" 的条目即使落在保留段里也会被跳过。原因很实际：系统提示在每次请求前由 _preparePromptAndToolLoadout() 重新生成（下一节详述），历史里的旧系统消息只会造成重复。跳过它们，等于把「系统提示」这件事完全交给组装层。

最后 contextEntries.push(...path.slice(compactionIdx + 1)) 把压缩之后的所有条目原样接上。这一段不再筛选，因为它本来就是「压缩后新产生的历史」，没有被摘要过。

第 3 段　投影：编辑叠加与旧压缩清零

buildSessionProjection() 在 buildContextEntries() 的结果上再做两件事。第一，收集所有 context_edit 条目，按 targetId 建索引；第二，对每条被编辑的条目调用 projectContextEntry()：replacement === null 时返回空数组（整条省略），否则把内容替换成 replacement.content。已核实这就是 pi 唯一的「历史裁剪」机制，只改投影，不改原文。

第二件事更隐蔽：

sourceEntry.type === "compaction" && index > 0 ? [] : projectContextEntry(...)

下标 0 的那条压缩贡献摘要；下标大于 0 的压缩条目贡献空消息。什么情况下会有第二条压缩？当 firstKeptEntryId 指向的那条原始条目，本身落在更早一次压缩的保留段里时，buildContextEntries() 会把它和它后面的旧压缩条目一起保留下来。旧压缩的摘要早已被新摘要覆盖，再展开一次就是重复计算。这一行是「投影必须理解自己的历史」的最小例子。

第 4 段　恢复：为什么不用重跑压缩

open() 只做三件事：解析路径、读会话头（拿 cwd）、构造 SessionManager。它不调用模型，不重建摘要，也不校验摘要是否过期。continueRecent() 更简单：找到最近的一个会话文件，交给同一个构造函数。

真正的「恢复」发生在下一次请求：buildSessionProjection() 现算一遍，把摘要 + 保留段 + 新条目摊平成消息。因为投影是纯函数，同样的条目和叶子必然得到同样的结果，所以恢复不需要额外的检查点文件，也不需要「上次压到哪」的元数据。压缩条目本身就是那个检查点。

代价有两条。第一，摘要质量无法回滚：如果一次压缩把关键约束写丢了，你只能回到压缩条目之前（/tree 换叶子）重来，不能「只重跑摘要」。第二，原文没有检索入口：E1–E5 还在文件里，但模型看不到，也没有工具能按 id 读回来。omp 在实验模式下补了 history://current/full，pi 没有。

第 5 段　走查：十一个条目如何变成五条消息

路径上有十一个条目：E1…E5、C1、E6…E9。其中 C1.firstKeptEntryId = E6，C1 还带了一个 systemMessage；另有一条 context_edit 把 E7 置空。投影结果如下：

E1–E5message否0在 firstKeptEntryId 之前

表注：消息数指 sessionEntryToContextMessages() 展开后的条数；系统消息若为 null 内容会被补成空字符串，不会报错。

把表里的数字加起来：0 + 2 + 1 + 0 + 1 + 1 = 5 条消息，而路径上有 11 个条目。这就是「条目数不等于消息数」的最直观例子。会话文件里一行都没少，模型只看到 5 条。

如果 E7 的编辑是 replacement: {content: "…"} 而不是 null，它会变成 1 条内容被替换的消息。替换只对 user / assistant / toolResult / custom 生效；system 消息即使被编辑也原样返回。已核实这是一个容易忽略的边界：编辑系统消息不会生效。

再看系统消息为什么是 2 条。压缩时 appendCompaction() 调 getCurrentSystemMessage(this.buildSessionProjection().messages)，把当时重放出的完整系统提示存进 CompactionEntry.systemMessage。已核实恢复时它和摘要一起展开，所以模型看到的开头是「系统提示 + 摘要」，而不是「只有摘要」。这也是为什么 buildContextEntries() 要跳过保留段里的旧系统消息：新的那份已经在压缩条目里了。

最后一个细节：如果系统的 content 是 null（旧版本或手改文件），sessionEntryToContextMessages() 会补成空数组/空字符串再返回。已核实这让投影对坏数据有韧性，但也意味着「空内容」与「不存在」在投影层看起来一样——排障时要回去看原始 JSON。

第 6 段　删掉压缩条目会发生什么

因为压缩只追加、不删除，所以「撤销一次压缩」在数据上是可行的：把那条 CompactionEntry 从会话文件里去掉（或把叶子移到它之前），下一次投影就会回到压缩前的完整历史。

但有三件事会跟着变。第一，上下文突然变大：原本被摘要掉的几万 token 全部回来，下一次请求可能直接超窗。第二，后续压缩的 firstKeptEntryId 可能失效：如果它指向的条目在新路径上不存在（例如你把整条分支切走了），buildContextEntries() 的 foundFirstKept 永远是假，保留段为空，只剩摘要。第三，文件清单丢失：那份 details.readFiles 只存在于被删的条目里。

所以「撤销压缩」不是无代价的时光机。pi 没有提供这个命令，只提供 /tree 换叶子——换叶子会重新走一遍投影，效果类似，但保留的是「另一条分支」，不是「压缩前的这一条」。

与 dsh 的 surfaceOp 对比会更清楚：dsh 把「模型可见历史」显式建模成一个 surface，压缩是往 surface 上追加一个 replace 操作；撤销就是再追加一个操作，日志本身不动。已核实pi 的做法更接近「日志 + 纯函数投影」：没有 surface 对象，只有条目与投影规则；撤销靠删条目或换叶子。前者可审计，后者更简单。

这也解释了为什么 pi 的压缩条目要带 systemMessage 快照：撤销时你可能切到一条没有系统消息的分支，摘要 + 旧系统提示的组合会缺失。快照让「压缩后的世界」自包含，代价是每条压缩都多存一份系统提示。

第 7 段　每次请求都重算，代价在哪

buildSessionProjection() 没有缓存。每次请求都从叶子回溯、筛条目、叠加编辑、展开消息。对一条几千条的会话，这是一次 O(n) 遍历；对树状会话，还要先走一遍 buildSessionPath()。

为什么不做缓存？因为失效条件太多：追加条目、切换叶子、追加 context_edit、写压缩、扩展改配置，任何一项都会改变投影。缓存的键要做成「叶子 id + 条目数 + 最新编辑 id + 压缩 id」，维护成本高于重算成本。

代价在超长会话里会显现。假设一条会话有 5 000 个条目，每次请求遍历一遍、给每条展开消息、再估算 token，可能花几十毫秒。对交互式 CLI 可以接受，对高频调用的 SDK 场景就值得优化。

真要优化，正确的切入点不是「缓存整个投影」，而是「增量维护投影」：条目只追加，叶子只在树导航时变；可以缓存「叶子 → 路径」与「路径 → 投影条目」，只在追加时更新尾部。这也是 v2 选择「按 seq 取段」的原因之一——它把「重算」变成了「查询」。

✓要点小结

  • 压缩只追加一条 CompactionEntry，磁盘上一条旧记录都不删。
  • buildContextEntries() 拼三段：压缩条目、firstKeptEntryId 起的保留段、压缩之后的条目。
  • 保留段里的系统消息会被跳过，因为系统提示在请求组装时重新生成。
  • context_edit 与「旧压缩贡献空消息」都只改投影，不改原文。
  • 恢复不重跑压缩：投影是纯函数，压缩条目自己就是检查点。

05 · 与其他 agent 的差异

四种「历史变短」的实现，差别在谁记住边界

「压缩后模型只看到一部分」是所有 agent 的共同结果，但边界的记法完全不同：pi 记一个 id，opencode v1 记一个 id 然后重排数组，opencode v2 记一个 seq 然后取连续段，omp 在 pi 的骨架上加了 /clear 边界。

三个对照值得记住：

一是id 与序号的差别。pi 用 id，因为它的条目是树，id 在分叉后仍然唯一；v1 也用 id，但它必须在数组里找这个 id 然后重排；v2 用单调递增的 seq，可以直接写 SQL 的 >=。前者灵活，后者快。

二是边界能否失效。pi 的边界一旦写下就不会失效；omp 的 /clear 可以写在压缩之后，让摘要和保留段一起作废。这不是「更好的设计」，而是「多一种用户动作」的代价：边界从一条变成两条，读取逻辑必须判断谁更晚。

三是投影的纯洁性。pi 的投影是纯函数，压缩条目 + 叶子决定一切；v1 的 filterCompacted 会在读取时改变数组顺序，所以「数组下标」不再等于「时间顺序」，任何按下标推断时间的代码都会出错。源码注释专门写了这句话。v2 用 seq 排序，把顺序重新变成可信的。

firstKeptEntryId 指向一条 system 消息时会发生什么？指向一条已被 context_edit 省略的条目时呢？

提示（不给答案）

第一种情况：foundFirstKept 会置真，但那条系统消息本身被 if 挡掉，所以保留段从它的下一条开始。结果不是空，而是「少一条」。

第二种情况：buildContextEntries 不关心编辑，它照样从那条开始保留；到了投影阶段，那条被置空，但后面的条目还在。所以「保留起点不可见」不会让保留段整体消失。

Q3

如果产品要求「压缩后仍能按 id 读回任意原文」，在 pi 的架构里最小改动是什么？为什么不能只加一个工具？

提示（不给答案）

原文一直在文件里，缺的是「寻址」和「权限」。先想 SessionManager 能不能按 id 查条目，再想工具拿到 id 后要不要校验它属于当前分支。

还要处理一个语义问题：如果读回的原文包含已被 context_edit 省略的内容，工具输出会不会把「本该看不见」的信息又带回上下文？omp 的做法是把它放在实验开关后面，并且只在压缩摘要里给一个 history:// 指针。
