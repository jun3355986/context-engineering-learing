压缩后重附清单

压缩把几万 token 的历史换成一段摘要。但摘要不会记得你正在改哪几个文件、正在用哪个技能、plan 文件里写了什么。Claude Code 的解法不是「让摘要更详细」，而是压缩完按一张固定清单，把文件、技能、plan、delta、钩子输出重新附上。这一节读这张清单。源码 v2.1.88

01 · 功能说明

压缩不是「恢复历史」，是「重新派生附件」

compactConversation() 在拿到摘要之后，并不试图把旧消息搬回来。它做的是：先把「当前文件状态」快照下来，清空读文件缓存，然后按一张固定清单重新生成附件——最近读过的文件、plan 文件、plan 模式指令、本会话调用过的技能、三类 delta 的全量重播、SessionStart 钩子的输出。最后把边界标记和摘要消息放在这些附件之前。源码 v2.1.88

摘要是「过去发生了什么」，附件是「现在继续工作还需要什么」。两者职责不同，所以分开生成。

这个区分很重要。如果让摘要负责记住文件内容，模型拿到的会是「用户改过 auth.ts」这种概括，而不是文件当前的真实内容；如果让附件负责记住历史，又会把几万 token 的旧消息搬回来，压缩就白做了。Claude Code 的选择是：历史交给摘要，工作现场交给附件。推断

整条链路可以分成六步：触发压缩 → 发摘要请求 → 清缓存并生成附件 → 拼边界与摘要 → 写回历史 → 下一轮请求。本节讲第 3 到第 4 步；触发与摘要请求在第 15 章，这里只交代必要的上下文。源码 v2.1.88

先给一个直觉上的量级：文件附件最多 5 个、每个最多 5 000 token、总预算 50 000；技能附件每个最多 5 000 token、总预算 25 000。两项加起来最多 75 000 token。压缩本来是为了腾空间，却又立刻塞回最多 75 000，这看起来矛盾，但注释给出了理由：这些是「继续工作必需的现场」，不是「历史」；没有它们，模型会重复读文件、重复加载技能，反而更贵。源码 v2.1.88

还有一个容易被忽略的前提：摘要请求本身是独立请求，发出去之前会剥掉图片与文档，只留文本标记（stripImagesFromMessages）。原因是摘要不需要图片，而图片很容易让压缩请求自己触发 prompt-too-long。也就是说，压缩链路里有两套上下文：一套是「给摘要模型看的」，一套是「压缩后给主模型看的」；前者尽量小，后者尽量全。两者的预算与内容都不一样。源码 v2.1.88

04 · 逐段解读

清单上的六类东西，按什么顺序回来

第 1 段　顺序：边界最前，摘要第二，附件在后

buildPostCompactMessages() 的顺序是：boundaryMarker → summaryMessages → messagesToKeep → attachments → hookResults。所有压缩路径共用这个函数，保证「不管自动还是手动、不管有没有保留段，顺序一致」。源码 v2.1.88

为什么边界必须在最前？因为它是「压缩发生在这里」的锚点，后续的历史读取、回退、诊断都靠它定位。为什么摘要第二？因为摘要描述的是「边界之前的历史」，紧贴边界才不会被误读成一条普通用户消息。为什么附件在摘要之后？因为附件是「当前工作现场」，属于「压缩之后」的上下文；放在摘要之前，会让模型以为它们也是被摘要的历史。推断

messagesToKeep 是部分压缩（partial compact）或 reactive compact 保留的消息段，可能为空。它在摘要之后、附件之前，语义是「摘要没覆盖到、但需要保留的近期消息」。钩子输出最后，因为它是外部系统对「压缩完成」这件事的响应，适合放在最尾部。源码 v2.1.88

第 2 段　先清再附：为什么要清 readFileState

代码在生成附件之前做了三件事：把 context.readFileState 拷成 preCompactReadFileState；清空 readFileState；清空 loadedNestedMemoryPaths。然后用那份快照去生成文件附件。源码 v2.1.88

顺序不能反。如果先清空再拷贝，快照就是空的，附件生成不出来；如果先拷贝、生成完再清空，生成过程中可能又把文件重新写进状态，清不干净。先拷贝、立刻清空、再用快照生成，保证「附件只反映压缩前的现场」，「压缩后的读文件状态从零开始」。推断

为什么要清空 readFileState？它记录「这个文件已经读过、内容是什么」，用于避免重复读、支持编辑前校验。压缩之后，历史里的「读过」记录已经不存在了，如果状态还留着，下一次 Read 可能被判定为「已读」而跳过，模型就看不到内容。清空是让状态和历史对齐。推断

但 sentSkillNames 故意不重置。注释解释：重新注入整份 skill_listing（约 4K token）是纯粹的缓存写入，收益很小；模型仍然有 SkillTool，已用技能的正文由 invoked_skills 附件保住。也就是说，技能列表不重发，技能正文单独重附。源码 v2.1.88

这里体现了一个原则：压缩后要恢复的是「能力」，不是「能力的目录」。技能列表（有哪些技能可用）是目录，模型不需要在每一轮都看到完整目录；技能正文（某个技能怎么用）是能力，正在用的技能必须能看到。文件也一样：目录树不需要重附，正在改的文件正文需要。推断

这个原则也解释了为什么文件重附有「数量上限」而技能有「总量上限」：文件是并列的现场，5 个足够覆盖当前工作集；技能是分层的说明，单个技能可能很长，需要先截单份再控总量。两种预算形状不同，但目的相同：在「够用」与「不撑爆」之间取一个可解释的边界。推断

再看一个细节：文件附件的预算是「整条附件消息」的估算，不是文件正文字数。路径、JSON 包装、元数据都算在内。这意味着一个 4 900 token 的文件，加上包装可能就超过 5 000，被截到更短；而一个 4 500 token 的文件可能刚好通过。预算越接近上限，包装开销越不可忽略。推断

技能附件也一样：truncateToTokens() 先按 token 截正文，roughTokenCountEstimation() 再估算整条消息。两道处理的目的不同：前者保证单个技能不超限，后者保证总量不超限。截断与预算分离，是这类「先裁剪、再装箱」逻辑的常见结构。源码 v2.1.88

这个结构也解释了为什么「单文件 5k + 总 50k」看起来浪费：真正的约束是「最多 5 个文件」，总预算只是兜底。如果未来把文件数上限调到 10，总预算就会开始起作用；现在它更像一个安全阀，而不是日常约束。推断

第 3 段　文件：5 个、每个 5k、总共 50k

createPostCompactFileAttachments() 的输入是那份快照。它先收集已经保留在 preservedMessages 里的文件路径，避免重复；再按 shouldExcludeFromPostCompactRestore() 排除特定路径；然后按 timestamp 倒序，取前 maxFiles 个。源码 v2.1.88

每个文件用 generateFileAttachment() 生成，限制 maxTokens: POST_COMPACT_MAX_TOKENS_PER_FILE（5 000）。生成后用 roughTokenCountEstimation() 估算整个附件消息的 token，累加到 usedTokens；如果加上这一份会超过 50 000，就整份丢弃（return false），而不是截断到剩余额度。源码 v2.1.88

为什么整份丢弃而不是截断？因为文件附件的目的，是让模型看到「当前文件的真实内容」。截断到剩几百 token，只留下文件头，既不能编辑也不能理解，反而占了一个附件位。丢弃至少让模型知道「这个文件没有被恢复」，可以选择重新读。推断

preservedMessages 这个参数也值得注意。它只在部分压缩（partial compact）时非空，用来告诉文件附件「这些文件已经由保留段覆盖了，不要再附一遍」。没有它，同一个文件会在保留段和附件里各出现一次，浪费预算，还可能让模型看到两个版本的同一文件。去重是压缩附件的基本要求，不只是省 token，更是避免歧义。推断

5 个、5k、50k 三个数字的关系是：5 × 5 000 = 25 000，理论上总预算有一倍余量。50 000 真正的作用，是给附件消息的 JSON 包装、路径、元数据，以及未来调整单文件上限留出空间；估算的是整条消息而不是纯正文，所以实际占用会高于 25 000，但通常仍到不了 50 000。推断

第 4 段　plan 与技能：行为约束也属于现场

plan 附件有两个：createPlanAttachmentIfNeeded() 附上 plan 文件的正文，createPlanModeAttachmentIfNeeded() 附上 plan 模式的行为指令。前者回答「计划是什么」，后者回答「现在还在 plan 模式，不要直接改代码」。只附正文不附模式，模型可能把计划当成已批准，直接开始执行。源码 v2.1.88

技能附件只包含「本会话调用过、且属于当前 agent」的技能。它按 invokedAt 倒序，每个技能先截到 5 000 token，再累加总预算 25 000；超出预算的技能整份丢弃，而不是继续截断。注释解释：技能文件通常「开头的安装/使用说明最重要」，所以单技能截断保留头部，比整份丢掉好；但总预算满了之后，再截断后面的技能只会得到无用的碎片，不如丢掉。源码 v2.1.88

这里也能看出「最近优先」的一致策略：文件按时间倒序，技能按调用时间倒序。压缩后最可能继续用的，是最近读的文件、最近调用的技能；更早的现场，交给摘要概括。推断

第 5 段　delta 重播：空历史 = 全量

三类 delta 都传了空数组 [] 作为 messages。上一节讲过，delta 函数会从历史里的旧 delta 重建「已公告集合」；历史为空，集合就是空，当前所有条目都会被算成「新增」，于是输出全量。源码 v2.1.88

这是一个很巧的复用：同一个函数，正常轮次做增量，压缩后做全量，不需要两套代码。代价是「全量」的语义依赖「空历史」这个约定；如果某天有人传了非空历史，重播就会变成增量，压缩后的第一轮可能缺少声明。所以调用点专门写了 callSite: 'compact_full'，并在注释里说明「compaction ate prior delta attachments」。源码 v2.1.88

三类 delta 分别是：延迟工具（deferred_tools_delta）、agent 列表（agent_listing_delta）、MCP 指令（mcp_instructions_delta）。它们共同的特点是「之前以增量形式存在于历史里，压缩会把它们删掉」。不重播，模型就不知道哪些工具已加载、哪些 agent 可用、哪些 MCP 指令生效。源码 v2.1.88

为什么不在压缩请求里让摘要顺便记住这些？因为摘要的职责是「概括对话」，不是「保存状态」。工具是否加载、agent 是否可用，是布尔/列表状态，不是叙事；让模型用自然语言复述这些状态，既容易漏，也浪费摘要预算。用结构化的 delta 重播，准确且可验证。推断

第 6 段　边界元数据：为什么要带已发现工具

边界标记除了 trigger 与 preTokens，还带一个 preCompactDiscoveredTools：压缩前从历史里提取的、已经加载过的延迟工具名。原因是摘要不会保留 tool_reference 块，而压缩后的 schema 过滤需要知道「哪些延迟工具已经加载过」，否则会把它们的完整定义重新发一遍，或者干脆不发。源码 v2.1.88

这是一个「状态不能只存在消息里」的例子。延迟工具的「已加载」状态，平时由消息里的 tool_reference 承载；压缩把消息换掉，状态就丢了。边界标记是另一个载体，专门在压缩这个断点上保存它。类似的还有 readFileState、sentSkillNames、delta 的已公告集合——它们都是「消息之外的状态」，压缩时必须逐个处理。推断

第 7 段　代价：压缩完可能立刻再压

源码在估算压缩后上下文时，专门加了一句注释：下一轮的 shouldAutoCompact 看到的不只是这批附件，还要加上约 20–40K 的系统提示、工具与 userContext。也就是说，附件预算 75K 只是「消息层」的增量，真实上下文还要再加上固定开销。源码 v2.1.88

如果压缩前接近窗口上限，压缩后摘要 + 75K 附件 + 20–40K 固定开销，很可能又回到阈值附近。源码用 willRetriggerNextTurn 这个指标显式记录这种情况：当压缩后估算值仍然大于等于自动压缩阈值时，标记为「下一轮还会触发」。这是「重附太多」的必然结果。源码 v2.1.88

取舍很清楚：少附一点，可能失去工作现场，模型要重新读文件、重新加载技能，多花几轮；多附一点，可能立刻再压一次，陷入「压缩—重附—再压缩」的循环。Claude Code 用预算上限（5 个文件、25K 技能）来限制最坏情况，但没有保证「一定不再触发」；它把这个风险暴露成指标，让上层决定要不要调阈值。推断

实际调参时，可以把「压缩后估算」拆成三项：摘要长度、附件长度、固定开销。前两项可控，第三项基本固定。如果压缩后仍然接近阈值，优先减附件，而不是把摘要压得更短；摘要太短会丢约束，附件太多只是多占空间。源码的 willRetriggerNextTurn 指标，就是给这个判断用的。推断

✓要点小结

  • 压缩后重附六类：文件、plan、plan 模式、技能、三类 delta、SessionStart 钩子。
  • 顺序固定：边界 → 摘要 → 保留段 → 附件 → 钩子。
  • 先快照 readFileState 再清空；sentSkillNames 故意不清。
  • 文件 5 个 / 单文件 5k / 总 50k；技能单 5k / 总 25k，超预算整份丢弃。
  • delta 传空历史得到全量重播；边界额外保存已发现的延迟工具。

05 · 与其他 agent 的差异

压缩后留什么：消息、文件、还是摘要里的清单

五家 agent 都做压缩，但「压缩后还记得什么」差别很大。Claude Code 用独立附件重附现场；pi 与 omp 把文件清单写进摘要；Grok 重新注入规则与最后请求；dsh 只保留摘要与尾部消息。推断

第一个对照是「文件内容是重附还是概述」。Claude Code 重附正文，模型可以直接编辑；pi、omp 只在摘要里列文件名，模型需要重新读；Grok 与 dsh 不重附。重附正文的好处是「继续工作不用重新读」，坏处是「可能立刻再次触发压缩」。这是「上下文预算」与「工具调用轮次」之间的直接交换。推断

第二个对照是「状态放在消息里还是消息外」。Claude Code 的附件是独立消息，delta 是独立消息，边界元数据是边界消息的字段；pi 把文件清单塞进摘要文本；dsh 把状态放在 surface 事件里。消息外状态（边界字段、readFileState）更省 token，但恢复时需要额外的重建逻辑；消息内状态更自解释，但占上下文。推断

第三个对照是「压缩后的第一轮是否完整」。Claude Code 显式重播 delta、重附技能与文件，目标是「第一轮就能继续干活」；pi 与 dsh 依赖「保留段 + 摘要」，第一轮可能需要重新读文件；Grok 重新注入规则与最后请求，保证「约束与目标」不丢，但文件内容仍要重读。三种目标对应三种成本：Claude Code 付 token，pi/dsh 付工具轮次，Grok 付规则重发的 token。推断

第四个对照是「压缩后的状态怎么校验」。Claude Code 的边界消息带 preCompactDiscoveredTools、摘要消息带 isCompactSummary、附件带类型，恢复时可以逐项检查「该有的有没有」；pi 的 CompactionEntry 带 firstKeptEntryId 与文件清单，也能校验；Grok 用 7 段装配顺序，顺序本身就是校验；dsh 用 surface 的 replace 区间，可以用 seq 检查连续性。没有校验的系统，压缩后只能靠「模型有没有抱怨」来判断，问题会延迟暴露。推断

06 · 思考题

三道题，从清单到预算

Q1

压缩前读过 8 个文件，每个 6 000 token。压缩后会重附几个？每个多大？总 token 大约多少？如果每个文件是 12 000 token，结论会变吗？

提示（不给答案）

先按时间倒序取前 5 个，所以最多 5 个。每个用 maxTokens: 5_000 生成，6 000 token 的文件会被截到 5 000。

5 × 5 000 = 25 000，低于 50 000 总预算，全部保留。如果是 12 000 token，仍然先截到 5 000，所以结论一样；总预算只有在「附件消息包装后超过 50k」时才会开始丢弃，通常 5 个 5k 的文件还到不了。

再注意顺序：文件是按「最近读/写时间」倒序取的，所以如果 8 个文件里最近读的 5 个包含大文件，它们会挤掉更早的小文件。不是「按大小取」，也不是「按重要性取」。

Q2

为什么 delta 重播要传空数组，而不是传压缩后的消息数组？如果传了压缩后的数组，会发生什么？

提示（不给答案）

delta 函数从历史里的旧 delta 重建「已公告集合」。压缩后的数组里已经没有旧 delta（它们被摘要替换了），所以传空数组和传压缩后数组，结果可能一样——都是空集合。

但语义不同：空数组明确表达「与无比较，输出全量」；传压缩后数组则依赖「压缩一定删掉了所有 delta」这个假设。如果未来某种部分压缩保留了 delta，传数组就会变成增量，第一轮可能漏声明。显式空数组是更稳的契约。

还有一个实际差别：传空数组不依赖消息数组的构造顺序。压缩后的消息数组可能包含边界、摘要、附件、钩子，构造时机不同；空数组是常量，任何时候都不会传错。

Q3

你的会话每次压缩后都立刻再次触发压缩。请从「附件预算、摘要长度、固定开销」三个方向各给一个诊断问题，并说出最可能的元凶。

提示（不给答案）

附件预算：文件与技能是否经常顶到 50k / 25k？如果每次都是 5 个满额文件 + 多个满额技能，重附本身就占了大头。

摘要长度：摘要是否包含大量原文摘录？摘要消息也是上下文的一部分，越长越容易回到阈值。固定开销：系统提示 + 工具 + userContext 约 20–40K，这部分不随压缩变小；如果窗口本身较小，压缩后的下限可能已经接近阈值。

最可能的元凶通常是「重附预算 + 固定开销」之和超过了「压缩腾出的空间」。先减附件数量或单文件上限，再考虑调高阈值；只调阈值会把问题推迟一轮，不解决循环。

还有一个检查项：压缩是否在同一轮里反复发生？如果 willRetriggerNextTurn 一直是真，说明压缩后的下限已经高于阈值，再压也不会更小。此时应该降低附件预算，或者换一个更大的窗口，而不是继续调压缩阈值。
