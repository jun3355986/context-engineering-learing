子代理隔离：把一场搜索关在另一个窗口里

子代理不是“更聪明的工具”，它是一次上下文预算的转移：把几十轮搜索、试错和工具输出留在一个你看不见的窗口里，只把结论交回来。设计一次委派，真正要定的是四件事：给它什么上下文、什么工具、什么返回格式，以及允许多深、多宽。

  • 约 18 分钟
  • 1 个交互
  • L2 → L3

读完你能做到

  1. 画出一次委派中父会话与子会话各自的 token 增量，并指出父会话只多了哪两段。
  2. 给定任务，选出合适的只读或计划子代理，并说出裁剪掉的工具与上下文各自省了什么、丢了什么。
  3. 在结构化返回与自由文本之间做选择，并解释深度、并发与 worktree 三个上限的代价。

01 · 先看清这笔转移

“它找了四十个文件，最后只说了三行”

下午三点，你问 Agent：“导出模块为什么有循环依赖？”它开始读文件。先读入口，再读被引用的工具函数，再读测试，再 grep 一遍调用方。四十分钟后，它给出三行结论：环在 index.ts 和 legacy.ts 之间，把后者改成 type-only import 就行。

结论是对的。但你的主会话里多了 38 条工具结果、约 12 万 token 的文件内容。接下来你还要在这个会话里改代码、跑测试、写说明——而那 12 万 token 已经挤在窗口里，压缩会丢掉细节，不压缩又装不下下一轮。你为一个只需要三行答案的问题，付了一整段上下文的租金。

子代理解决的不是“模型不够聪明”，而是“过程太占地方”。

它把一次任务搬到一个独立的上下文窗口里执行：子会话有自己的历史、自己的 token 计数、自己的工具池。父会话不再看见中间的每一次 read 和 grep，只看见两段：派发时的任务描述，和结束时的返回。中间那几十段输出，物理上仍然存在，只是存在另一个会话的日志里。

这笔转移有三条容易忽略的代价。第一，父会话失去了过程：它不知道子代理试过什么、排除过什么，只能相信返回。第二，子会话失去了父的隐性知识：你半小时前说过的“别动 public API”、你读过的那份迁移说明，子代理默认都看不见。第三，返回本身也会膨胀：如果子代理把整个分析过程写成自由文本，父会话省下的空间又会被还回去一部分。

所以“用子代理”不是一个开关，而是一组设计决定。本章按四组决定展开：上下文（给什么）、工具（能做什么）、返回（交回什么）、上限（能开多少）。每组的取舍，都会在后面的对比表和演示里出现。

先分清三种“多开”

子代理是独立上下文 + 只回传结果；并行工具调用是同一个上下文里同时发多个调用，结果仍然全部进父历史；worktree 是文件系统隔离，解决的是“两个代理同时改同一棵树”，不是上下文问题。三者可以组合，但不能互相替代。

02 · Codex 主线

把“独立”做在会话对象上

Codex 的子代理实现在本快照里是一组多代理工具：spawn_agent、send_message、followup_task、wait_agent。它没有把“子代理”做成一个特殊的提示词模板，而是做成另一个会话对象：自己的 Config、自己的历史、自己的 token 计数、自己的 rollout。提交固定为 76ed3b4。

2.1 创建：继承指令，不继承历史

子会话的 Config 在 child_config.rs 里构造：它继承父会话的 base_instructions 文本与来源信息，再把 subagent_developer_instructions 叠加到 developer_instructions 上。child_config.rs#L55-L160 已核实 继承的是“怎么做事”的说明书，不是“已经做了什么”的对话。

为什么只继承指令。指令是稳定的、可复用的：工具怎么用、输出什么风格、哪些操作要谨慎。历史则是本次委派要隔离的对象：如果子代理继承父的全部历史，它也会继承那 12 万 token 的文件内容，隔离就失去意义。代价是子代理不知道父已经排除了哪些方案，可能把一条死路再走一遍；父只能在任务描述里补一句“已经试过 X，不要再试”。

这一点和 Claude Code 的默认值一致，但开关不同：Claude Code 默认 contextMessages = []，只有显式传 forkContextMessages 才克隆父对话；Codex 则把“继承什么”拆成指令与历史两层，历史默认不继承。runAgent.ts#L248-L330 源码 v2.1.88

2.2 通信：完成消息是“输入项”，不是“合并上下文”

父子之间走的是代理间消息（InterAgentCommunication）。子代理结束时，它的完成消息作为一条输入项回到父会话，而不是把子会话的全部上下文并回父会话。spawn.rs#L37 multi_agents_spec.rs#L570-L610 已核实 恢复会话时，这条消息也会被回放，所以“子代理说过什么”在日志里是可追溯的。rollout_reconstruction.rs#L512-L515 已核实

父会话还能用 send_message 追加指令、用 followup_task 让子代理继续、用 wait_agent 等结果。wait.rs#L24 已核实 这条通道是“消息”，不是“共享内存”：子代理看不到父会话刚改的文件，父也看不到子代理的中间推理，除非双方把它写进消息。

为什么用消息而不是共享上下文。共享上下文会让隔离失效，还会让并发写入变成竞态：两个子代理同时改同一段历史，谁赢？消息通道把并发收敛成“收件箱”，每条消息都有明确的发送者与顺序。代价是多一次往返：父想问“你为什么排除方案 B”，必须再发一条消息，子代理可能已经结束，只能重启或读日志。

2.3 工具池：Codex 有机制，但把策略外置

Codex 的形态和 Claude Code、Grok Build 不同：它没有内置的 Explore / Plan 只读代理类型。子会话的 Config 与指令由父会话构造，角色约束由调用方通过 subagent_developer_instructions 写进去；工具池本身由配置决定，本次没有展开“是否裁剪写工具”这一层。也就是说，Codex 提供的是“独立会话 + 消息通道 + 指令叠加”这套机制，至于“只读”“只搜索”“不许跑测试”，要由发起方自己定义。

这种设计的好处是通用：同一个入口可以派“查资料”“写测试”“审 diff”“跑迁移”任何角色，不需要为每种角色维护一个内置模板。代价是约束靠提示词，不靠工具池：如果指令写得含糊，子代理仍然可能调用写工具。真正硬的隔离要在权限层做，而不是在提示词里做。

Claude Code 则把两类常用角色内置了：Explore 与 Plan 默认不注入 CLAUDE.md，也不注入 gitStatus，只读工具池排除写类工具。runAgent.ts#L370-L410 exploreAgent.ts#L15-L60 源码 v2.1.88 这是“角色内置”和“角色外置”的分野，没有绝对优劣，取决于你更怕“模板不够用”还是更怕“约束不够硬”。

2.4 并行与 worktree：能力在环境层，不在 core

本次只核对了 child_config.rs、spawn.rs 与多代理工具目录，没有在 core 里找到 worktree 级文件隔离；相关能力如果在运行环境或应用层，本快照没有给出实现1。这和 Grok Build 明确提供 isolation: worktree、Claude Code 的 isolation: "worktree" 形成对照：Codex 的 core 先把“上下文隔离”做扎实，文件隔离留给外层。

为什么文件隔离重要：两个子代理同时改同一个仓库，哪怕上下文完全独立，也会在磁盘上互相覆盖。上下文隔离只保证“模型看不到对方的中间输出”，不保证“文件不会被对方改坏”。如果任务涉及写文件，要么串行，要么给每个子代理一个 worktree，要么让它们只产出 patch、由父统一应用。

2.5 深度与并发：没有统一常量，不等于没有上限

本快照的 core 里没有找到统一的并发上限常量2。深度也不是一个写死的数字：它由调用方与上层调度决定。对比其他工具，上限通常是显式的：Grok Build 的 MAX_SUBAGENT_DEPTH = 1，opencode v1/v2 默认 1，oh-my-pi 默认 2，DeepSeek Harness 的 maxDepth 默认 1、0 表示禁止委派。

为什么多数 agent 把深度压到 1。每多一层，父会话就多一层“信任传递”：祖父只能看到父的返回，父只能看到子的返回，错误会被逐层转述。深度 1 让“谁说的”始终清楚，也让成本可预测：一次委派最多一个子会话。代价是复杂任务无法自然分解——一个“查清三个模块”的任务，只能由一个子代理顺序做，或者由父并发派三个。并发上限则是另一把闸：它防的不是递归爆炸，而是同时打满 API、磁盘和 CPU。上限越高，调度越复杂，结果合并也越难。

✓要点小结

  • 子代理的核心是独立上下文：继承指令，不继承父的历史；完成消息作为一条输入项回到父会话。
  • Codex 提供通用机制，把“只读/计划”这类角色约束外置到 subagent_developer_instructions，不内置角色模板。
  • 上下文隔离不解决文件冲突；worktree 是另一层能力，Codex 的 core 未见实现。
  • 深度与并发是两把不同的闸：一个防信任链过长，一个防资源打满。
  • 隔离的代价是父失去过程、子失去隐性知识、返回可能重新膨胀。

04 · 七个编码智能体

同一个“派出去”，七种边界

下面七个 agent 各有一个弹窗。可以按“子会话从哪来”分成三派：全新上下文（Claude Code、opencode v1/v2、oh-my-pi、Grok Build 的默认）、可选继承（Claude Code 的 forkContextMessages、DeepSeek Harness 的 fork provider）、没有这个能力（pi）。分野不在“会不会派”，而在“派出去之后，父还能控制多少”。弹窗里的“设计意图”是作者根据源码结构与参数命名做的分析，不是工具作者的自述4。

pi 为什么不做。pi 的 README 写得很直白：“Pi ships with powerful defaults but skips features like sub-agents and plan mode.”README.md#L19 已核实 在 packages/coding-agent/src 里检索 subagent、sub-agent、subAgent 均无命中。这不是“还没做”，而是一个明确的产品选择：pi 把默认面压到最小，把子代理、计划模式这类“多一层调度”的能力留给扩展。好处是核心可预测、上下文只有一条链路；代价是复杂任务只能在单会话里做，或者由用户自己写扩展。DeepSeek Harness 的子代理结论则整节标【推断】，因为它来自包 README 而不是逐行运行时代码3。

06 · 设计取舍

为什么“派出去”有五种不同做法

下面五组取舍，是这张表背后真正的分歧。每组都给出“选 A 的人在想什么”“选 B 的人在想什么”，以及一句代价。没有正确答案，只有和任务形状匹配的答案。

取舍一：空上下文，还是 fork 父对话

空上下文派（Claude Code 默认、opencode v1/v2、oh-my-pi、Grok Build）让子会话从零开始，只拿到任务描述。父的 12 万 token 历史一条都不带，隔离收益最大。fork 派（Claude Code 的 forkContextMessages、DeepSeek Harness 的 fork provider）克隆父的已完成历史，让子代理知道“前面发生过什么”，适合“接着排查同一个 bug”而不是“去查一个新问题”。

代价：空上下文会让子代理重复父已经排除的方案，任务描述必须写得很具体；fork 会把父的噪声也带过去，隔离收益变小，而且父历史里如果有过期的工具结果，子代理会把它当成事实。

取舍二：自由文本，还是结构化返回

自由文本派（Claude Code、opencode v1/v2、Grok Build 默认）让子代理用自己的话总结，父模型读起来自然，适合“解释原因”“给建议”。结构化派（oh-my-pi 的 outputSchema、Codex 的输入项类型）要求返回带字段，父可以程序化消费、校验、重试；permissive 允许从自由文本里解析兜底，strict 则要求严格符合 schema。

代价：结构化更可控，但 schema 会把“意外的发现”挡在外面——子代理可能看到了一个 schema 没定义的重要信号，却只能丢掉。自由文本更丰富，但父要再读一遍、再解析一遍，返回过长时等于把隔离省下的 token 还回去。opencode 的折中是“XML 信封 + 自由文本”：外层固定，内层自由。

取舍三：只读/计划代理的裁剪，裁到什么程度

深度裁剪派（Claude Code 的 Explore/Plan 不注入 CLAUDE.md 与 gitStatus；Grok Build 的 explore 只给 Read/List/Grep，plan 再加 TodoWrite）把“搜索”这件事压到最小工具集。Claude Code 的源码注释给出节省量级：每周 5–15 Gtok。全能力派（Codex 默认继承工具集、Grok 的 general-purpose）让子代理能读能写能跑测试，适合“实现 + 验证”一体的任务。

代价：裁掉 CLAUDE.md 省钱，但子代理不知道项目约定，给出的建议可能违反规范；裁掉 shell 意味着它不能跑测试验证自己的结论，只能“看起来对”。反过来，全能力子代理可能在你不知情时改了文件，父只看到一句“已完成”。

取舍四：共享工作区，还是 worktree

共享派（Grok Build 默认 isolation: none、opencode v1/v2、oh-my-pi 默认关闭 isolation）让子代理直接在同一个工作区读写，启动快、无需合并，适合只读任务或改动互不相交的并行任务。worktree 派（Grok Build 可选、Claude Code isolation: "worktree"、oh-my-pi 开启后走 worktree/patch）给每个子代理一棵独立的树，写完再合并。

代价：worktree 解决写冲突，但引入合并成本：同一文件两边都改，还是要人来解冲突；依赖安装、构建缓存、生成物都要重建，磁盘和时间都翻倍。共享工作区省掉这些，却可能出现“子代理 A 把子代理 B 刚改的文件覆盖了”，而且父从上下文里看不出来。

取舍五：同步等待，还是异步通知

同步派（opencode v1 默认前台、Codex 的 wait_agent）让父在派发后阻塞，拿到结果再继续，因果顺序清楚。异步派（DeepSeek Harness 立即返回 started subagent <childId>、opencode v2 的 background、Grok Build 默认 run_in_background: true）让父先去干别的，子代理完成后再用通知把结果送回。

代价：异步能把等待时间藏起来，但父要在“结果还没回来”时继续决策，可能基于旧状态行动；多个子代理同时完成时，还要处理顺序与冲突。同步简单，但一个慢子代理会卡住整条主链。深度上限通常和这一点联动：异步 + 深度 1，是最容易推理的组合；异步 + 深度 N，错误会沿着通知链逐层转述。

还有一个横切的取舍：返回要不要再摘要。oh-my-pi 在子代理输出超过 5,000 字符时再做一次摘要，Grok Build 默认不裁剪、把完整输出交回。前者保护父窗口，后者保护信息完整。选哪个，取决于你更怕“父被撑爆”还是更怕“关键细节被二次摘要吃掉”。

07 · 小测验

三道题，检验你是否真的会派

Q1

父会话原本 3,000 token。子代理跑了 7 步、共 40,000 token，返回结构化结果 400 token。父会话最终多少 token？如果把返回改成 3,000 token 的自由文本，隔离收益会怎么变？

解析

最终约 3,400 token（不含任务描述；加上约 150 token 的任务描述是 3,550）。中间 40,000 token 全部留在子会话。改成 3,000 token 自由文本后，父会话约 6,000 token：隔离仍然成立，但“省下多少”从约 92% 降到约 85%。结论：父会话增量只由任务描述与返回决定，与子代理跑多少步无关；返回形态是第二个预算旋钮。可以在演示里切换两种返回形态验证。

Q2

一个只读 Explore 子代理被裁掉了 CLAUDE.md、gitStatus 和写工具。它可能给出什么样的“正确但不可执行”的建议？你会怎么补？

解析

它可能建议“把导出改成默认导出”“直接升级依赖”，而项目规范要求具名导出、依赖升级要走审批；也可能建议改一个它看不见的生成文件。因为它没有写工具，也无法跑测试验证。补法有三条：父在任务描述里带 3–5 条硬约束；把规范文件的关键段落贴进任务；或者把“验证”拆给一个可写的子代理。见取舍三与 Claude Code 弹窗。

Q3

你要并行改 8 个互不相干的包，每个包都要跑测试。选共享工作区还是 worktree？如果 8 个任务改的是同一个入口文件，答案会变吗？

解析

互不相干时共享工作区更划算：启动快、无需合并，测试各自跑各自的包。若都改同一个入口文件，worktree 也救不了你——合并时仍要解冲突，只是把冲突从“运行中互相覆盖”推迟到“合并时显式冲突”。更稳的做法是串行，或让子代理只产出 patch、由父按顺序应用。见取舍四。
