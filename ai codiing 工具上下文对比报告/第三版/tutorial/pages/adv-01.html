取舍：没有最优解，只有代价清单

同一个模型、同一套工具，两个团队可以做出完全相反的选择，而且都能跑通。区别不在谁更先进，而在谁更清楚自己在为什么付费。这一页只讲六组选择的运行方式与代价。

  • 约 24 分钟
  • 7 张图
  • L4

读完你能做到

  1. 对六组取舍，分别说出两种做法怎么跑、省什么、丢什么。
  2. 给定任务长度、工具密度、预算与合规约束，选出一组组合，并写出它的代价。
  3. 识别三种常见的错误组合，判断应该改配置、改流程，还是改代码。

01 · 先把“取舍”与“优劣”分开

两个团队，同一套工具，相反的答案

周一上午，A 团队把压缩阈值调到 70%。他们的任务常常跑一整夜，宁可早一点压，也不愿在凌晨两点看到“上下文溢出”。B 团队把阈值留到 92%。他们每单任务只有二三十轮，压一次就丢一次细节，不如少压。

两家都没错。A 买“确定性”，B 买“保真度”。只问“哪个阈值更好”就问错了。该问：这个任务更怕丢细节，还是更怕跑不完？

取舍不是“好与坏”的选择，是“哪一种代价你现在付得起”的选择。

六组取舍都按四段写：怎么跑；省什么、丢什么；什么场景选哪边；代价一句话。

本页以第 1 级（文字）和第 2 级（图表）为主；第 3 级交互在第 25 章；第 4 级视频只在附录分镜里。

下面这张矩阵把六组选择放到同一张图上。横轴是“每次请求的平均上下文成本”，纵轴是“任务连续性”，也就是模型还能不能接着前面的细节干。位置是示意，不是实测；先判断自己站在哪个象限，再去看对应那一节。

02 · 取舍一

压缩早，还是压缩晚

怎么跑

早压在窗口用到 70%–85% 时就动手。DeepSeek Harness 的默认阈值是 thresholdRatio 0.8；Grok Build 用 85 常量、grok-4.6 目录用 80；Codex 的范围线默认取 min(模型声明上限, 窗口 × 90%)。第 15 章 2.1 这些数字不完全相同，但都在“还留得下一轮工具调用”的位置。

晚压把阈值推到 90%–95%。Codex 的整段硬线是窗口 × 95%；Claude Code 的自动压缩线是“有效窗口减 13k”，200k 窗口、20k 输出上限时约为 167k，也就是 83.5%。第 15 章 2.1 真正的“晚”不是某个固定百分比，而是“尽量拖到任务快结束”。

省什么、丢什么

早压省的是失败概率。压缩请求本身也要装下待压缩的历史。越早压，待压缩的历史越短，压缩请求自己超窗的概率越低；压完之后，剩下的路还长，这一次前缀失效的成本可以被更多轮摊薄。

早压丢的是细节寿命。一段对话本来还能再活十轮，你提前把它换成摘要，后面十轮都只能看摘要。文件里的精确行号、测试输出的具体断言、你当时那句“别动 public API”，都可能提前消失。

晚压省的是摘要次数。每压一次，都要重发一段历史、生成一次摘要、制造一次前缀失效。晚压把次数压到最少，也让最近的工作状态保留得更久。

晚压丢的是退路。压缩请求自己可能先撞墙。Codex 的处理是删掉最旧一条再重试；只剩一条时只能报错。第 15 章 2.5 这时损失的不是钱，是历史。

粗算一下。设摘要请求重发 H 个 token，压缩后第一次请求要重算 P 个 token。压 k 次，账面成本约 k × (H + P)。晚压让 k 变小，却让“压缩请求超窗、被迫删历史”的概率变大。公式只是示意：压缩次数不是免费的，压得晚也不是免费的。

什么场景选哪边

  • 早压：任务很长；工具输出很大；压缩请求曾超窗。
  • 晚压：只剩几轮；最近内容很贵；缓存节省大于多压一次。
  • 不压：只剩一两轮，且窗口装得下。

先估剩余轮数 R：R 小且窗口还有 15% 余量，就不压；R 大，或待压缩历史里有 50k 以上的工具输出，就早压。

代价一句话：早压用细节换确定性，晚压用确定性换细节。

03 · 取舍二

裁剪，还是摘要

怎么跑

裁剪不调用模型。它只改“模型能看到的投影”：把旧工具结果换成占位符，把过期文件读取删掉，把空搜索折叠。原文还在会话日志里，需要时可以按路径重新读回。Claude Code 的 microcompact 有一条时间触发路径，gapThresholdMinutes 默认 60 分钟、keepRecent 默认 5 条，但整条路径默认 disabled；oh-my-pi 保护最近 40k、只有能省下 20k 才动；Grok Build 在超过 50% 窗口时做软裁剪，每次保留头尾各 1,500 字符，10 轮后硬清。第 14 章

摘要调用模型。它把一段历史交给另一个请求，生成一份交接笔记，再用笔记替换原文。摘要可以跨语义压缩：把“读了 20 个文件、跑了 3 次测试”写成一句“已完成依赖梳理，测试仍有两个失败”。代价是原文里的精确字符串、数字和行号通常不再回来。第 15 章

省什么、丢什么

裁剪省 token，不省语义。它最适合“体积大、价值低、可重新获取”的内容：整份 lockfile、一次 80k 的测试日志、已经读过的文件全文。它不改变模型的理解，只让模型暂时看不见细节；需要时可再读一次。

摘要省得更多，但不可逆。它能把 100k 的历史压到 2k，也能把散落在 40 轮里的决策收成一段。代价是“哪一句是原话”消失了。摘要模型可能把“不要改 public API”写成“保持 API 稳定”，意思接近，约束强度不同。

先裁后压是常见的第三条路。DeepSeek Harness 在溢出恢复时先跑 pruner，再压缩；Claude Code 的文档也描述“先清旧工具输出、再摘要”，但源码里这条路径在外部构建默认不生效。第 14 章 先裁后压的好处是：压缩请求的输入更小，超窗概率更低；坏处是裁剪已经丢掉的东西，摘要也救不回来。

什么场景选哪边

  • 裁剪：重复读文件；日志长但只看结论；需要保留原文回读。
  • 摘要：决策散在很多轮；阶段已切换；可以接受“知道结论、不知道原话”。
  • 先裁后压：既有大块输出，又有大量决策；压缩请求经常接近上限。

判断标准：这段内容以后还会被逐字引用吗？ 会，就先裁剪；不会，就摘要。

代价一句话：裁剪省的是体积，摘要省的是体积加语义；前者可逆，后者不可逆。

04 · 取舍三

预加载，还是按需加载

怎么跑

预加载把规则、技能正文、MCP 工具定义一次性放进请求。模型第一轮就能看到全部能力，不需要“先找工具、再调用”。代价是这些 token 每一轮都要付，而且工具表越大，模型越容易在无关工具上分心。

按需加载先给目录，再给正文。Claude Code 的技能列表只放“名称 + 描述 + 何时使用”，每条描述硬截断 250 字符；MCP 工具默认延迟（tst 模式），另有按窗口 10% 触发的 auto 模式。SkillTool/prompt.ts#L20-L50 源码 v2.1.88 Codex 在模型支持 supports_search_tool 时，把 MCP 工具注册为延迟暴露，由 tool_search 拉取；Grok Build 则让 MCP 工具不进 tools，先 search_tool 再 use_tool。第 10 章

省什么、丢什么

预加载省一次往返。模型不用先检索、再读正文，首轮就能行动；工具定义稳定时，它还是缓存友好的，因为前缀不变。它丢的是“注意力预算”：工具越多，模型越可能选错，或者在系统提示里迷路。

按需加载省常驻 token。一个 40 个工具的 MCP 服务器，完整 schema 可能占几万 token；目录只占几百。它丢的是“发现确定性”：模型可能不知道某个能力存在，也可能先花一轮检索。多一次检索，就多一次延迟、多一次失败点。1 目录本身也要维护：描述太短，模型不知道何时用；太长，又回到预加载的体积。

什么场景选哪边

  • 选预加载：工具少于 10 个且稳定；任务短、延迟敏感；模型经常需要在一个回合内连续调用多个工具。
  • 选按需：MCP 服务器多；技能库大；会话很长；工具使用频率低且集中。
  • 选混合：核心工具预加载，长尾工具延迟；规则文件预加载，技能正文按需。多数生产工具最后都会走到这里。

判断标准：一份工具定义在 90% 的轮次里不调用，就延迟；每三轮调用一次，就预加载。

代价一句话：预加载把成本摊到每一轮，按需把成本集中到第一次使用。

05 · 取舍四

子代理，还是单会话

怎么跑

子代理开一份独立上下文。它有自己的系统提示、工具池、文件状态和预算；父会话只把任务描述送进去，子代理只把最终结果送回来。Claude Code 默认 contextMessages = []，也就是全新上下文；只读的 Explore / Plan 代理默认不注入 CLAUDE.md，也不注入 gitStatus。oh-my-pi 的 task 子会话默认深度 2，并要求 schema 校验返回；opencode v1/v2 默认深度 1；Grok Build 默认后台执行，可选 worktree 隔离。第 17 章

单会话把一切留在同一份历史里。模型能看到你前面说过的每一句约束、每一次失败、每一个被否决的方案。没有交接，也没有“子代理不知道上下文”的问题。

省什么、丢什么

子代理省父上下文。120 个文件的搜索结果、7 次工具调用、3 个失败分支，都留在子会话里；父会话只多出“任务描述”和“最终返回”两段。它还能隔离错误：一个子代理跑偏，不会把父会话的推理链带歪。

子代理丢共享语境。它不知道你十分钟前改过的约束，也不知道另一个子代理已经否决了某个方案。它要重新发现项目结构、重读规则、重踩坑；每一次“重新”都是 token 和时间。

单会话省交接。约束、决策、失败原因都在眼前，模型不需要猜。它丢的是预算：上下文线性增长，压缩更早发生。另一个风险是“错误传染”：一次错误推理留在历史里，后续每一轮都可能被它带偏。

什么场景选哪边

  • 子代理：大范围搜索；独立审查；并行验证互斥假设；worktree 隔离。
  • 单会话：修改高度耦合；约束多且分散；需要频繁回看失败。
  • 混合：主会话负责实现，子代理负责查资料、跑验证；父会话只收结论与文件指针。

判断标准：子任务需不需要知道主线的全部约束？ 需要，就别拆；不需要，就拆，并且把“返回什么”写清楚。

代价一句话：隔离买的是注意力，付的是重新发现。

06 · 取舍五

记忆，还是规则

怎么跑

规则是确定性的文件。它按固定路径发现、按固定顺序合并、每次会话都注入。Codex 的 AGENTS.md 从项目根到 cwd 逐级拼接，总量受 project_doc_max_bytes 默认 32 KiB 约束，超出从尾部截断；DeepSeek Harness 的整条基线消息默认上限 64 KiB；Claude Code 的 MEMORY.md 入口限制 200 行 / 25,000 字节。agents_md.rs#L60-L160 已核实

记忆是学习出来的。它由模型或后台管线写入，按项目隔离，按相关性检索，允许不完整、允许过期。Claude Code 有 auto memory 与 session memory；Grok Build 用 /flush 在压缩前抢救、/dream 定期整理，session 记忆按 30 天半衰期衰减；oh-my-pi 有 5 个后端但默认关闭。第 19 章

只留会话是第三条基线：什么都不持久化，只让这一次对话知道。它最干净，也最健忘。

省什么、丢什么

规则省重复发现，付每轮 token。“不要改 public API”“测试命令是 pnpm test:unit”写进规则文件，就不依赖模型记不记得。代价是规则一直在上下文里，占用预算；规则太细会变成没人维护的长文档，规则太粗又挡不住具体错误。

记忆省上下文，付可信度。它只在相关时被检索进来，体积小、适应性强。代价是它可能错，而且错误会跨会话复利：一次错误的“这个项目用 Jest”会被写进记忆，下一次会话一进门就被注入。2

只留会话最省，付重复成本。同类问题第二次出现时，模型要从头再发现一遍。它适合一次性任务，不适合长期项目。

什么场景选哪边

  • 规则：安全边界；public API；测试命令；目录结构。
  • 记忆：风格偏好；常见坑；模块的历史原因。
  • 会话：一次性排查；临时分支；只对今天有效的决定。

判断标准是一句话：这条信息错了，会不会造成不可接受的后果？ 会，就写规则；不会，但跨会话有用，就写记忆；只对这一次有效，就留在会话。

代价一句话：规则买确定性，记忆买适应性，两者都用上下文付费。

07 · 取舍六

服务端压缩，还是本地压缩

怎么跑

服务端压缩把“压什么、怎么压”交给 provider。客户端只发请求，拿回一段替换后的历史，或者一个 provider 自己维护的加密窗口。Codex 的远端 v2 压缩保留消息共享 64k 预算、单条上限 10k、流重试 2 次，并要求响应里的 compaction_count 恰好为 1；opencode v2 在模型元数据声明 compaction.type === "native" 时走原生压缩，拿回加密窗口；oh-my-pi 的默认方法链第一项就是 remote。compact_remote_v2.rs#L87-L91 已核实

本地压缩由客户端自己选候选、写模板、拼摘要、决定重附什么。Codex 本地只把真实用户消息纳入候选，预算 20k；Claude Code 压缩后按固定清单重附最近 5 个文件（每个 5k、总 50k）和本会话用过的技能（每个 5k、总 25k）；pi 保留 20k；DeepSeek Harness 保留窗口的 16%。第 15 章 2.2

省什么、丢什么

服务端省维护。不用自己处理切点、工具配对、超窗重试、模板版本；provider 升级，客户端跟着受益。它丢的是控制权：你看不到候选选择，改不了摘要模板，也很难要求“这三条约束必须逐字保留”。3

本地省控制权。你可以把领域约束写进摘要提示词，可以在压缩后重附文件，可以把摘要写进自己的日志，可以换模型、换 provider。它丢的是维护成本：切点算法、配对校验、失败兜底、模板回归，都要自己写。

混合路线先试服务端，失败再走本地。oh-my-pi 的方法链就是这个结构：remote 不可用就逐级回退。它把“省维护”和“有退路”放在一起，代价是两条链都要测。

什么场景选哪边

  • 服务端：单一 provider；任务通用；没有人力维护压缩链路。
  • 本地：合规或审计；必须保留领域约束；多 provider 可移植。
  • 混合：服务端为主、本地兜底；或反过来。

判断标准：能不能接受“摘要少了哪一句，你看不见”？ 能，服务端更省；不能，本地更稳。

代价一句话：服务端压缩用控制权换维护成本，本地压缩反过来。

08 · 把六个选择拼起来

先定约束，再定顺序

六组取舍会互相抵消：早压加“只留摘要、不重附”，细节丢得更快；子代理加自由文本长返回，父上下文会被“结果”撑爆。策略是一组互相匹配的选择。

下面这个顺序，把“不可协商的约束”放在最前面：

  1. 先写规则：安全、API、测试命令、目录结构。它们不参与压缩，也不该靠记忆。
  2. 再定隔离：任务耦合度高就单会话；需要大范围搜索或独立验证就子代理。
  3. 再定加载：核心工具预加载，长尾工具按需；规则预加载，技能正文按需。
  4. 再定预算：任务长、工具输出大就早压；任务短、最近细节贵就晚压或不压。
  5. 再定减量顺序：先裁剪可重取的旧结果，再摘要不可重取的决策。
  6. 最后定压缩位置：单 provider 先服务端；有合规或多 provider 需求就本地。

三种常见的错误组合

组合一：早压 + 只留摘要 + 不重附。 三件事都在省 token，叠加起来就把细节省没了。症状是模型记得目标，忘了约束。修法不是关掉压缩，而是把约束移进规则文件，并在压缩后做校验。

组合二：晚压 + 大工具输出。 两件事都在把上下文推向极限。压缩请求可能先超窗，工具只能删最旧历史。修法是先裁大块结果，再压缩；或者把阈值提前。

组合三：子代理 + 自由文本长返回。 子代理省下的父上下文，被返回一次性还回去。三个各返回 10k 字，父上下文就多 30k。修法是定 schema 与上限，全文落盘，只回结论与文件指针。

一张代价清单

选完任何一组，问五个问题：一，丢了什么还能重新获取？二，丢了什么不能？三，多花的 token 花在哪一轮？四，失败时有没有退路？五，这个选择在任务变长时会变坏吗？五个问题里有两个答不上来，就说明你选的不是策略，是习惯。

09 · 小结

把“为什么”留在纸面上

✓要点小结

  • 压缩早晚看“剩余轮数”和“压缩请求余量”，不看单一百分比。
  • 裁剪可逆、摘要不可逆；先裁后压能降低超窗概率。
  • 子代理买隔离，付重新发现；返回上限决定它是帮手还是负担。
  • 规则买确定性，记忆买适应性；硬约束不进规则，就会在压缩里裸奔。
  • 服务端压缩省维护，本地压缩省控制权。
