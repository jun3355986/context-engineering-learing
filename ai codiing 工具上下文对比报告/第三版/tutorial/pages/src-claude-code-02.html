只有一个消息级缓存断点

很多教程说「Claude Code 有四个缓存断点」。这句话只对了一半：系统提示最多切成四块，但消息层恰好只有一个 cache_control 标记。源码 v2.1.88这一节读 addCacheBreakpoints，看清「一个标记」如何覆盖整段前缀，以及 fork 为什么要把标记往前挪一位。

01 · 功能说明

两层标记：系统块可以多，消息块只能一个

Claude Code 的缓存标记分两层。系统提示层：splitSysPromptPrefix() 把数组切成最多四块，buildSystemPromptBlocks() 只给 cacheScope 非 null 的块套 cache_control。消息层：addCacheBreakpoints() 在每条请求里只给一条消息加标记，位置是最后一条消息。源码 v2.1.88

「四个断点」的说法混淆了两层：四块是系统提示的文本块上限，不是消息层的标记数。

为什么消息层只需要一个？因为请求是顺序排列的：系统块 → 工具 → 消息。给最后一条消息加标记，等于把「从请求开头到最后一条消息」整段都纳入缓存。前面的系统块、工具定义、历史消息，全都在这段前缀里。再加一个更靠前的标记，不会扩大覆盖范围，只会多保护一个「以后不会从这里继续」的位置。源码 v2.1.88

源码注释给出了更具体的机制：服务端（注释里叫 Mycro）在轮次之间驱逐 KV 页，凡是「在缓存前缀里、但不在 cache_store_int_token_boundaries 里」的位置，都会被释放。如果放了两个标记，倒数第二个位置也被保护，它的局部注意力页会多活一轮，尽管下一次请求根本不会从那里续写。多一个标记，就多一轮无用的 KV 占用。源码 v2.1.88

本节的结论可以压缩成一句话：系统层的块数是「文本切分」问题，消息层的标记数是「KV 页生命周期」问题。两者数字不同，不能互相套用。源码 v2.1.88

为了把后面几节读顺，先补三个背景概念。第一，cache_control 不是「打开缓存」的开关，而是「在这里画一条缓存边界」的标记；服务端会把边界之前的 token 前缀做哈希，命中时复用 KV，未命中时重新计算。第二，缓存写入有成本，通常比普通输入贵；缓存读取有折扣，通常比普通输入便宜。第三，标记的位置决定「写到哪」，不决定「从哪里失效」；失效点由第一个不同的字节决定，可能远在标记之前。源码 v2.1.88

把这三个概念放在一起，就能理解为什么「一个标记」是合理的：它把「写到哪里」固定在请求末尾，覆盖范围最大；至于「从哪里失效」，交给前缀比较，不需要额外的标记来「分段保护」。多标记唯一能改变的是「哪些位置被额外保护」，而这恰好是 Claude Code 不想要的。推断

04 · 逐段解读

一个标记，三种位置

第 1 段　默认：最后一条消息

markerIndex 默认是 messages.length - 1，也就是最后一条消息。无论最后一条是用户还是助手，标记都会加上；区别在于加在哪个内容块上：用户消息加在最后一个块，助手消息加在最后一个「可打点」的块。源码 v2.1.88

为什么是最后一条，而不是第一条或中间？因为缓存是前缀缓存：标记之前的全部内容构成一个可复用的前缀，标记之后的内容不参与。放最后，覆盖范围最大；放中间，后面的消息每轮都要重算。放第一条更糟，只缓存了系统提示与工具，历史全在缓存外。推断

这也意味着「上一轮的标记位置」就是这一轮的缓存读取起点。上一轮在消息 N 打了标记，这一轮请求的前 N 条与上一轮完全一致，服务端可以直接复用；新增的消息 N+1 到 M 在这一轮标记之后，下一轮才会被纳入前缀。缓存是「滞后一轮」生效的。推断

滞后一轮有一个实际后果：如果你在某一轮之后立刻 /clear 或切换模型，上一轮刚写入的尾巴可能永远用不上，白付一次写入成本。反过来，如果你连续多轮保持前缀不变，第一轮写入的成本会被后面每一轮的读取折扣摊薄。缓存的经济性取决于「这段前缀还会被用几次」，而不是「它有多大」。推断

这也解释了一个常见现象：短会话的缓存几乎不省钱，长会话才明显。第一轮没有可复用的前缀，第二轮才第一次命中，第三轮开始摊薄写入成本。如果会话平均只有两三轮，单标记、少断点的策略更划算；如果会话有几十轮，才值得为「多保护几个位置」付出写入成本。断点数量应该跟会话长度匹配，而不是跟请求大小匹配；这也解释了为什么 Claude Code 不追求「每个位置都保护」。推断

把这条规律带回单标记：它假设「会话足够长，尾部标记会被反复复用」，同时假设「中间位置不会被续写」。如果会话很短，这个假设不成立，但也无所谓，因为短会话本来就不靠缓存；如果会话很长，尾部标记的复用次数足够多，单标记的收益最大。它是一个「对长会话友好、对短会话无感」的选择。推断

这也解释了为什么压缩之后要重置缓存基线：压缩把历史换掉，上一轮的标记位置对应的是旧历史，新历史从第一条起就不同，缓存只能从头开始。此时继续沿用旧标记没有意义，不如让下一轮重新建立。推断

第 2 段　fork：为什么是倒数第二条

skipCacheWrite 为真时，markerIndex 变成 messages.length - 2。注释解释：这是「最后一个共享前缀点」，在这里写缓存是一次 no-op merge（条目已存在），fork 不会把自己的尾巴写进 KVCC。源码 v2.1.88

换成直白的话：fork 出来的会话，最后一条消息是 fork 自己新加的，父会话没有。如果把标记放在最后一条，等于要求服务端为「只有 fork 才有的尾巴」写一份新缓存；下次父会话或别的 fork 来读，这份缓存用不上，白占空间。放在倒数第二条，标记落在父子共享的前缀末尾，写入是合并到已有条目，不产生新尾巴。推断

为什么不是倒数第三条或更前？因为倒数第二条已经是「最后一个共享点」；再往前，覆盖范围变小，fork 自己的倒数第二条消息（如果也是新加的）就落在缓存外。这里的选择不是「越前越安全」，而是「刚好覆盖共享前缀」。推断

第 3 段　助手消息：最后一个可打点块

用户消息的处理简单：字符串内容直接套一个文本块；数组内容只给最后一个块套标记。助手消息复杂一些：它可能包含文本、工具调用、thinking、redacted thinking、connector 文本。代码从后往前判断，只有「最后一个块、且不是 thinking/redacted/connector」才套标记。源码 v2.1.88

用户消息为什么也只标最后一个块？因为一条用户消息可能包含多个内容块（文本、图片、文档）。缓存边界只能落在块上，不能落在消息中间；标最后一个块，等于把整条消息都纳入前缀。标第一个块则会把后面的图片、文档排除在缓存外，下一轮同样的图片还要重算。推断

为什么要跳过 thinking？注释没有解释，但从行为推断：thinking 块可能被服务端剥离、可能不参与缓存键、也可能不允许挂 cache_control。把标记挂在它上面，轻则无效，重则请求被拒。跳过它，让标记落到最后一个稳定的内容块上。推断

跳过 connector 文本也是同理：connector 文本可能由客户端动态拼接，字节不稳定。如果标记挂在它上面，下一轮拼接结果稍有不同，缓存就从这里失效。选择「最后一个稳定的块」，是在「覆盖范围」与「字节稳定性」之间取平衡。推断

第 4 段　系统层：两到三个标记，而不是四个

系统层最多四块，但只有 cacheScope 非 null 的块带标记。全局缓存模式下：归属头 null、CLI 前缀 null、静态块 global、动态块 null，实际只有 1 个系统标记。org 模式下：归属头 null、前缀 org、其余 org，实际 2 个。加上消息层 1 个，总数是 2 或 3。源码 v2.1.88

这个数字说明 Claude Code 刻意留了余量，没有把可用的断点槽位用满。留余量的原因，注释写在 buildSystemPromptBlocks() 里：「Do not add any more blocks for caching or you will get a 400」。再加就会超限。源码 v2.1.88

所以「四个断点」的正确说法是：系统提示最多四块，但 Claude Code 实际只打两到三个断点。把「块数」当成「断点数」，会误判它的缓存写入成本。源码 v2.1.88

再细看 splitSysPromptPrefix() 的 global 分支：归属头和 CLI 前缀都被显式设为 cacheScope: null，静态块设 global，动态块设 null。为什么归属头不缓存？因为它含请求级元数据（计费、指纹），每次可能不同，缓存它没有意义。为什么 CLI 前缀不缓存？因为它很短，缓存收益低于额外断点的成本。只有静态块足够大、足够稳定，值得单独占一个断点。推断

org 分支则把前缀与其余都设成 org：没有全局缓存能力时，退而求其次，用组织级缓存保住「同一组织内多个用户共享」的部分。此时静态与动态被合并到「其余」一块，边界不再起作用。也就是说，同一个数组在不同 provider 上会切出不同的块数，缓存行为也跟着变。源码 v2.1.88

第 5 段　TTL：为什么资格要锁存

getCacheControl() 默认返回 { type: 'ephemeral' }，满足条件时加 ttl: '1h'，scope === 'global' 时加 scope。1h 的资格由 should1hCacheTTL() 判断：Bedrock 显式开启、或用户是订阅者且未超限、且在 GrowthBook allowlist 里。源码 v2.1.88

资格判断被「锁存」在 bootstrap state 里：第一次算出来之后，整个会话不再重算。注释解释：如果会话中途 overage 状态翻转，TTL 从 ephemeral 变成 1h（或反过来），cache_control 的字节就变了，服务端缓存键跟着变，整段缓存失效，损失约 20K token。锁存是用「可能稍微不准确」换「字节稳定」。源码 v2.1.88

这也是缓存设计的一般规律：凡是会进入缓存键的字段，都要尽量在会话内稳定。TTL、scope、模型名、beta header，全都属于这一类。它们看起来是「元数据」，实际上和提示词正文一样，改一个字节就会让前缀失效。推断

第 6 段　代价：一个标记的边界

单标记的代价是「粒度粗」。如果一轮里只有最后一条消息变了，前面全部命中；如果倒数第 10 条消息被改写（比如压缩、编辑、重放），标记仍然在最后，但前缀从第 10 条开始就不一致，缓存只能命中前 9 条。标记位置不决定「从哪里失效」，只决定「缓存写到哪」；失效点由第一个不同的字节决定。推断

另一个代价是「fork 尾巴延迟缓存」。fork 的第一轮把标记前移，自己的尾巴不在缓存里；要到第二轮，尾巴变成「倒数第二条」或更早，才可能被纳入。对短命的 fork（只跑一两轮）来说，这意味着它几乎享受不到自己的缓存。推断

但这两个代价都换来了「不浪费 KV 页」。在长会话里，KV 页是稀缺资源；多保护一个不会再续写的位置，会挤掉真正需要的位置。单标记是一个偏保守、偏工程的选择：宁可粒度粗，也不浪费。推断

第 7 段　与 cache_edits 的配合

addCacheBreakpoints() 的后半段还有一条 useCachedMC 分支：当缓存编辑（cache editing）开启时，它会在结果里插入 cache_edits 块，删除指定的 cache_reference。这段逻辑不改变「消息层只有一个 cache_control」的规则，但它会改变「服务端缓存里保留什么」。源码 v2.1.88

两者配合的方式是：cache_control 决定「写到哪里」，cache_edits 决定「删掉哪些旧引用」。前者是空间上的边界，后者是内容上的修剪。对微压缩（microcompact）来说，这很关键：它想删掉旧工具结果，又不想让整个前缀失效，于是用 cache_edits 在服务端做「局部删除」，而不是在客户端改写消息。源码 v2.1.88

这也说明「单标记」不是孤立规则，而是和缓存编辑、TTL、scope 一起工作的。只改其中一个，另外两个可能失效。读这类代码时，最好把「标记、编辑、TTL」当成一组看，而不是三个独立开关。推断

第 8 段　失败模式：标记挂不上去的时候

第一种失败是「消息被规范化掉」。如果 markerIndex 指向的消息在 normalizeMessagesForAPI() 之后不存在了（比如空的 assistant 消息被过滤），标记就会落空。代码在 addCacheBreakpoints() 之前已经做过规范化，所以正常情况下不会发生；但任何在规范化之后再改消息数组的逻辑，都可能引入这个 bug。推断

第二种失败是「最后一条只有 thinking」。助手消息的数组内容如果最后一块是 thinking，标记会往前找，落到最后一个非 thinking 块；如果整条消息只有 thinking，没有任何块可打点，这条消息就不会带标记。此时缓存覆盖范围会缩短到最后一条有标记的消息，命中率下降，但不会报错。源码 v2.1.88

第三种失败是「消息为空数组」。messages.length - 1 会变成 -1，index === -1 永远不成立，结果没有任何消息带标记。这种请求通常也不会发生（空消息数组本身就会被上层拒绝），但代码没有显式防御。读到这里可以记一笔：单标记的实现假设「至少有一条消息」，这个假设没有被类型系统表达出来。推断

✓要点小结

  • 系统层最多四块，但只有非 null scope 带标记；实际 1–2 个。
  • 消息层恰好一个标记，默认在最后一条，覆盖它之前的全部内容。
  • fork 把标记前移到倒数第二条，落在共享前缀末尾，避免污染 KVCC。
  • 助手消息跳过 thinking / connector，标记落在最后一个稳定内容块。
  • TTL 资格锁存，是为了避免会话中途翻转导致缓存键变化。

05 · 与其他 agent 的差异

断点数量：一家一个，一家四个

「断点放几个」没有统一答案。它取决于服务端的驱逐策略、API 的断点上限、以及工具愿意为缓存写入付多少成本。下面四家代表四种取舍。推断

第一个对照是「断点数量与服务端策略」。Claude Code 的注释直接引用了服务端的驱逐实现，说明「一个标记」是针对 Mycro 的 KV 页回收策略做的优化；opencode 打四个点，是因为它要兼容多种 provider，无法假设某一种驱逐行为；Grok 留一个槽给网关，是因为网关可能自己加标记。断点数不是越多越好，而是要和「谁在回收、回收多快」匹配。推断

第二个对照是「系统层与消息层是否分开算」。Claude Code 明确分两层：系统块按 scope 打，消息层按位置打；opencode 也分两层，但消息层打两个点；Grok 把系统提示最后一块、最后一条可打点消息、上一轮边界都算进去，更像「按生命周期阶段」打点；pi 干脆不按消息打，改用 section patch 保前缀。分层方式不同，调参时能动的旋钮也不同。推断

第三个对照是「fork / 分支怎么处理」。Claude Code 显式把标记前移，避免 fork 尾巴污染共享缓存；opencode 没有等价的 fork 语义；Grok 的 rewind 通过 marker 截断重放，缓存影响由重放位置决定；pi 的 branch summary 走独立 section。分支越多，断点策略越需要「共享前缀」这个概念；没有分支的系统可以只考虑「最后一条」。推断

第四个对照是「断点是否可观测」。Claude Code 有一个独立的 promptCacheBreakDetection 模块，会对比系统提示哈希、工具哈希、TTL/scope 变化，判断「本可命中却没命中」的原因；opencode 在客户端只负责打标记，服务端命中率不可见；Grok 有 breakpoint 的显式数量约束，但归因较弱；pi 有 cache-stats，统计「上次命中、这次未命中」的浪费量，噪声下限 1024 token。断点策略越复杂，越需要可观测性来验证；否则调参只能靠猜。推断

把四个对照合起来看，Claude Code 的选择是「少而稳」：断点少、位置固定、TTL 锁存、fork 有特例。它不追求「每个位置都保护」，而是追求「共享前缀尽量长、写入尽量少、失效原因可解释」。这是一种偏运维的思路：缓存是成本中心，不是命中率竞赛。推断

06 · 思考题

三道题，从机制到取舍

Q1

如果在最后一条消息之前再加一个标记（比如倒数第 10 条），缓存覆盖范围会变大吗？命中率会提高吗？成本会怎么变？

提示（不给答案）

覆盖范围由「最靠后的标记」决定，前面的标记不会扩大它。倒数第 10 条的标记只保护那一段前缀，而最后一条的标记已经覆盖了它。

命中率不会提高，因为可复用的前缀没有变长；成本会增加，因为倒数第 10 条位置也被写入/保护，KV 页多活一轮。注释里的「second-to-last position is protected」说的就是这件事。

Q2

fork 时如果把 markerIndex 设为 messages.length - 3，会发生什么？为什么源码选倒数第二，而不是更保守的倒数第三？

提示（不给答案）

倒数第二是「最后一个共享前缀点」：再往后一条是 fork 自己新加的尾巴，父会话没有。倒数第三会把 fork 的倒数第二条也排除在缓存外，覆盖范围变小。

如果 fork 的倒数第二条也是新加的，那它本来就不该进共享缓存；但源码假设「只有最后一条是 fork 新增」，所以倒数第二正好是边界。这是一个基于调用方式的假设，不是通用规则。

Q3

你要给一个「每 10 条消息打一个断点」的新策略做评审。请从 API 上限、KV 页生命周期、失效点三个角度，写出你会问的三个问题。

提示（不给答案）

API 上限：一条请求最多几个 cache_control？加上系统层的 1–2 个，还剩几个给消息？超过会怎样（400）？

KV 页：每多一个断点，多保护哪些位置？这些位置下一轮还会被续写吗？如果不会，保护它们挤掉了谁？

失效点：断点之间的消息被改写时，缓存从哪一条开始失效？断点越密，失效范围越小，但写入次数越多；这笔账划不划算，要用命中率与写入成本一起算。

最后再问一句：这个策略在 fork 或压缩之后还成立吗？如果断点落在「已经被替换掉的历史」上，它保护的是一段不会再被读取的前缀，写入成本纯亏。断点策略必须和生命周期事件一起设计，不能只看稳态。
