日志与 surface 两层结构

DeepSeek Harness 把「发生过什么」和「模型看到什么」拆成了两层：底下一份只追加的日志，上面一层由日志派生出来的可见视图。压缩、裁剪、图片移出，全都不是「改历史」，而是「往视图上追加一条替换」。这一节读这层结构怎么建、怎么算、代价是什么。

01 · 功能说明

日志是唯一真相，surface 只是投影

DeepSeek Harness 的会话由一条只追加的事件日志构成，每个事件有一个单调递增的 seq。日志里什么都有：消息、轮次开始与结束、失败的尝试、压缩的锁与摘要、裁剪的计价。但模型只看得到其中五种：system/message、developer/message、user/message、assistant/message、tool/result。

这五种事件组成一个有序视图，叫 surface。它不复制日志，只记录「哪些 seq 当前可见、按什么顺序」。历史从来没有被修改过，被修改的只是这张索引。

为什么要多这一层？因为压缩和裁剪都需要「让一段历史不再可见」，但同时又需要「原始内容永远可查」。如果直接在日志上删行，前者做到了、后者丢了；如果只追加一条「摘要消息」而不遮蔽原文，原文还在模型的历史里，压缩等于没做。两层结构让两件事同时成立：日志保留一切，surface 决定可见性。

这张图里有三个容易混淆的点。第一，surface 上的顺序不等于 seq 的大小顺序：替换节点 seq 更大，却排在前面。第二，被遮蔽的节点仍在日志里，只是不再出现在 nodes 数组中。第三，替换发生时，surface 的节点数变少，但日志的长度只增不减。

正因为有这层结构，dsh 的所有上下文机制都能用同一种动作表达：压缩是「追加一条摘要 user 消息，替换一个区间」；裁剪是「追加一条内容更短的 tool/result，替换它自己」；图片移出是「追加一条 offload 决策，投影时把图换成占位文本」。三者共享同一套替换语义，也共享同一套缓存失效规则。

举个最小的例子。用户问一句、模型调一次工具、工具返回、模型回答，日志大概会新增六行：user/message、turn/start、assistant/message（带 tool-call）、tool/result、assistant/message（最终回答）、turn/end。surface 只新增四个节点——两个边界事件被排除。第二天回退或重放时，边界事件仍然在，但它们从来不影响模型看到什么。日志是「发生了什么」，surface 是「模型看到了什么」，两者的差集就是全部的过程性信息。

这个差集不是浪费。它正是审计、调试、计价的原料：一次失败的 agent/attempt 不进历史，但它是「为什么重试了三次」的唯一证据；一条 compaction/start 不进历史，但它是压缩锁的持有凭证。把过程性事件留在日志里、挡在 surface 外，是「可观测」与「上下文干净」能同时成立的原因。

代价也要说清楚：日志会比「模型实际看过的内容」大得多。一个跑了五十轮工具的长会话，surface 可能只有一百多个节点，日志却可能有上千条事件。这些事件不能删（删了就破坏 append-only），只能在恢复时跳过。所以「日志是唯一真相」的另一面是「日志会一直长」——这是第 3 节会提到的分页与检查点的由来。

// 唯一改动 nodes 的地方：一个已校验的 plan 落地
function applySurfacePlan(
  state: SurfaceFoldState,
  plan: SurfacePlan | undefined,
): SurfaceFoldReplacement | undefined {
  if (plan?.kind === 'append') {
    state.nodes.push(plan.seq) // 普通追加：只在尾部加一个节点
  } else if (plan?.kind === 'replace') {
    state.nodes.splice( // 把 startIdx..endIdx 换成这一个新节点
      plan.startIdx, plan.endIdx - plan.startIdx + 1, plan.seq)
    state.replaceGeneration += 1 // 位置结构变了：工具配对缓存要重建
    state.contentGeneration += 1 // 可见内容变了：派生历史要重建
  } else if (plan?.kind === 'project') {
    for (const [seq, message] of plan.messages) {
      state.projectedMessages.set(seq, message) // 插件改写既有消息，不增删节点
    }
    state.projections.add(plan.projection)
    state.contentGeneration += 1 // 内容变了，但位置没变
  }
  if (plan?.kind !== 'replace') return // 只有替换要向上报告被遮蔽的节点
  return {
    seq: plan.seq, start: plan.start, end: plan.end,
    shadowedSeqs: plan.shadowedSeqs, // 审计与计价都用这份清单
  }
}

// 派生模型可见历史：只读 surface 的节点数组，不读原始日志顺序
deriveMessages(): Message[] {
  const surface = this.surface
  const nodes = surface.nodes
  const generation = surface.contentGeneration
  if (generation !== this.derivedGeneration) {
    this.derived = [] // 发生过替换或投影：缓存整体作废
    this.derivedNodes = 0
    this.derivedGeneration = generation
  }
  for (const seq of nodes.slice(this.derivedNodes)) { // 只处理没见过的新节点
    const msg = this.deriveEventMessage(this.log[seq]!)
    if (msg) this.derived.push(msg) // 空内容的 system/assistant 投影为 null
  }
  this.derivedNodes = nodes.length
  return [...this.derived] // 每次返回新数组，元素是共享且深冻结的
}

04 · 逐段解读

五个决定，从「谁能进视图」到「缓存怎么失效」

第 1 段　五种事件才能进 surface，其他一律留在日志里

SURFACE_EVENT_TYPES 是一个五元素的集合，isSurfaceEligibleType() 只判断类型是否在其中。已核实这条规则把事件分成了两类：消息事件必须带 surfaceOp，非消息事件禁止带。类型系统用条件类型把这条约束写进了 SessionEvent：K extends SurfaceEventType 时有 surfaceOp，否则是 never。

运行时还有一道校验：一个类型不在集合里、却带了 surfaceOp，直接抛错。反过来，一个消息事件不带 surfaceOp，也抛错。已核实这不是防御性冗余，而是「surface 的完整性」依赖每一个消息事件都明确声明自己怎么进来——漏一个，派生历史就会少一条，而且不会有任何报错。

被排除在外的类型里，最重要的是 agent/attempt。一次失败的模型调用也是一条日志，但它不产生消息；重试成功之后，只有成功那一次进 surface。这解释了 dsh 为什么「没有把思考过程换成占位符」的机制：思考内容不在 surface 上，它根本不会进入模型可见历史。已核实

第 2 段　replace 的三个约束

替换不是随便指一个区间就行。落地前有三道校验，任何一道不过都抛错。

约束一：两端必须是当前 surface 上的节点。replacementRange() 用 startSeq 与 endSeq 在当前 nodes 数组里找下标，找不到就报错。这防止「替换一个已经被别人替换掉的范围」——那种操作在位置语义下没有意义，只会让视图错乱。

约束二：被遮蔽的 seq 必须全部出现在 sourceEventSeqs 里。这一条是审计要求：一条替换节点必须能说清「我替代了谁」。压缩的替换会带上摘要事件的 seq 与被遮蔽的全部节点 seq；裁剪的替换会带上它自己那一个 seq。已核实没有这份清单，重放时无法验证替换是否完整，也无法计算「这次替换省了多少 token」。

约束三：节点 0 的系统提示词只能被它自己替换。assertSystemHeadRewrite() 的判断很窄：只有当 startIdx === 0、原节点是 system/message、新事件也是 system/message、且只遮蔽一个节点时，才允许。已核实这保证了「第一条永远是系统提示词」，任何压缩都不能把它吞掉；同时也允许「重写系统提示词」这一种合法操作——比如换模型后重新渲染。注意保护范围只到节点 0：源码注释明确写着，后面的 system 节点没有这层保护，压缩区间可以遮蔽它们。已核实

还有一道只针对 tool/result 的校验：替换只能改 content，其余字段（调用 id、来源、错误标记、元数据）必须与原文深度相等。assertToolResultRewrite() 的做法很巧——把两边的 message.content 置为 null，再对整个 data 做结构化比较，不等就抛错。已核实这条约束保证了裁剪器不可能顺手改掉「这条结果属于哪个调用」，也就保证了工具配对关系不会因为裁剪而断掉。

第 3 段　两个 generation：为什么不是一个

replaceGeneration 只统计「位置结构变化」，contentGeneration 统计「位置变化或内容变化」。已核实分开的原因是两个消费者的敏感度不同。

派生历史只关心「模型看到的消息变没变」，所以用 contentGeneration：替换会变，插件改写某条消息的内容也会变，两者都要重建。工具配对缓存关心的是「节点顺序」，它只需要 replaceGeneration：插件改写一条消息的正文，不影响哪个 tool/result 跟着哪个 tool/call，缓存可以继续用。已核实

这是一个很实用的模式：不要用一个「脏标记」服务所有缓存，按「缓存依赖什么」拆成多个。拆多了管理成本高，拆少了会过度失效；两个通常是够用的——一个管结构，一个管内容。

看一个具体消费者：工具配对缓存（tool-pairing.ts）就是按 replaceGeneration 判断是否重建的。它缓存的是「每个切点是否平衡」这个布尔数组，一旦 nodes 被替换，下标与内容都会变，整个缓存作废；而插件只改某条消息的正文时，节点顺序没变，配对关系也不可能变，缓存继续有效。已核实如果只用一个 generation，要么每次内容改动都重建配对缓存（浪费），要么替换后不重建（错误）。

第 4 段　派生：纯追加 O(新增)，替换 O(全部)

deriveMessages() 的缓存有三个字段：derived（消息数组）、derivedNodes（已投影的节点数）、derivedGeneration（建缓存时的 generation）。每次调用先比 generation：不同就清空重建；相同就只处理 nodes.slice(derivedNodes) 这部分新节点。已核实

所以普通对话的成本是「新增几条消息就投影几条」，一次工具往返通常是一到两条，可以忽略。压缩之后成本是「整段历史重新投影」——这也解释了为什么压缩的代价不只是那次摘要调用，还包括之后第一次派生历史的全量遍历。

返回值的处理也值得注意：return [...this.derived] 每次给一个新数组，但数组里的 Message 对象是共享且深冻结的。已核实这样调用方可以随意排序、截取数组，却不可能改到日志里的原始消息。用「新容器 + 冻结元素」代替「深拷贝」，是这类高频读接口的常见写法。

还有一个小分支：if (msg) this.derived.push(msg)。空内容的 system、developer、assistant 消息会投影成 null，不进入历史，但它们在 surface 上仍然占一个位置。已核实为什么保留位置？因为位置是后续替换的锚点：一条空的 assistant 消息可能承载一次 max-tokens 步骤的用量，删掉它会让后面的 startSeq 失效。

把成本量化一下。假设 surface 有 100 个节点、一次工具往返新增 2 条消息：纯追加时，slice(derivedNodes) 只切出 2 个节点，投影两次，O(1)；压缩把 60 个节点折成 1 个之后，generation 变了，缓存清空，下一次派生要投影 41 个节点，O(n)。所以「压缩的代价」不只是那次摘要请求的 token，还包括之后第一次读历史时的一次全量遍历。对长会话来说，后者通常可以忽略（毫秒级），但它确实存在，而且随历史长度线性增长。

第 5 段　重放：同一份日志，同一份 surface

foldSurface() 是一个纯函数：从空状态开始，按 seq 顺序把每个事件喂给 applySurfaceEvent()，最后返回 nodes、替换历史与投影消息。已核实只要日志完整，重放出来的 surface 就与崩溃前一致——这是「日志是唯一真相」的技术含义。

为了保证这一点，代码对 seq 的连续性做了强制检查：planSurfaceEvent() 第一行就是「event.seq 必须等于期望值，否则抛错」。已核实不允许空洞，也不允许乱序。这让「按数组下标读日志」成为合法假设，省掉了大量查找。

重放也解释了分叉的实现：buildForkSeed(events, boundary) 复制到边界的前缀，追加一条 session/end-seed，再用合成 closer 补齐未闭合的 turn 与 step。新会话的日志从零开始，但它的 surface 与父会话在边界处一致。已核实和 Grok Build 的「同一文件多时间线」相比，这是另一种分支模型：分叉即复制，之后互不影响。

重放还有一个工程细节：SurfaceManager 不是每次都从 seq 0 开始。它接收一段「事件窗口」和一个 baseSeq，只折这一段，并把 _lastProcessedSeq 初始化成 baseSeq - 1。已核实这让「打开一个很长的会话」不需要把整份日志读进内存——读一个窗口、折一个窗口，剩下的靠持久化检查点衔接。代价是窗口边界必须完整：如果切在一个替换的中间，startSeq 就找不到了。所以分页的单位不是「随便 N 条」，而是「到某个已提交的边界」。

第 6 段　缓存失效：为什么收敛到一个变量

前缀缓存（prompt cache）的要求是「前缀逐字节一致」。在 dsh 的模型里，这句话可以精确翻译成：只要 nodes 数组的前 k 个节点及其内容没变，前 k 条消息的 token 序列就没变，缓存就能命中。于是「什么时候缓存失效」不再是散落在各处的判断，而是一个变量：contentGeneration 变了，派生历史就要重建，缓存从第一个变化的节点开始失效。

普通追加为什么不清缓存？因为 append 只往 nodes 尾部 push，前面的节点一个没动，contentGeneration 也不加一；缓存前缀保持有效，只有新增的尾部要计费。这也解释了 dsh 为什么把所有「改变历史」的操作都做成 replace 而不是「插入」：插入会让后面的节点整体位移，虽然内容没变，但位置变了，派生数组的顺序可能变；替换只影响被遮蔽的那一段，后面的节点下标变化但内容顺序不变。

不过要诚实地说：replace 仍然会让缓存从被替换处失效。压缩把中间的 60 个节点换成 1 个，从那个位置往后的所有 token 都变了，缓存只能命中前缀（系统提示词 + 节点 0 之前的内容）。dsh 的缓解办法是让摘要请求本身复用被遮蔽区间的逐字节前缀，先暖一次缓存，再让替换后的下一次请求去命中它——这是第 2 节要讲的「暖前缀」。

把这段和 Grok Build 对比会更清楚：Grok Build 的装配是「重新拼七个插槽」，前缀从第三个插槽就分叉；dsh 的替换是「原地折叠一段」，前缀能保留到被折叠的位置。同样是压缩，一个把缓存收益让给了「结构简单」，一个把结构复杂度换成了「缓存多命中一段」。没有免费的午餐，只有你把成本放在哪一步。理解了这一点，再去看两家的压缩代码，就不会觉得它们只是「写法不同」。

✓要点小结

  • 日志只追加、什么都有；surface 只收录五种消息事件，决定模型看到什么。
  • surfaceOp 只有两种：append 与 replace；替换必须指向现存节点、必须列出被遮蔽的 seq、不能动系统节点 0。
  • 替换用 splice 把一段节点折叠成一个；两个 generation 分别服务「结构缓存」与「内容缓存」。
  • 纯追加的派生是 O(新增)，替换后是 O(全部)；空内容节点占位但不产生消息。
  • 重放是纯函数，seq 必须连续；分叉是「复制前缀 + 合成收尾」。

05 · 与其他工具的差异

四种「日志与视图」的关系

把会话存储拆成「日志 + 视图」不是 dsh 独有的想法，但每家的切法不同：有的把视图做成数组，有的做成游标，有的干脆不显式建视图。

对照一：显式视图 vs 隐式过滤。dsh 把「哪些节点可见」变成一个真实存在的数据结构 nodes，替换时直接改它；Grok Build 不维护这个数组，而是在每次重放时用标记当场算出来。前者的好处是读取快、语义集中；后者的好处是磁盘格式极简、不需要把视图持久化。代价也对称：dsh 要在内存里维护两份（日志与节点数组），Grok Build 要在每个读路径上重复过滤。

对照二：替换 vs 追加。dsh 的压缩会把被遮蔽的区间从视图里「折叠掉」，所以压缩后 deriveMessages() 返回的历史真的变短了；pi 的做法是追加一条 CompactionEntry，重建时从 firstKeptEntryId 开始拼「摘要 + 尾巴」，旧条目仍在文件里但不会被读到。两者殊途同归，区别在「折叠」发生在写入时（dsh）还是读取时（pi）。写入时折叠的读取成本低，读取时折叠的写入成本低。

对照三：分叉 vs 回退。dsh 没有回退，只有 buildForkSeed 复制前缀；Grok Build 有回退，没有原生分叉（只能手动复制会话目录）。这是一组互补的能力：回退要求「同一份日志能表达多条时间线」，分叉要求「每条时间线有独立日志」。dsh 选了后者，于是它的日志永远是线性的、seq 永远连续，替换语义也更简单。

最后说这套结构的代价。一是认知成本：读代码的人必须同时记住「日志顺序」与「surface 顺序」两套坐标，一旦混用就会写出「按 seq 排序」这种看似合理、实际错误的代码。二是重放成本：日志越长，foldSurface 越慢，所以它必须配合检查点或分页；dsh 的做法是「加载事件窗口 + baseSeq」，把重放限制在一个窗口内。三是约束成本：每条消息事件都必须声明 surfaceOp，漏写就抛错。这三项加起来，换来的是一句很值钱的性质：任何时刻，模型看到的历史都能从日志精确重建，且原始内容永不丢失。

顺带说一句「为什么缓存失效能收敛」。别家的缓存失效通常是隐式的：改了一个字段、换了一个工具定义、重排了一条消息，缓存就在没人注意的时候失效了，只能靠事后看命中率下降来发现。dsh 把「可见内容变了」变成一个显式的计数器，任何改动都必须经过 applySurfacePlan 并让它加一，于是「缓存该不该失效」有了唯一答案。这个做法不能阻止失效，但能让失效变得可归因——这对排查「为什么这次请求这么贵」极其有用。

06 · 思考题

三道题，从推演到设计

Q1

surface 当前是 [0, 99, 7]（99 是一次早期替换产生的节点）。现在追加 replace { startSeq: 99, endSeq: 7 }，合法吗？替换后 nodes 是什么？如果 surface 是 [0, 3, 4, 7]，同样的参数还合法吗？

提示（不给答案）

先找下标：99 在位置 1，7 在位置 2。校验要求的是「start 的下标不大于 end 的下标」，不是「start 的数值小于 end 的数值」。

所以第一种合法，被遮蔽的是位置 1 到 2（99 与 7），替换后只剩 [0, 新节点]。第二种里 7 在位置 3、4 在位置 2，startIdx > endIdx，直接抛错。

再想一层：为什么数值会倒挂？因为 99 是一次替换产生的新节点，它的 seq 比 7 大，却排在 7 前面。

Q2

如果把 deriveMessages() 里的 generation 比较去掉，功能还正确吗？会退化成什么复杂度？如果只保留 replaceGeneration 呢？

提示（不给答案）

去掉比较，每次调用都会从头遍历全部节点。功能仍然正确——只是每次读历史都要 O(n) 投影，而工具循环里每步都要读一次。

只保留 replaceGeneration：插件改写某条消息内容（project 分支）时 generation 不变，缓存不会失效，于是模型继续看到旧内容。这是「缓存漏更新」，比慢更严重。

Q3

你要给一个已有系统加「压缩后还能审计原文」的能力。会选「日志 + 视图」还是「日志 + 回退标记」？请说出你的选择和两个必须付的代价。

提示（不给答案）

先明确需求差异：审计要的是「原始内容可查」，压缩要的是「模型看不见」。日志 + 视图能同时满足；日志 + 标记只能满足「时间线可回退」，压缩后的原文仍然要靠别的手段保留。

代价一：多一份内存结构（节点数组），且必须与日志严格同步。代价二：每个写消息的地方都要声明 surfaceOp，漏写即抛错；迁移旧代码时这是最大工作量。

再想一个反向问题：如果团队里有人写了一个「直接按 seq 读最近 N 条」的函数，会发生什么？
