多模态上下文

一张截图能省掉三百字描述，也可能一次吃掉两万 token。图片进入上下文之后，既不会自己变小，也不会自己消失；它要么被移出并留下占位，要么被压缩成摘要，要么被渲染成另一种图片。这一章讲这三种出口，以及每种出口的代价。

  • 第 9 类
  • 约 23 分钟
  • 0 个交互
  • L2 → L3

读完你能做到

  1. 画出图片在上下文里的生命周期：进入、保留、驱逐、占位，并说出每一站的判定条件。
  2. 比较按张、按字节、按像素三种计价口径，估算同一组截图在不同 agent 里的占用。
  3. 判断一次截图密集的调试该用“保留原图”“压缩前剥图”还是“历史转图”，并说出代价。

01 · 一张截图的三条路

“那个按钮明明是蓝色的”

下午五点，你在调一个前端样式。你给 Agent 发了六张截图：登录页、错误态、移动端、深色模式、两个对比图。它看得很准，第二轮就定位到 CSS 变量。第 20 轮，上下文到了 86%，触发压缩。压完它继续改，却开始说“登录按钮是灰色的”——因为那六张图在压缩时被剥掉了，摘要里只留下一句“用户提供了界面截图”。

图片在上下文里只有三条路：

  • 留下：原图继续占据窗口，按张或按像素计价。信息最完整，但最贵。
  • 移出 + 占位：把图从请求里去掉，换成一段文字（路径、附件名，或“图已不可见，不要凭记忆描述”）。便宜，但模型失去了视觉证据。
  • 换一种表示：压缩成文字摘要（附件转文字），或把文字历史渲染成图片（历史转图）。前者损失细节、保留语义；后者反过来，保留版面、损失可检索性。

多模态上下文的难点不是“能不能放图”，而是“图片什么时候该离开，离开时留下什么”。

这两个问题决定了三件事：模型还会不会“看见”那张图、它会不会凭记忆编造、以及下一次请求会不会因为图片太大被服务端拒绝。本章按生命周期拆开讲：进入时怎么规范化、保留时怎么计价、驱逐时按什么阈值、占位时写什么话。

02 · Codex 主线

直通、缩放提示、占位，以及两件没做的事

Codex 对图片的处理很克制：默认随消息直通模型；缩放时追加一条提示；模型不支持某模态时替换成固定占位文本；压缩时可以用一个特性给图片留单独预算。它没有“把历史渲染成图片”，也没有“把附件转成文字描述”。提交固定为 76ed3b4。

2.1 直通与缩放：只报尺寸，不重发图

图片默认随消息原样进入请求。当图片被缩放时，Codex 追加一条 <image_resize_notice> 片段，告知原尺寸与处理后尺寸，但不重发图片。image_resize_notice.rs#L1-L40 已核实

这个设计的意图是“让模型知道自己看到的是缩略图”。如果一张 4K 截图被压到 1,024 宽，模型仍可能按原图尺寸推理坐标，得出“按钮在 (1800, 920)”这种在缩放图上不成立的结论。提示里给出两组尺寸，模型就能按比例换算。代价是这条提示本身也占 token，而且它不解决“缩放丢了细节”的问题——小字被压糊之后，再告诉模型原尺寸也没用。

2.2 不支持时就占位，不静默丢图

模型不支持某模态时，历史规范化把图片/音频替换为固定占位文本：“image content omitted because you do not support image input”。unsupported_media.rs#L7-L22 已核实

“占位”与“删除”的区别在这里体现得很清楚：删除会让模型以为用户从没发过图；占位告诉它“有图，但你看不见”。后者能阻止模型编造，也能让它主动说“请把图里的文字贴出来”。代价是占位文本仍然占一点空间，且模型可能反复请求“再发一次”。

2.3 音频单独计价，不按字节折算

音频在截断预算中单独估算 token，不按字节折算。output-truncation/lib.rs#L160-L175 已核实 这一条容易被当成细节，但它决定预算怎么算。音频的 token 密度与字节数几乎无关（采样率、编码、时长共同决定），按字节折算会得到完全错误的预算。

它也给图片提了个醒：不同模态要用不同的计价函数。用一个统一的“字节 ÷ 4”处理文本、图片、音频，是很多实现出错的起点。

2.4 压缩时给图片留预算

Codex 有一个 CompactionImageBudget 特性，阶段为 Stable、默认开启，用于在压缩时为图片保留单独预算。features/lib.rs#L2072-L2076 已核实

这解决的是“压缩请求自己超窗”的问题：如果待压缩历史里有大量图片，压缩请求可能还没开始写摘要就被服务端拒绝。给图片单独留一笔预算，等于在压缩前先决定“哪些图值得带进摘要请求”。代价是预算怎么分没有统一答案：留多了压缩请求仍然超，留少了图片证据全丢。

2.5 Codex 没做的两件事

第一，没有历史转图。它不会把被丢弃的历史渲染成 PNG 再让模型“看图回忆”。第二，没有附件转文字。它不会先调用一个视觉模型把截图描述成文字，再把描述注入上下文；唯一的“文字化”是前面那条固定占位，不是模型生成的描述。

这两件事恰好是 omp 与 Grok 的强项。omp 的 snapcompact 把历史渲成图，Grok 在 Cursor 兼容 harness 下把用户附图先转成描述。它们代表了两种相反的思路：用图片换文本，还是用文本换图片。

03 · 生命周期

进入、保留、驱逐、占位

把七家的做法抽象一下，图片在上下文里会经过四站。每一站都有各自的判定条件，任何一站缺失，都会出现“图还在但模型看不见”或“图没了但模型以为还在”的问题。

进入：先规范化，再计价 缩放、转格式、校验体积。Claude Code 上限 2000×2000、base64 5 MB、目标原始体积 3.75 MB；opencode v2 读取侧 20 MiB；Codex 缩放后只发提示。
保留：计价口径决定策略 按张（Grok 765、opencode v2 1,500）、按固定字符（pi 4,800）、按帧（omp 5,024）、按 provider 计数（Claude Code）。口径不同，同一张图在两家能差一个数量级。
驱逐：从最旧开始 opencode v2 25 MiB → 15 MiB；Grok 请求体到“上限 − 3 MiB”开始，回收到一半；dsh 按适配器给的张数移出最早的图。
占位：告诉模型“别猜” 最好像 opencode v2 与 Grok 那样，明确写“图已移出、不要凭记忆断言内容、需要时重新读取或让用户重发”，而不是只留一个文件名。

3.1 三种计价口径，三种误差

  • 按张固定值Grok 765；opencode v2 1,500；omp 5,024/帧；pi 4,800 字符（≈1,200 token）。便宜、可预测，但与图片内容无关：一张纯色图和一张满是文字的截图算一样多。
  • 按像素 / tileClaude Code 限制 2000×2000 与 5 MB，实际计价交给 provider 的 tile 规则；这是最接近真实成本的口径，但客户端算不出来，只能“限制尺寸、不报数字”。
  • 按字节opencode v2 的 25 MiB / 15 MiB、Grok 的请求体预算、dsh 的适配器预算。它管的是“请求能不能发出去”，不是“模型看多少 token”；两者不能互相换算。

三种口径的误差方向不同。按张固定值对“文字截图”低估（文字多的图 token 更贵），对“纯色图”高估；按像素最准，但需要 provider 配合；按字节只保证传输成功，不保证窗口不爆。真正严谨的实现会同时维护两套数：一套给窗口预算（token），一套给请求体预算（字节）。opencode v2 与 Grok 都是这么做的。

04 · 三种出口

移出、转图、转文字

图片离开上下文有三种方式，代价完全不同。下面按“信息损失从少到多”排：移出 + 占位保留原图，随时可回读；历史转图保留版面，但变成另一张图；转文字保留语义，丢掉视觉细节。

4.1 移出 + 占位：最常见，也最容易被写坏

opencode v2 在请求组装阶段做两道媒体治理。第一道 unsupportedParts：模型能力不支持的模态被替换成一句 ERROR: Cannot read … 文本。第二道 boundImages：统计所有内联图片字节，超过 25 MiB 就开始从最旧的图片删起，删到 15 MiB 以下；移除文本明确要求模型“不要凭记忆断言图片内容，需要时重新读取或让用户重发”。model-request.ts#L122-L216 已核实 读取侧另有 20 MiB 的媒体摄取上限，超过直接报 MediaIngestLimitError。

Grok Build 用的是请求体预算加滞回：当序列化后的 body 达到“上限 − 3 MiB”时开始驱逐老图片，一直回收到“上限的一半”才停。被驱逐的图片替换为一段明确告知模型“图已不可见、不要凭记忆描述”的占位文本；工具结果里的图片驱逐则在该结果文本末尾追加同类说明。image_budget.rs#L9-L35 已核实

为什么清到一半，而不是清到阈值以下。如果只清到“刚好低于触发线”，下一张图进来又会越线，于是每轮都触发一次驱逐，每次都改动前缀，KV cache 反复失效。清到一半留出足够的缓冲，让接下来若干轮都不再越线。这是典型的滞回设计：用一次多删，换长期稳定。代价是可能一次删掉过多仍然有用的图。

dsh 走的是“路由拒绝时永久 offload”：图片适配器超预算时返回 IMAGE_OFFLOAD_REQUIRED 并附带需要移出的张数。dsh-compaction-image-offload 沿模型请求顺序遍历 surface，跳过 assistant 节点与已标记图片，标记恰好那么多最早的图片出现位置，每条决策追加一个 image/offload 事件。下一次投影时这些图片变成占位文本（附件名 + 可读路径），请求重试不消耗 provider 重试预算、也不写 llm/retry。选择跨路由、resume、replay 持久。image-offload/README.md#L12 推断1

为什么“永久”很重要。如果每次请求都重新判断要不要移出，同一张图可能在 A 请求里被删、在 B 请求里又回来，模型看到的世界不稳定，缓存也不稳定。把 offload 写成事件、跟着会话走，等于让“这张图已经不在”成为一个持久事实。代价是用户后来想再看那张图，必须重新发或重新读，系统不会自动恢复。

4.2 历史转图：omp 的 snapcompact

snapcompact 是 omp 压缩方法链里的一环：把被丢弃的历史序列化成文本、归一化后光栅化成 PNG 帧，交给视觉模型“读图”。帧形状按模型 id 选择：Claude 用 11on16-bw、Gemini 用 8on22-bw@2048、OpenAI 用 8on22-bw。帧存在 CompactionEntry.preserveData.snapcompact，每次重建上下文都重新挂回摘要消息。snapcompact.ts#L447-L483 已核实

它的计价回退常量是 FRAME_TOKEN_ESTIMATE = 5024，默认帧上限 80 帧。docs/compaction.md#L206-L219 已核实 80 帧 × 5,024 ≈ 40 万 token，这显然不是“无条件全渲”——实际会按预算裁帧，帧数由被丢弃历史的体积决定。

为什么要把文字渲成图。同样一段文字，作为文本要按 token 计价，作为图片可能按“张”计价，而一张图能装下很多字。对视觉模型来说，读一张密集排版的图，可能比读等量文本便宜。omp 的评测里用 SQuAD 做过对照，说明这不是纯理论。已核实

代价有三层。第一，需要视觉模型，纯文本模型用不了；第二，文字细节会糊，尤其是代码缩进与小字号，模型可能读错一个字符；第三，不可检索——文本可以被 grep、被引用、被精确复制，图片不行。所以它适合“交接性质的旧历史”，不适合“当前正在改的代码”。

omp 还有 inline snapcompact：可把系统提示词或工具结果直接渲染成图片，默认关闭（snapcompact.systemPrompt = "none"、snapcompact.toolResults = false）。context-settings.ts#L414-L443 已核实 默认关是对的：系统提示与工具结果需要被精确遵守，渲成图只会增加读错的风险。

4.3 压缩前剥图：最容易被忽略的一步

Claude Code 在压缩请求发送前调用 stripImagesFromMessages，把图片块替换成文本标记，理由写在注释里：摘要不需要图片，而图片容易让压缩请求自己触发 prompt-too-long。compact.ts#L133-L165 源码 v2.1.88 这一步是始终执行的，没有开关。

opencode 在压缩序列化时把图片压成一行 [Attached <mime>: <filename>]，不进摘要请求；v1 的 overflow 路径还会在重放触发溢出的用户消息时，把 isMedia(mime) 的 file part 换成同样的文本，并补偿一段“附件过大、请重试更小的文件”的说明。compaction.ts#L484-L487 已核实

Codex 不给图片剥掉，而是给它们留预算（CompactionImageBudget）；Grok 在压缩请求前按 max_request_bytes 做一次 image budget；dsh 把“摘要失败”也接到同一条 offload 瀑布上，只处理摘要选区内的图片，直到没有可移的为止。

剥图之后，图片在本地文件系统里仍然存在，但 Claude Code 本快照没有把历史图片复制到 tool-results/ 的代码路径；模型只能靠重新读取原文件或让用户重发。推断2

两种路线的分歧：剥图假设“摘要不需要视觉细节”，因此压缩后的模型只能依赖文字；留预算假设“图片是证据”，愿意为它承担压缩请求超窗的风险。前者更稳，后者更保真。代价分别是：剥图后模型再也看不到那张报错截图；留预算可能让压缩请求本身失败，进入重试或降级。

4.4 附件转文字：只有一家真的做了

Grok Build 的第三条路是“图片转文字”，但仅 Cursor 兼容 harness：它会把用户附图先送视觉模型生成描述，再把描述注入该轮用户消息（最多 16 张，超出打跳过标记）；失败则整轮失败、绝不静默丢图。其他 harness 走“持久化图片 + 前置 <image_files> 清单”。image_describe.rs#L1-L40 已核实

为什么只有一家这么做？因为“转文字”是一次额外的视觉模型调用：多一次延迟、多一笔费用，而且描述可能错。它的好处是后续所有模型调用都只处理文本，不再受图片预算约束，也不再需要视觉能力。代价是信息在第一次转写时就被压扁了：颜色、位置、像素级差异全部丢失，而这些恰恰是 UI 调试最需要的。

其他家的“附件转文字”大多只是占位，不是描述：Claude Code 的剥图标记、Codex 的 unsupported 文本、opencode 的 [Attached mime: name]。把它们当成“转文字”会高估模型掌握的信息——它只知道“有过一张图”，不知道图里是什么。

05 · 七个编码智能体

七种预算，七种占位

Codex 的直通与占位已在主线拆过。下面七个 agent 各有一个弹窗，重点看四个数：每张图怎么计价、体积上限是多少、什么时候驱逐、驱逐后留下什么话。这四个数决定了一次截图密集的会话能撑多久。

键盘：Esc 关闭；Tab 在弹窗内循环。Claude Code 的结论来自非官方 v2.1.88 源码，只代表该版本。

07 · 设计取舍

为什么同一张图能差一个数量级

下面五组取舍，解释“计价差一个数量级、驱逐策略完全相反”的原因。每组给两种路线与代价。

取舍一：按张固定价，还是按像素 / 字节

按张（Grok 765、opencode v2 1,500、omp 5,024/帧）实现简单、可预测，模型侧不需要知道图片内容。它假设“平均一张图大概这么多 token”，对截图、照片、图表一视同仁。

按像素 / tile（Claude Code 的尺寸限制背后是 provider 的 tile 计价）最接近计费真相：图越大、切块越多、token 越多。代价是客户端算不出来，只能限制尺寸、把数字留给 provider。按字节（opencode v2 的 25 MiB、Grok 的请求体）管的是传输，不是窗口，和 token 预算不能互换。

代价：按张固定值会让“文字密集的截图”被严重低估——一张 4K 代码截图可能有 3 万 token，按 1,500 算等于白送；按像素准确，但需要 provider 配合，跨模型不可移植；按字节只保证请求能发出去，可能在窗口层面早已爆掉。三种口径同时存在的现实含义是：你要分别问“窗口够不够”和“请求体够不够”，不能用同一个数回答。

取舍二：清到阈值以下，还是清到一半

清到阈值以下（最直觉的做法）每次只删到刚好不越线，节省最大化。清到一半（Grok）一次多删，留出滞回空间。

代价：前者会让会话在阈值附近反复抖动——来一张图越线、删一张图回线、下一轮又来一张，每次都改动请求前缀，缓存反复失效，用户看到的是“图片时有时无”。后者牺牲一部分仍然有用的图，换长期稳定。对缓存敏感的 provider，滞回几乎是必须的；对不计较缓存的自建服务，清到阈值以下更省。

取舍三：占位写路径，还是写“别信记忆”

只写路径（“完整结果在 /tmp/xxx.png”）假设模型会去读。多数时候它不会：路径太长、模型不知道这是图片、或者它觉得“我记得大概长什么样”。写“图已移出、不要凭记忆描述、需要时让用户重发”（opencode v2、Grok）直接干预模型的推理习惯。

代价：后者更啰嗦，占几十个 token，而且会让模型频繁请求“请重发图片”，打断用户。前者更安静，但模型可能在无意识中编造视觉细节——这是多模态上下文里最危险的失败，因为它看起来很有把握。

取舍四：历史转图，还是文本摘要

历史转图（omp 的 snapcompact）把旧历史渲成 PNG 帧，用视觉模型读。它保留了版面信息（缩进、表格、对齐），在“读一份旧报告”这类任务上可能比纯文本摘要更保真，单位 token 也可能更便宜。文本摘要保留语义与可检索性，但会丢掉版面。

代价：转图需要视觉模型，文字可能被 OCR 读错，且完全不可 grep；帧数上限（80）意味着超长历史仍要裁。文本摘要便宜、通用，但对“这段代码原来怎么缩进”这类问题无能为力。omp 把 snapcompact 放在方法链的第二位，前面还有 remote，说明它自己也不认为这是默认最优解。

取舍五：压缩前剥图，还是给图留预算

剥图（Claude Code 始终执行）保证压缩请求一定能发出去，代价是压缩后模型失去视觉证据。留预算（Codex 的 CompactionImageBudget、Grok 的 image budget）试图保住关键图片，代价是压缩请求可能自己超窗，进入重试甚至失败。

代价：剥图适合“图片只是辅助说明”的任务；留预算适合“图片就是证据”的任务，比如 UI 还原、图表读数。两者都不能兼顾，所以更细的实现会按图片类型或位置分配预算——这也是 Codex 把它做成特性开关、而不是全局策略的原因。

还有一组横切的取舍：永久 offload，还是每次请求重算。dsh 选择永久（写事件、跨 resume 生效），保证模型看到的世界稳定；opencode v2 与 Grok 每次请求按字节重算，保证“这一请求一定发得出去”。前者状态一致但可能过度删除，后者灵活但每轮都要扫描全部图片。两种都能工作，关键是别混用：一半永久、一半重算，会出现“这张图到底在不在”的不确定性。

08 · 小测验

三道题，检验你会不会算图

Q1

opencode v2 的会话里有 12 张内联图片，每张 2 MB，合计 24 MB。再加 3 张后会发生什么？会删掉几张、剩多少？

解析

12 张时 24 MB，低于 25 MiB 触发线，不驱逐。加到 15 张后 30 MB，越过 25 MiB，开始从最旧的删起，直到 ≤15 MiB：需要删掉 8 张（16 MB），剩 7 张（14 MB）。注意 25 MiB 与 15 MiB 是二进制单位，30 MB 十进制约 28.6 MiB，结论不变。见 4.1。

Q2

Grok Build 的图片驱逐为什么清到“请求体上限的一半”，而不是清到“刚好低于触发线”？这样做的好处与代价各是什么？

解析

为了滞回：只清到触发线以下，下一张图进来又会越线，于是每轮都触发驱逐、每轮都改动请求前缀，KV cache 反复失效。清到一半留出缓冲，接下来若干轮都不会再越线。代价是一次可能删掉过多仍然有用的图片。见 4.1 与 取舍二。

Q3

一次 UI 还原任务，你手上有 8 张截图，后续还要改 30 轮。你会选“一直保留原图”“压缩前剥图”还是“历史转图”？分别说出代价。

解析

没有单一正确答案，取决于截图是否持续被引用。若每轮都要对照像素，保留原图最可靠，代价是窗口被 8 张图长期占据，可能挤压代码与日志，并在压缩时被迫剥图。若截图只在开头定位问题、后面靠代码，压缩前剥图可接受，代价是压缩后模型再也看不到颜色与布局，容易凭记忆编造。历史转图适合“截图已经变成旧历史、但仍需保留版面”的中段，代价是需要视觉模型、文字可能读错、且不可检索。务实做法是保留原图 + 在摘要里写清关键视觉结论（颜色值、布局关系），而不是只留“用户发了截图”。见 第 04 节 与 取舍五。

agent 弹窗 · opencode-v1

opencode v1

agent 弹窗 · opencode-v2

opencode v2

v2 在请求组装阶段有两道媒体治理。第一道 unsupportedParts：模型能力不支持的模态（或 xAI 不支持的非 png/jpeg/webp 图片）被替换成一句 ERROR: Cannot read … 文本。第二道 boundImages：统计所有内联图片字节，超过 25 MiB 就开始从最旧的图片删起，删到 15 MiB 以下，替换文本明确要求模型“不要凭记忆断言图片内容，需要时重新读取或让用户重发”。读取侧另有 20 MiB 的媒体摄取上限。压缩侧的 messageToText 把图片压成 [Attached mime: name] 一行。

设计意图
用字节预算直接对齐“请求体能不能发出去”，并用明确的占位文案阻止模型编造。代价是字节与 token 不成正比：30 MiB 的高压缩截图可能只占很少 token，却仍被删。推断

agent 弹窗 · grok-build

Grok Build

Grok 把图片按 765 token/张计入估算，但真正的控制是请求体字节预算。内联图片的 data: URL 是请求体的主要构成。当序列化后的 body 达到“上限 − 3 MB”时开始驱逐老图片，一直回收到“上限的一半”才停。这种滞回避免每轮都跨过阈值、反复打断 KV cache。被驱逐的图片替换为一段明确告知模型“图已不可见、不要凭记忆描述”的占位文本。第二条路是服务端拒图：收到带 invalid_image 的 400 时，若整个请求里只有一个唯一图片 URL，把该图从 chat_history.jsonl 中剥离并重试。第三条路是图片转文字，仅 Cursor 兼容 harness：先送视觉模型生成描述，再注入该轮用户消息，最多 16 张。

关键参数与默认值
IMAGE_TOKEN_ESTIMATE = 765；驱逐触发 max_request_bytes − 3 MiB；回收目标 max_request_bytes / 2；剥离并发上限 16；转写上限 16 张；转写仅 is_cursor_harness()。已核实
设计意图
以请求体而不是 token 为主控，因为图片撑爆的是传输而不是窗口；滞回是为了缓存稳定。代价是删图与 token 预算脱钩，且拒图剥离只改 chat_history.jsonl，updates.jsonl 重放会恢复图片并再付一次剥离成本。推断
来源
image_budget.rs#L9-L35（预算与占位）· image_strip.rs#L1-L40（拒图剥离）· image_describe.rs#L1-L40（转写与 16 张上限）

官方文档与源码在“图片体积限制”上没有直接对应项：源码用请求体预算，不设单张像素上限；这也是它与 Claude Code 最大的差异。

agent 弹窗 · dsh

DeepSeek Harness

dsh 不移出图片，而是在路由拒绝时永久 offload：图片适配器（DeepSeek 的 file-mode / inline-fallback 预算、pi-ai 的 base64 界）在超预算时返回 IMAGE_OFFLOAD_REQUIRED 并附带需要移出的张数。dsh-compaction-image-offload 沿模型请求顺序遍历 surface，跳过 assistant 节点与已标记图片，标记恰好那么多最早的图片出现位置，每条决策追加一个 image/offload 事件（按当前消息事件 seq + 深度优先图片索引定位），消息事件与 surface 节点身份都不变。下一次投影时这些图片变成占位文本（附件名 + 可读路径），请求重试不消耗 provider 重试预算。

关键参数与默认值
触发码 IMAGE_OFFLOAD_REQUIRED（带 offloadImages 计数）；无自有配置，预算由适配器决定；选择顺序为请求顺序中最早出现、跳过 assistant；事件 image/offload；占位为附件名 + 可读路径。推断
设计意图
