零成本裁剪：软裁剪与硬清空

压缩要调一次模型，慢且贵。Grok Build 在压缩之前还有一道完全不调模型的减量：按「轮龄」把老工具结果先砍一刀。规则只有三条——最近三轮不动，中年结果留头留尾，太老的整条清空。这一节逐行读这三条规则，以及它们为什么只作用在请求副本上。

01 · 功能说明

在调模型之前，先把「死掉的历史」减掉

上下文减量按代价排序，最便宜的是「不调模型、只改请求」。Grok Build 把这一步放在请求构建里：每当要发一次请求，先把当前历史克隆一份，按轮龄裁剪克隆里的工具结果，再把克隆发出去。原始历史一个字节都不动。

这条链最重要的一句话是：裁剪发生在副本上。它省的是「这一次请求的 token」，不是「会话的 token」。

为什么值得单独讲？因为它处在一个很尴尬的位置：它比压缩便宜得多，却比压缩更容易被误解。用户看到 /context 显示 60%，以为什么都没发生；实际上发出去的请求可能只有 40%。反过来，用户以为「裁剪过了应该很省」，但下一轮读同一个文件，工具又返回一遍完整内容，因为裁剪从来不写回磁盘。

链路上还有一处顺序值得注意：裁剪排在图片预算之后。图片预算可能已经把一部分图片换成了占位文本，但裁剪的触发判断用的是 self.state.total_tokens，也就是裁剪前的会话估算值。换句话说，即使图片驱逐已经腾出了空间，只要会话估算还在 50% 以上，文本裁剪照样运行。这个设计选择很务实：两个机制各自独立、互不依赖，谁先谁后都不会导致对方失效。

本节要读的函数只有两个：should_prune()（要不要裁）和 prune_conversation()（怎么裁）。前者三行，后者四十四行。裁剪的全部规则都在这四十四行里。

// 请求构建时调用的入口：先问「要不要裁」，再裁这份副本（L107-L118）
pub(super) fn prune_items_for_turn_request(
    &self, mut items: Vec<ConversationItem>,
) -> Vec<ConversationItem> {
    if should_prune(self.state.total_tokens, self.state.sampling_config.context_window) {
        prune_conversation(&mut items, &self.pruning_config);
    }
    items
}
// 严格大于：正好 50% 不裁（测试 should_prune_gating 钉住了这一点）
pub(crate) fn should_prune(total_tokens: u64, context_window: std::num::NonZeroU64) -> bool {
    total_tokens > context_window.get() / 2
}
// 裁剪本体：从尾部往前扫，按「用户轮次」估算轮龄（L132-L177）
pub(crate) fn prune_conversation(conversation: &mut [ConversationItem], config: &PruningConfig) {
    if !config.enabled { return; } // 总开关
    let mut turn_from_end: usize = 0; // 0 = 当前这一轮
    let mut seen_first_user = false;
    for item in conversation.iter_mut().rev() { // 从最新一条往回走
        if matches!(item, ConversationItem::User(_)) {
            if seen_first_user { turn_from_end += 1; } // 遇到更早的 user 才算新的一轮
            seen_first_user = true;
            continue; // user 消息本身不裁
        }
        let ConversationItem::ToolResult(tool_result) = item else {
            continue; // 只处理工具结果，其余一律跳过
        };
// 分支一：最近 N 轮内的工具结果永不裁剪
        if turn_from_end < config.keep_last_n_turns { continue; }
// 分支二：超龄结果整条换成占位符，先判断是否已经是占位符，避免重复写
        if turn_from_end >= config.hard_clear_age_turns {
            if tool_result.content.as_ref() != HARD_CLEAR_PLACEHOLDER {
                tool_result.content = std::sync::Arc::<str>::from(HARD_CLEAR_PLACEHOLDER);
            }
            continue;
        }
// 分支三：中年结果，超过阈值才留头留尾，中间换成固定分隔符
        let content_len = tool_result.content.chars().count(); // 按字符数，不是字节
        if content_len > config.soft_trim_threshold {
            let head = safe_char_slice(&tool_result.content, 0, config.soft_trim_head);
            let tail = safe_char_slice_tail(&tool_result.content, config.soft_trim_tail);
            tool_result.content =
                std::sync::Arc::<str>::from(format!("{head}{SOFT_TRIM_SEPARATOR}{tail}"));
        }
    }
}
// 两个切片函数都遍历 chars，因此不会把多字节字符劈成半个
fn safe_char_slice(s: &str, start: usize, count: usize) -> String {
    s.chars().skip(start).take(count).collect()
}
fn safe_char_slice_tail(s: &str, count: usize) -> String {
    let total = s.chars().count();
    if count >= total { return s.to_string(); } // 短于尾巴预算就整条留
    s.chars().skip(total - count).collect()
}

04 · 逐段解读

四条规则，一个容易被忽略的副作用

第 1 段　轮龄：从「最后一条用户消息」往回数

裁剪不按时间、不按消息条数，而按「用户轮次」。理由很实际：一次用户请求可能触发三十次工具调用，按条数算，最近的三十条全是同一轮的工具结果；按轮算，它们同属第 0 轮，一起受保护。

实现方式是从后往前扫，维护两个变量。seen_first_user 记录「是否已经见过最新那条用户消息」，turn_from_end 记录「当前处在倒数第几轮」。遇到用户消息时：如果不是第一条，轮次加一；无论是不是，都把它标记为已见。已核实

这套计数有个容易读错的地方：工具结果不一定和用户消息交替出现。真实的顺序常常是「user → assistant(tool_call) → tool_result → assistant(tool_call) → tool_result → assistant」。从尾部往回扫，在遇到那条 user 之前，所有工具结果都属于第 0 轮；跨过它之后才变成第 1 轮。已核实所以「最近 3 轮」保护的是「最近三条用户请求及其全部工具结果」，而不是「最近三条消息」。

如果一段历史以工具结果开头（比如会话被截断、或者系统注入了一条合成消息），第一轮计数会从 0 开始，这些结果仍然受保护。这是保守的偏差：宁可少裁，也不误裁。

这里有一个值得注意的细节：Grok Build 的很多注入都是「合成用户消息」，比如日期滚动提醒、任务完成通知、MCP 连接提醒。这段代码只匹配 ConversationItem::User(_)，不检查 synthetic_reason；而同一个 crate 里的别处代码会检查这个字段。也就是说，一条合成提醒可能被当成「用户又提了一个新需求」，让轮龄多加一。1后果是：工具结果会比实际更早进入软裁剪区间。这个偏差是保守方向（多裁一点），不会导致漏裁。

第 2 段　软裁剪：头 1500 + 分隔符 + 尾 1500

软裁剪的条件是「内容字符数 > 4000」。注意这个 4000 是阈值，不是「裁到 4000」：裁剪后的长度是 1500 + 分隔符 + 1500，分隔符是 \n\n[…trimmed…]\n\n，大约 20 个字符。所以一条 4,001 字符的结果会被裁到约 3,020 字符，只省下四分之一；一条 40,000 字符的结果会省下 92%。已核实

为什么留头留尾，而不是只留头？因为工具输出里最有价值的两端不一样：开头是「这是什么」（文件名、命令、表格头），结尾是「结果是什么」（错误、汇总、最后一行输出）。中间大段是重复的日志或代码，删掉损失最小。这和 Codex 的 truncate_middle_with_token_budget 是同一个直觉，区别只在预算单位：Codex 按 token，Grok Build 按字符。

按默认值算一个具体例子。假设历史里有 12 条工具结果，每条 8,000 字符，轮龄都在 3 到 9 之间：每条裁到约 3,020 字符，净省 4,980 字符，12 条共省约 59,760 字符。按字节 ÷ 4 估算，约 15,000 token。如果窗口是 200,000，这一步就把水位从 60% 拉回 52.5%。差一点点还是压不下去——这正是「便宜手段只能削峰、不能替代压缩」的量化写照。

还有一个细节：soft_trim_threshold 判断的是当前内容的字符数。如果一条结果已经被软裁剪过一次（约 3,020 字符），它下次不会再被裁——因为 3,020 小于 4,000。这意味着软裁剪是幂等的，不会每轮都往里缩。这一点很重要：如果阈值被调到裁剪后的长度以下（比如 2,500），这条结果每轮都会重新进入裁剪函数，但删除区间此刻只覆盖中间那句分隔符，输出与输入几乎一样——白白消耗一次切片，内容不再变短。

两套口径：字符数与字节数

裁剪的阈值与切片都按 Unicode 字符（chars()）算，而压缩的 token 估算按 UTF-8 字节 ÷ 4 算。对纯 ASCII 的输出（大多数命令、日志、代码），两者只差 4 倍，不会造成困惑。对中文输出，一条 4,000 字的结果约 12,000 字节、估算 3,000 token，但它刚好卡在裁剪阈值上；而一条 4,000 字节的中文结果只有约 1,333 字，估算 1,000 token，却不会被裁剪。结果是：中文工具输出更容易躲过裁剪，却更容易触发压缩。

第 3 段　硬清空：整条换成一句占位符

轮龄达到 10 轮，工具结果整条被替换成 [Tool result omitted — too old]。这句话本身就占 token（约 10 个），但它换来的是把几万字符变成十个词。

代码里有一个看起来多余、其实必要的判断：如果内容已经是占位符，就不再写一次。写 Arc<str> 会分配新内存并触发引用计数变化；虽然结果一样，但每轮都重写一次是纯浪费。更重要的是，这个判断让函数对「已经裁剪过的历史」保持幂等——重复调用不会改变任何东西。已核实

硬清空是不可逆的，至少在这一份请求里。模型看到的就是一句话，没有指针、没有文件路径、没有「需要时重读」的提示。这是它和最省事的那种「落盘 + 指针」方案的差别：Grok Build 的工具层确实有落盘（bash 输出写到 <session_folder>/terminal/<tool_call_id>.log），但裁剪这一层不会去查那个路径，也不会把路径写进占位符。模型如果想恢复，只能重新执行一次工具调用。

这个选择的代价很具体：老旧但仍有用的信息（比如十轮前那次 ls 的目录结构）会被彻底抹掉，而重新获取它要花一次工具调用、一次往返、一次新的 token。收益是确定性：占位符长度固定、行为可预测、不需要维护「原文在哪」的索引。这是一个用「可恢复性」换「实现简单」的典型取舍。

第 4 段　为什么只改副本：三个直接后果

裁剪发生在 build_conversation_request() 里，作用对象是 self.state.conversation.clone() 产生的临时数组。这一点带来三个可以直接观察到的后果。

后果一：/context 与实发 token 不一致。状态栏与 /context 读的是会话状态里的估算值，裁剪只改副本，所以显示值偏高。用户看到 60%，实际发出去可能只有 45%。这不是 bug，是「显示的是会话，发出去的是请求」这个结构性差异。

后果二：下一轮从同样的原始内容重新裁。因为磁盘没变，每轮构建请求都要重新走一遍裁剪。好在这套规则是纯函数、成本是 O(n) 的字符串切片，比起一次模型调用可以忽略。但如果历史很长，每轮都扫一遍全部消息仍然有成本——这也是为什么它只在 50% 以上才启用。

后果三：缓存从第一个被裁的位置失效。这一点最容易被忽略。裁剪改的是历史中段的内容，而 prompt cache 要求前缀逐字节一致。一旦某条工具结果被裁，从它开始往后的所有 token 都要重新计费。所以「不调模型」不等于「零成本」：省下的是输入 token 的数量，付出的是缓存命中率的下降。推断2源码没有为裁剪做缓存守卫（对比 oh-my-pi 的 cacheWarmSuffixTokens），说明这个代价被接受了。

把三个后果放在一起看，这项机制的真实定位就清楚了：它是「压缩前的最后一道便宜闸门」，不是「常态化的瘦身」。50% 的触发线保证了它在大多数请求里根本不运行；一旦运行，说明这一轮已经接近需要压缩，缓存命中率本来就要被打断。

那为什么是 50%，不是 70% 或 85%？因为它和压缩阈值（默认 85%）之间需要留出一段「缓冲带」。50% 到 85% 这 35 个百分点，就是裁剪独立工作的区间：先靠确定性的切片把水位压下去，如果能压回 50% 以下，这一轮连压缩都不需要；压不下去也不要紧，压缩仍在 85% 那里等着。两条线的间距越大，裁剪承担的份额越多、压缩触发得越少；间距越小，裁剪就只是压缩前的一次「顺手打扫」。

这个设计还有一个隐含的好处：裁剪的粒度是「单条结果」，压缩的粒度是「整段历史」。前者可以只损失一小块，后者会损失全部细节。先用便宜的手段做小损失，再用昂贵的手段做大损失，是减量链条的通用顺序。Grok Build 把它写成了两级：50% 裁一次，85% 压一次。

第 5 段　三段式之外，它没做什么

这段代码只处理 ConversationItem::ToolResult，其他类型一律 continue。也就是说，它不做下面这些事：

不清理「过期文件读取」。同一个文件读了三次，三份内容都保留，只要轮龄不到 10。它不知道哪一份是新的。

不清理「空搜索结果」。一次零命中的 grep 与一次有结果的 grep 享受同样待遇。

不清理「思考过程」。推理内容不在 ConversationItem 的这几个变体里，走不到这段代码。

不压缩用户消息或助手回复。哪怕一条用户消息粘贴了五万字的需求文档，它也不会被裁——只有工具结果会。

这些「不做」划出了它的能力边界：它是一条按轮龄的、只针对工具结果的、确定性的减量链。所有需要「理解内容」的判断（这份读取是不是过期了、这次搜索是不是空的）都不在它的范围内，要么交给压缩模型，要么交给别的工具层机制。

✓要点小结

  • 触发线是 total_tokens > 窗口 / 2，严格大于，正好 50% 不裁。
  • 轮龄按「用户轮次」从尾往前数，最近 3 轮保护，10 轮以上硬清空。
  • 3 到 9 轮之间，内容超过 4,000 字符才裁成「头 1,500 + 分隔符 + 尾 1,500」，且幂等。
  • 只改请求副本：磁盘不变、/context 不变、下一轮重新裁、缓存从裁点失效。
  • 只处理工具结果；过期读取、空搜索、思考过程都不在范围内。

Claude Codeclaude-code 距上条助手消息 > 60 分钟 时间 + 白名单工具 整条清空，保留最近 5 条 另有 cache_edits 路径不动本地

表注：Grok Build 见本节 permalink；dsh 见 compaction-tool-result-pruner/src/config.ts；omp 见其 prune 实现；opencode v1 见 compaction.prune（默认 false）；Claude Code 为 v2.1.88 源码，时间触发路径默认 disabled。

分叉一：触发时机决定「这是常态还是应急」。Grok Build 用 50% 这条线，意味着它只在会话过半后启动；DeepSeek Harness 更靠后，必须等压缩被确认后才跑裁剪器，低于压力的会话一个字节都不动；opencode v1 更晚，在任务循环退出后异步跑；Claude Code 的时间路径则是「缓存已经冷了，不如顺便清掉」。四种时机对应四种心态：Grok Build 是「提前削峰」，dsh 是「先削峰再决定要不要摘要」，opencode 是「收尾时打扫」，Claude Code 是「反正缓存没了」。

分叉二：选择维度决定「谁被牺牲」。按轮龄选，牺牲的是「旧但可能仍重要」的内容；按单条大小选（dsh），牺牲的是「长但可能是唯一副本」的内容；按语义选（omp 的 superseded / useless），牺牲的是「已经被更新版本取代」的内容，这一种最精准，但需要工具层配合打标记。Grok Build 的代码里没有任何语义判断，它不知道一条结果是否过期——这是它和 omp 最大的差距。

分叉三：预算下限决定「值不值得裁」。omp 要求总节省 ≥ 20,000 token 才动手，opencode v1 要求可擦除量 > 20,000；Grok Build 没有这个下限，一条 4,001 字符的结果被裁到 3,020，净省 981 字符（约 245 token），也照裁。对小结果来说，这次裁剪的收益可能还不如它造成的缓存失效代价。Grok Build 用 50% 触发线间接控制了这个问题：能走到这一步，说明总量已经很大，单条收益小也不再计较。

分叉四：可恢复性决定「敢裁多狠」。dsh 敢把中间 3,000 多个码点直接换成一句标记，因为原始事件永久在 append-only 日志里，一个 seq 就能找回来；opencode 敢擦，因为只打了个时间戳，序列化时才显示占位符。Grok Build 敢硬清空，是因为它只改副本——磁盘上的完整历史还在，下一轮重建请求时又可以看到原文（虽然还是会被裁）。三种「敢」建立在三种不同的保险上，但只有 dsh 和 opencode 给了模型一条「按需找回」的路。

还有一个不在表里的对照：Codex 没有这一层。它的零模型减量只有两类——写入历史时按 TruncationPolicy 截断工具输出，以及压缩重试时删除最旧条目（remove_first_item，会同步移除配对的另一半）。前者是「进来时就裁」，后者是「压不下去才删」，中间没有「按轮龄打扫」这一步。已核实这解释了为什么 Codex 的旧工具结果往往又长又完整：它选择在写入那一刻就控制长度，而不是在发送前回扫一遍。

把四种分叉合起来看，Grok Build 的位置很清楚：它选择了一个简单、确定、不可恢复、但只作用于请求副本的方案。这个方案不需要工具层配合打标记，不需要维护原文索引，也不需要理解内容；代价是它无法区分「过期」与「仍然重要」，只能按年龄一刀切。如果你的任务是「长时间围绕同一批文件反复修改」，轮龄会把仍然有效的读取当成老结果裁掉；如果你的任务是「快速问答、上下文很短」，它根本不会启动。判断它适不适合，只要问一句：你的旧工具结果，是「过期了」还是「只是旧」？

06 · 思考题

三道题，从手算到改参数

Q1

一段历史从新到旧是：user A（最新）→ 12 条工具结果 → user B → 3 条工具结果 → user C → 1 条工具结果。默认配置下，哪些工具结果会被裁？分别落在哪个区间？

提示（不给答案）

从尾部往前扫，先遇到的是 user A 吗？不是——最旧的一条在数组开头。倒序遍历时，先看到的是 C 之后的那条工具结果。

注意 seen_first_user 的作用：第一次遇到 user 时只做标记、不加轮次。所以「C 之后的 1 条」轮龄是 0，「B 与 C 之间的 3 条」轮龄是 1，「A 与 B 之间的 12 条」轮龄是 2。三个都在保护区内——这道题的答案是「一条都不裁」，但你要能说清为什么。

Q2

把 soft_trim_threshold 从 4000 改成 2500，其他不变。会发生什么？请从「单条结果」和「重复调用」两个角度回答。

提示（不给答案）

裁剪后的长度是 1500 + 分隔符 + 1500，约 3,020 字符。把它和新的阈值 2,500 比一比：下一次请求时，这条已经裁过的结果还会不会被判定为「超长」？

如果会，那么每轮都会再进一次裁剪函数。第二次要删的区间是 [1500, 3020 − 1500) = [1500, 1520)——正好是那句分隔符本身。输出变成「头 1500 + 分隔符 + 尾 1500」，与输入等价。所以结果会稳定下来，不会越裁越短；真正损失的是每轮一次的切片开销。

Q3

如果给硬清空的占位符加上「原文件路径」，让模型可以按需重读，会带来什么好处和什么新问题？只改这一处够不够？

提示（不给答案）

好处很直接：模型从「永久丢失」变成「可按需取回」。参考 dsh 的 spill 与 Grok Build 自己的 bash 落盘路径，这个信息在工具层其实已经有了。

新问题有三个：路径本身占多少 token？模型怎么知道该不该重读（它看不到内容，只能盲猜）？重读会新增一次工具调用与一轮往返，这部分成本记在谁头上？

最后想「只改一处够不够」：占位符是 &str 常量，路径是动态的，需要把常量换成格式化的字符串；还要保证每条工具结果都知道自己的落盘位置；而 ConversationItem::ToolResult 里是否带着这个信息，是另一个要查的问题。
