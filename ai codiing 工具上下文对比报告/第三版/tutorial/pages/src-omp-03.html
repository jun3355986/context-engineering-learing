snapcompact 把历史渲成图

如果模型读一张密集排版的图，比读同样长度的文字更省 token，那么「压缩」这件事就不一定要写成摘要。snapcompact 把被丢弃的历史渲染成位图帧，让视觉模型直接读图，全程不调用 LLM。它激进、可测量、也只对能读图的模型成立。

  3. 算出 80 帧、每帧 5 024 token 的上界，并说出这个常量为什么偏保守。
  4. 说明帧如何「每次重建上下文都重新挂回」，以及多次压缩时归档为什么会被重渲。

读之前

这一节讨论的是「历史 → 图片」这一条极端路线，不是「图片进上下文」的常规用法。它成立的前提有两个：模型能读图，且图片计价比等价文字便宜。两个前提任一不成立，方法链会自动跳过它（第 1 节的闸门）。

01 · 功能说明

把「摘要」换成「一叠扫描件」

snapcompact 的输入是被丢弃的历史消息，输出是一份 CompactionResult：一段很短的摘要文本、若干 PNG 帧、以及一个 preserveData.snapcompact 归档对象。已核实它不调用任何模型，纯本地渲染，所以属于方法链里的「便宜且快」的一档。

它没有「理解」历史，只是把历史排版、光栅化、附上一句「这是归档的第 N 帧」。理解发生在之后——模型读图的时候。

管线可以拆成六步：

① 序列化。serializeConversation() 把消息转成纯文本，工具结果截到固定长度，思考块按选项省略。目的不是压缩，而是把结构化消息变成「可以排版的一篇文章」。

② 接上旧归档。如果上一次压缩也是 snapcompact，会把旧归档保留的源文本取出来，拼在新历史前面，作为一篇连续的稿子。已核实所以多次压缩不是「在图片上再压一层」，而是「把旧稿和新稿合并后重新排版」。

③ 选形状。resolveShapeForText() 先按模型 id 选变体，再做可读性检测；如果默认字体渲不全（缺字），退到 silver 网格；如果文本以中日韩宽字符为主，也优先 silver。已核实

④ 分页。planArchive() 把长文切成「头部文本 + 若干帧 + 尾部文本」，中间区域做 foveation：靠近两端用高质量帧，中间用更密的低质量帧。已核实

⑤ 渲染。每个计划页调用 renderSnapcompactPng()（Rust 原生实现），返回 base64 PNG 与行列数。已核实

⑥ 生成摘要文本。用模板把帧数、列数、行数、是否截断、文件清单填进去，得到一条很短的「归档说明」。已核实这条说明才是普通文本；真正的历史在帧里。

这套设计的核心赌注是「每 token 能装多少信息」。普通摘要用自然语言重写历史，信息密度取决于模型写得好不好；图片把原始字符直接印上去，密度取决于字号与网格。snapcompact 的 packages/snapcompact/research/ 里有一组可复现实验，用 SQuAD 抽取式 QA 的 recall / F1 衡量「读图后还能答对多少」，并把这个指标除以 provider 的计费 token。已核实帧形状表就是这些实验的结论，不是拍脑袋。

// 显式指定变体：直接用，但仍要按宿主支持的最大边收缩
export function resolveShape(model?: ShapeTarget, variant?: ShapeVariantName | "auto"): Shape {
    if (variant && variant !== "auto") return priceShape(fitHostImageEdge(SHAPE_VARIANTS[variant], model), model);
    // 否则按模型 id 选「评测赢家」，没测过的模型按 API 家族兜底
    const ideal = model?.id ? idealShapeVariant(model.id) : undefined;
    const base = SHAPE_VARIANTS[ideal?.variant ?? FAMILY_VARIANT[apiFamily(model?.api)]];
    // 有些模型行能读更大的帧且不加价，就覆盖 frameSize
    return priceShape(fitHostImageEdge(ideal?.frameSize ? { ...base, frameSize: ideal.frameSize } : base, model), model);
}

04 · 逐段解读

四个决定：多大、几帧、给谁看、怎么挂回去

第 1 段　形状：为什么不能所有模型用同一张图

图片的计费方式因 provider 而异。Anthropic 按视觉 patch 数计费，有 4 784 的上限；Gemini 3.x 对每张图收固定 1 120 token，与像素无关；OpenAI 的 patch 计费按面积比例。已核实同一张 2 048 px 的图，在 Gemini 上「加量不加价」，在按面积计费的模型上就贵得多。

所以 MODEL_VARIANTS 是一张「模型行 → 变体」的表：Claude 用 11on16-bw（Opus 4.7+ 与 Fable/Mythos 用 1 932 px 高分辨率），Gemini 用 8on22-bw 加 2 048 px，GPT/Codex 用 8on22-bw 的 1 568 px，Kimi 与 GLM 各有自己的选择。已核实这些不是「兼容性配置」，而是评测得出的「每美元能读回多少信息」。

还有一道 fitHostImageEdge()：如果宿主目录声明的 image-max-edge 比变体的 frameSize 小，就缩到上限。已核实否则一张超出边长的图会被 provider 静默缩放，字变小、可读性反而下降。

resolveShapeForText() 在此之上加了两条回退：默认字体渲不全所有字符 → 换 silver；CJK 宽字符占比 ≥ 25% 且至少 8 个 → 也换 silver。已核实第二条对中文用户很关键：等宽点阵字体渲染中文会缺字或糊成一团，必须先换字体再渲。

第 2 段　帧数与截断：80 是一个上界，不是目标

planArchive() 按形状算出每帧能装多少字符，再把文本切成「头部 + 帧 + 尾部」。maxFrames 先取调用方给的值，再与 MAX_FRAMES_DEFAULT 取小——调用方只能调低，不能调高。已核实

为什么要封顶？三个约束叠在一起：单请求图片数量上限（约 100 张）、每帧的视觉 token（高分辨率约 5 000）、以及请求体的 base64 字节预算（DEFAULT_FRAME_DATA_BYTES_BUDGET = 3 MB）。已核实80 帧 × 5 024 token ≈ 402k，已经是一个 200k 窗口的两倍；再多的帧，模型也放不下。

超过预算时从最旧的帧开始丢，丢掉的字符数记进 truncatedChars，摘要模板里会写「有多少字符被截断」。已核实这与文本摘要的「渐进遗忘」是同一个方向：越旧越先丢。

第 3 段　多次压缩：重渲，而不是叠图

第二次 snapcompact 不会「在旧图上再盖一层」。它把旧归档的 text（完整源文本）取出来，拼在新序列化文本前面，然后整体重新分页、重新渲染。已核实所以帧的数量与内容每次都会变，旧帧被新帧取代。

如果上一次是文本摘要（不是图片归档），就把摘要印在归档开头，标成 [Summary of earlier history]，再放新内容。已核实这保证了「从 soft 切到 snapcompact」不会丢历史。

代价是：每次压缩都要重渲全部历史。归档越长，渲染越慢、字节越多。源码里对「帧归档本身成为超预算成本」有专门的救援路径（#rescueSnapcompactFrameOverflow），会把归档按阈值重新渲成更少的帧。已核实

第 4 段　重挂：为什么每次重建都要塞回去

帧不是「一次性附件」。它们存在 CompactionEntry.preserveData.snapcompact 里，每次 buildSessionContext() 重建上下文时，由 snapcompactHistoryBlocksForContext() 转成 content blocks，塞进那条摘要消息。已核实这样做的原因很直接：模型每次请求都要重新看一遍归档，帧必须每次都在。

这也解释了为什么摘要文本里要写清「共几帧、每帧几列几行」：模型需要知道图里是什么布局，才能定位信息。文本是图的说明书。

第 5 段　三种计价，三种帧策略

「每帧 5 024 token」是一个保守上界，不是所有模型的真实账单。三种主流计价方式差别很大：

读者 计价方式 所选形状 80 帧的近似账单
Claudeanthropic视觉 patch，封顶 4 78411on16-bw，高配 1 932 px≈ 400 000 token（按上界）
Gemini 3.xgoogle每图固定 1 1208on22-bw，2 048 px≈ 89 600 token
GPT / Codexopenai按面积比例8on22-bw，1 568 px取决于 patch 面积

表注：形状与尺寸来自 MODEL_VARIANTS（snapcompact.ts#L383-L401）；Gemini 固定计费的注释在同文件 L394；账单列是按公开计费方式做的估算，不是源码常量。

这张表解释了两个设计选择。第一，为什么 Gemini 用 2 048 px：固定计费下，同样的钱塞进更多字符是纯赚。第二，为什么 FRAME_TOKEN_ESTIMATE 取 5 024 而不是平均值：它要覆盖最贵的形状，否则溢出守卫会低估归档大小。已核实对 Gemini 来说，这个上界高估了约 4.5 倍——保守，但不会让请求超窗。

还有一个容易忽略的成本：base64。80 帧 × 约 170 KB ≈ 13.6 MB，超过 DEFAULT_FRAME_DATA_BYTES_BUDGET = 3 MB 四倍多。已核实所以真正发出去时，帧会被字节预算裁掉一大半；MAX_FRAMES_DEFAULT 只是「归档能存多少」，不是「一次能发多少」。两个上限必须分开看，否则会得出「80 帧都能进请求」的错误结论。

第 6 段　五类失败模式

snapcompact 的失败不是「报个错」那么简单，每一类都要有对应的兜底：

模型不能读图。闸门直接判不可用，方法链跳到下一个。这是最干净的一类，因为发生在执行前。

字体渲不全。resolveShapeForText() 先做 scanRenderability()，不安全就换 silver；silver 也不安全就只能用默认形状硬渲，字符会变成占位方块。已核实这是「能跑但质量下降」，不会报错。

归档自己超预算。每次压缩都重渲全部历史，帧数增长可能超过恢复带；omp 用 #rescueSnapcompactFrameOverflow() 按阈值重算帧预算再渲一遍。已核实这是方法链里少见的「同一方法内部再试一次」。

请求体字节超限。413 错误会设置 excludeMediaMethods，后续压缩排除 snapcompact，避免「用更多图片救图片超限」。已核实

provider 图片数量上限。发送前的图片预算裁剪会按 provider 的数量限制移除超出部分，替换成 [image omitted: provider image limit]（session/provider-image-budget.ts）。已核实这意味着模型可能看到「摘要说有 40 帧，实际只有 20 帧」——摘要文本里的帧数是生成时的，不是发送时的。

最后一类最值得警惕：它不会失败，只会让模型「以为自己在读完整归档」。评估 snapcompact 的效果时，必须把「发送时裁剪」算进去，否则测的是「归档质量」，不是「模型实际看到的质量」。

✓要点小结

  • snapcompact 把被丢弃的历史渲成 PNG 帧，全程不调用 LLM；前提是模型能读图。
  • 形状按模型行选择（Claude 11on16、Gemini 8on22@2048、GPT 8on22@1568），再做字体可读性与 CJK 回退。
  • 帧上限 80，每帧保守按 5 024 token 估；超限从最旧丢，记 truncatedChars。
  • 多次压缩是「合并源文本后整体重渲」，不是叠图。
  • 帧存在 preserveData，每次重建上下文都重新挂回摘要消息。

05 · 与其他 agent 的差异

图片在四家里的四种命运

大多数 agent 把图片当「输入的一种」，只在预算紧张时驱逐；snapcompact 反过来，把图片当「历史的存储格式」。这个方向差异，决定了四家在多模态上的策略完全不同。

三点对照：

一是方向。pi 与两家 opencode 都在「减少图片」：估算、驱逐、序列化成占位文本。snapcompact 在「增加图片」，用图片替换文字。前者假设文字更便宜，后者假设在特定模型上图片更便宜。两个假设都成立，只是适用面不同。

二是可逆性。snapcompact 的归档里保留了完整源文本 text，所以每次压缩都能重渲；但它占的存储不小（一张 PNG 约 170 KB，80 帧约 13 MB）。opencode 的做法只留一行占位，存储几乎为零，代价是模型永远看不到图。

三是失败模式。snapcompact 最怕两件事：模型不支持图片（闸门直接跳过），以及帧归档本身超预算（需要 #rescueSnapcompactFrameOverflow 重渲更少帧）。文本摘要没有这两类失败，但它有另一类：摘要写丢了关键约束。没有哪种方法在所有维度上占优。

80 × 5 024 = 401 920。这已经超过 200k 窗口。

MAX_FRAMES_DEFAULT 是「归档能存多少」，不是「一次请求能带多少」。真正的裁剪发生在发送时的字节预算与调用方的 maxFrames。

Q2

同一个会话先做了一次 soft 摘要，再做 snapcompact。第二次的归档开头会是什么？如果反过来，先 snapcompact 再 soft，soft 能看到图片吗？

提示（不给答案）

看 includedPreviousSummary = !hasPreviousText && !!previousSummary：没有旧归档源文本、但有旧摘要时，把摘要印在 [Summary of earlier history] 后面。

反过来，soft 的摘要请求是纯文本序列化；图片在 serializeConversation() 里通常变成占位文本。所以「图上摘要」不会再被读成图，除非新方法显式解码。

Q3

你的模型每张图收固定 1 120 token，且能读 2 048 px。你会把帧调大还是调小？如果模型按面积计费呢？

提示（不给答案）

固定计费时，同一价格下塞进更多字符是纯赚——这正是 Gemini 用 8on22-bw + 2 048 的理由。

按面积计费时，像素翻倍价格也大致翻倍，收益取决于「每像素能读回多少字」。这就是 packages/snapcompact/research/ 里 recall / F1 ÷ 计费 token 那组实验要回答的问题。

别忘了宿主上限：fitHostImageEdge() 会把超过 image-max-edge 的帧缩回去。
