失败恢复：溢出、压缩失败与兜底

压缩是窗口快满时的最后一根绳子，但绳子自己也会断：压缩请求本身也要装下待压缩的历史。本章按一次失败发生的时间顺序拆开：怎么识别溢出、压不动时删什么、连续失败什么时候该停、以及哪三种情况再怎么压也没用。

  • 约 18 分钟
  • 1 张状态机
  • L2 → L3

读完你能做到

  1. 区分“主动压缩”与“溢出后恢复”，并说出两者各自允许重试几次。
  2. 给定一次压缩失败，判断下一步该删最旧、砍整组、换模型，还是直接停。
  3. 列出无法再压缩的三种情况，并为每种给出一个可操作的兜底动作。

01 · 一次真实的卡死

“它转了很久，然后什么都没了”

场景 · 三次重试之后，只剩一个转圈

周五下午，Agent 跑到第 62 轮。屏幕上先出现一行 “context length exceeded”，接着自动压缩启动；几秒后，同一行错误又出现一次。界面显示“正在压缩”，然后是第二次、第三次。十分钟后，用户点了取消，又点了 /clear。四十多分钟的排查记录没了——不是被压缩掉的，是从来没被写进可恢复的地方。

这个下午包含了失败恢复的全部难点。第一，恢复动作本身也要花上下文：压缩要把待压缩的历史再发一遍，这段历史可能已经超窗。第二，重试不一定改变结果：同样的 payload 再发一次，必然再超。第三，失败会叠加：一次压缩失败后，下一轮请求仍然超窗，于是再触发一次注定失败的压缩，形成循环。第四，用户看到的是“在忙”，不是“失败了”：没有显式的失败状态，人只会等。

失败恢复不是“再试一次”，而是“在一个更小的预算里，重新决定删什么、保什么、什么时候放弃”。

所以评价一个实现的恢复能力，不能只看“有没有重试”。要看四件事：它认不认得溢出、它每次重试改变了什么、它在第几次之后停止、以及停止时留下了什么状态。这四件事分别对应 2.1、2.2、2.4、2.5 四小节。

最贵的失败不是报错，是静默

取消、失败、正在压缩，是三种不同的状态。把它们混成一个“加载中”，用户就无法判断该等、该重试，还是该开新会话。Grok Build 把取消单独命名成 compact cancelled，dsh 给手动压缩定义了 busy / cancelled / changed / summary / commit / persistence 六个错误码，都是为了不把“失败”说成“稍等”。

02 · Codex 主线

先删最旧，再试一次

Codex 的恢复逻辑很短，短到可以一句话说完：压缩请求遇到 ContextWindowExceeded 时，如果待压缩输入不止一条，删掉最旧一条、重置重试计数、再试；如果只剩一条，就把总用量标记为“满”，返回错误。compact.rs#L359-L371 已核实 短，但它把本章的四个问题都碰到了。

2.1 识别：本地估算到线，还是服务端拒绝

溢出的信号有两种。一种是主动的：本地估算当前用量已到线，提前压缩。Codex 用两把尺子：整段线是窗口 × 95%，范围线默认取 min(模型声明的 auto_compact_token_limit, 窗口 × 90%)。openai_models.rs#L393-L395 openai_models.rs#L526-L540 已核实

另一种是被动的：请求已经发出去，服务端返回上下文超限。被动信号更可靠，因为它不依赖本地估算；但它来得更晚——此时这一轮已经失败，恢复只能“压缩后重发”。主动信号能避免一次失败，代价是估算偏保守时会过早压缩，白花一次摘要钱。

为什么两种都要有。本地估算用字节数除 4，对中文、代码、JSON 都会偏truncate.rs#L89-L98 已核实；只靠它，要么过早压，要么漏判。服务端拒绝是真相，但每次都是一次失败。两者配合，才是“平时靠估算、卡住靠错误码”。

2.2 缩小：为什么删的是“最旧一条”

同一个 payload 再发一次，必然再超。能改变的只有输入大小，所以重试前必须先删。Codex 删最旧一条，源码注释给了两个理由：保留基于前缀的缓存，同时让最近消息不受影响。

为什么不是删最新。最新消息通常包含这一轮的任务指令、最近的错误、刚改的文件路径。删它等于把“现在要做什么”丢掉，即使压缩成功，模型也不知道下一步干什么。为什么不是删一半。删一半会让输入大小骤降，但也会让摘要失去中段上下文；逐步删一条，可以在“刚好装下”的位置停下，信息损失最小。

代价是每重试一次就永久少一条历史。如果超窗的是一条不可分割的巨型消息（比如一次 80k 的测试日志），删到只剩它时就没有退路——这正是 3.3 节“无法再压缩”的第二种情况。

2.3 分类：哪些错误值得重试

Codex 把压缩失败分成几类，处理方式不同：

  • 中断、取消、会话预算耗尽、响应不完整：直接返回，不重试。这些不是“再试一次就能好”的错误，重试只会浪费钱。
  • 普通 provider 错误：按退避重试。网络抖动、限流属于这一类。
  • 轮后压缩失败：只记警告，已经完成的那一轮照样保留。因为压缩是“为下一轮做准备”，这一轮的工作不该被回滚。
  • 后台 / 投机压缩失败：直接丢弃结果，但已经发生的 token 仍然计费。

这四类可以在 compact.rs#L338-L388 与 async_compaction.rs#L125-L140 看到。已核实

为什么“取消”不能重试。取消是用户的意图，不是系统的故障。把取消当失败重试，会让用户按了停止却停不下来。这也是为什么“区分取消与失败”在恢复设计里不是文案问题，而是语义问题。

2.4 熔断：Codex 这一版没有

本快照里，Codex 没有会话级的“连续失败熔断”。每次请求到线，它仍会尝试压缩；压缩失败、删最旧、再失败，直到只剩一条才报错。推断1

没有熔断的直接后果是：如果某条历史注定压不动，用户每一轮都会再付一次压缩请求的钱，再等一次超时。代价不在 token 上，在延迟和可预期性上——用户不知道要等多久，也不知道等完会不会好。

有熔断的实现（Claude Code 连续 3 次）把“注定失败”变成“立刻告诉用户”。代价是熔断后即使环境已经变化（比如换了模型、删了大文件），本会话也不会再自动尝试，必须手动 /compact 或开新会话。这是“少花钱”与“不错过恢复机会”的取舍。

2.5 一致性：内存换了，检查点也要写

压缩成功后，Codex 先从空历史重建：放回选中的用户消息，最后放摘要；然后 replace_compacted_history 把重建后的历史装回内存，并向 rollout 追加一条 CompactedItem 检查点。session/mod.rs#L4321-L4356 已核实 源码还强调：压缩流中途的条目改成“成功后一次性提交”，避免半提交。

为什么顺序不能反。模型下一步只读内存；检查点是为了“以后还能恢复”。如果先写检查点、再换内存，中途崩溃就会出现“磁盘上已经压缩、内存里还是旧历史”的短暂不一致。反过来，先换内存、再写检查点，崩溃时最多是“内存前进了一步、磁盘还没记”，可以用下一条检查点兜住。代价是这套操作必须尽量原子：压缩流失败时不能提交一半，否则检查点和内存会对不上。

Q没有傻问题

问：删最旧一条之后，为什么“重置重试计数”？那不是会无限重试吗？

答：重置的是“这一次压缩内部的重试计数”，因为每次重试的输入已经变小了，不该沿用上一次的失败次数。它仍然受“只剩一条就报错”的终止条件约束，所以不会无限。真正可能无限的是外层：下一轮请求又超窗，又触发一次新的压缩。这就是需要熔断的地方。

✓要点小结

  • 溢出有主动（估算到线）和被动（服务端拒绝）两种信号，前者省一次失败，后者更可靠。
  • 重试前必须改变输入：Codex 删最旧一条，既缩小输入又尽量保住缓存前缀。
  • 取消、中断、预算耗尽不重试；只有“再试可能好”的错误才退避重试。
  • 本快照没有会话级熔断，注定失败的压缩会被反复触发，代价是延迟与可预期性。
  • 内存替换与检查点写入要尽量原子，失败不能半提交。

03 · 恢复路径

五个决策，三种绝境

把各家实现放在一条时间线上，一次恢复要连续做五个决策。任何一个决策做错，后面的重试都只是把错误放大。

  1. 识别：这是溢出，还是限流、超时、载荷过大？误判会把“重发必失败”的错误当成“等一下就好”。
  2. 缩小：删最旧、砍整组、降预算、剥图，还是换一个更大的窗口模型？
  3. 重试：同模型重发，还是换模型？重试几次？每次之间等多久？
  4. 放弃：第几次之后停？停了之后本会话还允不允许再自动压缩？
  5. 收尾：内存、日志、文件、工具副作用，哪些要回滚，哪些要保留？

3.1 无法再压缩的三种情况

“压缩失败”不等于“无法压缩”。前者是这一次调用出错，后者是结构上再怎么压也装不下。后者必须被单独识别，否则会陷入“失败—重试—再失败”的循环。各家文档里反复出现的，是下面三种4。

第一种：固定前缀本身就超窗。系统提示词、工具定义、规则文件、输出预留加起来已经接近或超过窗口。压缩只替换对话历史，动不了这些固定开销。Grok Build 明确把“系统提示词 + 工具定义逼近窗口”列为压缩无能为力的情况；dsh 的限制清单第一条也是“系统提示词 / 工具 / 会话前缀本身逼近窗口”。compaction-basic/README.md#L235-L246 已核实

怎么识别：把历史清空、只发固定前缀，仍然超窗；或者压缩后总量几乎没降。还能做什么：减少工具数量、把大工具表改成按需加载、缩短规则文件、换更大窗口的模型。这些都不是压缩能解决的，应该直接报给用户，而不是继续重试。

第二种：单个不可分割的单元超窗。一条 80k 的工具结果、一条超长的用户消息，或者一个无法再拆的工具单元。压缩的切点只能落在消息边界上，不能把一条消息切成两半（切了也不再是原来的工具结果）。Grok Build 的 full-replace 明确不能拆单元；dsh 把“单个不可分割的非工具节点”和“工具单元里不可裁剪的剩余部分”分别列为两条限制。compaction-basic/README.md#L243-L246 已核实

怎么识别：删到只剩这一条时仍超窗；或者切点算法反复回到同一个位置。还能做什么：在进入上下文之前就截断或落盘（第 13 章），把原文留在文件里；把这条消息拆成多条再发；或者直接放弃这一轮，让用户决定。推断

第三种：压缩本身不可用或不可完成。没有配置摘要模型；删到只剩一条后压缩请求仍超窗；摘要输出被 maxTokens 截断（隐藏推理吃掉了预算）；或者压缩锁没有释放，后续请求全被挡住。dsh 把“没有可用模型写摘要且还没有任何已路由请求”列为第四条限制；opencode v1 在压缩自身再溢出时直接 stop，没有第二次兜底。

怎么识别：错误发生在压缩请求内部，而不是主请求；日志里有“summary”“max tokens”“busy/lock”一类字样。还能做什么：换一个便宜的摘要模型；给摘要请求单独设更大的输出预算；清理孤儿锁；或者退回“不压缩、只裁剪”的路径（第 14 章）。

别把三种绝境混成一种

固定前缀超窗要“减固定开销”，单元超窗要“在进入上下文前处理”，压缩不可用要“修压缩链路”。三者对应的动作完全不同。把它们都归成“压缩失败，重试三次”，就是把一个结构问题当成一次网络抖动。

3.2 熔断：连续几次之后该停

Claude Code 的选择是连续 3 次自动压缩失败后熔断，本会话不再尝试。MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3，autoCompact.ts#L257-L350 源码 v2.1.88 另外还有递归保护：当请求来源是 compact 或 session_memory 时，禁止再触发自动压缩，避免“压缩请求触发压缩”的套娃。

为什么是 3 而不是 1。1 次太脆：一次网络抖动、一次临时限流就会让整个会话失去自动恢复能力。3 次能过滤掉瞬时错误，又不会让用户在注定失败的循环里等太久。代价是第 3 次仍然要付钱；如果前两次是瞬时错误、第三次是真正的结构问题，这三次都是白花的。

不同工具的“停”法不一样：

  • 计数熔断：Claude Code 连续 3 次失败后停，本会话不再自动压缩。
  • 次数上限：pi 的溢出恢复只允许一次 compact-and-retry，第二次直接报 “recovery failed after one compact-and-retry attempt”。
  • 进度守卫：omp 要求压缩后必须降到阈值的约 80% 以下才允许续跑；否则尝试本地救援，仍不行就告警并阻止自动续跑。
  • 分类抑制：Grok Build 把失败分成 size / auth / credit / schema / other；size 与 schema 是粘性抑制，只有上下文预算变化才解除，credit 等到一次成功响应才解除。
  • 直接停：opencode v1 压缩自身再溢出就 stop，没有第二次兜底；自动压缩关闭时溢出也直接报错。

3.3 恢复之后：五个一致性检查

压缩成功不等于恢复完成。恢复的目标是“模型看到的历史、磁盘上的日志、实际的文件系统”三者一致。至少要检查五件事。

  1. 内存与检查点同一次提交。Codex 先换内存、再写 CompactedItem；pi 在摘要失败时直接抛错、不写检查点；dsh 只有在 replaceGeneration 前进时才返回重试。已核实 反过来做，就会出现“日志说压了、内存还是旧的”。
  2. 工具调用与结果成对。失败那一轮的 assistant 消息和它的全部工具结果要一起省略，不能留下孤立的结果。pi 的 context_edit 就是先省略“失败的 assistant + 配对结果”，再走压缩。已核实
  3. 文件版本。摘要是压缩那一刻的快照，磁盘可能已经变了。Claude Code 压缩后会重附最近文件，这可能把旧版本内容带回上下文推断；恢复后应重读，而不是信任摘要里的代码。源码 v2.1.88
  4. 副作用不重放。工具可能已经写了文件、发了请求。重试的应该只是模型调用，不是已经成功的工具。这一点各家没有统一文档，实现上通常靠“只重发模型请求”保证。推断2
  5. 计数与预算。删最旧后 Codex 重置重试计数；熔断计数应该在成功后清零，否则一次早期失败会永久缩短本会话的恢复能力。清零时机在源码里没有统一约定，需要按实现核对。推断3

还有一个容易被忽略的收尾：告诉用户发生了什么。压缩成功、压缩失败、取消、熔断，是四种不同的结果。用户需要知道“你的历史被换成了摘要”“这次没压成功，但任务继续”“已停止自动压缩，请手动处理”。静默的成功和静默的失败一样危险：前者让人以为什么都没丢，后者让人以为还在处理。

04 · 七个工具

同一场溢出，七种收场

Codex 已经在主线里拆过。剩下七个工具可以按“第一次失败之后做什么”分成三派：删了再试（Codex、Claude Code、pi、dsh）、换条路再试（omp 先换模型、opencode v2 三级收缩、Grok 分类抑制）、试一次就停（opencode v1）。分野不在“重试几次”，而在“每次重试改变了什么”。

键盘：Esc 关闭；Tab 在弹窗内循环。Claude Code 的结论来自非官方 v2.1.88 源码，只代表该版本。

06 · 设计取舍

为什么有人只试一次，有人试十次

恢复策略的分歧，本质上是对“失败原因”的不同假设。假设是“网络抖动”，就会多试几次；假设是“结构上装不下”，就会尽快停。下面五组取舍，对应五种假设。

取舍一：重试次数多，还是少

多试派：opencode v2 普通重试最多 10 次，omp 的通用重试也是 10 次（退避 500→8000ms），pi 沿用 3 次。少试派：opencode v1 普通错误最多 5 次，Grok 压缩只试 3 次，pi 的溢出恢复只有 1 次。

代价：多试能扛住限流和抖动，但每次重试都要再发一遍历史，成本和延迟线性增长；少试省钱、反馈快，但一次瞬时错误就可能让本可以完成的任务失败。关键不是次数，而是每次重试是否改变了输入或环境：不改变的，多试一次就是多花一次钱。

取舍二：删最旧一条，还是砍整组 / 整轮

逐条派：Codex 删最旧一条，理由是保住前缀缓存、不影响最近消息。整组派：Claude Code 按 API 轮次分组，砍掉最旧的一组；dsh 选“最大的、平衡的头部区间”；pi 省略失败的 assistant 与配对结果。

代价：逐条删粒度细，能刚好卡在“装得下”的位置，但可能留下半组工具调用（如果删的那条正好是调用或结果）；整组删保证语义完整，但一次可能删掉很多还有用的内容，压缩后剩余空间忽大忽小。多数实现选择整组，是因为“历史合法”比“少删一点”更重要。

取舍三：先换模型，还是先压缩

先换模型：omp 在溢出或输出未完成时，如果配置了更大窗口的同族模型，先切模型重试，不压缩。先压缩：Codex、Claude Code、pi、dsh 都是先压缩，压缩不动才考虑别的。先裁剪：dsh 在压缩前先跑可选 pruner，pi 先把失败的那一组省略。

代价：换模型最快、信息损失最小，但更贵，而且行为会漂移——同一个任务换模型后可能给出不同风格的修改；先压缩省钱，但会丢细节；先裁剪最便宜，但只能省一部分。omp 的顺序（换模型 → 压缩 → 本地救援）是“用钱换信息”，Codex 的顺序是“用信息换钱”。

取舍四：熔断，还是一直试

熔断派：Claude Code 连续 3 次失败后停；pi 第二次溢出直接报错；opencode v1 压缩再溢出就停。一直试派：Codex 本快照没有会话级熔断，每次到线都会再试；Grok 用分类抑制而不是计数熔断，size / schema 类错误只有预算变化才解除。

代价：熔断让用户快速看到“这条路走不通”，但可能在环境已经变化（换了模型、删了大文件）后仍然拒绝尝试；一直试不会错过恢复机会，但会在注定失败的循环里反复烧钱、拖长等待。分类抑制是中间路线：不是“失败太多次”，而是“这类失败重试也没用”。

取舍五：失败后继续跑，还是立即停

继续派：dsh 在“替换之前失败”时记 warning，带着完整超预算历史继续，不阻断用户请求；omp 在压缩后仍高于水位时尝试本地救援，救援失败才阻止续跑。立即停派：opencode v1 压缩失败直接 stop；Grok 重试 3 次仍失败就报错。

代价：继续跑可能让用户把这一轮做完，但下一次请求大概率还会溢出，等于把失败推迟一轮；立即停让用户马上知道，但可能打断一个其实只差一次工具调用就能完成的任务。判断标准是“剩下的工作是否还需要模型调用”：如果这一轮已经是最后一次，继续跑是划算的；如果后面还有十轮，继续跑只是把问题延后。

还有一组横切的取舍：失败时保留已落地的裁剪，还是全部回滚。dsh 在 pruner 已落地但摘要失败时，从裁剪后的 surface 继续，不丢弃已经获得的削减；pi 的摘要失败则不写检查点。前者省一次重复劳动，后者保证“要么全成、要么全不动”。选哪个，取决于裁剪是否可逆、以及用户能否接受“历史已经变短但没有摘要”。

07 · 小测验

三道题，检验你会不会收场

Q1

压缩请求自己超窗。为什么“删最旧一条”比“删最新一条”好？如果删到只剩一条仍然超窗，Codex 会怎么做？

解析

删最旧一条既缩小了输入，又尽量保住基于前缀的缓存，同时不影响最近消息——最近消息通常包含这一轮要做什么、刚改了什么。删最新会丢掉当前任务指令，即使压缩成功，模型也不知道下一步。删到只剩一条仍超窗时，Codex 不再重试，把总用量标记为“满”并返回错误，因为输入已经不可再缩小。见2.2 缩小。

Q2

Claude Code 连续 3 次自动压缩失败后熔断。第 4 次如果其实能成功，会怎样？这个设计省下了什么，又牺牲了什么？

解析

本会话不会再自动尝试第 4 次，即使它本可以成功；用户必须手动 /compact 或开新会话。省下的是“每次请求都打一次注定失败的压缩”的钱和等待，也避免用户在无限循环里以为程序还在工作；牺牲的是“环境已经变化后自动恢复”的机会。代价由用户承担：他要知道有这个手动入口。见3.2 熔断。

Q3

说出三种“无法再压缩”的情况，并为每种给出一个和“继续重试压缩”不同的动作。

解析

一，固定前缀（系统提示 + 工具 + 规则 + 输出预留）本身超窗：应减少工具、按需加载、缩短规则或换更大窗口的模型，压缩动不了前缀。二，单个不可分割单元超窗（一条巨型工具结果或超长消息）：应在进入上下文前截断或落盘，或把消息拆开，切点无法把它切成两半。三，压缩本身不可用或不可完成（无摘要模型、摘要请求仍超窗、摘要被 maxTokens 截断、锁未释放）：应换摘要模型、单独给摘要输出预算、清理孤儿锁，或退回只裁剪的路径。见3.1 无法再压缩的三种情况。

工具弹窗 · claude-code

Claude Code

两条恢复路径。主动路径是 autocompact；被动路径是 reactive compact：API 返回 413 / prompt-too-long 时先把错误扣住，压缩成功后用 reactive_compact_retry 重试本轮，每轮只允许一次。压缩请求自身超窗时，按 API 轮次分组砍掉最旧一组，最多 3 次。

关键参数
MAX_PTL_RETRIES = 3；MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3；reactive compact 每轮 1 次；输出上限 8,000 被截断时升级到 64,000 重试一次。源码 v2.1.88
设计意图
被动路径把“失败”变成“一次内部重试”，用户看不到 413；熔断避免每次请求都打一次注定失败的压缩。代价是每轮只能被动恢复一次，且熔断后需要手动介入。递归保护（压缩请求内部禁止再压缩）防止套娃。
来源
autoCompact.ts#L257-L350、query.ts#L1150-L1183

官方文档只描述“溢出时压缩并重试”，没有给次数；源码更细。结论只代表非官方 v2.1.88 源码。两者一致

工具弹窗 · pi

pi

溢出时先做一次 context_edit：把失败的 assistant 与配对的工具结果一起省略，再跑 autoCompaction("overflow")。整个会话只允许一次 compact-and-retry，第二次溢出直接报 “recovery failed after one compact-and-retry attempt”。

关键参数
溢出恢复 1 次（_overflowRecoveryAttempted）；摘要重试沿用 maxRetries = 3；摘要失败（error / length / 尝试调工具）直接抛错，不写检查点。已核实
设计意图
先省略失败那一组，保证重试时历史里没有孤立工具结果；只给一次机会，避免在同一条超长历史上反复烧钱。代价是遇到瞬时错误也只剩一次机会，且没有本地救援层。
来源
agent-session.ts#L3007-L3077、compaction.ts#L585-L593

用户或扩展取消时保留已发生的编辑，但不追加 compaction；手动压缩会先 abort 当前回合，成功后不续跑被打断的那一轮。

工具弹窗 · omp

oh-my-pi

恢复顺序是“先升级模型，再压缩”：溢出或输出未完成时，若配置了更大窗口的同族模型，先切模型重试，不压缩。必须压缩时跳过 handoff，走 overflow 方法链，成功后 agent.continue()。

关键参数
恢复带宽 COMPACTION_RECOVERY_BAND = 0.8；输出未完成连续恢复上限 3 次；载荷拒绝需确证 token 溢出才压缩，本地估算有 ≥10% 余量时只告警；通用重试 10 次，退避 500→8000ms。已核实
设计意图
“进度守卫”要求压缩后必须降到阈值 80% 以下才允许续跑，否则先本地救援（更小帧、elide 到 artifact、丢图），仍不行就阻止自动续跑。代价是逻辑复杂，且换模型会让行为漂移。
来源
session-maintenance.ts#L328、compaction.md#L113-L150

413 不会被自动当成 token 溢出；这是为了避免“把网关的载荷限制误判成上下文超限”，代价是判断多一步。

工具弹窗 · opencode-v1

opencode v1

普通错误最多重试 5 次，退避 2s 起、带抖动；ContextOverflowError 不重试，转成压缩信号。自动压缩关闭时溢出直接报错并置 idle。压缩自身再溢出则写 “Session too large to compact…” 并 stop。

关键参数
RETRY_MAX_RETRIES = 5、初始 2000ms、因子 2、抖动 0.25、无 retry-after 时单次上限 30s；DOOM_LOOP_THRESHOLD = 3。已核实
设计意图
它把“压缩失败”当成终局，而不是再试一次：没有再收缩预算、没有第二次兜底。实现简单、行为可预期，代价是用户更早看到失败，长任务更容易中断。
来源
session/retry.ts#L26-L31、session/compaction.ts#L450-L459

连续 3 次相同工具 + 相同输入会触发 doom_loop 权限询问（默认 ask），这是另一条防循环机制，和压缩熔断不是一回事。

工具弹窗 · opencode-v2

opencode v2

溢出只在“还没产出任何输出”时触发 compact({reason:"overflow"})，每步一次；成功则新建 assistant 消息、重建上下文重发。压缩内部有自己的预算收缩阶梯：0.7 → 0.5 → 0.35，最后发 compaction.failed。

关键参数
普通重试最多 10 次、单次间隔上限 10s、retry-after 夹到 ≤15 分钟、超时类 3 次；输出截断续跑最多 2 次（第 3 次 output-limit）；不完整流续跑 1 次。已核实
设计意图
三级收缩是“在不换模型的前提下，反复把预算调小再试”，比一次失败就停更有韧性；代价是每次收缩都要重发历史，最坏情况要付三次压缩成本。
来源
runner/llm.ts#L265-L271、compaction.ts#L403-L455

v2 是 beta（v2.0.29）；压缩失败与中断也计费，评估成本时不要漏掉 UsageRecorded source:"compaction"。

工具弹窗 · grok-build

Grok Build

三条恢复路径，按代价从低到高：preflight 估算已超窗就先压缩；采样报上下文超限时识别错误文本，判定为确定性错误、不原样重发，转压缩后重发；压缩本身失败则按 Size / Auth / CreditBlock / Schema / Other 分类抑制。

关键参数
压缩重试 3 次 / 间隔 3s / 超时 120s；size、schema 为粘性抑制，只有上下文预算变化才解除；credit 等到一次成功响应；取消有独立文案 compact cancelled。已核实
设计意图
它不靠“失败次数”熔断，而靠“失败类型”抑制：重试也没用的错误立刻停，可能恢复的错误继续试。代价是分类依赖错误文本启发式，provider 改文案就可能失配。
来源
compaction.rs#L461-L480、failure.rs#L6-L59

full-replace 无法拆分单个不可分割单元；系统提示 + 工具定义逼近窗口时，压缩也无能为力。这两种情况应尽早报给用户。

工具弹窗 · dsh

DeepSeek Harness

溢出只认一种信号：适配器把 provider 的上下文超限规范化成 CONTEXT_WINDOW_EXCEEDED。接住后跳过常规阈值与保留策略，先跑可选 pruner，再选一个“最大的、平衡的头部区间”压缩；只有当 surface 的 replaceGeneration 前进时才返回重试。

关键参数
maxOverflowRetries 默认 1（0 只关闭恢复）；替换前失败 → 记 warning，带完整超预算历史继续；pruner 已落地但摘要失败 → 从已落地的 pruned surface 继续；手动错误码 busy / cancelled / changed / summary / commit / persistence。已核实
设计意图
replaceGeneration 是“这次重试到底有没有改变投影”的证据：没前进就原样抛错，避免无意义重试。代价是要求 surface 维护版本号，恢复路径与投影实现强耦合。
来源
compaction-basic/src/index.ts#L186-L234、compaction.md#L86-L99

未配对的 compaction/start 会被当成孤儿锁，阻塞后续压缩；这是“恢复失败”之外的另一类卡死，排查时先看锁。
