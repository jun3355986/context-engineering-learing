裁剪器与影子计价

DeepSeek Harness 的裁剪器只做一件很小的事：把超长工具结果的中间挖掉，换成一句固定标记。但它做这件事的方式很讲究——先写一条「这个节点值多少 token」的日志，再写替换。这条影子事件是整个 O(1) 上下文计价的地基。

01 · 功能说明

先削峰，再决定要不要摘要

压缩很贵：一次摘要调用、几秒到几十秒、还可能失败。所以在压缩之前，dsh 会先跑一次完全不调模型的裁剪：把当前 surface 上每一条超过 8,192 个码点的工具结果，中间挖掉，只留头 4,096、尾 1,024，中间换成 [... tool result middle pruned ...]。

关键在于它跑完会重新测量一次：如果裁剪已经把水位压到阈值以下，这次就完全不摘要了。

所以裁剪器的定位不是「压缩的预处理」，而是「压缩的替代品之一」。它先花零模型成本试一次，成功了就省下一次摘要；失败了也不要紧，压缩接着上。源码里的调用顺序写得很明确：过阈值 → 跑 pruner → 重测 → 仍然过阈值才选区摘要。已核实

这条设计有一个直接后果：裁剪器的每一次替换都必须「可计价」。因为重测要算出新的总 token，而总 token 是「所有 surface 节点价格之和」。如果一条节点被替换成了更短的内容，它的价格必须跟着变；如果计价服务不知道「这个节点被换过、原来值多少」，总数就会漂移。

dsh 的解法是「影子计价」：替换之前，先追加一条 compaction/prune 事件，写明「接下来这条替换，遮蔽的是哪个 seq、原价是多少 token」。计价投影读到它就把价格记在心里（一个「待用的报价」），读到紧接着的替换时用「新价 − 旧价」更新总数。已核实整个过程只需要一个整数和一个待用报价，不需要保留每个节点的价格。

裁剪器本身是一个 Cordis 服务，只暴露两个方法：pruneContent() 是纯函数，输入内容块、输出裁剪后的内容块；pruneSession() 遍历当前 surface 的工具结果、逐条替换。它声明依赖 tokenMeter（static inject = ['tokenMeter']），因为写影子事件时必须现场估一次价。已核实这个依赖不是可选的：没有计价能力，裁剪就只是「改短了内容」，下游投影无法知道总量变了多少，压力值会停在旧数上。

【注意】shadowedTokenCount 不是「被删那段文本」的价格

它记的是被替换节点的整条消息估价（estimateMessage(original)），包含角色框架与所有内容块；替换后的增量用 estimateMessage(新消息) 减去它。所以算出来的差值是「整条消息变短了多少」，不是「中间那段文本值多少」。这个区别在只有文本块时几乎看不出来，在结果里夹了图片或结构化块时就会差出不少——那些块的价格由 token meter 的块级规则决定，不由码点数决定。

// 返回裁剪后的内容；不超预算就返回 null（调用方据此跳过）
pruneContent(blocks: readonly ContentBlock[]): ContentBlock[] | null {
  const totalChars = this.measureContent(blocks) // 只数 text 块的码点
  if (totalChars <= this.config.thresholdChars) return null
  const removedStart = this.config.headChars // 删除区间 = [head, total - tail)
  const removedEnd = totalChars - this.config.tailChars
  const pruned: ContentBlock[] = []
  let consumed = 0
  let markerInserted = false // 整个结果只插一次标记
  for (const block of blocks) {
    if (block.type !== 'text') { pruned.push(block); continue } // 非文本整块保留
    const points = Array.from(block.text) // 按码点拆，不劈开代理对
    const blockStart = consumed
    const blockEnd = blockStart + points.length
    const headEnd = Math.min(points.length, Math.max(0, removedStart - blockStart))
    const tailStart = Math.min(points.length, Math.max(0, removedEnd - blockStart))
    const intersectsRemoved = blockStart < removedEnd && blockEnd > removedStart
    const marker = intersectsRemoved && !markerInserted ? PRUNE_MARKER : ''
    if (marker.length > 0) markerInserted = true
    const text = points.slice(0, headEnd).join('')
      + marker
      + points.slice(tailStart).join('')
    if (text.length > 0) pruned.push({ ...block, text })
    consumed = blockEnd // 累计到下一个块
  }
  if (!markerInserted) throw new Error('tool-result prune: failed to locate the removed text span')
  const charsAfter = this.measureContent(pruned)
  if (charsAfter > this.config.thresholdChars || charsAfter >= totalChars) {
    throw new Error('tool-result prune: replacement must be smaller and within threshold')
  }
  return pruned
}

04 · 逐段解读

五个决定，从「为什么是码点」到「为什么先写计价」

第 1 段　三个数字：阈值不是「裁到多少」

8192 是触发线，4096 与 1024 是保留量。裁剪后的长度等于 4096 + marker + 1024，标记本身约 38 个码点，所以结果约 5,158 码点。已核实一条 8,192 码点的结果被裁后只剩 63%，一条 80,000 码点的结果只剩 6.4%。

加载期校验要求 head + marker + tail ≤ threshold。已核实为什么要把 marker 算进去？因为如果三个数字凑得太紧（比如阈值 5,000、头 3,000、尾 2,000），标记一插进去，结果反而比原文还长。校验把这种配置挡在加载期，而不是等运行时抛「replacement must be smaller」。这是「把不可能的组合变成装不上」的又一个例子。

还有两个默认值没写在校验里，但同样重要：8192 是码点，不是字节，也不是 token；4096 与 1024 的比例是 4:1。头留得多、尾留得少，是因为工具输出的开头通常是「这是什么」（命令、文件名、表头），结尾通常是「结果是什么」（错误行、汇总）；中间是重复的日志。4:1 是一个经验比例，不是一个可推导的最优解。推断1

裁剪完成后，pruneSession() 还会返回一个汇总：每条被替换的记录（原 seq、新 seq、callId、前后码点数）与总节省量 charsRemoved。已核实这个返回值只用于日志与遥测，不参与决策——决策看的是重测后的 token 总数。分清「人类看的节省量」与「系统用的 token 数」很重要，两者单位不同，不能互相替代。

第 2 段　码点：为什么不用字节，也不用 UTF-16 码元

实现用 Array.from(text) 把字符串拆成码点数组，再 slice 与 join。已核实这是「按 Unicode 码点切」的标准写法。它保证不会把一个由两个 UTF-16 码元组成的字符（emoji、部分生僻字）劈成两半——劈开的结果是一个孤立代理项，序列化后可能变成 �，甚至让请求解析失败。

为什么不用字节切？因为字节切会把一个中文字符切成三段无意义的字节。为什么不用 String.prototype.slice（按 UTF-16 码元）？因为它对增补平面字符不友好。码点是这三者里唯一既能保证字符完整、又能直接对应「字符数」语义的单位。

代价是内存：Array.from 会把整段文本复制成一个数组，一个 8,000 码点的结果要多占几十 KB 的临时内存。对一个只在压缩前跑一次的路径，这个代价可以接受；如果要在每次请求都跑，就该换成「游标遍历 + 分段拼接」。推断2

切片还有一个容易忽略的行为：标记只在第一个与删除区间相交的文本块里插入一次。如果删除区间跨了三个文本块，第一个块留下「头 + 标记」，后两个块整块消失（因为 headEnd 与 tailStart 都算成 0，拼出来的文本为空，被 if (text.length > 0) 跳过）。非文本块（图片、结构化数据）则原样保留在原来的顺序里，不参与码点计数。已核实这保证了「删的是文本中间，不是内容结构」。

把收益算成 token。按 dsh 的固定密度（4 字符/token），一条 10,000 码点的纯文本结果约 2,500 token，裁到 5,158 码点后约 1,290 token，净省约 1,210 token。如果它前面已经有 20,000 token 的历史，这次裁剪只省了 6%，但代价是「从这条结果开始，后面的 prefix cache 全部失效」。所以单看「省了多少 token」会高估它的价值；真正的判断标准是「省下的输入费是否大于缓存失效的损失」——这也是它只在压缩确认后运行的原因。推断4

第 3 段　替换：只改 content，其余必须深度相等

第三段代码里，新消息是 { ...original, content }，只覆盖了 content 一个字段。已核实这不是随便写的：第 1 节讲过，surface 对 tool/result 的替换有一道校验，要求除 content 外所有字段与原文深度相等。也就是说，即使这段代码想改 callId，也会被拒绝。

这条约束保证了「裁剪不会破坏配对」。工具结果与工具调用靠 callId 关联；如果裁剪顺手改了 id，配对就断了，压缩选区算平衡时会算错，请求也会被服务端拒。把「只能改内容」写进 surface 层，比在每个裁剪器里各写一遍检查可靠得多。

替换事件带两个元数据：surfaceOp: { op: 'replace', startSeq: seq, endSeq: seq }（替换自己这一个节点）与 sourceEventSeqs: [seq]（我遮蔽的是谁）。已核实后者是重放时的关键：没有它，就无法验证「这条替换是否完整地覆盖了它声称覆盖的节点」。

新消息在写入前经过 freezeMessage()，成为深冻结对象。已核实这不是形式主义：surface 上的消息会被多个消费者共享（派生历史、计价、工具配对），只要有一处原地改了 content，其他消费者看到的就是被篡改的版本，而日志里又没有记录。冻结让「改内容」必须走「追加一条替换」的正规路径。

第 4 段　影子计价：为什么不能「替换完再算」

最有趣的是第三段代码的顺序：先 append('compaction/prune', …)，再 append('tool/result', …)。已核实为什么不先替换、再记一笔「省了多少」？因为投影是纯的：它按顺序折叠事件，折叠到替换时，必须立刻知道「被替换掉的那段原来值多少」，否则只能给增量记 0。

投影状态被刻意设计得很小：一个 running total、至多一个「待用报价」。报价里有 start、end、tokens 三个字段，来自 compaction/prune 或 compaction/summary。折叠到替换时，校验报价的区间与替换的区间一致，然后用 estimateMessage(新) − claim.tokens 更新总数。已核实

如果替换到达时没有报价，投影记 0 增量，并继续。源码注释解释了原因：早期版本的日志没有影子事件，而「有界状态无法重建被替换区间的价格」，所以只能容忍漂移，不能抛错——否则老会话根本打不开。但如果是「有报价、但区间对不上」，就直接抛错，因为那说明当前的生产者在违反协议，必须立刻暴露。已核实同一段代码里，「历史数据」宽容、「实时数据」严格，这个分界很值得学。

为什么只留「一个」待用报价，而不是一个队列？因为协议要求两者同步相邻：生产者写完报价，紧接着就写替换，中间不允许插入任何事件。既然只可能相邻，就没有必要排队；一个变量足够，而且能在越界时立刻报错。代价是这条约束必须被所有生产者遵守——压缩和裁剪都遵守了，第三个生产者（比如图片移出）如果也想改价格，必须走同样的两步。已核实

第 5 段　时机：只在压缩确认之后跑

裁剪器不是每轮都跑。调用方在确认「压力过阈值」或「已溢出」之后才调用 prune.pruneSession(agent.session)，跑完立刻 meter.measure(session) 重测。已核实低于压力的会话，一个字节都不动。

这个时机选择避免了两个问题。第一，避免无谓的缓存失效：裁剪会改历史中段，从改点开始缓存失效；如果每轮都裁，缓存永远命中不了。第二，避免「为了省一点而损失很多」：一条 8,200 码点的结果被裁到 5,158，省了约 760 token，但如果因此让后面几万 token 的缓存失效，净亏。

为什么只裁工具结果，不裁用户消息或助手回复？三个理由。第一，工具结果是唯一「可以重新获取」的内容：需要时重跑一次命令就行；用户的话不能重来。第二，工具结果是长度的主要来源：一次 cat 或一次测试输出，轻松上几万码点，而用户消息通常只有几百。第三，工具结果有稳定的结构（头是命令与表头、尾是结论），适合「留头留尾」；助手回复的结论可能在中段，砍中间会伤到语义。推断3

和 Grok Build 的 50% 触发线相比，dsh 的时机更晚：Grok Build 在会话过半时就开始裁，dsh 要等压缩确认。前者更积极，后者更保守。两种选择背后的假设不同——Grok Build 假设「长期会话迟早要压，先削一点是一点」；dsh 假设「压缩可能根本不需要，别为了预防而破坏缓存」。

重测用的不是「provider 上报的用量」，而是 meter.measure(session) 重放出来的本地估算。这一点很关键：provider 的用量只在「完整请求成功」之后才有，而裁剪发生在请求之前，还没有新用量可用。所以判断「压下去了没有」只能靠本地折叠——这也正是影子计价存在的理由：让本地折叠在发生替换之后仍然准确。已核实

✓要点小结

  • 8192 触发、留头 4096、留尾 1024；校验要求三者加标记不超过阈值。
  • 按 Unicode 码点切片，不劈开代理对；标记只插一次，非文本块原样保留。
  • 替换只改 content，其余字段必须与原文深度相等，否则 surface 层拒绝。
  • 影子计价：先写 compaction/prune 报价，再写替换；投影用「新价 − 旧价」更新总数。
  • 只在压缩确认后运行；跑完重测，压下去了就不摘要。

05 · 与其他 agent 的差异

四种「不调模型的裁剪」

同样是零模型成本，四家在「选谁、裁多少、怎么记账」上完全不同。最容易被忽略的是最后一项：记账。大多数 agent 裁完就完了，只有 dsh 把「裁了多少」写成一条可折叠的事件。

对照一：按单条大小 vs 按轮龄/预算。dsh 的判断只看这一条自己：超过 8,192 就裁，不管它多新、多旧、属于哪一轮。好处是规则简单、与顺序无关、可预测；坏处是「刚读到的关键文件」只要够长也会被裁。Grok Build 按轮龄，保护最近三轮，牺牲的是「老但仍有用的内容」；omp 与 opencode 按总预算，保护最近 40k token，牺牲的是「预算之外的旧内容」。三种维度对应三种「什么更可能还有用」的假设。

对照二：记账的必要性来自架构。dsh 必须记账，因为它的上下文压力是一个「折叠出来的标量」：所有节点价格之和。替换改变了某个节点的价格，折叠就必须知道变了多少。Grok Build 不需要，因为它的裁剪只改请求副本，压力值读的是会话状态，两者本来就是两套数——这也造成了「显示 60%、实发 45%」的现象。换句话说，记账不是裁剪的属性，是「单一计价来源」这个架构选择的副产品。

对照三：可恢复性的三种实现。dsh 的原文永久在日志里，一个 sourceEventSeqs 就能回溯；opencode 的原文也在，只是序列化时按时间戳省略；Grok Build 的原文在磁盘会话里，但请求副本上的占位符不带路径，模型无法按需找回。三者的「敢裁程度」依次递减，与它们「能不能找回」的能力一致。

最后一个值得注意的差异：只有 dsh 的裁剪是可在重放中复现的。因为替换事件、影子计价事件、原始事件三者都在日志里，重放到任何一点都能算出当时的 surface 与价格。Grok Build 的裁剪发生在请求构建时，日志里没有「这次裁了什么」的记录；omp 是原地改写并落盘，历史被覆盖。复现性不是免费的——它要求每一次变更都留下两条事件，而不是直接改内存中的对象。

还有一个不在表里的对照：Codex 没有这一层。它的减量在「写历史」时就做完了：工具输出按 TruncationPolicy 截断，中间换成 …N tokens truncated…，多块共享同一份预算。已核实所以它不需要「事后再裁」，也就不需要影子计价——代价是一旦截断就永久截断，模型想回看全文只能重新执行工具。dsh 把这件事推迟到「压缩确认后」，换来的是「进来时完整、需要时才裁」，以及「裁了还能从日志找回原文」。

06 · 思考题

三道题，从手算到改协议

Q1

一条工具结果有 10,000 个码点，全是一个文本块。裁剪后长度是多少？如果它被拆成两个文本块（各 5,000 码点），结果一样吗？标记会出现在哪里？

提示（不给答案）

删除区间是 [4096, 10000 − 1024) = [4096, 8976)。单个块：留前 4096 + 标记 + 从 8976 到末尾的 1024，合计约 5,158。

两个块各 5,000：第一个块与删除区间相交（4,096 到 5,000 被删），得到「前 4096 + 标记」；第二个块的 headEnd 与 tailStart 都算成 0（因为它整体落在删除区间里），拼出空串被跳过。所以总长度一样，标记在第一个块末尾。

Q2

如果把两条 append 的顺序反过来（先写替换、再写 compaction/prune），会发生什么？功能还能用吗？

提示（不给答案）

投影是顺序折叠的。替换先到时，报价还没出现，按规则记 0 增量——总数没有减少，但实际内容已经变短了。之后到来的报价会「武装」给下一个事件，而下一个事件可能是一条普通追加，于是报价被静默丢弃。

结果：surface 内容是对的，价格是错的，而且错得越来越大。重测时以为还没降下来，于是多跑一次不必要的摘要。功能「能用」，但省钱的初衷没了。

这也解释了为什么协议要求两者「同步相邻」：报价只对紧邻的下一个事件有效。

Q3

你要给一个没有「事件日志」的系统加同样的裁剪。会怎么实现「裁剪后总量准确」？说出你的方案和它比 dsh 少了什么。

提示（不给答案）

最简单的方案是「裁完重新全量估算」：遍历所有消息，重新算一遍总 token。准确，但每次裁剪都是 O(n)，而且如果系统里有多处缓存了这个总数，还要通知它们全部失效。

第二种是「增量更新」：裁剪函数直接返回「省了多少 token」，调用方把它从总数里减掉。这比全量估算便宜，但它要求「总数」只有一个持有者，且所有修改路径都记得更新它——这正是 dsh 用事件日志解决的问题。

少掉的东西：可重放性。dsh 的每一次裁剪都能从日志重建出当时的 surface 与价格；「直接改内存 + 手工减总数」在崩溃后无法复原「当时到底裁了什么、减了多少」。
