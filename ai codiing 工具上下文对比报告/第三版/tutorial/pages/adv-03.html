架构对比：四种把历史变短的路线

同样是“压缩到 64k”，有的工具改的是内存里的一个数组，有的工具只在日志上追加一条记录，还有的把这件事交给了服务端。功能表上看不出差别，架构图上差别很大——差在真相存在哪、减量动了谁、失败之后从哪儿恢复。

01 · 先别比功能文字 · Karpathy L1

三份目录，三种“历史”

场景 · 同一份需求，三种目录结构

三家公司都买了同一个模型，都要求“会话能恢复、能压缩、能回退”。A 公司的会话目录里只有一个 history.json，越用越大，压缩后旧内容就没了。B 公司每个会话是一个树，节点带父指针，压缩只追加一个节点。C 公司只有一个追加日志，另有一份“当前可见消息”的派生文件。三家都能跑，但出故障时，能查的东西完全不一样。

大多数人比较工具时，看的是功能清单：有没有自动压缩、阈值多少、保留多少。这张清单有用，但它回答不了下面这些问题：

  • 压缩之后，原始记录还在不在？在的话，谁能读到？
  • 同一个会话能不能同时存在两种历史（比如“审计版”和“模型版”）？
  • 回退到第 12 轮，是删掉后面的记录，还是只让它们“不可见”？
  • 压缩失败，是留下半截摘要，还是整段回滚？

这些问题的答案，不取决于阈值，取决于架构。本章把架构拆成四个部件：

  1. 真相源（source of truth）：哪份数据是“真正发生过的事”，不可篡改或只追加。
  2. 减量层：在哪一步、对哪份数据做缩短；改的是原文，还是只改“模型看到的视图”。
  3. 视图重建（projection）：每次请求前，模型看到的消息序列是怎么算出来的。
  4. 恢复单位：崩溃或回退时，从哪个粒度重来——一条消息、一个检查点，还是一整段日志。

架构的差别，最后都会落在一句话上：模型看到的历史，是不是磁盘上那份历史。

为什么先讲架构，而不是先讲参数？因为参数只能在架构允许的范围内调。一个覆盖式的实现，把阈值从 90% 调到 70%，能改变的只是“多久压一次”，改变不了“压完能不能回去”；一个日志式的实现，阈值调错最多是多压一次，原文还在，可以重新投影。同样一个“保留 20k”的数字，在前者意味着“只记得这 20k”，在后者意味着“模型这次只看这 20k”。参数相同，能力不同。

?动动脑

一个工具把会话写成追加日志，但压缩时直接覆盖了内存里的消息数组。它算“日志型”还是“覆盖型”？

提示：先问“真相源是哪一份”，再问“重启后模型看到的历史从哪里来”。两个答案可能不一致，这正是混合架构。

02 · 一张图看分叉图表 · Karpathy L2

五种架构，四个部件

下面这张图把五种架构放在同一组坐标里。每一行是一种架构，每一列是一个部件。读图顺序固定：先看第一列（真相在哪），再看第二列（减量动了谁），最后看第四列（坏了从哪恢复）。

读这张图时，容易犯两个错。第一个是把“日志”当成架构：几乎每个工具都写日志，日志只能说明“真相被保存了”，不能说明“模型看到的是哪一份”。第二个是把“压缩”当成一个动作：在 A 里压缩是覆盖，在 B、C 里压缩是追加一条记录，在 D 里压缩发生在你看不到的地方。同一个词，三种语义。

所以下面每讲一种架构，都按同一组问题走：数据流怎么走、上下文从哪里来、减量发生在哪、失败时怎么恢复、谁是这个架构的代表。

03 · 架构 A文字＋结构 · Karpathy L1–L2

单会话 + 压缩：覆盖，然后继续

这是最容易理解、也最早出现的一种。整个会话就是一个消息数组，按轮次往后追加。到阈值时，把前段交给模型写成摘要，用摘要替换前段，后面的消息原样保留。模型下一轮看到的是“摘要 + 保留段”，顺序和原来一样。

数据流
用户输入 → 追加到数组 → 调模型 → 追加助手消息与工具结果 → 超阈值时压缩 → 数组变短 → 继续。Codex session/mod.rs#L4321-L4376 已核实
上下文来源
当前数组本身。恢复时读最新检查点，再回放它之后的后缀，不从头重放。rollout_reconstruction.rs#L485-L520 已核实
减量在哪
压缩时一次性覆盖前段；平时靠工具输出截断做小减量。原文通常留在 rollout 或会话目录里，但不再进入模型。
失败恢复
从最新 CompactedItem 的替代历史起，回放后缀。压缩本身失败时，另一条路是删最旧条目再压。
代表
Codex 本地压缩、Grok Build 的 full-replace 装配、oh-my-pi 的五方法链。

它的优点是可预测。模型看到的消息序列和数组完全一致，没有“投影”这一步，调试时只要打印数组就知道模型看到了什么。实现成本也最低：一个列表、一个阈值、一次摘要调用。

它的代价是“覆盖”不可逆。压缩之后，内存里没有“压缩前的数组”了，只有存档里的原始记录。要做审计，得另写一套读存档的工具；要做“回到压缩前”，得从检查点重放。Grok Build 的做法是把摘要装配成固定七段，最近消息放在摘要之前；装配顺序固定，重放时不会因为消息位置变化而得到另一份历史。events/compaction.rs#L30-L60 已核实

还有一个隐蔽的代价：每次压缩都会让前缀缓存断一次。摘要替代了原来的开头，从摘要第一个 token 起，后面的缓存都不能复用。A 架构把“省下的输入 token”和“失效的缓存”放在同一笔账里，长任务上通常是划算的，短任务上不一定——这正是主线第 16 章要算的 CPS。

覆盖式实现还有一个边界要特别小心：压缩本身也可能超窗。要把待压缩的历史再发一遍给模型，输入比压缩前更大。Codex 的处理是删掉最旧条目再试，并把“删到不能再删”的情况单独兜底history.rs#L685-L700 已核实；Claude Code 连续失败三次就熔断autoCompact.ts#L257-L350 源码 v2.1.88。这些兜底在架构上属于“A 的失败分支”，如果一开始没留位置，后面很难补。

04 · 架构 B文字＋结构 · Karpathy L1–L2

树 + 投影：历史只追加，视图每次重算

B 把“历史”和“模型看到的历史”彻底分开。磁盘上是一棵条目树，每条消息是一个节点，带自己的 id 和父节点 id。压缩不删除任何节点，只追加一个“压缩条目”，里面记着摘要和“从哪个节点开始保留”。每次请求前，从当前叶子往回走，遇到压缩条目就换成摘要，再拼上保留段，得到这次要发的消息序列。

Claude Code 用的是同一种结构，但落点不同：会话按 parentUuid 串成链，写进 <sessionId>.jsonl；/compact 只替换内存历史并写入一条边界消息，原始记录仍在文件里。sessionStorage.ts#L1408-L1449 源码 v2.1.88 它的 /rewind 还多一层：不只截断对话，还把被跟踪的文件恢复到对应版本，最多保留 100 个快照。fileHistory.ts#L54-L57 两者一致

opencode v1 则把投影写进了主循环：每一步请求都从 SQLite 重新投影一次历史，先取“替代历史”，再插入提醒、跑插件改写、拼系统块。session/compaction.ts#L223-L269 已核实 所以它的历史不是“内存里那份”，而是“这一步算出来的那份”。

优点是可以有多种视图。同一棵树，可以给模型看压缩后的投影，给审计看完整节点；可以分叉出两条实验路径，互不影响。代价是投影逻辑复杂：切点必须落在合法边界（不能切在工具结果上）、压缩条目要能嵌套、回退后要保证投影仍然自洽。任何一个边界条件写错，模型看到的历史就会“少一条”或“多一条”。

多次压缩会把复杂度放大。第二次压缩的输入里已经有一条摘要，投影必须先决定“旧摘要还算不算数”，否则会出现“摘要里套摘要、保留段被算两遍”。pi 的做法是投影只认最新一条 CompactionEntry：从它的 firstKeptEntryId 起取保留段，再接上它之后的条目；更早的条目仍在文件里，但不参与这次投影。压了五次，投影只展开最后一次。session-manager.ts#L476-L512 已核实

05 · 架构 C文字＋结构 · Karpathy L1–L2

日志 + surface：两份数据，一份给审计，一份给模型

C 和 B 很像：都不删原文。差别在“视图”怎么表达。B 用树结构加压缩条目，投影时按结构遍历；C 用一条追加日志加一个可见面（surface），每条消息事件带一个操作：要么 append 到尾部，要么 replace(startSeq, endSeq) 遮蔽一段已有节点。派生函数走一遍 surface，就得到模型可见的消息。

追加事件 → 事件带 surfaceOp → deriveMessages() 生成消息 → 发送。session/src/index.ts#L966-L1005 已核实
上下文来源
派生结果。被 replace 遮蔽的事件还在日志里，但不再出现在派生历史中。session/src/surface.ts#L49-L56 已核实
减量在哪
追加一条 replace，把一段旧节点遮掉；不移动、不改写旧事件。
失败恢复
重放日志，结果确定。dsh 在模型请求前、顶层工具产生副作用前、下一步前刷盘，写不成功就不继续。
代表
DeepSeek Harness（dsh）。

这套结构最值得学的一点是把“缓存失效”收敛到一个变量。纯尾部追加时，缓存只需增量计算；只有发生 replacement，或消息投影规则变了（contentGeneration 变化），才整体重建。换句话说，架构从一开始就把“哪种操作会让缓存失效”写进了类型里，而不是事后去猜。

Grok Build 的回退是同一思路的另一个方向：日志只追加，回退时在文件末尾写一条 RewindMarker，指向要回到的 prompt 序号；重放器读到 marker 就把累积列表截回那个位置。rewind.rs#L400-L410 storage/mod.rs#L1655-L1677 已核实 磁盘上没有“分支”，只有同一文件里被 marker 隔开的多段时间线。它和 dsh 的 surface 只共享“只追加 + 逻辑截断”这一点，数据结构并不相同3。

优点是审计友好。“发生过什么”和“模型看到什么”是两份可以对照的数据，出了事故能复现。代价是两套语义必须严格对齐：任何一次派生规则变更（比如消息合并、角色归一化）都会改变历史，而日志本身没变。dsh 用 contentGeneration 显式标出这种变化，就是为了让缓存和审计都能判断“是不是同一份视图”。

第二层代价是膨胀。只追加意味着日志只增不减，一个长期使用的项目，日志体积会远超上下文本身。清理策略要自己定：按天归档、按会话封存、保留索引删除正文。清理时还要保证“重放仍然确定”，否则删日志等于改历史。

06 · 架构 D文字 · Karpathy L1

服务端压缩：把减法交给别人做

D 把减量搬到服务端。客户端照常发历史，服务端决定保留多少、摘要怎么写，然后返回一份“替换历史”。客户端拿到之后，用它覆盖本地历史，再写一条检查点。

Codex 的远端 v2 压缩是现成例子：保留消息共享 64,000 token 预算，单条 AgentMessage 上限 10,000，流式重试 2 次；客户端还要验收响应里的 compaction_count 恰好为 1，否则按致命错误处理。compact_remote_v2.rs#L87-L91 compact_remote_v2.rs#L458-L466 已核实

数据流
客户端发全量历史 → 服务端压缩 → 返回替换历史 → 客户端验收并写检查点。
上下文来源

减量在哪
服务端。客户端只有两个旋钮：什么时候发起、收到后接不接受。
失败恢复

代表
Codex 远端 v2 压缩。

优点是省实现。阈值、切点、摘要模板、重试策略都不用自己维护，模型升级时压缩策略也跟着升级。对只有一两个内部团队的场景，这是最省人力的选择。

代价有三条。第一，不可观测：你只看到“进去 180k、出来 40k”，看不到中间删了哪一段；出了问题只能靠对比输入输出。1 第二，不可移植：换模型供应商，压缩行为就换了，之前调好的阈值全部作废。第三，历史要出本机：对代码不能出内网的团队，这一条直接否决。

所以 D 很少单独出现。常见组合是“本地压缩兜底 + 服务端压缩优先”，或者“服务端压缩 + 本地完整日志”，把可观测性补回来。

什么时候值得用 D？三个条件最好同时成立：团队没有人力维护压缩链路；使用的模型只有一家、短期不换；历史里没有不能出内网的内容。少一条，就要重新算账——尤其第三条，它不是成本问题，是合规问题，不能用“省了多少 token”去换。

07 · 架构 E文字 · Karpathy L1

记忆增强：压缩之外再加一层外部存储

E 不是替代压缩，而是在压缩前后各加一步：压缩前把值得留的事实写进记忆库，压缩后按当前任务检索，把可能被摘要丢掉的内容补回上下文。它多了一份真相源，也多了一次“写入—检索—注入”的循环。

Grok Build 开启记忆后（默认关闭）的路径是：/flush 触发一次摘要写进记忆，压缩前自动跑一次（阈值比压缩阈值提前 4,000 token），压缩完成后再检索一次，把相关事实补回上下文。xai-grok-memory/flush.rs#L18-L58 13-memory.md#L398-L410 已核实 Codex 走的是后台两阶段管线：先从各线程的 rollout 提取候选，再合并成产物，读路径把记忆作为 developer 指令注入。memories/README.md#L1-L40 已核实

数据流
对话 → 压缩前写入记忆 → 压缩 → 检索 → 注入下一轮 → 继续。
上下文来源
摘要 + 保留下段 + 检索到的记忆条目，三部分。
减量在哪
压缩仍然做减法；记忆做的是“补回”，两者方向相反，必须一起调。
失败恢复
日志重放保证对话可复现；记忆要额外有快照或版本，否则“上次明明记住了”无法复现。
代表
Grok Build memory（默认关闭）、Codex memories、oh-my-pi 的多后端记忆（默认关闭）。

优点是把“跨会话”接上了。A 到 D 都只解决“这一次会话太长”，E 解决“下一次还要用上次的结论”。对长期维护同一个仓库的团队，这一层的价值比压缩本身大。

代价是污染与预算。一条错误的记忆会在之后每个会话里出现，而且比一次错误的摘要更难发现——摘要错了，下一次压缩会重写；记忆错了，会一直留在库里。所以 E 架构必须配套三件事：写入白名单、过期策略、可删除。另外，记忆注入会改变前缀，缓存又要断一次；检索预算太大，等于把压缩省下的空间还回去。

代码不能出内网，或必须离线 A / B / C，排除 D 减量在本地完成，历史不出机器。 压缩质量与模型能力绑定；升级要自己回归。
跨会话复用结论 E 记忆增强，叠在 A/B/C 上 压缩只保当前任务，记忆负责跨会话。 污染会长期存在；检索占预算；注入改前缀、断缓存。
高并发多租户，单机存不下 C 日志 + surface，或 D 日志与视图分离，便于分片与横向扩展；D 则把状态外移。 C 要自己做日志清理与一致性；D 要接受不可观测。
成本敏感，要调阈值 A 或 B（本地压缩） 阈值、保留量、缓存策略都在自己手里，能做 A/B。 要自己搭评测；调参成本转嫁到工程侧。

这张表是经验判断，不是对照实验结论2。“推荐”列假设你已经能改客户端；如果用的是现成产品，约束会反过来限制你可选的架构。

表里最容易被忽略的是最后两行。很多团队一开始按“先进程度”选了 B，后来发现真正卡住自己的是并发和存储，不得不把日志搬到服务端；也有团队为了省事选了 D，直到要做成本优化时才发现自己连“这次压缩删了哪段”都看不到。约束是慢变量，架构要跟着慢变量走。

举个读表的例子。一个 6 人团队，做内部代码助手，代码不能出内网，需要回退到上一版改法，但不需要跨会话记忆。读表顺序是：先命中“代码不能出内网”，排除 D；再命中“要回退”，选 B；最后确认代价——投影逻辑要自己维护，团队里至少有一个人能读懂会话文件格式。如果这一条不成立，退到 A 加“整文件快照”也能用，只是回退粒度变粗。选型不是选最好的，是选“代价付得起”的。

09 · 混合与迁移文字 · Karpathy L1

现实里没有纯种架构

把五种架构当成“类型”，不要当成“产品”。一个真实工具往往同时具备两三种特征：

  • Codex：内存里是 A（覆盖），磁盘上是追加 rollout 加检查点，远端点还会走 D。三种特征都在。
  • pi：B 的树 + 投影，但请求侧还有 section 级 patch，属于“只发变化”的缓存优化。
  • opencode v2：B 的树形条目，但检查点压成一条消息加 seq 边界，恢复粒度比 v1 粗。
  • Grok Build：A 的 full-replace，加 C 的 marker 截断，再加 E 的记忆，三层叠在一起。

所以判断一个工具属于哪种架构，不要看它“有没有日志”，要看三个动作：压缩时改的是原文还是视图、恢复时重放还是读检查点、模型看到的历史能不能和磁盘上的原文逐条对上。

9.1 迁移顺序：先把真相固定，再动视图

如果你现在的实现是 A，想往 B 或 C 迁，顺序不要反。一个可行的四步：

  1. 先把写入变成只追加：所有消息、工具结果、压缩动作都落成事件，不再覆盖。此时模型看到的仍是数组，行为不变。
  2. 再加一层投影：从事件算出“模型可见消息”，先让它和原数组逐条对齐，跑一轮回归，确认没有差异。
  3. 把压缩改成追加记录：压缩不再覆盖数组，而是追加一条带“保留起点”的记录，由投影负责替换。
  4. 最后才加分支与回退：有了树或 surface，分叉和回退才有地方落。

反过来做——先加分支、再改写入——会出现“分支指向的节点已经被覆盖”的情况，只能靠补丁修，越修越复杂。

三种常见误配

用 A 的存储做 B 的功能：只有一份数组，却想支持回退，最后只能靠“复制整个数组”当快照，存储随轮次平方增长。用 D 的黑盒做审计：服务端只回一份短历史，本地没存原文，出了事故无法复盘。用 E 补 A 的洞：摘要丢约束，就用记忆把约束再写一遍；两套写入时机不一致时，模型会同时看到“旧约束”和“新约束”。

10 · 小测验文字 · Karpathy L1

三道题，检验你会不会看架构

Q1

一个工具把每条消息写成 JSONL 的一行，压缩时在文件末尾追加一条“摘要 + 保留起点”，请求前再从当前末尾往回走生成消息序列。它属于哪种架构？如果它同时还允许切换分支，又多了什么？

解析

属于 B（树 + 投影）：追加条目、请求前投影、不删原文。允许切换分支，说明条目之间有父子关系，投影要从“当前叶子”回溯——这正是 pi 的做法。session-manager.ts#L476-L512 如果它只是追加日志、用 replace 遮蔽，而不维护父子关系，那更接近 C。

Q2

团队要求“代码不出内网”，但很想用服务端压缩，理由是“省实现”。你会怎么回答？给出一个折中方案。

解析

“代码不出内网”和“历史发给服务端压缩”直接冲突，不能靠配置绕过。折中是：本地做压缩（A 或 B），服务端只做模型推理。如果必须内网部署，压缩链路也只能自己实现，等于回到 A/B；厂商的“服务端压缩”不会跟着模型一起搬进内网。代价是压缩质量与维护成本回到自己身上，需要配一套评测（见第 05 章）。

Q3

有人说：“我们已经写了完整日志，所以架构是日志型，压缩丢东西也不怕。”这句话哪里不成立？

解析

“有日志”只说明真相被保存，不说明模型能看到它。如果压缩覆盖了内存数组，模型下一轮只看到摘要；日志再全，也要有人把它读回来。判断架构要看“模型看到的序列怎么来”，不是看“磁盘上有没有原文”。这也是 A 与 B/C 的分界。
