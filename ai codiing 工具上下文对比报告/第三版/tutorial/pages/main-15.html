扩展点：hooks 与插件

你不可能改每个 Agent 的源码，但几乎每个 Agent 都留了缝。缝的位置决定了你能做什么：有的缝能改提示词，有的能直接交出摘要，有的能整段换掉压缩实现。本章按“能改到多深”分三档，并说清每一档在升级时会不会悄悄坏掉。

01 · 一个三周的尝试

“上周还好好的”

场景 · 一个字段改名，注入静默消失

一个团队希望每次压缩后都保留“对外接口契约清单”，试了三种做法：写进项目规则文件，压缩后常被摘要稀释；写一个 PreCompact 钩子，把清单塞进压缩指令，头两周有效；第三周升级工具版本，钩子输出字段改名，进程仍然正常退出，清单却再也没进过上下文。没有人报错，直到一次重构改坏了公开 API。

扩展点的第一个问题，不是“能不能改”，而是“改了之后，升级时会不会静默失效”。静默失效比报错更难查：进程正常、日志正常、任务也能跑完，只是某条信息不再出现。等发现时，通常已经是一次线上事故。

要判断一个扩展点靠不靠谱，先问三个问题：

  • 它改的是哪一层？是提示词、摘要内容、切点算法，还是整个压缩实现？改得越深，能力越强，耦合也越重。
  • 它的契约是什么？是稳定的公开 API，还是带 experimental 前缀的内部接口？契约变了会不会报错？
  • 它失败时会发生什么？是阻断主流程、静默跳过，还是把错误写进上下文？

扩展点的设计，本质是在“可塑性”和“可维护性”之间画一条线。线画得越靠里，能改的越多，升级时越容易断。

02 · Codex 主线

四类扩展，一个不给碰的压缩

Codex 的扩展面不窄：hooks、skills、plugins、MCP 服务器，四类各有明确分工。但压缩是例外——它没有用户可替换的钩子，流程写死在 compact.rs 与 compact_remote_v2.rs，只能通过 provider 能力与 feature 开关影响走哪条路径。已核实

2.1 四类扩展各管什么

  • Hooks：挂在生命周期事件上的回调，由 hook_runtime 负责调度，hook_mcp_executor 负责 MCP 侧执行。它们的附加上下文以 hook_additional_context 片段进入历史，而不是改写系统提示词。
  • Skills：SKILL.md 加 frontmatter 的指令包，按需加载。它扩展的是“模型知道怎么做”，不是“模型能调用什么”。
  • Plugins：把 skills、MCP、apps 打成一个包，并在提示词里说明命名前缀（plugin_name:）。它扩展的是“一次性安装一组能力”。
  • MCP 服务器：工具并入统一工具表，扩展的是“模型能调用什么”。

这四类里，只有 hooks 能在运行时改变上下文；skills 与 plugins 主要改变“可用能力”，MCP 改变“工具表”。理解这个分工，才不会用错扩展点：想让模型记住一条规范，写 skill 或规则；想让它能查一个内部系统，接 MCP；想在每次工具调用后补一条状态，才用 hook。

2.2 hooks 的边界：能附加，不能改写

Codex 的 hook 输出不会直接变成系统提示词，而是作为 hook_additional_context 片段进入历史。位置在历史里，不在前缀里。这个设计有两个好处：一，不破坏已经缓存的前缀；二，注入内容与对话一起被压缩、一起被裁剪，不会永远占着固定开销。

代价是“重要性”下降。系统提示词里的规则，模型通常会当作硬约束；历史里的一条附加片段，可能被后来的工具输出淹没，也可能在压缩时被摘要掉。想让一条信息“永远在”，得放规则文件；想让一条信息“这次在”，才放 hook。

另一条边界是：hook 能阻断、能附加，但不能改压缩算法。压缩完成后，Codex 会触发一次 SessionStart(Compact) 钩子。session/mod.rs#L4375-L4380 已核实 这个钩子发生在摘要已经写回历史之后，它能做的是“再补一条上下文”，不能改摘要本身。

2.3 为什么压缩不开放

压缩是一致性敏感的流程：切点必须落在合法边界，工具调用与结果必须成对，摘要写回后内存与检查点必须同时更新。任何一条被插件改坏，都会产生一段“模型能看见但协议不合法”的历史。开放压缩，等于把这三个不变量交给第三方维护。

Codex 的选择是“不开放”，代价是用户想保留领域信息时，只能绕路：写进压缩模板（手动 /compact 可替换 compact_prompt）、写进规则文件、或者在压缩后用 SessionStart(Compact) 补一条交接清单。前两条改的是“摘要要写什么”，第三条改的是“摘要之后再加什么”，都不是“改压缩算法”。

这也解释了一个常见困惑：为什么有的工具能“自定义压缩”，有的只能“自定义压缩提示词”。差别在于愿不愿意把不变量交出去。

2.4 插件的命名前缀为什么算接口

Codex 的插件在提示词里用 plugin_name: 前缀标注技能来源。available_plugins_instructions.rs#L33-L42 已核实 这不是装饰：它让模型能区分“项目自带的技能”和“某个插件提供的技能”，也让用户在排查时知道该卸哪个包。

前缀一旦成为约定，就不能随便改。改了，模型对技能来源的判断会变，已有提示词里写死的“用 foo: 开头的技能”也会失效。扩展点的稳定性，往往就藏在这些看起来像文案的细节里。

Q没有傻问题

问：既然 Codex 压缩不可替换，那写 hook 还有什么意义？

答：hook 的意义不在“改压缩”，而在“压缩之后补一条”。比如压缩后把当前任务的验收命令、未完成的 todo、最近改过的文件清单再注入一次。它不能阻止摘要丢信息，但能让模型在下一轮马上看到“接着做什么”。这是“追加”而不是“改写”，代价小，也不会破坏前缀。

✓要点小结

  • Codex 有四类扩展：hooks（生命周期）、skills（指令包）、plugins（打包）、MCP（工具）。
  • hook 的附加上下文进历史，不进系统提示；能补，不能改前缀。
  • 压缩流程写死，没有用户可替换钩子；能改的只有压缩提示词与压缩后的补充。
  • 不开放压缩，是为了守住切点、配对、检查点三个不变量。
  • 插件命名前缀是稳定接口的一部分，不要随手改。

03 · 三档做法

改提示词、给摘要、换实现

把各家“自定义压缩”的能力排一下，会发现它们正好落成三档。档位越高，能改的越多；档位越高，也越依赖内部契约。

3.1 第一档：只改提示词

做法是给压缩引擎一段“额外指令”，让它知道摘要该重点保留什么。Claude Code 的 PreCompact 可以通过 mergeHookInstructions 改写自定义压缩指令；compact.ts#L411-L424 源码 v2.1.88 opencode v1 的 experimental.session.compacting 可以注入 context 或整体替换压缩提示词；omp 的 session.compacting 可以返回 {prompt, context, preserveData}。

能改：摘要要写什么、按什么顺序写、哪些字段必须出现。不能改：切点在哪、保留多少原文、摘要怎么放回历史、失败怎么重试。换句话说，它改的是“作文题”，不是“考试规则”。opencode v2 的 session.context 也能改系统提示与消息，但它改的是普通请求的上下文，不是压缩指令；v2 的压缩能力属于下一档。

代价：最安全，也最容易被稀释。模型可能只写一半、可能把指令当成建议；提示词越长，压缩请求自己的开销越大。适合“锦上添花”的信息，不适合“缺了就错”的硬约束。

3.2 第二档：直接给摘要

做法是跳过摘要模型，自己产出摘要，交给引擎写回。pi 的 session_before_compact 可以返回 {summary, firstKeptEntryId, tokensBefore, usage, details}，也可以直接取消压缩；omp 的 session_before_compact 返回 {cancel:true} 或一个完整的 CompactionResult；opencode v2 的 session.compaction 返回 {summary, tokens?, providerState?, metadata?} 时走 fromHook，跳过模型调用。

能改：摘要的全部内容、格式、来源（可以查数据库、可以拼模板、可以用另一个模型）。不能改：引擎仍然决定切点、保留段与重建顺序；你给的 firstKeptEntryId 必须落在合法边界上。

代价：可控性大幅提升，但你要自己保证摘要“不漏关键约束、不与保留段重复、不超出预算”。一旦摘要质量差，压缩后的任务失败率会直接上升，而且很难归因——看起来像模型变笨，其实是摘要写坏了。适合“有明确结构、可以程序化生成”的信息，比如接口清单、迁移步骤、验收命令。

3.3 第三档：换实现

做法是替换整个压缩后端。dsh 的插件体系里，ctx.compaction 可以被替换；自定义压缩的正确姿势是继承 CompactionEngine，实现 compactIfNeeded / compactNow / compactRegion，或者只覆写 summarize()。这是“一切皆插件”的架构：模型适配器、工具注册表、会话日志、agent 循环都可以换。

能改：切点算法、保留预算、摘要模型、重建方式、失败重试，全都能改。不能改：宿主对“压缩结果必须合法”的要求；你仍然要产出引擎能消费的结构。

代价：能力最强，耦合也最重。你依赖的是内部接口，不是公开协议；升级时构造函数、抽象方法、事件顺序都可能变。Codex、Grok Build、opencode v1/v2 都没有“注册自定义压缩算法”的接缝；pi 与 omp 也只有“整段替换产物”，没有“往方法链里插一个新方法”的注册表。真正能换实现的，只有 dsh 这类把内核也插件化的架构。

怎么选档

先问“缺了这条信息会不会错”。不会错，选第一档，成本最低。会错，但信息结构固定、可以程序化生成，选第二档。只有当前两档都做不到（比如你要改切点，或者要把压缩换成检索式摘要），才考虑第三档，并准备好跟着上游升级改代码。

3.4 PreCompact 与 PostCompact：为什么一个能改，一个只能看

“压缩前”和“压缩后”看起来只差一个时间点，能力却常常差一整档。原因在于提交点：压缩前，历史还没变，改指令、给摘要都只是影响“即将发生的写入”；压缩后，新的基线已经提交，内存、检查点、日志都指向新历史，此时再改，就是在改一个已经生效的检查点。

各家的具体差异：

  • Claude Code：PreCompact 可以改写自定义压缩指令，属于第一档。本快照的事件清单里没有 PostCompact；压缩后没有专门的钩子，要补内容只能在后续的 UserPromptSubmit 里注入。源码 v2.1.881
  • Grok Build：pre_compact 与 post_compact 都有，但 trait 都是 Observe——只能观察，不能改压缩内容，也不能阻止压缩。event.rs#L78-L180 已核实 它把“有事件”和“能改”分开了：两个位置都给你看，但都不给你写。
  • pi：session_before_compact 能取消或直接给产物（第二档）；session_compact 与 session_compact_failed 只观察。
  • omp：session_before_compact 能取消或给完整结果；session.compacting 能改提示词、追加 <additional-context>、写 preserveData；session_compact 只观察。
  • opencode v1：只有压缩前的 experimental.session.compacting（改提示词）与压缩后的 Session.Compacted 事件（观察）。
  • opencode v2：session.compaction 可以直接给摘要（第二档）；压缩的 Started / Ended / Failed 是事件。
  • Codex：没有 PreCompact；压缩后触发 SessionStart(Compact)，可以补上下文，但不能改摘要。
  • dsh：没有同名钩子，走 compaction/summary-error 瀑布与 CompactionEngine 子类（第三档）。

所以“PreCompact / PostCompact 能力差异”不是实现偷懒，而是提交点决定可写性。在提交点之前，你可以影响要写什么；在提交点之后，最安全的能力就是观察。少数 agent 允许在提交后追加（比如 Codex 的 SessionStart(Compact)），但那是“追加一条新消息”，不是“改已提交的摘要”。

3.5 插件与 MCP 的分工

这两个词经常被混用，但它们改的不是同一件事。

  • MCP 提供能力：工具、资源、提示模板。它让 Agent “能做一件新事”，比如查工单、读数据库。它本身不改变上下文组装；但工具定义会占 token，工具表一变，前缀缓存就可能失效。
  • 插件 提供打包与挂载：把 skills、agents、hooks、MCP 服务器打成一个可安装单元，并允许在生命周期上挂钩。它让 Agent “按某种方式工作”，比如每次提交前跑一次检查、压缩后补一条清单。

判据很简单：需要模型调用一个新能力，选 MCP；需要在某个时刻改变上下文或行为，选插件 / hook；需要长期存在的知识，选规则文件或技能。三者可以叠加，但不要用错层：把“必须遵守的规范”写成 hook 注入，压缩后可能就没了；把“一次性状态”写进系统提示，会破坏缓存。

还有一层容易被忽略的成本：MCP 的工具定义会进入工具表，而工具表通常位于请求前缀。装十个 MCP 服务器、每个暴露五个工具，前缀就可能多出几千 token；更麻烦的是，服务器重连或工具列表顺序变化，会让整张表重新排序，缓存从工具块开始失效。所以“按需加载 MCP”不只是省 token，也是保前缀（第 10 章）。插件如果顺带装了一组 MCP，效果一样：能力变多，前缀变重。

3.6 稳定性风险：五种会在升级时坏掉的地方

  1. 实验性命名空间：opencode v1 的 experimental.chat.system.transform、experimental.session.compacting，v2 的 experimental.ws.*。带这个前缀，就意味着“随时可能改”。
  2. 字段与事件 schema：Claude Code 的 hook 输出依赖 hookSpecificOutput.additionalContext 等字段；字段改名不会让进程崩溃，只会让注入静默消失。这就是开篇场景里发生的事。
  3. 能力语义变化：今天 Observe 只能看，明天可能支持改写；反过来也可能。依赖“它不能改”来做安全假设，同样有风险。
  4. 延迟与超时：hook 是同步执行的，跑得慢就会拖住主循环。一个每次工具调用都查网络的 hook，会把延迟从毫秒级拉到秒级。推断2
  5. 缓存副作用：在 UserPromptSubmit 里每轮注入 2k 上下文，看起来只是“多加一点”，实际上每轮都在改变历史尾部，可能让上一轮的缓存尾部失效，也可能让压缩更早触发。

降低风险的办法不是“不用扩展”，而是把扩展当成外部依赖来管：给它写契约测试（断言注入真的进了上下文）、给它加超时与降级（hook 失败时不阻断主流程）、给它记录版本（升级前后各跑一次同一任务）。这些做法会在第 23 章变成可观测指标。

契约测试可以很小：准备一个固定任务，跑完后断言“上下文里出现了某个只有 hook 才会写入的标记字符串”，再断言“压缩后这个标记仍在”。这条测试不关心模型答得好不好，只关心扩展有没有生效。它能在升级当天抓到字段改名、事件未触发、注入被去重这三类问题，成本只有几分钟。

04 · 七个编码智能体

同一道缝，七种开法

Codex 已经在主线里拆过。剩下七个 agent 可以按“缝开在哪”分三派：事件钩子（Claude Code、Grok Build）、进程内扩展（pi、omp、opencode v1/v2）、全插件内核（dsh）。第一派最容易接入，第三派能改得最深。

键盘：Esc 关闭；Tab 在弹窗内循环。Claude Code 的结论来自非官方 v2.1.88 源码，只代表该版本。

06 · 设计取舍

为什么有人只给看，有人给整段换

扩展点的每一次“开放”，都是在把某一层不变量交出去。下面五组取舍，对应五种交法。

取舍一：开放提示词，还是开放产物，还是开放实现

提示词派：Claude Code、opencode v1 只让扩展改压缩指令。引擎仍控制切点、预算、重建，摘要质量由模型负责。产物派：pi、omp、opencode v2 允许扩展直接交出摘要，引擎只负责写回。实现派：dsh 允许替换整个压缩后端。

代价：提示词派最安全，扩展写坏了最多是“摘要差一点”，不会产生非法历史；但能力有限，改不了“保留谁”。产物派可控性强，扩展要自己对摘要质量负责，写坏了会让压缩后的任务失败率上升；实现派能力最强，扩展要维护切点、配对、检查点，升级时最先坏。开放得越深，责任转移得越多。

取舍二：给“压缩前”写权限，还是只给“压缩后”观察

前写派：Claude Code 的 PreCompact、pi / omp 的 session_before_compact、opencode v2 的 session.compaction。它们都发生在提交点之前，改的是“即将写入的内容”。后看派：Grok 的 post_compact、pi / omp 的 session_compact、Codex 的 SessionStart(Compact)（只能追加）。

代价：前写能力强，但要求扩展理解压缩的约束（切点合法、配对完整、预算不超）；写坏了，错误会被写进新基线，后面很难修。后看最安全，但只能做事后补救，比如记录指标、追加一条提醒、触发一次外部索引；它救不回已经丢掉的细节。这也是为什么大多数 agent 把“写”放在前、“看”放在后。

取舍三：进程内扩展，还是外部命令

进程内：pi、omp、opencode 的扩展是同一进程里的模块，能直接拿到消息对象、工具定义、压缩准备数据，改起来最细；Grok 的 hooks 也是进程内事件回调。外部命令：Claude Code 的 hooks 是外部命令或 HTTP 端点，通过 stdin/stdout 与退出码通信。

代价：进程内延迟低、能力深，但扩展与内核同生共死，内核升级可能直接编译失败；外部命令隔离好、语言无关、可以独立部署，但每次调用都有进程启动开销，能力受限于协议（只能给 JSON、退出码、附加字段）。一个需要读内部对象的需求，外部命令做不到；一个需要独立团队维护的需求，进程内扩展不合适。

取舍四：插件，还是 MCP

MCP 扩展“能调用什么”：工具、资源、提示模板。它不改上下文组装，但工具定义会进工具表，影响 token 与缓存。插件 扩展“怎么工作”：打包 skills / agents / hooks / MCP，能在生命周期上挂行为。

代价：MCP 接入简单、跨客户端通用，但它只能提供能力，不能保证“什么时候被调用”；工具一多，工具表膨胀，前缀缓存更容易失效。插件能力强，能挂压缩前后、能注入上下文，但它是工具私有的，换一个 Agent 就要重写；插件还能带来供应链风险，安装前要确认来源。判据还是那句：能力用 MCP，时机用插件，长期知识用规则或技能。

取舍五：稳定公开 API，还是 experimental 快车道

稳定派：dsh 的 ctx.compaction、pi 的 session_before_compact 都是相对明确的扩展契约，文档与类型都在。快车道：opencode v1/v2 把大量钩子放在 experimental.* 下，能改得多，但不承诺兼容。

代价：稳定 API 升级慢，有些新能力要等很久才开放；experimental 能第一时间用上新能力，但升级时可能改名、改字段、改语义，而且失败往往是静默的。选择快车道，就要接受“每次升级都跑一遍契约测试”的成本；不接受这个成本，就不要用 experimental。

还有一组横切的取舍：全插件内核，还是硬编码核心。dsh 把模型适配器、工具注册表、会话日志、agent 循环都做成插件，任何一层都能换，代价是没有“特权核心”，排查问题要沿着插件树走；Codex 把压缩写死在核心里，行为一致、容易审计，代价是用户只能绕路。两者没有高下，取决于你更怕“改不动”还是更怕“不一致”。

07 · 小测验

三道题，检验你会不会选缝

Q1

PreCompact 通常能改什么、不能改什么？为什么 PostCompact 多半只能观察？

解析

PreCompact 在提交点之前，能改“即将写入的内容”，比如压缩指令、要重点保留的字段，有的实现还能直接给摘要；它不能改引擎的切点、保留预算和重建顺序。PostCompact 在提交点之后，新基线已经写进内存和检查点，此时改历史等于改一个已生效的检查点，所以大多数实现只给观察（Grok 的 pre/post 都是 Observe）。见3.4 PreCompact 与 PostCompact。

Q2

你只想让摘要稳定保留“对外接口契约清单”，不需要改切点或预算。选哪一档？为什么？如果清单必须逐字准确、不能由模型改写呢？

解析

第一档就够：用 PreCompact / session.compacting 把“必须保留接口契约，按文件与符号列出”写进压缩指令，成本最低，也不碰引擎不变量。如果清单必须逐字准确，第一档不够——模型可能改写或漏项，应选第二档，直接给出摘要（pi / omp / opencode v2 都支持跳过模型），由程序生成清单并放进摘要。只有当你还要改“保留哪些原文”“切点在哪”时，才需要第三档。见3.1、3.2。

Q3

一个团队在每次 UserPromptSubmit 注入 2k 的项目状态。两周后他们发现缓存命中率下降、首 token 延迟上升、压缩触发更早。请给出诊断和两个替代方案。

解析

诊断：每轮都在历史尾部追加 2k，输入持续变大，压缩提前；如果注入位置影响到上一轮的缓存尾部，命中率也会下降。两个替代：一，把稳定部分移出 hook，写进规则文件或技能，只在变化时注入差分；二，把“必须每轮都在”的少量状态压缩到几百 token，并放在固定位置，避免每轮改变前缀。若只是偶尔需要，改成按需读取（工具或技能），不要每轮注入。见3.6 稳定性风险与第 20 章的前缀三原则。

脚注

  1. “本快照没有 PostCompact”是反证式结论：已逐条核对 hooks.ts 的事件枚举与 hooksConfigManager.ts 的事件说明，未找到 PostCompact；官方文档可能列出本快照之外的事件，且新版本可能新增。因此正文按“本快照的事件清单里没有”表述，不推断线上版本一定没有。 ↩
  2. “hook 同步执行会拖住主循环”是根据 hooks 的调用方式推断的：Claude Code 的 hooks 通过子进程执行并等待结果，源码里能看到超时与异步选项，但没有找到“所有事件都在关键路径上串行”的统一说明。已检查 hooks.ts 的执行与超时分支，缺少端到端延迟测量。结论按“可能拖慢、需自行加超时”表述。 ↩
  3. dsh 的 hooks 兼容层“只支持 command 型”来自 hook-protocol 包 README，该节标【推断】；已核对其支持矩阵，http / mcp_tool / prompt / agent 会被跳过并告警。缺少运行时验证，因此正文按“兼容层能力有限”表述，不把它当作所有 dsh 版本的统一行为。 ↩
