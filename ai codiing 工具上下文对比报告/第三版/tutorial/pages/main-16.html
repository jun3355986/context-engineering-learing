评估与可观测：指标与 A/B

你改了阈值、换了压缩模板、加了一个 hook，怎么证明它更好？本章给一份可以直接抄的指标清单、一套评测集设计、一套 A/B 分流方法，以及几个最容易把结论带偏的陷阱。

  • 约 20 分钟
  • 4 张表
  • L3 → L5

读完你能做到

  1. 用 13 个指标搭一份上下文策略的评测清单，并说清每个指标对应哪条结论。
  2. 设计一个配对 A/B：分层抽样、同任务同初始状态、独立 workspace、分层分析。
  3. 判断一个“成本降了 18%”的结论是否可信，并指出它可能漏掉了什么。

01 · 一次庆祝得太早

“成本降了 18%，为什么还被叫停”

场景 · 省下的钱，赔在返工里

一个团队把自动压缩阈值从 90% 调到 75%，月底账单降了 18%，大家在群里发了红包。两周后，线上任务成功率掉了 6 个百分点；更糟的是，失败的任务往往已经跑了很久，返工要重读文件、重跑测试。复盘时他们发现：成本下降有一部分是因为任务提前失败、少跑了轮次——省下的不是效率，是没做完的工作。

这不是“指标选错了”这么简单，而是只看了一个能被作弊的指标。成本可以靠“少做事”降低，token 可以靠“少读文件”降低，压缩次数可以靠“不压缩”降低。任何一个单独看的指标，都有一种让它变好看却不改善结果的方法。

所以评测的第一原则不是“多采集”，而是让指标之间能互相证伪：成本必须和成功率一起看，压缩率必须和信息保留率一起看，缓存命中率必须和失效原因一起看。第二原则是让比较可复现：同一个任务、同一个初始仓库、同一个模型版本，只改一个变量。

没有对照的指标是观察，有对照的指标才是证据。

02 · Codex 主线

它给你原始数据，不给你结论

Codex 没有面向用户的评测框架，也没有 A/B 实验入口。它能提供的是三类副产品：rollout 存档（可离线重放并统计 token 与工具调用）、analytics 事件、OTEL 追踪。换句话说，工具负责“记录发生了什么”，不负责“判断哪种策略更好”。已核实

2.1 三样原始数据

  • rollout JSONL：按时间追加的会话记录，包含用户消息、模型输出、工具调用与结果、压缩检查点。它可以离线重放，重建某个时刻模型看到的历史。rollout_reconstruction.rs#L485-L520 已核实
  • TokenUsage：未缓存输入、缓存读、缓存写、输出，以及总量。它是算成本与命中率的唯一可靠来源。
  • OTEL / analytics：用于把一次任务串起来，看耗时、重试、错误分布。它们不直接给“上下文策略”的指标，但能提供时间线。

这三样加起来，足够做“事后归因”：这次任务为什么多花了 30%？是压缩次数多了、缓存失效多了，还是工具输出变大了？但都不足以做“事前预测”：换一个阈值会怎样，必须自己跑对照实验。

2.2 为什么“工具不自带评测”是常态

八个 agent 里，有成型评测设施的只有 pi 与 omp：pi 有 packages/evals，用 vitest-evals 跑“有文档 / 无文档”的对照；omp 有 snapcompact 的研究评测（SQuAD 的 recall / F1）和 packages/stats 的本地观测面板。Grok 算半套：遥测字段齐全，但没有运行器。其余工具大多只有记账与事件。没有一家提供“压缩策略 A/B”这种开箱即用的能力。

原因不难理解：上下文策略的效果高度依赖任务分布。一个在“读代码问答”上更好的压缩策略，可能在“跨文件重构”上更差；一个在短会话里省钱的阈值，在长会话里会让成功率下降。工具厂商很难替你定义“你的任务”，所以只能给你原始数据。

评测不是 agent 的附属功能，是你对自己任务分布的理解。

2.3 一个最小可用的评估管线

不需要一上来就搭平台。四步就够跑第一轮：

  1. 采集：每次任务记录一条结构化记录——任务 ID、分层、变体、模型版本、开始/结束时间、总 token（分未缓存/读/写）、压缩次数与耗时、是否溢出、是否成功、失败原因。
  2. 对齐：把“一次任务”作为一行，而不是“一次请求”。同一任务里的多次请求、压缩、重试，都要归到同一行，否则成本会被拆散。
  3. 分层：按任务类型（短/中/长/易溢出/约束保持）分组统计。总体均值只能用来做概览，不能用来下结论。
  4. 判定：先看护栏指标（成功率、溢出率）有没有退化，再看主指标（每成功任务成本、p95 延迟）。护栏破了，主指标再漂亮也不能上线。

2.4 从“能观测”到“能归因”

原始数据只能告诉你“变了”，归因才能告诉你“为什么变”。这一层各家差距很大。

  • Claude Code 有专门的缓存失效检测：对比系统提示词哈希、工具哈希、TTL/scope 变化，判断“本可命中却没命中”的原因，并把这些原因上报promptCacheBreakDetection.ts#L31。这是少数把归因做进产品的例子。源码 v2.1.88
  • Grok Build 把压缩当成一等遥测事件：AutoCompactFired 带压缩前 token 与百分比，CompactionTriggered 带触发原因、窗口、模型、是否子代理，CompactionCompleted 带耗时、压缩前后 token、退化重试次数、输入溢出重试次数。有了这些字段，压缩回收率、压缩耗时、退化重试率都能直接算。已核实
  • dsh 提供三个投影键：tokenUsage（未缓存输入、输出、缓存读、缓存写）、contextPressure（最新上报 prompt、下一请求预估、窗口）、contextBreakdown（system / tools / messages 的启发式构成）。客户端可以直接订阅，不需要事后解析日志。推断
  • opencode v1/v2 是“记账 + 事件”：每条 assistant 消息带 tokens 与 cost，压缩自身也记账（UsageRecorded source:"compaction"），失败与中断也计费。已核实

归因的价值在于“可行动”。知道“成本涨了”只能让人焦虑；知道“成本涨在压缩后的重附文件上”才能改。做评测时，至少要把成本拆成四块：普通输入、缓存写、缓存读、压缩请求。拆不开，就找不到杠杆。

Q没有傻问题

问：只有几个人的团队，也要做 A/B 吗？

答：不必一开始就做“线上分流”。可以先做“离线配对”：取 30–50 个历史任务，在同一初始仓库上，用两套配置各跑一遍。关键是“配对”和“同初始状态”，不是“线上”。跑完再看差异是否大于噪声；如果连离线配对都做不了，那任何“感觉更快了”的结论都只能算假设。

03 · 指标清单

十三个指标，六条结论

下面这份清单可以直接用。先记住六条结论，再看每个指标对应哪一条——指标不是越多越好，而是每条结论至少有一个指标能支持、一个指标能证伪。

本章的六条结论

C1 只看成本会奖励“提前失败”，必须用“每成功任务成本”。C2 缓存命中率是诊断指标，不是目标；压缩会主动制造一次失效。C3 压缩收益随剩余任务长度递减，短任务上压缩是净成本。C4 总体均值会被任务分层掩盖，必须分层报告。C5 A/B 必须配对同一任务与同一初始状态，否则差异来自任务难度。C6 样本量不足时，小差异不可解释；先算最小可检测效应。

溢出率OR 发生上下文超限的任务数 ÷ 总任务数；分“主动拦截”和“被动报错”两档。 从错误码与事件统计：ContextWindowExceeded、413、prompt-too-long 等，按任务去重。 主动拦截多说明阈值偏保守；被动报错多说明估算不准或恢复路径有问题。两者要分开。 C3
溢出恢复成功率RSR 溢出后最终完成的任务数 ÷ 发生溢出的任务数。 按任务串起“溢出事件 → 压缩 → 重试 → 结束”，看最终状态；失败任务要记录停在哪一步。 低于 70% 说明恢复路径不可靠；配合“恢复耗时 p95”看用户等待是否可接受。 C1 / C6
压缩失败率与熔断率 压缩失败次数 ÷ 压缩次数；熔断会话数 ÷ 总会话数。 从压缩事件、错误码、熔断标记统计；注意把“取消”排除在“失败”之外。 失败率高但熔断率低，说明重试在起作用；两者都高，说明有结构性问题（见第 21 章三种绝境）。 C6
上下文压力峰值CPP 一次任务中“单次请求输入 ÷ 有效窗口”的最大值，用同一口径估算。 优先用服务端 usage；没有就用“上次 usage + 本地增量估算”，并标注口径。dsh 的 contextPressure 直接给预估。 长期贴近 100% 说明阈值太晚或任务太重；长期低于 50% 说明阈值太早、压缩过度。看分布，不看单点。 C3
首 token 延迟TTFT 与 p95 从请求发出到收到第一个 token 的时间；按任务聚合看 p50 与 p95。 OTEL 或客户端计时；压缩、重试、工具执行要单独打点，才能拆出“慢在哪”。 p95 比均值更能反映用户体感。压缩带来的额外延迟要计入，不能只算模型时间。 C1
重复读取率RRR 同一文件被 read 的次数 ÷ 该文件被修改或引用的次数；也可统计“同一路径重复 read 的会话占比”。 从工具调用日志按路径聚合；区分“用户要求重读”和“模型不知道已读过”。 压缩后 RRR 明显上升，说明摘要没保住文件状态；这是“信息丢失”的行为侧证据，比探针更接近真实任务。 C3 / C4

口径提醒：CHR 在不同 provider 上的分母不同（有的把缓存写算进输入，有的单列），跨工具比较前先统一口径3；CPS 的单价要按实际账单，不要用公开价目猜。指标名是为了沟通，公式才是契约。

这张表怎么用？先选一个你要回答的问题，再选 2–3 个指标，不要一次上全。比如“把阈值从 90% 调到 75% 好不好”，主指标是 CPS，护栏是 SR 与 IRR，诊断是 CN 与 CRR。如果 CPS 降了但 SR 或 IRR 破了，结论就是“不成立”，不需要再看别的。

表里的 1 个百分点、80%、70%、50%、10% 都是起始阈值，用来启动讨论，不是行业标准。跑过几轮、有了自己的基线之后，再按任务分布调整；调整时把旧阈值一起写进实验记录，否则下一次没人知道为什么是 80。

04 · 评测集设计

先分层，再谈样本量

上下文策略的效果高度依赖任务形态。把所有任务混在一起算一个平均值，等于把“短任务上压缩是净亏”和“长任务上压缩是救命”平均掉，最后得到一个谁也不适用的数字。

4.1 六个任务层

  • T1 短任务：10 轮以内、单文件、目标明确。用来观察“压缩是否过早”“缓存是否稳定”。
  • T2 中任务：10–30 轮、3–5 个文件、需要读代码再改。最接近日常使用，应占样本的最大比例。
  • T3 长任务：30 轮以上、跨模块、需要多次测试。压缩的主要战场。
  • T4 易溢出：刻意构造接近窗口的任务，比如一次读入大日志、连续跑多次全量测试。用来测恢复路径，不要求全部成功，要求“失败得可预期”。
  • T5 约束保持：在第 1–3 轮给一条硬约束（“不要改 public API”“必须保留 x 字段”），最后检查是否遵守。专测压缩是否丢关键信息。
  • T6 干扰：包含大量无关工具输出、失败命令、重复文件读取。测“噪声下的有效上下文”。

分层不是越细越好。六层已经够覆盖“长度、溢出、约束、噪声”四个维度；再细会把样本切碎，每层都不够统计。每层至少 20 个任务，做层内比较时建议 30 个以上；总量 120–200 个任务，能支撑一次中等规模的策略对比。

4.2 一个任务单元要固定什么

评测集的最小单位不是“一句话”，而是一个可复现的任务单元。至少固定八项：

  1. 仓库与提交：同一个 commit，必要时打包成镜像或压缩包。
  2. 初始 workspace：干净工作区，不含上一次运行的残留文件。
  3. 工具权限：允许读哪些目录、能不能联网、能不能装依赖。
  4. 模型与版本：模型 ID、温度、最大输出；两臂必须一致，除非你研究的就是模型。
  5. 预算上限：最大轮数、最大 token、最大墙钟时间，超了记为失败。
  6. 验收脚本：可自动执行的测试或断言，退出码即结果。
  7. 探针问题：3–5 个，答案只能来自任务过程中出现过的信息。
  8. 初始提示：一字不差地固定，避免提示改写引入差异。

这八项里，最容易被忽略的是“初始 workspace”和“工具权限”。前者不干净，上一臂的文件会污染下一臂；后者不一致，一臂能联网、一臂不能，成本与成功率都不可比。

4.3 样本量：先算最小可检测效应

配对实验看的是“同一任务在两臂上是否一个成功、一个失败”。用 McNemar 检验的近似公式，可以估算需要的配对数。下表是示意，假设两臂不一致的比例（discordant rate）约 25%–30%：

4.4 信息保留率怎么测

IRR 是压缩策略最直接的质量指标，但很容易测错4。三个要点：

  • 问题只能来自被压缩段：如果答案在保留段里，测的是“模型会不会读”，不是“摘要保没保住”。
  • 答案要可判定：用“是/否”“具体路径”“具体数字”，不要用“你觉得这个方案怎么样”。
  • 别污染主任务：探针可以放在任务结束后另开会话，或作为最后一步插入；不要把探针塞进任务中间，改变任务本身的走向。

一个实用的探针组合：一条早期约束（“不要改哪个文件”）、一个具体路径（“上次改的配置文件在哪”）、一个决策理由（“为什么选方案 B”）、一个验收命令（“跑哪个测试”）。四个问题覆盖“约束、位置、意图、验证”，正好对应压缩最容易丢的四类信息。

05 · A/B 分流

配对，配对，还是配对

A/B 的目标不是“跑两套配置”，而是“让两套配置的差异只来自策略本身”。做到这一点，靠三件事：同一任务、同一初始状态、随机顺序。

5.1 分流单位：任务，不是请求

上下文策略是有状态的：同一会话里前面的压缩会影响后面的请求。按请求随机分流，会让同一会话一半用 A、一半用 B，历史被两套策略交替改写，最后两臂都不是干净的策略。正确做法是按“会话 / 任务”整体分流：一个任务从头到尾只用一个变体。

5.2 配对：同任务、同初始状态、随机顺序

配对的意思是：任务 X 在 A 臂跑一次，也在 B 臂跑一次，两边初始仓库、初始提示、模型版本完全一致。这样任务难度被抵消，差异只剩策略。顺序要随机：如果总是 A 先跑，磁盘缓存、依赖安装、甚至机器的热状态都会偏向 A。

如果任务本身有副作用（改文件、装依赖），两臂必须用独立 workspace；否则 B 臂会看到 A 臂改过的代码，测的就不是同一个任务了。这一点在“重构类”任务上尤其致命。

5.3 缓存混杂：最隐蔽的偏差

A/B 和缓存放在一起，很容易互相污染。假设 A 臂先跑，把系统提示与工具定义写进了缓存；B 臂随后跑，可能直接命中 A 留下的缓存，成本被低估。反过来，如果两臂用同一个缓存键交替跑，每次切换都会让对方的前缀失效，两臂都被高估。

做法是：两臂使用独立的缓存键（或独立的会话 ID），并在每臂开始前做一次冷启动；如果无法冷启动，就记录“是否命中”，在分析时把首次请求单独剔除。不要在报告里把“缓存命中带来的便宜”算成策略的功劳。

5.4 成本口径：把压缩本身算进去

压缩不是免费的：它要再发一遍历史、要生成摘要、可能还要重试。评估时必须把这几笔算进成本：

  • 压缩请求的输入与输出（按实际单价）。
  • 压缩失败后的重试成本，包括被丢弃但仍然计费的后台压缩。
  • 压缩后重附文件、技能、工具增量的成本。
  • 因为压缩导致的额外轮次（模型重新读文件、重新跑测试）。

只算“主请求”的成本，会系统性低估压缩策略的开销，尤其是那些“压缩很便宜、但压缩后要重读五个文件”的实现。

5.5 决策规则：护栏优先

上线前先定规则，不要等结果出来再解释。一个可用的规则是：

  1. 护栏：SR 下降不超过 1 个百分点，OR 不上升，IRR 不低于基线的 95% 且绝对值不低于 80%。任一不满足，直接不通过。
  2. 主指标：CPS 下降至少 10%，且置信区间不跨 0。
  3. 分层：至少 4 个任务层方向一致；如果只有长任务变好、短任务变差，要么缩小适用范围，要么放弃。
  4. 可运维性：新增的配置项、失败模式、监控项是否可接受；这一条不进入统计，但能否决。

规则写在实验开始之前，能防止“结果出来再挑指标”。这也是 C6 的实践含义：先算样本量，再定决策阈值，最后才跑。

08 · 设计取舍

为什么“有数据”不等于“有结论”

评测设计的分歧，往往不在统计方法，而在“愿意为因果付多少成本”。下面五组取舍，对应五种常见的妥协。

取舍一：离线评测，还是在线观测

离线派：固定任务集、固定初始仓库、两臂各跑一遍，结论可复现，适合回答“这个改动有没有用”。在线派：直接看真实流量的成功率、成本、延迟，分布真实，适合回答“上线后有没有变坏”。

代价：离线可控但离真实分布有距离，评测集选得不好会得出“实验室有效、线上无效”；在线真实但不可复现，任务在变、用户群体在变、模型也在变，很难把差异归给策略。成熟做法是两者配合：离线做筛选，在线做护栏。

取舍二：单臂绝对指标，还是配对 A/B

单臂派：只跑新策略，和历史基线比。成本低、上手快，适合早期探索。配对派：同一任务两臂都跑，差异只来自策略，适合下结论。

代价：单臂便宜，但“历史基线”受模型版本、任务分布、机器负载影响，差异很难归因；配对可信，但要双倍算力与时间，而且要求任务可重复执行。只改了阈值这种小改动，如果只用单臂，几乎必然把噪声当效果。

取舍三：自动验收，还是人工评审

自动派：用测试、构建、断言判定成功，规模大、成本低、可重复。人工派：让人看 diff、看解释、看是否“真的解决了问题”，能覆盖自动脚本测不到的语义质量。

代价：自动验收快，但容易被“通过测试但改错语义”骗过；人工评审准，但贵、慢、评分者间不一致。可行的折中是“自动做全量、人工做抽样”：自动跑 100%，人工只抽 10%–20%，并让两位评审独立打分，分歧大的样本再看一遍。

取舍四：总体均值，还是分层与分位数

均值派：一个数字，好汇报、好比较。分层派：按任务类型、长度、难度分组，再看每组的差值；延迟与成本再看 p50 / p95。

代价：均值简洁，但会被长尾和任务构成掩盖，辛普森悖论就是这么来的；分层更真实，但每层样本变少，置信区间变宽，汇报成本也更高。折中是“总体看方向、分层下结论”：总体只用来发现异常，决策必须落到层。

取舍五：成本优先，还是成功率优先

成本派：先压 CPS，把成功率当护栏。适合预算敏感、任务可重试的场景。成功率派：先保 SR，成本只要不失控即可。适合返工代价高、用户等待敏感的场景。

代价：成本优先容易滑向“少做事”，尤其是压缩阈值调低、工具输出截短这类改动；成功率优先容易过度保留、上下文膨胀、单任务成本上升。真正的目标函数应该是“每成功任务成本”，它同时包含两者；但它也有盲点——不衡量延迟和用户体验，需要额外护栏。

还有一组横切的取舍：大样本慢实验，还是小样本快迭代。大样本能检出小差异，但一轮要跑几周，期间模型和任务都变了；小样本反馈快，但只能看大差异。可行的节奏是“小样本筛方向、大样本确认关键决策”，不要把每个小改动都做成大实验。

09 · 常见陷阱

五个坑，外加一个附加项

陷阱一：辛普森悖论

总体看 A 更好，分层看每一层都是 B 更好。原因通常是两臂的任务构成不同：A 臂恰好分到了更多简单任务。解决办法只有一个——配对，或至少按层报告，不要只报总体均值。

陷阱二：幸存者偏差

只统计“完成的任务”，会漏掉失败任务已经花掉的成本。一个策略让 30% 的任务提前失败，剩下的 70% 看起来很便宜，CPS 可能反而更低。解决办法是把失败任务的成本计入分子（CPS 的分母是成功任务数，失败越多，CPS 越高），并单独报告成功率。

陷阱三：均值掩盖长尾

平均延迟 8 秒，听起来可以接受；p95 是 90 秒，用户早就取消了。成本和延迟都要看 p50 与 p95，尤其是压缩、重试这类“少数请求特别慢”的操作。均值适合做预算，分位数适合看体验。

陷阱四：指标泄漏与过拟合

用同一批任务调阈值、又用这批任务证明阈值好，等于把答案背下来。评测集要留出“开发集”和“保留集”：前者用来调参，后者只在最后跑一次。保留集被看过一次，就脏了。

陷阱五：把相关当因果

“压缩次数多的任务成功率也高”不代表压缩让任务成功。更可能是长任务本来就更容易成功（因为用户愿意投入），而长任务压缩次数自然多。只有对照实验能回答因果；观察数据只能提出假设。

陷阱六（附加）：任务提前结束的“假省钱”

压缩让模型更早放弃，轮次变少、成本变低，但任务没做完。这类“省钱”在总成本上很好看，在 CPS 上会暴露：分母（成功任务数）变小，分子（总成本）没怎么变，CPS 反而上升。看成本时永远同时看分母。

11 · 小测验

三道题，检验你会不会读结论

Q1

一次实验：成本降 18%，成功率从 72% 降到 66%，失败任务的成本已计入。这个策略能上线吗？还需要什么信息？

解析

不能。成功率掉了 6 个百分点，远超 1pp 的护栏；成本降 18% 很可能来自“少做任务”。先算 CPS：如果成功任务数下降 8%，总成本只降 18%，CPS 可能只降 10%，甚至不降。还需要看分层（是长任务变好、短任务变差，还是全面退化）、IRR（摘要是否丢约束）、OR（溢出是否增加）。见第 03 节指标清单与5.5 决策规则。

Q2

为什么不能把“缓存命中率越高越好”当成目标？举一个命中率更高、但结果更差的例子。

解析

因为命中率可以通过“不改前缀”来刷高：一直不压缩、不裁剪、不更新规则，命中率当然高，但窗口里塞满过期内容，模型更容易被旧信息带偏，成功率下降。压缩会主动制造一次失效，换来之后每次更小的输入；这时命中率下降是设计的一部分。正确用法是把它当诊断：突然下降时查失效原因，而不是设成 KPI。见 C2 与第 20 章。

Q3

10 个任务跑 A/B：A 成功 7 个，B 成功 6 个。能否得出“A 更好”的结论？为什么？应该怎么做？

解析

不能。样本太小，1 个任务的差异完全可能是噪声；而且这 10 个任务如果没分层，可能全落在短任务上，结论不能外推到长任务。做法：先按分层补样本（检测 20pp 差异约需 50–70 对，10pp 约需 150–230 对），用配对设计（同任务两臂都跑），报告差值或置信区间而不是两个孤立的成功数。见4.3 样本量与5.2 配对。

脚注

  1. opencode v1/v2 的“无评测能力”标【推断】：已检索 packages/ 下的命令与事件定义，只找到 per-step / per-compaction 的记账与 Step.Ended、Compaction.* 事件，没有找到评测集、指标定义或 A/B 分流。缺少对全部子命令的穷举，因此正文按“未提供开箱评测”表述，不外推为“永远不会有”。 ↩
  2. 样本量表按 McNemar 检验的正态近似估算，取 α = 0.05、power = 0.8、两臂不一致率 25%–30%；实际所需样本随基线成功率、不一致率与是否单侧检验变化。已用公式复算 20pp / 10pp / 5pp 三档，未做模拟验证。正式实验前应用自己的基线重算，不要直接照抄数字。 ↩
  3. “缓存命中率跨工具不可比”是推断：Codex 的 cached_tokens、opencode v2 的 cache.read、pi footer 的 cacheRead 在分母口径上是否包含缓存写，源码与文档没有统一说明；已核对三家的 usage 字段定义，缺少跨 provider 的对照测试。因此本章要求先统一口径再比较，不给出跨 agent 的“标准命中率”。 ↩
  4. “探针法测信息保留率”是本章建议的评测方法，不是任何 agent 的内置指标；八个 agent 里没有任何一家提供 IRR 这类字段。已逐个核对八个 agent 的评测相关源码，确认只有记账、事件与遥测。探针问题的设计、评分口径需要自行制定并在实验记录里写明。 ↩
