append-only 日志如何回退

回退的常规做法是删掉后面的记录，或者把文件重写成一份新的。Grok Build 两条都没走：日志一行不删，只追加一条「隧道标记」，等下次重放时按标记把列表截断。这一节读这条标记怎么写、怎么被读，以及为什么这个反直觉的设计值得学。

01 · 功能说明

回退不是「删掉」，是「宣布后面作废」

一次会话在磁盘上是一堆文件：updates.jsonl 是权威对话日志，chat_history.jsonl 是实际发给模型的消息，rewind_points.jsonl 是检查点索引，另有 summary.json、system_prompt.txt、tool_definitions.json 等。回退要解决的是「怎么让日志回到某个用户请求之前」，而日志本身是只追加的。

Grok Build 的答案是：不动旧行，在文件末尾追加一条 RewindMarker，指向要回到的那个 prompt index；所有读日志的路径先过一个过滤器，读到标记就把已累积的列表截回去。

这条设计之所以反直觉，是因为我们习惯把「日志」当成「事实的记录」，把「回退」当成「撤销事实」。这里两者被拆开了：日志记录的是「发生过什么」（包括「用户按了回退」这件事），而「当前有效的时间线」是从日志里算出来的。同一个文件里可以并存多条时间线，靠标记隔开。

这张图解释了一个常见的困惑：回退之后，如果直接去 updates.jsonl 里搜旧内容，还能搜到。不是回退失败，而是回退的语义是「从当前时间线里排除」，不是「从磁盘上抹掉」。这也意味着，任何绕过过滤器直接读文件的工具，都会看到被回退掉的内容——这是这套设计最需要小心的地方。

为什么要拆成这么多文件？因为它们的「权威性」不同。updates.jsonl 是事件流，负责「发生过什么」；chat_history.jsonl 是某一时刻实际发出去的消息，负责「模型看过什么」；rewind_points.jsonl 只是索引，丢了可以重建。回退只改前者的「可见性」，不动后两者。这种拆分让每种数据都有单一职责，代价是恢复时要按顺序重放并合并多个来源——这也解释了为什么「恢复」在这套代码里比「保存」复杂得多。

链路上有四个关键点：get_rewind_points() 列出可回退的位置；handle_rewind() 执行回退（截内存、写标记）；filter_rewind_lines() 是读磁盘时的入口；filter_rewind_by() 是真正的截断算法。本节按这个顺序读。

// 共用驱动：classify 负责「这一项是什么」，这里只负责记账与截断（L1572-L1597）
fn filter_rewind_by<T>(items: Vec<T>, classify: impl Fn(&T) -> RewindStep) -> Vec<T> {
    let mut result: Vec<T> = Vec::with_capacity(items.len());
    let mut prompt_starts: Vec<usize> = Vec::new(); // 每个已计数轮次在 result 里的起点
    let mut tracker = UserRunTurnTracker::new();
    for item in items {
        match classify(&item) {
            RewindStep::Rewind { target } => {
                // 目标越界时保留全部幸存者：宁可不回退，也不误删
                let trunc = prompt_starts.get(target).copied().unwrap_or(result.len());
                result.truncate(trunc); // 把累积列表截回目标轮次之前
                prompt_starts.truncate(target); // 轮次起点表同步收缩
                tracker.on_non_user(); // 标记之后不再处于 user run 中
                continue; // 标记本身不进入结果
            }
            RewindStep::UserChunk { prompt_index } => {
                if tracker.on_user_chunk(prompt_index) { // 这一块是否开启一个「计数轮次」
                    prompt_starts.push(result.len()); // 记录起点，供将来截断
                }
            }
            RewindStep::Other => tracker.on_non_user(), // 非 user 内容结束当前 run
        }
        result.push(item);
    }
    result
}
// 读入口：先做一次子串扫描，绝大多数会话在这里就返回了（L1655-L1660）
pub(crate) fn filter_rewind_lines(lines: Vec<&str>) -> Vec<&str> {
    if !lines.iter().any(|l| l.contains(&*REWIND_MARKER)) {
        return lines; // 没有回退标记：零解析成本
    }
    filter_rewind_by(lines, |line| rewind_step_for_line(line))
}

04 · 逐段解读

五个问题，从「怎么记账」到「为什么敢不删」

第 1 段　检查点：为什么每条用户请求都能回

get_rewind_points() 不维护一张单独的检查点表，它直接用 (0..current_prompt_index) 生成列表，再按文件快照的元数据补上「这一条有没有文件改动」。已核实注释写得很清楚：每个 prompt 都是一个 checkpoint，文件快照可能没有，但对话位置一定有。

这是一个成本很低的决定：不需要在每轮结束时写一条「检查点记录」，只需要维护一个自增的 prompt_index。代价是回退的粒度固定为「一条用户请求」，不能回退到某次工具调用中间。对用户来说这刚好是自然的粒度：人只会说「回到我上一条消息之前」，不会说「回到第三次 grep 之前」。

回退语义也由此确定：回退到 N 表示「保留 0 到 N−1，丢掉 N 及之后」，所以目标是 0 时只剩会话前言。这个语义在源码注释里被写死了两次（rewind.rs L118 与 L363），说明它是一个容易被后人改错的契约。

第 2 段　书签：prompt_starts 让截断变成 O(1)

过滤器的核心是一个数组 prompt_starts：每遇到一个「计数轮次」的用户消息块，就把当前 result 的长度压进去。于是 prompt_starts[k] 恰好是第 k 轮在结果数组里的起点。读到标记 Rewind { target } 时，取 prompt_starts[target] 截断，再把这个表也截到 target，两行代码完成回退。已核实

这个技巧值得记住：它把「回退到第 N 轮」从「找到第 N 轮的第一条消息」变成了「查一次表」。表是在顺序扫描时顺手建的，没有额外遍历。代价是内存里多一个 Vec<usize>，长度等于轮次数——相对于整份日志，可以忽略。

入口的预检是在原始字符串上做 contains，所以只要某条用户消息的正文里恰好出现了标记的名字，就会误走慢路径。这个误判没有正确性代价：慢路径照样会完整分类每一行，只是多花一次解析。用一次可能误命中的子串扫描换掉「每个会话都全量解析」，是很划算的交易。

越界处理是一个容易被忽略的细节：prompt_starts.get(target) 取不到时，unwrap_or(result.len()) 会把截断点设为「当前长度」，也就是什么都不截。这是 fail-open：标记损坏、轮次对不上、旧版本写的标记指向了不存在的轮次，结果都是「保留全部」而不是「清空」。对一个删除操作来说，这个方向选对了——宁可回退失败，也不能误删用户的对话。

另一个细节是 tracker.on_non_user()：标记之后立刻把「是否在 user run 中」置为 false。这一步保证标记后面的第一条用户消息一定开启新轮次，而不是被当成上一轮的续写。如果没有它，回退之后再提问，新问题可能被算进旧轮次，prompt_starts 就会错位。

顺带看一眼分类器。原始行路径的 rewind_step_for_line 并不完整反序列化，它只窥探三个位置：外层 method、params.update.sessionUpdate、以及 _meta 里的 promptIndex 与 hostTurn。只有「xai 方法 + sessionUpdate 等于 rewind 标记 + 带 target_prompt_index」三个条件同时成立才算 Rewind；ACP 的用户消息块只有在 _meta.promptIndex 存在时才被计为一轮，hostTurn 为真的块被排除（它不是人说的话，是宿主注入的轮次）。其余一律 Other。已核实

这套分类解释了为什么过滤器能同时处理「很老的日志」和「刚写的日志」：早期版本的日志里没有 promptIndex 标记，UserRunTurnTracker 就用「第一次见到带标记的块之前，所有 user run 都计数」的渐进规则兼容它们。兼容逻辑写在 tracker 里，而不是散在驱动里，所以驱动本身只有「记账 + 截断」两件事。

第 3 段　写标记：为什么放在最后一行

handle_rewind() 的顺序是：先算要保留多少条、截断内存会话、替换 chat state、取消正在进行的采样与图片剥离、清理压缩抑制状态、重新公告失败的服务端，然后才写标记。已核实标记放在最后，理由和「事务提交」一样：它是这次回退的「已生效」信号。如果进程在写标记之前崩了，磁盘上就没有这条回退，下次恢复会回到回退前的状态——一致，只是白做了一次操作。如果先写标记再截内存，中途崩溃就会留下「磁盘说回退了、内存没退」的分叉。

标记里只有两个字段：target_prompt_index 与 created_at。没有「回退原因」、没有「操作者」、没有「被丢弃的消息 id 列表」。这是有意的极小化：过滤器只需要目标位置；其余信息如果写进去，就要保证所有读者都理解它们，否则等于给格式加了负担。

写标记用的是 persist_xai_update_only，一个「只写 Xai 扩展 update、不改变 ACP 会话状态」的通道。这解释了为什么标记不会出现在模型可见的历史里：它是一条日志记录，不是一条消息。

同一段代码里还有一个值得注意的动作：回退会把「因预算导致的压缩抑制」清掉，但保留 credit / auth 这类账号级抑制。原因是清楚的——历史变短了，之前「压不动」的理由可能不成立了，应该给压缩一次新机会；而「余额不足」「登录过期」跟上下文长度无关，清掉只会让下一次请求再失败一次。已核实这种「按失败原因决定是否随状态变化而重置」的思路，在所有自动重试机制里都适用。

第 4 段　重放：三处调用点，一个算法

过滤器不是只在一个地方用。至少三条读路径都要过它：初次重放（prepare_replay_lines，replay.rs L485）、增量重放（filter_delta_replay_lines，L559）、以及会话更新流（extensions/session_updates.rs L150）。三处都调用同一个 filter_rewind_lines，所以「当前时间线」的定义只有一份。已核实

这里有一处设计值得学：filter_rewind_by 是一个泛型驱动，通过 classify 闭包适配两种输入。原始 JSONL 路径用 rewind_step_for_line，它先窥探 params.update.sessionUpdate 与 _meta.promptIndex，避免完整反序列化；typed 路径用 rewind_step_for_update，直接匹配枚举。两条路径共用同一份截断逻辑，测试里还有一条用例专门断言两者输出一致（via_lines 与 via_updates 对比）。已核实

这也是「一个算法、两种表示」的标准写法：把「是什么」交给调用方，把「怎么累积、怎么截断」留在驱动里。如果复制两份逻辑，早晚会出现「原始行路径修了、typed 路径忘了修」的 bug。

「分支」在磁盘上的样子也值得看一眼。假设原始文件是四行：轮0、轮1、轮2、轮3；用户回退到轮 1，文件末尾追加 marker→1；然后继续对话，写入 轮4。磁盘上现在是六行，过滤器读出来的时间线是「轮0、轮4」。如果再回退到轮 0，就再追加一条 marker→0，文件七行，时间线只剩「轮0」。

注意这里没有任何一行被改写。旧时间线（轮0…轮3）与新时间线（轮0、轮4）共存于同一个文件，边界就是标记。要恢复旧分支，理论上只需去掉后面的标记；但 Grok Build 没有提供这个操作，TUI 里的 /rewind 只往前走。真正的「多分支」能力在 pi 的树结构里，不在这个线性标记模型里。

第 5 段　与压缩的冲突：为什么回退前必须重放

会话一旦压缩过，prompt_index 就不能再用来直接截断内存里的对话了。原因很直白：压缩把 N+1 条用户消息合并成了一份摘要，内存里剩下的 User 项数量远小于 prompt_index。如果还按「数到第 N 条 User」来截，切点会落在错误的位置。

源码为此写了一个专门的判定 needs_compaction_replay()：只要 last_compaction_prompt_index 有值，就认为「发生过压缩」，回退必须走重放路径。已核实注释把原因说得很清楚：Compaction collapses N+1 user messages into ~3, so the conversation in memory no longer has the User count prompt_index implies.

重放时还要处理一个更细的问题：压缩后的历史里，系统消息与 <user_info> 前缀是重建出来的，可能与检查点里的原文不同。代码的做法是尽量用检查点里的 original_user_info 替换，拿不到就保留当前的。已核实这又是一次 fail-open：宁可前缀略有偏差，也不要因为找不到原文而中断回退。

压缩与回退能共存，靠的是同一套「日志里留原文」的约定：压缩不会删除被遮蔽的原事件，只是让它们不再进入当前历史。所以重放到压缩点时，仍然能复现出同一份压缩后历史。已核实反过来说，如果压缩是「删掉旧行、写一份摘要」，回退到压缩点之前就不可能了——这也是 append-only 最实际的收益之一。

第 6 段　三种回退模式：对话、文件、两者

标记只管对话。文件是否回滚是另一个维度，由 RewindMode 决定：All 同时回滚对话与文件，FilesOnly 只回滚文件，ConversationOnly 只回滚对话。TUI 发出的请求固定是 conversation_only 且带 force: true，所以命令行里的 /rewind 默认不动磁盘文件。已核实

回滚文件时会先做只读预览，检测三种冲突：文件被外部修改（modified_externally）、被外部删除（deleted_externally）、被外部创建（created_externally）。有冲突就不写，交给用户决定。已核实这一段逻辑比对话回退复杂得多，因为文件没有「追加标记」这种便宜的抽象——只能真的写回旧内容。

入口还有两个小细节：/rewind 的别名是 /undo；在空闲、输入框为空时快速按两次 Esc（800 毫秒内）等价于执行一次 /rewind。已核实这些是交互层的约定，不影响存储语义，但能解释为什么用户会觉得「回退很轻」——它被做成了一个不需要打命令的动作。

这形成一个有意思的对比：对话侧用「不删、只标记」实现了零风险回退；文件侧仍然要真的改文件，所以必须加预览与冲突检测。同一个功能，两种介质，成本差了一个数量级。

✓要点小结

  • 回退不删行：在 updates.jsonl 末尾追加 RewindMarker{target_prompt_index}。
  • 重放时用 prompt_starts 把累积列表截到目标轮次之前；越界则保留全部（fail-open）。
  • 检查点就是每个用户请求，不需要额外记录；回退粒度是一条 prompt。
  • 压缩过的会话不能按 User 项数快截，必须先重放日志。
  • 对话回滚零风险，文件回滚要预览与冲突检测——介质决定成本。

表注：Grok Build 见本节 permalink；dsh 见 research/dsh.md 第 11 节（明确「无 rewind / undo / 树状多分支」）；pi 见 research/pi.md 第 11 节（CURRENT_SESSION_VERSION = 3）；Claude Code 为 v2.1.88 源码（sessionStorage.ts 的 parentUuid 链、fileHistory.ts 的快照上限 100）。

对照一：标记 vs 分叉。Grok Build 的标记让「旧时间线」与「新时间线」共享一个文件，靠过滤器区分；它省掉了复制整个会话的成本，但要求所有读者都遵守同一条规则。DeepSeek Harness 反过来：没有回退，只有 buildForkSeed(events, boundary) 把前缀复制成一个新会话，再补一条 session/end-seed 与合成的 closers。前者的风险是「有人绕过过滤器」，后者的风险是「每次分叉都要复制一份历史」。已核实

对照二：线性回退 vs 树。Grok Build 的时间线是线性的：回退到第 2 轮会丢掉第 2 轮之后的全部内容，之后的新对话接在第 2 轮后面，旧的第 3 轮永久不可达（除非手动去文件里找）。pi 用 parentId 把会话组织成树，回退只是「移动叶子」，旧分支还在，下次可以再跳回去，并为离开的分支写一份 BranchSummaryEntry。已核实树更灵活，但每次跳转都要决定「要不要摘要」，而这个决定会影响上下文。

对照三：对话回退 vs 文件回退。四家里只有 Grok Build 与 Claude Code 明确区分这两件事。Claude Code 的做法是「每轮给被跟踪的文件建快照，最多 100 份」，回退时把文件恢复到对应版本；Grok Build 则是「三模式 + 冲突预览」。两者都承认同一个事实：对话可以靠标记 cheaply 回退，文件不能——文件系统没有 append-only 的语义，写回就是覆盖。

最后说这套设计的两个代价，值得在设计自己的会话层时提前想清楚。一是文件只增不减：每次回退都追加一条标记，被丢弃的分支永远留在文件里，长期会话的文件会包含大量不再可见的历史。Grok Build 没有做压缩或归档，清理需要外部工具。二是正确性依赖纪律：只要有一个人新写了一个读 updates.jsonl 的函数而忘了过 filter_rewind_lines，被回退的内容就会重新出现。这类 bug 很难在测试里发现，因为「多读了一点」通常不会报错。

作为对照，DeepSeek Harness 干脆不做回退，只做分叉。这个选择看起来是功能缺失，实际上是把「时间线」这件事变成了「多个会话」：每条会话的日志都是线性且不可变的，不需要过滤器，也不存在「绕过」的可能。代价是用户想撤销一句话时，得到的是一个新会话，而不是原会话回到过去。两家在同一个问题上的分歧，本质是「一条日志装多条时间线」还是「一条日志只装一条时间线」。

没有绝对的对错。前者适合需要完整审计轨迹、又希望磁盘上只有一份文件的团队；后者适合把「会话」当成不可变事实、宁可多复制几份也不愿引入隐式规则的架构。判断依据是同一个问题：你更怕文件膨胀，还是更怕有人读到了不该读的历史？

06 · 思考题

三道题，从推演到设计

Q1

日志依次是：轮 0、轮 1、轮 2、marker→1、轮 3、marker→1。过滤后剩下哪几轮？如果把最后一条换成 marker→9（不存在），又会剩下哪几轮？

提示（不给答案）

顺序扫描，维护 result 与 prompt_starts。第一个 marker 把 result 截到轮 1 的起点，prompt_starts 也截到长度 1（只剩轮 0 的起点）。

之后轮 3 被压进 prompt_starts，成为新的第 1 项。所以第二个 marker→1 截的是轮 3 的起点——它把轮 3 也丢掉了。

越界那条看 unwrap_or(result.len())：取不到就截到当前长度，等于不截。此时 prompt_starts 长度是 2，get(9) 取不到，所以轮 0 与轮 3 都留下。

Q2

如果去掉 filter_rewind_lines 开头的子串预检，功能还正确吗？会损失什么？如果去掉 tracker.on_non_user() 呢？

提示（不给答案）

预检只是跳过解析，不改变结果——它是一道性能优化。想一下：一个没有回退的普通会话，每次恢复要解析多少行 JSON？这个预检把它降到了多少次字符串比较？

on_non_user 影响的是「run 的边界」。去掉它，marker 之后的第一条用户消息会被当成上一轮的续写，on_user_chunk 返回 false，prompt_starts 少压一项。这个错位会在什么时候暴露？

Q3

你要给自己的 Agent 加回退。选「删日志」「追加标记」「复制分叉」中的哪一种？请给出你的选择，以及你会怎么防止「绕过过滤器」这个坑。

提示（不给答案）

三个维度打分：实现成本、磁盘成本、误用风险。删日志最省空间但不可审计；标记最省空间且可审计，但所有读路径都要遵守约定；分叉最安全（互不影响），但每次复制。

防绕过的常见手段有三种：把「读日志」收敛成一个返回「当前时间线」的函数，不暴露原始行；在文件名或目录上区分「原始日志」与「视图」；或者像 dsh 那样，让模型可见历史完全由 deriveMessages() 派生，根本没有第二条读路径。

最后想一个反例：如果你把过滤器放在「写」的路径上（回退时重写文件），会失去什么？
