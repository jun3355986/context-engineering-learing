16 类 × 8 工具总表

这张表是整本教程的压缩版：行是 16 类上下文能力，列是 8 个工具，每格一句话结论加可信度与来源缩写。它不替代正文，只帮你快速定位「谁做了什么、这个结论有多硬」。

读法

每格格式是一句话结论【可信度 · 来源】。来源缩写：c=Codex、cc=Claude Code、p=pi、o=oh-my-pi、v1=opencode v1、v2=opencode v2、g=Grok Build、d=DeepSeek Harness；§n 指该工具事实卡片的第 n 节。

Claude Code 的「已核实」均指 v2.1.88 源码；需要与官方文档交叉核对时，正文另标来源类型。「无此能力」是结论，不是「没查到」。整格空白只出现在确实没有该机制的 5 处；半空白（只覆盖一部分场景）按部分能力写，不写成有。

02 · 读矩阵的三个提醒

别把「一行」当成「一个结论」

一、哪些格子是推断

标【推断】的 10 格集中在 dsh（第 1、3、4、6、9、10、13、16 类）和 opencode v1/v2 的评估（第 16 类）。dsh 的推断来自同仓 docs/subsystems 与各包 README，不是逐行源码；它能说明「设计意图与开关」，但不能当作「运行时一定如此」。opencode 两版的评估格是「没找到评测框架」的否定式判断，属于推断而非已核实。1

另有 1 格【待核实】：opencode v1 是否有 /context 类视图，卡片只检索了出货 packages/opencode/src，没有穷举前端命令表。其余 8 份卡片内部共 22 条【待核实】细节（如 Codex worktree 隔离、pi/omp 单文件字节上限、Grok Build 官方记忆文档 404）没有升格成整格待核实，写章节时要带进脚注。2

二、哪些工具在某类上是空白

整格「无此能力」的有 5 处：pi 的子代理（第 10 类）与跨会话记忆（第 12 类）；opencode v1 的记忆（第 12 类）；opencode v2 的记忆（第 12 类）；dsh 的记忆（第 12 类）。

半空白要按「部分能力」写，不能写成有：Codex 没有独立的历史裁剪通道、没有历史转图、没有内置评测（第 7、9、16 类）；opencode v1/v2 没有树状多分支和 rewind（第 11 类）；dsh 没有 rewind/undo（第 11 类）；pi 没有自动裁剪（第 7 类）、没有图片驱逐（第 9 类）。同一类里「有机制」与「默认开启」是两件事：Claude Code 的 microcompact 默认关闭、omp 的记忆默认 off、Grok Build 的记忆默认 off，矩阵写的是机制存在，不是默认生效。

三、跨版本对比要注意什么

  • opencode v1 与 v2 是同一仓库的两个 tag，不能互相外推：v1 引 733b2c6，v2 引 042d083；v2 是 beta，字段与默认值可能在下个版本变化。
  • omp 是 pi 的 fork。同源代码不等于同默认值：阈值从「固定 16384 预留」改成「窗口 15% 下限」，压缩从单函数改成五方法链，记忆/子代理/checkpoint 是新增而非改进。
  • Claude Code 全部结论只代表非官方源码 v2.1.88，且函数名可能来自 source map 还原；与官方文档冲突的 4 处见下表，正文必须标【可能已变化】。
  • Grok Build 没有语义化版本号，只有仓库提交与 SOURCE_REV（monorepo SHA）；矩阵里的「Grok Build」指本快照，不指线上最新版。
  • Codex 与 dsh 用的是滚动 main/master 快照，不是发布版；引用时必须带提交号。
