# 评测：第 20 章两步改写（先核查，再改写）

> 第 1、2、5 节给作者看；第 3、4 节的提示词原样复制给被测 agent，**两步各开一个新会话**。
> 评分仍用 `评测-第20章-评分表.md`，另外看 `hedge` 的数字。不要让被测 agent 看到评分表、问题清单、口径表和修订方案。

## 1. 为什么分两步

第一轮 GPT 改写（提交 `652416e`）内容纠错做得好，但限定语从每千字 0.9 处涨到 7.9 处，读起来很累。论文 *Defensive Writing in GPT Models*（arXiv 2610.11355）的结论是：提示词要求核查说法时，模型会大量加限定；只要求润色时，所有被测模型都基本不加。所以把两件事拆开：

| 步骤 | 做什么 | 提示词的框法 | 限定语去哪 |
|---|---|---|---|
| 第 1 步 核查 | 对照源码找错，写成核查清单，另抽一张替换表 | 「核查」「找错」 | 清单末尾的「保留意见」，不进正文 |
| 第 2 步 改写 | 按替换表换句子，再改表达 | 「换句子 + 改写表达」，不提核实和审稿 | 替换表之外不新增；想加的写进汇报 |
| 兜底 | `hedge` 和改前比，超标逐句处理 | — | — |

论文里有三个结果直接决定了第 2 步的写法：

- **第 2 步只看替换表，不看完整清单。** 论文让模型先审稿、列出弱点，再按审稿意见修改。这一轮下来，所有模型的限定都比单次改写多得多，Claude 也一样；GPT 还会撤回 11–25% 的原有论断，连续三轮后段落长到原来的两到三倍。「按核查清单改」就是这种结构。清单里的「问题」「依据」「保留意见」读起来就是审稿意见，所以第 2 步只拿「原文 → 改成」。
- **第 2 步不判断说法强弱，只守一条硬规则。** 论文试过「每个论断按证据支持的强度来写」，GPT-6-astra 的限定只降了一半，GPT-5.5 一点没降。要求模型判断强弱，本身就是在让它核查。按论文的定义，写作者手里的材料支撑不了的限定就是防御性的。第 2 步的材料只有原稿和替换表，所以替换表之外新加的限定一律不要。
- **超标后不要让它「再检查一遍」。** 论文里每多一轮自审，限定就多一些。超标时按第 5 节的做法，只删你挑出来的句子。

兜底还是需要：论文里只给事实清单、让模型自己写结论时，最强的 GPT 仍然加得最多。如果第 2 步用 GPT 反复超标，就换一个模型做第 2 步，第 1 步仍然可以用 GPT。

## 3. 第 1 步提示词：核查（原样复制）

````text
你要核查一份中文技术教程里的一章，找出内容错误，整理成一份核查清单。这一步不改页面，改写会在另一个会话里做。

## 背景

- 教程在 `ai codiing 工具上下文对比报告/第三版/tutorial/`，是一组静态 HTML 页面，主题是编码智能体（coding agent）的上下文管理，对比了 8 个 agent（Codex、Claude Code、pi 等）的实现。
- 本次核查第 20 章「缓存友好设计」，文件是 `tutorial/pages/main-13.html`：正文 6 节、7 个 agent 弹窗、一张对比表、设计取舍和 3 道小测验。
- 第 5 章（`intro-05.html`）讲前缀缓存和失效点，第 6 章（`intro-06.html`）讲用户怎么管理上下文、各种做法的成本。本章要和这两章一致；有冲突时以有出处的一方为准。
- 页面里的源码链接都固定到了具体提交；调研笔记在 `第三版/research/`。

## 什么算错误

判断标准只有一条：读者照原文理解，或者照着去做，会不会得出错误的结论。会，就列进清单。常见的有：

- 数字、公式、算例算错，或者算例的假设不成立；
- 对 agent 行为、计价方式的描述和源码或文档不符；
- 结论说过了头：源码只支持一部分，原文说成了全部；
- 链接指向的代码和正文说的不是一回事；
- 和第 5、6 章矛盾；
- 小测验的答案错了，或者引用了正文里没有的说法。

原文说得对、只是没把所有前提都写出来的，不算错误，不进表格。你想补充的前提和提醒，写进清单末尾的「保留意见」。

公式和算例要自己重算一遍。同一个错误在页面里出现几次，就列几条，每条写清位置。

## 产出一：`第三版/review/核查-main-13.md`

一张表，每个错误一行：

| # | 位置 | 原文 | 问题 | 正确说法 | 依据 | 进正文的方式 |

- 位置：节号或弹窗名，加上原文开头几个字，方便定位。
- 正确说法：写成能直接放进教程的陈述句，一到两句。不写「不能据此认定」「仍取决于后端」这类限定；拿不准的部分，用「进正文的方式」这一列处理。原文说得太宽时，写出具体条件（哪个 agent、哪个版本、哪个参数），不写「在本章所查版本中」「视实现而定」这类不点名的范围。需要新的源码链接时，把链接写进这一列。
- 依据：源码链接（带行号）、文档链接，或者你重算的过程。
- 进正文的方式：只能填一种：直接陈述 / 加【推断】标签 / 加【待核实】标签和脚注 / 只写进汇报。

表格后面再写两节：

- 保留意见：够不上错误、但你想提醒的地方。这一节不会进正文。
- 没能核实的：查了什么，缺什么。

## 产出二：`第三版/review/替换-main-13.md`

从核查清单里抽出要改正文的行，交给下一步改写用。只要一张表，不写别的：

| # | 位置 | 原文 | 改成 | 方式 |

- 「改成」照抄核查清单的「正确说法」；「方式」照抄「进正文的方式」。
- 「只写进汇报」的行不抄。问题描述、依据、保留意见、没能核实的，都不抄。

## 约束

- 不改 `main-13.html`，也不改其他页面。
- `review/` 目录里只用 `tools/` 下的脚本，不读其他文件；不看 git 历史和其他分支。
- 不提交 git。

可用脚本（在 `第三版/` 目录下运行）：`python3 -I review/tools/prose_check.py text main-13` 抽出正文，加 `--modals` 抽出弹窗。

## 交付

用中文简短汇报：一共找到几条错误，各按哪种方式进正文；替换表有几行；哪些没能核实；在其他章节发现的问题。
````

## 4. 第 2 步提示词：改写（新会话，原样复制）

````text
你要改写一份中文技术教程里的一章，让它好读、好懂。需要换掉的句子已经列在一张替换表里；你负责把它们换进去，再改全章的表达。

## 背景

- 教程在 `ai codiing 工具上下文对比报告/第三版/tutorial/`，主题是编码智能体（coding agent）的上下文管理，对比了 8 个 agent 的实现。
- 本次改写第 20 章「缓存友好设计」，文件是 `tutorial/pages/main-13.html`：正文 6 节、7 个 agent 弹窗、一张对比表、设计取舍和 3 道小测验。
- 读者：有多年 Java/Spring 后端经验，熟悉软件工程，没读过这些 agent 的源码。他会照着教程理解机制、做判断，需要明确的说法。
- 第 1–6 章已经改好（`tutorial/pages/intro-01.html` 到 `intro-06.html`），可以参照它们的写法和语气。第 5 章讲前缀缓存和失效点，第 6 章讲各种做法的成本。
- 写作规范在 `tutorial/CONVENTIONS.md`。必读：§3 的「小节衔接」「篇幅基准」「阅读时长」；§4 的「中文表达」；§9 可信度标签；§10 Head First 卡片。不必通读。限定语以下面「要做的」第 3 条为准，和 CONVENTIONS 不一致时听这里的。

## 要做的

1. 换句子。`第三版/review/替换-main-13.md` 每一行：在「位置」找到「原文」，换成「改成」那一列的句子；「方式」是加标签的，按要求加【推断】或【待核实】和脚注。为了和上下文接顺，可以调整措辞和语序，意思不变，也不另加限定。你觉得某一行有问题，这一行先不换，在汇报里写明理由。
2. 改表达，目标是读起来像中文母语的技术作者写的：
   - 场景引入写具体：时间、频率、后果，让读者先有画面；
   - 行话第一次出现时给一句白话；
   - 每节第一句接住上一节的落点；
   - h2 标题直接说这一节讲什么，不写对联式、谜语式的标题；
   - 比喻沿用全书已定的：上下文窗口是一块白板；缓存比较是两排方块从第一块开始比，第一处不同的位置叫失效点；
   - 栏目名「没有傻问题」改成「你可能会问」；
   - 写作过程、页面怎么维护这类理由，读者不需要，从正文删掉；
   - 不用英文直译的词（比如把 shape 写成「形状」、knob 写成「旋钮」），不给模型安上情绪和性格；「本质上」「真正」「关键在于」「这意味着」这类口头禅，删了不丢意思的就删。
3. 限定语：替换表之外，不新增任何限定。「不能据此」「不一定」「仍取决于」「在本章所查版本中」这类话都算。原稿已有的限定保持原样。你觉得哪里非加不可，正文里不加，写进汇报。

## 约束

- 不按词表批量替换。「不是……而是」大多在纠正读者真会有的误解，只有同一段里连用两次以上，或者被否定的说法读者根本不会那样想时才改。
- 只改 `main-13.html`。在其他页面发现的问题写进汇报。
- 不改结构和组件：不增删小节；弹窗 id、链接、class 都不变；不新增 class，不写内联 style；不改 `assets/` 下的文件。
- 数字、源码链接、【已核实】【推断】【待核实】标签、脚注、测验都保留，替换表要求改的除外。
- 正文字数变化不超过 ±15%；页头的阅读时长按 CONVENTIONS §3 的公式重算。
- `review/` 目录里只读 `tools/` 下的脚本和 `替换-main-13.md`；不看 git 历史和其他分支。
- 不提交 git。

## 自检（在 `第三版/` 目录下运行）

```
python3 -I review/tools/prose_check.py check main-13    # 标签配对、h1、重复 id
python3 -I review/tools/prose_check.py time  main-13    # 阅读时长，和页头对比
python3 -I review/tools/prose_check.py scan  main-13    # 可疑措辞计数
python3 -I review/tools/prose_check.py terms main-13    # 行话第一次出现的位置
python3 -I review/tools/prose_check.py hedge main-13    # 限定语，和改前比
```

`hedge` 列出的新增限定句，应该都来自替换表。不是来自替换表的，删掉限定那部分，句子里的内容保留，不另加词。`hedge` 显示「超出」时不要交付。换一种说法绕开脚本不算处理。

## 交付

用中文汇报，按下面的顺序写：

1. 一句话结论：改了什么，没改什么。
2. 替换情况：每一行换在了哪里；没换的写理由。
3. 表达：按小节列出主要改动，每节 1–3 条，附 2–3 处改前、改后的对照。
4. 限定语：`hedge` 列出的新增限定句各来自替换表第几行；你觉得该加、但按规则没加的地方，逐条写出位置和理由。
5. 自检结果：check、time 的结果；scan、hedge 改前改后的数字。
````

然后：

- **内容**：按评分表 A1–A5 打分，和第一轮比。两步法的风险是第 1 步漏掉的错误第 2 步不会补，所以 A 项分数要重点看。
