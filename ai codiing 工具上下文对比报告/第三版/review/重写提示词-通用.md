# 重写提示词 · 通用版

> 适用：已有稿件要重写成"读得下去"的版本。区别于 `评测-第20章-两步改写提示词.md`——那份是第 20 章专用、且假设前面跑过核查；这份通用，自带诊断，不依赖替换表。

> **要动结构和标题的，不要用这份**，用 `整章重写提示词.md`。这份只管词句层，结构不动。

**版本**：v1 ｜ 2026-10-26

---

## 1. 为什么需要这份

项目里已有 `问题清单.md` C1–C11、`评测-第20章-两步改写提示词.md`、评分表、`prose_check.py`，流程是完整的。这份补的是其中缺的一块：**具体哪些词组算"奇怪"**。

原因："避免英文直译"这种指令，模型只能修它认识的那几个词。全站 91 处直译词，靠一句原则改不动 20 处。"形状""旋钮""发键""认账""同一道缝，七种开法"这些词，单看每个都是正常中文，不点名就识别不出来。

**依据**：直译词对照表全部来自 `问题清单.md` C1（附实测处数）；"一句一个主张""不超过 25 字"来自 Google 技术写作课程与《Style》；"每段补一句承接"对应《Style》的旧信息在前、新信息在后；"拆长句"对应问题清单 C9。诊断和重写的分段方式由编辑实务推得，无书目依据。

---

## 2. 两条前提

**（1）不要在任何一步提"核查""审阅""找错"。**

`问题清单.md` C11 引的论文（*Defensive Writing in GPT Models*，arXiv 2610.11355）已经测过：提示词里出现这类要求，限定语会成倍增长。第 20 章第一轮就是这样从每千字 0.9 处涨到 7.9 处。重写提示词里连"确保准确"都不能写。

**（2）字数不变要更易读，只能重新分配篇幅。**

规范要求 ±15%、不砍信息密度。那唯一的空间是：砍掉重复段和可推断段，补给需要解释的地方。不这么干，就只能靠加形容词凑，越改越密。

## 3. 第 1 段：诊断（原样复制）

```
你要改一份中文技术教程里的一章。内容是对的，问题是读者读起来吃力。
先不要改，读完输出一张诊断表。

读者：有多年 Java/Spring 后端经验，熟悉软件工程，没读过这些 agent 的源码。
判断标准只有一条：他读到这里会不会停下来想「这是什么意思」。会，就改。

输出一张表，不超过 15 行：
| 位置 | 原文（开头 8 字） | 为什么卡 | 类型 |

类型只能填这五种：
- 直译词：英文说法硬搬成中文，中文读者没有这个联想
- 名词化：把动作写成名词，句子失去主语和动作
- 缺复述：上一段讲到哪没说，直接进新内容
- 长句：一句话里三件事以上
- 比喻混用：同一件事前后用了两个比喻

只列会让读者停下来的，不列"可以更严谨"的。
```

## 4. 第 2 段：重写（原样复制）

```
按诊断表重写这一章。四个动作，按顺序做：

1. 换直译词。逐条对照下面的表，上下文里读着别扭就换：
   形状 → 格式 / 结构 / 方式（说曲线、图形的不改）
   旋钮 → 可调参数；杠杆 → 办法 / 着力点
   复利 → 越积越多；爆炸半径 → 影响范围
   买（buy）→ 求 / 要 / 换
   到场、说话 → 被加载 / 拼接
   钉住（pin）→ 用测试固定
   第一性原理 → 基本道理；默认面 → 默认功能
   发键、认账 → 发缓存键 / 读缓存用量
   缝、开法 → 扩展点 / 开放程度
   最粗、有哪些手 → 最大 / 有哪些工具可用
   面（surface）→ 接口 / 功能
   打点 → 分两种：讲「记录指标」的可留；讲「标记位置」的改成 标记 / 定位
   翻转 → 切换；锁存 → 固定住
   护栏 → 底线指标（保留，但第一次出现要解释）

   注意「形状」：全站 60 处，约一半讲的是图形、曲线、界面的形状，
   那些不改。改成「格式 / 结构 / 方式」的只有讲 API 返回、数据包、
   截断策略的那类（「Responses API 的形状」→「Responses API 的格式」）。
   这一条最容易被机械替换弄坏。

2. 名词化还原成动词：
   「对上下文进行压缩」→「压缩上下文」
   「完成对历史的裁剪」→「裁掉历史」
   「进行一个判断」→「判断」
   凡是「进行 / 完成 / 实现 + 名词」的，先试删掉前面那个动词。

3. 每段开头补一句承接。一句话复述上一段落点，再进新内容。
   只补这一句，不要补过渡段。

4. 拆长句。超过 40 字、含两个以上逗号从句的，拆成两句。
   一句只说一件事。

不要做的：
- 不加新信息，不删原有的事实、数字、链接、标签、脚注
- 不新增限定语（「不能据此」「仍取决于」「在本章所查版本中」）
- 不按词表机械替换：「不是……而是」多数在纠正读者真会有的误解，
  只在同段连用两次以上时才改
- 不写对联式、谜语式标题，标题直接说这一节讲什么
- 结构、小节、弹窗、class 都不动
```

## 5. 第 3 段：复核（原样复制）

```
改完了，只做三件事，不要重写第二遍：

1. 列出仍然读起来卡的地方，每处写一句为什么，不改。
2. 报告字数变化，以及你在哪几节砍了内容、补了内容。
3. 报告哪些直译词你判断不该换，理由是什么。

不要通读检查有没有事实错误。这一步不做核查。
```

最后那句不能删。不写它，模型会自动开始核查，限定语就上来了。

## 6. 配套的机械动作

改前改后各跑一次，数字进汇报：

```bash
cd "ai codiing 工具上下文对比报告/第三版"
python3 -I review/tools/prose_check.py scan  <id>    # 直译词、口头禅、长句计数
python3 -I review/tools/prose_check.py hedge <id>    # 限定语，默认和 HEAD 比
python3 -I review/tools/prose_check.py time  <id>    # 阅读时长，页头要同步
python3 -I review/tools/prose_check.py check <id>    # 标签配对、重复 id
```

`hedge` 比改前多出超过 1 处，就说明第 3 段那句没守住，或者重写时偷偷核查了。

## 7. 还缺什么

这份只处理"读起来吃力"和"奇怪词组"，不处理：

- **事实错误**（数字、公式、算例）——那是核查步骤的事，见第 20 章两步法第 1 步
- **跨章口径不一致**——以 `review/口径表.md` 为准
- **行话没解释**——`prose_check.py terms <id>` 会列出首现位置，按 `口径表.md` §4 补白话

三件事分开做。混在一次里，模型会为了"顺便检查"而加限定。
