# 教程修订 · 问题清单

> 用途：每个修订批次开工前读一遍；改完按「怎么查」自检。修订中发现新的问题类型，补到对应分类末尾，并写明出处。
> 来源：作者在 `docs/上下文教程修订.md` 里标出的句子（2026-10-21）、第 1–3 章试点修订、第 4–5 章修订反馈、第 6 章重写，以及 2026-10-24 的全书抽查。
> 自检命令都在 `review/tools/prose_check.py`，用法见脚本开头。

## 速览

- 问题分四类，修订时按 **A 事实与口径 → B 讲解断层 → C 中文表达 → D 页面一致性** 的顺序判断。
- 本轮的重点是 C：读起来自然、好懂、不别扭。但 A 类问题一旦发现就必须修。作者目前还没法自己判断内容对不对，内容错了，文字再顺也没用。
- 2026-10-21 的教训：当时按词表批量改写「不是……而是」，改完反而更不顺，最后全部回退。所以 C 类问题要逐句判断读者会不会卡住，不按词表替换。

**A3 说明：第 20 章 §2.4 的公式（已手算核对）**

原文假设 B=180k、P=30k、A=45k、r=0.1、w=1.25，算出「一次性多付 172.5k、之后每次省 121.5k、约 1.4 次回本」。这里有两处错误：

1. `invalidate = (B − P)(w − r)`：压缩之后旧历史就不再发送了，需要重新写入缓存的是摘要和保留段，也就是 `A − P`，而不是 `B − P`。
2. `savePerCall = (B − A)(1 − r)`：如果不压缩，这 `B − A` 的部分本来就会命中缓存，按 `r` 计价，不是按全价 1 计价。所以每次能省下的是 `(B − A)·r`。

按口径表 §3 重算：压缩后第一次请求比继续多付约 3.75k，之后每次省 13.5k。真正的一次性成本是压缩请求本身，主要花在摘要输出上，而原公式恰好把这一项排除了。结论「任务只剩一轮时不该压」仍然成立，但原因不是缓存失效，而是压缩请求本身的花费。这一节由第 14 批负责改，改法以口径表 §3 为准。

## C. 中文表达（本轮重点）

判断标准只有一条：**一个懂软件工程、但没读过这些源码的中文读者，读到这里会不会停下来想「这是什么意思」。** 会停下来，就要改。

### C1 英文直译词（全站 91 处）

| 直译 | 原稿例子 | 建议写法 |
|---|---|---|
| 形状（shape），57 处 | 「Responses API 形状」「截断形状」「返回形状」「任务形状」 | 格式、结构、方式、类型，按语境选。说曲线、图形的「形状」不用改 |
| 旋钮（knob），9 处 | 「保留量才是切点的主要旋钮」 | 可调参数、调节手段 |
| 杠杆（leverage） | 「都是比『少说两句』有效得多的杠杆」（作者标注）；第 23 章「拆不开，就找不到杠杆」 | 更有效的办法、着力点 |
| 复利（compound），4 处 | 「错误会跨会话复利」 | 错误会在之后的每次会话里重复出现，越积越多 |
| 爆炸半径（blast radius） | 「失效的爆炸半径」 | 影响范围 |
| 买（buy） | 「A 买确定性，B 买保真度」 | A 求稳，B 要保留细节 |
| 到场、说话 | 「哪几份会同时到场、按什么顺序说话」 | 哪几份会同时被加载、按什么顺序拼接 |
| 钉住（pin） | 「测试专门钉住这个语义」 | 用测试固定了这个行为 |
| 发键、认账；缝、开法 | 第 20 章标题「发键，认账」；第 22 章「同一道缝，七种开法」 | 直接写内容：「发送缓存键，读回缓存用量」「同一个扩展点，七种开放程度」 |
| 最粗、有哪些手 | 第 3 章原稿「排出谁最粗」；第 2 章原稿「有哪些手」（作者标注） | 最大、有哪些工具可用 |
| 第一性原理、默认面 | 「渐进披露的第一性原理」「把默认面压到最小」 | 基本道理、默认功能 |

`护栏`（guardrail metric）是 A/B 实验的常用词，可以保留，但第一次出现时要解释：「不能变差的底线指标，一旦变差就不上线」。

### C2 拟人：给模型安上情绪和性格

| 原稿 | 问题 | 改法 |
|---|---|---|
| 「模型通常只会热情地记录，不擅长怀疑自己」（第 19 章） | 读者会去想模型的「性格」，而不是机制 | 写清楚它拿到了什么信息、缺什么：「写入时没有校验步骤，旧记忆也没有过期机制」 |
| 「它觉得『我记得大概长什么样』」（第 16 章） | 同上 | 「模型手里只有路径，没有图片，它不会主动去读」 |
| 「模型可以在上下文快满时仍然觉得『再读一个文件就好』」（第 3 章原稿，作者标注） | 同上 | 「模型看不到窗口还剩多少，快满时照样会继续调用工具读文件」 |

「模型会以为工具返回了空」这类句子可以保留：它讲的是模型缺了什么信息，读者一看就懂。

### C3 比喻没落到实处、混用或太粗俗

- **说不清的比喻**：「两条线在同一个地方刹车」（第 3 章原稿，作者标注「这句话我看不明」）。改成直接陈述：「两条阈值线都设在窗口上限之前，各留了一段余量」。
- **同一件事换着比喻**：第 1–3 章原稿里，上下文窗口一会儿是「白板」，一会儿是「桌子」「一沓纸」，试点修订时已统一成白板；缓存比较在第 5 章是「方块」，到第 20 章又变成了「积木」。全书主比喻以口径表 §1 为准，一个比喻只用来说明一件事，说完立刻回到真实机制。
- **太粗俗**：「后面每一段都在替它擦屁股」（第 7 章）。改成「后面每一段都得替它补救」。

### C4 量词和说法含糊

- 「它们单条不大，但每轮都加」（第 3 章原稿，作者批注：已经加载过的还会加吗？）。要写清楚是「每轮新增一条」，还是「每轮请求都重新发送一遍」。
- 遇到「每轮」「每次」，要说明指的是用户的一轮，还是模型的一次请求。一轮用户对话里通常有多次请求。

### C5 标题写成对联或谜语

CONVENTIONS 要求标题直接说明本节内容或结论，但主线 16 章有不少对仗标题，读者从标题里看不出这一节讲什么：

- 「客户端只做两件事：发键，认账」「同一道缝，七种开法」「五个决策，三种绝境」「七种收场」
- 每章都套同一个模板：「三道题，检验你是否真的会 X」「同一棵树，七种走法」「为什么没有一种 X 通吃」

改法：标题直接写本节讲什么或结论是什么，比如「Codex 客户端只管两件事：发缓存键、读缓存用量」。测验节可以统一叫「小测验」，不必每章换一个说法。

### C6 直译的栏目标签

- 「没有傻问题」直译自 Head First 的「There are no Dumb Questions」，作者标注过，全站共 11 页使用。建议统一改成「你可能会问」（由第 0 批执行，同时改 CONVENTIONS §10 的模板）。
- 「收口」（第 6、7 章节标签）：直接写这一节讲什么，或者用「小结」。

### C7 口头禅（全站 142 处）

「本质上」「真正」「关键在于」「这意味着」「换句话说」。删掉后意思不变的就删；删掉后句子接不上的就保留。不定数量目标。

### C8 「不是……而是」句式（全站 168 处）

上一轮的结论仍然有效：大部分是在纠正读者真实会有的误解，删了会伤内容。只在下面两种情况下改：

1. 同一段里连着用了两次以上，读起来像在填表；
2. 被否定的那个说法，读者根本不会那样想（稻草人）。

### C9 长句（全站 424 句超过 60 字）

只拆用分号串起三四件事的长链、括号套括号的句子。一句话只说一件事。

### C10 引号

现在入门、主线、进阶部分用 “”，源码和附录部分用「」，两套各自基本统一；有 15 页混用了两种。不做全站替换，只把混用的页面统一成所在部分的主流写法，改到哪一页就顺手统一哪一页。

### C11 防御性限定（2026-10-25 新增）

对照源码改写时，正文里堆出「不能据此推定」「仍取决于后端」「不一定」「有机会」。第 20 章第一轮 GPT 改写后，这类句子从每千字 0.9 处涨到 7.3 处，场景被冲淡，结论被埋住。规则见 CONVENTIONS §4「限定语」，用 `hedge <id>` 和改前比。

背景：论文 *Defensive Writing in GPT Models*（arXiv 2610.11355）发现，提示词要求核查说法、提到审稿意见时，这类限定明显增多；只要求润色时基本不增。增量大多是「……并不能证明……」这类句子，抽检中多数是多余的，但也有约三成有道理，所以要逐句判断，不能批量删。
