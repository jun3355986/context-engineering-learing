# 评测：让不同 agent 改写第 20 章

> 给作者自己看的部分是第 1、2 节；第 3 节的提示词原样复制给被测的 agent。
> 评分标准在 `评测-第20章-评分表.md`。**不要让被测 agent 看到评分表**，也不要让它读到 `问题清单.md`、`口径表.md`、`修订方案-2026-10-24.md`，这三份里都写了本章的答案。

## 1. 为什么选第 20 章

第 20 章（`main-13.html`，缓存友好设计）四类问题都有，适合拉开差距：

- **内容**：有一处要动手重算才能发现的计算错误，而且同一个错误在页面里出现了好几次；另外还有和第 5 章矛盾的地方。只会润色文字的 agent 发现不了这些。
- **讲解**：有几个行话没有解释；有一段页面维护的理由漏进了正文。
- **表达**：有谜语式标题、和前文不一致的比喻、直译的栏目名。
- **规模**：正文约 6,500 字，加上 7 个弹窗、一张对比表和 3 道测验，一个会话能做完，又不至于太小。

## 2. 准备测试环境（每个 agent 一份）

每个 agent 在单独的 git worktree 里改，互不影响，事后可以逐个 diff。在仓库根目录运行：

```bash
cd /home/ubuntu/work/context-engineering-learing
NAME=agentA                      # 每个 agent 换一个名字
WT=../eval-ch20-$NAME
git worktree add -b eval/ch20-$NAME "$WT" HEAD

# 只给自检脚本，删掉写了答案的文档（如果这些文档已经提交过，worktree 里也会有）
SRC="ai codiing 工具上下文对比报告/第三版/review"
DST="$WT/$SRC"
mkdir -p "$DST/tools"
cp "$SRC/tools/prose_check.py" "$DST/tools/"
rm -f "$DST/问题清单.md" "$DST/口径表.md" "$DST/修订方案-2026-10-24.md" "$DST/评测-第20章-评分表.md" "$DST/评测-第20章-改写提示词.md"
```

然后在 `$WT` 目录里启动被测 agent，粘贴第 3 节的提示词。

- 各个 agent 都从同一个提交（当前 HEAD）出发，条件一致。
- 被测 agent 能联网的话，会去点页面里的 GitHub 源码链接核对。不能联网的 agent 只能依靠 `research/` 里的笔记，比较结果时把这一点考虑进去。
- 评完不要的 worktree，用 `git worktree remove --force ../eval-ch20-$NAME` 和 `git branch -D eval/ch20-$NAME` 清理。

## 3. 提示词（原样复制）

````text
你要修订一份中文技术教程里的一章。请先通读本提示，再动手。

## 背景

- 教程在 `ai codiing 工具上下文对比报告/第三版/tutorial/`，是一组静态 HTML 页面，主题是编码智能体（coding agent）的上下文管理，对比了 8 个 agent（Codex、Claude Code、pi 等）的实现。
- 读者：有多年 Java/Spring 后端经验，熟悉软件工程，但没读过这些 agent 的源码。他正在学这个主题，自己没法判断教程内容对不对。
- 本次只改第 20 章「缓存友好设计」，文件是 `tutorial/pages/main-13.html`。这一章包括正文 6 节、7 个 agent 弹窗、一张对比表、设计取舍和 3 道小测验。
- 第 1–6 章已经修订过（`tutorial/pages/intro-01.html` 到 `intro-06.html`）。第 5 章讲前缀缓存和失效点，第 6 章讲用户怎么管理上下文、各种做法的成本。本章的说法要和这两章一致；如果有冲突，以有出处的一方为准，并在汇报里说明。
- 写作规范在 `tutorial/CONVENTIONS.md`。重点读 §3（小节衔接、篇幅、阅读时长）、§4（正文排版）、§9（可信度标签）、§10（Head First 卡片），不必通读。
- 调研笔记在 `第三版/research/`，页面里的源码链接都固定到了具体提交。

## 目标（按优先级）

1. **内容正确**。页面里关于 agent 行为、计价和计算的说法，能核实的都要核实：点开页面里的源码链接，或者查 research 笔记。公式和算例要自己重算一遍，并检查假设是否成立。核实不了的标【待核实】，不要猜。发现错误就改正，并在汇报里写明原来错在哪、依据是什么。同一个错误如果在页面里出现了多次，每一处都要改。
2. **好懂**。读者要能顺着读下去：行话第一次出现时给一句白话解释；小节之间接得上；产品细节不打断主线，数字和细节可以移到段尾、补充框或弹窗里。
3. **中文自然**。读起来要像中文母语的技术作者写的。具体要避免：
   - 英文直译的词，比如把 shape 写成「形状」（「返回形状」「截断形状」）、knob 写成「旋钮」、leverage 写成「杠杆」、compound 写成「复利」、blast radius 写成「爆炸半径」；
   - 给模型或程序安上情绪和性格，比如「模型热情地记录，不擅长怀疑自己」；
   - 说不清的比喻，或者同一件事前后换着比喻。全书已经定下的比喻是：上下文窗口是一块白板（第 1、3 章）；缓存比较是两排方块从第一块开始比，第一处不同的位置叫失效点（第 5 章）；
   - 对联式、谜语式标题。别的章里的「同一道缝，七种开法」「五个决策，三种绝境」就属于这种。h2 标题要让人只看标题就知道这一节讲什么；
   - 直译的栏目名，比如 Head First 的「没有傻问题」，建议改成「你可能会问」；
   - 写作过程或页面维护的理由漏进正文。读者不需要知道这一页是怎么维护的；
   - 口头禅，比如「本质上」「真正」「关键在于」「这意味着」。删了不丢意思的才删。
4. **完整**。不丢信息：来源链接、参数、【已核实】【推断】【待核实】等标签、脚注、测验都要保留。

## 约束

- **不要按词表批量替换**。之前有人按词表把「不是……而是」句式统一改写过，作者读后觉得更不顺，已经全部回退了。这类句式大多是在纠正读者真实会有的误解，只有两种情况才改：同一段里连用了两次以上；或者被否定的那个说法，读者根本不会那样想。
- **只改 `main-13.html`**。在其他页面发现的问题写进汇报，不要去改。
- **不改结构和组件**：不增删小节；弹窗 id、链接、class 都不变；不新增 class，不写内联 style；不改 `assets/` 下的 css 和 js。
- **篇幅**：正文字数变化一般不超过 ±15%。
- **阅读时长**：页头的阅读时长按 CONVENTIONS §3 的公式重算。
- **只用这些材料**：`review/` 目录里只用 `tools/` 下的脚本，不读其他文件；也不要去看其他 git 分支。
- **不要提交 git**。

## 可用的自检脚本

在 `第三版/` 目录下运行：

- `python3 -I review/tools/prose_check.py text main-13`：抽出正文纯文本；加 `--modals` 抽弹窗
- `python3 -I review/tools/prose_check.py scan main-13`：统计可疑措辞
- `python3 -I review/tools/prose_check.py hits <类别或正则> main-13`：列出命中的句子
- `python3 -I review/tools/prose_check.py terms main-13`：列出行话第一次出现的位置
- `python3 -I review/tools/prose_check.py time main-13`：按公式算阅读时长
- `python3 -I review/tools/prose_check.py check main-13`：检查标签配对、h1 和重复 id

脚本命中不等于有错，要逐条判断。

## 交付

改完后用中文汇报，按下面的顺序写：

1. 一句话结论：改了什么，没改什么。
2. 内容错误：每条写「原文怎么说 → 改成了什么 → 依据」，依据可以是源码链接、文档，或者你重算的过程。
3. 讲解与表达：按小节列出主要改动，每节 1–3 条，并附 2–3 处改前、改后的对照。
4. 没把握或没做的：标了【待核实】的地方，以及在其他章节发现但没改的问题。
5. 自检结果：check、time 的结果，scan 改前改后的数字。
````
