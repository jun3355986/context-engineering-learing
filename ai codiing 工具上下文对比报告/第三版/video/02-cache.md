# 02 缓存：前缀为什么值钱

- **目标观众**：知道缓存能省钱、但说不清「为什么改一个字就全没了」的人。
- **预计时长**：3 分 05 秒；旁白 491 字（按 3.0–3.2 字/秒并留停顿估算）。
- **核心比喻**：一条已经铺好的铁轨。第一个不同的字节是道岔，之后全部重铺。
- **一句话论点**：缓存不是「相似就能复用」，而是「从第一个 token 起连续相同多长」；位置就是成本。
- **前置知识**：入门第 5 章的前缀缓存演示；不需要知道单价。

## 旁白完整版

先看一条已经铺好的轨道，每一段是请求里的一个片段：系统、工具、规则、历史。颜色越深，越不容易变。这条轨道每次请求都从头铺，只是服务端可以跳过前面已经铺过的部分。

第二次请求如果开头一模一样，服务端就不用重算，直接复用。这叫命中，命中部分按缓存读取计价。命中长度不按消息条数算，按连续相同的 token 前缀算。

「一模一样」是字节一样，不是意思一样。改一个日期字符，从那里到末尾全部作废。所以「改一个字」和「改一整段」，在缓存看来可能是同一件事。

像多米诺：第一个不同字节是道岔，之后不管内容变没变，都要重铺。缓存看的是「从头连续相同多长」。你想省得更多，就要让「相同」尽量长，而不是让「相似」尽量多。

所以稳定在前、易变在后。日期、todo、临时提醒放末尾，不要塞进系统提示。把日期放进系统提示，等于每天第一件事就是把整条轨道重铺一遍。

也不要在历史中间插东西。中间插一条，后面全重铺；末尾追加，只多铺一段。这也是为什么很多工具把提醒做成追加一条消息，而不是修改系统提示。

Claude Code 每条请求只有一个消息级标记，系统提示最多四块；opencode v2 自动断点上限四个；Grok 显式三处，留一槽给网关。断点不是越多越好。断点只能标在可缓存的位置，标错位置等于没标。

压缩必然重写前缀，也必然造成一次失效。该问的不是怎么不失效，而是这次失效换来了什么。缓存友好不是永不失效，是每次失效都换来更大的东西。
