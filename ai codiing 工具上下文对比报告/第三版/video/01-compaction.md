# 01 压缩：为什么历史必须被换掉

- **目标观众**：用过 `/compact`，但说不清它丢了什么的人；读完主线第 8 章仍觉得「摘要」抽象的人。
- **预计时长**：3 分 10 秒；旁白 643 字（按 3.0–3.2 字/秒并留停顿估算）。
- **核心比喻**：一整面墙的便签，换成一张索引卡，再加一小段还没读完的原文。
- **一句话论点**：压缩不是删除历史，是把「可读的长历史」换成「可读的索引 + 一小段原文」；代价是判断被交给了摘要。
- **前置知识**：知道 token 与上下文窗口的区别即可。

## 旁白完整版

先看一条线。它代表一次对话的历史。每发生一轮——你说一句话，它读一个文件，跑一次命令——线就向右长一格。线不会自己变短，只会越来越长。它没有刻度，但你能感觉到：越往右，越像刚才发生的事。

左边深蓝这一段是系统提示和工具说明，从第一轮到最后都不变；右边越来越浅，因为越靠后，越是一次性的。地基不动，楼才稳。这三段的边界，决定了哪些内容能在下一轮被复用。

当右端碰到红线，请求就装不下了。不是模型失忆，是这段历史根本没有进入这次请求。你没让它看见，它当然答不上来。窗口大小、输出预留、服务端的截断策略，都会改变它实际看见的长度。

压缩把左边一大段抽走，换成一张青色卡片：目标、已完成、做过的决定、待办、改过的文件。写卡片的是模型自己，所以它一定带有判断，也一定带有遗漏。如果卡片上写「已完成登录改造」，却没写「不要动数据库迁移」，下一轮它很可能就去动迁移。

右边一小段不动，仍然是蓝的。压缩后的形状是「一张卡片 + 一小段原文」。这不是删除，是把可读的长历史换成索引，再加一段没读完的原文。注意，保留尾部不是保留最后几条消息，而是按 token 预算从后往前装。

切点不能穿过工具调用与结果的齿轮，否则会被弹回最近的合法边界。这就是为什么压缩点总比你预期的更靠前。不同工具对合法边界的定义不同，但底线一样：不能把调用和结果拆开。

三个真实数字：Codex 本地候选预算两万 token；远端保留六万四千，单条不超过一万；Claude Code 在有效窗口前留一万三千缓冲。它们都在回答：留多少原文才够继续。还有一个差别：本地预算数的是候选消息，远端预算数的是保留消息。

所以压缩的代价不是少了几个字，而是把判断交给了摘要。下次它忘了约束，先去看那张卡片写了什么、漏了什么。判断一次压缩好不好，不要只看短了多少，要看下一轮有没有因为缺约束而返工。
